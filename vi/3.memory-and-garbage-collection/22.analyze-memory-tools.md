# What tools help analyze memory? (Những công cụ nào giúp phân tích bộ nhớ?)

## Junior Level

**Các công cụ phân tích bộ nhớ:**

| Công cụ         | Dùng để làm gì   | Khi nào     |
| --------------- | ---------------- | ----------- |
| **Eclipse MAT** | Phân tích dump   | Sau OOME    |
| **VisualVM**    | Giám sát         | Development |
| **jcmd**        | Kiểm tra nhanh   | Production  |
| **JProfiler**   | Profiling        | Development |

**Quan trọng nhất:** Eclipse MAT (miễn phí)
- Mở heap dump
- Hiển thị đối tượng nào chiếm nhiều bộ nhớ nhất
- Tìm các rò rỉ

---

## Middle Level

### jcmd (tiện ích dòng lệnh)

```bash
jcmd <pid> GC.class_histogram   # Danh sách các class
jcmd <pid> GC.heap_dump dump.hprof  # Chụp dump
jcmd <pid> VM.native_memory summary  # Native Memory
```

### Eclipse MAT

```
Các tính năng chính:
  → Dominator Tree (ai giữ lại nhiều bộ nhớ nhất)
  → Path to GC Roots (chuỗi tham chiếu đến root)
  → OQL (các truy vấn vào dump)
  → Leak Suspects Report (phân tích tự động)
```

### JFR và JMC

```
Java Flight Recorder (được tích hợp sẵn trong JVM):
  → Chi phí < 1%
  → Có thể để bật trong production

JDK Mission Control (GUI):
  → Trực quan hóa các bản ghi JFR
  → OldObjectSample → các rò rỉ mà không cần dump
```

### Các công cụ thương mại

| Công cụ       | Ưu điểm             | Nhược điểm |
| ------------- | ------------------- | ---------- |
| **JProfiler** | Profiling trực tiếp (live) | Trả phí    |
| **YourKit**   | Theo dõi cấp phát (allocation) | Trả phí    |
| **gceasy.io** | Phân tích GC log    | Cloud      |

## Senior Level

### Sự nguy hiểm của Dump

```
Heap Dump = Stop-The-World!
  → Heap 32 GB trên HDD → khoảng dừng 30-60 giây
  → Heap 32 GB trên SSD → 5-15 giây

Trong Kubernetes:
  → Liveness Probe timeout → pod bị giết!

Giải pháp cho các Heap lớn:
  → JFR OldObjectSample (không có STW)
  → class_histogram (khoảng dừng < 1 giây)
```

### Các ví dụ OQL

```sql
-- Tìm tất cả các HashMap có > 1000 phần tử
SELECT map FROM java.util.HashMap map
WHERE map.size > 1000

-- Tìm các chuỗi trùng lặp
SELECT toString(s.value) as val, count(*) as cnt
FROM java.lang.String s
GROUP BY toString(s.value)
HAVING count(*) > 100

-- Tìm các rò rỉ ThreadLocal
SELECT tl, tl.referents.@length as size
FROM java.lang.ThreadLocal tl
WHERE tl.referents.@length > 100
```

### Arthas (Alibaba)

```bash
# Chẩn đoán tương tác trên server
java -jar arthas-boot.jar

[arthas]$ dashboard     # Tổng quan Heap/Native/Metaspace
[arthas]$ heapdump      # Chụp dump
[arthas]$ vmtool        # Kiểm tra đối tượng
[arthas]$ memory        # Chi tiết bộ nhớ
```

### NMT (Native Memory Tracking)

```bash
-XX:NativeMemoryTracking=detail

jcmd <pid> VM.native_memory detail

# Hiển thị:
# Java Heap, Class, Thread, Code, GC
# Compiler, Internal, Symbol, Arena Chunk
→ Tìm các rò rỉ nằm ngoài Heap
```

### Best Practices

1. **jcmd** > jmap (chuẩn hiện đại)
2. **JFR** để giám sát production
3. **MAT** để phân tích dump
4. **Cẩn thận với các dump** → khoảng dừng STW
5. **NMT** cho Native Memory
6. **gceasy.io** để phân tích GC log
7. **Arthas** cho các môi trường phức tạp

### Tóm tắt cho Senior

- **jcmd** = chuẩn CLI hiện đại
- **MAT** = Dominator Tree + Path to GC Roots
- **JFR** = < 1% chi phí, an toàn cho production
- **NMT** = Native Memory Tracking
- **Dump** = STW (tất cả các luồng dừng lại). JVM phải đóng băng đồ thị đối tượng ở trạng thái nhất quán: không có cấp phát, giải phóng, hay thay đổi tham chiếu nào trong lúc dump. Trên Heap lớn, dump có thể mất 10-60 giây.
- **OQL** = SQL cho các dump
- **Arthas** = chẩn đoán tương tác

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Eclipse MAT — phân tích dump: Dominator Tree, Path to GC Roots, OQL, Leak Suspects Report (miễn phí)
- jcmd — chuẩn CLI hiện đại: `GC.class_histogram`, `GC.heap_dump`, `VM.native_memory`
- JFR + JMC — giám sát production, < 1% chi phí; OldObjectSample → các rò rỉ mà không cần dump
- NMT (`-XX:NativeMemoryTracking=detail`): Native Memory Tracking — hiển thị Java Heap, Class, Thread, Code, GC, Internal
- Dump = STW: trên 32 GB HDD → 30-60 giây; trong Kubernetes Liveness Probe timeout → pod bị giết
- OQL — các truy vấn kiểu SQL vào dump: tìm các HashMap lớn, các chuỗi trùng lặp, các rò rỉ ThreadLocal
- Arthas (Alibaba): chẩn đoán tương tác trên server — dashboard, heapdump, vmtool, memory

**Các câu hỏi phụ thường gặp:**
- **Tại sao jcmd tốt hơn jmap?** — jmap đã bị deprecated; jcmd là chuẩn hiện đại, dùng JVM Attach API, nhiều lệnh hơn
- **Khi nào JFR tốt hơn dump?** — Heap > 64 GB: dump quá lớn, mất nhiều thời gian để chụp/phân tích; JFR < 1% chi phí, không có STW
- **NMT cho thấy gì mà Heap Dump không có?** — Native Memory: Code Cache, Thread Stacks, các cấu trúc GC, Internal — tất cả những gì nằm ngoài Heap
- **Tại sao dump yêu cầu STW?** — JVM phải đóng băng đồ thị ở trạng thái nhất quán: không có cấp phát/giải phóng nào trong lúc dump

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi chụp dump trong production mà không cảnh báo" — STW 30-60 giây; trong Kubernetes pod sẽ bị giết
- "jmap là công cụ tốt nhất" — jmap đã bị deprecated; hãy dùng jcmd
- "Heap Dump cho thấy toàn bộ bộ nhớ JVM" — Heap Dump chỉ On-Heap; Native Memory yêu cầu NMT
