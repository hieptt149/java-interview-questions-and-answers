# When should you create your own exceptions? (Khi nào nên tạo exception của riêng bạn?)

## Junior Level

### Khi nào bạn NÊN tạo

**1. Cho các lỗi nghiệp vụ:**
```java
public class InsufficientFundsException extends RuntimeException {
    public InsufficientFundsException(String message) {
        super(message);
    }
}
```

**2. Khi bạn cần truyền thông tin bổ sung:**
```java
public class OrderTimeoutException extends RuntimeException {
    private final Long orderId;
    private final int timeoutSeconds;

    public OrderTimeoutException(Long orderId, int timeoutSeconds) {
        super("Order " + orderId + " timed out after " + timeoutSeconds + "s");
        this.orderId = orderId;
        this.timeoutSeconds = timeoutSeconds;
    }
}
```

**3. Khi các exception tiêu chuẩn không phù hợp:**
```java
// Thay vì IllegalArgumentException chung chung
throw new InvalidEmailException("Email must contain @ and domain");
```

### Khi nào bạn KHÔNG NÊN tạo

**Đừng tạo** nếu các exception tiêu chuẩn phù hợp:
```java
// Không cần custom exception
if (age < 0) throw new IllegalArgumentException("Age < 0");

// Không cần custom exception
if (user == null) throw new NullPointerException("User is null");
```

### Nguyên tắc đơn giản

Tạo exception của riêng bạn khi:
- Đó là một lỗi nghiệp vụ (không phải một bug code)
- Bạn cần các trường bổ sung
- Bạn cần một HTTP status riêng

---

### Custom hay standard exception?

Tạo custom nếu bạn cần:
- Một khối catch riêng cho loại lỗi này
- Một HTTP status riêng (404, 409, 422)
- Các trường bổ sung (orderId, retryAfter)

Dùng standard nếu:
- Ghi log một message là đủ
- Lỗi chung chung và không cần xử lý đặc biệt

---

## Middle Level

### Chi phí kiến trúc của custom exception

Mỗi exception mới là một class trong Metaspace. Trong các hệ thống lớn với hàng nghìn exception, điều này làm tăng thời gian khởi động và mức tiêu thụ bộ nhớ.

### Khi nào tạo - chi tiết

**1. Validation nghiệp vụ:**
```java
throw new CouponExpiredException("Coupon expired on " + expiryDate);
// @ControllerAdvice sẽ biến thành 400 Bad Request kèm JSON
```

**2. Exception Translation ở biên của tầng:**
```java
try {
    repository.save(order);
} catch (SQLException e) {
    throw new DataAccessException("Failed to save order", e);
}
```

**3. Tính thông tin:**
Cần các trường bổ sung: `retryAfter`, `errorCode`, `entityId`.

### Khi nào KHÔNG nên tạo

**1. Flow Control - anti-pattern:**
```java
// ANTI-PATTERN: exception như if-else
try {
    User user = findUser(id); // ném UserFoundException nếu tìm thấy
    // bước tiếp theo...
} catch (UserFoundException e) {
    // Luồng "bình thường" thông qua exception!
}

// Thay vào đó:
Optional<User> user = findUser(id);
if (user.isPresent()) { /* bước tiếp theo */ }
```

Các benchmark cho thấy chậm hơn 100-1000 lần. Giá trị tuyệt đối: trả về Optional ~10ns, tạo exception ~1-5 micro giây (tùy vào độ sâu stack và JVM).

**2. Trùng lặp JDK:**
```java
// Không cần nếu IllegalArgumentException mô tả được tình huống
throw new InvalidAgeException("Age < 0");
// Tốt hơn:
throw new IllegalArgumentException("Age must be positive, got: " + age);
```

### Cây phân cấp exception

```
RuntimeException
  -- BusinessException
        -- OrderException
        |     -- OrderNotFoundException
        |     -- OrderAlreadyShippedException
        -- PaymentException
              -- InsufficientFundsException
              -- PaymentProviderException
```

## Senior Level

### Domain-Driven Exception

Trong kiến trúc chất lượng, một exception là một **sự kiện của mô hình domain**, không chỉ là một "lỗi".

### Immutable Exception cho Highload

Cho các lỗi nghiệp vụ xảy ra thường xuyên mà không cần debug stack:

```java
public class FastValidationException extends RuntimeException {
    public FastValidationException(String message) {
        super(message, null, false, false);
    }

    // Các instance định nghĩa sẵn
    public static final FastValidationException EMPTY_EMAIL =
        new FastValidationException("Email is required");
    public static final FastValidationException INVALID_PHONE =
        new FastValidationException("Invalid phone format");
}
```

### Cây phân cấp Exception và nhóm

Xây dựng cây phân cấp để bắt theo nhóm:

```java
// Có thể bắt tất cả các lỗi nghiệp vụ
catch (BusinessException e) { return 400; }

// Hoặc cụ thể hơn
catch (OrderNotFoundException e) { return 404; }
```

### Serialization và microservice

```java
public class BusinessException extends RuntimeException {
    private static final long serialVersionUID = 1L;
    // Không có cái này - InvalidClassException khi deserialize
}
```

### Rò rỉ PII và bảo mật

Đừng thêm các trường như `creditCardNumber` vào exception. Nếu nó lọt vào log - vi phạm PCI DSS.

PII (Personally Identifiable Information) - dữ liệu cá nhân.
PCI DSS - tiêu chuẩn bảo mật thẻ thanh toán. Dữ liệu thẻ trong log = vi phạm tiêu chuẩn.

### Phân tích dựa trên metric

```java
// Đếm qua Micrometer
meterRegistry.counter("exceptions.coupon_expired").increment();

// Số CouponExpiredException tăng vọt - một chỉ báo nghiệp vụ
```

### Error Code

Mỗi custom exception - một mã chuỗi duy nhất:

```java
public enum ErrorCode {
    ERR_USER_NOT_FOUND("USR-001"),
    ERR_INSUFFICIENT_FUNDS("PAY-002"),
    ERR_COUPON_EXPIRED("COU-003");

    private final String code;
}
```

Frontend dùng mã để bản địa hóa.

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Tạo custom exception cho các lỗi nghiệp vụ khi bạn cần các trường bổ sung hoặc một HTTP status riêng
- ĐỪNG dùng exception làm flow control (anti-pattern) - chậm hơn 100-1000 lần so với `if/else` hoặc `Optional`
- Xây dựng cây phân cấp: `BusinessException` -> `OrderException` -> `OrderNotFoundException` để nhóm các khối catch
- Mỗi custom exception - một mã chuỗi duy nhất (`ERR-001`) để bản địa hóa và cho frontend
- Đừng phơi bày PII trong message (mật khẩu, số thẻ) - vi phạm PCI DSS
- Với highload: immutable exception với các instance định nghĩa sẵn và `writableStackTrace = false`

**Các câu hỏi phụ thường gặp:**
- **Cách quyết định: custom hay standard?** - Nếu bạn cần một khối catch riêng, HTTP status, hoặc các trường bổ sung - custom; nếu message là đủ - standard
- **Tại sao exception làm flow control là một anti-pattern?** - Tạo stack trace tốn 1-5 micro giây, `Optional` - ~10ns; cộng thêm code trở nên khó đọc
- **Cách tổ chức cây phân cấp exception?** - Một cha chung (`BusinessException`) để bắt theo nhóm + các lớp con cụ thể cho từng HTTP status
- **Làm gì với exception trong microservice?** - Ở biên, chuyển dịch thành định dạng tiêu chuẩn (RFC 7807), bên trong service dùng custom

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi dùng exception thay cho if-else" - Đây là một anti-pattern với suy giảm hiệu suất nghiêm trọng
- "Tôi tạo một exception cho mỗi lần validation" - `IllegalArgumentException` thường là đủ
- "Tôi không quan tâm đến bảo mật của message" - PII trong log = vi phạm GDPR/PCI DSS
