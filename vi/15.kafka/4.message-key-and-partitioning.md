# What is message key and how does it affect partitioning (Message key là gì và nó ảnh hưởng đến việc phân vùng như thế nào)

---

## 🟢 Junior Level

### Message Key Là Gì?

**Message Key** là một giá trị quyết định **partition nào** một message sẽ rơi vào. Key là "địa chỉ" để định tuyến một message.

**Tại sao:** một cách để nói với Kafka: "tất cả các event liên quan đến user/order này nên được xử lý ở một nơi." Không có key, các event cho cùng một user sẽ rải rác trên các partition khác nhau và có thể đến không theo thứ tự.

### Phép So Sánh

Hãy nghĩ về một **sân bay**:
- Key = mã đích chuyến bay (ví dụ: "KYIV-BA101")
- Partition = cổng cụ thể
- Tất cả hành khách với cùng mã đi đến cùng một cổng
- Hành khách với các mã khác nhau — đến các cổng khác nhau

```
key="KYIV-BA101" → cổng 5 (partition 1)
key="NYC-AA202"  → cổng 3 (partition 0)
key="PARIS-AF303" → cổng 7 (partition 2)
```

Một phép so sánh tốt hơn: một key là số vụ án tại tòa. Tất cả tài liệu cho cùng một vụ án
đi vào một hồ sơ và được xử lý theo thứ tự nghiêm ngặt. Tài liệu cho các
vụ án khác nhau — trong các hồ sơ khác nhau, thứ tự giữa chúng không quan trọng.

### Tại Sao Cần Đến Key?

1. **Đảm bảo thứ tự** — các message có cùng key đi đến một partition → giữ thứ tự
2. **Nhóm lại** — tất cả event cho một user/object được xử lý cùng nhau

### Ví Dụ

```java
// Có key — thứ tự được đảm bảo
ProducerRecord<String, String> record =
    new ProducerRecord<>("orders", "user-123", "Order created");
//                    topic         key          value

// user-123 luôn rơi vào cùng một partition
```

```
Có key:
  user-123 → partition 1 → thứ tự: login → browse → purchase

Không có key:
  msg-1 → partition 2
  msg-2 → partition 0  // thứ tự không được đảm bảo
  msg-3 → partition 1
```

### Khi Nào KHÔNG Nên Dùng Message Key

1. **Thứ tự message không quan trọng** và cần throughput tối đa — key=null
2. **Các key có skew mạnh** (phân phối không đồng đều) — hot partition
3. **Kích thước key quá lớn** (>1KB) — overhead CPU khi hash

## 🟡 Middle Level

### Các Đảm Bảo Về Thứ Tự

```
Partition 0: các event của user-456 (nghiêm ngặt theo thứ tự)
Partition 1: các event của user-123 (nghiêm ngặt theo thứ tự)
Partition 2: các event của user-789 (nghiêm ngặt theo thứ tự)
```

**Quan trọng:** Thứ tự chỉ được đảm bảo **trong một partition duy nhất**! Giữa các partition — không có đảm bảo.

### Thuật Toán Hash

```
partition = Math.abs(Utils.murmur2(keyBytes)) % numPartitions
```

Kafka dùng **MurmurHash 2** để phân phối đồng đều các key trên các partition.

### Chọn Một Key Tốt

| Key             | Phân phối                           | Khi nào dùng                                                                                                                |
| --------------- | -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `userId`        | ✅ Đồng đều (nhiều user)                 | Các event của user                                                                                                                |
| `orderId`       | ✅ Đồng đều                              | Các event của đơn hàng                                                                                                               |
| `"all"`         | ❌ Hot partition                        | Đừng dùng cho các hệ thống event-driven. Chấp nhận được cho broadcast (cấu hình toàn cục), nhưng cần lưu ý rủi ro hot partition.          |
| `null`          | ✅ Sticky partitioning                  | Khi thứ tự không quan trọng                                                                                                             |
| `aggregateId`   | ✅ Đồng đều                              | Event sourcing                                                                                                             |

### Null Key

```java
// key = null → sticky partitioning
// Thứ tự KHÔNG được đảm bảo
ProducerRecord<String, String> record =
    new ProducerRecord<>("orders", "Order created");
```

### So Sánh Chiến Lược Key

| Chiến lược                           | Thứ tự            | Throughput   | Phân phối      |
| ---------------------------------- | ------------------- | ------------ | ----------------- |
| **Business Key** (userId)          | ✅ Trong partition  | Trung bình       | Tùy vào dữ liệu   |
| **Composite Key** (userId_orderId) | ✅                   | Trung bình       | Tốt              |
| **Salted Key** (userId + random)   | ⚠️ Một phần           | Tốt         | Xuất sắc         |
| **Null Key**                       | ❌                   | Tối đa      | Đồng đều           |

### Các Lỗi Thường Gặp

| Lỗi                         | Hậu quả                       | Giải pháp                          |
| ------------------------------- | --------------------------------- | ---------------------------------- |
| Key null khi cần thứ tự| Các event của user bị trộn lẫn          | Dùng userId làm key                 |
| Cùng một key cho mọi thứ         | Hot partition                     | Các key khác nhau cho các entity khác nhau |
| Key lớn (JSON)                | Overhead CPU khi hash           | Các key gọn nhẹ (UUID, Long)         |
| Thay đổi số lượng partition        | Phân phối key thay đổi          | Tạo một topic mới                |

## 🔴 Senior Level

### Cài Đặt Nội Bộ — MurmurHash 2

```java
// org.apache.kafka.common.utils.Utils
public static int murmur2(byte[] data) {
    int length = data.length;
    int seed = 0x9747b28c;  // seed của Kafka
    // ... thuật toán MurmurHash2 ...
    return fmix(hash(length, seed, data));
}

// Tính toán partition
int hash = Utils.murmur2(keyBytes);
int partition = Math.abs(hash) % numPartitions;
```

**Tại Sao MurmurHash 2:**
- Không mã hóa (non-cryptographic), nhanh (các thao tác bitwise)
- Hiệu ứng thác đổ (avalanche effect) — thay đổi 1 bit → ~50% các bit kết quả thay đổi
- Phân phối đồng đều — va chạm tối thiểu cho dữ liệu thực tế

**Edge case Integer.MIN_VALUE:**
```java
// Math.abs(Integer.MIN_VALUE) == Integer.MIN_VALUE (âm!)
// Kafka dùng một bitmask:
int partition = (hash & 0x7fffffff) % numPartitions;
```

### Các Đảm Bảo Về Thứ Tự Key — Mô Hình Hình Thức

```
Trong một partition: FIFO nghiêm ngặt (thứ tự toàn phần)
Giữa các partition: thứ tự một phần (chỉ có thứ tự nhân quả với thiết kế rõ ràng)

Về mặt hình thức:
  ∀ các message m1, m2:
    key(m1) == key(m2) → partition(m1) == partition(m2) → order(m1, m2) được giữ nguyên
    key(m1) != key(m2) → order(m1, m2) KHÔNG được đảm bảo
```

### Các Chiến Lược Key Nâng Cao

**1. Composite Key Để Chống Hot Partition:**
```java
// Composite key: entity + sub-entity
String key = userId + "_" + orderId;
// Cung cấp phân phối đều hơn
// Nhưng: thứ tự chỉ trong userId_orderId, không trong userId
```

**2. Key Salting (phân vùng ngẫu nhiên trong một entity):**
```java
// N-ary salting: phân phối các event của một user trên N partition
int salt = ThreadLocalRandom.current().nextInt(10);
String key = userId + "_" + salt;
// Thứ tự bị mất, nhưng throughput tăng N lần
// Dùng khi thứ tự KHÔNG quan trọng
```

**3. Time-based Key Rotation:**
```java
// Key bao gồm một time bucket
String key = userId + "_" + (System.currentTimeMillis() / 3600000);
// Key thay đổi mỗi giờ → các message rơi vào partition mới
// Hữu ích cho các tổng hợp theo cửa sổ thời gian
```

**4. Consistent Hashing Cho Các Partition Động:**
```
Cách tiếp cận dựa trên ring: giảm thiểu việc di chuyển key khi N thay đổi
Các thư viện: ketama, jmpmv/consistent-hashing
Ứng dụng: các hệ thống multi-tenant, cơ sở dữ liệu sharded
```

### Vấn Đề Key Evolution — Phân Tích Hình Thức

```
Trước: partition = hash(key) % 3
  key="user-1" → hash("user-1") % 3 = 1 → Partition 1

Sau: partition = hash(key) % 6
  key="user-1" → hash("user-1") % 6 = 4 → Partition 4

Cùng key → partition khác nhau → thứ tự bị phá vỡ!

Về mặt toán học:
  P(new_partition != old_partition) = 1 - (old_N / new_N)
  Với 3 → 6: P = 1 - 3/6 = 50% các key di chuyển
  Với 10 → 100: P = 1 - 10/100 = 90% các key di chuyển
```

**Giải pháp:**
1. Lập kế hoạch số lượng partition với biên độ (10 lần nhu cầu hiện tại)
2. Dùng consistent hashing (custom partitioner)
3. Tạo một topic mới với số lượng partition mong muốn và di chuyển qua dual-write

### Tác Động Của Kích Thước Key Đến Hiệu Năng

| Kích thước key         | Overhead memory | CPU (hash) | Network      | Khuyến nghị |
| ---------------- | --------------- | ---------- | ------------ | -------------- |
| Long (8 byte)   | Tối thiểu         | ~5 ns      | Tối thiểu      | ✅ Tối ưu      |
| UUID (36 byte)  | Trung bình          | ~20 ns     | Trung bình       | ✅ Chấp nhận được   |
| String (100 byte)| Đáng chú ý     | ~50 ns     | Đáng chú ý   | ⚠️ Chấp nhận được  |
| JSON (10 KB)     | Đáng kể     | ~500 µs    | Đáng kể  | ❌ Tránh        |

**Dấu chân memory:**
```
Key được lưu trữ trong:
- Producer RecordBatch → MemoryRecord (heap)
- Broker Log → MessageSet (page cache + heap)
- Consumer ConsumerRecord (heap)

Tổng: 3 × kích_thước_key × throughput × retention
Với các key 10KB ở 10K msg/s = ~3 GB/s lưu lượng memory
```

### Edge Case (3+)

1. **Key Null + Idempotent Producer:** Với `enable.idempotence=true` và `key=null`, Kafka sinh ra các số sequence ở cấp partition. Vì sticky partitioning chuyển đổi các partition, các số sequence không xung đột. Nhưng nếu `partitioner.class` là tùy chỉnh và không tất định — `OutOfOrderSequenceException` có thể xảy ra.

2. **Không Khớp Schema Serialize Key:** Producer serialize key dưới dạng String (`StringSerializer`), consumer deserialize dưới dạng ByteArray (`ByteArrayDeserializer`). Key "hoạt động" cho việc phân vùng, nhưng business logic của consumer nhận `byte[]` thay vì `String` mong đợi. Test serialize ở cả hai đầu.

3. **Các Key Unicode Và MurmurHash:** `MurmurHash` hoạt động trên các byte. Key `"café"` trong UTF-8 = `[99, 97, 102, 195, 169]`, trong Latin-1 = `[99, 97, 102, 233]`. Các encoding khác nhau → các byte khác nhau → các partition khác nhau. Đảm bảo tất cả các producer dùng cùng encoding (UTF-8 theo mặc định trong Kafka).

4. **Đột Biến Key Trong Processor:** Trong Kafka Streams hoặc ksqlDB, nếu một processor thay đổi key message (`map((key, value) -> new KeyValue<>(newKey, value))`), message được phân phối lại đến một partition mới. Điều này gây ra một shuffle — một thao tác tốn kém. Dùng `through()` để kiểm soát repartitioning rõ ràng.

5. **Key Rỗng (không phải null, mà là chuỗi rỗng):** `key=""` → `MurmurHash("")` = hằng số → tất cả các message với key rỗng đi đến một partition. Điều này giống như một hot partition, nhưng khó phát hiện hơn (key "tồn tại" nhưng vô dụng).

### Các Con Số Hiệu Năng

| Chỉ số                             | Giá trị                  | Điều kiện                 |
| ---------------------------------- | ---------------------- | -------------------------- |
| Độ trễ MurmurHash                 | ~5-50 ns               | Tùy kích thước key        |
| Overhead tính toán partition         | < 100 ns               | Bao gồm cả serialize    |
| Serialize key (String, 36 byte)| ~100 ns              | Encoding UTF-8             |
| Tác động của key nóng lên p99           | Tăng độ trễ 3-10 lần | 1 key = 50% lưu lượng     |

### Câu Chuyện Production Thực Tế

> **Tình huống:** Một công ty ride-sharing dùng `driverId` làm key cho topic `rides`. Với 10,000 tài xế đang hoạt động, phân phối đều (20 partition). Nhưng trong giờ cao điểm, top 50 tài xế (hoạt động nhiều nhất) tạo ra 40% tất cả các event.
>
> **Vấn đề:** P99 latency cho các đơn hàng tăng từ 15ms lên 500ms. Lag trên các partition "nóng" đạt 30K message. Khách hàng phàn nàn về các đơn hàng bị "kẹt".
>
> **Phân tích:**
> ```
> Top-10 key theo khối lượng:
>   driver-42: 15K msg/phút → Partition 7
>   driver-17: 12K msg/phút → Partition 3
>   driver-88: 11K msg/phút → Partition 14
>   Trung bình: 50 msg/phút mỗi tài xế
> ```
>
> **Giải pháp:**
> 1. Giới thiệu key kết hợp: `driverId + "_" + (timestamp / 60000)` — key thay đổi mỗi phút
> 2. Tăng partition từ 20 lên 60
> 3. Cho các tổng hợp (đếm chuyến đi mỗi tài xế) dùng Kafka Streams với `.groupByKey()` — tự động repartition
> 4. Thiết lập alert khi mất cân bằng throughput mỗi partition > 3x
>
> **Bài học:** Phân phối key đồng đều ≠ tải đồng đều. Phân tích **phân phối tần suất** của các key, không chỉ cardinality.

### Monitoring (JMX + Burrow)

**Các metrics JMX:**
```
kafka.producer:type=ProducerMetrics,client-id=producer-1,key=record-send-rate
kafka.producer:type=ProducerMetrics,client-id=producer-1,key=batch-size-avg

```

**Monitoring tùy chỉnh:**
```java
// Interceptor để phân tích phân phối key
public class KeyDistributionInterceptor implements ProducerInterceptor {
    private final Map<String, Long> keyCounts = new ConcurrentHashMap<>();

    public ProducerRecord onSend(ProducerRecord record) {
        keyCounts.merge(String.valueOf(record.key()), 1L, Long::sum);
        return record;
    }
}
```

### Các Thực Hành Tốt Nhất Cho Highload

1. **Key = business entity ID gọn nhẹ** (Long > UUID > String)
2. **Phân tích phân phối tần suất** của các key trước production
3. **Composite/salted key** để chống hot partition (đánh đổi: thứ tự)
4. **Tránh thay đổi số lượng partition** — tạo một topic mới
5. **Test trên dữ liệu giống production** — các key thực có skew
6. **Giám sát throughput mỗi partition** — alert khi mất cân bằng > 3x
7. **Chuỗi rỗng != null** — key rỗng nghĩa là hot partition
8. **Nhất quán Unicode** — tất cả các producer phải dùng UTF-8

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- Key quyết định partition: `MurmurHash2(key) % numPartitions`
- Các message có cùng key luôn rơi vào một partition → thứ tự được đảm bảo
- Không có key (null) — Sticky Partitioning, không có thứ tự
- Composite key (`userId + "_" + orderId`) — cho phân phối đều
- Key lớn (>1KB) — overhead CPU khi hash mỗi message
- Khi thay đổi số lượng partition, cùng key → partition khác nhau
- Chuỗi rỗng ≠ null — key rỗng = hot partition (tất cả vào một partition)
- Key = business entity ID gọn nhẹ (Long > UUID > String)

**Các câu hỏi phụ thường gặp:**
- *Điều gì xảy ra nếu key=null?* — Sticky Partitioning, thứ tự không được đảm bảo.
- *Tại sao không dùng JSON làm key?* — Key 10KB × 10K msg/s = ~3 GB/s lưu lượng memory.
- *Làm sao đảm bảo thứ tự với key nóng?* — Composite/salted key, đánh đổi: mất một phần thứ tự.
- *Vấn đề Key Evolution là gì?* — Khi thay đổi N trong `hash(key) % N`, 50-90% các key di chuyển.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Key đảm bảo thứ tự toàn cục" — chỉ trong một partition
- "Chuỗi rỗng giống như null" — rỗng = hot partition, null = sticky
- "Bạn có thể thay đổi số lượng partition mà không có hậu quả" — các key di chuyển
- "Key chỉ được lưu trữ trong producer" — được lưu trong RecordBatch, Log, ConsumerRecord (3×)
