# Which GCs minimize stop-the-world pauses? (Những GC nào giúp giảm thiểu các khoảng dừng stop-the-world?)

## Junior Level

**GC low-latency** — các collector giúp giảm thiểu các khoảng dừng của ứng dụng.

**Các loại chính:**
- **ZGC** — khoảng dừng < 1 ms (tốt nhất)
- **Shenandoah** — khoảng dừng < 1 ms
- **G1** — khoảng dừng 20-200 ms (thỏa hiệp)

**Cách chúng làm điều đó:**
- Thực hiện phần lớn công việc **đồng thời (concurrently)** với ứng dụng
- Chỉ dừng lại để quét GC Roots

---

## Middle Level

### Các chiến lược giảm thiểu

| GC             | Chiến lược                       | Khoảng dừng |
| -------------- | -------------------------------- | --------- |
| **ZGC**        | Colored Pointers + Load Barriers | < 1 ms    |
| **Shenandoah** | Load Reference Barriers          | < 1 ms    |
| **G1**         | Regions + Mixed GC               | 20-200 ms |

### Allocation Stall — mối nguy hiểm

```
Ứng dụng tạo rác nhanh hơn tốc độ concurrent marking có thể hoàn thành.
Luồng của ứng dụng bị chặn và tự bắt đầu evacuate các đối tượng. Nguy hiểm: nếu stall xảy ra thường xuyên,
throughput còn giảm nhiều hơn cả khi dùng Parallel GC.
```

### So sánh

| GC                   | Khoảng dừng điển hình | Chi phí CPU    | Throughput     |
| -------------------- | ------------- | -------------- | -------------- |
| **Parallel**         | 100-1000 ms   | Tối thiểu      | Tối đa         |
| **G1**               | 20-200 ms     | Trung bình     | Tốt            |
| **ZGC/Shenandoah**   | < 1 ms        | Cao            | -5-15%         |

### Generational ZGC (Java 21+)

```
Chia theo thế hệ:
  → -50% chi phí CPU
  → Throughput gần như bằng G1
  → Khoảng dừng vẫn < 1 ms
```

### Khi nào KHÔNG dùng GC low-latency

```
❌ Khi mức sử dụng CPU cao, các barrier sẽ làm nó tệ hơn — ứng dụng dành nhiều thời gian cho GC hơn là cho công việc.
❌ Xử lý theo lô → các khoảng dừng không quan trọng
❌ Heap < 4 GB → G1 hiệu quả hơn
```

## Senior Level

### Concurrent Evacuation

```
ZGC/Shenandoah di chuyển các đối tượng KHÔNG cần STW:
  → Ứng dụng đọc tham chiếu → Load Barrier
  → Nếu đối tượng đã di chuyển → Self-healing
  → G1: Evacuation = STW (hạn chế)
```

### Chi phí Barrier (Barrier Overhead)

```
Write Barriers (G1):
  → Trên mỗi lần ghi tham chiếu
  → chi phí ~1-2 ns

Load Barriers (ZGC):
  → Trên mỗi lần đọc tham chiếu
  → chi phí ~5-15 ns
  → Nhưng Self-healing trong Fast Path

Kết quả: ZGC chậm hơn 5-15%
```

### Tinh chỉnh cho các khoảng dừng tối thiểu

```bash
# ZGC
-XX:+UseZGC -XX:+ZGenerational
-XX:ConcGCThreads=4
-XX:SoftMaxHeapSize=24g

# G1
-XX:MaxGCPauseMillis=100
-XX:InitiatingHeapOccupancyPercent=45
```

### Best Practices

1. **ZGC (Java 21+)** cho SLA < 10 ms
2. **G1** cho SLA 100-200 ms
3. **Giám sát** Allocation Stall
4. **ConcGCThreads** = số lõi / 4
5. **Tránh** các mảng lớn
6. **SoftMaxHeapSize** để trả bộ nhớ về OS

### Tóm tắt cho Senior

- **ZGC/Shenandoah** = < 1 ms, chi phí CPU 5-15% (phụ thuộc vào workload và phiên bản Java; Generational ZGC có hồ sơ chi phí khác).
- **Concurrent Evacuation** = chìa khóa cho low latency
- **Allocation Stall** = mối nguy hiểm ẩn giấu
- **Generational ZGC** = cân bằng tốt nhất
- **G1** = thỏa hiệp cho hầu hết các ứng dụng
- **Chi phí barrier** = cái giá cho các khoảng dừng thấp

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- ZGC và Shenandoah: khoảng dừng < 1 ms thông qua Concurrent Evacuation (các đối tượng được di chuyển KHÔNG cần STW)
- ZGC: Colored Pointers + Load Barriers (~5-15 ns chi phí khi đọc); Shenandoah: Load Reference Barriers (rẻ hơn)
- G1: Write Barriers (~1-2 ns khi ghi), khoảng dừng 20-200 ms thông qua Mixed GC + region
- Allocation Stall: ứng dụng tạo rác nhanh hơn concurrent marking; throughput giảm nhiều hơn cả khi dùng Parallel GC
- Generational ZGC (Java 21+): -50% chi phí CPU, throughput gần như bằng G1, khoảng dừng vẫn < 1 ms
- Khi nào KHÔNG dùng GC low-latency: mức sử dụng CPU cao (các barrier làm nó tệ hơn), xử lý theo lô, Heap < 4 GB
- Tinh chỉnh: ZGC `-XX:ConcGCThreads=4` (số lõi/4), G1 `-XX:MaxGCPauseMillis=100`

**Các câu hỏi phụ thường gặp:**
- **Tại sao ZGC/Shenandoah có chi phí 5-15%?** — Các barrier được chèn vào trên mỗi lần đọc/ghi tham chiếu; CPU tốn thời gian cho các phép kiểm tra
- **Điều gì xảy ra nếu đặt MaxGCPauseMillis=10 ms cho G1?** — G1 không thể nằm gọn → To-space exhausted → Full GC (hàng giây!)
- **Tại sao Generational ZGC tốt hơn single-generational?** — Young GC thường xuyên hơn và nhanh hơn; -50% chi phí; các Allocation Stall gần như biến mất
- **Khi nào G1 tốt hơn ZGC?** — SLA 100-200 ms chấp nhận được, throughput quan trọng hơn; các ứng dụng CPU-bound; Heap < 4 GB

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "ZGC không có chi phí" — hy sinh 5-15% throughput để có khoảng dừng < 1 ms
- "Allocation Stall không nguy hiểm" — throughput giảm nhiều hơn cả khi dùng Parallel GC
- "GC low-latency luôn tốt hơn" — với xử lý theo lô hoặc các tác vụ CPU-bound, Parallel/G1 hiệu quả hơn
