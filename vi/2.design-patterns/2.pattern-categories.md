# What Pattern Categories Exist? (Có những nhóm Pattern nào?)

## Junior Level

Pattern được chia thành **ba nhóm chính** tùy thuộc vào việc chúng giúp bạn làm gì:

**1. Creational (Khởi tạo)** — che giấu CÁI GÌ được tạo ra, KHI NÀO, và NHƯ THẾ NÀO. Code không nên phụ thuộc vào các class cụ thể thông qua `new`.
- Ví dụ `Builder` — tạo đối tượng phức tạp theo từng bước
- Ví dụ `Singleton` — đảm bảo chỉ có một instance duy nhất
- Ví dụ `Factory` — tạo đối tượng thông qua một factory (nhà máy)

**2. Structural (Cấu trúc)** — giúp kết nối các class
- Ví dụ `Adapter` — làm cho các interface khác nhau trở nên tương thích
- Ví dụ `Decorator` — thêm chức năng thông qua việc bao bọc (wrapping)
- Ví dụ `Proxy` — thay thế một đối tượng bằng một vật đại diện (surrogate)

**3. Behavioral (Hành vi)** — quyết định: ai gọi ai, khi nào, và trong điều kiện nào.
- Ví dụ `Strategy` — hoán đổi các thuật toán
- Ví dụ `Observer` — đăng ký nhận sự kiện
- Ví dụ `Iterator` — duyệt qua các phần tử

**Ví dụ minh họa đơn giản:** Xây một ngôi nhà
- **Creational** — cách tạo ra gạch, cửa sổ, cửa ra vào
- **Structural** — cách kết nối chúng lại với nhau
- **Behavioral** — cách mọi người sẽ sử dụng ngôi nhà

### Khi nào KHÔNG nên suy nghĩ theo hướng phân loại nhóm

Đối với các ứng dụng CRUD đơn giản, việc phân loại pattern theo nhóm là thừa thãi. Chỉ sử dụng một pattern khi nó giải quyết được một vấn đề cụ thể.

## Middle Level

### 1. Creational Patterns (Các pattern khởi tạo)

**Trọng tâm:** Đóng gói (Encapsulating) việc tạo đối tượng

**Tại sao:** Giảm sự phụ thuộc (Decoupling) của hệ thống vào các cách triển khai cụ thể

```java
// Không có Factory — sự phụ thuộc chặt chẽ (tight coupling)
User user = new User();
Order order = new Order();

// Có Factory — tính linh hoạt
User user = userFactory.create();
Order order = orderFactory.create();
```

**Các pattern chính:**
- `Singleton` — chỉ có một instance duy nhất
- `Factory Method` — tạo đối tượng thông qua phương thức của subclass
- `Abstract Factory` — tạo ra các họ (family) đối tượng
- `Builder` — tạo đối tượng theo từng bước
- `Prototype` — sao chép đối tượng

**Trong Java hiện đại:**
```java
// Các static factory method trong interface
List<String> list = List.of("a", "b", "c");  // Thay vì new ArrayList()
Optional<String> opt = Optional.of(value);   // Factory Method
```

### 2. Structural Patterns (Các pattern cấu trúc)

**Trọng tâm:** Kết hợp các class thành các cấu trúc lớn hơn

**Tại sao:** Giải quyết các vấn đề về tính tương thích mà không cần kế thừa

```java
// Decorator — thêm chức năng
InputStream input = new BufferedInputStream(
                        new FileInputStream("file.txt")
                    );

// Adapter — tính tương thích interface
List<String> list = Collections.enumeration(arrayList);
```

**Các pattern chính:**
- `Adapter` — kết hợp các interface không tương thích
- `Decorator` — thêm trách nhiệm tại thời điểm chạy (runtime)
- `Proxy` — vật đại diện để kiểm soát quyền truy cập
- `Facade` — interface đơn giản hóa cho một subsystem (hệ thống con)
- `Composite` — cấu trúc dạng cây

**Trong Spring:**
```java
// Proxy — nền tảng của mọi "phép thuật" trong Spring
@Transactional      // Proxy bao quanh bean
@Cacheable         // Proxy có kèm caching
@Async             // Proxy dành cho tính bất đồng bộ
```

### 3. Behavioral Patterns (Các pattern hành vi)

**Trọng tâm:** Các thuật toán và cách phân phối trách nhiệm

**Tại sao:** Quản lý động lực của việc truyền tín hiệu

```java
// Strategy — hoán đổi các thuật toán
Comparator<String> byLength = (a, b) -> a.length() - b.length();
list.sort(byLength);

// Observer — đăng ký nhận sự kiện
button.addActionListener(e -> System.out.println("Clicked!"));
```

**Các pattern chính:**
- `Strategy` — họ (family) các thuật toán
- `Observer` — đăng ký nhận các thay đổi
- `Chain of Responsibility` — chuỗi các handler (bộ xử lý)
- `State` — hành vi phụ thuộc vào trạng thái
- `Template Method` — bộ khung của thuật toán

### 4. Phân loại mở rộng

**Concurrency Patterns (Các pattern đồng thời):**
```java
// Read-Write Lock
ReadWriteLock rwLock = new ReentrantReadWriteLock();

// Producer-Consumer
BlockingQueue<String> queue = new LinkedBlockingQueue<>();
ExecutorService executor = Executors.newFixedThreadPool(10);
```

**Architectural Patterns (Các pattern kiến trúc):**
- `MVC` — Model-View-Controller
- `Hexagonal Architecture` — port và adapter
- `CQRS` — phân tách đọc/ghi

**Cloud-Native Patterns:**
- `Circuit Breaker` — bảo vệ khỏi các lỗi dây chuyền (cascading failures)
- `Saga` — các transaction phân tán
- `Retry` — thử lại
- `Bulkhead` — cô lập tài nguyên

## Senior Level

### Ý nghĩa kiến trúc của việc phân loại

**Nhóm = mức độ quản lý sự phức tạp:**

| Nhóm       | Vấn đề được giải quyết               | Dấu hiệu code có mùi (Code Smell)                     |
| -------------- | ----------------------------- | ------------------------------- |
| **Creational** | Sự phụ thuộc chặt chẽ khi tạo đối tượng   | Có quá nhiều `new` trong code nghiệp vụ    |
| **Structural** | Độ phức tạp của các mối quan hệ  | Bùng nổ subclass, không tương thích |
| **Behavioral** | Logic tương tác            | `switch/if-else` khổng lồ          |

### Creational: Đảo ngược sự phụ thuộc trong thực tiễn

DIP (Dependency Inversion Principle — Nguyên lý đảo ngược phụ thuộc) — phụ thuộc vào trừu tượng, không phải chi tiết.
OCP (Open/Closed Principle) — mở để mở rộng, đóng để sửa đổi.

```
Nếu code nghiệp vụ có nhiều `new` → vi phạm DIP

Giải pháp:
  1. Simple Factory (phương thức static)
  2. Factory Method (kế thừa)
  3. Abstract Factory (các họ đối tượng)
  4. DI Container (Spring)
```

**Sự tiến hóa:**
```java
// Cấp 1: Simple Factory
public static UserService create() { return new UserServiceImpl(); }

// Cấp 2: Factory Method
public abstract class Factory { abstract UserService create(); }

// Cấp 3: Abstract Factory
public interface AppFactory {
    UserService createUser();
    OrderService createOrder();
    PaymentService createPayment();
}

// Cấp 4: DI Container
@Component
public class UserService { }  // Spring sẽ tự tạo nó
```

### Structural: Composition vs Kế thừa

**Decorator thay vì kế thừa:**
```java
// Kế thừa → bùng nổ class
class BufferedFileInputStream extends FileInputStream { }
class EncryptedFileInputStream extends FileInputStream { }
class BufferedEncryptedFileInputStream extends FileInputStream { }
// → 2^n class cho n chức năng!

// Decorator → composition (kết hợp)
new BufferedInputStream(
  new CipherInputStream(
    new FileInputStream("file.txt")
  )
)
// → n class cho n chức năng
```

### Behavioral: Đa hình (Polymorphism) thay vì switch

```java
// Cách tiếp cận thủ tục (Procedural)
switch (paymentType) {
    case CREDIT_CARD: processCreditCard(); break;
    case PAYPAL: processPayPal(); break;
    case CRYPTO: processCrypto(); break;
}

// Cách tiếp cận OOP (Strategy)
interface PaymentStrategy { void process(); }
class CreditCardPayment implements PaymentStrategy { ... }
class PayPalPayment implements PaymentStrategy { ... }

paymentStrategy.process();  // Đa hình
```

**Java hiện đại:**
```java
// Enum Map Strategy
Map<PaymentType, PaymentStrategy> strategies = Map.of(
    CREDIT_CARD, this::processCreditCard,
    PAYPAL, this::processPayPal,
    CRYPTO, this::processCrypto
);

strategies.get(type).process();
```

### Sự liên kết giữa các nhóm trong các hệ thống thực tế

**Spring Context như một "Meta-Factory" (Siêu nhà máy):**
```
ApplicationContext (Creational)
  → tạo ra các bean
    → bao bọc trong Proxy (Structural)
      → thứ quản lý hành vi (Behavioral)
```

**Chuỗi điển hình:**
```
Abstract Factory (Creational)
  → trả về Proxy (Structural)
    → thứ bao bọc logic nghiệp vụ
      → được quản lý thông qua Strategy (Behavioral)
        → được xây dựng thông qua Builder (Creational)
          → có Chain of Responsibility (Behavioral) để validation
```

### Ảnh hưởng đến hiệu năng

**JIT và đa hình (polymorphism):**
```
Monomorphic call (1 cách triển khai)
  → JIT inline code
  → 0 chi phí phát sinh

Bimorphic call (2 cách triển khai)
  → JIT vẫn tối ưu hóa được
  → Chi phí phát sinh tối thiểu

Megamorphic call (>2 cách triển khai)
  → Gọi gián tiếp thông qua vtable
  → Giảm CPU đáng kể có thể đo lường được
```

**Tối ưu hóa hot-path (đường dẫn nóng):**
```java
// Thay vì interface → enum
public enum CompressionType {
    GZIP { @Override public byte[] compress(byte[] data) { ... } },
    LZ4 { @Override public byte[] compress(byte[] data) { ... } };
    public abstract byte[] compress(byte[] data);
}

// → JIT tối ưu hóa bảng enum switch tốt hơn
```

### Đào sâu về các Cloud-Native Pattern

**Circuit Breaker:**
```java
@CircuitBreaker(name = "backendA", fallbackMethod = "fallback")
public String getData() {
    return restTemplate.getForObject("http://service-a", String.class);
}
```

**Saga Pattern:**
```
Order Service → tạo đơn hàng
  ↓
Payment Service → trừ tiền
  ↓
Inventory Service → giữ chỗ sản phẩm
  ↓ (nếu có lỗi)
Compensating Transactions (Giao dịch bù trừ) → hoàn tác tất cả
```

### Kinh nghiệm Production

**Tình huống thực tế: Việc phân loại giúp tìm ra nguyên nhân gốc rễ**
- Hệ thống: hơn 200 class, khó hiểu cái gì ở đâu
- Phân tích theo nhóm:
  - Creational: 30 class Factory (overengineering)
  - Structural: 50 Decorator (cần thiết)
  - Behavioral: 80 Strategy (trùng lặp)
- Giải pháp:
  - Thay thế Factory bằng DI
  - Hợp nhất Strategy → Map
- Kết quả: giảm 40% số class, tăng khả năng đọc

### Best Practices (Thực hành tốt nhất)

1. **Xác định nhóm** khi chọn một pattern
2. **Creational** → chống lại `new` trong code nghiệp vụ
3. **Structural** → composition > kế thừa
4. **Behavioral** → đa hình > switch
5. **Cloud-Native** là bắt buộc đối với microservices
6. **Kiểm tra sự liên kết** giữa các pattern
7. **Suy nghĩ về JIT** khi chọn cách triển khai
8. **Java hiện đại** đơn giản hóa nhiều nhóm

### Tóm tắt cho Senior

- **Creational** = chống lại sự phụ thuộc chặt chẽ khi tạo đối tượng
- **Structural** = quản lý độ phức tạp của các mối quan hệ
- **Behavioral** = quản lý logic tương tác
- **Nhóm** = mức độ quản lý sự phức tạp kiến trúc
- **Sự liên kết**: các pattern từ những nhóm khác nhau hoạt động cùng nhau
- **JIT**: megamorphic call ảnh hưởng đến hiệu năng
- **Cloud-Native** pattern rất quan trọng đối với microservices
- **Spring Context** = siêu nhà máy của tất cả các nhóm

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Ba nhóm chính: Creational (tạo đối tượng), Structural (kết hợp class), Behavioral (tương tác)
- Creational che giấu quá trình tạo đối tượng, Structural giải quyết vấn đề tương thích, Behavioral quản lý thuật toán
- Trong Java hiện đại: Factory Method được thay thế bằng Supplier<T>, Singleton — bằng DI container (Spring @Component)
- Spring @Transactional, @Cacheable, @Async hoạt động thông qua Proxy (pattern Structural)
- Cloud-Native pattern: Circuit Breaker, Saga, Retry, Bulkhead — bắt buộc đối với microservices
- Việc phân nhóm giúp xác định các vấn đề kiến trúc gốc rễ và chọn ra giải pháp phù hợp
- Sự tiến hóa: Simple Factory → Factory Method → Abstract Factory → DI Container

**Các câu hỏi phụ thường gặp:**
- **Pattern nào thay thế switch trong code nghiệp vụ?** — Strategy (Behavioral), Map<Enum, Function>
- **Megamorphic call là gì?** — Lời gọi phương thức với >2 cách triển khai interface, JIT không thể inline
- **Spring quản lý việc tạo bean như thế nào?** — ApplicationContext như một "siêu nhà máy" của tất cả các nhóm pattern
- **Khi nào việc phân nhóm pattern là thừa thãi?** — Trong các ứng dụng CRUD đơn giản và các dự án prototype

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi không cần phân nhóm, tôi viết code không dùng pattern" — thể hiện sự thiếu hiểu biết về nền tảng kiến trúc
- "Tất cả pattern đã lỗi thời với Spring" — chính bản thân Spring cũng sử dụng pattern ở bên dưới
- "Creational pattern chỉ cần thiết trong Java" — chúng áp dụng được cho bất kỳ ngôn ngữ OOP nào
- "Structural pattern chỉ dành cho GUI" — Adapter, Decorator, Proxy có mặt ở khắp mọi nơi trong Spring
