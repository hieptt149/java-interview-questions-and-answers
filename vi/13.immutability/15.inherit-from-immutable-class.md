# Can you inherit from an immutable class? (Bạn có thể kế thừa từ một immutable class không?)

---

## Basic Level

Về mặt kỹ thuật — có, nếu class **không** được đánh dấu `final`. Nhưng đây là một **ý tưởng tồi**, vì một subclass có thể thêm các trường mutable, và khi đó code kỳ vọng một object bất biến sẽ nhận được một object mutable.

### Ví Dụ Về Vấn Đề
```java
// Class "immutable", nhưng không có final
public class ImmutableBase {
    private final String value;
    public ImmutableBase(String v) { this.value = v; }
    public String getValue() { return value; }
}

// Subclass thêm tính mutable
public class MutableChild extends ImmutableBase {
    private String extra; // trường mutable
    public void setExtra(String e) { this.extra = e; }
}
```

### Giải Pháp
Luôn khai báo các immutable class là `final`:
```java
public final class ImmutablePoint { ... } // không thể kế thừa
```

---

## Intermediate Level

### Tại Sao Kế Thừa Phá Vỡ Tính Bất Biến

1. **Các trường mutable mới** — một subclass có thể thêm `private String extra` với một setter
2. **Ghi đè method** — một subclass có thể ghi đè các getter, trả về dữ liệu khác
3. **hashCode không ổn định** — các immutable object thường cache hashCode; một subclass với các trường mutable làm cho cache này không còn hợp lệ

### Các Lựa Chọn Thay Thế Cho Kế Thừa

**1. Composition thay vì kế thừa**
```java
public final class ExtendedPoint {
    private final ImmutablePoint point;
    private final String label;
    // ...
}
```

**2. Constructor private + static factory**
```java
public final class ImmutableObject {
    private final String data;
    private ImmutableObject(String data) { this.data = data; }
    public static ImmutableObject of(String data) { return new ImmutableObject(data); }
}
```

### Các Ví Dụ Từ JDK
Tất cả các immutable class cơ bản đều là `final`: `String`, `Integer`, `BigDecimal`, `LocalDate`.

## Advanced Level

### Tính Đa Hình Như Một Mối Đe Dọa

Nếu một method kỳ vọng `ImmutableBase` và dựa vào tính bất biến của nó (ví dụ: cache một kết quả dựa trên `getValue()`), việc thay thế bằng `MutableChild` có thể dẫn đến:
- **Vi phạm bất biến (invariant)** — dữ liệu thay đổi sau khi validate
- **Bỏ qua bảo mật (Security Bypass)** — subclass trả về dữ liệu khác sau khi validate
- **Mất tính thread-safe** — subclass truy cập các trường không phải `final` mà không đồng bộ hóa

### Sealed Classes (preview trong Java 15, ổn định trong Java 17)

Nếu cần kế thừa có giới hạn:
```java
public sealed class Shape permits Circle, Rectangle {
    // Cả hai class được phép cũng phải là immutable
}
```

### Tóm Tắt Cho Advanced
- Trong hầu hết các trường hợp, kế thừa từ một immutable class là một anti-pattern. Ngoại lệ: hệ thống phân cấp sealed class (Java 17+), nơi mọi lớp con cũng đều bất biến
- Luôn đánh dấu các immutable class là `final`
- Tính bất biến không chỉ là các trường `final` — nó còn có nghĩa là **cấm thay đổi logic** thông qua tính đa hình
- Dùng **Sealed classes** để kế thừa có kiểm soát trong Java 17+

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Về mặt kỹ thuật là có thể (nếu không có `final`), nhưng đó là một anti-pattern — subclass thêm tính mutable
- Subclass có thể: thêm các trường mutable, ghi đè getter, làm hashCode không ổn định
- Giải pháp: luôn `final class` cho các immutable class
- Các lựa chọn thay thế: composition thay vì kế thừa, sealed classes (Java 17+)
- Tất cả các immutable class cơ bản của JDK đều là final: String, Integer, BigDecimal, LocalDate
- Sealed classes cho phép kế thừa có giới hạn với sự kiểm soát các lớp con

**Các câu hỏi phụ thường gặp:**
- *Tại sao kế thừa phá vỡ tính bất biến?* — Subclass thêm các trường mutable hoặc ghi đè getter
- *Nếu tôi cần mở rộng chức năng thì sao?* — Composition: bọc immutable object trong một class final mới
- *Sealed classes vs final?* — Sealed cho phép các lớp con cụ thể, final cấm tất cả
- *Tính đa hình như một mối đe dọa?* — Method dựa vào tính bất biến, subclass thay thế dữ liệu sau khi validate

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Kế thừa từ một immutable class là ổn" — đó là một anti-pattern
- "Subclass không thể thay đổi các trường final" — đúng, nhưng nó có thể ghi đè getter
- "Sealed classes = final" — sealed cho phép kế thừa, nhưng có giới hạn
- "Bạn có thể thêm một trường mutable trong subclass" — điều đó phá hủy hợp đồng bất biến
