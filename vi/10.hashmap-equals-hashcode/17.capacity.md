# What is Capacity in HashMap? (Capacity trong HashMap là gì?)

## 🟢 Junior Level

**Capacity** là số lượng ô (bucket) trong mảng nội bộ của HashMap.

- **Giá trị mặc định:** 16
- **Luôn là lũy thừa của hai:** 16, 32, 64, 128, 256...

**Ví dụ:**
```java
HashMap<String, Integer> map = new HashMap<>();
// capacity = 16 (mặc định)
// Ở 12 phần tử (16 * 0.75) — tăng lên 32

HashMap<String, Integer> map2 = new HashMap<>(64);
// capacity = 64 ngay từ đầu
```

**Ví dụ minh họa đơn giản:** Capacity là số lượng hộp thư trong một chung cư. Nhiều hộp thư hơn = ít khả năng hai lá thư rơi vào cùng một hộp.

## 🟡 Middle Level

### Các tính chất của Capacity

| Tham số    | Giá trị    | Mô tả                    |
| ---------- | ---------- | ------------------------ |
| Mặc định   | 16         | Kích thước ban đầu       |
| Tối thiểu  | 1          | Nhỏ nhất có thể          |
| Tối đa     | 2^30       | Max (1.073.741.824)      |
| Bước       | x2         | Tăng đôi mỗi lần resize  |

### Tại sao luôn là lũy thừa của hai?

Điều này cần cho công thức nhanh:
```java
index = (n - 1) & hash;  // Chỉ hoạt động khi n = 2^k
```

Nếu n là 15 (không phải lũy thừa của hai):
```
n-1 = 14 => 0000 1110
```
Bit thấp nhất luôn là 0 — mọi bucket lẻ đều rỗng. Điều này thảm họa cho va chạm.

### Làm tròn Initial Capacity

```java
new HashMap(10)  // capacity trở thành 16
new HashMap(33)  // capacity trở thành 64
new HashMap(100) // capacity trở thành 128
```

Method `tableSizeFor()` tìm lũy thừa của hai gần nhất hướng lên.

### Quan hệ với Threshold

```
threshold = capacity * loadFactor
```

Ở capacity=16, loadFactor=0.75: threshold = 12. Ở phần tử thứ 13 — resize.

### Ảnh hưởng tới hiệu năng

**Quá nhỏ:** Resize thường xuyên (O(n)), tăng vọt latency
**Quá lớn:** Iterate chậm (duyệt qua các bucket rỗng). Capacity lớn được biện minh khi: (1) bạn biết số lượng phần tử mong đợi và muốn tránh resize; (2) Map sống lâu và thường được đọc. KHÔNG được biện minh: cho các Map tạm/nhỏ.

## 🔴 Senior Level

### Hiện thực bên trong

```java
transient Node<K,V>[] table; // Bản thân mảng
```

Khi `new HashMap()` được tạo, mảng là `null`. Khởi tạo là lười, ở lần `put()` đầu tiên.

### tableSizeFor() — Thuật toán tìm lũy thừa của hai

```java
static final int tableSizeFor(int cap) {
    int n = cap - 1;
    n |= n >>> 1;
    n |= n >>> 2;
    n |= n >>> 4;
    n |= n >>> 8;
    n |= n >>> 16;
    return (n < 0) ? 1 : (n >= MAXIMUM_CAPACITY) ? MAXIMUM_CAPACITY : n + 1;
}
```

Thủ thuật bit này lấp tất cả các bit ở bên phải bit set cao nhất, rồi cộng 1.

### Tối ưu Resize

Khi tăng đôi capacity (Java 8+):
```java
// Phần tử hoặc ở nguyên vị trí hoặc dịch chuyển tới oldIndex + oldCap
if ((e.hash & oldCap) == 0) {
    // Cùng chỉ số
} else {
    // Chỉ số + oldCapacity
}
```
Không cần tính lại các hash — một bit được kiểm tra.

### Hệ quả về bộ nhớ

- capacity=16: mảng ~128 byte (16 tham chiếu × 8 byte)
- capacity=1.000.000: mảng ~4-8MB (ngay cả với 0 phần tử!). Các tham chiếu trên một JVM 64-bit không có compressed references: 1M × 8 byte ≈ 8MB. Với UseCompressedOops (mặc định, nén các tham chiếu xuống 4 byte): 1M × 4 byte ≈ 4MB.
- Khi iterate: O(capacity + size) — các bucket rỗng cũng được duyệt

### Các trường hợp biên (Edge Case)

1. **capacity = MAXIMUM_CAPACITY (2^30):** Không tăng thêm nữa
2. **capacity > MAXIMUM_CAPACITY:** Lỗi (threshold = Integer.MAX_VALUE)
3. **Initial capacity = 0:** Được cho phép, put đầu tiên tạo capacity = 1

### Best Practices Production

```java
// Cho 1000 phần tử:
int expected = 1000;
int capacity = (int)(expected / 0.75f) + 1; // 1334
// HashMap làm tròn thành 2048
new HashMap<>(capacity);
```

Điều này ngăn resize và đảm bảo latency ổn định.

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Capacity = số lượng bucket, luôn là lũy thừa của hai (16, 32, 64...)
- Mặc định = 16, Tối đa = 2^30, tăng đôi khi resize
- new HashMap(10) → capacity = 16 (làm tròn lên lũy thừa của hai qua tableSizeFor)
- Công thức chỉ số: `(n-1) & hash` chỉ hoạt động khi n = 2^k
- Khởi tạo lười: mảng được tạo ở lần put đầu tiên (Java 8+)
- tableSizeFor() — thuật toán bit: lấp tất cả các bit ở bên phải bit cao nhất + 1
- Khi iterate: O(capacity + size) — các bucket rỗng cũng được duyệt

**Các câu hỏi phụ thường gặp:**
- **Điều gì xảy ra với capacity = 0?** — được cho phép, put đầu tiên tạo capacity = 1
- **Tại sao không dùng các số nguyên tố?** — cho `(n-1) & hash`, cần một lũy thừa của hai; Hashtable dùng các số nguyên tố với `%`
- **tableSizeFor tìm lũy thừa của hai như thế nào?** — qua chuỗi `n |= n >>> k` (1,2,4,8,16 bit)
- **Bao nhiêu bộ nhớ ở capacity = 1M?** — ~4-8MB (mảng các tham chiếu, phụ thuộc UseCompressedOops)

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Capacity có thể là bất kỳ số nào" — không, luôn là lũy thừa của hai
- "HashMap tạo mảng trong constructor" — không, một cách lười ở lần put đầu tiên
- "capacity = 10 tạo 10 bucket" — không, làm tròn thành 16
