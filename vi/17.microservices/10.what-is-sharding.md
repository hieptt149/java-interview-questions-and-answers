# What is sharding (Sharding là gì)

## Junior Level

**Sharding** là việc chia một database lớn thành **nhiều phần nhỏ hơn (shard)**, mỗi phần trên server riêng của nó.

Khác với read replica (các bản sao dữ liệu để đọc), các shard chứa dữ liệu KHÁC NHAU.
Mỗi shard là một phần độc lập của tập dữ liệu.

```
DB lớn (100M bản ghi) -> chậm

Sharding:
Shard 1: user A-F (server 1)
Shard 2: user G-M (server 2)
Shard 3: user N-Z (server 3)
```

**Tại sao:**
- **Scaling** — mỗi shard trên server riêng của nó
- **Hiệu năng** — index trở nên nhỏ hơn, vừa hoàn toàn trong RAM, độ sâu B-tree giảm. Truy vấn quét ít trang hơn — nhanh hơn.
- **Độ tin cậy** — một shard sập, các shard khác vẫn hoạt động

## Middle Level

### Khi Nào KHÔNG Nên Sharding

Đừng shard cho đến khi bạn đạt đến giới hạn lưu trữ hoặc ghi của một server duy nhất.
Với các tập dữ liệu lên đến ~100GB, sharding thường thừa thãi — độ phức tạp vận hành của nó
lớn hơn lợi ích.

### Các Chiến Lược Sharding

**1. Range-based:**
```
Shard 1: ID 1-1000
Shard 2: ID 1001-2000
Shard 3: ID 2001-3000
```

**2. Hash-based:**
```
shard = hash(key) % num_shards
user_123 -> hash("user_123") % 3 = shard 2
```

**3. Directory-based:**
```
Bảng tra cứu: key -> shard
user_123 -> shard 2
user_456 -> shard 1
```

### Các Lỗi Thường Gặp

1. **Hot shard:**
```
Tất cả user mới đi vào một shard
-> tải không đồng đều
Giải pháp: hash-based thay vì range-based
```
(Hot spot — một shard nhận traffic không cân xứng nhiều hơn.
Cross-shard join — các truy vấn kết hợp dữ liệu từ các shard khác nhau (tốn kém).)

## Senior Level

### Đánh Đổi Kiến Trúc

| Range     | Hash             | Directory               |
| --------- | ---------------- | ----------------------- |
| Đơn giản hơn   | Đồng đều hơn        | Linh hoạt hơn           |
| Hot spot | Khó rebalance | Single point of failure |

### Kinh Nghiệm Production

**Resharding:**
```
Khi thêm một shard mới:
1. Tính toán lại phân phối hash
2. Di chuyển dữ liệu
3. Cập nhật routing

MongoDB, Cassandra hỗ trợ auto-resharding
```

### Best Practices

```
✅ Hash-based để phân phối đồng đều
✅ Giám sát kích thước mỗi shard
✅ Lập kế hoạch resharding trước
✅ Cross-shard join — tránh chúng

❌ Không giám sát hot spot
❌ Quá nhiều truy vấn cross-shard
```

## Interview Cheat Sheet

**Cần phải biết:**
- Sharding — chia một DB thành các phần (shard), mỗi phần trên server riêng
- Mỗi shard chứa dữ liệu KHÁC NHAU (khác với read replica)
- Các chiến lược: range-based, hash-based, directory-based
- Hash-based phân phối đồng đều hơn, range-based đơn giản hơn nhưng có hot spot
- Resharding — di chuyển dữ liệu khi thêm shard
- Cross-shard JOIN tốn kém — tránh chúng
- Đừng sharding cho đến khi đạt giới hạn lưu trữ/ghi (~100GB+)

**Các câu hỏi phụ thường gặp:**
- **Hot shard là gì?** Một shard nhận traffic không cân xứng nhiều hơn — giải pháp: hash-based thay vì range-based.
- **Cách thực hiện resharding?** Tính toán lại phân phối -> di chuyển dữ liệu -> cập nhật routing. MongoDB/Cassandra hỗ trợ auto-resharding.
- **Range vs hash vs directory?** Range đơn giản hơn, hash đồng đều hơn, directory linh hoạt hơn (nhưng SPOF).
- **Khi nào sharding là thừa thãi?** Tập dữ liệu lên đến ~100GB — độ phức tạp vận hành lớn hơn lợi ích.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Sharding = read replica" — không, replica = bản sao, shard = dữ liệu khác nhau
- "Range-based luôn tốt hơn" — không, hot spot với phân phối không đồng đều
- "Cross-shard JOIN là thực hành bình thường" — không, chúng tốn kém, tránh chúng
- "Sharding cần thiết ngay từ đầu" — không, bắt đầu khi bạn đạt giới hạn
