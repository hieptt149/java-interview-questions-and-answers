# Difference Between State and Strategy? (Sự khác nhau giữa State và Strategy?)

## Junior Level

Cả hai pattern trông có vẻ giống nhau, nhưng **mục đích** của chúng lại khác nhau:

**Strategy** — chọn thuật toán **từ bên ngoài** (client quyết định):
```java
// Client chọn strategy
order.setPaymentStrategy(new CreditCardPayment());  // Từ bên ngoài
order.pay();
```

**State** — thay đổi hành vi **từ bên trong** (đối tượng tự quyết định):
```java
// Đối tượng tự thay đổi trạng thái của chính nó
order.process();  // Bên trong: nếu đã thanh toán -> giao hàng, nếu chưa -> đợi
```

**Ví dụ minh họa đơn giản:**
- **Strategy:** Bạn chọn tuyến đường trong thiết bị định vị (bằng ô tô/đi bộ)
- **State:** Đèn giao thông tự thay đổi màu (đỏ -> vàng -> xanh)

## Middle Level

### Strategy: Điều khiển từ bên ngoài

```java
interface SortStrategy { void sort(List<Integer> list); }

class QuickSort implements SortStrategy { ... }
class MergeSort implements SortStrategy { ... }

// CLIENT quyết định
List<Integer> data = new ArrayList<>();
Sorter sorter = new Sorter();
sorter.setStrategy(new QuickSort());  // Client đã chọn
sorter.sort(data);
```

### State: Điều khiển từ bên trong

```java
interface OrderState { void process(Order order); }

class Order {
    private OrderState state;
    void setState(OrderState s) { this.state = s; }
    void process() { state.process(this); } // ủy quyền (delegation) cho state
}

class NewState implements OrderState {
    public void process(Order order) {
        // Việc tạo state trực tiếp (new PaidState()) là một anti-pattern (phụ thuộc chặt chẽ).
        // Cách tiếp cận đúng: chuyển trạng thái thông qua Registry/Factory.
        order.setState(new PaidState());
    }
}

class PaidState implements OrderState {
    public void process(Order order) {
        order.setState(new ShippedState());
    }
}

// ĐỐI TƯỢNG tự thay đổi trạng thái của chính nó
Order order = new Order();
order.setState(new NewState());
order.process();  // Bên trong: NewState -> PaidState
order.process();  // Bên trong: PaidState -> ShippedState
```

### So sánh

| Tiêu chí          | Strategy                        | State                       |
| ------------------ | ------------------------------- | ---------------------------- |
| **Ai quyết định**    | Client                          | Bản thân đối tượng               |
| **Khi nào thay đổi**   | Tại thời điểm chạy, theo lựa chọn              | Khi trạng thái thay đổi          |
| **Sự phụ thuộc**   | Các strategy không biết về nhau | Các state biết về việc chuyển trạng thái |
| **Mục tiêu**           | Thay thế thuật toán           | Quản lý hành vi          |

## Senior Level

### Ý định kiến trúc (Architecture Intent)

```
Strategy = Dependency Injection dành cho thuật toán
  -> Inject đúng thuật toán cần dùng
  -> Các thuật toán độc lập với nhau

State = Máy trạng thái hữu hạn (Finite State Machine)
  -> Các trạng thái được liên kết bởi các bước chuyển
  -> Mỗi trạng thái biết về các trạng thái tiếp theo
```

### Sự khác biệt về mức độ phụ thuộc (Coupling)

```java
// Strategy: các strategy KHÔNG biết về nhau
class CreditCardPayment implements PaymentStrategy { }
class PayPalPayment implements PaymentStrategy { }
// Không có sự phụ thuộc giữa chúng

// State: các state biết về việc chuyển trạng thái
class NewState implements OrderState {
    public void process(Order order) {
        order.setState(new PaidState());  // Biết về PaidState!
    }
}
// Được liên kết thông qua context
```

### Kinh nghiệm Production

**Tình huống thực tế:**
- Order: có 5 trạng thái
- Ban đầu dùng Strategy -> client quản lý việc chuyển trạng thái
- Lỗi: đơn hàng chuyển từ "Delivered" (Đã giao) sang "New" (Mới)
- Giải pháp: máy trạng thái (state machine) có kiểm tra tính hợp lệ của bước chuyển
- Kết quả: không thể xảy ra các bước chuyển không hợp lệ

### Best Practices (Thực hành tốt nhất)

1. **Strategy** để hoán đổi thuật toán
2. **State** để quản lý vòng đời (lifecycle)
3. **Enum** cho các trạng thái đơn giản
4. **Spring Statemachine** cho ứng dụng doanh nghiệp (enterprise)
5. **Kiểm tra tính hợp lệ của bước chuyển** trong State

### Tóm tắt cho Senior

- **Strategy** = client chọn thuật toán
- **State** = đối tượng tự quản lý hành vi của chính nó
- **Strategy** = các thuật toán độc lập
- **State** = các bước chuyển được liên kết giữa các trạng thái
- **State Machine** ngăn ngừa các bước chuyển không hợp lệ

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Strategy — client chọn thuật toán từ bên ngoài, State — đối tượng tự thay đổi hành vi từ bên trong
- Strategy: các thuật toán độc lập với nhau, State: các trạng thái được liên kết bởi các bước chuyển
- Strategy = Dependency Injection dành cho thuật toán, State = Máy trạng thái hữu hạn (Finite State Machine)
- State ngăn ngừa các bước chuyển không hợp lệ (không thể chuyển từ "Delivered" sang "New")
- Template Method — thay thế từng phần của thuật toán thông qua kế thừa, Strategy — toàn bộ thuật toán thông qua composition
- Đối với các trạng thái đơn giản: Enum có các phương thức trừu tượng, đối với enterprise: Spring Statemachine
- Việc tạo state trực tiếp (new PaidState()) — phụ thuộc chặt chẽ, cách tiếp cận đúng: chuyển trạng thái thông qua Registry/Factory

**Các câu hỏi phụ thường gặp:**
- **Khi nào nên dùng State thay vì Strategy?** — Khi có một vòng đời với các bước chuyển hợp lệ (đơn hàng, tài liệu)
- **Tại sao các state cần phải biết về các bước chuyển?** — Nếu không, client có thể thực hiện một bước chuyển không hợp lệ
- **Template Method khác Strategy như thế nào?** — Template Method = từng phần của thuật toán (kế thừa), Strategy = toàn bộ thuật toán (composition)
- **Cần làm gì nếu có quá nhiều bước chuyển?** — Máy trạng thái với bảng chuyển trạng thái (transition table), Spring Statemachine

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Strategy và State giống nhau" — mục đích và cách điều khiển hoàn toàn khác nhau
- "Client nên quản lý các trạng thái" — vậy thì đó là Strategy, không phải State
- "State machine là overengineering" — với 5+ trạng thái, sẽ có lỗi về bước chuyển nếu không có nó
- "Các state không nên biết về nhau" — vậy thì không thể kiểm tra tính hợp lệ của các bước chuyển
