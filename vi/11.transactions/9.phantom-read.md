# What is Phantom Read? (Phantom Read là gì?)

## 🟢 Junior Level

**Phantom Read** là một hiện tượng bất thường của transaction, trong đó cùng một phép chọn dữ liệu trong một transaction trả về số lượng dòng khác nhau vì một transaction khác đã insert hoặc delete các bản ghi khớp điều kiện.

**Ví dụ minh họa đơn giản:** Bạn đếm số người trong một phòng (được 10). Trong lúc bạn quay đi, có người bước vào. Bạn đếm lại — giờ là 12. Những người "mới" này là các bóng ma (phantom).

**Ví dụ SQL:**

```sql
-- Transaction 1
BEGIN;
SELECT COUNT(*) FROM orders WHERE status = 'pending';  -- trả về 5

-- Trong khi Transaction 1 đang mở, Transaction 2 thực hiện:
-- INSERT INTO orders (status) VALUES ('pending');
-- COMMIT;

-- Transaction 1 lặp lại cùng query:
SELECT COUNT(*) FROM orders WHERE status = 'pending';  -- trả về 6 — một phantom!
COMMIT;
```

**Khác biệt then chốt so với non-repeatable read:**
- Non-repeatable read — **giá trị của một dòng đã tồn tại** thay đổi (UPDATE/DELETE).
- Phantom read — một dòng **hoàn toàn mới** xuất hiện (INSERT).

**Isolation level nào bảo vệ:**
| Level            | Phantom có thể xảy ra? |
| ---------------- | ------------------ |
| Read Uncommitted | Có                |
| Read Committed   | Có                |
| Repeatable Read  | Tùy DBMS    |
| Serializable     | Không                 |

**Khi nào điều này quan trọng:** Tính tổng, tạo báo cáo, kiểm tra tính duy nhất trước khi insert.

## 🟡 Middle Level

### Cách Nó Hoạt Động Nội Bộ

Phantom read xảy ra vì hầu hết DBMS ở các level dưới Serializable đọc một **snapshot dữ liệu**, nhưng không khóa **các khoảng key**.

Khi bạn thực thi `SELECT WHERE status = 'pending'`, cơ sở dữ liệu trả về các dòng tồn tại tại thời điểm chụp snapshot. Nhưng nếu một transaction khác insert một dòng mới với `status = 'pending'`, query lặp lại của bạn sẽ thấy nó như một "phantom".

### Các Kịch Bản Thực Tế

**Kịch bản 1: Tạo Báo Cáo**
```java
@Transactional
public Report generateDailyReport(LocalDate date) {
    int orderCount = orderRepo.countByDate(date);       // 100 đơn hàng
    double totalAmount = orderRepo.sumByDate(date);     // Tính cho 100 đơn hàng

    // Nếu một đơn hàng mới cho cùng ngày được insert tại thời điểm này,
    // orderCount và totalAmount trở nên không nhất quán
    return new Report(orderCount, totalAmount);
}
```

**Kịch bản 2: Kiểm Tra Tính Duy Nhất Trước Khi Insert**
```java
@Transactional
public void registerUser(String email) {
    long count = userRepo.countByEmail(email);  // = 0
    // Một transaction khác insert một user với email này và commit
    userRepo.save(new User(email));              // Trùng lặp! Hoặc unique violation nếu có index
}
```

### Các Lỗi Thường Gặp

| Lỗi                                                              | Hậu quả                                                                          | Giải pháp                                           |
| -------------------------------------------------------------------- | ------------------------------------------------------------------------------------ | -------------------------------------------------- |
| SELECT lặp lại trong một transaction dài để validate dữ liệu            | Nhận các dòng phantom, logic nghiệp vụ sai                                                       | Rút ngắn transaction hoặc dùng Serializable            |
| COUNT() + xử lý kết quả tiếp theo                           | Thiếu hoặc thừa bản ghi                                                              | Dùng `FOR UPDATE` hoặc Serializable                   |
| Giả định Repeatable Read bảo vệ khỏi phantom trong PostgreSQL        | Kỳ vọng không đúng như thực tế — trong PG RR bảo vệ khỏi phantom, trong MySQL thì không           | Nắm rõ đặc thù DBMS của bạn                                       |

### So Sánh: Các DBMS Khác Nhau Xử Lý Phantom Ở Repeatable Read Như Thế Nào

| DBMS         | Phantom ở RR?                      | Cơ chế                                        |
| ------------ | ------------------------------------ | ------------------------------------------------ |
| PostgreSQL   | **Không** (bảo vệ qua MVCC)           | Snapshot từ lần đọc đầu tiên, không thấy dòng mới   |
| MySQL/InnoDB | **Không** (bảo vệ qua Next-Key Lock) | Gap Lock chặn các khoảng                           |
| Oracle       | **Không** (MVCC)                      | Tương tự PostgreSQL                            |
| SQL Server   | **Có** (không bảo vệ)                | Ở RR thấy các dòng mới khi query lặp lại            |

### Khi Nào KHÔNG Cần Lo Lắng Về Phantom

- **Các báo cáo chỉ đọc** với sai số chấp nhận được
- **Caching** — nếu dữ liệu có thể hơi cũ
- **Thống kê** — số đếm gần đúng có thể chấp nhận được

## 🔴 Senior Level

### Hiện Thực Nội Bộ: MVCC Và Predicate Lock

> **Các thuật ngữ:**
> - **Predicate lock** — một lock không nằm trên một dòng cụ thể, mà nằm trên ĐIỀU KIỆN của query (WHERE status='pending').
> - **RW-dependency** — tình huống T1 đọc dữ liệu mà T2 sau đó ghi.
> - **Coarsening (làm thô)** — gộp nhiều lock chi tiết thành một lock thô hơn để tiết kiệm bộ nhớ.

#### Cách Tiếp Cận MVCC (PostgreSQL)

Trong PostgreSQL, phantom read ở level Repeatable Read được ngăn chặn bởi kiến trúc MVCC:

```
Mỗi dòng chứa các trường hệ thống:
  - xmin: transaction ID đã insert dòng
  - xmax: transaction ID đã delete dòng (0 = còn sống)

Khi SELECT:
  1. Một snapshot được chụp với xmin hiện tại
  2. Chỉ các dòng có xmin < snapshot.xmin mới hiển thị
  3. Một dòng mới từ transaction khác có xmin > snapshot.xmin → VÔ HÌNH
```

Điều này có nghĩa: PostgreSQL trên RR **thực tế** bảo vệ khỏi phantom, mặc dù chuẩn ANSI không yêu cầu điều đó. Đây là một tác dụng phụ của thiết kế MVCC.

#### Predicate Lock (Serializable Trong PostgreSQL)

Ở level Serializable, PostgreSQL sử dụng **Serializable Snapshot Isolation (SSI)**:

```
Khi thực thi: SELECT * FROM orders WHERE status = 'pending'

1. Một predicate lock được đăng ký trên khoảng index (hoặc full table scan)
2. Nếu một transaction khác thực hiện INSERT INTO orders (status='pending')
   - Một RW-dependency được phát hiện: T1 đọc predicate, T2 ghi vào nó
3. Khi commit, đồ thị phụ thuộc được kiểm tra
4. Nếu tìm thấy chu trình nguy hiểm → một transaction nhận:
   ERROR: could not serialize access due to read/write dependencies
   SQLSTATE: 40001
```

#### Next-Key Locking (MySQL/InnoDB)

MySQL ở Repeatable Read sử dụng cách tiếp cận khác:

```sql
-- Query: SELECT * FROM orders WHERE status = 'pending' FOR UPDATE;

InnoDB khóa:
1. Record lock: các dòng khớp điều kiện
2. Gap lock: các khoảng GIỮA các dòng tìm thấy
3. Next-key lock: kết hợp của 1 + 2

Một Gap Lock trên khoảng (10, 20) sẽ không cho phép INSERT INTO orders (id=15, ...)
```

**Vấn đề:** Gap Lock có thể gây ra deadlock kiểu phantom:

```
T1: SELECT * FROM t WHERE id BETWEEN 10 AND 20 FOR UPDATE;  -- khóa khoảng (10,20)
T2: SELECT * FROM t WHERE id BETWEEN 15 AND 25 FOR UPDATE;  -- khóa khoảng (15,25) — xung đột!
-- T1 và T2 chờ lẫn nhau → DEADLOCK
```

### Đánh Đổi Về Kiến Trúc (Trade-off)

**Cách A: Chấp nhận phantom read (Read Committed)**
- ✅ Ưu điểm: Throughput tối đa, không có range lock
- ❌ Nhược điểm: Application phải chịu được các lần đọc lặp lại không nhất quán
- Phù hợp cho: các hệ thống CRUD throughput cao nơi độ chính xác đọc lặp lại không quan trọng

**Cách B: Ngăn phantom read (Repeatable Read / Serializable)**
- ✅ Ưu điểm: Tính nhất quán nghiêm ngặt, hành vi xác định
- ❌ Nhược điểm: Throughput giảm 2-10 lần, nguy cơ serialization failure (tỷ lệ abort 5-30%)
- Phù hợp cho: hệ thống tài chính, đặt chỗ, kho hàng

**Cách C: Ngăn chặn ở cấp độ application (Optimistic Locking)**
- ✅ Ưu điểm: Không có DB lock, mở rộng theo chiều ngang
- ❌ Nhược điểm: Độ phức tạp hiện thực, cần retry, eventual consistency
- Phù hợp cho: microservice, CQRS, event sourcing

### Các Trường Hợp Biên Và Đặc Biệt

**1. Phantom Với UPDATE:**
```sql
-- Transaction 1:
BEGIN;
UPDATE orders SET status = 'processed' WHERE status = 'pending';
-- Ảnh hưởng 5 dòng

-- Transaction 2 (giữa hai SELECT trong T1):
INSERT INTO orders (status) VALUES ('pending');
COMMIT;

-- Transaction 1:
SELECT COUNT(*) FROM orders WHERE status = 'pending';
-- Trả về 1 (dòng vừa được insert, nếu level = Read Committed)
```

**2. Phantom Với Bảng Tạm (Temporary Table):**
Các bảng tạm trong PostgreSQL KHÔNG được SSI theo dõi. Phantom read vẫn có thể xảy ra ngay cả ở Serializable nếu dữ liệu đi qua bảng tạm.

**3. Phantom Với Sequence:**
`nextval('seq')` không bị rollback khi transaction abort. Điều này tạo ra các "khoảng trống" trong đánh số có thể bị nhầm là phantom khi audit.

**4. Phantom DELETE:**
```java
// Transaction 1 đọc 100 bản ghi
List<Order> orders = orderRepo.findAllPending();

// Transaction 2 xóa 50 trong số đó và commit

// Transaction 1 cố gắng update cả 100
// 50 bản ghi đã biến mất — UPDATE ảnh hưởng 0 dòng
// Mất dữ liệu âm thầm
```

**5. Index-only scan phantom:**
Nếu một query dùng covering index, nó có thể thấy số lượng dòng khác so với query dùng full table scan, do đặc thù visibility của MVCC snapshot.

### Tác Động Đến Hiệu Năng

| Phương pháp bảo vệ             | Tác động Latency                   | Tác động Throughput     | Bộ nhớ                                 |
| ----------------------------- | --------------------------------- | --------------------- | -------------------------------------- |
| Serializable (SSI)            | +50-200ms                        | Thấp hơn 2-10 lần           | Predicate lock: ~5-20MB shared memory |
| SELECT ... FOR UPDATE         | +5-50ms                          | Thấp hơn 1.5-3 lần          | Row lock: ~200 byte/lock               |
| Gap Lock (MySQL)             | +10-100ms                        | Thấp hơn 2-5 lần            | Gap lock: ~100 byte/lock               |
| Optimistic Locking            | +0ms (happy path), +50ms (retry) | Tùy contention | Cột @Version: 4 byte/dòng            |
| Locking ở application (Redis)   | +5-15ms                          | Thấp hơn 1.2-2 lần          | Redis key: ~100 byte                  |

**Các con số phụ thuộc vào phiên bản PG, phần cứng, và pattern tải (PostgreSQL 15, 8 core, NVMe):**
- Read Committed: ~50,000 TPS. Dùng như bậc độ lớn (order of magnitude), không phải giá trị tuyệt đối.
- Repeatable Read: ~48,000 TPS (gần như không có overhead cho tải chỉ đọc)
- Serializable: ~8,000 TPS với contention ghi trung bình (giảm 84% do abort)

### Tác Động Đến Bộ Nhớ

- **Predicate lock (SSI):** Được lưu trong shared memory. Dưới tải cao, xảy ra coarsening (gộp) lên đến cấp độ relation lock. Kích thước: ~128 byte cho mỗi predicate lock.
- **Gap lock (MySQL):** Được lưu trong bảng lock của InnoDB. Với nhiều gap lock, có thể xảy ra cạn kiệt `innodb_table_locks`.
- **MVCC snapshot:** Mỗi transaction đang hoạt động giữ một snapshot. Với các transaction chạy dài, các phiên bản dòng cũ (dead tuple) không thể bị xóa → table bloat.

### Các Khía Cạnh Concurrency

**Pattern serialization failure:**
```
T1: đọc khoảng [A, B]
T2: đọc khoảng [B, C]
T3: insert vào [A, B] và commit
T4: insert vào [B, C] và commit

T1 commit → kiểm tra: T3 ghi vào khoảng của T1 → RW-dependency
T2 commit → kiểm tra: T4 ghi vào khoảng của T2 → RW-dependency

Nếu hình thành một chu trình → một transaction bị abort
```

### Tình Huống Thực Tế Trong Production

**Tình huống:** Hệ thống xử lý thanh toán tại một công ty fintech (2024).

**Vấn đề:** Ở level Read Committed trong lúc tạo báo cáo hàng ngày, đã xảy ra phantom. Báo cáo hiển thị 10,000 giao dịch tổng cộng $5M, nhưng phân tích chi tiết cho thấy 50 giao dịch ($250K) đã được insert SAU COUNT ban đầu nhưng vẫn được tính vào tổng cuối cùng.

**Chuyện gì đã xảy ra:**
```java
// BatchJob, chạy hàng ngày
@Transactional
public DailyReport generateReport() {
    int count = txRepo.countByDate(today);         // snapshot 1
    BigDecimal sum = txRepo.sumByDate(today);       // snapshot 2

    // Tại thời điểm này payment gateway xác nhận 50 giao dịch
    // và chúng được insert vào DB (Read Committed)

    List<Transaction> txs = txRepo.findAllByDate(today); // snapshot 3 — các dòng mới hiển thị!
    // count = 10,000, nhưng txs.size() = 10,050
    // sum được tính từ 10,050 giao dịch, nhưng count = 10,000
}
```

Lỗi: ba snapshot khác nhau trong một transaction. Snapshot 1 (count=10000), Snapshot 3 (txs.size=10050). Sum được tính từ 10050 bản ghi, nhưng count=10000. Ở Repeatable Read, cả ba query sẽ dùng cùng một snapshot.

**Giải pháp:** Chuyển sang Repeatable Read (PostgreSQL) đã giải quyết vấn đề mà không cần thay đổi code, vì snapshot MVCC đảm bảo tính nhất quán của tất cả các SELECT trong một transaction.

**Tác động:**
- Trước: 0.5% báo cáo có sai lệch
- Sau: 0% sai lệch
- Hiệu năng: không thay đổi (workload chỉ đọc trên RR là miễn phí trong PG)

### Giám Sát Và Chẩn Đoán

**PostgreSQL — theo dõi serialization failure:**
```sql
-- Kiểm tra xung đột
SELECT datname, conflicts, deadlocks
FROM pg_stat_database
WHERE datname = 'your_db';

-- Các predicate lock đang hoạt động
SELECT * FROM pg_locks WHERE mode LIKE '%Serializable%';
```

**MySQL — theo dõi xung đột gap lock:**
```sql
-- Log deadlock
SHOW ENGINE INNODB STATUS\G

-- Các lock hiện tại
SELECT * FROM information_schema.innodb_locks;
```

**Cấp độ application (Micrometer):**
```java

```

### Best Practices Cho Highload

1. **Tránh Serializable cho các workload đọc nặng** — dùng Repeatable Read (PostgreSQL) hoặc Read Committed với kiểm tra nhất quán ở cấp độ application.
2. **Rút ngắn transaction** — transaction càng ngắn, cửa sổ cho phantom càng nhỏ.
3. **Dùng `FOR UPDATE` có chọn lọc** — chỉ cho các query quan trọng, không cho toàn bộ báo cáo.
4. **Materialize snapshot** — cho các báo cáo lớn, tạo một bảng tạm với dữ liệu snapshot và làm việc với nó.
5. **Event Sourcing cho audit** — thay vì SELECT lặp lại, dùng một event stream có thứ tự được đảm bảo.
6. **Data versioning** — thêm cột `version` để phát hiện các thay đổi liên quan đến phantom.

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Phantom Read — SELECT lặp lại trả về một tập dòng khác (INSERT/DELETE từ transaction khác)
- Khác biệt so với Non-Repeatable Read: Phantom = dòng mới, NRR = dòng đã tồn tại thay đổi
- Ở Repeatable Read: PostgreSQL ngăn phantom qua MVCC, MySQL qua Gap Lock
- Ở Serializable: được ngăn hoàn toàn qua SSI (PostgreSQL) hoặc 2PL
- Predicate lock trong SSI khóa không phải dòng mà là ĐIỀU KIỆN của query (WHERE status='pending')
- Ca thực tế: báo cáo hiển thị 10,000 giao dịch, nhưng phân tích chi tiết tìm thấy 10,050 — phantom

**Các câu hỏi phụ thường gặp:**
- Tại sao PG ngăn phantom ở RR mặc dù chuẩn ANSI không yêu cầu? — Tác dụng phụ của MVCC: snapshot không thấy dòng mới
- Next-Key Locking trong MySQL là gì? — Record Lock + Gap Lock, chặn cả dòng lẫn khoảng
- Khi nào phantom không nguy hiểm? — Báo cáo chỉ đọc với sai số chấp nhận được, caching, thống kê
- Làm sao giám sát phantom trong production? — Theo dõi serialization failure, giám sát các transaction chạy dài

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Repeatable Read ngăn phantom trong mọi DBMS" — SQL Server cho phép phantom ở RR
- "Phantom Read = lỗi của DBMS" — đây là hành vi được mong đợi ở các level dưới Serializable
- "FOR UPDATE giải quyết mọi vấn đề phantom" — FOR UPDATE khóa các dòng cụ thể, không phải các khoảng
