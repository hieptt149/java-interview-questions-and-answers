# What is stored in Stack? (Những gì được lưu trữ trong Stack?)

## Junior Level

**Stack** — một vùng bộ nhớ riêng tư (private) cho mỗi luồng (thread).

**Tại sao mỗi luồng có Stack riêng:** mỗi luồng có chuỗi lời gọi phương thức riêng của nó. Các luồng không thể dùng chung một Stack — nếu không, các biến cục bộ (local variable) của luồng này sẽ nhìn thấy được từ luồng khác.

**Ví dụ minh họa đơn giản:** Một chồng đĩa. Khi bạn gọi một phương thức — bạn đặt một chiếc đĩa lên trên cùng. Khi phương thức kết thúc (return) — bạn lấy chiếc đĩa đó ra. Bạn luôn làm việc với chiếc đĩa trên cùng.

**Những gì được lưu trữ:**
- Kiểu nguyên thủy (primitive): `int x = 10;`, `double price = 99.9;`
- Tham chiếu (reference) đến các đối tượng: `User user = ...;` (tham chiếu nằm trong Stack, đối tượng nằm trong Heap)
- Thông tin về lời gọi phương thức (method call information)

**Ví dụ:**
```java
public void methodA() {
    int a = 5;         // Stack
    methodB();         // Frame mới trên stack
}

public void methodB() {
    int b = 10;        // Stack (trong frame riêng của nó)
    // Khi phương thức kết thúc → b bị loại bỏ
}
```

**Kích thước Stack:** `-Xss` (mặc định 1 MB)
**Lỗi:** `StackOverflowError` khi đệ quy vô hạn

## Middle Level

### Cấu trúc Stack Frame

```
Stack Frame (được tạo khi gọi phương thức):
┌─────────────────────────────────┐
│ Local Variable Table            │
│   [0] = this                    │
│   [1] = param1                  │
│   [2] = param2                  │
│   [3] = biến cục bộ             │
├─────────────────────────────────┤
│ Operand Stack                   │
│   Cho các phép tính: push, pop  │
│   a + b → push a, push b, add   │
├─────────────────────────────────┤
│ Dynamic Linking                 │
│   → Constant Pool (phương thức, trường) │
├─────────────────────────────────┤
│ Return Address                  │
│   → Nơi cần quay về             │
└─────────────────────────────────┘
```

### Chính xác thì có gì trong Stack

```java
public class Example {
    public void process(int x) {
        int local = x * 2;        // Stack (primitive)
        String s = "hello";       // Stack (tham chiếu) → "hello" nằm trong Heap
        User user = new User();   // Stack (tham chiếu) → đối tượng nằm trong Heap
        int[] arr = new int[10];  // Stack (tham chiếu) → mảng nằm trong Heap
    }
}
```

**QUAN TRỌNG:** Chỉ có **tham chiếu** đến các đối tượng được lưu trong Stack, chứ không phải bản thân các đối tượng!

### StackWalker API (Java 9+)

```java
// Cách cũ (nặng nề)
StackTraceElement[] stack = new Throwable().getStackTrace();

// Cách hiện đại (lazy, nhanh)
StackWalker walker = StackWalker.getInstance();
walker.forEach(frame -> System.out.println(frame.getClassName()));

// Có lọc (filtering)
String caller = StackWalker.getInstance()
    .walk(frames -> frames
        .skip(1)  // Bỏ qua phương thức hiện tại
        .findFirst()
        .map(StackWalker.StackFrame::getClassName)
        .orElse(null));
```

## Senior Level

### Stack Frame: Bên trong (Under the Hood)

```
JVM Specification:
  Frame được tạo khi gọi phương thức
  Kích thước được tính toán tại thời điểm biên dịch (đã biết số lượng biến cục bộ)

Local Variable Table:
  - Mảng các word (mỗi word 32 bit)
  - long/double chiếm 2 slot
  - Index 0 = 'this' đối với các phương thức non-static
  - Tham số phương thức nằm trước tiên

Operand Stack:
  - Độ sâu cũng được biết tại thời điểm biên dịch
  - Được dùng cho các lệnh byte-code
  - Ví dụ: a + b + c
    → push a → push b → iadd → push c → iadd
```

### Virtual Threads và Stack (Java 21+)

```
Platform thread (trước Java 21):
  Stack = một khối cố định của bộ nhớ native (1 MB thông qua -Xss)
  → Hạn chế: ~1000 luồng cho mỗi 1 GB RAM
  → Không thể thay đổi kích thước khi đang chạy

Virtual thread (Java 21+):
  Stack = một đối tượng trong Heap!
  → Mount (gắn): được sao chép vào stack của Carrier Thread
  → Yield (nhường, khi blocking): được sao chép ngược lại vào Heap
  → Kết quả: hàng triệu luồng!

Bộ nhớ cho mỗi virtual thread:
  → ~2 KB — giá trị ban đầu cho một virtual thread rỗng. Stack tăng dần một cách động khi độ sâu lời gọi tăng lên.
  → Tăng lên một cách động khi cần
```

### Tail Call Optimization (TCO)

```java
// Đệ quy đuôi (tail recursion)
public int sum(int n, int acc) {
    if (n == 0) return acc;
    return sum(n - 1, acc + n);  // Lời gọi ở đuôi (tail call)
}

// Trong các ngôn ngữ có TCO → cùng một frame được tái sử dụng
// Java KHÔNG hỗ trợ TCO trực tiếp!
// Nhưng JIT thực hiện Method Inlining:

// Sau khi Inlining:
public int sum(int n, int acc) {
    while (n != 0) {
        acc += n;
        n--;
    }
    return acc;
}
// → 1 frame thay vì N!
```

### Stack và Escape Analysis

```java
// JIT có thể cấp phát đối tượng trên Stack!
public void process() {
    Point p = new Point(10, 20);  // Thường nằm trong Heap

    // Nếu JIT thấy rằng 'p' không "thoát" (escape) khỏi phương thức:
    // 1. Scalar Replacement: phân rã thành int x=10, y=20
    // 2. Stack Allocation: tạo trên Stack
    // 3. Lock Elision: loại bỏ synchronized nếu chỉ có một luồng

    System.out.println(p.x + p.y);  // Chỉ được dùng ở đây
}

// Kiểm tra: -XX:+PrintEscapeAnalysis -XX:+DoEscapeAnalysis
```

### Stream API như một Iterator

```java
// Stream = Iterator nâng cao với đánh giá lười (lazy evaluation)
list.stream()
    .filter(s -> s.startsWith("A"))   // Không thực thi cho đến thao tác terminal
    .map(String::toUpperCase)         // Không thực thi
    .forEach(System.out::println);    // Terminal → khởi chạy pipeline

// Khác với Iterator:
// 1. Composability (khả năng kết hợp) — có thể xây dựng các chuỗi
// 2. Lazy (lười) — chỉ tính toán khi cần
// 3. Parallel (song song) — tự động song song hóa
// 4. Functional (hàm) — không có side effect
```

### Kinh nghiệm Production

**Tình huống thực tế: StackOverflowError trong production**
- Phân tích cú pháp JSON lồng nhau sâu → đệ quy 10,000+ cấp
- `-Xss` = 1 MB → StackOverflowError
- Giải pháp:
  1. Tăng `-Xss` lên 2 MB (tạm thời)
  2. Viết lại parser theo kiểu lặp (iterative) (vĩnh viễn)

**Tình huống thực tế: Virtual Threads đã cứu server**
- REST API: 10,000 request đồng thời
- Platform thread: 10,000 × 1 MB = 10 GB RAM cho các stack
- Virtual thread: 10,000 × ~2 KB = 20 MB trong Heap
- Tiết kiệm: 99.8% RAM!

### Best Practices

1. **Stream API** cho các phép biến đổi phức tạp
2. **StackWalker** để phân tích chuỗi lời gọi
3. **Tránh đệ quy sâu** — hãy dùng vòng lặp
4. **Virtual Threads** (Java 21+) cho các ứng dụng có tính đồng thời cao. Không dùng cho các tác vụ CPU-bound — chúng không đem lại lợi ích và còn thêm chi phí mount/unmount.
5. **Escape Analysis** giúp JIT tối ưu hóa việc cấp phát

### Tóm tắt cho Senior

- **Stack** = bộ nhớ thực thi bị phân mảnh, theo từng frame một
- **Virtual Threads** = stack nằm trong Heap → định kích thước động → hàng triệu luồng. Không dành cho các tác vụ CPU-bound.
- **StackWalker** = kiểm tra stack theo kiểu lười, +hiệu năng
- **Escape Analysis** = Stack Allocation + Lock Elision
- **TCO** không được hỗ trợ, nhưng **Method Inlining** giải quyết được vấn đề đó
- **Stream API** = Iterator lười với khả năng kết hợp (composability)

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Stack lưu trữ: các kiểu nguyên thủy cục bộ, các tham chiếu đến đối tượng, thông tin về lời gọi phương thức
- Mỗi luồng có Stack riêng (mặc định 1 MB, tham số `-Xss`)
- Stack frame: Local Variable Table + Operand Stack + Dynamic Linking + Return Address
- Khi phương thức kết thúc, frame bị loại bỏ ngay lập tức — không cần GC
- Virtual Threads (Java 21+): stack nằm trong Heap dưới dạng đối tượng, ~2 KB thay vì 1 MB
- JIT có thể cấp phát đối tượng trên Stack thông qua Escape Analysis nếu nó không "thoát" ra ngoài
- Java không hỗ trợ Tail Call Optimization trực tiếp, nhưng JIT thực hiện Method Inlining

**Các câu hỏi phụ thường gặp:**
- **Điều gì xảy ra khi đệ quy vô hạn?** — `StackOverflowError`, Stack bị tràn
- **Tại sao Virtual Threads cho phép hàng triệu luồng?** — Stack nằm trong Heap, kích thước động (~2 KB so với 1 MB cố định)
- **Có thể thay đổi kích thước Stack khi đang chạy không?** — Không, `-Xss` được thiết lập khi JVM khởi động. Virtual Threads giải quyết điều này bằng cách định kích thước động.
- **Operand Stack là gì?** — Stack toán hạng bên trong frame dành cho các lệnh byte-code (push/pop/add)

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Các đối tượng được lưu trong Stack" — chỉ có tham chiếu đến đối tượng được lưu trong Stack
- "Stack được chia sẻ giữa tất cả các luồng" — Stack là riêng tư cho mỗi luồng
- "Java hỗ trợ TCO" — Java KHÔNG hỗ trợ Tail Call Optimization
