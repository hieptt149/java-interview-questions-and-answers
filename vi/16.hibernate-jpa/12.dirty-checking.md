# What is Dirty Checking in Hibernate (Dirty checking trong Hibernate là gì)

## Overview

Dirty checking là một cơ chế tự động theo dõi các thay đổi của entity trong persistence context và lưu chúng vào database. Đây là một trong những tính năng chính của Hibernate giúp loại bỏ nhu cầu viết truy vấn UPDATE thủ công.

---

## Junior Level

### Dirty Checking Là Gì

Dirty checking - Hibernate tự động **theo dõi các thay đổi** của entity trong persistence context và tự động tạo ra một truy vấn UPDATE khi lưu.

```java
@Transactional
public void updateUser(Long id, String name) {
    // 1. Tải từ DB - entity trở thành Persistent
    User user = entityManager.find(User.class, id);

    // 2. Thay đổi trường - Hibernate "nhận thấy" thay đổi
    user.setName(name);

    // 3. KHÔNG cần em.merge() hoặc em.save()!
    // Khi commit - Hibernate tự động thực hiện UPDATE
}
```

### Cách Hoạt Động - Đơn Giản

```
1. Tải: Hibernate tải entity và lưu "snapshot" của nó
2. Thay đổi: bạn sửa đổi một trường trong object
3. Flush: Hibernate so sánh snapshot với trạng thái hiện tại
4. Nếu khác nhau -> tạo ra UPDATE SQL
5. Nếu giống nhau -> không làm gì cả
```

### Ví Dụ

```java
@Transactional
public void updateEmail(Long userId, String newEmail) {
    User user = entityManager.find(User.class, userId);  // snapshot
    user.setEmail(newEmail);                              // thay đổi
    // Khi thoát phương thức -> commit -> flush -> UPDATE
}

// SQL tương đương:
// UPDATE users SET email = ? WHERE id = ?
```

## Middle Level

### Cơ Chế Dirty Checking Chi Tiết

```
Bước 1: Tải entity
- entityManager.find(User.class, 1L)
- Hibernate tạo EntityEntry với snapshot
- snapshot = bản sao của tất cả các trường tại thời điểm tải

Bước 2: Thay đổi
- user.setName("New Name")
- Hibernate KHÔNG làm gì ngay lập tức

Bước 3: Flush (khi commit hoặc rõ ràng)
- Hibernate duyệt qua tất cả entity trong persistence context
- Với mỗi cái: so sánh snapshot với trạng thái hiện tại
- Nếu tìm thấy thay đổi -> lên lịch UPDATE
- Thực thi tất cả các UPDATE vào DB
- Cập nhật snapshot
```

### Khi Nào Flush Xảy Ra

```java
// 1. Khi commit transaction (tự động)
@Transactional
public void update() {
    user.setName("New");
}  // commit -> flush -> UPDATE

// 2. Khi entityManager.flush() (rõ ràng)
entityManager.flush();  // UPDATE được thực thi

// 3. Trước khi thực thi một truy vấn (để trả về dữ liệu thực tế)
user.setName("New");
List<User> users = entityManager.createQuery("FROM User", User.class)
    .getResultList();  // flush xảy ra trước cái này!
```

### Tối Ưu - Entity Chỉ Đọc

```java
// Nếu entity sẽ không bị sửa đổi - đánh dấu là read-only
@Query("SELECT u FROM User u WHERE u.id = :id")
@Lock(LockModeType.OPTIMISTIC)
User findReadOnly(@Param("id") Long id);

// Hoặc thông qua hint
User user = entityManager.createQuery("FROM User u WHERE u.id = :id", User.class)
    .setParameter("id", id)
    .setHint("org.hibernate.readOnly", true)
    .getSingleResult();

// Ưu điểm:
// 1. Không tạo snapshot (tiết kiệm bộ nhớ)
// 2. Dirty checking không thực thi
// 3. Ít overhead flush hơn
```

### Các Lỗi Thường Gặp

```java
// UPDATE thừa
user.setName(user.getName());  // giá trị không đổi
// Hibernate sẽ dirty check, không tìm thấy thay đổi, và bỏ qua UPDATE. Tuy nhiên bản thân việc kiểm tra có overhead cho mỗi trường - với 10k entity đây là hàng triệu phép so sánh.

// Dirty checking cho các context lớn
@Transactional
public void processAll() {
    List<User> users = userRepository.findAll();  // 10k user
    for (User user : users) {
        // dirty checking cho 10k entity - chậm!
        processUser(user);
    }
}

// Giải pháp: clear định kỳ
@Transactional
public void processAll() {
    List<User> users = userRepository.findAll();
    for (int i = 0; i < users.size(); i++) {
        processUser(users.get(i));
        if (i % 100 == 0) {
            entityManager.flush();
            entityManager.clear();  // reset dirty checking
        }
    }
}
```

## Senior Level

### Triển Khai Nội Bộ

```
PersistenceContext:

StatefulPersistenceContext {
    entityEntries: Map<Object, EntityEntry>
}

EntityEntry {
    loadedState: Object[]    // snapshot khi tải
    state: Object[]          // trạng thái hiện tại
    status: Status          // MANAGED, DELETED, READ_ONLY
    id: Serializable
    version: Object
}

Thuật toán flush:
1. Với mỗi entity trong entityEntries:
   if entity.status == MANAGED:
     if !Arrays.equals(entry.loadedState, entry.state):
       scheduleUpdate(entity)
2. Thực thi tất cả các UPDATE đã lên lịch
3. Cập nhật loadedState = state
```

### Đặc Tính Hiệu Năng

```
Overhead của dirty checking:
- O(N) trong đó N = số lượng entity trong persistence context
- Với mỗi entity: so sánh mảng của tất cả các trường
- Với 10k+ entity - có thể chậm đáng kể

Tối ưu:
- read-only hint -> O(0) (bỏ qua entity)
- clear() định kỳ -> giảm N
- StatelessSession -> không có dirty checking
```

### @SelectBeforeUpdate

```java
@Entity
@SelectBeforeUpdate(true)
public class User {
    // Trước UPDATE, Hibernate thực hiện một SELECT
    // Để kiểm tra xem dữ liệu có thực sự thay đổi không
    // Hữu ích khi entity thường "được cập nhật" mà không có thay đổi thực sự
}
```

Đánh đổi: một SELECT thêm để tránh một UPDATE không cần thiết. Có lợi khi
entity thường "được lưu" mà không có thay đổi thực sự và UPDATE tốn kém
(trigger, auditing).

### Batch Update

```java
@Transactional
public void batchUpdate(List<User> users) {
    for (int i = 0; i < users.size(); i++) {
        User managed = entityManager.merge(users.get(i));
        managed.setStatus("processed");

        if (i % 50 == 0) {
            entityManager.flush();    // thực thi UPDATE
            entityManager.clear();    // xóa context
        }
    }
}
```

### Best Practices

```
Dirty checking cho cập nhật đơn giản
Read-only hint cho truy vấn chỉ đọc
entityManager.clear() cho các thao tác lớn
Hiểu khi nào flush xảy ra
Flush + clear định kỳ trong các thao tác batch

Dirty checking cho persistence context lớn
Không có read-only hint khi không cần cập nhật
Bỏ qua tác động hiệu năng
UPDATE thủ công khi dirty checking là đủ
```

## Interview Cheat Sheet

**Cần phải biết:**
- Dirty checking - Hibernate tự động theo dõi thay đổi của các entity managed
- Khi tải, một snapshot được lưu; khi flush, so sánh với trạng thái hiện tại
- Không cần merge() hoặc save() rõ ràng để cập nhật entity managed
- Overhead O(N) trong đó N = số lượng entity trong persistence context
- Flush xảy ra khi: commit, entityManager.flush(), trước truy vấn
- Read-only hint tiết kiệm bộ nhớ - không tạo snapshot, dirty checking bị bỏ qua

**Các câu hỏi phụ thường gặp:**
- **Khi nào UPDATE xảy ra?** Khi flush: snapshot != trạng thái hiện tại -> UPDATE SQL được tạo
- **Tại sao dirty checking chậm với 10k+ entity?** So sánh mảng O(N) cho mỗi trường của mỗi entity
- **@SelectBeforeUpdate là gì?** SELECT trước UPDATE để kiểm tra dữ liệu có thay đổi không - đánh đổi: SELECT vs UPDATE không cần thiết
- **Cách tối ưu?** Read-only hint, clear() định kỳ, StatelessSession cho các thao tác bulk

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi luôn gọi merge() sau khi thay đổi" - không cần thiết cho managed, SELECT thừa
- "Dirty checking cho 100k entity mà không có clear" - overhead O(N), sẽ chậm
- "Không có read-only hint cho report" - overhead snapshot và dirty checking không cần thiết
- "Tôi không hiểu khi nào flush xảy ra" - quan trọng cho transaction
