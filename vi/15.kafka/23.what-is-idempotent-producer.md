# What is idempotent producer (Idempotent producer là gì)

## Junior Level

### Định Nghĩa

**Idempotent producer** — một producer đảm bảo rằng **các trùng lặp sẽ không vào Kafka** khi retry.

```java
props.put("enable.idempotence", "true");
// Tự động đặt:
// acks=all
// retries=Integer.MAX_VALUE
// max.in.flight.requests.per.connection=5
```

### Tại Sao Cần Đến Nó?

```
Không có idempotence:
  Producer gửi → lỗi network → retry → trùng lặp trong Kafka

Có idempotence:
  Producer gửi → lỗi network → retry → broker từ chối trùng lặp
```

### Nó Hoạt Động Như Thế Nào?

```
Mỗi producer nhận một PID (Producer ID) duy nhất
Mỗi message nhận một Sequence Number
Broker theo dõi sequence

Trùng lặp với cùng PID + Sequence → bị từ chối
```

## Middle Level

### Khi Nào KHÔNG Nên Dùng Idempotent Producer

1. **Tương thích với các broker cũ** (trước 0.11) — idempotence không được hỗ trợ
2. **Latency cực thấp với trùng lặp chấp nhận được** — có thể tắt để giảm overhead tối thiểu

### Cơ Chế Nội Bộ

```
PID (Producer ID) — ID producer duy nhất
Sequence Number — tăng lên cho mỗi message
Broker kiểm tra sequence:
  - Nếu sequence = mong đợi → ghi
  - Nếu sequence < mong đợi → trùng lặp, từ chối
  - Nếu sequence > mong đợi → không đúng thứ tự, lỗi
```

### Các Cài Đặt Tự Động

```
enable.idempotence=true tự động đặt:
  acks=all
  retries=Integer.MAX_VALUE
  max.in.flight.requests.per.connection=5 (từ Kafka 1.1, trước đó bị giới hạn ở 1).

Không cần cấu hình thủ công!
```

### Transactional Producer

```java
// Cho exactly-once semantics
props.put("transactional.id", "my-tx-id");
props.put("enable.idempotence", "true");

producer.initTransactions();
producer.beginTransaction();
producer.send(record);
producer.commitTransaction();
```

### Các Lỗi Thường Gặp

1. **Không có idempotence khi dùng retry:**
```
Retry → trùng lặp trong topic
→ Xử lý hai lần
```

2. **Sửa đổi PID thủ công:**
```
PID được sinh ra tự động
Các thay đổi thủ công sẽ phá vỡ cơ chế
```

3. **enable.idempotence=false với retry:**
```
Retry được bật, idempotence bị tắt
→ Trùng lặp khi retry
```

## Senior Level

### Cài Đặt Nội Bộ

**Gán PID:**
```
Khi tạo một producer:
1. Producer → request InitProducerId → Broker
2. Broker → sinh ra PID duy nhất
3. Broker → trả về PID + epoch
4. Producer → dùng PID cho tất cả các message
```

**Quản Lý Sequence Number:**
```
Mỗi cặp producer-partition có số sequence riêng của nó:
  Producer P1, Partition 0 → seq=0
  Producer P1, Partition 0 → seq=1
  Producer P1, Partition 1 → seq=0 (partition khác)

Số sequence tăng lên theo mỗi message
```

**Xác Thực Của Broker:**
```
Broker kiểm tra:
1. PID khớp với producer hiện tại
2. Số sequence = mong đợi (không nhỏ hơn)
3. Nếu sequence < mong đợi → trùng lặp, từ chối
4. Nếu sequence > mong đợi → không đúng thứ tự, lỗi
```

### Exactly-Once Semantics

```
Idempotent producer là nền tảng của exactly-once:
1. Producer: enable.idempotence=true
2. Producer: transactional.id (cho các transaction)
3. Consumer: isolation.level=read_committed

Chỉ cho các kịch bản Kafka-to-Kafka!
```

### Các Kịch Bản Lỗi

**1. Restart Producer:**
```
Producer restart → PID mới
Các số sequence cũ không ảnh hưởng
Producer mới bắt đầu với sequence=0
```

**2. Broker Failover:**
```
Leader dừng hoạt động → leader mới
Leader mới biết số sequence cuối cùng
Tiếp tục xác thực từ cùng điểm đó
```

**3. Network Partition:**
```
Producer → đã gửi → lỗi network → retry
Broker đã nhận → đã ghi → ack bị mất
Producer → retry → broker thấy trùng lặp → từ chối
```

### Tác Động Hiệu Năng

```
Overhead idempotent producer:
  Tăng ~5-10% latency
  Giảm ~5% throughput
  Overhead CPU tối thiểu

Đánh đổi: độ tin cậy vs hiệu năng
```

### Monitoring

**Các metrics chính:**
```
kafka.producer:produce-throttle-time-avg
kafka.producer:failed-authentication-rate
kafka.producer:idempotent-rate (nếu có)
```

### Các Thực Hành Tốt Nhất

```
✅ enable.idempotence=true theo mặc định (Kafka 3.0+); với các phiên bản cũ hơn, đặt nó rõ ràng.
✅ Cho exactly-once — thêm transactional.id
✅ Không thay đổi các cài đặt mặc định
✅ Giám sát các lần gửi thất bại

❌ Không có idempotence khi dùng retry
❌ Sửa đổi PID thủ công
❌ enable.idempotence=false với retry
❌ Không có xử lý các lỗi gửi
```

### Các Quyết Định Kiến Trúc

1. **Idempotence theo mặc định** — overhead tối thiểu, độ tin cậy tối đa
2. **Transactional ID cho exactly-once** — các kịch bản Kafka-to-Kafka
3. **Các số sequence mỗi partition** — xác thực độc lập
4. **Xác thực phía broker** — bảo vệ khỏi trùng lặp ở phía broker

### Tóm Tắt Cho Senior

- Idempotent producer ngăn chặn trùng lặp khi retry
- PID + Sequence Number — cơ chế loại bỏ trùng lặp
- Tự động đặt acks=all và retries=INT_MAX
- Exactly-once yêu cầu transactional.id
- Overhead hiệu năng tối thiểu, lợi ích độ tin cậy tối đa

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- Idempotent producer đảm bảo: các trùng lặp sẽ không vào Kafka khi retry
- PID (Producer ID) + Sequence Number — cơ chế loại bỏ trùng lặp phía broker
- `enable.idempotence=true` tự động đặt: acks=all, retries=INT_MAX, max.in.flight=5
- Broker kiểm tra sequence: nếu < mong đợi → từ chối trùng lặp; nếu > → lỗi không đúng thứ tự
- Số sequence mỗi partition — xác thực độc lập cho mỗi partition
- Cho exactly-once: thêm `transactional.id` + Transaction API
- Overhead: tăng ~5-10% latency, giảm ~5% throughput — tối thiểu

**Các câu hỏi phụ thường gặp:**
- *Điều gì xảy ra nếu không có idempotence khi retry?* — Retry → trùng lặp trong topic → xử lý hai lần.
- *PID có được sinh ra thủ công không?* — Không, tự động bởi broker khi tạo producer.
- *Broker xử lý failover như thế nào?* — Leader mới biết số sequence cuối cùng và tiếp tục xác thực.
- *enable.idempotence=false với retry — điều gì xảy ra?* — Retry được bật, trùng lặp có thể xảy ra.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Idempotent producer có thể tắt cho production" — retry không có idempotence = trùng lặp
- "PID có thể được cấu hình thủ công" — được sinh ra tự động bởi broker
- "Idempotence bảo vệ khỏi trùng lặp giữa các producer khác nhau" — chỉ trong một producer
- "Exactly-once hoạt động mà không cần transactional.id" — cần transactional.id cho các transaction
