# What Anti-patterns Contradict SOLID Principles? (Những anti-pattern nào mâu thuẫn với các nguyên tắc SOLID)

## 🟢 Junior Level

**Anti-pattern** là những lỗi thiết kế điển hình có vẻ tiện lợi ngay bây giờ nhưng tạo ra các vấn đề lớn sau này. Hầu hết chúng trực tiếp mâu thuẫn với các nguyên tắc SOLID.

Hãy tưởng tượng xây một ngôi nhà: một anti-pattern là khi tất cả dây điện từ các ổ cắm đều dẫn đến một hộp nối duy nhất. Nó hoạt động ngày hôm nay, nhưng nếu bạn cần thêm một ổ cắm mới — bạn sẽ phải làm lại mọi thứ.

### Các Anti-pattern Chính

**1. God Object**
Một class làm mọi thứ: làm việc với DB, gửi email, tạo báo cáo, xử lý thanh toán.
- **Vi phạm**: SRP — class có quá nhiều trách nhiệm
- **Dấu hiệu**: Một class với 1000+ dòng và 30+ dependency

```java
// God Object — làm MỌI THỨ
public class ApplicationManager {
    public void createUser(User user) { /* ... */ }
    public void sendEmail(User user) { /* ... */ }
    public void generateReport() { /* ... */ }
    public void processPayment(BigDecimal amount) { /* ... */ }
    public void connectToDatabase() { /* ... */ }
    // 50 phương thức nữa...
}
```

**2. Anemic Domain Model**
Các class entity chỉ chứa trường và getter/setter, trong khi tất cả logic được chuyển sang các service khổng lồ.
- **Vi phạm**: Encapsulation — dữ liệu và logic bị tách rời

```java
// Anemic model — chỉ dữ liệu, không có logic
public class Order {
    private Long id;
    private BigDecimal total;
    private List<OrderItem> items;
    // chỉ getter và setter
}

// Tất cả logic ở đây
public class OrderService {
    public BigDecimal calculateTotal(Order order) { /* ... */ }
    public void addItem(Order order, OrderItem item) { /* ... */ }
    public boolean isValid(Order order) { /* ... */ }
}
```

**3. Feature Envy**
Một phương thức của class A liên tục truy cập dữ liệu và phương thức của class B. Nó "ghen tị" với class B và nên thuộc về nó.
- **Vi phạm**: Encapsulation và SRP

```java
// Feature Envy: phương thức phụ thuộc vào dữ liệu của class khác
public class OrderReport {
    public String formatOrder(Order order) {
        return "Order #" + order.getId()
            + " Total: " + order.getTotal()
            + " Items: " + order.getItems().size()
            + " Customer: " + order.getCustomer().getName();
    }
}
// Phương thức này "ghen tị" với Order và nên nằm trong đó
```

**4. Circular Dependency**
Service A phụ thuộc vào B, và B phụ thuộc vào A.
- **Vi phạm**: DIP — không thể sử dụng các module một cách độc lập

```java
// Circular Dependency: A → B → A
@Service
public class OrderService {
    private final PaymentService paymentService; // phụ thuộc vào PaymentService
}

@Service
public class PaymentService {
    private final OrderService orderService; // phụ thuộc vào OrderService
}
```

### Khi Nào Điều Này Xảy Ra

- Trong các startup phát triển nhanh không có code review
- Khi developer không biết SOLID
- Khi "chúng ta sẽ refactor sau" không bao giờ đến

## 🟡 Middle Level

### STUPID — Từ Trái Nghĩa Của SOLID (từ ghi nhớ mô tả các anti-pattern đối lập với SOLID)

| STUPID                     | Mô Tả                                     | Vi Phạm SOLID            |
| -------------------------- | ----------------------------------------------- | -------------------------- |
| **S**ingleton              | Trạng thái toàn cục cản trở việc test               | DIP                       |
| **T**ight Coupling         | Sự kết nối module chặt chẽ                          | DIP, SRP                  |
| **U**ntestability          | Không thể test cô lập                     | DIP                       |
| **P**remature Optimization | Tối ưu hóa trước khi tìm ra nút thắt cổ chai thực sự    | OCP                       |
| **I**ndistinct Names       | Tên class và phương thức không rõ ràng                  | SRP                       |
| **D**uplication            | Trùng lặp code                                | DRY (họ hàng của SOLID)    |

### Big Ball of Mud

Một hệ thống không có kiến trúc rõ ràng, nơi các dependency rối rắm một cách hỗn loạn.
- **Vi phạm**: Tất cả các nguyên tắc SOLID
- **Dấu hiệu**: Dependency graph trông như một cuộn len rối
- **Cách chữa**: Pattern **Strangler Fig** — thay thế module dần dần

### Stovepipe System

Nhiều module độc lập, kết nối kém, trùng lặp chức năng của nhau và có định dạng dữ liệu riêng.
- **Vi phạm**: DIP và ISP
- **Hậu quả**: Không thể tích hợp và chi phí bảo trì khổng lồ

### Các Lỗi Thường Gặp

1. **Lỗi**: "Nó hoạt động, vậy nên kiến trúc ổn."
   **Giải pháp**: Hoạt động hôm nay — không có nghĩa nó sẽ hoạt động ngày mai. Đánh giá chi phí thêm một tính năng mới.

2. **Lỗi**: "God Object chỉ là một class trung tâm tiện lợi."
   **Giải pháp**: Nếu một class biết về DB, email, PDF, và thanh toán — nó trở thành một điểm lỗi duy nhất và một nút thắt cổ chai.

3. **Lỗi**: "Circular Dependency — Spring sẽ xử lý nó thông qua proxy."
   **Giải pháp**: Spring thực sự tạo proxy, nhưng điều này che giấu vấn đề. Dùng cách tiếp cận event-driven hoặc trích xuất một interface chung.

### Khi Nào KHÔNG Nên Chống Lại Anti-pattern

- **Legacy đang bảo trì**: Nếu hệ thống sẽ sớm được thay thế, refactoring sẽ không đáng
- **Prototype**: Đối với MVP, tốc độ quan trọng hơn kiến trúc
- **Script một lần**: Một tiện ích cho việc nhập dữ liệu một lần

### So Sánh Anti-pattern

| Anti-pattern          | Độ Khó Phát Hiện           | Độ Khó Sửa         | Tác Động Đến Team                    |
| --------------------- | ------------------------------ | -------------------------- | ------------------------------ |
| God Object            | Dễ (theo kích thước class)           | Trung bình (refactoring)      | Chặn công việc song song          |
| Anemic Model          | Trung bình (cần phân tích domain) | Cao (di chuyển logic)    | Service phát triển không kiểm soát  |
| Circular Dependency   | Dễ (lỗi khởi động)           | Trung bình (event/interface)  | Overhead proxy Spring         |
| Big Ball of Mud       | Dễ (cảm giác chung)           | Rất cao                 | Làm tê liệt sự phát triển            |
| Feature Envy          | Trung bình (cần phân tích tĩnh) | Thấp (di chuyển phương thức)     | Code khó hiểu                |

## 🔴 Senior Level

### Triển Khai Nội Bộ: Tại Sao Các Anti-pattern "Bám Dính"

**God Object Và Tải Nhận Thức:**
Bộ não con người có thể giữ 7+/-2 mục trong bộ nhớ làm việc. Một God Object với 50 phương thức và 30 trường vượt quá giới hạn này 5-10 lần. Developer tránh sửa đổi những gì họ không thể hiểu — code "đóng băng."

**Circular Dependency Và JVM Classloader:**
```
OrderService.class -> đang tải -> cần PaymentService
PaymentService.class -> đang tải -> cần OrderService
```
Spring giải quyết vấn đề này thông qua **CGLIB proxy**: tạo một subclass bao bọc. Nhưng điều này có nghĩa:
- Thêm indirection (gián tiếp) trên mỗi lời gọi (~1-3ns overhead)
- `this` bên trong phương thức tham chiếu đến proxy, không phải object thực
- `@Transactional` trên các phương thức như vậy có thể không hoạt động đúng (vấn đề proxy-self-invocation)

**Anemic Model Và ORM:**
Hibernate/JPA yêu cầu constructor không tham số, getter/setter, `equals`/`hashCode` theo ID. Điều này đẩy về phía anemic model. Nhưng đây không phải là "vi phạm" — đó là một **đánh đổi kiến trúc** giữa sự thuần khiết OOP và khả năng tương thích ORM.

### Đánh Đổi Kiến Trúc

**Anemic Domain Model:**
- Ưu điểm: Tương thích ORM (Hibernate); serialization đơn giản (JSON); dễ hiểu cho developer junior
- Nhược điểm: Business logic trải rộng trên các service; các service phát triển thành God Object; không có encapsulation của các bất biến (invariant)

**Rich Domain Model:**
- Ưu điểm: Logic gần dữ liệu; các bất biến được bảo vệ; khả năng test; tương thích DDD
- Nhược điểm: Độ phức tạp tích hợp ORM; cần một team trưởng thành; khó serialize hơn

**Chấp Nhận Anti-pattern (Thực Dụng):**
- Ưu điểm: Tốc độ phát triển; ít boilerplate hơn; onboarding đơn giản hơn
- Nhược điểm: Nợ kỹ thuật tăng lên; trong 2 năm — Big Ball of Mud; chi phí thay đổi tăng theo cấp số nhân

### Edge Cases

1. **Static Utility Class**: `Math`, `Collections`, `StringUtils` — về mặt hình thức vi phạm DIP (không thể thay thế triển khai). Nhưng chúng ổn định và độc lập với domain.
   **Giải pháp**: Chấp nhận như một ngoại lệ hợp lệ. Chúng không thay đổi và không mang trạng thái.

2. **Annotation Framework**: `@Entity`, `@Service`, `@RestController` — sự ràng buộc framework vi phạm DIP. Nhưng framework không hoạt động nếu không có chúng.
   **Giải pháp**: Cô lập annotation trong tầng Infrastructure. Domain Layer không nên phụ thuộc vào Spring/Hibernate.

3. **Class DTO**: Các class để truyền dữ liệu giữa các tầng. Về mặt hình thức — anemic model. Nhưng trách nhiệm duy nhất của chúng là vận chuyển.
   **Giải pháp**: Dùng record (Java 14+) cho DTO bất biến. Đây không phải là anti-pattern, đó là một pattern.

4. **God Object Một Phần**: Một class 5000 dòng trong đó 4000 dòng là code được sinh tự động (mapper, builder).
   **Giải pháp**: Loại trừ code được sinh tự động khỏi các metric. SonarQube hỗ trợ loại trừ annotation `@Generated`.

### Hiệu Năng

**God Object Và Contention:**
```
Request 1 -> GodObject.methodA() -> lock trên fieldX
Request 2 -> GodObject.methodB() -> lock trên fieldX (contention!)
```
God object thường trở thành các điểm đồng bộ hóa. Nếu 10 thread gọi các phương thức khác nhau của một object với trạng thái mutable chung — bạn sẽ gặp contention. Dưới contention cao, throughput giảm đáng kể.

**Speculative Generality Và Bộ Nhớ:**
Anti-pattern "abstraction dự phòng" (tạo interface và tầng cho các yêu cầu tương lai giả định) làm phình to hệ thống phân cấp class:
- Mỗi interface = class object trong metaspace (~1-3KB)
- 100 interface không dùng = ~100-300KB metaspace
- Mỗi factory = object bổ sung cho DI container
- Trong thực tế: các dự án có speculative generality có nhiều class hơn đáng kể, hầu hết chỉ có một triển khai

**Circular Dependency Và Thời Gian Khởi Động:**
Spring khi phát hiện circular dependency:
1. Thử constructor injection -> thất bại
2. Thử setter injection + CGLIB proxy -> thành công (kèm cảnh báo)
3. Việc tạo proxy thêm ~5-10ms mỗi dependency
4. Với 50 circular dependency — +250-500ms vào thời gian khởi động

### Kinh Nghiệm Production

**War Story: Hệ Thống Xử Lý Thanh Toán (2022)**

Startup fintech, xử lý 50K thanh toán/ngày. `PaymentManager` — God Object với 15,000 dòng, 89 dependency. Hoạt động trong 2 năm, sau đó:
- Thêm nhà cung cấp thanh toán mới: 3-4 tuần
- Bug regression: 5-7 mỗi release
- Merge conflict: hàng ngày
- Developer mới: 3 tháng để có PR đầu tiên

**Refactoring qua Strangler Fig:**
1. Trích xuất interface `PaymentProvider` từ các phương thức của `PaymentManager`
2. Dần dần di chuyển mỗi nhà cung cấp vào một class riêng biệt
3. Orchestrator trở thành một coordinator (300 dòng thay vì 15,000)
4. Kết quả: nhà cung cấp mới trong 2 ngày, 0 bug regression mỗi quý

**War Story: Hệ Thống Ngân Hàng Legacy (2024)**

Ngân hàng, core trên Java 8 (đã di chuyển lên 17). `TransactionProcessor` — Big Ball of Mud, 40,000 dòng. Dependency graph: 200+ class, mỗi class phụ thuộc vào mọi class khác.

**Chẩn đoán:**
```
Metric SonarQube:
- Technical Debt: ước tính bằng số năm công sức để sửa (metric có điều kiện)
- Cognitive Complexity: 450 (giới hạn 15)
- LCOM4: 12.0
- Circular Dependencies: 23
```

**Cách tiếp cận:**
1. Đóng băng `TransactionProcessor` — không thay đổi thêm
2. Xây dựng Strangler Fig xung quanh nó: `TransactionEngine` mới với SOLID sạch
3. API Gateway định tuyến: loại giao dịch mới -> engine mới, cũ -> legacy
4. Trong 8 tháng, di chuyển 100% traffic
5. Kết quả: Technical Debt giảm đáng kể

### Giám Sát Và Chẩn Đoán

- **Công Cụ Phân Tích Tĩnh**:
  - **SonarQube**: Cognitive Complexity, LCOM4, Số Lượng Dependency, Duplications
  - **PMD**: Phát hiện God Class, Excessive Imports, Coupling Between Objects
  - **Checkstyle**: Class Data Abstraction Coupling (CDAC)

- **ArchUnit** — kiểm tra tự động trong CI/CD:
```java
@ArchTest
static final ArchRule no_god_objects =
    noClasses()
        .that().resideInAPackage("..service..")
        .should().haveMoreThan(10Dependencies())
        .orShould().haveMoreThan(50Methods())
        .as("No God objects in service layer");

@ArchTest
static final ArchRule no_circular_dependencies =
    slices()
        .matching("com.company.(*)..")
        .should().beFreeOfCycles()
        .as("No circular dependencies between modules");

@ArchTest
static final ArchRule no_feature_envy =
    noClasses()
        .that().haveSimpleNameEndingWith("Service")
        .should().accessClassesThat().haveSimpleNameEndingWith("Entity")
        .moreThan(3)
        .as("Services should not envy entities too much");
```

- **Trực Quan Hóa Dependency Graph**:
  - **JDepend**: Metric coupling và abstraction
  - **IntelliJ IDEA Dependency Matrix**: Đồ thị trực quan
  - **Structure101**: Tự động phát hiện chu trình và vi phạm tầng

- **Các Metric Chính**:
| Metric                 | Bình Thường  | Nghiêm Trọng   |
| ---------------------- | ------- | ---------- |
| Dependency mỗi class | <= 10   | > 20       |
| LCOM4                  | <= 1    | > 3        |
| Cognitive Complexity   | <= 15   | > 50       |
| Circular dependency  | 0       | > 3        |
| Kích thước class (dòng)     | <= 300  | > 1000     |

### Best Practices Cho Highload

- **Immutability Mặc Định**: God Object hầu như luôn có trạng thái mutable chung. Làm cho object bất biến — điều này tự động ngăn contention.
- **Event-Driven Decoupling**: Thay vì dependency trực tiếp giữa các service, dùng event bus (Kafka, Spring Events). Điều này phá vỡ circular dependency.
- **Bounded Contexts (DDD)**: Chia hệ thống theo ngữ cảnh business. God Object vi phạm ranh giới — không cho phép gọi trực tiếp giữa các ngữ cảnh.
- **Feature Flags Cho Strangler Fig**: Khi refactor một God Object, giữ cả code cũ và mới đồng thời. Chuyển đổi qua feature flag, không phải qua deployment.

### Xu Hướng Tương Lai

- **AI-assisted Refactoring**: Các công cụ hiện đại (IntelliJ IDEA AI Assistant, CodeRabbit) tự động gợi ý chia God Object dựa trên phân tích đồng định vị phương thức.
- **Module System Enforcement (JPMS)**: `module-info.java` của Java 9+ chính thức hóa các dependency. Circular dependency trở thành lỗi compile-time, không phải vấn đề runtime.
- **ArchUnit as Code**: Test kiến trúc trở thành công dân hạng nhất trong CI/CD. Phát hiện anti-pattern — không phải ý kiến code review, mà là một test thất bại.

## Tóm Tắt

- Anti-pattern là triệu chứng của "thiết kế thối rữa." Hầu hết chúng là vi phạm trực tiếp SOLID.
- **Anemic Domain Model** — anti-pattern phổ biến và gây tranh cãi nhất trong Java Enterprise.
- Chống lại code **STUPID** thông qua văn hóa Code Review và phân tích tĩnh tự động.
- SOLID — không phải một tôn giáo, mà là thuốc chống lại anti-pattern. Áp dụng một cách thực dụng.
- Cách tốt nhất để chống lại Big Ball of Mud là **ngăn chặn** nó xuất hiện.

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- STUPID — từ trái nghĩa của SOLID: Singleton, Tight Coupling, Untestability, Premature Optimization, Indistinct Names, Duplication
- God Object — một class làm mọi thứ, vi phạm SRP, >1000 dòng, >30 dependency
- Anemic Domain Model — chỉ dữ liệu, không có logic; tất cả logic trong các service khổng lồ
- Circular Dependency — Spring giải quyết qua CGLIB proxy, nhưng điều này che giấu vấn đề thiết kế
- Big Ball of Mud — hệ thống không có kiến trúc, chữa bằng Strangler Fig (thay thế dần dần)
- Feature Envy — phương thức của class A liên tục truy cập dữ liệu của class B; nên nằm trong B
- Speculative Generality — "abstraction dự phòng," làm phình to hệ thống phân cấp mà không có lợi ích

**Các câu hỏi phụ thường gặp:**
- **Tại sao Circular Dependency là một vấn đề?** — CGLIB proxy: overhead +1-3ns, `this` = proxy không phải object thực, `@Transactional` có thể không hoạt động đúng
- **Anemic Model luôn xấu?** — Không, đối với ORM (Hibernate) — đó là một đánh đổi; cô lập trong Data Access Layer
- **Cách refactor Big Ball of Mud?** — Đóng băng code cũ -> Strangler Fig xung quanh nó -> API Gateway định tuyến -> di chuyển dần dần
- **Metric anti-pattern?** — Dependencies > 20, LCOM4 > 3, Cognitive Complexity > 50, Kích thước class > 1000 dòng

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Nó hoạt động, vậy nên kiến trúc ổn" (hoạt động hôm nay — không có nghĩa có thể bảo trì ngày mai)
- "Circular Dependency — Spring sẽ xử lý nó thông qua proxy" (che giấu vấn đề, overhead proxy)
- "God Object — một class trung tâm tiện lợi" (điểm lỗi duy nhất, nút thắt cổ chai, không thể test)
