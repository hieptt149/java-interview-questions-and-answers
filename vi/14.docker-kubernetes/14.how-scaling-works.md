# How does scaling work in Kubernetes? (Scaling hoạt động như thế nào trong Kubernetes?)

---

## Junior Level

### Giải Thích Đơn Giản

**Scaling** là quá trình thay đổi lượng tài nguyên được cấp cho một ứng dụng. Trong Kubernetes, bạn có thể scale ở hai cấp độ:

1. **Nhiều bản sao ứng dụng hơn** (ngang - horizontal) — khởi chạy thêm các Pod
2. **Nhiều tài nguyên hơn cho một Pod** (dọc - vertical) — cấp thêm CPU/RAM

### Scaling Ngang (Nhiều Bản Sao Hơn)

```
1 bản sao:     [App]          ← 100 req/s → chậm lại
3 bản sao:   [App] [App] [App]  ← 100 req/s → hoạt động nhanh
```

Đây là cách tiếp cận phổ biến nhất. Nhiều bản sao hơn = xử lý được nhiều request hơn.

### Scaling Dọc (Nhiều Tài Nguyên Hơn)

```
RAM thấp:    [App: 256MB]   ← OutOfMemoryError
RAM cao:   [App: 1GB]     ← hoạt động bình thường
```

Cách tiếp cận ít phổ biến hơn. Không phải ứng dụng nào cũng có thể dùng hiệu quả nhiều tài nguyên hơn.

### Scale Thủ Công

```bash
# Tăng số lượng replica lên 5
kubectl scale deployment myapp --replicas=5

# Kiểm tra
kubectl get deployment myapp
```

### Scale Tự Động

Kubernetes có thể tự động thay đổi số lượng replica:
- **HPA** (Horizontal Pod Autoscaler) — dựa trên CPU hoặc các metrics khác
- **Cluster Autoscaler** — thêm server (Node) khi tài nguyên không đủ

### Những Gì Một Junior Developer Nên Nhớ

- Horizontal = nhiều bản sao hơn (cách tiếp cận phổ biến nhất)
- Vertical = nhiều tài nguyên hơn mỗi Pod
- Thủ công: `kubectl scale deployment --replicas=N`
- Tự động: HPA theo CPU, Cluster Autoscaler theo Node
- HPA yêu cầu Requests (tài nguyên tối thiểu) phải được chỉ định

## Middle Level

### Các Loại Scaling

#### HPA — Horizontal Pod Autoscaler

HPA không hoạt động tốt với các workload stateful (cơ sở dữ liệu) — các Pod mới không có dữ liệu. Với các ứng dụng stateful, hãy dùng StatefulSet + scale thủ công.

Thay đổi số lượng replica Pod:
```bash
# HPA: duy trì ~50% mức sử dụng CPU
kubectl autoscale deployment myapp --cpu-percent=50 --min=2 --max=10
```

Các nguồn metrics:
- **Resource metrics**: CPU, Memory (từ Metrics Server)
- **Custom metrics**: các metrics kinh doanh từ Prometheus
- **External metrics**: các hàng đợi bên ngoài (AWS SQS, RabbitMQ)

#### VPA — Vertical Pod Autoscaler

VPA (Vertical Pod Autoscaler) — tự động điều chỉnh các request CPU/RAM cho các Pod.

Thay đổi các request và limit CPU/RAM của một Pod:
- Yêu cầu Pod restart để áp dụng
- Hữu ích để tìm các resource request tối ưu
- **Không khuyến nghị** dùng cùng với HPA trên CPU

#### Cluster Autoscaler

Thêm/loại bỏ các Node trong cluster:
- Nếu các Pod ở trạng thái Pending (không đủ tài nguyên) → thêm Node
- Nếu các Node ít được sử dụng → loại bỏ chúng để tiết kiệm chi phí

### HPA Đưa Ra Quyết Định Như Thế Nào?

Công thức:
```
desiredReplicas = ceil[currentReplicas × (currentMetricValue / desiredMetricValue)]
```

Ví dụ:
- CPU mong muốn: 50%
- CPU hiện tại: 100%
- Replica hiện tại: 2
- Quyết định: ceil[2 × (100/50)] = 4 replica

### Các Yêu Cầu Để HPA Hoạt Động

1. **Metrics Server** phải được cài đặt
2. **Requests** phải được chỉ định trong Pod (HPA tính phần trăm từ Requests)

```yaml
resources:
  requests:
    cpu: "500m"     # Bắt buộc cho HPA
    memory: "256Mi"
  limits:
    cpu: "1"
    memory: "512Mi"
```

### Vấn Đề "Race Condition"

Nếu HPA phản ứng quá nhanh với các đợt tăng đột biến, hệ thống rơi vào dao động (oscillation):
- CPU tăng đột biến → HPA thêm Pod → tải giảm → HPA loại bỏ Pod → tăng đột biến lại

**Giải pháp:** Cấu hình các khoảng thời gian cooldown (behavior trong HPA).

### Những Gì Một Middle Developer Nên Nhớ

- HPA — phương pháp scaling chính
- VPA — để tinh chỉnh tài nguyên (không cùng với HPA)
- Cluster Autoscaler — để quản lý dung lượng cluster
- HPA yêu cầu Metrics Server và Resource Requests
- Cấu hình cooldown để tránh dao động

## Senior Level

### Scaling Như Một Chiến Lược Kiến Trúc

Scaling trong Kubernetes không chỉ là "thêm nhiều Pod hơn" — đó là một **chiến lược đa cấp độ** ảnh hưởng đến kiến trúc ứng dụng, chi phí hạ tầng, và SLA.

### Bức Tranh Scaling Đầy Đủ

```
Cấp độ ứng dụng:
├── HPA (ngang): nhiều replica hơn
└── VPA (dọc): nhiều tài nguyên hơn

Cấp độ cluster:
├── Cluster Autoscaler: nhiều Node hơn
└── Karpenter: tối ưu hóa loại instance

Cấp độ tải:
├── Dựa trên tài nguyên: CPU, Memory
├── Custom metrics: RPS, độ dài hàng đợi, latency
└── External: các metrics kinh doanh
```

### HPA: Cấu Hình Nâng Cao

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapp-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  minReplicas: 2
  maxReplicas: 20
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 60
  - type: Resource
    resource:
      name: memory
      target:
        type: AverageValue
        averageValue: 512Mi
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60
      policies:
      - type: Pods
        value: 4
        periodSeconds: 60
    scaleDown:
      stabilizationWindowSeconds: 300
      policies:
      - type: Pods
        value: 1
        periodSeconds: 120
```

### Custom Metrics Cho HPA

```yaml
metrics:
- type: Pods
  pods:
    metric:
      name: http_requests_per_second
    target:
      type: AverageValue
      averageValue: "100"
```

Yêu cầu Prometheus Adapter để phơi bày metrics cho API K8s.

### KEDA: Autoscaling Dựa Trên Event

[KEDA](https://keda.sh) — scaling dựa trên event:

```yaml
triggers:
- type: kafka
  metadata:
    bootstrapServers: kafka:9092
    consumerGroup: mygroup
    topic: mytopic
    lagThreshold: "100"
```

Hỗ trợ: Kafka, RabbitMQ, Redis, AWS SQS, Azure Service Bus, và nhiều loại khác.

### Scale To Zero

**Knative + Kourier:**
- Không có lưu lượng → 0 replica
- Khi có request → khởi động nhanh (cold start ~100ms-2s)
- Lý tưởng cho các workload event-driven, serverless

Yêu cầu:
- Khởi động ứng dụng nhanh (GraalVM Native Image)
- Queue Proxy để đệm các request trong khi scale up

### VPA: Các Giới Hạn Và Xung Đột

**Không dùng với HPA trên CPU:**
- HPA muốn nhiều Pod hơn khi CPU cao
- VPA muốn nhiều CPU hơn mỗi Pod
- Xung đột → hành vi không thể dự đoán

**Khuyến nghị:**
- HPA cho các workload stateless (ngang)
- VPA cho các workload stateful/monolithic (dọc)
- VPA ở chế độ `Off` cho các khuyến nghị (nên đặt gì trong requests)

### Cluster Autoscaler vs Karpenter

| Đặc điểm    | Cluster Autoscaler | Karpenter                          |
| ----------------- | ------------------ | ---------------------------------- |
| Tốc độ             | Chậm (vài phút)     | Nhanh (vài giây)                     |
| Chọn instance| Giới hạn            | Được tối ưu hóa                          |
| Instance Spot    | Có                | Có (tốt hơn)                       |
| Nhà cung cấp          | Riêng cho từng cloud     | AWS (đa cloud đang phát triển)   |

### Kinh Tế Học Scaling

```
Không có autoscaling:
- Tải đỉnh: 100 replica (2 giờ mỗi ngày)
- Thời gian còn lại: 10 replica nhàn rỗi
- Chi phí: 100 × 24h

Với autoscaling:
- Đỉnh: 100 replica (2 giờ)
- Ngoài giờ đỉnh: 10 replica (22 giờ)
- Chi phí: 100×2h + 10×22h = ~30% tiết kiệm
```

### Xử Lý Sự Cố (Troubleshooting)

**HPA không scale:**
```bash
kubectl describe hpa myapp
# Conditions:
#   AbleToScale    False   SucceededRescale  (last transition: ...)
#   ScalingActive  False   FailedGetResourceMetric
```

Kiểm tra:
1. Metrics Server có đang chạy không?
2. Requests đã được chỉ định chưa?
3. Metrics có khả dụng không?

**Các Pod ở trạng thái Pending trong khi scale:**
- Không đủ tài nguyên trên các Node → Cluster Autoscaler nên kích hoạt
- Kiểm tra giới hạn quota: `kubectl describe resourcequota`

### Tóm Tắt Cho Senior

- HPA — để xử lý tải, VPA — để tinh chỉnh tài nguyên, CA — để quản lý dung lượng.
- Đừng dùng HPA và VPA đồng thời trên cùng một metric.
- Custom metrics (Prometheus Adapter) cho scaling hướng kinh doanh.
- KEDA cho scaling event-driven (Kafka, RabbitMQ, SQS).
- Scale-to-zero (Knative) cho các workload serverless.
- Các chính sách behavior kiểm soát tốc độ scale up/down, ngăn dao động.
- Karpenter nhanh hơn và thông minh hơn Cluster Autoscaler (AWS).
- Luôn cấu hình Resource Requests & Limits, nếu không autoscaling sẽ không hoạt động.

## Interview Cheat Sheet

**Cần phải biết:**
- HPA — ngang (nhiều Pod hơn), VPA — dọc (nhiều CPU/RAM hơn), CA — nhiều Node hơn
- Công thức HPA: `desiredReplicas = ceil[current × (currentMetric / desiredMetric)]`
- HPA yêu cầu Metrics Server và Resource Requests trong pod spec
- Đừng dùng HPA và VPA đồng thời trên cùng một metric (xung đột)
- Custom metrics (Prometheus Adapter) cho scaling hướng kinh doanh
- Các chính sách behavior (stabilization window) ngăn dao động
- KEDA — scaling event-driven (Kafka, RabbitMQ, SQS); Knative — scale-to-zero

**Các câu hỏi phụ thường gặp:**
- *"Tại sao HPA không hoạt động nếu không có requests?"* — HPA tính phần trăm từ requests; không có nó thì không có baseline
- *"Scaling dựa trên memory có phải là ý tưởng tốt không?"* — Không với Java (JVM không trả lại memory cho OS ngay lập tức)
- *"KEDA là gì?"* — Kubernetes Event-driven Autoscaling; scaling theo event (hàng đợi, stream)
- *"Karpenter vs Cluster Autoscaler?"* — Karpenter nhanh hơn, thông minh hơn khi chọn loại instance

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "HPA và VPA cùng nhau cho CPU" (chúng xung đột, hành vi không thể dự đoán)
- "Scale ứng dụng Java theo memory" (quản lý memory của JVM phá vỡ metric)
- "Cluster Autoscaler thay thế HPA" (CA thêm Node, HPA thêm Pod — các cấp độ khác nhau)
- "Đặt maxReplicas = 1000 mà không kiểm soát" (rủi ro chi phí khổng lồ)
