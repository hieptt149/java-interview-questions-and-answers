# How to organize REST API versioning? (Cách tổ chức versioning cho REST API?)

## Junior Level

**API versioning** (quản lý phiên bản API) là một cách để quản lý các thay đổi mà không làm hỏng các client hiện có.

### Tại sao cần versioning?
Khi bạn thay đổi một API (bỏ trường, đổi cấu trúc), các client cũ có thể ngừng hoạt động. Versioning cho phép hỗ trợ nhiều phiên bản cùng lúc.

### Các chiến lược chính:

**1. Phiên bản trong URL — cách tiếp cận phổ biến nhất trong ngành (GitHub, Stripe, AWS). Dễ định tuyến và debug nhất:**
```
/api/v1/users
/api/v2/users
```

**2. Phiên bản trong header:**
```
GET /users
Accept-Version: v2
```

**3. Phiên bản trong content type:**
```
GET /users
Accept: application/vnd.myapi.v2+json
```

### Thế nào là một thay đổi "phá vỡ" (Breaking Change)?
- Bỏ hoặc đổi tên trường
- Đổi cấu trúc (object trở thành array)
- Thêm trường bắt buộc mới
- Đổi kiểu dữ liệu (Integer → String)

## Middle Level

### Các chiến lược versioning

#### 1. URI Versioning (`/v1/users`)
- **Ưu:** Dễ cấu hình cache trên CDN. Logging và định tuyến đơn giản
- **Nhược:** URL thay đổi theo từng phiên bản mới

#### 2. Header Versioning (`Accept-Version: v2`)
- **Ưu:** Một endpoint phục vụ nhiều phiên bản khác nhau
- **Nhược:** Cần một header `Vary: Accept-Version`, nếu không cache sẽ trả V1 cho một người dùng V2

#### 3. Media Type Versioning (`Accept: application/vnd.myapi.v2+json`)
- **Ưu:** Gần nhất với tinh thần REST theo Roy Fielding (người tạo ra REST), vì nó dùng Content Negotiation. Tuy nhiên, trên thực tế nó hiếm khi được dùng do độ phức tạp khi debug.
- **Nhược:** Khó hiện thực và debug hơn

### Contract Testing (Pact)

Trong microservice, versioning thường được thay thế bằng **contract testing** (kiểm thử hợp đồng):
- Consumer mô tả nó cần những trường nào
- Provider kiểm tra ở mỗi lần build xem nó có phá vỡ kỳ vọng của client hay không
- Cho phép cập nhật "mượt mà" mà không cần đổi major version

### API Gateway và Blue-Green Deployment

Một API Gateway (Kong, Spring Cloud Gateway) có thể đóng vai trò như một **Version Router (bộ định tuyến phiên bản)**:
- 10% lưu lượng có header `v2` → phiên bản mới (Canary Release — phiên bản mới nhận một tỷ lệ nhỏ lưu lượng, ví dụ 10%. Nếu không có lỗi — lưu lượng được chuyển dần hoàn toàn sang).
- 90% → phiên bản cũ

### Hiệu suất

- **Sunset Policy (RFC 8594):** Luôn đặt một "ngày khai tử" cho phiên bản cũ. Dùng header `Sunset`
- **Backward Compatibility Layer (lớp tương thích ngược):** Tạo một "adapter" ở tầng API Gateway để biến đổi các request định dạng cũ thành định dạng mới

### Các trường hợp biên (Edge Case)

- **Database Schema:** Phần khó nhất — khi phiên bản mới yêu cầu thay đổi schema DB
  - **Giải pháp:** Chiến lược "Expand and Contract" — migration DB không downtime: 1) Expand — thêm cột mới mà không bỏ cột cũ. 2) Migrate dữ liệu. 3) Contract — bỏ cột cũ.
- **Side Effect (tác dụng phụ):** Nếu v1 ghi vào bảng A, và v2 — vào bảng B, hãy đảm bảo analytics tính đến cả hai nguồn

## Senior Level

### Quản lý hợp đồng (Contract)

Versioning là về việc quản lý **hợp đồng** giữa provider và consumer. Bất kỳ thay đổi nào đòi hỏi sửa code phía client đều là "phá vỡ".

### Cái gì phá vỡ hợp đồng?
- Bỏ hoặc đổi tên trường trong JSON
- Đổi cấu trúc (object trở thành array)
- Đổi logic validation (thêm trường bắt buộc mới)
- Đổi kiểu dữ liệu (Integer → String)

### Hạ tầng và Kiểm thử

#### Contract Testing (Pact)
Cho phép cập nhật "mượt mà" mà không cần đổi major version:
- Consumer mô tả các kỳ vọng
- Provider kiểm tra tính tương thích ở mỗi lần build

#### API Gateway và Canary Release
API Gateway đóng vai trò như một Version Router:
- Canary Release: 10% lưu lượng sang v2, 90% sang v1
- Giám sát lỗi trên phiên bản mới trước khi chuyển đổi hoàn toàn

### Hiệu suất và Highload

#### Sunset Policy (RFC 8594)
Dùng header `Sunset` để cảnh báo client về việc phiên bản sắp bị loại bỏ (deprecation):
```
Sunset: Sat, 31 Dec 2026 23:59:59 GMT
```

#### Backward Compatibility Layer
Nếu việc hỗ trợ phiên bản cũ tốn kém — hãy tạo một adapter proxy trên API Gateway. Điều này cho phép loại bỏ code cũ khỏi microservice chính.

### Chẩn đoán

- **Metric: `api_version_usage_total`:** Đếm số request theo từng phiên bản. Đây là cách duy nhất để biện minh hợp lý cho việc loại bỏ một phiên bản cũ
- **Deprecation Header:** Dùng `Deprecation: true` để tự động giám sát việc sử dụng các endpoint đã bị loại bỏ
- **Database Strategy:** Expand and Contract — trước tiên thêm cột mới, rồi migrate, rồi bỏ cột cũ

## Interview Cheat Sheet

**Cần phải biết:**
- 3 chiến lược: URL (`/v1/users`), header (`Accept-Version: v2`), Media Type (`application/vnd.myapi.v2+json`)
- URL Versioning — cách tiếp cận phổ biến nhất (GitHub, Stripe, AWS), dễ định tuyến nhất
- Breaking Changes: bỏ/đổi tên trường, đổi cấu trúc, thêm trường bắt buộc mới, đổi kiểu dữ liệu
- Contract Testing (Pact) cho phép cập nhật API mà không đổi major version
- Sunset Policy (RFC 8594): header `Sunset` cảnh báo về việc phiên bản sắp bị loại bỏ
- Expand and Contract — migration DB không downtime: thêm cột → migrate → bỏ cột cũ
- API Gateway có thể đóng vai trò Version Router với Canary Release (10% sang v2)

**Các câu hỏi phụ thường gặp:**
- Cái gì phá vỡ một hợp đồng API? — Bỏ trường, đổi cấu trúc, thêm trường bắt buộc mới, đổi kiểu dữ liệu
- Tại sao Media Type Versioning hiếm khi được dùng? — Khó hiện thực và debug hơn, dù gần với tinh thần REST hơn
- Contract Testing là gì? — Consumer mô tả kỳ vọng, Provider kiểm tra tính tương thích ở mỗi lần build
- Làm sao migrate DB trong lúc versioning? — Expand and Contract: thêm cột mới, migrate dữ liệu, bỏ cột cũ

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "URL versioning là một anti-pattern" — đó là cách tiếp cận phổ biến nhất trong ngành
- "Các thay đổi không phá vỡ thì không cần versioning" — kể cả thêm một trường cũng có thể làm hỏng client
- "Contract Testing thay thế hoàn toàn versioning" — nó cho phép cập nhật mượt mà nhưng không loại bỏ versioning
- "Media Type Versioning là lựa chọn tốt nhất" — đúng về lý thuyết, nhưng hiếm khi dùng trên thực tế
