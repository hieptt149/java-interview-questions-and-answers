# What are -Xms and -Xmx parameters? (Các tham số -Xms và -Xmx là gì?)

## Junior Level

**-Xms** và **-Xmx** — các tham số để cấu hình kích thước bộ nhớ Java Heap.

**-Xms** — kích thước Heap ban đầu (lấy bao nhiêu bộ nhớ lúc khởi động)
**-Xmx** — kích thước Heap tối đa (sẽ không lấy nhiều hơn mức này)

**Ví dụ:**
```bash
java -Xms512m -Xmx2g MyApp
# Khởi động: 512 MB
# Tối đa: 2 GB
```

**Trong hầu hết các kịch bản production:** `-Xms` = `-Xmx` (ngăn ngừa chi phí phát sinh khi resize). Ngoại lệ: các tiện ích CLI (-Xms nhỏ để khởi động nhanh), các môi trường bị hạn chế bộ nhớ.
→ Không có khoảng dừng để mở rộng bộ nhớ

---

## Middle Level

### Reserved vs Committed

```
-Xmx4g:
  → JVM reserve (đặt trước) 4 GB bộ nhớ ảo
  → Bộ nhớ vật lý được cấp phát khi cần

-Xms4g:
  → 4 GB bộ nhớ vật lý được cấp phát ngay lập tức
```

### Tại sao -Xms = -Xmx

```
Nếu -Xms < -Xmx:
  1. Ứng dụng tăng lên → cần Heap lớn hơn
  2. JVM cố gắng tránh việc mở rộng: trước hết chạy GC để giải phóng không gian trong Heap hiện tại.
     Trong các GC hiện đại (G1), đây thường là Young/Mixed GC, không phải Full GC.
     Nhưng nếu GC không giúp được → JVM yêu cầu thêm bộ nhớ từ OS.
  3. Khoảng dừng!
  4. Mở rộng → một system call

Nếu -Xms = -Xmx:
  → Không có khoảng dừng resize
  → Các ngưỡng GC ổn định
  → Hành vi có thể dự đoán được
```

### Docker/Kubernetes

```bash
# Cách tiếp cận hiện đại (Java 11+):
-XX:InitialRAMPercentage=75.0
-XX:MaxRAMPercentage=75.0

# JVM đọc giới hạn của container
# → 75% RAM của container = Heap
# → Linh hoạt: thay đổi giới hạn trong YAML → Heap thay đổi
```

### AlwaysPreTouch

```bash
-XX:+AlwaysPreTouch

# Lúc khởi động: cấp phát vật lý tất cả các trang (page)
# → Khởi động lâu hơn
# → Không có các micro-delay (độ trễ nhỏ) khi truy cập lần đầu
# → Đảm bảo rằng bộ nhớ đã được cấp phát
```

## Senior Level

### Transparent Huge Pages (THP)

```
Linux: Huge Pages = 2 MB thay vì 4 KB
  → Ít TLB miss hơn
  → +5-10% hiệu năng

Vấn đề: THP xung đột với G1
  → Các khoảng dừng GC dài

Giải pháp:
  1. Tắt THP ở cấp kernel
  2. Dùng static Huge Pages:
     -XX:+UseLargePages
```

### Native Memory = không chỉ là Heap

```
RSS (tổng bộ nhớ tiến trình) =
  Heap (-Xmx)
  + Metaspace
  + Code Cache
  + Thread Stacks (-Xss × số luồng)
  + Direct Buffers
  + GC Overhead

→ -Xmx30g trên server 32 GB = OOM Killer!
→ Chừa lại 20-30% cho Native Memory
```

### NMT (Native Memory Tracking)

```bash
-XX:NativeMemoryTracking=summary

jcmd <pid> VM.native_memory summary

# Hiển thị:
# Java Heap: 30 GB
# Class: 50 MB
# Thread: 100 MB
# Code: 80 MB
# GC: 200 MB
# Internal: 50 MB
# ...
```

### Best Practices

1. **-Xms = -Xmx** trong production
2. **RAMPercentage** cho các container
3. **AlwaysPreTouch** để ổn định
4. **Chừa lại 20-30%** cho Native Memory
5. **NMT** để giám sát
6. **Tránh THP** với G1
7. **Đừng đặt -Xmx quá sát** với RAM

### Tóm tắt cho Senior

- **-Xms = -Xmx** = không có khoảng dừng resize
- **RAMPercentage** = tính linh hoạt trong các container
- **AlwaysPreTouch** = không có độ trễ page fault
- **RSS > -Xmx** = hãy tính đến Native Memory
- **NMT** = giám sát bộ nhớ đầy đủ
- **THP** = cẩn thận với G1
- **OOM Killer** = nếu -Xmx quá sát với RAM

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- `-Xms` — kích thước Heap ban đầu, `-Xmx` — tối đa; trong production `-Xms = -Xmx` để ngăn các khoảng dừng resize
- Reserved vs Committed: `-Xmx` reserve bộ nhớ ảo; `-Xms` cấp phát ngay bộ nhớ vật lý
- Khi mở rộng Heap (`-Xms < -Xmx`): JVM trước hết chạy GC → nếu không giúp được → một system call tới OS → khoảng dừng
- Docker/Kubernetes: `-XX:InitialRAMPercentage=75.0` / `-XX:MaxRAMPercentage=75.0` — JVM đọc giới hạn của container
- AlwaysPreTouch: lúc khởi động, cấp phát vật lý tất cả các trang → khởi động lâu hơn, nhưng không có micro-delay khi truy cập lần đầu
- RSS = Heap + Metaspace + Code Cache + Thread Stacks + Direct Buffers + GC Overhead; chừa lại 20-30% RAM cho Native Memory
- Transparent Huge Pages (THP): +5-10% hiệu năng, nhưng xung đột với G1 → các khoảng dừng GC dài

**Các câu hỏi phụ thường gặp:**
- **Tại sao `-Xms = -Xmx` trong production?** — Không có khoảng dừng mở rộng Heap; các ngưỡng GC ổn định; hành vi có thể dự đoán được
- **Điều gì xảy ra nếu `-Xmx30g` trên một server 32 GB?** — OOM Killer giết tiến trình: RSS > 32 GB (Metaspace + Stacks + Code Cache thêm 2-4 GB nữa)
- **Tại sao AlwaysPreTouch?** — Ngăn các độ trễ page fault khi truy cập trang lần đầu; đảm bảo bộ nhớ thực sự được cấp phát
- **Tại sao THP xung đột với G1?** — G1 dùng các region với kích thước khác nhau; THP (các trang 2 MB) gây phân mảnh → các khoảng dừng GC dài

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "`-Xmx` là toàn bộ bộ nhớ tiến trình" — RSS lớn hơn đáng kể: Metaspace, Stacks, Code Cache, Direct Buffers
- "THP luôn cải thiện hiệu năng" — xung đột với G1; hãy tắt hoặc dùng static Huge Pages
- "Trong container, JVM tự động dùng toàn bộ giới hạn" — không có RAMPercentage, JVM nhìn thấy host, không phải container (Java 8 không có bản vá)
