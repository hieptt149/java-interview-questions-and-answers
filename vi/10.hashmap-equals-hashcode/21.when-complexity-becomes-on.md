# When Can Time Complexity Become O(n)? (Khi nào độ phức tạp thời gian có thể trở thành O(n)?)

## 🟢 Junior Level

Mặc dù HashMap thường hoạt động trong O(1) (tức thời), trong một số trường hợp nó có thể chậm xuống O(n) (tỷ lệ thuận với số lượng phần tử).

**Khi nào điều này xảy ra:**

1. **Java cũ (trước phiên bản 8):** Mọi va chạm được lưu trong một list → O(n)
2. **Table nhỏ (capacity < 64):** Ngay cả với 8 va chạm, một tree không được tạo
3. **hashCode() rất kém:** Nếu nó luôn trả về cùng một con số — mọi thứ trong một bucket
4. **Iterate toàn bộ map:** `forEach` duyệt qua mọi bucket, kể cả các bucket rỗng

> Iterate (forEach) LUÔN là O(capacity + size) — đây là hành vi bình thường, không phải suy giảm. Riêng biệt: suy giảm get/put từ O(1) xuống O(n) hoặc O(log n).

**Ví dụ:**
```java
// hashCode tồi — LUÔN trả về 1
class BadKey {
    @Override public int hashCode() { return 1; }
}
// Mọi phần tử trong một bucket → tìm kiếm như trong một list → O(n)
```

## 🟡 Middle Level

### Các kịch bản suy giảm xuống O(n)

| Kịch bản                        | Mô tả                                    | Giải pháp                      |
| ------------------------------- | ---------------------------------------- | ------------------------------ |
| Java 7                          | Không có treeification, mọi va chạm — list | Nâng cấp Java                 |
| capacity < 64 + hashCode tồi    | Treeification không kích hoạt            | Sửa hashCode() của key         |
| hashCode = hằng số              | Mọi phần tử trong một bucket             | Sửa hashCode()                 |
| Iterate                         | Duyệt qua mọi bucket                     | Đừng tạo capacity khổng lồ     |
| Hash Flooding Attack            | Kẻ tấn công tạo các key                  | Java 8+ bảo vệ                 |

### Phân tích chi tiết: capacity < 64

```java
HashMap<BadKey, String> map = new HashMap<>(); // capacity = 16, threshold = 12
// 8 phần tử < threshold(12) → resize KHÔNG xảy ra
// Treeification không kích hoạt: capacity(16) < 64
// Ở phần tử thứ 13 → resize thành 32 → vẫn < 64 → tree KHÔNG được tạo
// Ở phần tử thứ 25 → resize thành 64 → giờ >= 64 → treeification kích hoạt
```

### Iterate: O(capacity + size)

```java
HashMap<String, Integer> map = new HashMap<>(1_000_000);
map.put("one", 1);
// Iterate: duyệt 1.000.000 bucket, trong đó 1 được lấp đầy
// Độ phức tạp: O(1.000.001) ≈ O(n)!
```

**Giải pháp:** Đừng ước lượng capacity quá cao khi không cần.

### Hash Flooding Attack

Kẻ tấn công tạo các key có cùng hash:
- Java 7: O(n²) khi chèn n phần tử → DoS
- Java 8+: O(n log n) — được giảm nhẹ, nhưng overhead vẫn còn

### Các sai lầm thường gặp

1. **Không nâng cấp Java** — Java 7 dễ bị DoS qua HashMap
2. **Capacity ước lượng quá cao** — iterate chậm
3. **Bỏ qua hashCode** — các key là object với phân bố kém

## 🔴 Senior Level

### Cơ chế bên trong: MIN_TREEIFY_CAPACITY

```java
static final int MIN_TREEIFY_CAPACITY = 64;
```

Ngưỡng này nghĩa là với capacity < 64, HashMap ưu tiên resize hơn treeification. Tại điểm này, bucket bị tràn vẫn là một list → O(n).

### Tại sao Java 7 dễ bị tấn công

Trong Java 7, khi Hash Flooding:
```java
// Kẻ tấn công gửi POST với 10.000 tham số có cùng hash
// Tomcat tạo một HashMap cho các tham số
// Chèn 10.000 phần tử vào một bucket: 10.000² = 100.000.000 so sánh
// CPU: 100% → server không phản hồi = DoS
```

CVE-2012-2743 — một lỗ hổng đã biết.

### Edge Case: Comparable và Treeification

Nếu các key không implement `Comparable`:
```java
// HashMap dùng tieBreakOrder():
static int tieBreakOrder(Object a, Object b) {
    return (System.identityHashCode(a) <= System.identityHashCode(b)) ? -1 : 1;
}
```
Điều này tạo một tree, nhưng có overhead — cân bằng ít hiệu quả hơn.

### O(n) khi Iterate: Phân tích sâu

```java
for (Map.Entry<K, V> entry : map.entrySet()) { ... }
```

Iterator duyệt:
```java
for (int i = index; i < table.length; ++i) {
    // Bỏ qua các bucket rỗng
}
```
Mỗi bucket rỗng là một lần kiểm tra. Ở capacity=1M và size=10 — 999.990 lần iterate "rỗng".

### Ảnh hưởng Production

Trong một API gateway với capacity hàng triệu và size nhỏ:
- Iterate để logging: 5-10ms thay vì 0.1ms như mong đợi
- Tính tổng cộng: overhead đáng kể trên các lời gọi thường xuyên

### Các chiến lược giảm nhẹ

1. **Java hiện tại (17+)** — treeification + các bản vá bảo mật
2. **hashCode đúng đắn** — các unit test về phân bố
3. **Capacity đầy đủ** — công thức `(expected / 0.75) + 1`
4. **ConcurrentHashMap** — cho các môi trường đa luồng, cũng được bảo vệ

### Benchmark: O(n) vs O(log n)

Ở 1024 va chạm trong một bucket:
- O(n) = 1024 so sánh ≈ 5 µs
- O(log n) = 10 so sánh ≈ 0.1 µs
- Khác biệt: **50x**

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Iterate (forEach) LUÔN là O(capacity + size) — đây là hành vi bình thường, KHÔNG phải suy giảm
- Suy giảm get/put: O(1) → O(n) ở capacity < 64 + hashCode tồi (tree không được tạo)
- Suy giảm get/put: O(1) → O(log n) khi treeification (Java 8+, capacity >= 64)
- Java 7: O(n) khi va chạm, dễ bị Hash Flooding DoS (CVE-2012-2743)
- Ở 1024 va chạm: O(n) = 1024 so sánh so với O(log n) = 10 — khác biệt 50x
- Hash Flooding Attack: kẻ tấn công tạo các key → DoS; Java 8+ được giảm nhẹ qua treeification

**Các câu hỏi phụ thường gặp:**
- **Tại sao capacity < 64 chặn treeification?** — HashMap ưu tiên resize: nó sẽ trải các phần tử
- **Khi nào O(n) có thể xảy ra trong Java 8+?** — ở capacity < 64 + 8+ va chạm, hoặc hashCode = hằng số
- **tieBreakOrder là gì?** — fallback cho tree khi các key không phải Comparable, dùng System.identityHashCode
- **Làm sao phòng thủ Hash Flooding?** — Java 8+ tự động qua treeification; giám sát chất lượng hashCode

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "forEach suy giảm xuống O(n)" — không, đây là độ phức tạp bình thường O(capacity + size)
- "Tăng capacity giải quyết va chạm" — không, sửa hashCode mới giải quyết
- "Java 8 hoàn toàn được bảo vệ khỏi DoS" — không, overhead từ treeification vẫn còn
