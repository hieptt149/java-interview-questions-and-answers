# At what level can you use @Transactional? (@Transactional có thể dùng ở cấp độ nào?)

## 🟢 Junior Level

Annotation `@Transactional` có thể được đặt trên **method**, **class**, hoặc **interface**. Nhưng không phải lựa chọn nào cũng tốt như nhau.

### Cấp Độ Method (Được Khuyến Nghị)

Cách tiếp cận chính xác nhất. Bạn kiểm soát từng method riêng lẻ. **Tại sao:** mỗi method có thể có propagation, isolation, readOnly riêng của nó. Điều này mang lại sự linh hoạt tối đa mà không có side effect lên các method lân cận.

```java
@Service
public class UserService {

    @Transactional
    public void createUser(User user) {
        userRepository.save(user);
    }

    @Transactional(readOnly = true)
    public User findById(Long id) {
        return userRepository.findById(id).orElse(null);
    }
}
```

### Cấp Độ Class

Tất cả các method public của class trở thành transactional. **Tại sao:** thuận tiện khi toàn bộ class là một service với một trách nhiệm duy nhất (chỉ CRUD). Nhưng nếu có các method không cần transactional — overhead không cần thiết trên mỗi lời gọi.

```java
@Service
@Transactional  // Tất cả các method public đều transactional
public class UserService {
    public void createUser(User user) { ... }
    public User findById(Long id) { ... }
}
```

### Cấp Độ Interface (Không Được Khuyến Nghị)

@Transactional trên một interface chỉ hoạt động với JDK Dynamic Proxy. Nếu Spring dùng CGLIB (mặc định cho các class không có interface) — annotation trên interface bị bỏ qua. Vì vậy best practice là đặt @Transactional trên class hoặc method.

```java
public interface UserService {
    @Transactional  // Chỉ hoạt động với JDK Dynamic Proxy
    User findById(Long id);
}
```

### Nơi KHÔNG Nên Dùng

**Trên controller** — anti-pattern. Controller chịu trách nhiệm về HTTP, transaction chịu trách nhiệm về tính toàn vẹn dữ liệu. Trộn lẫn chúng dẫn đến việc giữ connection DB trong lúc serialize JSON.

### Quy Tắc Vàng

`@Transactional` — trên **tầng service** (Business Logic Layer). Không trên Controller, không trên Repository (trừ các query modifying tùy chỉnh).

### Khi Nào KHÔNG Nên Đặt @Transactional Ở Cấp Độ Class

1. **Có các method không cần transactional** — overhead không cần thiết trên mỗi lời gọi
2. **Propagation/isolation khác nhau** — phải override trên từng method, gây khó hiểu
3. **Class chứa cả method đọc và ghi** — phải đặt readOnly trên từng method đọc

## 🟡 Middle Level

### Độ Ưu Tiên Của Annotation

Nếu annotation có trên cả class và method — **method thắng**.

```java
@Service
@Transactional(readOnly = true)  // Mặc định cho tất cả các method
public class UserService {

    public User findById(Long id) { ... }  // readOnly = true (kế thừa)

    @Transactional  // Ghi đè — readOnly = false, REQUIRED
    public void updateUser(User user) { ... }
}
```

### Cấp Độ Repository

Các repository của Spring Data đã được đánh dấu `@Transactional(readOnly = true)`.

```java
public interface UserRepository extends JpaRepository<User, Long> {
    // findById, findAll — đã transactional (readOnly)

    @Modifying
    @Transactional  // Bắt buộc cho UPDATE/DELETE
    @Query("UPDATE User u SET u.active = false WHERE u.id = :id")
    void deactivate(@Param("id") Long id);
}
```

**Quan trọng:** Nếu bạn gọi một method `@Modifying` từ một service có `@Transactional(readOnly = true)` — bạn nhận `TransactionRequiredException`, vì tham số của service ghi đè tham số của repository.

### Tại Sao @Transactional Trên Controller Là Anti-Pattern

```java
@RestController
@Transactional  // XẤU!
public class UserController {
    @PostMapping("/users")
    public User create(@RequestBody User user) {
        User saved = userService.create(user);
        return saved;  // Serialize JSON bên trong transaction!
    }
}
```

Các vấn đề:
- Connection DB bị giữ trong lúc serialize JSON
- Lazy-loading kích hoạt các query N+1 ở tầng controller
- Dưới tải → cạn kiệt connection pool

### So Sánh Các Cấp Độ

| Cấp độ       | Độ chính xác | Tính linh hoạt | Khi nào nên dùng                              |
| ----------- | --------- | ----------- | ---------------------------------------- |
| Method      | Cao      | Cao        | Luôn được khuyến nghị                       |
| Class       | Trung bình    | Trung bình        | Khi tất cả các method cùng loại (chỉ CRUD)   |
| Interface   | Thấp       | Thấp        | ❌ Không được khuyến nghị                        |
| Controller  | —         | —           | ❌ Anti-pattern                           |

### Các Lỗi Thường Gặp

| Lỗi                                          | Điều gì xảy ra                                           | Cách khắc phục                        |
| ------------------------------------------------ | ------------------------------------------------------ | --------------------------------- |
| `@Transactional` trên interface + CGLIB            | Annotation không hiển thị, không có transaction                 | Đặt trên class hiện thực       |
| `@Modifying` bên trong service readOnly             | `TransactionRequiredException`                         | Ghi đè `readOnly = false`       |
| `readOnly = true` cấp độ class không có ghi đè   | Các method ghi cũng bị readOnly                            | Đánh dấu tường minh các method ghi |
| `@Transactional` trên method final                 | CGLIB không thể override — annotation bị bỏ qua             | Xóa `final`                    |

### Khi Nào KHÔNG Nên Dùng

| Tình huống          | Tại sao                                    | Giải pháp thay thế                              |
| ------------------ | -------------------------------------- | ----------------------------------------- |
| SELECT đơn giản theo ID| Dư thừa                              | Không dùng `@Transactional` hoặc `readOnly = true` |
| Lời gọi HTTP trong method| Giữ connection DB trong lúc I/O mạng | Đưa HTTP ra ngoài transaction            |
| Xử lý nền | Có thể bất đồng bộ                | `@Async` với transaction riêng biệt       |
| Caching            | Không yêu cầu tính nguyên tử              | Không dùng transaction                           |

## 🔴 Senior Level

### Thứ Tự Giải Quyết Annotation

```java
// AbstractFallbackTransactionAttributeSource
protected TransactionAttribute findTransactionAttribute(Method method, Class<?> targetClass) {
    // 1. Kiểm tra method trước tiên (ưu tiên cao nhất)
    TransactionAttribute attr = determineTransactionAttribute(method);
    if (attr != null) return attr;

    // 2. Kiểm tra class khai báo method
    attr = determineTransactionAttribute(method.getDeclaringClass());
    if (attr != null) return attr;

    // 3. Kiểm tra bridge method (interface vs hiện thực)
    if (ClassUtils.isUserLevelMethod(method, targetClass)) {
        Method specificMethod = ClassUtils.getMostSpecificMethod(method, targetClass);
        attr = determineTransactionAttribute(specificMethod);
        if (attr != null) return attr;

        attr = determineTransactionAttribute(specificMethod.getDeclaringClass());
    }
    return null;
}
```

**Nguyên tắc then chốt:** Annotation cấp độ method LUÔN ghi đè cấp độ class. Kết hợp cụ thể nhất thắng.

### Tác Động Của Loại Proxy Đến Việc Phát Hiện Annotation

#### JDK Dynamic Proxy (Dựa Trên Interface)
```java
public interface UserService {
    @Transactional
    User findById(Long id);
}

@Service
public class UserServiceImpl implements UserService {
    // Không có @Transactional — HOẠT ĐỘNG, proxy trên interface
    public User findById(Long id) { ... }
}
```

#### CGLIB Proxy (Dựa Trên Class)
```java
public interface UserService {
    @Transactional  // BỊ BỎ QUA với CGLIB!
    User findById(Long id);
}

@Service
public class UserServiceImpl implements UserService {
    // Không có @Transactional — KHÔNG HOẠT ĐỘNG với CGLIB
    public User findById(Long id) { ... }
}
```

CGLIB tạo một subclass của `UserServiceImpl`, không phải một proxy của interface. Annotation trên interface không hiển thị.

**Giải pháp:** Luôn đặt `@Transactional` trên class/method hiện thực, không bao giờ trên interface.

### OSIV (Open Session in View) — Phân Tích Sâu

```yaml
# application.yml — mặc định là true!
spring:
  jpa:
    open-in-view: true
```

Với OSIV:
```
Request → Filter mở Session → Controller → Service → Render View → Filter đóng Session
```

**Các vấn đề:**
1. **Query N+1**: Lazy loading trong lúc serialize JSON kích hoạt thêm các query
2. **Connection bị giữ**: Connection bị chiếm giữ trong lúc render view
3. **Vấn đề hiệu năng ẩn giấu**: Lazy loading che giấu việc fetch không hiệu quả

**Giải pháp — vô hiệu hóa OSIV:**
```yaml
spring:
  jpa:
    open-in-view: false
```

```java
@Transactional(readOnly = true)
public UserDTO getUserWithDetails(Long id) {
    User user = userRepository.findByIdWithDetails(id);  // Eager fetch
    return UserDTO.from(user);  // Entity được load đầy đủ
}
```

### Các Trường Hợp Biên (Tối Thiểu 3)

1. **Bridge method**: Java sinh các bridge method với generics. Spring phải giải quyết đúng `@Transactional` từ bridge method đến method mục tiêu. Một số phiên bản Spring có bug với `@Transactional` trên các method generic.

2. **Kế thừa với override**: Nếu `BaseService.save()` có `@Transactional(timeout = 10)`, và `DerivedService.save()` — không có annotation, hành vi phụ thuộc vào loại proxy. CGLIB có thể không tìm thấy annotation trong superClass trong một số điều kiện nhất định.

3. **Nhiều `@Transactional` trên cùng method**: Nếu method kế thừa `@Transactional` từ cả interface lẫn class — chỉ một cái được áp dụng (thứ tự không xác định). Spring lấy cái tìm thấy đầu tiên.

4. **`@Transactional` trên các class `@Configuration`**: Các method tạo bean bên trong class `@Configuration` không tự động được bọc trong transaction. `@Transactional` trên method `@Bean` không có tác dụng — bean được tạo bên ngoài context transaction.

### Kiến Trúc Theo Tầng

```
┌─────────────────────────────────────────┐
│  Tầng Controller                        │
│  - Request/response HTTP                 │
│  - Validation                            │
│  - KHÔNG @Transactional                     │
├─────────────────────────────────────────┤
│  Tầng Service                           │
│  - Logic nghiệp vụ                        │
│  - @Transactional Ở ĐÂY ✓                │
│  - Ranh giới transaction được định nghĩa ở đây   │
├─────────────────────────────────────────┤
│  Tầng Repository                        │
│  - Truy cập dữ liệu                           │
│  - Spring Data tự động transactional        │
│  - Chỉ @Transactional cho @Modifying    │
└─────────────────────────────────────────┘
```

**Quy tắc:** Ranh giới transaction nên khớp với ranh giới use-case nghiệp vụ, không phải các thao tác kỹ thuật.

### Các Con Số Về Hiệu Năng

| Thao tác                            | Thời gian       |
| ------------------------------------ | ---------- |
| Giải quyết annotation (cache của Spring) | ~0.1 μs    |
| Lời gọi proxy                     | ~1-2 μs    |
| Thiết lập transaction                    | ~5-10 μs   |
| Lấy connection (HikariCP)    | ~50-200 μs |

### Tác Động Đến Bộ Nhớ

- `@Transactional` cấp độ class tạo proxy cho tất cả các method public
- Mỗi method giải quyết `TransactionAttribute` (được cache)
- Các mục ThreadLocal: ~1 KB mỗi transaction đang hoạt động
- L1 cache của Hibernate: tăng tuyến tính theo số entity được load

### Thread Safety

Bản thân annotation là bất biến (immutable) và thread-safe. Trạng thái transaction được lưu trong ThreadLocal — mỗi thread được cô lập. Bean singleton an toàn dưới các lời gọi đồng thời.

### Câu Chuyện Thực Tế Trong Production

Dự án microservice: `@Transactional` được đặt trên interface `UserService`. Trong môi trường dev — JDK Dynamic Proxy hoạt động (interface tồn tại). Trong production — CGLIB (tự động cấu hình của Spring Boot). Kết quả: trong production các transaction không mở, dữ liệu commit mà không rollback khi có lỗi. Bug chỉ xuất hiện dưới tải. Sửa lỗi: chuyển `@Transactional` sang class hiện thực.

### Best Practices Cho Highload

1. **Độ chi tiết cấp độ method**: Kiểm soát chính xác — chỉ các method ghi có `@Transactional`, các method đọc có `readOnly = true`.
2. **Vô hiệu hóa OSIV** trong production: `spring.jpa.open-in-view: false`.
3. **Không bao giờ đặt `@Transactional` trên interface**: CGLIB — thất bại âm thầm.
4. **Tránh `@Transactional` cấp độ class** trong các service lớn — một số method có thể không cần transaction.
5. **Cân nhắc kích thước connection pool**: `@Transactional` giữ connection trong suốt thời gian method. Method dài = cạn kiệt pool.
6. **Dùng `@Transactional(readOnly = true)` trên các service truy vấn**: Có thể định tuyến đến read replica qua `AbstractRoutingDataSource`.

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- @Transactional được đặt trên method (được khuyến nghị), class, hoặc interface
- Method thắng class — annotation cấp độ method luôn ghi đè cấp độ class
- Quy tắc vàng: @Transactional trên tầng service, KHÔNG trên Controller hoặc Repository
- @Transactional trên interface chỉ hoạt động với JDK Dynamic Proxy, bị bỏ qua với CGLIB
- Các repository của Spring Data đã có @Transactional(readOnly = true) — @Modifying cần ghi đè
- OSIV (Open Session in View) mặc định là true — gây ra các query N+1, nên vô hiệu hóa

**Các câu hỏi phụ thường gặp:**
- Tại sao @Transactional trên Controller là anti-pattern? — Connection bị giữ trong lúc serialize JSON, lazy loading N+1
- OSIV là gì và tại sao nên vô hiệu hóa? — Session mở cho đến khi render view, che giấu N+1, giữ connection
- Khi nào @Transactional cấp độ class hợp lý? — Khi tất cả các method cùng loại (chỉ CRUD)
- Điều gì xảy ra với method @Modifying bên trong service readOnly? — TransactionRequiredException

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "@Transactional trên interface luôn hoạt động" — CGLIB âm thầm bỏ qua
- "Controller với @Transactional — thực hành bình thường" — nguy cơ cạn kiệt connection pool
- "OSIV = tốt" — che giấu các vấn đề hiệu năng, các query N+1
