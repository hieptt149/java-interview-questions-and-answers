# How does message compression work (Message compression hoạt động như thế nào)

## Junior Level

### Định Nghĩa

**Compression** — nén các batch message để giảm mức sử dụng network và dung lượng đĩa.

```
Không có compression: batch 1MB
Với lz4: batch 300KB (tiết kiệm 70%)
```

### Các Thuật Toán Khả Dụng

```
gzip   — compression tốt nhất, tốc độ chậm
snappy — compression trung bình, tốc độ nhanh
lz4    — compression tốt, tốc độ rất nhanh
zstd   — compression xuất sắc, tốc độ trung bình
```

### Cấu Hình

```java
props.put("compression.type", "lz4");
// Các lựa chọn: none, gzip, snappy, lz4, zstd
```

### Tại Sao Cần Đến Compression?

```
✅ Ít I/O network hơn
✅ Ít dung lượng đĩa trên broker hơn
✅ Truyền message nhanh hơn
✅ Chi phí thấp hơn cho lưu lượng network
```

## Middle Level

### So Sánh Thuật Toán

| Thuật toán  | Compression | Tốc độ      | Sử dụng CPU   | Khuyến nghị  |
| ---------- | ----------- | ---------- | ----------- | --------------- |
| **gzip**   | Tốt nhất        | Chậm       | Cao        | Hiếm khi dùng     |
| **snappy** | Trung bình      | Nhanh       | Thấp         | Latency thấp     |
| **lz4**    | Tốt        | Rất nhanh  | Thấp         | Lựa chọn mặc định  |
| **zstd**   | Xuất sắc   | Trung bình     | Trung bình      | Compression tối đa |

### Cấu Hình Compression

**Producer:**
```java
props.put("compression.type", "lz4");
// Compression được áp dụng cho toàn bộ batch
```

**Broker:**
```properties
# Cài đặt toàn cục (có thể ghi đè ở cấp topic)
compression.type=producer — broker KHÔNG nén lại message; nó chấp nhận
định dạng của producer. Giá trị "uncompressed" buộc broker giải nén.
```

**Topic:**
```bash
kafka-configs.sh --alter --topic orders \
  --add-config compression.type=lz4 \
  --bootstrap-server localhost:9092
```

### Tỷ Lệ Compression

```
Các ví dụ tỷ lệ compression:
  Dữ liệu JSON: 3:1 - 5:1
  Văn bản: 4:1 - 10:1
  Dữ liệu nhị phân: 1.5:1 - 2:1
  Dữ liệu đã nén rồi: 1:1 (không có tác dụng)
```

### Các Lỗi Thường Gặp

1. **gzip cho throughput cao:**
```
Overhead CPU cao → bottleneck
→ Trì hoãn xử lý
```

2. **Không có compression:**
```
Message lớn → nhiều mức sử dụng network hơn
→ Chi phí cao hơn, truyền chậm hơn
```

3. **Nén dữ liệu đã nén rồi:**
```
gzip trên các file đã gzip → không có tác dụng
→ Lãng phí CPU
```

## Senior Level

### Cài Đặt Nội Bộ

**Luồng Compression:**
```
1. Producer tích lũy các message trong một batch
2. Batch được serialize
3. Thuật toán compression được áp dụng
4. Batch đã nén được gửi đến broker
5. Broker lưu trữ nó đã nén
6. Consumer nhận nó đã nén, giải nén
```

**Giải Nén:**
```
Giải nén xảy ra trên consumer:
- Sử dụng CPU trên consumer
- Trong suốt với ứng dụng
- Thư viện client Kafka tự động xử lý
```

### Chọn Thuật Toán

**lz4 — lựa chọn mặc định:**
```
Ưu điểm:
- Compression/giải nén rất nhanh
- Tỷ lệ compression tốt
- Sử dụng CPU thấp
- Lý tưởng cho hầu hết các use case

Các use case:
- Mục đích chung
- Các hệ thống throughput cao
- Yêu cầu latency thấp
```

**zstd — compression tối đa:**
```
Ưu điểm:
- Tỷ lệ compression tốt nhất
- Cấp độ compression có thể cấu hình
- Nhanh hơn gzip

Các use case:
- Tiết kiệm dung lượng đĩa
- Replication chéo DC (tiết kiệm băng thông)
- Lưu trữ dài hạn
```

**snappy — lựa chọn legacy:**
```
Ưu điểm:
- Compression nhanh
- Hỗ trợ trong các client cũ hơn

Các use case:
- Tương thích với các hệ thống legacy
- Latency thấp với compression vừa phải
```

### Tinh Chỉnh Cấp Độ Compression

```java
// zstd hỗ trợ cấu hình cấp độ
// 1-22 (mặc định 3)
props.put("compression.type", "zstd");
// Trong một số client:
props.put("zstd.level", "9");  // cao hơn = compression tốt hơn
```

### Tác Động Hiệu Năng

```
Overhead CPU:
  none:  0%
  lz4:   ~5%
  snappy: ~10%
  zstd:  ~15-20%
  gzip:  ~30-40%

Tiết kiệm network:
  none:  0%
  lz4:   ~50-70%
  snappy: ~40-60%
  zstd:  ~60-80%
  gzip:  ~70-85%

(giá trị gần đúng cho dữ liệu JSON/text; con số thực tế phụ thuộc vào loại dữ liệu
và nên được test trên khối lượng công việc production)
```

### Monitoring

**Các metrics chính:**
```
kafka.producer:compression-rate-avg
kafka.producer:compression-time-avg
kafka.consumer:decompression-time-avg
kafka.server:bytes-in-per-sec
kafka.server:bytes-out-per-sec
```

**Các Alert:**
```yaml
- Tỷ lệ compression < 1.2 → điều tra
- Thời gian compression > ngưỡng → warning
- Sử dụng CPU trên các broker > ngưỡng → warning
```

### Các Thực Hành Tốt Nhất

```
✅ lz4 theo mặc định cho hầu hết các trường hợp
✅ zstd để tiết kiệm dung lượng đĩa/băng thông
✅ Giám sát sử dụng CPU trên các broker
✅ Compression trên batch (không phải mỗi message)
✅ Test tỷ lệ trên dữ liệu production

❌ Không có compression cho production
❌ gzip cho các hệ thống throughput cao
❌ Nén dữ liệu đã nén rồi
❌ Không có giám sát tỷ lệ compression
❌ Bỏ qua tác động CPU
```

### Các Quyết Định Kiến Trúc

1. **lz4 — cân bằng** — lựa chọn tốt nhất cho hầu hết các trường hợp
2. **zstd — tiết kiệm** — khi dung lượng đĩa/băng thông quan trọng
3. **Compression trên batch** — tỷ lệ tốt hơn
4. **Giám sát tỷ lệ compression** — chỉ báo hiệu quả

### Tóm Tắt Cho Senior

- lz4 — cân bằng tốt nhất cho hầu hết các trường hợp
- zstd — khi cần compression tối đa
- Compression được áp dụng cho toàn bộ batch
- Đánh đổi overhead CPU so với tiết kiệm network
- Giám sát tỷ lệ compression rất quan trọng cho hiệu quả

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- Compression nén các batch để giảm I/O network và mức sử dụng đĩa
- Các thuật toán: gzip (compression tốt nhất, chậm), snappy (nhanh), lz4 (cân bằng), zstd (compression xuất sắc)
- lz4 — lựa chọn mặc định: rất nhanh, tỷ lệ tốt, CPU thấp (~5%)
- Compression được áp dụng cho toàn bộ batch — batch lớn hơn = tỷ lệ tốt hơn
- JSON/text: tỷ lệ 3:1 - 5:1; nhị phân: 1.5:1 - 2:1; đã nén rồi: 1:1
- Producer nén, consumer giải nén trong suốt (thư viện client xử lý)
- Broker KHÔNG nén lại — chấp nhận định dạng của producer

**Các câu hỏi phụ thường gặp:**
- *Nên chọn thuật toán nào?* — lz4 cho hầu hết các trường hợp, zstd để tiết kiệm dung lượng đĩa/băng thông.
- *Giải nén xảy ra ở đâu?* — Trên consumer, trong suốt với ứng dụng.
- *Bạn có thể nén dữ liệu đã nén rồi không?* — Có thể, nhưng không có tác dụng (1:1), lãng phí CPU.
- *Overhead của gzip là gì?* — ~30-40% CPU, hiếm khi dùng trong các hệ thống throughput cao.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Broker nén lại các message" — nó chấp nhận định dạng của producer
- "gzip là lựa chọn tốt nhất cho production" — overhead CPU cao, lz4 tốt hơn
- "Compression trên mỗi message" — trên toàn bộ batch
- "Compression miễn phí" — overhead CPU 5-40% tùy thuộc vào thuật toán
