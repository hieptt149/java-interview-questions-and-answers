# What is race condition? (Race condition là gì?)

Race condition là một bug nơi **tính đúng đắn của một chương trình phụ thuộc vào thứ tự thực thi thread không dự đoán được**. Khác với deadlock (nơi các thread bị chặn vĩnh viễn), trong một race condition chương trình **vẫn chạy nhưng cho ra kết quả sai**. Điều này làm cho race condition đặc biệt nguy hiểm — một ứng dụng có thể chạy trên môi trường test nhiều tháng và bùng nổ trong production.

---

## Junior Level

### Hiểu biết cơ bản

**Race Condition** — một bug nơi kết quả của chương trình phụ thuộc vào thứ tự thực thi thread không dự đoán được. Tại sao nó xảy ra: các bộ xử lý hiện đại và JVM thực thi các lệnh không đúng thứ tự nghiêm ngặt, mà với các tối ưu — và không có đồng bộ hóa tường minh, hai thread có thể "trộn lẫn" các thao tác của chúng sao cho một thread đọc một giá trị cũ hoặc trung gian.

**Tại sao nó không ngẫu nhiên:** một race condition nảy sinh từ một pattern cụ thể — ít nhất một thread **đọc** dữ liệu, ít nhất một thread **ghi** dữ liệu, và không có rào chắn đồng bộ hóa nào giữa việc đọc và ghi.

### Ví dụ minh họa đơn giản

Hai người đồng thời cố viết một con số vào một cuốn sổ dùng chung:
- Người A đọc: "5"
- Người B đọc: "5"
- Người A viết: "6"
- Người B viết: "6"
- **Kết quả:** 6 thay vì 7 như mong đợi!

### Ví dụ kinh điển: Bộ đếm

```java
public class UnsafeCounter {
    private int count = 0;

    public void increment() {
        count++; // KHÔNG an toàn! Đây là 3 thao tác:
        // 1. Đọc count từ bộ nhớ
        // 2. Tăng thêm 1
        // 3. Ghi ngược lại
    }

    public int getCount() {
        return count;
    }
}

// Hai thread:
for (int i = 0; i < 1000; i++) counter.increment();
for (int i = 0; i < 1000; i++) counter.increment();
// Mong đợi: 2000
// Thực tế: 1500-1999 (các bản cập nhật bị mất!)
```

### Tại sao count++ không Atomic?

```
Thread 1:          Thread 2:
LOAD count (0)
                   LOAD count (0)  ← Cùng giá trị ban đầu!
INC (0 → 1)        INC (0 → 1)
STORE count (1)    STORE count (1) ← Ghi đè!
// Kết quả: 1 thay vì 2
```

### Các loại Race Condition

| Loại                  | Mô tả                                              | Ví dụ                                       |
| --------------------- | -------------------------------------------------- | ------------------------------------------- |
| **Read-Modify-Write** | Đọc → sửa → ghi dựa trên giá trị cũ                | `count++`                                   |
| **Check-then-Act**    | Kiểm tra → hành động dựa trên kết quả kiểm tra     | `if (map.get(key) == null) put(key, value)` |
| **Lazy Init Race**    | Object có thể bị khởi tạo dở dang                  | Singleton không có volatile                 |

## Middle Level

### Read-Modify-Write

```java
// Vấn đề:
AtomicInteger counter = new AtomicInteger(0);
int value = counter.get();    // READ
counter.set(value + 1);       // MODIFY + WRITE (không atomic cùng nhau!)
// Hai thread có thể đọc cùng một giá trị
```

### Check-then-Act

```java
// Vấn đề:
if (!map.containsKey(key)) {    // CHECK
    map.put(key, new Value());  // ACT
}
// Hai thread có thể đồng thời vượt qua kiểm tra và cả hai đều put
```

**Giải pháp:**

```java
// An toàn:
map.putIfAbsent(key, new Value()); // Check-then-act atomic
```

### Nguyên nhân ở mức phần cứng: CPU Reordering

Các bộ xử lý thực thi các lệnh **không theo thứ tự** (Out-of-order execution):

```java
// Code nguồn:
data = new Data();   // Lệnh 1
ready = true;        // Lệnh 2

// Bộ xử lý có thể sắp xếp lại:
ready = true;        // Đầu tiên — rẻ hơn
data = new Data();   // Rồi

// Một thread khác thấy ready = true, nhưng data vẫn là null!
```

Không có Memory Barrier (`volatile`, `synchronized`), bộ xử lý tự do sắp xếp lại.

### Volatile KHÔNG bảo vệ khỏi Race Condition

```java
// Sai lầm thường gặp:
volatile int count = 0;

count++; // VẪN không an toàn!
// volatile đảm bảo visibility, nhưng KHÔNG đảm bảo atomicity
// Đây vẫn là 3 thao tác: đọc → sửa → ghi
```

### Heisenbug

Các race condition là "Heisenbug":
- Không xuất hiện trên máy của developer (1-2 core)
- Bùng nổ trên production server (64 core)
- Không thể tái hiện trong debugger (debug thay đổi timing)

```java
// Một test "thỉnh thoảng pass, thỉnh thoảng fail":
@Test
public void testCounter() {
    Counter counter = new Counter();
    Thread t1 = new Thread(() -> { for(int i=0;i<1000;i++) counter.increment(); });
    Thread t2 = new Thread(() -> { for(int i=0;i<1000;i++) counter.increment(); });
    t1.start(); t2.start();
    t1.join(); t2.join();
    assertEquals(2000, counter.getCount()); // Thỉnh thoảng 1998, thỉnh thoảng 1995...
}
```

## Senior Level

### Bên trong: Interleaving

Các race condition xảy ra do **interleaving** — việc trộn lẫn các lệnh từ các thread khác nhau:

```
Thread 1:  LOAD count    INC    STORE count
Thread 2:          LOAD count    INC    STORE count
                 ↑
                 Ở đây Thread 2 đọc giá trị CŨ
```

Các interleaving có thể xảy ra cho hai thread với `count++`:

```
1. P1: LOAD→INC→STORE, P2: LOAD→INC→STORE  → Kết quả: 2 (OK)
2. P1: LOAD, P2: LOAD→INC→STORE, P1: INC→STORE  → Kết quả: 1 (BUG!)
3. P1: LOAD→INC, P2: LOAD→INC→STORE, P1: STORE  → Kết quả: 1 (BUG!)
```

### Vấn đề ABA (một biến thể của Race Condition)

```
Thread 1: đọc giá trị A
Thread 2: đổi A → B → A
Thread 1: "Giá trị chưa thay đổi" — tiếp tục dựa trên dữ liệu cũ
```

### Benign Race (race lành tính)

Trong các trường hợp hiếm, race condition là có chủ đích:

```java
// Bộ đếm gần đúng — ta chấp nhận mất các bản cập nhật để đổi lấy tốc độ
volatile int approxCount = 0;

public void increment() {
    approxCount++; // Race condition — nhưng OK cho thống kê
}
```

### Visibility vs Atomicity

| Vấn đề         | Mô tả                                   | Giải pháp                 |
| -------------- | --------------------------------------- | ------------------------- |
| **Visibility** | Thread không thấy thay đổi từ thread khác| `volatile`               |
| **Atomicity**  | Thao tác gộp bị gián đoạn               | `synchronized`, `Atomic*` |

```java
// volatile giải quyết visibility, nhưng KHÔNG giải quyết atomicity:
volatile int count = 0;
count++; // Race condition vẫn tồn tại!

// synchronized giải quyết cả visibility và atomicity:
synchronized(lock) {
    count++; // An toàn
}
```

### Chẩn đoán

#### JCStress

```java
@JCStressTest
@Outcome(id = "1", expect = ACCEPTABLE_INTERESTING, desc = "Race condition!")
@Outcome(id = "2", expect = ACCEPTABLE, desc = "OK")
public class CounterStressTest {
    int count = 0;

    @Actor
    public void actor1() { count++; }

    @Actor
    public void actor2(I_IntResult1 r) { r.r1 = count; }
}

// Chạy:
// java -jar jcstress.jar -f CounterStressTest
```

#### Phân tích tĩnh: Error Prone

```bash
# Google Error Prone sẽ tìm các pattern Check-then-Act
javac -Xplugin:ErrorProne MyClass.java
```

```java
// Error Prone sẽ cảnh báo:
if (map.get(key) == null) {    // Race check-then-act
    map.put(key, value);
}
```

#### Concurrency Testing với CountDownLatch

```java
@Test
public void testRaceCondition() throws Exception {
    int threads = 10;
    CountDownLatch startLatch = new CountDownLatch(1);
    CountDownLatch doneLatch = new CountDownLatch(threads);

    for (int i = 0; i < threads; i++) {
        new Thread(() -> {
            try {
                startLatch.await(); // Tất cả chờ
                for (int j = 0; j < 1000; j++) {
                    counter.increment();
                }
            } finally {
                doneLatch.countDown();
            }
        }).start();
    }

    startLatch.countDown(); // "GO!" — tất cả bắt đầu đồng thời
    doneLatch.await();

    assertEquals(threads * 1000, counter.getCount());
}
```

### Best Practices

1. **Dùng Atomic*** cho các thao tác increment/set đơn giản
2. **Dùng synchronized** cho các thao tác gộp
3. **Dùng các Concurrent collection** — ConcurrentHashMap, ConcurrentLinkedQueue
4. **Tránh Check-then-Act** — dùng các phiên bản atomic tương đương (putIfAbsent)
5. **volatile không phải thread-safe** — volatile chỉ dành cho visibility
6. **Test trên các hệ thống đa xử lý** — không chỉ ở local
7. **Dùng JCStress** để stress test
8. **Phân tích tĩnh** — Error Prone tìm các pattern race điển hình

## Khi nào KHÔNG cần lo lắng về Race Condition

- **Ứng dụng đơn luồng** — không có song song, không có race
- **Mọi dữ liệu đều immutable** — nếu các object không thay đổi sau khi tạo, race condition không thể xảy ra (không có ghi)
- **Dữ liệu không rời khỏi method** — các biến cục bộ được lưu trên stack của thread, các thread khác không truy cập được
- **Chỉ các thao tác atomic chỉ đọc** — nếu mọi thread chỉ đọc (kể cả không có volatile), race condition không thể xảy ra
- **Các bộ đếm/metric gần đúng** — đôi khi một race condition là chấp nhận được: mất 1-2 bản cập nhật mỗi triệu thao tác không ảnh hưởng đến business logic (ví dụ, bộ đếm lượt xem)

## Race Condition vs Deadlock: Các khác biệt then chốt

| Tiêu chí            | Race Condition                              | Deadlock                                        |
| ------------------- | ------------------------------------------- | ----------------------------------------------- |
| **Triệu chứng**     | Kết quả sai                                 | Bế tắc hoàn toàn                                |
| **Nguyên nhân**     | Đồng bộ hóa không đủ                        | Đồng bộ hóa quá mức/không đúng                  |
| **Phát hiện**       | Stress test, JCStress, các bất thường production| Thread dump, jstack, ThreadMXBean            |
| **Tái hiện**        | Không ổn định, phụ thuộc timing             | Ổn định (nếu các điều kiện được thỏa)           |
| **Giải pháp**       | Thêm đồng bộ hóa (synchronized, Atomic)     | Bỏ đồng bộ hóa hoặc sắp thứ tự khóa             |
| **Nguy hiểm**       | Hỏng dữ liệu âm thầm (tệ hơn)               | Vấn đề thấy được (tốt hơn)                      |

Các race condition thường **nguy hiểm hơn** deadlock: deadlock thấy được ngay lập tức (ứng dụng treo), trong khi một race condition có thể âm thầm làm hỏng dữ liệu nhiều tháng.

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Race condition — một bug nơi kết quả của chương trình phụ thuộc vào thứ tự thực thi thread không dự đoán được
- Ba loại: Read-Modify-Write (count++), Check-then-Act (if-not-then-put), Lazy Init Race
- `count++` — 3 thao tác (đọc → sửa → ghi), không atomic ngay cả với `volatile int`
- `volatile` đảm bảo visibility, nhưng KHÔNG đảm bảo atomicity
- Race condition vs Deadlock: race = đồng bộ hóa không đủ (hỏng dữ liệu âm thầm), deadlock = đồng bộ hóa quá mức (bế tắc hoàn toàn)
- Heisenbug: không tái hiện trên máy của developer, bùng nổ trong production với nhiều core hơn

**Các câu hỏi phụ thường gặp:**
- **Tại sao volatile không bảo vệ khỏi race condition?** — volatile đảm bảo mọi thread thấy giá trị mới nhất, nhưng thao tác read-modify-write vẫn có thể bị một thread khác gián đoạn giữa đọc và ghi
- **Vấn đề ABA là gì?** — Thread 1 đọc A, Thread 2 đổi A→B→A, Thread 1 "không nhận ra thay đổi" và tiếp tục dựa trên dữ liệu cũ
- **Benign race condition là gì?** — Một race được dung thứ có chủ đích, ví dụ, một bộ đếm gần đúng nơi mất 1-2 bản cập nhật mỗi triệu không ảnh hưởng đến business logic
- **Làm sao test race condition?** — CountDownLatch để bắt đầu đồng thời, JCStress để stress test, test trên ARM/M1 (reordering hung hãn hơn)

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "volatile là đủ cho một bộ đếm thread-safe" — volatile không cung cấp atomicity cho các thao tác gộp
- "Race condition là khi các thread chặn lẫn nhau" — đó là deadlock, race condition là một kết quả sai
- "Trên laptop 2 core của tôi test luôn pass" — race condition xuất hiện với nhiều core hơn, điều đó không có nghĩa bug không có ở đó
- "Nếu chương trình thỉnh thoảng chạy đúng — thì không có race condition" — race condition phụ thuộc timing, "thỉnh thoảng chạy" CHÍNH LÀ triệu chứng
