# How to avoid race condition? (Làm sao tránh race condition?)

Khác với file 21 (race condition là gì), file này mô tả các **chiến lược phòng ngừa cụ thể**. Ý tưởng then chốt: một race condition xảy ra khi ít nhất một thread đọc, ít nhất một thread ghi, và không có đồng bộ hóa giữa chúng. Mọi chiến lược đều quy về ba cách tiếp cận: **đồng bộ hóa** việc truy cập, **cô lập** dữ liệu, hoặc **loại bỏ** mutable shared state.

---

## Junior Level

### Hiểu biết cơ bản

Một race condition xảy ra khi nhiều thread truy cập dữ liệu dùng chung và ít nhất một thread sửa đổi nó. Để tránh race condition, bạn cần đảm bảo **atomicity** hoặc **cô lập** dữ liệu.

**"Atomicity" nghĩa là gì trên thực tế:** một thao tác trông như tức thời với các thread khác — hoặc nó chưa bắt đầu hoặc nó đã hoàn tất. Một trạng thái trung gian không bao giờ được quan sát thấy. synchronized đạt được điều này qua khóa, các lớp Atomic qua các lệnh CPU CAS (Compare-And-Swap).

**"Cô lập" dữ liệu nghĩa là gì:** mỗi thread làm việc với bản sao riêng của nó, và các kết quả được kết hợp chỉ sau khi hoàn thành. Điều này tốn nhiều bộ nhớ hơn nhưng loại bỏ hoàn toàn sự cạnh tranh.

### Chiến lược 1: synchronized

```java
public class SafeCounter {
    private int count = 0;

    // Chỉ một thread có thể thực thi method này tại một thời điểm
    public synchronized void increment() {
        count++;
    }

    public synchronized int getCount() {
        return count;
    }
}
```

### Chiến lược 2: Các lớp Atomic

```java
public class SafeCounter {
    private AtomicInteger count = new AtomicInteger(0);

    // Thao tác atomic — không có race condition
    public void increment() {
        count.incrementAndGet();
    }

    public int getCount() {
        return count.get();
    }
}
```

### Chiến lược 3: Các object Immutable

```java
// Object immutable — không thể bị thay đổi, race condition không thể xảy ra
public final class Config {
    private final String value;

    public Config(String value) {
        this.value = value;
    }

    public String getValue() {
        return value; // Luôn an toàn
    }
}
```

### Chiến lược 4: ThreadLocal

```java
// Mỗi thread có bản sao riêng của nó — không có shared state
ThreadLocal<SimpleDateFormat> dateFormat = ThreadLocal.withInitial(
    () -> new SimpleDateFormat("yyyy-MM-dd")
);

public String formatDate(Date date) {
    return dateFormat.get().format(date); // An toàn
}
```

### So sánh các cách tiếp cận

| Phương pháp   | Ưu điểm                        | Nhược điểm                    |
| ------------- | ----------------------------- | ---------------------------- |
| synchronized  | Đáng tin cậy, đơn giản         | Nặng khi tranh chấp          |
| Atomic        | Nhanh (lock-free)             | Chỉ cho các thao tác đơn giản|
| Immutability  | Lý tưởng để scale             | Áp lực GC                    |
| ThreadLocal   | Zero contention               | Rủi ro rò rỉ trong các pool  |

## Middle Level

### Chiến lược đồng bộ hóa (Bi quan)

#### Khóa (Locking)

```java
// synchronized — vùng critical
synchronized(lock) {
    // Chỉ một thread — các thread khác BLOCKED
    counter++;
    total += counter;
}

// ReentrantLock — nhiều tùy chọn hơn
ReentrantLock lock = new ReentrantLock();
lock.lock();
try {
    counter++;
} finally {
    lock.unlock(); // Luôn trong finally!
}
```

#### Biến Atomic (Lạc quan)

```java
AtomicInteger counter = new AtomicInteger(0);

// updateAndGet — check-then-act atomic
counter.updateAndGet(current -> {
    if (current < MAX) {
        return current + 1;
    }
    return current; // Không increment
});

// computeIfPresent — thao tác atomic trên một map
ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>();
map.computeIfPresent("key", (k, v) -> v + 1);
```

### Chiến lược cô lập (Lạc quan/Thiết kế)

#### Các object Immutable

```java
// Thay vì mutate — tạo một object mới
public class State {
    private final int count;
    private final String name;

    public State(int count, String name) {
        this.count = count;
        this.name = name;
    }

    // Copy-on-write
    public State withCount(int newCount) {
        return new State(newCount, this.name);
    }
}

// Sử dụng:
State current = new State(0, "test");
current = current.withCount(1); // Object mới — không có race condition
```

#### ThreadLocal

```java
ThreadLocal<UserContext> context = new ThreadLocal<>();

// Quan trọng: luôn dọn dẹp trong các thread pool!
executor.submit(() -> {
    try {
        context.set(new UserContext("user123"));
        process();
    } finally {
        context.remove(); // BẮT BUỘC!
    }
});
```

#### Các Concurrent Collection

```java
// Thay vì HashMap + synchronized:
ConcurrentHashMap<String, String> map = new ConcurrentHashMap<>();

map.putIfAbsent("key", "value");  // Atomic
map.compute("key", (k, v) -> ...); // Atomic
map.merge("key", 1, Integer::sum); // Atomic

// Segmented lock — nhiều thread ghi đồng thời
```

### Pattern Safe Publication

Các race condition thường xảy ra trong lúc tạo object. Các cách để publish an toàn:

```java
// 1. Static initialization (được đảm bảo bởi ClassLoader)
public static final Config INSTANCE = new Config();

// 2. Các field final
public class Safe {
    public final String value;
    public Safe(String v) { this.value = v; }
}

// 3. Field volatile
private volatile Config config;
config = new Config();

// 4. synchronized
synchronized(lock) {
    config = new Config();
}
```

### So sánh các cách tiếp cận cho Highload

| Phương pháp   | Ưu điểm         | Nhược điểm                    | Khi nào                |
| ------------- | --------------- | ---------------------------- | ---------------------- |
| synchronized  | Đáng tin cậy, đơn giản | Context switch, deadlock| Các trường hợp đơn giản|
| Atomic/CAS    | Rất nhanh       | CPU khi tranh chấp cao       | Bộ đếm, cờ             |
| Immutability  | Scale được      | GC do việc sao chép          | Phong cách functional  |
| ThreadLocal   | Không tranh chấp| Rò rỉ trong các pool         | Context của request    |

## Senior Level

### Bên trong: JVM đảm bảo Atomicity như thế nào

#### synchronized → Monitor Enter/Exit

```
monitorenter:
  1. Cố acquire monitor
  2. Khi tranh chấp — thread đi vào EntryList (BLOCKED)
  3. Khi ra — mọi thay đổi được flush xuống bộ nhớ

monitorexit:
  1. Release monitor
  2. Invalidate cache của các thread khác
```

#### Atomic → CAS ở mức CPU

```assembly
lock cmpxchg [memory], new_value
; Atomic ở mức memory bus
; Các core khác không thể truy cập ô này
```

### Các pattern Lock-free

```java
// Lock-free linked list — đơn giản hóa
class LockFreeStack<T> {
    private AtomicReference<Node<T>> head = new AtomicReference<>(null);

    public void push(T value) {
        Node<T> newNode = new Node<>(value);
        Node<T> oldHead;
        do {
            oldHead = head.get();
            newNode.next = oldHead;
        } while (!head.compareAndSet(oldHead, newNode));
    }
}
```

### Bên trong ConcurrentHashMap

```
Java 7: Khóa mức Segment (16 segment)
Java 8+: CAS + synchronized ở mức bucket (node)

get():       Gần như lock-free (đọc volatile)
put():       CAS cho bucket mới, synchronized cho va chạm
compute():   synchronized trên bucket cụ thể — không phải toàn bộ map
```

#### FindBugs / SpotBugs

```java
// SpotBugs sẽ tìm ra:
public class RaceCondition {
    private int data = 0; // Không đồng bộ, được truy cập từ nhiều thread

    public void write() {
        data = 42; // Race condition!
    }

    public int read() {
        return data; // Race condition!

}
```

ARM: Weakly ordered — race condition xuất hiện thường xuyên hơn

Test trên ARM (M1/M2) — nhiều cơ hội bắt được race hơn!

### Các pattern phòng ngừa

#### 1. Confinement (Cô lập)

```java
// Dữ liệu không rời khỏi method — không có race condition
public int process() {
    int local = 0; // Biến cục bộ — chỉ trong thread này
    for (int i = 0; i < 100; i++) {
        local += i;
    }
    return local;
}
```

#### 2. Immutability

```java
// Immutable = thread-safe theo định nghĩa
public record User(String name, int age) {}
```

#### 3. Các Collection thread-safe

```java
// CopyOnWriteArrayList — cho ghi hiếm, đọc thường xuyên
List<String> list = new CopyOnWriteArrayList<>();
list.add("item"); // Sao chép toàn bộ mảng — đắt cho ghi thường xuyên

// ConcurrentLinkedQueue — hàng đợi lock-free
Queue<String> queue = new ConcurrentLinkedQueue<>();
queue.offer("item"); // CAS — lock-free
```

### Best Practices

1. **Tránh mutable shared state** — cách tiếp cận tốt nhất
2. **Dùng Atomic** cho các bộ đếm và cờ đơn giản
3. **Dùng ConcurrentHashMap** thay vì HashMap + synchronized
4. **Các object immutable** — thread-safe theo định nghĩa
5. **ThreadLocal** — luôn dọn dẹp trong finally
6. **Safe Publication** — final, volatile, hoặc synchronized khi tạo
7. **Test trên các hệ thống đa xử lý** — ARM/M1 hung hãn hơn x86
8. **Phân tích tĩnh** — SpotBugs, Error Prone tìm các race điển hình

## Khi nào KHÔNG áp dụng các chiến lược này

- **Không có shared state** — nếu các thread không trao đổi dữ liệu, race condition không thể xảy ra
- **Dữ liệu là immutable** — các object immutable là thread-safe theo định nghĩa, không cần đồng bộ hóa
- **Các thao tác chỉ đọc** — nếu mọi thread chỉ đọc, race condition không thể xảy ra
- **Một thread ghi, các thread khác đọc sau** — nếu việc ghi xảy ra trước khi việc đọc bắt đầu (ví dụ, khởi tạo trước khi thread bắt đầu), thì không có race
- **Chấp nhận mất các bản cập nhật** — cho các metric và thống kê, đôi khi chấp nhận được việc mất 1-2 trên một triệu bản cập nhật (các bộ đếm gần đúng)

## synchronized vs Atomic vs ConcurrentHashMap: Chọn gì?

| Tình huống                                   | Lựa chọn               | Tại sao                                         |
| -------------------------------------------- | ---------------------- | ---------------------------------------------- |
| Bộ đếm đơn giản (increment)                  | AtomicLong             | CAS nhanh hơn khóa, không có overhead monitor  |
| Nhiều thao tác như một transaction           | synchronized           | Cần thực thi atomic một nhóm thao tác          |
| Cache/map với truy cập đồng thời             | ConcurrentHashMap      | Segmented lock, song song cao hơn              |
| Context của request (user session)           | ThreadLocal            | Cô lập hoàn toàn, zero contention              |
| Object tạo một lần và không bao giờ thay đổi  | Immutable (final field)| Thread-safe không cần đồng bộ hóa, miễn phí    |

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- 4 chiến lược chính: synchronized, các lớp Atomic, các object Immutable, ThreadLocal
- synchronized = khóa bi quan (chặn khi vào), Atomic = lạc quan/CAS (thử mà không khóa)
- ConcurrentHashMap dùng CAS + synchronized ở mức bucket, không phải trên toàn bộ map
- Safe Publication: static initialization, các field final, volatile, hoặc synchronized
- ThreadLocal — luôn dọn dẹp trong finally, nếu không sẽ rò rỉ trong các thread pool

**Các câu hỏi phụ thường gặp:**
- **Khi nào chọn Atomic thay vì synchronized?** — Cho các thao tác đơn giản (increment, set, compare-and-swap). Cho một nhóm thao tác như một transaction — synchronized
- **Tại sao CopyOnWriteArrayList đắt cho ghi thường xuyên?** — Mỗi add sao chép toàn bộ mảng, chỉ phù hợp cho ghi hiếm/đọc thường xuyên
- **x86 khác ARM như thế nào trong bối cảnh các race?** — x86 là strongly ordered, ARM là weakly ordered — các race condition xuất hiện thường xuyên hơn trên ARM/M1

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "volatile giải quyết mọi vấn đề đa luồng" — volatile chỉ dành cho visibility, không phải cho atomicity
- "ConcurrentHashMap hoàn toàn lock-free" — get() gần như lock-free, nhưng put()/compute() dùng synchronized trên bucket
- "ThreadLocal không thể gây rò rỉ bộ nhớ" — trong các thread pool ThreadLocal sống lâu hơn tác vụ, không có remove() bản sao còn lại mãi mãi
- "Immutability là miễn phí" — tạo nhiều bản sao tạo áp lực GC
