# What is a stack trace? (Stack trace là gì?)

## Junior Level

### Định nghĩa

**Stack trace** - một danh sách các phương thức đã được gọi trước khi một exception xảy ra. Nó cho thấy đường thực thi từ điểm lỗi tới điểm khởi động chương trình.

**Stack frame** - một phần tử trong chuỗi lời gọi. Mỗi lần một chương trình gọi một phương thức, JVM tạo một "frame" trong bộ nhớ lưu: các biến local, tham số, địa chỉ trả về. Stack trace chỉ đơn giản là một danh sách các frame như vậy, từ phương thức hiện tại tới `main()`.

### Ví dụ

```java
public class Main {
    public static void main(String[] args) {
        method1();
    }

    static void method1() {
        method2();
    }

    static void method2() {
        throw new RuntimeException("Error!");
    }
}
```

Stack trace:
```
java.lang.RuntimeException: Error!
    at Main.method2(Main.java:12)
    at Main.method1(Main.java:8)
    at Main.main(Main.java:4)
```

### Cách đọc

Đọc **từ trên xuống dưới**:

```
java.lang.RuntimeException: Error!
    at Main.method2(Main.java:12)
    at Main.method1(Main.java:8)
    at Main.main(Main.java:4)
```

Phân tích từng dòng:
1. **`java.lang.RuntimeException: Error!`** - kiểu exception (`RuntimeException`) và message (`Error!`). Đây là dòng quan trọng nhất: nó nói CÁI GÌ đã xảy ra
2. **`at Main.method2(Main.java:12)`** - lỗi xảy ra trong phương thức `method2` của class `Main`, file `Main.java`, dòng 12. Đây là stack frame đang active tại thời điểm lỗi
3. **`at Main.method1(Main.java:8)`** - `method2` được gọi từ `method1` ở dòng 8. Đây là stack frame trước đó
4. **`at Main.main(Main.java:4)`** - `method1` được gọi từ `main` ở dòng 4. Đây là gốc của stack (điểm vào)

**Ví dụ minh họa:** hãy tưởng tượng một vệt vụn bánh mì. `main()` để lại một mẩu vụn, gọi `method1()`, cái này để lại một mẩu vụn và gọi `method2()`, nơi mọi thứ đổ vỡ. Stack trace là đường quay lại điểm bắt đầu.

### Bạn sẽ thấy nó ở đâu

- Trong console khi chạy chương trình
- Trong log của server
- Khi gọi `exception.printStackTrace()`

### Khi nào KHÔNG nên thu thập stack trace (Lưu ý về hiệu suất)

Tạo một stack trace là một **thao tác đắt đỏ** (~1-5 micro giây). JVM duyệt tất cả các stack frame và sao chép chúng vào một mảng.

**Đừng thu thập stack trace nếu:**
- **Exception được dùng cho control flow** (anti-pattern) - ví dụ: ném `NotFoundException` thay vì trả về `Optional.empty()`. Ở mức 1000 request mỗi giây, những mili giây này cộng dồn lại
- **Hệ thống tải cao** - trong hot-path (code được gọi hàng nghìn lần mỗi giây) tạo một exception với stack đầy đủ tạo tải đáng kể lên CPU và GC
- **Luồng được lường trước/bình thường** - nếu `NumberFormatException` khi parse đầu vào của người dùng là một tình huống được lường trước, đừng ghi log stack đầy đủ, message là đủ

**Giải pháp thay thế cho các exception nhẹ:** trong Java có một mẹo với `fillInStackTrace()` - bạn có thể ghi đè nó trong exception của bạn thành `return this;` để không thu thập stack. Nhưng khi đó bạn mất thông tin về nguồn gốc lỗi.

## Middle Level

### Cấu trúc bên trong

Stack trace là một mảng các object `java.lang.StackTraceElement`:

```java
StackTraceElement[] elements = Thread.currentThread().getStackTrace();
for (StackTraceElement el : elements) {
    System.out.println(el.getClassName());   // "com.example.MyClass"
    System.out.println(el.getMethodName());  // "myMethod"
    System.out.println(el.getLineNumber());  // 42
    System.out.println(el.getFileName());    // "MyClass.java"
    System.out.println(el.isNativeMethod()); // false
}
```

Mỗi phần tử chứa:
- Tên file
- Tên class
- Tên phương thức
- Số dòng (nếu biên dịch với `-g`)
- Cờ native method

### StackWalker API (Java 9+)

Trước Java 9, `getStackTrace()` luôn sao chép **toàn bộ** stack vào một mảng - đắt đỏ.

`StackWalker` đọc stack một cách lười (lazy):

```java
StackWalker.getInstance().forEach(frame ->
    System.out.println(frame.getClassName() + " @ " + frame.getLineNumber())
);
```

Ưu điểm:
- Đọc lười (dưới dạng stream)
- Bỏ qua các frame không cần thiết (Spring proxy, Hibernate)
- Truy cập tới các object `Class`, không chỉ các tên chuỗi

### Stack trace trong code Reactive

Trong code async (Project Reactor / WebFlux), stack trace cổ điển là vô dụng - nó chỉ hiển thị phần bên trong của các thread Netty.

Giải pháp: `Hooks.onOperatorDebug()` - "dán" các mảnh logic của stack lại với nhau, nhưng ảnh hưởng đến hiệu suất.

## Senior Level

### Chi phí FillInStackTrace

Phần lớn thời gian được dùng để duyệt stack frame native (`fillInStackTrace`). Phương thức lồng nhau càng sâu (Spring!), việc tạo exception càng đắt đỏ.

### Stack trace trong log

In stack đầy đủ ở mỗi lần 404 - lấp đầy đĩa và làm nghẹn I/O.

**Best Practice:** stack đầy đủ chỉ cho `ERROR`, với các business exception được lường trước - chỉ message và `cause`.

### OmitStackTraceInFastThrow

Khi lặp lại cực kỳ thường xuyên cùng một exception, JVM (HotSpot) tối ưu nó và ngừng điền stack trace:

```
java.lang.NullPointerException
// Không có stack!
```

Cờ `-XX:-OmitStackTraceInFastThrow` tắt tối ưu hóa này để debug.

### Obfuscation

Với obfuscation (Proguard/R8), stack trace trở thành `a.b.c(SourceFile:1)`. Giải mã yêu cầu các file mapping.

### Chẩn đoán

- **`Thread.getAllStackTraces()`** - ảnh chụp của tất cả các thread. Bản "nhà nghèo" tương đương `jstack` để chẩn đoán deadlock.
- **Async Trace ID** - trong các hệ thống phân tán dùng `Span ID / Trace ID` (OpenTelemetry) để liên kết các stack giữa các microservice.
- **`jstack <pid>`** - thread dump đầy đủ kèm các monitor
- **Log có cấu trúc JSON** - stack trace như một trường riêng có thể lập chỉ mục trong ELK

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Stack trace - danh sách các stack frame từ điểm lỗi tới `main()`
- Mỗi frame lưu: tên class, tên phương thức, số dòng, tên file
- Tạo stack trace - thao tác đắt đỏ (~1-5 micro giây); JVM duyệt tất cả các frame
- `StackWalker` (Java 9+) đọc stack một cách lười, hiệu quả hơn `getStackTrace()`
- Cờ `-XX:-OmitStackTraceInFastThrow` tắt tối ưu hóa của JVM vốn xóa stack khi lặp lại thường xuyên
- Trong code async (WebFlux) stack trace cổ điển là vô dụng - chỉ hiển thị phần bên trong của framework

**Các câu hỏi phụ thường gặp:**
- **Cách đọc stack trace?** - Từ trên xuống dưới: dòng đầu là kiểu exception và message, rồi - đường từ vị trí lỗi tới điểm vào
- **Khi nào KHÔNG nên thu thập stack trace?** - Trong hot-path (hàng nghìn lời gọi/giây), luồng được lường trước (validation đầu vào), khi exception được dùng cho flow control
- **`fillInStackTrace()` là gì?** - Phương thức native duyệt các stack frame; có thể ghi đè thành `return this` để bỏ qua (nhưng mất thông tin)
- **StackWalker hoạt động như thế nào?** - Đọc stack lười dưới dạng stream, có thể bỏ qua các frame, truy cập tới các object `Class` không chỉ chuỗi

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Stack trace là miễn phí - tôi luôn in nó" - Tạo stack tải cho CPU và GC, đặc biệt trong highload
- "Trong code async stack trace hiển thị bức tranh đầy đủ" - Trong code reactive nó chỉ hiển thị phần bên trong của Netty/EventLoop
- "OmitStackTraceInFastThrow là một bug" - Đó là một tối ưu hóa của HotSpot cho các exception lặp lại thường xuyên
