# How to ensure fault tolerance of microservices (Cách đảm bảo fault tolerance cho microservice)

## 🟢 Junior Level

**Fault tolerance** là khả năng của một hệ thống tiếp tục hoạt động khi các thành phần riêng lẻ thất bại.

**Các pattern chính:**
1. **Circuit Breaker** — mở mạch khi có lỗi, trả về fallback
2. **Retry** — lặp lại một call thất bại với độ trễ
3. **Timeout** — giới hạn thời gian chờ response
4. **Fallback** — đường thay thế khi thất bại
5. **Bulkhead** — tách các thread pool để lỗi ở một cái không ảnh hưởng đến các cái khác

```
Service A → Circuit Breaker → Retry → Timeout → Fallback → kết quả
```

## 🟡 Middle Level

### Resilience4j

```java
// "backend" — tên cấu hình từ application.yml.
// fallbackMethod — phương thức được gọi khi circuit breaker kích hoạt.
// Resilience4j chặn call thông qua AOP proxy.
@CircuitBreaker(name = "backend", fallbackMethod = "fallback")
@Retry(name = "backend")
@TimeLimiter(name = "backend")
@Bulkhead(name = "backend")
public CompletableFuture<String> callBackend(String input) {
    return backendService.callAsync(input);
}

public CompletableFuture<String> fallback(String input, Throwable t) {
    return CompletableFuture.completedFuture("fallback: " + input);
}
```

### Cấu Hình

```yaml
resilience4j:
  circuitbreaker:
    instances:
      backend:
        failureRateThreshold: 50
        waitDurationInOpenState: 10s
  retry:
    instances:
      backend:
        maxAttempts: 3
        waitDuration: 1s
  timelimiter:
    instances:
      backend:
        timeoutDuration: 5s
```

### Các Lỗi Thường Gặp

1. **Retry không có exponential backoff:**
```
3 lần retry không có delay ngay lập tức → quá tải service (traffic tăng gấp ba).
Cần exponential backoff với jitter — xem file 20.
Giải pháp: exponential backoff + jitter
```

## 🔴 Senior Level

### Chaos Engineering

```
Test fault tolerance:
- Chaos Monkey (Netflix) — ngẫu nhiên kill các service
- Gremlin — chèn lỗi (fault injection)
- Toxiproxy — độ trễ network

Mục tiêu: tìm điểm yếu trước khi lên production
```

### Kinh Nghiệm Production

**Multi-region deployment:**
```
Region 1 (active) → traffic
Region 2 (passive) → standby
Region 1 sập → failover sang Region 2
```

### Best Practices

```
✅ Circuit Breaker cho các call bên ngoài
✅ Retry với exponential backoff
✅ Timeout trên tất cả các call
✅ Fallback cho graceful degradation
✅ Bulkhead để cô lập
✅ Monitoring và alerting

❌ Không có timeout
❌ Retry không có backoff
❌ Không có fallback
❌ Không có monitoring
```

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- 5 pattern chính: Circuit Breaker, Retry, Timeout, Fallback, Bulkhead
- Circuit Breaker chặn các call đến một service không hoạt động
- Retry với exponential backoff + jitter thử lại các call với độ trễ tăng dần
- Timeout giới hạn thời gian chờ — bảo vệ khỏi treo
- Fallback là một đường thay thế khi thất bại (graceful degradation)
- Bulkhead cô lập tài nguyên — lỗi ở một cái không ảnh hưởng đến các cái khác
- Chaos Engineering (Chaos Monkey, Gremlin) test fault tolerance trước khi lên production

**Các câu hỏi phụ thường gặp:**
- **Tại sao retry không có backoff là xấu?** Tăng gấp ba traffic đến một service đang lỗi — làm vấn đề tệ hơn.
- **Chaos Engineering là gì?** Cố ý gây ra lỗi (kill một service, thêm độ trễ) để tìm điểm yếu.
- **Resilience4j vs Hystrix?** Hystrix ở chế độ maintenance, Resilience4j là chuẩn hiện đại.
- **Multi-region deployment đảm bảo fault tolerance như thế nào?** Region 1 sập → failover sang Region 2.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Retry không có backoff là ổn" — không, quá tải service
- "Không cần Circuit Breaker, chúng ta có network đáng tin cậy" — lỗi có thể ở phía service
- "Fallback = bỏ qua lỗi" — không, đó là một đường thay thế (cache, giá trị mặc định)
- "Bulkhead = Circuit Breaker" — không, Bulkhead cô lập tài nguyên, CB chặn các call
