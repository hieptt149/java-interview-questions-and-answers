# How do AtomicInteger, AtomicLong work? (AtomicInteger, AtomicLong hoạt động như thế nào?)

---

## Junior Level

### Hiểu biết cơ bản

`AtomicInteger` và `AtomicLong` là các wrapper thread-safe bọc quanh các primitive `int` và `long`.

**Tại sao:** khi nhiều thread đồng thời sửa đổi một biến `int` thông thường, các bản cập nhật bị mất. AtomicInteger giải quyết điều này bằng cách đảm bảo atomicity của mỗi thao tác mà không cần khóa. Chúng cung cấp các thao tác atomic (không thể chia nhỏ) không cần khóa qua CAS. Atomic = các thread khác không thể nhìn thấy một trạng thái trung gian.

### Tạo và các thao tác cơ bản

```java
// Tạo
AtomicInteger atomicInt = new AtomicInteger(0);
AtomicLong atomicLong = new AtomicLong(0L);

// Increment/decrement
atomicInt.incrementAndGet();  // ++i (trả về giá trị mới)
atomicInt.getAndIncrement();  // i++ (trả về giá trị cũ)
atomicInt.decrementAndGet();  // --i
atomicInt.getAndDecrement();  // i--

// Số học
atomicInt.addAndGet(10);      // i += 10
atomicInt.getAndAdd(10);      // trả về giá trị cũ, rồi += 10

// Gán
atomicInt.set(100);           // Gán trực tiếp
atomicInt.getAndSet(200);     // Trả về giá trị cũ, gán giá trị mới

// CAS
atomicInt.compareAndSet(200, 300); // Nếu == 200, đặt thành 300

// Lấy
int value = atomicInt.get();  // Giá trị hiện tại
```

### Ví dụ: Bộ đếm request

```java
public class RequestCounter {
    private final AtomicInteger count = new AtomicInteger(0);

    public void handleRequest(Request req) {
        int currentCount = count.incrementAndGet();
        System.out.println("Request #" + currentCount);
        // Xử lý...
    }

    public int getTotalRequests() {
        return count.get();
    }
}
```

### Tại sao không dùng int cho gọn?

```java
// KHÔNG an toàn:
int count = 0;
count++; // 3 thao tác: đọc → sửa → ghi
// Hai thread có thể đọc cùng một giá trị và mất một bản cập nhật

// An toàn:
AtomicInteger count = new AtomicInteger(0);
count.incrementAndGet(); // Thao tác atomic — CAS ở mức CPU
```

### Các method chính

| Method                    | Mô tả                    | Trả về          |
| ------------------------- | ------------------------ | --------------- |
| `get()`                   | Giá trị hiện tại         | int/long        |
| `set(v)`                  | Gán giá trị              | void            |
| `incrementAndGet()`       | ++i                      | Giá trị mới     |
| `getAndIncrement()`       | i++                      | Giá trị cũ      |
| `addAndGet(delta)`        | i += delta               | Giá trị mới     |
| `getAndAdd(delta)`        | i += delta               | Giá trị cũ      |
| `compareAndSet(exp, upd)` | CAS                      | true/false      |
| `updateAndGet(fn)`        | Cập nhật qua một hàm     | Giá trị mới     |

## Middle Level

### Cấu trúc bên trong

```java
public class AtomicInteger extends Number implements java.io.Serializable {
    // 1. field volatile cho visibility
    private volatile int value;

    // 2. VarHandle để truy cập bộ nhớ trực tiếp (Java 9+)
    private static final VarHandle VALUE;

    static {
        try {
            MethodHandles.Lookup l = MethodHandles.lookup();
            VALUE = l.findVarHandle(AtomicInteger.class, "value", int.class);
        } catch (ReflectiveOperationException e) {
            throw new Error(e);
        }
    }

    public AtomicInteger(int initialValue) {
        value = initialValue;
    }
}
```

### Các method ghi khác nhau

```java
AtomicInteger counter = new AtomicInteger(0);

// 1. set(v) — ghi volatile thông thường
counter.set(100);
// Lập tức được mọi thread nhìn thấy, rào chắn bộ nhớ đầy đủ

// 2. lazySet(v) — ghi nới lỏng (Java 9+: setOpaque)
counter.lazySet(100);
// Không đảm bảo visibility ngay lập tức, nhưng nhanh hơn vì không đặt một rào chắn bộ nhớ đầy đủ — bộ xử lý không bắt buộc phải lập tức đồng bộ các cache line với các core khác.
// Hữu ích để reset trạng thái mà sẽ sớm được đọc bởi cùng thread đó

// 3. compareAndSet(exp, upd) — CAS đầy đủ
counter.compareAndSet(0, 100);
// Nếu == 0, đặt thành 100. Rào chắn đầy đủ.

// 4. updateAndGet(fn) — cập nhật qua một hàm
counter.updateAndGet(x -> x * 2); // Nhân với 2
```

| Method              | Happens-Before | Tốc độ   | Khi nào dùng           |
| ------------------- | -------------- | -------- | ---------------------- |
| `set(v)`            | Có             | Chuẩn    | Ghi thông thường       |
| `lazySet(v)`        | Không (eventual)| Nhanh hơn| Reset cờ               |
| `compareAndSet`     | Có             | Chuẩn    | Các thuật toán lock-free|
| `weakCompareAndSet` | Không          | Nhanh hơn| Các chu kỳ được tối ưu |

### An toàn trên các hệ thống 32-bit

```java
// Trên một JVM 32-bit:
long value = 0x0123456789ABCDEFL;
// Được ghi trong HAI bước:
// 1. 0x89ABCDEF (32 bit thấp)
// 2. 0x01234567 (32 bit cao)
// Một thread khác có thể thấy một giá trị "lẫn lộn"!

// AtomicLong đảm bảo atomicity:
AtomicLong atomicLong = new AtomicLong(0x0123456789ABCDEFL);
// Dùng lệnh CMPXCHG8B hoặc khóa nội bộ
```

### updateAndGet — Thao tác atomic linh hoạt

```java
AtomicInteger flags = new AtomicInteger(0);

// Đặt atomic một bit
flags.updateAndGet(current -> current | 0x01);

// Xóa atomic một bit
flags.updateAndGet(current -> current & ~0x01);

// Đảo atomic một bit
flags.updateAndGet(current -> current ^ 0x01);
```

### False Sharing (vấn đề cache line)

Khi hai instance AtomicInteger nằm cạnh nhau trong một mảng, chúng có thể rơi vào cùng một CPU cache line 64 byte. Nếu thread A ghi vào `counters[0]` và thread B đọc `counters[1]` — chúng cạnh tranh cho một cache line, dù đây là các bộ đếm khác nhau.

**Giải pháp:** annotation `@Contended` (Java 8+, cần `-XX:-RestrictContended`) — thêm padding xung quanh field để nó chiếm một cache line riêng.

```java
@sun.misc.Contended
AtomicInteger counter; // 64 byte padding trước và sau
```

Với các mảng long[], false sharing là có thật:
```java
long[] counters = new long[8];
// counters[0] và counters[1] trong cùng một cache line → hai thread cạnh tranh
```

## Khi nào AtomicInteger là một lựa chọn kém

1. **Tranh chấp cao (100+ thread)**: CAS contention giết chết hiệu năng — dùng LongAdder
2. **Các thao tác gộp**: cập nhật atomic hai field — cần synchronized
3. **Các phép tính dài giữa đọc và ghi**: CAS sẽ liên tục thất bại — tốt hơn nên dùng Lock

## Senior Level

### Bên trong: VarHandle và Memory Access API

Java 9+ dùng VarHandle thay vì Unsafe:

```java
// Atomic qua VarHandle
public final int getAndAdd(int delta) {
    return (int)VALUE.getAndAdd(this, delta);
}

// VarHandle dịch thành các lệnh native:
// VALUE.getAndAdd → lock xadd [memory], delta (x86)
```

#### getAndAdd ở mức x86

```assembly
; lock xadd — phép cộng atomic trả về giá trị cũ
; eax = delta, [memory] = counter

lock xadd [memory], eax
; [memory] = [memory] + eax
; eax = giá trị cũ của [memory]
```

### AtomicIntegerFieldUpdater — Tiết kiệm bộ nhớ

Cho các trường hợp hàng triệu object cần một atomic int:

```java
// XẤU: hàng triệu object AtomicInteger thừa
class User {
    AtomicInteger loginAttempts = new AtomicInteger(0); // 24 byte × 1M = 24MB
}

// TỐT: một field + một static updater
class User {
    volatile int loginAttempts = 0; // 4 byte × 1M = 4MB

    private static final AtomicIntegerFieldUpdater<User> UPDATER =
        AtomicIntegerFieldUpdater.newUpdater(User.class, "loginAttempts");

    public int incrementAttempts() {
        return UPDATER.incrementAndGet(this);
    }
}
```

### CAS Contention và ID Generator

```java
// XẤU: ID generator toàn cục ở 1000 RPS
AtomicLong idGenerator = new AtomicLong(0);
public long nextId() {
    return idGenerator.incrementAndGet(); // Tranh chấp cao!
}

// TỐT: cấp phát range ID
public class IdRangeGenerator {
    private final AtomicLong nextRangeStart = new AtomicLong(0);
    private static final long RANGE_SIZE = 1000;

    // Cấp một lô ID — mỗi service/thread nhận range riêng
    public IdRange allocateRange() {
        long start = nextRangeStart.getAndAdd(RANGE_SIZE);
        return new IdRange(start, start + RANGE_SIZE);
    }
}
```

### Hiệu năng và tải cao (Highload)

#### Benchmark (xấp xỉ)

| Thao tác                             | Thời gian| Ghi chú             |
| ------------------------------------ | -------- | ------------------- |
| `get()`                              | ~1 ns    | Đọc volatile        |
| `set()`                              | ~5 ns    | Ghi volatile        |
| `incrementAndGet()` (không tranh chấp)| ~5-10 ns | Một CAS             |
| `incrementAndGet()` (100 thread)     | ~100+ ns | CAS contention      |
| `lazySet()`                          | ~2-3 ns  | Không có rào chắn đầy đủ|

#### Tối ưu qua Batching

```java
// Bộ đếm cục bộ + flush atomic
public class BatchedCounter {
    private int local = 0;
    private final AtomicInteger flushed = new AtomicInteger(0);

    public synchronized void increment() {
        local++;
        if (local >= 100) { // Flush mỗi 100
            flushed.addAndGet(local);
            local = 0;
        }
    }

    public int getTotal() {
        synchronized(this) {
            return flushed.get() + local;
        }
    }
}
```

### Best Practices

1. **AtomicInteger cho các bộ đếm** — khi tranh chấp vừa phải
2. **AtomicLong cho các bộ đếm 64-bit** — an toàn trên các JVM 32-bit
3. **LongAdder khi tranh chấp cao** — cell phân tán
4. **lazySet để reset cờ** — nhanh hơn set
5. **updateAndGet cho các cập nhật phức tạp** — hàm atomic
6. **AtomicIntegerFieldUpdater để tiết kiệm bộ nhớ** — hàng triệu object
7. **Cấp phát range ID** — thay vì AtomicLong toàn cục ở 1000+ RPS

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- AtomicInteger/AtomicLong — các wrapper thread-safe bọc quanh int/long, cung cấp atomicity không cần khóa
- Hoạt động qua CAS (compare-and-swap) — một lệnh CPU phần cứng (lock cmpxchg trên x86)
- Java 9+ dùng VarHandle thay vì Unsafe để truy cập bộ nhớ
- incrementAndGet() = chu kỳ spin: đọc → tính → CAS → thử lại khi thất bại
- lazySet() — ghi nới lỏng không có rào chắn bộ nhớ đầy đủ, nhanh hơn cho việc reset cờ
- Khi tranh chấp cao (100+ thread), CAS contention giết chết hiệu năng — cần LongAdder
- AtomicLong đảm bảo đọc/ghi atomic ngay cả trên các JVM 32-bit (nơi long được ghi trong 2 bước)
- AtomicIntegerFieldUpdater tiết kiệm bộ nhớ khi hàng triệu object cần một atomic field

**Các câu hỏi phụ thường gặp:**
- **getAndIncrement() khác incrementAndGet() như thế nào?** — Cái đầu trả về giá trị cũ (i++), cái sau — giá trị mới (++i)
- **Tại sao CAS tốt hơn synchronized?** — Không có context switch, deadlock không thể xảy ra, ~5ns vs ~1000ns khi tranh chấp thấp
- **False sharing là gì?** — Hai AtomicInteger trong cùng một CPU cache line cạnh tranh dù ở các địa chỉ khác nhau; giải quyết bằng @Contended
- **Khi nào AtomicInteger là một lựa chọn kém?** — Tranh chấp cao (LongAdder tốt hơn), các thao tác gộp (cần synchronized), các phép tính dài giữa đọc/ghi

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Atomic dùng synchronized bên trong" — không, nó là CAS lock-free
- "AtomicInteger luôn nhanh hơn synchronized" — không, ở 8+ thread synchronized có thể nhanh hơn
- "compareAndSet chặn thread khi thất bại" — không, nó chỉ trả về false, thread spin trong một vòng lặp
