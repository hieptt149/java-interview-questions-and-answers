# What is rebalancing and when does it happen (Rebalancing là gì và khi nào nó xảy ra)

## Junior Level

### Định Nghĩa

**Rebalancing** là quá trình phân phối lại các partition giữa các consumer trong một group.

**"Chi phí":** trong quá trình rebalance, các consumer KHÔNG đọc message. Với eager rebalancing — dừng hoàn toàn trong 5-30 giây. Trong thời gian này, lag tăng, và với lỗi dây chuyền — theo kiểu tuyết lở.

```
Trước rebalance:
  C1 → P0, P1
  C2 → P2, P3

Sau khi thêm C3:
  C1 → P0, P1
  C2 → P2
  C3 → P3
```

### Khi Nào Rebalancing Xảy Ra?

```
1. Một consumer mới được thêm vào
2. Một consumer crash hoặc mất kết nối
3. Các partition mới được thêm vào một topic
4. Một consumer thay đổi đăng ký topic của nó
```

### Điều Gì Xảy Ra Trong Quá Trình Rebalance?

```
1. Tất cả các consumer dừng đọc
2. Kafka phân phối lại các partition
3. Mỗi consumer nhận các partition mới
4. Việc đọc tiếp tục
```

**Quan trọng:** Với eager rebalancing — dừng hoàn toàn. Với cooperative (Kafka 2.3+) — việc xử lý tiếp tục
trên các partition còn lại, chỉ các partition đã di chuyển gặp downtime.

### Ví Dụ Code

```java
// Consumer tự động tham gia vào rebalance
props.put("group.id", "my-group");
consumer.subscribe(List.of("orders"));
// Khi một consumer mới với cùng group.id được thêm vào
// một rebalance tự động sẽ xảy ra
```

## Middle Level

### Quá Trình Rebalancing (Từng Bước)

```
1. Trigger — sự kiện (consumer mới, timeout, v.v.)
2. Group coordinator bắt đầu rebalance
3. Tất cả các consumer thu hồi các partition của họ
4. Gán mới được tính toán
5. Các consumer nhận các partition mới
6. Việc đọc tiếp tục
```

### Các Loại Rebalance

**Eager Rebalancing (cũ):**
```
Tất cả các consumer dừng hoàn toàn
Phân phối lại toàn bộ partition
Tất cả các consumer tiếp tục làm việc
→ Downtime hoàn toàn của group
```

**Cooperative Rebalancing (Kafka 2.3+):**
```
Di chuyển partition dần dần
Các consumer tiếp tục làm việc với các partition còn lại
→ Downtime tối thiểu
```

### ConsumerRebalanceListener

```java
consumer.subscribe(List.of("orders"), new ConsumerRebalanceListener() {
    @Override
    public void onPartitionsRevoked(Collection<TopicPartition> partitions) {
        // Commit offset trước khi mất partition
        consumer.commitSync();
        // Dọn dẹp tài nguyên cục bộ
        cleanup(partitions);
    }

    @Override
    public void onPartitionsAssigned(Collection<TopicPartition> partitions) {
        // Khởi tạo các partition mới
        initialize(partitions);
    }
});
```

### Vượt Max Poll Interval

```java
// Nếu xử lý batch mất quá lâu
props.put("max.poll.interval.ms", "300000");  // 5 phút

// Nếu consumer không gọi poll() trong khoảng thời gian này
// → được coi là chết → bị loại khỏi group → rebalance
```

### Các Lỗi Thường Gặp

1. **Rebalance thường xuyên:**
```
Vượt max poll interval → consumer bị loại → rebalance
→ Downtime → mất hiệu năng
```

2. **Không có ConsumerRebalanceListener:**
```
Mất dữ liệu khi rebalance (offset không được commit)
```

3. **Timeout quá ngắn:**
```
session.timeout.ms=5000 → false positive
→ Consumer bị coi là chết → rebalance không cần thiết
```

## Senior Level

### Cài Đặt Nội Bộ

**Group Coordinator:**
```
Broker coordinator lưu trữ trạng thái group:
- Danh sách thành viên (danh sách các consumer)
- Các gán partition
- Các offset đã commit (trong __consumer_offsets)
```

**Giao thức Rebalancing:**
```
Thuật ngữ:
  Group Coordinator — broker quản lý thành viên group.
  JoinGroup — consumer nói "Tôi muốn tham gia group".
  SyncGroup — leader phân phối kết quả gán.

1. Giai đoạn Join:
   - Consumer → request JoinGroup
   - Coordinator → thu thập tất cả các thành viên
   - Coordinator → chọn leader group

2. Giai đoạn Assignment:
   - Leader → tính toán gán
   - Leader → request SyncGroup
   - Coordinator → phân phối các gán

3. Giai đoạn Heartbeat:
   - Các consumer → các request Heartbeat
   - Coordinator → xác nhận còn sống
```

### Cooperative Rebalancing — Chi Tiết

**Incremental Cooperative Rebalancing:**
```
Thay vì dừng hoàn toàn:
1. Thu hồi một số partition
2. Gán các partition mới
3. Tiếp tục làm việc
4. Lặp lại nếu cần

Ưu điểm:
- Downtime tối thiểu
- Giữ tính cục bộ dữ liệu
- Tính khả dụng tốt hơn
```

**Cấu hình:**
```java
props.put("partition.assignment.strategy",
    "org.apache.kafka.clients.consumer.CooperativeStickyAssignor");
```

### Các Tham Số Tinh Chỉnh

```yaml
# Quản lý session
session.timeout.ms: 30000           # 30 giây cho đến khi phát hiện
heartbeat.interval.ms: 10000        # 10 giây (1/3 của session timeout)

# Quản lý poll
max.poll.interval.ms: 300000        # 5 phút cho việc xử lý
max.poll.records: 500               # batch để xử lý

# Chiến lược gán
partition.assignment.strategy: cooperative-sticky
```

### Các Kịch Bản Lỗi

**1. Network Partition:**
```
Consumer mất kết nối đến broker
→ Timeout heartbeat → timeout session → rebalance
→ Khi network phục hồi → consumer kết nối lại → tham gia group
```

**2. GC Pause:**
```
session.timeout.ms=30000, GC pause=35 giây.
Consumer không gửi heartbeat trong 35 giây. Broker chờ 30 giây → loại bỏ →
rebalance. Sau GC, consumer kết nối lại → tham gia group → nhận các partition mới.

GC pause dài → consumer không gửi heartbeat
→ Broker coi consumer đã chết → rebalance
→ Sau GC, consumer biết về rebalance
```

**3. Xử Lý Chậm:**
```
Xử lý batch > max.poll.interval.ms
→ Broker coi consumer đã chết → rebalance
→ Consumer tiếp tục → nhận gán mới
```

### Giám Sát Rebalancing

**Các metrics chính:**
```
kafka.consumer.coordinator:num-rebalances
kafka.consumer.coordinator:time-since-last-rebalance
kafka.consumer:assigned-partitions
kafka.consumer:commit-latency-avg
```

**Các Alert:**
```yaml
- Rebalance thường xuyên hơn mỗi 10 phút → warning
- Rebalance thường xuyên hơn mỗi 5 phút → critical
- Consumer chưa gửi heartbeat > 30s → critical
- Consumer lag tăng → warning
```

### Xử Lý Sự Cố

**1. Xác định nguyên nhân:**
```java
// Log hiển thị:
"Heartbeat session expired" → session.timeout.ms quá ngắn
"Max poll interval exceeded" → xử lý quá chậm
"Member is dead" → consumer crash
```

**2. Giải quyết vấn đề:**
```
Vấn đề heartbeat:
  → Tăng session.timeout.ms
  → Kiểm tra kết nối network

Vấn đề poll interval:
  → Giảm max.poll.records
  → Tối ưu hóa xử lý
  → Tăng max.poll.interval.ms
```

### Các Thực Hành Tốt Nhất

```
✅ Cooperative rebalancing
✅ Session timeout đủ lớn (30s+)
✅ Xử lý message nhanh
✅ ConsumerRebalanceListener để xử lý graceful
✅ Static membership cho các instance ổn định
✅ Giám sát tần suất rebalance

❌ Rebalance thường xuyên mà không điều tra
❌ Eager rebalancing cho production
❌ Timeout quá ngắn
❌ Không có xử lý onPartitionsRevoked
❌ Bỏ qua consumer lag
```

### Các Quyết Định Kiến Trúc

1. **Cooperative rebalancing** — tiêu chuẩn cho production
2. **Static membership** — cho các instance ổn định
3. **Tinh chỉnh đúng cách** — cân bằng giữa thời gian phát hiện và false positive
4. **Monitoring** — phát hiện vấn đề sớm

### Tóm Tắt Cho Senior

- Rebalancing — quá trình quan trọng cho tính khả dụng của group
- Cooperative rebalancing giảm thiểu gián đoạn
- Giao thức group coordinator: join → sync → heartbeat
- Tinh chỉnh tham số rất quan trọng cho sự ổn định
- Giám sát tần suất rebalance — chỉ báo vấn đề sớm

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- Rebalancing — phân phối lại các partition giữa các consumer trong một group
- Trigger: consumer mới, crash, session timeout, thêm partition
- Eager rebalancing: dừng hoàn toàn 5-30 giây; Cooperative: 1-5 giây, việc xử lý tiếp tục
- ConsumerRebalanceListener: commitSync trong onPartitionsRevoked, dọn dẹp trạng thái
- Vượt max poll interval — nguyên nhân phổ biến: consumer không gọi poll() kịp thời
- Giao thức Group Coordinator: JoinGroup → Assignment (Leader) → SyncGroup → Heartbeat
- Static membership (`group.instance.id`) — loại bỏ rebalance khi rolling deploy

**Các câu hỏi phụ thường gặp:**
- *Eager vs cooperative rebalancing là gì?* — Eager: tất cả dừng lại. Cooperative: chỉ các partition đã di chuyển.
- *Điều gì xảy ra với session.timeout quá ngắn?* — False positive, các rebalance không cần thiết.
- *Làm sao tránh rebalance khi GC pause?* — Tăng session.timeout.ms, static membership.
- *Ai tính toán gán?* — Leader consumer (eager) hoặc Group Coordinator (KIP-848, Kafka 3.0+).

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Rebalancing nhanh và không đau đớn" — downtime 5-30 giây (eager)
- "Bạn có thể bỏ qua các rebalance thường xuyên" — dấu hiệu của vấn đề timeout hoặc xử lý
- "Eager rebalancing tốt nhất cho production" — cooperative giảm thiểu gián đoạn
- "Rebalancing không ảnh hưởng đến xử lý" — dừng hoàn toàn với eager
