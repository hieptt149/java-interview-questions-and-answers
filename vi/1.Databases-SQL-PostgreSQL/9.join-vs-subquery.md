# # What is Better: JOIN or Subquery? (JOIN hay subquery tốt hơn?)

## 🟢 Junior Level

**Không có câu trả lời chắc chắn** — điều này tùy thuộc vào tình huống cụ thể. Trong hầu hết các cơ sở dữ liệu hiện đại (bao gồm cả PostgreSQL), optimizer thường chuyển đổi các subquery (truy vấn con) thành JOIN, vì vậy hiệu năng có thể giống hệt nhau.

**Quy tắc đơn giản:**
- **JOIN** — khi bạn cần dữ liệu từ cả hai bảng
- **Subquery (EXISTS/IN)** — khi bạn chỉ cần kiểm tra sự tồn tại

**Ví dụ:**
```sql
-- JOIN: lấy người dùng VÀ đơn hàng của họ
SELECT u.name, o.amount
FROM users u
JOIN orders o ON u.id = o.user_id;

-- EXISTS: kiểm tra xem người dùng có đơn hàng hay không
SELECT * FROM users u
WHERE EXISTS (
    SELECT 1 FROM orders o WHERE o.user_id = u.id
);
```

**Khi nào nên dùng cái gì:**
- Cần các cột từ cả hai bảng → **JOIN**
- Chỉ cần lọc dữ liệu → **EXISTS/IN**
- Logic phức tạp có tổng hợp (aggregation) → **subquery**

## 🟡 Middle Level

### Optimizer xử lý Subquery như thế nào

PostgreSQL có thể thực hiện **Unnesting** (làm phẳng) — chuyển đổi subquery thành JOIN ở cấp độ execution plan. Điều này có nghĩa là subquery bạn viết ra được thực thi về mặt vật lý như một phép join giữa các bảng, thường nhanh hơn.

Thường thì, **Semi-Join** được sử dụng — một loại join đặc biệt: với mỗi dòng trong bảng bên trái, nó kiểm tra xem có ít nhất một dòng khớp trong bảng bên phải hay không, và trả về dòng của bảng bên trái CHỈ MỘT LẦN (không trùng lặp). Không có cú pháp SQL trực tiếp nào cho Semi-Join — nó xảy ra bên trong planner.

```sql
-- Subquery trong WHERE
SELECT * FROM users
WHERE id IN (SELECT user_id FROM orders WHERE amount > 100);

-- Optimizer chuyển đổi thành:
SELECT * FROM users
INNER JOIN (SELECT user_id FROM orders WHERE amount > 100) o
ON users.id = o.user_id;
-- Plan: Hash Semi-Join (rất hiệu quả)
```

### Semi-Join vs JOIN

**Vấn đề với JOIN: Join Amplification (Khuếch đại JOIN)**
```sql
-- ❌ Nếu một người dùng có 10 đơn hàng, họ sẽ xuất hiện 10 lần!
SELECT DISTINCT u.* FROM users u
JOIN orders o ON u.id = o.user_id;
-- Sau đó DISTINCT loại bỏ trùng lặp (tốn thêm sort/hash)

-- ✅ EXISTS sử dụng Semi-Join (không trùng lặp!)
SELECT * FROM users u
WHERE EXISTS (
    SELECT 1 FROM orders o WHERE o.user_id = u.id
);
-- Dừng lại sau lần khớp đầu tiên → nhanh hơn
-- EXISTS sử dụng Semi-Join: ngay khi tìm thấy dòng khớp ĐẦU TIÊN cho dòng
-- của bảng bên trái, việc quét bảng bên phải cho dòng đó dừng lại
-- (short-circuit evaluation - đánh giá ngắn mạch). Không cần xây dựng
-- toàn bộ kết quả join rồi mới thực hiện DISTINCT để loại bỏ trùng lặp.
```

### Optimization Fences (Rào cản tối ưu hóa)

Một số cấu trúc ngăn không cho optimizer làm phẳng subquery:

| Rào cản                 | Điều gì xảy ra                          |
| --------------------- | ------------------------------------- |
| `LIMIT` / `OFFSET`    | Subquery thực thi riêng biệt           |
| `DISTINCT`            | Không thể được kéo vào JOIN             |
| `GROUP BY` / Hàm tổng hợp | Subquery được materialized (vật chất hóa) |
| `UNION` / `INTERSECT` | Node riêng biệt trong plan                  |

```sql
-- ❌ LIMIT tạo ra một rào cản
SELECT * FROM users u
WHERE id IN (SELECT user_id FROM orders ORDER BY amount DESC LIMIT 10);
-- Plan: SubPlan (thực thi cho mỗi dòng!)

-- ✅ Thay thế bằng JOIN LATERAL
SELECT u.*, o.amount
FROM users u
LEFT JOIN LATERAL (
    SELECT amount FROM orders
    WHERE o.user_id = u.id
    ORDER BY amount DESC
    LIMIT 10
) o ON true;
```

### Scalar Subquery (Truy vấn con trả về giá trị đơn) trong SELECT

```sql
-- ❌ KHÔNG TỐT: subquery thực thi cho mỗi dòng
SELECT u.name,
       (SELECT SUM(amount) FROM orders o WHERE o.user_id = u.id) as total
FROM users u;
-- Plan: SubPlan (1,000,000 subquery cho 1,000,000 người dùng!)

-- ✅ TỐT: JOIN + GROUP BY
SELECT u.name, SUM(o.amount) as total
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.name;
-- Plan: Hash Join + HashAggregate (nhanh hơn nhiều!)
```

### CTE (WITH) và việc Materialization (vật chất hóa)

**PostgreSQL 12+:** CTE được inline (nội tuyến) theo mặc định:

**Trước PG 12** CTE LUÔN LUÔN được materialized — đây là một rào cản tối ưu hóa. Subquery bên trong CTE được tính toán một lần, và kết quả được lưu vào một cấu trúc tạm thời. Điều này có thể là điểm cộng (tránh phải tính toán lặp lại) và cũng là điểm trừ (optimizer không thể "nhìn vào bên trong" CTE để áp dụng các bộ lọc từ truy vấn bên ngoài).

```sql
-- PG 12+: CTE này sẽ được inline vào truy vấn chính
WITH active_users AS (
    SELECT * FROM users WHERE status = 'ACTIVE'
)
SELECT * FROM active_users u
JOIN orders o ON u.id = o.user_id;
-- Plan: giống như thể bạn viết JOIN trực tiếp
```

**Kiểm soát việc materialization:**
```sql
-- Ép buộc materialization (tính CTE một lần)
WITH c AS MATERIALIZED (
    SELECT user_id, SUM(amount) as total FROM orders GROUP BY user_id
)
SELECT * FROM users u JOIN c ON u.id = c.user_id;

-- Ép buộc inlining
WITH c AS NOT MATERIALIZED (
    SELECT * FROM orders WHERE amount > 100
)
SELECT * FROM c JOIN users u ON c.user_id = u.id;
```

### Các lỗi thường gặp

1. **Scalar subquery trong SELECT trên dữ liệu lớn**
   ```sql
   -- ❌ Thảm họa về hiệu năng
   SELECT u.name, (SELECT COUNT(*) FROM orders WHERE user_id = u.id)
   FROM users u;  -- 1 triệu dòng → 1 triệu subquery!
   ```

2. **NOT IN với NULL**
   ```sql
   -- ❌ Trả về kết quả rỗng nếu có NULL!
   SELECT * FROM users
   WHERE id NOT IN (SELECT user_id FROM orders);

   -- ✅ Hãy dùng NOT EXISTS
   SELECT * FROM users u
   WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
   ```

3. **DISTINCT thừa với JOIN**
   ```sql
   -- ❌ DISTINCT sau JOIN — dấu hiệu của Join Amplification
   SELECT DISTINCT u.* FROM users u
   JOIN orders o ON u.id = o.user_id;

   -- ✅ EXISTS hiệu quả hơn
   SELECT * FROM users u
   WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
   ```

### So sánh thực tiễn

| Tình huống                 | Công cụ tốt nhất       | Tại sao                                 |
| ------------------------- | --------------- | ------------------------------------ |
| Dữ liệu từ cả hai bảng     | **JOIN**        | Có nhiều chiến lược thực thi nhất         |
| Kiểm tra sự tồn tại           | **EXISTS**      | Hash Semi-Join, không trùng lặp        |
| Lấy dữ liệu phụ thuộc (top-N) | **LATERAL**   | Sử dụng index bên trong                  |
| Tổng hợp theo từng dòng       | **JOIN + GROUP BY** | Một lượt duyệt thay vì N subquery |
| Logic phức tạp có LIMIT  | **LATERAL**     | Planner nhìn thấy được index                 |

## 🔴 Senior Level

### Unnesting và Decorrelation (Khử tương quan)

**Cách optimizer "làm phẳng" subquery:**

```sql
-- Truy vấn gốc
SELECT * FROM users u
WHERE u.id IN (
    SELECT o.user_id FROM orders o
    WHERE o.amount > (SELECT AVG(amount) FROM orders)
);

-- Các bước biến đổi:
-- 1. Scalar subquery AVG → InitPlan (tính một lần)
-- 2. Subquery IN → Hash Semi-Join
-- 3. Plan cuối cùng:
--    InitPlan: AVG(amount)
--    → Hash Semi-Join (users ↔ orders)
```

**Decorrelation (Khử tương quan):**
```sql
-- Correlated subquery (phụ thuộc vào dòng bên ngoài)
SELECT * FROM users u
WHERE EXISTS (
    SELECT 1 FROM orders o WHERE o.user_id = u.id AND o.amount > 100
);

-- Sau khi decorrelation:
-- Hash Semi-Join:
--   1. Xây dựng hash từ orders WHERE amount > 100
--   2. Quét users, kiểm tra sự hiện diện trong hash
-- Độ phức tạp: O(N + M) thay vì O(N × M)!
```

### SubPlan vs InitPlan vs Param

**SubPlan:** Thực thi cho mỗi dòng của truy vấn bên ngoài
```sql
EXPLAIN SELECT u.name,
       (SELECT SUM(amount) FROM orders o WHERE o.user_id = u.id)
FROM users u;

-- Plan:
-- Seq Scan on users
--   SubPlan 1
--     -> Aggregate
--        -> Index Scan on orders (user_id = u.id)
-- ⚠️ Thực thi 1,000,000 lần!
```

**InitPlan:** Thực thi một lần trước truy vấn chính
```sql
EXPLAIN SELECT * FROM users
WHERE amount > (SELECT AVG(amount) FROM orders);

-- Plan:
-- InitPlan 1
--   -> Aggregate (AVG)
--      -> Seq Scan on orders
-- → Seq Scan on users (với bộ lọc từ kết quả InitPlan)
-- ✅ Thực thi 1 lần!
```

### Memoize Node (PostgreSQL 14+)

**Memoize** — một node trong execution plan giúp lưu bộ nhớ đệm (cache) kết quả của subquery. Nếu subquery được gọi lại với cùng tham số, kết quả sẽ được lấy từ cache thay vì thực thi lại. Cache bị giới hạn về bộ nhớ (tham số `memoize_cache_size`, mặc định 10MB cho mỗi node Memoize).

Một tối ưu hóa mang tính cách mạng cho correlated subquery:

```sql
-- Truy vấn với LATERAL (buộc phải dùng Nested Loop)
SELECT u.name, o.amount
FROM users u
LEFT JOIN LATERAL (
    SELECT amount FROM orders o
    WHERE o.user_id = u.id
    ORDER BY created_at DESC
    LIMIT 1
) o ON true;

-- PostgreSQL 14+: có thể chèn thêm Memoize
-- Plan:
-- Nested Loop
--   → Seq Scan on users
--   → Memoize
--       → Limit
--          → Index Scan Backward on orders

-- Memoize lưu bộ nhớ đệm kết quả cho mỗi user_id
-- Nếu user_id lặp lại → lấy từ cache!
-- 🚀 Tăng tốc 10-100 lần trên dữ liệu có sự lặp lại
```

**Giám sát Memoize:**
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ... LATERAL ...;

-- Tìm trong plan:
-- Memoize  (cost=... rows=... actual rows=...)
--   Hits: 500000  ← lấy từ cache
--   Misses: 10000 ← tính toán lại
--   Evictions: 500  ← bị đẩy ra khỏi cache
```

### LATERAL JOIN: Khi nào và tại sao

**Lateral chọn Nested Loop:**
```
LATERAL gần như luôn luôn → Nested Loop
→ Rất tốt nếu bảng outer nhỏ (< 10,000 dòng)
→ Thảm họa nếu bảng outer lớn (> 1,000,000 dòng)
```

**Các giải pháp thay thế cho dữ liệu lớn:**

```sql
-- ❌ LATERAL trên 1 triệu người dùng → chậm
SELECT u.name, last_order.amount
FROM users u
LEFT JOIN LATERAL (
    SELECT amount FROM orders o
    WHERE o.user_id = u.id
    ORDER BY created_at DESC
    LIMIT 1
) last_order ON true;

-- ✅ Window Function → Hash Join
SELECT name, amount
FROM (
    SELECT u.name, o.amount,
           ROW_NUMBER() OVER(PARTITION BY u.id ORDER BY o.created_at DESC) as rn
    FROM users u
    INNER JOIN orders o ON u.id = o.user_id
) sub
WHERE rn = 1;

-- ✅ DISTINCT ON → Sort + Unique
SELECT DISTINCT ON (u.id) u.name, o.amount
FROM users u
INNER JOIN orders o ON u.id = o.user_id
ORDER BY u.id, o.created_at DESC;
```

### CTE: MATERIALIZED vs NOT MATERIALIZED

**Khi nào nên dùng MATERIALIZED:**
```sql
-- CTE được sử dụng nhiều lần → materialization có lợi
WITH expensive_calc AS MATERIALIZED (
    SELECT user_id, SUM(amount) * 1.2 as total
    FROM orders
    GROUP BY user_id
)
SELECT * FROM users u JOIN expensive_calc ec ON u.id = ec.user_id
UNION ALL
SELECT * FROM archived_users au JOIN expensive_calc ec ON au.id = ec.user_id;
-- CTE được tính 1 lần, sử dụng 2 lần
```

**Khi nào nên dùng NOT MATERIALIZED:**
```sql
-- CTE được sử dụng 1 lần + có bộ lọc → inlining tốt hơn
WITH filtered_orders AS NOT MATERIALIZED (
    SELECT * FROM orders WHERE amount > 1000 AND status = 'COMPLETED'
)
SELECT * FROM users u
JOIN filtered_orders fo ON u.id = fo.user_id
WHERE u.created_at > '2024-01-01';
-- Cho phép optimizer "đẩy" bộ lọc u.created_at vào bên trong CTE
```

### Các trường hợp đặc biệt (Edge Cases)

1. **Hàm biến động (Volatile functions) trong subquery**
   ```sql
   -- NOW() ổn định trong phạm vi một truy vấn
   SELECT * FROM users WHERE created_at < NOW();

   -- RANDOM() được tính toán lại mỗi lần!
   SELECT * FROM users WHERE id = (SELECT FLOOR(RANDOM() * 1000000));
   -- Trả về các giá trị KHÁC NHAU cho mỗi dòng!
   ```

2. **Subquery trong UPDATE/DELETE**
   ```sql
   -- ❌ Correlated subquery trong UPDATE → chậm
   UPDATE orders o SET status = 'VIP'
   WHERE user_id IN (SELECT id FROM users WHERE vip = true);

   -- ✅ Cú pháp FROM → JOIN
   UPDATE orders o SET status = 'VIP'
   FROM users u
   WHERE o.user_id = u.id AND u.vip = true;
   -- Plan: Hash Join (nhanh hơn nhiều!)
   ```

3. **Subquery rỗng**
   ```sql
   -- Nếu subquery trả về 0 dòng:
   -- IN () → FALSE
   -- NOT IN () → TRUE (cẩn thận với NULL!)
   -- EXISTS () → FALSE
   -- NOT EXISTS () → TRUE
   ```

### So sánh hiệu năng

| Cách tiếp cận                | Độ phức tạp        | Khi nào sử dụng                         |
| ----------------------- | ----------------- | ------------------------------------ |
| **JOIN**                | O(N + M) với Hash Join | Dữ liệu từ cả hai bảng          |
| **EXISTS/IN**           | O(N + M) với Semi-Join | Kiểm tra sự tồn tại                  |
| **Scalar Subquery**     | O(N × M)          | **Nên tránh** trên dữ liệu lớn             |
| **LATERAL**             | O(N × log M)      | Lấy dữ liệu phụ thuộc, bảng outer nhỏ   |
| **CTE MATERIALIZED**    | O(M) + O(N)       | CTE được sử dụng > 1 lần                   |
| **CTE NOT MATERIALIZED**| Giống như JOIN         | CTE được sử dụng 1 lần                     |

### Kinh nghiệm Production

**Tình huống thực tế #1: SubPlan giết chết API**
- REST API: tính toán số dư cho mỗi trong 10,000 người dùng
- Truy vấn: scalar subquery trong SELECT
- Thời gian: 45 giây (10,000 subquery!)
- Giải pháp:
  ```sql
  -- Thay thế bằng JOIN + GROUP BY
  SELECT u.*, COALESCE(SUM(o.amount), 0) as balance
  FROM users u
  LEFT JOIN orders o ON u.id = o.user_id
  GROUP BY u.id;
  ```
- Kết quả: 200ms (nhanh hơn 225 lần)

**Tình huống thực tế #2: Memoize cứu vãn LATERAL**
- Báo cáo: top-5 đơn hàng cho mỗi khách hàng (100,000 khách hàng)
- LATERAL không có Memoize: > 5 phút
- Sau khi dùng PG 14 với Memoize: 3 giây
- Tỷ lệ Hits/Misses: 95%/5% (nhiều khách hàng có đơn hàng giống nhau trong cache)

**Tình huống thực tế #3: CTE materialization**
- Phân tích dữ liệu: CTE có tổng hợp được dùng trong 4 UNION ALL
- Không có MATERIALIZED: CTE được tính 4 lần → 2 phút
- Với MATERIALIZED: được tính 1 lần → 30 giây
- Nhưng: nếu CTE nhỏ, MATERIALIZED có thể làm chậm đi (chi phí phát sinh)

### Giám sát (Monitoring)

```sql
-- 1. Kiểm tra SubPlan trong plan
EXPLAIN (ANALYZE, BUFFERS)
SELECT u.name, (SELECT COUNT(*) FROM orders WHERE user_id = u.id)
FROM users u;
-- Tìm "SubPlan" → tiềm ẩn vấn đề

-- 2. Kiểm tra hiệu quả của Memoize
EXPLAIN (ANALYZE)
SELECT ... LATERAL ...;
-- Memoize (Hits: X, Misses: Y)
-- Hit rate = Hits / (Hits + Misses)
-- > 80% → tuyệt vời, < 50% → Memoize không giúp ích gì

-- 3. CTE materialization
EXPLAIN (ANALYZE)
WITH c AS MATERIALIZED (...)
SELECT ...;
-- CTE Scan on c → đã materialized
-- Tìm "CTE c" trong các subplan → đã inline

-- 4. Tìm các scalar subquery trong pg_stat_statements
SELECT query, mean_exec_time
FROM pg_stat_statements
WHERE query ~ 'SELECT.*\(SELECT.*FROM.*\).*FROM'
ORDER BY mean_exec_time DESC;
```

### Best Practices (Thực hành tốt nhất)

1. **EXISTS > DISTINCT JOIN** khi kiểm tra sự tồn tại
2. **NOT EXISTS > NOT IN** (tránh bẫy NULL)
3. **Tránh scalar subquery trong SELECT** trên dữ liệu lớn
4. **LATERAL** chỉ dùng cho các tập outer nhỏ (< 10,000 dòng)
5. **Quản lý CTE** một cách có ý thức thông qua MATERIALIZED / NOT MATERIALIZED
6. **UPDATE/DELETE** hãy dùng FROM/USING thay vì subquery
7. **Memoize (PG 14+)** có thể cứu vãn LATERAL — hãy kiểm tra Hit rate
8. Luôn kiểm tra plan bằng `EXPLAIN (ANALYZE)`

### Tóm tắt cho Senior

- Optimizer hỗ trợ **Unnesting** và **Decorrelation** đối với subquery
- **SubPlan** cho mỗi dòng → thảm họa; hãy thay thế bằng JOIN
- **Memoize (PG 14+)** lưu bộ nhớ đệm kết quả LATERAL → hãy kiểm tra Hits/Misses
- **CTE trong PG 12+** được inline theo mặc định; hãy quản lý thông qua MATERIALIZED
- **EXISTS = Semi-Join** (không có Join Amplification)
- **LATERAL ≈ Nested Loop** → chỉ dùng cho các tập outer nhỏ
- **UPDATE/DELETE** thông qua FROM/USING thay vì correlated subquery
- Luôn kiểm tra plan: tìm **SubPlan**, **Batches**, **CTE Scan**

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- PostgreSQL hỗ trợ Unnesting — chuyển đổi subquery thành JOIN (Hash Semi-Join)
- SubPlan = thực thi cho mỗi dòng → O(N × M) → THẢM HỌA
- InitPlan = thực thi một lần → O(M) + O(N) → rất tốt
- EXISTS = Semi-Join: không có Join Amplification (trùng lặp từ JOIN), dừng sau lần khớp đầu tiên
- NOT EXISTS > NOT IN: NOT IN với NULL trả về kết quả rỗng
- Memoize (PG 14+): lưu bộ nhớ đệm kết quả LATERAL → Hit rate > 80% = tuyệt vời
- CTE trong PG 12+: được inline theo mặc định (NOT MATERIALIZED), hãy quản lý một cách tường minh
- Scalar subquery trong SELECT = N subquery → JOIN + GROUP BY tốt hơn
- UPDATE FROM / DELETE USING nhanh hơn correlated subquery
- Luôn kiểm tra EXPLAIN (ANALYZE)

**Các câu hỏi phụ thường gặp:**
- "Tại sao EXISTS tốt hơn DISTINCT JOIN?" → Semi-Join không tạo ra trùng lặp, không cần sort cho DISTINCT
- "Khi nào Memoize không giúp ích?" → Tất cả các key đều duy nhất → 0% Hits
- "CTE nên dùng MATERIALIZED hay NOT MATERIALIZED?" → MATERIALIZED nếu được sử dụng > 1 lần
- "Tại sao scalar subquery trong SELECT lại không tốt?" → N subquery cho N dòng

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "Subquery luôn luôn chậm hơn JOIN" (EXISTS đã decorrelated có thể nhanh hơn)
- ❌ "NOT IN là an toàn" (NULL trả về kết quả rỗng!)
- ❌ "CTE luôn luôn được materialized" (PG 12+ inline theo mặc định)
