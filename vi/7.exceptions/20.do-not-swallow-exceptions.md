# Why you should not swallow exceptions (catch empty)? (Tại sao không nên nuốt exception (empty catch)?)

## Junior Level

### "Nuốt" (swallowing) exception là gì

Đó là việc bắt một exception mà không có hành động nào:

```java
try {
    processOrder(order);
} catch (Exception e) {
    // Rỗng - exception bị "nuốt"
}
// Chương trình tiếp tục như thể không có gì xảy ra
```

### Cơ chế: tại sao exception bị mất

Khi JVM thực thi một khối `catch`, nó **gỡ** exception khỏi stack xử lý lỗi. Nếu khối `catch` rỗng:
1. JVM tạo một object exception (việc này đã tốn chu kỳ CPU cho `fillInStackTrace()`)
2. Đi vào khối `catch` - không có gì ở đó
3. **Tiếp tục thực thi sau `catch`** - object exception trở nên không thể tiếp cận và sẽ bị GC thu gom
4. **Không có code nào ở trên trong stack biết về lỗi** - phương thức đã gọi `processOrder()` nghĩ rằng mọi thứ đều ổn

Nó giống như một tiếng chuông cửa bạn nghe thấy nhưng quyết định không mở - vị khách đã đi, và bạn thậm chí không biết đó là ai.

### Tại sao điều đó tệ

Khi một exception bị nuốt, chương trình đi vào một **trạng thái không nhất quán (inconsistent)**:

```java
try {
    connection.beginTransaction();
    connection.save(order); // SQLException!
    connection.commit();    // Sẽ thực thi - dữ liệu một phần bị mất
} catch (SQLException e) {
    // Rỗng - transaction commit với dữ liệu không đầy đủ
}
```

**Kết quả:** một phần dữ liệu được ghi, một phần thì không. Logic nghiệp vụ bị hỏng. Trong log - im lặng.

### Nên làm gì thay vào đó

```java
// Tối thiểu - ghi log nó
try {
    processOrder(order);
} catch (Exception e) {
    log.error("Failed to process order", e);
}

// Tốt hơn - rethrow
try {
    processOrder(order);
} catch (Exception e) {
    log.error("Failed to process order", e);
    throw new OrderProcessingException("Order failed", e);
}
```

## Middle Level

### Khi nào điều đó là CHẤP NHẬN ĐƯỢC

Chỉ một vài tình huống mà khối catch rỗng (hoặc gần như rỗng) là OK:

**1. Đóng resource (trước Java 7):**
```java
} finally {
    try { if (socket != null) socket.close(); }
    catch (IOException ignored) { /* Không thể làm gì - socket sẽ đóng dù sao đi nữa */ }
}
```
Giải pháp hiện đại: **try-with-resources** (nó tự xử lý các suppressed exception).

**2. Các gián đoạn được lường trước khi shutdown:**
```java
try {
    Thread.sleep(1000);
} catch (InterruptedException e) {
    // Khôi phục trạng thái interrupt - bắt buộc!
    Thread.currentThread().interrupt();
}
```
Ở đây catch không rỗng - chúng ta khôi phục cờ interrupted.

**3. Các thao tác tùy chọn có thể bỏ qua:**
```java
// Caching - nếu cache không khả dụng, tính trực tiếp
try {
    cache.put(key, value);
} catch (CacheException e) {
    // Cache là một tối ưu hóa, không phải một yêu cầu. Việc nó không khả dụng không phải lỗi nghiệp vụ.
    // Tối thiểu - log debug:
    log.debug("Cache unavailable, skipping", e);
}
```

**4. Dọn dẹp khi shutdown:**
```java
try {
    temporaryFile.delete();
} catch (IOException e) {
    // File là tạm, OS sẽ dọn /tmp khi khởi động lại dù sao đi nữa
    log.debug("Failed to delete temp file {}", temporaryFile, e);
}
```

**Nguyên tắc then chốt:** nếu bạn bỏ qua một exception, hãy đảm bảo:
- Đó là một **quyết định có ý thức**, không phải sự lười biếng
- Hậu quả của lỗi **không ảnh hưởng đến logic nghiệp vụ**
- Có ít nhất một `log.debug()` để debug

### Khi nào KHÔNG nên dùng empty catch

1. **Logic nghiệp vụ** - hầu như không bao giờ. Kể cả `log.debug()` cũng tốt hơn sự trống rỗng, vì nó cho một manh mối để debug. Ngoại lệ duy nhất: nếu đặc tả nghiệp vụ nói rõ "bỏ qua lỗi này" - nhưng vẫn ghi log ở DEBUG
2. **Trong transaction** - `SQLException` bị nuốt dẫn tới commit dữ liệu một phần
3. **Trong stream API** - `null` trong collection thay vì lỗi âm thầm phá vỡ downstream
4. **Trong code async** - `CompletableFuture` với exception bị nuốt không bao giờ hoàn thành theo kiểu exceptionally
5. **Trong middleware** - exception bị nuốt trả về client `200 OK` thay vì lỗi

### Hidden Latency (độ trễ ẩn)

Nuốt exception che giấu các vấn đề hiệu suất. Service sập khi timeout, các lỗi bị nuốt - bạn chỉ thấy thao tác chậm mà không hiểu nguyên nhân.

### CPU Spikes

Việc xảy ra và nuốt exception thường xuyên vẫn tải cho CPU trên `fillInStackTrace()`. Exception "im lặng" không phải là "miễn phí".

### Functional Stream

Nuốt bên trong `forEach` hoặc `map` - collection với dữ liệu không đầy đủ mà không có cảnh báo:

```java
list.stream()
    .map(item -> {
        try {
            return process(item);
        } catch (Exception e) {
            // Bị nuốt - kết quả null
            return null;
        }
    })
    .collect(Collectors.toList()); // [result1, null, result3, null]
```

### Global Exception Handler

Nếu bạn nuốt một exception ở giữa chuỗi, `@ControllerAdvice` trong Spring trả về `200 OK` cho client - lừa dối API.

## Senior Level

### Quiet Failure và các hệ thống zombie

Một exception bị nuốt biến hệ thống thành một "zombie" - nó hoạt động, nhưng sai. Không có cơ chế tự chữa lành (self-healing), đây là một thảm họa.

### Static Analysis

Các luật của SonarQube ("Exceptions should not be ignored") và IntelliJ Inspections ("Empty catch block") nên là **chặn (blocking)** trong CI/CD.

### Ghi log ít nhất ở DEBUG

Nếu một exception có thể bị bỏ qua - hãy ghi log nó ít nhất ở level `DEBUG`:

```java
try {
    optionalResource.close();
} catch (IOException e) {
    log.debug("Failed to close optional resource", e);
}
```

Điều này sẽ tiết kiệm nhiều giờ debug.

### Self-Healing System

Nếu bạn bỏ qua một lỗi - nên có một cơ chế **tự chữa lành**:

```java
try {
    cache.put(key, value);
} catch (CacheException e) {
    log.warn("Cache unavailable, falling back to direct computation", e);
    return computeDirectly(); // Tự chữa lành
}
```

### Phát hiện dựa trên metric

```java
try {
    processOrder(order);
} catch (Exception e) {
    meterRegistry.counter("exceptions.swallowed", "type", e.getClass().getSimpleName()).increment();
    log.debug("Swallowed exception", e);
}
```

### Chẩn đoán

- **SonarQube** - chặn các khối catch rỗng
- **IntelliJ Inspections** - tô sáng `catch (Exception e) {}`
- **Prometheus/Grafana** - cảnh báo dựa trên các bất thường trong các exception bị nuốt
- **Thread Dump** - nếu thread "treo" sau một exception bị nuốt

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Nuốt exception đưa chương trình vào trạng thái không nhất quán mà không có bản ghi log
- `catch` rỗng vẫn tốn CPU trên `fillInStackTrace()` - exception "im lặng" không miễn phí
- Các tình huống chấp nhận được: đóng resource (trước Java 7), `InterruptedException` với khôi phục cờ, cache tùy chọn
- Tối thiểu - `log.debug()` kể cả khi bỏ qua có ý thức
- Trong transaction, `SQLException` bị nuốt = commit dữ liệu một phần
- Trong code async, exception bị nuốt = `CompletableFuture` không bao giờ hoàn thành theo kiểu exceptionally
- SonarQube và IntelliJ Inspections nên chặn các khối catch rỗng trong CI/CD

**Các câu hỏi phụ thường gặp:**
- **Khi nào CÓ THỂ nuốt một exception?** - Các thao tác tùy chọn (cache), dọn dẹp khi shutdown, nhưng tối thiểu với `log.debug()`
- **Làm gì với `InterruptedException`?** - Khôi phục cờ: `Thread.currentThread().interrupt()`
- **Tại sao nó thảm họa trong transaction?** - Lỗi bị nuốt = commit một phần, dữ liệu hỏng
- **Cách phát hiện vấn đề trong production?** - Các luật SonarQube, metric swallowed exception của Prometheus, thread dump

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi có các khối catch rỗng khắp nơi nếu lỗi không nghiêm trọng" - đây là một hệ thống zombie
- "Tôi nuốt exception trong logic nghiệp vụ" - không bao giờ chấp nhận được
- "Catch rỗng không ảnh hưởng hiệu suất" - `fillInStackTrace()` tốn chu kỳ CPU
- "Tôi không cần log, tôi biết lỗi xảy ra" - không có log thì không có debug
