# How does consumer balancing work in a group (Cân bằng consumer trong một group hoạt động như thế nào)

---

## 🟢 Junior Level

### Cân Bằng Là Gì?

**Cân bằng (Balancing)** là quá trình tự động phân phối các partition giữa các consumer trong một group. Chính Kafka quyết định consumer nào đọc các partition nào.

**Tại sao:** không có nó, bạn sẽ phải gán thủ công các partition cho mỗi consumer. Khi số lượng consumer hoặc partition thay đổi — mọi thứ được tính toán lại tự động.

### Phép So Sánh

Hãy nghĩ về một **tiệm pizza** nơi bạn cần cắt pizza (các partition) cho bạn bè (các consumer):
- 3 miếng, 3 người bạn → mỗi người nhận 1 miếng
- 3 miếng, 2 người bạn → một người nhận 2 miếng, người kia nhận 1 miếng
- 3 miếng, 5 người bạn → 3 người nhận mỗi người 1 miếng, 2 người đói

### Quy Tắc Cơ Bản

```
Số lượng consumer đang hoạt động <= Số lượng partition
```

### Ví Dụ

```
3 partition, 3 consumer:
  C1 → P0
  C2 → P1
  C3 → P2  ← cân bằng lý tưởng

Thêm C4:
  C1 → P0
  C2 → P1
  C3 → P2
  C4 → chờ (không có partition tự do)
```

### Cách Nó Hoạt Động Trong Code

```java
// Tất cả các consumer với cùng group.id
props.put("group.id", "my-group");
consumer.subscribe(List.of("orders"));
// Kafka sẽ tự động phân phối các partition
```

## 🟡 Middle Level

### Các Chiến Lược Cân Bằng

| Chiến lược              | Thuật toán                   | Khi nào dùng                                                                                                                                                            |
| --------------------- | --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Range**             | Chia các partition theo dải | Hoạt động tốt khi số partition là bội số của số consumer. Với phép chia lẻ — không đồng đều. Cho production với scaling động, CooperativeSticky tốt hơn.          |
| **RoundRobin**        | Luân phiên các partition       | Khi bạn cần sự đồng đều                                                                                                                                               |
| **Sticky**            | Giảm thiểu di chuyển          | Production (Kafka 2.2+)                                                                                                                                                |
| **CooperativeSticky** | Di chuyển từng bước       | Production (Kafka 2.3+, khuyến nghị)                                                                                                                                   |

### Range Assignor — Chi Tiết

```
Partition 0,1,2,3 → 2 consumer:
  C1: 0, 1  (2 partition)
  C2: 2, 3  (2 partition)
  → Đồng đều

Partition 0,1,2,3,4 → 2 consumer:
  C1: 0, 1, 2  (3 partition)
  C2: 3, 4     (2 partition)
  → Không đồng đều! (Range = numPartitions / numConsumers)
```

### RoundRobin Assignor

```
Partition 0,1,2,3,4 → 2 consumer:
  C1: 0, 2, 4  (3 partition)
  C2: 1, 3     (2 partition)
  → Tốt hơn một chút với số lẻ
```

### Quá Trình Rebalancing

```
1. Sự kiện kích hoạt (consumer mới, crash, timeout)
2. Group coordinator bắt đầu rebalance
3. Tất cả các consumer nhận thông báo
4. Tất cả các consumer dừng đọc (eager)
   hoặc tiếp tục với một số partition (cooperative)
5. Gán mới được tính toán
6. Gán được phân phối đến các consumer
7. Các consumer bắt đầu đọc các partition mới
```

### ConsumerRebalanceListener

```java
consumer.subscribe(List.of("orders"), new ConsumerRebalanceListener() {
    @Override
    public void onPartitionsRevoked(Collection<TopicPartition> partitions) {
        // 1. Commit offset trước khi mất partition
        consumer.commitSync();
        // 2. Dọn dẹp tài nguyên cục bộ
        cleanup(partitions);
    }

    @Override
    public void onPartitionsAssigned(Collection<TopicPartition> partitions) {
        // 3. Khởi tạo các partition mới
        initialize(partitions);
    }
});
```

### Vấn Đề Chaos Rebalancing

```
session.timeout.ms=10000, xử lý batch = 15 giây,
max.poll.interval.ms=300000. Consumer không thể gọi poll() kịp thời → bị loại →
rebalance → tải lên các consumer còn lại tăng → một cái khác crash → tuyết lở.

Các consumer crash → rebalance → các consumer mới crash → chu kỳ

Nguyên nhân:
- session.timeout.ms quá ngắn
- Xử lý lâu (vượt max.poll.interval.ms)
- Vấn đề memory/CPU

Giải pháp:
- Tăng timeout
- Tối ưu hóa xử lý
- Thêm monitoring
```

### So Sánh Chiến Lược

| Tiêu chí                           | Range   | RoundRobin                                     | Sticky   | CooperativeSticky   |
| ---------------------------------- | ------- | ---------------------------------------------- | -------- | ------------------- |
| Đồng đều                         | ⚠️      | ✅                                              | ✅        | ✅                   |
| Giảm thiểu di chuyển                  | ❌       | ❌                                              | ✅        | ✅                   |
| Downtime khi rebalance              | Hoàn toàn    | Hoàn toàn                                           | Hoàn toàn     | Một phần             |
| Phiên bản Kafka                      | Tất cả     | Tất cả                                            | 2.2+     | 2.3+                |
| Server-Side Assignment (KIP-848)  | 3.0+    | Loại bỏ round-trip SyncGroup, rebalance nhanh hơn |         |                     |

### Các Lỗi Thường Gặp

| Lỗi                         | Hậu quả                          | Giải pháp                              |
| ------------------------------- | ------------------------------------ | -------------------------------------- |
| Rebalance thường xuyên             | Downtime hệ thống liên tục             | Tăng timeout, static membership  |
| Không có ConsumerRebalanceListener    | Mất offset khi rebalance             | Luôn dùng listener                   |
| Phân phối không đồng đều             | Một consumer bị quá tải           | Assignor CooperativeSticky            |
| Range assignor trong production    | Không đồng đều + downtime hoàn toàn           | Chuyển sang CooperativeSticky        |

## 🔴 Senior Level

### Giao Thức Group Coordinator — Sơ Đồ Đầy Đủ

```
Giai đoạn 1: JoinGroup
┌──────────────┐          ┌──────────────────┐          ┌──────────────┐
│  Consumer A  │          │ Group Coordinator│          │  Consumer B  │
└──────┬───────┘          └────────┬─────────┘          └──────┬───────┘
       │ JoinGroup Request          │                          │
       │ (group.id, memberId)       │                          │
       │───────────────────────────►│                          │
       │                            │ JoinGroup Request        │
       │                            │◄─────────────────────────│
       │                            │                          │
       │ Leader được chọn (đầu tiên       │                          │
       │ trong danh sách thành viên)            │                          │
       │                            │                          │
       │◄───────────────────────────│ JoinGroup Response       │
       │ (leaderId, allMembers)     │ (memberId, leaderId)     │
       │                            │─────────────────────────►│

Giai đoạn 2: Assignment (trên Leader)
       │                            │                          │
       │ Leader tính toán            │                          │
       │ gán qua             │                          │
       │ PartitionAssignor          │                          │
       │ assignment = {             │                          │
       │   A: [P0, P1],             │                          │
       │   B: [P2]                  │                          │
       │ }                          │                          │

Giai đoạn 3: SyncGroup
       │                            │                          │
       │ SyncGroup Request          │                          │
       │ (gán cho tất cả)             │                          │
       │───────────────────────────►│                          │
       │                            │                          │
       │                            │◄─────────────────────────│ SyncGroup Response
       │                            │                          │ (gán riêng của mình)
       │◄───────────────────────────│                          │
       │ SyncGroup Response         │                          │
       │ (gán: P0, P1)     │                          │
```

**Kafka 3.0+ (KIP-848):** Assignment được tính toán trên Coordinator, không phải Leader. Loại bỏ round-trip SyncGroup.

### Eager vs Cooperative Rebalancing — Nội Bộ

**Eager Rebalancing:**
```java
// org.apache.kafka.clients.consumer.internals.AbstractCoordinator
// onJoinComplete:
//   1. onPartitionsRevoked(TẤT CẢ các partition)  // Dừng MỌI THỨ
//   2. newAssignment = computeAssignment()
//   3. onPartitionsAssigned(newAssignment)  // Bắt đầu MỚI
// Dừng hoàn toàn = dừng hoàn toàn
```

**Cooperative Rebalancing:**
```java
// CooperativeStickyAssignor:
//   1. onPartitionsRevoked(TẬP HỢP CON partition)  // Chỉ những cái đang rời đi
//   2. onPartitionsAssigned(TẬP HỢP CON partition)  // Chỉ những cái mới
//   3. Tiếp tục làm việc với các partition còn lại

// Thuật toán:
//   currentAssignment = {P0, P1, P2}
//   newAssignment = {P0, P3}  // P1 và P2 rời đi, P3 được thêm vào
//   revoked = {P1, P2}         // Chỉ những cái này
//   assigned = {P3}            // Chỉ những cái này
//   tiếp tục xử lý P0     // Đừng dừng lại!
```

**Incremental Cooperative Rebalancing:**
```
Với nhiều thay đổi:
  Vòng 1: thu hồi P1, gán P3
  Vòng 2: thu hồi P2, gán P4
  ...
  Mỗi vòng — ngắn (thường < 1 giây)
  Việc xử lý tiếp tục trên các partition còn lại
```

### Static Membership — Cách Nó Hoạt Động Nội Bộ

```java
props.put("group.instance.id", "consumer-1");
```

**Giao thức:**
```
Consumer động (không có group.instance.id):
  Join → được gán memberId = UUID → restart = memberId mới → rebalance

Consumer tĩnh (có group.instance.id):
  Join → được gán memberId = group.instance.id
  → restart = cùng memberId → KHÔNG rebalance (trong session.timeout)
  → Coordinator chờ session.timeout.ms trước khi loại bỏ
```

**Điều Kiện Để Không Rebalance:**
- Consumer quay lại trong `session.timeout.ms`
- `group.instance.id` không được dùng bởi consumer khác
- Số lượng partition không thay đổi

**group.instance.id Trùng Lặp:**
```
Nếu hai consumer có cùng group.instance.id:
  Cái thứ hai nhận FencedInstanceIdException
  → Consumer thứ hai chấm dứt
  → Điều này ngăn chặn xử lý trùng lặp
```

### Cấu Hình Production

```yaml
# Cấu hình production tối ưu
group.id: order-processors
group.instance.id: consumer-${HOSTNAME}     # Static membership
partition.assignment.strategy: cooperative-sticky
session.timeout.ms: 30000                    # 30 giây
heartbeat.interval.ms: 10000                 # 1/3 của session timeout
max.poll.interval.ms: 300000                 # 5 phút
max.poll.records: 500                        # batch để xử lý
enable.auto.commit: false                    # Manual commit
```

### Edge Case (3+)

1. **Cascading Rebalance (Thundering Herd):** Một consumer crash → rebalance → các consumer còn lại nhận nhiều partition hơn → tải tăng → một consumer khác crash do quá tải → một rebalance khác → tuyết lở. **Giải pháp:** Tăng `session.timeout.ms`, dùng `max.poll.records` để kiểm soát tải, thiết lập các alert monitoring khi consumer lag tăng.

2. **Rebalance Trong Quá Trình Deployment:** Với rolling deploy N instance và eager rebalancing, N rebalance xảy ra. Mỗi rebalance = downtime 5-30 giây. Với 20 instance = downtime 100-600 giây. **Giải pháp:** Static membership + cooperative rebalancing = 0 rebalance trong quá trình rolling deploy.

3. **Partition Stall Sau Rebalance:** Sau rebalance, một consumer mới nhận một partition và bắt đầu từ offset đã commit. Nếu xử lý là stateful (ví dụ: windowed aggregation), consumer mới không có trạng thái cục bộ → kết quả không chính xác cho đến khi tính toán lại hoàn toàn. **Giải pháp:** External state store (RocksDB, Redis) theo key partition; hoặc state replay khi gán.

4. **Cross-Rack Rebalance:** Trong một cluster multi-rack, khi gán các partition cho một consumer ở rack khác, độ trễ tăng (round-trip network). Range/RoundRobin không tính đến rack-awareness. **Giải pháp:** Custom PartitionAssignor với gán nhận biết rack; hoặc Consumer Sidecar trong cùng rack với các broker.

5. **Rebalance Storm Với K8s HPA:** Horizontal Pod Autoscaler thêm pod khi CPU tăng → các consumer mới kích hoạt rebalance → xử lý chậm lại (overhead rebalance) → CPU tăng thêm nữa → HPA thêm nhiều pod hơn → vòng lặp vô hạn. **Giải pháp:** Đừng dùng HPA cho các Kafka consumer. Thay vào đó — custom metric (consumer lag) với các ngưỡng và khoảng thời gian cooldown.

### Các Con Số Hiệu Năng

| Chỉ số                                  | Eager              | Cooperative                |
| --------------------------------------- | ------------------ | -------------------------- |
| Độ trễ rebalance                       | 5-30 giây       | 1-5 giây                |
| Xử lý trong quá trình rebalance             | Dừng hoàn toàn          | Tiếp tục (một phần)        |
| Di chuyển partition                      | Tất cả                | Từng bước                |
| Tác động lên consumer lag                  | Cao (tăng đột biến 2-10x) | Thấp (tăng đột biến 1.2-2x)         |
| Số lần rebalance mỗi rolling deploy | N (mỗi instance)   | 0 (với static membership) |

### Câu Chuyện Production Thực Tế

> **Tình huống:** Một dịch vụ streaming với 25 consumer trong group `event-processors` (25 partition). Range assignor, dynamic membership. Mỗi đêm lúc 02:00 — rolling deploy tự động (cập nhật container).
>
> **Vấn đề:** 25 rebalance tuần tự × 15 giây = 375 giây (6+ phút) downtime mỗi đêm. Trong thời gian này, lag tăng đến 500K event. Buổi sáng người dùng thấy các đề xuất "bị chậm".
>
> **Vấn đề bổ sung:** Range assignor với 25 partition và 24 consumer (một cái đang rebalance) gán 2 partition cho một consumer và 1 cho các cái còn lại. Consumer bị quá tải crash → một rebalance khác → một crash khác → lỗi dây chuyền.
>
> **Chẩn đoán:**
> ```
> kafka-consumer-groups.sh --describe --group event-processors
> # STATE=Rebalancing → STATE=Stable → STATE=Rebalancing (chu kỳ)
> # Lag: 0 → 500K → 0 (trong vòng 15 phút sau deploy)
> ```
>
> **Giải pháp:**
> 1. `CooperativeStickyAssignor` — rebalance trở thành 2 giây thay vì 15
> 2. `group.instance.id=${POD_NAME}` — rolling deploy = 0 rebalance
> 3. `session.timeout.ms=45000`, `heartbeat.interval.ms=15000` — biên độ timeout
> 4. ConsumerRebalanceListener với commitSync + state flush
> 5. K8s PodDisruptionBudget: maxUnavailable=1
> 6. HPA dựa trên lag thay vì CPU (custom metric qua Prometheus Adapter)
>
> **Kết quả:** Rolling deploy — 0 rebalance, 0 downtime, lag < 1K.
>
> **Bài học:** Eager rebalancing + dynamic membership + rolling deploy = lỗi dây chuyền được đảm bảo. Cooperative + static membership = deploy không downtime.

### Các Thực Hành Tốt Nhất Cho Highload

1. **CooperativeStickyAssignor** — tiêu chuẩn cho production (Kafka 2.3+)
2. **Static membership** (`group.instance.id`) — loại bỏ rebalance khi rolling deploy
3. **Tinh chỉnh heartbeat:** `heartbeat.interval.ms = session.timeout.ms / 3`
4. **ConsumerRebalanceListener** — commitSync + dọn dẹp trạng thái trong `onPartitionsRevoked`
5. **Giám sát tần suất rebalance** — alert khi > 1 rebalance mỗi 10 phút
6. **Tinh chỉnh max.poll.records** theo độ trễ — mục tiêu: xử lý < max.poll.interval.ms
7. **Đừng dùng HPA dựa trên CPU** — hãy dùng custom metric (consumer lag)
8. **PodDisruptionBudget** — maxUnavailable=1 để ngăn các rebalance dây chuyền
9. **Nhận biết cross-rack** — custom assignor cho các cluster multi-rack
10. **Xử lý stateful** — external state store (RocksDB, Redis) theo key partition

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- Cân bằng = phân phối tự động các partition giữa các consumer trong một group
- Các chiến lược: Range (không đồng đều), RoundRobin, Sticky, CooperativeSticky (khuyến nghị)
- Cooperative rebalancing: di chuyển từng bước, việc xử lý tiếp tục trên các partition còn lại
- ConsumerRebalanceListener là bắt buộc: commitSync trong onPartitionsRevoked
- Static membership (`group.instance.id`) — 0 rebalance khi rolling deploy
- Chaos rebalance: một cái crash → tải tăng → một cái khác crash → tuyết lở
- Tinh chỉnh heartbeat: `heartbeat.interval.ms = session.timeout.ms / 3`

**Các câu hỏi phụ thường gặp:**
- *Cascading rebalance là gì?* — Một consumer crash → tải lên các cái khác → một cái khác crash → tuyết lở.
- *Tại sao HPA dựa trên CPU tồi cho Kafka?* — Rebalance làm chậm xử lý → CPU tăng → nhiều pod hơn → vòng lặp vô hạn.
- *ConsumerRebalanceListener làm gì?* — Commit offset và dọn dẹp trạng thái trước khi mất partition.
- *Làm sao tránh rebalance khi deploy?* — Static membership + CooperativeStickyAssignor.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Range assignor là tiêu chuẩn cho production" — không đồng đều, hãy dùng CooperativeSticky
- "Nhiều consumer hơn = luôn nhiều throughput hơn" — bị giới hạn bởi số lượng partition
- "Rebalancing là tức thì" — 5-30 giây (eager), 1-5 (cooperative)
- "Bạn có thể bỏ qua session.timeout.ms" — quá ngắn = các rebalance giả
