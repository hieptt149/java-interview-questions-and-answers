# What is the difference between synchronized method and synchronized block? (Sự khác biệt giữa synchronized method và synchronized block là gì?)

---

## Junior Level

### Hiểu biết cơ bản

Cả hai cách đều cung cấp đồng bộ hóa, nhưng chúng khác nhau ở **cái gì chính xác** bị khóa và **object nào** được dùng làm khóa.

### synchronized method

```java
public class Counter {
    private int count = 0;

    // Khóa TOÀN BỘ method
    // Object khóa: this (instance hiện tại)
    public synchronized void increment() {
        count++;
    }

    // Static method
    // Object khóa: Counter.class (object class)
    public static synchronized void resetAll() {
        // ...
    }
}
```

### synchronized block

```java
public class Counter {
    private int count = 0;
    private final Object lock = new Object();

    public void increment() {
        // Khóa CHỈ block này
        // Object khóa: bất kỳ object nào được chỉ định
        synchronized(lock) {
            count++;
        }
    }
}
```

### Bảng so sánh

| Đặc điểm               | synchronized method                                                    | synchronized block                                                    |
| ---------------------- | -------------------------------------------------------------------- | --------------------------------------------------------------------- |
| **Object khóa**        | Luôn là `this` (hoặc `Class`)                                        | Bất kỳ object nào                                                     |
| **Phạm vi khóa**       | Toàn bộ method                                                       | Chỉ block được chỉ định                                               |
| **Tính dễ đọc**        | Cao hơn (khai báo — declarative)                                    | Thấp hơn (nhiều lồng nhau hơn)                                        |
| **Tính linh hoạt**     | Thấp                                                                 | Cao                                                                   |
| **Tính an toàn**       | Thấp hơn (bất kỳ code bên ngoài nào cũng có thể acquire `this` và chặn method) | Cao hơn (object khóa private không truy cập được từ bên ngoài, ít rủi ro deadlock hơn) |

### Khi nào dùng cái nào

- **Method** — khi toàn bộ method phải atomic và không có vấn đề với việc truy cập `this` từ bên ngoài
- **Block** — khi chỉ một phần của method cần đồng bộ hóa, hoặc bạn cần kiểm soát object khóa

## Middle Level

### Khác biệt ở mức Bytecode

#### synchronized block

Dùng các lệnh **`monitorenter`** và **`monitorexit`** tường minh:

```java
public void increment() {
    synchronized(lock) {
        count++;
    }
}
```

Bytecode:
```
public void increment();
  Code:
     0: aload_0
     1: getfield      #2  // Field lock:Ljava/lang/Object;
     4: dup
     5: astore_1
     6: monitorenter        // ← ACQUIRE
     7: aload_0
     8: dup
     9: getfield      #3    // Field count:I
    12: iconst_1
    13: iadd
    14: putfield      #3    // Field count:I
    17: aload_1
    18: monitorexit         // ← RELEASE (lối ra bình thường)
    19: goto          27
    22: astore_2
    23: aload_1
    24: monitorexit         // ← RELEASE (khi có exception)
    25: aload_2
    26: athrow
    27: return
```

#### synchronized method

Dùng cờ **`ACC_SYNCHRONIZED`** trong các thuộc tính của method:

```java
public synchronized void increment() {
    count++;
}
```

Bytecode (chú ý — KHÔNG có monitorenter/monitorexit!):
```
public synchronized void increment();
  flags: ACC_PUBLIC, ACC_SYNCHRONIZED  // ← Cờ đồng bộ hóa
  Code:
    stack=3, locals=1, args_size=1
       0: aload_0
       1: dup
       2: getfield      #2  // Field count:I
       5: iconst_1
       6: iadd
       7: putfield      #2  // Field count:I
      10: return
```

JVM tự động acquire và release monitor khi gọi một method có cờ này.

**ACC_SYNCHRONIZED** — một cờ trong bytecode (ACC = access flags). JVM thấy cờ này và tự động bọc lời gọi method trong monitor enter/exit.

### Độ mịn (Granularity — phạm vi)

```java
// XẤU: synchronized method khóa toàn bộ method
public synchronized void processOrder(Order order) {
    validate(order);        // Không cần khóa
    calculatePrice(order);  // Không cần khóa
    updateInventory(order); // Cần khóa
    sendNotification(order);// Không cần khóa (thao tác I/O!)
}

// TỐT: synchronized block chỉ cho vùng critical
public void processOrder(Order order) {
    validate(order);         // Không khóa
    calculatePrice(order);   // Không khóa

    synchronized(inventoryLock) {
        updateInventory(order); // Chỉ cái này bị khóa
    }

    sendNotification(order); // Không khóa
}
```

### Private Lock

```java
public class SafeCounter {
    // XẤU: ai đó bên ngoài có thể làm synchronized(counter)
    public synchronized void increment() {
        count++;
    }

    // TỐT: private lock — không ai bên ngoài acquire được nó
    private final Object lock = new Object();

    public void increment() {
        synchronized(lock) {
            count++;
        }
    }
}
```

**Tại sao private lock tốt hơn:**

1. **Đóng gói** — code bên ngoài không thể chặn object của bạn
2. **Ngăn deadlock** — code bên ngoài không thể tạo deadlock với khóa của bạn
3. **Ngăn starvation** — code bên ngoài không thể làm đói (starve) các method của bạn
4. **Nhiều khóa** — bạn có thể có các khóa khác nhau cho các resource khác nhau

### Nhiều khóa trong một class

```java
public class UserProfileCache {
    private final Map<Integer, Profile> profiles = new HashMap<>();
    private final Map<Integer, Avatar> avatars = new HashMap<>();

    // Các khóa riêng cho các resource độc lập
    private final Object profilesLock = new Object();
    private final Object avatarsLock = new Object();

    public Profile getProfile(int id) {
        synchronized(profilesLock) {
            return profiles.get(id);
        }
    }

    public Avatar getAvatar(int id) {
        synchronized(avatarsLock) {
            return avatars.get(id);
        }
    }

    // Cả hai khóa đồng thời
    public void clearAll() {
        synchronized(profilesLock) {
            synchronized(avatarsLock) {
                profiles.clear();
                avatars.clear();
            }
        }
    }
}
```

---

## Khi nào synchronized method là một lựa chọn hợp lý

1. **Các method nhỏ** — toàn bộ method cần phải atomic
2. **Các inner class** — không có truy cập `this` từ bên ngoài
3. **Không có tranh chấp** — chỉ một thread truy cập object

**Khi nào synchronized block tốt hơn:** khi bạn cần khóa chỉ một phần của method, hoặc khi bạn cần một object khóa riêng.

## Senior Level

### Bên trong: cờ ACC_SYNCHRONIZED

Một `synchronized` method KHÔNG chứa các lệnh monitorenter/monitorexit trong bytecode. Thay vào đó, JVM kiểm tra cờ khi gọi method:

```
// Mã giả của JVM khi gọi method:
if (method.hasFlag(ACC_SYNCHRONIZED)) {
    monitor.enter(method.isStatic() ? clazz : receiver);
    try {
        invokeMethod();
    } finally {
        monitor.exit(method.isStatic() ? clazz : receiver);
    }
}
```

Cách này chạy nhanh hơn một chút (khác biệt ~0-5%, không đáng chú ý trên thực tế), vì nó không cần các lệnh bổ sung trong thân method.

### Các tối ưu hóa của trình biên dịch JIT

#### Lock Coarsening

```java
// Trước tối ưu:
for (int i = 0; i < items.size(); i++) {
    synchronized(lock) {
        total += items.get(i).price;
    }
}

// Sau Lock Coarsening:
synchronized(lock) {
    for (int i = 0; i < items.size(); i++) {
        total += items.get(i).price;
    }
}
```

JIT gộp nhiều khóa trên cùng một object thành một khóa lớn.

**Quan trọng:** Điều này chỉ hoạt động nếu JIT có thể chứng minh rằng bên trong vòng lặp không có điểm nào mà một thread khác có thể nhìn thấy một trạng thái trung gian.

#### Lock Elision

```java
public void process() {
    // Object này KHÔNG escape khỏi method
    StringBuilder sb = new StringBuilder();
    synchronized(sb) { // JIT sẽ loại bỏ khóa này!
        sb.append("data");
    }
}
```

Escape Analysis xác định:
1. **GlobalEscape** — object được trả về hoặc lưu vào một field → khóa KHÔNG bị loại bỏ
2. **ArgEscape** — object được truyền làm argument nhưng không được lưu → khóa có thể bị loại bỏ
3. **NoEscape** — object hoàn toàn cục bộ → khóa bị loại bỏ

Với `synchronized(this)`, điều này hoạt động ít thường xuyên hơn, vì `this` gần như luôn "escape".

### Bảng so sánh (nâng cao)

| Đặc điểm          | synchronized method     | synchronized block                     |
| ----------------- | ----------------------- | -------------------------------------- |
| **Bytecode**      | cờ `ACC_SYNCHRONIZED`   | các lệnh `monitorenter/exit`           |
| **Object khóa**   | Luôn là `this` hoặc `Class`| Bất kỳ object nào (ưu tiên `private final`) |
| **Độ tin cậy**    | Thấp hơn (khóa public)  | Cao hơn (khóa được đóng gói)           |
| **Lock Elision**  | Hiếm khi hoạt động      | Thường xuyên hoạt động                 |
| **Độ mịn**        | Toàn bộ method          | Chỉ vùng critical                      |
| **I/O bên trong** | Chặn trong lúc I/O      | Có thể dời I/O ra ngoài khóa           |

### Hiệu năng và tải cao (Highload)

#### Tránh Static Synchronized

```java
// RẤT XẤU: khóa mức class
public class Config {
    private static Map<String, String> settings = new HashMap<>();

    public static synchronized void set(String key, String value) {
        settings.put(key, value); // Chặn TẤT CẢ những ai dùng Config.class
    }
}
```

Đây là loại đồng bộ hóa nguy hiểm nhất — nó có thể làm tê liệt toàn bộ hệ thống.

**Giải pháp:**

```java
public class Config {
    private static final Map<String, String> settings = new ConcurrentHashMap<>();
    private static final Object settingsLock = new Object();

    public static void set(String key, String value) {
        settings.put(key, value); // ConcurrentHashMap — lock-free
    }
}
```

#### Ảnh hưởng hiệu năng

| Thao tác              | Thời gian | Ghi chú                   |
| --------------------- | --------- | ------------------------- |
| Method (không tranh chấp) | ~10-20 ns | overhead ACC_SYNCHRONIZED |
| Block (không tranh chấp)  | ~10-20 ns | monitorenter/exit         |
| Method (có tranh chấp)    | ~1000+ ns | Context switch            |
| Block (có tranh chấp)     | ~1000+ ns | Context switch            |
| Block (private lock)  | ~10-20 ns | Ít tranh chấp hơn         |

### Best Practices

1. **Ưu tiên synchronized block** — nhiều kiểm soát hơn
2. **Dùng private final Object lock** — đóng gói
3. **Giảm thiểu phạm vi khóa** — đừng chặn I/O
4. **Tránh synchronized(this)** — ai đó bên ngoài có thể chặn
5. **Tránh static synchronized** — khóa mức class nguy hiểm
6. **Cân nhắc ConcurrentHashMap** — thường tốt hơn synchronized HashMap
7. **Giám sát tranh chấp** — nếu tăng dần, chuyển sang segmented lock

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- synchronized method dùng cờ ACC_SYNCHRONIZED, block dùng các lệnh monitorenter/monitorexit
- synchronized method khóa toàn bộ method trên `this` (hoặc `Class` cho static); block chỉ khóa phần được chỉ định trên bất kỳ object nào
- Private lock (`private final Object lock`) an toàn hơn: code bên ngoài không thể acquire khóa của bạn và tạo deadlock
- JIT áp dụng Lock Elision cho synchronized block (object cục bộ) thường xuyên hơn cho synchronized(this)
- Độ mịn: block cho phép dời I/O và các thao tác dài ra ngoài đồng bộ hóa
- Hiệu năng khi không tranh chấp là như nhau (~10-20 ns), khác biệt nằm ở tính linh hoạt và an toàn

**Các câu hỏi phụ thường gặp:**
- **Tại sao synchronized(this) nguy hiểm?** — Bất kỳ code bên ngoài nào cũng có thể làm `synchronized(obj)` và chặn các method của bạn
- **Có thể có nhiều khóa trong một class không?** — Có, các private final Object khác nhau cho các resource khác nhau (profiles, avatars, v.v.)
- **Khi nào synchronized method là một lựa chọn hợp lý?** — Các method nhỏ, toàn bộ method là atomic, không có truy cập `this` từ bên ngoài
- **Tại sao static synchronized nguy hiểm?** — Khóa mức class (`ClassName.class`) — một khóa cho TẤT CẢ các instance

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Synchronized method nhanh hơn block" — không, hiệu năng như nhau khi không tranh chấp
- "Synchronized(this) an toàn nếu class là nội bộ" — nói chung là không, đóng gói bị phá vỡ
- "Monitorenter tồn tại trong synchronized method" — không, có cờ ACC_SYNCHRONIZED
- "Private lock chỉ để cho đẹp" — không, nó ngăn deadlock và starvation từ bên ngoài
