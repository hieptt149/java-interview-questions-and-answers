# What is better: extend Exception or RuntimeException? (Cái nào tốt hơn: extends Exception hay RuntimeException?)

## Junior Level

**Câu hỏi then chốt:** bên gọi có nên bị **ép buộc** phải xử lý lỗi này không?

**Cây quyết định (Decision Tree):**
1. Lỗi đầu vào/validation -> `IllegalArgumentException` (unchecked)
2. Lỗi quy tắc nghiệp vụ -> `BusinessException` (unchecked)
3. Lỗi hệ thống bên ngoài -> tùy:
   - Nếu có thể phục hồi (retry giúp ích) -> checked
   - Nếu không (service sập) -> unchecked

Trong Java có hai loại exception chính:

- **Checked Exception** (kế thừa từ `Exception`, nhưng không phải `RuntimeException`) - compiler **bắt buộc** xử lý. Tại sao: để lập trình viên quyết định một cách có ý thức lúc viết code cách phản ứng với lỗi này. Đó là một dạng tài liệu được xây dựng vào trong ngôn ngữ.
- **Unchecked Exception** (kế thừa từ `RuntimeException`) - compiler **không bắt buộc** xử lý. Tại sao: JVM được thiết kế sao cho các exception này biểu thị các lỗi lập trình (bug) không thể phục hồi ngay lập tức - chúng cần được sửa trong code, không phải bắt.

```java
// Checked - phải khai báo throws hoặc catch
public class DatabaseException extends Exception {
    public DatabaseException(String msg) { super(msg); }
}

// Unchecked - không cần khai báo
public class ValidationException extends RuntimeException {
    public ValidationException(String msg) { super(msg); }
}
```

**Khuyến nghị (không phải một quy tắc tuyệt đối):**
- Lỗi của **người dùng** (nhập sai, vi phạm quy tắc nghiệp vụ) -> thường là `RuntimeException`, vì code gọi không thể phục hồi - nó phải sửa logic
- Lỗi của **hệ thống bên ngoài** (mạng, DB, filesystem) -> thường là `Exception`, vì code gọi có thể hành động: retry, chuyển sang backup, thông báo cho người dùng

### Ví dụ sử dụng

```java
// Checked - hệ thống bên ngoài không khả dụng
public User findUser(Long id) throws DatabaseException {
    // SQL có thể lỗi - code gọi PHẢI biết điều này
    // Trong JDBC cổ điển - checked (SQLException). Trong Spring Data/JPA - unchecked (DataAccessException). Lựa chọn tùy vào framework.
    return userRepository.findById(id)
        .orElseThrow(() -> new DatabaseException("User not found: " + id));
}

// Unchecked - lỗi lập trình
public void validateAge(int age) {
    if (age < 0) {
        throw new ValidationException("Age cannot be negative");
    }
}
```

## Middle Level

### Khi nào extends Exception (Checked)

**Dùng checked exception khi:**

1. **Bên gọi có thể phục hồi**
```java
public Connection getConnection() throws ConnectionPoolExhaustedException {
    // Bên gọi có thể chờ và thử lại
}
```

2. **Đó là một tình huống được lường trước**, không phải một bug
```java
public Document readDocument(String path) throws FileNotFoundException {
    // File có thể không tồn tại - điều này là bình thường
}
```

3. **API yêu cầu xử lý bắt buộc**
```java
public void transferMoney(Account from, Account to, BigDecimal amount)
        throws InsufficientFundsException {
    // Bên gọi PHẢI xử lý trường hợp không đủ tiền
}
```

### Khi nào extends RuntimeException (Unchecked)

**Dùng unchecked exception khi:**

1. **Lỗi lập trình** (bug, sai tham số)
```java
public User getUser(Long id) {
    if (id == null) {
        throw new IllegalArgumentException("ID cannot be null");
    }
    // ...
}
```

2. **Không thể phục hồi**
```java
public Config loadConfig(String path) {
    if (!Files.exists(path)) {
        throw new ConfigurationException("Config file missing: " + path);
        // Chương trình không thể hoạt động mà không có cấu hình
    }
}
```

3. **Phong cách Spring / hiện đại** - hầu hết các framework ưa chuộng unchecked
```java
@Service
public class OrderService {
    public Order createOrder(OrderRequest req) {
        if (req.items().isEmpty()) {
            throw new BusinessRuleException("Order must have items");
        }
        // Spring xử lý RuntimeException -> 400 Bad Request
    }
}
```

### Bảng so sánh

| Tiêu chí               | Exception (Checked)       | RuntimeException (Unchecked) |
| ---------------------- | ------------------------- | ---------------------------- |
| Xử lý bắt buộc         | Có                        | Không                        |
| Khai báo trong throws  | Bắt buộc                  | Không bắt buộc               |
| Dùng điển hình         | Hệ thống bên ngoài, I/O   | Lỗi logic, validation        |
| Phục hồi               | Có thể                    | Thường không thể             |
| Xử lý trong Spring     | Cần `@ControllerAdvice`   | Tự động -> 400/500           |
| Độ dài dòng code       | Cao (try/catch khắp nơi)  | Thấp                         |

### Các lỗi điển hình

1. **Checked exception cho validation:**
```java
// Xấu - validation không cần phục hồi, code gọi không thể sửa email không hợp lệ ngay lập tức
// Ngoài ra, checked exception ép try/catch khắp nơi, làm code khó đọc hơn
public void setEmail(String email) throws InvalidEmailException { ... }

// Tốt - RuntimeException, vì đó là một lỗi lập trình (truyền email sai)
public void setEmail(String email) {
    if (!isValid(email)) {
        throw new InvalidEmailException(email); // RuntimeException
    }
}
```

2. **Bọc checked trong unchecked mà không có lý do:**
```java
// Mất thông tin về vấn đề thực sự
try {
    fileInputStream.read();
} catch (IOException e) {
    throw new RuntimeException(e); // Mất ngữ cảnh!
}

// Bọc mà vẫn giữ cause và ngữ cảnh
try {
    fileInputStream.read();
} catch (IOException e) {
    throw new DataReadException("Failed to read file: " + filePath, e);
}
```

### Khi nào KHÔNG nên dùng RuntimeException

Đừng dùng RuntimeException (tức là chọn checked Exception) nếu:
- **Bạn viết một public library** - checked exception đóng vai trò tài liệu: lập trình viên thấy ngay những lỗi nào có thể xảy ra và phải xử lý chúng
- **Code gọi có thể phục hồi** - ví dụ: service không khả dụng tạm thời (retry giúp ích), hoặc file bị khóa bởi một tiến trình khác (chờ và thử lại)
- **Hệ thống then chốt**: bỏ qua lỗi = thiệt hại tài chính hoặc mối đe dọa bảo mật. Checked exception - bảo hiểm chống lỗi âm thầm
- **Dự án không có một global error handler duy nhất** - unchecked exception sẽ đi qua mà không được để ý, checked sẽ ít nhất ép suy nghĩ về việc xử lý

### Khi nào KHÔNG nên dùng checked Exception

Đừng dùng checked Exception (tức là chọn RuntimeException) nếu:
- **Đó là một lỗi lập trình** - `null` thay vì object, tuổi âm, danh sách bắt buộc rỗng. Những lỗi như vậy cần được sửa trong code, không phải bắt
- **Bạn dùng Spring/Web framework** - framework đã có global handler (`@ControllerAdvice`) biến RuntimeException thành HTTP status đúng
- **Quá nhiều boilerplate** - nếu `throws` đi qua 10 tầng của ứng dụng, đó là tạp nhiễu, không phải thông tin hữu ích

## Senior Level

### Góc nhìn kiến trúc

Checked exception là một **thí nghiệm của Java** không được các ngôn ngữ khác đón nhận:
- **C#** - chỉ unchecked
- **Kotlin** - chỉ unchecked
- **Go** - nhiều giá trị trả về (error, result)
- **Rust** - `Result<T, E>` (xử lý tường minh ở mức kiểu)

### Vấn đề với checked exception: rò rỉ abstraction

```java
// Tầng DAO "rò rỉ" vào Controller qua SQLException
public interface UserRepository {
    User findById(Long id) throws SQLException;  // SQLException - chi tiết hiện thực!
}

// Bọc trong domain exception
public interface UserRepository {
    User findById(Long id);  // Interface sạch sẽ
    // Bên trong: catch (SQLException e) -> throw new RepositoryException(e)
}
```

### Spring và checked exception

Spring **chuyển đổi** hầu hết các checked exception thành unchecked:

```java
@Repository
public class JpaUserRepository {
    // JPA ném PersistenceException (unchecked)
    // Spring chuyển đổi thành DataAccessException (unchecked)
    // ControllerAdvice bắt -> HTTP status
}
```

### Hiệu suất

Lúc runtime không có khác biệt - cả hai đều tạo stack trace. Khác biệt là ở lúc phát triển: checked yêu cầu khai báo `throws` ở mọi phương thức đi lên trên stack, unchecked - không. Đây là overhead lúc phát triển, không phải lúc thực thi. Tạo một exception (stack trace) là đắt đỏ (~1-5 micro giây), nhưng kiểu kế thừa không ảnh hưởng đến điều này.

### Cách tiếp cận Java hiện đại

```java
// Domain Exception - unchecked, kèm ngữ cảnh
public class OrderNotFoundException extends RuntimeException {
    public OrderNotFoundException(Long orderId) {
        super("Order not found: " + orderId);
        this.orderId = orderId;
    }
    private final Long orderId;
    public Long getOrderId() { return orderId; }
}

// Infrastructure Exception - unchecked, kèm cause
public class ExternalServiceException extends RuntimeException {
    public ExternalServiceException(String serviceName, Throwable cause) {
        super("External service failed: " + serviceName, cause);
        this.serviceName = serviceName;
    }
    private final String serviceName;
}

// Retryable Exception - unchecked, kèm marker
public class TransientException extends RuntimeException {
    // Đánh dấu các exception có thể được retry
}
```

### Khung quyết định (Decision Framework)

```
Các câu hỏi để ra quyết định:
|
+-- Bên gọi có thể PHỤC HỒI không?
|   +-- Có -> Exception (checked)
|   +-- Không -> RuntimeException (unchecked)
|
+-- Đây có phải là một lỗi LẬP TRÌNH không?
|   +-- Có -> RuntimeException (IllegalArgumentException, IllegalStateException)
|   +-- Không -> Xem tiếp
|
+-- Đây có phải là một API cho lập trình viên bên thứ ba không?
|   +-- Có -> Exception (ép buộc xử lý)
|   +-- Không -> RuntimeException (ít boilerplate hơn)
|
+-- Framework có xử lý exception không? (Spring)
    +-- Có -> RuntimeException (framework xử lý)
    +-- Không -> Tùy vào ngữ cảnh
```

### Best Practices

```java
// Cây phân cấp domain exception
BaseException (RuntimeException)
+-- ValidationException
+-- NotFoundException
+-- BusinessRuleException
+-- ExternalServiceException

// Cây phân cấp infrastructure exception
InfrastructureException (RuntimeException)
+-- DatabaseException
+-- NetworkException
+-- TimeoutException

// Global exception handler
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(NotFoundException.class)
    ResponseEntity<ErrorResponse> handleNotFound(NotFoundException e) {
        return ResponseEntity.status(404).body(new ErrorResponse(e.getMessage()));
    }

    @ExceptionHandler(ValidationException.class)
    ResponseEntity<ErrorResponse> handleValidation(ValidationException e) {
        return ResponseEntity.status(400).body(new ErrorResponse(e.getMessage()));
    }
}
```

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- `Exception` (checked) - compiler bắt buộc xử lý; `RuntimeException` (unchecked) - không
- Chọn checked khi bên gọi có thể phục hồi (retry, fallback); unchecked - cho các lỗi lập trình
- Trong các Spring/Web framework hãy ưa chuộng unchecked - `@ControllerAdvice` tự động ánh xạ tới các HTTP status
- Checked exception - thí nghiệm của Java, không được C#, Kotlin, Go, Rust đón nhận
- Bọc checked trong unchecked mà vẫn giữ cause (`new DataReadException("msg", e)`)
- Decision Framework: có thể phục hồi -> checked; lỗi là bug -> unchecked; public library -> checked

**Các câu hỏi phụ thường gặp:**
- **Tại sao Spring ưa chuộng unchecked?** - Framework đã có global handler; checked thêm boilerplate mà không có lợi ích
- **Rò rỉ abstraction qua checked exception là gì?** - Khi `SQLException` "rò rỉ" từ DAO tới Controller qua `throws` - chi tiết hiện thực lọt vào interface
- **Khi nào checked exception tốt hơn?** - Public library, hệ thống then chốt (tài chính, bảo mật), lỗi tạm thời (retry giúp ích)
- **Có khác biệt về hiệu suất không?** - Lúc runtime không, cả hai đều tạo stack trace; khác biệt là ở overhead lúc phát triển (throws qua tất cả các tầng)

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi luôn dùng checked - nó an toàn hơn" - Điều này dẫn tới boilerplate và rò rỉ abstraction
- "Tôi bọc tất cả checked trong RuntimeException mà không có lý do" - Thông tin về vấn đề thực sự bị mất
- "Checked exception = chậm hơn" - Không có khác biệt lúc runtime, khác biệt chỉ ở lượng code
