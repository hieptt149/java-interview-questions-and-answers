# What is a checked exception and when to use it? (Checked exception là gì và khi nào dùng nó?)

## Junior Level

### Định nghĩa

**Checked exception** - một loại exception mà trình biên dịch (compiler) Java bắt buộc bạn phải xử lý.

**Tại sao:** những người thiết kế Java muốn ép lập trình viên phải quyết định một cách tường minh cách phản ứng với các lỗi bên ngoài có thể lường trước - một file có thể bị thiếu, mạng có thể rớt. Không có checked exception, những tình huống này dễ bị bỏ sót. Nếu một phương thức có thể ném một checked exception, bạn phải:
1. Bọc lời gọi trong `try-catch`
2. Hoặc thêm `throws` vào chữ ký phương thức

### Ví dụ

```java
// Compiler sẽ ép buộc xử lý IOException
public String readFile() throws IOException {
    return Files.readString(Paths.get("data.txt"));
}

// Phải xử lý
public void safeRead() {
    try {
        Files.readString(Paths.get("data.txt"));
    } catch (IOException e) {
        System.err.println("Failed to read: " + e.getMessage());
    }
}
```

### Khi nào dùng

Dùng một checked exception nếu:
- **Lỗi được lường trước** - file có thể bị thiếu, mạng có thể rớt
- **Lỗi có thể phục hồi** - có thể retry, thử một đường khác
- **Nó quan trọng** - không thể chỉ đơn giản "quên" tình huống này đi

### Các checked exception thường gặp

- `IOException` - vấn đề I/O
- `SQLException` - lỗi database
- `ClassNotFoundException` - không tìm thấy class
- `InterruptedException` - thread bị ngắt (interrupt)

## Middle Level

### Chọn cái gì: throws hay try-catch?

- **throws** - khi phương thức không thể quyết định cách xử lý. Hãy để bên gọi quyết định.
- **try-catch** - khi bạn có thể xử lý ngay tại chỗ: ghi log, trả về một giá trị mặc định, retry.

### Cơ chế biên dịch

Trình biên dịch `javac` kiểm tra call graph. Nếu ở đâu đó trong chuỗi có một phương thức với checked exception được gọi và nó không được xử lý, việc biên dịch sẽ thất bại.

### Exception Translation

Trong các dự án lớn với kiến trúc nhiều tầng, việc lan truyền các checked exception phá vỡ tính đóng gói của tầng. Trong các dự án nhỏ hơn, việc lan truyền chúng lên trên là chấp nhận được.

```java
public Order createOrder(Order order) {
    try {
        return orderRepository.save(order);
    } catch (SQLException e) {
        throw new OrderStorageException("Failed to save order", e);
    }
}
```

`OrderStorageException` là một runtime exception. Logic nghiệp vụ không phụ thuộc vào JDBC.

### Ba điều kiện để dùng checked exception

1. **Lỗi được lường trước** - không phải một bug code, mà là một hoàn cảnh bên ngoài
2. **Lỗi có thể phục hồi** - code gọi có thể làm gì đó với nó
3. **Quan trọng cho nghiệp vụ** - không thể bị bỏ qua

### Lambda và checked exception

Các functional interface không hỗ trợ checked exception:

```java
// Sẽ không biên dịch được!
list.stream().map(path -> Files.readString(path))
// Tại sao: interface Function<T,R> không khai báo throws trong chữ ký apply() của nó.
// Nên lambda không thể lan truyền một checked exception - compiler sẽ không cho phép.

// Giải pháp - wrapper
list.stream().map(path -> {
    try {
        return Files.readString(path);
    } catch (IOException e) {
        throw new UncheckedIOException(e);
    }
})
```

## Senior Level

### Bên trong: thuộc tính Exceptions

Trong file `.class`, thông tin về `throws` được lưu trong thuộc tính `Exceptions` của phương thức. JVM không dùng nó để kiểm soát lúc runtime - chỉ cho bộ xác minh (verifier) của compiler.

### Tính tương thích nhị phân (Binary Compatibility)

**Thêm một checked exception** vào một phương thức trong một thư viện đã tồn tại **phá vỡ tính tương thích nhị phân**. Tất cả client sẽ ngừng biên dịch được.

**Bỏ một exception** - tương thích nhị phân, nhưng để lại code thừa trong các client.

### Ghi đè (Overriding) và LSP

Nguyên tắc Liskov Substitution quy định các luật:
- Phương thức của lớp con **không được ném** các exception của lớp cha
- Có thể ném **các kiểu con (subtype)** của các exception của lớp cha
- **Không thể** ném các checked exception mới

### Hiệu suất

Một checked exception vẫn là một `Throwable` với `fillInStackTrace()` đắt đỏ. Với các tình huống "được lường trước" xảy ra thường xuyên, tốt hơn nên trả về `Optional<T>` hoặc các object Result.

### Các trường hợp biên (Edge Case)

- **InterruptedException** - một checked exception "tốt". Khi bắt, hãy khôi phục trạng thái: `Thread.currentThread().interrupt()`
- **Generic Throws** - Java cho phép `public <E extends Exception> void doWork() throws E`
- **throws Exception** - đừng bao giờ viết thế này trong một public API

### Giám sát

Đừng ném `Exception` hoặc `Throwable`. Hãy tạo các kiểu của riêng bạn để phân tách lỗi rõ ràng trong Micrometer/Prometheus.

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Checked exception - compiler bắt buộc xử lý (`try-catch` hoặc `throws`)
- Dùng nếu lỗi được lường trước, có thể phục hồi, và quan trọng cho nghiệp vụ
- Thường gặp: `IOException`, `SQLException`, `ClassNotFoundException`, `InterruptedException`
- `throws` - khi phương thức không thể quyết định cách xử lý; `try-catch` - khi bạn có thể
- Exception Translation - bọc checked trong domain unchecked cho các tầng kiến trúc
- Lambda không hỗ trợ checked exception - cần wrapper trong `UncheckedIOException`
- Thêm một checked exception phá vỡ tính tương thích nhị phân của một thư viện
- Khi ghi đè, phương thức của lớp con không thể thêm các checked exception mới (LSP)

**Các câu hỏi phụ thường gặp:**
- **Tại sao checked exception không hoạt động với lambda?** - Các functional interface (`Function`, `Predicate`) không khai báo `throws` trong chữ ký của chúng
- **Điều gì xảy ra khi thêm một checked exception vào API của một public library?** - Tất cả client sẽ ngừng biên dịch được - phá vỡ tính tương thích nhị phân
- **Cách xử lý InterruptedException đúng cách?** - Bắt và khôi phục trạng thái: `Thread.currentThread().interrupt()`
- **Khi nào một checked exception tốt hơn unchecked?** - Khi bên gọi có thể làm gì đó với nó (retry, chọn một đường thay thế)

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi viết `throws Exception` ở khắp nơi để khỏi phải suy nghĩ" - điều này phá vỡ hợp đồng của phương thức
- "Checked exception là vấn đề của JVM, không phải của ứng dụng" - không, đây là các lỗi của ứng dụng
- "Tôi bắt tất cả các checked exception và không làm gì cả" - âm thầm nuốt lỗi
