# What are Compact Strings in Java 9+? (Compact String trong Java 9+ là gì?)

## 🟢 Junior Level

**Compact String** là một tối ưu hóa được giới thiệu trong Java 9 cho phép các chuỗi chiếm **một nửa bộ nhớ** nếu chúng chỉ chứa các ký tự Latin đơn giản (chữ cái tiếng Anh, chữ số, dấu câu cơ bản).

**Cách nó hoạt động trước Java 9:**
Mỗi ký tự được lưu trong 2 byte (UTF-16), ngay cả với các chữ cái đơn giản như "a", "b", "c". Chuỗi "Hello" chiếm 10 byte.

**Cách nó hoạt động trong Java 9+:**
- Nếu chuỗi chỉ chứa các ký tự "đơn giản" (Latin-1, U+0000–U+00FF) → **1 byte mỗi ký tự**
- Nếu có các ký tự phức tạp (Cyrillic, chữ tượng hình, emoji) → **2 byte mỗi ký tự**, như trước
- Java tự động quyết định định dạng nào để dùng — bạn không cần thay đổi bất cứ điều gì trong code

**Ví dụ:**
```java
String english = "Hello World";  // 5 byte (sẽ là 10 trong Java 8)
String russian = "Привет Мир";    // 10 byte (UTF-16, như trước)
```

**Ví dụ minh họa đơn giản:** Hãy tưởng tượng một chiếc vali. Trước đây, Java luôn đóng gói đồ vào một vali lớn (2 byte), ngay cả khi bạn chỉ mang theo vớ. Giờ Java nhìn: nếu có ít đồ — dùng vali nhỏ (1 byte), nếu nhiều — vali lớn (2 byte).

**Bạn không cần thay đổi bất cứ điều gì.** Điều này hoạt động hoàn toàn trong suốt.

## 🟡 Middle Level

### Cách Nó Được Hiện Thực Nội Bộ

Trong Java 9, trường `char[] value` được thay thế bằng `byte[] value` + cờ `coder`:

```java
public final class String {
    @Stable
    private final byte[] value;  // Trước đây là char[]
    private final byte coder;    // 0 = Latin-1, 1 = UTF-16
}
```

- **coder = 0 (LATIN1):** 1 byte mỗi ký tự, khoảng U+0000–U+00FF
- **coder = 1 (UTF16):** 2 byte mỗi ký tự, tất cả các ký tự Unicode

### Chuyển Đổi Tự Động

```java
String latin = "Hello";      // coder = LATIN1, 1 byte/ký tự
String cyrillic = "Привет";  // coder = UTF16, 2 byte/ký tự

// Nối Latin-1 + Cyrillic → UTF-16 (toàn bộ chuỗi mở rộng)
String mixed = latin + cyrillic; // coder = UTF16 cho toàn bộ chuỗi
```

### Bảng Các Lỗi Điển Hình

| Lỗi                                              | Hậu quả                       | Giải pháp                                                                 |
| ---------------------------------------------------- | ----------------------------------- | ------------------------------------------------------------------------ |
| Nghĩ compact string là nén (như gzip)  | Kỳ vọng tiết kiệm cho mọi dữ liệu     | Đây chỉ là một định dạng lưu trữ hiệu quả hơn, chỉ cho Latin-1              |
| Kỳ vọng cần bật `-XX:+CompactStrings`       | Nhầm lẫn với các cờ                | Được bật theo mặc định từ Java 9. Cờ `-XX:-CompactStrings` **vô hiệu hóa** |
| Kỳ vọng substring "hạ cấp" coder             | Sử dụng bộ nhớ không hiệu quả           | JVM không tự động "hạ cấp" UTF-16 → Latin-1                   |

### So Sánh Bộ Nhớ

| Chuỗi           | Java 8 (`char[]`) | Java 9+ (`byte[]`) | Tiết kiệm |                                             |
| ---------------- | ----------------- | ------------------ | ------- | ------------------------------------------- |
| `"Hello"`        | 10 byte          | 5 byte            | **50%** |                                             |
| `"Hello World"`  | 22 byte           | 11 byte           | **50%** |                                             |
| `"Привет"`       | 12 byte          | 12 byte           | 0%      |                                             |
| `"Hello Привет"` | 24 byte          | 24 byte           | 0%      |                                             |
| `""` (rỗng)     | ~40 byte          | ~40 byte          | 0%      | Object String (~24) + byte[] rỗng (~16)    |

### Khi Nào KHÔNG Nên Dựa Vào Compact String
- **Văn bản Cyrillic/Trung Quốc/Nhật Bản** — luôn UTF-16, không tiết kiệm
- **Văn bản trộn lẫn** (Latin + Cyrillic) — toàn bộ chuỗi trở thành UTF-16
- **Chuỗi con từ các chuỗi UTF-16** — kế thừa coder UTF-16, ngay cả khi chuỗi con chỉ chứa ASCII

## 🔴 Senior Level

### Hiện Thực Nội Bộ — JEP 254

**JEP 254: Compact Strings** (Java 9) thay đổi biểu diễn nội bộ của String:

```java
// Các method then chốt với kiểm tra coder
public int length() {
    return value.length >> coder; // LATIN1: >> 0 = không dịch; UTF16: >> 1 = /2
}

public char charAt(int index) {
    if (isLatin1()) {
        return (char)(value[index] & 0xff);
    }
    return StringUTF16.getChar(value, index);
}

public boolean equals(Object anObject) {
    if (this == anObject) return true;
    if (anObject instanceof String another) {
        if (coder == another.coder) { // Kiểm tra coder trước!
            return isLatin1()
                ? StringLatin1.equals(value, another.value)
                : StringUTF16.equals(value, another.value);
        }
    }
    return false; // coder khác nhau → chắc chắn không bằng nhau
}
```

Mỗi method của String giờ kiểm tra `coder` và ủy quyền công việc cho `StringLatin1` hoặc `StringUTF16`. Các delegate này dùng **intrinsic method** của JVM — JIT compiler sinh code tối ưu hóa SIMD cho việc so sánh từng byte.

### Đánh Đổi Về Kiến Trúc (Trade-off)

**Ưu điểm:**
- Tiết kiệm bộ nhớ: **40–50%** cho các ứng dụng Enterprise điển hình (JSON key, log level, HTTP header — tất cả ASCII)
- Áp lực GC: ít object hơn trong Heap → GC pause ít thường xuyên hơn
- Cache locality: dữ liệu gọn hơn → nhiều hơn được chứa trong L1/L2 CPU cache → xử lý nhanh hơn
- **Tối ưu hóa miễn phí** — không cần thay đổi code

**Nhược điểm:**
- Overhead nhỏ khi kiểm tra `coder` trong mỗi method (JIT thường loại bỏ qua constant folding)
- Nối Latin-1 + UTF-16 → UTF-16 (toàn bộ chuỗi mở rộng)
- Phải viết lại tất cả các tối ưu hóa intrinsic cho hai định dạng
- Code reflection làm việc với `char[]` bị hỏng

### Các Trường Hợp Biên (Tối Thiểu 3)

**1. Không khớp coder khi nối chuỗi:**
```java
String latin = "Hello";     // Latin-1
String cyrillic = "Мир";    // UTF-16
String result = latin + " " + cyrillic; // Toàn bộ chuỗi → UTF-16
// Ngay cả "Hello " cũng mở rộng thành UTF-16 trong kết quả
// Mất mát: 6 byte → 12 byte cho phần Latin-1
```

**2. Substring không "hạ cấp" coder:**
```java
String mixed = "Hello Мир";    // UTF-16 (chứa Cyrillic)
String sub = mixed.substring(0, 5); // "Hello" — vẫn UTF-16!
// JVM không tự động "hạ cấp" xuống Latin-1
// sub chiếm 10 byte thay vì 5 byte có thể
```

**3. Reflection và byte[]:**
```java
// Trong Java 9+ bạn không thể chỉ lấy value qua reflection
// byte[] value thay vì char[] — phá vỡ code reflection cũ
// Module system (Java 9+) hạn chế thêm quyền truy cập vào các trường nội bộ
Field valueField = String.class.getDeclaredField("value");
valueField.setAccessible(true); // Yêu cầu --add-opens java.base/java.lang
```

**4. Coder khi tạo qua constructor:**
```java
// new String(byte[], Charset) xác định coder theo nội dung
byte[] ascii = {72, 101, 108, 108, 111}; // "Hello"
String s = new String(ascii, StandardCharsets.UTF_8); // coder = LATIN1

byte[] cyrillicBytes = {(byte)0xD0, (byte)0x9F}; // "П" trong UTF-8
String s2 = new String(cyrillicBytes, StandardCharsets.UTF_8); // coder = UTF16
```

### Hiệu Năng

| Thao tác           | Java 8 (`char[]`) | Java 9+ Compact         | Cải thiện |
| ------------------- | ----------------- | ----------------------- | ----------- |
| Bộ nhớ "Hello"      | 22 byte          | 11 byte                | **-50%**    |
| Bộ nhớ "Hello World!"| 34 byte         | 18 byte                | **-47%**    |
| `charAt()`          | ~1ns              | ~1ns (intrinsic)        | Giống nhau        |
| `equals()` (Latin-1)| ~2ns              | ~1.5ns (SIMD trên `byte[]`)| **-25%**   |
| `equals()` (UTF-16) | ~2ns              | ~2ns                    | Giống nhau        |
| Throughput GC       | Cơ sở          | **+10–15%**             | Tốt hơn      |

// Các giá trị gần đúng (JMH). Giá trị thực tế phụ thuộc vào CPU và JVM.

**Bộ nhớ (JVM 64-bit, CompressedOops):**
- String Latin-1: 24 byte (header object) + 16 + N byte (`byte[]`) ≈ **40 + N byte**
- String UTF-16: 24 byte + 16 + 2N byte ≈ **40 + 2N byte**
- Với 1M chuỗi "Hello": tiết kiệm **~5MB** trong Heap

### Thread Safety

`String` vẫn hoàn toàn thread-safe. Trường `coder` là `final`, mảng `value` là `@Stable` (annotation JVM đảm bảo tính bất biến sau khi construct). Không có race condition khi đọc từ nhiều thread.

### Câu Chuyện Thực Tế Trong Production

**Kịch bản:** Migration Java 8 → 17 trong microservice (4GB Heap, Spring Boot, JSON API).

- **Trước:** Mức sử dụng Heap 75% (3GB), Full GC mỗi 20 phút, latency p99 = 15ms
- **Sau:** Mức sử dụng Heap 55% (2.2GB), Full GC mỗi 45 phút, latency p99 = 10ms
- Các key JSON (`"id"`, `"name"`, `"type"`, `"status"`) — tất cả Latin-1 → tiết kiệm 50%
- Không một dòng code — nâng cấp trong suốt

**Kịch bản 2:** Parser tải cao (1M dòng/giây, log):
- Các chuỗi: các key JSON — tất cả Latin-1
- Tiết kiệm: ~200MB/giây cấp phát → ~100MB/giây
- Thời lượng Young GC giảm 30%
- **Vấn đề:** Các chuỗi con từ các chuỗi UTF-16 kế thừa coder UTF-16 → mức tiêu thụ bộ nhớ cao bất ngờ cho các chuỗi "đơn giản". Sửa lỗi: tạo chuỗi tường minh qua constructor.

### Best Practices Cho Highload

- Compact String được **bật theo mặc định** — không cần hành động gì
- Cho lợi ích tối đa: lưu dữ liệu ở Latin-1 khi có thể (key ASCII, giá trị enum, trạng thái)
- **Đừng cố "hạ cấp" coder thủ công** — JIT xử lý tốt hơn
- `-XX:-CompactStrings` để vô hiệu hóa (nhưng tại sao?)
- Lợi ích rõ nhất trong các ứng dụng có nhiều chuỗi: web, parse JSON, logging, HTTP header
- Khi migration Java 8 → 9+: kiểm tra code reflection làm việc với `char[] value`
- Cho độ trễ cực thấp: compact string cải thiện cache locality → ít cache miss L1/L2 hơn

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Compact String (JEP 254, Java 9+) — tối ưu hóa: Latin-1 (1 byte/ký tự) thay vì UTF-16 (2 byte)
- `byte[] value` + `byte coder` thay vì `char[] value` (Java 8 trở về trước)
- coder = 0 → Latin-1 (U+0000–U+00FF), coder = 1 → UTF-16
- Được bật theo mặc định, cờ `-XX:-CompactStrings` vô hiệu hóa
- Nối Latin-1 + UTF-16 → kết quả là UTF-16 (toàn bộ chuỗi mở rộng)
- Tiết kiệm: 40-50% bộ nhớ cho các ứng dụng Enterprise điển hình (key JSON, HTTP header — tất cả ASCII)
- Chuỗi con từ chuỗi UTF-16 kế thừa coder UTF-16, ngay cả khi chuỗi con chỉ chứa ASCII

**Các câu hỏi phụ thường gặp:**
- **Tiết kiệm bộ nhớ nào từ Compact String?** — 40-50% cho các chuỗi Latin-1. Trong ứng dụng web điển hình, 70% chuỗi là Latin-1, giảm Heap tổng thể 20-30%.
- **Điều gì xảy ra khi nối Latin-1 + Cyrillic?** — Toàn bộ chuỗi trở thành UTF-16. Phần Latin-1 mở rộng thành 2 byte/ký tự.
- **`substring()` có hạ cấp coder từ UTF-16 xuống Latin-1 không?** — Không. Chuỗi con từ một chuỗi UTF-16 vẫn là UTF-16, ngay cả khi nó chỉ chứa ASCII.
- **Bạn có cần bật Compact String bằng một cờ không?** — Không, được bật theo mặc định từ Java 9. `-XX:-CompactStrings` — vô hiệu hóa.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "Compact String — nén như gzip" — nó chỉ là một định dạng lưu trữ hiệu quả hơn
- ❌ "Cần bật `-XX:+CompactStrings`" — đã được bật theo mặc định
- ❌ "Compact String hoạt động cho Cyrillic" — Cyrillic = UTF-16, không tiết kiệm
- ❌ "Java tự động hạ cấp UTF-16 → Latin-1" — nó không hạ cấp, chỉ nâng cấp
