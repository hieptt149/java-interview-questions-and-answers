# How HashMap Handles Collisions? (HashMap xử lý va chạm như thế nào?)

## 🟢 Junior Level

Khi hai key rơi vào cùng một bucket, HashMap không hoảng loạn — nó lưu cả hai dưới dạng một chuỗi (linked list).

**Cách nó hoạt động:** Mỗi phần tử trong một bucket chứa một tham chiếu `next` tới phần tử tiếp theo. Bucket trỏ tới phần tử đầu tiên, phần tử đầu trỏ tới phần tử thứ hai, và cứ thế. Giống các toa tàu: để tìm đúng toa, bạn phải đi qua tất cả từ đầu.

**Ví dụ minh họa đơn giản:** Hãy tưởng tượng một hộp thư với hai lá thư cho những người khác nhau. Bên trong hộp thư là một danh sách: "Thư 1 — cho Alice, Thư 2 — cho Bob". Khi người đưa thư đến, họ kiểm tra cả hai lá thư.

**Ví dụ:**
```java
HashMap<String, String> map = new HashMap<>();
map.put("Aa", "Hello");    // hashCode = 2112
map.put("BB", "World");    // hashCode = 2112 — va chạm!
// Cả hai phần tử được lưu trong cùng một bucket
System.out.println(map.get("Aa")); // "Hello" — tìm đúng cái
System.out.println(map.get("BB")); // "World" — cũng tìm được
```

## 🟡 Middle Level

### Java 7 vs Java 8+

| Đặc điểm       | Java 7                            | Java 8+                       |
| ---------------- | --------------------------------- | ----------------------------- |
| Điểm chèn        | Đầu list                          | Đuôi list                     |
| Cấu trúc         | Chỉ linked list                   | List → cây đỏ-đen             |
| Độ phức tạp      | O(n)                              | O(log n)                      |
| Cycling          | Có thể xảy ra khi resize đa luồng | Đã sửa                        |

**Tại sao ngưỡng = 8?** Với k ≤ 7, một linked list nhanh hơn một cây: overhead của việc duyệt cây (các tham chiếu parent/left/right, kiểm tra màu) lớn hơn lợi ích O(log k). Đó là lý do treeification bắt đầu ở 8, không phải 2 hay 3.

### Cơ chế Treeification

Các tham số chuyển đổi:
- `TREEIFY_THRESHOLD = 8` — ở phần tử thứ 9, `treeifyBin()` được gọi
- `MIN_TREEIFY_CAPACITY = 64` — nếu table nhỏ hơn 64, resize được thực hiện thay vì treeification
- `UNTREEIFY_THRESHOLD = 6` — chuyển đổi nghịch khi thu nhỏ

### Thuật toán put khi va chạm

1. Tính chỉ số bucket
2. Duyệt cấu trúc hiện có (list hoặc tree)
3. Kiểm tra nhanh: `p.hash == hash`
4. Kiểm tra chính xác: `p.key == key || p.key.equals(key)`
5. Nếu khớp — giá trị được cập nhật
6. Nếu không khớp — node mới được thêm vào đuôi
7. Ở độ dài list >= 8 — treeification (Java 8+)

### Các sai lầm thường gặp

1. **hashCode() kém** — gây va chạm hàng loạt và suy giảm
2. **Dùng HashMap trong đa luồng** — va chạm khuếch đại các data race
3. **Các key mutable** — sửa đổi key làm phần tử không thể tiếp cận

## 🔴 Senior Level

### Hiện thực bên trong

Khi va chạm, HashMap duyệt chuỗi:
```java
for (int binCount = 0; ; ++binCount) {
    if ((e = p.next) == null) {
        p.next = newNode(hash, key, value, null);
        if (binCount >= TREEIFY_THRESHOLD - 1)
            treeifyBin(tab, hash);
        break;
    }
    if (e.hash == hash && ((k = e.key) == key || (key != null && key.equals(k))))
        break;
    p = e;
}
```

Tối ưu: `hash` được so sánh trước (so sánh int nhanh), rồi `equals()` chỉ được gọi nếu cần.

### Cấu trúc TreeNode

```java
static final class TreeNode<K,V> extends LinkedHashMap.Entry<K,V> {
    TreeNode<K,V> parent, left, right, prev;
    boolean red;
    // + kế thừa hash, key, value, next
}
```

`TreeNode` chiếm ~64-80 byte so với ~32-48 byte cho `Node`. Vậy treeification là một sự đánh đổi giữa tốc độ và bộ nhớ.

### Các đánh đổi kiến trúc

**List vs Tree:**
- List: bộ nhớ tối thiểu, nhưng tìm kiếm O(k)
- Tree: tìm kiếm O(log k), nhưng ~2x bộ nhớ và overhead cân bằng
- Ngưỡng 8 được chọn theo thống kê: với một hashCode tốt, xác suất 8 va chạm là không đáng kể

### Multi-threaded Resize

Trong Java 7, chèn đầu (head insertion) trong lúc resize đảo ngược thứ tự phần tử. Trong môi trường đa luồng, điều này tạo các tham chiếu vòng (vòng lặp vô hạn khi get()). Java 8 chuyển sang chèn đuôi (tail insertion), giữ nguyên thứ tự. Trong ConcurrentHashMap, CAS + synchronized trên đầu bucket được dùng.

CAS (Compare-And-Swap) — một lệnh CPU atomic: "so sánh một giá trị với giá trị mong đợi và, nếu khớp, thay bằng giá trị mới". Dùng cho thread safety mà không cần khóa.

### Ảnh hưởng tới GC

Va chạm nặng tạo áp lực GC:
- Nhiều object Node nhỏ
- TreeNode thậm chí nặng hơn
- put/remove thường xuyên — churn trong Young Gen

### Best Practices

1. `hashCode()` chất lượng — phòng thủ tốt nhất chống va chạm
2. Với các key là object, hãy implement `Comparable` — điều này tăng tốc treeification
3. Trong production, giám sát: latency get/put tăng dần = dấu hiệu va chạm

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Separate Chaining — dùng trong HashMap: va chạm = list/tree trong bucket
- Java 7: chèn đầu, Java 8+: chèn đuôi (ngăn cycling)
- Tree ở 8 phần tử, chuyển đổi nghịch ở 6 (hysteresis để ổn định)
- Thuật toán put khi va chạm: kiểm tra hash trước (nhanh), rồi equals (chính xác)
- TreeNode chiếm ~2x bộ nhớ so với Node (~64-80 byte so với ~32-48 byte)
- CAS + synchronized trên đầu bucket — cách ConcurrentHashMap giải quyết va chạm đa luồng

**Các câu hỏi phụ thường gặp:**
- **Tại sao ngưỡng = 8?** — với k ≤ 7, list nhanh hơn tree (ít overhead trên các tham chiếu và cân bằng)
- **Tại sao chuyển đổi nghịch ở 6, không phải 7?** — hysteresis: ngăn dội qua dội lại khi dao động
- **Điều gì xảy ra nếu mọi hashCode = 1?** — Java 7: O(n²) DoS, Java 8+: tree, nhưng có overhead
- **Tại sao chèn đuôi trong Java 8?** — chèn đầu đảo ngược list khi resize → vòng lặp vô hạn trong đa luồng

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Va chạm là không thể xảy ra với một hashCode tốt" — chúng có thể xảy ra, chỉ là hiếm
- "Tree luôn tốt hơn list" — không, với k nhỏ, list nhanh hơn
- "HashMap an toàn trong đa luồng" — không, ngay cả với treeification
