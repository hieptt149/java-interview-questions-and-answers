# What is Dependency Injection? (Dependency Injection là gì?)

## Junior Level

**Dependency Injection (DI)** (tiêm phụ thuộc) là một pattern trong đó các đối tượng nhận các phụ thuộc (dependency) của mình từ bên ngoài, thay vì tự tạo chúng bằng `new`.

**Tại sao:** Không có DI, một class bị gắn chặt (tightly coupled) với các phụ thuộc của nó. Nó không thể được test một cách độc lập (không thể inject mock vào), và việc thay đổi implementation đòi hỏi phải sửa code. DI giải quyết điều này bằng cách để các phụ thuộc được cung cấp từ bên ngoài.

**Ví dụ minh họa đơn giản:** Thay vì tự lắp ráp một chiếc xe hơi, nó được giao đến cho bạn theo đơn đặt hàng.

**Không có DI:**
```java
// Class tự tạo các phụ thuộc
public class OrderService {
    private OrderRepository repo = new OrderRepository();
}
```

**Có DI:**
```java
// Phụ thuộc đến từ bên ngoài
public class OrderService {
    private final OrderRepository repo;

    public OrderService(OrderRepository repo) {
        this.repo = repo;  // Spring sẽ tự truyền vào đúng repository
    }
}
```

**Tại sao:**
- Dễ test (thay repository bằng một mock)
- Các class không phụ thuộc trực tiếp lẫn nhau
- Spring tự quản lý tất cả các đối tượng

### Khi nào KHÔNG cần DI

1. **Script đơn giản** — một class, một phụ thuộc, không có test — DI chỉ thêm phức tạp mà không có lợi ích
2. **Value Object / DTO** — các đối tượng dữ liệu đơn giản, chúng không có phụ thuộc
3. **Hệ thống nhạy về hiệu năng với latency (độ trễ) cỡ microsecond** — DI container thêm overhead lúc khởi động (thường là không đáng kể)

## Middle Level

### Vòng đời DI trong Spring

```
1. Registration: Quét (@Component, @Bean) -> BeanDefinition
2. Instantiation: Tạo đối tượng (reflection)
3. Population: Tiêm phụ thuộc (@Autowired)
4. Initialization: @PostConstruct, Tạo Proxy (@Transactional)
5. Ready: Bean sẵn sàng hoạt động
```

BeanDefinition là một "công thức" mà Spring dùng để tạo một bean: tên class đầy đủ, scope, các phụ thuộc, lazy/eager, v.v.

Tạo Proxy — Spring tạo một đối tượng thay thế (proxy) chặn các lời gọi phương thức và thêm hành vi (transaction, security). Chi tiết trong file [[13. What is a proxy in Spring]] (Proxy trong Spring là gì).

### Các kiểu Injection

| Kiểu             | Ví dụ                               | Ưu điểm                        | Nhược điểm                                      |
| --------------- | ------------------------------------ | --------------------------- | ----------------------------------------- |
| **Constructor** | `public Service(Repo r) {}`          | Immutable, dễ test, fail-fast | Nhiều tham số                          |
| **Setter**      | `@Autowired void setRepo(Repo r) {}` | Phụ thuộc tùy chọn (optional)       | Có thể quên gọi                      |
| **Field**       | `@Autowired Repo repo;`              | Ít code hơn                   | Phụ thuộc bị ẩn, khó test |

### Circular Dependency (phụ thuộc vòng)

```java
// A phụ thuộc B, B phụ thuộc A
// Constructor Injection -> lỗi lúc khởi động
// @Lazy -> Spring tạo một proxy, phụ thuộc thật được inject sau
```

### Prototype trong Singleton

```java
// Prototype được tạo MỘT LẦN khi được inject vào Singleton
@Autowired PrototypeBean proto;  // Bị kẹt với một instance duy nhất

// ObjectProvider - mới mỗi lần
@Autowired ObjectProvider<PrototypeBean> provider;
PrototypeBean bean = provider.getObject();  // Mới!
```

## Senior Level

### BeanDefinition: Thông tin meta

```
BeanDefinition lưu trữ:
  -> Tên class
  -> Scope (Singleton, Prototype)
  -> Các tham số constructor
  -> Chế độ autowire
  -> Các phương thức Init/Destroy

-> Có thể được sửa đổi qua BeanFactoryPostProcessor TRƯỚC KHI tạo bean
```

### Proxy và DI

```
DI xảy ra TRƯỚC KHI tạo proxy!
  1. Spring tạo đối tượng
  2. Inject các phụ thuộc
  3. BeanPostProcessor.postProcessAfterInitialization -> tạo Proxy

-> Đó là lý do @Transactional không hoạt động với self-invocation!
-> Gọi this.method() sẽ đi vòng qua proxy
```

### Constructor Injection và Circular Dependency

```
Constructor Injection yêu cầu các phụ thuộc NGAY LẬP TỨC.
  -> Spring không thể tạo A mà không có B
  -> Spring không thể tạo B mà không có A
  -> BeanCurrentlyInCreationException

Field Injection:
  -> Spring tạo A và B qua constructor mặc định
  -> Sau đó điền vào các field
  -> Bug ẩn: NPE trong @PostConstruct
```

### Kinh nghiệm Production

**Tình huống thực tế: Field Injection che giấu vấn đề**
- 50 service, các phụ thuộc vòng qua Field Injection
- Ứng dụng khởi động được nhưng crash ngay ở request đầu tiên
- Giải pháp: chuyển sang Constructor Injection
- Kết quả: lỗi xuất hiện lúc khởi động -> sửa nhanh

### Best Practices

1. **Constructor Injection** — luôn dùng làm mặc định
2. **@Lazy** — chỉ cho các vòng phụ thuộc (refactoring vẫn tốt hơn)
3. **ObjectProvider** — cho Prototype trong Singleton
4. **Field Injection** — KHÔNG dùng
5. **> 5 phụ thuộc** -> vi phạm SRP, hãy tách class ra
6. **DI != Service Locator** -> đừng kéo context vào trong code

### Tóm tắt cho Senior

- **DI** = một hiện thực của Inversion of Control. IoC là nguyên tắc tổng quát ("framework gọi code của bạn, không phải ngược lại"). DI là một hiện thực cụ thể của IoC, trong đó các phụ thuộc được cung cấp từ bên ngoài. Không phải mọi IoC đều là DI, nhưng mọi DI đều là IoC.
- **Constructor** — tính bất biến (immutability), dễ test, fail-fast
- **BeanFactoryPostProcessor** -> sửa đổi metadata trước khi tạo
- **Proxy** được tạo SAU DI -> self-invocation không hoạt động
- **Circular deps** -> Constructor vỡ ngay lập tức, Field che giấu
- **Prototype trong Singleton** -> ObjectProvider hoặc @Lookup
- **Field Injection** — nợ kỹ thuật (technical debt)

## Interview Cheat Sheet

**Cần phải biết:**
- DI là một pattern trong đó các đối tượng nhận phụ thuộc từ bên ngoài, không phải bằng cách tự tạo qua `new`
- DI hiện thực Inversion of Control (IoC): framework gọi code của bạn, không phải ngược lại
- Ba kiểu injection: constructor, setter, field
- DI giúp test dễ hơn (mock), giảm coupling, đơn giản hóa việc thay đổi implementation
- Spring quản lý vòng đời DI: Registration -> Instantiation -> Population -> Initialization -> Ready
- Circular dependency: constructor vỡ ngay lập tức, field che giấu vấn đề
- Prototype trong Singleton cần ObjectProvider, nếu không sẽ chỉ có một instance
- > 5 phụ thuộc -> vi phạm SRP, hãy tách class ra

**Các câu hỏi phụ thường gặp:**
- **DI khác IoC như thế nào?** IoC là nguyên tắc tổng quát, DI là một hiện thực cụ thể của IoC.
- **BeanDefinition là gì?** Một "công thức" của bean: tên class, scope, các phụ thuộc, các phương thức init/destroy.
- **Tại sao @Transactional không hoạt động với self-invocation?** Lời gọi `this.method()` đi vòng qua proxy, mà proxy được tạo SAU DI.
- **Làm sao để giải quyết circular dependency?** Refactoring (tách ra một service dùng chung), @Lazy như một cách chữa cháy, hoặc setter injection.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Field Injection là một lựa chọn tốt cho production" (nó là anti-pattern, che giấu các phụ thuộc)
- "DI thêm quá nhiều overhead, tự làm bằng `new` thì tốt hơn" (overhead là không đáng kể, lợi ích lớn hơn nhiều)
- "Circular dependency không sao, Spring tự giải quyết" (Spring che giấu một vấn đề kiến trúc)
- "Mọi đối tượng đều nên là bean với DI" (DTO, Value Object, Entity là các đối tượng thông thường)
