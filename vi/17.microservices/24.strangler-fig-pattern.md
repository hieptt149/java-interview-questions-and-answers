# What is Strangler Fig pattern (Strangler Fig pattern là gì)

## 🟢 Junior Level

**Strangler Fig** là một pattern để **migration dần dần** từ một monolith sang microservices.

**Analogy tự nhiên:** một cây sung (fig tree) mọc quấn quanh một cây khác, dần dần thay thế nó cho đến khi cây gốc biến mất.

```
Monolith: [==============]

Bước 1:  [==========] + [User Service]
Bước 2:  [======] + [User Service] + [Order Service]
Bước 3:  [==] + [User Service] + [Order Service] + [Payment Service]
Bước 4:  [User Service] + [Order Service] + [Payment Service]
```

---

## 🟡 Middle Level

### Cách Hoạt Động

**1. API Gateway phía trước monolith:**
```
Client → API Gateway → Monolith (theo mặc định)
                     → Service mới (nếu tồn tại)
```

**2. Migration dần dần:**
```
1. Trích xuất chức năng User → User Service
2. Route /api/users → User Service
3. Trích xuất Order → Order Service
4. Route /api/orders → Order Service
5. Tiếp tục cho đến khi monolith biến mất
```

### Các Lỗi Thường Gặp

1. **Big bang migration:**
```
2 năm phát triển → tất cả cùng lúc → rủi ro cao
Strangler: rủi ro thấp, migration từng bước
```

## 🔴 Senior Level

### Dual Write Pattern

```
Khi migration dữ liệu:
1. Ghi vào monolith VÀ vào DB mới
2. Đọc từ DB mới
3. So sánh dữ liệu
4. Loại bỏ việc ghi vào monolith
```

// Dual write problem: nếu ghi vào hệ thống cũ thành công nhưng ghi vào hệ thống mới thất bại,
// dữ liệu trở nên không đồng bộ. Giải pháp: pattern Outbox hoặc CDC.

### Kinh Nghiệm Production

**Feature flags:**
```java
@Value("${feature-flag.use-new-user-service:false}")
private boolean useNewUserService;

// Feature flags là một pattern riêng biệt, nhưng chúng giúp ích cho Strangler Fig:
// bạn có thể chuyển traffic sang hệ thống mới mà không cần deployment.

@GetMapping("/users/{id}")
public User getUser(@PathVariable Long id) {
    if (useNewUserService) {
        return newUserService.getUser(id);
    }
    return monolith.getUser(id);
}
```

### Best Practices

```
✅ API Gateway với routing
✅ Feature flags
✅ Dual write khi migration dữ liệu
✅ Migration từng bước

❌ Big bang migration
❌ Không có feature flags
❌ Không có monitoring trong quá trình migration
```

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- Strangler Fig — migration dần dần từ monolith sang microservices
- API Gateway phía trước monolith — route đến các service mới hoặc monolith
- Migration từng bước: trích xuất chức năng → route đến service mới → lặp lại
- Dual write pattern khi migration dữ liệu — ghi vào DB cũ và mới
- Feature flags — chuyển traffic mà không cần deployment
- Pattern Outbox hoặc CDC giải quyết vấn đề dual write (dữ liệu không đồng bộ)
- Big bang migration = 2 năm phát triển → tất cả cùng lúc → rủi ro cao

**Các câu hỏi phụ thường gặp:**
- **Dual write problem là gì?** Ghi vào hệ thống cũ thành công, ghi vào hệ thống mới thất bại, dữ liệu trở nên không đồng bộ — giải pháp: Outbox hoặc CDC.
- **Tại sao cần feature flags?** Bạn có thể chuyển traffic sang hệ thống mới mà không cần deployment, rollback nhanh.
- **Cách giám sát migration?** So sánh response từ hệ thống cũ và mới, metric lỗi, latency.
- **Thứ tự migration?** Bắt đầu với chức năng ít quan trọng nhất, dần dần chuyển đến core.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Big bang migration nhanh hơn" — không, rủi ro cao hơn, khó rollback hơn
- "Dual write không có Outbox là ổn" — không, dữ liệu trở nên không đồng bộ
- "Không cần feature flags, chỉ cần deploy" — không có feature flags, rollback = deployment mới
- "Migration không có monitoring" — không, bạn cần thấy vấn đề theo thời gian thực
