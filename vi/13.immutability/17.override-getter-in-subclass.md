# What happens if you override getter in subclass of immutable class? (Điều gì xảy ra nếu bạn ghi đè getter trong subclass của một immutable class?)

---

## Basic Level

Nếu immutable class không phải là `final`, một subclass có thể ghi đè một getter và trả về dữ liệu khác. Điều này phá vỡ mọi kỳ vọng của code dựa vào tính bất biến.

```java
public class ImmutableBase {  // không final — sai lầm
    private final String data;
    public ImmutableBase(String data) { this.data = data; }
    public String getData() { return data; }
}

public class MutableChild extends ImmutableBase {
    private String dynamicData;
    public void setDynamicData(String d) { this.dynamicData = d; }

    @Override
    public String getData() {
        // Lưu ý: trường final data của lớp cha vẫn không đổi,
        // nhưng getData() trả về một giá trị khác.
        return dynamicData; // kết quả bị thay thế!
    }
}
```

---

## Intermediate Level

### Tại Sao Điều Này Nguy Hiểm

1. **Vi phạm logic collection** — nếu một object nằm trong `HashMap` và getter của nó (được dùng trong `equals()`) trả về dữ liệu khác — object trở nên không thể tìm thấy

2. **Lỗ hổng bảo mật** — một method bảo mật kiểm tra `getData()` để tìm các ký tự bị cấm, và subclass thay thế kết quả sau khi validate

3. **Mất tính thread-safe** — getter của subclass truy cập các trường không phải `final` mà không đồng bộ hóa → "dirty reads" trong môi trường đa luồng

### Cách Tự Bảo Vệ
Luôn làm cho các immutable class là `final`:
```java
public final class ImmutableBase { ... } // không thể kế thừa
```

Ngay cả với một final class, một getter vẫn có thể trả về một object mutable — đây là một hình thức
khác của việc vi phạm tính bất biến, xem file 29.

## Advanced Level

### Vấn Đề Sâu Xa

Việc ghi đè một getter phá hủy **hợp đồng bất biến** ở cấp độ business logic, ngay cả khi các trường `final` về mặt kỹ thuật không thay đổi. JMM đảm bảo khả năng hiển thị của các trường `final`, nhưng nó không thể đảm bảo rằng một method sẽ trả về chính xác những trường đó.

### Ví Dụ Thực Tế
```java
public void authorize(ImmutableCredentials creds) {
    if (securityManager.check(creds.getToken())) {
        // Ở đây một subclass có thể trả về một token khác
        api.call(creds.getToken());
    }
}
```

### Giải Pháp

1. **`final` class** — cấm hoàn toàn việc kế thừa
2. **`sealed` class** (Java 17+) — chỉ cho phép các lớp con cụ thể, đã được kiểm chứng
3. **Composition** — thay vì kế thừa

### Tóm Tắt Cho Advanced
- Ghi đè một getter phá hủy các đảm bảo bất biến thông qua tính đa hình
- JMM không bảo vệ chống lại việc thay thế logic method
- Luôn `final` cho các immutable class
- Các class `sealed` — để kế thừa có kiểm soát

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Một subclass có thể ghi đè một getter và trả về dữ liệu khác — hợp đồng bất biến bị phá vỡ
- Vi phạm logic collection: object trong HashMap trở nên không thể tìm thấy nếu getter tham gia vào equals
- Lỗ hổng bảo mật: getter thay thế kết quả sau khi validate (TOCTOU)
- Mất tính thread-safe: getter của subclass truy cập các trường không phải final mà không đồng bộ hóa
- JMM đảm bảo khả năng hiển thị của các trường final, nhưng không đảm bảo logic method
- Giải pháp: `final` class (cấm hoàn toàn), `sealed` class (kế thừa có kiểm soát), composition

**Các câu hỏi phụ thường gặp:**
- *Các trường final của lớp cha không thay đổi — vấn đề là gì?* — Getter trả về dữ liệu KHÁC, phá vỡ hợp đồng
- *Ví dụ về một lỗ hổng thực tế?* — authorize() kiểm tra token, subclass trả về một token khác khi lưu
- *JMM liên quan đến điều này như thế nào?* — JMM bảo vệ dữ liệu của trường final, nhưng không thể đảm bảo method sẽ trả về chính xác những trường đó
- *Sealed class có giải quyết vấn đề không?* — Có, nếu tất cả các class được phép cũng đều bất biến

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Getter của subclass không nguy hiểm — các trường final vẫn giống nhau" — getter có thể trả về bất cứ thứ gì
- "Đây chỉ là vấn đề của HashMap" — không, đó là bảo mật, tính thread-safe, và business logic
- "Bạn có thể test getter" — tính đa hình cho phép thay thế tại runtime
- "Composition luôn tệ hơn kế thừa" — với tính bất biến, composition là con đường an toàn duy nhất
