# How HashMap Determines Which Bucket to Put an Element In? (HashMap xác định đặt một phần tử vào bucket nào như thế nào?)

## 🟢 Junior Level

HashMap xác định số bucket theo hai bước:

1. **Lấy hash code của key** — gọi `key.hashCode()`, thứ trả về một con số 32-bit — "dấu vân tay số" của object. Một hashCode tốt phân bố các object đều khắp dải; một cái tồi thì gom cụm chúng.
2. **Trộn các bit** — XOR hash code với chính nó, dịch phải 16 vị trí
3. **Áp dụng một mask** — dùng công thức `(array_size - 1) & hash`

**Ví dụ đơn giản:**
```java
String key = "hello";
int hash = key.hashCode();           // ví dụ, 99162322
int index = (16 - 1) & hash;         // Với size 16: index = 2
```

**Tại sao nó nhanh như vậy:** Thay vì phép chia (vốn chậm), bitwise AND (`&`) được dùng, thứ thực thi trong 1 chu kỳ CPU.

## 🟡 Middle Level

### Bước 1: Hàm nhiễu loạn bit (Bit Perturbation)

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

**Tại sao XOR và dịch 16?**
- Kích thước mảng thường nhỏ (16, 32, 64...), nên chỉ các bit thấp được dùng cho chỉ số
- Nếu `hashCode()` chỉ khác nhau ở các bit cao — va chạm xảy ra
- Dịch `>>> 16` chuyển các bit cao xuống các vị trí thấp
- XOR trộn thông tin bit cao vào các bit thấp
- **Kết quả:** ngay cả với một hashCode kém, các phần tử vẫn phân bố đều

**Tại sao cụ thể là XOR và dịch 16?** Hàm perturbation (từ tiếng Latin 'perturbare', 'trộn lẫn') đảm bảo rằng ngay cả khi hashCode() chỉ khác nhau ở các bit cao, sau khi trộn thì sự khác biệt cũng xuất hiện ở các bit thấp.

### Bước 2: Phép màu Lũy thừa của hai

```java
int index = (n - 1) & hash;
```

Nếu n = 16 (2^4):
```
n-1 = 15 => 0000 1111 (mask)
hash   => 1101 0110
&      => 0000 0110 (kết quả: 6)
```

Điều này tương đương về mặt toán học với `hash % 16`. `&` thực thi trong 1 chu kỳ (phép toán bitwise), trong khi `%` cần phép chia — 10-50 chu kỳ tùy CPU.

### Caching hashCode

`String` cache hashCode của nó trong một field `hash` private. Các thao tác HashMap thường xuyên hưởng lợi rất lớn từ điều này.

### Các sai lầm thường gặp

1. **hashCode kém** — luôn trả về 1 đặt mọi phần tử vào một bucket
2. **Mutable key** — sửa đổi các field của key sau put làm thay đổi hash, khiến phần tử không thể tiếp cận

### Đừng cố "cải thiện" việc hashing

Đừng tạo các công thức hashing kỳ lạ mà không profiling. Hàm spread của OpenJDK đã được kiểm thử kỹ lưỡng. Một "tối ưu" tồi thường tệ hơn mặc định.

## 🔴 Senior Level

### Hiện thực bên trong

Trong source OpenJDK (HashMap.java):
```java
// method putVal:
if ((p = tab[i = (n - 1) & hash]) == null)
    tab[i] = newNode(hash, key, value, null);
```

Việc xác định chỉ số xảy ra **ở mọi thao tác** — get, put, remove. Đó là lý do tối ưu hashing là then chốt.

### Tại sao Lũy thừa của hai là bắt buộc

Nếu size là 15 (không phải lũy thừa của hai):
```
n-1 = 14 => 0000 1110 (mask)
```
Bit thấp nhất luôn bị zero — mọi bucket lẻ (1, 3, 5...) không bao giờ được dùng. Điều này gây mất 50% capacity và tăng gấp đôi va chạm.

### Hiệu năng

- Tính hash: O(1), 2 phép toán (XOR + dịch)
- Xác định chỉ số: O(1), 2 phép toán (& và trừ)
- Overhead tổng thể: tối thiểu, nhưng được gọi hàng tỷ lần trong các ứng dụng lớn

### Các trường hợp biên (Edge Case)

1. **key == null**: `hash(null)` trả về 0, null luôn ở `table[0]`
2. **hashCode() = hằng số**: mọi phần tử trong một bucket, suy giảm xuống O(n)/O(log n)
3. **Các String có cùng hashCode**: `"Aa"` và `"BB"` đều cho 2112 — một va chạm đã biết trong Java

### Bảo mật: Hash Flooding

Một kẻ tấn công có thể tạo các key có cùng hash. Trong Java 8+, treeification bảo vệ khỏi DoS, nhưng overhead CPU vẫn tăng do việc tái cân bằng cây.

### Tối ưu cho Record

Trong Java 14+, các kiểu `record` sinh `hashCode()` tự động dựa trên tất cả các component. Điều này đảm bảo một contract tốt, nhưng với các record phức tạp có các field collection, hashCode có thể đắt.

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Bước 1: `hash(key) = key.hashCode() ^ (key.hashCode() >>> 16)` — hàm spread
- Bước 2: `index = (n-1) & hash` — mask bitwise thay vì `%`
- XOR trộn các bit cao vào các bit thấp — bảo vệ khỏi các hashCode kém
- `&` thực thi trong 1 chu kỳ, `%` cần 10-50 chu kỳ
- String cache hashCode — các lời gọi lặp lại là O(1)
- null cho hash = 0, luôn ở table[0]
- Với các size không phải 2^n, công thức hỏng — các bucket lẻ không bao giờ được dùng

**Các câu hỏi phụ thường gặp:**
- **Tại sao cụ thể là XOR và dịch 16?** — int 32-bit, một nửa bit cao, một nửa bit thấp; XOR trộn bit cao vào bit thấp
- **Nếu hashCode = hằng số thì sao?** — mọi phần tử trong một bucket, suy giảm xuống O(n)
- **Tại sao không dùng `%`?** — phép chia chậm (10-50 chu kỳ), `&` = 1 chu kỳ
- **"Aa" và "BB" có cho cùng hashCode không?** — có, 2112 — một va chạm đã biết

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "HashMap dùng hashCode trực tiếp" — không, có một hàm spread
- "Index = hashCode % size" — không, `(n-1) & hash`
- "Bạn có thể cải thiện hàm spread" — cái chuẩn của OpenJDK đã được kiểm thử kỹ lưỡng
