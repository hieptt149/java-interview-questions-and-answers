# When to Use Builder? (Khi nào nên dùng Builder?)

## Junior Level

**Builder** là một pattern dùng để tạo các đối tượng phức tạp theo từng bước.

**Từng bước** = bạn gọi một phương thức cho mỗi trường, theo bất kỳ thứ tự nào, và chỉ có `build()` mới tạo ra đối tượng cuối cùng. Đối tượng không bao giờ tồn tại ở trạng thái được điền một phần.

**Vấn đề:** Khi một đối tượng có nhiều tham số, constructor trở nên cồng kềnh:

```java
// Constructor kiểu "kính viễn vọng" (telescoping) — không rõ cái nào là cái nào
User user = new User("Ivan", "Ivanov", "ivan@mail.com",
                     "+79001234567", "Moscow", 25, true, false);
```

**Giải pháp — Builder:**
```java
// Rõ ràng cái nào là cái nào
User user = User.builder()
    .firstName("Ivan")
    .lastName("Ivanov")
    .email("ivan@mail.com")
    .phone("+79001234567")
    .city("Moscow")
    .age(25)
    .active(true)
    .build();
```

**Khi nào nên sử dụng:**
- Có nhiều hơn 3-4 tham số trong constructor
- Có các tham số tùy chọn (optional)
- Cần làm cho code dễ đọc

### Khi nào KHÔNG nên dùng Builder

1. **Đối tượng có 1-2 tham số** — constructor dễ đọc hơn
2. **Value object** (Point(x,y)) — constructor hoặc static factory method
3. **Hot-path** (hàng triệu lần tạo/giây) — chi phí phát sinh do đối tượng builder

### Builder vs Factory Method

**Builder** — khi có nhiều tham số (4+), đặc biệt là các tham số tùy chọn.
**Factory Method** — khi có nhiều cách để tạo một đối tượng (fromJSON, fromXML, fromCSV).
**Constructor** — khi có 1-2 tham số bắt buộc.

## Middle Level

### Các vấn đề mà Builder giải quyết

**1. Telescoping constructors (Constructor kiểu kính viễn vọng):**
```java
// 4 constructor cho tất cả các tổ hợp
public User(String name) { ... }
public User(String name, String email) { ... }
public User(String name, String email, int age) { ... }
public User(String name, String email, int age, String city) { ... }

// Builder — bất kỳ tổ hợp nào
User.builder().name("Ivan").city("Moscow").build();
```

**2. JavaBeans (setter) — không an toàn:**
```java
// Đối tượng có thể ở trạng thái không hợp lệ
User user = new User();
user.setName("Ivan");
user.setEmail("ivan@mail.com");
// ... trạng thái trung gian có thể bị các luồng khác nhìn thấy!
user.setAge(25);
user.validate();  // Quên gọi phương thức này?
```

**3. Builder đảm bảo đối tượng không bao giờ ở trạng thái được điền một phần:**
```java
// Tất cả các trường được thiết lập trước khi đối tượng có thể truy cập được
User user = User.builder()
    .name("Ivan")
    .email("ivan@mail.com")
    .age(25)
    .build();  // Validation bên trong build()
// Đối tượng hoặc được tạo hoàn chỉnh hoặc ném ra exception
```

### Triển khai Builder

```java
public class User {
    private final String name;     // final — tính bất biến (immutability)!
    private final String email;
    private final int age;
    private final String city;     // Trường tùy chọn

    private User(Builder builder) {
        this.name = builder.name;
        this.email = builder.email;
        this.age = builder.age;
        this.city = builder.city;
    }

    public static Builder builder() {
        return new Builder();
    }

    public static class Builder {
        private String name;
        private String email;
        private int age;
        private String city;

        public Builder name(String name) {
            this.name = name;
            return this;  // Fluent API
        }

        public Builder email(String email) {
            this.email = email;
            return this;
        }

        public Builder age(int age) {
            this.age = age;
            return this;
        }

        public Builder city(String city) {
            this.city = city;
            return this;
        }

        public User build() {
            // Validation
            if (name == null || name.isEmpty()) {
                throw new IllegalStateException("Name is required");
            }
            if (email == null || !email.contains("@")) {
                throw new IllegalStateException("Valid email required");
            }
            return new User(this);
        }
    }
}
```

### Lombok Builder

```java
// Thay vì 100 dòng code:
@Builder
public class User {
    private final String name;
    private final String email;
    private final int age;
    private final String city;
}

// Cách sử dụng
User user = User.builder()
    .name("Ivan")
    .email("ivan@mail.com")
    .build();
```

### Các lỗi thường gặp

1. **Builder cho một đối tượng đơn giản**
   ```java
   // Overengineering
   @Builder
   public class Point {
       private int x;
       private int y;
   }

   // Constructor là đủ dùng
   public class Point {
       public Point(int x, int y) { this.x = x; this.y = y; }
   }
   ```

2. **Đối tượng có thể thay đổi (mutable) sau khi build**
   ```java
   // Builder đã được tạo, nhưng các trường không phải final
   public class User {
       private String name;  // Có thể bị thay đổi!
   }

   // Trường final
   public class User {
       private final String name;  // Không thể bị thay đổi
   }
   ```

## Senior Level

**Wither** — phương thức trong lập trình hàm (functional programming) trả về một đối tượng mới với một trường đã được thay đổi.
**GC pressure (áp lực GC)** — việc cấp phát thường xuyên kích hoạt các chu kỳ GC thường xuyên.
**Step Builder (Staged Builder)** — compiler ngăn việc bỏ qua các bước thông qua các kiểu interface.

### Step Builder (Staged Builder)

Đảm bảo các trường bắt buộc được điền **tại thời điểm biên dịch (compile time)**:

```java
public class User {
    private final String name;    // Bắt buộc
    private final String email;   // Bắt buộc
    private final String city;    // Tùy chọn

    private User(String name, String email, String city) {
        this.name = name;
        this.email = email;
        this.city = city;
    }

    // Interface cho mỗi bước
    public interface NameStep { EmailStep name(String name); }
    public interface EmailStep { CityStep email(String email); }
    public interface CityStep {
        CityStep city(String city);
        User build();
    }

    // Triển khai
    public static NameStep builder() {
        return new UserBuilder();
    }

    private static class UserBuilder implements NameStep, EmailStep, CityStep {
        private String name;
        private String email;
        private String city;

        public EmailStep name(String name) {
            this.name = name;
            return this;
        }

        public CityStep email(String email) {
            this.email = email;
            return this;
        }

        public CityStep city(String city) {
            this.city = city;
            return this;
        }

        public User build() {
            return new User(name, email, city);
        }
    }
}

// Cách sử dụng — compiler sẽ không cho phép bạn bỏ qua các bước!
User user = User.builder()
    .name("Ivan")     // Bắt buộc
    .email("i@m.com") // Bắt buộc
    .city("Moscow")   // Tùy chọn
    .build();

// Sẽ không biên dịch được:
User.builder().name("Ivan").build();  // Lỗi: không có email()!
```

### Copy Builder (toBuilder)

```java
@Builder(toBuilder = true)
public class User {
    private final String name;
    private final String email;
    private final int age;
}

// Tạo một bản sao có một trường được thay đổi
User updated = user.toBuilder()
    .email("new@email.com")
    .build();

// User gốc không thay đổi!
// -> Hoàn hảo cho các cấu trúc immutable
```

### Validation trong Builder

```java
@Builder
public class Order {
    private final LocalDate startDate;
    private final LocalDate endDate;
    private final BigDecimal amount;

    @Builder
    private Order(LocalDate startDate, LocalDate endDate, BigDecimal amount) {
        // Validation giữa các trường (Cross-field validation)
        if (startDate != null && endDate != null && startDate.isAfter(endDate)) {
            throw new IllegalArgumentException("startDate must be before endDate");
        }
        if (amount != null && amount.compareTo(BigDecimal.ZERO) < 0) {
            throw new IllegalArgumentException("amount cannot be negative");
        }

        this.startDate = startDate;
        this.endDate = endDate;
        this.amount = amount;
    }
}
```

### Hiệu năng: Chi phí phát sinh về bộ nhớ (Memory Overhead)

```java
// Mỗi Builder = một đối tượng bổ sung trong Heap
User user = User.builder()  // -> new Builder()
    .name("Ivan")
    .build();

// Trong Hot-path (1 triệu đối tượng/giây):
// -> 1 triệu đối tượng Builder -> áp lực lên GC

// Benchmark:
// Constructor thông thường: 10ns
// Builder: 15ns (+50% chi phí phát sinh)

// Đối với các đường dẫn quan trọng — hãy dùng constructor!
```

### Builder với Kế thừa

```java
// Vấn đề: Builder của lớp cha trả về Builder, không phải subclass
@Builder
public class User {
    private String name;
}

@Builder
public class Admin extends User {  // Lombok không hỗ trợ điều này
    private String role;
}

// Giải pháp: @SuperBuilder
@SuperBuilder
public class User {
    private String name;
}

@SuperBuilder
public class Admin extends User {  // Hoạt động!
    private String role;
}

Admin admin = Admin.builder()
    .name("Ivan")  // Từ lớp cha
    .role("ADMIN") // Từ subclass
    .build();
```

### Record + Builder

```java
// Record không có Builder theo mặc định
public record User(String name, String email, int age) {}

// Builder thủ công cho Record
public class User {
    public static Builder builder() { return new Builder(); }

    public static class Builder {
        private String name;
        private String email;
        private int age;

        public Builder name(String name) { this.name = name; return this; }
        public Builder email(String email) { this.email = email; return this; }
        public Builder age(int age) { this.age = age; return this; }

        public User build() { return new User(name, email, age); }
    }
}

// Hoặc sử dụng Record với Lombok @Builder
@Builder
public record User(String name, String email, int age) {}
```

### Kinh nghiệm Production

**Tình huống thực tế #1: Builder ngăn chặn được lỗi**
- DTO có 15 trường, 10 trường tùy chọn
- 2^10 = 1024 tổ hợp constructor
- Giải pháp: Builder -> bất kỳ tổ hợp nào
- Kết quả: giảm 80% code, tăng khả năng đọc

**Tình huống thực tế #2: Step Builder ngăn chặn được lỗi**
- API client: 5 tham số bắt buộc
- Các lập trình viên thường quên điền chúng
- Giải pháp: Step Builder
- Kết quả: đảm bảo tại thời điểm biên dịch, 0 lỗi

### Best Practices (Thực hành tốt nhất)

1. **Builder cho >4 tham số** hoặc các trường tùy chọn
2. **Trường final** — làm cho đối tượng bất biến
3. **Validation trong build()** — tuyến phòng thủ cuối cùng
4. **Step Builder** cho các trường bắt buộc quan trọng
5. **toBuilder()** cho các cấu trúc immutable
6. **Lombok @Builder** để tiết kiệm code
7. **Tránh** dùng trong Hot-path (áp lực GC)
8. **@SuperBuilder** cho kế thừa

### Tóm tắt cho Senior

- **Builder** = tạo đối tượng nguyên tử (atomic) + tính bất biến (immutability)
- **Step Builder** = đảm bảo tại thời điểm biên dịch cho các trường bắt buộc
- **toBuilder** = logic Wither cho các đối tượng immutable
- **Chi phí phát sinh về bộ nhớ:** +50% cho việc tạo đối tượng Builder
- **Hot-path:** tránh dùng Builder — hãy dùng constructor
- **Validation:** giữa các trường trong build(), theo từng bước trong các phương thức
- **Record:** Builder thủ công hoặc Lombok @Builder
- **Kế thừa:** @SuperBuilder giải quyết vấn đề về kiểu

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Builder giải quyết vấn đề telescoping constructor (4+ tham số) và JavaBeans (setter) không an toàn
- Builder đảm bảo tính nguyên tử: đối tượng không bao giờ ở trạng thái được điền một phần
- Step Builder (Staged Builder) — đảm bảo tại thời điểm biên dịch cho các trường bắt buộc thông qua các kiểu interface
- toBuilder() — logic Wither: tạo một bản sao có các trường đã thay đổi cho các đối tượng immutable
- Chi phí phát sinh về bộ nhớ: +50% cho việc tạo đối tượng Builder, tránh dùng trong Hot-path (1 triệu+ lần tạo/giây)
- Lombok @Builder tiết kiệm ~100 dòng code, @SuperBuilder cho kế thừa
- Các trường nên là final — Builder mà không có tính bất biến sẽ mất đi mục đích của nó

**Các câu hỏi phụ thường gặp:**
- **Khi nào KHÔNG nên dùng Builder?** — 1-2 tham số (constructor dễ đọc hơn), value object (Point), Hot-path (áp lực GC)
- **Builder khác Factory Method như thế nào?** — Builder dành cho nhiều tham số (4+), Factory Method dành cho các cách tiếp cận tạo khác nhau
- **Step Builder là gì?** — Pattern mà compiler ngăn việc bỏ qua các bước bắt buộc thông qua các kiểu interface
- **Tại sao các trường nên là final?** — Tính bất biến: sau khi build() đối tượng không thể bị thay đổi, nếu không Builder sẽ mất đi ý nghĩa của nó

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi dùng Builder cho các đối tượng có 1-2 tham số" — overengineering, constructor dễ đọc hơn
- "Không cần Builder khi đã có Lombok" — Lombok sinh ra cùng một Builder, nguyên tắc vẫn giữ nguyên
- "Các trường có thể mutable sau khi build()" — như vậy Builder không giải quyết được vấn đề an toàn
- "Step Builder giống với Builder thông thường" — Step Builder mang lại các đảm bảo tại thời điểm biên dịch
