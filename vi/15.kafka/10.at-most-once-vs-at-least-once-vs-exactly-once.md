# What is the difference between at-most-once, at-least-once and exactly-once (Sự khác biệt giữa at-most-once, at-least-once và exactly-once là gì)

## Junior Level

### Định Nghĩa

**At-most-once:**
- Message sẽ được delivered 0 hoặc 1 lần
- Có thể bị mất khi có lỗi
- ~1x độ trễ cơ sở

**At-least-once:**
- Message sẽ được delivered 1 hoặc nhiều lần
- Có thể bị trùng lặp khi retry
- Dữ liệu sẽ không bị mất

**Exactly-once:**
- Message sẽ được delivered chính xác 1 lần
- Không mất mát, không trùng lặp
- Độ trễ 2-3 lần

### Ví Dụ Thực Tế

```
At-most-once:
  Đã gửi SMS → không kiểm tra xem đã được delivered chưa
  → Có thể không đến

At-least-once:
  Đã gửi SMS → không nhận xác nhận → gửi lại
  → Có thể đến hai lần

Exactly-once:
  Đã gửi SMS → nhận ID duy nhất → xác minh việc delivery
  → Đến chính xác một lần
```

### Khi Nào Dùng Cái Gì

| Ngữ nghĩa     | Khi nào dùng                             |
| ------------- | --------------------------------------- |
| At-most-once  | Metrics, log, monitoring               |
| At-least-once | Hầu hết các hệ thống kinh doanh                   |
| Exactly-once  | Tài chính, billing, các thao tác ngân hàng    |

## Middle Level

### Cách Nó Hoạt Động Trong Kafka

**At-most-once:**
```java
// Producer — không chờ xác nhận
props.put("acks", "0");

// Consumer — commit ngay khi nhận
props.put("enable.auto.commit", "true");
```

**At-least-once:**
```java
// Producer — chờ xác nhận từ tất cả
props.put("acks", "all");
props.put("enable.idempotence", "true");
props.put("retries", Integer.MAX_VALUE);

// Consumer — commit sau khi xử lý
props.put("enable.auto.commit", "false");
consumer.commitSync();  // sau process()
```

**Exactly-once:**
```java
// Producer
props.put("enable.idempotence", "true");
props.put("transactional.id", "my-tx-id");

// Consumer
props.put("isolation.level", "read_committed");
```

### Bảng So Sánh

| Tham số        | At-most-once  | At-least-once  | Exactly-once  |
| ---------------- | ------------- | -------------- | ------------- |
| Mất dữ liệu        | Có           | Không             | Không            |
| Trùng lặp       | Không            | Có            | Không            |
| Hiệu năng      | Tối đa       | Cao           | Trung bình         |
| Độ phức tạp       | Tối thiểu       | Trung bình         | Cao          |
| Use case         | Metrics       | Các event kinh doanh| Tài chính       |

### Idempotency — Chìa Khóa Cho At-Least-Once

```java
// Xử lý idempotent
public void process(Message msg) {
    if (!alreadyProcessed(msg.getId())) {
        doProcess(msg);
        markAsProcessed(msg.getId());
    }
}
```

### Các Lỗi Thường Gặp

1. **At-least-once không có xử lý trùng lặp:**
```
Trùng lặp → tính phí hai lần → bug trong business logic
```

2. **Exactly-once mà không hiểu các giới hạn:**
```
Kafka → PostgreSQL → exactly-once không hoạt động
Kafka không kiểm soát transaction PostgreSQL
```

3. **Commit trước khi xử lý:**
```java
consumer.commitSync();  // ❌
process(records);       // Nếu crash — mất dữ liệu
```

## Senior Level

### Vấn Đề "EndOfWorld"

**Exactly-once trong Kafka chỉ hoạt động "sẵn có" (out of the box) cho Kafka-to-Kafka:**
```
Kafka → Xử lý → Kafka  ✅ Hoạt động
Kafka → Xử lý → PostgreSQL  ❌ Không hoạt động
```

**Tại sao?**
```
Kafka chỉ có thể đảm bảo commit nguyên tử cho:
- Ghi vào topic Kafka
- Commit các offset trong __consumer_offsets

Kafka không thể quản lý một transaction PostgreSQL!
```

Pattern Outbox: (1) INSERT vào outbox_table + business_data trong một transaction DB.
(2) Một process riêng biệt đọc outbox_table và gửi đến Kafka.
(3) Sau khi delivery thành công — DELETE khỏi outbox_table.

### Các Giải Pháp Cho Các Hệ Thống Bên Ngoài

**1. Ghi Idempotent:**
```java
// PostgreSQL — UPSERT theo key duy nhất
INSERT INTO orders (id, data)
VALUES (?, ?)
ON CONFLICT (id) DO NOTHING;
```

**2. Pattern Outbox:**
```
1. Thao tác kinh doanh → ghi vào outbox (cùng transaction)
2. CDC (Debezium) → đọc outbox
3. Gửi đến Kafka
4. Consumer → xử lý → ghi vào đích
```

**3. Two-Phase Commit (XA — không khuyến nghị):**
```
Giai đoạn Prepare → tất cả người tham gia sẵn sàng
Giai đoạn Commit → tất cả commit
Vấn đề: lock, sự phức tạp, hiệu năng
```

### Chi Tiết Cài Đặt Nội Bộ

**Idempotent Producer:**
```
PID (Producer ID) + Sequence Number
Broker từ chối trùng lặp theo sequence
Hoạt động ở cấp partition
```

**Transaction:**
```
Transaction Coordinator → quản lý trạng thái
Topic __transaction_state → lưu trữ trạng thái
Commit/Abort → các thao tác nguyên tử
```

### Phân Tích Hiệu Năng

```
So sánh độ trễ (tương đối):
At-most-once:     1x
At-least-once:    1.2x
Exactly-once:     2-3x

So sánh throughput (tương đối):
At-most-once:     100%
At-least-once:    85-95%
Exactly-once:     50-70%
```

### Khi Nào Dùng Cái Gì

**At-most-once:**
- Metrics monitoring
- Log ứng dụng
- Phân tích real-time (chấp nhận mất mát)

**At-least-once:**
- Hầu hết các hệ thống kinh doanh
- Xử lý đơn hàng
- Thông báo
- Cập nhật cache

**Exactly-once:**
- Các giao dịch tài chính
- Billing
- Chuyển khoản ngân hàng
- Chỉ các kịch bản Kafka-to-Kafka

### Các Thực Hành Tốt Nhất

```
✅ Chọn at-least-once theo mặc định
✅ Hướng đến các consumer idempotent
✅ Exactly-once chỉ cho Kafka-to-Kafka
✅ Pattern Outbox cho các hệ thống bên ngoài
✅ Ghi idempotent vào DB

❌ At-most-once cho dữ liệu quan trọng
❌ Exactly-once cho Kafka → Database
❌ Không có xử lý trùng lặp
❌ Bỏ qua các đánh đổi hiệu năng
```

### Các Quyết Định Kiến Trúc

1. **At-least-once + consumer idempotent** — cân bằng tối ưu
2. **Exactly-once yêu cầu cấu hình tham số transaction broker (transaction.state.log.replication.factor >= 2). Trong Kafka 1.0+ hỗ trợ transaction được bật theo mặc định.**
3. **Pattern Outbox — giải pháp phổ quát cho end-to-end**
4. **Ghi idempotent — rẻ hơn và đáng tin cậy hơn transaction**

### Tóm Tắt Cho Senior

- Chọn at-least-once theo mặc định
- Hướng đến việc làm cho các consumer idempotent
- Exactly-once chỉ hoạt động Kafka-to-Kafka
- Với các hệ thống bên ngoài hãy dùng Outbox hoặc ghi idempotent
- Hiểu các đánh đổi hiệu năng của mỗi ngữ nghĩa

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- At-most-once: độ trễ 1x, có thể mất, cho metrics/log
- At-least-once: độ trễ 1.2x, có thể trùng lặp, cho các hệ thống kinh doanh
- Exactly-once: độ trễ 2-3x, throughput 50-70%, chỉ cho tài chính
- Exactly-once chỉ hoạt động sẵn có cho Kafka-to-Kafka
- Cho Kafka → DB: pattern Outbox hoặc ghi idempotent (UPSERT)
- At-least-once + consumer idempotent — cân bằng tối ưu cho hầu hết các hệ thống
- Commit TRƯỚC khi xử lý = mất dữ liệu, commit SAU = at-least-once

**Các câu hỏi phụ thường gặp:**
- *Tại sao exactly-once không hoạt động với các hệ thống bên ngoài?* — Kafka không thể quản lý một transaction PostgreSQL.
- *Pattern Outbox là gì?* — INSERT vào outbox_table trong cùng transaction → Debezium CDC → Kafka.
- *Ngữ nghĩa nào là mặc định?* — At-least-once, hướng đến các consumer idempotent.
- *Overhead của exactly-once là gì?* — Độ trễ 2-3x, throughput 50-70%.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Exactly-once hoạt động cho Kafka → HTTP API" — HTTP không hỗ trợ các transaction Kafka
- "At-most-once cho đơn hàng" — mất đơn hàng là không chấp nhận được
- "Trùng lặp không phải vấn đề" — tính phí hai lần = bug trong business logic
- "Commit trước khi xử lý là thực hành tiêu chuẩn" — đó là mất dữ liệu
