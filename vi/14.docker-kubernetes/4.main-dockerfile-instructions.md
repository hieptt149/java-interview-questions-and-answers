# What are the main instructions used in Dockerfile? (Các instruction chính được dùng trong Dockerfile là gì?)

## Junior Level

### Các Instruction Chính

Một Dockerfile bao gồm các instruction, mỗi instruction tạo một layer mới trong image. Dưới đây là các instruction chính:

### Các Instruction Định Nghĩa Môi Trường

| Instruction | Nó làm gì                     | Ví dụ                |
| ----------- | -------------------------------- | ---------------------- |
| `FROM`      | Đặt image nền              | `FROM openjdk:17-slim` |
| `WORKDIR`   | Đặt thư mục làm việc       | `WORKDIR /app`         |
| `ENV`       | Đặt các biến môi trường       | `ENV APP_PORT=8080`    |

### Các Instruction Thao Tác File

| Instruction | Nó làm gì                              |
| ----------- | ----------------------------------------- |
| `COPY`      | Sao chép các file từ host vào image     |
| `ADD`       | Giống COPY, nhưng có thể giải nén archive        |

### Các Instruction Thực Thi Lệnh

| Instruction    | Nó làm gì                                  |
| -------------- | --------------------------------------------- |
| `RUN`          | Thực thi một lệnh trong quá trình build image         |
| `CMD`          | Lệnh mặc định khi container khởi động         |
| `ENTRYPOINT`   | Lệnh khởi chạy chính của container                 |

### Các Instruction Cấu Hình

| Instruction | Nó làm gì                        |
| ----------- | ----------------------------------- |
| `EXPOSE`    | Ghi tài liệu về port ứng dụng      |
| `USER`      | Chỉ định user để chạy       |

### Ví Dụ Đơn Giản

```dockerfile
FROM openjdk:17-jdk-slim       # Image nền
WORKDIR /app                    # Thư mục làm việc
COPY myapp.jar app.jar          # Sao chép file jar
EXPOSE 8080                     # Port (chỉ để ghi tài liệu)
ENTRYPOINT ["java", "-jar", "app.jar"]  # Lệnh khởi chạy
```

### COPY vs ADD

- **COPY** — lựa chọn được ưu tiên (95% trường hợp).
- **ADD** — nếu bạn cần tự động giải nén tar archive hoặc tải từ URL (nhưng với URL, RUN curl tốt hơn).

Exec form `["cmd", "arg"]` — lệnh chạy trực tiếp. Shell form `cmd arg` — thông qua shell `/bin/sh -c`.
ENV — biến khả dụng cả trong quá trình build lẫn trong container đang chạy. ARG — chỉ trong quá trình build.

### Cần Nhớ

- `FROM` luôn là instruction đầu tiên
- `RUN` — thực thi trong quá trình build, `CMD`/`ENTRYPOINT` — khi khởi chạy
- `COPY` — lựa chọn được ưu tiên (95% trường hợp). `ADD` — nếu bạn cần tự động giải nén tar archive hoặc tải URL.
- `EXPOSE` không mở port, chỉ ghi tài liệu về nó
- Dùng `WORKDIR` thay vì `RUN cd ...`

## Middle Level

### Phân Loại Instruction

#### 1. Các Instruction Định Nghĩa Môi Trường

**FROM** — đặt image nền. Bất kỳ Dockerfile nào cũng bắt đầu với instruction này. Thực hành tốt nhất: chỉ định một phiên bản cụ thể (`openjdk:17-slim`), không phải `latest`.

**ENV** — đặt các biến môi trường. Khả dụng cả trong quá trình build lẫn trong container đang chạy.
```dockerfile
ENV JAVA_OPTS="-Xmx512m"
ENV APP_ENV=production
```

**ARG** — định nghĩa các biến chỉ khả dụng **trong quá trình build**.
```dockerfile
ARG APP_VERSION=1.0.0
RUN echo "Building version $APP_VERSION"
```

**WORKDIR** — đặt thư mục làm việc. Tất cả các lệnh sau đó thực thi tương đối với nó.
```dockerfile
WORKDIR /app    # tốt hơn RUN cd /app
```

#### 2. Các Instruction Thao Tác File

**COPY** — sao chép các file từ host vào image.
```dockerfile
COPY pom.xml /app/
COPY src/ /app/src/
```

**ADD** — phiên bản mở rộng của COPY. Có thể giải nén archive (`.tar.gz`) và tải file từ URL.
```dockerfile
ADD app.tar.gz /app/  # tự động giải nén
```

#### 3. Các Instruction Thực Thi Lệnh

**RUN** — thực thi một lệnh trong quá trình build và ghi lại kết quả vào một layer mới.
```dockerfile
# Kết hợp các lệnh để giảm số layer
RUN apt-get update && \
    apt-get install -y git curl && \
    rm -rf /var/lib/apt/lists/*
// Xóa trong cùng RUN là quan trọng: nếu bạn xóa trong một RUN riêng biệt,
// các file vẫn còn ở layer bên dưới và sẽ nằm trong image.
```

**CMD** — đặt lệnh mặc định khi container khởi động. Dễ bị ghi đè.
```dockerfile
CMD ["--server.port=8080"]
```

**ENTRYPOINT** — định nghĩa lệnh khởi chạy chính. Khó bị ghi đè hơn.
```dockerfile
ENTRYPOINT ["java", "-jar", "/app.jar"]
```

#### 4. Các Instruction Cấu Hình Truy Cập

**EXPOSE** — ghi tài liệu về port. **Không thực sự publish** nó (bạn cần `-p` khi khởi chạy).

**USER** — chỉ định user để chạy.
```dockerfile
RUN useradd -r appuser
USER appuser
```

**VOLUME** — tạo một điểm mount cho dữ liệu tồn tại lâu dài.
```dockerfile
VOLUME ["/data"]
```

### Các Lỗi Thường Gặp

| Lỗi                                         | Hậu quả                            | Cách tránh                                         |
| ----------------------------------------------- | -------------------------------------- | ---------------------------------------------------- |
| `RUN apt-get update` trong một layer riêng biệt        | Cache lỗi thời, không tìm thấy package    | Kết hợp `update && install` trong một RUN               |
| Dùng shell form `CMD java -jar`                | Signal không đến được ứng dụng     | Dùng exec form `["java", "-jar"]`                     |
| Truyền secret qua ARG                         | Mật khẩu hiển thị trong `docker history`   | Dùng BuildKit secrets (`--mount=type=secret`)          |
| Xóa file trong một RUN riêng biệt                | File vẫn còn trong các layer bên dưới          | Xóa trong cùng RUN nơi bạn đã tạo chúng        |
| Nhiều CMD/ENTRYPOINT                         | Chỉ cái cuối cùng được tính                | Một CMD, một ENTRYPOINT mỗi file                     |

### So Sánh CMD vs ENTRYPOINT

| Instruction      | Có thể ghi đè?              | Mục đích chính            |
| ---------------- | -------------------------- | ----------------------- |
| **ENTRYPOINT**   | Khó khăn (`--entrypoint`) | Lệnh cố định       |
| **CMD**          | Rất dễ dàng                | Các tham số mặc định      |

### Thực Hành Tốt Nhất

1. Kết hợp các lệnh `RUN` qua `&&` để giảm số layer
2. Dọn dẹp cache package trong cùng layer `RUN`
3. Dùng `WORKDIR` thay vì chuỗi `RUN cd`
4. Luôn dùng Multi-stage build để tách build và runtime

### Cần Nhớ

- Mỗi `RUN`, `COPY`, `ADD` tạo một layer mới
- Thứ tự instruction ảnh hưởng đến caching
- Dùng Exec form `["cmd", "arg"]` thay vì Shell form
- Dọn dẹp cache trong cùng layer với việc cài đặt
- `ENTRYPOINT` + `CMD` cùng nhau — thực hành tốt nhất

## Senior Level

### Kiến Trúc Instruction Và Tác Động Đến Image

Việc hiểu các sắc thái của instruction là quan trọng để tạo ra các image an toàn, gọn nhẹ, và build nhanh.

### Phân Tích Sâu: Mô Hình Theo Lớp

Mỗi instruction `RUN`, `COPY`, `ADD` tạo một **layer mới**. Các layer là các filesystem chỉ đọc được kết hợp thông qua UnionFS (Overlay2).

**Hậu quả quan trọng:** xóa một file trong một layer mới không loại bỏ nó khỏi image — chỉ một entry "whiteout" được tạo. Kích thước file trong image = tổng của tất cả các layer nơi nó xuất hiện.

```dockerfile
# TỒI: file vẫn còn trong layer bên dưới
RUN apt-get update && apt-get install -y package
RUN rm -rf /var/lib/apt/lists/*

# TỐT: một layer, cache được dọn dẹp ngay lập tức
RUN apt-get update && \
    apt-get install -y package && \
    rm -rf /var/lib/apt/lists/*
```

### Đánh Đổi (Trade-offs)

| Quyết định              | Điểm cộng                            | Điểm trừ                                 |
| --------------------- | ------------------------------- | ------------------------------------- |
| Shell form            | Tiện lợi (pipe, biến)  | Vấn đề PID 1, signal không đến được    |
| Exec form             | Xử lý signal đúng cách          | Không có chức năng của shell                |
| ARG cho cấu hình        | Đơn giản                          | Hiển thị trong `docker history`, không phải runtime |
| ENV cho cấu hình        | Khả dụng tại runtime            | Hiển thị trong `docker inspect`           |
| ADD cho URL           | Không cần RUN curl/wget          | Cache khó dự đoán, không có retry         |
| RUN curl/wget         | Kiểm soát, retry, checksum        | Layer bổ sung                      |

### ARG vs ENV: Các Sắc Thái

| Đặc điểm            | ARG            | ENV   |
| ------------------------- | -------------- | ----- |
| Khả dụng trong quá trình build    | Có            | Có   |
| Khả dụng trong container    | Không             | Có   |
| Hiển thị trong `docker inspect` | Không           | Có   |
| Hiển thị trong `docker history` | Có (giá trị!) | Có   |

**Cảnh báo bảo mật:** Các giá trị ARG hiển thị trong `docker history`. Đừng truyền secret qua ARG!

```dockerfile
# TỒI: mật khẩu hiển thị trong docker history
ARG DB_PASSWORD=secret123

# TỐT: BuildKit secrets
RUN --mount=type=secret,id=db_pass cat /run/secrets/db_pass
```

### Shell Form vs Exec Form: Sắc Thái Quan Trọng

**Exec form** (khuyến nghị):
```dockerfile
ENTRYPOINT ["java", "-jar", "/app.jar"]
```
Chạy trực tiếp như một process với PID 1. Xử lý signal đúng cách (`SIGTERM`, `SIGKILL`). Quan trọng cho graceful shutdown trong Kubernetes.

**Shell form**:
```dockerfile
ENTRYPOINT java -jar /app.jar
```
Chạy như một subprocess của `/bin/sh -c`. Các signal của OS đến shell `sh`, không phải ứng dụng. Ứng dụng có thể bị "giết" đột ngột mà không hoàn thành các transaction.

**Vấn đề PID 1:** trong Linux, process với PID 1 có hành vi đặc biệt — nó không nhận SIGTERM theo mặc định. Giải pháp: exec form, tini, hoặc `docker run --init`.

### Edge Case

- **ONBUILD trong multi-stage**: các instruction `ONBUILD` thực thi khi image được dùng làm nền. Trong multi-stage điều này có thể dẫn đến các side effect không mong muốn.
- **Glob pattern trong COPY**: `COPY target/*.jar` — nếu không có file nào tồn tại, build thất bại. Nếu có nhiều file, tất cả được sao chép vào thư mục chỉ định.
- **Symbolic link**: `COPY` theo (follow) các symlink trên host. Điều này có thể bao gồm các file không mong muốn.
- **Timestamp**: `COPY` giữ nguyên mtime của file. Điều này ảnh hưởng đến tính tất định của build. BuildKit `--metadata-file` giúp theo dõi.
- **ENV và escaping**: `ENV FOO=bar\ baz` — khoảng trắng trong giá trị. `ENV FOO="bar baz"` — các dấu ngoặc kép được bao gồm trong giá trị.

### HEALTHCHECK: Nghĩa Vụ Production

```dockerfile
HEALTHCHECK --interval=30s --timeout=3s --retries=3 --start-period=60s \
  CMD curl -f http://localhost:8080/actuator/health || exit 1
```

Không có HEALTHCHECK, orchestrator không biết ứng dụng có còn sống hay không. Container có thể đang `Running`, nhưng ứng dụng bên trong — đã chết (deadlock, hết bộ nhớ).

### BuildKit: Các Tính Năng Nâng Cao

```dockerfile
# Cú pháp BuildKit
# syntax=docker/dockerfile:1

# Secrets
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm install

# SSH forwarding (cho các repo git private)
RUN --mount=type=ssh git clone git@github.com:org/private-repo.git

# Cache mount (cho các trình quản lý package)
RUN --mount=type=cache,target=/root/.m2 mvn package

# TMPFS mount
RUN --mount=type=tmpfs,target=/tmp make
```

### ONBUILD: Instruction Cho Các Image Cha

```dockerfile
# Trong image nền
ONBUILD COPY . /app
ONBUILD RUN mvn package
```

Được dùng để tạo các image cha tự động hóa các bước cho các con của chúng. Nguy hiểm trong multi-stage: `ONBUILD` không thực thi cho các stage tiếp theo.

### LABEL: Metadata Cho CI/CD

```dockerfile
LABEL maintainer="team@example.com"
LABEL version="1.0.0"
LABEL org.opencontainers.image.source="https://github.com/org/repo"
LABEL org.opencontainers.image.revision="abc123"
```

Hữu ích cho việc theo dõi image trong registry, tự động hóa, tuân thủ.

### Hiệu Năng

| Tối ưu hóa             | Tác động                              |
| ------------------------ | ----------------------------------- |
| Tách pom.xml và src | Tỷ lệ cache hit > 90%                |
| Kết hợp các lệnh RUN     | Ít hơn 20-40% layer                 |
| Alpine thay vì bản đầy đủ   | Kích thước nhỏ hơn 60-80%                  |
| Multi-stage build        | Image cuối cùng nhỏ hơn 50-70%          |
| BuildKit cache mount     | Build lặp lại nhanh hơn 50%          |

### Tóm Tắt

- Mỗi lệnh `RUN`, `COPY`, `ADD` tạo một layer mới — xóa các file tạm trong cùng layer.
- Dùng Exec form cho `CMD` và `ENTRYPOINT` — quan trọng cho việc xử lý signal.
- ARG hiển thị trong `docker history` — đừng truyền secret.
- `HEALTHCHECK` là một thành phần bắt buộc của các image production.
- BuildKit (`--mount=type=secret/cache/ssh`) — tiêu chuẩn build hiện đại.
- Tối ưu hóa layer = tiết kiệm dung lượng registry + deploy nhanh hơn.

## Interview Cheat Sheet

**Cần phải biết:**
- RUN thực thi trong quá trình build, CMD/ENTRYPOINT — khi khởi chạy container
- Mỗi RUN/COPY/ADD tạo một layer mới; xóa trong một RUN riêng biệt không loại bỏ file khỏi image
- Exec form `["cmd", "arg"]` quan trọng cho việc xử lý signal (graceful shutdown)
- ARG hiển thị trong `docker history` — đừng truyền secret; dùng BuildKit secrets
- ENV khả dụng tại runtime, ARG — chỉ trong quá trình build
- HEALTHCHECK bắt buộc cho các image production
- BuildKit: `--mount=type=secret/cache/ssh` — tiêu chuẩn build hiện đại

**Các câu hỏi phụ thường gặp:**
- *"Tại sao shell form lại tồi?"* — Chạy qua `/bin/sh -c`, các signal của OS không đến được ứng dụng (vấn đề PID 1)
- *"Tại sao kết hợp các lệnh RUN với &&?"* — Mỗi instruction = một layer; kết hợp giảm số lượng layer
- *"ONBUILD làm gì?"* — Các instruction thực thi khi image được dùng làm nền (cho các image cha)
- *"EXPOSE có mở một port không?"* — Không, chỉ ghi tài liệu; ánh xạ thực sự qua `-p` khi khởi chạy

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "EXPOSE làm cho port có thể truy cập được từ bên ngoài" (chỉ ghi tài liệu, cần `-p`)
- "Tôi truyền mật khẩu qua ARG" (hiển thị trong `docker history`)
- "Tôi xóa file trong một layer RUN riêng biệt" (file vẫn còn trong layer bên dưới)
- "Tôi dùng shell form cho ENTRYPOINT" (vấn đề PID 1, signal bị mất)
