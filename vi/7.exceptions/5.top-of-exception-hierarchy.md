# What is at the top of the exception hierarchy? (Cái gì nằm ở đỉnh của cây phân cấp exception?)

## Junior Level

### Gốc của cây phân cấp - java.lang.Throwable

Ở đỉnh cao nhất của cây phân cấp của tất cả các object có thể được ném và bắt là lớp **`java.lang.Throwable`**.

```
Object
  └── Throwable
        ├── Error (lỗi JVM nghiêm trọng)
        │     ├── OutOfMemoryError
        │     ├── StackOverflowError
        │     └── NoClassDefFoundError
        │
        └── Exception (lỗi ứng dụng)
              ├── RuntimeException (unchecked)
              │     ├── NullPointerException
              │     └── IllegalArgumentException
              │
              └── Checked Exceptions
                    ├── IOException
                    └── SQLException
```

### Hai nhánh chính

**Error** - các vấn đề JVM nghiêm trọng:
- `OutOfMemoryError` - hết bộ nhớ
- `StackOverflowError` - đệ quy vô hạn
- Đừng bắt chúng - hệ thống đang ở trạng thái không ổn định

**Exception** - các lỗi ứng dụng:
- Có thể và nên được xử lý
- Chia thành checked và unchecked

Error - các vấn đề mà ứng dụng không thể sửa (bộ nhớ, stack).
Exception - các vấn đề mà nó có thể.
Sự phân tách trong cây phân cấp cho phép bắt Exception mà không bắt Error.

### Ví dụ

```java
// Throwable - cha của tất cả các exception
try {
    // một đoạn code
} catch (Throwable t) {
    // Bắt MỌI THỨ, bao gồm cả Error (thường thì bạn không làm thế này)
    System.err.println("Caught: " + t.getMessage());
}
```

## Middle Level

### Tại sao Throwable implement Serializable?

Serialization - chuyển đổi một object thành byte để truyền qua mạng hoặc lưu trữ. Điều này cần cho RMI (remote method invocation), JMX, caching. Một exception phải serializable được để "đi lại" giữa các JVM.

Điều này then chốt cho các hệ thống phân tán (RMI, JMX). Khi một exception xảy ra trên server, JVM serialize nó cùng với stack trace và gửi tới client.

### Các lớp con chính của Error

- **`OutOfMemoryError`** - các kiểu con khác nhau:
  - `Java heap space` - heap đầy
  - `Metaspace` - không còn bộ nhớ cho metadata của class
  - `Unable to create new native thread` - OS từ chối cấp thread

- **`ThreadDeath`** - được ném khi `Thread.stop()` (deprecated). Đây là một `Error` để một `catch (Exception e)` thông thường không nuốt mất nó.

- **`NoClassDefFoundError`** - class có mặt lúc biên dịch nhưng thiếu lúc runtime. Tính toàn vẹn của môi trường bị phá vỡ.

### Vấn đề lan truyền qua ExecutorService

Khi một exception xảy ra bên trong một thread của pool, nó bị bắt bởi `ExecutorService` và lưu bên trong `Future`:

```java
Future<?> future = executor.submit(() -> {
    throw new RuntimeException("Task failed!");
});

// Exception bị "giấu" bên trong Future
try {
    future.get(); // ExecutionException được ném ra ở đây
} catch (ExecutionException e) {
    System.err.println("Cause: " + e.getCause()); // RuntimeException
}
// ExecutorService bắt mọi exception từ các task và lưu chúng bên trong Future.
// Khi future.get() được gọi, exception được bọc trong ExecutionException.
// Để tới được cause: e.getCause().
```

### fillInStackTrace()

fillInStackTrace() - một phương thức native (viết bằng C/C++, không phải Java). Nó duyệt call stack ở mức OS, tạo một ảnh chụp (snapshot) của tất cả các frame. Điều này đắt đỏ: đòi hỏi chuyển tiếp giữa code Java và native + duyệt toàn bộ stack.

Khi `getStackTrace()` được gọi, cấu trúc native được chuyển đổi thành mảng `StackTraceElement[]` - đây là một tối ưu hóa lười (lazy), nhưng việc điền cấu trúc native vẫn đắt đỏ.

## Senior Level

### Bên trong: trường backtrace ẩn

Bên trong `Throwable` có một trường `private Object backtrace`, được điền bởi phương thức native `fillInStackTrace()`. Nó giữ một tham chiếu tới call stack native trong bộ nhớ JVM.

**Cạm bẫy Serialization:** trong quá trình serialize, `backtrace` native bị mất, và JVM chuyển đổi nó thành một mảng các object Java. Điều này làm tăng kích thước gói tin và tải CPU.

### Tắt stack trace để tăng hiệu suất

```java
public class FastException extends RuntimeException {
    public FastException(String message) {
        // enableSuppression = true, writableStackTrace = false
        super(message, null, true, false);
    }
}
```

Tăng tốc việc tạo lên hàng chục lần - việc duyệt stack native không được thực thi.

### Immutable Exception

Trong các hệ thống tải cao, các instance tĩnh được tạo ra:

```java
public static final MyException INVALID_DATA =
    new MyException("Invalid data", null, true, false);
```

Không tạo object mới, nhưng log sẽ có các stack trace giống hệt nhau.

### Suppressed Exception

Được giới thiệu trong Java 7 cho try-with-resources. Nếu một exception xảy ra trong `try`, và một cái thứ hai - khi đóng resource trong `finally`, cái đầu tiên trở thành cái chính, cái thứ hai được thêm vào dưới dạng `suppressed`:

```java
try {
    resource.doWork(); // IOException #1
} finally {
    resource.close();  // IOException #2
}
// IOException #1 - chính, #2 - suppressed
```

### Chẩn đoán

- **Đừng bao giờ** làm `catch (Throwable t)` trong logic nghiệp vụ - sẽ bắt `OutOfMemoryError`
- **Root Cause Analysis** - dùng `ExceptionUtils.getRootCause()` để tìm nguyên nhân gốc
- **Hệ thống phân tán** - ở biên của service, trích xuất message và mã lỗi, chỉ truyền DTO

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Gốc của cây phân cấp - `java.lang.Throwable` (không phải `Exception`)
- Hai nhánh: `Error` (các vấn đề JVM nghiêm trọng) và `Exception` (lỗi ứng dụng)
- Error - `OutOfMemoryError`, `StackOverflowError`, `NoClassDefFoundError` - đừng bắt
- Exception chia thành `RuntimeException` (unchecked) và các checked exception
- `fillInStackTrace()` - phương thức native, duyệt call stack, thao tác đắt đỏ
- Suppressed exception - cơ chế Java 7 cho try-with-resources (lưu exception thứ hai)
- Tắt stack trace (`writableStackTrace = false`) tăng tốc việc tạo lên hàng chục lần
- Trong quá trình serialize, `backtrace` native bị mất - chuyển đổi thành object Java

**Các câu hỏi phụ thường gặp:**
- **Tại sao Throwable implement Serializable?** - Cho RMI, JMX, caching - exception "đi lại" giữa các JVM
- **Điều gì xảy ra nếu bạn bắt OutOfMemoryError?** - JVM có thể ở trạng thái không ổn định, thao tác tiếp theo sẽ thất bại
- **Suppressed exception là gì?** - Khi cả try và close() đều ném hai exception, cái thứ hai được thêm vào danh sách suppressed của cái đầu tiên
- **Tại sao không tạo immutable exception cho mọi thứ?** - Stack trace giống hệt nhau làm việc debug khó hơn

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Gốc của cây phân cấp là Exception" - không, là Throwable
- "Tôi bắt Throwable trong logic nghiệp vụ cho chắc chắn" - nó sẽ bắt OutOfMemoryError
- "fillInStackTrace() là một phương thức Java thông thường" - không, nó là native, duyệt stack ở mức OS
