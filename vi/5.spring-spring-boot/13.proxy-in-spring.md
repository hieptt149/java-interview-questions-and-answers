# What is a Proxy in Spring? (Proxy trong Spring là gì?)

## Junior Level

**Proxy** là một đối tượng trung gian mà Spring tạo bao quanh bean của bạn.

**Ví dụ minh họa đơn giản:** Một nhân viên lễ tân. Bạn muốn nói chuyện với giám đốc, nhưng trước tiên bạn phải qua nhân viên lễ tân — người kiểm tra giấy tờ, ghi lại lịch hẹn của bạn, v.v.

```java
@Service
public class UserService {
    @Transactional  // Spring sẽ tạo một Proxy bao quanh bean này
    public void save(User user) { }
}

// Bạn nhận được không phải UserService, mà là một Proxy!
// Proxy -> mở transaction -> gọi save() -> đóng transaction
```

**Tại sao:**
- Thêm chức năng mà không thay đổi code của bạn
- @Transactional, @Async, @Cacheable — tất cả đều hoạt động qua proxy

## Middle Level

### Hai loại Proxy

**JDK Dynamic Proxy:**
```java
// Qua interface
public interface UserService { void save(User user); }

// Spring tạo:
class UserServiceProxy implements UserService {
    private UserService target;
    public void save(User user) {
        // Trước lời gọi
        target.save(user);
        // Sau lời gọi
    }
}
```

**CGLIB:**
```java
// Qua kế thừa
class UserServiceProxy extends UserService {
    // Override các phương thức
}

// Không thể proxy các class/phương thức final!
```

### Mặc định của Spring Boot

```
Spring Boot 2.x/3.x: proxy-target-class=true theo mặc định, nên CGLIB luôn được dùng, kể cả khi có interface. Spring 1.x: JDK Dynamic Proxy theo mặc định.

Tại sao:
  -> Ít vấn đề về kiểu hơn
  -> Có thể inject theo class, không phải theo interface
```

### Self-invocation (tự gọi trong cùng đối tượng)

```java
@Service
public class UserService {
    public void outer() {
        inner();  // @Transactional sẽ KHÔNG hoạt động!
    }

    @Transactional
    public void inner() { }
}

// outer() -> inner() đi thẳng, vòng qua proxy!
```

## Senior Level

### Chuỗi Interceptor

```
Lời gọi phương thức trên proxy:
  1. SecurityInterceptor -> kiểm tra quyền
  2. TransactionInterceptor -> mở transaction
  3. CacheInterceptor -> kiểm tra cache
  4. Phương thức đích -> code của bạn
  5. Commit/Rollback
  6. Trả về kết quả

-> Mỗi interceptor = một Advice
-> Thứ tự được xác định bởi @Order
```

### Cách kiểm tra một Proxy

```java
// Trong debugger:
// JDK: com.sun.proxy.$Proxy123
// CGLIB: UserService$$EnhancerBySpringCGLIB$$abc123

// Theo lối lập trình:
AopUtils.isAopProxy(bean);
AopUtils.isCglibProxy(bean);
AopUtils.getTargetClass(proxy);  // khi bạn làm việc với một đối tượng nhưng không biết nó là proxy hay bản gốc (ví dụ khi so sánh kiểu qua instanceof hoặc getDeclaredMethod).
```

### Kinh nghiệm Production

**Tình huống thực tế: phương thức final không được proxy**
```java
@Service
public class UserService {
    @Transactional
    public final void save(User user) { }  // final!
}

// CGLIB tạo một subclass và override các phương thức.
// Các phương thức final không thể được override, nên lời gọi đi
// thẳng - vòng qua logic của proxy (transaction, logging, v.v.)

// Transaction KHÔNG được tạo!
// -> Dữ liệu được lưu KHÔNG có transaction
// -> Bug trên production!
```

### Best Practices

1. **JDK Proxy** -> qua interface
2. **CGLIB** -> qua kế thừa (không final!)
3. **Self-invocation** -> transaction không hoạt động
4. **AopUtils.getTargetClass()** -> cho reflection
5. **Tránh final** trên các phương thức được proxy
6. **Spring Boot** -> CGLIB theo mặc định

### Tóm tắt cho Senior

- **Proxy** = lớp bọc cho AOP
- **JDK** = interface, **CGLIB** = kế thừa
- **Spring Boot** -> luôn CGLIB
- **Self-invocation** = lời gọi vòng qua proxy
- **Các phương thức final** -> không được CGLIB proxy
- **Chuỗi interceptor** -> thứ tự qua @Order

## Interview Cheat Sheet

**Cần phải biết:**
- Proxy = đối tượng bọc thêm chức năng AOP mà không thay đổi code
- Hai loại: JDK Dynamic Proxy (qua interface) và CGLIB (qua kế thừa)
- Spring Boot 2.x/3.x: proxy-target-class=true theo mặc định -> luôn CGLIB
- @Transactional, @Async, @Cacheable — tất cả đều hoạt động qua proxy
- Self-invocation: gọi `this.method()` đi thẳng, bỏ qua proxy
- Các class final và phương thức final KHÔNG thể được proxy qua CGLIB
- Chuỗi interceptor: Security -> Transaction -> Cache -> Phương thức đích

**Các câu hỏi phụ thường gặp:**
- *Làm sao kiểm tra một bean có phải proxy không?* -> AopUtils.isAopProxy(bean), AopUtils.isCglibProxy(bean)
- *Tại sao self-invocation không hoạt động?* -> this trỏ tới Target, không phải Proxy
- *Làm sao lấy class gốc từ một proxy?* -> AopUtils.getTargetClass(proxy)
- *Sự khác nhau giữa JDK Proxy và CGLIB là gì?* -> JDK cần interface, CGLIB tạo một subclass

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "CGLIB có thể proxy các phương thức final" — không thể, không kế thừa được
- "Self-invocation hoạt động với CGLIB" — không hoạt động, this = Target
- "Proxy thêm overhead đáng kể" — cỡ nanosecond, không đáng kể
- "Spring tạo một proxy cho mọi bean" — chỉ khi có các annotation AOP
