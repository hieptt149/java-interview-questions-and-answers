# Which exceptions cause rollback by default? (Những exception nào gây ra rollback theo mặc định?)

## 🟢 Junior Level

Spring **không** rollback transaction với tất cả các exception. Có một quy tắc rõ ràng.

### Quy Tắc Mặc Định

Spring tự động rollback chỉ với:
- **RuntimeException** (NullPointerException, IllegalArgumentException, v.v.)
- **Error** (OutOfMemoryError, StackOverflowError, v.v.)

Đây là các **Unchecked Exception** — những exception không cần khai báo trong `throws`.

**Cơ chế:** TransactionInterceptor bắt exception và kiểm tra: nếu loại = RuntimeException hoặc Error → setRollbackOnly(). Nếu loại = Exception (nhưng không phải RuntimeException) → commit, như thể method đã hoàn thành bình thường.

### Điều Gì KHÔNG Kích Hoạt Rollback

**Checked Exception** — các subclass của `Exception` (nhưng không phải `RuntimeException`):
- `IOException`
- `SQLException`
- Bất kỳ `extends Exception` tùy chỉnh nào

Nếu các exception này được ném từ một method `@Transactional` — Spring sẽ **COMMIT**.

### Ví Dụ

```java
@Transactional
public void process() {
    throw new RuntimeException("fail");  // ROLLBACK ✅
}

@Transactional
public void process2() throws IOException {
    throw new IOException("fail");  // COMMIT ❌ — dữ liệu sẽ được lưu!
}
```

### Ví Dụ Minh Họa

Hãy nghĩ về một hệ thống báo động: RuntimeException = hỏa hoạn (bỏ mọi thứ và sơ tán = rollback). Checked Exception = kiểm tra định kỳ (tiếp tục làm việc = commit).

### Cách Thay Đổi Hành Vi

```java
@Transactional(rollbackFor = Exception.class)  // Rollback cho TẤT CẢ các exception
public void process() throws IOException { ... }
```

## 🟡 Middle Level

### Tại Sao Spring Chọn Chính Sách Này?

Quyết định kiến trúc từ triết lý EJB:

- **RuntimeException** — lỗi hệ thống không lường trước được hoặc bug. Trạng thái hệ thống không xác định → phải rollback.
- **Checked Exception** — tình huống nghiệp vụ được dự đoán trước (ví dụ: `InsufficientFundsException`). Lập trình viên nên xử lý và có thể commit các thay đổi.

> Hành vi này không thay đổi kể từ Spring 2.x và giống nhau trong Spring Boot 3.x. Nhưng trong Spring 6+ với Ahead-of-Time compilation có thể có những điểm tinh vi với việc giải quyết loại exception — hãy kiểm thử nó.

### Phân Loại Đầy Đủ

| Loại exception             | Ví dụ                                        | Rollback theo mặc định?      |
| -------------------------- | ---------------------------------------------- | ------------------------- |
| `RuntimeException`         | NullPointerException, IllegalArgumentException | ✅ Có                     |
| `Error`                    | OutOfMemoryError, StackOverflowError           | ✅ Có                     |
| Checked Exception          | IOException, SQLException                      | ❌ Không                      |
| Custom checked             | `BusinessException extends Exception`          | ❌ Không                      |
| Spring DataAccessException | DataIntegrityViolationException                | ✅ Có (nó là RuntimeException) |

// Tại sao commit: BusinessException kế thừa từ Exception (không phải RuntimeException).
// Spring thấy checked exception → xử lý như "hoàn thành bình thường" → commit.
// Kết quả: dữ liệu được lưu một phần, mặc dù logic nghiệp vụ "thất bại".

### Cách Cấu Hình Rollback Cho Checked Exception

```java
// Cho tất cả các Exception
@Transactional(rollbackFor = Exception.class)
public void businessMethod() throws MyCheckedException { ... }

// Cho một exception cụ thể
@Transactional(rollbackFor = IOException.class)
public void readFile() throws IOException { ... }

// Cho nhiều exception
@Transactional(rollbackFor = {IOException.class, MyBusinessException.class})
public void process() throws IOException, MyBusinessException { ... }

// Loại trừ một RuntimeException cụ thể khỏi rollback
@Transactional(noRollbackFor = MyCustomRuntimeException.class)
public void processWithExceptionHandling() { ... }
```

### Vấn Đề Với Khối Catch

Nếu bạn bắt một exception bên trong method — Spring sẽ không biết về nó:

```java
@Transactional
public void save() {
    try {
        repository.save(user);
        throw new RuntimeException();
    } catch (Exception e) {
        log.error("Error occurred");
        // TRANSACTION SẼ ĐƯỢC COMMIT! Spring không thấy exception.
    }
}
```

Để transaction rollback, exception phải **thoát ra** khỏi ranh giới method của proxy.

### Các Lỗi Thường Gặp

| Lỗi                     | Điều gì xảy ra                                         | Cách khắc phục                          |
| --------------------------- | ---------------------------------------------------- | ----------------------------------- |
| Không biết chính sách mặc định  | COMMIT khi có checked exception                          | `rollbackFor = Exception.class`     |
| Bắt và nuốt           | Spring thấy trả về bình thường → COMMIT                   | Ném lại hoặc `setRollbackOnly()`      |
| Sai hệ thống phân cấp exception   | `BusinessException extends Exception` — không rollback  | Kế thừa từ `RuntimeException`     |
| Thứ tự AOP                | Aspect tùy chỉnh bắt exception trước TransactionInterceptor | Kiểm tra thứ tự aspect       |
| Method `@Async`             | Exception không lan truyền đến transaction của bên gọi   | Context transaction riêng biệt        |

### Khi Nào KHÔNG Nên Dùng Rollback

| Tình huống             | Tại sao                                         | Giải pháp thay thế                               |
| --------------------- | ------------------------------------------- | ----------------------------------------- |
| Thành công từng phần trong batch | Một item thất bại ≠ toàn bộ batch thất bại    | Xử lý, tiếp tục, commit phần còn lại             |
| Validation nghiệp vụ   | Tình huống được dự đoán trước, dữ liệu hợp lệ cho đến khi có lỗi  | `noRollbackFor = ValidationException.class` |
| Graceful degradation  | Hệ thống nên hoạt động ở chế độ suy giảm         | Không rollback, mà là logic fallback          |

### So Sánh Các Cách Tiếp Cận

| Cách tiếp cận                          | Ưu điểm                                  | Nhược điểm                                | Khi nào nên dùng                    |
| --------------------------------- | ------------------------------------- | ----------------------------------- | ------------------------------ |
| RuntimeException (mặc định)        | Rollback tự động, code tối thiểu      | Không dùng cho lỗi nghiệp vụ dự đoán trước    | Bug, lỗi hệ thống            |
| `rollbackFor = Exception.class`   | Tất cả các exception = rollback             | Có thể rollback những gì không nên      | Khi bất kỳ lỗi nào = trạng thái không hợp lệ |
| `setRollbackOnly()` lập trình  | Rollback có điều kiện                  | Boilerplate, gắn kết với Spring        | Các quy tắc nghiệp vụ phức tạp            |

## 🔴 Senior Level

### Giải Quyết Quy Tắc Rollback — Nội Bộ Spring

```java
// RuleBasedTransactionAttribute.rollbackOn()
@Override
public boolean rollbackOn(Throwable ex) {
    // Kiểm tra các quy tắc rollback tùy chỉnh trước
    for (RollbackRuleAttribute rule : rollbackRules) {
        int depth = rule.getDepth(ex);
        if (depth >= 0) {
            return rule instanceof RollbackRuleAttribute;
        }
    }
    // Mặc định: rollback với RuntimeException và Error
    return (ex instanceof RuntimeException || ex instanceof Error);
}
```

Method `getDepth()` duyệt qua hệ thống phân cấp exception:
```java
public int getDepth(Throwable ex) {
    return getDepth(ex.getClass(), 0);
}

private int getDepth(Class<?> exceptionClass, int depth) {
    if (exceptionClass.getName().contains(this.exceptionName)) {
        return depth;  // Tìm thấy khớp
    }
    if (exceptionClass == Throwable.class) {
        return -1;  // Không khớp, dừng tìm kiếm
    }
    return getDepth(exceptionClass.getSuperclass(), depth + 1);
}
```

### Các Quy Tắc Rollback Dựa Trên String

```java
@Transactional(rollbackForClassName = {"MyBusinessException"})
public void process() { ... }
```

Spring giải quyết tên class tại thời điểm chạy:
```java
// Constructor của RollbackRuleAttribute với String
public RollbackRuleAttribute(String exceptionPattern) {
    this.exceptionName = exceptionPattern;
    // KHÔNG được validate khi khởi động — được giải quyết một cách lazy
}
```

**Nguy cơ:** Lỗi chính tả trong tên class → quy tắc âm thầm không kích hoạt → không rollback.

### Kết Hợp rollbackFor Và noRollbackFor

```java
@Transactional(
    rollbackFor = Exception.class,
    noRollbackFor = {NotFoundException.class, ValidationException.class}
)
public void process() {
    // Exception → rollback
    // NotFoundException → KHÔNG rollback (commit dù có exception)
    // ValidationException → KHÔNG rollback
    // RuntimeException → rollback (subclass của Exception)
}
```

**Thứ tự khớp quy tắc:**
1. Khớp cụ thể nhất thắng (sâu nhất trong hệ thống phân cấp)
2. Cùng độ sâu — quy tắc khớp đầu tiên
3. Các quy tắc mặc định (RuntimeException, Error) được kiểm tra cuối cùng

### Hệ Thống Phân Cấp DataAccessException Của Spring

Spring bọc tất cả các exception cơ sở dữ liệu trong hệ thống phân cấp `DataAccessException`:

```
DataAccessException (RuntimeException)
├── DataIntegrityViolationException    — Vi phạm FK, ràng buộc unique
├── DuplicateKeyException              — Key trùng lặp
├── CannotAcquireLockException         — Lock timeout/deadlock
├── QueryTimeoutException              — Query timeout
├── CannotSerializeTransactionException — Serialization failure
└── ... còn nhiều nữa
```

Tất cả chúng đều là **RuntimeException** → kích hoạt rollback theo mặc định. Đây là lý do tại sao exception translation quan trọng:
```java
@Repository  // Kích hoạt exception translation
public class UserRepositoryImpl {
    // SQLException → DataAccessException (RuntimeException) → rollback
}
```

### Các Trường Hợp Biên (Tối Thiểu 3)

1. **Lỗi chính tả String trong `rollbackForClassName`**: `@Transactional(rollbackForClassName = "BusinesException")` — bị bỏ qua âm thầm. Spring không validate tên class khi khởi động. Exception được ném, nhưng rollback không xảy ra.

2. **Các quy tắc xung đột**: `rollbackFor = Exception.class` + `noRollbackFor = RuntimeException.class`. Hành vi phụ thuộc vào thứ tự khớp quy tắc — khớp cụ thể nhất thắng. RuntimeException sâu hơn trong hệ thống phân cấp → noRollbackFor cho nó thắng → không rollback cho RuntimeException, rollback cho checked Exception.

3. **Thứ tự AOP**: Aspect xử lý exception tùy chỉnh có thể bắt exception **trước** `TransactionInterceptor`. TransactionInterceptor thấy trả về bình thường → COMMIT. Giải pháp: `@Order` để kiểm soát thứ tự aspect.

4. **`@Async` với checked exception**: Method `@Async` có context transaction riêng biệt. Checked exception không lan truyền đến bên gọi. Transaction của bên gọi không biết về lỗi → COMMIT. Object Future giữ exception — cần kiểm tra `future.get()`.

5. **Exception được bọc**: `CompletionException` bọc checked exception gốc. Quy tắc rollback tìm kiếm khớp trên `CompletionException` (RuntimeException) → rollback. Nhưng checked exception gốc có thể không khớp với quy tắc.

### Vấn Đề Khối Catch — Phân Tích Sâu

```java
@Transactional
public void problematicMethod() {
    try {
        repository.save(entity);
        throw new DataAccessException("something went wrong") {};
    } catch (DataAccessException e) {
        log.error("Failed", e);
        // EXCEPTION ĐÃ BỊ BẮT — TransactionInterceptor không bao giờ thấy nó
        // Transaction SẼ ĐƯỢC COMMIT
    }
}
```

**Các giải pháp:**

```java
// Giải pháp 1: Ném lại
@Transactional
public void method1() {
    try {
        repository.save(entity);
        throw new RuntimeException("fail");
    } catch (RuntimeException e) {
        log.error("Failed", e);
        throw e;  // Interceptor sẽ thấy nó
    }
}

// Giải pháp 2: setRollbackOnly
@Transactional
public void method2() {
    try {
        repository.save(entity);
        throw new IOException("fail");
    } catch (IOException e) {
        log.error("Will rollback", e);
        TransactionAspectSupport.currentTransactionStatus()
            .setRollbackOnly();
    }
}

// Giải pháp 3: Bọc trong RuntimeException
@Transactional
public void method3() {
    try {
        repository.save(entity);
        throw new IOException("fail");
    } catch (IOException e) {
        throw new RuntimeException("Wrapped", e);  // Kích hoạt rollback
    }
}
```

### Các Con Số Về Hiệu Năng

| Thao tác                               | Thời gian                                            |
| --------------------------------------- | ----------------------------------------------- |
| Giải quyết quy tắc rollback (đã cache)       | ~0.5 μs                                         |
| Lời gọi `setRollbackOnly()`                | ~1 μs                                           |
| Kiểm tra loại exception (chuỗi instanceof) | ~0.1 μs                                         |
| Rollback DB thực tế                      | 1-5 ms (PostgreSQL O(1)), 5-50 ms (InnoDB O(N)) |

### Tác Động Đến Bộ Nhớ

- Các quy tắc rollback được lưu trong `TransactionAttribute` — một object mỗi method
- Với nhiều quy tắc (rollbackForClassName có lỗi chính tả) — lãng phí bộ nhớ cho các quy tắc vô dụng
- Các object exception trên stack — có thể lớn (stack trace). Stack trace dài = áp lực bộ nhớ với các lần rollback thường xuyên.

### Thread Safety

Các quy tắc rollback là bất biến (immutable) — thread-safe. `TransactionSynchronizationManager` lưu trạng thái trong ThreadLocal — các lời gọi đồng thời được cô lập.

### Câu Chuyện Thực Tế Trong Production

Service xử lý đơn hàng dùng `BusinessException extends Exception` cho các lỗi validation "được dự đoán trước". `@Transactional` không có `rollbackFor`. Khi vi phạm quy tắc nghiệp vụ, exception được ném, nhưng transaction COMMIT — đơn hàng tạo dở dang vẫn còn trong cơ sở dữ liệu. Client thấy lỗi, nhưng đơn hàng bị treo ở trạng thái "pending". Giải pháp: `rollbackFor = Exception.class` trên tất cả các method ghi + integration test.

### Best Practices Cho Highload

1. **Chính sách thống nhất**: `rollbackFor = Exception.class` trên tất cả các method ghi — mặc định cơ bản. Không có ngoại lệ.
2. **Giảm thiểu checked exception**: Chuyển các exception nghiệp vụ sang hệ thống phân cấp RuntimeException. Ít boilerplate hơn, rollback đúng theo mặc định.
3. **Không bao giờ nuốt exception**: Nếu đã bắt — `setRollbackOnly()` hoặc ném lại.
4. **Kiểm thử hành vi rollback**: Integration test nên xác minh dữ liệu thực sự được rollback.
5. **Giám sát tỷ lệ rollback**: % cao = vấn đề trong validation, không phải trong transaction.
6. **Dùng `noRollbackFor` có chọn lọc**: Chỉ cho các exception thực sự có nghĩa là "đây không phải lỗi, hãy tiếp tục".

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Spring chỉ rollback với RuntimeException và Error — checked exception → commit
- DataAccessException (tất cả subclass) — RuntimeException → rollback theo mặc định
- @Transactional(rollbackFor = Exception.class) — rollback cho TẤT CẢ các exception
- Nếu exception bị bắt bên trong method — Spring không thấy → commit, cần setRollbackOnly() hoặc ném lại
- rollbackForClassName (dựa trên string) — rủi ro: lỗi chính tả bị bỏ qua âm thầm, không validate khi khởi động
- noRollbackFor loại trừ các exception cụ thể khỏi rollback (ví dụ: ValidationException)

**Các câu hỏi phụ thường gặp:**
- Tại sao Spring chọn chính sách này? — RuntimeException = bug (rollback), Checked = tình huống nghiệp vụ dự đoán trước
- Điều gì xảy ra khi rollbackFor + noRollbackFor xung đột? — Khớp cụ thể nhất thắng (sâu nhất trong hệ thống phân cấp)
- Giải quyết quy tắc rollback hoạt động như thế nào? — RuleBasedTransactionAttribute.rollbackOn() duyệt hệ thống phân cấp exception
- Tại sao @Async không lan truyền checked exception? — Context transaction riêng biệt, exception nằm trong Future

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tất cả các exception gây ra rollback" — chỉ RuntimeException và Error
- "Exception bị bắt = Spring sẽ rollback" — Spring không thấy các exception đã bị bắt
- "rollbackForClassName = cách đáng tin cậy" — lỗi chính tả bị bỏ qua âm thầm
