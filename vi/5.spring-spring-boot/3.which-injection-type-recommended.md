# Which Injection Type is Recommended and Why? (Kiểu injection nào được khuyến nghị và tại sao?)

## Junior Level

**Khuyến nghị: Constructor Injection!**

```java
// Đúng
@Service
@RequiredArgsConstructor
public class OrderService {
    private final OrderRepository repo;
}

// Sai
@Service
public class OrderService {
    @Autowired private OrderRepository repo;  // Field injection
}
```

**Tại sao:**
1. Có thể để field `final`
2. Ứng dụng sẽ crash ngay lập tức nếu thiếu phụ thuộc
3. Dễ test mà không cần Spring

---

## Middle Level

### Ưu điểm của Constructor Injection

**1. Tính bất biến (immutability):**
```java
private final Repo repo;  // Không thể thay đổi sau khi tạo
```

**2. Fail-fast:**
```
Constructor: lỗi lúc khởi động nếu thiếu phụ thuộc
Field: đối tượng được tạo, NPE ở lần gọi phương thức đầu tiên
```

**3. Test:**
```java
// Constructor: test không cần Spring
OrderService service = new OrderService(mockRepo);

// Field: cần @SpringBootTest hoặc reflection
```

**4. Vòng phụ thuộc:**
```
Constructor -> lỗi ngay lập tức -> sửa kiến trúc
Field -> vẫn chạy -> bug lúc runtime
```

### Cách Spring chọn một constructor

```java
// Một constructor duy nhất -> Spring tự động dùng nó
public Service(Repo repo) { }  // Không cần @Autowired!

// Nhiều constructor:
// 1. Tìm @Autowired
// 2. Nếu không có -> constructor mặc định
// 3. Nếu không có -> lỗi
```

### Vấn đề vòng phụ thuộc

```java
// A -> B -> A qua các constructor
// Spring không thể tạo cái nào cả -> lỗi

// Refactoring: tách ra một service dùng chung C
// A -> C, B -> C (không còn vòng!)

// Cách chữa cháy: @Lazy
public Service(@Lazy Dependency dep) { }
// -> Spring inject một proxy, phụ thuộc thật ở lần gọi đầu tiên
```

### Khi nào Constructor Injection KHÔNG tối ưu

1. **Quá nhiều phụ thuộc** (10+) — dấu hiệu class làm quá nhiều việc (vi phạm SRP). Hãy tách thành các class nhỏ hơn.
2. **Circular dependency** — Spring không thể tạo bean. Dùng setter injection hoặc @Lazy.
3. **Kế thừa với phụ thuộc bắt buộc** — class con phải truyền phụ thuộc cho class cha qua `super()`.

## Senior Level

### Xung đột với CGLIB Proxy

```
Spring AOP tạo một proxy qua subclass:
  1. new Service(...) -> đối tượng thật
  2. CGLIB subclass -> proxy

-> Constructor chạy HAI LẦN!
-> Logic nặng trong constructor = vấn đề

Giải pháp:
  -> Constructor = chỉ gán field
  -> Khởi tạo -> đưa vào @PostConstruct
```

### Bên trong: Spring inject như thế nào

```
AutowiredAnnotationBeanPostProcessor:
  1. Tìm thấy constructor có @Autowired (hoặc constructor duy nhất)
  2. Phân giải các phụ thuộc qua BeanFactory
  3. Gọi constructor

-> Reflection -> overhead
-> Constructor Injection nhanh hơn một chút lúc khởi động (một constructor so với tất cả các field). Trên thực tế chênh lệch là tối thiểu, lý do chính là tính an toàn và khả năng test.
```

### Kinh nghiệm Production

**Tình huống thực tế: Field Injection che giấu 20 vòng phụ thuộc**
- Ứng dụng khởi động được nhưng crash ngẫu nhiên
- 4 giờ debug -> tìm ra các circular dependency
- Chuyển sang Constructor Injection -> lỗi lúc khởi động -> sửa trong 10 phút

### Best Practices

1. **Constructor** — luôn dùng làm mặc định
2. **@RequiredArgsConstructor** — Lombok cho tiện
3. **@Lazy** — không chỉ cho circular dependency. Cũng hữu ích để lazy loading các bean nặng (tiết kiệm bộ nhớ và thời gian khởi động).
4. **Field Injection** — không khuyến nghị cho code production. Chấp nhận được trong test (các class test thường không bị soi về DI pattern).
5. **> 5 tham số** -> vi phạm SRP
6. **Constructor** = chỉ gán field

### Tóm tắt cho Senior

- **Constructor** = tính bất biến, fail-fast, dễ test
- **Field** = nợ kỹ thuật (technical debt)
- **Vòng phụ thuộc** -> Constructor vỡ ngay lập tức (tốt!)
- **CGLIB** -> constructor bị gọi hai lần
- **@Lazy** -> proxy tạm, cái thật khi được gọi
- **SRP** -> > 5 phụ thuộc = tách class ra

## Interview Cheat Sheet

**Cần phải biết:**
- Kiểu được khuyến nghị là Constructor Injection: tính bất biến (`final`), fail-fast, test tiện lợi không cần Spring
- Constructor Injection làm cho các phụ thuộc trở nên tường minh — bạn thấy được class cần gì
- Nếu thiếu một phụ thuộc, ứng dụng crash lúc khởi động, không phải lúc runtime (NPE)
- Test không cần Spring: `new Service(mockRepo)` — nhanh và đơn giản
- Circular dependency qua constructor làm vỡ lúc khởi động — điều này là tốt, vấn đề lộ ra ngay
- Constructor chỉ nên chứa phần gán field, toàn bộ logic đưa vào `@PostConstruct`
- `@Lazy` giải quyết vòng phụ thuộc qua proxy tạm, nhưng đó là cách chữa cháy — refactoring vẫn tốt hơn
- > 5 tham số constructor -> vi phạm SRP, hãy tách class ra

**Các câu hỏi phụ thường gặp:**
- **Tại sao @Lazy là cách chữa cháy?** Nó che giấu circular dependency mà không loại bỏ vấn đề kiến trúc.
- **Tại sao constructor bị chạy hai lần với CGLIB?** Spring tạo đối tượng thật + một proxy subclass, cả hai đều gọi constructor.
- **Spring chọn constructor như thế nào?** Nếu có một constructor — tự động. Nếu nhiều — tìm `@Autowired`.
- **Khi nào Constructor Injection KHÔNG tối ưu?** Quá nhiều phụ thuộc (10+), vòng phụ thuộc, kế thừa với phụ thuộc bắt buộc.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Field Injection chấp nhận được trong code production" (không khuyến nghị, chỉ trong test)
- "@Lazy là giải pháp đúng cho vòng phụ thuộc" (chữa cháy, refactoring tốt hơn)
- "Càng nhiều phụ thuộc càng tốt — class càng mạnh" (vi phạm SRP, hãy tách thành các phần)
- "Constructor Injection chậm hơn vì Reflection" (chênh lệch chỉ tính bằng millisecond, điểm chính là tính an toàn)
