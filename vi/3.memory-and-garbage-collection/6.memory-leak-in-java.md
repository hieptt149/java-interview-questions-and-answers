# What is a memory leak in Java? (Memory leak trong Java là gì?)

## Junior Level

**Memory Leak (rò rỉ bộ nhớ)** — khi các đối tượng không còn cần thiết nữa vẫn nằm lại trong bộ nhớ và không được GC loại bỏ.

**Trong C/C++** một rò rỉ là khi bộ nhớ đã được giải phóng nhưng con trỏ vẫn còn (dangling pointer — con trỏ treo). **Trong Java** — ngược lại: một đối tượng lẽ ra có thể bị xóa, nhưng một tham chiếu vẫn giữ cho nó sống.

**Ví dụ minh họa đơn giản:** Bạn đã vứt rác đi nhưng quên đóng nắp thùng. Rác vẫn cứ chất đống lên mặc dù bạn đã "vứt nó đi".

**Trong Java, rò rỉ không phải là "mất" bộ nhớ, mà là **giữ lại (retain)** nó:**
- Đối tượng không còn cần thiết nữa → nhưng một tham chiếu đến nó vẫn còn
- GC không thể xóa → vẫn còn tham chiếu
- Bộ nhớ dần dần cạn kiệt → `OutOfMemoryError`

**Ví dụ:**
```java
// ❌ Rò rỉ: các đối tượng được thêm vào, không bao giờ bị loại bỏ
static List<String> history = new ArrayList<>();

public void add(String data) {
    history.add(data);  // Tăng vô hạn!
    // Dữ liệu cũ không còn cần nữa, nhưng vẫn nằm trong bộ nhớ
}
```

**Triệu chứng:**
- Có thể biểu hiện dưới dạng chậm đi (do GC thường xuyên), nhưng thường không có triệu chứng gì cho đến khi đột ngột OOM.
- GC chạy liên tục
- Cuối cùng: `OutOfMemoryError`

---

### Khi nào ThreadLocal an toàn

ThreadLocal an toàn nếu bạn chắc chắn gọi `.remove()` trong `finally`
và không truyền tham chiếu đối tượng ra bên ngoài luồng.

## Middle Level

### Cơ chế rò rỉ

```
Rò rỉ trong Java = giữ lại tham chiếu một cách ngoài ý muốn

Đối tượng còn sống chừng nào còn có đường đi từ GC Roots:
  GC Root → Static Field → Map → Đối tượng của bạn

Nếu bạn quên xóa khỏi Map → đối tượng sống mãi mãi!
```

### Các loại rò rỉ

**1. On-Heap Leaks (trong Heap):**
```java
// Các collection tĩnh (static)
static Map<String, Object> cache = new HashMap<>();
cache.put(key, value);  // Không bao giờ bị loại bỏ

// ThreadLocal
ThreadLocal<User> user = new ThreadLocal<>();
user.set(currentUser);
// Quên user.remove() → đối tượng sống chừng nào luồng còn sống

// Event Listeners
button.addActionListener(listener);
// Quên removeListener → listener sống mãi mãi
```

**2. Metaspace Leaks:**
```java
// ClassLoader leak
// Khi redeploy, ClassLoader cũ không được unload
→ Tất cả các class vẫn còn trong Metaspace
→ OutOfMemoryError: Metaspace
```

**3. Off-Heap Leaks (Native Memory):**
```java
// DirectByteBuffer — bộ nhớ nằm ngoài Heap
ByteBuffer buf = ByteBuffer.allocateDirect(100 * 1024 * 1024);
// 100 MB nằm ngoài -Xmx!
// Nếu không được dọn dẹp → OOM Killer giết tiến trình
```

### Chẩn đoán

**Triệu chứng:**
1. **Sawtooth Pattern (mẫu hình răng cưa)** — đồ thị bộ nhớ tăng lên sau mỗi lần thu gom
2. **GC Thrashing** — GC chạy liên tục, CPU 100%
3. **OutOfMemoryError** — kết quả cuối cùng

**Công cụ:**
```bash
# Chụp memory dump khi OOM
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/tmp/dump.hprof

# Phân tích qua Eclipse MAT
→ Dominator Tree → Path to GC Roots
→ Tìm xem ai đang giữ các đối tượng
```

### Các nguồn phổ biến

```java
// 1. Các collection tĩnh
static List<Data> allData = new ArrayList<>();

// 2. ThreadLocal không dọn dẹp
ThreadLocal<Connection> conn = new ThreadLocal<>();
// Trong thread pool, các luồng được tái sử dụng → dữ liệu tích lũy

// 3. Inner class (tham chiếu ngầm đến outer class)
class Outer {
    class Inner { }  // Giữ tham chiếu đến Outer.this
}

// 4. Tài nguyên không được đóng
InputStream is = new FileInputStream("file.txt");
// Quên is.close() → các buffer nằm trong bộ nhớ
```

## Senior Level

### Giải phẫu một rò rỉ: Shallow vs Retained Heap

```
Shallow Heap = kích thước của bản thân đối tượng
  Object Header (16) + các trường + padding

Retained Heap = tất cả những gì sẽ bị xóa cùng với đối tượng
  Đối tượng + tất cả các đối tượng CHỈ có thể tiếp cận thông qua nó

Ví dụ:
  Map node: 64 byte (Shallow)
  Nhưng giữ: 500 MB dữ liệu (Retained!)

→ Trong MAT, hãy nhìn vào Retained Heap, không phải Shallow!
```

### Đào sâu ClassLoader Leak

```
ClassLoader → đã nạp 1000 class
Mỗi class → InstanceKlass trong Metaspace
Mỗi class → các trường tĩnh → các đối tượng trong Heap

Nếu ClassLoader không bị GC:
  → 1000 class vẫn còn trong Metaspace
  → Tất cả các trường tĩnh vẫn còn trong Heap
  → Tất cả các đối tượng mà chúng tham chiếu → cũng vậy

Nguyên nhân:
  - ThreadLocal giữ đối tượng từ ClassLoader
  - Trường tĩnh trong class hệ thống tham chiếu đến ứng dụng
  - JDBC driver được đăng ký trong DriverManager
  - Các logger giữ tham chiếu đến các class của ứng dụng
```

### Native Memory Tracking (NMT)

```bash
# Bật NMT
-XX:NativeMemoryTracking=detail

# Phân tích
jcmd <pid> VM.native_memory summary

# Đầu ra:
Native Memory Tracking:
  Java Heap: 2 GB
  Class: 50 MB
  Thread: 100 MB
  Code: 80 MB
  GC: 200 MB
  Compiler: 30 MB
  Internal: 50 MB
  Symbol: 20 MB
  Native Memory Tracking: 10 MB
  Arena Chunk: 5 MB
  Unknown: 15 MB  ← Rò rỉ ở đây?
```

### Hệ thống phân tán và rò rỉ

```
Trong một cluster, một rò rỉ có thể bị che khuất:
  Node 1: bộ nhớ tăng → load balancer chuyển sang Node 2
  Node 2: bộ nhớ tăng → chuyển sang Node 3
  → Sụp đổ dây chuyền (avalanche) toàn bộ cluster!

Giải pháp:
  - Liveness/Readiness probe
  - Fail-fast khi OOME
  - Giám sát bộ nhớ trên mỗi node
```

### Kinh nghiệm Production

**Tình huống thực tế #1: ThreadLocal trong Tomcat**
- Web app: ThreadLocal cho UserContext
- Quên `remove()` trong `finally`
- Thread pool của Tomcat: các luồng được tái sử dụng
- Kết quả: UserContext của User A hiển thị với User B
- + Memory Leak: Context tích lũy 3 tháng → Metaspace OOM

Đây là HAI vấn đề: (1) memory leak — Context tích lũy và không bao giờ bị loại bỏ,
(2) lỗ hổng bảo mật — dữ liệu của người dùng này truy cập được bởi người dùng khác qua
ThreadLocal không được dọn dẹp.

**Tình huống thực tế #2: DirectByteBuffer**
- Netty server: `allocateDirect()` cho mỗi request
- GC không chạy (Heap gần như trống)
- Native Memory: 8 GB → OOM Killer giết tiến trình
- Giải pháp: `-XX:MaxDirectMemorySize=2g` + giám sát

### Best Practices

1. **Luôn đóng tài nguyên** (try-with-resources)
2. **ThreadLocal.remove()** trong `finally`
3. **Inner class → static** nếu không cần đến outer
4. **Cache có giới hạn (bounded)** (Caffeine, Guava)
5. **HeapDumpOnOutOfMemoryError** — bắt buộc trong production
6. **NMT** để giám sát Native Memory
7. **Delta Analysis** — so sánh các dump trước/sau khi tải
8. **Fail-fast** — thà chết còn hơn làm việc với trạng thái bị hỏng

### Tóm tắt cho Senior

- **Rò rỉ trong Java** = giữ lại tham chiếu ngoài ý muốn
- **Shallow vs Retained Heap** — hãy nhìn vào Retained!
- **ClassLoader Leaks** — nguy hiểm nhất (Metaspace)
- **Native Memory** — không nhìn thấy trong Heap Dump (cần NMT)
- **ThreadLocal** — nghi phạm số 1
- **Delta Analysis** — so sánh hai dump
- **Phân tán** — rò rỉ có thể giết cả cluster
- **Fail-fast** > trạng thái zombie

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Rò rỉ trong Java — không phải mất bộ nhớ, mà là giữ lại tham chiếu ngoài ý muốn (GC không thể xóa vì có đường đi từ GC Root)
- Shallow Heap = kích thước riêng của đối tượng; Retained Heap = tất cả những gì sẽ bị xóa cùng đối tượng — trong MAT hãy nhìn vào Retained!
- Top-3 nguồn rò rỉ: các collection tĩnh, ThreadLocal không có `.remove()`, tài nguyên không được đóng
- 3 loại rò rỉ: On-Heap (trong Heap), Metaspace (ClassLoader leak), Off-Heap (DirectByteBuffer)
- `HeapDumpOnOutOfMemoryError` — bắt buộc trong production
- Sawtooth Pattern: "sàn" của đồ thị bộ nhớ tăng lên sau mỗi lần GC — dấu hiệu của rò rỉ
- Trong các hệ thống phân tán, một rò rỉ trên một node có thể gây sụp đổ dây chuyền cả cluster

**Các câu hỏi phụ thường gặp:**
- **Rò rỉ trong Java khác rò rỉ trong C như thế nào?** — Trong C, bộ nhớ được giải phóng nhưng con trỏ vẫn còn (dangling pointer); trong Java — ngược lại: đối tượng lẽ ra có thể bị xóa, nhưng tham chiếu giữ lại nó
- **Tại sao ThreadLocal nguy hiểm trong thread pool?** — Các luồng được tái sử dụng; dữ liệu của request trước còn lại và hiển thị với request tiếp theo
- **Delta Analysis là gì?** — So sánh hai heap dump (trước/sau khi tải) để xác định các class đang tăng lên
- **Tại sao Inner Class có thể gây rò rỉ?** — Non-static inner class ngầm giữ một tham chiếu đến `Outer.this`

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Java không thể có memory leak, đã có GC" — rò rỉ xảy ra qua việc giữ lại tham chiếu
- "ThreadLocal an toàn vì luồng sẽ chết" — Trong thread pool, các luồng KHÔNG chết
- "Cứ tăng -Xmx là rò rỉ biến mất" — điều này che khuất vấn đề, OOM vẫn sẽ xảy ra
