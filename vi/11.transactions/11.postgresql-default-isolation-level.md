# What Is the Default Isolation Level in PostgreSQL (Isolation level mặc định trong PostgreSQL là gì)

## 🟢 Junior Level

Isolation level mặc định trong PostgreSQL là **Read Committed**.

**Điều này có nghĩa gì một cách đơn giản:** Mỗi lệnh `SELECT` trong một transaction chỉ thấy dữ liệu đã được lưu (commit) bởi các transaction khác. Quan trọng: mỗi SELECT thấy snapshot riêng của nó. Do đó, hai SELECT trong cùng một transaction có thể trả về dữ liệu khác nhau. Nhưng nếu bạn chạy `SELECT` hai lần trong một transaction, query thứ hai có thể thấy dữ liệu mới xuất hiện sau query đầu tiên.

**Ví dụ minh họa đơn giản:** Bạn đang đọc một news feed. Mỗi lần bạn refresh trang (`SELECT` mới), bạn thấy tin tức mới nhất. Nhưng bạn không thấy các bản nháp chưa được xuất bản (dữ liệu chưa commit).

**Ví dụ SQL:**

```sql
-- Trạng thái ban đầu: account.balance = 1000

-- Transaction 1
BEGIN;
SELECT balance FROM accounts WHERE id = 1;  -- thấy 1000
-- (chờ...)

-- Transaction 2 (chạy song song)
BEGIN;
UPDATE accounts SET balance = 1500 WHERE id = 1;
COMMIT;  -- dữ liệu đã lưu

-- Transaction 1 tiếp tục:
SELECT balance FROM accounts WHERE id = 1;  -- thấy 1500! (dữ liệu mới)
COMMIT;
```

**Điều gì được bảo vệ và điều gì không ở Read Committed:**

| Hiện tượng bất thường                     | Có thể xảy ra?  | Mô tả                                          |
| --------------------------- | ---------- | ---------------------------------------------------- |
| Dirty Read                  | **Không**     | Không thấy dữ liệu chưa commit                         |
| Non-repeatable Read         | **Có**    | SELECT lặp lại có thể trả về giá trị khác          |
| Phantom Read                | **Có**    | SELECT lặp lại có thể trả về các dòng khác            |

**Cách thay đổi isolation level:**

```sql
-- Cho session hiện tại
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;

-- Trong Spring
@Transactional(isolation = Isolation.REPEATABLE_READ)
```

## 🟡 Middle Level

### Cách Nó Hoạt Động Nội Bộ

PostgreSQL hiện thực Read Committed thông qua **MVCC (Multi-Version Concurrency Control)**:

> **Các thuật ngữ:**
> - **xmin/xmax** — các trường hệ thống trong mỗi dòng PG, lưu trữ transaction ID tạo ra nó.
> - **Dead tuple** — các phiên bản dòng cũ không còn cần thiết cho bất kỳ transaction đang hoạt động nào.
> - **TOAST** — cơ chế của PG để lưu trữ các giá trị lớn (TEXT, JSONB) riêng biệt với dòng chính.
> - **Autovacuum** — tiến trình nền của PG xóa các dead tuple.

```
Mỗi dòng trong PostgreSQL chứa hai trường hệ thống:
  - xmin: ID của transaction đã insert dòng này
  - xmax: ID của transaction đã xóa dòng này (0 = dòng còn sống)

Khi SELECT:
  1. PostgreSQL chụp snapshot hiện tại
  2. Kiểm tra: xmin < current_transaction_id và dòng "hiển thị"
  3. Mỗi lệnh SELECT nhận một snapshot MỚI
```

**Điểm then chốt:** Không giống một số DBMS khác, PostgreSQL ở level Read Committed tạo một snapshot mới **cho mỗi lệnh**, không phải cho toàn bộ transaction. Do đó, một SELECT lặp lại có thể thấy dữ liệu đã được commit bởi các transaction khác sau SELECT đầu tiên.

### Ứng Dụng Thực Tế

**Khi Read Committed Là Đủ:**

1. **Các ứng dụng CRUD** — hầu hết các ứng dụng web hoạt động đúng trên Read Committed
2. **Các báo cáo không yêu cầu tính nhất quán nghiêm ngặt** — sai số nhỏ có thể chấp nhận được
3. **Các hệ thống tải cao** — overhead tối thiểu, throughput tối đa

**Khi Read Committed KHÔNG Đủ:**

1. **Các tính toán tài chính** — cần dữ liệu nhất quán trong suốt toàn bộ transaction
2. **Migration dữ liệu** — cần một snapshot ổn định
3. **Các bất biến nghiệp vụ phức tạp** — các kiểm tra phụ thuộc vào nhiều bảng

### Các Kịch Bản Thực Tế

**Kịch bản 1: Vấn Đề Đọc Lặp Lại Ở Read Committed**
```java
@Transactional  // Read Committed theo mặc định
public void transfer(Long fromId, Long toId, BigDecimal amount) {
    // Snapshot 1
    Account from = accountRepo.findById(fromId);
    Account to = accountRepo.findById(toId);

    // Ở đây một transaction khác có thể thay đổi số dư của 'from'

    // Snapshot 2 — có thể thấy dữ liệu khác!
    BigDecimal fromBalance = from.getBalance();
    BigDecimal toBalance = to.getBalance();

    // Nếu dữ liệu thay đổi, việc chuyển tiền có thể không chính xác
    from.setBalance(fromBalance.subtract(amount));
    to.setBalance(toBalance.add(amount));
}
```

**Kịch bản 2: Báo Cáo Nhất Quán Ở Repeatable Read**
```java
@Transactional(isolation = Isolation.REPEATABLE_READ)
public Report generateReport(LocalDate date) {
    // Tất cả các SELECT thấy cùng snapshot
    int count = txRepo.countByDate(date);
    BigDecimal sum = txRepo.sumByDate(date);
    // count và sum được đảm bảo nhất quán
    return new Report(count, sum);
}
```

### Các Lỗi Thường Gặp

| Lỗi                                                         | Hậu quả                               | Giải pháp                                                                |
| --------------------------------------------------------------- | ----------------------------------------- | ----------------------------------------------------------------------- |
| Giả định `@Transactional` cho một snapshot nhất quán           | SELECT lặp lại thấy dữ liệu khác       | Dùng Repeatable Read cho các báo cáo nhất quán                              |
| Transaction dài trên Read Committed                              | Cửa sổ xung đột lớn hơn               | Rút ngắn transaction                                                 |
| Read Committed cho các thao tác tài chính                         | Lost Update, tính toán sai       | SQL nguyên tử (`SET balance = balance - ?`) hoặc Repeatable Read + FOR UPDATE |
| Bỏ qua `default_transaction_isolation`                        | Các session khác nhau có thể có level khác nhau | Đặt level tường minh trong code hoặc cấu hình                     |

### So Sánh Các Isolation Level Trong PostgreSQL

| Level                        | Dirty Read  | Non-repeatable Read | Phantom Read    | Throughput (tương đối) |
| ---------------------------- | ----------- | ------------------- | --------------- | --------------------- |
| Read Uncommitted             | Có thể xảy ra    | Có thể xảy ra            | Có thể xảy ra        | 1.0x                  |
| **Read Committed (mặc định)** | **Không**      | **Có**             | **Có**         | **1.0x**              |
| Repeatable Read              | Không          | Không                   | Không (trong PG)      | 0.95x                 |
| Serializable                 | Không          | Không                   | Không              | 0.3-0.5x              |

> Các con số là tương đối cho workload đọc nặng (80% SELECT). Với workload ghi nặng (80% UPDATE), sự khác biệt sẽ lớn hơn: RC=1.0x, RR=0.8x, Serializable=0.2x.

**Quan trọng:** Trong PostgreSQL, Repeatable Read cũng bảo vệ chống lại phantom read (nhờ MVCC), điều này vượt ra ngoài chuẩn ANSI SQL.

### Khi Nào KHÔNG Nên Thay Đổi Mặc Định

- **Các thao tác CRUD tiêu chuẩn** — Read Committed là một lựa chọn mặc định tốt cho các thao tác CRUD tiêu chuẩn.
- **Microservice với eventual consistency** — isolation nghiêm ngặt là dư thừa
- **Các hệ thống đọc nặng tải cao** — overhead của Serializability không đáng để đánh đổi

## 🔴 Senior Level

### Hiện Thực Nội Bộ: MVCC Và Quản Lý Snapshot

#### Transaction ID Và Các Quy Tắc Visibility

```c
// Logic visibility đơn giản hóa trong PostgreSQL (src/backend/access/common/heaptuple.c)

bool HeapTupleSatisfiesVisibility(HeapTuple htup, Snapshot snapshot) {
    TransactionId xmin = htup->t_data->t_xmin;  // transaction insert
    TransactionId xmax = htup->t_data->t_xmax;  // transaction delete

    // Quy tắc Read Committed:
    // 1. Nếu xmin chưa commit → dòng không hiển thị
    // 2. Nếu xmax đã commit → dòng không hiển thị (đã xóa)
    // 3. snapshot được tạo mới cho MỖI query

    // Quy tắc Repeatable Read:
    // snapshot được tạo MỘT LẦN tại query đầu tiên trong transaction
    // và được tái sử dụng cho tất cả các query tiếp theo
}
```

**Transaction ID wraparound:**
- PostgreSQL dùng transaction ID 32-bit (~4 tỷ)
- Sau khi tràn, xảy ra wraparound
- Autovacuum phải "đóng băng" (freeze) các dòng cũ (`xmax = FrozenTransactionId`)
- Nếu autovacuum không theo kịp → cơ sở dữ liệu ngừng hoạt động (transaction ID wraparound failure)

#### Overhead Của Việc Tạo Snapshot

```
Read Committed:
  - Snapshot mới cho mỗi query
  - Snapshot = mảng các transaction ID đang chạy
  - Kích thước: O(active_transactions)
  - Cấp phát: ~100-500 byte mỗi snapshot

Repeatable Read / Serializable:
  - Snapshot được tạo một lần tại query đầu tiên
  - Được giữ nguyên cho đến khi kết thúc transaction
  - Bổ sung: theo dõi SSI serializable transaction (~1KB overhead)
```

#### MVCC Và Dead Tuple

Mỗi `UPDATE` hoặc `DELETE` không xóa vật lý dòng, mà đánh dấu nó là dead:

```
UPDATE accounts SET balance = 1500 WHERE id = 1;

Phiên bản dòng cũ:
  xmin = 100, xmax = 200 (transaction mới), balance = 1000  → DEAD TUPLE

Phiên bản dòng mới:
  xmin = 200, xmax = 0, balance = 1500  → LIVE TUPLE
```

**Overhead:**
- Dead tuple chiếm dung lượng đĩa (table bloat: tăng 2-10 lần)
- Các index cũng tích lũy các mục dead
- AutoVacuum phải định kỳ dọn dẹp (overhead I/O: 10-30% throughput đĩa)

### Đánh Đổi Về Kiến Trúc (Trade-off)

**Cách A: Read Committed (mặc định)**
- ✅ Ưu điểm: Overhead tối thiểu, semantics đơn giản, không có serialization failure, throughput tối đa
- ❌ Nhược điểm: Non-repeatable read, phantom read, không thể tin cậy tính nhất quán trong các transaction dài
- Phù hợp cho: 90% các ứng dụng web, microservice, CRUD

**Cách B: Repeatable Read**
- ✅ Ưu điểm: Snapshot nhất quán, bảo vệ khỏi phantom (trong PG), hành vi có thể dự đoán
- ❌ Nhược điểm: Lỗi snapshot-too-old với các transaction chạy dài, nhiều dead tuple hơn
- Phù hợp cho: báo cáo, migration, xử lý batch

**Cách C: Serializable (SSI)**
- ✅ Ưu điểm: ACID đầy đủ, đảm bảo tính đúng đắn cho mọi transaction đồng thời
- ❌ Nhược điểm: Serialization failure (tỷ lệ abort 10-30%), overhead predicate lock (5-20MB shared memory), throughput thấp hơn 2-10 lần
- Phù hợp cho: các hệ thống tài chính nơi tính đúng đắn quan trọng hơn hiệu năng

### Các Trường Hợp Biên Và Đặc Biệt

**1. Snapshot Too Old (Repeatable Read / Serializable):**
```
T1: BEGIN ISOLATION LEVEL REPEATABLE READ;
T1: SELECT * FROM accounts;  -- tạo snapshot

// ... 10 phút trôi qua ...
// AutoVacuum xóa các dead tuple, bao gồm cả các phiên bản chỉ hiển thị với snapshot của T1

T1: SELECT * FROM accounts;
-- ERROR: could not serialize access due to concurrent update
-- hoặc: ERROR: snapshot too old
```

**Giải pháp:** Tăng `vacuum_freeze_min_age` hoặc rút ngắn transaction.

**2. Read Committed Và Contention UPDATE:**
```sql
-- T1 và T2 đồng thời:
T1: UPDATE accounts SET balance = balance - 100 WHERE id = 1;
T2: UPDATE accounts SET balance = balance - 100 WHERE id = 1;

-- PostgreSQL: T2 chờ T1, sau đó T2 khởi động lại UPDATE với snapshot mới
-- T2 thấy kết quả của T1 và trừ thêm 100
-- Kết quả: balance -= 200 (chính xác!)

-- NHƯNG nếu logic ở cấp độ application (read-modify-write):
-- T1: SELECT balance → 1000
-- T2: SELECT balance → 1000
-- T1: UPDATE balance = 900
-- T2: UPDATE balance = 900  ← Lost Update!
```

**3. DDL Bên Trong Transaction Ở Read Committed:**
```sql
BEGIN;
ALTER TABLE accounts ADD COLUMN new_col TEXT;  -- DDL
SELECT * FROM accounts;  -- snapshot mới thấy cột mới
-- Các session khác chưa thấy new_col cho đến khi COMMIT
-- Nhưng có thể xảy ra blocking!
```

**4. Read Committed Và Foreign Key:**
```sql
-- T1: INSERT INTO orders (user_id) VALUES (999);
-- T2: DELETE FROM users WHERE id = 999;

-- FK check trong T1 xác minh sự tồn tại của user_id = 999
-- Ở Read Committed, FK check tạo một snapshot riêng
-- Nếu T2 đã commit DELETE → vi phạm FK!
```

**5. Read Committed Và Cursor:**
```sql
BEGIN;
DECLARE cur CURSOR FOR SELECT * FROM accounts;
FETCH 10 FROM cur;  -- snapshot 1

-- Một transaction khác sửa đổi dữ liệu

FETCH 10 FROM cur;  -- snapshot 2, có thể thấy dữ liệu khác!
-- Cursor KHÔNG đảm bảo tính nhất quán ở Read Committed
```

### Tác Động Đến Hiệu Năng

| Level           | Latency (p50) | Latency (p99) | Throughput       | Overhead Bộ nhớ                            |
| --------------- | ------------- | ------------- | ---------------- | ------------------------------------------ |
| Read Committed  | 1-3ms         | 5-15ms        | 50,000+ TPS      | Snapshot: ~200 byte/query                 |
| Repeatable Read | 1-3ms         | 5-20ms        | 48,000 TPS       | Snapshot: ~200 byte/tx + giữ dead tuple |
| Serializable    | 5-20ms        | 50-200ms      | 8,000-15,000 TPS | Predicate lock: 5-20MB shared memory      |

**Các con số cụ thể (PostgreSQL 15, 8 core, NVMe, pgbench):**
> Các con số dành cho một cấu hình cụ thể. Trên phần cứng/phiên bản của bạn, chúng có thể khác một bậc độ lớn.
- Read Committed: ~55,000 TPS chỉ SELECT
- Repeatable Read: ~52,000 TPS chỉ SELECT (overhead 5% từ việc giữ snapshot)
- Serializable: ~12,000 TPS với contention trung bình (giảm 78%)

**Workload ghi (50% đọc, 50% ghi):**
- Read Committed: ~25,000 TPS
- Repeatable Read: ~24,000 TPS
- Serializable: ~6,000 TPS (serialization failure + retry)

### Tác Động Đến Bộ Nhớ

- **Mảng snapshot:** ~200 byte mỗi snapshot. Ở 1000 query/giây = tỷ lệ cấp phát 200KB/giây.
- **Giữ dead tuple (RR/SRL):** Với các transaction chạy dài, các dead tuple không được vacuum. Một bảng 1GB có thể phình lên 5-10GB.
- **Predicate lock (Serializable):** Pool shared memory (~64MB mặc định). Khi tràn → coarsening lock → nhiều serialization failure hơn.
- **TOAST bloat:** Các trường lớn (TEXT, JSONB) được lưu trong bảng TOAST. Các dead TOAST tuple cũng tích lũy.

### Các Khía Cạnh Concurrency

**Các pattern serialization failure (SSI):**
```
T1: đọc khoảng A (predicate lock trên A)
T2: ghi vào khoảng A
T1: ghi vào khoảng B
T2: đọc khoảng B (predicate lock trên B)

Đồ thị phụ thuộc:
  T1 → (đọc A) → T2 → (ghi A) = RW-dependency
  T2 → (đọc B) → T1 → (ghi B) = RW-dependency

Chu trình: T1 → T2 → T1 → serialization failure
```

**Tỷ lệ abort dưới contention:**
- 10 writer đồng thời: ~5% serialization failure
- 50 writer đồng thời: ~15-25% serialization failure
- 100+ writer đồng thời: ~30-50% (không phù hợp cho production)

### Tình Huống Thực Tế Trong Production

**Tình huống:** Hệ thống thanh toán (2024), PostgreSQL 14, xử lý 5000 transaction/giây.

**Vấn đề:** Đối soát số dư hàng ngày cho thấy sai lệch 0.01-0.05%. Với doanh thu hàng ngày $10M, điều này có nghĩa là $1,000-5,000 bị "mất".

**Nguyên nhân gốc rễ:** Batch job trên Read Committed:
```java
@Transactional  // Read Committed
public BigDecimal calculateDailyTotal(LocalDate date) {
    // Snapshot 1: 10,000 giao dịch
    List<Transaction> txs = txRepo.findByDate(date);

    // Trong lúc tính toán, payment gateway xác nhận các giao dịch mới
    // Snapshot 2: các dòng mới đã commit

    BigDecimal total = txs.stream()
        .map(Transaction::getAmount)
        .reduce(BigDecimal.ZERO, BigDecimal::add);

    // Một query khác trong cùng transaction:
    int count = txRepo.countByDate(date);  // Snapshot 3 — thấy nhiều dòng hơn!

    // total được tính từ 10,000, count = 10,050
    // Sai lệch trong báo cáo
}
```

**Giải pháp:** Chuyển sang Repeatable Read:
```java
@Transactional(isolation = Isolation.REPEATABLE_READ)
public BigDecimal calculateDailyTotal(LocalDate date) {
    // Tất cả các SELECT thấy cùng snapshot
    List<Transaction> txs = txRepo.findByDate(date);
    int count = txRepo.countByDate(date);  // cùng snapshot, count nhất quán
    // ...
}
```

**Kết quả:**
- Sai lệch: từ 0.05% xuống 0%
- Throughput: không thay đổi (workload chỉ đọc)
- Latency: +0.1ms (không đáng kể)

### Giám Sát Và Chẩn Đoán

**Thống kê nội bộ PostgreSQL:**
```sql
-- Kiểm tra isolation level của các transaction đang hoạt động
SELECT pid, datname, backend_xid, state,
       wait_event_type, query
FROM pg_stat_activity
WHERE state = 'active';

-- Serialization failure (PostgreSQL 14+)
SELECT datname, conflicts, deadlocks
FROM pg_stat_database
WHERE datname = 'your_db';

-- Thống kê MVCC: dead tuple
SELECT
    schemaname, relname,
    n_dead_tup, n_live_tup,
    ROUND(100.0 * n_dead_tup / NULLIF(n_dead_tup + n_live_tup, 0), 2) AS dead_pct
FROM pg_stat_user_tables
ORDER BY dead_pct DESC;

-- Các transaction chạy dài (nguy cơ giữ snapshot)
SELECT pid, now() - xact_start AS duration, query
FROM pg_stat_activity
WHERE state = 'active' AND xact_start < now() - interval '5 minutes'
ORDER BY xact_start;
```

**Giám sát ở cấp độ application:**
```java
// Micrometer: theo dõi việc sử dụng isolation level
Counter.builder("db.transaction.isolation")
    .tag("level", "read_committed")
    .tag("operation", "daily_report")
    .register(meterRegistry);

// Theo dõi serialization failure
Counter.builder("db.transaction.serialization_failure")
    .tag("isolation", "serializable")
    .register(meterRegistry);
```

### Best Practices Cho Highload

1. **Giữ Read Committed làm mặc định** — đây là lựa chọn tối ưu cho 90% workload.
2. **Dùng Repeatable Read có chọn lọc** — chỉ cho các báo cáo và batch job cần một snapshot nhất quán.
3. **Tránh Serializable cho các workload ghi nặng** — tỷ lệ abort khiến nó không phù hợp với >50 writer đồng thời.
4. **SQL nguyên tử thay vì read-modify-write** — `UPDATE SET balance = balance - ?` loại bỏ lost update mà không cần nâng isolation level.
5. **Rút ngắn transaction** — transaction càng ngắn, việc giữ dead tuple và overhead snapshot càng ít.
6. **Cấu hình autovacuum tích cực** cho các bảng update nhiều:
   ```sql
   ALTER TABLE accounts SET (
     autovacuum_vacuum_threshold = 50,
     autovacuum_vacuum_scale_factor = 0.05
   );
   ```
7. **Giám sát tuổi snapshot** — cảnh báo với các transaction hơn 5 phút.
8. **Connection pooling với prepared statement** — giảm overhead tạo snapshot cho mỗi query.

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Mặc định PostgreSQL: Read Committed — mỗi SELECT thấy snapshot riêng của dữ liệu đã commit
- Read Committed cấm dirty read nhưng cho phép non-repeatable và phantom read
- PostgreSQL MVCC: xmin/xmax trên mỗi dòng, dead tuple → dọn dẹp bằng VACUUM
- Ở RC, hai SELECT trong một transaction có thể trả về dữ liệu khác nhau (snapshot theo statement)
- Cho các báo cáo nhất quán: Repeatable Read (một snapshot cho mỗi transaction)
- Serializable trong PG qua SSI — throughput thấp hơn 2-10 lần, cần logic retry

**Các câu hỏi phụ thường gặp:**
- Read Committed trong PG khác gì với RC trong các DBMS khác? — Luôn dùng MVCC, không có RC dựa trên locking
- Khi nào nên thay đổi mặc định? — Tính toán tài chính (RR), migration dữ liệu (RR), hệ thống tài chính (Serializable)
- Snapshot too old là gì? — Với các transaction RR dài, AutoVacuum xóa các phiên bản cũ → lỗi
- Làm sao giám sát MVCC trong PG? — `pg_stat_user_tables.n_dead_tup`, các transaction chạy dài qua `pg_stat_activity`

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "PostgreSQL có Read Uncommitted" — tự động nâng lên Read Committed
- "Ở RC, tất cả SELECT trong một transaction trả về cùng kết quả" — snapshot theo statement
- "Serializable = chỉ cần thêm annotation" — cần logic retry và giám sát tỷ lệ abort
