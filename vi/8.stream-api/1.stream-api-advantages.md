# What advantages does Stream API provide? (Stream API mang lại những ưu điểm gì?)

## Junior Level

**Stream API** là một cách để mô tả một chuỗi các phép tính trên dữ liệu mà không thực sự lưu trữ dữ liệu đó.

**Không giống một collection** (thứ lưu các phần tử trong bộ nhớ), một stream là một pipeline các thao tác được tính toán một cách lười (lazily). Bạn mô tả CÁI GÌ cần làm (filter, map, collect), và Stream quyết định LÀM THẾ NÀO để thực thi nó.

**Các ưu điểm chính:**
- **Dễ đọc:** Code trở nên khai báo (declarative) — bạn mô tả "cái gì" cần làm, không phải "làm thế nào"
- **Ít bug hơn:** Giảm khả năng gặp lỗi vòng lặp (off-by-one, sai chỉ số)
- **Chuỗi thao tác:** Các phép biến đổi phức tạp có thể được diễn đạt trong một chuỗi duy nhất

```java
// Cách cũ
List<String> result = new ArrayList<>();
for (String s : list) {
    if (s.startsWith("A")) {
        result.add(s.toUpperCase());
    }
}

// Stream API
List<String> result = list.stream()
    .filter(s -> s.startsWith("A"))
    .map(String::toUpperCase)
    .collect(Collectors.toList());
```

### Khi nào KHÔNG nên dùng Stream API

1. **Các thao tác đơn giản trên các collection nhỏ** (< 100 phần tử) — for/for-each thông thường đơn giản hơn và nhanh hơn
2. **Code nhạy về độ trễ (latency)** — overhead của pipeline là ~micro giây, nhưng đáng kể trong các hot path
3. **Làm việc với các primitive mà không boxing** — hãy dùng IntStream/LongStream, không phải Stream<Integer>

## Middle Level

### Stream API hoạt động bên trong như thế nào

Stream không lưu dữ liệu — nó mô tả các **phép tính** trên dữ liệu. Thành phần then chốt là **Spliterator** (Splitable Iterator):
- Có thể chia dữ liệu thành các phần để xử lý song song
- Báo cáo các đặc điểm của nguồn: `ORDERED`, `DISTINCT`, `SORTED`, `SIZED`

Các đặc điểm (characteristics) của Spliterator:
- **ORDERED** — các phần tử có một thứ tự xác định
- **DISTINCT** — tất cả các phần tử là duy nhất
- **SORTED** — các phần tử đã được sắp xếp
- **SIZED** — biết chính xác kích thước (ArrayList, mảng). Then chốt cho tính song song!

### Các loại thao tác

**Intermediate — lazy:**
- `filter`, `map`, `flatMap`, `peek` — stateless
- `sorted`, `distinct`, `limit`, `skip` — stateful (cần buffer)

**Terminal — kích hoạt việc thực thi:**
- `collect`, `reduce`, `forEach`, `count`, `findFirst`, `anyMatch`

### Lazy Evaluation
Các thao tác intermediate không được thực thi cho tới khi một thao tác terminal được gọi. Điều này cho phép tối ưu hóa và làm việc với các stream vô hạn.

## Senior Level

### Internal Iteration vs External Iteration

**External Iteration** (for-each, Iterator):
- Bạn kiểm soát "làm thế nào" để lặp
- Trình biên dịch JIT bị hạn chế trong việc tối ưu hóa

**Internal Iteration** (Stream API):
- JIT có thể áp dụng Loop Unrolling và Vectorization (SIMD)
- Bản thân Stream API quyết định thứ tự thực thi tối ưu

### Hiệu suất và Highload

**Primitive Stream:**
```java
// XẤU — tạo hàng triệu object Integer
list.stream().map(String::length).reduce(0, Integer::sum)

// TỐT — làm việc với các primitive
list.stream().mapToInt(String::length).sum()
```

**Fusion:** Các hiện thực hiện đại kết hợp nhiều thao tác intermediate thành một lượt duyệt duy nhất.

**Khi nào KHÔNG nên dùng:**
- Các vòng lặp đơn giản trên các collection nhỏ (tới ~1000 phần tử) — for-i nhanh hơn vì không có overhead của việc tạo pipeline và Spliterator. Trên các tập dữ liệu lớn khác biệt sẽ san phẳng.
- Các side effect phức tạp (code trở nên khó đọc)
- Các thao tác I/O (chặn ForkJoinPool)

### Tính song song — các cạm bẫy

`.parallel()` dùng `ForkJoinPool.commonPool()` dùng chung — sử dụng không kiểm soát có thể làm chậm toàn bộ ứng dụng. Quy tắc thực nghiệm: tính song song đáng dùng khi `N * Q > 10.000`.

### Chẩn đoán
- Chỉ dùng `peek()` để debug
- IntelliJ Stream Debugger trực quan hóa luồng dữ liệu
- JMH cho các benchmark parallel stream

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Stream API — một cách khai báo để mô tả các phép tính trên dữ liệu, không lưu dữ liệu trong bộ nhớ
- Các ưu điểm chính: dễ đọc, ít lỗi vòng lặp, chuỗi thao tác tiện lợi
- Các thao tác intermediate là lazy, terminal — kích hoạt việc thực thi
- Spliterator — thành phần then chốt để chia dữ liệu và tính song song
- Primitive Stream (IntStream, LongStream) hiệu quả hơn các phiên bản boxed
- `.parallel()` dùng ForkJoinPool.commonPool() dùng chung
- Đừng dùng trên các collection nhỏ và trong các thao tác I/O

**Các câu hỏi phụ thường gặp:**
- Khi nào Stream API tệ hơn for-each? — Trên các collection < 100 phần tử, trong các hot path có độ trễ then chốt, cho các thao tác đơn giản
- Fusion là gì? — JVM kết hợp nhiều thao tác intermediate thành một lượt duyệt duy nhất
- Tại sao parallelStream nguy hiểm? — ForkJoinPool dùng chung, các thread bị chặn giết chết hiệu suất của toàn bộ ứng dụng
- Cách chẩn đoán các vấn đề? — JMH cho benchmark, IntelliJ Stream Debugger, peek() để debug

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Stream API luôn nhanh hơn for-each" — không, overhead của pipeline đáng kể trên dữ liệu nhỏ
- "ParallelStream sẽ tăng tốc mọi tác vụ" — chỉ CPU-bound với N*Q > 10.000
- "Stream lưu dữ liệu" — không, nó là một pipeline các phép tính, dữ liệu nằm ở nguồn
- "Stream có thể tái sử dụng" — không, IllegalStateException khi tái sử dụng
