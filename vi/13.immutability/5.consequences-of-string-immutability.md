# What are the consequences of String immutability? (Hậu quả của tính bất biến của String là gì?)

---

## Basic Level

### Hậu Quả Tích Cực

1. **Các chuỗi thread-safe** — có thể được truyền giữa các thread mà không gặp vấn đề
2. **Tiết kiệm bộ nhớ** — các chuỗi giống hệt nhau được lưu một lần (String Pool)
3. **Có thể dùng làm key HashMap** — hashCode không thay đổi

### Hậu Quả Tiêu Cực

1. **Mỗi thao tác tạo một object mới** — điều này tiêu tốn bộ nhớ
2. **Nối chuỗi trong vòng lặp là một ý tưởng tồi**:
```java
String s = "";
for (int i = 0; i < 1000; i++) {
    s += i; // 1000 object được tạo!
}
```

### Giải Pháp — StringBuilder
```java
StringBuilder sb = new StringBuilder();
for (int i = 0; i < 1000; i++) {
    sb.append(i); // Một object, sửa đổi tại chỗ
}
String s = sb.toString();
```

## Intermediate Level

### Tác Động Đến Hiệu Năng

Vấn đề cấp phát quá mức trong vòng lặp dẫn đến:
1. Lấp đầy **Young Generation** (Eden space)
2. Tăng tần suất các **chu kỳ GC**
3. Phân mảnh bộ nhớ

**Quy tắc**: cho các sửa đổi hàng loạt, luôn dùng:
- **StringBuilder** — đơn luồng, nhanh
- **StringBuffer** — đa luồng, chậm hơn

### Hậu Quả Bảo Mật: Làm Việc Với Mật Khẩu

Một object `String` với mật khẩu sẽ vẫn ở trong bộ nhớ cho đến khi GC quyết định thu gom nó. Bạn không thể lập trình để "xóa sạch" nội dung của nó.

**Khuyến nghị**: cho dữ liệu nhạy cảm, dùng `char[]`:
```java
char[] password = console.readPassword();
// Pattern cho các ứng dụng console (System.console().readPassword()).
// Cho ứng dụng web — các cách tiếp cận khác (HTTPS, secure cookie, đừng lưu mật khẩu).
// ... dùng nó
Arrays.fill(password, (char) 0); // đặt về 0
```

### Thiết Kế Code

Tính bất biến của String khuyến khích một **phong cách hàm (functional style)** — các method không sửa đổi tham số mà trả về kết quả. Điều này làm code dễ dự đoán và dễ kiểm thử (Pure Function).

## Advanced Level

### Áp Lực GC Và Các Tối Ưu Hóa

Tính bất biến của String tạo ra tải GC, nhưng:
- Các chuỗi tồn tại ngắn được dọn dẹp hiệu quả trong Minor GC
- **String Deduplication** chỉ có sẵn với G1 GC (cờ `-XX:+UseStringDeduplication`). Không được hỗ trợ với ZGC/Shenandoah.
- **Compact String** (Java 9+) giảm 50% mức tiêu thụ bộ nhớ cho các ký tự Latin

### Các Điểm Tinh Vi Về Bảo Mật

**Tấn công TOCTOU (Time-of-Check to Time-of-Use)**: không thể xảy ra với các chuỗi bất biến, vì một chuỗi không thể thay đổi giữa lúc kiểm tra và lúc sử dụng.

Nhưng có mặt trái:
- Các chuỗi chứa mật khẩu/token **vẫn còn trong heap dump** ở dạng văn bản thuần
- Các chuỗi có thể bị **swap ra đĩa** bởi OS
- Việc intern chuỗi làm cho các chuỗi tồn tại lâu (Old Gen)

### Tác Động Đến Các Tối Ưu Hóa JIT

JIT compiler có thể tối ưu hóa mạnh mẽ code liên quan đến chuỗi:
- **Constant folding** — tính toán các biểu thức hằng số tại thời điểm biên dịch
- **String intrinsics** — các method native cho `equals()`, `hashCode()`, `indexOf()`
- **Escape analysis** — loại bỏ các cấp phát không cần thiết trong lúc nối chuỗi

### Tóm Tắt Cho Advanced
- Tính bất biến "đắt nhưng đáng tin cậy": 1000 lần nối = 1000 object trên heap; StringBuilder = 1 object.
- Chi phí chính — tải GC từ việc dùng vòng lặp bất cẩn
- Với các bí mật, dùng `char[]`/`byte[]` có thể được đặt về 0
- Với các hệ thống tải cao, quan trọng cần hiểu sự khác biệt giữa `String` và `StringBuilder`
- Khi làm việc với các bí mật, hãy nhớ sự hiện diện "còn sót lại" của các chuỗi trong heap

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Tích cực: thread-safety, String Pool, key HashMap ổn định
- Tiêu cực: mỗi thay đổi = object mới, nối chuỗi trong vòng lặp tạo N object
- StringBuilder — giải pháp cho các sửa đổi hàng loạt (đơn luồng, nhanh)
- Mật khẩu trong String — thực hành xấu: không thể đặt về 0, vẫn còn trong heap dump
- Cho các bí mật dùng `char[]` + `Arrays.fill(password, (char) 0)`
- String Deduplication — chỉ G1 GC (`-XX:+UseStringDeduplication`), không ZGC/Shenandoah
- Các tối ưu hóa JIT: constant folding, string intrinsics, escape analysis

**Các câu hỏi phụ thường gặp:**
- *Tại sao nối chuỗi trong vòng lặp lại xấu?* — 1000 lần lặp = 1000 object trên heap → áp lực GC
- *Tại sao không thể lưu mật khẩu trong String?* — Không thể lập trình để xóa sạch, vẫn còn trong bộ nhớ cho đến khi GC
- *Tấn công TOCTOU là gì?* — Time-of-Check to Time-of-Use: chuỗi thay đổi giữa lúc kiểm tra và lúc sử dụng; không thể xảy ra với String bất biến
- *Khi nào nên dùng StringBuilder vs String?* — StringBuilder cho vòng lặp và sửa đổi hàng loạt, String cho lưu trữ và truyền tải

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "String += trong vòng lặp thì ổn thôi" — với 1000 lần lặp đó là 1000 object
- "Mật khẩu có thể lưu trong String" — chúng không thể được xóa an toàn khỏi bộ nhớ
- "char[] luôn an toàn hơn String" — `char[]` cũng có thể ở trong heap dump; nhưng nó có thể được đặt về 0
- "String Deduplication hoạt động ở mọi nơi" — chỉ G1 GC với cờ đó
