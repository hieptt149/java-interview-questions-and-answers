# Are there disadvantages to immutable objects? (Có nhược điểm nào với các immutable object không?)

---

## Basic Level

Có, tính bất biến có những mặt trái.

### Nhược Điểm

1. **Tiêu tốn bộ nhớ** — mỗi lần sửa đổi tạo ra một object mới
2. **Chậm hơn với các cập nhật thường xuyên** — dữ liệu cần được sao chép
3. **Nhiều code hơn** — cần viết constructor, `equals`, `hashCode`, `toString`

### Ví Dụ Về Vấn Đề
```java
String s = "";
for (int i = 0; i < 10000; i++) {
    s += i; // 10000 object được tạo ra!
}
```

### Giải Pháp
Dùng `StringBuilder` cho các sửa đổi thường xuyên và các object bất biến để lưu trữ.

---

## Intermediate Level

### 1. Hiệu Năng Với Các Cập Nhật Thường Xuyên

Với các kịch bản sửa đổi mỗi giây một trường trong một object lớn:
- Cấp phát liên tục các object mới → tải lên **Young Gen**
- GC không phải lúc nào cũng có thể che giấu các khoảng dừng (GC Jitter)
- **Ví dụ**: game logic (tọa độ của 1000 đơn vị)

### 2. Tiêu Tốn Bộ Nhớ

Việc lưu trữ nhiều phiên bản trung gian của các object tồn tại lâu (ví dụ: trong một cache) làm phình to **Old Generation**. Không có structural sharing, mức tiêu thụ RAM tăng tuyến tính.

### 3. Boilerplate Trước Khi Có Java Records

Trước khi có Record, việc tạo một immutable class đòi hỏi:
- Nhiều trường `final`
- Constructor dài dòng
- `equals`, `hashCode`, `toString` thủ công
- Pattern **Builder** để tạo tiện lợi

### 4. Vấn Đề Tính Bất Biến Sâu

Đảm bảo tính bất biến 100% cho một đồ thị object phức tạp là khó. Một defensive copy bị quên có thể phá hủy sự an toàn của toàn bộ class.

### 5. Giới Hạn Kế Thừa

Các immutable class phải là `final` — điều này làm cho các pattern kế thừa cổ điển trở nên bất khả thi.

### Cách Giảm Nhẹ Các Nhược Điểm

1. **StringBuilder** cho việc nối chuỗi trong vòng lặp
2. **Pattern Builder** để tạo các object phức tạp
3. **Record** (Java 16+) để có boilerplate tối thiểu

## Advanced Level

### Tương Tác Với Các Framework

**Hibernate/JPA** — yêu cầu một constructor không tham số và setter để proxy và lazy loading. Các entity thực sự bất biến với Hibernate là một nhiệm vụ không tầm thường:
- Dùng annotation `@Immutable`
- Hoặc làm việc thông qua DTO

**Jackson** — yêu cầu `@JsonCreator`, `@JsonProperty` để deserialize thành các object/record bất biến.

### Đánh Đổi (Trade-offs)

| Kịch bản                | Immutability                    | Mutability          |
| ------------------------ | -------------------------------- | -------------------- |
| Cập nhật tần suất cao     | Kém (áp lực GC)                  | Tốt                  |
| Đọc đa luồng             | Xuất sắc (lock-free)              | Kém (tranh chấp)      |
| Tích hợp framework        | Khó khăn                         | Đơn giản             |
| Ngăn ngừa bug             | Xuất sắc                         | Trung bình           |

### Chiến Lược Giảm Nhẹ

- **Builder** + `toBuilder()` — "sửa đổi" tiện lợi các object bất biến
- **Record** — boilerplate tối thiểu
- **Persistent Collections** (Vavr) — $O(\log n)$ thay vì $O(n)$
- **Cách tiếp cận kết hợp** — mutable để xử lý, immutable để lưu trữ

### Tóm Tắt Cho Advanced
- Nhược điểm chính — **overhead cấp phát** trong các kịch bản cập nhật tần suất cao
- Khả năng tương thích kém với các framework legacy (Hibernate, JPA)
- Để bù đắp: **Builder**, **Record**, **Persistent Collections**
- Tính bất biến là một sự đánh đổi: an toàn so với hiệu năng trong các trường hợp cụ thể

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Nhược điểm: áp lực GC (cấp phát thường xuyên), overhead sao chép, boilerplate trước khi có Record
- Tính bất biến sâu là khó — một bản sao bị quên phá hủy sự an toàn
- Giới hạn kế thừa — các immutable class phải là `final`
- Hibernate/JPA yêu cầu setter và constructor không tham số — khó khăn với các entity bất biến
- Jackson yêu cầu `@JsonCreator` + `@JsonProperty` để deserialize
- Giảm nhẹ: StringBuilder, pattern Builder, Record, Persistent Collections (Vavr)

**Các câu hỏi phụ thường gặp:**
- *Làm việc với Hibernate như thế nào?* — Annotation `@Immutable` hoặc làm việc qua DTO
- *Jackson không thể deserialize Record?* — Cần `@JsonCreator` + `@JsonProperty` (tốt hơn trong các phiên bản mới hơn)
- *Khi nào tính bất biến gây hại?* — Cập nhật tần suất cao: game logic, tọa độ của 1000 đơn vị
- *GC Jitter là gì?* — Các khoảng dừng Minor GC không phải lúc nào cũng dự đoán được — độ trễ tăng đột biến

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tính bất biến không có nhược điểm" — áp lực GC và boilerplate là có thật
- "Hibernate hoạt động tuyệt vời với immutable" — nó yêu cầu setter, constructor không tham số
- "Record giải quyết mọi vấn đề" — các collection và framework vẫn phức tạp
- "Mutability luôn nhanh hơn" — trong môi trường đa luồng không lock, immutability nhanh hơn
