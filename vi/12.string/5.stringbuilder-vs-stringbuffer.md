# When to Use StringBuilder vs StringBuffer? (Khi nào nên dùng StringBuilder vs StringBuffer?)

## 🟢 Junior Level

Cả hai class đều được thiết kế để **sửa đổi** chuỗi. Không như `String` thông thường, chúng có thể thay đổi nội dung mà không cần tạo object mới.

**Khác biệt chính:** `StringBuffer` là thread-safe (synchronized), `StringBuilder` thì không.

**Ví dụ:**
```java
// StringBuilder — dùng trong 99% các trường hợp
StringBuilder sb = new StringBuilder();
sb.append("Hello");
sb.append(" ");
sb.append("World");
String result = sb.toString(); // "Hello World"

// StringBuffer — chỉ khi chuỗi được dùng từ nhiều thread
StringBuffer sb2 = new StringBuffer();
sb2.append("Hello");
```

**Quy tắc:** Dùng `StringBuilder` theo mặc định. `StringBuffer` chỉ hợp lý khi một buffer được chia sẻ giữa các thread. Trong code legacy
nó xuất hiện thường xuyên hơn, nhưng đây là một di tích lịch sử, không phải một khuyến nghị.

## 🟡 Middle Level

### Cách Nó Hoạt Động

Cả hai class kế thừa từ `AbstractStringBuilder` và làm việc với một mảng `byte[]` nội bộ (Java 9+) hoặc `char[]` (trước Java 9):

```java
// Cấu trúc nội bộ
AbstractStringBuilder {
    byte[] value;   // Mảng dữ liệu
    int count;      // Số lượng ký tự hiện tại
}
```

**Capacity ban đầu:** 16 ký tự theo mặc định. Khi tràn, mảng mở rộng: `newCapacity = (oldCapacity << 1) + 2` (nhân đôi + 2).

### Ứng Dụng Thực Tế
```java
// StringBuilder — xây dựng một chuỗi trong một thread (trường hợp điển hình)
StringBuilder sb = new StringBuilder();
for (User user : users) {
    sb.append(user.getName()).append(", ");
}
```

### Các Lỗi Điển Hình
1. **Lỗi:** Dùng `StringBuffer` "để phòng khi cần"
   **Giải pháp:** Đồng bộ hóa thêm overhead ngay cả trong code đơn luồng

2. **Lỗi:** Không chỉ định capacity khi biết kích thước
   **Giải pháp:** `new StringBuilder(1024)` tránh việc cấp phát lại không cần thiết

### So Sánh
| Tiêu chí          | StringBuilder  | StringBuffer                                                                                        |
| ------------------ | -------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Thread safety      | Không             | Có (synchronized)                                                                                  |
| Tốc độ (1 thread)   | Nhanh hơn         | Chậm hơn 1.5-2.5 lần. Mỗi method synchronized đòi hỏi monitorenter/monitorexit + memory barrier.     |
Ở chế độ đơn luồng, JVM có thể loại bỏ một phần lock, nhưng không hoàn toàn. |
| Tốc độ (N thread)  | Race condition | Đúng, nhưng contention |
| Khi nào được giới thiệu    | Java 5         | Java 1.0                                                                                            |
| Khuyến nghị     | **Theo mặc định** | Chỉ cho truy cập chia sẻ thực sự                                                                         |

## 🔴 Senior Level

### Hiện Thực Nội Bộ

```java
// StringBuffer — tất cả các method đều synchronized
@Override
public synchronized StringBuffer append(Object obj) {
    toStringCache = null;
    super.append(String.valueOf(obj));
    return this;
}

// StringBuilder — không có synchronized
@Override
public StringBuilder append(Object obj) {
    return append(String.valueOf(obj));
}
```

Khác biệt then chốt: mọi method của `StringBuffer` đều có `synchronized`, nghĩa là phải lấy monitor object mỗi khi gọi.

### Đánh Đổi Về Kiến Trúc (Trade-off)

**StringBuffer:**
- Ưu điểm: Thread-safe, tương thích ngược với legacy
- Nhược điểm: Monitor trên mỗi method, memory barrier, false sharing dưới contention

**StringBuilder:**
- Ưu điểm: Không có overhead synchronization, hiệu năng tối ưu
- Nhược điểm: Không thread-safe — race condition khi truy cập song song

### Tối Ưu Hóa Của JVM: Lock Elision

JVM hiện đại (HotSpot) dùng **Escape Analysis** + **Lock Elision**:
```java
void method() {
    StringBuffer sb = new StringBuffer(); // Escape: không thoát khỏi phạm vi method
    sb.append("a");                       // JIT có thể loại bỏ synchronized
    sb.append("b");
}
```
Nếu JIT chứng minh được object không "thoát" khỏi thread — việc đồng bộ hóa bị loại bỏ. Nhưng:
- Điều này không được đảm bảo (phụ thuộc vào `-XX:+EliminateLocks`, ngân sách biên dịch)
- Bản thân việc phân tích tốn chu kỳ CPU
- `StringBuilder` nhanh "ngay từ đầu" mà không cần phép màu JIT

### Các Trường Hợp Biên

1. **Biased Locking (đã loại bỏ trong Java 15):** Trước đây JVM "thiên vị" monitor cho thread đầu tiên, khiến các lần chiếm giữ tiếp theo miễn phí. Điều này có nghĩa là trong Java 15+, overhead của StringBuffer ở chế độ đơn luồng thậm chí còn cao hơn trước.

2. **Công thức resize:** `(oldCapacity << 1) + 2`. Với capacity=16 → 34 → 70 → 142. Với kích thước đã biết, luôn đặt capacity trong constructor.

3. **toStringCache trong StringBuffer:** `StringBuffer` cache kết quả `toString()` gần nhất. Nếu buffer không thay đổi, `toString()` lặp lại trả về cache — nhưng đây là một tối ưu hóa nhỏ.

4. **Compact String Java 9+:** Cả hai class đều dùng `byte[]` với cờ `coder`. Ký tự Latin = 1 byte, các ký tự khác = 2 byte.

### Hiệu Năng (Benchmark JMH)
| Thao tác     | StringBuilder | StringBuffer (không contention) | StringBuffer (4 thread) |
| ------------- | ------------- | ---------------------------- | ------------------------ |
| append 1M     | ~15ms         | ~25ms                        | ~120ms                   |
| toString      | ~2ms          | ~2ms (cache)                 | ~2ms                     |
| Bộ nhớ        | ~2MB          | ~2MB + monitor               | ~2MB + overhead monitor  |

### Kinh Nghiệm Production
**Kịch bản:** Render báo cáo HTML (tổng 50KB) từ 10,000 bản ghi:
- Không có capacity: 12 lần realloc + copy → 15ms
- Với `new StringBuilder(51200)`: 0 lần realloc → 3ms
- `StringBuffer` trong cùng kịch bản: 20ms (lock elision có giúp, nhưng không hoàn toàn)

### Best Practices Cho Highload
- Luôn chỉ định `initialCapacity` nếu kích thước có thể dự đoán được
- Trong vòng lặp: `StringBuilder` **bên ngoài** vòng lặp, `append` **bên trong**
- `StringBuffer` — chỉ khi buffer được chia sẻ giữa các thread (trường hợp cực kỳ hiếm)
- Cho việc nối chuỗi bên ngoài vòng lặp: `invokedynamic` của Java 9+ thường hiệu quả hơn StringBuilder thủ công

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- `StringBuilder` — mutable, KHÔNG thread-safe, dùng trong 99% các trường hợp
- `StringBuffer` — mutable, thread-safe (synchronized), legacy từ Java 1.0
- Cả hai đều làm việc với `byte[]` nội bộ (Java 9+) / `char[]` (trước Java 9), mở rộng khi tràn: `newCapacity = (old << 1) + 2`
- Capacity ban đầu mặc định — 16 ký tự. Với kích thước đã biết — đặt trong constructor
- `StringBuilder` nhanh hơn `StringBuffer` 1.5-2.5 lần ở chế độ đơn luồng
- Trong vòng lặp: tạo `StringBuilder` TRƯỚC vòng lặp, `append` BÊN TRONG

**Các câu hỏi phụ thường gặp:**
- **Tại sao `StringBuffer` chậm hơn?** — Mọi method đều `synchronized`: lấy monitor, memory barrier, giải phóng. Ngay cả trong một thread.
- **Khi nào việc mở rộng xảy ra?** — Khi tràn: 16 → 34 → 70 → 142. Mỗi lần mở rộng = cấp phát mảng mới + `System.arraycopy`.
- **Bạn có thể dùng `StringBuffer` để an toàn không?** — Nếu mỗi thread dùng buffer riêng của mình — `StringBuilder` an toàn. `StringBuffer` chỉ cần cho truy cập chia sẻ thực sự.
- **JVM làm gì để tối ưu hóa `StringBuffer`?** — Lock Elision qua Escape Analysis: nếu object không "thoát" khỏi thread — JIT có thể loại bỏ `synchronized`. Nhưng không được đảm bảo.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "`StringBuffer` — lựa chọn được khuyến nghị" — đã lỗi thời, `StringBuilder` là mặc định
- ❌ "StringBuilder thread-safe" — không, race condition khi truy cập song song
- ❌ "Không cần đặt capacity" — không có capacity: 12+ lần realloc cho một chuỗi 50KB
- ❌ "`StringBuffer` cần cho mọi ứng dụng đa luồng" — chỉ khi MỘT buffer được chia sẻ giữa các thread
