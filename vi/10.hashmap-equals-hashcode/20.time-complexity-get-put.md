# What is the Time Complexity of get() and put() Operations in HashMap? (Độ phức tạp thời gian của các thao tác get() và put() trong HashMap là gì?)

## 🟢 Junior Level

Trong HashMap, các thao tác chính (`get`, `put`, `remove`) hoạt động **rất nhanh** — trung bình trong **O(1)**, tức là thời gian hằng số.

**Điều này nghĩa là:**
```java
HashMap<String, Integer> map = new HashMap<>();

map.put("key1", 100);   // O(1) — tức thời
map.get("key1");        // O(1) — tức thời
map.remove("key1");     // O(1) — tức thời
```

Với một hashCode tốt, tra cứu mất khoảng cùng thời gian bất kể kích thước của map. Với một hashCode kém (nhiều va chạm) — thời gian tăng tỷ lệ thuận.

**Trường hợp xấu nhất:** Nếu mọi key rơi vào một bucket, tìm kiếm chậm xuống O(n) trong Java 7 hoặc O(log n) trong Java 8+. Nhưng điều này hiếm khi xảy ra với một `hashCode()` đúng đắn.

## 🟡 Middle Level

### Bảng tóm tắt

| Thao tác      | Trường hợp trung bình | Xấu nhất (Java 7)   | Xấu nhất (Java 8+)   |
| ------------- | ---------------- | ------------------- | -------------------- |
| get()         | O(1)             | O(n)                | O(log n)             |
| put()         | O(1)*            | O(n)                | O(log n)             |
| remove()      | O(1)             | O(n)                | O(log n)             |
| containsKey() | O(1)             | O(n)                | O(log n)             |
| iterate       | O(capacity + size) | O(capacity + size) | O(capacity + size)   |

*put() — O(1) khấu hao (amortized), vì resize định kỳ = O(n)

### Tại sao O(1)?

1. Tính `hash(key)`: O(1) — một vài phép toán bitwise
2. Xác định chỉ số: O(1) — `(n-1) & hash`
3. Truy cập mảng: O(1) — truy cập trực tiếp theo chỉ số
4. So sánh trong bucket: O(1) — trung bình 1-2 phần tử

### Chi phí khấu hao của put()

Resize là một thao tác O(n), nhưng xảy ra hiếm (cấp số nhân — geometric progression):
- 16 → 32 → 64 → 128 → ...
- Chi phí khấu hao: O(1)

### Các yếu tố ảnh hưởng tới tốc độ thực tế

| Yếu tố                | Ảnh hưởng                                     |
| --------------------- | -------------------------------------------- |
| Chi phí của `equals()`| equals nặng = hằng số lớn                    |
| Chất lượng của `hashCode()` | Nhiều va chạm → O(log n)             |
| Load Factor           | Cao hơn = nhiều va chạm hơn                  |
| Kích thước key        | Các string dài = hashCode/equals chậm       |

### Các sai lầm thường gặp

1. **Nghĩ O(1) = cùng thời gian luôn luôn** — hằng số phụ thuộc vào chất lượng hashCode
2. **Bỏ qua khấu hao** — resize có thể gây tăng vọt latency
3. **Nhầm với iterate** — `forEach` = O(capacity + size), không phải O(1)

### Khi nào KHÔNG nên dùng HashMap

1. **Cần latency dự đoán được** — resize gây tăng vọt, cân nhắc LinkedHashMap với capacity cố định
2. **Cần sắp xếp** — TreeMap O(log n)
3. **Truy cập đa luồng** — ConcurrentHashMap

## 🔴 Senior Level

### Phân tích bên trong

```java
// Bên trong get():
// 1. hash(key):         ~3 chu kỳ (XOR + dịch)
// 2. index = (n-1)&hash: ~1 chu kỳ
// 3. tab[index]:         ~1 chu kỳ (L1 cache hit) hoặc ~100 chu kỳ (RAM miss)
// 4. equals():           từ 1 chu kỳ (tham chiếu) tới O(k) (so sánh string)
```

Latency thực tế phụ thuộc vào **cache locality**:
- L1 hit: ~1 ns
- L2 hit: ~4 ns
- L3 hit: ~15 ns
- RAM miss: ~100 ns

### Trường hợp xấu nhất: Khi nào O(n) có thể xảy ra

Trong Java 8+, O(n) tồn tại trong ba trường hợp:

1. **capacity < 64** — treeification không kích hoạt, ở 8+ va chạm = O(n)
2. **hashCode() trả về một hằng số cho mọi key** — mọi phần tử trong một bucket
3. **Java 7**: không có treeification, luôn O(n) khi va chạm

O(log n) — giới hạn suy giảm khi treeification.

### Dữ liệu Benchmark (Java 21, Intel i9)

| Thao tác         | Kích thước | Latency trung bình | P99     |
| ---------------- | -------- | --------------- | ------- |
| get()            | 1K       | 5 ns            | 12 ns   |
| get()            | 1M       | 8 ns            | 25 ns   |
| put()            | 1K       | 8 ns            | 20 ns   |
| put() (có resize) | 1M→2M   | 150 ns          | 5000 ns |
| iterate          | 1M       | 200 µs          | 250 µs  |

### ConcurrentHashMap vs HashMap

| Chỉ số            | HashMap   | ConcurrentHashMap   |
| ----------------- | --------- | ------------------- |
| get (một thread)  | 5 ns      | 8 ns                |
| get (8 thread)    | Không áp dụng | 60 ns            |
| put (một thread)  | 8 ns      | 15 ns               |
| put (8 thread)    | Không áp dụng | 120 ns           |

### Các trường hợp biên (Edge Case)

1. **hashCode() = hằng số**: O(n) cho Java 7, O(log n) cho Java 8+
2. **Capacity khổng lồ, ít phần tử**: iterate O(capacity) chiếm ưu thế
3. **Các key String với giá trị dài**: equals() = O(k), với k là độ dài string

### Tinh chỉnh Production

- Đặt trước capacity loại bỏ resize O(n)
- Giám sát P99 latency phát hiện các tăng vọt do resize
- Event JFR `jdk.HashMapResize` (Java 17+) để profiling

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Trường hợp trung bình: get/put/remove = O(1) qua hash + lập chỉ mục + equals
- Xấu nhất Java 7: O(n) — linked list trong bucket
- Xấu nhất Java 8+: O(log n) — tree khi va chạm
- Iterate: O(capacity + size) — KHÔNG phải O(1), duyệt qua mọi bucket
- put() — O(1) khấu hao: resize O(n) nhưng xảy ra hiếm (cấp số nhân)
- Latency thực tế phụ thuộc cache locality: L1 hit ~1ns, RAM miss ~100ns

**Các câu hỏi phụ thường gặp:**
- **Tại sao O(1) chứ không phải O(log n)?** — trung bình 1-2 phần tử trong một bucket với một hashCode tốt
- **Độ phức tạp khấu hao là gì?** — resize riêng lẻ thì đắt, nhưng trung bình qua N lần chèn = O(1)
- **Khi nào O(n) có thể xảy ra trong Java 8+?** — capacity < 64, hashCode = hằng số, hoặc Java 7
- **Overhead của ConcurrentHashMap?** — ~60% trên một thread, nhưng là lựa chọn đúng đắn duy nhất cho đa luồng

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "O(1) = cùng thời gian luôn luôn" — không, hằng số phụ thuộc vào hashCode, equals, cache locality
- "Iterate = O(1)" — không, O(capacity + size)
- "HashMap luôn nhanh hơn TreeMap" — không, TreeMap là O(log n) nhưng cho sắp xếp và latency dự đoán được
