# How to implement authentication and authorization in microservices (Cách triển khai authentication và authorization trong microservices)

## 🟢 Junior Level

**Authentication** — bạn là ai? (xác minh danh tính)

**Authorization** — bạn được phép làm gì? (kiểm tra quyền)

**Cách tiếp cận phổ biến nhất — JWT token:**
```
1. Client → Login Service → username/password
2. Login Service → JWT token
3. Client → JWT token → API Gateway → xác thực token
4. API Gateway → chuyển tiếp đến các service + userId trong header
```

**JWT token** chứa:
- Người dùng là ai (userId, roles)
- Chữ ký (để ngăn giả mạo)

## 🟡 Middle Level

### JWT Trong API Gateway

```java
@Component
public class AuthFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain chain) {
        String token = request.getHeader("Authorization");

        if (token != null && token.startsWith("Bearer ")) {
            try {
                // JwtUtil — lớp tiện ích ví dụ. Trong production, hãy dùng Spring Security JWT
                // hoặc một thư viện như java-jwt (Auth0) / nimbus-jose-jwt.
                Claims claims = JwtUtil.parseToken(token.substring(7));
                request.setAttribute("userId", claims.get("userId"));
                request.setAttribute("roles", claims.get("roles"));
            } catch (JwtException e) {
                response.setStatus(HttpStatus.UNAUTHORIZED.value());
                return;
            }
        }

        chain.doFilter(request, response);
    }
}
```

### OAuth 2.0 / OpenID Connect

```
Client → Auth Server (Keycloak) → Authorization Code
Client → Auth Server → Access Token + ID Token
Client → API Gateway + Access Token → Service
```

### Các Lỗi Thường Gặp

1. **Xác thực token ở mỗi service:**
```
Mỗi service xác thực token → overhead mã hóa (ký JWT là RSA/ECDSA).
Ở 10K req/s qua 20 service = 200K thao tác HMAC/RSA. Giải pháp: API Gateway
xác thực một lần và truyền kết quả qua header.
```

---

### Khi Nào KHÔNG Nên Dùng JWT

- **Yêu cầu thu hồi cao** — JWT khó thu hồi (cần blacklist)
- **Session-based tốt hơn** khi cần chấm dứt session ngay lập tức
- **OAuth2 Device Flow** cho các thiết bị không có trình duyệt

## 🔴 Senior Level

### Token Propagation

```
Gateway → Service A → Service B
         Access Token được truyền dọc theo chuỗi
```

### mTLS (mutual TLS)

```
Service A ↔ Service B: xác minh chứng chỉ lẫn nhau
Bảo vệ bổ sung cho giao tiếp service-to-service
```

### Kinh Nghiệm Production

**Keycloak + Spring Security:**
```yaml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: http://keycloak:8080/realms/myrealm
          jwk-set-uri: http://keycloak:8080/realms/myrealm/protocol/openid-connect/certs
```

### Best Practices

```
✅ Xác thực token trong Gateway
✅ Luôn dùng HTTPS
✅ Access token sống ngắn
✅ Refresh token
✅ mTLS cho service-to-service
✅ Xoay vòng signing key

❌ Lưu trữ bí mật trong token
❌ Không có expiration
❌ Xác thực ở mỗi service
❌ HTTP cho token
```

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- Authentication = bạn là ai, authorization = bạn được phép làm gì
- JWT token: userId + roles + chữ ký, được truyền trong header Authorization: Bearer
- API Gateway xác thực token một lần — các service nhận kết quả qua header (tránh overhead mã hóa)
- OAuth 2.0 / OpenID Connect — cách tiếp cận chuẩn với Auth Server (Keycloak)
- mTLS cho service-to-service — xác minh chứng chỉ lẫn nhau
- Access token sống ngắn + refresh token — cân bằng bảo mật
- KHÔNG dùng JWT khi có yêu cầu thu hồi cao (cần blacklist)

**Các câu hỏi phụ thường gặp:**
- **Tại sao không xác thực ở mỗi service?** Chữ ký RSA/ECDSA tốn kém. Ở 10K req/s qua 20 service = 200K thao tác HMAC.
- **Cách thu hồi một JWT?** JWT khó thu hồi — cần blacklist hoặc token sống ngắn. Để thu hồi ngay lập tức — session-based tốt hơn.
- **JWT vs OAuth2?** JWT là một định dạng token, OAuth2 là một giao thức. OAuth2 có thể dùng JWT làm access token.
- **mTLS là gì?** Mutual TLS — cả hai service xác minh chứng chỉ của nhau — bảo vệ service-to-service.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Mỗi service xác thực JWT" — không, overhead mã hóa, Gateway xác thực một lần
- "JWT có thể lưu trữ bí mật" — không, JWT được ký nhưng KHÔNG được mã hóa (payload có thể đọc được)
- "Access token không có expiration" — không, nếu bị lộ, kẻ tấn công có quyền truy cập vĩnh viễn
- "HTTP cho các service nội bộ" — không, token luôn qua HTTPS
