# How is Single Responsibility Related to Cohesion (Single Responsibility liên quan đến Cohesion như thế nào)

## 🟢 Junior Level

**Cohesion** là một phép đo mức độ liên quan chặt chẽ của các phương thức và trường của một class với nhau. **SRP** và cohesion liên hệ chặt chẽ: khi một class có một trách nhiệm duy nhất, các thành phần của nó tự nhiên hướng đến một mục tiêu — đó là cohesion cao.

**Analogy đơn giản:** Hãy tưởng tượng một đội. Nếu mọi người làm việc trên một nhiệm vụ (cohesion cao) — mọi thứ tuyệt vời. Nếu mọi người làm việc riêng của mình (cohesion thấp) — hỗn loạn.

**Ví dụ cohesion cao:**
```java
// Cohesion cao: tất cả các phương thức làm việc với order
public class OrderService {
    public Order createOrder() { /* ... */ }
    public void cancelOrder(Order order) { /* ... */ }
    public BigDecimal calculateTotal(Order order) { /* ... */ }
}
```

**Ví dụ cohesion thấp:**
```java
// Cohesion thấp: các phương thức làm những việc hoàn toàn khác nhau
public class UserManager {
    public void sendEmail() { /* email */ }
    public void calculateSalary() { /* lương */ }
    public void generateReport() { /* report */ }
    public void saveToDatabase() { /* DB */ }
}
```

**Khi nào nên hướng tới cohesion cao:**
- Khi thiết kế các class mới nơi trách nhiệm chưa ổn định
- Khi refactor các class "phình to"
- Đừng theo đuổi cohesion hoàn hảo trong prototype và MVP — tốc độ quan trọng hơn ở đó

## 🟡 Middle Level

### Cách Hoạt Động

**Cohesion** — một đặc tính nội bộ của một class: các phần của nó được "dán" với nhau tốt như thế nào cho một mục đích chung. **SRP** — một quy tắc bên ngoài chỉ ra nơi để cắt hệ thống.

**Mối liên hệ**: Tuân theo SRP nói chung dẫn đến cohesion cao. Một class với một trách nhiệm duy nhất tự nhiên có các phương thức làm việc trên một tác vụ. Nhưng có các ngoại lệ — ví dụ, một orchestrator class có thể điều phối một số hệ thống con trong khi vẫn ở trong một trách nhiệm duy nhất.

### Các Cấp Độ Cohesion Của Myers (phân loại bởi Glenford Myers, tác giả của "Reliable Software Through Composite Design")

| Cấp độ               | Mô tả                              | Ví dụ            | Chất lượng      |
| ------------------- | ---------------------------------------- | ------------------ | ------------ |
| **Functional**      | Class làm một việc                     | `StringTokenizer`  | ✅ Lý tưởng      |
| **Sequential**      | Các phương thức tạo thành một pipeline                  | `ImageTransformer` | ✅ Tốt       |
| **Communicational** | Các phương thức làm việc trên cùng dữ liệu            | `OrderRepository`  | ✅ Chấp nhận được |
| **Procedural**      | Các phương thức thực thi theo một thứ tự cụ thể      | `StartupInitializer` | ⚠️ Chịu được |
| **Temporal**        | Các phương thức thực thi cùng lúc         | `ConfigLoader`     | ⚠️ Chịu được  |
| **Utility**         | Nhóm yếu                            | `CommonUtils`      | ❌ Xấu        |
| **Coincidental**    | Nhóm ngẫu nhiên                          | `Helper`           | ❌ Khủng khiếp   |

### Metric LCOM (Lack of Cohesion in Methods)

LCOM phân tích bao nhiêu phương thức chia sẻ các trường chung. Được tính bởi các bộ phân tích tĩnh (SonarQube, jdepend):
- Nếu 10 phương thức: 5 làm việc với trường A, 5 với trường B → LCOM cao → class nên chia thành 2 class
- LCOM = 0: tất cả các phương thức chia sẻ các trường chung (cohesion cao)
- LCOM > 1.0: các phương thức tạo thành các nhóm độc lập (cohesion thấp)

### Cân Bằng SRP Và Coupling

**Mục tiêu**: Cohesion Cao + Coupling Thấp

| Cách tiếp cận                                                                | Cohesion   | Coupling   | Kết quả      |
| ----------------------------------------------------------------------- | ---------- | ---------- | ----------- |
| **God Object** (một class làm mọi thứ — vi phạm SRP)               | Thấp        | Thấp        | ❌ Dễ vỡ   |
| **Atomic Dust** (các class quá nhỏ — hàng trăm class 5 dòng)         | Cao       | Khủng khiếp  | ❌ Phức tạp   |
| **Cân bằng**                                                             | Cao       | Thấp        | ✅ Lý tưởng     |

### Các Lỗi Thường Gặp

| Lỗi                                                                                                                   | Giải pháp                                                                                                                             |
| ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Class có "And/Or/Manager" trong tên                                                                                   | Chia theo trách nhiệm                                                                                                                              |
| LCOM > 1.0                                                                                                                | Trích xuất các class riêng biệt                                                                                                                             |
| Package-by-Layer (nhóm theo tầng kỹ thuật: tất cả controller, tất cả service, tất cả repository) → cohesion thấp           | Package-by-Feature (nhóm theo tính năng nghiệp vụ: Order, User, Payment — mỗi package chứa controller + service + repository riêng của nó) |

### Khi Nào KHÔNG Theo Đuổi Cohesion Hoàn Hảo

- Prototype/MVP (tốc độ quan trọng hơn)
- Các tiện ích nhỏ (lên đến 200 dòng)
- Khi cân bằng bị phá vỡ theo hướng khác (atomic dust)

## 🔴 Senior Level

### Triển Khai Nội Bộ: LCOM4 Và Đồ Thị Cohesion

**LCOM4** (LCOM phiên bản 4, cải tiến bởi Henderson-Sellers) được tính thông qua một đồ thị dependency:
- Node = các phương thức + trường
- Cạnh = phương thức dùng trường
- Nếu đồ thị chia thành N component → class nên được chia thành N phần

```
Các phương thức: [m1, m2, m3, m4, m5]
Các trường: [f1, f2, f3, f4]

m1→f1, m2→f1, m3→f2  (Component 1)
m4→f3, m5→f4          (Component 2)

LCOM4 = 2 → chia thành 2 class
```

### Đánh Đổi Kiến Trúc

**SRP Nghiêm Ngặt (Functional Cohesion):**
- ✅ Ưu điểm: Khả năng test lý tưởng, side effect tối thiểu, refactoring dễ dàng
- ❌ Nhược điểm: Bùng nổ class, coupling cao giữa các class, tải nhận thức

**SRP Cân Bằng (Communicational Cohesion):**
- ✅ Ưu điểm: Cân bằng giữa khả năng test và khả năng điều hướng
- ❌ Nhược điểm: Yêu cầu phán đoán trưởng thành, nguy cơ suy thoái dần dần

### Edge Cases

1. **Anemic Domain Model** (các class chỉ có getter/setter, không có business logic — tất cả tính toán chuyển sang service): Các class chỉ có getter/setter → LCOM = 0, nhưng điều đó không có nghĩa là "tốt"
   - **Giải pháp**: DDD (Domain-Driven Design — một cách tiếp cận nơi business logic sống gần dữ liệu, không phải trong các service riêng biệt) — giữ logic gần dữ liệu

2. **Package-by-Layer vs Package-by-Feature**:
   - Layer: `[Controller, Service, DAO]` → cohesion thấp ở cấp độ package
   - Feature: `[Order, User, Payment]` → cohesion cao, SRP ở cấp độ module

3. **Ranh Giới Transaction**: Một class điều phối một transaction qua nhiều domain
   - **Giải pháp**: Pattern Orchestrator, nhưng business logic trong các service riêng biệt

### Hiệu Năng

**Cache Locality:**
```
Cohesion cao:
  class OrderProcessor { fields: order, items, total }
  → Dữ liệu gần nhau trong bộ nhớ → tỷ lệ L1 cache hit >90%

Cohesion thấp:
  class GodObject { fields: order, email, db, cache, log, ... }
  → Dữ liệu rải rác → tỷ lệ L1 cache miss >30%
```

**Tác Động Cache CPU**: Cohesion cao → spatial locality tốt hơn → +15-30% throughput

### Thread Safety

- **Các class cohesion cao**: Thường đơn giản hơn để đồng bộ (một lock mỗi class)
- **Cohesion thấp (God Object)**: Nhiều trách nhiệm → tranh chấp lock → bottleneck

### Kinh Nghiệm Production

**Refactoring BillingEngine (12,000 dòng):**
LCOM4 = 8, 6 trường được dùng bởi các tập con phương thức khác nhau. Chia thành:
- `TaxCalculator` (Functional cohesion)
- `InvoiceGenerator` (Sequential cohesion)
- `PaymentProcessor` (Communicational cohesion)
- `BillingOrchestrator` (coordinator)

**Kết quả**: LCOM4 = 1.0 cho mỗi cái, bug deployment ↓70%.

### Monitoring

**ArchUnit:**
```java
@ArchTest
static void classes_should_have_high_cohesion = classes()
    .should().haveSimpleNameNotContaining("Manager")
    .andShould().haveSimpleNameNotContaining("Utils")
    .andShould().haveLessThanNDependencies(7);
```

**SonarQube**: LCOM > 1.0 → Code Smell, Cognitive Complexity > 15

**jdepend**: Báo cáo metric → Lack of Cohesion in Methods

### Best Practices Cho Highload

- **Package-by-Feature** cho cohesion module
- **LCOM4 < 1.0** như một metric mục tiêu
- **Functional Cohesion** cho các class hot-path
- **ArchUnit** để kiểm tra tự động

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- Cohesion — các phương thức của class hướng tới một mục tiêu tốt như thế nào; SRP → Cohesion cao
- Các cấp độ cohesion của Myers: Functional (lý tưởng) → Sequential → Communicational → Procedural → Temporal → Utility → Coincidental (khủng khiếp)
- LCOM (Lack of Cohesion in Methods): LCOM = 0 → cohesion cao, LCOM > 1.0 → đáng để chia
- LCOM4: nếu đồ thị dependency chia thành N component → chia class thành N phần
- Mục tiêu: Cohesion Cao + Coupling Thấp — tránh God Object và Atomic Dust
- Package-by-Feature cho cohesion cao, Package-by-Layer cho cohesion thấp
- Cohesion cao → spatial locality tốt hơn → +15-30% throughput (tác động cache CPU)

**Các câu hỏi phụ thường gặp:**
- **Nên hướng tới cấp độ cohesion nào?** — Functional cho hot-path, Communicational cho hầu hết các class
- **LCOM4 = 2 nghĩa là gì?** — Class nên được chia thành 2 class độc lập
- **Anemic Domain Model và cohesion?** — Getter/setter → LCOM = 0, nhưng đó không phải "tốt" — logic được chuyển sang service
- **Atomic Dust là gì?** — Các class quá nhỏ (hàng trăm class 5 dòng), cohesion cao nhưng coupling khủng khiếp

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Luôn theo đuổi cohesion hoàn hảo" (prototype/MVP — tốc độ quan trọng hơn)
- "LCOM = 0 luôn có nghĩa là thiết kế tốt" (Anemic Domain Model cũng cho LCOM = 0)
- "Package-by-Layer là cách tiếp cận tốt nhất" (cohesion thấp ở cấp độ package, Package-by-Feature tốt hơn)
