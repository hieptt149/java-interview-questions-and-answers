# What is index cardinality? (Index cardinality là gì?)

## 🟢 Junior Level

**Cardinality (độ đa dạng giá trị)** là số lượng giá trị duy nhất (unique values) trong một cột của bảng.

**Tại sao điều này quan trọng:** Bộ lập kế hoạch truy vấn (query planner) của PostgreSQL sử dụng cardinality để quyết định có nên sử dụng index hay đọc toàn bộ bảng. Cardinality cao = nhiều giá trị duy nhất = index hoạt động hiệu quả. Cardinality thấp = ít giá trị duy nhất = Seq Scan có khả năng sẽ nhanh hơn dùng index.

**Ví dụ minh họa đơn giản:** Hãy tưởng tượng một túi bi có nhiều màu khác nhau. Cardinality là có bao nhiêu màu **khác nhau** trong túi (không tính có bao nhiêu viên bi của mỗi màu).

**Ý tưởng chính:**
- Cardinality cao = nhiều giá trị duy nhất (ví dụ: email)
- Cardinality thấp = ít giá trị duy nhất (ví dụ: giới tính: Nam/Nữ)
- Index hiệu quả hơn trên các trường có cardinality **cao**

**Ví dụ:**
```sql
-- Bảng users (1,000,000 dòng)

-- Cardinality cao
SELECT COUNT(DISTINCT email) FROM users;  -- ~1,000,000 (duy nhất)

-- Cardinality thấp
SELECT COUNT(DISTINCT gender) FROM users; -- 2 (Nam và Nữ)

-- Index trên email — lựa chọn tuyệt vời ✅
-- Index trên gender — lựa chọn kém ❌
```

**Khi nào điều này quan trọng:**
- Khi lựa chọn trường để tạo index
- Khi phân tích lý do tại sao một index không được sử dụng
- Khi tối ưu hóa các truy vấn chậm

## 🟡 Middle Level

### Cardinality vs Selectivity (Độ chọn lọc)

Hai khái niệm này có liên quan nhưng khác biệt:

| Thuật ngữ               | Định nghĩa                        | Ví dụ                      |
| ------------------ | --------------------------------- | ----------------------------- |
| **Cardinality**    | Số lượng giá trị duy nhất           | `COUNT(DISTINCT city) = 500` |
| **Selectivity**    | Cardinality / Tổng số dòng         | `500 / 1,000,000 = 0.0005`   |

**Cardinality càng cao → selectivity càng cao → index càng hiệu quả.**

**Tại sao:** Selectivity cao có nghĩa là truy vấn sẽ trả về ít dòng. Index Scan đọc 3-4 page của B-tree + 1 page Heap cho mỗi dòng tìm thấy. Nếu có 100,000 dòng trong tổng số 1,000,000 — đó là 100,000 lần đọc Heap ngẫu nhiên, chậm hơn so với một lần đọc tuần tự toàn bộ bảng (Seq Scan).

### PostgreSQL ước tính cardinality như thế nào

PostgreSQL thu thập thống kê thông qua lệnh `ANALYZE` (chạy tự động):

```sql
-- Xem thống kê cột
SELECT
    attname as column_name,
    n_distinct,              -- Ước tính độ duy nhất
    correlation              -- Tương quan với thứ tự vật lý
FROM pg_stats
WHERE tablename = 'users'
  AND attname = 'email';
```

**n_distinct:**
- Nếu **> 0** — số lượng tuyệt đối các giá trị duy nhất
- Nếu **< 0** (ví dụ: -1) — tỷ lệ so với tổng số (-1 = 100% duy nhất)

### Ảnh hưởng đến việc lựa chọn execution plan

```sql
-- Cardinality cao (email)
EXPLAIN SELECT * FROM users WHERE email = 'test@example.com';
-- Plan: Index Scan (sẽ tìm thấy 1 dòng trong số 1 triệu)

-- Cardinality thấp (status)
EXPLAIN SELECT * FROM users WHERE status = 'ACTIVE';
-- Plan: Seq Scan (sẽ trả về 500,000 dòng — index không có lợi)
```

**Ngưỡng chuyển đổi (ước lượng):**

| % dòng trong kết quả    | Plan                                                                                                      |
| ------------------- | --------------------------------------------------------------------------------------------------------- |
| < 1-5%              | Index Scan                                                                                                |
| 5-20%               | Bitmap Index Scan (thu thập các TID vào một bitmap, sau đó đọc heap — ít thao tác I/O ngẫu nhiên hơn Index Scan)      |
| > 20%               | Seq Scan                                                                                                  |

### Data Skew (Lệch dữ liệu)

```sql
-- Bảng orders: 1,000,000 dòng
SELECT status, COUNT(*)
FROM orders
GROUP BY status;

-- Kết quả:
-- ACTIVE:   950,000 (95%)
-- PENDING:   40,000 (4%)
-- ERROR:     10,000 (1%)

-- Truy vấn 1: WHERE status = 'ERROR' → Index Scan (giá trị hiếm)
-- Truy vấn 2: WHERE status = 'ACTIVE' → Seq Scan (giá trị phổ biến)

**Tại sao có các plan khác nhau:** PostgreSQL lưu trữ MCV (Most Common Values — các giá trị phổ biến nhất) — một danh sách các giá trị xuất hiện nhiều nhất kèm theo tần suất của chúng. Đối với 'ERROR' (1%), planner biết rằng nó sẽ tìm thấy ~10,000 dòng trong số 1 triệu — Index Scan có lợi. Đối với 'ACTIVE' (95%) — 950,000 dòng, việc đọc bằng Seq Scan sẽ rẻ hơn (một lần đọc tuần tự so với 950,000 lần đọc ngẫu nhiên).
```

PostgreSQL lưu trữ **Most Common Values (MCV — các giá trị phổ biến nhất)** và có thể chọn các plan khác nhau cho các giá trị khác nhau!

### Các lỗi thường gặp

1. **Tạo index trên các trường có cardinality thấp**
   ```sql
   -- ❌ Không tốt: chỉ có 2 giá trị
   CREATE INDEX idx_users_gender ON users(gender);
   -- Seq Scan vẫn sẽ được chọn cho hầu hết các truy vấn
   ```

2. **Bỏ qua cardinality kết hợp (composite cardinality)**
   ```sql
   -- Riêng lẻ: city (500), age (80) — cardinality trung bình
   -- Kết hợp: (city, age) → cardinality của sự kết hợp lại cao!
   CREATE INDEX idx_users_city_age ON users(city, age);
   ```

3. **Thống kê lỗi thời**
   ```sql
   -- Sau khi bulk insert, thống kê đã lỗi thời
   -- Planner có thể chọn sai plan

   -- Giải pháp: cập nhật thống kê
   ANALYZE users;
   ```

### Ví dụ thực tiễn

```sql
-- Kiểm tra cardinality của cột
SELECT
    attname as column_name,
    n_distinct,
    CASE
        WHEN n_distinct < 0 THEN 'Cao (' || ABS(n_distinct) * 100 || '%)'
        WHEN n_distinct < 100 THEN 'Thấp'
        WHEN n_distinct < 10000 THEN 'Trung bình'
        ELSE 'Cao'
    END as cardinality_level
FROM pg_stats
WHERE tablename = 'users';
```

## 🔴 Senior Level

### Postgres ước tính cardinality như thế nào: Đào sâu chi tiết

Thống kê được lưu trong `pg_statistic` (truy cập thông qua `pg_stats`):

**Các trường (fields) quan trọng:**

1. **n_distinct**
   ```sql
   -- Ước tính độ duy nhất
   -- Ví dụ:
   -- -1.0 = 100% duy nhất (mỗi giá trị đều là duy nhất)
   -- -0.5 = 50% duy nhất
   -- 100 = chính xác 100 giá trị duy nhất
   ```

2. **most_common_vals (MCV)**
   ```
   -- Top các giá trị xuất hiện thường xuyên nhất và tần suất của chúng
   -- Ví dụ cho status:
   -- MCV: ['ACTIVE', 'PENDING', 'ERROR']
   -- Freq: [0.95, 0.04, 0.01]

   -- Planner sử dụng thông tin này để ước tính chính xác:
   -- WHERE status = 'ERROR' → Index Scan (1% số dòng)
   -- WHERE status = 'ACTIVE' → Seq Scan (95% số dòng)
   ```

3. **histogram_bounds**
   ```
   -- Phân bố giá trị cho các giá trị không nằm trong MCV
   -- Chia khoảng giá trị thành các bucket (mặc định 100 bucket)
   -- Được dùng để ước tính selectivity theo khoảng giá trị
   ```

4. **correlation**
   ```
   -- Một con số từ -1 đến 1
   -- Cho biết thứ tự dòng vật lý (physical order)
   -- khớp với thứ tự logic của các giá trị trong index đến mức nào

   -- correlation = 1.0 → các dòng trên đĩa được sắp xếp giống như trong index
   -- correlation = 0.0 → hoàn toàn hỗn loạn (Random I/O)
   -- correlation = -1.0 → được sắp xếp theo thứ tự ngược lại
   ```

### Extended Statistics (Thống kê mở rộng) (PostgreSQL 10+)

**Vấn đề:** PostgreSQL giả định các cột **độc lập** với nhau.

```sql
-- Truy vấn
SELECT * FROM cars
WHERE make = 'Honda' AND model = 'Civic';

-- Planner nghĩ:
-- P(make='Honda') = 0.1
-- P(model='Civic') = 0.05
-- P(cả hai) = 0.1 * 0.05 = 0.005 (0.5%)

-- Thực tế:
-- Nếu make='Honda', thì model='Civic' có khả năng cao hơn nhiều!
-- P(cả hai) = 0.03 (3%) — gấp 6 lần!
```

**Giải pháp: Extended Statistics**

```sql
-- 1. Functional Dependencies (Phụ thuộc hàm)
-- Nếu biết model, ta biết được make
CREATE STATISTICS s_make_model (dependencies)
ON make, model FROM cars;

-- 2. N-Distinct
-- Cardinality của các tổ hợp cột
CREATE STATISTICS s_city_age (ndistinct)
ON city, age FROM users;

-- 3. MCV cho các tổ hợp (PG 13+)
-- Các tổ hợp giá trị phổ biến nhất
CREATE STATISTICS s_status_priority (mcv)
ON status, priority FROM orders;

-- Áp dụng
ANALYZE cars;
ANALYZE users;
ANALYZE orders;
```

> Ở PG 12 trở xuống, loại `mcv` không khả dụng — hãy dùng `dependencies` và `ndistinct`.

**Kiểm tra:**
```sql
-- Xem thống kê mở rộng
SELECT * FROM pg_stats_ext
WHERE tablename = 'cars';

-- Cụ thể là ndistinct
SELECT
    stxname,
    stxkeys,
    stxndistinct
FROM pg_statistic_ext
WHERE stxname = 's_city_age';
```

### Ảnh hưởng của statistics_target

```sql
-- Mặc định: 100 bucket histogram
SHOW default_statistics_target;

-- Đối với các cột có phân bố "bất thường", hãy tăng độ chính xác
ALTER TABLE users ALTER COLUMN email SET STATISTICS 1000;
ALTER TABLE orders ALTER COLUMN status SET STATISTICS 500;

-- Cập nhật thống kê
ANALYZE users;
ANALYZE orders;

-- ⚠️ Chi phí: ANALYZE sẽ mất nhiều thời gian hơn
-- Nhưng việc lập kế hoạch (planning) sẽ chính xác hơn
```

### Các trường hợp đặc biệt (Edge Cases)

1. **Correlation làm mất tác dụng index**
   ```sql
   -- Kiểm tra
   SELECT attname, correlation
   FROM pg_stats
   WHERE tablename = 'orders'
     AND attname = 'created_at';

   -- correlation = 0.05 → Random I/O
   -- Giải pháp: CLUSTER (sắp xếp lại bảng)
   CLUSTER orders USING idx_orders_created;
   -- ⚠️ Khóa bảng! Hãy thực hiện trong khung giờ bảo trì (maintenance window)
   ```

2. **Thống kê lỗi thời**
   ```sql
   -- Kiểm tra: lần cuối ANALYZE chạy khi nào
   SELECT
       relname,
       last_analyze,
       last_autoanalyze,
       n_mod_since_analyze  -- Số thay đổi kể từ lần ANALYZE cuối
   FROM pg_stat_user_tables
   WHERE n_mod_since_analyze > 100000;  -- Nhiều thay đổi!

   -- Giải pháp
   ANALYZE VERBOSE orders;
   ```

3. **Bảng được phân vùng (Partitioned Tables)**
   ```sql
   -- Đối với các bảng được phân vùng, thống kê được thu thập trên từng partition
   -- Planner có thể ước tính sai
   -- Giải pháp: tăng statistics_target trên các partition quan trọng
   ALTER TABLE orders_y2024 ALTER COLUMN created_at SET STATISTICS 1000;
   ```

### Hiệu năng

**Ảnh hưởng đến việc lập kế hoạch (planning):**

| statistics_target     | Độ chính xác của plan      | Thời gian ANALYZE   |
| --------------------- | ------------------ | -------------- |
| 10 (tối thiểu)          | Thấp                | Nhanh          |
| 100 (mặc định)         | Tốt                | Bình thường         |
| 1000                  | Xuất sắc          | Lâu hơn 10 lần     |
| 10000                 | Tối đa          | Lâu hơn 100 lần    |

**Dung lượng bộ nhớ của thống kê:**
- Mỗi bucket histogram: ~24 byte
- Với statistics_target = 100: ~2.4 KB mỗi cột
- Với 1000: ~24 KB mỗi cột
- Ảnh hưởng đến RAM: tối thiểu

### Kinh nghiệm Production

**Tình huống thực tế #1: Data Skew giết chết hiệu năng**
- Nền tảng ghi log: 500 triệu bản ghi
- Bảng: `level` (DEBUG: 80%, INFO: 15%, ERROR: 5%)
- Vấn đề: Các truy vấn ERROR bị chậm
- Nguyên nhân: statistics_target = 100, danh sách MCV không bao phủ hết tất cả các level
- Giải pháp:
  ```sql
  ALTER TABLE logs ALTER COLUMN level SET STATISTICS 1000;
  ANALYZE logs;
  ```
- Kết quả: Planner ước tính selectivity chính xác, Index Scan được dùng cho ERROR

**Tình huống thực tế #2: Correlated Columns (Các cột có tương quan)**
- E-commerce: đơn hàng theo `(country, city)`
- Vấn đề: Planner ước tính sai lệch 2 bậc độ lớn
- Nguyên nhân: city phụ thuộc nhiều vào country (Moscow chỉ có ở Nga)
- Giải pháp:
  ```sql
  CREATE STATISTICS s_country_city (ndistinct, dependencies)
  ON country, city FROM orders;
  ANALYZE orders;
  ```
- Kết quả: Việc ước tính số dòng trở nên chính xác, planner chọn đúng Join

### Giám sát (Monitoring)

```sql
-- 1. Kiểm tra độ mới của thống kê
SELECT
    relname,
    last_analyze,
    last_autoanalyze,
    n_mod_since_analyze,
    CASE
        WHEN n_mod_since_analyze > 100000 THEN 'CẦN ANALYZE'
        ELSE 'OK'
    END as status
FROM pg_stat_user_tables
ORDER BY n_mod_since_analyze DESC;

-- 2. Kiểm tra correlation
SELECT
    attname,
    ROUND(correlation::numeric, 3) as correlation,
    CASE
        WHEN ABS(correlation) < 0.3 THEN 'THẤP - Random I/O'
        WHEN ABS(correlation) < 0.7 THEN 'TRUNG BÌNH'
        ELSE 'CAO - Sequential I/O'
    END as assessment
FROM pg_stats
WHERE tablename = 'orders'
ORDER BY ABS(correlation) ASC;

-- 3. Kiểm tra n_distinct
SELECT
    attname,
    n_distinct,
    CASE
        WHEN n_distinct < 0 THEN 'Cao (' || ABS(n_distinct) * 100 || '%)'
        WHEN n_distinct < 100 THEN 'Thấp'
        WHEN n_distinct < 10000 THEN 'Trung bình'
        ELSE 'Cao'
    END as cardinality
FROM pg_stats
WHERE tablename = 'users';

-- 4. Kiểm tra thống kê mở rộng
SELECT
    stxname,
    stxkeys::regclass[],
    stxndistinct,
    stxdependencies
FROM pg_statistic_ext;
```

### Best Practices (Thực hành tốt nhất)

1. **Giám sát `n_mod_since_analyze`** — nếu > 10% của bảng, hãy chạy ANALYZE
2. **Tăng `statistics_target`** cho các cột có phân bố bất thường
3. **Sử dụng Extended Statistics** cho các cột có tương quan
4. **Kiểm tra correlation** — < 0.3 nghĩa là Random I/O
5. **Đừng quên chạy ANALYZE** sau khi bulk insert/delete
6. **Danh sách MCV** nên bao phủ > 80% dữ liệu để lập kế hoạch chính xác

### Tóm tắt cho Senior

- Cardinality là một **tham số đầu vào quan trọng** cho bộ tối ưu hóa (optimizer)
- **n_distinct**, **MCV**, **histogram**, **correlation** — 4 trụ cột của thống kê
- **Data Skew** — nguyên nhân phổ biến gây ra plan sai; hãy kiểm tra MCV
- **Extended Statistics** (PG 10+) giải quyết vấn đề các cột có tương quan
- **correlation < 0.3** → Random I/O → nên cân nhắc dùng CLUSTER
- **statistics_target** — cân bằng giữa độ chính xác và thời gian ANALYZE
- Thường xuyên kiểm tra `pg_stats` và `pg_statistic_ext`

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Cardinality = số lượng giá trị duy nhất; Selectivity = cardinality / tổng số dòng
- n_distinct: `-1` = 100% duy nhất, `500` = chính xác 500 giá trị duy nhất
- MCV (Most Common Values): các giá trị xuất hiện nhiều nhất + tần suất — dành cho dữ liệu bị lệch (skewed)
- Correlation: `-1..1` — thứ tự vật lý khớp với thứ tự logic đến mức nào
- correlation = 0 → Random I/O (hỗn loạn trên đĩa), correlation = 1 → Sequential I/O
- Extended Statistics (PG 10+): `dependencies`, `ndistinct`, `mcv` cho các cột có tương quan
- statistics_target = 100 (mặc định), 1000 — cho các cột bị lệch (ANALYZE lâu hơn 10 lần)

**Các câu hỏi phụ thường gặp:**
- "Tại sao index trên status (ACTIVE/PENDING) không được sử dụng?" → Cardinality thấp, Seq Scan nhanh hơn
- "Điều gì xảy ra nếu statistics_target quá thấp?" → Planner ước tính sai số dòng
- "Làm sao để giải quyết vấn đề các cột có tương quan (country, city)?" → `CREATE STATISTICS ... (dependencies)`
- "correlation = 0.05 có nghĩa là gì?" → Thứ tự gần như hỗn loạn → cần CLUSTER hoặc index mới

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "Một index trên trường chỉ có 2 giá trị (Nam/Nữ) sẽ tăng tốc tìm kiếm" (Seq Scan vẫn nhanh hơn)
- ❌ "n_distinct = -1 nghĩa là không có giá trị duy nhất" (ngược lại — 100% duy nhất!)
- ❌ "statistics_target không ảnh hưởng đến hiệu năng" (nó ảnh hưởng đến thời gian ANALYZE và độ chính xác của plan)
