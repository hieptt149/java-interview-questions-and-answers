# What is DLQ (Dead Letter Queue) in Kafka (DLQ (Dead Letter Queue) trong Kafka là gì)

## Junior Level

### Định Nghĩa Đơn Giản

**DLQ (Dead Letter Queue)** — một topic Kafka đặc biệt nơi các message không thể xử lý sau nhiều lần thử được gửi đến. Đó là một "bộ cô lập" cho dữ liệu có vấn đề.

### Phép So Sánh

Hãy tưởng tượng một nhà máy gói quà. Một công nhân lấy một món quà và cố gắng gói nó. Nếu món quà bị hỏng (vỡ, nứt):
1. Thử lại (retry)
2. Nếu sau 3 lần thử vẫn hỏng — đặt nó vào giỏ "hàng lỗi" (DLQ)
3. Tiếp tục gói các món quà tiếp theo

Băng chuyền không dừng lại, và các món quà lỗi có thể được kiểm tra và sửa sau.

### Ví Dụ Với Spring Kafka

```java
@Configuration
public class KafkaConfig {

    @Bean
    public ConcurrentKafkaListenerContainerFactory<String, String> kafkaListenerContainerFactory(
            ConsumerFactory<String, String> consumerFactory,
            KafkaTemplate<String, String> kafkaTemplate) {

        var factory = new ConcurrentKafkaListenerContainerFactory<String, String>();
        factory.setConsumerFactory(consumerFactory);

        // Cấu hình DLQ
        factory.setCommonErrorHandler(new DefaultErrorHandler(
            new DeadLetterPublishingRecoverer(kafkaTemplate),
            new FixedBackOff(1000L, 3)  // 3 retry, cách nhau 1 giây
        ));

        return factory;
    }
}
```

### Cái Gì Đi Đến DLQ

- Dữ liệu hỏng (JSON không hợp lệ, không khớp schema)
- Không thể xử lý (cơ sở dữ liệu không khả dụng > số retry tối đa)
- Vi phạm quy tắc kinh doanh (giá âm, email không hợp lệ)
- Lỗi dịch vụ bên ngoài (API bị rate limit, timeout)

### Khi Nào Dùng

- **Dữ liệu quan trọng** — các message không thể bị mất
- **Cần phân tích** — hiểu tại sao việc xử lý thất bại
- **Compliance** — audit và khả năng truy vết
- **Production** — luôn có một kế hoạch DLQ

### Làm Giàu Message DLQ

Chỉ đơn giản gửi message gốc đến DLQ là không đủ. Context phải được thêm vào:

```java
public class DLQEnricher {

    public ProducerRecord<String, String> enrichForDLQ(
            ConsumerRecord<String, String> original,
            Exception error) {

        ProducerRecord<String, String> dlqRecord = new ProducerRecord<>(
            original.topic() + "-dlq",  // orders → orders-dlq
            original.key(),
            original.value()
        );

        // Metadata để debug
        dlqRecord.headers().add("x-original-topic", original.topic().getBytes(StandardCharsets.UTF_8));
        dlqRecord.headers().add("x-original-partition", String.valueOf(original.partition()).getBytes());
        dlqRecord.headers().add("x-original-offset", String.valueOf(original.offset()).getBytes());
        dlqRecord.headers().add("x-original-timestamp", String.valueOf(original.timestamp()).getBytes());
        dlqRecord.headers().add("x-consumer-group", "order-service".getBytes());
        dlqRecord.headers().add("x-error-message", error.getMessage().getBytes(StandardCharsets.UTF_8));
        dlqRecord.headers().add("x-error-stacktrace", getStackTrace(error).getBytes(StandardCharsets.UTF_8));
        dlqRecord.headers().add("x-retry-count", "3".getBytes());
        dlqRecord.headers().add("x-dlq-timestamp", String.valueOf(System.currentTimeMillis()).getBytes());

        return dlqRecord;
    }
}
```

### Các Pattern DLQ

| Pattern           | Mô tả                                | Khi Nào Dùng                    |
| ----------------- | ------------------------------------------ | ------------------------------ |
| **Single DLQ**    | Một topic DLQ duy nhất cho tất cả các lỗi               | Các hệ thống đơn giản                 |
| **Per-topic DLQ** | `topic-dlq` cho mỗi topic                 | Trách nhiệm team khác nhau|
| **Per-error DLQ** | `topic-dlq-validation`, `topic-dlq-timeout`| Phân tích chi tiết              |
| **Multi-level DLQ**| DLQ → DLQ2 → Xem xét thủ công               | Các hệ thống compliance cao        |

### DLQ Consumer — Xử Lý DLQ

```java
// DLQ Consumer — đọc DLQ và quyết định phải làm gì
@KafkaListener(topics = "orders-dlq", groupId = "dlq-handler")
public void handleDLQ(ConsumerRecord<String, String> record) {
    String originalTopic = getHeader(record, "x-original-topic");
    String errorMessage = getHeader(record, "x-error-message");
    String stacktrace = getHeader(record, "x-error-stacktrace");

    // Phân loại lỗi
    if (errorMessage.contains("Timeout")) {
        // Lỗi tạm thời — retry
        retryMessage(record);
    } else if (errorMessage.contains("ConstraintViolation")) {
        // Vấn đề dữ liệu — xem xét thủ công
        sendToManualReview(record);
    } else if (errorMessage.contains("Schema")) {
        // Không khớp schema — sửa producer
        alertProducerTeam(record);
    } else {
        // Không xác định — xem xét thủ công
        sendToManualReview(record);
    }
}
```

### Bảng Các Lỗi Thường Gặp

| Lỗi                   | Triệu chứng                          | Hậu quả                      | Giải pháp                    |
| ----------------------- | --------------------------------- | ---------------------------------- | --------------------------- |
| Không có DLQ             | Poison pill chặn consumer       | Consumer lag ∞, pipeline đình trệ    | Thêm DLQ                     |
| DLQ không có monitoring  | DLQ tăng vô hạn            | Đầy đĩa, bỏ lỡ lỗi          | Alert khi kích thước DLQ           |
| DLQ không có metadata    | Không thể debug               | Hàng giờ dành cho điều tra          | Làm giàu header              |
| DLQ = topic gốc    | Vòng lặp vô hạn                     | Message bật qua lại giữa các topic     | Topic DLQ riêng biệt              |
| DLQ không có retention   | DLQ chiếm dụng đĩa vĩnh viễn                | Đầy đĩa                         | Cấu hình retention           |
| Không có DLQ consumer    | Các message DLQ tích lũy          | Không phục hồi tự động             | DLQ consumer để auto-retry |

### Khi Nào KHÔNG Nên Dùng DLQ

- **Dữ liệu không thể khôi phục** — log, metrics có thể bị mất
- **Các thao tác idempotent** — retry an toàn để lặp lại vô hạn
- **Môi trường test** — có thể đơn giản restart
- **Khối lượng rất thấp** (< 10 msg/phút) — đơn giản hơn để alert và sửa thủ công
- Với các thao tác hoàn toàn idempotent với retry tự động, DLQ có thể thừa thãi —
  alerting khi hết retry là đủ.

#### DLQ Trong Spring Kafka — DeadLetterPublishingRecoverer

```java
// Cài đặt nội bộ
public class DeadLetterPublishingRecoverer implements ConsumerRecordRecoverer {

    private final Function<ConsumerRecord<?, ?>, TopicPartition> destinationResolver;
    private final KafkaTemplate<Object, Object> template;

    @Override
    public void accept(ConsumerRecord<?, ?> record, Exception exception) {
        // 1. Xác định topic DLQ
        TopicPartition dest = destinationResolver.apply(record);

        // 2. Tạo record đã làm giàu
        ProducerRecord<Object, Object> dlqRecord = createProducerRecord(record, exception);

        // 3. Gửi đến DLQ (sync để đảm bảo delivery)
        template.send(dlqRecord).get();  // Chặn!

        // 4. Log
        log.error("Sent to DLQ: topic={}, partition={}, offset={}",
                  record.topic(), record.partition(), record.offset());
    }

    // Làm giàu header
    private ProducerRecord<Object, Object> createProducerRecord(
            ConsumerRecord<?, ?> record, Exception exception) {
        // Sao chép key, value
        // Thêm các header:
        //   - KafkaHeaders.DLT_EXCEPTION_FQCN (tên class exception)
        //   - KafkaHeaders.DLT_EXCEPTION_MESSAGE (message exception)
        //   - KafkaHeaders.DLT_ORIGINAL_TOPIC
        //   - KafkaHeaders.DLT_ORIGINAL_PARTITION
        //   - KafkaHeaders.DLT_ORIGINAL_OFFSET
        //   - KafkaHeaders.DLT_ORIGINAL_TIMESTAMP
    }
}
```

#### Kafka Streams — Branching Cho DLQ

```java
// Kafka Streams không có DLQ tích hợp sẵn
// Triển khai qua branching

KStream<String, String> orders = builder.stream("orders");

// Tách: hợp lệ vs không hợp lệ
KStream<String, String>[] branches = orders.branch(
    (key, value) -> isValid(value),   // stream hợp lệ
    (key, value) -> !isValid(value)   // không hợp lệ → DLQ
);

// Hợp lệ → xử lý
branches[0].process(() -> orderProcessor);

// Không hợp lệ → topic DLQ
branches[1].mapValues(value -> enrichWithMetadata(value, "validation-error"))
            .to("orders-dlq");
```

### Đánh Đổi (Trade-offs)

| Khía cạnh               | Không Có DLQ                     | Có DLQ              |
| -------------------- | -------------------------------- | ---------------------- |
| An toàn dữ liệu          | Thấp (mất dữ liệu poison pill)     | Cao                  |
| Tính khả dụng hệ thống  | Thấp (đình trệ khi lỗi)            | Cao                  |
| Độ phức tạp           | Thấp                             | Trung bình                  |
| Thời gian debug        | Hàng giờ-ngày                      | Vài phút                 |
| Overhead lưu trữ     | 0%                              | 0.1–1% (các message DLQ) |
| Overhead vận hành | Cao (điều tra thủ công)     | Thấp (tự động hóa)          |

### Edge Case

**1. DLQ Overflow — Khi Chính DLQ Trở Thành Vấn Đề:**

```
Kịch bản:
  Bug producer → tất cả các message đều không hợp lệ
  100K message/phút → DLQ
  Topic DLQ: replication factor 3, retention 7 ngày
  Lưu trữ DLQ: 100K × 60 × 24 × 7 × 1KB = 10GB/ngày

Vấn đề: DLQ lấp đầy đĩa nhanh hơn topic chính!

Giải quyết:
  1. DLQ retention.ms = 86400000 (1 ngày, không phải 7)
  2. DLQ consumer để drain nhanh
  3. Alert khi tỷ lệ DLQ > ngưỡng
  4. Circuit breaker: dừng gửi đến DLQ, chỉ alert
```

**2. Thứ Tự Và Tính Nhân Quả DLQ:**

```
Kịch bản:
  Partition 0: order-1 (thành công), order-2 (DLQ), order-3 (thành công)
  order-3 phụ thuộc vào order-2 (cập nhật sau khi tạo)
  order-2 trong DLQ → order-3 được xử lý nhưng thất bại (không có order-2)

Vấn đề: Tính nhân quả bị phá vỡ — xử lý downstream phụ thuộc vào message trong DLQ

Giải quyết:
  1. Pattern Saga: order-3 kiểm tra điều kiện tiên quyết
  2. Hành động bù trừ: nếu order-2 trong DLQ → rollback order-1
  3. Phân vùng theo correlation key — các message liên quan trong cùng partition
```

**3. DLQ Replay — Gửi Lại Từ DLQ:**

```java
// DLQ replay consumer
@KafkaListener(topics = "orders-dlq", groupId = "dlq-replayer")
public void replay(ConsumerRecord<String, String> record) {
    String errorMessage = getHeader(record, "x-error-message");
    String originalTopic = getHeader(record, "x-original-topic");

    if (errorMessage.contains("Timeout") && isDatabaseHealthy()) {
        // Retry — lỗi là tạm thời
        originalProducer.send(new ProducerRecord<>(
            originalTopic, record.key(), record.value()
        ));
        log.info("Replayed from DLQ: {}", record.offset());
    } else {
        // Không thể retry — xem xét thủ công
        log.warn("Non-replayable DLQ message: {}", record.offset());
    }
}
// Khi lỗi lặp lại — gửi đến hàng đợi manual-review, KHÔNG retry vô hạn.
// Pattern DLQ-cho-DLQ: sau N retry → một DLQ thứ hai → can thiệp thủ công.
```

**4. DLQ Và Exactly-Once Semantics:**

```
Vấn đề:
  Consumer đọc message → lỗi → gửi đến DLQ → commit offset
  Consumer crash SAU khi gửi DLQ, TRƯỚC khi commit
  Khi restart: message được đọc lại → gửi đến DLQ lần nữa → trùng lặp trong DLQ

Giải quyết:
  1. Producer DLQ transactional:
     transaction {
       process(record);
       if (error) dlqProducer.send(dlqRecord);
       consumer.commitSync();
     }
  2. Key deduplication DLQ = topic gốc + partition + offset
  3. Producer DLQ idempotent
```

**5. Cô Lập DLQ Multi-tenant:**

```
Kịch bản:
  Nền tảng SaaS, 100 tenant, các topic Kafka dùng chung
  Lỗi Tenant A → DLQ
  Lỗi Tenant B → cùng DLQ
  Tenant C thấy các message DLQ từ A và B (rò rỉ dữ liệu!)

Giải quyết:
  Các topic DLQ theo tenant:
    orders-tenant-a-dlq
    orders-tenant-b-dlq
  Hoặc DLQ với header tenant-id + ACL
```

### Hiệu Năng (Các Con Số Production)

| Pattern DLQ       | Overhead     | Tác Động Throughput  | Tác Động Latency | Lưu Trữ   |
| ----------------- | ------------ | ------------------ | -------------- | --------- |
| Không có DLQ            | 0%           | 0%                 | 0ms            | 0         |
| Gửi DLQ sync     | +10–30ms/msg | -5%                | +20ms          | 0.1–1%    |
| Gửi DLQ async    | +1ms         | -1%                | +2ms           | 0.1–1%    |
| DLQ + làm giàu  | +15–40ms/msg | -8%                | +30ms          | 0.5–2%    |
| DLQ transactional | +50ms        | -15%               | +50ms          | 0.1–1%    |

### Câu Chuyện Production Thực Tế

**Tình huống:** FinTech, xử lý giao dịch. Một DLQ tồn tại nhưng không được giám sát.

**Vấn đề:** Phát hiện rằng topic DLQ đã tăng lên 50M message trong 3 tháng. 50M giao dịch $10–500 mỗi cái không được xử lý. Rủi ro tài chính tiềm ẩn: $5M+.

**Điều tra:**
- DLQ consumer đã tồn tại nhưng crash 3 tháng trước
- Không ai nhận thấy (không có alerting)
- Các message DLQ tích lũy mà không được xử lý
- Retention = -1 (vô hạn) → rủi ro đầy đĩa
- Nguyên nhân gốc rễ: thay đổi schema producer, các message validate trong DLQ
- 50M message = các lỗi vi phạm schema

**Giải quyết:**
1. **Ngay lập tức:** Alert khi kích thước DLQ > 1000 message
2. **Ngắn hạn:** Restart DLQ consumer + replay cho các lỗi có thể retry
3. **Trung hạn:** Validate schema ở phía producer (phòng ngừa)
4. **Dài hạn:** Tự động phân loại DLQ + auto-retry cho các lỗi tạm thời
5. **Vận hành:** Dashboard DLQ, chế độ trực on-call để xem xét DLQ

**Post-mortem:**
- DLQ không có monitoring = không có DLQ (cảm giác an toàn giả)
- Chính sách retention DLQ là bắt buộc
- Schema registry để validate producer
- Quy trình xem xét DLQ thường xuyên (hàng ngày)

### Các Thực Hành Tốt Nhất Cho Highload

```
✅ Topic DLQ riêng biệt (đừng dùng lại topic gốc)
✅ Làm giàu DLQ với metadata (topic, partition, offset, exception)
✅ Chính sách retention DLQ (1–7 ngày, không vô hạn)
✅ Alert cho các message DLQ (không bao giờ DLQ âm thầm)
✅ DLQ consumer để retry/replay tự động
✅ Dashboard DLQ (số lượng message, loại lỗi, tuổi)
✅ Validate schema ở phía producer (ngăn ngừa poison pill)
✅ Định tuyến DLQ theo loại lỗi để phân loại tự động
✅ Producer DLQ idempotent (ngăn các message DLQ trùng lặp)
✅ Circuit breaker trên tỷ lệ gửi DLQ (ngăn DLQ overflow)

❌ Không có DLQ trong production
❌ DLQ không có monitoring/alerting
❌ DLQ không có chính sách retention (đầy đĩa)
❌ DLQ = topic gốc (vòng lặp vô hạn)
❌ Không có DLQ consumer (các message tích lũy vĩnh viễn)
❌ Không có metadata trong DLQ (không thể debug)
❌ DLQ không có làm giàu (mất context)
```

### Các Quyết Định Kiến Trúc

1. **DLQ — không chỉ là một topic, mà là một quy trình** — producer → DLQ → consumer → replay → sửa
2. **Làm giàu là quan trọng** — không có metadata, DLQ vô dụng cho việc debug
3. **Tự động phân loại** — phân loại các lỗi DLQ để xử lý tự động
4. **Phòng ngừa > chữa trị** — validate schema, kiểm tra phía producer
5. **Retention DLQ** — cân bằng giữa nhu cầu debug và mức sử dụng đĩa

### Tóm Tắt Cho Senior

- DLQ — chính sách bảo hiểm chống lại poison pill và mất dữ liệu
- DLQ không có monitoring = không có DLQ (cảm giác an toàn giả)
- Các header làm giàu — quan trọng cho việc debug và khả năng replay
- DLQ consumer cần thiết cho khả năng retry/replay tự động
- Định tuyến theo lỗi → phân loại tự động → giảm xem xét thủ công
- Validate schema ở producer — cách tốt nhất để giảm khối lượng DLQ
- Chính sách retention DLQ là bắt buộc để quản lý đĩa
- DLQ transactional cho ngữ nghĩa DLQ exactly-once
- Ở highload: tỷ lệ DLQ có thể trở thành vấn đề — cần circuit breaker
- Dashboard DLQ + quy trình on-call — cần thiết cho vận hành

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- DLQ — một topic đặc biệt cho các message không được xử lý sau retry tối đa
- Làm giàu DLQ: topic gốc, partition, offset, message exception, stacktrace, timestamp
- Các pattern: Single DLQ, Per-topic DLQ (`topic-dlq`), Per-error DLQ, Multi-level DLQ
- DLQ consumer: đọc DLQ, phân loại lỗi, retry hoặc xem xét thủ công
- Chính sách retention DLQ (1-7 ngày) — không có nó, đầy đĩa là chắc chắn
- DLQ không có monitoring = không có DLQ (cảm giác an toàn giả)
- Producer DLQ transactional ngăn các message DLQ trùng lặp

**Các câu hỏi phụ thường gặp:**
- *Tại sao làm giàu các message DLQ?* — Không có metadata, việc debug và replay là không thể.
- *Điều gì nếu producer DLQ cũng thất bại?* — Giới hạn retry → hàng đợi manual-review.
