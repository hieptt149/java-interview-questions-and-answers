# What is exception chaining? (Exception chaining là gì?)

## Junior Level

### Định nghĩa

**Exception chaining** - một cơ chế liên kết nhiều exception với nhau, trong đó mỗi exception trỏ tới `cause` (nguyên nhân) của nó.

### Ví dụ

```java
try {
    // Code có thể ném SQLException
    connection.executeQuery("SELECT * FROM users");
} catch (SQLException e) {
    // Bọc trong exception của chúng ta, giữ lại cause
    throw new DataAccessException("Failed to query database", e);
    //                                              cause ^
}
```

### Cách lấy cause

```java
try {
    service.process();
} catch (DataAccessException e) {
    Throwable cause = e.getCause(); // SQLException gốc
    System.out.println("Root cause: " + cause.getMessage());
}
```

### Tại sao cần nó

- **Giữ stack trace** - lỗi gốc không bị mất
- **Thêm ngữ cảnh** - mỗi tầng thêm thông tin của riêng nó
- **Ẩn chi tiết** - client không phụ thuộc vào `SQLException`

### Khi nào KHÔNG nên dùng exception chaining

1. **Validation đầu vào** - `IllegalArgumentException("age must be positive")` không cần một cause
2. **Lỗi của lập trình viên** - `NullPointerException` không được bọc, nó được sửa
3. **Lồng nhau sâu 10+** - stack trace trở nên không đọc được, hãy dùng cắt bớt (truncation)
4. **Trong các signal exception** - các signal exception nhẹ không có ngữ cảnh (`FastException`)
5. **Ở biên của microservice** - truyền DTO với mã lỗi, đừng serialize toàn bộ chuỗi

## Middle Level

### Trường cause trong Throwable

Bên trong `Throwable` có một trường `private Throwable cause = this;`.

Giá trị mặc định `this` nghĩa là cause chưa được đặt.

Phương thức `initCause(Throwable)` hoặc constructor `super(message, cause)` đặt trường này.

**Hạn chế:** cause chỉ có thể được đặt **một lần**. `initCause` lặp lại -> `IllegalStateException`.

### Các tầng kiến trúc của chuỗi

```
Tầng Web:       catch (DataAccessException e) -> 500 Internal Server Error
                     ^
Tầng Service:   catch (SQLException e) -> throw new DataAccessException("...", e)
                     ^
Tầng DAO:       catch (SQLException e) -> lan truyền đi tiếp
                     ^
JDBC Driver:    ném SQLException
```

Ở mỗi bước `cause` được giữ lại, nên trong log bạn có thể lần theo tới nguyên nhân thực sự.

### Tìm Root Cause

```java
// Apache Commons Lang
Throwable root = ExceptionUtils.getRootCause(e);

// Guava
Throwable root = Throwables.getRootCause(e);

// Thủ công
Throwable t = e;
while (t.getCause() != null) {
    t = t.getCause();
}
// t - root cause
```

### Suppressed so với Cause

- **Cause** - "tại sao tôi lỗi" (nguyên nhân gốc)
- **Suppressed** - "cái gì khác cũng sai trong lúc tôi đang lỗi" (thường là khi đóng resource)

## Senior Level

### Stack Trace Bloat (stack trace phình to)

Các chuỗi sâu (10+ tầng) tạo ra các log văn bản khổng lồ. Chúng tải cho I/O và chiếm dung lượng đĩa.

**Tối ưu hóa:** khi ghi log, hãy cấu hình các giới hạn độ sâu stack hoặc dùng log JSON, nơi stack trace là một trường riêng có thể lập chỉ mục.

### Cấp phát Object và GC

Mỗi mắt xích trong chuỗi - một object trong heap. Trong các hệ thống Highload, các lỗi thường xuyên với các chuỗi sâu có thể gây tải cho GC.

### Phụ thuộc vòng (Circular Dependency)

JVM ngăn chuỗi bị vòng lặp:

```java
e1.initCause(e2);
e2.initCause(e1); // IllegalArgumentException
```

### Serialization

Khi truyền một chuỗi qua mạng (RMI/gRPC), tất cả các mắt xích phải serializable được. Nếu một trong các exception lồng nhau là một class tùy chỉnh mà client không có - việc deserialize toàn bộ chuỗi thất bại.

**Giải pháp:** ở biên của microservice, chỉ truyền DTO với message và mã lỗi.

### Phân tích Log

Đảm bảo định dạng log bao gồm `%ex` (Logback) hoặc một marker tương tự tiết lộ `cause`. Một số cấu hình cũ chỉ ghi message của exception trên cùng.

### Chẩn đoán

- **IntelliJ Debugger** - mở rộng node `cause` để thấy toàn bộ cây lỗi
- **ELK/Splunk** - `cause` như một trường riêng để lập chỉ mục
- **Metric** - đếm độ sâu chuỗi qua `getSuppressed().length`
- **Root Cause Tracking** - mỗi mắt xích của chuỗi nên được ghi log kèm Trace ID

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Exception chaining - cơ chế liên kết các exception qua `cause` (nguyên nhân)
- `Throwable` lưu `private Throwable cause = this` - đặt qua constructor hoặc `initCause()`
- Cause chỉ có thể được đặt một lần - `initCause()` lặp lại -> `IllegalStateException`
- Mỗi tầng kiến trúc thêm ngữ cảnh của riêng nó: DAO -> Service -> Controller
- `getCause()` lấy exception gốc, `getRootCause()` - nguyên nhân gốc
- Cause so với Suppressed: cause = "tại sao tôi lỗi", suppressed = "cái gì khác cũng sai trong lúc tôi đang lỗi"
- Các chuỗi sâu (10+) tạo Stack Trace Bloat - log khổng lồ, tải cho GC

**Các câu hỏi phụ thường gặp:**
- **Cách tìm root cause?** - Vòng lặp `while (t.getCause() != null) t = t.getCause()` hoặc `ExceptionUtils.getRootCause(e)`
- **Cause khác suppressed như thế nào?** - Cause - nguyên nhân gốc, suppressed - các lỗi song song (thường là khi close)
- **Có thể làm cho một chuỗi bị vòng lặp không?** - Không, JVM ngăn điều đó: `e1.initCause(e2); e2.initCause(e1)` -> `IllegalArgumentException`
- **Các vấn đề serialization với chuỗi?** - Tất cả các mắt xích phải Serializable; ở biên của microservice hãy truyền DTO

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Có thể gọi `initCause()` nhiều lần" - chỉ một lần
- "Chaining và suppressed giống nhau" - không, cause = nguyên nhân gốc, suppressed = các lỗi song song
- "Một chuỗi 20 exception là ổn" - Stack Trace Bloat, tải cho I/O và GC
- "Tôi serialize toàn bộ chuỗi qua mạng" - DTO với mã lỗi thay cho serialization
