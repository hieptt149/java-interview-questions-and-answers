# What are Design Patterns? (Design Pattern là gì?)

## Junior Level

**Design pattern (mẫu thiết kế)** là các giải pháp được ghi chép lại trong sách và bài báo, đã được áp dụng nhiều lần trong các dự án thực tế và được chứng minh là hiệu quả.

**Tại sao cần thiết:** Không cần phải thiết kế một giải pháp từ đầu. Tiết kiệm 2-5 giờ cho mỗi công việc vì pattern đã được kiểm chứng và được các lập trình viên khác hiểu rõ.

**Ví dụ minh họa đơn giản:** Hãy tưởng tượng bạn đang xây một ngôi nhà. Bạn không cần phải phát minh lại cách xây mái nhà hay móng nhà mỗi lần — đã có những bản thiết kế tiêu chuẩn đã được chứng minh là hiệu quả. Pattern chính là những "bản thiết kế tiêu chuẩn" như vậy dành cho code.

**Tại sao cần thiết:**
- Không cần phải phát minh lại bánh xe (reinvent the wheel)
- Sử dụng các giải pháp đã hoạt động tốt
- Giao tiếp với đồng nghiệp bằng một ngôn ngữ chung ("ở đây ta cần một Singleton")

**Ví dụ:**
```java
// Pattern Singleton — chỉ có một instance (thực thể) duy nhất của class
public class Logger {
    private static Logger instance = new Logger();
    private Logger() {}
    public static Logger getInstance() { return instance; }

    public void log(String message) {
        System.out.println(message);
    }
}

// Cách sử dụng
Logger.getInstance().log("Hello!");
```

**Khi nào nên sử dụng:**
- Khi gặp phải một vấn đề điển hình
- Khi code trở nên phức tạp và khó hiểu
- Khi bạn cần làm cho code rõ ràng hơn đối với các lập trình viên khác

## Middle Level

### Các cấp độ của Pattern

| Cấp độ              | Ví dụ                             | Nơi áp dụng         |
| ------------------ | ------------------------------------ | ---------------------- |
| **Language Idioms (Thành ngữ ngôn ngữ)** | Try-with-resources, Optional, Streams | Cú pháp Java           |
| **GoF Patterns**   | Strategy, Decorator, Observer, Factory | Tương tác giữa các class     |
GoF (Gang of Four — Gamma, Helm, Johnson, Vlissides, tác giả của cuốn "Design Patterns", 1994).
| **Enterprise**     | Repository, Unit of Work, Data Mapper | Xử lý dữ liệu        |
| **Cloud/Distributed (Phân tán)** | Circuit Breaker, Saga, CQRS       | Microservices         |

### Các nhóm chính

**1. Creational (Khởi tạo)**
- Giúp tạo đối tượng
- Ví dụ: Singleton, Factory, Builder
- **Tại sao:** Che giấu quá trình tạo đối tượng

**2. Structural (Cấu trúc)**
- Giúp kết hợp các class và đối tượng
- Ví dụ: Adapter, Decorator, Proxy
- **Tại sao:** Làm cho các interface khác nhau tương thích với nhau

**3. Behavioral (Hành vi)**
- Mô tả sự tương tác giữa các đối tượng
- Ví dụ: Strategy, Observer, Chain of Responsibility
- **Tại sao:** Quản lý các thuật toán và luồng dữ liệu

### Pattern trong Java hiện đại

Nhiều pattern kinh điển đã trở nên đơn giản hơn với Java 8-21:

```java
// Strategy kinh điển (nhiều class)
public interface PaymentStrategy { void pay(); }
public class CreditCardStrategy implements PaymentStrategy { ... }
public class PayPalStrategy implements PaymentStrategy { ... }

// Java hiện đại (lambda)
public void processPayment(UnaryOperator<BigDecimal> paymentStrategy) {
    BigDecimal result = paymentStrategy.apply(amount);
}

// Cách sử dụng
processPayment(amount -> amount.subtract(discount));
```

### Các lỗi thường gặp

1. **Golden Hammer (Búa vàng)**
   ```java
   // Sử dụng một pattern ở mọi nơi chỉ vì ta biết nó
   // Tạo ra Abstract Factory cho một đối tượng duy nhất

   // Chỉ sử dụng khi thực sự cần thiết
   // if-else đơn giản còn tốt hơn là trừu tượng hóa không cần thiết
   ```

2. **Overengineering (Thiết kế thừa)**
   - Quá nhiều tầng trừu tượng
   - Khó đọc và khó debug
   - Stack trace với 50 tầng

3. **Cargo Cult (Bắt chước mù quáng)**
   - Sao chép mù quáng mà không hiểu
   - Triển khai Cloneable thay vì dùng copy constructor

### Khi nào KHÔNG nên sử dụng pattern

1. **Các ứng dụng CRUD đơn giản** — code trực tiếp dễ đọc hơn là trừu tượng hóa
2. **Các dự án prototype cuối tuần** — tốc độ quan trọng hơn kiến trúc
3. **Khi pattern không giải quyết được vấn đề của bạn** — đừng ép công việc phải khớp với pattern

## Senior Level

### Pattern như một hợp đồng kiến trúc (Architectural Contract)

Ở mức độ sâu hơn, một pattern định nghĩa:

1. **Phân tách trách nhiệm (Separation of Concerns)**
   - Đối tượng nào chịu trách nhiệm về cái gì
   - Ranh giới rõ ràng giữa các thành phần

2. **Interface tương tác**
   - Giảm thiểu sự phụ thuộc (Loose Coupling)
   - Các hợp đồng giữa các module

3. **Điểm mở rộng (Extension Points)**
   - Nơi hệ thống có thể được mở rộng mà không cần sửa đổi code hiện có
   - Nguyên lý Open/Closed trong thực tiễn

### Sự tiến hóa của Pattern trong Java hiện đại (8-21+)

**Strategy / Command → Lambda:**
```java
// Trước: 10+ class
// Sau: Function<T, R>, Consumer<T>, Predicate<T>
```

**Template Method → Composition (Kết hợp):**
```java
// Thay vì kế thừa — truyền lambda vào constructor
public class Processor {
    private final Function<Data, Result> transformer;

    public Processor(Function<Data, Result> transformer) {
        this.transformer = transformer;
    }
}
```

**Singleton / Prototype → DI Container:**
```java
// Spring quản lý vòng đời (lifecycle)
@Component  // Mặc định là Singleton scope
public class UserService { }

@Scope("prototype")
public class OrderProcessor { }
```

**Proxy → Spring AOP:**
```java
// @Transactional, @Cacheable — tất cả đều là Proxy ở bên dưới
// JDK Dynamic Proxy hoặc CGLIB ở bên dưới
@Transactional
public void processOrder() { }
```

### Đánh đổi trong kiến trúc (Architectural Trade-offs)

**Những gì ta đạt được:**
- Tính linh hoạt và khả năng mở rộng
- Khả năng kiểm thử (testability)
- Sự rõ ràng đối với những ai đã quen thuộc với pattern
- Sự phụ thuộc lỏng lẻo (loose coupling)

**Những gì ta phải đánh đổi:**
- Số lượng class tăng lên
- Nhiều tầng gián tiếp (indirection)
- Độ phức tạp khi debug
- Chi phí phát sinh về hiệu năng (performance overhead)

### Megamorphic Calls và JIT

```java
// Pattern ảnh hưởng đến hiệu năng JVM!

// Monomorphic call (1 cách triển khai) → được inline
PaymentStrategy strategy = new CreditCard();
strategy.pay();  // JIT inline code này → 0 chi phí phát sinh

// Bimorphic call (2 cách triển khai) → vẫn nhanh
// Megamorphic call (>2 cách triển khai) → gọi gián tiếp thông qua vtable
// → Giảm CPU đáng kể có thể đo lường được trong hot path (đường dẫn nóng)!
```

**Tối ưu hóa:**
```java
// Đối với các đường dẫn quan trọng: enum thay vì interface
public enum PaymentType {
    CREDIT_CARD {
        @Override public void pay() { /* code */ }
    },
    PAYPAL {
        @Override public void pay() { /* code */ }
    };
    public abstract void pay();
}
// → JIT tối ưu hóa enum switch tốt hơn
```

### Pattern trong các hệ thống phân tán (Distributed Systems)

**Các pattern Cloud-Native:**
```
Circuit Breaker → khả năng chịu lỗi (fault tolerance)
Saga → các transaction phân tán
Sidecar → hạ tầng đi kèm với service
CQRS → phân tách việc đọc và ghi
Event Sourcing → nhật ký sự kiện thay vì trạng thái
```

**Sự liên kết giữa các Pattern:**
```
Abstract Factory (Creational)
  → trả về Proxy (Structural)
    → thứ bao bọc logic nghiệp vụ
      → được quản lý thông qua Strategy (Behavioral)

Chain of Responsibility (Behavioral)
  → được xây dựng thông qua Builder (Creational)

Facade (Structural)
  → đơn giản hóa interface đến một subsystem (hệ thống con)
    → được quản lý thông qua Strategy (Behavioral)
```

### Nguyên tắc về sự vừa đủ (Sufficiency Principle)

**Pattern tốt nhất là pattern giải quyết được công việc với lượng code tối thiểu:**

```java
// Thiết kế thừa (Overengineering)
public interface MessageValidator { boolean validate(Message m); }
public class EmailValidator implements MessageValidator { ... }
public class PhoneValidator implements MessageValidator { ... }
public class ValidatorFactory { ... }
public class ValidationStrategy { ... }

// Đủ dùng (Sufficient)
public boolean isValid(Message m) {
    return m.getType() == EMAIL
        ? emailRegex.matcher(m.getContent()).matches()
        : phoneRegex.matcher(m.getContent()).matches();
}

// Chỉ cần pattern KHI:
// - Có kế hoạch mở rộng (các loại validation mới)
// - Logic phức tạp trong mỗi nhánh
// - Cần được kiểm thử riêng biệt
```

### Kinh nghiệm Production

**Tình huống thực tế #1: Overengineering giết chết tính dễ đọc**
- Dự án: 15 pattern trong 10,000 dòng code
- Vấn đề: lập trình viên mới mất 2 tuần để onboarding (làm quen)
- Giải pháp: đơn giản hóa còn 5 pattern chính
- Kết quả: onboarding chỉ mất 3 ngày, ít lỗi hơn

**Tình huống thực tế #2: Lạm dụng pattern trong Spring**
- Singleton thủ công thay vì @Component
- Vấn đề: không thể mock trong các bài test
- Giải pháp: ủy quyền (delegate) cho Spring IoC
- Kết quả: khả năng kiểm thử + tính linh hoạt

### Best Practices (Thực hành tốt nhất)

1. **Hiểu biết về các pattern**, nhưng đừng sử dụng chúng một cách không cần thiết
2. **Java hiện đại** đơn giản hóa nhiều pattern (lambda, Record)
3. **DI container** thay thế cho việc dùng Singleton/Prototype/Factory thủ công
4. **Composition > Inheritance (Kết hợp tốt hơn kế thừa)** — linh hoạt hơn và ít mong manh hơn
5. **Sự đơn giản** — nếu if-else là đủ, đừng làm phức tạp thêm
6. **Ghi chép lại (Document)** — tại sao bạn chọn pattern này
7. **Xác minh** — pattern có vi phạm SOLID hay không
8. **Suy nghĩ về JIT** — megamorphic call ảnh hưởng đến CPU

### Tóm tắt cho Senior

- Pattern là một **công cụ để chống lại sự phức tạp**, không phải là mục tiêu
- **Java hiện đại** làm cho nhiều pattern trở nên "vô hình" (lambda, Record)
- **DI Container** — người quản lý Singleton/Factory/Prototype của bạn
- **Đánh đổi:** tính linh hoạt vs tính dễ đọc, khả năng mở rộng vs độ phức tạp
- **Tối ưu hóa JIT:** monomorphic > megamorphic call
- **Nguyên tắc về sự vừa đủ:** pattern tốt nhất = lượng code tối thiểu
- **Các hệ thống phân tán** — các pattern mới (Saga, Circuit Breaker)
- Pattern nên đáp ứng một **nhu cầu thực tế**, không phải nhu cầu lý thuyết

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Pattern là các giải pháp đã được kiểm chứng cho các vấn đề điển hình, tiết kiệm 2-5 giờ cho mỗi công việc
- Ba nhóm: Creational (khởi tạo), Structural (cấu trúc), Behavioral (hành vi)
- GoF (Gang of Four) — Gamma, Helm, Johnson, Vlissides, tác giả của cuốn sách năm 1994
- Java hiện đại (8-21) đơn giản hóa nhiều pattern: lambda thay thế Strategy, DI thay thế Singleton
- Nguyên tắc về sự vừa đủ: pattern tốt nhất = lượng code tối thiểu, nếu if-else là đủ — đừng làm phức tạp thêm
- Overengineering giết chết tính dễ đọc: 15 pattern trong 10K dòng code — đó là một anti-pattern
- Composition được ưa chuộng hơn kế thừa — linh hoạt hơn và ít mong manh hơn
- Megamorphic call (>2 cách triển khai) ảnh hưởng đến các tối ưu hóa JIT và CPU trong hot path

**Các câu hỏi phụ thường gặp:**
- **Khi nào KHÔNG nên sử dụng pattern?** — CRUD đơn giản, prototype, pattern không giải quyết được vấn đề
- **Idiom khác với pattern như thế nào?** — Idiom là đặc thù cho ngôn ngữ (try-with-resources), pattern mang tính phổ quát
- **Bạn biết những pattern cloud-native nào?** — Circuit Breaker, Saga, CQRS, Event Sourcing, Sidecar
- **Golden Hammer là gì?** — Sử dụng một pattern yêu thích ở mọi nơi có thể

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi dùng pattern ở mọi nơi mà tôi biết" — đó là overengineering
- "Singleton giải quyết được mọi vấn đề" — Singleton được coi là một anti-pattern trong nhiều trường hợp
- "Pattern luôn luôn cải thiện hiệu năng" — thường thì chúng lại thêm chi phí phát sinh
- "Tôi không dùng pattern, tôi viết đơn giản hơn" — thể hiện sự thiếu hiểu biết về các giải pháp kiến trúc cơ bản
