# What is WeakHashMap? (WeakHashMap là gì?)

## 🟢 Junior Level

**WeakHashMap** là một Map mà trong đó các key có thể bị **tự động loại bỏ** khi không còn tham chiếu nào đến chúng.

**Ví dụ minh họa đơn giản:** Bạn đặt đồ vật lên một cái kệ. Nếu bạn quên mất một món đồ và không ai cần đến nó → người dọn dẹp sẽ vứt nó đi.

```java
WeakHashMap<Object, String> map = new WeakHashMap<>();

Object key = new Object();
map.put(key, "value");

key = null;  // Không còn tham chiếu nào đến key!
System.gc(); // System.gc() chỉ là một gợi ý; trên thực tế, việc loại bỏ sẽ xảy ra ở lần GC tiếp theo

map.size();  // → 0 (entry đã bị loại bỏ!)
```

## 🟡 Middle Level

### Cách nó hoạt động

**WeakReference** — một tham chiếu không ngăn cản GC thu gom đối tượng. Nếu chỉ có các WeakReference trỏ đến một đối tượng, GC sẽ thu gom nó.

**ReferenceQueue** — một hàng đợi nơi GC đặt các tham chiếu "đã chết". WeakHashMap định kỳ kiểm tra hàng đợi này.

**expungeStaleEntries()** — một phương thức nội bộ của WeakHashMap loại bỏ các entry có key đã chết ở mỗi thao tác (get, put, size).

```
1. Key được bọc trong một WeakReference
2. Khi GC: nếu không còn strong reference → key bị thu gom
3. Entry được đặt vào ReferenceQueue
4. Ở lần gọi BẤT KỲ phương thức nào của map:
   → expungeStaleEntries() rút cạn hàng đợi
   → Entry bị loại bỏ khỏi map
```

### Các bẫy

**1. Các String literal không bao giờ bị loại bỏ:**
```java
// ❌ Sẽ không bao giờ bị loại bỏ!
WeakHashMap<String, String> map = new WeakHashMap<>();
map.put("literal", "value");  // Literal sống mãi mãi trong String Pool!
```

**2. Strong reference từ Value đến Key:**
```java
// ❌ Memory leak!
class Value { Object keyRef; }

map.put(key, new Value(key));  // Value giữ key!
// Key sẽ không bao giờ bị thu gom!
```

### Khi nào dùng

```java
// ✅ Metadata cho các đối tượng
WeakHashMap<Component, String> tooltips = new WeakHashMap<>();
tooltips.put(button, "Click me");
// Khi button bị loại bỏ → tooltip sẽ bị loại bỏ tự động

// ✅ KHÔNG dành cho cache!
// → WeakReference bị dọn ở MỖI lần Minor GC
// → Minor GC — thu gom rác trong Young Generation, xảy ra mỗi vài giây/mili-giây khi các đối tượng được tạo ra một cách tích cực.
// → Cho cache: hãy dùng Caffeine hoặc SoftReference

// **Tại sao KHÔNG dành cho cache:** WeakHashMap loại bỏ các entry ở MỖI lần Minor GC.
// Nếu bạn cache kết quả của một phép tính tốn kém, nó có thể biến mất trong vòng vài mili-giây.
// Chỉ dùng WeakHashMap cho cache nếu các key là các đối tượng identity duy nhất, không phải dữ liệu.
// Hoặc tốt hơn — java.lang.ref.SoftReference (không bị thu gom ở Minor GC).
```

## 🔴 Senior Level

### Cơ chế ReferenceQueue

```java
// WeakHashMap bên trong:
class Entry<K,V> extends WeakReference<K> {
    V value;
    Entry<K,V> next;

    Entry(K key, V value, ReferenceQueue<K> queue) {
        super(key, queue);  // Hàng đợi để thông báo
        this.value = value;
    }
}

// GC phát hiện một key chỉ còn weak
// → Đặt Entry vào ReferenceQueue
// → expungeStaleEntries() ở lần gọi map tiếp theo
```

### Dọn dẹp lười (Lazy cleanup)

```java
// WeakHashMap KHÔNG tự dọn dẹp bản thân nó!
// Việc dọn dẹp xảy ra khi BẤT KỲ phương thức nào được gọi:

map.put(new Object(), "x");
// ... GC đã thu gom key ...
// map vẫn chứa entry "đã chết"!

map.size();  // → Chỉ bây giờ nó mới được dọn dẹp!

// → Nếu bạn không gọi các phương thức trong một thời gian dài → memory leak!
```

### WeakHashMap so với các giải pháp thay thế

| Giải pháp        | Khi nào                           |
| ---------------- | --------------------------------- |
| **WeakHashMap**  | Vòng đời gắn với key              |
| **Caffeine Cache** | Cache đầy đủ tính năng (LRU, TTL)  |
| **SoftReference**  | Cache, bị thu gom khi có nguy cơ OOM |
| **ThreadLocal**    | Dữ liệu gắn với luồng             |

**Sự khác biệt so với `Map<WeakReference<K>, V>`:** WeakHashMap tự động loại bỏ các entry đã chết — bạn không cần dọn dẹp ReferenceQueue theo cách thủ công. Trong `Map<WeakReference<K>, V>`, các tham chiếu đã chết tích lũy vô thời hạn.

### Chẩn đoán rò rỉ

```
Heap Dump: tìm Entry có referent = null
  → Entry vẫn nằm trong mảng table
  → Các phương thức của map đã không được gọi trong một thời gian
  → "Lazy cleanup" đã không được kích hoạt

Giải pháp: map.size() sẽ buộc dọn dẹp
```

### Kinh nghiệm Production

**Tình huống thực tế: Metadata của Component**
```java
// UI framework: metadata cho các component
WeakHashMap<Component, Properties> meta = new WeakHashMap<>();

// Component bị loại bỏ → meta tự dọn dẹp
// → Không có memory leak!
```

### Best Practices

1. **Metadata** — trường hợp sử dụng chính
2. **KHÔNG phải cache** — việc dọn dẹp quá quyết liệt
3. **Các String literal** — sẽ không bao giờ bị loại bỏ
4. **Các tham chiếu Value → Key** — memory leak!
5. **Gọi các phương thức** thường xuyên để kích hoạt dọn dẹp
6. **Heap Dump** — tìm Entry có referent null

### Tóm tắt cho Senior

- **WeakHashMap** = tự động loại bỏ theo vòng đời của key
- **ReferenceQueue** → dọn dẹp lười khi gọi phương thức
- **Các String literal** → không bị loại bỏ (String Pool)
- **Value → Key** → strong reference = rò rỉ
- **KHÔNG phải cache** → hãy dùng Caffeine
- **Metadata** → trường hợp sử dụng chính
- **Heap Dump** → Entry có referent null

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- WeakHashMap — các key được bọc trong WeakReference, tự động bị loại bỏ khi không còn strong reference
- ReferenceQueue — GC đặt các tham chiếu "đã chết" vào đây, WeakHashMap kiểm tra hàng đợi ở bất kỳ lần gọi phương thức nào
- expungeStaleEntries() — dọn dẹp lười, được gọi ở get/put/size — nếu không được gọi trong một thời gian dài, xảy ra memory leak
- Các String literal KHÔNG bị loại bỏ — chúng sống mãi mãi trong String Pool
- Strong reference từ Value đến Key = rò rỉ! Key sẽ không bao giờ bị GC thu gom
- Trường hợp sử dụng chính: metadata (tooltip, thuộc tính của các component UI), KHÔNG phải cache
- Cho cache: Caffeine (LRU, TTL) hoặc SoftReference (không bị thu gom ở Minor GC)
- Sự khác biệt so với Map<WeakReference<K>, V>: WeakHashMap tự động dọn dẹp các entry đã chết, không cần làm thủ công

**Các câu hỏi phụ thường gặp:**
- **Tại sao WeakHashMap KHÔNG phù hợp cho cache?** — Nó loại bỏ các entry ở MỖI lần Minor GC. Một kết quả đã cache của một phép tính tốn kém có thể biến mất trong vòng vài mili-giây.
- **Làm sao buộc dọn dẹp một WeakHashMap?** — Gọi bất kỳ phương thức nào: size(), get(), put(). expungeStaleEntries() sẽ kiểm tra ReferenceQueue và loại bỏ các entry đã chết.
- **Điều gì xảy ra nếu Value tham chiếu đến Key?** — Một strong reference từ Value ngăn Key bị GC thu gom — entry sẽ không bao giờ bị loại bỏ, gây ra memory leak.
- **Tại sao các String literal không bị loại bỏ khỏi WeakHashMap?** — Các String literal sống trong String Pool — chúng luôn có một strong reference từ ClassLoader.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "WeakHashMap là một cache tốt" — việc dọn dẹp quá quyết liệt, hãy dùng Caffeine thay thế
- ❌ "WeakHashMap tự dọn dẹp bản thân ở nền (background)" — việc dọn dẹp chỉ xảy ra khi gọi phương thức (lazy)
- ❌ "Các String literal bị loại bỏ khỏi WeakHashMap" — không, chúng sống trong String Pool mãi mãi
- ❌ "WeakReference và SoftReference là như nhau" — SoftReference không bị thu gom ở Minor GC, chỉ khi có nguy cơ OOM
