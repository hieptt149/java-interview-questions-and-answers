# How to work with Optional in Stream? (Cách làm việc với Optional trong Stream?)

## 🟢 Junior Level

`Optional` và `Stream` thường làm việc cùng nhau. Các kịch bản chính:

Optional.empty() — một "container không có giá trị". Tương tự null, nhưng an toàn: bạn không thể vô tình nhận NPE, bạn phải gọi get/orElse một cách tường minh.

**1. Stream chứa Optional:**
```java
// Trước: Stream<Optional<User>>
// Cần: Stream<User> (không có các cái rỗng)

ids.stream()
    .map(repo::findById)       // trả về Optional<User>
    .filter(Optional::isPresent)
    .map(Optional::get)
    .collect(toList());
```

**2. Trả về Optional từ các thao tác stream:**
```java
Optional<User> firstAdmin = users.stream()
    .filter(User::isAdmin)
    .findFirst();  // trả về Optional
```

**Quan trọng:** Đừng bao giờ gọi `.get()` mà không kiểm tra `.isPresent()`.

## 🟡 Middle Level

### Phong cách Java 9+: Optional.stream()

Một cách thanh lịch để loại bỏ các Optional rỗng:
```java
List<User> activeUsers = ids.stream()
    .map(repository::findById)  // Stream<Optional<User>>
    .flatMap(Optional::stream)   // Các Optional rỗng biến mất!
    .toList();
```

**Bên trong:** `Optional.stream()` trả về `Stream.of(value)` hoặc `Stream.empty()`.

### Tránh .get() trong các lambda

```java
// XẤU — một quả bom hẹn giờ
.map(o -> o.get())

// TỐT — an toàn
.flatMap(Optional::stream)
.map(o -> o.orElse(defaultValue))
```

orElse() — được đánh giá LUÔN LUÔN, ngay cả khi Optional không rỗng. orElseGet() — được đánh giá CHỈ KHI Optional rỗng. Nếu giá trị mặc định là đắt đỏ (truy vấn DB) — luôn dùng orElseGet!

### Các phương thức nâng cao (Java 9-11)

**`ifPresentOrElse(action, emptyAction)`:**
```java
optional.ifPresentOrElse(
    user -> sendNotification(user),
    () -> log.warn("User not found")
);
```

**`or(Supplier)`:**
```java
// Chuỗi tìm kiếm: cache → DB → API
findByIdInCache(id)
    .or(() -> findByIdInDb(id))
    .or(() -> findByIdInApi(id));
```

### Khi nào KHÔNG nên dùng Optional trong Stream

1. **Kiểm tra null đơn giản** — `if (x != null)` thông thường dễ đọc hơn
2. **Bên trong một vòng lặp chặt (tight loop)** — tạo Optional = cấp phát, có thể gây căng thẳng cho GC
3. **Như một trường của class** — Optional không serializable, không dành cho các trường

## 🔴 Senior Level

### Đừng dùng Optional cho các trường Entity

Lưu `Optional` trong các trường của class (đặc biệt là JPA) là một anti-pattern:
- `Optional` không serializable
- Tăng mức tiêu thụ bộ nhớ
- Chỉ dùng như một **giá trị trả về** của phương thức

### Highload: Optional Overhead

Tạo hàng triệu object `Optional` có thể tốn kém:
- **Value Type (Project Valhalla):** Trong tương lai, `Optional` sẽ trở thành một "Inline Type" không có overhead
- **Hiện tại:** Với hàng tỷ primitive, hãy dùng các "magic value" (`-1`, `0`) hoặc `OptionalInt`

### Các trường hợp biên (Edge Case)

**NullPointerException:** `Optional.of(null)` ném NPE ngay lập tức. Dùng `Optional.ofNullable()`.

**Parallel Stream:** `Optional` trong các parallel stream là an toàn — `Optional` là immutable.

### Chẩn đoán

**Sonar Rule:** "Optional should be used as a return type only". Chỉ bỏ qua trong các trường hợp ngoại lệ.

**Debug:** Khi debug `flatMap(Optional::stream)`, các giá trị rỗng chỉ đơn giản biến mất khỏi visualizer — điều này có thể gây nhầm lẫn.

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- `filter(Optional::isPresent).map(Optional::get)` — phong cách Java 8 cũ để gỡ bọc
- `flatMap(Optional::stream)` — Java 9+, cách thanh lịch để loại bỏ các Optional rỗng
- `orElse()` được đánh giá LUÔN LUÔN, `orElseGet()` — chỉ khi Optional rỗng (cho các giá trị mặc định đắt đỏ)
- `Optional.of(null)` ném NPE — dùng `Optional.ofNullable()`
- Optional — chỉ như một giá trị trả về của phương thức, KHÔNG như một trường của class
- Optional không serializable và không dành cho các trường Entity của JPA
- `ifPresentOrElse(action, emptyAction)` và `or(Supplier)` — Java 9+ cho xử lý nâng cao
- Trong các vòng lặp chặt, tạo hàng triệu Optional gây căng thẳng cho GC — cân nhắc OptionalInt/Long

**Các câu hỏi phụ thường gặp:**
- **orElse khác orElseGet như thế nào?** — orElse luôn đánh giá tham số của nó; orElseGet — chỉ khi Optional rỗng. Cho các giá trị mặc định đắt đỏ (truy vấn DB) — luôn orElseGet.
- **Cách biến Stream<Optional<T>> thành Stream<T>?** — `.flatMap(Optional::stream)` (Java 9+) — các Optional rỗng sẽ biến mất.
- **Tại sao không nên dùng Optional như một trường của class?** — Không serializable, tăng bộ nhớ, làm phức tạp code — chỉ dành cho các giá trị trả về.
- **Optional có an toàn trong parallelStream không?** — Có, Optional là immutable, nhưng overhead của việc tạo object vẫn còn.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Bạn có thể gọi .get() mà không kiểm tra" — sai, một Optional rỗng sẽ ném NoSuchElementException
- "Optional là một sự thay thế cho null trong các trường của class" — sai, đây là một anti-pattern, Optional chỉ dành cho các kiểu trả về
- "orElse và orElseGet giống nhau" — sai, orElse được đánh giá luôn luôn, orElseGet — một cách lazy
- "Optional.of(null) sẽ trả về một Optional rỗng" — sai, nó ném NullPointerException
