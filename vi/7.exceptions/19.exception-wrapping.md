# What is exception wrapping (wrapping)? (Exception wrapping là gì?)

## Junior Level

### Định nghĩa

**Wrapping** - tạo một exception mới chứa exception gốc dưới dạng một `cause`.

**Chuỗi nhân quả (Chain of causality)** - một dãy các exception trong đó mỗi cái sau bọc cái trước. Hãy tưởng tượng một con búp bê Nga (matryoshka): exception ngoài cùng là tầng service, bên trong nó - exception database, và sâu hơn nữa - lỗi mạng. Khi bạn thấy một stack trace có wrapping, JVM in toàn bộ chuỗi từ ngoài cùng tới sâu nhất (root cause).

### Ví dụ

```java
try {
    // Code có thể ném SQLException
    connection.executeQuery("SELECT * FROM users");
} catch (SQLException e) {
    // Bọc trong exception của chúng ta
    throw new DataAccessException("Failed to query users", e);
    //                                                           ^--- cause
}
```

Chuỗi nhân quả trong log sẽ trông như:
```
DataAccessException: Failed to query users
    at UserService.getUsers(UserService.java:25)
Caused by: SQLException: Connection timeout
    at DBConnection.executeQuery(DBConnection.java:42)
```
Dòng `Caused by:` - chuyển sang mắt xích tiếp theo trong chuỗi.

### Tại sao wrap

1. **Thêm ngữ cảnh:** `"Failed to query users table for active users"` rõ ràng hơn `"Connection timeout"`
2. **Ẩn chi tiết hiện thực:** logic nghiệp vụ không nên biết về `SQLException`
3. **Giữ cause:** `e` được truyền vào - stack trace của lỗi gốc không bị mất
4. **Cây phân cấp thống nhất:** tất cả các service exception - là kiểu con của `ServiceException`

### Khi nào KHÔNG nên dùng wrapping

1. **Validation đầu vào** - `IllegalArgumentException` không cần wrapping. Đây là một lỗi lập trình, nó cần được sửa, không phải bọc
2. **Lỗi của lập trình viên** - `NullPointerException`, `IndexOutOfBoundsException` không nên bị bắt và bọc. Những exception này chỉ ra một bug - hãy để chúng tới global handler
3. **Lồng nhau quá sâu** - nếu đã 5+ tầng `cause`, đừng thêm một cái nữa nếu không có lý do chính đáng. Một chuỗi 10 exception = stack trace không đọc được
4. **Timeout và retry** - khi tự động retry, đừng bọc mỗi lần thử, chỉ bọc lỗi cuối cùng. Nếu không bạn có: `RetryException` -> `TimeoutException` -> `TimeoutException` -> `TimeoutException` -> `SocketException`
5. **Code nhạy về hiệu suất** - mỗi exception được bọc = object mới + `fillInStackTrace()`. Trong hot-path đây là overhead đáng kể
6. **Anti-pattern "wrap-a-wrap"** - đừng bọc một exception vốn đã là wrapper của cùng một mức abstraction:
```java
// XẤU - ServiceException và DataAccessException ở cùng một mức, vô nghĩa
try {
    repo.findUser(id);
} catch (DataAccessException e) {
    throw new ServiceException("User lookup failed", e);
    // DataAccessException đã đủ abstract, wrapping là vô nghĩa
}

// TỐT - chỉ wrap khi chuyển giữa các mức abstraction
// Tầng DAO (SQLException) -> tầng Service (DataAccessException) -> Controller (ServiceException)
```
7. **Lan truyền mà không thêm ngữ cảnh** - nếu wrapper không thêm message hay metadata mới nào, nó là tạp nhiễu:
```java
// Vô nghĩa - cùng message và cause
throw new MyException(e.getMessage(), e);
```

### Cách lấy cause

```java
try {
    service.process();
} catch (DataAccessException e) {
    Throwable cause = e.getCause(); // SQLException gốc
    System.out.println("Root cause: " + cause.getMessage());
}
```

## Middle Level

### Cách nó được cấu trúc trong Throwable

Lớp `Throwable` có một trường `private Throwable cause = this;`.

Khi truyền vào constructor `super(cause)`, `initCause()` được gọi.

**Quan trọng:** `initCause()` chỉ có thể được gọi một lần. Lời gọi lặp lại - `IllegalStateException`.

### Exception Translation trong kiến trúc sạch

Wrapping - thay đổi mức abstraction:

```java
// Xấu - client phụ thuộc vào Stripe
public interface PaymentService {
    void charge(Card card) throws StripeException;
}

// Tốt - client phụ thuộc vào domain
public interface PaymentService {
    void charge(Card card) throws PaymentProviderException;
}

// Hiện thực bọc lại
public class StripePaymentService implements PaymentService {
    public void charge(Card card) {
        try {
            stripeApi.charge(card);
        } catch (StripeException e) {
            throw new PaymentProviderException("Stripe charge failed", e);
        }
    }
}
```

Bạn có thể chuyển từ Stripe sang PayPal mà không thay đổi chữ ký phương thức.

### Ngăn mất ngữ cảnh

```java
// TỆ HƠN - mất kiểu cause và stack trace
throw new MyException(e.getMessage());

// TỐT HƠN - truyền cả object
throw new MyException("Context: processing order " + orderId, e);
```

## Senior Level

### Độ sâu của Stack Trace

Khi wrapping sâu (DB -> Hibernate -> Spring -> Service -> Controller) stack trace trở nên khổng lồ. Điều này làm tăng thời gian định dạng và khối lượng log.

**Giải pháp:** ở các tầng trung gian dùng các exception "nhẹ" không có stack trace, nếu cause gốc (`cause`) đã chứa tất cả stack cần thiết.

### Memory Overhead

Mỗi object trong chuỗi `cause` - một tham chiếu sống. Nếu bạn lưu các object như vậy trong bộ nhớ (hàng đợi xử lý lỗi) - dọn dẹp bộ nhớ bị trì hoãn.

### Circular Reference (tham chiếu vòng)

`Throwable` được bảo vệ khỏi các chu trình vô hạn:

```java
e1.initCause(e2);
e2.initCause(e1); // IllegalArgumentException
```

### Reflection và InvocationTargetException

Với `Method.invoke()` bất kỳ exception nào cũng **luôn** bị bọc trong `InvocationTargetException`:

```java
try {
    method.invoke(obj);
} catch (InvocationTargetException e) {
    Throwable realException = e.getCause(); // Lỗi thực sự
}
```

### Unwrapping (gỡ bọc) để debug

```java
// Apache Commons Lang
Throwable root = ExceptionUtils.getRootCause(e);

// Guava
Throwable root = Throwables.getRootCause(e);

// Thủ công
Throwable t = e;
while (t.getCause() != null) {
    t = t.getCause();
}
```

### Custom Metadata khi wrapping

Thêm metadata biết được ở tầng hiện tại:

```java
public class ServiceException extends RuntimeException {
    private final Long orderId;
    private final String action;

    public ServiceException(String message, Throwable cause, Long orderId, String action) {
        super(message, cause);
        this.orderId = orderId;
        this.action = action;
    }
}
```

### Chẩn đoán

- **Log Analysis** - đảm bảo định dạng log tiết lộ `cause` (`%ex` trong Logback)
- **IntelliJ Debugger** - mở rộng node `cause` để thấy toàn bộ cây lỗi
- **Log có cấu trúc JSON** - `cause` như một trường riêng để lập chỉ mục

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Wrapping - tạo một exception mới với cái gốc làm `cause` (búp bê Nga)
- Constructor `super(message, cause)` gọi `initCause()` - chỉ có thể gọi một lần
- Chuỗi nhân quả hiện trong log qua `Caused by:`
- Wrapping thay đổi mức abstraction: DAO -> Service -> Controller
- Mất ngữ cảnh: `new MyException(e.getMessage())` - xấu, mất kiểu và stack trace
- `InvocationTargetException` khi reflection luôn bọc lỗi thực sự
- Tránh anti-pattern wrap-a-wrap - đừng bọc các wrapper cùng mức

**Các câu hỏi phụ thường gặp:**
- **Có thể gọi `initCause()` hai lần không?** - Không, sẽ nhận `IllegalStateException`
- **Tại sao truyền `cause` thay vì chỉ `e.getMessage()`?** - Để giữ kiểu và stack trace của lỗi gốc
- **Khi nào KHÔNG nên wrap?** - Validation, lỗi lập trình viên (NPE), lồng nhau sâu 5+ tầng
- **Cách lấy root cause thủ công?** - Vòng lặp `while (t.getCause() != null) t = t.getCause()`

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi bọc tất cả các exception không phân biệt" - đây là một anti-pattern
- "Tôi dùng `e.getMessage()` thay vì `cause`" - mất kiểu và stack trace
- "Wrapping là để giấu lỗi khỏi bên gọi" - không, là để thêm ngữ cảnh
- "Độ sâu lồng nhau không quan trọng" - 10+ tầng làm stack trace không đọc được
