# What is Dockerfile? (Dockerfile là gì?)

## Junior Level

### Giải Thích Đơn Giản

**Dockerfile** là một file văn bản chứa các instruction để build một Docker image.

Đây là một file khai báo (declarative): bạn mô tả image nên trông như thế nào, và Docker tìm ra cách build nó. Nó giống như một công thức nấu ăn: bạn viết các bước, và Docker lắp ráp chúng thành một image sẵn sàng chạy có thể được khởi chạy như một container.

### Phép So Sánh

Một Dockerfile là một **công thức nấu ăn**. `FROM` là nguyên liệu nền (ví dụ: bột), `COPY` là thêm nguyên liệu, `RUN` là quá trình nấu, `ENTRYPOINT` là cách món ăn được phục vụ. Từ một công thức bạn có thể nấu bao nhiêu món ăn giống hệt nhau (container) tùy ý.

### Ví Dụ

```dockerfile
# 1. Image nền
FROM openjdk:17-jdk-slim

# 2. Thư mục làm việc
WORKDIR /app

# 3. Sao chép file
COPY myapp.jar app.jar

# 4. Port ứng dụng
EXPOSE 8080

# 5. Lệnh khởi chạy
ENTRYPOINT ["java", "-jar", "app.jar"]
```

```bash
# Build image từ Dockerfile
docker build -t myapp .

# Chạy container
docker run -p 8080:8080 myapp
```

### Các Instruction Chính

| Instruction  | Nó làm gì                                           |
| ------------ | ------------------------------------------------------ |
| `FROM`       | Chỉ định image nền (ví dụ: `openjdk:17`)          |
| `WORKDIR`    | Đặt thư mục làm việc                             |
| `COPY`       | Sao chép các file vào image                           |
| `RUN`        | Thực thi một lệnh trong quá trình build                        |
| `EXPOSE`     | Ghi tài liệu về port ứng dụng                         |
| `ENTRYPOINT` | Lệnh khởi chạy ứng dụng                             |

### Cần Nhớ

- Dockerfile là một công thức để tạo một Docker image
- Mỗi instruction tạo một layer mới trong image
- `FROM` luôn là instruction đầu tiên
- Dùng các phiên bản image cụ thể, không phải `latest`
- `docker build` lắp ráp image, `docker run` khởi chạy container

### Khi Nào KHÔNG Cần Dockerfile

Nếu bạn dùng platform-as-a-service (Heroku, Railway, Render), bạn có thể không cần Dockerfile — nền tảng tự build image từ code.

## Middle Level

### Cách Việc Build Image Hoạt Động

Khi bạn chạy `docker build .`:

1. Docker client gửi nội dung của thư mục hiện tại (**Build Context**) đến Docker daemon.
2. Daemon thực thi các instruction từ Dockerfile từng bước một.
3. Mỗi instruction tạo một **layer** mới trong image.
4. Các layer được cache — nếu một instruction không thay đổi, Docker dùng cache.

### Build Context Và .dockerignore

Build Context là toàn bộ nội dung thư mục được gửi đến Docker. Để tránh gửi các file không cần thiết (`.git`, `target/`, log), dùng **`.dockerignore`**:

```
.git
target/
*.log
.idea/
```

### Các Layer Và Caching

Docker dùng một filesystem theo lớp (UnionFS/Overlay2):
- Mỗi lệnh (`RUN`, `COPY`, `ADD`) tạo một layer mới
- Các layer được cache — nếu instruction và các file không thay đổi, Docker lấy layer sẵn có từ cache

**Quy tắc tối ưu hóa:** Đặt các instruction ít thay đổi ở đầu, các instruction thường xuyên thay đổi ở cuối.

```dockerfile
# TỒI: mỗi lần thay đổi code làm mất hiệu lực cache dependency
COPY src /app/src
COPY pom.xml /app
RUN mvn -f /app/pom.xml clean package

# TỐT: dependency được cache riêng
COPY pom.xml /app
RUN mvn -f /app/pom.xml dependency:go-offline
// Docker cache một layer nếu instruction và TẤT CẢ các layer trước đó không đổi.
// pom.xml thay đổi — làm mất hiệu lực tất cả các layer sau đó.
COPY src /app/src
RUN mvn -f /app/pom.xml clean package
```

### Các Lỗi Thường Gặp

| Lỗi                     | Hậu quả                           | Cách tránh                    |
| --------------------------- | ------------------------------------- | -------------------------------- |
| `FROM openjdk:latest`       | Build không tất định              | `FROM openjdk:17-jdk-slim`     |
| Không có `.dockerignore`          | Build chậm, image lớn             | Tạo `.dockerignore`          |
| Tất cả các lệnh trong một RUN     | Không thể dùng cache một phần             | Tách các bước logic riêng          |
| Chạy ứng dụng với quyền root         | Rủi ro bảo mật                         | `USER appuser`                  |
| Một layer khổng lồ duy nhất              | Không có caching, rebuild chậm              | Tách dependency và code  |

### Các Nguyên Tắc Chính Của Một Dockerfile Tốt

1. **Trách nhiệm đơn nhất (single responsibility)** — một container, một process.
2. **Giảm thiểu kích thước** — dùng các image nền nhẹ (`alpine`, `slim`, `distroless`).

Alpine — phân phối Linux tối thiểu (~5 MB), thường được dùng làm nền cho các image.
3. **Bảo mật** — đừng chạy ứng dụng với `root`. Dùng `USER`.
4. **Phiên bản cụ thể** — luôn ghim (pin) phiên bản chính xác của các image nền.

### Multi-stage Build

Cho phép biên dịch code trong một image tạm thời và chỉ sao chép artifact vào image cuối cùng:

```dockerfile
# Stage 1: Build
FROM maven:3.8-openjdk-17 AS build
COPY src /app/src
COPY pom.xml /app
RUN mvn -f /app/pom.xml clean package -DskipTests

# Stage 2: Runtime
FROM openjdk:17-jdk-slim
COPY --from=build /app/target/app.jar /app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app.jar"]
```

### Cần Nhớ

- Mỗi instruction = một layer mới
- Caching là chìa khóa cho build nhanh
- Thứ tự instruction quan trọng đối với hiệu năng
- Dùng `.dockerignore` để loại trừ các file không cần thiết
- Multi-stage build là tiêu chuẩn cho các image production

## Senior Level

### Dockerfile Như Infrastructure as Code

Một Dockerfile không chỉ là một script build — nó là **nền tảng của Infrastructure as Code (IaC)** ở cấp độ ứng dụng. Nó quyết định khả năng tái tạo (reproducibility), bảo mật, và hiệu quả delivery.

### Phân Tích Sâu Về Quá Trình Build

#### Build Context Và Tác Động Của Nó Đến CI/CD

```
docker build . → tar archive của toàn bộ thư mục → gửi đến Docker daemon
```

**Vấn đề:** context lớn = truyền chậm (đặc biệt với daemon từ xa). `.dockerignore` hoạt động giống như `.gitignore` nhưng cho Docker. Trong CI/CD, context có thể bao gồm artifact từ các lần build trước.

**Thực hành tốt nhất:**
```dockerignore
# Loại trừ mọi thứ trừ những gì cần thiết
**
!src/
!pom.xml
!Dockerfile
```

### Cơ Chế Caching: Hiểu Sâu

Docker tính một hash cho mỗi layer dựa trên: chính instruction đó, hash của các layer trước đó, nội dung file (cho `COPY` và `ADD`).

**Cache mất hiệu lực khi:** instruction thay đổi, các file được sao chép thay đổi, hash của layer cha thay đổi.

**Pattern "Dependency Layer" cho Java:**

```dockerfile
FROM maven:3.8-openjdk-17 AS build
WORKDIR /build
COPY pom.xml .
RUN mvn dependency:go-offline -B   # hiếm khi thay đổi → được cache
COPY src ./src
RUN mvn package -DskipTests        # thường xuyên thay đổi
```

Điều này mang lại tỷ lệ cache hit trên 90% cho các build không có thay đổi dependency.

### Đánh Đổi (Trade-offs)

| Quyết định       | Điểm cộng                                   | Điểm trừ                                                  |
| -------------- | --------------------------------------- | ------------------------------------------------------ |
| Image Alpine  | Kích thước tối thiểu (~5MB nền)               | musl libc ≠ glibc, vấn đề với các thư viện native        |
| Image Slim    | Tương thích glibc, kích thước nhỏ        | Lớn hơn alpine                                     |
| Distroless     | Bề mặt tấn công tối thiểu                 | Không có shell để debug, cần các container debug tạm thời|
| Nhiều layer    | Caching tốt hơn                         | Nhiều metadata hơn, pull chậm hơn                             |
| Ít layer     | Pull nhanh                              | Caching kém hơn                                          |

### Edge Case

- **Alpine + thư viện native**: Alpine dùng musl libc. Các thư viện JNI (Netty epoll, PostgreSQL native) có thể yêu cầu glibc. Giải pháp: dùng `debian-slim` hoặc build cho musl.
- **Build timeout**: `RUN apt-get update` có thể treo do vấn đề mạng. Giải pháp: dùng mirror, retry logic.
- **Build không tất định**: `apt-get update` không ghim phiên bản package cho kết quả khác nhau. Giải pháp: `apt-get install -y package=1.2.3-1`.
- **Build đa nền tảng**: Build image amd64 trên ARM (Apple Silicon). Giải pháp: `docker buildx` với mô phỏng QEMU hoặc remote builder.

### Bảo Mật Dockerfile

```dockerfile
# Dockerfile sẵn sàng cho production với Spring Boot
FROM maven:3.9-eclipse-temurin-17 AS build
WORKDIR /build
COPY pom.xml .
RUN mvn dependency:go-offline -B
COPY src ./src
RUN mvn package -DskipTests -B

FROM eclipse-temurin:17-jre-alpine
RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser
WORKDIR /app
COPY --from=build /build/target/*.jar app.jar
EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=3s \
  CMD wget -qO- http://localhost:8080/actuator/health || exit 1
ENTRYPOINT ["java", "-XX:+UseG1GC", "-jar", "app.jar"]
```

**Các quy tắc quan trọng:**
- Đừng dùng `latest`
- Đừng chạy với quyền root
- Filesystem chỉ đọc nếu có thể
- Giảm thiểu bề mặt tấn công
- Dùng `HEALTHCHECK`

### Tác Động Đến CI/CD Pipeline

```
developer → git push → CI chạy docker build →
  cache hit? → nhanh (vài giây) : chậm (vài phút) →
  docker push → CD deploy
```

**Tối ưu hóa CI:** registry cache (pull image trước đó), BuildKit cache, chia sẻ layer giữa các image.

**BuildKit** (Docker 23+): thực thi song song các bước độc lập, quản lý secret (`--mount=type=secret`), SSH forwarding (`--mount=type=ssh`), cache mount (`--mount=type=cache`).

### Hiệu Năng

| Image nền                      | Kích thước    | Thời gian pull | Thời gian khởi động |
| ------------------------------- | ------- | --------- | ---------- |
| `openjdk:17`                    | ~500 MB | ~30s      | ~5s        |
| `openjdk:17-slim`               | ~300 MB | ~15s      | ~5s        |
| `eclipse-temurin:17-jre-alpine` | ~100 MB | ~5s       | ~4s        |
| `distroless/java17`             | ~80 MB  | ~4s       | ~4s        |

### Monitoring

- `docker history <image>` — phân tích các layer và kích thước của chúng
- `docker build --progress=plain` — output build chi tiết
- `dive <image>` — trình phân tích layer tương tác
- BuildKit `--progress=trace` — theo dõi từng bước

### Câu Chuyện Production

Một team 50 developer gặp phải các build CI mất 12 phút. Phân tích cho thấy: mỗi lần tất cả các dependency Maven được tải lại từ đầu. Triển khai multi-stage build với việc cache pom.xml riêng biệt đã giảm thời gian xuống còn 2 phút (cải thiện 83%). Ngoài ra: chuyển sang image slim giảm kích thước từ 650MB xuống 280MB, giúp deploy nhanh hơn 2.3 lần và tiết kiệm 40% dung lượng lưu trữ trong registry.

### Tóm Tắt

- Dockerfile là một công thức để tạo một artifact bất biến. Hiểu về layer caching là chìa khóa cho CI/CD nhanh.
- Luôn hướng đến việc giảm thiểu số layer và dùng Multi-stage build.
- Dockerfile phải tất định (deterministic) (phiên bản cụ thể, không phải `latest`).
- Bảo mật: user non-root, image nền tối thiểu, health check.
- Ở quy mô lớn, việc tối ưu hóa Dockerfile tiết kiệm hàng trăm giờ CI/CD và hàng gigabyte lưu trữ.

## Interview Cheat Sheet

**Cần phải biết:**
- Dockerfile — công thức khai báo để tạo một Docker image bất biến
- Mỗi instruction (RUN, COPY, ADD) tạo một layer chỉ đọc mới
- Layer caching là chìa khóa cho build nhanh: thứ tự instruction rất quan trọng
- Multi-stage build — tiêu chuẩn production: build trong một image, runtime trong image khác
- Exec form `["cmd", "arg"]` là bắt buộc cho CMD/ENTRYPOINT (xử lý signal)
- Bảo mật: user non-root, tag cụ thể, image nền tối thiểu
- BuildKit: secret (`--mount=type=secret`), SSH forwarding, cache mount

**Các câu hỏi phụ thường gặp:**
- *"Tại sao thứ tự instruction lại quan trọng?"* — Thay đổi một instruction làm mất hiệu lực tất cả các layer cache sau đó
- *".dockerignore là gì?"* — Loại trừ các file khỏi build context (giống .gitignore cho Docker)
- *"Tại sao Alpine có thể là một vấn đề?"* — musl libc ≠ glibc; các thư viện JNI có thể không hoạt động
- *"COPY khác ADD như thế nào?"* — ADD có thể giải nén archive và tải từ URL, nhưng COPY được ưu tiên

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi dùng tag `latest` cho tiện" (build không tất định)
- "Tôi truyền secret qua ARG" (hiển thị trong `docker history`)
- "Tôi chạy ứng dụng với quyền root trong container" (rủi ro bảo mật)
- "ADD tốt hơn COPY" (COPY là thực hành tốt nhất trong 95% trường hợp)
