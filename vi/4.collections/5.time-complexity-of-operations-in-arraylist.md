# What is the time complexity of operations in ArrayList? (Độ phức tạp thời gian của các thao tác trong ArrayList là gì?)

## 🟢 Junior Level

**Time complexity (độ phức tạp thời gian)** — một thao tác mất bao lâu tùy thuộc vào kích thước của list.

| Thao tác        | Độ phức tạp | Giải thích                                                                                                                    |
| --------------- | ---------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `get(index)`    | **O(1)**   | Tức thì, truy cập theo index                                                                                                   |
| `add(e)`        | **O(1)***  | Thời gian hằng số trung bình. Khi mảng đầy, xảy ra resize (sao chép tất cả các phần tử), nhưng điều này hiếm khi xảy ra.        |
| `add(index, e)` | **O(n)**   | Cần dịch chuyển các phần tử                                                                                                    |
| `remove(index)` | **O(n)**   | Cần dịch chuyển các phần tử                                                                                                    |
| `contains(e)`   | **O(n)**   | Tìm kiếm tuyến tính                                                                                                            |
| `size()`        | **O(1)**   | Kích thước được lưu trữ                                                                                                        |

**Ví dụ:**
```java
ArrayList<String> list = new ArrayList<>();

list.add("A");        // O(1) — nhanh
list.get(0);          // O(1) — tức thì!
list.add(0, "B");     // O(n) — dịch chuyển tất cả các phần tử
list.remove(0);       // O(n) — dịch chuyển tất cả các phần tử
list.contains("A");   // O(n) — iterate
```

## 🟡 Middle Level

### Amortized O(1) cho add(e)

**Độ phức tạp phân bổ (amortized)** = nếu bạn thực hiện N thao tác, tổng thời gian = O(N), nên một thao tác trung bình = O(1). Một thao tác đơn lẻ có thể mất O(n) trong lúc resize, nhưng điều này hiếm khi xảy ra (mỗi khi lấp đầy ~1.5 lần).

```java
// add(e) = O(1) trung bình, nhưng đôi khi O(n)

// Tại sao?
// 1. Còn chỗ trống trong mảng → O(1)
// 2. Mảng đầy → resize (O(n))

// Resize: mảng mới × 1.5
// capacity: 10 → 15 → 22 → 33 → 49 → ...

// Độ phức tạp phân bổ:
// N lần thêm = O(N) tổng cộng
// Một lần thêm = O(1) trung bình
```

### Chi tiết các thao tác

```java
// get(index): O(1)
// → array[index] → tức thì

// add(e): O(1)* phân bổ
// → Nếu còn chỗ: array[size++] = e
// → Nếu không: resize + arraycopy

// add(index, e): O(n)
// → System.arraycopy(index, index+1, size-index)
// → array[index] = e
// → Native code → nhanh!

// remove(index): O(n)
// → System.arraycopy(index+1, index, size-index-1)
// → array[size-1] = null (cho GC)

// contains(e): O(n)
// → for (int i = 0; i < size; i++)
//     if (element.equals(e)) return true;
```

### Các thao tác hàng loạt (bulk) (Java 8+)

```java
// removeIf(predicate): O(n)
// → Một lần duyệt để tìm các phần tử
// → Một lần dịch chuyển để xóa
// → Thay vì O(n²) trong vòng lặp!

// replaceAll(operator): O(n)
// → Thao tác trực tiếp trên mảng
// → Không tạo iterator

// removeAll(collection): O(n × m)
// → Với mỗi phần tử kiểm tra collection
```

### Các tối ưu hóa

```java
// 1. ensureCapacity(size)
// → Loại bỏ các lần resize nếu biết trước kích thước
// → new ArrayList<>(1_000_000);

// 2. trimToSize()
// → Thu nhỏ mảng về kích thước thực tế
// → Sau khi xóa hàng loạt

// 3. ArrayList đã được sắp xếp
// → Collections.binarySearch() → O(log n)
// → Thay vì contains O(n)!
```

## 🔴 Senior Level

### Đào sâu về System.arraycopy

```
ArrayList.remove(0):
  → System.arraycopy(src, 1, dest, 0, size-1)

Bên trong:
  → JVM intrinsic — phương thức mà JVM thay thế bằng một lệnh máy tối ưu
  → memmove — hàm sao chép bộ nhớ chuẩn của C
  → SIMD — xử lý song song ở cấp CPU
  → Di chuyển 64 byte cho mỗi chu kỳ đồng hồ (cache line)

→ O(n) về lý thuyết, nhưng hằng số RẤT NHỎ
→ Với 1000 phần tử: ~1 μs
→ Nhanh hơn LinkedList O(1) có cấp phát!
```

### Resize: tại sao 1.5x?

```java
// Một số cài đặt std::vector của C++ dùng 2x (libstdc++ GCC), số khác dùng 1.5x hoặc 2x (libc++ Clang).
// Java ArrayList: 1.5x

// Tại sao?
// 1.5x cho phép tái sử dụng bộ nhớ:
//   10 → 15 (giải phóng 0-9)
//   15 → 22 (giải phóng 0-14)
//   22 → 33 (0-21 vẫn đang bận, nhưng 0-9 trống!)
//   → Có thể tái sử dụng khối 0-9

// 2x không cho phép:
//   10 → 20 (0-9 trống)
//   20 → 40 (0-19 bận)
//   → Khối 0-9 quá nhỏ cho 40
//   → Phân mảnh heap!
```

### Giới hạn Băng thông Bộ nhớ (Memory Bandwidth)

```
Với các list lớn (> 1M):
  add(e) bị giới hạn bởi tốc độ ghi RAM
  → ~25 GB/s cho DDR4
  → 1M ref (8 MB) → ~0.3 ms

Đây là giới hạn vật lý!
```

### CPU Pipeline và Branch Prediction

Branch prediction (dự đoán rẽ nhánh) — CPU dự đoán kết quả của điều kiện (if) và nạp trước các lệnh tiếp theo. Nếu dự đoán đúng — code thực thi không có độ trễ. Pipeline — CPU xử lý nhiều lệnh cùng lúc ở các giai đoạn khác nhau.

```java
// contains(e): tìm kiếm tuyến tính
for (int i = 0; i < size; i++) {
    if (array[i].equals(e)) return true;
}

// CPU branch predictor:
// → Trong lúc tìm kiếm, dự đoán "không tìm thấy"
// → Pipeline không bị gián đoạn
// → Gần như O(n) không có hình phạt (penalty)
```

### Kinh nghiệm Production

**Trường hợp thực tế: ensureCapacity tiết kiệm 30 lần resize**
```java
// ❌ Không có ensureCapacity
ArrayList<String> list = new ArrayList<>();
for (int i = 0; i < 1_000_000; i++) {
    list.add(data[i]);  // ~30 lần resize!
}

// ✅ Có ensureCapacity
ArrayList<String> list = new ArrayList<>(1_000_000);
for (int i = 0; i < 1_000_000; i++) {
    list.add(data[i]);  // 0 lần resize!
}

// Kết quả: -15% thời gian
```

### Best Practices

1. **get(index)** = O(1) — dùng cho các lần đọc thường xuyên
2. **add(e)** = O(1)* phân bổ — các lần resize là hiếm
3. **add(0, e)** = O(n) — nhưng nhanh nhờ SIMD
4. **removeIf()** = O(n) — thay vì vòng lặp xóa
5. **ensureCapacity()** — nếu biết trước kích thước
6. **binarySearch()** = O(log n) — cho các list đã sắp xếp
7. **trimToSize()** — sau khi xóa hàng loạt

### Tóm tắt cho Senior

- **get(index)** = O(1) — cache locality hoàn hảo
- **add(e)** = O(1)* phân bổ — resize × 1.5
- **add/remove(index)** = O(n) — nhưng SIMD làm nó nhanh hơn
- **contains** = O(n) → binarySearch = O(log n)
- **System.arraycopy** = memmove native
- **resize 1.5x** — ít phân mảnh hơn 2x
- **removeIf** = O(n) thay vì O(n²)
- **ensureCapacity** = tiết kiệm 30+ lần sao chép

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- get(index) = O(1), add(e) = O(1)* phân bổ, add/remove(index) = O(n)
- Amortized O(1): resize hiếm khi xảy ra (mỗi khi lấp đầy ~1.5 lần), N lần thêm = O(N) tổng cộng
- Resize × 1.5 (không phải 2x) — cho phép tái sử dụng bộ nhớ đã giải phóng, ít phân mảnh heap hơn
- System.arraycopy() = JVM intrinsic → memmove + SIMD — di chuyển 64 byte cho mỗi chu kỳ, hằng số RẤT nhỏ
- removeIf() = O(n) thay vì O(n²) trong vòng lặp — một lần duyệt để tìm + một lần dịch chuyển để xóa
- ensureCapacity() tiết kiệm 30+ lần resize khi nạp 1M phần tử (-15% thời gian)
- Với ArrayList đã sắp xếp: Collections.binarySearch() = O(log n) thay vì contains O(n)
- CPU branch prediction làm cho tìm kiếm tuyến tính gần như không có hình phạt — pipeline không bị gián đoạn

**Các câu hỏi phụ thường gặp:**
- "amortized O(1)" nghĩa là gì? — Một thao tác đơn lẻ có thể là O(n) trong lúc resize, nhưng O(1) trung bình qua N thao tác
- Tại sao resize 1.5x không phải 2x? — 1.5x cho phép tái sử dụng các khối bộ nhớ cũ, 2x gây phân mảnh heap
- Khi nào contains() có thể nhanh hơn O(n)? — Nếu list đã được sắp xếp — binarySearch = O(log n)
- Tại sao System.arraycopy() nhanh? — memmove native + các lệnh SIMD + CPU prefetching

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "add(e) luôn là O(1)" — trong lúc resize nó là O(n), thuật ngữ đúng là "amortized O(1)"
- ❌ "remove(index) = O(n) nghĩa là nó chậm" — System.arraycopy() rất nhanh nhờ SIMD
- ❌ "ArrayList luôn là O(n) cho tìm kiếm" — nếu đã sắp xếp, binarySearch = O(log n)
- ❌ "resize 2x tốt hơn vì hiếm hơn" — 2x gây phân mảnh heap và lãng phí bộ nhớ
