# When Is It Better to Use Composition Instead of Inheritance (Khi nào nên dùng Composition thay vì Inheritance)

## 🟢 Junior Level

**Composition được ưu tiên hơn inheritance** trong hầu hết các trường hợp. Đây là một trong những quy tắc chính từ cuốn "Effective Java" của Joshua Bloch. Inheritance tạo ra một mối liên hệ cứng nhắc giữa các class, trong khi composition thì linh hoạt.

**Analogy đơn giản:** Inheritance — giống như một hình xăm (mãi mãi), composition — giống như quần áo (có thể thay đổi bất cứ lúc nào).

**Vấn đề với inheritance:**
```java
// Xấu: inheritance để tái sử dụng code
public class MyHashSet extends HashSet<String> {
    private int addCount = 0;

    @Override
    public boolean add(String s) {
        addCount++;
        return super.add(s);
    }

    @Override
    public boolean addAll(Collection<? extends String> c) {
        addCount += c.size();  // LỖI: addAll gọi add!
        return super.addAll(c); // Sẽ đếm hai lần
    }
}
```

**Giải pháp composition:**
```java
// Tốt: composition + delegation
public class CountingHashSet {
    private final Set<String> set = new HashSet<>();
    private int addCount = 0;

    public boolean add(String s) {
        addCount++;
        return set.add(s);
    }

    public int getAddCount() { return addCount; }
}
```

**Khi nào dùng composition:**
- Khi bạn cần tái sử dụng code, nhưng không có mối quan hệ IS-A
- Khi bạn cần thay đổi hành vi tại runtime
- Khi parent class không được thiết kế cho inheritance

## 🟡 Middle Level

### Cách Hoạt Động

**Inheritance = White-box reuse**: subclass thấy nội bộ của parent (các trường và phương thức `protected`). Điều này tạo ra coupling mạnh.

**Composition = Black-box reuse**: tương tác chỉ thông qua public interface. Delegate có thể được thay thế mà không thay đổi code của delegator.

VTable — bảng con trỏ phương thức. Monomorphic = JIT biết loại chính xác → inlining (~1 ns). Megamorphic = 3+ loại → table lookup (~10-20 ns).

### Ứng Dụng Thực Tế

#### Khi composition thắng thế:

**1. Tránh Tính Dễ Vỡ (Fragile Base Class)**
```java
// Stack kế thừa Vector — vi phạm encapsulation
public class MyStack extends Vector<String> {
    public void push(String item) { addElement(item); }
    public String pop() { return removeElementAt(size() - 1); }
}
// Vấn đề: client có thể gọi insertElementAt(0) → LIFO bị phá vỡ!
// Stack giả định LIFO (last in — first out).
// Nhưng Vector cho phép insertElementAt(0, item) — chèn vào đầu.
// Bất kỳ client Vector nào cũng có thể né tránh invariant LIFO của stack.
```

**2. Polymorphism Động**
```java
// Thay đổi strategy tại runtime
public class PaymentService {
    private PaymentProcessor processor;

    public void setProcessor(PaymentProcessor processor) {
        this.processor = processor;  // Thay đổi tại runtime
    }
}
```

**3. API Purity**
Composition cho phép chỉ để lộ các phương thức cần thiết ra bên ngoài, ẩn các chi tiết nội bộ.

### Các Lỗi Thường Gặp

| Lỗi                                           | Giải pháp                          |
| ------------------------------------------------- | ---------------------------------- |
| Kế thừa từ `ArrayList` để thêm chức năng      | Composition với trường `List`     |
| `Stack extends Vector` — invariant bị phá vỡ         | `Stack` với `List` nội bộ      |
| Inheritance để truy cập các trường protected            | Truyền dữ liệu thông qua constructor  |

### Khi Nào Inheritance CHẤP NHẬN ĐƯỢC

| Trường hợp                    | Ví dụ                          | Tại sao OK                          |
| ----------------------- | --------------------------------- | -------------------------------- |
| **Mối quan hệ IS-A**   | `Dog extends Animal`             | Hierarchy loại thực sự             |
| **Mở rộng framework** | `AbstractHttpMessageConverter`   | Được thiết kế để mở rộng             |
| **Nhóm logic**    | `BaseEntity` với `id`, `createdAt` | Các trường chung cho tất cả entity |

// BaseEntity là một sự thỏa hiệp. Nó không phải SRP thuần túy, mà là chủ nghĩa thực dụng:
// tất cả các entity DB cần một id. Điều quan trọng là BaseEntity
// không chứa business logic, chỉ các trường hạ tầng.

### Khi Nào KHÔNG Nên Dùng Composition

- Các framework với Template Method (được thiết kế cho inheritance)
- Khi cần truy cập vào các phương thức `protected` của parent
- Khi polymorphism thông qua base type là quan trọng

## 🔴 Senior Level

### Triển Khai Nội Bộ Ở Cấp Độ JVM

**Overhead VTable:**
```
Inheritance:
  Object → A → B → C → D → E (5 cấp)
  e.foo() → invokevirtual → VTable lookup → 5 lần đuổi theo con trỏ

Composition với final:
  class Service { private final Delegate d; }
  s.d.run() → monomorphic call → JIT inline → 1 lệnh gọi trực tiếp
```

**Bố Cục Bộ Nhớ:**
```
Inheritance: Object Header (12) + các trường A + các trường B + các trường C = một object lớn
Composition: Service (16 header + ref) + Delegate (16 header + các trường) = hai object + tham chiếu
```

### Đánh Đổi Kiến Trúc

**Inheritance:**
- ✅ Ưu điểm: Polymorphism, tái sử dụng code, Template Method, mở rộng framework
- ❌ Nhược điểm: Fragile base class, ô nhiễm API, binding tĩnh, coupling

**Composition:**
- ✅ Ưu điểm: Linh hoạt tại runtime, API sạch, khả năng test, coupling lỏng lẻo
- ❌ Nhược điểm: Boilerplate (delegation), nhiều object hơn, overhead gián tiếp

### Edge Cases

1. **Diamond Problem**: Java cấm multiple inheritance của class
   - **Giải pháp**: Composition + nhiều interface (default method)

2. **Sealed Class (Java 17+)**: Giới hạn phạm vi các subclass
   ```java
   public sealed class Expr permits Constant, Plus, Minus { }
   // Hierarchy có thể dự đoán, pattern matching
   ```

3. **Ràng Buộc Framework**: Spring/Hibernate đôi khi yêu cầu inheritance
   - **Giải pháp**: Cô lập trong một tầng, dùng composition cho business logic

### Hiệu Năng

| Metric           | Inheritance                | Composition         |
| ---------------- | -------------------------- | -------------------- |
| **Độ sâu VTable** | 5+ cấp → megamorphic    | N/A (lệnh gọi trực tiếp)  |
| **Inlining**     | Khó hơn với hierarchy sâu | Dễ hơn với final   |
| **Bộ nhớ**       | Một object lớn           | N object + tham chiếu    |
| **Startup**      | Nhanh hơn (ít object hơn)     | Hơi chậm hơn         |

- **VTable lookup**: ~1-3 ns cho monomorphic, ~10-20 ns cho megamorphic
- **Delegate final**: JIT inline → ~0.3 ns (lệnh gọi trực tiếp)

### Thread Safety

- **Inheritance**: Một monitor cho toàn bộ object → tranh chấp
- **Composition**: Các lock khác nhau cho các delegate khác nhau → concurrency chi tiết hơn

```java
class ConcurrentService {
    private final ReadDelegate read = new ReadDelegate();
    private final WriteDelegate write = new WriteDelegate();
    // Các lock khác nhau → thực thi song song
}
```

### Kinh Nghiệm Production

**Refactoring trong e-commerce:**
`OrderProcessor extends BaseService` với 3000 dòng. Vấn đề: thay đổi logic validation phá vỡ việc lưu. Refactoring: trích xuất `OrderValidator`, `OrderRepository`, `NotificationService` thông qua composition. **Kết quả**: bug regression giảm 65%.

### Monitoring

**ArchUnit:**
```java
@ArchTest
static void no_deep_inheritance = classes()
    .should().haveLessThanNAncestors(3)
    .because("Deep inheritance is fragile");
```

**SonarQube**: Depth of Inheritance Tree > 5 → Code Smell

### Best Practices Cho Highload

- **Delegate final** để inline
- **Sealed class** cho inheritance có kiểm soát
- **Interface + Composition** thay vì các hierarchy sâu
- **Pure DI** cho các phần quan trọng về hiệu năng
- Chọn composition theo mặc định, nhưng không cực đoan. Inheritance — khi có một IS-A thực sự, framework yêu cầu nó, hoặc các trường hạ tầng chung.

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- Composition được ưu tiên: linh hoạt tại runtime, API sạch, khả năng test, coupling lỏng lẻo
- `Stack extends Vector` — vi phạm invariant: Vector cho phép `insertElementAt(0)` — LIFO bị phá vỡ
- `MyHashSet extends HashSet` — đếm hai lần: `addAll` gọi `add` nội bộ, counter tăng gấp đôi
- VTable: 5+ cấp → megamorphic (~10-20 ns), delegate final → JIT inline (~0.3 ns)
- Diamond Problem được giải quyết bằng composition + nhiều interface (default method)
- Sealed Class (Java 17+) — giới hạn phạm vi các subclass

**Các câu hỏi phụ thường gặp:**
- **Tại sao `Stack extends Vector` xấu?** — Client Vector có thể né tránh invariant LIFO của stack thông qua `insertElementAt`
- **Khi nào inheritance CHẤP NHẬN ĐƯỢC?** — Mối quan hệ IS-A, mở rộng Framework, nhóm logic (`BaseEntity`)
- **False sharing trong ngữ cảnh God Object là gì?** — Các trường của các trách nhiệm khác nhau trong cùng cache line → các CPU core làm mất hiệu lực cache của nhau
- **Thread Safety: composition vs inheritance?** — Composition: các lock khác nhau cho các delegate khác nhau → concurrency chi tiết hơn

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Kế thừa từ `ArrayList` là cách bình thường để thêm chức năng" (vi phạm encapsulation)
- "Composition luôn cho hiệu năng tốt hơn" (trong hot path với switch trên enum — inheritance có thể nhanh hơn)
- "BaseEntity là một vi phạm SRP" (chủ nghĩa thực dụng: tất cả entity cần một id, điều quan trọng — không có business logic)
