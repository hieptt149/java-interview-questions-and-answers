# What is the difference between AutoCloseable and Closeable? (Sự khác biệt giữa AutoCloseable và Closeable là gì?)

## Junior Level

### Câu trả lời ngắn gọn

`Closeable` là một trường hợp đặc biệt của `AutoCloseable` chỉ dành cho các thao tác I/O.

```
AutoCloseable (java.lang)
  └── Closeable (java.io)
        └── FileInputStream, BufferedReader, v.v.
```

### Các khác biệt chính

| Đặc điểm       | Closeable            | AutoCloseable      |
| -------------- | -------------------- | ------------------ |
| Package        | `java.io`            | `java.lang`        |
| Exception      | `throws IOException` | `throws Exception` |
| Mục đích       | Chỉ I/O              | Bất kỳ resource nào |

### Ví dụ

```java
// Closeable - chỉ I/O
try (FileInputStream fis = new FileInputStream("file.txt")) {
    fis.read();
} // close() throws IOException

// AutoCloseable - bất kỳ resource nào
try (Connection conn = dataSource.getConnection()) {
    conn.createStatement().executeQuery("SELECT 1");
} // close() throws SQLException
```

### Nên dùng cái nào

- Cho file, stream - `Closeable` (đã được implement sẵn trong JDK)
- Cho các resource tùy chỉnh (DB, transaction) - `AutoCloseable`

---

## Middle Level

### Cây phân cấp (từ Java 7)

`Closeable` kế thừa `AutoCloseable`. Điều này được làm để tương thích ngược - tất cả các class I/O cũ hoạt động được trong try-with-resources.

### Khác biệt về hợp đồng

**Idempotency:**
- `Closeable` - Javadoc yêu cầu idempotency: "nếu đã đóng, lời gọi không có tác dụng"
- `AutoCloseable` - Javadoc khuyến nghị: "khuyến nghị mạnh mẽ..."
- Trên thực tế, cả hai đều nên là idempotent.

**Lý do:** một số resource (transaction) có thể ném exception khi cố đóng một transaction đã đóng.

### Flushable & Closeable

Nhiều class `Closeable` cũng implement `Flushable`:

Flushable - interface với phương thức flush(). Flush = đẩy dữ liệu đã buffer ra. BufferedOutputStream.close() trước tiên gọi flush() để ghi dữ liệu đã buffer ra đĩa.

```java
public class BufferedOutputStream extends FilterOutputStream
    implements Flushable, Closeable {

    public void close() throws IOException {
        flush(); // Đẩy buffer ra trước khi đóng
        out.close();
    }
}
```

Khi đóng, `close()` thường gọi `flush()`. Nhưng điều này phụ thuộc vào cách hiện thực.

### Exception Narrowing (thu hẹp exception)

Khi implement `AutoCloseable` cho các service của bạn, hãy bỏ `throws Exception`:

```java
// Xấu
public class MyService implements AutoCloseable {
    public void close() throws Exception { }
}

// Tốt
public class MyService implements AutoCloseable {
    public void close() { } // Không throws - sạch sẽ và an toàn
}
```

---

### Nên implement cái nào trong class của bạn

- **Closeable** - nếu class của bạn là một I/O stream (làm việc với byte/ký tự)
- **AutoCloseable** - nếu class của bạn là bất kỳ resource nào khác (DB connection, transaction, lock)

## Senior Level

### Ưu tiên của Suppressed Exception

Khi đóng nhiều resource trong TWR, thứ tự - **LIFO** (Last In, First Out). Exception từ resource bên trong nhất được thêm cuối cùng vào danh sách suppressed.

// Khi đóng A, B, C (theo thứ tự này), nếu cả ba đều lỗi:
// A - exception chính
// B và C - suppressed (thứ tự: B rồi C, LIFO)

### Interrupted Close

Nếu `close()` là chặn (blocking) (đóng một network pool) và thread bị interrupt - `InterruptedException`. TWR không xử lý interrupt một cách kỳ diệu - bạn vẫn cần `catch`.

### Static Analysis

`instanceof Closeable` cũng có nghĩa là `instanceof AutoCloseable`. Nhưng không đúng theo chiều ngược lại!

### Các trường hợp biên (Edge Case)

- **Resource dạng transaction** - `close()` có thể có nghĩa là "commit". Lời gọi lặp lại phải an toàn
- **Resource dùng chung** - nếu resource được dùng bởi nhiều component, đóng một cái không được làm hỏng các cái khác

### Chẩn đoán

Trong các hệ thống Highload, rò rỉ file descriptor do chọn sai giữa hai interface này trong các wrapper tùy chỉnh - một trong những nguyên nhân thường gặp nhất của JVM crash sau vài ngày hoạt động.

- **`lsof -p <pid>`** - hiển thị các file descriptor đang mở
- **`jstack`** - hiển thị các thread bị chặn trong `close()`
- **Metric** - theo dõi số lượng connection đang mở qua Micrometer

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- `Closeable` kế thừa từ `AutoCloseable` (cây phân cấp: `AutoCloseable` <- `Closeable`)
- `Closeable` nằm trong `java.io`, throws `IOException`; `AutoCloseable` nằm trong `java.lang`, throws `Exception`
- `Closeable` - chỉ cho các I/O stream; `AutoCloseable` - cho bất kỳ resource nào (DB, transaction, lock)
- Cả hai đều nên là idempotent, nhưng với `Closeable` đó là một yêu cầu nghiêm ngặt của Javadoc
- Khi implement, hãy thu hẹp kiểu exception hoặc bỏ `throws` hoàn toàn
- Thứ tự đóng trong TWR - LIFO (mở sau cùng đóng đầu tiên)

**Các câu hỏi phụ thường gặp:**
- **Nên implement interface nào trong class của bạn?** - `Closeable` nếu nó là một I/O stream, `AutoCloseable` cho mọi thứ khác
- **Exception Narrowing là gì?** - Khi implement `AutoCloseable`, thay `throws Exception` bằng kiểu cụ thể hoặc bỏ đi
- **Tại sao `Closeable` throws `IOException`?** - Về mặt lịch sử: được tạo cho các thao tác I/O, nơi `IOException` là lỗi duy nhất được lường trước
- **Điều gì xảy ra nếu bạn đóng một resource dùng chung từ hai component?** - Lời gọi thứ hai phải an toàn (idempotency); nếu không - bug kiến trúc

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Chúng giống nhau" - Khác package, khác hợp đồng, và khác mục đích
- "AutoCloseable chỉ throws RuntimeException" - Throws `Exception` (checked), nhưng bạn có thể thu hẹp
- "Thứ tự đóng không quan trọng" - LIFO là then chốt: resource bên ngoài nhất đóng cuối cùng
