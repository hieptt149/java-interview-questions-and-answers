# How does Circuit Breaker work and what states does it have (Circuit Breaker hoạt động như thế nào và có những trạng thái nào)

## Junior Level

Một Circuit Breaker có **ba trạng thái**:

1. **CLOSED** — mọi thứ bình thường, các call đi qua
2. **OPEN** — service đang "hỏng", các call bị chặn, fallback được trả về ngay lập tức
3. **HALF-OPEN** — call thử nghiệm để kiểm tra

```
Bắt đầu: CLOSED (các call đi qua)
        ↓ quá nhiều lỗi
       OPEN (chặn các call trong 10 giây)
        ↓ đã hết thời gian
       HALF-OPEN (một call thử nghiệm)
        ↓ thành công -> CLOSED
        ↓ lỗi -> OPEN (chờ lại)
```

---

## Middle Level

### Chi Tiết Chuyển Đổi

**CLOSED -> OPEN:**
```
failureRate > ngưỡng (ví dụ 50%)
HOẶC slowCallRate > ngưỡng (ví dụ > 50% call chậm)
```

**OPEN -> HALF-OPEN:**
```
waitDurationInOpenState đã hết (ví dụ 10 giây)
```

**HALF-OPEN -> CLOSED:**
```
permittedNumberOfCallsInHalfOpenState call thành công
(ví dụ 3 call thành công)
```

**HALF-OPEN -> OPEN:**
```
Bất kỳ lỗi nào trong trạng thái HALF-OPEN
```

### Các Lỗi Thường Gặp

1. **Kích thước sliding window sai:**
```
slidingWindowSize = 5 -> quá nhỏ
Một lỗi = tỷ lệ lỗi 20%
Tốt hơn: 10-100 call
```

## Senior Level

### Triển Khai Nội Bộ

**Theo dõi metric:**
```java
// Ring buffer để lưu kết quả các call
class SlidingWindow {
    private final CircularArray measurements;

    void record(CallResult result) {
        measurements.add(result);
        // Nếu minCalls không bao giờ đạt được — breaker sẽ KHÔNG open, ngay cả khi TẤT CẢ
        // call THẤT BẠI. Điều này quan trọng: dưới traffic thấp circuit breaker có thể không kích hoạt.
        if (measurements.size() >= minCalls) {
            double failureRate = calculateFailureRate();
            if (failureRate > threshold) {
                stateTransition(CLOSED, OPEN);
            }
        }
    }
}
```

### Kinh Nghiệm Production

**Monitoring:**
```java
// Metric cho monitoring
CircuitBreaker.Metrics metrics = circuitBreaker.getMetrics();
metrics.getFailureRate();       // % lỗi
metrics.getNumberOfBufferedCalls();
metrics.getNumberOfFailedCalls();
```

### Best Practices

// Các pattern này KHÔNG phải là lựa chọn thay thế cho nhau, chúng bổ sung cho nhau:
// Retry + Timeout + CircuitBreaker được dùng cùng nhau.

```
✅ minimumNumberOfCalls = 10+ (mẫu có ý nghĩa thống kê)
✅ failureRateThreshold = 50% (thỏa hiệp: đừng open từ một lỗi, nhưng đừng chờ đến khi mọi thứ sụp đổ)
✅ waitDurationInOpenState = 10-60s (đủ thời gian để service phụ thuộc khởi động lại, nhưng không quá lâu)
✅ permittedCallsInHalfOpen = 3-5

❌ Sliding window quá nhỏ
❌ Thời gian chờ quá ngắn
❌ Không giám sát metric
```

## Interview Cheat Sheet

**Cần phải biết:**
- Ba trạng thái: CLOSED, OPEN, HALF-OPEN với quy tắc chuyển đổi rõ ràng
- CLOSED->OPEN: tỷ lệ lỗi > ngưỡng (50%), OPEN->HALF-OPEN: đã hết thời gian chờ
- HALF-OPEN->CLOSED: N call thành công, HALF-OPEN->OPEN: bất kỳ lỗi nào
- Sliding window (dựa trên count hoặc thời gian) để theo dõi metric
- minimumNumberOfCalls = 10+ cho một mẫu có ý nghĩa thống kê
- Dưới traffic thấp circuit breaker có thể không kích hoạt (chưa đạt minCalls)
- Ring buffer để lưu kết quả các call

**Các câu hỏi phụ thường gặp:**
- **permittedNumberOfCallsInHalfOpen là gì?** Cần bao nhiêu call thử nghiệm trong HALF-OPEN — nếu tất cả thành công, quay lại CLOSED.
- **Tại sao minimumNumberOfCalls quan trọng?** Không có nó, breaker sẽ open từ 1-2 lỗi khi traffic thấp.
- **Cách giám sát CB?** Metric: tỷ lệ lỗi, các call được buffer, các call thất bại, trạng thái hiện tại.
- **Count-based vs time-based window?** Count-based = N call cuối cùng, time-based = các call trong T giây.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Sliding window = 5 là đủ" — không, một lỗi = tỷ lệ lỗi 20%
- "Wait duration = 1 giây" — service sẽ không có đủ thời gian để khởi động lại
- "CB hoạt động mà không có metric" — không thể cấu hình mà không có giám sát
- "HALF-OPEN cho qua tất cả traffic" — không, chỉ permittedNumberOfCalls
