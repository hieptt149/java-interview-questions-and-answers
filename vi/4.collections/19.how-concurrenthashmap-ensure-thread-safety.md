# How does ConcurrentHashMap ensure thread-safety? (ConcurrentHashMap đảm bảo thread-safety như thế nào?)

## 🟢 Junior Level

**ConcurrentHashMap** là thread-safe nhờ ba cơ chế:

1. **CAS** — cho việc chèn vào một bucket rỗng (không có khóa)
2. **Volatile** — để tất cả các luồng nhìn thấy dữ liệu mới nhất
3. **Synchronized** — chỉ cho các va chạm (khóa một bucket duy nhất)

**Cách chúng hoạt động cùng nhau:**
- **CAS** = chèn một phần tử mới mà không có khóa
- **Volatile** = tính khả kiến (visibility) của các thay đổi giữa các luồng (mỗi luồng ngay lập tức nhìn thấy các phần tử mới)
- **Synchronized** = bảo vệ khi có va chạm (khi hai luồng ghi vào cùng một bucket đồng thời)

```java
// An toàn từ các luồng khác nhau:
ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>();

// Luồng 1:
map.put("A", 1);

// Luồng 2 (đồng thời):
map.put("B", 2);

// Cả hai đều an toàn!
```

## 🟡 Middle Level

### Ba trụ cột của an toàn

**1. CAS (Compare-And-Swap):**
```java
// Cho một bucket rỗng:
if (CAS(table[i], null, newNode)) {
    // Thành công! Đã chèn mà không có khóa
} else {
    // Luồng khác đã chèn → thử lại
}
```

**2. Volatile:**
```java
// Tất cả các trường đều volatile:
transient volatile Node[] table;
volatile V val;
volatile Node next;

// → Các lần ghi của một luồng nhìn thấy được bởi tất cả
// → get() không có khóa!
```

**3. Synchronized cho mỗi bucket:**
```java
// Khi có va chạm:
synchronized (firstNode) {  // Chỉ bucket này!
    // Chèn/xóa
}
// → Các bucket khác làm việc song song!
```

### Các phương thức nguyên tử (atomic)

```java
map.putIfAbsent(key, value);      // Nguyên tử
map.computeIfAbsent(key, func);   // Nguyên tử
map.merge(key, value, func);      // Nguyên tử

// Nếu không có các phương thức này:
// ❌ Race condition!
// Race condition từng bước:
// Luồng 1: containsKey = false (key không có mặt)
// Luồng 2: containsKey = false (key vẫn không có mặt)
// Luồng 1: put(key, value1)  ← đã chèn
// Luồng 2: put(key, value2)  ← GHI ĐÈ! Mất bản cập nhật (lost update).
if (!map.containsKey(key)) {
    map.put(key, value);  // Luồng khác có thể xen vào!
}
```

## 🔴 Senior Level

### Khi nào KHÔNG dùng ConcurrentHashMap

1. **Truy cập đơn luồng** — overhead của CAS/volatile mà không có lý do
2. **Map chỉ đọc sau khi publish** — HashMap là đủ (sau khi publish an toàn)
3. **Cần các giá trị null** — CHM cấm các key và value null

### ForwardingNode và Parallel Resizing

```java
// Khi resize:
// Bucket cũ → ForwardingNode

// Luồng ghi nhìn thấy ForwardingNode:
if (node instanceof ForwardingNode) {
    // Giúp với việc resize!
    table = helpTransfer(table, forwardingNode);
}

→ Resize được phân tán, không chặn tất cả các luồng!
```

### CounterCells (pattern LongAdder)

LongAdder — chiến lược: thay vì một biến volatile duy nhất (contention khi ghi đồng thời), một mảng các bộ đếm. Mỗi luồng ghi vào cell riêng của nó, kết quả = tổng của tất cả các cell.

```java
// Thay vì một size volatile duy nhất:
transient volatile CounterCell[] counterCells;

// Mỗi luồng:
counterCells[hash(threadId) & mask].value++;

// size() = sum(counterCells)

→ Contention tối thiểu!
```

### Bảo vệ Treeification

```
> 8 phần tử trong một bucket → cây đỏ-đen
→ Ngay cả khi bị tấn công Hash DoS: O(log n)

// Thay thế Node → TreeNode
// Đồng bộ hóa vẫn trên HEAD
```

### ReservationNode

ReservationNode = một node placeholder khóa bucket trong khi giá trị đang được tính toán trong `computeIfAbsent`. Ngăn các bản trùng lặp từ các luồng khác.

```java
// computeIfAbsent cho một bucket rỗng:
// Chèn ReservationNode → đồng bộ hóa trên nó
// → Ngăn các bản trùng lặp trong khi hàm tính toán
```

### Chẩn đoán contention

```java
// Nếu CHM chậm:
// 1. async-profiler → trạng thái blocked
// 2. Nhiều luồng trên CHM.put
// 3. → Tất cả đều đụng vào một bucket!

// Nguyên nhân: hashCode() tệ
// → Tất cả các key hash vào một bucket
// → Synchronized trên một bucket duy nhất
// → 0 song song!

// Giải pháp: viết lại hashCode()
```

### Java 7 so với Java 8+

```
Java 7: Segment[] segments (16 cố định)
  → Khóa cho mỗi segment
  → size() = khóa TẤT CẢ các segment

Java 8+: Node-level locking
  → Khóa cho mỗi bucket
  → CAS cho các bucket rỗng
  → size() = tổng của các CounterCell
  → Parallel resizing
```

### Best Practices

1. **CAS** = lock-free cho các key mới
2. **Volatile** = tính khả kiến mà không có khóa
3. **Synchronized** = chỉ cho mỗi bucket
4. **helpTransfer** = parallel resize
5. **CounterCells** = size() có khả năng mở rộng
6. **hashCode tệ** = kẻ thù chính
7. **compute** = đừng chặn quá lâu

### Tóm tắt cho Senior

- **CAS** cho các bucket rỗng, **Synchronized** cho các va chạm
- **Volatile** = đọc lock-free
- **ForwardingNode** = parallel resize
- **CounterCells** = pattern LongAdder cho size
- **Treeification** = bảo vệ DoS
- **hashCode tệ** = contention = 0 song song
- **helpTransfer** = các luồng giúp với việc resize

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Ba cơ chế thread-safety: CAS (chèn lock-free vào bucket rỗng), volatile (tính khả kiến giữa các luồng), synchronized (bảo vệ va chạm ở cấp bucket)
- CAS = lệnh CPU nguyên tử: "ghi giá trị mới chỉ khi giá trị hiện tại bằng với giá trị mong đợi." Hai luồng ghi đồng thời — một cái thành công, cái kia thử lại.
- Các trường volatile: table, Node.val, Node.next — get() không có khóa, đảm bảo happens-before
- Synchronized chỉ trên HEAD của bucket — các bucket khác làm việc song song
- Các phương thức nguyên tử: putIfAbsent, computeIfAbsent, merge — thay thế check-then-act (race condition)
- ForwardingNode khi resize — các luồng ghi nhìn thấy nó và gọi helpTransfer() (parallel resize)
- CounterCells = pattern LongAdder: mảng các bộ đếm, mỗi luồng ghi vào cell riêng của nó, size() = tổng
- Treeification khi có > 8 phần tử cho mỗi bucket — bảo vệ Hash DoS, O(log n) ngay cả khi bị tấn công
- ReservationNode trong computeIfAbsent — placeholder ngăn các bản trùng lặp từ các luồng khác

**Các câu hỏi phụ thường gặp:**
- **Tại sao không thể thay CHM bằng HashMap trong code đa luồng?** — Race condition: hai luồng đồng thời làm containsKey = false, cả hai làm put — một cái ghi đè cái kia. Mất các bản cập nhật.
- **Race condition trong ngữ cảnh của Map là gì?** — Luồng 1 kiểm tra "key không có mặt", Luồng 2 kiểm tra "key không có mặt", cả hai chèn — cái thứ hai ghi đè cái thứ nhất. Được giải quyết bằng computeIfAbsent (nguyên tử).
- **Làm sao chẩn đoán contention trong CHM?** — async-profiler hiển thị thời gian bị chặn. Nguyên nhân: hashCode() tệ → tất cả các key trong một bucket → synchronized trên một bucket duy nhất → 0 song song.
- **CHM của Java 8+ khác Java 7 như thế nào?** — Java 7: Segment[] (16 cố định, khóa cho mỗi segment). Java 8+: node-level locking + CAS, parallel resize, CounterCells.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "CHM khóa toàn bộ map khi ghi" — chỉ một bucket (synchronized trên HEAD)
- ❌ "get() trong CHM dùng synchronized" — không, đọc lock-free thông qua volatile
- ❌ "CHM dùng Segment locking trong Java 8+" — đó là lỗi thời, giờ là node-level locking
- ❌ "computeIfAbsent có thể được thay bằng containsKey + put" — không, đó không phải là nguyên tử, race condition
