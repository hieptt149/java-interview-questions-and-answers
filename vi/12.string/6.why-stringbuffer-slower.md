# Why StringBuffer is Slower than StringBuilder? (Tại sao StringBuffer chậm hơn StringBuilder?)

## 🟢 Junior Level

`StringBuffer` chậm hơn vì mỗi một trong các method của nó đều được đánh dấu bằng từ khóa `synchronized`. Điều này có nghĩa là trước khi thực thi bất kỳ thao tác nào (kể cả một `append` đơn giản), Java phải lấy một "monitor" (lock) của object.

**Ví dụ minh họa đơn giản:** Hãy tưởng tượng một cánh cửa phòng tắm:
- `StringBuilder` — một cánh cửa không có khóa. Bước vào và làm việc của bạn.
- `StringBuffer` — một cánh cửa có khóa. Bạn cần mở khóa trước, bước vào, làm việc, khóa lại. Ngay cả khi bạn ở một mình trong tòa nhà.

**Ví dụ:**
```java
StringBuilder sb = new StringBuilder();  // Không lock — nhanh
StringBuffer sb2 = new StringBuffer();   // Có lock — chậm hơn

for (int i = 0; i < 1_000_000; i++) {
    sb.append("x");   // ~15ms
    sb2.append("x");  // ~25ms (chậm hơn 60%)
}
```

// Các con số là gần đúng (JMH, đơn luồng, JDK 17, x86_64).
// Có thể khác trên phần cứng của bạn, nhưng tỷ lệ vẫn giữ nguyên.

**Khi nào điều này quan trọng:** Chỉ khi bạn gọi hàng triệu thao tác. Với các tác vụ thông thường sự khác biệt không đáng chú ý.

## 🟡 Middle Level

### Tại Sao synchronized Làm Chậm Mọi Thứ

Mỗi method synchronized của `StringBuffer` đòi hỏi:
1. **Lấy Monitor** — kiểm tra xem object có bị khóa bởi thread khác không
2. **Memory Barrier** — bộ xử lý đồng bộ hóa cache với bộ nhớ chính
3. **Giải phóng Monitor** — sau khi method hoàn thành

Ngay cả khi chỉ có một thread duy nhất, JVM vẫn thực hiện các bước này.

### Nơi Nó Được Dùng Trong Thực Tế
`StringBuffer` là di sản từ Java 1.0. Trong code hiện đại nó thực tế không được dùng. Kịch bản duy nhất: một object StringBuilder thực sự được dùng từ nhiều thread (đây bản thân nó là một pattern hiếm và đáng ngờ).

### Các Lỗi Điển Hình
1. **Lỗi:** Nghĩ rằng `StringBuffer` cần thiết cho "sự an toàn"
   **Giải pháp:** Nếu mỗi thread dùng buffer riêng của mình — `StringBuilder` an toàn

2. **Lỗi:** Dùng `StringBuffer` cho việc nối chuỗi trong vòng lặp "để phòng khi cần"
   **Giải pháp:** Việc nối chuỗi trong vòng lặp gần như luôn là đơn luồng — `StringBuilder`

### So Sánh Hiệu Năng (Chế Độ Đơn Luồng)
| Thao tác  | StringBuilder  | StringBuffer   | Chênh lệch |
| ---------- | -------------- | -------------- | ---------- |
| 1M append  | ~15ms          | ~25ms          | +66%       |
| 1M insert  | ~20ms          | ~35ms          | +75%       |
| 1M delete  | ~10ms          | ~18ms          | +80%       |

## 🔴 Senior Level

### Hiện Thực Nội Bộ

```java
// StringBuffer — MỌI method public đều synchronized
public synchronized StringBuffer append(String str) {
    toStringCache = null;
    super.append(str);
    return this;
}

// StringBuilder — KHÔNG một method synchronized nào
public StringBuilder append(String str) {
    super.append(str);
    return this;
}
```

Cả hai đều ủy quyền cho `AbstractStringBuilder`, nhưng wrapper `StringBuffer` thêm synchronized trên mỗi lời gọi.

### Điều Gì Đứng Sau synchronized

1. **Monitor Enter/Exit:** Các lệnh JVM `monitorenter` và `monitorexit`
2. **Memory Barrier:** LoadLoad, StoreStore, LoadStore, StoreLoad — bộ xử lý flush và làm mất hiệu lực các dòng cache
3. **Object Header:** Thông tin chủ sở hữu lock được ghi trong mark word của object

### Tối Ưu Hóa Của JVM: Lock Elision Và Lock Coarsening

**Lock Elision (loại bỏ lock):**
```java
void foo() {
    StringBuffer sb = new StringBuffer(); // Escape analysis: object không "thoát"
    sb.append("a");                       // JIT: synchronized có thể bị loại bỏ!
    sb.append("b");
}
```
HotSpot qua Escape Analysis có thể chứng minh object không hiển thị với các thread khác và loại bỏ synchronized.

**Lock Coarsening (mở rộng lock):**
```java
StringBuffer sb = ...;
sb.append("a");  // lấy monitor
sb.append("b");  // lấy monitor
sb.append("c");  // lấy monitor

// JIT có thể gộp thành một lock:
// synchronized(sb) { append("a"); append("b"); append("c"); }
```

// JIT chỉ áp dụng coarsening nếu nó thấy các lời gọi tuần tự
// trong một method có thể biên dịch. Nếu các lời gọi trải rộng qua các
// method khác nhau — coarsening là không thể.

**Nhưng:** Các tối ưu hóa này không được đảm bảo. Chúng phụ thuộc vào:
- `-XX:+EliminateLocks` (bật theo mặc định)
- Ngân sách biên dịch C2
- Kích thước method (ngân sách inlining)

### Các Trường Hợp Biên

1. **Biased Locking (đã loại bỏ trong Java 15):** Trước đây JVM "thiên vị" monitor cho thread đầu tiên, khiến các lần chiếm giữ tiếp theo miễn phí. Đã bị loại bỏ do overhead trong container.

2. **Truy cập bị tranh chấp:** Nếu 2+ thread thực sự cạnh tranh cho `StringBuffer`:
   - Thread A: BỊ CHẶN → context switch → OS scheduling → tiếp tục
   - Context switch: ~1-10μs (đắt hơn nhiều so với lấy monitor không tranh chấp)

3. **False Sharing:** Monitor của object `StringBuffer` có thể gây ra false sharing với các object lân cận trong dòng cache.

### Hiệu Năng (Benchmark Chi Tiết)
| Kịch bản               | StringBuilder | StringBuffer   | Chênh lệch       |
| ---------------------- | ------------- | -------------- | ----------- |
| 1 thread, không escape    | 15ms          | 18ms (elision) | +20%        |
| 1 thread, escape      | 15ms          | 25ms           | +66%        |
| 4 thread, không contention | 15ms x4     | 25ms x4        | +66%        |
| 4 thread, có contention  | 15ms x4       | **200ms**      | **+1233%**  |

### Kinh Nghiệm Production
**Kịch bản:** Logging trong một web service (50K RPS):
- `StringBuffer` cho việc format mỗi log: latency p99 = 8ms
- `StringBuilder`: latency p99 = 5ms
- Chênh lệch 3ms × 50K = 150 CPU-giây/giây → 150 core bị lãng phí

### Best Practices Cho Highload
- `StringBuilder` — lựa chọn mặc định
- `StringBuffer` — **chỉ** khi một buffer thực sự được chia sẻ giữa các thread
- Nếu bạn cần một buffer thread-safe, tốt hơn nên dùng `StringBuilder` + đồng bộ hóa bên ngoài (kiểm soát độ chi tiết)
- Cho hiệu năng tối đa: `StringBuilder` với `initialCapacity` + tránh cấp phát lại

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- `StringBuffer` chậm hơn do `synchronized` trên mỗi method
- synchronized đòi hỏi: monitorenter/monitorexit, memory barrier, giải phóng monitor
- Ngay cả ở chế độ đơn luồng, JVM vẫn thực hiện tất cả các bước đồng bộ hóa
- JVM có thể tối ưu hóa qua Lock Elision (Escape Analysis), nhưng điều này không được đảm bảo
- Biased Locking đã loại bỏ trong Java 15 — overhead của `StringBuffer` ở chế độ đơn luồng thậm chí còn cao hơn
- Contention (2+ thread): context switch ~1-10μs, đắt hơn nhiều so với lấy monitor

**Các câu hỏi phụ thường gặp:**
- **`StringBuffer` chậm hơn bao nhiêu?** — ~66% chậm hơn ở chế độ đơn luồng, ~1200%+ với contention 4 thread.
- **Lock Elision là gì?** — JIT qua Escape Analysis chứng minh object không hiển thị với các thread khác và loại bỏ `synchronized`. Không được đảm bảo.
- **Lock Coarsening là gì?** — JIT gộp các lời gọi synchronized tuần tự thành một lock. Chỉ hoạt động trong một method có thể biên dịch.
- **Tại sao Biased Locking bị loại bỏ?** — overhead trong container. Trong Java 15+, overhead của `StringBuffer` thậm chí còn cao hơn.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "`StringBuffer` nhanh hơn ở chế độ đơn luồng" — chậm hơn do synchronized
- ❌ "JVM luôn tối ưu hóa synchronized" — Lock Elision không được đảm bảo
- ❌ "`StringBuffer` cần cho mọi chương trình đa luồng" — chỉ khi MỘT buffer được chia sẻ
- ❌ "Sự khác biệt không đáng chú ý trong thực tế" — ở 50K RPS: 3ms × 50K = 150 CPU-giây/giây bị lãng phí
