# What is a memory leak and how to detect it? (Memory leak là gì và cách phát hiện nó?)

## Junior Level

**Memory Leak (rò rỉ bộ nhớ)** — các đối tượng không còn cần thiết nữa nhưng vẫn nằm lại trong bộ nhớ.

**Ví dụ minh họa đơn giản:** Bạn đã vứt rác đi nhưng quên đóng cửa. Rác cứ chất đống lên.

**Triệu chứng:**
- Ứng dụng ngày càng chậm hơn
- GC chạy liên tục
- Cuối cùng là `OutOfMemoryError`

**Cách phát hiện:**
1. Bật dump: `-XX:+HeapDumpOnOutOfMemoryError`
2. Mở dump trong Eclipse MAT
3. Tìm các đối tượng lớn nhất
4. Hiểu tại sao chúng không bị loại bỏ

## Middle Level

### Phương pháp luận Delta Analysis

```
1. Baseline: dump sau khi khởi động và warmup
2. Load: stress test
3. Cooldown: System.gc() để buộc dọn dẹp (CHỈ để chẩn đoán, KHÔNG dùng trong production!)
4. Snapshot: dump thứ hai
5. Compare: các class nào đã tăng lên?
```

### Shallow vs Retained Heap

```
Shallow Heap = kích thước riêng của đối tượng
Retained Heap = tất cả những gì sẽ bị xóa cùng với nó

Ví dụ:
  Map node: 64 byte (Shallow)
  Giữ: 500 MB dữ liệu (Retained!)

→ Trong MAT, hãy nhìn vào Retained Heap!
```

### Công cụ

| Công cụ         | Khi nào               | Chi phí (Overhead) |
| --------------- | --------------------- | ------------ |
| **Eclipse MAT** | Phân tích dump        | Offline (0%) |
| **JFR/JMC**     | Giám sát production   | < 1%         |
| **jcmd**        | Kiểm tra nhanh        | Thấp         |
| **JProfiler**   | Development           | Cao          |

### Các nguồn rò rỉ phổ biến

```java
// 1. Các collection tĩnh
static Map<String, Object> cache = new HashMap<>();

// 2. ThreadLocal
ThreadLocal<User> user = new ThreadLocal<>();
// Quên remove()

// 3. Các listener
eventBus.subscribe(listener);
// Quên unsubscribe

// 4. Tài nguyên không được đóng
InputStream is = new FileInputStream("file");
// Quên close()
```

## Senior Level

### Dominator Tree (Cây thống trị)

```
MAT: Dominator Tree
  → Hiển thị các đối tượng đang giữ lại nhiều bộ nhớ nhất
  → Bản thân chúng không nhất thiết là lớn nhất
  → Một đối tượng nhỏ có thể giữ hàng gigabyte!
```

### Path to GC Roots

```
MAT: Path to GC Roots (loại trừ weak/soft)
  → Hiển thị chuỗi tham chiếu đến root
  → Thấy ngay ai đang giữ đối tượng

Các root rò rỉ điển hình:
  - Trường tĩnh → Map → đối tượng của bạn
  - ThreadLocal → đối tượng của bạn
  - Thread → đối tượng của bạn
```

### OQL (Object Query Language)

```sql
-- Tìm tất cả các chuỗi > 1000 ký tự
SELECT s.value.toString()
FROM java.lang.String s
WHERE s.value.length > 1000

-- Tìm các chuỗi trùng lặp
SELECT toString(s.value) as val, count(*) as cnt
FROM java.lang.String s
GROUP BY toString(s.value)
HAVING count(*) > 100
```

### JFR OldObjectSample

```
Java Flight Recorder:
  → Sự kiện OldObjectSample
  → Hiển thị các đối tượng đã sống sót qua nhiều lần GC
  → Trực quan hóa đường đi đến GC Roots
  → KHÔNG cần chụp một dump!

→ Phương pháp an toàn duy nhất cho Heap > 100 GB
```

### Sawtooth Pattern (Mẫu hình răng cưa)

```
Sawtooth Pattern: "sàn" (mức sử dụng tối thiểu sau GC) tăng lên qua từng chu kỳ.
Điều này có nghĩa là: sau mỗi lần thu gom, có nhiều đối tượng còn lại hơn — một rò rỉ.

Đồ thị bộ nhớ sau GC:

Bình thường:
  |\    |\    |\
  | \   | \   | \
  |__\  |__\  |__\
  ← đáy ở cùng một mức

Rò rỉ:
  |\      |\        |\
  | \     | \       | \
  |__\    |___\     |____\
  ← đáy đang dâng lên!
```

### Kinh nghiệm Production

**Tình huống thực tế: ClassLoader Leak**
- Redeploy Tomcat 10 lần → Metaspace 256 MB → 4 GB
- Nguyên nhân: ThreadLocal giữ đối tượng từ ClassLoader của ứng dụng
- Giải pháp: ThreadLocal.remove() trong ServletContextListener

### Best Practices

1. **Delta Analysis** — so sánh hai dump
2. **Retained Heap** > Shallow Heap
3. **Path to GC Roots** → loại trừ weak/soft
4. **JFR OldObjectSample** cho các Heap lớn
5. **Sawtooth Pattern** → giám sát
6. **HeapDumpOnOutOfMemoryError** — bắt buộc
7. **Tự động hóa** việc chụp dump

### Tóm tắt cho Senior

- **Delta Analysis** = so sánh dump trước/sau
- **Retained Heap** = tác động thực sự lên bộ nhớ
- **Dominator Tree** = tìm ra thủ phạm
- **Path to GC Roots** = chuỗi tham chiếu
- **JFR OldObjectSample** = giải pháp thay thế dump cho các Heap lớn
- **Sawtooth Pattern** = chỉ báo rò rỉ trực quan
- **ClassLoader Leaks** = nguy hiểm nhất

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Memory Leak trong Java — giữ lại tham chiếu ngoài ý muốn; GC không loại bỏ vì có đường đi từ GC Root
- Delta Analysis: Baseline (dump sau warmup) → Load → Cooldown → Snapshot → So sánh các class đang tăng
- Shallow Heap = kích thước đối tượng; Retained Heap = tất cả những gì bị xóa cùng nó → trong MAT hãy nhìn vào Retained!
- Sawtooth Pattern: "sàn" của đồ thị bộ nhớ tăng lên sau mỗi lần GC — chỉ báo rò rỉ trực quan
- Dominator Tree (MAT): hiển thị các đối tượng giữ lại nhiều bộ nhớ nhất; một đối tượng nhỏ có thể giữ hàng gigabyte!
- Path to GC Roots (loại trừ weak/soft): hiển thị chuỗi tham chiếu đến root → 99% các rò rỉ = Static hoặc Thread
- JFR OldObjectSample: hiển thị các đối tượng đã sống sót qua nhiều lần GC; KHÔNG cần chụp dump; cho Heap > 100 GB

**Các câu hỏi phụ thường gặp:**
- **Tại sao Retained Heap quan trọng hơn Shallow Heap?** — Map node: 64 byte Shallow, nhưng giữ 500 MB Retained; loại bỏ node giải phóng 500 MB
- **Tại sao Delta Analysis thay vì một dump duy nhất?** — Một dump duy nhất cho thấy "cái gì tồn tại"; hai dump cho thấy "cái gì đang tăng" — rò rỉ
- **Tại sao JFR tốt hơn dump cho các Heap lớn?** — Dump 128 GB = STW 30-60 giây; trong Kubernetes Liveness Probe timeout → pod bị giết; JFR < 1% chi phí
- **OQL là gì?** — Object Query Language: các truy vấn kiểu SQL vào dump (tìm các chuỗi lớn, các bản trùng lặp, các rò rỉ ThreadLocal)

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi chụp dump trong production trên 128 GB mà không cảnh báo" — STW 30-60 giây, Liveness Probe fail → pod bị giết
- "System.gc() trước Delta Analysis — thực hành bình thường" — KHÔNG dùng trong production! Chỉ trong lúc chẩn đoán, và một cách cẩn thận
- "Shallow Heap cho thấy tác động thực sự của đối tượng" — Retained Heap cho thấy bao nhiêu sẽ được giải phóng khi loại bỏ
