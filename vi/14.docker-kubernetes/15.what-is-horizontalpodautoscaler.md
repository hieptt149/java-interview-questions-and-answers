# What is HorizontalPodAutoscaler (HPA)? (HorizontalPodAutoscaler (HPA) là gì?)

---

## Junior Level

### Giải Thích Đơn Giản

**HorizontalPodAutoscaler (HPA)** là một controller Kubernetes tự động thay đổi số lượng Pod dựa trên tải. Nhiều request → nhiều Pod hơn. Ít request → ít Pod hơn.

### Phép So Sánh Đơn Giản

HPA giống như một quản lý nhà hàng:
- Nhiều khách hàng → mở thêm quầy thu ngân
- Ít khách hàng → đóng các quầy thừa, tiết kiệm tài nguyên

### HPA Hoạt Động Như Thế Nào?

1. HPA kiểm tra mức sử dụng CPU của Pod mỗi 15 giây
2. Nếu CPU vượt mục tiêu → thêm các Pod
3. Nếu CPU dưới mục tiêu → loại bỏ các Pod
4. Số lượng Pod luôn nằm trong giới hạn min/max

### Ví Dụ Đơn Giản

```bash
# Tự động duy trì ~50% CPU, từ 2 đến 10 Pod
kubectl autoscale deployment myapp --cpu-percent=50 --min=2 --max=10
```

Hoặc qua YAML:
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapp-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 50
```

### Cần Gì Để HPA Hoạt Động?

1. **Metrics Server** — thu thập các metrics CPU/Memory
2. **Requests** trong Pod — HPA tính phần trăm từ Request, không phải từ Limit

```yaml
resources:
  requests:
    cpu: "500m"    # Bắt buộc!
```

### Những Gì Một Junior Developer Nên Nhớ

- HPA tự động thay đổi số lượng Pod
- Hoạt động dựa trên CPU (hoặc các metrics khác)
- Yêu cầu Metrics Server và Resource Requests
- Đặt min/max replica để kiểm soát
- HPA sẽ không scale xuống dưới minReplicas

## Middle Level

### Công Thức HPA

```
desiredReplicas = ceil[currentReplicas × (currentMetricValue / desiredMetricValue)]
```

// desiredReplicas = ceil(currentReplicas * (currentMetric / desiredMetric))
// Ví dụ: ceil(2 * (300m / 200m)) = ceil(2 * 1.5) = ceil(3.0) = 3 Pod

**Ví dụ:**
- CPU mong muốn: 50%
- CPU hiện tại: 100%
- Replica hiện tại: 2
- Kết quả: ceil[2 × (100/50)] = 4 replica

### Các Nguồn Metrics

| Loại         | Nguồn            | Ví dụ              |
| ------------ | ----------------- | -------------------- |
| **Resource** | Metrics Server    | CPU, Memory          |
| **Pods**     | Prometheus Adapter| RPS, latency         |
| **Object**   | Prometheus Adapter| Request mỗi hàng đợi   |
| **External** | Hệ thống bên ngoài  | Độ dài hàng đợi AWS SQS |

### Scaling Dựa Trên Memory: Tại Sao Là Ý Tưởng Tồi

Các ứng dụng Java không phải lúc nào cũng trả lại memory cho OS ngay sau GC. Điều này dẫn đến:
- HPA thấy mức sử dụng memory cao
- Thêm Pod liên tục
- Lãng phí tài nguyên

**Khuyến nghị:** Scale theo CPU hoặc các metrics kinh doanh, không theo memory.

### Behavior: Cấu Hình Tốc Độ Scaling

```yaml
behavior:
  scaleUp:
    stabilizationWindowSeconds: 60
    policies:
    - type: Pods
      value: 4
      periodSeconds: 60
  scaleDown:
    stabilizationWindowSeconds: 300
    policies:
    - type: Pods
      value: 1
      periodSeconds: 120
```

Scale Down chậm hơn Scale Up — điều này bảo vệ khỏi việc loại bỏ Pod quá sớm.

### Xung Đột HPA Và VPA

Đừng dùng HPA và VPA đồng thời cho CPU:
- HPA thêm Pod khi CPU cao
- VPA tăng CPU mỗi Pod
- Chúng "đấu tranh" với nhau → không ổn định

### Những Gì Một Middle Developer Nên Nhớ

- Công thức HPA: replica mong muốn = hiện tại × (metric hiện tại / metric mong muốn)
- Scaling dựa trên memory là một anti-pattern cho Java
- Behavior kiểm soát tốc độ scale up/down
- Đừng dùng HPA + VPA cho cùng một metric
- maxReplicas bảo vệ ngân sách khỏi các đợt tăng đột biến không mong muốn

## Senior Level

### HPA Như Một Hệ Thống Quản Lý Dung Lượng

HPA không chỉ là "auto scaling" — nó là một **công cụ để cân bằng giữa SLA và tối ưu hóa chi phí**.

### Thuật Toán HPA v2: Phân Tích Chi Tiết

**Chu kỳ quyết định:**
```
Mỗi 15 giây (syncPeriod):
1. Lấy các metrics cho tất cả các pod mục tiêu
2. Tính replica mong muốn cho mỗi metric
3. Lấy MAX trên tất cả các metrics
4. Áp dụng các chính sách behavior (giới hạn scale up/down)
5. Thực thi giới hạn min/max
6. Patch spec.replicas của Deployment
```

**Stabilization Window:**
- Khi Scale Up: mặc định 60s (phản ứng nhanh)
- Khi Scale Down: mặc định 300s (thận trọng)

Stabilization window là một khoảng thời gian "cooldown" sau khi scale. Ngăn chặn flapping (scale lên xuống nhanh chóng trong quá trình dao động tải).

Điều này ngăn chặn "thrashing" — việc thêm/loại bỏ Pod liên tục.

### HPA Đa Metric

```yaml
metrics:
- type: Resource
  resource:
    name: cpu
    target:
      type: Utilization
      averageUtilization: 70
- type: Pods
  pods:
    metric:
      name: http_requests_per_second
    target:
      type: AverageValue
      averageValue: "100"
```

HPA chọn **MAX** từ các tính toán trên tất cả các metrics.

### Prometheus Adapter Cho Custom Metrics

```yaml
# Prometheus rule
- record: http_requests_per_second
  expr: rate(http_requests_total[5m])

# Cấu hình Prometheus Adapter
rules:
- seriesQuery: 'http_requests_per_second{namespace!="",pod!=""}'
  resources:
    overrides:
      namespace: {resource: "namespace"}
      pod: {resource: "pod"}
  name:
    matches: "^(.*)"
    as: "${1}"
  metricsQuery: sum(rate(<<.Series>>{<<.LabelMatchers>>}[2m])) by (<<.GroupBy>>)
```

### HPA Và Các Ứng Dụng Java: Đặc Thù

**JIT Warmup:**
- Các Pod mới có JIT "lạnh"
- Các request đầu tiên được xử lý chậm hơn
- CPU có thể tăng đột biến tạm thời → HPA thêm nhiều Pod hơn nữa (over-shooting)

**Giải pháp:**
1. Readiness Probe với kiểm tra warmup
2. Độ trễ ban đầu cho HPA (stabilization window)
3. Startup Probe cho quá trình warmup dài

**G1 GC Và CPU:**
- G1 GC dùng CPU cho việc đánh dấu đồng thời (concurrent marking)
- HPA có thể hiểu nhầm điều này là tải
- Cấu hình `-XX:ConcGCThreads` và `-XX:ParallelGCThreads`

### Scaling Dựa Trên Hàng Đợi (KEDA)

```yaml
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: worker-scaling
spec:
  scaleTargetRef:
    name: worker-deployment
  minReplicaCount: 1
  maxReplicaCount: 50
  triggers:
  - type: rabbitmq
    metadata:
      queueName: tasks
      queueLength: "10"
      activationQueueLength: "5"
```

KEDA tạo một HPA với các custom metrics.

### Xử Lý Sự Cố (Troubleshooting)

**HPA hiển thị `<unknown>`:**
```bash
kubectl get hpa
# NAME         REFERENCE           TARGETS   MINPODS   MAXPODS
# myapp-hpa    Deployment/myapp    <unknown> 2         10
```

Nguyên nhân:
1. Metrics Server chưa được cài đặt
2. Không có requests trong pod spec
3. Metrics chưa được thu thập (chờ 1-2 phút)

**HPA không scale:**
```bash
kubectl describe hpa myapp-hpa
# Warning: FailedGetResourceMetric  unable to fetch metrics
```

### Tối Ưu Hóa Chi Phí Qua HPA

```yaml
# Giới hạn ngân sách
maxReplicas: 20  # không quá 20 Pod = kiểm soát chi phí

# Scale down chậm
scaleDown:
  stabilizationWindowSeconds: 600  # 10 phút
```

### Tóm Tắt Cho Senior

- HPA — công cụ scaling ngang chính.
- Thuật toán: MAX(replica mong muốn mỗi metric), với các chính sách behavior.
- Luôn đặt một maxReplicas hợp lý để kiểm soát ngân sách.
- Behavior (stabilization window) ngăn chặn thrashing.
- Dựa scaling trên CPU hoặc các custom metrics kinh doanh, không phải memory.
- KEDA cho scaling event-driven (hàng đợi, stream).
- Đặc thù Java: JIT warmup, GC overhead — cần tính đến trong cấu hình.
- Xung đột HPA + VPA trên CPU — dùng riêng biệt.

## Interview Cheat Sheet

**Cần phải biết:**
- HPA tự động scale số lượng Pod theo CPU, memory, custom, hoặc external metrics
- Công thức: `desiredReplicas = ceil[current × (currentMetric / desiredMetric)]`
- Yêu cầu Metrics Server và Resource Requests (tính % từ requests, không phải limits)
- Behavior: stabilization window (scale up 60s, scale down 300s theo mặc định)
- HPA chọn MAX từ các tính toán trên tất cả các metrics
- Scaling dựa trên memory là một anti-pattern cho Java (JVM GC, trả lại memory chậm trễ)
- KEDA — HPA event-driven (Kafka, RabbitMQ, SQS); scale-to-zero với Knative

**Các câu hỏi phụ thường gặp:**
- *"Tại sao HPA hiển thị `<unknown>`?"* — Metrics Server chưa được cài đặt, không có requests, hoặc metrics chưa được thu thập
- *"Java JIT warmup và HPA?"* — Các Pod mới "lạnh", CPU tăng đột biến → HPA over-shooting; dùng startupProbe
- *"HPA + VPA cùng nhau?"* — Không cho cùng một metric; VPA ở chế độ `Off` cho các khuyến nghị
- *"Tại sao cần maxReplicas?"* — Bảo vệ ngân sách khỏi các đợt tăng tải không mong muốn

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Scale Java theo mức sử dụng memory" (JVM không trả lại memory ngay sau GC)
- "HPA không cần requests" (không hoạt động, hiển thị `<unknown>`)
- "Đặt periodSeconds=1 để phản ứng nhanh" (thrashing, tải thêm)
- "HPA thay thế Cluster Autoscaler" (HPA → Pod, CA → Node; các cấp độ khác nhau)
