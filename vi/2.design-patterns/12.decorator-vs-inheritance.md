# Advantage of Decorator over Inheritance? (Ưu điểm của Decorator so với kế thừa (Inheritance)?)

## Junior Level

**Decorator** là một pattern giúp thêm chức năng mới cho một đối tượng bằng cách **bao bọc (wrapping)** nó trong một đối tượng khác.

**Vấn đề của kế thừa:** Nếu bạn cần các tổ hợp tính năng khác nhau, bạn sẽ gặp phải sự bùng nổ số lượng class.

**Ví dụ về kế thừa:**
```java
// 2^n class cho n chức năng
class Coffee { }
class MilkCoffee extends Coffee { }
class SugarCoffee extends Coffee { }
class MilkSugarCoffee extends Coffee { }  // Đã có 4 class!
class WhippedCreamMilkSugarCoffee extends Coffee { }  // Và còn nhiều nữa...
```

**Giải pháp — Decorator:**
```java
// n class cho n chức năng
interface Coffee { double getCost(); }

class SimpleCoffee implements Coffee {
    public double getCost() { return 1.0; }
}

// Các decorator
class MilkDecorator implements Coffee {
    private final Coffee coffee;
    public MilkDecorator(Coffee coffee) { this.coffee = coffee; }
    public double getCost() { return coffee.getCost() + 0.5; }
}

class SugarDecorator implements Coffee {
    private final Coffee coffee;
    public SugarDecorator(Coffee coffee) { this.coffee = coffee; }
    public double getCost() { return coffee.getCost() + 0.2; }
}

// Bất kỳ tổ hợp nào!
Coffee order = new MilkDecorator(
                   new SugarDecorator(
                       new SimpleCoffee()
                   )
               );
System.out.println(order.getCost()); // 1.7
```

**Ưu điểm chính:** Các decorator có thể được kết hợp một cách tùy ý mà không cần tạo ra các class mới.

## Middle Level

### So sánh: Kế thừa vs Decorator

| Tiêu chí              | Kế thừa   | Decorator                         |
| ---------------------- | ------------- | ---------------------------------- |
| **Khi nào được thêm vào**         | Compile-time (thời điểm biên dịch)  | Runtime (thời điểm chạy)                           |
| **Số lượng class**        | 2^n           | n decorator + component gốc     |
| **Tổ hợp**       | Cố định         | Tùy ý                               |
| **Tính linh hoạt**        | Thấp           | Cao                              |

### Java I/O — Ví dụ kinh điển

```java
// Decorator trong thực tế
InputStream input = new BufferedInputStream(
                        new CipherInputStream(
                            new GZIPInputStream(
                                new FileInputStream("file.txt")
                            )
                        )
                    );

// Mỗi lớp là một decorator:
// FileInputStream -> đọc file
// GZIPInputStream -> giải nén dữ liệu
// CipherInputStream -> giải mã
// BufferedInputStream -> đệm dữ liệu (buffer)
```

### Khi nào KHÔNG nên dùng Decorator

```java
// Overengineering (thiết kế thừa) đối với chức năng đơn giản
class LoggingUserService extends UserService {
    @Override
    public void create(User user) {
        log.info("Creating user: " + user);
        super.create(user);
    }
}

// Composition hoặc AOP là đủ dùng
```

## Senior Level

### Composition thay vì kế thừa

```
Decorator = trường hợp đặc biệt của composition

Kế thừa: "is-a" (Coffee LÀ MỘT Beverage)
Composition: "has-a" (Decorator CÓ MỘT Coffee)

-> Composition linh hoạt hơn và ít mong manh hơn
```

### Trách nhiệm động (Dynamic Responsibility)

```java
// Đây là Chain of Responsibility / Pipeline, không phải Decorator kinh điển.
// Decorator kinh điển = các lớp bao bọc lồng nhau: new Compression(new Encryption(new Stream()))
// Thêm/loại bỏ trách nhiệm tại thời điểm chạy (runtime)
public class Order {
    private List<OrderDecorator> decorators = new ArrayList<>();
    private BigDecimal basePrice;

    public void addDecorator(OrderDecorator d) { decorators.add(d); }
    public void removeDecorator(Class<? extends OrderDecorator> type) {
        decorators.removeIf(d -> d.getClass().equals(type));
    }

    public BigDecimal getPrice() {
        BigDecimal price = basePrice;
        for (OrderDecorator d : decorators) {
            price = d.calculate(price);
        }
        return price;
    }
}
```

### Kinh nghiệm Production

**Tình huống thực tế: Java I/O Decorator**
- Spring: ResponseBodyAdvice = Decorator cho HTTP response
- Thêm logging, nén, mã hóa
- Nếu không có Decorator: sẽ cần kế thừa các controller

### Best Practices (Thực hành tốt nhất)

1. **Decorator** khi cần composition tại thời điểm chạy
2. **Kế thừa** cho các mối quan hệ "is-a"
3. **Composition** được ưu tiên hơn so với kế thừa
4. **Cùng một interface** cho decorator và component
5. **AOP** có thể thay thế các decorator đơn giản

### Tóm tắt cho Senior

- **Decorator** = thêm trách nhiệm tại thời điểm chạy
- **Composition > Kế thừa** — linh hoạt hơn và ít mong manh hơn
- **Java I/O** = ví dụ kinh điển về Decorator
- **2^n vs n** — sự khác biệt về khả năng mở rộng
- **AOP** thay thế các decorator đơn giản (@Transactional)

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Decorator thêm chức năng thông qua việc bao bọc, kế thừa — thông qua việc mở rộng class
- Khả năng mở rộng: Decorator = n class cho n chức năng, kế thừa = 2^n class (bùng nổ tổ hợp)
- Java I/O — ví dụ kinh điển: BufferedInputStream(CipherInputStream(GZIPInputStream(FileInputStream)))
- Composition thay vì kế thừa: Decorator là một trường hợp đặc biệt của composition, ít mong manh hơn so với kế thừa
- Decorator hoạt động tại thời điểm chạy, kế thừa — tại thời điểm biên dịch
- AOP (@Transactional, @Cacheable) thay thế các decorator đơn giản
- Thêm/loại bỏ động các decorator tại thời điểm chạy (pattern Pipeline/Chain)

**Các câu hỏi phụ thường gặp:**
- **Khi nào Decorator trở thành overengineering?** — Chức năng đơn giản, composition hoặc AOP là đủ dùng
- **Decorator khác Adapter như thế nào?** — Decorator thêm chức năng, Adapter thay đổi interface
- **Tại sao Java I/O là một ví dụ về Decorator?** — Mỗi stream bao bọc một stream khác, thêm vào chức năng riêng của nó
- **Có thể loại bỏ các decorator tại thời điểm chạy được không?** — Có thể, nếu bạn lưu trữ một danh sách các decorator (pattern Pipeline)

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Kế thừa luôn luôn tốt hơn Decorator" — bùng nổ tổ hợp class (2^n)
- "Decorator và Proxy giống nhau" — Proxy kiểm soát quyền truy cập, Decorator thêm chức năng
- "Tôi dùng Decorator cho việc ghi log" — AOP (@Aspect) phù hợp hơn
- "Decorator khó hiểu" — Java I/O sử dụng nó, nó rất trực quan
