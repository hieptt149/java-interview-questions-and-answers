# How HashMap Works Internally? (HashMap hoạt động bên trong như thế nào?)

## 🟢 Junior Level

**HashMap** là một collection trong Java lưu dữ liệu theo định dạng "key-value" (Map). Nó cho phép tra cứu, thêm và xóa các phần tử theo key rất nhanh.

Ý tưởng cốt lõi: HashMap dùng một **hash table** — một mảng bucket (bin) nội bộ.

**Tại sao nó nhanh:** Khác với ArrayList, thứ duyệt qua mọi phần tử (O(n)), HashMap tính một con số đặc biệt (hash) của key và đi thẳng tới ô đúng — như đi tới một số tủ khóa cụ thể thay vì kiểm tra từng tủ. Khi bạn thêm một phần tử, HashMap tính hash của key để xác định đặt nó vào bucket nào. Khi tìm kiếm, nó tính lại cùng hash đó và đi thẳng tới bucket đúng.

**Ví dụ:**
```java
Map<String, Integer> ages = new HashMap<>();
ages.put("Alice", 30);  // hashCode("Alice") = 63154590 → index = 15 → table[15]
ages.put("Bob", 25);    // hashCode("Bob") = 66133 → index = 5 → table[5]
System.out.println(ages.get("Alice")); // 30 — cùng hash, cùng index 15
```

**Khi nào dùng:**
- Khi bạn cần tra cứu nhanh theo key
- Khi thứ tự phần tử không quan trọng
- Khi bạn cần một trong những lựa chọn nhanh nhất cho việc tra cứu (trung bình O(1))

### Khi nào KHÔNG nên dùng HashMap

1. **Cần thứ tự chèn** — dùng LinkedHashMap
2. **Sắp xếp theo key** — TreeMap
3. **Truy cập đa luồng** — ConcurrentHashMap
4. **Bộ nhớ then chốt với ít phần tử** — ArrayList với tìm kiếm tuyến tính có thể rẻ hơn

## 🟡 Middle Level

### Cách nó hoạt động bên trong

HashMap gồm một số field then chốt:

```java
transient Node<K,V>[] table; // Mảng bucket (được khởi tạo lười ở lần put đầu tiên)
int threshold;               // Ngưỡng resize (capacity * loadFactor)
final float loadFactor;      // Hệ số tải (mặc định 0.75)
transient int size;          // Số lượng phần tử hiện tại
```

**Cách put() hoạt động:**
1. Ở lần `put()` đầu tiên, một mảng 16 bucket được tạo (khởi tạo lười, Java 8+). Trong Java 7, mảng được tạo lúc construct.
2. `hash(key)` được tính — một hash code đã được **spread** (nhiễu loạn — perturbed) của key.

**Spreading** — các bit cao của hash code được 'trộn' với các bit thấp qua XOR. XOR là một phép toán bitwise: nếu các bit khác nhau → 1, giống nhau → 0. Điều này giảm thiểu va chạm ngay cả với một hàm hashCode kém: các khác biệt ở bit cao được 'mang' xuống các bit thấp, thứ được dùng để lập chỉ mục.
3. Chỉ số bucket được xác định: `index = (n - 1) & hash`
4. Nếu bucket rỗng — một `Node` mới được tạo
5. Nếu bucket đã có phần tử — `equals()` được kiểm tra để tìm key đã tồn tại
6. Nếu tìm thấy key — giá trị bị ghi đè, nếu không — node mới được thêm

**Cách get() hoạt động:**
1. Tính hash của key
2. Xác định chỉ số bucket
3. Tìm phần tử trong bucket qua `equals()`

### Các sai lầm thường gặp

1. **Dùng các object mutable làm key** — nếu các field của key bị sửa đổi sau `put()`, phần tử trở nên không thể tiếp cận
2. **Override equals mà không override hashCode** — các object bằng nhau rơi vào các bucket khác nhau
3. **Truy cập đồng thời** — HashMap không thread-safe

### So sánh với các giải pháp thay thế

| Hiện thực         | Độ phức tạp tra cứu | Thứ tự          | Thread Safety       |
| ----------------- | ------------------- | --------------- | ------------------- |
| HashMap           | O(1)                | Không           | Không               |
| TreeMap           | O(log n)            | Được sắp xếp    | Không               |
| LinkedHashMap     | O(1)                | Thứ tự chèn     | Không               |
| ConcurrentHashMap | O(1)                | Không           | Có                  |

## 🔴 Senior Level

### Hiện thực bên trong

**Hàm hash (spread):**

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

Phép `XOR` giữa 16 bit cao và 16 bit thấp giảm thiểu va chạm cho các mảng nhỏ, nơi chỉ số chỉ được xác định bởi các bit thấp qua mask `(n-1)`.

**Xác định chỉ số:**
```java
index = (n - 1) & hash;
```
`&` được dùng thay cho `%` — nó nhanh hơn hàng chục lần. Nó yêu cầu kích thước mảng luôn là lũy thừa của hai.

### Các đánh đổi kiến trúc

**Separate Chaining vs Open Addressing:**
- HashMap dùng separate chaining — các va chạm được giải quyết bằng linked list/tree trong mỗi bucket
- ✅ Ưu điểm: bền vững với các hàm hash kém, xóa đơn giản hơn
- ❌ Nhược điểm: cấp phát các object Node riêng (overhead bộ nhớ, cache locality kém)
- Open addressing (như trong `ThreadLocalMap`) tiết kiệm bộ nhớ nhưng chịu ảnh hưởng của clustering

**Treeification (Java 8+):**
- Ở 8 phần tử trong một bucket và capacity >= 64, linked list chuyển thành một cây đỏ-đen (red-black tree).

**Red-black tree** — một cây tìm kiếm nhị phân cân bằng nơi mỗi node được 'tô màu' đỏ hoặc đen. Các quy tắc tô màu đảm bảo cân bằng: tìm kiếm luôn là O(log n).

**Hysteresis** (độ trễ) — khoảng cách giữa ngưỡng chuyển đổi thuận (8 → tree) và nghịch (6 → list). Điều này ngăn 'churn' — khi cấu trúc liên tục lật qua lật lại khi tải dao động.
- Độ phức tạp tìm kiếm trường hợp xấu nhất: O(n) -> O(log n)
- `TreeNode` chiếm ~2x bộ nhớ so với `Node`
- Ngưỡng chuyển đổi nghịch: 6 phần tử (hysteresis để ngăn churn)

### Các trường hợp biên (Edge Case)

1. **Hash Flooding Attack** — kẻ tấn công tạo các key có cùng hash; trước Java 8 điều này gây DoS qua O(n); Java 8+ bảo vệ qua treeification
2. **Concurrent resize** — trong Java 7, resize song song gây cycling danh sách; Java 8+ đã sửa qua tail insertion, nhưng mất dữ liệu vẫn có thể xảy ra
3. **Null key** — luôn đi vào `table[0]`, vì `hash(null) = 0`

### Hiệu năng

- Trường hợp trung bình: O(1) cho get/put/remove
- Trường hợp xấu nhất: O(log n) (Java 8+), O(n) (Java 7)
- Chi phí put khấu hao (amortized): O(1) (resize là O(n), nhưng xảy ra hiếm)
- Memory footprint: mỗi Node — object header + int hash + K key + V value + Node next ≈ 32-48 byte mỗi entry (không tính key/value)

### Tối ưu Resize

Khi tăng đôi mảng (Java 8+), không cần tính lại các hash. Một bit được kiểm tra:
```java
if ((e.hash & oldCap) == 0) {
    // Ở lại cùng chỉ số
} else {
    // Chuyển tới oldIndex + oldCapacity
}
```

### Kinh nghiệm Production

Trong các hệ thống tải cao, các lần resize thường xuyên gây tăng vọt latency. Nên đặt `initialCapacity = (expectedSize / 0.75) + 1` để tránh các thao tác O(n) lúc runtime.

### Best Practices cho Highload
- Dùng `ConcurrentHashMap` cho truy cập đa luồng
- Tính trước capacity
- Dùng các key immutable với hashCode chất lượng
- Tránh các null key để dễ portable hơn

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- HashMap = mảng bucket + linked list/tree (Java 8+)
- put/get hoạt động trong O(1) trường hợp trung bình
- Khởi tạo lười: mảng được tạo ở lần put đầu tiên
- Hàm spread: XOR của 16 bit cao và thấp để phân bố đều
- Lập chỉ mục qua `(n-1) & hash` — nhanh hơn phép chia
- Ở 8 phần tử trong bucket và capacity >= 64 — treeification (list → red-black tree)
- null key được cho phép (một cái), luôn ở table[0]
- Không thread-safe — dùng ConcurrentHashMap cho concurrency

**Các câu hỏi phụ thường gặp:**
- **Tại sao capacity luôn là lũy thừa của hai?** — để dùng mask bitwise nhanh thay vì phép chia
- **Load factor 0.75 là gì?** — cân bằng giữa bộ nhớ và va chạm, được biện minh bởi phân phối Poisson
- **Điều gì xảy ra với một hashCode tồi?** — mọi phần tử trong một bucket, suy giảm xuống O(n) hoặc O(log n)
- **Tại sao không dùng HashMap trong đa luồng?** — data race, mất dữ liệu, hỏng cấu trúc trong lúc resize

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "HashMap dùng phép chia để lập chỉ mục" — không, mask bitwise
- "HashMap là thread-safe" — không, đó là ConcurrentHashMap
- "Ở 8 phần tử luôn là một cây" — chỉ khi capacity >= 64
