# What is Saga pattern and when to use it (Saga pattern là gì và khi nào dùng nó)

## Junior Level

**Saga** là một pattern để quản lý **distributed transaction** trong microservices.

Trong một monolith, một ACID transaction đảm bảo rằng tất cả các thay đổi hoặc được commit hoặc được rollback cùng nhau.
Trong microservices, dữ liệu được trải rộng trên các database khác nhau, và không có cơ chế nào có thể thay đổi mọi thứ một cách atomic cùng lúc.

Trong một monolith có một database và các transaction thông thường (ACID). Trong microservices, mỗi service có database riêng, và bạn không thể tạo một transaction duy nhất qua nhiều service.

**Saga giải quyết vấn đề này:**
- Chia một transaction lớn thành **một chuỗi các local transaction**
- Mỗi local transaction chạy trong service riêng của nó
- Nếu có gì đó sai — **compensating transaction** (rollback) được thực thi

```
Ví dụ — đơn hàng cửa hàng online:
1. Order Service: tạo đơn hàng
2. Payment Service: tính phí
3. Inventory Service: giữ chỗ sản phẩm
4. Shipping Service: giao hàng

Nếu Payment thất bại -> hủy đơn hàng (compensation)
Nếu Inventory thất bại -> hoàn tiền + hủy đơn hàng
// Điều người dùng thấy: đơn hàng được tạo -> thanh toán được xử lý -> hàng được giữ chỗ.
// Nếu Shipping thất bại: compensation hủy tất cả, người dùng thấy "đơn hàng đã bị hủy".
// Eventual consistency thường mất từ vài giây đến vài phút.
```

## Middle Level

### Hai loại Saga

**1. Choreography:**
```
Mỗi service publish một event -> các service khác lắng nghe và phản ứng

Order Service -> "OrderCreated" -> Payment Service
Payment Service -> "PaymentCompleted" -> Inventory Service
Inventory Service -> "InventoryReserved" -> Shipping Service
```

**2. Orchestration:**
```
Một orchestrator trung tâm quản lý toàn bộ quy trình

        Orchestrator
       /    |    \     \
  Order  Payment  Inventory  Shipping
```

### Khi nào dùng

**Saga phù hợp khi:**
- Một transaction trải rộng qua nhiều service
- Eventual consistency chấp nhận được (không cần nhất quán ngay lập tức)
- Không có một database duy nhất

**Nếu yêu cầu nghiệp vụ pháp lý yêu cầu ACID nghiêm ngặt (chuyển khoản ngân hàng),
Saga có thể không phù hợp nếu không có các đảm bảo bổ sung (lock, two-phase commit).**

### Các lỗi thường gặp

1. **Thiếu compensation:**
```
Order -> Payment -> Inventory (thất bại)
Cần: refund(payment) + cancel(order)
Nếu quên refund -> tiền bị trừ, không có đơn hàng nào tồn tại
```

## Senior Level

### Triển Khai Nội Bộ

**Saga log:**
```
Mỗi Saga phải ghi log:
1. Các bước đã bắt đầu
2. Các bước đã hoàn thành
3. Các compensation

Điều này cho phép khôi phục trạng thái sau khi restart
```

### Đánh Đổi Kiến Trúc

| Choreography             | Orchestration                          |
| ----------------------- | ------------------------------------- |
| Không có single point of failure | Orchestrator — single point of failure |
| Khó theo dõi luồng      | Dễ giám sát                            |
| Phụ thuộc vòng lặp      | Không có phụ thuộc vòng lặp            |
| Tốt cho Saga đơn giản   | Tốt cho Saga phức tạp                  |

### Edge Cases

**1. Idempotency:**
```
Một compensating transaction có thể được gọi hai lần
-> Cần idempotency

refund(paymentId):
    if alreadyRefunded(paymentId): return
    doRefund(paymentId)
    markRefunded(paymentId)
```

**2. Thất bại một phần:**
```
Saga: A -> B -> C (thất bại)
Compensation: compensate(B) -> compensate(A)

Nếu compensate(B) cũng thất bại -> retry + alert
```

### Kinh Nghiệm Production

**Order Saga:**
```java
@SagaDefinition
public class OrderSaga {

    @StartSaga
    @SagaEventHandler(associationProperty = "orderId")
    public void handle(OrderCreatedEvent event) {
        SagaLifecycle.start();
        commandGateway.send(new ReserveInventoryCommand(event.orderId()));
    }

    @SagaEventHandler(associationProperty = "orderId")
    public void handle(InventoryReservedEvent event) {
        commandGateway.send(new ProcessPaymentCommand(event.orderId()));
    }

    @SagaEventHandler(associationProperty = "orderId")
    public void handle(PaymentCompletedEvent event) {
        commandGateway.send(new ShipOrderCommand(event.orderId()));
        SagaLifecycle.end();
    }

    @SagaEventHandler(associationProperty = "orderId")
    public void handle(InventoryReservationFailedEvent event) {
        // Compensation — hủy đơn hàng
        commandGateway.send(new CancelOrderCommand(event.orderId()));
        SagaLifecycle.end();
    }
}
```

### Best Practices

```
✅ Ghi log mỗi bước của Saga
✅ Triển khai idempotency cho các compensation
✅ Dùng timeout cho mỗi bước
✅ Giám sát latency giữa các bước

❌ Đừng dùng cho các thao tác CRUD đơn giản
❌ Đừng quên các compensating transaction
❌ Đừng bỏ qua các thất bại một phần
```

## Interview Cheat Sheet

**Cần phải biết:**
- Saga — pattern cho distributed transaction không có một database duy nhất
- Hai loại: Choreography (dựa trên event) và Orchestration (dựa trên coordinator)
- Compensating transaction hoàn tác các bước theo thứ tự ngược lại
- Eventual consistency — dữ liệu không nhất quán ngay lập tức
- Idempotency là yếu tố quan trọng cho các compensation
- Transactional Outbox đảm bảo việc gửi event
- Choreography — 2-3 service, Orchestration — 5+ service
- Saga timeout bảo vệ khỏi các transaction bị treo

**Các câu hỏi phụ thường gặp:**
- **Saga khác 2PC như thế nào?** Saga không khóa tài nguyên, làm việc với các database không đồng nhất, nhưng cung cấp eventual consistency thay vì ACID nghiêm ngặt.
- **Điều gì xảy ra nếu một compensation cũng thất bại?** Retry + alert để can thiệp thủ công.
- **Khi nào KHÔNG nên dùng Saga?** Cho các thao tác CRUD đơn giản trong một service duy nhất hoặc khi cần ACID nghiêm ngặt (chuyển khoản ngân hàng).
- **Cách giám sát Saga?** Ghi log mỗi bước, theo dõi thời lượng giữa các bước, dùng distributed tracing.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Saga đảm bảo ACID" — không, eventual consistency
- "Compensation = ROLLBACK" — không, đó là một transaction mới
- "Choreography tốt hơn cho 10 service" — không, orchestration tốt hơn
- "Không cần Saga nếu có Kafka" — Kafka chỉ là transport, vẫn cần logic
