# What is the difference between PUT and PATCH? (Sự khác biệt giữa PUT và PATCH là gì?)

## Junior Level

Cả hai phương thức đều được dùng để cập nhật một tài nguyên, nhưng chúng hoạt động khác nhau.

### PUT — Cập nhật toàn bộ
- Thay thế toàn bộ phần biểu diễn của tài nguyên bằng những gì client đã gửi. Các trường không có trong request body phải bị xóa hoặc đặt về giá trị mặc định.
- Cần gửi tất cả các trường, kể cả những trường không đổi
- Nếu một trường bị bỏ sót — nó sẽ bị xóa hoặc đặt thành null

```
PUT /users/1
{
  "name": "Ivan",
  "age": 30,
  "email": "ivan@example.com"
}
```

### PATCH — Cập nhật một phần
- Chỉ cập nhật các trường được gửi
- Tiết kiệm băng thông: với một object 200 trường, thay đổi một trường qua PATCH tiết kiệm ~95% request body.

```
PATCH /users/1
{
  "age": 31
}
// Tất cả các trường khác giữ nguyên không đổi
```

### So sánh:

| Tiêu chí          | PUT                    | PATCH                     |
| ---------------- | --------------------- | ------------------------- |
| Khối lượng dữ liệu | Toàn bộ object        | Chỉ các trường đã đổi     |
| Idempotency      | Luôn idempotent        | Tùy vào cách hiện thực    |
| Tương tự SQL     | UPDATE tất cả các cột  | UPDATE các cột cụ thể     |

### Khi nào PUT tốt hơn PATCH

Dùng PUT để thay thế toàn bộ các object nhỏ — đơn giản hơn để hiện thực và không mập mờ.
Dùng PATCH cho các object lớn hoặc khi nhiều client có thể sửa các trường khác nhau song song.

## Middle Level

### Ngữ nghĩa của phương thức

#### PUT (Replace)
- **Idempotency:** Luôn idempotent. Bất kể bạn gửi cùng một request bao nhiêu lần — kết quả vẫn như nhau
- **Tương tự DB:** `UPDATE users SET name=?, age=?, email=? ...` (cập nhật tất cả các cột)

#### PATCH (Cập nhật một phần)
- **Idempotency:** Không được đảm bảo. Tùy vào cách hiện thực
- **Tương tự DB:** `UPDATE users SET age = age + 1` (không idempotent) hoặc `SET age = 30` (idempotent)

### Các đặc tả của PATCH

1. **JSON Merge Patch (RFC 7386):**
   - Client gửi JSON: `{"age": 31}`
   - Server chỉ đơn giản merge nó với object hiện tại
   - **Nhược điểm:** Khó xóa một trường (cần thống nhất rằng `null` nghĩa là xóa)

   Khác biệt then chốt: Merge Patch nói "cái gì cần thay đổi" (declarative — khai báo),
   còn JSON Patch nói "thay đổi như thế nào" (một dãy các thao tác: add, remove, replace).

2. **JSON Patch (RFC 6902):**
   - Client gửi một mảng các chỉ thị:
   ```json
   [
     { "op": "replace", "path": "/age", "value": 31 },
     { "op": "remove", "path": "/middleName" }
   ]
   ```
   - **Ưu điểm:** Tính nguyên tử và linh hoạt. Có thể thêm phần tử vào mảng, xóa các trường cụ thể

### Optimistic Locking (ETag)
1. Client nhận một tài nguyên có header `ETag: "v1"`
2. Client gửi `PUT/PATCH` với header `If-Match: "v1"`
3. Nếu `ETag` đã thành "v2" — server trả về **412 Precondition Failed**

### Chẩn đoán
- **422 Unprocessable Entity:** Nếu PATCH bất khả thi về mặt logic (ví dụ: xóa một trường bắt buộc)
- **Hibernate/JPA:** Với PATCH, dùng `nullValuePropertyMappingStrategy = IGNORE` trong MapStruct để tránh vô tình ghi đè các trường

## Senior Level

### Vấn đề "Lost Updates" (mất cập nhật) và Optimistic Locking

Điều gì xảy ra nếu hai người dùng đồng thời đọc một tài nguyên (age=20) và quyết định cập nhật nó?

- **Vấn đề của PUT:** Người thứ nhất cập nhật thành 21, người thứ hai — thành 25. Thay đổi của người thứ nhất bị **mất**.
- **Giải pháp của PATCH:** Nếu PATCH thực hiện `age = age + 1`, kết quả sẽ là 22 (cả hai thay đổi đều được tính).

### Hiệu suất và Highload

- **Băng thông:** PATCH tiết kiệm băng thông trên các object lớn (hồ sơ có hàng trăm trường)
- **Validation:** PUT dễ validate hơn (schema đầy đủ). PATCH cần logic validation phức tạp kiểu "chỉ các trường được gửi"
- **Reflection trong Java:** Hiện thực PATCH thường cần Jackson `JsonNode` để xác định một trường là `null` hay vắng mặt

### Hiện thực PATCH trong Spring
Hãy cẩn thận với `merge()` trong Hibernate. Nếu bạn tạo một object mới và gọi `merge()`, bạn có thể vô tình ghi đè các trường không được gửi trong PATCH, biến nó thành một PUT bị hỏng.

### Các trường hợp biên (Edge Case)
- Nếu PATCH chứa `{"op": "add", "path": "/tags", "value": "new"}` — điều này **không** idempotent (khi retry, một tag khác sẽ được thêm)
- Với PATCH idempotent, dùng các thao tác có tính tất định (replace, remove)

## Interview Cheat Sheet

**Cần phải biết:**
- PUT thay thế toàn bộ tài nguyên — các trường không có trong request bị xóa hoặc đặt null
- PATCH chỉ cập nhật các trường được gửi — tiết kiệm băng thông trên các object lớn
- PUT luôn idempotent; PATCH chỉ idempotent với các thao tác có tính tất định
- JSON Merge Patch (RFC 7386) — cách tiếp cận declarative: "cái gì cần thay đổi"
- JSON Patch (RFC 6902) — cách tiếp cận imperative: mảng các thao tác (add, remove, replace)
- Optimistic Locking qua ETag + If-Match ngăn xung đột khi cập nhật đồng thời
- PUT dễ validate hơn (schema đầy đủ), PATCH cần validate dữ liệu một phần phức tạp

**Các câu hỏi phụ thường gặp:**
- Lost Update Problem là gì? — Hai client đọc và cập nhật một tài nguyên song song; thay đổi của client đầu tiên bị mất
- Làm sao hiện thực PATCH trong Hibernate? — Dùng nullValuePropertyMappingStrategy = IGNORE trong MapStruct
- Server trả về gì khi 412 Precondition Failed? — ETag đã đổi kể từ lúc đọc, tài nguyên đã cũ
- Khi nào PUT tốt hơn PATCH? — Với các object nhỏ và khi cần thay thế toàn bộ một cách rõ ràng

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "PATCH luôn idempotent" — thêm vào một collection thì không idempotent
- "PUT chỉ cập nhật các trường được gửi" — PUT thay thế toàn bộ object
- "Không có khác biệt giữa PUT và PATCH" — PUT = thay thế toàn bộ, PATCH = cập nhật một phần
- "Merge Patch và JSON Patch giống nhau" — Merge Patch là declarative, JSON Patch là một dãy các thao tác
