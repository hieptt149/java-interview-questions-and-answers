# Give an Example of Single Responsibility Principle Violation (Cho một ví dụ về vi phạm Single Responsibility Principle)

## 🟢 Junior Level

**Vi phạm Single Responsibility Principle (SRP)** xảy ra khi một class xử lý nhiều thứ không liên quan cùng lúc. Một class như vậy thường được gọi là **God Object** — nó biết và làm quá nhiều.

**Analogy đơn giản:** Hãy tưởng tượng một người vừa làm bác sĩ, vừa lái xe, vừa nấu ăn cùng lúc. Họ có thể làm tất cả, nhưng chất lượng sẽ thấp, và nếu họ ốm — mọi thứ sụp đổ.

**Ví dụ vi phạm SRP:**
```java
// Xấu: OrderProcessor làm quá nhiều thứ
public class OrderProcessor {

    public void processOrder(Order order) {
        // 1. Validation đơn hàng
        if (order.getAmount().compareTo(BigDecimal.ZERO) <= 0) {
            throw new IllegalArgumentException("Invalid amount");
        }

        // 2. Lưu vào database
        saveToDatabase(order);

        // 3. Gửi email cho khách hàng
        sendEmail(order);

        // 4. Logging
        logToSystem(order);
    }

    private void saveToDatabase(Order order) { /* 50 dòng code */ }
    private void sendEmail(Order order) { /* 50 dòng code */ }
    private void logToSystem(Order order) { /* 50 dòng code */ }
}
```

**Tại sao điều này xấu:**
- Nếu phương thức gửi email thay đổi — bạn phải sửa đổi class chịu trách nhiệm cho đơn hàng
- Khó test: để xác minh validation, bạn cần mock database và email
- Không thể tái sử dụng: bạn không thể dùng `saveToDatabase` riêng biệt

**Cách sửa:**
```java
// Tốt: mỗi trách nhiệm trong class riêng của nó
public class OrderProcessor {
    private final OrderValidator validator;
    private final OrderRepository repository;
    private final EmailService emailService;
    private final Logger logger;

    public void processOrder(Order order) {
        validator.validate(order);
        repository.save(order);
        emailService.sendOrderConfirmation(order);
        logger.log("Order processed: " + order.getId());
    }
}
```

## 🟡 Middle Level

### Cấu Trúc Của Vi Phạm SRP

Vi phạm SRP tạo ra **các dependency ngầm** trong hệ thống. Thay đổi một chi tiết nhỏ (ví dụ, định dạng ngày trong log) có thể phá vỡ một quy trình nghiệp vụ quan trọng (ví dụ, lưu đơn hàng), vì tất cả điều này sống trong một file.

### Các Ví Dụ Vi Phạm SRP Điển Hình

#### 1. Spring `@Service` — "Bãi rác"

Một anti-pattern phổ biến trong các dự án Spring: một service với hàng chục repository.

```java
@Service
public class GeneralService {
    @Autowired private UserRepository userRepo;
    @Autowired private OrderRepository orderRepo;
    @Autowired private ProductRepository productRepo;
    @Autowired private PromoRepository promoRepo;
    @Autowired private AuditRepository auditRepo;
    // ... thêm 15 repository nữa

    // Mỗi @Autowired tạo một proxy object. 20+ dependency = 20+ proxy
    // = chuỗi gọi phức tạp. Khi test, mỗi cái trong 20 cái cần được mock.

    // Phương thức này vi phạm SRP: kết hợp logic của 5 domain khác nhau
    public void checkout(Long userId, Long cartId) {
        // 200 dòng logic
    }
}
```

**Hậu quả:** Bất kỳ Git merge nào cũng gây xung đột, vì 10 developer sửa file này hàng ngày.

#### 2. God Object Trong Business Logic

```java
public class EmployeeManager {
    // Trách nhiệm HR
    public void hireEmployee(Employee emp) { }
    public void fireEmployee(Long id) { }

    // Kế toán
    public BigDecimal calculateSalary(Employee emp) { }
    public BigDecimal calculateTax(Employee emp) { }

    // Hạ tầng IT
    public void createEmailAccount(Employee emp) { }
    public void assignLaptop(Employee emp) { }

    // Reporting
    public void generateDepartmentReport() { }
}
```

**Vấn đề:** Các stakeholder khác nhau (HR, kế toán, IT) yêu cầu thay đổi trong một class.

### Chẩn Đoán Vi Phạm SRP

| Dấu hiệu                      | Ý nghĩa                                                                                                                                                                                                                                               |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Quy tắc "Và"**            | Nếu mô tả class chứa "và" ("nó làm X **VÀ** Y **VÀ** Z")                                                                                                                                                                                                   |
| **Quá tải Mock**        | Nhiều hơn 5 mock trong một unit test                                                                                                                                                                                                                            |
| **Kích thước danh sách import**      | Danh sách import chiếm >20 dòng                                                                                                                                                                                                                                 |
| **Độ phức tạp Cyclomatic** | Nhiều nhánh if/else cho các kịch bản khác nhau. Cyclomatic Complexity — số đường thực thi độc lập trong một phương thức. Được tính bằng số nhánh `if/else/switch` + 1. CC = 10 nghĩa là cần 10+ test để bao phủ hoàn toàn. Cao hơn = khó test hơn.          |
| **Merge Conflict**       | Xung đột Git thường xuyên khi sửa file                                                                                                                                                                                                                |

### Các Lỗi Thường Gặp

1. **Lỗi**: Tạo các class `Utils`, `Helper`, `Manager`
   **Giải pháp**: Chia theo các lĩnh vực domain (`PasswordHasher`, `DateFormatter`). Trong DDD, `Manager`/`Orchestrator` là các pattern điều phối hợp pháp. Vấn đề không phải là tên, mà là class trộn lẫn business logic với hạ tầng.

2. **Lỗi**: Kết hợp các thao tác CRUD vào một service
   **Giải pháp**: Tách theo khả năng nghiệp vụ (`OrderCreator`, `OrderCanceler`)

3. **Lỗi**: Trộn lẫn business logic và hạ tầng
   **Giải pháp**: Tách các thao tác DB, HTTP, queue thành các tầng riêng biệt

### Refactoring: Từ God Object Sang Orchestrator

**Bước 1:** Xác định các trách nhiệm khác nhau
**Bước 2:** Tạo các class riêng biệt cho mỗi cái
**Bước 3:** Dùng composition để ủy quyền
**Bước 4:** Class gốc trở thành một bộ điều phối (Orchestrator)

## 🔴 Senior Level

### Triển Khai Nội Bộ: Tại Sao God Object Là "Chất Độc" Cho Một Dự Án

Vi phạm SRP tạo ra các vấn đề nền tảng ở cấp độ kiến trúc:

### 1. Tính Dễ Vỡ

Khi chúng ta thay thế một dependency (ví dụ, Splunk → ELK), chúng ta phải test lại **toàn bộ** logic của class, vì tất cả các phương thức sống trong một file và có thể chia sẻ các trường hoặc trạng thái chung.

```java
// God Object dễ vỡ
public class OrderProcessor {
    private final HttpClient httpClient;  // Dùng cho email VÀ logging
    private final Connection dbConnection; // Dùng cho order VÀ audit

    public void process(Order order) {
        // Nếu httpClient hỏng — cả email và logging đều thất bại
        // Không thể cập nhật logging mà không có nguy cơ làm hỏng email
    }
}
```

### 2. Tính Bất Động

Một God Object không thể tái sử dụng mà không kéo theo tất cả các dependency của nó. Điều này vi phạm nguyên tắc **Mobility** — khả năng của các component hoạt động trong các ngữ cảnh khác nhau.

### 3. Khả Năng Test Thấp

```java
// Test cho God Object — cơn ác mộng
@Test
void testProcessOrder() {
    // Cần mock: DB, email, logging, analytics, inventory...
    when(mockDb.save(any())).thenReturn(true);
    when(mockEmail.send(any())).thenReturn(true);
    when(mockLog.log(any())).thenReturn(true);
    when(mockAnalytics.track(any())).thenReturn(true);
    when(mockInventory.reserve(any())).thenReturn(true);
    // 20 dòng mock cho 5 dòng logic thực
}
```

### Đánh Đổi Kiến Trúc

**Phân rã nghiêm ngặt:**
- ✅ Ưu điểm: Khả năng test lý tưởng, deploy độc lập, ranh giới rõ ràng
- ❌ Nhược điểm: Nhiều class, phức tạp khi điều hướng, overhead giao tiếp

**Phân rã vừa phải:**
- ✅ Ưu điểm: Cân bằng giữa khả năng đọc và linh hoạt
- ❌ Nhược điểm: Yêu cầu phán đoán trưởng thành, suy thoái dần dần

### Edge Cases

1. **Ranh Giới Transaction**: Khi một transaction trải rộng qua nhiều domain
   - **Giải pháp**: Dùng `@Transactional` ở cấp độ orchestrator, nhưng business logic trong các service riêng biệt

2. **Pattern CQRS**: Tách trách nhiệm Command và Query
   - **Ví dụ**: `OrderCommandService` (tạo/xóa) vs `OrderQueryService` (đọc)

3. **Kiến Trúc Event-Driven**: Tách thông qua các event
   - **Ví dụ**: OrderCreatedEvent → các handler riêng biệt cho Email, Analytics, Inventory

### Hiệu Năng

- **Overhead lệnh gọi phương thức**: Delegation thêm các lệnh gọi phương thức. JIT thực hiện **inlining**, overhead ~0
- **Bộ nhớ**: Nhiều object hơn → nhiều tham chiếu hơn. GC xử lý điều này hiệu quả (generational GC)
- **ClassLoader**: Nhiều class hơn → nhiều metadata hơn trong Metaspace (vài KB mỗi class)

### Kinh Nghiệm Production

**Câu chuyện thực tế từ một dự án enterprise:**

Trong một dự án ngân hàng, có một `PaymentProcessor` với 5000+ dòng và 40 dependency. Các vấn đề:
- Bất kỳ thay đổi nào cũng mất 3-4 ngày (phân tích + test)
- 30% tất cả các bug production là do side effect
- Merge conflict hàng ngày
- Developer mới mất 2-3 tháng để onboard

**Giải pháp:** Refactoring dần dần trong 4 sprint:
1. Trích xuất `PaymentValidator`, `PaymentRepository`, `NotificationService`
2. Tạo `FraudDetectionService`, `ComplianceChecker`
3. `PaymentOrchestrator` điều phối các lệnh gọi
4. Giao tiếp event-driven thông qua Spring Events

**Kết quả:**
- Số lượng bug giảm 70%
- Thời gian code review giảm từ 2 giờ xuống 30 phút
- Các tính năng mới được thêm trong 1-2 ngày thay vì một tuần

### Monitoring Và Chẩn Đoán

**Static analysis:**
```java
// Test ArchUnit để xác minh SRP
@ArchTest
static void services_should_have_single_responsibility = classes()
    .that().resideInAPackage("..service..")
    .should().haveSimpleNameNotContaining("Manager")
    .andShould().haveSimpleNameNotContaining("Utils")
    .andShould().haveLessThanNDependencies(7);
```

**Các metric cần theo dõi:**
- Dòng mỗi class (< 300)
- Số phương thức (< 10)
- Độ phức tạp cyclomatic (< 15)
- Số dependency (< 7)
- Số mock trong test (< 5)

### Best Practices Cho Highload

- **Domain-Driven Design**: Aggregate Root có một trách nhiệm trong Aggregate
- **Package-by-Feature**: Nhóm theo khả năng nghiệp vụ, không phải theo tầng kỹ thuật
- **Hexagonal Architecture**: Tách các tầng domain, application và infrastructure
- **Event Sourcing**: Tách trạng thái thông qua model event

### Mối Quan Hệ Với Các Pattern Khác

- **SRP + Decorator**: Thêm trách nhiệm mà không vi phạm SRP
- **SRP + Chain of Responsibility**: Mỗi handler — một trách nhiệm
- **SRP + Strategy**: Mỗi strategy — một trách nhiệm

### Tóm Tắt Cho Senior

- Vi phạm SRP biến hệ thống thành **"lâu đài bằng bài"** — thay đổi một chi tiết phá vỡ mọi thứ
- Tìm các dấu hiệu **God Object**: các phương thức khổng lồ, hàng chục dependency, merge conflict thường xuyên
- Dùng **phân rã theo ý nghĩa nghiệp vụ**, không phải theo chức năng kỹ thuật
- Nhớ: SRP làm cho code **sạch**, không phải **nhỏ** — cân bằng giữa cohesion và số lượng file
- **ArchUnit** là bạn của bạn để xác minh tự động các ranh giới kiến trúc
- SRP là một **khoản đầu tư** vào khả năng bảo trì, không phải "quan liêu"

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- God Object — một class biết và làm quá nhiều, vi phạm SRP
- Quy tắc "Và": nếu mô tả class chứa "và" — SRP bị vi phạm
- Spring `@Service` với 20+ repository — một God Object điển hình trong enterprise
- Refactoring: xác định trách nhiệm → tạo các class riêng biệt → delegation
- Vi phạm SRP tạo ra tính dễ vỡ, tính bất động, và khả năng test thấp
- Characterization Test — bước đầu tiên của refactoring legacy không có test
- Kiến trúc event-driven giúp tách các trách nhiệm thông qua các event

**Các câu hỏi phụ thường gặp:**
- **Cách chẩn đoán một God Object?** — >300 dòng, >10 phương thức, >7 dependency, >5 mock trong test
- **Orchestrator là gì?** — Một bộ điều phối ủy quyền công việc cho các service riêng biệt, không chứa business logic
- **Cách refactor mà không có test?** — Characterization Test / Golden Master: bắt lại hành vi hiện tại, sau đó chia tách
- **CQRS và SRP?** — Tách Command và Query là một ví dụ về SRP ở cấp độ service

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Manager là một tên class bình thường" (thường đó là một God Object)
- "Nếu code hoạt động — không cần SRP" (hoạt động hôm nay, nhưng không thể bảo trì ngày mai)
- "20 dependency trong một service là bình thường" (dấu hiệu rõ ràng vi phạm SRP)
