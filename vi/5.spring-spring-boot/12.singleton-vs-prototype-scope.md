# Difference between Singleton and Prototype Scope? (Sự khác nhau giữa Singleton và Prototype Scope?)

## Junior Level

|                     | Singleton    | Prototype        |
| ------------------- | ------------ | ---------------- |
| **Instance**     | Một         | Mới mỗi lần |
| **@PreDestroy**     | Được gọi | KHÔNG được gọi  |
| **Khi nào được tạo** | Lúc khởi động   | Khi có yêu cầu      |

```java
@Service  // Singleton
public class A { }

@Scope("prototype")
@Service
public class B { }

A a1 = context.getBean(A.class);
A a2 = context.getBean(A.class);
a1 == a2  // -> true (cùng một đối tượng!)

B b1 = context.getBean(B.class);
B b2 = context.getBean(B.class);
b1 == b2  // -> false (các đối tượng khác nhau!)
```

## Middle Level

### Singleton

```java
// Theo mặc định!
// Lưu trong cache singletonObjects
// -> Truy cập nhanh, không tạo mới mỗi lần

// Phải là Stateless!
// -> Tất cả các thread dùng chung một đối tượng
// -> Đừng lưu dữ liệu trong các field!
```

### Prototype

```java
// Mỗi lần yêu cầu -> đối tượng mới
// Vòng đời đầy đủ: constructor -> @PostConstruct
// NHƯNG: @PreDestroy KHÔNG được gọi!

// Bạn chịu trách nhiệm dọn dẹp:
PrototypeBean bean = context.getBean(PrototypeBean.class);
try {
    // sử dụng
} finally {
    bean.cleanup();  // Thủ công!
}
```

### Vấn đề Prototype trong Singleton

```java
// Prototype bị "đóng băng"
@Service
public class SingletonService {
    @Autowired PrototypeBean proto;  // Được tạo MỘT LẦN!
}

// Tại sao: Singleton được tạo một lần, và tất cả các phụ thuộc của nó được inject
// vào lúc tạo. PrototypeBean được tạo một lần trong lúc inject và
// sau đó được tái sử dụng - Spring không tạo instance mới ở mỗi lần
// truy cập vào singleton bean.

// ObjectProvider
@Service
public class SingletonService {
    @Autowired ObjectProvider<PrototypeBean> provider;

    public void process() {
        PrototypeBean proto = provider.getObject();  // Mới!
    }
}
```

## Senior Level

### Circular Dependency (phụ thuộc vòng)

```
Singleton:
  -> Spring có thể giải quyết qua earlySingletonObjects

Prototype:
  -> Về nguyên tắc không thể giải quyết!
  -> A -> B -> A -> đệ quy vô hạn
  -> BeanCurrentlyInCreationException
```

### Overhead về hiệu năng

```
Singleton:
  -> Được tạo một lần
  -> Truy cập nhanh từ cache

Prototype:
  -> Vòng tạo đầy đủ mỗi lần
  -> Reflection, BPP, @PostConstruct
  -> Khi yêu cầu thường xuyên -> chậm!
```

### Memory Leak (rò rỉ bộ nhớ)

```
Prototype với tài nguyên:
  -> File/connection đã mở
  -> Spring không gọi @PreDestroy
  -> Tài nguyên không được giải phóng -> rò rỉ!

Giải pháp:
  -> try-finally với cleanup()
  -> Hoặc BeanPostProcessor để theo dõi
```

### Kinh nghiệm Production

**Tình huống thực tế: rò rỉ Prototype**
```
Trong một tình huống mà mỗi Prototype bean mở một connection:
10.000 request/giây -> 10.000 connection -> DB sập

Giải pháp: Singleton + ObjectPool
```

### Best Practices

1. **Singleton** — 95% các trường hợp (Stateless!)
2. **Prototype** — các đối tượng stateful nặng
3. **ObjectProvider** — Prototype trong Singleton
4. **Prototype** -> tự dọn dẹp tài nguyên
5. **Tránh** các vòng phụ thuộc trong Prototype
6. **Nếu bạn chỉ cần một đối tượng mà không cần DI, @PostConstruct và proxy hóa — một lời gọi `new` thông thường nhanh hơn Prototype từ Spring context.**

### Tóm tắt cho Senior

- **Singleton** = cache, Stateless, @PreDestroy hoạt động
- **Prototype** = mới mỗi lần, @PreDestroy KHÔNG hoạt động
- **Prototype trong Singleton** -> ObjectProvider
- **Vòng phụ thuộc** -> không thể giải quyết cho Prototype
- **Tài nguyên** -> dọn dẹp thủ công trong Prototype
- **Hiệu năng** -> Prototype tốn kém hơn Singleton

## Interview Cheat Sheet

**Cần phải biết:**
- Singleton = một instance, được cache; Prototype = mới ở mỗi `getBean()`
- @PreDestroy chỉ được gọi cho Singleton, với Prototype — KHÔNG BAO GIỜ
- Prototype trong Singleton = vấn đề: Prototype được tạo một lần và "đóng băng"
- Circular dependency có thể giải quyết cho Singleton (qua earlySingletonObjects), nhưng KHÔNG cho Prototype
- Hiệu năng: Prototype tốn kém hơn — vòng tạo đầy đủ mỗi lần (reflection, BPP, @PostConstruct)
- Tài nguyên trong Prototype — rò rỉ, dọn dẹp thủ công qua try-finally
- Nếu bạn chỉ cần một đối tượng mà không cần DI — dùng `new`, không phải Prototype

**Các câu hỏi phụ thường gặp:**
- *Làm sao lấy một Prototype mới bên trong một Singleton?* -> ObjectProvider.getObject()
- *Tại sao circular dependency không thể giải quyết cho Prototype?* -> Đệ quy tạo vô hạn, Spring ném BeanCurrentlyInCreationException
- *Singleton được lưu ở đâu?* -> cache singletonObjects (ConcurrentHashMap)
- *Khi nào Prototype là hợp lý?* -> Các đối tượng stateful nặng, khi không thể dùng Singleton + ThreadLocal

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "@PreDestroy hoạt động cho Prototype" — không hoạt động
- "Singleton được tạo ở mỗi lần yêu cầu" — được tạo một lần
- "Prototype nhanh hơn Singleton" — ngược lại, vòng đầy đủ mỗi lần
- "Vòng phụ thuộc trong Prototype được giải quyết qua @Lazy" — về nguyên tắc không thể giải quyết
