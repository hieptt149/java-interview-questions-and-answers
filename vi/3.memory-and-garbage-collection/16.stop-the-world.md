# What is stop-the-world? (Stop-the-world là gì?)

## Junior Level

**Stop-The-World (STW)** — khi JVM **dừng tất cả các luồng của ứng dụng** để thực hiện GC.

**Ví dụ minh họa đơn giản:** Hãy tưởng tượng bạn đang làm việc trong văn phòng, và đột nhiên có thông báo sơ tán. Mọi người dừng lại và chờ cho đến khi việc kiểm tra hoàn tất.

**Tại sao cần STW:**
1. GC — cần một trạng thái bộ nhớ nhất quán (các đối tượng không được di chuyển trong lúc duyệt)
2. Các thao tác không phải GC: thread dump, biased lock revocation, class redefinition (JVM TI)

**Kéo dài bao lâu:**
- ZGC: < 1 ms
- G1: 20-200 ms
- Full GC: hàng giây

## Middle Level

### Safepoints

```
Các luồng không thể dừng ngay lập tức!
→ Phải đến được một Safepoint (điểm dừng)

Nơi chúng được đặt:
  - Trước khi thoát khỏi phương thức
  - Ở cuối các vòng lặp
  - Trước các lời gọi phương thức

Cơ chế: Safepoint Poll
  → JVM đánh dấu trang bộ nhớ (page) là không thể truy cập
  → Luồng đọc → SIGSEGV → chuyển sang trạng thái chờ
```

### TTSP (Time To Safepoint)

```
Thời gian từ lệnh "dừng" đến luồng cuối cùng dừng lại

Các vấn đề:
  - Counted Loops (vòng lặp int) → có thể không có Safepoint nào
  - I/O nặng → luồng đang ở trong một system call
  - Swapping → trang Safepoint nằm trong swap

Giải pháp: -XX:+UseCountedLoopSafepoints
```

### Thread-Local Handshakes (Java 11+)

```
Trước đây: dừng TẤT CẢ các luồng để thao tác trên một luồng
Bây giờ: Handshake (bắt tay) với một luồng cụ thể
  → Các luồng khác vẫn tiếp tục làm việc!
  → Ví dụ: Thread Dump, Biased Lock revocation
```

### Chẩn đoán

```bash
# Safepoint logs
-Xlog:safepoint
-Xlog:safepoint+stats

# Hãy tìm:
# "reaching safepoint" → thời gian chờ
# Nếu > 100 ms → vấn đề!
```

## Senior Level

### Cơ chế Safepoint Polling

```
Safepoint Page:
  Bình thường: page có thể truy cập → đọc tức thì
  STW: Guard Page → SIGSEGV → luồng chờ

JIT chèn phép kiểm tra tại mỗi Safepoint:
  movl r0, [safepoint_page]  // Fast Path
  → Nếu page không thể truy cập → trap
```

JVM dùng polling page (trang bộ nhớ) thay vì kiểm tra một flag
vì việc đọc từ cache (page gần như luôn nằm trong L1) nhanh hơn
việc rẽ nhánh (branching). Đây là "fast path" — chi phí gần như bằng 0.

### Vấn đề Counted Loops

```java
// ❌ JIT không chèn Safepoint vào các counted loop
for (int i = 0; i < 1_000_000_000; i++) {
    // Một tỉ vòng lặp không có phép kiểm tra nào!
    // GC chờ → TTSP = hàng giây
}

// Giải pháp:
-XX:+UseCountedLoopSafepoints
// → JIT chèn phép kiểm tra mỗi N vòng lặp
// → chi phí ~1-2%
```

### JNI và STW

```
Các luồng JNI: JVM không thể kiểm tra stack của chúng trong lúc STW.
JVM chờ luồng JNI quay trở về code Java (đến được safepoint).
Luồng JNI KHÔNG phải "đang làm việc trong lúc STW" — nó bị chặn khi cố gắng quay về Java.
```

### JFR Safepoint Events

```
Java Flight Recorder:
  → Sự kiện 'Safepoint Begin'
  → Thời gian: entering (đi vào) + waiting (chờ) + cleanup (dọn dẹp)
  → Trực quan hóa trong JMC

Tìm các vấn đề:
  → Nếu entering > 50 ms → vấn đề TTSP
  → Nếu waiting > entering → một luồng đang làm chậm mọi thứ
```

### Best Practices

1. **Giám sát TTSP** qua safepoint logs
2. **Counted Loops** → UseCountedLoopSafepoints
3. **Handshakes (Java 11+)** → ít STW toàn cục hơn
4. **JFR** để trực quan hóa
5. **Tránh** các vòng lặp dài không có Safepoint
6. **JNI** → giám sát thời gian ở trong native

### Tóm tắt cho Senior

- **STW** = không chỉ GC, mà cả các thao tác JVM khác
- **Safepoints** = cơ chế điều phối các luồng
- **TTSP** = thời gian để đi vào STW (có thể dài hơn bản thân quá trình GC!)
- **Counted Loops** = nguyên nhân phổ biến của TTSP dài
- **Handshakes (Java 11+)** = giảm các khoảng dừng toàn cục
- **JFR** = công cụ phân tích tốt nhất

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- STW — JVM dừng TẤT CẢ các luồng của ứng dụng; không chỉ để GC, mà còn để thread dump, biased lock revocation, class redefinition
- Safepoints — các điểm trong code (thoát phương thức, cuối vòng lặp) nơi luồng có thể dừng; cơ chế: Safepoint Poll (Guard Page → SIGSEGV)
- TTSP (Time To Safepoint) — thời gian từ lệnh "dừng" đến luồng cuối cùng dừng lại; có thể dài hơn bản thân quá trình GC!
- Counted Loops — JIT không chèn Safepoint vào các vòng lặp `for (int i...)` → TTSP = hàng giây; giải pháp: `-XX:+UseCountedLoopSafepoints`
- Thread-Local Handshakes (Java 11+) — thao tác với một luồng cụ thể mà không dừng tất cả các luồng khác
- Các luồng JNI: JVM chờ luồng JNI quay trở về code Java; luồng KHÔNG làm việc trong lúc STW, nó bị chặn khi cố gắng quay về
- Polling page — việc đọc từ cache (page gần như luôn nằm trong L1) nhanh hơn việc rẽ nhánh; chi phí gần như bằng 0

**Các câu hỏi phụ thường gặp:**
- **Tại sao TTSP có thể dài hơn bản thân quá trình GC?** — Counted Loops không có Safepoint, I/O nặng (luồng trong một system call), swapping trang Safepoint
- **Làm sao chẩn đoán TTSP dài?** — `-Xlog:safepoint` (tìm "reaching safepoint" > 100 ms); JFR: sự kiện Safepoint Begin → entering/waiting/cleanup
- **Thread-Local Handshakes là gì?** — Java 11+: bắt tay với một luồng cụ thể thay vì dừng tất cả; ví dụ: Thread Dump, Biased Lock revocation
- **Tại sao Safepoint Polling nhanh hơn kiểm tra flag?** — Đọc L1 cache (page gần như luôn ở đó) nhanh hơn rẽ nhánh; fast path = gần như 0 chi phí

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "STW chỉ dành cho GC" — STW cũng dành cho thread dump, biased lock revocation, class redefinition
- "Các luồng JNI làm việc trong lúc STW" — luồng JNI bị chặn khi cố gắng quay về Java; JVM chờ nó
- "Counted Loops không ảnh hưởng đến hiệu năng" — không có Safepoint, TTSP có thể là hàng giây
