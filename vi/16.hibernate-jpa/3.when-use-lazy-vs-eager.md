# When to Use Lazy vs Eager Loading (Khi nào dùng Lazy vs Eager loading)

## Overview

Việc lựa chọn giữa `LAZY` và `EAGER` là lựa chọn giữa khả năng mở rộng và sự tiện lợi khi phát triển. Trong phát triển Java/Spring hiện đại, có một "quy tắc vàng": **dùng LAZY theo mặc định cho đại đa số các association**.

---

## Junior Level

### Quy Tắc Cơ Bản

**Hầu như luôn luôn dùng LAZY.** EAGER - chỉ khi bạn biết chính xác tại sao.

**LAZY khi:**
- Association `@OneToMany` hoặc `@ManyToMany`
- Dữ liệu liên quan không phải lúc nào cũng cần
- Collection lớn
- Dữ liệu có thể nặng khi tải

**EAGER khi:**
- `@ManyToOne` và dữ liệu **luôn luôn** cần thiết
- Các association nhỏ, bắt buộc (dữ liệu tham chiếu)
- Dữ liệu cần thiết trong 100% các lần dùng entity parent

```java
// LAZY - items không phải lúc nào cũng cần
@OneToMany(mappedBy = "order", fetch = FetchType.LAZY)
private List<OrderItem> items;

// LAZY - user không phải lúc nào cũng cần
@ManyToOne(fetch = FetchType.LAZY)
private User user;

// EAGER chỉ hợp lý cho các association nhỏ, bắt buộc
// UserProfile là một entity nhỏ, luôn hiển thị cùng User,
// nếu không có nó User sẽ không đầy đủ. EAGER hợp lý ở đây.
@OneToOne(fetch = FetchType.EAGER)
private UserProfile profile;  // luôn cần cùng với User
```

### Khi Nào LAZY Là Lựa Chọn Tồi

1. **Batch processing** khi tất cả dữ liệu liên quan đều cần thiết - tốt hơn nên tải ngay lập tức thông qua JOIN FETCH
2. **Các bảng tham chiếu nhỏ** (1-10 bản ghi) - overhead của lazy loading vượt quá lợi ích
3. **Các entity LUÔN LUÔN cần cùng nhau** - hai truy vấn riêng biệt chậm hơn một JOIN

## Middle Level

### Các Khuyến Nghị Thực Tế

```
@ManyToOne -> LAZY (hầu như luôn luôn, bất chấp mặc định EAGER)
@OneToMany -> LAZY (mặc định, đừng thay đổi)
@OneToOne -> LAZY (thường bị quên ghi đè)
@ManyToMany -> LAZY (mặc định, đừng thay đổi)
```

### Tại Sao Nên Ghi Đè @ManyToOne Thành LAZY

```java
@Entity
public class Order {
    // Mặc định là EAGER, nhưng chúng ta ghi đè
    @ManyToOne(fetch = FetchType.LAZY)
    private User user;
}

// Khi tải Order mà không có JOIN:
// Không có LAZY: SELECT o.*, u.* FROM orders o JOIN users u ON ...
// Có LAZY: SELECT o.* FROM orders o (user chỉ tải khi truy cập)
```

### Các Ví Dụ Về Quyết Định Đúng Đắn

```java
// LAZY cho collection
@OneToMany(mappedBy = "order", fetch = FetchType.LAZY)
private List<OrderItem> items;

// LAZY cho @ManyToOne
@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "user_id")
private User user;

// LAZY cho @OneToOne
@OneToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "address_id")
private Address address;

// Tải khi cần - thông qua JOIN FETCH
@Query("SELECT DISTINCT o FROM Order o " +
       "JOIN FETCH o.user " +
       "JOIN FETCH o.items " +
       "WHERE o.id = :id")
Order findByIdComplete(@Param("id") Long id);
```

### Các Lỗi Thường Gặp

```java
// EAGER cho các collection lớn
@OneToMany(fetch = FetchType.EAGER)
private List<Order> orders;
// Tải TẤT CẢ order -> suy giảm hiệu năng

// EAGER "phòng khi cần"
@ManyToOne(fetch = FetchType.EAGER)
private Category category;
// Ngay cả khi category không được hiển thị - JOIN thừa
```

## Senior Level

### Đánh Đổi Kiến Trúc

| LAZY                                      | EAGER                      |
| ----------------------------------------- | -------------------------- |
| Linh hoạt và mở rộng tốt hơn              | Đơn giản hơn để phát triển  |
| Cần suy nghĩ về việc tải                  | Luôn khả dụng               |
| Có thể gây LazyInitializationException    | Có thể gây N+1 problem      |
| Tải động                                  | Tải tĩnh                    |
| Phù hợp cho microservices                 | Phù hợp cho monolith        |

### Chiến Lược Senior Developer: "LAZY + Tải Động"

Thay vì khai báo tĩnh `FetchType` trong Entity, hãy dùng **tải động**:

```
1. Toàn cục: LAZY cho tất cả association
2. Cục bộ: FETCH khi cần trong một truy vấn cụ thể
   - JPQL: JOIN FETCH
   - Spring Data JPA: @EntityGraph
   - Criteria API: root.fetch("association")
```

### Tại Sao "LAZY Theo Mặc Định" Là Đúng

```
Nếu bạn khai báo một association là EAGER:
-> Bạn KHÔNG BAO GIỜ có thể làm cho nó lazy trong một truy vấn cụ thể
-> Hibernate vẫn sẽ fetch dữ liệu

Nếu bạn khai báo một association là LAZY:
-> Bạn có thể "biến nó thành" EAGER bất cứ lúc nào thông qua JOIN FETCH
-> LAZY mang lại tính linh hoạt tối đa
```

### DTO Projection Thay Vì EAGER

```java
// Thay vì EAGER loading - dùng DTO cho API
@Query("""
    SELECT new com.example.OrderDto(
        o.id, o.date, o.status, u.name, u.email
    )
    FROM Order o JOIN o.user u
    WHERE o.id = :id
    """)
OrderDto findOrderDto(@Param("id") Long id);

// Ưu điểm:
// 1. Một truy vấn thay vì hai
// 2. Ít dữ liệu trong bộ nhớ hơn
// 3. Không có vấn đề serialization
// 4. Kiểm soát được API contract
```

### Kiến Trúc Microservice

Trong microservices với một DB chung (không khuyến nghị, nhưng vẫn xảy ra) LAZY đặc biệt quan trọng vì dữ liệu thừa = tải thêm lên một tài nguyên chung. Trong microservices đúng đắn với các DB riêng biệt, câu hỏi này được giải quyết ở cấp độ API contract.

### Kinh Nghiệm Production

```java
// Spring Data JPA với @EntityGraph
public interface OrderRepository extends JpaRepository<Order, Long> {

    @EntityGraph(attributePaths = {"user", "items"})
    Optional<Order> findByIdWithDetails(Long id);

    @EntityGraph(attributePaths = {"user"})
    List<Order> findByUserId(Long userId);

    // Không có EntityGraph - chỉ Order không có association
    List<Order> findByStatus(String status);
}
```

### Best Practices

```
LAZY theo mặc định cho TẤT CẢ association
Ghi đè @ManyToOne và @OneToOne thành LAZY
JOIN FETCH khi dữ liệu cần thiết
@EntityGraph để tải động
DTO projection cho chỉ đọc/API
Giám sát truy vấn DB

EAGER cho collection
EAGER "phòng khi cần"
Giải quyết LazyInitializationException thông qua EAGER
Tải entity cho các thao tác chỉ đọc đơn giản
```

### Tóm Tắt Cho Senior

- **EAGER** - tĩnh và xâm lấn, không thể bị hủy
- **LAZY** - động và linh hoạt, có thể tải khi cần
- Ghi đè các association EAGER mặc định (`OneToOne`, `ManyToOne`) thành LAZY
- Giải quyết `LazyInitializationException` thông qua thiết kế transaction đúng đắn hoặc Entity Graph, không phải bằng cách chuyển sang EAGER

## Interview Cheat Sheet

**Cần phải biết:**
- Quy tắc vàng: LAZY theo mặc định cho TẤT CẢ association
- Ghi đè @ManyToOne và @OneToOne thành LAZY (mặc định của chúng là EAGER)
- EAGER không thể bị hủy trong một truy vấn, LAZY có thể được tải thông qua JOIN FETCH
- LAZY mang lại tính linh hoạt tối đa - tải động khi cần
- DTO projection cho API thay vì tải toàn bộ entity
- Trong microservices, LAZY đặc biệt quan trọng để giảm tải DB

**Các câu hỏi phụ thường gặp:**
- **Khi nào EAGER hợp lý?** Các association nhỏ, bắt buộc (dữ liệu tham chiếu), dữ liệu cần thiết trong 100% trường hợp
- **Tại sao ghi đè @ManyToOne thành LAZY?** Ngay cả khi không cần user - JOIN thừa nếu không có LAZY
- **Nên làm gì với LazyInitializationException?** Thiết kế transaction đúng đắn, Entity Graph, DTO - KHÔNG chuyển sang EAGER

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "EAGER cho @ManyToOne - đó là mặc định, tôi không đụng vào nó" - cần ghi đè thành LAZY
- "Tôi giải quyết LazyInitializationException thông qua EAGER" - tạo ra N+1
- "LAZY chỉ cho collection" - LAZY cho tất cả association bao gồm cả @ManyToOne
