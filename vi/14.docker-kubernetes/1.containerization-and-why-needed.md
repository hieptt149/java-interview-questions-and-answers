# What is containerization and why is it needed? (Containerization là gì và tại sao cần đến nó?)

## Junior Level

### Giải Thích Đơn Giản

**Containerization (đóng gói container hóa)** là một công nghệ để đóng gói một ứng dụng cùng với tất cả các dependency của nó (thư viện, cấu hình, tiện ích hệ thống) vào một khối cô lập duy nhất — một **container**.

**Một container không phải là một file và không phải là một archive.** Nó là một Linux process (tiến trình) bình thường mà kernel cho phép chỉ nhìn thấy các file, network, và các process của riêng nó (thông qua namespaces và cgroups).

Bạn viết một ứng dụng Java. Nó chạy trên máy của bạn, nhưng khi bạn đưa nó cho đồng nghiệp hoặc deploy lên server — các lỗi xảy ra: "Tôi có phiên bản Java khác", "thiếu thư viện", "cài đặt môi trường khác". Containerization giải quyết vấn đề này: bạn đóng gói mọi thứ cần thiết vào một image duy nhất, và nó hoạt động giống nhau ở mọi nơi.

Một image là một template/class (giống như một class trong OOP). Một container là một instance đang chạy của một image (giống như một object).

### Phép So Sánh

Một container giống như một **shipping container (container vận chuyển)**. Không quan trọng bên trong có gì (đồ điện tử, quần áo, thực phẩm) — cần cẩu và tàu đều xử lý nó giống nhau. Tương tự với các container phần mềm: không quan trọng ứng dụng nào bên trong (Java, Python, Node.js) — Docker xử lý chúng một cách thống nhất.

### Ví Dụ

```dockerfile
# Dockerfile đơn giản cho một ứng dụng Java
FROM openjdk:17-jdk-slim
COPY myapp.jar /app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app.jar"]
```

```bash
# Build và chạy
docker build -t myapp .
docker run -p 8080:8080 myapp
```

### Các Lợi Ích Chính

1. **"Chạy được trên máy tôi" không còn là vấn đề nữa** — cùng một image chạy trên máy của developer, môi trường test, và production.
2. **Khởi động nhanh** — một container khởi động trong vài giây vì nó không cần boot OS riêng của nó — nó dùng kernel của host đang chạy sẵn. Các VM boot toàn bộ một OS.
3. **Nhẹ** — các container chiếm megabyte, không phải gigabyte.
4. **Cô lập** — các ứng dụng không xung đột với nhau về thư viện và phiên bản.

### Cần Nhớ

- Container = ứng dụng + tất cả dependency của nó trong một package
- Các container chạy giống nhau trên bất kỳ máy nào có Docker
- Các container nhẹ và nhanh
- Kubernetes được dùng để quản lý nhiều container

### Khi Nào KHÔNG Nên Dùng Container

1. **Các ứng dụng GUI** — các container được tối ưu hóa cho các service headless
2. **Các hệ thống realtime** với yêu cầu kernel nghiêm ngặt
3. **Các ứng dụng yêu cầu cô lập hoàn toàn** — VM tốt hơn

## Middle Level

### Containerization Hoạt Động Như Thế Nào Bên Dưới

Containerization dựa trên hai cơ chế then chốt của Linux kernel:

#### 1. Namespaces — cung cấp sự cô lập

Mỗi container nhận được không gian cô lập riêng của nó:

| Namespace | Nó cô lập cái gì                                    |
| --------- | --------------------------------------------------- |
| `PID`     | Các process (container chỉ thấy các process của riêng nó)   |
| `NET`     | Network (các network interface và port riêng của nó)      |
| `MNT`     | Filesystem (điểm mount riêng của nó)                    |
| `UTS`     | Hostname                                            |
| `IPC`     | Giao tiếp giữa các process                         |
| `USER`    | Người dùng và nhóm                                  |

#### 2. Control Groups (cgroups) — cung cấp giới hạn tài nguyên

Cgroups cho phép đặt các giới hạn cứng: một container có thể dùng bao nhiêu CPU và RAM, giới hạn disk I/O, giới hạn network. Không có cgroups, một container "tham lam" có thể chiếm toàn bộ tài nguyên hệ thống.

### Container vs Máy Ảo

| Đặc điểm     | Container             | Máy Ảo              |
| ------------------ | ---------------------- | ----------------------------- |
| **Kiến trúc**   | Dùng chung kernel OS       | Mỗi VM có Guest OS riêng của nó  |
| **Cô lập**      | Cấp process          | Cấp phần cứng                   |
| **Tốc độ khởi động**  | Vài giây                | Vài phút                       |
| **Kích thước image**     | Vài chục/vài trăm MB    | Vài gigabyte                       |
| **Hiệu năng**    | Gần như native          | Overhead từ hypervisor           |

### Các Lỗi Thường Gặp

| Lỗi                             | Hậu quả                        | Cách tránh               |
| ----------------------------------- | ----------------------------------- | -------------------------- |
| Lưu dữ liệu bên trong container       | Dữ liệu mất khi restart               | Dùng Volume                |
| Chạy với quyền root                     | Rủi ro bảo mật                      | Dùng `USER nonroot`         |
| Dùng tag `latest`                  | Build không tất định           | Ghim (pin) phiên bản image         |
| Bỏ qua `.dockerignore`            | Build chậm, dư thừa file            | Tạo `.dockerignore`     |

Volume — bộ nhớ ngoài tồn tại qua các lần restart container.

### Tại Sao Containerization Quan Trọng Trong Các Dự Án Thực Tế

1. **Immutable Infrastructure (hạ tầng bất biến)** — chúng ta không thay đổi code trên server. Chúng ta tạo một image mới, test nó, và deploy. Rollback là tức thì.
2. **Environments Parity (sự tương đồng giữa các môi trường)** — developer, QA, và Production dùng cùng một artifact.
3. **Kiến trúc microservices** — các container lý tưởng để chạy hàng trăm thành phần độc lập nhỏ.
4. **Các pipeline CI/CD** — các container đã trở thành phương thức delivery tiêu chuẩn: build → test → image → deploy.

### Cần Nhớ

- Containerization dựa trên Namespaces (cô lập) và Cgroups (tài nguyên)
- Các container nhẹ hơn và nhanh hơn VM nhưng có sự cô lập kém nghiêm ngặt hơn
- Containerization là nền tảng của microservices và CI/CD
- Rủi ro chính: dùng chung kernel và sự phức tạp trong quản lý trạng thái

## Senior Level

### Kiến Trúc Nội Bộ Sâu Xa

Một container là một **Linux process bình thường** bị giới hạn thông qua các system call của kernel. Không có mô phỏng, không có lớp trung gian. Trình tự khi khởi động một container:

1. **Clone syscall** với các cờ `CLONE_NEWPID | CLONE_NEWNET | CLONE_NEWNS | CLONE_NEWUTS | CLONE_NEWIPC` — tạo một process với các namespace mới.
2. **Chroot/pivot_root** — thay đổi root filesystem của container.
3. **Cài đặt Cgroups** — đặt các giới hạn CPU, memory, I/O qua cgroup v2 (unified hierarchy).
4. **Seccomp/AppArmor** — áp dụng các security profile, giới hạn các syscall khả dụng.

### Các Đánh Đổi (Trade-offs)

| Khía cạnh             | Ưu điểm                                    | Nhược điểm                                   |
| ------------------ | -------------------------------------------- | ---------------------------------------------- |
| Dùng chung kernel      | Overhead tối thiểu (< 1% CPU)                  | Lỗ hổng kernel ảnh hưởng đến tất cả container    |
| Bản chất ngắn hạn (ephemeral)   | Dễ thay thế, scale                       | Không thể lưu trạng thái bên trong             |
| UnionFS (Overlay2) | Tái sử dụng layer, tiết kiệm disk/RAM                | Overhead disk I/O với nhiều layer             |
| Network namespace  | Cô lập network                            | Sự phức tạp: NAT, DNS, service discovery        |

### Edge Case

- **Container Escape**: thông qua các lỗ hổng kernel (Dirty COW, CVE-2019-5736 runc), các capability cấu hình sai, mount `/proc`/`/sys`. Giảm thiểu: seccomp profile, AppArmor/SELinux, rootfs chỉ đọc, loại bỏ tất cả các capability.
- **Zombie process**: process PID 1 trong một container mặc định không nhận SIGTERM và không reap các process con. Giải pháp: exec form hoặc tini.
- **Clock skew (lệch đồng hồ)**: các container có thể bị lệch đồng bộ đồng hồ với host, quan trọng đối với TLS và distributed consensus.
- **Inode exhaustion (cạn kiệt inode)**: các container với nhiều file nhỏ có thể làm cạn kiệt inode trên host, ngay cả khi vẫn còn dung lượng đĩa.

### Hiệu Năng

| Chỉ số           | Container                        | VM                             |
| ---------------- | --------------------------------- | ------------------------------ |
| Overhead CPU     | < 1%                              | 5-15%                          |
| Overhead Memory  | Vài MB mỗi container              | GB mỗi Guest OS                |
| Network          | Gần như native                     | Ảo hóa NIC                |
| Disk I/O         | Overhead nhỏ từ Overlay2      | Ảo hóa storage controller |
| Mật độ          | 100+ mỗi server                   | 10-30 mỗi server               |
| Sử dụng CPU  | 60-80%                            | 20-40%                          |

### Bảo Mật Production

```dockerfile
# Cách tiếp cận sẵn sàng cho production
FROM gcr.io/distroless/java17-debian12  # bề mặt tấn công tối thiểu
RUN addgroup --system appgroup && adduser --system appuser --ingroup appgroup
USER appuser                              # non-root
COPY --chown=appuser:appgroup app.jar /app.jar
# Filesystem chỉ đọc được cấu hình trong docker run / K8s
# Seccomp profile, AppArmor profile — ở cấp độ runtime
```

**Các nguyên tắc chính:**
- Đừng dùng `--privileged`
- Loại bỏ tất cả các capability, chỉ thêm những cái cần thiết
- Root filesystem chỉ đọc nếu có thể
- Quét image trong CI/CD (Trivy, Snyk)
- Bảo vệ runtime (Falco)

### Câu Chuyện Production

Một công ty đã di chuyển một monolith từ VM sang container. Kết quả: thời gian deploy giảm từ 45 phút xuống 90 giây, mật độ đóng gói tăng 4 lần, chi phí hạ tầng giảm 40%. Nhưng nó đòi hỏi: tái cấu trúc lại logging (stdout → ELK), thiết lập health check, triển khai monitoring tập trung (Prometheus + Grafana), viết lại quản lý trạng thái (volume ngoài), đào tạo team về Kubernetes. Containerization không chỉ là công nghệ, mà còn là **sự thay đổi quy trình**.

### Monitoring

- **Golden Signals**: latency (độ trễ), traffic (lưu lượng), errors (lỗi), saturation (bão hòa)
- **Công cụ**: Prometheus (metrics), cAdvisor (metrics container), Jaeger (tracing), ELK/EFK (log)
- **Các chỉ số chính**: số lần restart, mức sử dụng memory so với giới hạn, CPU throttling, network I/O, thời gian uptime của container
- **Alerting**: OOMKilled, CrashLoopBackOff, HighRestartRate

### Tóm Tắt

- Containerization là tiêu chuẩn delivery phần mềm hiện đại. Nền tảng: Namespaces + Cgroups.
- Ưu điểm chính: khả năng tái tạo (reproducibility) và tốc độ. Rủi ro chính: dùng chung kernel và sự phức tạp trong quản lý trạng thái.
- Các container ảnh hưởng đến kiến trúc: các ứng dụng phải ngắn hạn (ephemeral), có thể cấu hình từ bên ngoài, tự phục hồi (self-healing).
- Ở quy mô lớn, cần một orchestrator (Kubernetes), điều này thêm vào sự phức tạp riêng của nó.
- Với multi-tenancy và tuân thủ nghiêm ngặt, cân nhắc MicroVM (Firecracker, Kata Containers).

## Interview Cheat Sheet

**Cần phải biết:**
- Container = một Linux process, bị giới hạn qua namespaces + cgroups
- Namespaces cung cấp sự cô lập (PID, NET, MNT), cgroups — giới hạn tài nguyên
- Các container dùng chung kernel host, VM có kernel riêng — do đó có sự khác biệt về tốc độ và kích thước
- Image = template (class), container = instance đang chạy (object)
- Các container là ngắn hạn (ephemeral) — trạng thái được lưu trong volume ngoài
- Cho production: user non-root, FS chỉ đọc, quét image
- Containerization là nền tảng của microservices và CI/CD

**Các câu hỏi phụ thường gặp:**
- *"Tại sao container nhanh hơn VM?"* — Không cần boot Guest OS, dùng chung kernel, khởi động trong vài giây
- *"Namespace là gì?"* — Cơ chế của Linux kernel cô lập tài nguyên process (PID, network, FS)
- *"Bạn có thể chạy một container Linux trên Windows không?"* — Có, qua WSL2 hoặc một VM với Linux kernel
- *"Overlay2 là gì?"* — FS theo lớp (layered) tái sử dụng các layer cơ sở giữa các image

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Một container là một VM nhẹ" (không, kiến trúc hoàn toàn khác)
- "Các container hoàn toàn cô lập" (dùng chung kernel = rủi ro container escape)
- "Dữ liệu bên trong container tồn tại lâu dài" (ngắn hạn, cần volume)
- "Container = một file" (đó là một Linux process với namespaces/cgroups)
