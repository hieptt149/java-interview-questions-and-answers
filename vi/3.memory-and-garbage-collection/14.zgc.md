# What is ZGC? (ZGC là gì?)

## Junior Level

**ZGC (Z Garbage Collector)** — collector với khoảng dừng tối thiểu (< 1 ms), không phụ thuộc vào kích thước Heap. Throughput thấp hơn G1 khoảng 5-15%.

**Ưu điểm chính:** Các khoảng dừng *về cơ bản* không phụ thuộc vào kích thước Heap và thường < 1 ms. Dưới tải cực lớn, có thể có sai lệch.

**Khi nào dùng:**
- Các hệ thống real-time
- High-frequency trading
- Khi SLA < 10 ms

## Middle Level

### Các công nghệ chính

**1. Colored Pointers:**
```
Con trỏ 64-bit:
  Bit 0-41: địa chỉ đối tượng
  Bit 42-45: metadata (trạng thái GC)

→ GC hiểu được trạng thái đối tượng chỉ bằng cách đọc con trỏ
→ Không cần truy cập vào bộ nhớ của đối tượng!

Colored Pointers — trong các con trỏ 64-bit, ZGC dùng các bit cao
để lưu trữ metadata (thế hệ, finalizable, weak, v.v.).
JVM "tô màu" các con trỏ, tiết kiệm được một cấu trúc dữ liệu riêng.
```

**2. Load Barriers:**
```
Trên mỗi lần đọc tham chiếu:
  → Kiểm tra màu (color) của con trỏ
  → Nếu đối tượng đã di chuyển → sửa địa chỉ (Self-healing)
  → chi phí ~5-15% CPU

Load Barriers — kiểm tra trên MỖI lần đọc tham chiếu. Nếu con trỏ
"sai" (đối tượng đã di chuyển), Load Barrier tự động
sửa con trỏ (Self-Healing).
```

**3. Concurrent Evacuation:**
```
Các đối tượng được di chuyển KHÔNG cần dừng ứng dụng!
  → Khác với G1 (Evacuation = STW)
  → Chỉ dừng để quét GC Roots
```

### ZGC vs G1

| Tiêu chí   | G1        | ZGC    |
| ---------- | --------- | ------ |
| Khoảng dừng | 20-200 ms | < 1 ms |
| Throughput | Cao       | -5-10% |
| Heap tối đa | 64 GB     | 16 TB  |
| Barriers   | Write     | Load   |

### Generational ZGC (Java 21+)

```
Trước Java 21: một thế hệ duy nhất
  → Quét toàn bộ Heap trong mỗi lần thu gom

Trước Java 21, ZGC là non-generational — điều này gây ra Allocation Stall
khi tốc độ cấp phát cao. Generational ZGC (Java 21+) giải quyết
vấn đề này.

Java 21+: các thế hệ Young và Old
  → -50% chi phí CPU
  → Các Allocation Stall gần như biến mất
```

### Khi nào KHÔNG dùng

```
❌ CPU bound (90%+) → Load Barriers sẽ làm nó tệ hơn
❌ Heap < 4 GB → G1 hiệu quả hơn
❌ Các hệ thống 32-bit → ZGC yêu cầu 64-bit
```

### Tinh chỉnh (Tuning)

```bash
-XX:+UseZGC -XX:+ZGenerational  # Java 21+
-XX:SoftMaxHeapSize=24g          # Trả bộ nhớ về một cách tích cực
-XX:ConcGCThreads=4              # Các luồng GC
```

## Senior Level

### Multi-mapping

```
Một vùng bộ nhớ vật lý được ánh xạ (map) tới 3 địa chỉ ảo
  → Các tổ hợp bit metadata khác nhau
  → OS không thấy xung đột con trỏ
  → Cho phép các con trỏ "được tô màu" hoạt động

Multi-mapping — kỹ thuật ánh xạ một vùng Heap tới nhiều
địa chỉ ảo, để mã hóa metadata trong các địa chỉ con trỏ.
```

### Self-Healing Pointers

```
Load Barrier khi đọc:
  1. Đọc con trỏ
  2. Kiểm tra bit Remapped
  3. Nếu không Remapped → đối tượng đã di chuyển
  4. Tính địa chỉ mới
  5. Cập nhật con trỏ trong Heap (CAS)
  6. Trả về địa chỉ mới

→ Con trỏ "tự chữa lành" (heal) chính nó trên mỗi lần đọc
```

### Đào sâu Allocation Stall

```
Nguyên nhân: GC không thể đánh dấu rác đủ nhanh
  → Các luồng của ứng dụng chờ bộ nhớ

Giải pháp:
  1. Tăng Heap
  2. Tăng ConcGCThreads
     `ConcGCThreads` mặc định là số lõi / 4.
     Tăng nếu bạn thấy Allocation Stall; giảm nếu GC chiếm quá nhiều CPU.
  3. Generational ZGC (Java 21+)
  4. Giảm Allocation Rate
```

### Best Practices

1. **Java 21+** — dùng Generational ZGC
2. **ConcGCThreads** = số lõi / 4
3. **SoftMaxHeapSize** cho các container
4. **Giám sát** Allocation Stall trong logs
5. **Chi phí CPU 5-15%** — hãy tính đến điều đó

### Tóm tắt cho Senior

- **ZGC** = Colored Pointers + Load Barriers + Concurrent Evacuation
- **Khoảng dừng < 1 ms** là hằng số, không phụ thuộc vào Heap
- **Generational (Java 21+)** = -50% chi phí
- Các con trỏ **Self-healing** thông qua Load Barriers
- **Allocation Stall** = rủi ro chính
- **Chi phí CPU 5-15%** — cái giá cho low latency

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- ZGC: khoảng dừng < 1 ms, không phụ thuộc vào kích thước Heap (lên đến 16 TB); throughput thấp hơn G1 khoảng 5-15%
- Colored Pointers: các bit cao của con trỏ 64-bit lưu trữ metadata (thế hệ, trạng thái GC)
- Load Barriers: trên mỗi lần đọc tham chiếu, kiểm tra màu con trỏ + Self-healing (nếu đối tượng đã di chuyển)
- Concurrent Evacuation: các đối tượng được di chuyển KHÔNG cần STW (khác với G1, nơi Evacuation = STW)
- Multi-mapping: một vùng Heap vật lý được ánh xạ tới 3 địa chỉ ảo để mã hóa metadata
- Generational ZGC (Java 21+): chia thành Young/Old → -50% chi phí CPU, các Allocation Stall gần như biến mất
- Khi nào KHÔNG dùng: CPU bound (90%+), Heap < 4 GB, các hệ thống 32-bit

**Các câu hỏi phụ thường gặp:**
- **Tại sao ZGC chậm hơn G1 về throughput?** — Load Barriers trên mỗi lần đọc tham chiếu thêm 5-15% chi phí CPU
- **Allocation Stall trong ZGC là gì?** — GC không thể đánh dấu rác đủ nhanh → các luồng ứng dụng chờ; giải pháp: tăng Heap, ConcGCThreads, hoặc Generational ZGC
- **Self-Healing pointers là gì?** — Load Barrier đọc con trỏ → kiểm tra bit Remapped → nếu đối tượng đã di chuyển, tính địa chỉ mới và cập nhật con trỏ (CAS)
- **Tại sao Multi-mapping?** — Một vùng Heap tới 3 địa chỉ ảo → mã hóa metadata trong các địa chỉ mà không có xung đột con trỏ

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "ZGC dùng Write Barriers" — ZGC dùng Load Barriers (khi đọc); G1 dùng Write Barriers (khi ghi)
- "ZGC hoạt động trên các hệ thống 32-bit" — ZGC yêu cầu hệ thống 64-bit (Colored Pointers dùng các bit cao)
- "ZGC luôn tốt hơn G1" — với CPU-bound hoặc xử lý theo lô, G1 cho throughput tốt hơn
