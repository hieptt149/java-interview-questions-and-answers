# When Does Rehashing (Resize) Occur in HashMap? (Khi nào Rehashing (Resize) xảy ra trong HashMap?)

## 🟢 Junior Level

**Rehashing (resize)** là quá trình tăng kích thước mảng nội bộ của HashMap. Nó xảy ra trong ba trường hợp:

1. **`put()` đầu tiên** — khi tạo HashMap, mảng rỗng, `put` đầu tiên tạo nó
2. **Vượt ngưỡng (threshold)** — khi số lượng phần tử > `capacity * loadFactor`
3. **Treeification với một table nhỏ** — 8 phần tử trong một bucket và capacity < 64

**Ví dụ:**
```java
HashMap<String, Integer> map = new HashMap<>(); // table = null
map.put("key1", 1);  // put đầu tiên: mảng 16 bucket được tạo
// ... thêm 11 phần tử nữa (tổng 12)
map.put("key13", 13); // phần tử thứ 13: capacity tăng lên 32
```

**Tại sao nó quan trọng?** Resize là một thao tác O(n) chậm. Tốt hơn là đặt kích thước đúng ngay từ đầu.

## 🟡 Middle Level

### Các Trigger Resize

| Trigger           | Điều kiện                          | Hành động                |
| ----------------- | ---------------------------------- | ------------------------ |
| put đầu tiên      | `table == null`                    | Mảng kích thước 16 được tạo |
| Vượt ngưỡng       | `++size > threshold`               | Mảng tăng đôi            |
| Treeification     | 8 phần tử trong bucket, capacity < 64 | Resize thay vì tree   |

### Công thức Threshold

```java
threshold = capacity * loadFactor;
// Theo mặc định: 16 * 0.75 = 12
```

### Điều gì xảy ra trong lúc Resize?

1. Một mảng mới lớn gấp 2x được tạo
2. Mọi phần tử được chuyển sang mảng mới
3. Threshold được tính lại

**Hiệu năng:**
- Thời gian: O(n) — duyệt qua mọi phần tử
- Bộ nhớ: hai mảng tồn tại tạm thời
- GC pressure: tạo tải cho garbage collector

### Làm sao tránh Resize?

```java
// Nếu bạn biết sẽ có 1000 phần tử:
int capacity = (int)(1000 / 0.75f) + 1;
new HashMap<>(capacity);
```

### Các sai lầm thường gặp

1. **Không tính đến việc làm tròn** — `new HashMap(1000)` cho capacity 1024, threshold 768
2. **Resize trong hot path** — trong một vòng lặp với các put thường xuyên, resize gây tăng vọt latency
3. **Multi-threaded resize** — trong Java 7, gây cycling

### Khi nào Resize là chấp nhận được

Resize là chấp nhận được: khi nạp dữ liệu ban đầu (một lần), cho các thao tác không then chốt về latency. KHÔNG chấp nhận được: trong hot path của một HTTP request handler, trong các hệ thống real-time.

## 🔴 Senior Level

### Lazy Initialization

```java
public V put(K key, V value) {
    return putVal(hash(key), key, value, false, true);
}

final V putVal(int hash, K key, V value, boolean onlyIfAbsent, boolean evict) {
    Node<K,V>[] tab;
    if ((tab = table) == null || (n = tab.length) == 0)
        n = (tab = resize()).length; // Resize đầu tiên!
    ...
}
```

Resize đầu tiên xảy ra ở `put()` đầu tiên — điều này tạo mảng ban đầu.

### Resize khi Treeification

Ngoài resize do threshold, ở 8 phần tử trong một bucket và capacity < 64, một resize xảy ra THAY VÌ treeification — đây là một nỗ lực để trải các phần tử qua các bucket mới, thay vì chuyển một list thành một tree.

### Nguy hiểm của Multi-threaded Resize

HashMap không thread-safe:
- **Java 7:** Resize song song → các tham chiếu vòng → vòng lặp vô hạn
- **Java 8+:** Đã sửa qua tail insertion, nhưng mất dữ liệu vẫn có thể xảy ra

```java
// Thread A và B đồng thời làm resize:
// Cả hai tạo một mảng mới, chuyển các phần tử
// Kết quả: mất phần tử, hành vi không xác định
```

### Ảnh hưởng tới hiệu năng

Resize là một trong những thao tác đắt nhất của HashMap:
- Cấp phát mảng mới: O(capacity)
- Sao chép phần tử: O(size)
- Tổng: O(n)

Trong các hệ thống nhạy về latency, điều này gây tăng vọt từ vài phần nghìn mili giây (với các Map nhỏ) tới 100+ ms (với các Map có hàng triệu phần tử; phụ thuộc JVM và kích thước HashMap).

### Giám sát Production

Dấu hiệu của các vấn đề resize:
- Các độ trễ định kỳ (spike) trong các metric latency
- Tăng hoạt động GC trong lúc resize
- Memory profiling: sự tồn tại đồng thời của hai mảng

### Best Practices

```java
// Guava:
Map<K, V> map = Maps.newHashMapWithExpectedSize(expectedSize);

// Hoặc thủ công:
new HashMap<>((int)(expectedSize / 0.75f) + 1);
```

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Ba trigger: put đầu tiên (tạo mảng), ++size > threshold, treeification ở capacity < 64
- threshold = capacity * loadFactor; theo mặc định 16 * 0.75 = 12
- Resize = O(n): cấp phát mảng mới + sao chép phần tử
- Lazy Initialization: mảng được tạo ở lần put đầu tiên, không phải trong constructor (Java 8+)
- Java 7: resize song song → vòng lặp vô hạn; Java 8+: đã sửa, nhưng mất dữ liệu vẫn có thể xảy ra
- Resize trong hot path — nguyên nhân của các tăng vọt latency

**Các câu hỏi phụ thường gặp:**
- **Tại sao resize tăng đôi, không phải +16?** — tăng đôi cho chèn khấu hao O(1)
- **Có thể tránh resize không?** — có, đặt initialCapacity = (expected / 0.75) + 1
- **Tại sao treeification trigger resize?** — nỗ lực trải các phần tử thay vì tạo một tree
- **Resize có chấp nhận được không?** — khi nạp ban đầu thì có; trong hot path của HTTP handler — không

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Resize xảy ra ở mọi put" — không, chỉ khi threshold bị vượt
- "Java 8 hoàn toàn an toàn khi resize" — không, mất dữ liệu vẫn có thể xảy ra
- "Resize tính lại hashCode" — không, một bit được kiểm tra (hash & oldCap)
