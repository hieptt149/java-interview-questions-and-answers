# What is CAS (Compare-And-Swap)? (CAS (Compare-And-Swap) là gì?)

---

## Junior Level

### Hiểu biết cơ bản

**CAS (Compare-And-Swap)** là một lệnh CPU atomic cho phép cập nhật một giá trị chỉ khi nó chưa thay đổi kể từ lúc được đọc. Đây là nền tảng của các thuật toán **lock-free**.

### Ví dụ minh họa đơn giản

Hãy tưởng tượng một máy ATM:
1. Bạn kiểm tra số dư: 1000 đồng
2. Bạn muốn rút 200 đồng (mong đợi còn lại 800)
3. ATM kiểm tra: "số dư có còn là 1000 không?"
4. Nếu có — rút 200, số dư mới 800
5. Nếu không (ai đó đã rút rồi) — hủy thao tác, cần thử lại

**Khác biệt then chốt so với synchronized:** CAS là một cách tiếp cận lạc quan (optimistic — thử, nếu thất bại thì thử lại). synchronized là một cách tiếp cận bi quan (pessimistic — khóa lại và làm, không ai xen vào được).

### CAS hoạt động như thế nào

```java
// CAS nhận 3 tham số:
// 1. Địa chỉ bộ nhớ
// 2. Giá trị mong đợi
// 3. Giá trị mới

boolean CAS(address, expectedValue, newValue) {
    if (memory[address] == expectedValue) {
        memory[address] = newValue;
        return true;  // Thành công!
    }
    return false; // Thất bại — giá trị đã thay đổi
}
```

### Ví dụ với AtomicInteger

```java
AtomicInteger counter = new AtomicInteger(0);

counter.incrementAndGet(); // Bên trong:
// 1. Đọc giá trị hiện tại (current = 0)
// 2. Tính giá trị mới (next = 1)
// 3. CAS: nếu value == 0, đặt thành 1
//    Nếu CAS thất bại — lặp lại từ bước 1
```

### Spin-loop

```java
public final int incrementAndGet() {
    for (;;) { // Vòng lặp vô hạn
        int current = get();        // Đọc
        int next = current + 1;     // Tính
        if (compareAndSet(current, next)) { // CAS
            return next;            // Thành công!
        }
        // CAS thất bại — ai đó khác đã cập nhật giá trị
        // Sang vòng lặp tiếp theo
    }
}
```

### Khi nào CAS nhanh hơn khóa?

| Kịch bản            | CAS                           | synchronized                    |
| ------------------- | ----------------------------- | ------------------------------- |
| Tranh chấp thấp     | Nhanh hơn (không khóa)         | Chậm hơn (acquire/release)      |
| Tranh chấp vừa      | Nhanh hơn                      | Trung bình                      |
| Tranh chấp cao      | Chậm hơn (vòng lặp vô hạn)     | Nhanh hơn (các thread bị park)  |

## Middle Level

### Thuật toán ở mức phần cứng

Trên kiến trúc x86, CAS được hiện thực qua lệnh **`LOCK CMPXCHG`**:

```assembly
; rax = giá trị mong đợi
; rcx = giá trị mới
; [memory] = giá trị thực tế trong bộ nhớ

lock cmpxchg [memory], rcx
; Nếu [memory] == rax:
;   [memory] = rcx      ← Ghi giá trị mới
;   ZF = 1              ← Cờ thành công
; Ngược lại:
;   rax = [memory]      ← Nạp giá trị thực tế
;   ZF = 0              ← Cờ thất bại
```

`lock` prefix khóa memory bus trong suốt thời gian thao tác — các core khác không thể truy cập ô nhớ này.

### CAS trong Java: Unsafe và VarHandle

#### Trước Java 9: sun.misc.Unsafe

  Trước Java 9: sun.misc.Unsafe (truy cập bộ nhớ trực tiếp, nguy hiểm)
  Java 9+: VarHandle (thay thế an toàn cho Unsafe, JEP 193)
  Lưu ý: Unsafe vẫn truy cập được trong Java 9+ qua `--add-opens`, nhưng không khuyến nghị.

```java
// Truy cập bộ nhớ trực tiếp (không khuyến nghị)
Unsafe unsafe = ...;
long offset = ...; // Offset của field trong bộ nhớ

int current;
do {
    current = unsafe.getIntVolatile(obj, offset);
} while (!unsafe.compareAndSwapInt(obj, offset, current, current + 1));
```

#### Java 9+: VarHandle

```java
// API có kiểu và an toàn
private static final VarHandle VALUE;
static {
    MethodHandles.Lookup l = MethodHandles.lookup();
    VALUE = l.findVarHandle(MyClass.class, "value", int.class);
}

int current;
do {
    current = (int) VALUE.getVolatile(this);
} while (!VALUE.compareAndSet(this, current, current + 1));
```

### Lock-free vs Wait-free

Trong một buổi phỏng vấn, việc phân biệt là quan trọng:

  Đây là một phân cấp đảm bảo tiến triển (progress guarantee):
  - **Wait-free** (mạnh nhất): MỌI thread hoàn thành thao tác trong một số bước hữu hạn
  - **Lock-free** (giữa): ÍT NHẤT MỘT thread hoàn thành thao tác trong một số bước hữu hạn
  - **Obstruction-free** (yếu nhất): thread hoàn thành nếu mọi thread khác bị treo

  Wait-free → Lock-free → Obstruction-free: mỗi cái sau yếu hơn cái trước.

| Thuật ngữ            | Đảm bảo                                                | Ví dụ                  |
| -------------------- | ------------------------------------------------------ | ---------------------- |
| **Lock-free**        | Ít nhất một thread hoàn thành thao tác trong thời gian hữu hạn | AtomicInteger      |
| **Wait-free**        | Mọi thread hoàn thành trong một số bước hữu hạn        | LongAdder.add()        |
| **Obstruction-free** | Thread hoàn thành nếu các thread khác không xen vào    | Một số hiện thực STM   |

  STM (Software Transactional Memory) — bộ nhớ giao dịch phần mềm: các thao tác thực thi trong một transaction, rồi commit atomic. Một cách tiếp cận thay thế cho lập trình lock-free.

### Exponential Back-off

Khi tranh chấp cao, một chu kỳ spin đơn giản lãng phí CPU. Giải pháp — các khoảng dừng:

```java
public int incrementWithBackoff() {
    int backoff = 1;
    for (;;) {
        int current = get();
        int next = current + 1;
        if (compareAndSet(current, next)) {
            return next;
        }
        // CAS thất bại — dừng
        Thread.onSpinWait(); // Gợi ý cho bộ xử lý

        // `Thread.onSpinWait()` — một gợi ý cho JVM/CPU: "Tôi đang trong một chu kỳ spin, bạn có thể tối ưu". Trên x86 đây là lệnh PAUSE, thứ giảm tiêu thụ điện năng và cải thiện hiệu năng chu kỳ spin.
        Thread.sleep(ThreadLocalRandom.current().nextInt(0, backoff));
        backoff = Math.min(backoff * 2, MAX_BACKOFF); // Tăng theo cấp số nhân
    }
}
```

### Vấn đề ABA

```
Thời gian  Thread 1        Thread 2        Stack (head)
──────────────────────────────────────────────────
t1    đọc A                              A → B → C
t2                  CAS(A, B)            B → C
t3                  CAS(B, A)            A → C (giá trị mới!)
t4    CAS(A, D) → THÀNH CÔNG!
      Nhưng stack đã thay đổi! B và C bị mất!
```

#### Giải pháp: AtomicStampedReference

```java
// Lưu giá trị + số version
AtomicStampedReference<String> ref = new AtomicStampedReference<>("A", 0);

int[] stampHolder = new int[1];
String value = ref.get(stampHolder);
int stamp = stampHolder[0];

// CAS chỉ khi cả giá trị VÀ version đều khớp
ref.compareAndSet("A", "D", stamp, stamp + 1);
```

## Khi nào CAS KHÔNG phù hợp

1. **Các thao tác gộp**: cần cập nhật atomic hai field — CAS làm việc trên một field
2. **Tranh chấp cao (100+ thread)**: chu kỳ CAS lãng phí CPU, tốt hơn nên dùng LongAdder hoặc Lock
3. **Các phép tính dài**: nếu hàng mili giây trôi qua giữa đọc và CAS — CAS sẽ liên tục thất bại
4. **Vấn đề ABA**: giá trị đổi A→B→A, CAS "không nhận ra" — cần AtomicStampedReference

## Senior Level

### Bên trong: Memory Ordering

CAS cung cấp một **rào chắn bộ nhớ đầy đủ** (StoreLoad):

```
Trước CAS:  Mọi lần ghi được đảm bảo đã hoàn tất
CAS:        Cập nhật atomic
Sau CAS:    Mọi lần đọc thấy dữ liệu mới nhất
```

Trên các kiến trúc khác nhau:

| Kiến trúc    | Hiện thực CAS      | Rào chắn                            |
| ------------ | ------------------ | ----------------------------------- |
| **x86**      | `lock cmpxchg`     | Rào chắn đầy đủ (x86 là strongly ordered) |
| **ARM**      | vòng lặp `ldxr/stxr`| Cần lệnh `dmb`                      |
| **RISC-V**   | vòng lặp `lr.w/sc.w`| Cần `fence`                        |

### Chu kỳ Spin và bão hòa CPU

Khi tranh chấp rất cao, các thread có thể spin mãi mãi:

```java
// Vấn đề: 100 thread, 1 biến CAS
for (;;) {
    int current = get();
    int next = current + 1;
    if (compareAndSet(current, next)) // Cả 100 thread liên tục thất bại
        return next;
    // CPU ở 100%, nhưng không có tiến triển!
}
```

**Giải pháp:**
1. **Exponential Back-off** — dừng giữa các lần thử
2. **LongAdder** — phân tán qua các cell
3. **Fallback về khóa** — nếu tranh chấp quá cao

### Hiệu năng: CAS vs Mutex

| Chỉ số                           | CAS              | Mutex (synchronized) |
| -------------------------------- | ---------------- | -------------------- |
| **Latency (không tranh chấp)**   | ~5-10 ns         | ~10-20 ns            |
| **Latency (có tranh chấp)**      | ~100+ ns (spin)  | ~1000+ ns (park)     |
| **Dùng CPU (có tranh chấp)**     | 100% (spin-loop) | ~0% (bị park)        |
| **Throughput (tranh chấp thấp)** | Cao hơn          | Thấp hơn             |
| **Throughput (tranh chấp cao)**  | Thấp hơn         | Cao hơn              |

**Điểm then chốt:** Khi tải rất cao, một mutex có thể tốt hơn vì nó "park" các thread thay vì đốt CPU.

### Bus Traffic và Cache Coherence

Trên các hệ thống đa xử lý, CAS thường xuyên gây ra:

1. **Cache Line Invalidation** — mỗi CAS gửi Invalidate tới tất cả các core
2. **Bus Traffic** — giao tiếp giữa các core dày đặc
3. **Memory Bandwidth Saturation** — bus bị nghẽn, các thao tác thông thường chậm lại

**Giải pháp:** Các cấu trúc segmented (như `ConcurrentHashMap`) hoặc `LongAdder`.

#### Đo lường tranh chấp

```java
// Ước lượng tranh chấp bằng code
AtomicLong counter = new AtomicLong(0);
long start = System.nanoTime();
for (int i = 0; i < 1_000_000; i++) {
    counter.incrementAndGet();
}
long elapsed = System.nanoTime() - start;
System.out.println("Average time: " + (elapsed / 1_000_000) + " ns");
// Lớn hơn nhiều so với 10 ns → tranh chấp
```

### Best Practices

1. **CAS cho các thao tác đơn giản** — increment, set, get
2. **Back-off khi tranh chấp** — `Thread.onSpinWait()` như một gợi ý CPU
3. **LongAdder cho các bộ đếm** — khi tranh chấp cao
4. **AtomicStampedReference** — khi vấn đề ABA có thể xảy ra
5. **Đừng dùng CAS cho các thao tác dài** — chuyển sang khóa
6. **Giám sát CAS failure** — qua JFR hoặc profiling
7. **Tránh CAS cho nhiều field** — dùng synchronized

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- CAS = Compare-And-Swap: so sánh atomic giá trị với giá trị mong đợi và ghi giá trị mới nếu khớp
- Trên x86: `lock cmpxchg` (`lock` prefix khóa memory bus); trên ARM: `ldxr/stxr`; trên RISC-V: `lr.w/sc.w`
- CAS cung cấp một rào chắn bộ nhớ đầy đủ (StoreLoad) — mọi lần ghi trước CAS đã hoàn tất, mọi lần đọc sau CAS là mới nhất
- CAS là cách tiếp cận lạc quan (thử/thử lại), synchronized là bi quan (khóa và làm)
- Lock-free (AtomicInteger) vs Wait-free (LongAdder): lock-free = ít nhất một thread hoàn thành; wait-free = mọi thread hoàn thành
- Vấn đề ABA: giá trị được trả về A→B→A, CAS sẽ không nhận ra; giải pháp — AtomicStampedReference (giá trị + version)
- Khi tranh chấp cao, chu kỳ CAS lãng phí CPU (100%); giải pháp — exponential back-off hoặc chuyển sang LongAdder/Lock

**Các câu hỏi phụ thường gặp:**
- **Khi nào CAS nhanh hơn synchronized?** — Khi tranh chấp thấp/vừa (không có overhead khóa/parking)
- **Khi nào synchronized nhanh hơn CAS?** — Khi tranh chấp cao (100+ thread): CAS spin và đốt CPU, mutex park các thread
- **`Thread.onSpinWait()` làm gì?** — Gợi ý cho JVM/CPU "Tôi đang trong một chu kỳ spin"; trên x86 = lệnh PAUSE, giảm tiêu thụ điện năng
- **CAS khác volatile như thế nào?** — volatile = chỉ visibility; CAS = visibility + ghi atomic (compare-and-swap)

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "CAS luôn nhanh hơn synchronized" — không, khi tranh chấp cao một mutex hiệu quả hơn
- "CAS không có vấn đề bộ nhớ" — không, CAS đặt một rào chắn bộ nhớ đầy đủ, thứ rất đắt
- "Vấn đề ABA là một bug của Java" — không, nó là một vấn đề nền tảng của các thuật toán CAS trong bất kỳ ngôn ngữ nào
- "Wait-free và lock-free giống nhau" — không, wait-free mạnh hơn: MỌI thread hoàn thành, lock-free — ít nhất MỘT
