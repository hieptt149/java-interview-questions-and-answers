# How to Implement Optimistic Locking in JPA (Cách triển khai optimistic locking trong JPA)

## Overview

Optimistic locking (khóa lạc quan) là một chiến lược kiểm soát đồng thời cho phép nhiều transaction đọc cùng dữ liệu nhưng ngăn chặn các cập nhật xung đột thông qua kiểm tra version.

---

## Junior Level

### Optimistic Locking Là Gì

Optimistic locking cho phép nhiều transaction **đọc cùng dữ liệu**, nhưng khi **cập nhật**, kiểm tra xem dữ liệu có bị thay đổi bởi một transaction khác không.

Được triển khai thông qua annotation **`@Version`**:

```java
@Entity
public class Order {
    @Id
    private Long id;

    @Version
    private Integer version;  // Hibernate tự động tăng

    private String status;
}
```

### Cách Hoạt Động

```java
// Transaction 1
Order order1 = em.find(Order.class, 1L);  // version = 1

// Transaction 2
Order order2 = em.find(Order.class, 1L);  // version = 1
order2.setStatus("shipped");
em.flush();  // version = 2, UPDATE WHERE version = 1

// Transaction 1
order1.setStatus("cancelled");
em.flush();  // OptimisticLockException!
// UPDATE WHERE version = 1 -> 0 dòng được cập nhật -> exception
```

### Tại Sao "Lạc Quan"

Vì chúng ta **lạc quan** giả định rằng xung đột sẽ không xảy ra, và không khóa dữ liệu khi đọc. Xung đột chỉ được phát hiện tại thời điểm ghi.

## Middle Level

### LockModeType Cho Optimistic Locking

```java
// OPTIMISTIC - kiểm tra version khi commit/flush
em.lock(order, LockModeType.OPTIMISTIC);

// OPTIMISTIC_FORCE_INCREMENT - luôn tăng version
em.lock(order, LockModeType.OPTIMISTIC_FORCE_INCREMENT);
// Ngay cả khi order không thay đổi, version vẫn sẽ tăng
```

### Xử Lý OptimisticLockException

OptimisticLockException chứa thông tin về entity và version mong đợi/thực tế.
Trong log: "Row was updated or deleted by another transaction".

```java
try {
    order.setStatus("cancelled");
    entityManager.flush();
} catch (OptimisticLockException e) {
    // Refresh dữ liệu từ DB và thử lại
    entityManager.refresh(order);
    // logic retry
    order.setStatus("cancelled");
    entityManager.flush();
}
```

### Retry Với Spring

```java
@Retryable(value = OptimisticLockException.class, maxAttempts = 3)
@Transactional
public Order updateOrder(OrderDto dto) {
    Order order = entityManager.find(Order.class, dto.id());
    order.setStatus(dto.status());
    return order;
}
```

### Các Lỗi Thường Gặp

```java
// Không có @Version - không có optimistic locking
@Entity
public class Order {
    // không có @Version -> xung đột không được phát hiện
}

// Thay đổi version thủ công
order.setVersion(0);  // phá vỡ cơ chế

// Bỏ qua OptimisticLockException
try {
    em.flush();
} catch (OptimisticLockException e) {
    // âm thầm bỏ qua -> mất dữ liệu
}
```

## Senior Level

### Triển Khai Nội Bộ

```
@Version -> cột version trong DB

Khi UPDATE:
UPDATE orders SET status = ?, version = version + 1
WHERE id = ? AND version = ?

Nếu 0 dòng được cập nhật -> OptimisticLockException

Quy trình:
1. Khi INSERT: version = 0 (cho Integer/Long). Khi UPDATE lần đầu: version = 1.
2. Khi UPDATE: version = version + 1
3. Mệnh đề WHERE bao gồm kiểm tra version
4. Nếu version không khớp -> 0 dòng -> exception
```

### Các Kiểu Trường Version

```java
@Version
private Integer version;  // int - tự động tăng

@Version
private Long version;     // long - tự động tăng

@Version
private Timestamp version;  // timestamp - tự động cập nhật
```

### Khi Nào Dùng OPTIMISTIC_FORCE_INCREMENT

```java
// Khi cần tăng version mà không thay đổi entity
// Ví dụ, khi collection con thay đổi

@Entity
public class Order {
    @Version
    private Integer version;

    @OneToMany(mappedBy = "order")
    private List<OrderItem> items;
}

// Khi items thay đổi - cần tăng version của Order
em.lock(order, LockModeType.OPTIMISTIC_FORCE_INCREMENT);
// version của Order tăng, mặc dù bản thân Order không thay đổi
```

### Các Pattern Production

```java
// Pattern 1: Retry với exponential backoff
@Retryable(
    value = OptimisticLockException.class,
    maxAttempts = 3,
    backoff = @Backoff(delay = 100, multiplier = 2)
)
@Transactional
public Order updateWithRetry(OrderDto dto) {
    Order order = entityManager.find(Order.class, dto.id());
    order.setStatus(dto.status());
    return order;
}

// Pattern 2: Refresh và retry thủ công
@Transactional
public Order updateWithManualRetry(OrderDto dto) {
    int maxRetries = 3;
    for (int i = 0; i < maxRetries; i++) {
        try {
            Order order = entityManager.find(Order.class, dto.id());
            order.setStatus(dto.status());
            entityManager.flush();
            return order;
        } catch (OptimisticLockException e) {
            if (i == maxRetries - 1) throw e;
            entityManager.clear();  // clear và thử lại
        }
    }
    throw new IllegalStateException("Unreachable");
}
```

### Optimistic vs Pessimistic

|                        | Optimistic                | Pessimistic                |
| ---------------------- | ------------------------- | -------------------------- |
| **Khóa**               | Không (chỉ khi ghi)       | Có (khi đọc)                |
| **Xung đột**           | Phát hiện khi ghi          | Ngăn ngừa khi đọc            |
| **Hiệu năng**          | Cao (không có khóa)       | Thấp hơn (có khóa)           |
| **Deadlock**           | Không thể xảy ra           | Có thể xảy ra                |
| **Khi nào**            | Xung đột hiếm               | Xung đột thường xuyên         |

### Best Practices

```
@Version trên tất cả các entity có thể thay đổi
Retry khi OptimisticLockException
OPTIMISTIC_FORCE_INCREMENT khi cần
@Retryable để retry tự động
Giám sát tần suất xung đột

Không có @Version cho dữ liệu quan trọng
Không có logic retry
Thay đổi version thủ công
Pessimistic locking mà không có lý do
Bỏ qua OptimisticLockException
```

## Interview Cheat Sheet

**Cần phải biết:**
- Optimistic locking thông qua @Version - tự động tăng version ở mỗi UPDATE
- Mệnh đề WHERE bao gồm kiểm tra version: WHERE id = ? AND version = ?
- Khi xung đột (0 dòng được cập nhật) -> OptimisticLockException
- LockModeType: OPTIMISTIC (kiểm tra version), OPTIMISTIC_FORCE_INCREMENT (luôn tăng)
- Pattern retry: @Retryable(value = OptimisticLockException.class, maxAttempts = 3)
- Các kiểu version: Integer, Long (tự động tăng), Timestamp (rủi ro - bỏ lỡ xung đột nếu cập nhật xảy ra trong cùng mili giây)

**Các câu hỏi phụ thường gặp:**
- **Tại sao "lạc quan"?** Giả định không có xung đột, chỉ khóa khi ghi
- **Khi nào dùng OPTIMISTIC_FORCE_INCREMENT?** Khi collection con thay đổi, cho việc invalidate cache
- **Cái nào tốt hơn - optimistic vs pessimistic?** Optimistic - hiệu năng cao, xung đột hiếm; Pessimistic - xung đột thường xuyên, dữ liệu quan trọng
- **Timestamp vs Integer cho @Version?** Integer đáng tin cậy hơn - Timestamp có thể bỏ lỡ xung đột nếu cập nhật xảy ra trong cùng mili giây

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Không có @Version cho dữ liệu tài chính" - có thể xảy ra mất cập nhật
- "Thay đổi version thủ công" - phá vỡ cơ chế khóa
- "Tôi bỏ qua OptimisticLockException" - dữ liệu bị mất âm thầm
- "Pessimistic locking theo mặc định" - khóa không cần thiết, có thể xảy ra deadlock
