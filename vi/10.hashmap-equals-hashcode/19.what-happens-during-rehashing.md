# What Happens During Rehashing (Resize)? (Điều gì xảy ra trong lúc Rehashing (Resize)?)

## 🟢 Junior Level

Trong lúc rehashing, HashMap tạo một mảng mới **lớn gấp 2x** và chuyển mọi phần tử sang đó.

**Ví dụ đơn giản:**
```java
HashMap<String, Integer> map = new HashMap<>(); // 16 bucket
// Thêm 13 phần tử...
// Resize kích hoạt:
// 1. Mảng mới 32 bucket được tạo
// 2. Cả 13 phần tử được chuyển sang các bucket mới
// 3. Mảng cũ bị bỏ đi
```

**Ví dụ minh họa:** Bạn có một cái tủ với 16 kệ, và nó đầy. Bạn mua một cái tủ 32 kệ và chuyển mọi thứ. Một số thứ ở lại cùng số kệ, số khác chuyển tới các kệ mới.

**Điểm chính:** Resize là một thao tác O(n) chậm. Tốt hơn là tránh nó bằng cách đặt kích thước đúng ngay từ đầu.

## 🟡 Middle Level

### Thủ thuật bit: (hash & oldCap)

Vì capacity luôn là lũy thừa của hai, khi tăng đôi một bit được thêm vào mask:

```
Mask cũ (15): 0000 1111
Mask mới (31):  0001 1111
                   ^
                   Bit mới = oldCap
```

Kiểm tra một bit xác định số phận của phần tử:
```java
if ((e.hash & oldCap) == 0) {
    // Ở lại chỉ số cũ
} else {
    // Chuyển tới oldIndex + oldCapacity
}
```

### Hình thành các list Lo và Hi

Khi duyệt một bucket, HashMap tạo hai list tạm:
- **Lo List**: các phần tử ở lại vị trí
- **Hi List**: các phần tử chuyển tới `index + oldCap`

### Giữ nguyên thứ tự (Java 8+)

Java 8 dùng Tail Insertion — thứ tự phần tử được giữ nguyên. Điều này ngăn cycling linked list (vấn đề của Java 7). Tuy nhiên, HashMap vẫn **KHÔNG thread-safe** — khi resize đồng thời, mất phần tử là có thể. Cho truy cập đa luồng, dùng ConcurrentHashMap.

### Chuyển Tree

Nếu bucket là một tree:
1. Tree được chia thành các phần Lo và Hi
2. Nếu một phần có <= 6 phần tử → untreeify (về lại list)
3. Nếu > 6 → tree mới trong bucket mới

### Overhead

| Resource | Chi phí                                              |
| -------- | ---------------------------------------------------- |
| Bộ nhớ   | Hai mảng đồng thời (cũ + mới)                        |
| CPU      | O(n) — duyệt qua mọi phần tử                         |
| GC       | Áp lực từ các object tạm và mảng cũ                  |

## 🔴 Senior Level

### Thuật toán Resize trong Java 8+:

1. Tạo một mảng mới gấp 2x kích thước cũ
2. Với mỗi bucket, chia các phần tử thành hai nhóm theo một bit của hash:
   - **Lo** (bit = 0): ở lại cùng chỉ số
   - **Hi** (bit = 1): chuyển tới `index + oldCap`
3. Mảng cũ = null cho GC

**Tại sao cái này hiệu quả:** không cần tính lại hashCode — chỉ kiểm tra MỘT bit (`hash & oldCap`). Các phần tử hoặc ở nguyên vị trí hoặc dịch chuyển một offset cố định.

### TreeNode.split()

Khi chia tree:
```java
// Nếu một phần có <= UNTREEIFY_THRESHOLD (6) — untreeify
if (lc <= UNTREEIFY_THRESHOLD)
    tab[index] = loHead.untreeify(map);
else {
    tab[index] = loHead;
    if (hiHead != null) loHead.treeify(tab); // Tái cân bằng
}
```

### Memory Pressure

Khi resize capacity=1M → capacity=2M:
- Mảng mới: ~16MB (1M tham chiếu × 8 byte × 2 do UseCompressedOops)
- Mảng cũ: thêm ~16MB cho tới khi GC
- Ở đỉnh: +32MB trong Heap

### Ảnh hưởng tới GC

- Mảng cũ → rác ngay lập tức (Young/Middle Gen)
- Tái phân bố tham chiếu → write barrier cho GC
- Trong G1: có thể trigger mixed GC nếu mảng cũ ở Old Gen

### ConcurrentHashMap: Parallel Resize

Trong ConcurrentHashMap, resize được thực hiện song song:
- Nhiều thread có thể giúp chuyển các phần tử
- `transferIndex` được dùng để phối hợp
- ForwardingNode chỉ báo tiến độ

### Kinh nghiệm Production

Trong các hệ thống nhạy về latency:
- Resize gây tăng vọt từ 10ms tới 100+ms
- Giải pháp: tính trước capacity
- Giám sát: event JFR `jdk.HashMapResize` (Java 17+)

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Mảng mới = 2x cái cũ, các phần tử được phân bố qua thủ thuật bit (hash & oldCap)
- Lo List: ở lại vị trí, Hi List: chuyển tới index + oldCap
- hashCode KHÔNG được tính lại — MỘT bit được kiểm tra
- Java 8+: Tail Insertion giữ nguyên thứ tự, ngăn cycling (vấn đề của Java 7)
- TreeNode.split(): ở <= 6 phần tử → untreeify (về lại list)
- GC pressure: mảng cũ + mới = đỉnh tăng đôi bộ nhớ mảng

**Các câu hỏi phụ thường gặp:**
- **Tại sao không tính lại hash?** — khi tăng đôi một lũy thừa của hai, một bit được thêm vào mask
- **Điều gì xảy ra khi resize đồng thời?** — mất phần tử, hành vi không xác định
- **ConcurrentHashMap resize như thế nào?** — song song, qua transferIndex và ForwardingNode
- **Bao nhiêu bộ nhớ khi resize 1M → 2M?** — ~32MB đỉnh (hai mảng ~16MB mỗi cái)

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Khi resize, mọi hashCode được tính lại" — không, một bit được kiểm tra
- "HashMap là thread-safe khi resize" — không, ngay cả trong Java 8+
- "Các phần tử được phân bố ngẫu nhiên" — không, một cách tất định theo một bit
