# When should you create an index? (Khi nào nên tạo index?)

## 🟢 Junior Level

Hãy tạo index khi **việc tìm kiếm trên bảng trở nên chậm** và bạn hiểu rõ trường nào đang được sử dụng để tìm kiếm.

**Ví dụ minh họa đơn giản:** Nếu bạn thường xuyên tra cứu một liên hệ trong danh bạ điện thoại theo số điện thoại, việc tạo một mục lục riêng "theo số" là hợp lý.

**Ý tưởng chính:**
- Index cần thiết để tăng tốc tìm kiếm
- Tạo index cho các trường trong WHERE, JOIN, ORDER BY
- Không tạo index "để phòng khi cần"

**Ví dụ:**
```sql
-- Truy vấn chậm khi không có index
SELECT * FROM users WHERE email = 'test@example.com';

-- Tạo một index
CREATE INDEX idx_users_email ON users(email);

-- Bây giờ truy vấn nhanh hơn
SELECT * FROM users WHERE email = 'test@example.com';
```

**Khi nào nên tạo:**
- Trường được sử dụng thường xuyên trong WHERE
- Trường được sử dụng trong JOIN để liên kết bảng
- Trường được sử dụng trong ORDER BY để sắp xếp
- Bảng có kích thước lớn (hơn 10,000 dòng)

## 🟡 Middle Level

### Cách xác định nhu cầu tạo index

**1. Phân tích truy vấn chậm**
```sql
-- Bật ghi log truy vấn chậm
-- postgresql.conf:
-- log_min_duration_statement = 1000  -- ghi log các truy vấn > 1 giây
```

**2. Extension pg_stat_statements**
```sql
-- Bật extension
CREATE EXTENSION pg_stat_statements;

-- Tìm các truy vấn chậm nhất
SELECT query,
       calls,
       mean_exec_time as avg_time_ms,
       total_exec_time as total_time_ms
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

### Các tiêu chí chính để tạo index

**1. Các trường trong WHERE có độ chọn lọc (selectivity) cao**
```sql
-- ✅ Độ chọn lọc cao (nhiều giá trị duy nhất)
CREATE INDEX idx_users_email ON users(email);

-- ❌ Độ chọn lọc thấp (ít giá trị duy nhất)
CREATE INDEX idx_users_gender ON users(gender); -- Nam/Nữ
```

**2. Foreign Key (Khóa ngoại)**
```sql
-- Nên tạo index cho FK!
CREATE TABLE orders (
    id SERIAL PRIMARY KEY,
    user_id INTEGER REFERENCES users(id)  -- ← tạo index cho cột này!
);

-- Tạo index trên FK
CREATE INDEX idx_orders_user_id ON orders(user_id);

-- Tại sao? Khi xóa một user, PG sẽ kiểm tra xem có tồn tại đơn hàng nào không
-- Không có index → Seq Scan trên orders (rất chậm với bảng lớn)
```

**Trường hợp ngoại lệ:** Bảng chứa FK có < 1000 dòng (Seq Scan vẫn nhanh), hoặc bạn không bao giờ xóa/cập nhật các bản ghi cha (parent records).

**3. Các trường dùng cho JOIN**
```sql
-- Đối với Nested Loop Join, các index trên trường join là rất quan trọng
SELECT * FROM orders o
JOIN users u ON o.user_id = u.id;

-- Các index:
-- orders(user_id) ← để tìm đơn hàng của người dùng
-- users(id) ← đã có sẵn (PRIMARY KEY)
```

**4. Các trường dùng cho ORDER BY / GROUP BY**
```sql
-- Một index cho phép bạn tránh phải sắp xếp (sorting)
CREATE INDEX idx_orders_created ON orders(created_at DESC);

-- Truy vấn không cần Sort (dữ liệu đã được sắp xếp sẵn)
SELECT * FROM orders ORDER BY created_at DESC LIMIT 10;
```

### Các lỗi thường gặp

1. **Tạo index mà không phân tích khối lượng công việc (workload)**
   - ❌ Tạo index "để phòng khi cần"
   - ✅ Hãy phân tích truy vấn thông qua `EXPLAIN` trước

2. **Index trùng lặp**
   ```sql
   -- ❌ Hai index giống hệt nhau
   CREATE INDEX idx1 ON users(email);
   CREATE INDEX idx2 ON users(email);
   ```

3. **Index trên các bảng nhỏ**
   - Bảng < 1000 dòng → Seq Scan nhanh hơn
   - Index chỉ chiếm thêm dung lượng

### Chi phí của index

**Mỗi index đồng nghĩa với:**
1. INSERT/UPDATE/DELETE chậm hơn (cây cần được cập nhật)
2. Chiếm dung lượng đĩa (từ 10% đến hơn 100% kích thước bảng)
3. Tải RAM (index cần nằm trong bộ nhớ để hoạt động hiệu quả)

### Quy tắc thực tiễn

```sql
-- Trước khi tạo index, hãy kiểm tra:
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM users WHERE email = 'test@example.com';

-- Nếu bạn thấy Seq Scan và tỷ lệ buffer hits thấp → index sẽ giúp ích
-- Nếu đã là Index Scan → có thể index đã tồn tại rồi
```

## 🔴 Senior Level

### Cách xác định nhu cầu: Phân tích khối lượng công việc (Workload Analysis)

**pg_stat_statements — công cụ chính:**
```sql
-- Tìm các truy vấn có total_exec_time cao nhất
SELECT
    query,
    calls,
    mean_exec_time,
    total_exec_time,
    rows,
    shared_blks_read,    -- Đọc từ đĩa (không tốt)
    shared_blks_hit      -- Đọc từ cache (tốt)
FROM pg_stat_statements
WHERE dbid = (SELECT oid FROM pg_database WHERE datname = current_database())
ORDER BY total_exec_time DESC
LIMIT 20;

-- Chỉ số quan trọng: shared_blks_read / calls > 100
-- → Truy vấn đọc nhiều page từ đĩa → cần một index
```

**HypoPG — index giả định (hypothetical indexes):**
```sql
-- Extension để kiểm thử các kịch bản "nếu như"
CREATE EXTENSION hypopg;

-- Tạo một index ảo (KHÔNG chiếm dung lượng thực!)
SELECT * FROM hypopg_create_index(
    'CREATE INDEX idx_orders_user_date ON orders(user_id, created_at DESC)'
);

-- Kiểm tra xem planner có chọn index đó hay không
EXPLAIN SELECT * FROM orders WHERE user_id = 123 ORDER BY created_at DESC LIMIT 10;
-- Trong plan bạn sẽ thấy: Index Scan using <hypothetical>...

-- Xóa index giả định
SELECT * FROM hypopg_drop_index(indexrelid);
```

### Đánh đổi trong kiến trúc (Architectural Trade-offs)

**1. Write Amplification (Khuếch đại ghi)**
```
Mỗi index mới =
  + INSERT/UPDATE/DELETE chậm hơn (cây cần được cập nhật)
  + Tải WAL (Write Ahead Log: PostgreSQL trước tiên ghi tất cả các thay đổi vào các file WAL, sau đó mới áp dụng vào dữ liệu chính. Mỗi index làm tăng khối lượng WAL vì các thay đổi trong index cũng cần được ghi log)
  + Tăng Replica Lag (bản sao replica không theo kịp)
  + Bloat (index phình to theo thời gian)
```

**2. Hợp nhất index**
```sql
-- ❌ Trước: 3 index riêng lẻ
CREATE INDEX idx_a ON t(a);              -- 2 GB
CREATE INDEX idx_a_b ON t(a, b);         -- 5 GB
CREATE INDEX idx_a_b_c ON t(a, b, c);    -- 8 GB
-- Tổng: 15 GB, việc ghi chậm đi x3

-- ✅ Sau: 1 index bao phủ tất cả các tiền tố
CREATE INDEX idx_a_b_c ON t(a, b, c);    -- 8 GB
-- Bao phủ: WHERE a, WHERE a,b, WHERE a,b,c
-- Tiết kiệm: 7 GB, việc ghi nhanh hơn 3 lần
```

**3. Partial Index (Index bán phần) cho các giá trị hiếm**
```sql
-- Chỉ index các lỗi (5% tổng số bản ghi)
CREATE INDEX idx_orders_errors ON orders(id, error_message)
WHERE status = 'ERROR';

-- Tiết kiệm dung lượng: nhỏ hơn 95% so với một index đầy đủ
-- Tăng tốc: chỉ cho các truy vấn quan trọng
```

### Các trường hợp đặc biệt (Edge Cases)

1. **Tạo index trong Production**
   ```sql
   -- ❌ Chặn ghi (ShareLock)
   CREATE INDEX idx ON orders(user_id);

   -- ✅ Không chặn, nhưng mất nhiều thời gian hơn
   CREATE INDEX CONCURRENTLY idx ON orders(user_id);

   -- ⚠️ Nếu bị gián đoạn, sẽ ở trạng thái INVALID
   SELECT indexrelid::regclass, indisvalid
   FROM pg_index
   WHERE NOT indisvalid;
   ```

2. **Tối ưu hóa Bulk Load (nạp dữ liệu hàng loạt)**
   ```sql
   -- Khi chèn hàng triệu dòng:
   -- 1. Xóa các index
   DROP INDEX idx_orders_user_id;

   -- 2. Chèn dữ liệu
   COPY orders FROM '/data/orders.csv';

   -- 3. Tạo lại các index (nhanh hơn là cập nhật trên mỗi lần insert)
   CREATE INDEX idx_orders_user_id ON orders(user_id);
   ```

3. **Ngăn ngừa index bloat (phình index)**
   ```sql
   -- Đối với các index được cập nhật thường xuyên
   CREATE INDEX idx_orders_status ON orders(status)
   WITH (fillfactor = 70);

   -- 30% của page được để trống → ít split hơn
   ```

### Hiệu năng

**Ảnh hưởng đến việc ghi (các con số ước tính):**

| Số lượng index     | Độ trễ INSERT   | Khối lượng WAL   |
| --------------------- | ---------------- | ------------ |
| 1-2                   | +5-10%           | Cơ bản         |
| 5-7                   | +50-100%         | x2-x3        |
| 10-15                 | +200-500%        | x5-x10       |

**Quy tắc 10-15%:**
- Nếu một index được sử dụng trong < 10-15% tổng số truy vấn → có khả năng là không cần thiết
- Seq Scan trên một bảng nằm vừa hoàn toàn trong cache có thể nhanh hơn Index Scan

### Kinh nghiệm Production

**Tình huống thực tế #1:**
- Startup fintech: 50 triệu giao dịch
- Vấn đề: Truy vấn báo cáo > 30 giây
- Phân tích thông qua `pg_stat_statements`:
  - Top 3 truy vấn chiếm 80% thời gian
  - Cả 3 đều dùng `WHERE user_id = ? AND created_at > ?`
- Giải pháp:
  - `CREATE INDEX CONCURRENTLY idx_transactions_user_date ON transactions(user_id, created_at DESC)`
  - Thêm `INCLUDE (amount, type)` để có Index-Only Scan
- Kết quả: Truy vấn chỉ còn < 100ms (nhanh hơn 300 lần)

**Tình huống thực tế #2:**
- E-commerce: 200 triệu đơn hàng
- Vấn đề: INSERT chậm xuống còn 2 giây, Replica Lag > 60 giây
- Phân tích:
  - 18 index trên bảng orders
  - 12 trong số đó chỉ được sử dụng < 5 lần mỗi tháng
  - Khối lượng WAL: 500 MB/phút
- Giải pháp:
  - Xóa 12 index không sử dụng
  - Hợp nhất phần còn lại thành 6 index
  - Kết quả: INSERT < 100ms, Replica Lag < 5 giây

### Giám sát (Monitoring)

```sql
-- 1. Kiểm tra việc sử dụng index
SELECT
    schemaname,
    relname as table_name,
    indexrelname as index_name,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch,
    pg_size_pretty(pg_relation_size(indexrelid)) as size
FROM pg_stat_user_indexes
WHERE schemaname = 'public'
ORDER BY idx_scan ASC  -- Không sử dụng nằm ở cuối
LIMIT 20;

-- 2. Kiểm tra Foreign Key không có index
SELECT
    conrelid::regclass AS table_with_fk,
    conname AS fk_constraint,
    confrelid::regclass AS referenced_table
FROM pg_constraint
WHERE contype = 'f'
  AND NOT EXISTS (
    SELECT 1 FROM pg_index
    WHERE indrelid = conrelid
      AND indkey[0] = ANY(conkey)
  );

-- 3. Kiểm tra các index trùng lặp
-- (các index có cùng tập hợp cột)
SELECT
    a.indexrelid::regclass as index1,
    b.indexrelid::regclass as index2,
    pg_get_indexdef(a.indexrelid) as definition
FROM pg_index a
JOIN pg_index b ON a.indrelid = b.indrelid
  AND a.indexrelid < b.indexrelid
  AND a.indkey::text = b.indkey::text;

-- 4. HypoPG để kiểm thử
SELECT * FROM hypopg_list_indexes();
```

### Best Practices (Thực hành tốt nhất)

1. **Phân tích khối lượng công việc (workload)** thông qua `pg_stat_statements` trước khi tạo
2. **Kiểm thử giả thuyết** thông qua `HypoPG`
3. **Nên tạo index cho Foreign Key**
4. **Sử dụng CONCURRENTLY** trong production
5. **Hợp nhất** các index theo tiền tố
6. **Loại bỏ các index không sử dụng** thường xuyên
7. **Giám sát Replica Lag** khi thêm index mới
8. **Đối với Bulk Load** — xóa và tạo lại index

### Tóm tắt cho Senior

- Sử dụng **pg_stat_statements** để tìm các truy vấn gây nghẽn cổ chai (bottleneck)
- Kiểm tra giả thuyết thông qua **HypoPG** trước khi tạo index thực tế
- **Nên tạo index cho Foreign Key** — nguyên nhân phổ biến gây ra Seq Scan
- Trong production — chỉ dùng **CONCURRENTLY**
- **Hợp nhất** các index: `(a)`, `(a,b)`, `(a,b,c)` → thành một `(a,b,c)`
- Giám sát **Replica Lag** và **khối lượng WAL** sau khi thêm index
- Loại bỏ các index không sử dụng — mỗi index là một **loại thuế cho việc ghi (write tax)**

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Phân tích khối lượng công việc thông qua `pg_stat_statements` trước khi tạo
- **Nên tạo index cho Foreign Key** — nguyên nhân phổ biến gây ra Seq Scan
- `CONCURRENTLY` trong production (không chặn ghi, nhưng mất nhiều thời gian hơn)
- HypoPG — kiểm thử "nếu như" mà không cần tạo index thực tế
- Write Amplification: mỗi index = +INSERT/UPDATE/DELETE + khối lượng WAL
- Bulk Load: xóa index → chèn dữ liệu → tạo lại (nhanh hơn)
- `fillfactor = 70-80` cho các index được cập nhật thường xuyên

**Các câu hỏi phụ thường gặp:**
- "Làm sao để biết một index có cần thiết không?" → `shared_blks_read / calls > 100` trong pg_stat_statements
- "Cần làm gì trước khi bulk insert?" → Xóa index → COPY → tạo lại
- "Làm sao để kiểm tra một index có giúp ích không?" → HypoPG + EXPLAIN
- "Replica Lag là gì và index ảnh hưởng đến nó như thế nào?" → Nhiều index hơn → nhiều WAL hơn → replica bị tụt lại phía sau

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "Tôi sẽ tạo một index rồi xem sao" (hãy phân tích workload trước!)
- ❌ "Index để phòng khi cần cũng không gây hại gì" (Write Amplification!)
- ❌ "Tôi sẽ tạo index trong production mà không dùng CONCURRENTLY" (khóa ghi!)
