# How to get a heap dump? (Cách lấy được một heap dump?)

## Junior Level

**Các cách để lấy một Heap Dump:**

```bash
# 1. Tự động khi OOME (bắt buộc!)
java -XX:+HeapDumpOnOutOfMemoryError -jar app.jar

# 2. Thủ công qua jcmd
jcmd <PID> GC.heap_dump dump.hprof

# 3. Qua VisualVM (GUI)
# → Click chuột phải vào tiến trình → Heap Dump
```

**Tìm PID ở đâu:**
```bash
jps  # Danh sách các tiến trình Java
# hoặc
ps aux | grep java
```

## Middle Level

### jcmd (phương pháp được khuyến nghị)

```bash
# Chuẩn hiện đại
jcmd <PID> GC.heap_dump /tmp/dump.hprof

# Có nén (Java 11+)
jcmd <PID> GC.heap_dump -gz=1 /tmp/dump.hprof.gz
# → 32 GB → 6-10 GB

# Chỉ các đối tượng còn sống (Full GC!)
jcmd <PID> GC.heap_dump -all=false /tmp/live.hprof
```

### Kubernetes

```bash
# 1. Vào trong pod
kubectl exec -it <pod> -- bash

# 2. Chụp dump
# Trong các container, Java có thể là PID 1 (không có init process) hoặc có
# PID riêng (với tini/dumb-init hoặc container awareness của Java 11+).
# Kiểm tra qua `jps`.
jcmd 1 GC.heap_dump -gz=1 /tmp/dump.hprof.gz

# 3. Tải về
kubectl cp <pod>:/tmp/dump.hprof.gz ./dump.hprof.gz

# 4. Dọn dẹp
rm /tmp/dump.hprof.gz
```

### Phương pháp lập trình (Programmatic)

```java
// ⚠️ com.sun.management.* — API nội bộ của JDK (đặc thù HotSpot).
// Không được đảm bảo trên các JVM không phải HotSpot (OpenJ9, GraalVM Native Image).
import com.sun.management.HotSpotDiagnosticMXBean;

public void dumpHeap(String path, boolean live) {
    HotSpotDiagnosticMXBean bean = ManagementFactory
        .newPlatformMXBeanProxy(
            ManagementFactory.getPlatformMBeanServer(),
            "com.sun.management:type=HotSpotDiagnostic",
            HotSpotDiagnosticMXBean.class);
    bean.dumpHeap(path, live);
}
```

## Senior Level

### Các nguy hiểm của Dump trong Production

```
Khoảng dừng STW → Liveness Probe fail → pod bị giết!

Giải pháp:
  1. Tăng các timeout của probe
  2. Dùng JFR thay vì dump
  3. Chụp dump trên một replica
```

### PII và Bảo mật

```
Dump chứa:
  → Mật khẩu, token, các session
  → Dữ liệu cá nhân

→ Chỉ truyền qua các kênh an toàn
→ RedactHprof để che (mask) các chuỗi
→ Hạn chế quyền truy cập file
```

### Arthas

```bash
# Giải pháp thay thế cho jcmd
curl -L https://arthas.aliyun.com/arthas-boot.jar -o arthas-boot.jar
java -jar arthas-boot.jar

[arthas]$ heapdump /tmp/dump.hprof
→ Tự động tìm PID
→ CLI tiện lợi
```

### Best Practices

1. **jcmd** — phương pháp chính thức
2. **-gz=1 (Java 11+)** — nén
3. **Kubernetes** → một volume bên ngoài
4. **JFR** cho các Heap lớn
5. **Bảo mật** — che (mask) PII
6. **Cẩn thận** với -all=false (Full GC!)

### Tóm tắt cho Senior

- **jcmd** > jmap (chuẩn hiện đại)
- **Gzip (Java 11+)** = tiết kiệm
- **Kubernetes** → một volume bên ngoài
- **JFR** > Dump cho > 64 GB
- **PII** = dump chứa các bí mật
- **Arthas** = giải pháp thay thế tiện lợi

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- jcmd — phương pháp chính thức: `jcmd <PID> GC.heap_dump /tmp/dump.hprof`; nén: `-gz=1` (Java 11+)
- Tự động: `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/var/log/dumps/` — bắt buộc trong production
- Kubernetes: vào trong pod → `jcmd 1 GC.heap_dump -gz=1 /tmp/dump.hprof.gz` → `kubectl cp` → dọn dẹp
- `-all=false` (live): chỉ các đối tượng còn sống; yêu cầu Full GC trước dump → khoảng dừng STW bổ sung
- PII và Bảo mật: dump chứa mật khẩu, token, các session; truyền qua các kênh an toàn; RedactHprof để che
- Các nguy hiểm trong production: STW → Liveness Probe fail → pod bị giết; giải pháp: tăng timeout, dùng JFR, chụp trên replica
- Phương pháp lập trình: `HotSpotDiagnosticMXBean.dumpHeap()` — đặc thù HotSpot, không hoạt động trên OpenJ9/GraalVM Native Image

**Các câu hỏi phụ thường gặp:**
- **Tại sao `-gz=1` quan trọng?** — Nén khi đang chạy: 32 GB → 6-10 GB; tiết kiệm không gian đĩa và thời gian truyền tải
- **Nếu Java là PID 1 trong container thì sao?** — Trong các container, Java có thể là PID 1 (không có init process); `jcmd 1` hoạt động; kiểm tra qua `jps`
- **Tại sao phương pháp lập trình không đa nền tảng?** — `com.sun.management.HotSpotDiagnosticMXBean` — API nội bộ của JDK; chỉ HotSpot
- **Khi nào Arthas tốt hơn jcmd?** — Arthas tự động tìm PID, CLI tương tác tiện lợi; tốt khi `jcmd` không có sẵn

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "jmap là phương pháp tốt nhất" — jmap đã bị deprecated; hãy dùng jcmd
- "Live dump nhanh hơn và an toàn hơn" — Live dump yêu cầu Full GC → khoảng dừng STW bổ sung
- "Có thể lưu dump an toàn trong ephemeral storage của Kubernetes" — ephemeral storage bị lấp đầy bởi dump → pod sẽ không restart
