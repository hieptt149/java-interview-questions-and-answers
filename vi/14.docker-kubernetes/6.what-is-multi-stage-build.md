# What is multi-stage build? (Multi-stage build là gì?)

## Junior Level

### Giải Thích Đơn Giản

**Multi-stage build** là một cách để tạo một Docker image nhỏ bằng cách dùng nhiều stage trong một Dockerfile duy nhất.

Một Dockerfile có thể có nhiều instruction FROM — mỗi cái bắt đầu một stage mới. Chỉ các file từ stage cuối cùng nằm trong image. Trong stage đầu tiên bạn build ứng dụng, trong stage thứ hai — bạn chạy nó. Chỉ file sẵn sàng nằm trong image cuối cùng, và tất cả các công cụ build bị bỏ lại "ngoài mạn tàu."

### Phép So Sánh

Hãy tưởng tượng bạn đang nướng một cái bánh. Bạn cần: máy trộn, khuôn, lò nướng, nguyên liệu. Nhưng khi bạn đưa bánh cho khách hàng — bạn không đưa họ máy trộn và khuôn. Khách hàng chỉ nhận được cái bánh hoàn thành. Multi-stage build cũng giống vậy: bạn cần Maven và JDK để build, nhưng chỉ cần JRE và file jar để chạy.

### Vấn Đề Không Có Multi-stage

```dockerfile
FROM maven:3.8-openjdk-17
COPY src ./src
COPY pom.xml .
RUN mvn package -DskipTests
# Image nặng ~800 MB (Maven + JDK + source code + dependency)
CMD ["java", "-jar", "target/app.jar"]
```

### Multi-stage Hoạt Động Như Thế Nào

```dockerfile
# Stage 1: Build
FROM maven:3.8-openjdk-17-slim AS builder
WORKDIR /build
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn package -DskipTests

# Stage 2: Runtime
FROM openjdk:17-jdk-slim
WORKDIR /app
COPY --from=builder /build/target/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

**Kết quả:** image nặng ~300 MB thay vì ~800 MB!

### Giải Thích Từng Bước

1. `FROM ... AS builder` — stage đầu tiên được đặt tên "builder"
2. `COPY --from=builder` — sao chép một file từ stage đầu tiên sang stage thứ hai
3. Stage thứ hai là image cuối cùng đi đến production

### Cần Nhớ

- Multi-stage build = nhiều `FROM` trong một Dockerfile
- Mỗi `FROM` là một stage riêng biệt
- `COPY --from=name` sao chép các file từ một stage khác
- Image cuối cùng chỉ chứa stage cuối cùng
- Vì chỉ FROM cuối cùng nằm trong image cuối cùng. Tất cả các stage trước đó
(trình biên dịch, dependency, source code) bị bỏ lại "ngoài mạn tàu."
- Điều này giảm kích thước và tăng bảo mật

## Middle Level

### Tại Sao Multi-stage Build Xuất Hiện?

Trước công nghệ này có hai hướng đi:
1. **Mọi thứ trong một image** — image cuối cùng chứa Maven, JDK, source code. Kích thước phình to, bề mặt tấn công lớn.
2. **Builder Pattern** — các script phức tạp để chuyển artifact giữa các image. Bất tiện, cần các script bên ngoài.

Multi-stage build giải quyết cả hai vấn đề, cho phép mô tả mọi thứ trong một Dockerfile.

### Phân Tích Chi Tiết

```dockerfile
# STAGE 1: Build (đặt tên 'builder')
FROM maven:3.8-openjdk-17-slim AS builder
WORKDIR /build
COPY pom.xml .
RUN mvn dependency:go-offline     # Cache dependency
COPY src ./src
RUN mvn package -DskipTests

# STAGE 2: Image cuối cùng (Runtime)
FROM openjdk:17-jdk-slim
WORKDIR /app
COPY --from=builder /build/target/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "app.jar"]
```

### Các Lỗi Thường Gặp

| Lỗi                                | Hậu quả                        | Cách tránh                          |
| -------------------------------------- | ----------------------------------- | -------------------------------- |
| Đường dẫn sai trong `COPY --from`            | Không tìm thấy file trong quá trình build        | Dùng đường dẫn tuyệt đối                    |
| Sao chép code trước dependency       | Cache không hoạt động, build chậm     | pom.xml trước, sau đó src               |
| Quên dùng `AS` cho các stage      | Không thể tham chiếu theo tên            | Luôn đặt tên cho các stage của bạn                  |
| Dùng `latest` ở bất kỳ stage nào            | Không tất định                    | Ghim phiên bản của tất cả các image nền       |
| Sao chép toàn bộ `/build`                | File thừa trong image cuối cùng         | Chỉ sao chép artifact                |

### Lợi Ích

1. **Kích thước tối thiểu** — image cuối cùng chỉ chứa JRE và `.jar`.
2. **Bảo mật** — không có công cụ build, bề mặt tấn công nhỏ hơn.
3. **Tiện lợi CI/CD** — toàn bộ quá trình trong một file.
4. **Caching** — Docker cache mỗi stage độc lập.

### Các Kỹ Thuật Nâng Cao

**Dừng ở một stage cụ thể:**
```bash
docker build --target builder -t my-app-test .
```

**Dùng các image bên ngoài:**
```dockerfile
COPY --from=nginx:latest /etc/nginx/nginx.conf /my/path
```

**Nhiều stage trung gian:**
```dockerfile
FROM node:18 AS frontend-build
# ... build frontend

FROM maven:17 AS backend-build
# ... build backend

FROM openjdk:17-slim
COPY --from=backend-build /app.jar .
COPY --from=frontend-build /dist ./static/
```

### Tối Ưu Hóa Cache

```dockerfile
FROM maven:3.8-openjdk-17-slim AS builder
WORKDIR /build
COPY pom.xml .
RUN mvn dependency:go-offline -B  # Cache dependency
COPY src ./src
RUN mvn package -DskipTests -B
```

Khi code thay đổi, layer dependency được lấy từ cache.

### So Sánh Các Cách Tiếp Cận

| Cách tiếp cận                 | Kích thước    | Bảo mật  | Độ phức tạp |
| ------------------------ | ------- | --------- | ---------- |
| Single-stage             | ~800 MB | Thấp       | Thấp        |
| Multi-stage (slim)       | ~300 MB | Trung bình    | Trung bình     |
| Multi-stage (alpine)     | ~120 MB | Cao       | Trung bình     |
| Multi-stage (distroless) | ~80 MB  | Rất cao | Cao       |

### Cần Nhớ

- Multi-stage build là tiêu chuẩn ngành
- Tách "công cụ build" và "môi trường runtime"
- Dùng `slim` hoặc `alpine` ở stage cuối cùng
- Bạn có thể sao chép các file từ các image bên ngoài
- `--target` cho phép build một stage cụ thể

### Khi Nào KHÔNG Nên Dùng Multi-stage Build

Với Python/Node.js không có bước biên dịch, multi-stage thường không cần thiết — chỉ cần COPY và RUN.
Multi-stage hữu ích khi có một bước build (Java, Go, C++) không cần thiết ở runtime.

## Senior Level

### Multi-stage Build Như Một Kiến Trúc Pattern

Multi-stage build triển khai **nguyên tắc đặc quyền tối thiểu (least privilege)** ở cấp độ image: image runtime chỉ chứa những gì cần thiết cho việc thực thi, không có gì thừa.

### Phân Tích Bảo Mật

**Không có multi-stage:**
```
Image: maven:3.8-openjdk-17 (~800 MB)
Chứa: Maven, trình biên dịch Java, source code, tất cả dependency
Rủi ro: kẻ tấn công có thể biên dịch lại code, dùng trình biên dịch cho các exploit
```

**Với multi-stage:**
```
Image: openjdk:17-jre-slim (~300 MB)
Chứa: JRE + file jar
Rủi ro: tối thiểu — không có công cụ để sửa đổi code
```

### Đánh Đổi (Trade-offs)

| Cách tiếp cận                 | Kích thước    | Bảo mật       | Độ phức tạp   | Debug          |
| ------------------------ | ------- | -------------- | ------------ | -------------- |
| Single-stage             | ~800 MB | Thấp            | Thấp          | Dễ           |
| Multi-stage (slim)       | ~300 MB | Trung bình         | Trung bình       | Bình thường         |
| Multi-stage (jlink)      | ~100 MB | Cao           | Cao         | Khó           |
| Multi-stage (distroless) | ~80 MB  | Rất cao      | Cao         | Rất khó      |
| Multi-stage (native)     | ~50 MB  | Tối đa        | Rất cao    | Cần debugger |

jlink — công cụ JDK để tạo một phiên bản Java tối thiểu chỉ với các module cần thiết.

### Spring Boot 3.x + jlink

```dockerfile
FROM ubuntu AS jre-build
RUN apt-get update && apt-get install -y openjdk-17-jdk-headless
RUN jlink \
    --add-modules java.base,java.sql,java.xml \
    --strip-debug \
    --no-man-pages \
    --no-header-files \
    --compress=2 \
    --output /jre

FROM eclipse-temurin:17-jdk-slim AS builder
# ... build ...

FROM debian:buster-slim
COPY --from=jre-build /jre /jre
COPY --from=builder /build/target/app.jar /app.jar
ENV JAVA_HOME=/jre
ENV PATH="$JAVA_HOME/bin:$PATH"
ENTRYPOINT ["java", "-jar", "/app.jar"]
```

JRE tùy chỉnh nặng 40-60 MB thay vì JDK đầy đủ 300+ MB.

### Các Image Distroless

```dockerfile
FROM maven:3.9-eclipse-temurin-17 AS build
# ... build ...

FROM gcr.io/distroless/java17-debian12
COPY --from=build /build/target/app.jar /app.jar
ENTRYPOINT ["java", "-jar", "/app.jar"]
```

Các image distroless chỉ chứa runtime và không có shell/package manager. Kẻ tấn công không thể chạy `sh` bên trong container.

### Edge Case

- **Không tìm thấy file ở stage thứ hai:** dùng đường dẫn tuyệt đối. `COPY --from=builder /build/target/*.jar app.jar` — nếu chỉ có một file jar, glob hoạt động. Nếu có nhiều — tất cả được sao chép vào `/app.jar` như một thư mục.
- **Cache không hoạt động:** code được sao chép trước dependency. Giải pháp: `pom.xml` trước, sau đó `RUN dependency:go-offline`, sau đó `src`.
- **File tạm khi build:** nếu `RUN` tạo các file tạm, chúng vẫn còn trong layer của stage builder. Điều này ổn — chúng sẽ không nằm trong image cuối cùng.
- **Secret ở stage build:** nếu stage build cần truy cập một Maven repo private, dùng BuildKit `--mount=type=ssh` hoặc `--mount=type=secret`. Đừng truyền token qua ARG.
- **Cross-compilation:** build image ARM trên host amd64. Dùng `docker buildx` với QEMU hoặc remote builder.

### Native Image (GraalVM) + Multi-stage

```dockerfile
FROM ghcr.io/graalvm/native-image:ol8-java17 AS builder
WORKDIR /build
COPY pom.xml .
COPY src ./src
RUN native-image -jar target/app.jar -o app

FROM debian:buster-slim
COPY --from=builder /build/app /app
ENTRYPOINT ["/app"]
```

Image cuối cùng: ~50-100 MB, khởi động tức thì (< 100ms), memory tối thiểu. Đánh đổi: thời gian build Native Image dài (vài phút), không phải tất cả các tính năng Spring đều được hỗ trợ (cần Spring Native / AOT).

// Native Image — biên dịch Java thành một binary native.
// Điểm cộng: khởi động < 100ms. Điểm trừ: build mất vài phút,
// không phải tất cả các tính năng Spring đều được hỗ trợ (reflection, proxy).

### Hiệu Năng

| Chiến lược            | Kích thước image | Thời gian khởi động | Dấu chân RAM |
| ------------------- | ---------- | ------------ | ------------- |
| JDK đầy đủ            | ~500 MB    | ~5-8s        | ~400-600 MB   |
| JRE slim            | ~300 MB    | ~5-8s        | ~300-500 MB   |
| jlink custom JRE    | ~100 MB    | ~4-6s        | ~200-400 MB   |
| Distroless          | ~80 MB     | ~4-6s        | ~200-400 MB   |
| GraalVM Native      | ~50 MB     | < 0.1s       | ~50-150 MB    |

### Xử Lý Sự Cố (Troubleshooting)

**Vấn đề:** không tìm thấy file.
```dockerfile
COPY --from=builder /build/target/app.jar app.jar
# LỖI: file not found
```
**Giải pháp:** kiểm tra đường dẫn tuyệt đối. Dùng `RUN ls -la /build/target/` ở stage builder để debug. Hoặc `docker build --target builder` để kiểm tra image trung gian.

**Vấn đề:** cache không hoạt động.
```dockerfile
# TỒI
COPY src ./src
COPY pom.xml .
RUN mvn package
```
**Giải pháp:** đổi thứ tự. `pom.xml` trước, sau đó `RUN dependency:go-offline`, sau đó `src`.

### Câu Chuyện Production

Một team microservices (40+ service) dùng các image single-stage 700-900 MB. Deploy một service mất 3-5 phút (pull image). Tổng dung lượng registry tiêu tốn 35 GB. Triển khai multi-stage với các image distroless giảm kích thước trung bình xuống 90 MB, thời gian deploy xuống 30 giây, registry xuống 4 GB. Tiết kiệm: 88% dung lượng lưu trữ, 90% thời gian deploy. Lợi ích bổ sung: các image distroless vượt qua audit bảo mật mà không có vấn đề gì — không có shell, không có package manager, bề mặt tấn công tối thiểu.

### Monitoring

- `docker images` — theo dõi kích thước image
- `dive <image>` — phân tích nội dung của mỗi layer
- Metrics kích thước registry — giám sát lưu trữ image
- Tỷ lệ cache hit của build — hiệu quả caching trong CI/CD
- Kết quả quét image (Trivy, Snyk) — số lượng lỗ hổng mỗi image

### Tóm Tắt

- Multi-stage build là tiêu chuẩn để tạo các image production.
- Cách tốt nhất để cân bằng sự tiện lợi phát triển với sự gọn nhẹ của image.
- Luôn tách "công cụ build" và "môi trường runtime."
- Để tối ưu hóa tối đa: jlink, distroless, GraalVM Native Image.
- Cache dependency riêng biệt với code — chìa khóa cho các build CI/CD nhanh.
- Bảo mật: image càng nhỏ, bề mặt tấn công càng nhỏ.
- Dùng `--target` để test các stage trung gian.

## Interview Cheat Sheet

**Cần phải biết:**
- Multi-stage build = nhiều FROM trong một Dockerfile; chỉ cái cuối cùng nằm trong image cuối cùng
- Tách "công cụ build" (Maven, JDK) và "môi trường runtime" (JRE, jar)
- Giảm kích thước: single-stage ~800MB → multi-stage slim ~300MB → distroless ~80MB
- Bảo mật: không có công cụ build trong image production, bề mặt tấn công nhỏ hơn
- Cache dependency riêng biệt với code — chìa khóa cho các build CI/CD nhanh
- Để tối ưu hóa tối đa: jlink (JRE tùy chỉnh), distroless, GraalVM Native Image
- `--target` cho phép build và test một stage trung gian

**Các câu hỏi phụ thường gặp:**
- *"Tại sao image nhỏ đi?"* — Trình biên dịch, source code, dependency build không nằm trong image cuối cùng
- *"Distroless là gì?"* — Image không có shell/package manager; kẻ tấn công không thể chạy `sh` bên trong container
- *"Khi nào KHÔNG cần multi-stage?"* — Python/Node.js không có bước biên dịch; COPY + RUN là đủ
- *"jlink mang lại gì?"* — JRE tùy chỉnh chỉ với các module cần thiết (40-60MB thay vì 300MB)

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi dùng một image cho cả build và runtime" (kích thước phình to, rủi ro bảo mật)
- "Multi-stage làm chậm build" (caching làm nó nhanh hơn)
- "Tôi sao chép toàn bộ thư mục builder" (chỉ cần artifact)
- "Các image distroless không thể debug" (các container debug ngắn hạn giải quyết điều này)
