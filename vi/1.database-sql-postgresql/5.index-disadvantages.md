# What are the disadvantages of indexes? (Nhược điểm của index là gì?)

## 🟢 Junior Level

**Index có một mặt trái:** chúng tăng tốc việc đọc nhưng lại làm chậm việc ghi.

**Ví dụ minh họa đơn giản:** Hãy tưởng tượng một cuốn sách có mục lục. Khi bạn thêm một chương mới, bạn không chỉ cần viết nó vào sách mà còn phải cập nhật mục lục. Nếu có nhiều mục lục — bạn cần cập nhật từng cái một.

**Các nhược điểm chính:**
- ⚠️ **INSERT/UPDATE/DELETE chậm hơn** — mỗi index đều cần được cập nhật
- ⚠️ **Chiếm dung lượng đĩa** — đôi khi còn nhiều hơn cả bản thân bảng
- ⚠️ **Cần bảo trì** — bạn cần theo dõi trạng thái của chúng

**Ví dụ:**
```sql
-- Bảng có 5 index
-- Khi chèn 1 dòng:
-- 1. Ghi dòng dữ liệu vào bảng
-- 2. Cập nhật index #1
-- 3. Cập nhật index #2
-- 4. Cập nhật index #3
-- 5. Cập nhật index #4
-- 6. Cập nhật index #5
-- Tổng cộng: 6 thao tác thay vì 1!
```

**Quy tắc:** Chỉ tạo index khi thực sự cần thiết.

## 🟡 Middle Level

### Write Amplification (Khuếch đại ghi)

Mỗi index làm tăng số lượng thao tác ghi:

```
1 lần INSERT vào bảng
= 1 lần ghi vào bảng
+ N lần ghi vào các index
+ Ghi vào WAL (Write Ahead Log)
```

**Ảnh hưởng đến hiệu năng:**

| Số lượng index     | Độ trễ INSERT   | Khối lượng WAL  |
| --------------------- | ---------------- | ----------- |
| 1                     | 1 ms             | 1x          |
| 5                     | 5-10 ms          | 5x          |
| 10                    | 20-50 ms         | 10x         |

### Chặn HOT updates

**HOT (Heap Only Tuple)** — một tối ưu hóa của PostgreSQL cho phép cập nhật một dòng mà không cần cập nhật index.

**Heap** — vùng lưu trữ chính của bảng, nơi chứa các dòng dữ liệu thực tế. Index chỉ chứa key + tham chiếu (TID) trỏ đến Heap. Với HOT, một phiên bản mới của dòng được ghi vào cùng page Heap với cùng TID — các index vẫn còn hợp lệ, không cần phải động đến chúng.

```sql
-- Bảng có một index trên status
CREATE INDEX idx_orders_status ON orders(status);

-- ❌ UPDATE này phải cập nhật index
UPDATE orders SET status = 'SHIPPED' WHERE id = 123;

-- ✅ UPDATE này có thể dùng HOT (status không được index)
UPDATE orders SET note = 'New note' WHERE id = 123;
```

**Điều kiện để có HOT:**
- Các cột bị thay đổi **không được index**
- Page Heap còn không gian trống

### Bloat (Phình index)

Index dễ bị phân mảnh (fragmentation) hơn cả bảng:

```sql
-- Vấn đề: Page Splits khi chèn vào giữa
-- Index trên email: 'A...', 'B...', 'C...'
-- Chèn 'B...' → page bị tràn → Split

-- Giải pháp: fillfactor
CREATE INDEX idx_orders_status ON orders(status)
WITH (fillfactor = 70);
-- 30% của page được để trống → ít split hơn
```

**VACUUM KHÔNG trả lại không gian cho hệ điều hành:**
- `VACUUM` đánh dấu không gian là trống để dùng cho các lần ghi mới
- Kích thước file vật lý không hề giảm
- Cần `REINDEX` để nén lại

### Tranh chấp RAM (RAM contention)

```sql
-- Kiểm tra kích thước các index
SELECT
    indexrelname,
    pg_size_pretty(pg_relation_size(indexrelid)) as size
FROM pg_stat_user_indexes
WHERE relname = 'orders'
ORDER BY pg_relation_size(indexrelid) DESC;

-- Nếu tổng kích thước index > RAM khả dụng
-- → Cache Miss → Random I/O → giảm hiệu năng
```

### Thời gian lập kế hoạch truy vấn (Query planning time)

Bộ tối ưu hóa (optimizer) xem xét tất cả các index hiện có:
- 5-10 index → thời gian lập kế hoạch < 1 ms
- 20-30 index → thời gian lập kế hoạch 10-50 ms
- 100+ index → thời gian lập kế hoạch > 100 ms!

### Khi nào KHÔNG nên tạo index

- Bảng < 10,000 dòng (Seq Scan nhanh hơn)
- Cột có cardinality (độ đa dạng giá trị) thấp (ví dụ: giới tính: Nam/Nữ)
- Trường hiếm khi được dùng trong WHERE/JOIN
- Bảng có tần suất ghi rất cao

## 🔴 Senior Level

### Write Amplification và các file log WAL

**Ảnh hưởng chi tiết đến I/O:**

```
Thao tác INSERT không có index:
├── Ghi Heap page: 1
├── Ghi WAL: 1 page
└── Số thao tác I/O: 1-2

Thao tác INSERT với 10 index:
├── Ghi Heap page: 1
├── Ghi Index page: 10
├── Ghi WAL: 11 page
├── Page Splits có thể xảy ra: +10-20 lần ghi
└── Số thao tác I/O: 15-30
```

**Ảnh hưởng đến Replica Lag:**
- Mỗi index tạo ra các mục WAL
- Replica phải phát lại (replay) TẤT CẢ các mục
- Với 10+ index: khối lượng WAL tăng 10-15 lần
- Replica không theo kịp → Replica Lag tăng lên
- **Quan trọng đối với các hệ thống có Read Replicas**

### Chặn HOT updates: Phân tích chuyên sâu

**Cơ chế HOT:**
```sql
-- Heap page (fillfactor = 100, không còn chỗ trống)
┌─────────────────────────────────┐
│ Row1 | Row2 | Row3 | ... | Full│
└─────────────────────────────────┘

-- UPDATE Row2 không có HOT:
-- 1. Tạo một phiên bản mới của Row2 trên một page khác
-- 2. Cập nhật TẤT CẢ các index (TID mới)
-- 3. Đánh dấu phiên bản cũ là đã chết (dead)

-- UPDATE Row2 với HOT (còn không gian trống trên page):
-- 1. Tạo một phiên bản mới của Row2 ở gần đó
-- 2. Chỉ cập nhật Heap (không động đến các index!)
-- 3. Đánh dấu phiên bản cũ là đã chết
-- 4. Các index vẫn còn hợp lệ (TID không thay đổi)
```

**Giám sát HOT:**
```sql
-- Kiểm tra hiệu quả của HOT
SELECT
    schemaname,
    relname,
    n_tup_hot_update,  -- Số lần HOT update
    n_tup_upd,         -- Tổng số lần update
    ROUND(100.0 * n_tup_hot_update / NULLIF(n_tup_upd, 0), 2) as hot_ratio
FROM pg_stat_user_tables
WHERE n_tup_upd > 0
ORDER BY hot_ratio DESC;

-- hot_ratio > 70% → xuất sắc (giá trị điển hình cho một khối lượng công việc OLTP khỏe mạnh)
-- hot_ratio < 20% → có vấn đề: hầu hết các lần update buộc phải cập nhật index,
--   cho thấy có quá nhiều index hoặc fillfactor quá nhỏ
```

### Index Bloat: Chẩn đoán và xử lý

**Nguyên nhân gây Bloat:**
1. **Page Splits** — chèn vào giữa một danh sách đã sắp xếp
2. **Xóa dữ liệu (Deletions)** — các page bị bỏ trống một nửa
3. **Cập nhật các cột có index** — tạo phiên bản mới, phiên bản cũ trở thành dead (chết)

**Chẩn đoán:**
```sql
-- 1. Kiểm tra thông qua pgstattuple
CREATE EXTENSION pgstattuple;

SELECT
    index_name,
    avg_leaf_density,      -- Bình thường: 70-90%
    leaf_fragmentation     -- Bình thường: < 20%
FROM pgstatindex('idx_orders_email');

-- 2. So sánh kích thước với kích thước dự kiến
SELECT
    schemaname,
    relname as table_name,
    indexrelname as index_name,
    pg_size_pretty(pg_relation_size(indexrelid)) as actual_size,
    idx_scan,
    -- Nếu kích thước lớn một cách đáng ngờ → Bloat
    CASE
        WHEN pg_relation_size(indexrelid) > 1000000000  -- > 1 GB
             AND idx_scan < 100
        THEN 'POSSIBLE BLOAT'
        ELSE 'OK'
    END as status
FROM pg_stat_user_indexes
WHERE schemaname = 'public'
ORDER BY pg_relation_size(indexrelid) DESC;
```

**Xử lý:**
```sql
-- 1. REINDEX (chặn ghi!)
REINDEX INDEX idx_orders_email;

-- 2. REINDEX CONCURRENTLY (không chặn, PG 12+)
REINDEX INDEX CONCURRENTLY idx_orders_email;

-- 3. pg_repack (không khóa, là một extension)
-- Cài đặt: CREATE EXTENSION pg_repack;
-- Chạy: pg_repack -t orders -d mydb
```

### Tranh chấp Shared Buffers

**Tính toán ví dụ:**
```
Cho biết:
- RAM: 64 GB
- shared_buffers: 16 GB (25%)
- Bảng: 10 GB
- Index: 20 GB

Vấn đề:
- Bảng + Index = 30 GB > 16 GB shared_buffers
- Một phần index bị đẩy ra khỏi bộ nhớ, lưu ra đĩa
- Tỷ lệ Cache Miss > 40%
- Random I/O thay vì đọc từ RAM

Giải pháp:
- Xóa các index không sử dụng → còn 8 GB
- Tăng shared_buffers lên 32 GB
- Tỷ lệ Cache Hit > 95%
```

**Giám sát Cache Hit:**
```sql
-- Kiểm tra hiệu quả của cache
SELECT
    sum(heap_blks_read) as heap_read,
    sum(heap_blks_hit) as heap_hit,
    ROUND(100.0 * sum(heap_blks_hit) /
          NULLIF(sum(heap_blks_read) + sum(heap_blks_hit), 0), 2)
          as cache_hit_pct
FROM pg_statio_user_tables;

-- > 99% → xuất sắc
-- 95-99% → bình thường
-- < 95% → có vấn đề (không đủ RAM hoặc quá nhiều index)
```

### Chi phí phát sinh cho thời gian lập kế hoạch (Planning Time Overhead)

```sql
-- Bật ghi log thời gian lập kế hoạch
SET log_min_duration_statement = 0;
SET log_parser_stats = on;

-- Trong log bạn sẽ thấy:
-- duration: 0.123 ms  parse
-- duration: 0.456 ms  plan
-- duration: 12.345 ms execute

-- Nếu plan > execute → quá nhiều index/bảng
```

**geqo_threshold:** Khi có > 12 bảng trong một truy vấn, thuật toán di truyền (GEQO — Genetic Query Optimizer) sẽ được kích hoạt, và nó có thể chọn ra một plan không tối ưu.

### Kinh nghiệm Production

**Tình huống thực tế #1: Bloat giết chết hiệu năng**
- Nền tảng SaaS: 100 triệu người dùng
- Index trên email: 8 GB (đáng lẽ chỉ nên là 2 GB)
- Triệu chứng: Tìm kiếm email > 500ms, tỷ lệ Cache Hit 60%
- Nguyên nhân: 2 năm cập nhật mà không REINDEX → 75% Bloat
- Giải pháp: `REINDEX INDEX CONCURRENTLY idx_users_email`
- Kết quả: Index giảm còn 2.1 GB, tìm kiếm < 5ms, Cache Hit 98%

**Tình huống thực tế #2: Replica Lag do index**
- E-commerce: 15 index trên bảng orders (200 triệu dòng)
- Vấn đề: Replica Lag > 120 giây
- Phân tích: Khối lượng WAL 1 GB/phút, replica không theo kịp
- Giải pháp:
  - Xóa 10 index không sử dụng
  - Khối lượng WAL giảm xuống còn 200 MB/phút
  - Replica Lag < 5 giây

### Dashboard giám sát

```sql
-- 1. Top index theo kích thước
SELECT
    indexrelname,
    pg_size_pretty(pg_relation_size(indexrelid)) as size,
    idx_scan
FROM pg_stat_user_indexes
ORDER BY pg_relation_size(indexrelid) DESC
LIMIT 10;

-- 2. Các index không sử dụng (ứng viên để loại bỏ)
SELECT
    relname as table_name,
    indexrelname as index_name,
    pg_size_pretty(pg_relation_size(indexrelid)) as size,
    idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0
  AND NOT indisunique  -- không phải UNIQUE!
ORDER BY pg_relation_size(indexrelid) DESC;

-- 3. Tỷ lệ HOT theo từng bảng
SELECT
    relname,
    n_tup_hot_update,
    n_tup_upd,
    ROUND(100.0 * n_tup_hot_update / NULLIF(n_tup_upd, 0), 2) as hot_pct
FROM pg_stat_user_tables
WHERE n_tup_upd > 1000
ORDER BY hot_pct ASC
LIMIT 10;

-- 4. Kiểm tra fill factor
SELECT
    c.relname as index_name,
    c.reloptions
FROM pg_class c
JOIN pg_index i ON i.indexrelid = c.oid
WHERE c.reloptions::text LIKE '%fillfactor%'
  AND c.relkind = 'i';
```

### Best Practices (Thực hành tốt nhất)

1. **Giám sát tỷ lệ HOT** — mục tiêu > 70%
2. **Kiểm tra Bloat** thường xuyên thông qua `pgstattuple`
3. **REINDEX CONCURRENTLY** hàng quý cho các index "nóng" (hot indexes)
4. **Xóa các index không sử dụng** — `idx_scan = 0` trong một tháng → ứng viên để loại bỏ
5. **fillfactor = 70-80** cho các index được cập nhật thường xuyên
6. **Giám sát Replica Lag** sau khi thêm index
7. **Giới hạn số lượng** — tối đa 5-7 index cho mỗi bảng
8. **Cache Hit Rate** > 95% — nếu thấp hơn, hãy giảm bớt index hoặc thêm RAM

### Tóm tắt cho Senior

- Index là một **loại thuế cho việc ghi (write tax)** (Write Amplification, WAL, Replica Lag)
- **Tỷ lệ HOT-update** < 20% → quá nhiều index
- **Bloat** là điều không thể tránh khỏi — xử lý bằng `REINDEX CONCURRENTLY`
- **Tranh chấp Shared Buffers** — index đẩy dữ liệu ra khỏi cache
- **Planning Time** tăng theo số lượng index
- Giám sát: `pgstattuple`, `pg_stat_user_indexes`, tỷ lệ HOT, tỷ lệ Cache Hit
- **Loại bỏ không thương tiếc** — nếu một index không được sử dụng trong một tháng, nó không cần thiết

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Write Amplification: 1 lần INSERT = 1 lần ghi bảng + N lần ghi index + WAL
- HOT (Heap Only Tuple): tối ưu hóa UPDATE mà không cần cập nhật index (nếu cột đó không được index)
- Tỷ lệ HOT > 70% → xuất sắc, < 20% → quá nhiều index
- Index Bloat: Page Splits → phân mảnh → cần `REINDEX CONCURRENTLY`
- VACUUM KHÔNG làm giảm kích thước file → cần REINDEX để nén lại
- Tranh chấp Shared Buffers: index đẩy dữ liệu ra khỏi bộ nhớ → Cache Miss → Random I/O
- Planning Time: 5-10 index < 1ms, 20-30 → 10-50ms, 100+ → > 100ms

**Các câu hỏi phụ thường gặp:**
- "Tại sao 15 index lại không tốt?" → Replica Lag, Write Amplification, Cache Miss
- "Làm sao để kiểm tra Bloat của index?" → `pgstattuple`, avg_leaf_density < 50% → cần REINDEX
- "HOT là gì và tại sao nó quan trọng?" → UPDATE mà không cần cập nhật index → nhanh hơn
- "Tại sao Cache Hit Rate giảm khi số lượng index tăng lên?" → Index đẩy dữ liệu ra khỏi RAM

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "Càng nhiều index càng tốt" (Write Amplification!)
- ❌ "VACUUM làm giảm kích thước file index" (sai, REINDEX mới làm được điều đó)
- ❌ "HOT là một loại phép thuật nào đó" (thực ra chỉ là UPDATE mà không cần cập nhật index!)
- ❌ "Planning Time không quan trọng" (100+ index → thời gian lập kế hoạch > 100ms)
