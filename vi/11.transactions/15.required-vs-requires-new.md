# What is the difference between REQUIRED and REQUIRES_NEW (Sự khác biệt giữa REQUIRED và REQUIRES_NEW là gì)

## 🟢 Junior Level

**REQUIRED** và **REQUIRES_NEW** là hai loại propagation transaction phổ biến nhất trong Spring. Khác biệt chính: REQUIRED sử dụng một transaction đã tồn tại, còn REQUIRES_NEW luôn tạo một transaction mới.

**Ví dụ minh họa đơn giản:**
- **REQUIRED** — như làm việc trên một tài liệu chung với một đồng nghiệp. Cả hai cùng chỉnh sửa cùng file. Nếu một người quyết định xóa hết — cả hai đều mất công việc của mình.
- **REQUIRES_NEW** — như hai tài liệu riêng biệt. Mỗi người làm việc trên file của riêng mình. Nếu một người làm hỏng tài liệu của họ — người kia không bị ảnh hưởng.

**Ví dụ SQL:**

```java
// REQUIRED (mặc định)
@Transactional  // propagation = REQUIRED
public void createOrder(Order order) {
    orderRepo.save(order);
    auditService.log(order);  // REQUIRED → cùng commit
    // Nếu createOrder thất bại — CẢ order VÀ audit đều rollback
}

// REQUIRES_NEW
@Transactional
public void createOrder(Order order) {
    orderRepo.save(order);
    auditService.log(order);  // REQUIRES_NEW → commit độc lập
    // Nếu createOrder thất bại — order rollback, NHƯNG audit đã được lưu
}
```

**Các khác biệt then chốt:**

| Đặc điểm       | REQUIRED                | REQUIRES_NEW            |
| -------------------- | ----------------------- | ----------------------- |
| Transaction mới      | Chỉ khi chưa tồn tại     | Luôn luôn                  |
| Tạm ngưng hiện tại      | Không                      | Có                     |
| Commit               | Một commit chung ở cuối   | Độc lập             |
| Rollback bên trong       | Rollback toàn bộ tx    | Chỉ tx bên trong              |
| Rollback bên ngoài       | Rollback cả bên trong    | KHÔNG ảnh hưởng bên trong   |

**Khi nào nên dùng REQUIRED:**
- Logic nghiệp vụ tiêu chuẩn (90% các trường hợp)
- Khi tất cả các thao tác phải nguyên tử

**Khi nào nên dùng REQUIRES_NEW:**
- Audit, logging
- Thông báo phải được lưu độc lập
- Các thao tác không nên phụ thuộc vào transaction bên ngoài

## 🟡 Middle Level

### Cách Nó Hoạt Động Nội Bộ

**REQUIRED:**
```
Lời gọi: serviceA.methodA() → proxy → TransactionInterceptor

1. Interceptor kiểm tra: có transaction đang hoạt động không?
   - Có → tham gia, tăng reference count
   - Không → tạo mới qua TransactionManager

2. Method thực thi
3. Khi commit:
   - Nếu tx bên ngoài → commit
   - Nếu tx bên trong (join) → không làm gì (chỉ commit ở bên ngoài)
4. Khi rollback:
   - setRollbackOnly() → đánh dấu toàn bộ transaction để rollback
   - tx bên ngoài khi commit thấy rollback-only → UnexpectedRollingBackException
```

**REQUIRES_NEW:**
```
Lời gọi: serviceA.methodA() → proxy → innerService.methodB(REQUIRES_NEW)

1. Tạm ngưng transaction hiện tại:
   - Connection gỡ khỏi ThreadLocal
   - Các transaction synchronization bị tạm ngưng
   - Trạng thái TransactionSynchronizationManager reset

2. Transaction vật lý mới được tạo:
   - Connection mới từ pool
   - BEGIN mới trong DB

3. Method thực thi
4. Khi commit → commit transaction bên trong
5. Khi rollback → rollback transaction bên trong
6. Khôi phục transaction bên ngoài:
   - Connection gắn lại vào ThreadLocal
   - Các synchronization được khôi phục
```

### Ứng Dụng Thực Tế

**Kịch bản 1: REQUIRED Cho Logic Nghiệp Vụ Nguyên Tử**
```java
@Service
public class OrderService {

    @Autowired private PaymentService paymentService;
    @Autowired private InventoryService inventoryService;

    @Transactional  // REQUIRED
    public OrderResult placeOrder(Order order) {
        // Tất cả các thao tác phải nguyên tử
        inventoryService.reserve(order.getItems());    // REQUIRED — tham gia
        PaymentResult payment = paymentService.charge(order.getTotal());  // REQUIRED — tham gia

        if (!payment.isSuccess()) {
            throw new PaymentFailedException();
            // Rollback: CẢ reserve VÀ charge đều rollback — nhất quán
        }

        orderRepo.save(order);
        return OrderResult.success();
    }
}
```

**Kịch bản 2: REQUIRES_NEW Cho Audit**
```java
@Service
public class PaymentService {

    @Autowired private AuditService auditService;

    @Transactional  // REQUIRED
    public PaymentResult processPayment(Payment payment) {
        // Audit TRƯỚC payment — phải được lưu ngay cả khi gateway thất bại
        auditService.logPaymentAttempt(payment);  // REQUIRES_NEW

        try {
            PaymentResult result = gateway.charge(payment);
            auditService.logPaymentSuccess(payment);  // REQUIRES_NEW
            return result;
        } catch (GatewayException e) {
            auditService.logPaymentFailure(payment, e);  // REQUIRES_NEW
            throw e;
            // Payment rollback, nhưng audit của lần thử đã commit rồi
        }
    }
}

@Service
public class AuditService {

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void logPaymentAttempt(Payment payment) {
        auditRepo.save(new AuditEntry(payment, "ATTEMPT"));
        // Commit — độc lập với transaction bên ngoài
    }
}
```

**Kịch bản 3: REQUIRES_NEW Cho Các Side-Effect Độc Lập**
```java
@Service
public class NotificationService {

    @Transactional(propagation = Propagation.REQUIRES_NEW, timeout = 5)
    public void sendOrderConfirmation(Order order) {
        // Nếu gửi email thất bại — order vẫn nên được lưu
        emailService.send(order.getEmail(), "Order Confirmed");
        notificationRepo.save(new Notification(order, "EMAIL_SENT"));
        // Commit — thông báo được lưu ngay cả khi tx bên ngoài rollback
    }
}
```

### Các Lỗi Điển Hình

| Lỗi                                                 | Hậu quả                                                                                                                                                                                                                 | Giải pháp                                               |
| ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| REQUIRED + exception bên trong                              | Toàn bộ transaction bị đánh dấu rollback-only                                                                                                                                                                                       | try-catch bên trong method con hoặc REQUIRES_NEW          |
| REQUIRES_NEW cho dữ liệu liên quan                           | Commit bên trong tạo ra dữ liệu không nhất quán — NẾU transaction bên trong ghi dữ liệu phụ thuộc logic vào bên ngoài (ví dụ: order_items không có order). Với dữ liệu độc lập (audit) — đây là hành vi đúng.                            | Dùng REQUIRED cho các thao tác liên quan về mặt logic          |
| REQUIRES_NEW không có timeout                            | Tx bên trong bị treo chặn tx bên ngoài                                                                                                                                                                                              | Luôn đặt `timeout` cho REQUIRES_NEW                  |
| Giả định REQUIRES_NEW = nguyên tử với bên ngoài            | Tx bên trong commit ngay lập tức, bên ngoài có thể rollback                                                                                                                                                                                             | Hiểu rõ: REQUIRES_NEW = tx độc lập            |
| REQUIRED khi được gọi qua `this`                         | Propagation bị bỏ qua                                                                                                                                                                                                          | Dùng bean riêng biệt hoặc self-injection                    |

### So Sánh: REQUIRED vs REQUIRES_NEW

| Đặc điểm            | REQUIRED              | REQUIRES_NEW                    |
| ------------------------- | --------------------- | -------------------------------- |
| Transaction vật lý     | 1                     | 2+                              |
| Tạm ngưng tx bên ngoài          | Không                    | Có                             |
| Sử dụng connection          | 1                     | 2 (suspend + mới)               |
| Commit độc lập        | Không                    | Có                               |
| Lan truyền rollback      | Toàn bộ chuỗi          | Chỉ tx của riêng nó                     |
| Ảnh hưởng khi bên ngoài rollback     | Rollback bên trong      | Không ảnh hưởng bên trong            |
| Overhead throughput       | Tối thiểu               | +10-20%                         |
| Áp lực connection pool  | Thấp                    | Cao (x2 mỗi lời gọi)              |
| Nguy cơ deadlock             | Thấp                    | Trung bình (2 connection)          |
| Trường hợp sử dụng                  | Logic nghiệp vụ cốt lõi   | Audit, logging, thông báo   |

### Khi Nào KHÔNG Nên Dùng REQUIRES_NEW

- **Logic nghiệp vụ nguyên tử** — nếu tất cả các thao tác phải commit/rollback cùng nhau
- **Các hệ thống tải cao** — overhead suspend/resume + áp lực connection pool
- **Microservice với eventual consistency** — mỗi service tự quản lý transaction của riêng mình
- **Khi tx bên trong phụ thuộc vào dữ liệu của tx bên ngoài** — commit bên trong có thể commit dữ liệu chưa hoàn chỉnh

## 🔴 Senior Level

### Hiện Thực Nội Bộ: Suspend/Resume Và Transaction Synchronization

#### Cơ Chế Suspend (REQUIRES_NEW)

```java
// AbstractPlatformTransactionManager.suspend()

protected final SuspendedResourcesHolder suspend(@Nullable Object transaction) {
    if (transaction != null) {
        // 1. Tạm ngưng các transaction synchronization (Hibernate session, v.v.)
        List<TransactionSynchronization> suspendedSynchronizations =
            doSuspendSynchronization();

        // 2. Gỡ connection khỏi ThreadLocal
        // Spring lưu connection JDBC trong ThreadLocal qua ConnectionHolder.
        // unbindResource = tách connection khỏi thread hiện tại
        // bindResource = gắn lại
        ConnectionHolder conHolder = (ConnectionHolder)
            TransactionSynchronizationManager.unbindResource(obtainDataSource());

        // 3. Reset trạng thái TransactionSynchronizationManager
        boolean wasActive = TransactionSynchronizationManager.isActualTransactionActive();
        TransactionSynchronizationManager.setActualTransactionActive(false);
        IsolationLevel currentIsolation =
            TransactionSynchronizationManager.getCurrentTransactionIsolationLevel();
        TransactionSynchronizationManager.setCurrentTransactionIsolationLevel(null);
        TransactionSynchronizationManager.setReadOnly(false);
        TransactionSynchronizationManager.setCurrentTransactionName(null);

        return new SuspendedResourcesHolder(
            conHolder, suspendedSynchronizations, wasActive, currentIsolation);
    }
    return null;
}
```

**Điều gì bị tạm ngưng:**
```java
// doSuspendSynchronization() — tạm ngưng tất cả các synchronization đã đăng ký

// Các callback TransactionSynchronization:
interface TransactionSynchronization {
    void suspend();    // Được gọi khi suspend
    void resume();     // Được gọi khi resume
    void beforeCommit(boolean readOnly);
    void beforeCompletion();
    void afterCommit();
    void afterCompletion(int status);
}

// Các synchronization đã đăng ký bao gồm:
// - Synchronization của Hibernate Session
// - Synchronization của JPA EntityManager
// - Các synchronization tùy chỉnh (đăng ký bởi code application)
```

#### Cơ Chế Resume

```java
// AbstractPlatformTransactionManager.resume()

protected final void resume(@Nullable Object transaction,
                             @Nullable SuspendedResourcesHolder resourcesHolder) {
    if (resourcesHolder != null) {
        Object suspendedResources = resourcesHolder.getSuspendedResources();

        if (suspendedResources != null) {
            // 1. Gắn lại connection vào ThreadLocal
            TransactionSynchronizationManager.bindResource(
                obtainDataSource(), resourcesHolder.getConnectionHolder());
        }

        // 2. Khôi phục các synchronization
        doResumeSynchronization(resourcesHolder.getSuspendedSynchronizations());

        // 3. Khôi phục trạng thái
        TransactionSynchronizationManager.setActualTransactionActive(
            resourcesHolder.wasActive());
        TransactionSynchronizationManager.setCurrentTransactionIsolationLevel(
            resourcesHolder.getSuspendedIsolationLevel());
    }
}
```

#### Logic Tham Gia (Join) Của REQUIRED

```java
// handleExistingTransaction() — trường hợp REQUIRED

case PROPAGATION_REQUIRED:
    // Tham gia transaction hiện có
    // KHÔNG tạo transaction mới
    // Reference count được tăng lên

    return prepareTransactionStatus(
        definition,           // cùng tham số
        transaction,          // cùng object transaction
        false,                // newTransaction = false
        false,                // newSynchronization = false
        debugEnabled,
        null);                // không có tài nguyên tạm ngưng

// Quan trọng: lan truyền rollback
// Nếu method bên trong (REQUIRED) ném RuntimeException:
// 1. TransactionInterceptor bắt exception
// 2. Gọi: status.setRollbackOnly()
// 3. AbstractPlatformTransactionManager đánh dấu TOÀN BỘ transaction
// 4. Method bên ngoài không thể hủy điều này
```

**Lan Truyền Cờ Rollback-Only:**
```java
// AbstractPlatformTransactionManager

public final void rollback(TransactionStatus status) throws TransactionException {
    if (status.isCompleted()) {
        return;  // Đã hoàn thành rồi
    }

    DefaultTransactionStatus defStatus = (DefaultTransactionStatus) status;

    if (defStatus.isNewTransaction()) {
        // Đây là tx bên ngoài → thực hiện rollback
        doRollback(defStatus);
    } else {
        // Đây là tx bên trong (join) → chỉ đánh dấu rollback-only
        defStatus.setRollbackOnly();
        // tx bên ngoài khi commit sẽ thấy cờ này và rollback
    }
}
```

### Đánh Đổi Về Kiến Trúc (Trade-off)

**Cách A: REQUIRED**
- ✅ Ưu điểm: Tính nguyên tử (tất cả hoặc không gì cả), đơn giản, overhead tối thiểu (1 connection), tương thích ORM đầy đủ
- ❌ Nhược điểm: Không chịu được thất bại từng phần, exception bên trong → rollback toàn bộ, lan truyền rollback-only
- Phù hợp cho: các transaction tài chính, xử lý đơn hàng, bất kỳ thao tác nào yêu cầu tính nguyên tử đầy đủ

**Cách B: REQUIRES_NEW**
- ✅ Ưu điểm: Commit độc lập, xử lý thất bại từng phần, audit trail, cô lập khỏi các thất bại của tx bên ngoài
- ❌ Nhược điểm: Overhead suspend/resume (5-15ms), sử dụng connection x2, nguy cơ dữ liệu không nhất quán (bên trong đã commit, bên ngoài rollback)
- Phù hợp cho: audit logging, gửi thông báo, các side-effect độc lập, theo dõi compliance

**Cách C: REQUIRES_NEW + Bù Trừ (Compensation)**
```java
@Transactional
public void processWithCompensation(Data data) {
    try {
        sideEffectService.doWork(data);  // REQUIRES_NEW — commit
    } catch (Exception e) {
        // sideEffect đã commit rồi — cần bù trừ
        compensationService.undoSideEffect(data);  // REQUIRES_NEW
        throw e;  // Rollback tx bên ngoài
    }
}
```
- ✅ Ưu điểm: Kết hợp tốt nhất của cả hai — độc lập + bù trừ
- ❌ Nhược điểm: Độ phức tạp, cần hiện thực undo cho từng side-effect
- Phù hợp cho: các pattern saga, hệ thống phân tán, eventual consistency

### Các Trường Hợp Biên Và Đặc Biệt

**1. Lan Truyền Rollback-Only (Vấn Đề Phổ Biến Nhất):**
```java
@Transactional
public void outerMethod() {
    try {
        innerService.innerMethod();  // REQUIRED
    } catch (Exception e) {
        // Đã bắt exception...
    }
    // ...nhưng transaction đã bị đánh dấu rollback-only!
    // Khi commit: UnexpectedRollingBackException
}

@Transactional
public void innerMethod() {  // REQUIRED
    repo.save(entity);
    throw new RuntimeException("fail");
    // TransactionInterceptor: status.setRollbackOnly()
}
```

**Tại sao điều này xảy ra:**
```
innerMethod() — REQUIRED, tham gia transaction hiện có
Khi có exception:
  → TransactionInterceptor.completeTransactionAfterThrowing()
  → tm.rollback(txInfo.getTransactionStatus())
  → AbstractPlatformTransactionManager.rollback()
  → isNewTransaction() = false (tham gia)
  → defStatus.setRollbackOnly()  // KHÔNG phải doRollback!

Method bên ngoài khi commit:
  → tm.commit(status)
  → status.isRollbackOnly() = true
  → doRollback(status)  // Rollback bắt buộc!
  → throw UnexpectedRollingBackException
```

**Các giải pháp:**
```java
// Giải pháp A: REQUIRES_NEW
innerService.innerMethod();  // REQUIRES_NEW — chỉ rollback tx của riêng nó

// Giải pháp B: try-catch bên trong method con
@Transactional
public void innerMethod() {
    try {
        repo.save(entity);
        throw new RuntimeException("fail");
    } catch (Exception e) {
        log.error("Inner failed, but won't rollback outer", e);
        // Exception không lan truyền → tx bên ngoài không bị đánh dấu rollback-only
    }
}

// Giải pháp C: noRollbackFor
@Transactional(noRollbackFor = BusinessException.class)
public void innerMethod() {
    repo.save(entity);
    throw new BusinessException("fail");  // Không gây rollback
}
```

**2. REQUIRES_NEW Và Cạn Kiệt Connection Pool:**
```
Tải: 100 request đồng thời
Mỗi request: 1 tx bên ngoài + 2 lời gọi REQUIRES_NEW = 3 connection

Tổng số connection cần: 100 × 3 = 300
Kích thước pool HikariCP: 50

Kết quả:
  - 50 request nhận được connection
  - 250 chờ connectionAcquisitionTimeout (mặc định 30 giây)
  - Timeout → request thất bại
```

**Giải pháp:**
```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 150  # >= max_concurrent × max_nested_tx
      connection-timeout: 5000  # thất bại nhanh hơn
```

**3. REQUIRES_NEW Và Hibernate Session:**
```java
@Transactional
public void outerMethod() {
    Entity outer = em.find(Entity.class, 1L);  // được load trong Session 1
    outer.setName("outer-change");

    innerService.innerMethod();  // REQUIRES_NEW → suspend Session 1, tạo Session 2

    // Session 2 KHÔNG thấy các thay đổi từ Session 1 (chưa flush)
    // Nếu innerMethod đọc cùng entity → thấy giá trị cũ

    // Khi resume Session 1:
    // Session 1 vẫn chứa "outer-change" ở trạng thái dirty
    // Nhưng các thay đổi chưa được ghi vào DB
}
```

**Tác động:** Tx bên trong có thể đọc dữ liệu cũ (stale). Giải pháp: `em.flush()` trước lời gọi REQUIRES_NEW.

**4. Transaction Synchronization Và REQUIRES_NEW:**
```java
// tx bên ngoài đăng ký synchronization
TransactionSynchronizationManager.registerSynchronization(
    new TransactionSynchronization() {
        @Override
        public void afterCommit() {
            // Được gọi sau khi tx bên ngoài commit
        }

        @Override
        public void afterCompletion(int status) {
            // Được gọi sau khi tx bên ngoài hoàn thành
        }

        @Override
        public void suspend() {
            // Được gọi khi REQUIRES_NEW suspend
        }

        @Override
        public void resume() {
            // Được gọi khi REQUIRES_NEW resume
        }
    }
);

// tx bên trong (REQUIRES_NEW) có các synchronization riêng của nó
// afterCommit của bên trong được gọi sau khi bên trong commit, KHÔNG phải bên ngoài
```

**5. REQUIRES_NEW Và Isolation Level:**
```java
@Transactional
public void outerMethod() {
    // tx bên ngoài dùng isolation mặc định (hoặc đặt trên bên ngoài)

    innerService.innerMethod();  // REQUIRES_NEW
    // tx bên trong có thể đặt isolation level riêng của nó
}

@Transactional(propagation = Propagation.REQUIRES_NEW,
               isolation = Isolation.SERIALIZABLE)
public void innerMethod() {
    // tx bên trong: SERIALIZABLE
    // tx bên ngoài: DEFAULT (Read Committed)
    // Các isolation level này KHÔNG ảnh hưởng lẫn nhau (tx vật lý khác nhau)
}
```

**6. REQUIRES_NEW Và Timeout:**
```java
@Transactional(propagation = Propagation.REQUIRES_NEW, timeout = 5)
public void innerMethod() {
    // timeout = 5 giây CHỈ cho tx bên trong
    // timeout của tx bên ngoài KHÔNG bị ảnh hưởng

    longRunningOperation();  // Nếu > 5 giây → timeout tx bên trong
    // tx bên ngoài tiếp tục (nhưng bên trong đã rollback)
}
```

**7. Tầng REQUIRES_NEW Lồng Nhau:**
```java
@Transactional
public void level0() {
    level1Service.level1();  // REQUIRES_NEW → suspend L0, tạo L1

    @Transactional(propagation = REQUIRES_NEW)
    public void level1() {
        level2Service.level2();  // REQUIRES_NEW → suspend L1, tạo L2
    }
}

// Ngăn xếp connection:
// L0: connection-1 (tạm ngưng)
// L1: connection-2 (tạm ngưng)
// L2: connection-3 (đang hoạt động)
//
// Thứ tự commit: L2 → resume L1 → L1 commit → resume L0 → L0 commit
// Thứ tự rollback: L2 rollback → resume L1 → L1 có thể tiếp tục hoặc rollback
```

### Tác Động Đến Hiệu Năng

| Metric                          | REQUIRED        | REQUIRES_NEW                     |
| -------------------------------- | --------------- | -------------------------------- |
| Latency (overhead)              | ~0ms (cơ sở) | +5-15ms (suspend/resume)         |
| Sử dụng connection                | 1               | 2+ (mỗi lời gọi lồng nhau)             |
| Throughput (một lời gọi)        | 25,000 TPS      | 20,000 TPS (-20%)                |
| Throughput (5 lồng nhau)           | 25,000 TPS      | 10,000 TPS (-60%)                |
| Áp lực connection pool        | 1x              | Nx (N = độ sâu lồng nhau)           |
| Overhead sync Hibernate Session | Không có            | Flush + clear mỗi lần suspend/resume |

**Các con số dùng để minh họa tỷ lệ tương đối (Spring Boot 3.2, PostgreSQL 15, HikariCP pool=50). Giá trị tuyệt đối phụ thuộc vào DB, schema, phần cứng, và tải. Điều quan trọng cần nắm — REQUIRES_NEW thêm overhead 20-60% mỗi cấp lồng nhau.**
```
Kịch bản: 1 tx bên ngoài + 1 lời gọi REQUIRES_NEW
  - Suspend: ~2ms
  - Lấy connection mới: ~0.5ms
  - Thực thi tx bên trong: cơ sở
  - Commit bên trong: ~1ms
  - Resume: ~2ms
  - Tổng overhead: ~5.5ms mỗi lời gọi REQUIRES_NEW
    Suspend bao gồm: unbind Connection khỏi ThreadLocal (~0.1ms), suspend Hibernate
    Session và flush L1 cache (~1.5ms), hủy đăng ký transaction synchronization (~0.4ms).

Kịch bản: 1 tx bên ngoài + 3 lời gọi REQUIRES_NEW
  - Tổng overhead: ~16.5ms
  - Giảm throughput: ~35%

Kích thước connection pool:
  - Chỉ REQUIRED: pool = max_concurrent_requests
  - Với 1 REQUIRES_NEW: pool = max_concurrent_requests × 2
  - Với N REQUIRES_NEW: pool = max_concurrent_requests × (N + 1)
```

### Tác Động Đến Bộ Nhớ

- **ConnectionHolder tạm ngưng:** ~2KB (tham chiếu connection + trạng thái)
- **Các TransactionSynchronization tạm ngưng:** ~500 byte – 5KB (tùy số lượng)
- **Trạng thái ThreadLocal mỗi lần suspend:** ~1-2KB
- **Trạng thái Hibernate Session (tạm ngưng):** ~100KB – 5MB (tùy kích thước L1 cache)
- **EntityManager của tx bên trong:** ~100KB – 5MB (PersistenceContext mới)

**Tổng cộng mỗi lời gọi REQUIRES_NEW:** ~200KB – 10MB (chủ yếu là trạng thái Hibernate Session)

### Các Khía Cạnh Concurrency

**Thực thi đồng thời của REQUIRES_NEW:**
```
Thread-1: outer(REQUIRED) → suspend → inner1(REQUIRES_NEW) → commit → resume → outer commit
Thread-2: outer(REQUIRED) → suspend → inner2(REQUIRES_NEW) → commit → resume → outer commit

inner1 và inner2 thực thi song song (connection khác nhau)
outer1 và outer2 chờ ở giai đoạn suspend cho đến khi bên trong hoàn thành

Nguy cơ deadlock:
  - Tx bên trong có thể khóa các dòng mà tx bên ngoài cần sau resume
  - Tx bên ngoài có thể khóa các dòng mà tx bên trong cần
  → Deadlock (có thể phát hiện bởi deadlock detector của DB)
```

**Kịch bản deadlock:**
```
T1-outer: UPDATE accounts SET balance = 900 WHERE id = 1;  -- khóa dòng 1
T1-inner(REQUIRES_NEW): UPDATE accounts SET balance = 800 WHERE id = 2;  -- khóa dòng 2
T2-inner(REQUIRES_NEW): UPDATE accounts SET balance = 700 WHERE id = 1;  -- chờ dòng 1
T2-outer: UPDATE accounts SET balance = 600 WHERE id = 2;  -- chờ dòng 2

→ Deadlock! T1-inner chờ T2-outer, T2-inner chờ T1-outer

Timeline: T=0: T1-outer khóa dòng 1. T=1: T2-inner thử dòng 1 — BỊ CHẶN.
T=2: T1-inner khóa dòng 2. T=3: T2-outer thử dòng 2 — BỊ CHẶN.
Deadlock detector: T2-outer → T1-inner → T2-inner → T1-outer → chu trình.
```

### Tình Huống Thực Tế Trong Production

**Tình huống:** Nền tảng dữ liệu y tế (2024), Spring Boot 3.1, MySQL 8.0, xử lý 5,000 hồ sơ bệnh nhân/giờ.

**Vấn đề:** Khi xử lý hồ sơ bệnh nhân, audit log bị mất khi xử lý thất bại. Đợt kiểm toán theo quy định phát hiện 15% các lần truy cập không được ghi log.

**Code gốc:**
```java
@Transactional
public void processPatientRecord(PatientRecord record) {
    // Audit với REQUIRED — một phần của transaction chung
    auditService.logAccess(record);  // REQUIRED

    // Xử lý dữ liệu — có thể thất bại
    Data validated = validateAndTransform(record);
    patientRepo.save(validated);

    // Nếu validateAndTransform thất bại → rollback TẤT CẢ, kể cả audit
    // Bản ghi audit bị mất → vi phạm compliance
}
```

**Nguyên nhân gốc rễ:** `auditService.logAccess()` dùng REQUIRED theo mặc định. Khi có bất kỳ thất bại xử lý nào, bản ghi audit rollback cùng transaction chính.

**Giải pháp:**
```java
@Transactional
public void processPatientRecord(PatientRecord record) {
    // Audit TRƯỚC khi xử lý — REQUIRES_NEW
    auditService.logAccess(record);  // REQUIRES_NEW → commit ngay lập tức

    try {
        Data validated = validateAndTransform(record);
        patientRepo.save(validated);
    } catch (Exception e) {
        // Xử lý bản ghi thất bại, nhưng audit truy cập được giữ nguyên
        throw e;
    }
}

@Service
public class AuditService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void logAccess(PatientRecord record) {
        auditRepo.save(new AuditEntry(record, "ACCESS_ATTEMPT"));
        // Commit — độc lập với transaction bên ngoài
    }
}
```

**Kết quả:**
- Độ phủ audit: từ 85% lên 100%
- Compliance: đã pass đợt kiểm toán theo quy định
- Throughput: -3% (overhead của REQUIRES_NEW) — chấp nhận được
- Connection pool: tăng từ 30 lên 45

### Giám Sát Và Chẩn Đoán

**Theo dõi việc sử dụng REQUIRES_NEW:**
```java
@Aspect
@Component
public class TransactionPropagationMonitor {
    private final MeterRegistry registry;

    @Around("@annotation(transactional)")
    public Object monitor(ProceedingJoinPoint pjp, Transactional transactional) throws Throwable {
        String propagation = transactional.propagation().name();
        Timer.Sample sample = Timer.start(registry);

        try {
            Object result = pjp.proceed();
            sample.stop(Timer.builder("spring.transaction.execution")
                .tag("propagation", propagation)
                .tag("result", "success")
                .register(registry));
            return result;
        } catch (Throwable ex) {
            sample.stop(Timer.builder("spring.transaction.execution")
                .tag("propagation", propagation)
                .tag("result", "failure")
                .register(registry));
            throw ex;
        }
    }
}
```

### Best Practices Cho Highload

1. **Giảm thiểu lồng REQUIRES_NEW** — mỗi cấp thêm overhead suspend/resume + connection.
2. **Đặt timeout cho REQUIRES_NEW** — ngăn các transaction bên trong bị treo.
3. **Đặt kích thước connection pool phù hợp** — pool = max_concurrent × (1 + max_nested_REQUIRES_NEW).
4. **Flush trước REQUIRES_NEW nếu bên trong đọc cùng dữ liệu** — `em.flush()` để tránh đọc dữ liệu cũ.
5. **Dùng REQUIRED cho các thao tác liên quan nguyên tử** — không bao giờ tách logic nguyên tử qua REQUIRES_NEW.
6. **Audit luôn = REQUIRES_NEW** — dữ liệu audit phải tồn tại ngay cả khi bên ngoài rollback.

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- REQUIRED dùng transaction hiện có (hoặc tạo mới), REQUIRES_NEW luôn tạo mới và tạm ngưng bên ngoài
- REQUIRED: 1 transaction vật lý, REQUIRES_NEW: 2+ transaction vật lý
- Lan truyền rollback-only của REQUIRED: RuntimeException bên trong đánh dấu toàn bộ tx để rollback
- REQUIRES_NEW: overhead suspend/resume (~5-15ms), dùng 2 connection
- Commit bên trong của REQUIRES_NEW là độc lập — rollback bên ngoài không ảnh hưởng đến nó
- Kích thước connection pool: với REQUIRES_NEW, pool = max_concurrent × (1 + nesting_depth)

**Các câu hỏi phụ thường gặp:**
- Điều gì xảy ra nếu REQUIRED bên trong ném exception và bên ngoài bắt nó? — Transaction bị đánh dấu rollback-only → UnexpectedRollingBackException khi commit
- Tại sao REQUIRES_NEW cần 2 connection? — Connection bên ngoài bị tạm ngưng, một connection mới được tạo cho tx bên trong
- Khi nào nên dùng REQUIRES_NEW vs REQUIRED? — REQUIRES_NEW: audit/logging, side-effect độc lập; REQUIRED: logic nghiệp vụ nguyên tử
- Hibernate Session hoạt động như thế nào với REQUIRES_NEW? — Session bị tạm ngưng, một Session mới được tạo — bên trong không thấy được các thay đổi chưa flush của bên ngoài

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "REQUIRES_NEW và REQUIRED giống nhau đối với các lời gọi bên trong" — REQUIRED tham gia, REQUIRES_NEW suspend+tạo mới
- "Rollback bên ngoài ảnh hưởng đến bên trong của REQUIRES_NEW" — REQUIRES_NEW đã commit rồi, độc lập
- "REQUIRES_NEW không ảnh hưởng đến hiệu năng" — overhead 20-60% mỗi cấp lồng nhau
