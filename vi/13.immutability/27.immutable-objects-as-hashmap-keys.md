# Can you use immutable objects as keys in HashMap? (Bạn có thể dùng immutable object làm key trong HashMap không?)

---

## Basic Level

**Không chỉ có thể, mà còn rất được khuyến khích!** Các immutable object là key lý tưởng cho `HashMap`.

```java
Map<String, Integer> ages = new HashMap<>();
ages.put("Ivan", 25);  // String — bất biến
ages.put("Ivan", 30);  // Cập nhật theo cùng một key

System.out.println(ages.get("Ivan")); // 30
```

### Tại Sao Điều Này Tốt

- `hashCode()` không đổi — object luôn ở đúng bucket
- `equals()` hoạt động ổn định
- Không cần lo lắng về việc key bị "thất lạc"

### Các Key Tốt Nhất
- `String` — phổ biến nhất
- `Integer`, `Long` — các wrapper nguyên thủy
- `LocalDate`, `UUID` — các định danh ổn định
- `Record` — các key kết hợp từ nhiều trường

---

## Intermediate Level

### Cách HashMap Hoạt Động Với Key

1. `put(key, value)` — `key.hashCode()` được tính → bucket được xác định
2. `get(key)` — `key.hashCode()` được tính lại → tìm trong cùng bucket đó
3. Nếu `hashCode()` đã thay đổi — key bị "thất lạc" trong một bucket khác

### Các Immutable Object Cache hashCode

`String` tính `hashCode` một lần và cache nó:
```java
// Bên trong String
private int hash; // 0 theo mặc định
public int hashCode() {
    if (hash == 0 && value.length > 0) {
        hash = ...; // chỉ tính một lần
    }
    return hash;
}
```

### Vấn Đề Với Key Mutable
```java
List<String> key = new ArrayList<>(List.of("A"));
map.put(key, 42);
key.add("B");           // đã thay đổi key!
map.get(key);           // null — hashCode đã thay đổi
```
Object vẫn nằm về mặt vật lý trong bucket, nhưng `get` lại tìm ở nơi khác.

Quan trọng: equals và hashCode phải dùng cùng một tập hợp các trường.
Nếu hashCode dùng `id` nhưng equals dùng `id + name` thì hai object có cùng id
nhưng khác name sẽ rơi vào cùng một bucket nhưng lại không bằng nhau.

## Advanced Level

### Key Lý Tưởng Cho HashMap

```java
public record CompositeKey(String type, Long id) {} // tự động final, equals, hashCode

Map<CompositeKey, Entity> map = new HashMap<>();
map.put(new CompositeKey("user", 1L), user);
```

### Chiến Lược Nếu Key Phải Là Mutable

1. **Dùng một định danh**: `Long id` thay vì chính object đó
2. **Remove → sửa đổi → add lại**:
   ```java
   map.remove(key);
   key.changeSomething();
   map.put(key, value);
   ```
3. **IdentityHashMap** — so sánh theo `==`, không theo `equals()`/`hashCode()`

### hashCode Cho Các Key Kết Hợp

Record sinh ra hashCode qua `Objects.hashCode` cho mỗi trường.
Khi có va chạm (collision), HashMap xây dựng một cây (O(log n) thay vì O(n)).
Với các key kết hợp, kết hợp hashCode của tất cả các trường quan trọng.

### Tóm Tắt Cho Advanced
- Các key bất biến đảm bảo **tính tất định (determinism)** của các collection dựa trên hash
- Ngăn ngừa các bug khó tìm và rò rỉ bộ nhớ
- `Record` — lựa chọn lý tưởng cho các key kết hợp
- Thiết kế các key collection như các entity bất biến
- `hashCode` được cache — tối ưu hóa bổ sung

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Các immutable object là key LÝ TƯỞNG: hashCode ổn định, không có rủi ro thất lạc trong bucket
- String, Integer, LocalDate, Record — các key tốt nhất
- String cache hashCode — chỉ tính một lần, tăng tốc các lần tra cứu lặp lại
- Record sinh equals/hashCode qua `Objects.hashCode` cho mỗi trường
- Key mutable = object thất lạc: hashCode thay đổi, get tìm trong một bucket khác
- Khi có va chạm, HashMap xây dựng một cây — O(log n) thay vì O(n)

**Các câu hỏi phụ thường gặp:**
- *Tại sao một key mutable nguy hiểm?* — hashCode thay đổi → object bị "thất lạc" → rò rỉ logic
- *Record như một key?* — Lý tưởng: tự động final, equals, hashCode trên tất cả các trường
- *Nếu key phải là mutable?* — IdentityHashMap (so sánh theo ==) hoặc remove → mutate → put
- *equals và hashCode có phải khớp nhau không?* — Có, dùng cùng một tập hợp các trường

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Key mutable trong HashMap là ổn" — object trở nên không thể truy cập được
- "hashCode không cần cache" — với các immutable object đó là một tối ưu hóa
- "ArrayList làm key là một ý tưởng tốt" — nó là mutable, hashCode sẽ thay đổi
- "IdentityHashMap giải quyết mọi vấn đề" — so sánh theo ==, không phải equals — một trường hợp sử dụng cụ thể
