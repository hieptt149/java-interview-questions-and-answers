# Can You Modify String Contents via Reflection? (Bạn có thể sửa đổi nội dung String qua Reflection không?)

## 🟢 Junior Level

**Về mặt kỹ thuật — có, nhưng đây là một ý tưởng cực kỳ tồi.**

String được thiết kế như một class **bất biến (immutable)**. Điều này có nghĩa là sau khi tạo, một chuỗi không thể được sửa đổi. Nhưng Java Reflection cho phép bạn "nhìn vào bên trong" bất kỳ object nào và thay đổi ngay cả các trường `private` và `final`.

**Ví dụ (đừng làm điều này!):**
```java
String s = "Hello";
Field valueField = String.class.getDeclaredField("value");
valueField.setAccessible(true);

// Java 9+: value là byte[]
byte[] value = (byte[]) valueField.get(s);
value[0] = (byte) 'J'; // Thay đổi byte trực tiếp

System.out.println(s); // "Jello" — chuỗi đã thay đổi!
```

**Ví dụ minh họa đơn giản:** String giống như một chai nước đã niêm phong. Nhà sản xuất kỳ vọng bạn sẽ không mở nó. Nhưng nếu bạn vặn nắp ra (reflection) và nhuộm màu nước — chai vẫn trông giống "nước", nhưng nội dung đã khác.

**Tại sao điều này nguy hiểm:**
1. **Tất cả các tham chiếu đến chuỗi này cũng sẽ thay đổi** — các phần khác của chương trình sẽ thấy "Jello" thay vì "Hello"
2. **String Pool sẽ bị hỏng** — literal `"Hello"` trong code giờ có thể có nghĩa là "Jello"
3. **Bảo mật gặp rủi ro** — hash mật khẩu, key, token có thể bị thay đổi

**Kết luận:** Không bao giờ sửa đổi String qua reflection trong code thực tế.

## 🟡 Middle Level

### Cách Nó Hoạt Động

Trước Java 9:
```java
// String lưu char[] value
Field valueField = String.class.getDeclaredField("value");
valueField.setAccessible(true);
char[] value = (char[]) valueField.get(s);
value[0] = 'J';
```

Java 9+ (Compact String):
```java
// String lưu byte[] value + byte coder
Field valueField = String.class.getDeclaredField("value");
valueField.setAccessible(true);
byte[] value = (byte[]) valueField.get(s);
value[0] = (byte) 'J';
```

Trường `coder` xác định các byte được diễn giải như thế nào. Nếu chuỗi là Latin-1 (coder=0) và bạn ghi một byte ngoài khoảng Latin-1 — chuỗi vẫn là Latin-1, nhưng dữ liệu trở nên hỏng.

### Hậu Quả Thực Tế

```java
String key = "password";
String cached = key; // Một tham chiếu khác đến cùng chuỗi

// Sửa đổi qua reflection
Field f = String.class.getDeclaredField("value");
f.setAccessible(true);
byte[] v = (byte[]) f.get(key);
v[0] = (byte) 'P';

System.out.println(key);    // "Password"
System.out.println(cached); // "Password" — cũng thay đổi!
```

### Bảng Các Lỗi Điển Hình

| Lỗi                        | Hậu quả                                                          | Giải pháp                                                   |
| ------------------------------ | ----------------------------------------------------------------------- | ------------------------------------------------------------ |
| Sửa đổi String trong String Pool| Tất cả các tham chiếu đến literal thấy giá trị đã thay đổi                          | Đừng sửa đổi literal; chỉ làm việc với `new String(...)`    |
| Sửa đổi trường hash           | `hashCode()` trả về giá trị cũ, `HashMap.get()` không tìm thấy key        | Đừng đụng vào trường `hash`; nếu giá trị thay đổi — reset hash    |
| Sửa đổi trong đa luồng  | Data race, hành vi không xác định                                         | String bất biến — đây là contract cho mọi thread    |
| Module system Java 9+          | `setAccessible(true)` ném `InaccessibleObjectException`            | `--add-opens java.base/java.lang=ALL-UNNAMED`              |

### So Sánh Các Cách Tiếp Cận

| Method                | Hoạt động?    | Nguy hiểm      | Java 8  | Java 9+     |
| --------------------- | --------- | ----------- | ------- | ----------- |
| Sửa đổi `value[]`      | Có       | Nghiêm trọng    | ✅       | ✅ (byte[])  |
| Sửa đổi `coder`        | Có       | Nghiêm trọng    | N/A     | ✅           |
| Sửa đổi `hash`         | Có       | Cao        | ✅       | ✅           |
| Tạo String mutable | Không        | N/A         | ❌       | ❌           |

### Khi Nào KHÔNG Nên Dùng Reflection Trên String
- **Code production** — không bao giờ
- **Thư viện** — không bao giờ (bạn sẽ phá vỡ code của người khác)
- **Các hệ thống đa luồng** — data race được đảm bảo
- **Code nhạy cảm về bảo mật** — bypass kiểm tra, injection
- **Kịch bản hợp lệ duy nhất:** unit test, mocking framework, deep serialization

## 🔴 Senior Level

### Hiện Thực Nội Bộ — Reflection Và AccessibleObject

**Cơ chế reflection trong JVM:**
```java
// Field.setAccessible(true) bên trong:
// 1. Kiểm tra quyền truy cập module (Java 9+)
// 2. Đặt cờ override trong AccessibleObject
// 3. Vô hiệu hóa các kiểm tra truy cập trên get/put qua JNI
```

**Module System Java 9+ (JEP 261):**
Với hệ thống module, quyền truy cập vào các trường nội bộ bị hạn chế:
```java
// Không có cờ JVM — ném InaccessibleObjectException
Field f = String.class.getDeclaredField("value");
f.setAccessible(true); // ❌ InaccessibleObjectException

// Yêu cầu cờ JVM:
// --add-opens java.base/java.lang=ALL-UNNAMED
```

**Các trường của String (Java 9+):**
```java
public final class String {
    @Stable
    private final byte[] value;  // bất biến sau khi construct
    private final byte coder;    // 0 = LATIN1, 1 = UTF16
    private int hash;            // lazy: 0 = chưa được tính
    // serialPersistentFields, caseInsensitiveComparator, ...
}
```

`@Stable` — annotation JVM (từ `jdk.internal.vm.annotation`) báo cho JIT compiler: trường được đặt một lần trong constructor và không bao giờ thay đổi. Điều này cho phép:
- **Constant folding:** JIT thay thế giá trị trực tiếp vào máy code
- **Cache trong register:** giá trị được cache trong register CPU
- **Escape analysis:** các tối ưu hóa dựa trên tính bất biến

**Sửa đổi trường `@Stable` phá vỡ các tối ưu hóa JIT:** code đã biên dịch có thể dùng giá trị cũ (đã cache).

### Các Trường Hợp Biên (Tối Thiểu 3)

**1. Làm ô nhiễm String Pool:**
```java
String s1 = "Hello"; // Literal → String Pool
String s2 = "Hello"; // Cùng tham chiếu từ pool

Field f = String.class.getDeclaredField("value");
f.setAccessible(true);
byte[] v = (byte[]) f.get(s1);
v[0] = (byte) 'J';

System.out.println(s2); // "Jello" — literal trong code giờ có nghĩa là "Jello"!
// Bất kỳ code mới nào String s = "Hello" có thể nhận object đã sửa đổi
// Hành vi JVM được định nghĩa — literal trong pool bị sửa đổi. Nhưng code đã biên dịch JIT mà
// đã constant-fold giá trị gốc có thể thấy kết quả không nhất quán.
```

**2. Hỏng key HashMap:**
```java
String key = "key";
Map<String, String> map = new HashMap<>();
map.put(key, "value");

// Sửa đổi key qua reflection
Field f = String.class.getDeclaredField("value");
f.setAccessible(true);
byte[] v = (byte[]) f.get(key);
v[0] = (byte) 'K'; // "Key"

// Trường hash vẫn chứa hash của "key"
map.get("Key");  // null — hash không khớp
map.get("key");  // null — chuỗi đó không còn tồn tại (giá trị đã thay đổi)
// HashMap bị hỏng!
```

**3. Không khớp coder — ghi byte UTF-16 vào chuỗi Latin-1:**
```java
String s = "Hello"; // coder = LATIN1
Field vf = String.class.getDeclaredField("value");
Field cf = String.class.getDeclaredField("coder");
vf.setAccessible(true);
cf.setAccessible(true);

byte[] v = (byte[]) vf.get(s);
v[0] = (byte) 0xD0; // Byte Cyrillic vào chuỗi Latin-1!

// s.charAt(0) trả về (char) 0xD0 = 208 (ký tự không hợp lệ)
// s.getBytes(UTF_8) trả về byte hỏng
// equals() có thể hoạt động không thể đoán trước
```

**4. Sửa đổi đồng thời — data race:**
```java
// Thread A đọc chuỗi
char c = s.charAt(0);

// Thread B đồng thời thay đổi value[] qua reflection
v[0] = (byte) 'X';

// Thread A: giá trị c có thể là cũ hoặc mới — data race
// happens-before bị phá vỡ: không có synchronization cho các trường final
// bị sửa đổi qua reflection
```

**5. Security Manager Và Reflection (Java 17+):**
Trong Java 17+, `SecurityManager` bị deprecated, và quyền truy cập module nghiêm ngặt theo mặc định.
Ngay cả với `--add-opens`, một số trường nội bộ JVM có thể được bảo vệ ở cấp độ native code.

### Hiệu Năng

| Thao tác                        | Thời gian      | Ghi chú                                              |
| -------------------------------- | --------- | ------------------------------------------------- |
| `setAccessible(true)`            | ~50–200ns | Một lần, nhưng với kiểm tra module đắt hơn    |
| `Field.get()`                    | ~20–50ns  | Overhead lời gọi JNI                                 |
| `Field.set()` trên trường final     | ~20–50ns  | Nhưng phá vỡ các tối ưu hóa JIT                      |
| `String.hashCode()` sau khi mutate| Sai| Trường hash không được tính lại                    |
| JIT deoptimization               | ~1–10μs   | Nếu JIT đã biên dịch code với String đã constant-fold  |

**JIT deoptimization:** Nếu JIT đã biên dịch một method dùng chuỗi này (ví dụ, qua constant folding `"Hello"` → inline), thì việc thay đổi giá trị gây ra **deoptimization** — JVM loại bỏ code đã biên dịch và diễn giải lại. Điều này tốn 1–10μs và có thể xảy ra lặp lại.

### Thread Safety

**String không thread-safe sau khi mutate qua reflection.** Contract bất biến bị phá vỡ:
- Không có `volatile` trên `value[]` — các thread khác có thể không thấy thay đổi (hoặc thấy nó một phần)
- Không có memory barrier — happens-before không được thiết lập
- Annotation `@Stable` cho phép JIT cache giá trị trong register — thread có thể không bao giờ thấy thay đổi

### Câu Chuyện Thực Tế Trong Production

**Kịch bản:** Framework testing (PowerMock/Mockito) dùng reflection để mock String trong unit test.

```java
// Test thay đổi hằng số chuỗi
Field f = String.class.getDeclaredField("value");
f.setAccessible(true);
byte[] v = (byte[]) f.get("CONSTANT");
// ... sửa đổi giá trị
```

Vấn đề: các test pass riêng lẻ, nhưng **khi chạy song song** (Maven Surefire, forkCount > 1), một test thay đổi chuỗi trong String Pool, và test khác thất bại với `AssertionError`. String Pool được chia sẻ giữa tất cả các test trong cùng một JVM.

**Sửa lỗi:** Cô lập test trong các JVM riêng biệt (`forkMode=always`) hoặc tránh mock các object bất biến.

**Kịch bản 2:** Thư viện deep serialization (Kryo) tối ưu hóa serialization String bằng cách sửa đổi trực tiếp `value[]` nội bộ. Sau khi migration sang Java 17 với `--add-opens` chưa được cấu hình → `InaccessibleObjectException` trong production. Sửa lỗi: chuyển sang serialization tiêu chuẩn.

### Giám Sát

```bash
# Kiểm tra quyền truy cập module
java --add-opens java.base/java.lang=ALL-UNNAMED -jar app.jar

# JFR — các sự kiện truy cập reflection
java -XX:StartFlightRecording=filename=recording.jfr ...
# Trong JDK Flight Recorder: không có event đặc biệt cho reflection,
# nhưng có thể bắt qua các custom event

# Log GC — nếu mutation gây rò rỉ bộ nhớ
java -Xlog:gc*:file=gc.log ...

# jcmd — kiểm tra các cờ
jcmd <pid> VM.flags | grep add-opens
```

```java
// Phát hiện truy cập reflection tại thời điểm chạy
// (Java 9+: có thể đặt ReflectionFilter tùy chỉnh)
// Hoặc qua java.lang.instrument — chặn Field.setAccessible()

// Kiểm tra khả năng truy cập trường
try {
    Field f = String.class.getDeclaredField("value");
    f.setAccessible(true);
    System.out.println("Accessible: " + f.canAccess(""));
} catch (InaccessibleObjectException e) {
    System.out.println("Blocked by module system");
}
```

### Best Practices Cho Highload

- **Không bao giờ** sửa đổi String qua reflection trong code production
- Cho **unit test**: dùng các JVM cô lập hoặc tránh mock các object bất biến
- Cho **serialization**: dùng các cơ chế tiêu chuẩn (Serializable, JSON, Protobuf)
- Nếu thực sự cần thiết (phát triển framework):
  - Chỉ dùng `--add-opens` cho các module cần thiết
  - Đừng sửa đổi các literal từ String Pool
  - Reset trường `hash` sau khi sửa đổi `value[]`
  - Ghi tài liệu về yêu cầu này cho tất cả người dùng framework
- Cho các ứng dụng **nhạy cảm về bảo mật**: đặt Security Manager (đến Java 17) hoặc dùng các cờ JVM để chặn reflection
- **Thay thế:** `MethodHandles.privateLookupIn()` (Java 9+) — truy cập trường có kiểm soát hơn
- Cho **các chuỗi mutable**: dùng `char[]`, `byte[]`, `StringBuilder`, hoặc `ByteBuffer` — chúng được thiết kế cho việc này

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Về mặt kỹ thuật có thể sửa đổi `byte[] value` qua reflection, nhưng cực kỳ nguy hiểm
- Java 9+: module system chặn `setAccessible(true)` mà không có `--add-opens java.base/java.lang=ALL-UNNAMED`
- Annotation `@Stable` trên `value` — JIT dùng constant folding, việc sửa đổi phá vỡ các tối ưu hóa
- Sửa đổi một literal trong String Pool ảnh hưởng đến TẤT CẢ các tham chiếu đến literal đó trong toàn bộ ứng dụng
- Hỏng key HashMap: sửa đổi key qua reflection → `hashCode()` trả về giá trị cũ → `get()` không tìm thấy
- Kịch bản hợp lệ duy nhất: unit test, mocking framework, deep serialization

**Các câu hỏi phụ thường gặp:**
- **Điều gì xảy ra khi sửa đổi một literal qua reflection?** — Tất cả các tham chiếu đến literal đó thấy giá trị đã thay đổi. `String s = "Hello"` có thể trở thành `"Jello"`.
- **Tại sao annotation `@Stable` quan trọng?** — JIT cache giá trị trong register, thực hiện constant folding. Việc sửa đổi gây ra deoptimization (~1-10μs).
- **Module system (Java 9+) bảo vệ khỏi reflection như thế nào?** — `setAccessible(true)` ném `InaccessibleObjectException` mà không có cờ `--add-opens`.
- **Điều gì xảy ra với HashMap khi key bị sửa đổi?** — Trường hash không được tính lại, `get()` không tìm thấy key, HashMap bị hỏng.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "Reflection trên String — thực hành bình thường" — đây là một antipattern, vi phạm contract bất biến
- ❌ "Bạn có thể sửa đổi một chuỗi mà không có hậu quả" — phá vỡ String Pool, HashMap, các tối ưu hóa JIT
- ❌ "`setAccessible()` luôn hoạt động" — bị chặn bởi module system trong Java 9+
- ❌ "Điều này thread-safe nếu sửa đổi trong một thread" — `@Stable` cho phép JIT cache, các thread khác có thể thấy giá trị cũ
