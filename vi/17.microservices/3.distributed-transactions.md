# How to implement distributed transactions in microservices (Cách triển khai distributed transaction trong microservices)

## Junior Level

Trong microservices **không có một database duy nhất**, vì vậy các transaction thông thường (ACID) không hoạt động.

**Hai cách tiếp cận:**

1. **Saga** — một chuỗi các local transaction với compensation
2. **Two-Phase Commit (2PC)** — các giao thức distributed transaction (hiếm khi dùng)

**Saga phổ biến hơn 2PC vì nó không khóa tài nguyên trong suốt toàn bộ transaction
và làm việc với các database không đồng nhất, trong khi 2PC yêu cầu hỗ trợ
two-phase commit từ tất cả các bên tham gia.**
```
Đơn hàng sản phẩm:
1. Order Service: tạo đơn hàng (local transaction)
2. Payment Service: tính phí (local transaction)
3. Inventory Service: giữ chỗ sản phẩm (local transaction)

Nếu bước 2 thất bại -> hủy đơn hàng (compensation)
```

**Mục tiêu:** Eventual consistency — dữ liệu nhất quán, nhưng không phải ngay lập tức.

### Khi Nào KHÔNG Nên Triển Khai Distributed Transaction

Nếu bạn có thể thiết kế lại sao cho một service sở hữu toàn bộ dữ liệu —
hãy tránh hoàn toàn distributed transaction. Đây là giải pháp đáng tin cậy nhất.

## Middle Level

### Triển Khai Saga

**1. Choreography (dựa trên event):**
```java
// Order Service
@Transactional
public void createOrder(Order order) {
    orderRepository.save(order);
    eventPublisher.publish(new OrderCreatedEvent(order.getId()));
}

// Payment Service
@EventListener
public void onOrderCreated(OrderCreatedEvent event) {
    try {
        paymentService.charge(event.orderId());
        eventPublisher.publish(new PaymentCompletedEvent(event.orderId()));
    } catch (Exception e) {
        eventPublisher.publish(new PaymentFailedEvent(event.orderId(), e));
    }
}

// Order Service — compensation
@EventListener
public void onPaymentFailed(PaymentFailedEvent event) {
    orderService.cancelOrder(event.orderId());
    eventPublisher.publish(new OrderCancelledEvent(event.orderId()));
}
```

**2. Orchestration (coordinator):**
```java
@Component
public class OrderOrchestrator {
    public void processOrder(Order order) {
        try {
            orderService.create(order);
            paymentService.charge(order);
            inventoryService.reserve(order);
        } catch (PaymentException e) {
            orderService.cancel(order);
            throw e;
        } catch (InventoryException e) {
            paymentService.refund(order);
            orderService.cancel(order);
            throw e;
        }
    }
}
```

### Các Lỗi Thường Gặp

1. **Thiếu idempotency:**
```
Event được gửi hai lần -> thanh toán sẽ bị tính phí hai lần!
Giải pháp: kiểm tra orderID trước khi xử lý
```

2. **Mất event:**
```
Event publisher crash -> event không được gửi
Giải pháp: pattern transactional outbox
```

## Senior Level

### Transactional Outbox Pattern

Outbox — một table đặc biệt trong cùng database nơi, trong cùng transaction với dữ liệu nghiệp vụ,
một event được ghi. CDC (Change Data Capture, Debezium) đọc log database và gửi
event đến Kafka.

```java
// Vấn đề: làm sao đảm bảo việc gửi event?
// Giải pháp: table Outbox trong cùng transaction

@Transactional
public void createOrder(Order order) {
    orderRepository.save(order);
    outboxRepository.save(new OutboxEvent(
        "OrderCreated", order.getId(), payload
    ));
    // Cả hai được lưu trong cùng một transaction!
}

// CDC (Change Data Capture) hoặc polling đọc outbox
// và publish đến Kafka
@Component
public class OutboxPublisher {
    @Scheduled(fixedDelay = 1000)
    public void publishPending() {
        List<OutboxEvent> events = outboxRepository.findPending();
        for (OutboxEvent event : events) {
            kafkaTemplate.send(event.getTopic(), event.getPayload());
            outboxRepository.markPublished(event.getId());
        }
    }
}
```

### Đánh Đổi Kiến Trúc

| Cách tiếp cận | Ưu điểm                     | Nhược điểm                 |
| ------------ | --------------------------- | ------------------------- |
| **Saga**     | Linh hoạt, mở rộng được       | Compensation phức tạp      |
| **2PC**      | Nhất quán nghiêm ngặt          | Khóa, chậm                 |
| **Eventual** | Đơn giản                      | Không có đảm bảo           |

### Edge Cases

**1. Các Saga đồng thời:**
```
Saga1: Order A -> giữ chỗ inventory item1
Saga2: Order B -> giữ chỗ inventory item1
Cạnh tranh -> một trong hai order sẽ thất bại
Giải pháp: optimistic/pessimistic locking
```

**2. Saga timeout:**
```java
// Ví dụ minh họa (Axon Framework). API thực tế phụ thuộc vào thư viện.
// Bảo vệ khỏi các Saga bị "treo"
@SagaConfiguration
public class OrderSagaConfig {
    @Bean
    public SagaConfiguration<OrderSaga> orderSaga() {
        return SagaConfiguration.sagaManagedBy(OrderSaga.class)
            .sagaTimeout(Duration.ofMinutes(5));
    }
}
```

### Kinh Nghiệm Production

**Debezium CDC + Kafka:**
```
Database -> Debezium -> Kafka -> Event Consumer

Table Outbox -> Debezium CDC -> Kafka topic -> Saga handler

Điều này đảm bảo:
- Gửi at-least-once
- Thứ tự event
- Phục hồi sau thất bại
```

### Best Practices

```
✅ Dùng Transactional Outbox
✅ Triển khai idempotency ở mỗi bước
✅ Thêm Saga timeout
✅ Ghi log mỗi bước
✅ Giám sát thời lượng Saga

❌ Đừng dùng 2PC trừ khi cần thiết
❌ Đừng bỏ qua các Saga đồng thời
❌ Đừng quên các compensation
```

## Interview Cheat Sheet

**Cần phải biết:**
- Hai cách tiếp cận chính: Saga và Two-Phase Commit (2PC)
- Saga phổ biến hơn: không khóa tài nguyên, làm việc với các database khác nhau
- Transactional Outbox đảm bảo việc gửi event (ghi trong cùng transaction với dữ liệu nghiệp vụ)
- CDC (Debezium) đọc outbox và publish đến Kafka
- Idempotency bắt buộc ở mỗi bước
- Các Saga đồng thời cần cơ chế locking
- Saga timeout bảo vệ khỏi các transaction bị treo
- Cách tiếp cận tốt nhất — tránh distributed transaction thông qua thiết kế lại

**Các câu hỏi phụ thường gặp:**
- **Tại sao Saga tốt hơn 2PC?** 2PC khóa tài nguyên trong suốt toàn bộ transaction và yêu cầu hỗ trợ từ tất cả các bên tham gia. Saga bất đồng bộ và linh hoạt.
- **Cách đảm bảo việc gửi event?** Transactional Outbox + CDC — ghi event trong cùng transaction với dữ liệu nghiệp vụ.
- **Eventual consistency là gì?** Dữ liệu sẽ trở nên nhất quán theo thời gian, nhưng không phải ngay lập tức.
- **Cách xử lý các Saga đồng thời?** Optimistic/pessimistic locking ở cấp độ tài nguyên.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "2PC là giải pháp tốt nhất cho microservices" — không, quá chậm và gây khóa
- "Không cần Outbox, Kafka đảm bảo việc gửi" — Kafka đảm bảo việc gửi, nhưng không đảm bảo tính atomic với database
- "Eventual consistency = dữ liệu có thể sai" — không, nó sẽ trở nên đúng
- "Không cần distributed transaction, mọi thứ có thể ở trong một service" — không phải lúc nào cũng khả thi
