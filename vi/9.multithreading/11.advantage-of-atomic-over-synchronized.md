# What is the advantage of Atomic classes over synchronized? (Ưu điểm của các lớp Atomic so với synchronized là gì?)

---

## Junior Level

### Hiểu biết cơ bản

Các lớp Atomic và `synchronized` là hai cách tiếp cận khác nhau đối với thread safety:

| Cách tiếp cận    | Nguyên lý                                                    | Ví dụ minh họa                                            |
| ---------------- | ---------------------------------------------------------- | --------------------------------------------------------- |
| **synchronized** | Bi quan: "Tranh chấp sẽ xảy ra — tôi khóa ngay lập tức"    | Một người vào phòng, những người khác xếp hàng chờ         |
| **Atomic**       | Lạc quan: "Tranh chấp khó xảy ra — tôi thử nhanh"           | Mọi người cùng thử vào một lúc, ai thành công — được cập nhật |

### Ví dụ đơn giản

```java
// synchronized — người bi quan
public class SynchronizedCounter {
    private int count = 0;

    public synchronized void increment() {
        count++; // Chỉ một thread tại một thời điểm, các thread khác chờ
    }
}

// Atomic — người lạc quan
public class AtomicCounter {
    private AtomicInteger count = new AtomicInteger(0);

    public void increment() {
        count.incrementAndGet(); // Thử CAS nhanh, nếu thất bại — thử lại
    }
}
```

### Khi nào dùng cái nào

| Tình huống                  | Lựa chọn      | Tại sao                                                                    |
| --------------------------- | ------------- | --------------------------------------------------------------------------- |
| Bộ đếm đơn giản             | Atomic        | Nhanh hơn (CAS ~5ns vs synchronized ~1000ns — không context switch), không deadlock |
| Thao tác gộp                | synchronized  | Cần khóa nhiều field                                                       |
| Cờ                          | AtomicBoolean | Nhẹ hơn synchronized                                                       |
| Cập nhật nhiều field        | synchronized  | Atomic chỉ làm việc trên một field                                         |

## Middle Level

### Tại sao Atomic nhanh hơn?

#### 1. Không có Context Switch

```
synchronized (khi tranh chấp):
  Thread → BLOCKED → OS park → Context Switch → ~1000-5000 ns

Atomic (CAS):
  Thread → RUNNABLE → thử CAS → ~5-10 ns (không context switch)
```

Với `synchronized`, thread chuyển sang trạng thái BLOCKED, thứ cần gọi vào kernel của OS và context switching — hàng nghìn chu kỳ CPU.

Atomic dùng **Spin-waiting**: thread không ngủ, mà thử lại CAS trong một vòng lặp. Cách này nhanh hơn vì nó không chuyển quyền điều khiển cho hệ điều hành (không context switch).

#### 2. Đảm bảo tiến triển (Progress Guarantee)

| Vấn đề                 | synchronized        | Atomic                                                                                                              |
| ---------------------- | ------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **Deadlock**           | Có thể              | **Không thể** (với các thao tác Atomic riêng lẻ; nhưng business logic dựa trên nhiều Atomic vẫn có thể treo)        |
| **Priority Inversion** | Có thể              | Không thể                                                                                                          |
| **Quên unlock**        | Không áp dụng (tự động) | Không áp dụng                                                                                                  |

```java
// synchronized — deadlock có thể xảy ra
synchronized(lockA) {
    synchronized(lockB) { // Nếu một thread khác làm ngược lại → deadlock
        // ...
    }
}

// Atomic — deadlock không thể xảy ra
counter1.incrementAndGet(); // Luôn hoàn thành
counter2.incrementAndGet(); // Luôn hoàn thành
```

### Chu kỳ CAS hoạt động như thế nào

```java
// Hiện thực incrementAndGet đơn giản hóa
public final int incrementAndGet() {
    for (;;) {                    // Chu kỳ spin
        int current = get();      // 1. Đọc giá trị volatile
        int next = current + 1;   // 2. Tính giá trị mới
        if (compareAndSet(current, next)) { // 3. CAS
            return next;          // Thành công!
        }
        // CAS thất bại — ai đó khác đã cập nhật
        // Sang vòng lặp tiếp theo (không bị chặn!)
    }
}
```

### Khi nào Atomic TỆ HƠN synchronized?

#### 1. Tranh chấp cao

```
100 thread đồng thời làm incrementAndGet():
  - CAS liên tục thất bại
  - Các thread spin trong các chu kỳ, đốt CPU ở 100%
  - Gần như không có tiến triển

Trong trường hợp này synchronized có thể hiệu quả hơn:
  - Các thread xếp hàng
  - CPU không bị lãng phí cho các chu kỳ rỗng
```

#### 2. Các thao tác gộp

```java
// Atomic không giúp cập nhật atomic x và y
AtomicInteger x = new AtomicInteger(0);
AtomicInteger y = new AtomicInteger(0);

// KHÔNG an toàn!
void swap() {
    int temp = x.get();
    x.set(y.get()); // Một thread khác có thể thấy trạng thái trung gian
    y.set(temp);
}

// synchronized — an toàn
synchronized(lock) {
    int temp = x;
    x = y;
    y = temp;
}
```

#### 3. Các thao tác dài

```java
// XẤU: thao tác dài trong chu kỳ CAS
atomicRef.updateAndGet(current -> {
    // Phép tính dài — CPU sẽ đốt khi tranh chấp!
    return expensiveTransformation(current);
});

// TỐT: thao tác dài trong synchronized
synchronized(lock) {
    ref = expensiveTransformation(ref); // Các thread khác chờ, CPU không đốt
}
```

## Senior Level

### Bên trong: Bus Contention

Ngay cả khi CAS thành công, nó vẫn sinh ra traffic trên data bus:

```
Thread trên Core 1 làm CAS:
  1. lock cmpxchg [memory], new_value
  2. Khóa memory bus
  3. Invalidate các cache line trên mọi core khác
  4. Chờ Ack từ mọi core
  5. Mở khóa bus
```

Nhiều biến Atomic có thể "làm nghẽn" memory bus của server.

### Lock-free vs Wait-free vs Obstruction-free

| Thuật ngữ            | Đảm bảo                                        | Ví dụ           |
| -------------------- | --------------------------------------------- | --------------- |
| **Lock-free**        | Ít nhất một thread hoàn thành trong thời gian hữu hạn | AtomicInteger   |
| **Wait-free**        | Mọi thread hoàn thành trong số bước hữu hạn    | LongAdder.add() |
| **Obstruction-free** | Thread hoàn thành nếu các thread khác không xen vào | Một số STM      |

`synchronized` — không thuộc loại nào ở trên (blocking):
- Thread có thể bị chặn vô thời hạn (deadlock, starvation)

### Hiệu năng: Điểm hòa vốn (Break-Even Point)

```
Số thread    | Atomic (ns/op) | synchronized (ns/op)
───────────────────────────────────────────────────────
1            | 5              | 10
2            | 10             | 15
4            | 20             | 20
8            | 50             | 25
16           | 200            | 30
32           | 1000+          | 40
64           | Spin!          | 50
```

Các con số là xấp xỉ, phụ thuộc CPU/JVM. Hãy đo trên phần cứng của bạn qua JMH.

**Điểm hòa vốn:** ~4-8 thread cho các thao tác đơn giản. Sau đó, `synchronized` trở nên nhanh hơn.

### LongAdder như một sự tiến hóa của ý tưởng Atomic

```java
// Vấn đề: AtomicInteger ở 100 thread → CAS contention
AtomicInteger counter = new AtomicInteger(0);

// Giải pháp: LongAdder phân tán qua các cell
LongAdder counter = new LongAdder();
counter.increment(); // Mỗi thread vào cell riêng của nó
long total = counter.sum(); // Cộng tất cả các cell
```

LongAdder bên trong:
```java
// Giá trị base + mảng cell
volatile long base;
volatile Cell[] cells; // Mỗi thread hash vào cell riêng của nó

// @Contended padding — tránh False Sharing
static final class Cell {
    @Contended
    volatile long value;
}
```

### Chẩn đoán

#### Thread Dump

```bash
jstack <pid>
```

```
# Nếu synchronized chậm — ta thấy các thread BLOCKED
"worker-1" BLOCKED (on object monitor)
  - waiting to lock <0x000...>

# Nếu Atomic chậm — không có BLOCKED, các thread ở RUNNABLE
"worker-1" RUNNABLE
  at AtomicInteger.compareAndSet(...)
  // Thread spin trong chu kỳ CAS
```

#### `-XX:+PrintAssembly`

```assembly
# synchronized → các lời gọi OS nặng
call runtime_monitor_enter

# Atomic → một lệnh duy nhất
lock cmpxchg dword ptr [rax], rcx
```

### Best Practices

1. **Atomic cho các thao tác đơn giản** khi tranh chấp thấp/vừa
2. **synchronized cho các thao tác gộp** hoặc khi tranh chấp cao
3. **LongAdder cho các bộ đếm** khi tải cực lớn
4. **Tránh Atomic cho các phép tính dài** — chu kỳ CAS sẽ đốt CPU
5. **Giám sát**: không có BLOCKED trong dump, nhưng hệ thống chậm → tìm Atomic đang nóng
6. **Back-off**: `Thread.onSpinWait()` như một gợi ý CPU khi CAS retry

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Atomic = cách tiếp cận lạc quan (thử nhanh, thử lại khi xung đột), synchronized = bi quan (khóa ngay lập tức)
- Atomic dùng chu kỳ CAS (spin-waiting): thread không ngủ, thử lại — không context switch
- synchronized chuyển thread sang BLOCKED (~1000-5000 ns), Atomic ở lại RUNNABLE (~5-10 ns)
- Điểm hòa vốn: ~4-8 thread cho các thao tác đơn giản — sau đó synchronized có thể trở nên nhanh hơn
- Atomic đảm bảo tiến triển lock-free (ít nhất một thread hoàn thành), synchronized có thể deadlock
- Atomic KHÔNG giúp với các thao tác gộp (cập nhật 2+ field) — cần synchronized ở đó
- Khi tranh chấp cao, CAS liên tục thất bại, các thread đốt CPU ở 100% — LongAdder hoặc synchronized tốt hơn
- LongAdder tiến hóa ý tưởng Atomic: phân tán việc đếm qua các cell (per-thread), cộng khi đọc

**Các câu hỏi phụ thường gặp:**
- **Tại sao Atomic nhanh hơn khi tranh chấp thấp?** — Không có context switch hay lời gọi OS, một lệnh lock cmpxchg
- **Lock-free vs wait-free là gì?** — Lock-free: ít nhất một thread hoàn thành; wait-free: mọi thread hoàn thành trong số bước hữu hạn (LongAdder.add)
- **Điều gì xảy ra ở mức CPU trong lúc CAS?** — Khóa memory bus → invalidate các cache line trên mọi core → chờ Ack → mở khóa
- **Khi nào synchronized tốt hơn Atomic?** — Tranh chấp cao (8+ thread), các thao tác gộp, các phép tính dài

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Atomic luôn nhanh hơn synchronized" — không, điểm hòa vốn là ~4-8 thread
- "Atomic dùng khóa" — không, nó là một chu kỳ CAS lock-free
- "Deadlock không thể xảy ra trong bất kỳ code nào có Atomic" — các thao tác Atomic riêng lẻ an toàn, nhưng business logic qua nhiều Atomic vẫn có thể treo
