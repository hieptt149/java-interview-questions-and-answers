# How to Specify Your Own Executor for CompletableFuture? (Cách chỉ định Executor riêng cho CompletableFuture)

## 🟢 Junior Level

Tất cả các phương thức `*Async` đều có một phiên bản nạp chồng (overload) chấp nhận một `Executor`:

```java
ExecutorService executor = Executors.newFixedThreadPool(10);

CompletableFuture<String> cf = CompletableFuture.supplyAsync(() -> {
    return fetchData();
}, executor);  // Executor tùy chỉnh

cf.thenApplyAsync(s -> transform(s), executor);  // cũng dùng Executor tùy chỉnh
```

**Tại sao:**
- Kiểm soát số lượng thread
- Cách ly khỏi các tác vụ khác
- Khả năng giám sát

---

## 🟡 Middle Level

### Chiến Lược Chọn Pool

**I/O-Bound (HTTP, DB, File):**
```java
Executor ioExecutor = new ThreadPoolExecutor(
    10, 100, 60L, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(1000),  // Hàng đợi có giới hạn là bắt buộc!
    new ThreadFactoryBuilder().setNameFormat("io-pool-%d").build(),
    new ThreadPoolExecutor.CallerRunsPolicy()  // Backpressure
);
```

**CPU-Bound (Tính toán, Mapping):**
```java
Executor cpuExecutor = Executors.newFixedThreadPool(
    Runtime.getRuntime().availableProcessors()
);
```

**Virtual Threads (Java 21+):**
```java
Executor vtExecutor = Executors.newVirtualThreadPerTaskExecutor();
CompletableFuture.supplyAsync(task, vtExecutor);
```

### Cái Bẫy Của Việc Truyền Executor

`Executor` phải được truyền ở **mỗi** giai đoạn bất đồng bộ:

```java
// ❌ Xấu: chỉ giai đoạn đầu tiên ở pool riêng, phần còn lại — trong commonPool
CF.supplyAsync(task, myExecutor)
  .thenApplyAsync(transform);  // commonPool!

// ✅ Tốt: duy trì sự cách ly
CF.supplyAsync(task, myExecutor)
  .thenApplyAsync(transform, myExecutor);
```

### Quản Lý Vòng Đời

```java
@PreDestroy
public void shutdown() {
    ((ExecutorService) executor).shutdown();
}
```

Không có `shutdown()` — các "thread zombie" ngăn cản việc kết thúc tiến trình đúng cách.

## 🔴 Senior Level

### Triển Khai Nội Bộ

**CallerRunsPolicy như Backpressure:**
```
Khi hàng đợi đầy → tác vụ chạy trong thread gọi.
Điều này tự nhiên làm chậm bên tạo ra request.
```

**Đặt Tên Thread:**
Luôn dùng `ThreadFactory` (Guava, Spring) để đặt tên cho các thread. Không có điều này, việc phân tích heap dump trong các sự cố trở nên bất khả thi.

### Kỹ Thuật Nâng Cao: ManagedBlocker

Nếu bạn dùng `ForkJoinPool` (bao gồm cả `commonPool`) cho các tác vụ có thể chặn, bạn có thể dùng interface **`ManagedBlocker`**.
- **Bên dưới**: Điều này cho phép pool tạo động một thread mới để bù đắp cho thread bị chặn, duy trì mức độ parallelism. Việc triển khai này phức tạp hơn một `FixedThreadPool` đơn giản, nhưng hiệu quả hơn nhiều.

```java
// Ví dụ triển khai ManagedBlocker cho các thao tác chặn:
class BlockingAdapter<T> implements ForkJoinPool.ManagedBlocker {
    private T result;
    private final Supplier<T> task;
    private boolean isDone = false;

    public boolean block() {
        result = task.get();  // thao tác chặn
        isDone = true;
        return true;
    }
    public boolean isReleasable() { return isDone; }
    public T getResult() { return result; }
}
```

### Đánh Đổi Kiến Trúc

| Cách tiếp cận             | Ưu điểm                      | Nhược điểm                    |
| -------------------- | ------------------------- | ----------------------- |
| **FixedThreadPool**  | Kích thước dự đoán được          | Không có work-stealing        |
| **CachedThreadPool** | Tự động mở rộng              | Thread không giới hạn       |
| **Virtual Threads**  | Lý tưởng cho I/O             | Chỉ Java 21+           |
| **ManagedBlocker**   | Bù đắp việc chặn     | Triển khai phức tạp  |

### Edge Cases

- **Spring @Async**: Nếu bạn dùng `CompletableFuture` cùng với `@Async`, Spring có thể inject `TaskExecutor` riêng của nó. Hãy đảm bảo bạn kiểm soát cấu hình của nó.

### Khi Nào KHÔNG Nên Dùng Executor Tùy Chỉnh

- **Tác vụ CPU-bound** — ForkJoinPool.commonPool() là tối ưu (work-stealing)
- **Ít tác vụ** — overhead tạo pool > lợi ích

### Best Practices

```java
// ✅ Luôn dùng Executor riêng cho production
CompletableFuture.supplyAsync(task, ioExecutor);

// ✅ CallerRunsPolicy cho backpressure
new ThreadPoolExecutor.CallerRunsPolicy();

// ✅ Đặt tên thread để chẩn đoán
new ThreadFactoryBuilder().setNameFormat("pool-%d").build();

// ✅ Virtual Threads cho I/O (Java 21+)
Executors.newVirtualThreadPerTaskExecutor();

// ❌ Không có shutdown() khi thoát
// ❌ commonPool cho I/O
// ❌ Hàng đợi không giới hạn
```

### Tóm Tắt Cho Senior
- Truyền một `Executor` là chuẩn mực cho Production.
- Tách các workload I/O và CPU vào các pool khác nhau.
- Dùng `CallerRunsPolicy` để bảo vệ khỏi quá tải.
- Trên Java 21, di chuyển sang `VirtualThreadPerTaskExecutor` cho các tác vụ I/O.

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- Tất cả các phương thức *Async đều có phiên bản nạp chồng với Executor
- I/O-Bound: ThreadPoolExecutor(core=10, max=100, CallerRunsPolicy)
- CPU-Bound: FixedThreadPool(availableProcessors)
- Virtual Threads (Java 21+): Executors.newVirtualThreadPerTaskExecutor() — lý tưởng cho I/O
- Executor phải được truyền ở MỖI giai đoạn bất đồng bộ của chuỗi

**Các câu hỏi phụ thường gặp:**
- **Tại sao CallerRunsPolicy?** — Backpressure: khi hàng đợi tràn, tác vụ chạy trong thread gọi, làm chậm bên tạo request
- **Tại sao ThreadFactory với tên?** — Chẩn đoán: không có tên thread, việc phân tích jstack bất khả thi
- **Điều gì xảy ra nếu không truyền Executor cho thenApplyAsync?** — commonPool được dùng — mất tính cách ly
- **Tại sao dùng ManagedBlocker?** — Bù đắp việc chặn trong ForkJoinPool: pool tạo một thread bổ sung thay cho thread bị chặn

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "CachedThreadPool cho production" — thread không giới hạn → OOM
- "Executor chỉ cần ở giai đoạn đầu tiên" — mỗi *Async không có Executor sẽ đi vào commonPool
- "Không có shutdown() cũng ổn" — thread zombie ngăn cản việc kết thúc tiến trình
