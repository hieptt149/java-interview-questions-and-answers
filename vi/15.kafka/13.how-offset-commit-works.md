# How does offset commit work (Commit offset hoạt động như thế nào)

## Junior Level

### Định Nghĩa

**Commit offset** là việc lưu lại số của message **đã xử lý** cuối cùng trong Kafka.

**Nó được lưu ở đâu:** vào một topic Kafka nội bộ đặc biệt (`__consumer_offsets`). Khi restart, consumer đọc vị trí cuối cùng của nó từ đó và tiếp tục từ đó. Không có commit — nó bắt đầu từ đầu.

```java
// Commit tự động
props.put("enable.auto.commit", "true");
props.put("auto.commit.interval.ms", "5000");  // mỗi 5 giây

// Commit thủ công
props.put("enable.auto.commit", "false");
consumer.commitSync();  // sau khi xử lý
```

### Tại Sao Cần Commit?

```
Không có commit:
  Consumer crash → khi restart đọc lại mọi thứ từ đầu
  → Trùng lặp, lãng phí xử lý

Có commit:
  Consumer crash → khi restart tiếp tục từ commit cuối cùng
  → Trùng lặp tối thiểu
```

### Ví Dụ

```java
while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (var record : records) {
        process(record);  // xử lý
    }
    consumer.commitSync();  // commit sau khi xử lý
}
```

## Middle Level

### Sync vs Async Commit

**Sync Commit:**
```java
// Chờ xác nhận của broker
consumer.commitSync();
// Sync commit: độ trễ 5-50ms mỗi commit. Ở 100 commit/giây — overhead 500-5000ms.
// Async commit: <5ms (không chặn).
// Khi lỗi — ném exception
```

**Async Commit:**
```java
// Không chờ xác nhận
consumer.commitAsync((offsets, exception) -> {
    if (exception != null) {
        log.error("Commit failed", exception);
    }
});
// Nhanh hơn, nhưng có thể mất khi lỗi
```

### Khi Nào Dùng Cái Nào?

| Loại commit   | Khi nào dùng                                  |
| ------------- | -------------------------------------------- |
| commitSync()  | Dữ liệu quan trọng, throughput thấp                |
| commitAsync() | Throughput cao, chấp nhận trùng lặp hiếm  |
| auto.commit   | Prototype, không dùng cho production                   |

### Batch Commit

```java
// Commit mỗi N message
int count = 0;
for (var record : records) {
    process(record);
    if (++count % 100 == 0) {
        consumer.commitAsync();
    }
}
```

### Các Offset Có Thể Commit

```java
// Commit các offset cụ thể
Map<TopicPartition, OffsetAndMetadata> offsets = new HashMap<>();
offsets.put(new TopicPartition("orders", 0), new OffsetAndMetadata(1000));
offsets.put(new TopicPartition("orders", 1), new OffsetAndMetadata(2000));
consumer.commitSync(offsets);
```

### Các Lỗi Thường Gặp

1. **Commit trước khi xử lý:**
```java
consumer.commitSync();  // ❌ commit trước
process(records);       // sau đó xử lý
// Nếu crash → mất dữ liệu
```

2. **Commit trong vòng lặp xử lý:**
```java
for (var record : records) {
    process(record);
    consumer.commitSync();  // ❌ quá thường xuyên
}
```

## Senior Level

### Cài Đặt Nội Bộ

**Quá Trình Commit:**
```
1. Consumer → request CommitOffset → Broker
2. Broker → ghi vào topic __consumer_offsets
3. Broker → xác nhận commit
4. Consumer → nhận xác nhận
```

**Topic __consumer_offsets:**
```
- Topic Kafka nội bộ
- Compacted (log compaction)
- Lưu trữ offset cho tất cả các consumer group
- Key: group.id + topic + partition
- Value: offset + metadata + timestamp
```

### Độ Trễ Commit Offset

```
Độ trễ sync commit:
  Bình thường: 5-20ms
  Có vấn đề: >100ms
  Tác động: chặn xử lý

Độ trễ async commit:
  Bình thường: <5ms (không chặn)
  Tác động: tối thiểu
```

### Các Kịch Bản Lỗi

**1. Lỗi commit:**
```
Consumer → commit → lỗi network → broker không nhận
Khi restart:
  - Offset đã commit là cũ
  - Các message sẽ được xử lý lại
  - Xử lý idempotent giải quyết vấn đề
```

**2. Lỗi broker trong quá trình commit:**
```
Consumer → commit → broker đã ghi → broker crash trước khi xác nhận
Consumer → retry commit → leader mới
Commit có thể bị mất hoặc lặp lại
```

### Các Pattern Quản Lý Offset

**1. Per-Record Commit:**
```java
// Commit mỗi message (độ tin cậy tối đa)
for (var record : records) {
    process(record);
    Map<TopicPartition, OffsetAndMetadata> offsets = new HashMap<>();
    offsets.put(new TopicPartition(record.topic(), record.partition()),
                new OffsetAndMetadata(record.offset() + 1));
    consumer.commitSync(offsets);
}
```

**2. Batch Commit Với Xử Lý Lỗi:**
```java
try {
    for (var record : records) {
        process(record);
    }
    consumer.commitSync();
} catch (Exception e) {
    // Không commit → các message sẽ được đọc lại
    log.error("Processing failed, will retry", e);
}
```

**3. Async Commit Với Retry:**
```java
consumer.commitAsync((offsets, exception) -> {
    if (exception != null) {
        // Sync commit — một lần thử retry duy nhất. Nếu nó cũng thất bại — log lỗi.
        // Đừng retry vô hạn để tránh chặn việc xử lý.
        try {
            consumer.commitSync(offsets);
        } catch (Exception e) {
            log.error("Commit retry failed", e);
        }
    }
});
```

### Metadata Offset

```java
// Lưu metadata cùng offset
OffsetAndMetadata metadata = new OffsetAndMetadata(
    offset,
    "processed-at=" + System.currentTimeMillis()
);
consumer.commitSync(Map.of(partition, metadata));
```

### Tối Ưu Hóa Hiệu Năng

```
Đánh đổi tần suất commit:
  Commit thường xuyên hơn → ít trùng lặp hơn, nhiều overhead hơn
  Commit ít thường xuyên hơn → nhiều throughput hơn, nhiều trùng lặp hơn khi lỗi

Khuyến nghị:
  - Dữ liệu quan trọng: commit sau mỗi batch
  - Throughput cao: commit mỗi N message
  - Cân bằng: commitAsync với retry khi lỗi
```

### Giám Sát Commit Offset

**Các metrics chính:**
```
kafka.consumer:commit-latency-avg
kafka.consumer:commit-rate
kafka.consumer:failed-commit-rate
kafka.consumer:last-commit-latency
```

**Các Alert:**
```yaml
- Độ trễ commit > 100ms → warning
- Tỷ lệ commit thất bại > 1% → critical
- Không có commit trong > 5 phút → critical
```

### Các Thực Hành Tốt Nhất

```
✅ commitSync() sau khi xử lý batch
✅ commitAsync() cho throughput cao
✅ Xử lý các lỗi commit
✅ Xử lý idempotent để bảo vệ khỏi trùng lặp
✅ Giám sát độ trễ commit

❌ Auto commit cho dữ liệu quan trọng
❌ Commit trước khi xử lý
❌ Commit trong vòng lặp không cần thiết
❌ Bỏ qua các lỗi commit
❌ Không có giám sát sức khỏe commit
```

### Các Quyết Định Kiến Trúc

1. **Sync commit cho độ tin cậy** — dữ liệu quan trọng
2. **Async commit cho throughput** — các hệ thống khối lượng cao
3. **Xử lý lỗi là bắt buộc** — retry hoặc alert
4. **Xử lý idempotent** — bảo vệ khỏi trùng lặp khi retry

### Tóm Tắt Cho Senior

- Quá trình commit: consumer → __consumer_offsets → xác nhận của broker
- Sync vs async — đánh đổi giữa độ tin cậy và hiệu năng
- Các kịch bản lỗi cần xử lý retry
- Metadata có thể lưu thông tin bổ sung
- Giám sát độ trễ commit rất quan trọng cho sức khỏe production

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- Commit offset — lưu lại số của message đã xử lý cuối cùng trong `__consumer_offsets`
- Sync commit: đáng tin cậy, 5-50ms, chặn; Async commit: <5ms, không chặn, có thể mất
- Commit SAU khi xử lý = at-least-once; commit TRƯỚC = mất dữ liệu khi crash
- Batch commit: mỗi N message — cân bằng giữa overhead và trùng lặp
- Auto commit commit offset đã nhận, không phải offset đã xử lý — không dùng cho production
- Khi lỗi: offset đã commit là cũ → các message sẽ được xử lý lại (xử lý idempotent)
- Metadata offset cho phép lưu thông tin bổ sung (timestamp, trạng thái xử lý)

**Các câu hỏi phụ thường gặp:**
- *Khi nào dùng sync vs async?* — Sync cho dữ liệu quan trọng, async cho throughput cao.
- *Điều gì xảy ra khi async commit thất bại?* — Fallback về sync commit (một lần thử retry duy nhất).
- *Làm sao commit các offset cụ thể?* — `commitSync(Map<TopicPartition, OffsetAndMetadata>)`.
- *Tại sao auto commit tồi cho production?* — Commit các message chưa xử lý, không kiểm soát lỗi.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Auto commit là tiêu chuẩn cho production" — commit các message chưa xử lý
- "Commit trong mỗi vòng lặp message là ổn" — overhead khổng lồ
- "Async commit không có xử lý lỗi là ổn" — mất offset khi lỗi
- "Offset được commit tự động bởi broker" — đó là logic phía client
