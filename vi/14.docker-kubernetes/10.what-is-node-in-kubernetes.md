# What is Node in Kubernetes? (Node trong Kubernetes là gì?)

---

## Junior Level

### Giải Thích Đơn Giản

**Node** là một server làm việc nơi K8s "đặt" các Pod. Scheduler quyết định đặt mỗi Pod lên Node nào. Trong Kubernetes, một Node là "con ngựa thồ" thực thi các lệnh từ trung tâm điều khiển (Control Plane).

### Phép So Sánh Đơn Giản

Nếu Kubernetes là một công ty xây dựng:
- **Control Plane** — văn phòng quản lý (đưa ra quyết định)
- **Node** — công trường (nơi công việc thực sự diễn ra)
- **Pod** — đội công nhân trên công trường

### Mỗi Node Có Gì

1. **kubelet** — agent giám sát các container và báo cáo cho Control Plane
2. **kube-proxy** — xử lý các quy tắc định tuyến network
3. **Container Runtime** — chương trình để chạy container (thường là containerd)

### Các Loại Node

- **Worker Node** — chạy các ứng dụng (Pod)
- **Control Plane Node** — quản lý cluster (thường không chạy ứng dụng)

### Node Làm Gì?

- Nhận lệnh từ Control Plane
- Khởi chạy các Pod
- Giám sát sức khỏe của chúng
- Gửi thông tin tài nguyên (CPU, RAM)

### Những Gì Một Junior Developer Nên Nhớ

- Node là một server nơi các container chạy
- Mỗi Node có: kubelet, kube-proxy, container runtime
- Worker Node chạy các ứng dụng
- Control Plane Node quản lý cluster
- Nếu một Node bị dừng hoạt động, K8s chờ ~5 phút (pod-eviction-timeout) để chắc chắn Node
thực sự đã chết, không chỉ tạm thời mất network. Chỉ sau đó nó mới di chuyển các Pod.

## Middle Level

### Các Thành Phần Nội Bộ Của Node

#### kubelet

kubelet — agent trên mỗi Node "báo cáo" trạng thái container cho Control Plane.

Agent quan trọng nhất trên Node:
- Giám sát các Pod được gán cho Node này
- Giao tiếp với API server
- Khởi động và dừng các container
- Thực hiện health check
- Gửi trạng thái Node (Ready, NotReady)

#### kube-proxy
Proxy network:
- Duy trì các quy tắc định tuyến (iptables/IPVS)
- Cho phép Service hoạt động (cân bằng tải lưu lượng)
- Chuyển tiếp lưu lượng đến đúng các Pod

#### Container Runtime
Môi trường khởi chạy container:
- Tiêu chuẩn hiện đại: **containerd** hoặc **CRI-O**
- Docker-shim đã bị loại bỏ trong K8s v1.24+. Thay vì Docker, containerd hoặc CRI-O được dùng.

### Tài Nguyên Của Node

```
Capacity:          8 CPU, 32 GiB RAM    (tài nguyên vật lý)
kube-reserved:     1 CPU, 2 GiB RAM     (dành riêng cho K8s)
system-reserved:   0.5 CPU, 1 GiB RAM   (dành riêng cho OS)
─────────────────────────────────────────
Allocatable:       6.5 CPU, 29 GiB RAM  (khả dụng cho các Pod)
```

Các Pod chỉ có thể dùng tài nguyên **Allocatable**.

### Các Điều Kiện Của Node

| Điều kiện            | Nó có nghĩa gì                         |
| -------------------- | ------------------------------------- |
| `Ready`              | Node khỏe mạnh và có thể nhận Pod    |
| `MemoryPressure`     | RAM trống thấp                          |
| `DiskPressure`       | Dung lượng đĩa thấp                        |
| `PIDPressure`        | Quá nhiều process                       |
| `NetworkUnavailable` | Vấn đề network                       |

### Eviction

Khi tài nguyên Node cạn kiệt, kubelet bắt đầu loại bỏ các Pod:

1. **BestEffort** (không có requests/limits) — bị loại bỏ đầu tiên
2. **Burstable** (requests < limits) — bị loại bỏ thứ hai
3. **Guaranteed** (requests == limits) — bị loại bỏ cuối cùng

### Chẩn Đoán

```bash
# Thông tin Node
kubectl describe node <name>

# Mức tiêu thụ tài nguyên
kubectl top node

# Log của kubelet
journalctl -u kubelet
```

### Những Gì Một Middle Developer Nên Nhớ

- kubelet là process then chốt; nó crash sẽ làm tê liệt Node
- Luôn đặt Resource Requests & Limits
- Allocatable < Capacity (một phần được dành riêng cho OS và K8s)
- Eviction bảo vệ Node khỏi quá tải
- `kubectl describe node` — lệnh chẩn đoán chính

### Khi Nào KHÔNG Nên Quản Lý Node Thủ Công

ĐỪNG quản lý Node thủ công trong production — hãy dùng các managed node group (EKS, GKE)
hoặc IaC (Terraform).

## Senior Level

### Node Như Một Sự Trừu Tượng Hóa Hạ Tầng

Một Node là cầu nối giữa hạ tầng vật lý và thế giới trừu tượng của Kubernetes. Hiểu cách nó hoạt động là quan trọng cho việc lập kế hoạch dung lượng (capacity planning), troubleshoot, và tối ưu hóa.

### Node Pressure Và Eviction: Phân Tích Sâu

#### Ngưỡng (Thresholds)

Kubelet dùng các ngưỡng để vào chế độ pressure:

```
memory.available < 100Mi       → MemoryPressure
nodefs.available < 15%         → DiskPressure
nodefs.inodesFree < 10%        → DiskPressure (Inodes)
pid.available < 5%             → PIDPressure
```

#### Thuật Toán Eviction

```
1. Kubelet phát hiện điều kiện pressure
2. Đánh dấu Node với Condition tương ứng
3. Bắt đầu quá trình eviction:
   a. Tìm các Pod để loại bỏ (theo QoS class)
   b. Chấm dứt graceful (SIGTERM → chờ → SIGKILL)
   c. Giải phóng tài nguyên
4. Nếu pressure vẫn tiếp tục — lặp lại
```

#### Graceful vs Forceful Eviction

- **Graceful**: kubelet gửi SIGTERM, chờ `terminationGracePeriodSeconds`
- **Forceful**: Nếu Node là NotReady lâu hơn `pod-eviction-timeout` (mặc định 5 phút), Control Plane loại bỏ các Pod một cách cưỡng chế

### Node Allocatable: Phân Tích Chi Tiết

```yaml
# Cấu hình kubelet
kubeReserved:
  cpu: "500m"
  memory: "1Gi"
  ephemeral-storage: "1Gi"
systemReserved:
  cpu: "200m"
  memory: "500Mi"
evictionHard:
  memory.available: "200Mi"
  nodefs.available: "10%"
```

**Quan trọng:** `kubeReserved` và `systemReserved` không thực thi việc dành riêng thực sự — chúng là các giá trị mang tính thông tin cho scheduler. Cho các giới hạn cứng, cần cgroups.

### Cân Nhắc Khi Tải Cao (Highload)

#### Mật Độ

- Theo mặc định K8s giới hạn ~110 Pod mỗi Node
- Các yếu tố giới hạn:
  - Số lượng IP trong VPC (AWS)
  - Tải kube-proxy (các quy tắc iptables)
  - Tải etcd (nhiều Pod hơn = nhiều object hơn)
  - Overhead CPU từ kubelet

#### HugePages

Với các ứng dụng nặng (DB, cache in-memory):
```yaml
resources:
  limits:
    hugepages-2Mi: 1Gi
    memory: 4Gi
```

Yêu cầu cấu hình ở cấp độ OS:
```bash
sysctl -w vm.nr_hugepages=512
```

### Edge Case

#### Node NotReady

```
Dòng thời gian:
T+0s:    Node ngừng gửi heartbeat
T+40s:   Điều kiện Node = NotReady
T+5m:    Eviction Pod bắt đầu
T+5m+:   Các Pod được tạo lại trên các Node khác
```

**Tinh chỉnh:**
```yaml
# Các cờ kube-controller-manager
--node-monitor-period=5s
--node-monitor-grace-period=40s
--pod-eviction-timeout=5m
```

#### Kernel Panic

Nếu kernel bị crash — kubelet không thể báo cáo. Control Plane chờ timeout heartbeat. Đây là trường hợp khó nhất cho tự động hóa.

### Node Affinity Và Taint

#### Taint (Đẩy)
```bash
# Taint một Node
kubectl taint nodes node1 gpu=true:NoSchedule

# Chỉ các Pod có toleration phù hợp mới chạy
```

```yaml
tolerations:
- key: "gpu"
  operator: "Equal"
  value: "true"
  effect: "NoSchedule"
```

#### Node Affinity (Hút)
```yaml
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchExpressions:
        - key: disktype
          operator: In
          values: [ssd]
```

### Node Problem Detector

DaemonSet để giám sát sức khỏe Node:
- Giám sát kernel, đĩa, network
- Báo cáo vấn đề lên API
- Tích hợp với Prometheus

### Node Autoscaling

**Cluster Autoscaler:**
- Thêm các Node khi các Pod đang Pending
- Loại bỏ các Node ít sử dụng
- Tích hợp với nhà cung cấp cloud

**Karpenter (AWS):**
- Nhanh hơn và linh hoạt hơn
- Chọn loại instance tối ưu
- Hỗ trợ các instance Spot

### Tóm Tắt Cho Senior

- Node — sự trừu tượng hóa trên "phần cứng." kubelet là process then chốt.
- Luôn cấu hình **Resource Requests & Limits** để eviction đúng cách.
- Phân biệt `Capacity` (tài nguyên vật lý) và `Allocatable` (khả dụng cho các Pod).
- Thuật toán eviction ưu tiên theo QoS class.
- Ở tải cao: giới hạn mật độ, HugePages, node affinity.
- Timeout NotReady (5 phút) — tham số có thể tinh chỉnh cho các hệ thống quan trọng.
- Taints/Tolerations + Node Affinity — công cụ cho các Node chuyên biệt.

## Interview Cheat Sheet

**Cần phải biết:**
- Node — server làm việc của K8s; Worker Node chạy các Pod, Control Plane quản lý cluster
- Các thành phần Node: kubelet (agent), kube-proxy (network), container runtime (containerd)
- Allocatable < Capacity — một phần tài nguyên được dành riêng cho OS và K8s
- Eviction loại bỏ các Pod theo QoS class: BestEffort → Burstable → Guaranteed
- Node NotReady: K8s chờ ~5 phút (pod-eviction-timeout) trước khi di chuyển các Pod
- Taint (đẩy) + Toleration (chấp nhận) + Node Affinity (hút) — lập lịch
- Cluster Autoscaler / Karpenter — thêm/loại bỏ Node tự động

**Các câu hỏi phụ thường gặp:**
- *"Điều gì xảy ra nếu kubelet crash?"* — Các Pod trên Node trở nên không được quản lý; Node → NotReady
- *"Allocatable là gì?"* — Tài nguyên khả dụng cho các Pod (Capacity trừ đi phần dành riêng cho OS và K8s)
- *"Khi nào Pod eviction kích hoạt?"* — Khi có MemoryPressure, DiskPressure, PIDPressure trên Node
- *"Cluster Autoscaler khác Karpenter như thế nào?"* — Karpenter nhanh hơn, thông minh hơn khi chọn instance

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Node = Pod" (Node là server, Pod là đơn vị khởi chạy trên nó)
- "kubelet chạy trên Control Plane" (kubelet chỉ chạy trên Worker Node)
- "Capacity = tài nguyên cho các Pod" (là Allocatable, không phải Capacity)
- "Docker-shim vẫn được dùng" (đã bị loại bỏ trong K8s v1.24; containerd/CRI-O)
