# How is data distributed across partitions (Dữ liệu được phân phối như thế nào giữa các partition)

---

## 🟢 Junior Level

### Quy Tắc Cơ Bản

Dữ liệu được phân phối giữa các partition dựa trên **message key**:

```
partition = hash(key) % number_of_partitions
```

### Phép So Sánh

Hãy nghĩ về **việc phân loại thư vào các hộp thư**:
- Mỗi lá thư có một mã zip (key)
- Máy phân loại thư nhìn vào mã và đặt lá thư vào một hộp thư cụ thể (partition)
- Các lá thư có cùng mã luôn đi đến cùng một hộp thư

```
key="user-1" → luôn partition 2
key="user-2" → luôn partition 0
key="user-3" → luôn partition 1
```

### Có Key Và Không Có Key

**Có key** — thứ tự được đảm bảo:
```java
// user-123 luôn rơi vào cùng một partition
ProducerRecord<String, String> record =
    new ProducerRecord<>("orders", "user-123", "Order created");
```

**Không có key** — phân phối đều (sticky partitioning):
```java
// Sẽ rơi vào một partition ngẫu nhiên, phân phối đều
ProducerRecord<String, String> record =
    new ProducerRecord<>("orders", "Order created");
```

## 🟡 Middle Level

### Partitioner — Cách Nó Hoạt Động

Kafka dùng một **Partitioner** để xác định partition đích.

**Thuật toán tiêu chuẩn:**
```
Nếu key != null → MurmurHash2(key) % numPartitions
Nếu key == null → Sticky Partitioning (batch vào một partition)
```

### Sticky Partitioning (Kafka 2.4+)

```
Cách tiếp cận cũ (Round-Robin):
  msg1 → P0, msg2 → P1, msg3 → P2, msg4 → P0 ...
  Mỗi message → partition mới → các batch nhỏ

Sticky Partitioning:
  msg1-50 → P0 (cho đến khi batch đầy)
  msg51-100 → P2
  msg101-150 → P1
  Batch lớn hơn → throughput cao hơn → độ trễ thấp hơn
```

Round-Robin — cách tiếp cận cũ (trước Kafka 2.4), được dùng khi key=null.
Được thay thế bởi Sticky Partitioning.

### Custom Partitioner

```java
public class RegionPartitioner implements Partitioner {
    @Override
    public int partition(String topic, Object key, byte[] keyBytes,
                        Object value, byte[] valueBytes, Cluster cluster) {
        List<PartitionInfo> partitions = cluster.partitionsForTopic(topic);
        int numPartitions = partitions.size();
        return Math.abs(key.hashCode()) % numPartitions;
    }

    @Override
    public void configure(Map<String, ?> configs) {}

    @Override
    public void close() {}
}
```

```java
props.put("partitioner.class", "com.example.RegionPartitioner");
```

### Vấn Đề Hot Partition

```
Tất cả message với key="all" → một partition
Hot partition → bottleneck → 100% CPU trên một broker
Các partition khác nhàn rỗi
```

### So Sánh Chiến Lược

| Chiến lược            | Thứ tự            | Throughput   | Khi nào dùng               |
| ------------------- | ------------------- | ------------ | -------------------------- |
| **Dựa trên Key**       | ✅ Trong partition  | Trung bình       | Cần thứ tự theo key      |
| **Sticky (không key)** | ❌                  | Tối đa      | Thứ tự không quan trọng    |
| **Round-Robin**     | ❌                  | Trung bình       | Phân phối đều         |
| **Custom**          | Tùy             | Tùy      | Logic kinh doanh            |

### Các Lỗi Thường Gặp

| Lỗi                          | Hậu quả                    | Giải pháp                              |
| -------------------------------- | ------------------------------ | ------------------------------------- |
| Các key không đồng đều                      | Hot partition                 | Thêm salt vào các key                      |
| Không có key khi cần thứ tự   | Các message bị trộn lẫn          | Dùng key = business entity ID      |
| Key null cho các event liên quan      | Mất thứ tự                  | Key = aggregate ID                    |
| Thêm partition                | Phân phối key thay đổi       | Tạo một topic mới                    |

## 🔴 Senior Level

### Cài Đặt Nội Bộ — Default Partitioner

```java
// org.apache.kafka.clients.producer.internals.DefaultPartitioner
public int partition(String topic, Object key, byte[] keyBytes,
                     Object value, byte[] valueBytes, Cluster cluster,
                     int numPartitions) {
    if (keyBytes == null) {
        // Sticky partitioning
        return stickyPartitionCache.partition(topic, cluster);
    }
    // MurmurHash 2
    int hash = Utils.murmur2(keyBytes);
    return Math.abs(hash) % numPartitions;
}
```

**MurmurHash 2:**
- Không phải mã hóa (non-cryptographic), nhanh. Được tối ưu hóa cho các chỉ thị CPU (bit shift, XOR), không yêu cầu các thao tác mã hóa đặc biệt. Nhanh hơn 5-10 lần so với SHA-256.
- Phân phối đồng đều tốt (va chạm tối thiểu)
- Output 32-bit → `Math.abs` → modulo

**Sticky Partition Cache:**
```java
class StickyPartitionCache {
    int index;      // partition hiện tại
    int epoch;      // epoch để vô hiệu hóa khi metadata thay đổi

    int partition(String topic, Cluster cluster) {
        // Trả về cùng partition cho đến khi batch đầy
        // Sau đó chọn một cái mới (ngẫu nhiên trong số khả dụng)
    }
}
```

### UniformStickyPartitioner (Kafka 3.3+)

```java
// org.apache.kafka.clients.producer.UniformStickyPartitioner
// Phiên bản cải tiến của sticky partitioning
// Đảm bảo phân phối đều hơn khi key == null
// Chọn partition tiếp theo qua bounded random
// Giải quyết vấn đề không đồng đều của sticky partitioning —
// đảm bảo phân phối đồng đều hơn qua bounded random thay vì sticking đơn giản.
```

### Consistent Hashing Cho Các Partition Động

```
Vấn đề: hash(key) % N thay đổi khi N thay đổi
Giải pháp: Consistent Hashing (dựa trên ring)

Ring: 2^32 vị trí
Mỗi partition chiếm một vài vị trí trên ring
Key → hash → partition gần nhất trên ring

Khi thêm một partition:
  Cách tiếp cận cũ: ~50% key di chuyển
  Consistent hashing: ~1/N key di chuyển

Các thư viện: ketama, aws-dynamodb-consistent-hash
```

### Edge Case (3+)

1. **Integer Overflow Với MurmurHash:** `Utils.murmur2()` trả về một int có dấu. `Math.abs(Integer.MIN_VALUE)` trả về `Integer.MIN_VALUE` (âm). Kafka xử lý điều này qua `hash & 0x7fffffff` (bitmask). Không có điều này — `NegativeArraySizeException` hoặc partition sai.

2. **Overhead Serialize Key:** Key lớn (ví dụ: object JSON 10KB) được serialize → MurmurHash xử lý 10KB mỗi message → bottleneck CPU. Giải pháp: hash key trước khi gửi (SHA-256 → 8 byte đầu tiên) hoặc dùng key gọn nhẹ (UUID, Long).

3. **Partitioner + Transactional Producer:** Khi dùng `transactional.id`, partitioner được gọi **trước khi** transaction bắt đầu. Nếu partitioner phụ thuộc vào metadata cluster (Custom Partitioner) và metadata đã cũ — message có thể rơi vào một partition không phải leader → `NotLeaderForPartitionException` → transaction abort.

4. **Custom Partitioner + Thay Đổi Key:** Nếu một custom partitioner dùng dữ liệu bên ngoài (ví dụ: config từ một cơ sở dữ liệu) để định tuyến, và dữ liệu đó thay đổi — phân phối trở nên không tất định. Cùng một key trong các batch khác nhau rơi vào các partition khác nhau.

5. **Sticky Partitioning + Batch Nhỏ:** Với `batch.size=16KB` và các message nhỏ (100 byte), batch đầy sau ~160 message. Nhưng với `linger.ms=0`, batch được gửi ngay lập tức — sticky partitioner chuyển sang một partition mới mỗi message, hiệu quả trở thành round-robin với overhead bổ sung.

### Các Con Số Hiệu Năng

| Chỉ số                           | Giá trị                  | Điều kiện                          |
| -------------------------------- | ---------------------- | ------------------------------------ |
| Throughput MurmurHash            | ~2 GB/s                | Một core, CPU hiện đại             |
| Overhead sticky partition        | ~10-50 ns/message       | Không có serialize key           |
| Tác động hot partition             | Tăng độ trễ 3-10 lần | 90% lưu lượng trong 1 partition trong 10|
| batch.size tối ưu               | 256KB                  | Cân bằng latency/throughput          |
| Tỷ lệ compression (key tương tự) | 5-10x                  | lz4, các key tương tự trong cùng partition |

### Câu Chuyện Production Thực Tế

> **Tình huống:** Hệ thống thanh toán với 20 partition trên topic `transactions`. Key = `merchantId`. Trong quá trình test với dữ liệu tổng hợp (1000 merchant), phân phối đều. Trong production — 3 merchant lớn tạo ra 70% lưu lượng.
>
> **Vấn đề:** 3 partition xử lý 70% tải. Consumer lag trên các partition này tăng đến 500K message. Hai consumer khác nhàn rỗi. P99 latency tăng từ 10ms lên 200ms.
>
> **Chẩn đoán:**
> ```bash
> # JMX: BytesInPerSec mỗi partition
> kafka-run-class.sh kafka.tools.GetOffsetShell \
>   --broker-list localhost:9092 --topic transactions --time -1
> # Hiển thị: P7=50GB, P12=45GB, P15=42GB, còn lại < 5GB
> ```
>
> **Giải pháp:**
> 1. Thêm "salt" vào các key: `key = merchantId + "_" + ThreadLocalRandom.nextInt(10)`
> 2. Tăng partition lên 60 (mỗi key "được salt" phân phối đều hơn)
> 3. Giới thiệu `UniformStickyPartitioner` cho các message không có key
> 4. Thiết lập giám sát throughput mỗi partition trong Grafana
>
> **Bài học:** Luôn test phân phối trên dữ liệu **giống production**, với các key thực, không phải tổng hợp.

### Các Thực Hành Tốt Nhất Cho Highload

1. **Key = business entity ID** (userId, orderId) — đảm bảo thứ tự và khả năng truy vết
2. **Phân phối đều rất quan trọng** — kiểm tra byte mỗi partition trong histogram
3. **Sticky partitioning theo mặc định** — tối ưu cho throughput khi không có key
4. **Custom partitioner cho logic kinh doanh** — nhưng làm cho nó tất định
5. **Nếu bạn dùng key cho các đảm bảo về thứ tự** — đừng thêm partition, hãy tạo một topic mới. Nếu thứ tự không quan trọng (key=null), thêm partition là an toàn.
6. **Tinh chỉnh batch:** `batch.size=256KB`, `linger.ms=10` cho throughput cao
7. **Compression:** `lz4` — cân bằng CPU/compression tốt nhất cho dữ liệu được phân vùng
8. **Test trên dữ liệu giống production** — các key thực thường có skew

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- Có key: `MurmurHash2(key) % numPartitions` — phân phối tất định
- Không có key: Sticky Partitioning (Kafka 2.4+) — batch vào một partition để tăng throughput
- Thứ tự chỉ được đảm bảo trong một partition (một key = một partition)
- Hot partition — vấn đề với các key không đồng đều; giải quyết bằng cách salt key
- Khi thêm partition, `hash(key) % N` thay đổi — thứ tự bị phá vỡ
- UniformStickyPartitioner (Kafka 3.3+) — sticky partitioning cải tiến
- Custom Partitioner — cho logic định tuyến kinh doanh
- Test phân phối trên dữ liệu giống production, không phải tổng hợp

**Các câu hỏi phụ thường gặp:**
- *Sticky Partitioning là gì?* — Với key=null, các message batch vào một partition cho đến khi đầy, sau đó chuyển sang cái khác.
- *Làm sao xử lý hot partition?* — Salt key: `key = entityId + "_" + random(N)`.
- *Điều gì xảy ra khi bạn thêm partition?* — Cùng key rơi vào các partition khác nhau → thứ tự bị phá vỡ.
- *Kafka dùng hash nào?* — MurmurHash 2, nhanh, không mã hóa.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Không có key, thứ tự vẫn được đảm bảo" — không có key thì sticky/ngẫu nhiên, không có thứ tự
- "Thêm partition không ảnh hưởng đến các key" — nó có ảnh hưởng, `hash(key) % N` thay đổi
- "Round-Robin được dùng theo mặc định" — đã được thay thế bởi Sticky Partitioning
- "Key có thể có kích thước bất kỳ mà không có hậu quả" — key lớn = overhead CPU khi hash
