# Why you should not call System.gc()? (Tại sao bạn không nên gọi System.gc()?)

## Junior Level

**System.gc()** — thực hành xấu vì:

1. **Dừng ứng dụng** — tất cả các luồng chờ
2. **GC thông minh hơn bạn** — tự biết khi nào cần dọn dẹp
3. **Lãng phí CPU** — thường không đem lại lợi ích gì

```java
// ❌ Đừng làm thế này!
System.gc();  // "Giúp đỡ" GC

// ✅ Hãy tin tưởng JVM
// GC sẽ quyết định khi nào cần thiết
```

---

## Middle Level

### Phá hủy các mô hình thích ứng (Adaptive Model)

```
Các GC hiện đại (G1, ZGC) tự học:
  → Allocation Rate
  → Promotion Rate
  → Pause Time Goals

System.gc() = một cú sốc từ bên ngoài:
  → Reset các thống kê
  → GC học lại từ đầu
  → Các khoảng dừng không dự đoán được
```

### Concurrent Mode Failure

```
Concurrent Mode Failure (G1) — concurrent marking không hoàn thành kịp thời,
Old Gen bị lấp đầy → fallback sang Full GC. Đây là khoảng dừng dài nhất trong G1.
System.gc() có thể gây ra kịch bản này nếu được gọi vào thời điểm sai.
```

### Làm sao tìm ra thủ phạm

```bash
# 1. GC Logs
-Xlog:gc*
→ "Pause Full (System.gc())"

# 2. JFR
→ Sự kiện "System GC"
→ Stack trace đầy đủ

# 3. Giải pháp
-XX:+ExplicitGCInvokedConcurrent  # Concurrent
# hoặc
-XX:+DisableExplicitGC  # Bỏ qua
```

## Senior Level

### JIT Deoptimization

```
Full GC → class unloading → deoptimization của các phương thức hot.
Code Cache được dọn dẹp riêng (CodeCache sweeper).

  → Sau GC: thông dịch code (interpretation)
  → Throughput giảm trong vài giây

→ "Dùng búa tạ để sửa đồng hồ Thụy Sĩ" — System.gc() thô bạo dừng
  tất cả các tối ưu hóa của JVM để buộc thu gom rác.
```

### GC Thrashing

```
Cố gắng "chữa" OOM qua System.gc():
  → Giải phóng được rất ít bộ nhớ
  → Tiêu tốn 95% CPU cho GC
  → Che khuất vấn đề thực sự

→ Tốt hơn là crash và restart
```

### Production: DisableExplicitGC

```bash
-XX:+DisableExplicitGC
# → Bỏ qua tất cả các lời gọi System.gc()
# → Ngoại trừ Direct Buffers (cẩn thận!)

# Giải pháp thay thế:
-XX:+ExplicitGCInvokedConcurrent
# → Concurrent GC thay vì Full GC STW
```

### Best Practices

1. **Trường hợp sử dụng hợp pháp duy nhất** — benchmark (JMH)
2. **JFR** để tìm ra người gọi
3. **ExplicitGCInvokedConcurrent** cho production
4. **Đừng catch OOME** qua System.gc()
5. **Tìm ra rò rỉ**, đừng "giúp đỡ" GC

### Tóm tắt cho Senior

- **System.gc()** = "dùng búa tạ để sửa đồng hồ Thụy Sĩ" — thô bạo dừng tất cả các tối ưu hóa của JVM
- **Phá hủy** các mô hình GC thích ứng
- **Concurrent Mode Failure** → Full GC STW
- **JIT deoptimization** → mất Throughput
- **JFR** = tìm ra người gọi
- **DisableExplicitGC** hoặc **ExplicitGCInvokedConcurrent**

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- System.gc() — anti-pattern: Full GC = STW (hàng giây), reset các thống kê thích ứng của GC, JIT deoptimization các phương thức hot
- G1/ZGC tự học (Allocation Rate, Promotion Rate, Pause Time Goals); System.gc() = cú sốc từ bên ngoài → GC học lại từ đầu
- Concurrent Mode Failure (G1): concurrent marking không hoàn thành → Old Gen đầy → Full GC STW; System.gc() có thể gây ra điều này
- JIT deoptimization: Full GC → class unloading → các phương thức hot → thông dịch → throughput giảm trong vài giây
- GC Thrashing: cố gắng "chữa" OOM qua System.gc() → 95% CPU cho GC → che khuất vấn đề thực sự
- Production: `-XX:+ExplicitGCInvokedConcurrent` (concurrent GC thay vì STW) hoặc `-XX:+DisableExplicitGC` (bỏ qua, cẩn thận với Direct Buffers!)
- Trường hợp sử dụng hợp pháp duy nhất — benchmark (JMH)

**Các câu hỏi phụ thường gặp:**
- **Tại sao System.gc() phá hủy các mô hình thích ứng?** — G1/ZGC tích lũy các thống kê (allocation rate, promotion rate); System.gc() = Full GC đột ngột → reset thống kê → GC "quên" hành vi của ứng dụng
- **Concurrent Mode Failure là gì?** — Concurrent marking của G1 không hoàn thành trước khi Old Gen đầy → fallback sang Full GC (khoảng dừng dài nhất trong G1)
- **Làm sao tìm ai gọi System.gc()?** — `-Xlog:gc*` (tìm "Pause Full (System.gc())"); JFR (sự kiện "System GC" với stack trace đầy đủ)
- **Tại sao JIT deoptimization xảy ra?** — Full GC → class unloading → các phương thức đã được JIT biên dịch bị loại bỏ → biên dịch lại từ đầu

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi gọi System.gc() để bảo trì phòng ngừa" — GC tự biết; gọi thủ công = STW + phá hủy các mô hình thích ứng
- "Tôi catch OOME và gọi System.gc()" — GC Thrashing: 95% CPU cho GC; tốt hơn là fail-fast và restart
- "System.gc() cải thiện hiệu năng" — "dùng búa tạ để sửa đồng hồ Thụy Sĩ"; thô bạo dừng tất cả các tối ưu hóa của JVM
