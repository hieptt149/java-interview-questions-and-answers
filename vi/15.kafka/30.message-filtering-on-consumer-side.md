# How to implement message filtering on consumer side in Kafka (Cách triển khai lọc message ở phía consumer trong Kafka)

## Junior Level

### Định Nghĩa

Kafka **không hỗ trợ** lọc ở phía broker. Tất cả message từ một topic được gửi đến consumer, và nó quyết định cái nào để xử lý và cái nào để bỏ qua.

Đây là một quyết định kiến trúc trong Kafka — broker hoạt động như một "đường ống thông minh" (smart pipe) và không xem xét nội dung message. Điều này đơn giản hóa broker và mang lại hiệu năng tối đa.

### Analogy

Hãy tưởng tượng một hộp thư. Người đưa thư (Kafka) giao TẤT CẢ các lá thư. Bạn (consumer) mở hộp thư và:
- Quảng cáo → thùng rác (bạn bỏ qua nó)
- Hóa đơn điện → bạn thanh toán nó (xử lý nó)
- Thư từ bạn bè → bạn đọc nó (xử lý nó)

Người đưa thư không lọc — anh ta mang mọi thứ đến. Việc lọc là công việc của bạn.

### Ví Dụ Cơ Bản

```java
KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);
consumer.subscribe(List.of("orders"));

while (true) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> record : records) {
        // Lọc ở phía consumer
        if (shouldProcess(record)) {
            process(record);
        }
        // Chúng ta bỏ qua nó — nhưng offset vẫn di chuyển
    }
    consumer.commitSync();
}

private boolean shouldProcess(ConsumerRecord<String, String> record) {
    // Ví dụ: chúng ta chỉ xử lý các đơn hàng > $100
    Order order = parseOrder(record.value());
    return order.amount() > 100;
}
```

### Khi Nào Điều Này Quan Trọng

- **Nhiều loại sự kiện trong một topic** — lọc theo loại
- **Multi-tenant** — lọc theo tenant ID
- **Feature flags** — lọc theo điều kiện
- **Quyền riêng tư dữ liệu** — lọc dữ liệu nhạy cảm

## Middle Level

### Các Phương Pháp Lọc

#### 1. Lọc phía Consumer (đơn giản nhất)

```java
ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
for (ConsumerRecord<String, String> record : records) {
    Order order = parseOrder(record.value());

    if (order.status().equals("COMPLETED") && order.amount() > 100) {
        process(order);
    }
    // Chúng ta bỏ qua PENDING, CANCELLED, các đơn hàng nhỏ
}
```

#### 2. Lọc thông qua Kafka Streams

```java
StreamsBuilder builder = new StreamsBuilder();
KStream<String, Order> orders = builder.stream("orders");

// Lọc
orders.filter((key, order) -> order.amount() > 100 && order.status().equals("COMPLETED"))
      .to("important-orders");  // topic mới

// Hoặc side-output cho các message đã lọc
orders.branch(
    (key, order) -> order.amount() > 100,              // stream 1: quan trọng
    (key, order) -> order.amount() <= 100              // stream 2: bình thường
)[0].to("important-orders");
```

#### 3. Lọc thông qua ksqlDB

```sql
-- Tạo một stream đã lọc
CREATE STREAM important_orders AS
    SELECT *
    FROM orders
    WHERE amount > 100
      AND status = 'COMPLETED'
    EMIT CHANGES;

-- Consumer đọc stream đã lọc sẵn
-- consumer.subscribe(List.of("important_orders"))
```

#### 4. Lọc phía Producer (lựa chọn tốt nhất)

```java
// Producer quyết định ghi vào topic nào
if (order.amount() > 100) {
    producer.send(new ProducerRecord("important-orders", order));
} else {
    producer.send(new ProducerRecord("normal-orders", order));
}
```

### Bảng Các Lỗi Thường Gặp

| Lỗi                                   | Triệu Chứng                     | Hậu Quả                          | Giải Pháp                              |
| ------------------------------------ | -------------------------------- | ---------------------------------- | -------------------------------------- |
| Lọc không commit offset               | Offset không di chuyển cho các message đã lọc | Xử lý trùng lặp khi restart | Commit offset ngay cả cho các message đã lọc |
| Lọc sau khi xử lý đầy đủ              | Lãng phí CPU                      | Đã xử lý, rồi bị loại bỏ           | Lọc TRƯỚC khi xử lý                     |
| Lọc trong logic phức tạp              | Khó bảo trì                       | Bug trong logic filter             | Tách filter thành một bước riêng biệt   |
| Không giám sát số lượng đã lọc        | Không thể thấy filter có hoạt động | Không thể tinh chỉnh              | Metric: đã xử lý vs đã lọc              |
| Tất cả message trong một topic        | Mỗi consumer đều lọc              | Lãng phí network + CPU             | Chia thành các topic ở phía producer    |
| Không có routing thay thế             | Các message đã lọc bị mất         | Mất dữ liệu                        | DLQ hoặc topic riêng cho các message đã lọc |

### So Sánh Các Phương Pháp

| Phương pháp          | Độ phức tạp | Overhead Network       | Overhead CPU | Khi Nào Sử Dụng          |
| ------------------- | ----------- | --------------------- | ------------ | ------------------------ |
| **Consumer filter**  | Thấp        | Cao (tất cả message)   | Thấp         | Filter đơn giản           |
| **Kafka Streams**    | Trung bình  | Trung bình             | Trung bình   | Chuyển đổi phức tạp        |
| **ksqlDB**           | Trung bình  | Trung bình             | Thấp         | Lọc kiểu SQL               |
| **Producer routing** | Thấp        | Thấp                   | Thấp         | **Best practice**         |

### Khi Nào Lọc Phía Consumer Là Chấp Nhận Được

- **Điều kiện đơn giản** — lọc theo key, status, amount
- **Topic dung lượng thấp** — chi phí network không đáng kể
- **Giải pháp tạm thời** — fix nhanh trước khi routing đúng đắn
- **Consumer đa mục đích** — consumer cần thấy mọi thứ để audit

### Khi Nào KHÔNG Nên Dùng Lọc Phía Consumer

- **Topic dung lượng cao** — lãng phí network/đĩa/CPU
- **Quyền riêng tư dữ liệu** — dữ liệu nhạy cảm không nên đến được consumer
- **Quy định** — GDPR, PCI-DSS yêu cầu phân tách dữ liệu
- **Tối ưu chi phí** — lãng phí network/đĩa ở quy mô lớn

## Senior Level

### Cơ Chế Nội Bộ Sâu

#### Tại Sao Kafka Không Hỗ Trợ Lọc Phía Server

```
Quyết định kiến trúc của Kafka:
  Broker = lưu trữ ngu ngơ (dumb storage) + replication
  Trí tuệ nằm ở producer và consumer

Lý do:
  1. Độ phức tạp broker — logic filter trên mỗi broker
  2. Hiệu năng — quét tất cả message để filter = O(n) mỗi fetch
  3. Linh hoạt — logic filter phụ thuộc vào ứng dụng
  4. Nhất quán — các consumer khác nhau, filter khác nhau

Kết quả:
  FetchRequest → trả về TẤT CẢ message trong khoảng
  Consumer → nhận TẤT CẢ → lọc cục bộ
  Broker không biết/không quan tâm về tiêu chí filter
```

**KIP-290 và KIP-359** đã thảo luận về lọc phía server nhưng bị từ chối do độ phức tạp và tác động đến hiệu năng.

#### Lọc Consumer Và Quản Lý Offset

```java
// QUAN TRỌNG: quản lý offset khi lọc

// ĐÚNG:
ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
for (ConsumerRecord<String, String> record : records) {
    if (shouldProcess(record)) {
        process(record);
    }
    // Offset tiến lên cho TẤT CẢ message (đã xử lý + đã lọc)
}
consumer.commitSync();  // commit offset mới nhất

// SAI:
ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
for (ConsumerRecord<String, String> record : records) {
    if (shouldProcess(record)) {
        process(record);
        // Chỉ commit cho cái đã xử lý — offset không tiến lên cho cái đã lọc
        consumer.commitSync();  // ❌
    }
}
// Các message đã lọc sẽ bị đọc lại khi restart!
```

#### Lọc Kafka Streams — Cơ Chế Nội Bộ

```
Lọc Kafka Streams:
  builder.stream("orders")              // đọc từ topic
         .filter(predicate)              // áp dụng filter
         .to("filtered-topic");          // ghi vào topic mới

Luồng nội bộ:
  1. Source node: đọc từ topic "orders"
  2. Filter node: áp dụng predicate, loại bỏ cái không khớp
  3. Sink node: ghi cái khớp vào "filtered-topic"

Điểm chính:
  Các message đã lọc được ĐỌC từ "orders" nhưng KHÔNG được GHI vào "filtered-topic"
  I/O network: topic orders → ứng dụng Streams (tất cả message)
  I/O network: ứng dụng Streams → filtered-topic (chỉ cái khớp)

  Điều này tốt hơn lọc consumer (tiết kiệm I/O ghi)
  Nhưng tệ hơn producer routing (lãng phí I/O đọc)
```

### Đánh Đổi

| Khía cạnh        | Lọc Consumer            | Producer routing      | Kafka Streams        |
| --------------- | ---------------------- | -------------------- | ------------------ |
| Network (đọc)    | Tất cả message          | Chỉ cái cần thiết      | Tất cả message       |
| Network (ghi)    | N/A                     | Ghi theo từng topic    | Ghi theo từng topic   |
| Đĩa broker        | Tất cả message          | Chia theo topic        | Chia theo topic       |
| CPU consumer      | Filter + xử lý          | Chỉ xử lý               | N/A (ứng dụng riêng)  |
| Độ phức tạp       | Thấp                    | Thấp-Trung bình        | Trung bình-Cao        |
| Linh hoạt         | Cao (filter động)       | Thấp (routing tĩnh)    | Cao                   |
| Quyền riêng tư dữ liệu | Thấp (tất cả dữ liệu bị lộ) | Cao (phân tách)  | Cao (phân tách)       |

### Edge Cases

**1. Phụ thuộc message đã lọc:**

```
Kịch bản:
  Topic "orders": order-1 (status=PENDING, $50), order-2 (status=COMPLETED, $200)
  order-2 tham chiếu order-1 (đơn hàng trả lại)

  Filter consumer: status=COMPLETED
  order-1 → bị lọc ra (PENDING)
  order-2 → được xử lý
  Vấn đề: xử lý order-2 thất bại vì order-1 không có trong hệ thống

Giải quyết:
  1. Đừng lọc các message phụ thuộc
  2. Xử lý TẤT CẢ message, lọc ở cấp độ hành động
  3. Dùng các topic riêng theo status (producer routing)
```

**2. Yêu cầu filter động:**

```
Kịch bản:
  Tiêu chí filter thay đổi tại runtime:
    Thứ Hai: amount > 100
    Thứ Ba: amount > 50
    Thứ Tư: amount > 200

  Phía consumer: dễ dàng, reload config filter
  Producer routing: khó, các producer cần cập nhật
  ksqlDB: dễ dàng, ALTER STREAM

Giải quyết cho consumer:
  volatile FilterConfig currentFilter;

  while (running) {
      FilterConfig filter = currentFilter;  // đọc atomic
      ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
      for (ConsumerRecord<String, String> record : records) {
          if (filter.matches(record)) {
              process(record);
          }
      }
      consumer.commitSync();
  }

  // Cập nhật filter (từ config service):
  void updateFilter(FilterConfig newFilter) {
      currentFilter = newFilter;  // ghi atomic
  }
```

**3. Lọc với đảm bảo thứ tự:**

```
Kịch bản:
  Partition 0: [order-1(PENDING), order-1(COMPLETE), order-2(NEW)]
  Filter: status=COMPLETE

  order-1(PENDING) → bị lọc ra
  order-1(COMPLETE) → được xử lý
  order-2(NEW) → bị lọc ra

  Vấn đề: order-2(NEW) đáng lẽ phải được xử lý TRƯỚC order-1(COMPLETE)
  Việc lọc đã phá vỡ thứ tự!

Giải quyết:
  1. Đừng lọc các message ảnh hưởng đến thứ tự
  2. Lọc ở cấp topic (producer routing), không phải consumer
  3. Xử lý TẤT CẢ, lọc ở cấp độ hành động
```

**4. Lọc và DLQ:**

```java
// Các message đã lọc → DLQ để audit
ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
for (ConsumerRecord<String, String> record : records) {
    if (shouldProcess(record)) {
        process(record);
    } else {
        // Không xử lý, nhưng không mất
        dlqProducer.send(new ProducerRecord<>(
            "orders-filtered",  // topic riêng để audit
            record.key(),
            record.value()
        ));
    }
}
consumer.commitSync();
```

**5. Lọc dung lượng cao — tác động hiệu năng:**

```
Kịch bản:
  1M message/phút trong topic
  Filter: 99% bị lọc ra, 1% được xử lý
  Consumer nhận 1M, xử lý 10K

Chi phí network: 1M message × 1KB = 1GB/phút (99% lãng phí!)
Chi phí CPU: deserialize 1M, filter 1M, xử lý 10K
Chi phí đĩa: 1M message được lưu trữ (99% không bao giờ cần)

Ở quy mô này:
  Lọc consumer = không thể chấp nhận
  Producer routing BẮT BUỘC
  Hoặc Kafka Streams pre-filtering
```

### Hiệu Năng (Con Số Production)

| Phương pháp                     | Throughput  | I/O Network        | Overhead CPU               | Overhead Đĩa         |
| ------------------------------- | ----------- | ----------------- | ------------------------- | -------------------- |
| Không lọc                        | 100K msg/s  | 100%              | cơ sở                      | 100%                 |
| Lọc consumer (90% filter)       | 100K msg/s  | 100%              | +5% (deserialize + filter) | 100%                 |
| Filter Kafka Streams             | 100K msg/s  | 2× (đọc + ghi)     | +15% (overhead Streams)    | 10% (chỉ cái đã lọc) |
| Producer routing                 | 100K msg/s  | 10% (chỉ cần thiết) | cơ sở                      | 10%                  |
| Filter ksqlDB                    | 100K msg/s  | 2× (đọc + ghi)     | +10% (ksqlDB)              | 10%                  |

### Production War Story

**Tình huống:** Payment gateway, 500K giao dịch/phút. Một topic "all-transactions" với tất cả các loại: authorization, capture, refund, void.

**Vấn đề:** Consumer xử lý refund nhận tất cả 500K msg/phút, lọc ra 95% (chỉ refund là cần thiết). Network: 500MB/phút, CPU: 40% cho deserialize + filter. Sau khi scale lên 2M msg/phút — network bão hòa, consumer crash.

**Điều tra:**
```
Kiến trúc hiện tại:
  Producer → all-transactions (500K msg/phút)
                          ↓
  Consumer Auth: lọc 90% (xử lý 50K)
  Consumer Capture: lọc 85% (xử lý 75K)
  Consumer Refund: lọc 95% (xử lý 25K) ← vấn đề
  Consumer Void: lọc 98% (xử lý 10K)

  Tổng network: 500K × 4 consumer = 2M lượt gửi message/phút
  95% lưu lượng này bị lãng phí!
```

**Giải quyết:**
```
Kiến trúc mới (producer routing):
  Producer → auth-topic (50K msg/phút)     → Consumer Auth (xử lý 100%)
           → capture-topic (75K msg/phút)  → Consumer Capture (xử lý 100%)
           → refund-topic (25K msg/phút)   → Consumer Refund (xử lý 100%)
           → void-topic (10K msg/phút)     → Consumer Void (xử lý 100%)

  Tổng network: 160K lượt gửi message/phút (giảm 92%!)
  CPU: 0% lãng phí cho lọc
  Đĩa: giảm 68% (chỉ lưu dữ liệu cần thiết)
```

**Bài học sau sự cố:** Lọc consumer là OK cho dung lượng thấp. Ở quy mô > 100K msg/phút — producer routing là bắt buộc.

### Monitoring (JMX, Prometheus, Burrow)

**Các metric ứng dụng:**
```java
// Metric filter
Counter messagesReceived = meterRegistry.counter("kafka.consumer.messages.received");
Counter messagesProcessed = meterRegistry.counter("kafka.consumer.messages.processed");
Counter messagesFiltered = meterRegistry.counter("kafka.consumer.messages.filtered");

Timer processingTime = Timer.builder("kafka.consumer.processing.time")
    .publishPercentiles(0.5, 0.95, 0.99)
    .register(meterRegistry);

// Trong vòng lặp consumer:
messagesReceived.increment();
if (shouldProcess(record)) {
    processingTime.record(() -> process(record));
    messagesProcessed.increment();
} else {
    messagesFiltered.increment();
}
```

### Các Thực Hành Tốt Nhất Cho Highload

```
✅ Producer routing cho dung lượng cao (>100K msg/phút)
✅ Lọc consumer cho các trường hợp đơn giản, dung lượng thấp
✅ Kafka Streams cho lọc phức tạp + chuyển đổi
✅ ksqlDB cho lọc kiểu SQL
✅ Giám sát tỷ lệ filter (tỷ lệ đã xử lý so với đã nhận)
✅ Alert khi tỷ lệ filter cao (>90% = mùi kiến trúc)
✅ Các topic riêng theo loại message (trách nhiệm producer)
✅ DLQ cho các message đã lọc (audit trail)
✅ Config filter động cho các thay đổi tại runtime
✅ Lọc TRƯỚC khi xử lý (chỉ deserialize khi cần)

❌ Lọc consumer cho các topic dung lượng cao
❌ Lọc không giám sát (lãng phí một cách mù quáng)
❌ Tất cả message trong một topic (anti-pattern ở quy mô lớn)
❌ Lọc các message ảnh hưởng đến thứ tự
❌ Không có routing thay thế cho dữ liệu đã lọc
❌ Logic filter phức tạp trong consumer (khó bảo trì)
```

### Các Quyết Định Kiến Trúc

1. **Producer routing > Lọc consumer** — chuyển trí tuệ về producer
2. **Tỷ lệ filter như một mùi kiến trúc** — >90% filter = kiến trúc sai
3. **Một topic mỗi loại message** — lọc tự nhiên tại nguồn
4. **Kafka Streams như một tầng filter** — lọc trung gian trước các consumer
5. **Audit trail cho dữ liệu đã lọc** — DLQ hoặc topic riêng

### Tóm Tắt Cho Senior

- Kafka KHÔNG hỗ trợ lọc phía server — quyết định kiến trúc
- Lọc consumer = đơn giản nhất nhưng kém hiệu quả nhất (lãng phí network/đĩa/CPU)
- Producer routing = hiệu quả nhất nhưng kém linh hoạt nhất
- Tỷ lệ filter > 90% = tín hiệu mạnh mẽ cho thay đổi kiến trúc
- Quản lý offset: commit cho TẤT CẢ message (đã xử lý + đã lọc), không chỉ cái đã xử lý
- Thứ tự có thể bị phá vỡ do lọc — cẩn thận với các message phụ thuộc
- Filter động: dùng config volatile, cập nhật atomic
- Ở highload (>100K msg/phút): lọc consumer không thể chấp nhận
- Giám sát tỷ lệ filter — metric chính cho sức khỏe kiến trúc
- Best practice: một topic mỗi loại message, không cần lọc

**Cần phải biết:**
- Kafka KHÔNG hỗ trợ lọc phía server — quyết định kiến trúc (broker = đường ống ngu ngơ)

- Producer routing — best practice: các loại message khác nhau → các topic khác nhau
- Kafka Streams / ksqlDB — lọc trung gian trước các consumer
- Quản lý offset: commit cho TẤT CẢ message (đã xử lý + đã lọc), không chỉ cái đã xử lý

- Lọc có thể phá vỡ thứ tự cho các message phụ thuộc

**Các câu hỏi phụ thường gặp:**
- *Tại sao Kafka không hỗ trợ lọc phía server?* — Độ phức tạp broker, quét O(n), tác động hiệu năng.
- *Tỷ lệ filter 95% — có phải là vấn đề không?* — Có, 95% network/đĩa bị lãng phí; cần producer routing.
- *Làm sao đảm bảo việc lọc không phá vỡ offset?* — Commit offset cuối cùng của batch, bao gồm các message đã lọc.
- *Khi nào lọc phía consumer là chấp nhận được?* — Dung lượng thấp, filter đơn giản, giải pháp tạm thời.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Kafka lọc message trên broker" — nó không làm vậy, quyết định kiến trúc
- "Lọc consumer cho dung lượng cao là bình thường" — không thể chấp nhận ở >100K msg/phút
- "Tỷ lệ filter 95% là thực hành tốt" — mùi kiến trúc, cần producer routing
- "Offset chỉ được commit cho các message đã xử lý" — các message đã lọc sẽ bị đọc lại
