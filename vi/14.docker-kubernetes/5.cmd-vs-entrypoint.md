# What is the difference between CMD and ENTRYPOINT? (Sự khác biệt giữa CMD và ENTRYPOINT là gì?)

## Junior Level

### Giải Thích Đơn Giản

Cả hai instruction đều định nghĩa những gì sẽ chạy khi container khởi động, nhưng chúng có vai trò khác nhau:

- **ENTRYPOINT** — chương trình chính của container (ví dụ: `java`)
- **CMD** — các tham số mặc định cho chương trình đó (ví dụ: `-jar app.jar`)

RUN — thực thi trong quá trình BUILD image. CMD/ENTRYPOINT — khi KHỞI CHẠY container.

### Phép So Sánh

Hãy nghĩ về một lời gọi hàm trong lập trình:
- `ENTRYPOINT` — tên hàm
- `CMD` — các tham số mặc định

```
java -jar app.jar
^^^^^ ^^^^^^^^^^^^
 |        |
ENTRYPOINT  CMD
```

### Cách Chúng Hoạt Động Cùng Nhau

```dockerfile
ENTRYPOINT ["java", "-jar", "/app.jar"]
CMD ["--server.port=8080"]
```

Chạy `docker run myapp` thực thi: `java -jar /app.jar --server.port=8080`

Chạy `docker run myapp --server.port=9090` thực thi: `java -jar /app.jar --server.port=9090`

### Hai Dạng Viết

**Exec form** (khuyến nghị) — như một mảng JSON:
```dockerfile
ENTRYPOINT ["java", "-jar", "/app.jar"]
```

**Shell form** — như một chuỗi thông thường:
```dockerfile
ENTRYPOINT java -jar /app.jar
```

Luôn dùng Exec form — nó xử lý đúng cách các signal shutdown.

### Cần Nhớ

- `ENTRYPOINT` — lệnh cố định, `CMD` — các tham số mặc định
- Chúng có thể được dùng cùng nhau
- `CMD` dễ bị ghi đè khi khởi chạy, `ENTRYPOINT` — không
- Luôn dùng Exec form `["cmd", "arg1", "arg2"]`
- Chỉ có thể có một `CMD` và một `ENTRYPOINT` trong một Dockerfile

## Middle Level

### Hành Vi Chi Tiết

#### ENTRYPOINT

Định nghĩa file thực thi chính của container:
- **Tính ổn định**: khó bị ghi đè vô tình (cần cờ `--entrypoint`)
- **Mục đích**: biến container thành một "binary có thể thực thi"
- **Tham số**: tất cả các tham số truyền vào `docker run` được nối vào cuối lệnh `ENTRYPOINT`

#### CMD

Định nghĩa lệnh hoặc tham số mặc định cho `ENTRYPOINT`:
- **Tính linh hoạt**: rất dễ bị ghi đè. Bất kỳ tham số nào ở cuối `docker run` đều thay thế hoàn toàn `CMD`
- **Mục đích**: cung cấp hành vi tiêu chuẩn mà người dùng có thể dễ dàng thay đổi

### Ba Kịch Bản Sử Dụng

**Kịch bản 1: Chỉ CMD**
```dockerfile
CMD ["java", "-jar", "/app.jar"]
```
`docker run myapp` → `java -jar /app.jar`
`docker run myapp echo hello` → `echo hello` (CMD bị thay thế hoàn toàn)

**Kịch bản 2: Chỉ ENTRYPOINT**
```dockerfile
ENTRYPOINT ["java", "-jar", "/app.jar"]
```
`docker run myapp` → `java -jar /app.jar`
`docker run myapp --debug` → `java -jar /app.jar --debug`

**Kịch bản 3: ENTRYPOINT + CMD (khuyến nghị)**
```dockerfile
ENTRYPOINT ["java", "-jar", "/app.jar"]
CMD ["--server.port=8080"]
```
`docker run myapp` → `java -jar /app.jar --server.port=8080`
`docker run myapp --server.port=9090` → `java -jar /app.jar --server.port=9090`

Kịch bản 3 (ENTRYPOINT + CMD) — được khuyến nghị.
Kịch bản 1 — cho các script đơn giản.
Kịch bản 2 — khi container nên hoạt động như một "file thực thi".

### Các Lỗi Thường Gặp

| Lỗi                            | Hậu quả                                    | Cách tránh                                      |
| ---------------------------------- | ---------------------------------------------- | ------------------------------------------------- |
| Shell form `ENTRYPOINT java -jar`  | Signal không đến được ứng dụng            | Exec form `["java", "-jar"]`                      |
| Nhiều CMD trong Dockerfile        | Chỉ cái cuối cùng được tính                       | Một CMD mỗi file                                  |
| CMD không có ENTRYPOINT             | CMD dễ bị thay thế vô tình            | Dùng cặp ENTRYPOINT + CMD                         |
| ENTRYPOINT không có CMD             | Developer không thể ghi đè để debug            | Thêm CMD với các tham số mặc định                   |
| Nhầm lẫn về việc ghi đè            | Container chạy sai thứ                 | Hiểu rằng `docker run myapp arg` thay thế CMD |

### Ghi Đè Khi Khởi Chạy

```bash
# Ghi đè CMD — chỉ cần truyền tham số
docker run myapp --custom-arg

# Ghi đè ENTRYPOINT — dùng cờ
docker run --entrypoint /bin/bash myapp
```

### Shell Form vs Exec Form: Sắc Thái Quan Trọng

**Exec form** — lệnh chạy trực tiếp như một process với PID 1. Xử lý đúng cách các signal shutdown. Quan trọng cho Kubernetes và Docker Stop.

**Shell form** — lệnh chạy như một subprocess của `/bin/sh -c`. Các signal của OS đến shell `sh`, không phải ứng dụng. Ứng dụng có thể bị "giết" đột ngột mà không hoàn thành các transaction.

### Cần Nhớ

- Dùng Exec form cho cả hai instruction
- `ENTRYPOINT` cho phần không đổi của lệnh
- `CMD` cho các tham số có thể thay đổi
- Chỉ một `CMD` và một `ENTRYPOINT` được tính (cái cuối cùng trong file)
- Không có việc xử lý signal đúng cách, ứng dụng không thể shutdown đúng cách

### Khi Nào KHÔNG Nên Dùng ENTRYPOINT

Đừng dùng ENTRYPOINT nếu image được dùng cho các lệnh khác nhau
(ví dụ: một image curl/wget cho các request khác nhau). Trong trường hợp này CMD linh hoạt hơn.

## Senior Level

### Thiết Kế Kiến Trúc Của ENTRYPOINT Và CMD

Sự khác biệt giữa ENTRYPOINT và CMD không chỉ là cú pháp — nó là một **design pattern** để tạo các image container có thể tái sử dụng.

### Pattern "Executable Container"

ENTRYPOINT biến một container thành một file thực thi:
```dockerfile
ENTRYPOINT ["java"]
CMD ["-jar", "/app.jar"]
```

Container hành xử như một binary:
```bash
docker run myapp -version          # java -version
docker run myapp -jar other.jar    # java -jar other.jar
```

### Vấn Đề PID 1 Và Xử Lý Signal

Trong Linux, một process với PID 1 có hành vi đặc biệt:
- Không nhận signal theo mặc định (bỏ qua SIGTERM)
- Có trách nhiệm "nhận nuôi" các process mồ côi
- Không tự động kết thúc khi có signal không được xử lý

PID 1 — process chính trong container. Nếu nó không thể kết thúc đúng cách (xử lý SIGTERM),
ứng dụng sẽ bị "giết" đột ngột qua SIGKILL.

**Vấn đề của shell form:**
```dockerfile
ENTRYPOINT java -jar /app.jar
```

Các process trong container:
```
PID 1: /bin/sh -c "java -jar /app.jar"
PID 7: java -jar /app.jar
```

SIGTERM đến `/bin/sh`, nơi không biết phải làm gì với `java`. Kết quả: `docker stop` chờ 10 giây và gửi SIGKILL. Ứng dụng không thực hiện graceful shutdown — các transaction bị gián đoạn, các kết nối không được đóng.

**Các giải pháp:**

1. **Exec form** (khuyến nghị):
```dockerfile
ENTRYPOINT ["java", "-jar", "/app.jar"]
```
Ứng dụng là PID 1, nhận signal trực tiếp.

2. **Tini (hệ thống init)**:
```dockerfile
ENTRYPOINT ["tini", "--", "java", "-jar", "/app.jar"]
```
Tini — init tối thiểu, forward signal đúng cách và reap các process zombie.

3. **Cờ Docker --init**:
```bash
docker run --init myapp
```

### Tương Tác Với Kubernetes

Trong Kubernetes, ENTRYPOINT và CMD ánh xạ đến các trường của container:

| Docker       | Kubernetes  |
| ------------ | ----------- |
| `ENTRYPOINT` | `command`   |
| `CMD`        | `args`      |

```yaml
containers:
- name: app
  image: myapp
  command: ["java", "-jar"]     # ghi đè ENTRYPOINT
  args: ["--server.port=9090"]   # ghi đè CMD
```

**Quan trọng:** nếu `command` và `args` được chỉ định trong manifest Kubernetes, chúng **thay thế hoàn toàn** ENTRYPOINT và CMD của Docker.

### Đánh Đổi (Trade-offs)

| Cách tiếp cận           | Điểm cộng                              | Điểm trừ                               |
| ------------------ | --------------------------------- | ------------------------------------ |
| Chỉ CMD           | Linh hoạt cho developer         | Dễ bị thay thế vô tình        |
| Chỉ ENTRYPOINT    | Ổn định                         | Khó ghi đè để debug      |
| ENTRYPOINT + CMD   | Tốt nhất của cả hai                      | Cần hiểu sự tương tác      |
| Entrypoint script  | Khởi tạo linh hoạt             | Thêm một layer, cần bảo trì    |
| Tini               | Signal đúng + reap zombie     | Dependency bổ sung               |

### Edge Case

- **Ghi đè trong Kubernetes**: `command` trong manifest K8s thay thế hoàn toàn ENTRYPOINT. Nếu developer kỳ vọng một entrypoint script chạy migration, nhưng K8s đã ghi đè `command` — các migration sẽ không chạy.
- **Kế thừa ENTRYPOINT**: nếu image nền có một ENTRYPOINT và Dockerfile con không có, ENTRYPOINT của cha được kế thừa. Điều này có thể dẫn đến hành vi không mong muốn.
- **Phân tích mảng JSON**: `ENTRYPOINT ["java", "-jar", "/app.jar"]` — đây là JSON. Một lỗi trong dấu ngoặc kép hoặc dấu phẩy sẽ khiến build thất bại.
- **CMD dạng shell form + ENTRYPOINT dạng exec form**: `ENTRYPOINT ["java"]` + `CMD -jar app.jar` — CMD chạy như `/bin/sh -c "java -jar app.jar"`, ENTRYPOINT bị bỏ qua.

### Pattern "Entry Point Script"

Với các ứng dụng phức tạp, một entrypoint script được dùng:

```dockerfile
COPY docker-entrypoint.sh /usr/local/bin/
RUN chmod +x /usr/local/bin/docker-entrypoint.sh
ENTRYPOINT ["docker-entrypoint.sh"]
CMD ["java", "-jar", "/app.jar"]
```

```bash
#!/bin/sh
# docker-entrypoint.sh

# Chạy các migration
if [ "$RUN_MIGRATIONS" = "true" ]; then
    java -jar /app.jar --migrate
    exit 0
fi

# Khởi chạy ứng dụng (exec thay thế process của script)
exec "$@"
```

`exec "$@"` thay thế process của shell script bằng lệnh đích, giữ nguyên PID 1 và signal. Không có `exec`, script vẫn là PID 1 và signal không đến được ứng dụng.

### Anti-pattern

1. **Shell form không xử lý signal:** `ENTRYPOINT java -jar /app.jar` — graceful shutdown không hoạt động.
2. **Nhiều CMD/ENTRYPOINT:** chỉ cái cuối cùng được tính.
3. **ENTRYPOINT không có CMD trong các image dành cho developer:** không thể ghi đè để debug.
4. **Entrypoint script không có `exec`:** script vẫn là PID 1, signal bị mất.
5. **Secret trong CMD/ENTRYPOINT:** `CMD ["java", "-jar", "app.jar", "--db-password=secret"]` — hiển thị trong `docker inspect` và `ps`.

### Hiệu Năng

| Cách tiếp cận         | Thời gian shutdown         | Graceful shutdown | Reap zombie |
| ---------------- | --------------------- | ----------------- | ----------- |
| Shell form       | 10s (timeout SIGKILL) | Không                | Không          |
| Exec form        | < 1s (SIGTERM)        | Có                | Không          |
| Exec form + tini | < 1s                  | Có                | Có          |
| Docker --init    | < 1s                  | Có                | Có          |

### Tóm Tắt

- Dùng **Exec form** cho cả hai instruction — quan trọng cho việc xử lý signal.
- `ENTRYPOINT` + `CMD` cùng nhau tạo ra một image linh hoạt và có thể tái sử dụng.
- Hiểu ánh xạ đến `command`/`args` của Kubernetes.
- Vấn đề PID 1 là có thật: dùng exec form hoặc tini.
- Các entrypoint script với `exec "$@"` — tiêu chuẩn cho các kịch bản khởi tạo phức tạp.
- Chỉ một instruction `CMD` và một instruction `ENTRYPOINT` có thể tồn tại trong một Dockerfile (cái cuối cùng được tính).

## Interview Cheat Sheet

**Cần phải biết:**
- ENTRYPOINT — lệnh cố định (PID 1), CMD — các tham số mặc định
- ENTRYPOINT + CMD cùng nhau — pattern được khuyến nghị ("executable container")
- Exec form `["cmd", "arg"]` là bắt buộc để xử lý signal đúng cách
- Docker CMD dễ bị ghi đè (`docker run image args`), ENTRYPOINT — qua `--entrypoint`
- Trong K8s: Docker ENTRYPOINT → `command`, CMD → `args` (thay thế hoàn toàn)
- Vấn đề PID 1: process không có signal handler không thể graceful shutdown
- Giải pháp cho PID 1: exec form, tini, hoặc `docker run --init`

**Các câu hỏi phụ thường gặp:**
- *"Điều gì xảy ra với `docker run myapp arg`?"* — `arg` thay thế CMD, được nối vào ENTRYPOINT
- *"Tại sao shell form nguy hiểm trong K8s?"* — Signal đến `/bin/sh`, không phải ứng dụng; graceful shutdown không hoạt động
- *"`exec "$@"` làm gì trong một entrypoint script?"* — Thay thế process của script bằng lệnh đích, giữ nguyên PID 1
- *"Bạn có thể có nhiều CMD trong một Dockerfile không?"* — Có, nhưng chỉ cái cuối cùng được tính

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "CMD và ENTRYPOINT là cùng một thứ" (ngữ nghĩa và hành vi ghi đè khác nhau)
- "Tôi dùng shell form cho tiện" (graceful shutdown bị hỏng)
- "Trong K8s command và args bổ sung cho ENTRYPOINT/CMD của Docker" (chúng thay thế hoàn toàn!)
- "PID 1 không quan trọng trong một container" (quan trọng cho việc xử lý signal)
