# When Is It Better to Use CompletableFuture vs Reactive Programming? (Khi nào nên dùng CompletableFuture so với reactive programming)

## 🟢 Junior Level

### Câu Trả Lời Ngắn Gọn

- **CompletableFuture** — khi bạn cần thực hiện một request bất đồng bộ và nhận một kết quả.
- **Reactive programming (Reactor, RxJava)** — khi bạn cần xử lý một luồng dữ liệu (0..N phần tử).

```java
// CompletableFuture — một request, một phản hồi
CompletableFuture<User> cf = userService.findByIdAsync(1L);
User user = cf.join();

// Reactor — luồng phần tử
Flux<Event> events = eventService.streamAll();
events.subscribe(System.out::println);
```

**Quy tắc chung:** Nếu bạn cần 2-3 lời gọi API song song — hãy dùng `CompletableFuture`. Nếu bạn có luồng dữ liệu — hãy dùng Reactor.

## 🟡 Middle Level

### Khi CompletableFuture Là Đủ

```java
// Trường hợp sử dụng điển hình: các lời gọi song song
CompletableFuture<User> userFuture = userClient.getByIdAsync(userId);
CompletableFuture<Order> orderFuture = orderClient.getLatestAsync(userId);

CompletableFuture<UserWithOrder> combined = userFuture.thenCombine(
    orderFuture, UserWithOrder::new
);
```

CompletableFuture bao phủ 90% các tác vụ microservice:
- Truy vấn DB
- Gọi một API bên ngoài
- Kết hợp nhiều kết quả

### Khi Bạn Cần Reactivity

**1. Backpressure**

`CompletableFuture` không có cơ chế backpressure. Nếu bên tạo dữ liệu sinh ra dữ liệu nhanh hơn bên tiêu thụ có thể xử lý, hàng đợi trong `Executor` sẽ tăng lên cho đến khi `OutOfMemoryError`.

`Flux` reactive cho phép bên tiêu thụ yêu cầu số lượng phần tử mà nó có thể xử lý:
```java
// Consumer kiểm soát tốc độ
flux.subscribe(element -> process(element), error -> {}, () -> {},
    subscription -> subscription.request(10));  // chỉ 10 phần tử
```

**2. Xử Lý Stream**

Nếu bạn cần xử lý dữ liệu ngay khi nó đến (từng phần từ S3, Kafka topic, WebSocket), `CompletableFuture` buộc bạn phải hoặc thu thập mọi thứ trong bộ nhớ hoặc viết các chuỗi đệ quy phức tạp. `Flux` làm điều này ngay từ đầu.

### So Sánh

| Đặc điểm      | CompletableFuture | Reactive (Reactor)  |
| ------------------- | ----------------- | ------------------- |
| **Kết quả**         | Đúng 1         | 0 ... ∞             |
| **Backpressure**    | Không                | Có                 |
| **Toán tử**       | ~20               | ~200                |
| **Đường cong học tập**  | Thấp               | Cao                 |
| **Debug**       | Trung bình            | Khó khăn            |

## 🔴 Senior Level

### Tác Động Của Virtual Threads (Java 21+)

Với **Virtual Threads**, nhu cầu về reactive programming trong các tác vụ I/O điển hình được giảm bớt:

```java
// Thay vì code reactive — code đồng bộ đơn giản
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    User user = userClient.getById(userId);       // chặn, nhưng rẻ
    Order order = orderClient.getLatest(userId);  // mở rộng tốt
    return new UserWithOrder(user, order);
}
```

Virtual Threads làm cho code đồng bộ chặn có thể mở rộng được. Reactivity vẫn còn liên quan chỉ ở những nơi các yếu tố sau quan trọng:
- **Bản chất event-driven** (streaming, WebSocket)
- **Backpressure** (kiểm soát tải)

### Project Loom Và Project Valhalla

**Project Loom** (Virtual Threads) có sẵn trong Java 21 và đơn giản hóa việc viết code chặn có thể mở rộng.

**Project Valhalla** (value types) đang được phát triển — có khả năng giảm overhead của `CompletableFuture` thông qua chuyên biệt hóa kiểu nguyên thủy, nhưng điều này chưa được xác nhận.

### Ma Trận Quyết Định Cuối Cùng

1. **CompletableFuture** — 2-3 lời gọi API song song, kết hợp kết quả.
2. **CompletableFuture + Virtual Threads** — các thao tác chặn có thể mở rộng.
3. **Reactive** — gateway cho hàng triệu sự kiện, Kafka Streams, cần backpressure.

### Tóm Tắt

- **CF** — cho các **request** bất đồng bộ.
- **Reactive** — cho các **luồng** bất đồng bộ.
- Đừng dùng reactivity nơi CF là đủ; độ phức tạp bảo trì của code reactive là rất lớn.

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- CompletableFuture — 1 request, 1 kết quả. ~20 toán tử, đường cong học tập thấp
- Reactive (Reactor) — 0..N phần tử, backpressure, ~200 toán tử, đường cong học tập cao
- CF cho 2-3 lời gọi API song song. Reactor cho streaming, Kafka, WebSocket
- Virtual Threads (Java 21+) giảm nhu cầu về Reactor trong các tác vụ I/O điển hình
- Ma Trận Quyết Định: CF → CF + Virtual Threads → Reactive (theo độ phức tạp)

**Các câu hỏi phụ thường gặp:**
- **Khi nào chọn CompletableFuture?** — 2-3 lời gọi API song song, kết hợp kết quả
- **Khi nào Reactive?** — Cần backpressure, bản chất event-driven (Kafka, WebSocket), hàng triệu sự kiện
- **Virtual Threads có "giết chết" Reactor không?** — Không. VT cho chặn I/O, Reactor cho streaming + backpressure
- **Backpressure là gì?** — Consumer kiểm soát tốc độ: yêu cầu request(N) phần tử, ngăn OOM

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Reactive luôn tốt hơn CompletableFuture" — độ phức tạp bảo trì rất lớn, CF là đủ cho 90% tác vụ
- "Virtual Threads thay thế Reactive" — không, VT không cung cấp backpressure hoặc streaming
- "CompletableFuture hỗ trợ backpressure" — không, dưới quá tải hàng đợi tăng đến OOM
