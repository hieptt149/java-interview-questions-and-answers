# What advantages do immutable objects provide? (Immutable object mang lại ưu điểm gì?)

---

## Basic Level

Immutable object là các object không thể thay đổi sau khi tạo. Thay vì sửa đổi chúng, một object mới với dữ liệu mới được tạo ra.

### Các Ưu Điểm Chính

1. **Dễ hiểu** — một object luôn ở một trạng thái, không cần theo dõi lịch sử sửa đổi
2. **An toàn** — không ai có thể vô tình thay đổi dữ liệu của object
3. **Dễ kiểm thử hơn** — object luôn hành xử theo cùng một cách

### Ví Dụ Đơn Giản
```java
String s1 = "Hello";
String s2 = s1.concat(" World"); // s1 không thay đổi, s2 là một chuỗi mới
// s1 vẫn là "Hello"
```

### Cái Giá Của Tính Bất Biến

1. **Áp lực GC quá mức** khi tạo hàng loạt object (1000 lần nối = 1000 object)
2. **Overhead sao chép** cho các cấu trúc lớn (deep copy O(n))
3. **API bất tiện** — mỗi thay đổi = tạo một object mới

## Intermediate Level

### Thread-Safety Không Cần Lock

Immutable object **thread-safe theo mặc định**:
- Nhiều thread có thể đồng thời đọc một object mà không có nguy cơ Race Condition
- Không cần `synchronized`, `ReentrantLock` — không có lock, không có Deadlock

### Key Lý Tưởng Cho HashMap

`hashCode()` của object sẽ không bao giờ thay đổi — object sẽ không bị "thất lạc" trong bucket của hash table.

### Không Có Side Effect

Các method trả về các object mới thay vì sửa đổi các object hiện có. Bạn có thể truyền một object vào bất kỳ method nào và tự tin rằng nội dung của nó sẽ không thay đổi.

### Tái Sử Dụng (Pattern Flyweight)
- **String Pool** — các chuỗi giống hệt nhau chia sẻ một object
- **Integer Cache** — các số từ -128 đến 127 được tái sử dụng
- `Boolean.TRUE` / `Boolean.FALSE` — các instance duy nhất

### Ví Dụ: Trả Về An Toàn Từ Getter
```java
public final class Config {
    private final Map<String, String> properties;

    public Config(Map<String, String> properties) {
        this.properties = Map.copyOf(properties);
    }

    public Map<String, String> getProperties() {
        return properties; // an toàn — Map.copyOf đã trả về một map bất biến
    }
}
```

## Advanced Level

### Các Đảm Bảo Của Java Memory Model

Các trường được đánh dấu `final` nhận được các đảm bảo visibility đặc biệt. Sau khi constructor hoàn thành, tham chiếu đến object được coi là được **publish an toàn** — bất kỳ thread nào cũng sẽ thấy các giá trị đúng mà không cần thêm memory barrier.

### Tác Động Đến Garbage Collection

- Immutable object được tạo trong Young Generation và chết ở đó
- Sửa đổi một object cũ trong Old Generation yêu cầu một **Write Barrier** — immutable object loại bỏ overhead như vậy
- Các tham chiếu được thiết lập một lần khi tạo — GC không cần theo dõi các thay đổi liên thế hệ

### Khả Năng Mở Rộng Trong Các Hệ Thống Phân Tán

- **Truy cập Lock-free** — đọc mà không cần lock loại bỏ contention giữa các thread, cái mà dưới contention cao có thể giảm throughput 50-90%.
- **Không có side-effect** — phù hợp với các nguyên tắc lập trình hàm
- **Cache Friendly** — caching an toàn mà không có nguy cơ dữ liệu bị "nhiễm độc"

### Tóm Tắt Cho Advanced
- Ưu điểm chính: **giảm tải nhận thức (cognitive load)** trong môi trường đa luồng. Không cần nghĩ: "Còn ai có thể thay đổi object này không?". Bạn đọc một object — và tự tin rằng nó sẽ không thay đổi dưới tay bạn.
- Lợi ích từ việc loại bỏ lock vượt qua chi phí cấp phát dưới các workload đọc nặng. Thay vì `synchronized` trên mỗi lần đọc — chỉ cần đọc mà không cần lock. Dưới các workload ghi nặng, việc cấp phát các object mới có thể trở thành một nút thắt cổ chai.
- Tính bất biến là nền tảng cho các Domain Model đáng tin cậy
- Trong các hệ thống tải cao, tính bất biến thắng nhờ khả năng mở rộng

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Thread-safety không cần lock — không có race condition, không có Deadlock
- Key lý tưởng cho HashMap — `hashCode()` không bao giờ thay đổi
- Pattern Flyweight — String Pool, Integer Cache, tái sử dụng object
- Các method không có side-effect — phù hợp với các nguyên tắc lập trình hàm
- Publish an toàn thông qua các trường `final` — các đảm bảo visibility của JMM
- Đọc lock-free loại bỏ contention (throughput 50-90% dưới contention cao)
- Lợi ích GC: không có Write Barrier, các object Young Generation được dọn dẹp miễn phí
- Cache Friendly — caching an toàn mà không có nguy cơ dữ liệu bị "nhiễm độc"

**Các câu hỏi phụ thường gặp:**
- *Tại sao immutable object thread-safe?* — Không có ghi sau khi tạo = race condition là không thể xảy ra
- *Tính bất biến ảnh hưởng đến GC như thế nào?* — Các object tồn tại ngắn được dọn dẹp trong Minor GC, không có tham chiếu xuyên thế hệ
- *Flyweight là gì?* — Pattern để tái sử dụng các object giống hệt nhau (String Pool, Integer Cache)
- *Có cái giá nào cho tính bất biến không?* — Áp lực GC quá mức khi tạo hàng loạt, overhead sao chép

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tính bất biến luôn làm chậm mọi thứ" — trên các workload đọc nặng không có lock, nó nhanh hơn
- "synchronized cần thiết cho các immutable object" — chúng thread-safe theo mặc định
- "Immutable object không thể cache được" — chúng LÝ TƯỞNG cho caching
- "Flyweight chỉ dành cho chuỗi" — Integer, Boolean cũng dùng pattern này
