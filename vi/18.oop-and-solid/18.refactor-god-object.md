# How to Refactor God Object? (Cách refactor God Object?)

---

## 🟢 Junior Level

### Định Nghĩa Đơn Giản

**God Object** là một class "làm mọi thứ." Nó chứa hàng trăm phương thức, hàng chục trường, và chịu trách nhiệm cho nhiều tác vụ không liên quan. Đây là một anti-pattern vì một class như vậy không thể đọc, test, và bảo trì.

### Analogy

Hãy tưởng tượng một con dao đa năng Thụy Sĩ khổng lồ với 200 công cụ. Để tìm đúng tuốc nơ vít, bạn phải xem qua mọi thứ: từ cái mở nắp chai đến cái cưa. Tốt hơn là có một bộ 10 con dao nhỏ, mỗi cái cho một nhiệm vụ riêng.

### Ví Dụ Đơn Giản

```java
// XẤU: God Object — làm MỌI THỨ
public class UserManager {
    public void createUser() { ... }
    public void deleteUser() { ... }
    public void sendEmail() { ... }
    public void generateReport() { ... }
    public void connectToDatabase() { ... }
    public void validateInput() { ... }
    public void logActivity() { ... }
    public void exportToPdf() { ... }
    // 50 phương thức nữa...
}

// TỐT: chia theo trách nhiệm
public class UserService { public void createUser() { ... } }
public class EmailService { public void sendEmail() { ... } }
public class ReportService { public void generateReport() { ... } }
public class Logger { public void logActivity() { ... } }
```

### Khi Nào Dùng (nói chính xác hơn, khi nào KHÔNG nên để lại một God Object)

- Khi một class có > 30 phương thức — đã đến lúc suy nghĩ về nó.
- Khi một class có các phương thức cho DB, UI, email, và business logic cùng lúc.
- Khi bạn không thể mô tả class này làm gì trong một câu.

## 🟡 Middle Level

### Cách Hoạt Động Nội Bộ

Các God Object phát triển theo tiến hóa. Không ai tạo ra một cái có chủ ý — nó xảy ra thông qua entropy dần dần:

1. **Bắt đầu:** Một service nhỏ với 3 phương thức.
2. **Phát triển:** "Tôi sẽ chỉ thêm một phương thức nữa ở đây, tại sao phải tạo một class mới?"
3. **Khủng hoảng:** 200 phương thức, 50 trường, thời gian biên dịch tăng, các test mất vài phút.

Metric **LCOM (Lack of Cohesion in Methods)** chính thức hóa vấn đề:
- LCOM > 1.0 nghĩa là các phương thức của class không liên quan với nhau — class là ứng viên để chia tách.

### Thuật Toán Phân Rã

**Bước 1: Phân Tích Tính Năng**

Nhóm các phương thức và trường theo ý nghĩa nghiệp vụ, mà không đụng vào code:

| Nhóm              | Các phương thức                                              | Các trường                         | Class Mới       |
| ------------------ | ---------------------------------------------------- | ------------------------------ | --------------- |
| CRUD User          | `createUser`, `deleteUser`, `updateUser`             | `userRepository`               | `UserService`   |
| Email              | `sendEmail`, `sendWelcomeEmail`, `sendResetPassword` | `emailClient`, `emailTemplate` | `EmailService`  |
| Logging            | `logLogin`, `logError`, `logAudit`                   | `logWriter`                    | `AuditLogger`   |
| Report             | `generateReport`, `exportToPdf`, `exportToCsv`       | `reportTemplate`               | `ReportService` |

**Bước 2: Trích Xuất Các Interface (ISP)**

Nếu God Object được dùng bởi các client khác nhau cho các mục đích khác nhau, trích xuất các interface hẹp:
```java
public interface UserReader { User findById(Long id); }
public interface UserWriter { void save(User user); }
public interface UserNotifier { void notifyUser(Long userId, String message); }
```
Mỗi client chỉ phụ thuộc vào interface nó cần, không phải toàn bộ monolith.

**Bước 3: Trích Xuất Các Class Thông Qua Delegation**

Đầu tiên, biến God Object thành một facade:
```java
public class UserManager { // God Object cũ
    private final UserService userService = new UserService();
    private final EmailService emailService = new EmailService();

    // Các delegate — giữ các client không thay đổi trong lúc này
    public void createUser(User u) { userService.create(u); }
    public void sendEmail(String to, String msg) { emailService.send(to, msg); }
}
```
Sau đó dần dần chuyển các client sang dùng trực tiếp các class mới.

### Các Lỗi Refactoring Thường Gặp

| Lỗi                                                                                                                               | Giải pháp                                                                                                                                                                                 |
| --------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Shared state:** 50 trường được dùng qua lại bởi tất cả các phương thức                                                                        | Truyền trạng thái như các tham số phương thức hoặc tạo một **Context Object**                                                                                                                           |
| **Tính toàn vẹn transaction:** God Object đảm bảo tính atomic thông qua `synchronized`                                                            | Sau khi chia tách, cần một transaction coordinator hoặc pattern Saga (một mẫu cho distributed transaction: nếu một bước thất bại, một hành động compensating rollback lại các bước trước đó)              |
| **Class ký sinh:** Trích xuất một class, nhưng nó vẫn phụ thuộc vào 80% các trường của God Object                                         | Đào sâu phân tích — có lẽ việc trích xuất quá hời hợt                                                                                                                         |
| **Big Ball of Mud:** Mọi thứ kết nối với mọi thứ, không có ranh giới rõ ràng                                                         | Bắt đầu với test — nếu một phương thức không thể test mà không có 20 mock, đó là điểm cắt của bạn                                                                                                   |

### So Sánh Các Cách Tiếp Cận

| Cách tiếp cận          | Ưu điểm                                                      | Nhược điểm                                           | Khi Nào Áp Dụng                              |
| ----------------- | --------------------------------------------------------- | ------------------------------------------------- | ------------------------------------------ |
| **Extract Class** | Tách biệt rõ ràng, mỗi class — một trách nhiệm           | Overhead thời gian, cần cập nhật tất cả client         | Chiến lược chính                              |
| **Facade**        | Ẩn nhanh chóng độ phức tạp, client không hỏng              | Biện pháp tạm thời — Facade vẫn biết mọi thứ | Giai đoạn trung gian                         |
| **Mediator**      | Tách rời các phương thức đã giao tiếp tích cực với nhau | Thêm một class nữa                           | Khi có giao tiếp nội bộ dày đặc  |
| **Strategy**      | Thay thế logic điều kiện (if/switch) bằng polymorphism   | Nhiều class hơn                                      | Khi God Object có 50+ nhánh if/else   |

### Khi Nào KHÔNG Nên Refactor

- **Legacy không có test** — viết characterization test trước, sau đó refactor. Không có test, bạn sẽ không biết liệu bạn có làm hỏng gì không.
- **Dự án end-of-life** — nếu mọi thứ sẽ bị xóa trong một tháng, khoản đầu tư sẽ không đáng giá.
- **God DTO** — nếu "God Object" chỉ là một DTO với 100 trường và không có hành vi, đó không phải là vấn đề thiết kế, mà là vấn đề domain model (giải quyết thông qua Bounded Context).

## 🔴 Senior Level

### Triển Khai Nội Bộ Sâu

#### Cấp Độ JVM: Bố Cục Bộ Nhớ God Object

Một class lớn với 50 trường tạo ra một object với overhead đáng kể:

```
Object Header:  12 byte (mark word + con trỏ class)
50 trường:      50 × 4 byte (tham chiếu) = 200 byte
Padding:        ~4 byte (padding đến ranh giới 8 byte)
Tổng:          ~216 byte mỗi instance
```

Sau khi chia thành 10 class với 5 trường mỗi cái:
```
10 × (12 header + 20 ref + 0 padding) = 10 × 32 = 320 byte
+ 9 × 4 byte (tham chiếu giữa các object) = 36 byte
Tổng: ~356 byte
```

**Overhead:** ~140 byte mỗi instance (nhiều hơn 65%). Về con số tuyệt đối — không đáng kể cho các ứng dụng nghiệp vụ. Nhưng trong highload với hàng triệu object — 140 MB cho mỗi 1 triệu instance.

#### Bytecode Và JIT

God Object với 200 phương thức:
- Constant pool tăng lên — nhiều overhead tải class hơn.
- JIT không thể inline hiệu quả các phương thức từ một class khổng lồ — các register CPU tràn, JIT rơi lại về interpreter.
- **Các phương thức hot** (được gọi thường xuyên) "chìm" giữa các phương thức cold — JIT compiler dành ngân sách biên dịch để phân tích toàn bộ class.

Sau khi chia tách:
- Các phương thức hot trong các class nhỏ được inline mạnh mẽ.
- Ngân sách biên dịch JIT được dùng hiệu quả.
- Sử dụng CPU instruction cache cao hơn — code class nhỏ vừa trong L1 cache (32 KB).

### Đánh Đổi Kiến Trúc

| Cách tiếp cận                        | Ưu điểm                                                | Nhược điểm                                                                          |
| ------------------------------- | --------------------------------------------------- | ----------------------------------------------------------------------------- |
| **Phân rã hoàn toàn**          | Mỗi class SRP, dễ test, dễ thay thế       | "Class Explosion" — 50 class nhỏ thay vì một, điều hướng khó hơn   |
| **Phân rã một phần**       | Cân bằng giữa đơn giản và tính module           | Các ranh giới có thể mờ nhạt                                                      |
| **Facade + các class nội bộ**   | Tương thích ngược, migration dần dần           | Facade vẫn là một điểm coupling                                               |
| **Không đụng vào**                 | Không có rủi ro làm hỏng                               | Nợ kỹ thuật tăng, onboard developer mới mất nhiều tuần                   |

### Edge Cases

**1. Shared Mutable State:**
God Object với 50 trường được dùng qua lại bởi tất cả các phương thức. Khi chia tách, mỗi trường mới phải "thuộc về" một class.

**Giải pháp — Context Object:**
```java
public class OrderProcessingContext {
    public Order order;
    public User customer;
    public PaymentMethod payment;
    public ShippingDetails shipping;
}
// Được truyền như một tham số thay vì shared state
```

**2. Tính Toàn Vẹn Transaction Sau Khi Chia Tách:**
```java
// Trước: một phương thức synchronized trong God Object
public synchronized void processOrder() {
    saveToDb(order);       // Repository 1
    sendEmail(customer);   // Service 2
    updateInventory(item); // Service 3
}
```
Sau khi chia tách, `processOrder` phải điều phối 3 service. `synchronized(this)` không còn hoạt động nữa.

**Giải pháp:**
- Trong một monolith: `@Transactional` trên phương thức facade.
- Trong một hệ thống phân tán: **Saga Pattern** với các compensating transaction.

**3. Circular Dependency Sau Khi Chia Tách:**
```java
class UserService { EmailService email; }
class EmailService { UserService user; } // CHU TRÌNH!
```
Xảy ra khi các class được trích xuất tham chiếu lẫn nhau.

**Giải pháp:** Đưa vào một coordinator thứ ba (`UserNotificationOrchestrator`) hoặc dùng event (`ApplicationEventPublisher`).

**4. God Object Như Một Class "Util":**
```java
public class Utils {
    public static void sort(...) { ... }
    public static void validate(...) { ... }
    public static void format(...) { ... }
    public static void encrypt(...) { ... }
}
```
Một God Object static. Không thể mock, không thể kế thừa.

**Giải pháp:** Chia thành `SortUtils`, `Validator`, `Formatter`, `Encryptor` — hoặc tốt hơn, dùng các thư viện có sẵn (Guava, Apache Commons).

### Tác Động Hiệu Năng

| Metric             | God Object (200 phương thức)      | Sau Khi Chia Tách                                 |
| ------------------ | ----------------------------- | ------------------------------------------------ |
| Class loading      | 50-100 KB metaspace           | 10 × 5 KB = 50 KB metaspace                     |
| JIT warmup         | 30-60 giây (phân tích 200 phương thức) | 10-20 giây (mỗi class biên dịch riêng biệt)  |
| L1 I-cache miss    | 15-25% (code không vừa)     | 5-8% (các class nhỏ thân thiện với cache)          |
| Benchmark (ops/ms) | ~8,000 (hot path)             | ~12,000 (+50% sau khi tách logic hot/cold)   |

**Tách Logic Hot vs Cold:**
- Hot: validation, tính toán, serialization — được gọi hàng nghìn lần/giây.
- Cold: logging, cấu hình, metric — được gọi vài lần/giây.
- Khi chúng ở trong một class, JIT biên dịch cả hai loại vào một blob code — CPU cache bị ô nhiễm.
- Tách biệt mang lại ưu tiên cho các class hot trong instruction cache.

### Tác Động Bộ Nhớ Và GC

- **God Object:** Một object lớn = một cấp phát lớn. Nếu object > 512 KB — nó đi thẳng đến Old Generation (TLAB overflow), kích hoạt Full GC.
- **Các object đã chia tách:** Nhiều object nhỏ = cấp phát trong Eden, thu gom Young GC nhanh.
- **GC pause:** God Object 1 MB = 10-50 ms cho Full GC. 100 object nhỏ = 1-3 ms cho Young GC.

### Thread Safety

- **God Object + `synchronized`** = bottleneck. Một monitor khóa TẤT CẢ các phương thức, ngay cả các phương thức không liên quan. Thread A gọi `logActivity()`, Thread B chờ, mặc dù nó gọi `createUser()` — chúng không xung đột trên dữ liệu, nhưng bị khóa trên cùng một monitor.
- **Sau khi chia tách:** Mỗi class có monitor riêng của nó. `AuditLogger.synchronized` và `UserService.synchronized` không khóa lẫn nhau.
- **Lock striping:** Thay vì một `synchronized`, dùng `ReentrantLock` cho mỗi nhóm dữ liệu logic.

### Câu Chuyện Chiến Tranh Production

**Vấn đề:** Một payment service `PaymentProcessor` có 4500 dòng, 120 phương thức, 35 trường. Nó xử lý 500 transaction/giây. Dưới tải đỉnh (Black Friday, 5000 transaction/giây) service suy giảm: latency tăng từ 50 ms lên 2 giây.

**Chẩn đoán:**
- Async Profiler cho thấy 60% CPU dành cho tranh chấp `synchronized` — 15 thread chờ trên một monitor.
- LCOM = 4.2 (giá trị quan trọng > 1.0) — class có 4 cụm phương thức không liên quan.
- Kích thước file class: 180 KB (chuẩn < 20 KB).

**Giải pháp (từng bước, không dừng service):**
1. **Tuần 1:** Viết các characterization test (các test bắt lại hành vi hệ thống hiện tại — bạn không biết liệu nó có đúng không, nhưng bạn biết nó hoạt động; sau khi refactoring, các test này đảm bảo hành vi không thay đổi) cho mỗi phương thức public (87 test).
2. **Tuần 2:** Trích xuất `PaymentValidator` (15 phương thức) — LCOM giảm xuống 3.1.
3. **Tuần 3:** Trích xuất `PaymentLogger` (8 phương thức), `FraudDetector` (20 phương thức) — LCOM 1.8.
4. **Tuần 4:** `PaymentProcessor` trở thành một facade, delegate đến 4 class mới. Client không thay đổi.
5. **Tuần 5:** Thay thế `synchronized` bằng `ReentrantReadWriteLock` — các thao tác đọc (kiểm tra status) không còn khóa lẫn nhau.
6. **Tuần 6:** Chuyển các client sang gọi trực tiếp các service mới, loại bỏ facade.

**Kết quả:**
- Latency ở 5000 TPS: 50 ms (trước đây 2000 ms — cải thiện 40 lần).
- GC pause: 3 ms (trước đây 50 ms).
- LCOM: 0.4 (chuẩn < 1.0).

### Monitoring Và Chẩn Đoán

**ArchUnit** — các quy tắc cho CI:
```java
@ArchTest
static final ArchRule no_god_objects =
    noClasses().that().haveNameNotMatching(".*(Config|Application).*")
        .should().haveMethodsMoreThan(30);
```

**SonarQube** — các metric:
- `NCSS` (Non-Commenting Source Statements) — mục tiêu: < 500 mỗi class.
- `Cyclomatic Complexity` — mục tiêu: < 15 mỗi phương thức.
- `LCOM` — mục tiêu: < 1.0.
- Quy tắc `S1448`: "Classes should not have too many methods" (ngưỡng mặc định: 35).

**Structure101** — trực quan hóa "ngôi sao" kết nối. God Object xuất hiện như một node có độ tập trung tối đa.

**jQAssistant** — phân tích dựa trên Neo4j:
```cypher
MATCH (c:Class)
WHERE size((c)-[:DECLARES]->()) > 50
RETURN c.name, size((c)-[:DECLARES]->()) as methodCount
ORDER BY methodCount DESC
```

**IntelliJ IDEA** — plugin "Metrics Reloaded": hiển thị LCOM, coupling, độ sâu inheritance ngay trong editor.

### Best Practices Cho Highload

1. **Tách logic hot/cold** — các class hot nên nhỏ và thân thiện với JIT.
2. **Độ chi tiết lock** — một `synchronized` trên God Object = không có nguy cơ deadlock, nhưng throughput bị giết chết. Chia tách = locking chi tiết hơn.
3. **Context Object thay vì shared state** — truyền context bất biến, tránh mutation.
4. **Saga cho distributed transaction** — sau khi chia God Object thành microservices, `@Transactional` không còn hoạt động nữa.
5. **Refactoring dần dần** — delegation trước (facade), sau đó migration client, sau đó loại bỏ facade. Không Big Bang.
6. **Characterization test TRƯỚC TIÊN** — không có chúng, refactoring một God Object là bắn trong bóng tối.
7. **Bounded Context (DDD)** (bounded context từ Domain-Driven Design — chia hệ thống theo ranh giới nghiệp vụ, nơi mỗi phần có model và thuật ngữ riêng của nó) — cắt theo ranh giới nghiệp vụ, không phải kỹ thuật. `UserService`, `PaymentService`, `NotificationService` — đây là các bounded context.

### Tóm Tắt Cho Senior

- Cắt God Object theo **Bounded Context** (từ DDD), không phải các tầng kỹ thuật.
- Dùng delegation như một bước trung gian — migration an toàn không có downtime.
- Đừng sợ "Class Explosion" — 20 class SRP nhỏ tốt hơn một con quái vật không thể quản lý.
- God Object không chỉ khó đọc — nó **mở rộng không tốt** trong môi trường đa luồng (bottleneck monitor duy nhất).
- Các characterization test là bước đầu tiên bắt buộc. Không có chúng, bạn không refactoring — bạn đang đoán.

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- God Object — một class với hàng trăm phương thức/trường, làm "mọi thứ," LCOM > 1.0
- Thuật toán: Phân Tích Tính Năng → Extract Class (delegation) → các interface ISP → migration client
- Characterization Test — bước đầu tiên bắt buộc cho legacy không có test
- Strangler Fig: thay thế dần dần thông qua facade, không Big Bang
- Tách logic Hot vs Cold: các class hot nhỏ để thân thiện JIT, cold — có thể lớn hơn
- Saga Pattern cho distributed transaction sau khi chia God Object thành microservices
- Bounded Context (DDD) — cắt theo ranh giới nghiệp vụ, không phải các tầng kỹ thuật

**Các câu hỏi phụ thường gặp:**
- **Cách chia shared mutable state?** — Context Object: truyền trạng thái như một tham số thay vì các trường dùng chung
- **Nên làm gì với circular dependency sau khi chia tách?** — Coordinator thứ ba hoặc Event-driven (`ApplicationEventPublisher`)
- **God Object và Thread Safety?** — Một `synchronized` khóa TẤT CẢ phương thức; chia tách → locking chi tiết hơn
- **Các metric của God Object?** — >30 phương thức, >15 trường, LCOM > 1.0, Cognitive Complexity > 15, >7 dependency

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "God Object có thể refactor mà không có test" (bắn trong bóng tối, regression đảm bảo)
- "Chia tất cả cùng lúc trong một sprint" (refactoring dần dần: facade → migration → loại bỏ)
- "20 class nhỏ tệ hơn một God Object" (20 class SRP tốt hơn một con quái vật không thể quản lý)
