# What is the equals() and hashCode() Contract? (Contract của equals() và hashCode() là gì?)

## 🟢 Junior Level

**Contract của equals() và hashCode()** là một tập các quy tắc mà các method `equals()` và `hashCode()` trong Java phải tuân theo. Nếu bị vi phạm, các collection như HashMap và HashSet sẽ hoạt động sai.

**Hai quy tắc đơn giản:**
1. Nếu hai object bằng nhau theo `equals()`, `hashCode()` của chúng **phải** giống nhau
2. Nếu `hashCode()` giống nhau — các object **không nhất thiết** bằng nhau (cái này gọi là va chạm)

**Ví dụ contract đúng:**
```java
public class Person {
    private String name;
    private int age;

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Person)) return false;
        Person p = (Person) o;
        return age == p.age && name.equals(p.name);
    }

    @Override
    public int hashCode() {
        return 31 * name.hashCode() + age;
    }
}
```

**Quy tắc chính:** nếu một object sẽ được dùng làm key trong HashMap/HashSet — hãy override cả hai method. Ngoại lệ: nếu bạn CỐ Ý muốn hành vi identity (ví dụ, cho weak reference).

## 🟡 Middle Level

### Contract của equals()

Method `equals()` phải hành xử như khái niệm toán học về 'bằng nhau':
- **Tính phản xạ (Reflexivity):** một object bằng chính nó: `a.equals(a) = true`
- **Tính đối xứng (Symmetry):** nếu A bằng B, thì B bằng A
- **Tính bắc cầu (Transitivity):** nếu A=B và B=C, thì A=C

| Tính chất        | Mô tả                                              |
| ---------------- | -------------------------------------------------- |
| Reflexivity      | `x.equals(x)` luôn là `true`                       |
| Symmetry         | Nếu `x.equals(y)`, thì `y.equals(x)`               |
| Transitivity     | Nếu `x.equals(y)` và `y.equals(z)`, thì `x.equals(z)` |
| Consistency      | Các lời gọi lặp lại cho cùng kết quả               |
| So sánh với null | `x.equals(null)` luôn là `false`                   |

### Contract của hashCode()

1. **Consistency**: giá trị không đổi nếu các field từ `equals()` không đổi
2. **Liên kết bắt buộc**: `x.equals(y)` → `x.hashCode() == y.hashCode()`
3. **Liên kết không bắt buộc**: cùng hashCode ≠ các object bằng nhau

### Cách implement đúng

Thuật toán của Joshua Bloch:
```java
int result = 17;
result = 31 * result + field1;
result = 31 * result + (field2 != null ? field2.hashCode() : 0);
return result;
```

**Tại sao 17 và 31:** 17 — 'hạt giống số nguyên tố' ban đầu, để hash của các field đầu không bằng zero. 31 — một số nguyên tố lẻ: nhân với 31 = dịch trái 5 bit trừ 1 (`31 * i = (i << 5) - i`), thứ hiệu quả trên CPU. Tràn số nguyên (integer overflow) không phải là một bug — nó bình thường: hash LUÔN wrap-around, điều này được xây dựng vào toán học.

### Các sai lầm thường gặp

1. **Override equals, quên hashCode** — các bản trùng lặp trong HashSet
2. **Dùng các field mutable** — key "vỡ" sau khi sửa đổi
3. **Bug kinh điển của JDK:** `Timestamp` extends `Date`. `date.equals(timestamp)` có thể trả về true, nhưng `timestamp.equals(date)` — false, vì Timestamp kiểm tra nano giây mà Date không có. Tính đối xứng bị vi phạm!

### Khi nào KHÔNG nên dùng equals/hashCode tùy chỉnh

Đừng dùng equals/hashCode cho các object có business identity có thể thay đổi. Ví dụ, một entity với ID tự sinh: trước khi lưu id=null, sau — id=42. Hai object với id=null 'bằng nhau', nhưng sau khi lưu — chúng không bằng. Điều này vi phạm consistency trong HashMap.

## 🔴 Senior Level

### Hiện thực bên trong trong HashMap

HashMap dùng cả hai method cho tìm kiếm O(1):
1. `hashCode()` → tìm bucket: `index = (n-1) & hash(key)`
2. `equals()` → tìm key bên trong bucket

**Hệ quả của việc vi phạm:**
- Các object bằng nhau với các hashCode khác nhau rơi vào các bucket khác nhau → `get()` trả về `null`
- `HashSet` cho phép các bản trùng lặp → vi phạm business logic
- `remove()` không tìm thấy object → rò rỉ bộ nhớ

### Vi phạm tính đối xứng trong kế thừa

```java
class Point2D { int x, y; }
class Point3D extends Point2D { int z; }
```

Nếu `Point3D.equals()` kiểm tra cả 3 field, nhưng `Point2D.equals()` chỉ 2:
- `new Point2D(1,1).equals(new Point3D(1,1,0))` → `true` (Point2D không thấy z)
- `new Point3D(1,1,0).equals(new Point2D(1,1))` → `false` (Point2D không phải instanceof Point3D)
- **Vi phạm tính đối xứng!**

Giải pháp: dùng `getClass()` thay vì `instanceof`, hoặc kết hợp thay vì kế thừa.

### Các trường hợp biên (Edge Case)

1. **URL.equals()** — thực hiện các request DNS, vi phạm consistency khi mạng lỗi
2. **Float.NaN** — `Float.NaN.equals(Float.NaN)` = true, nhưng `Float.NaN == Float.NaN` = false
3. **Mảng** — `equals()` so sánh các tham chiếu, không phải nội dung; dùng `Arrays.equals()`

### Hệ quả về hiệu năng

- hashCode kém → va chạm → HashMap suy giảm xuống O(log n) hoặc O(n)
- equals() nặng (so sánh các string/mảng byte lớn) → hằng số lớn trong O(1)
- Caching hashCode (như trong `String`) — then chốt cho hiệu năng

### Java 14+: Record

```java
public record Person(String name, int age) {}
```

Record tự động sinh `equals()` và `hashCode()` dựa trên tất cả các component, đảm bảo tuân thủ contract.

### Bảo mật

Vi phạm contract có thể dẫn tới các tấn công DoS qua Hash Flooding. Một `hashCode()` chất lượng không chỉ là tính đúng đắn, mà còn là bảo mật.

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- equals() — tính phản xạ, đối xứng, bắc cầu, consistency, null = false
- hashCode() — nếu equals = true, hashCode PHẢI khớp
- Chiều ngược lại là sai: cùng hashCode ≠ các object bằng nhau (va chạm)
- Thuật toán của Bloch: khởi tạo 17, hệ số nhân 31 (=(i<<5)-i), bao gồm mọi field từ equals
- 31 — số nguyên tố lẻ, JVM tối ưu phép nhân qua dịch bit
- Tràn số nguyên — bình thường, hash luôn wrap-around
- Record (Java 14+) tự động sinh cả hai method

**Các câu hỏi phụ thường gặp:**
- **Điều gì xảy ra nếu bạn chỉ override equals?** — các object bằng nhau rơi vào các bucket khác nhau, get trả về null
- **Tại sao 31, không phải 17 hay 37?** — 31 = (i<<5)-i, một phép toán thay vì phép nhân
- **Vi phạm tính đối xứng là gì?** — A.equals(B) = true, nhưng B.equals(A) = false (bug kinh điển: Timestamp vs Date)
- **Khi nào KHÔNG nên override?** — khi cần ngữ nghĩa identity (so sánh theo tham chiếu, không phải nội dung)

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "hashCode phải là duy nhất" — không, va chạm được cho phép
- "Bạn có thể chỉ override một method" — không, luôn là cặp
- "URL là một key tốt" — không, URL.equals() thực hiện các request DNS, vi phạm consistency
