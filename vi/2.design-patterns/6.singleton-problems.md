# What Are Problems with Singleton? (Những vấn đề của Singleton là gì?)

## Junior Level

Các vấn đề của Singleton được chia thành ba nhóm: **khả năng kiểm thử** (không thể mock), **kiến trúc** (sự phụ thuộc bị ẩn giấu), **cơ sở hạ tầng** (vấn đề về khả năng mở rộng - scaling).

1. **Khó kiểm thử** — không thể thay thế bằng một mock
2. **Sự phụ thuộc bị ẩn giấu** — không nhìn thấy được rằng một class đang sử dụng Singleton
3. **Trạng thái toàn cục (Global state)** — các bài test ảnh hưởng lẫn nhau
4. **Không có khả năng mở rộng** — trong một cluster, mỗi node sẽ nhận được Singleton riêng của mình

**Ví dụ về vấn đề:**
```java
// Singleton gây cản trở cho các bài test
public class OrderService {
    public void create() {
        Database.getInstance().save(...);  // DB thật!
    }
}

@Test
void testOrder() {
    // Không thể thay thế Database bằng một cái test được!
    // Test đi thẳng vào DB thật
}
```

**Giải pháp:** Thay vì tự viết Singleton thủ công, hãy sử dụng một DI container (Spring) tự quản lý tính duy nhất của instance cho bạn.
Spring `@Component` + singleton scope = cùng là Singleton, nhưng có khả năng kiểm thử.

## Middle Level

### 1. Các vấn đề khi kiểm thử

**Flaky Tests (Test không ổn định)** — các bài test đôi khi pass đôi khi fail một cách ngẫu nhiên mà không có sự thay đổi nào trong code.

```java
// Singleton = Flaky Tests
@Test
void test1() {
    Counter.getInstance().increment();
    assertEquals(1, Counter.getInstance().getCount());
}

@Test
void test2() {
    // Counter đã = 1 từ test1 rồi!
    assertEquals(1, Counter.getInstance().getCount()); // THẤT BẠI!
}

// Giải pháp: DI
public class Counter {
    private int count = 0;
    public void increment() { count++; }
    public int getCount() { return count; }
}

@Test
void test1() {
    Counter counter = new Counter();  // Mới cho mỗi bài test
    counter.increment();
    assertEquals(1, counter.getCount());
}
```

### 2. Tight Coupling (Sự phụ thuộc chặt chẽ)

```java
// Sự phụ thuộc bị ẩn giấu
public class OrderService {
    public void process() {
        Logger.getInstance().log("...");       // Sự phụ thuộc bị ẩn giấu
        Config.getInstance().getTimeout();     // Một cái khác
        Cache.getInstance().get("key");        // Và một cái khác nữa
    }
}
// Nhìn vào constructor — không thể biết được cần gì để nó hoạt động!

// Sự phụ thuộc tường minh thông qua constructor
public class OrderService {
    private final Logger logger;
    private final Config config;
    private final Cache cache;

    public OrderService(Logger logger, Config config, Cache cache) {
        this.logger = logger;
        this.config = config;
        this.cache = cache;
    }
}
// Ngay lập tức có thể biết được cần gì
```

### 3. Lock Contention (Tranh chấp khóa)

```java
// Singleton có trạng thái = nghẽn cổ chai (bottleneck)
public class SessionManager {
    private final Map<String, Session> sessions = new HashMap<>();

    public synchronized void addSession(String id, Session session) {
        sessions.put(id, session);  // Tất cả các luồng đều phải đợi!
    }
}

// Ở mức 1000 req/giây -> hàng đợi để chờ synchronized method
```

### 4. Rò rỉ bộ nhớ (Memory Leaks)

**Metaspace** — vùng bộ nhớ JVM dành cho metadata của class.

```java
// Singleton sống mãi mãi
public class DataLoader {
    private static DataLoader instance;
    private List<Data> cache = new ArrayList<>();  // Tăng dần!

    private DataLoader() {}
    public static DataLoader getInstance() {
        if (instance == null) instance = new DataLoader();
        return instance;
    }
}

// Trong Tomcat khi redeploy:
// ClassLoader cũ không bị GC -> Rò rỉ Metaspace
// -> OutOfMemoryError: Metaspace
```

### 5. Không hoạt động trong một Cluster

```
Node 1: Singleton -> counter = 1
Node 2: Singleton -> counter = 1
Node 3: Singleton -> counter = 1

// Kỳ vọng: một counter chung cho tất cả các node
// Thực tế: một counter riêng cho mỗi node!
```

### Giải pháp: Dependency Injection

```java
// Spring quản lý vòng đời
@Component
public class UserService {
    private final UserRepository repo;

    public UserService(UserRepository repo) {
        this.repo = repo;  // Sự phụ thuộc tường minh
    }
}

// Dễ dàng thay thế trong các bài test
@Test
void test() {
    UserRepository mockRepo = mock(UserRepository.class);
    UserService service = new UserService(mockRepo);
    // Kiểm thử một cách cô lập
}
```

## Senior Level

### Sự suy thoái kiến trúc

**Vi phạm SOLID:**

| Nguyên lý                 | Cách Singleton vi phạm nó                    |
| ------------------------- | -------------------------------------------- |
| **Single Responsibility** | Class vừa quản lý logic vừa quản lý vòng đời của chính nó   |
| **Open/Closed**           | Không thể mở rộng mà không cần sửa đổi            |
| **Liskov Substitution**   | Không thể thay thế bằng một subclass            |
| **Interface Segregation** | Phụ thuộc vào cách triển khai cụ thể         |
| **Dependency Inversion**  | Phụ thuộc vào class cụ thể, không phải trừu tượng   |

### Deadlock khi khởi tạo Static

```java
// Sự phụ thuộc lẫn nhau trong các static initializer
public class A {
    static { B.getInstance(); }  // Đợi B
    private static A instance = new A();
    public static A getInstance() { return instance; }
}

public class B {
    static { A.getInstance(); }  // Đợi A
    private static B instance = new B();
    public static B getInstance() { return instance; }
}

// Thread 1: load A -> đợi B
// Thread 2: load B -> đợi A
// -> DEADLOCK ngay ở giai đoạn Class Loading!
// -> Rất khó để phát hiện
```

### Khả năng mở rộng theo chiều ngang (Horizontal Scaling)

```java
// Singleton vô dụng đối với ID phân tán
public class IdGenerator {
    private static long counter = 0;
    public static synchronized long nextId() { return ++counter; }
}

// Trong một cluster 5 node:
// Node 1: 1, 2, 3
// Node 2: 1, 2, 3  <- Trùng lặp!
// Node 3: 1, 2, 3

// Giải pháp: bộ sinh phân tán (distributed generator)
// Redis INCR, Snowflake ID, UUID
```

### Quản lý vòng đời (Lifecycle Management)

```java
// Singleton không có shutdown()
public class ConnectionPool {
    private static ConnectionPool instance;
    private List<Connection> connections;

    private ConnectionPool() {
        connections = createConnections();  // Đã mở 10 kết nối
    }

    // Làm sao để đóng khi ứng dụng tắt (shutdown)?
    // Không có phương thức chuẩn nào!
}

// Spring: @PreDestroy
@Component
public class ConnectionPool {
    @PreDestroy
    public void shutdown() {
        connections.forEach(Connection::close);
    }
}
```

### Tranh chấp luồng (Thread Contention) khi tải cao (Highload)

```java
// Singleton có thể thay đổi (mutable) = nghẽn cổ chai
public class MetricsCollector {
    private static MetricsCollector instance;
    private final Map<String, Long> metrics = new ConcurrentHashMap<>();

    public void increment(String name) {
        metrics.merge(name, 1L, Long::sum);  // ConcurrentHashMap, nhưng...
    }

    public Map<String, Long> getMetrics() {
        return new HashMap<>(metrics);  // ...sao chép mỗi lần!
    }
}

// Ở mức 10,000 req/giây:
// ConcurrentHashMap giảm tranh chấp, nhưng việc sao chép trong getMetrics() tạo ra 10,000 đối tượng/giây -> áp lực lên GC.

// Giải pháp: ThreadLocal hoặc metric phân tán
```

### Đào sâu về Rò rỉ bộ nhớ do ClassLoader

```
Tomcat redeploy:
1. ClassLoader của webapp cũ đáng lẽ phải bị GC
2. Nhưng Singleton.class có một trường static -> tham chiếu
3. ClassLoader không thể bị GC
4. Tất cả các class của webapp vẫn ở trong bộ nhớ
5. Metaspace tăng dần -> OutOfMemoryError

// Giải pháp:
// 1. ĐỪNG sử dụng static Singleton trong webapp
// 2. Sử dụng DI container (Spring)
// 3. Bản thân Spring tự dọn dẹp khi tắt (shutdown)
```

### Kinh nghiệm Production

**Tình huống thực tế #1: Singleton giết chết khả năng mở rộng**
- Rate Limiter được triển khai như Singleton
- 5 node trong cluster
- Kỳ vọng: 100 req/phút cho toàn bộ các node
- Thực tế: 100 req/phút MỖI NODE (tổng cộng 500!)
- Giải pháp: rate limiter dựa trên Redis

**Tình huống thực tế #2: Deadlock static trong production**
- Hai Singleton khởi tạo lẫn nhau
- Deadlock khi khởi động -> ứng dụng bị treo
- Mất 4 giờ để debug -> tìm ra thông qua thread dump
- Giải pháp: loại bỏ sự phụ thuộc vòng tròn (circular dependency)

**Tình huống thực tế #3: Rò rỉ bộ nhớ**
- Metaspace tăng thêm 50 MB mỗi lần deploy
- Sau 10 lần deploy -> OutOfMemoryError
- Nguyên nhân: Singleton giữ ClassLoader
- Giải pháp: chuyển sang dùng Spring DI

### Best Practices (Thực hành tốt nhất)

1. **ĐỪNG sử dụng Singleton thủ công** trong các ứng dụng Spring
2. **DI Container** quản lý vòng đời tốt hơn
3. **Tránh trạng thái có thể thay đổi (mutable state)** trong Singleton
4. **Đối với các cluster** -> các giải pháp phân tán (Redis, ZK)
5. **Giám sát Metaspace** khi sử dụng static

ZK (Zookeeper) — hệ thống điều phối phân tán.

6. **@PreDestroy** để tắt (shutdown) đúng cách
7. **ThreadLocal** để giảm tranh chấp
8. **Sự phụ thuộc tường minh** thông qua constructor

### Tóm tắt cho Senior

- **Vi phạm SOLID:** Singleton vi phạm 5 trong số 6 nguyên lý
- **Deadlock static:** khó phát hiện, mang tính thảm khốc
- **Rò rỉ ClassLoader:** OOM ở Metaspace khi redeploy
- **Lầm tưởng về cluster:** Singleton != tính duy nhất trong hệ thống phân tán
- **Tranh chấp luồng:** trạng thái có thể thay đổi = nghẽn cổ chai
- **Vòng đời:** không có cơ chế tắt (shutdown) chuẩn
- **DI Container** giải quyết TẤT CẢ những vấn đề này
- **Quy tắc:** Singleton chỉ dùng cho các tiện ích stateless hoặc SDK

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Singleton vi phạm SOLID: SRP (quản lý vòng đời), DIP (sự phụ thuộc bị ẩn giấu), OCP (không thể mở rộng), LSP (không thể thay thế), ISP (phụ thuộc cụ thể)
- Không thể kiểm thử: không thể mock, trạng thái giữa các test -> flaky test
- Deadlock khi khởi tạo static — hai Singleton khởi tạo lẫn nhau -> deadlock khi khởi động
- Rò rỉ bộ nhớ do ClassLoader: trong Tomcat khi redeploy, Singleton ngăn cản GC -> Metaspace OOM
- Trong một cluster, Singleton vô dụng — mỗi node tự tạo instance riêng của mình
- Trạng thái có thể thay đổi trong Singleton = nghẽn cổ chai do tranh chấp luồng
- DI Container giải quyết TẤT CẢ những vấn đề này

**Các câu hỏi phụ thường gặp:**
- **Singleton vi phạm những nguyên lý SOLID nào?** — SRP (trách nhiệm kép), DIP (sự phụ thuộc bị ẩn giấu), OCP (không thể mở rộng), LSP (không thể thay thế)
- **Deadlock khi khởi tạo static là gì?** — Hai class trong các static block đợi lẫn nhau -> deadlock ở giai đoạn Class Loading
- **Tại sao Singleton lại gây rò rỉ trong Tomcat?** — Trường static giữ lại ClassLoader -> ClassLoader không bị GC -> Metaspace tăng dần
- **Làm sao để giải quyết vấn đề khả năng kiểm thử?** — DI: truyền sự phụ thuộc thông qua constructor thay vì Singleton.getInstance()

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Singleton có khả năng kiểm thử hoàn hảo" — không thể mock, có trạng thái giữa các test
- "Tôi không dùng DI, Singleton đơn giản hơn" — sự phụ thuộc bị ẩn giấu = nợ kỹ thuật
- "Trong một cluster, Singleton giải quyết được việc điều phối" — mỗi node tự tạo instance riêng của mình
- "Deadlock static là điều không thể xảy ra" — có thể xảy ra khi có sự phụ thuộc vòng tròn của các static initializer
