# What is HATEOAS? (HATEOAS là gì?)

## Junior Level

**HATEOAS** (Hypermedia As The Engine Of Application State — Hypermedia là động cơ điều khiển trạng thái ứng dụng) là một nguyên tắc REST trong đó server trả về không chỉ dữ liệu mà còn cả các **link** tới những hành động khả dĩ.

### Ví dụ đơn giản:

Không có HATEOAS:
```json
{
  "id": 101,
  "status": "NEW"
}
```

Có HATEOAS:
```json
{
  "id": 101,
  "status": "NEW",
  "_links": {
    "self": { "href": "/orders/101" },
    "payment": { "href": "/orders/101/pay" },
    "cancel": { "href": "/orders/101/cancel" }
  }
}
```

### Tại sao cần đến nó?
- Client không cần "biết" các URL — nó chỉ đi theo các link
- Nếu server đổi URL, client sẽ không bị hỏng
- API trở nên tự tài liệu hóa (self-documenting)

### Ví dụ minh họa:
Nó giống như một website: bạn không thuộc lòng tất cả các URL, bạn chỉ nhấp vào các link trên trang.

## Middle Level

### Khái niệm Affordances

Trong HATEOAS, các link không chỉ là URL — chúng là các **Affordance**:
- **Affordance** (trong ngữ cảnh HATEOAS) — một gợi ý từ server cho client về những hành động nào hiện tại là khả dĩ. Giống như một nút trên trang web "gợi ý" rằng nó có thể được nhấp. Nếu server không trả về link `rel="delete"` — nghĩa là việc xóa hiện tại không khả dĩ.
- Nếu người dùng không có quyền xóa — server đơn giản là **không gửi** link `rel="delete"`
- Client không cần phải lặp lại logic nghiệp vụ để kiểm tra quyền
- Chỉ cần: `if (response.links.delete) showDeleteButton()`

### Chuẩn HAL (Hypertext Application Language)

Định dạng phổ biến nhất. Dùng trường `_links`:
```json
{
  "id": 101,
  "status": "NEW",
  "_links": {
    "self": { "href": "/orders/101" },
    "payment": { "href": "/orders/101/pay" },
    "cancel": { "href": "/orders/101/cancel" }
  }
}
```

### Spring HATEOAS

Thư viện này dùng **`RepresentationModel`** và **`LinkDiscoverer`**:
- **`WebMvcLinkBuilder`** xây dựng link một cách động bằng cách đọc các mapping của controller
- **Vấn đề:** Đằng sau một proxy (Nginx/API Gateway), các link có thể chứa một IP nội bộ
- **Giải pháp:** Cấu hình các header `X-Forwarded-*` và `ForwardedHeaderFilter`

### Hiệu suất

- **Payload Overhead (chi phí kích thước payload):** Với một tài nguyên đơn lẻ, overhead là 30-50%. Với các collection 100+ phần tử — lên tới 2-3 lần, vì mỗi phần tử chứa link riêng của nó.
- **Tối ưu hóa:** Chỉ đặt link ở khung nhìn chi tiết (Single Resource), trong danh sách — chỉ `self`
- **Chi phí CPU:** Sinh link cho 1000 phần tử tốn tài nguyên (reflection trong Spring)

### Các trường hợp biên (Edge Case)

- **Versioning:** Nếu bạn đổi đường dẫn endpoint thanh toán, một client dùng HATEOAS sẽ không nhận ra — nó lấy URL từ link. Điều này mang lại khả năng tương thích ngược hoàn hảo
- **Client Caching:** Cache các response có HATEOAS có thể nguy hiểm nếu các link phụ thuộc vào quyền của người dùng. Nếu các response HATEOAS được cache và các link phụ thuộc vào quyền của người dùng, hãy thêm `Vary: Authorization`, nếu không CDN có thể trả về một response đã cache với link của người khác.

## Senior Level

### Khi nào KHÔNG nên dùng HATEOAS

1. **Microservice nội bộ** — overhead mà không có lợi ích
2. **Ứng dụng di động với các màn hình cố định** — URL không đổi
3. **Hệ thống Highload** — nơi từng byte đều quan trọng
4. **Client và backend là cùng một đội** — mức độ ràng buộc (coupling) vốn đã tối thiểu

### HATEOAS như một State Machine

HATEOAS hiện thực mẫu **State Machine (máy trạng thái)** ở tầng giao thức mạng:
- Client là một bộ thực thi "ngờ nghệch" chỉ đi theo các link
- Server quản lý trạng thái ứng dụng thông qua các link có sẵn
- Điều này giảm mạnh mức độ ràng buộc giữa frontend và backend

### Spring HATEOAS (bên trong)

- **`RepresentationModel`** — lớp cơ sở cho các tài nguyên có link
- **`LinkDiscoverer`** — phân tích và tìm các link trong response
- **Vấn đề proxy:** `WebMvcLinkBuilder` xây dựng link dựa trên các mapping nội bộ. Đằng sau Nginx/API Gateway, các link chứa một IP nội bộ

### Hiệu suất và Highload

#### Payload Overhead
Trong các hệ thống Highload, HATEOAS có thể là một vấn đề:
- Với một tài nguyên đơn lẻ, overhead là 30-50%. Với các collection 100+ phần tử — lên tới 2-3 lần
- Chi phí CPU để sinh link cho mỗi phần tử (reflection)

#### Các tối ưu hóa
1. Chỉ đặt link ở Single Resource, trong Collection — chỉ `self`
2. Định dạng link nhỏ gọn (tên `rel` tối thiểu)
3. Cache các template của link

### Chẩn đoán và Giám sát

- **Discoverability (khả năng khám phá):** Bạn có thể "đi dạo" qua API bằng HAL Browser, nhấp vào các link
- **Broken Links (link hỏng):** Việc giám sát nên kiểm tra tính hợp lệ của các link được sinh ra. Nếu `self` trỏ tới 404 — đó là một lỗi của bộ sinh link
- **Vary Header:** Nếu các response HATEOAS được cache và các link phụ thuộc vào quyền của người dùng, hãy thêm `Vary: Authorization`, nếu không CDN có thể trả về một response đã cache với link của người khác.

## Interview Cheat Sheet

**Cần phải biết:**
- HATEOAS = Hypermedia As The Engine Of Application State — server trả về dữ liệu + link tới các hành động
- Client không cần biết URL — nó đi theo các link từ response của server
- Affordance — server gợi ý về các hành động có sẵn; không có link `rel="delete"` = không thể xóa
- Chuẩn HAL dùng trường `_links` với `self`, `payment`, `cancel`, v.v.
- Payload Overhead: 30-50% cho một tài nguyên đơn lẻ, lên tới 2-3 lần cho các collection 100+ phần tử
- HATEOAS không cần thiết cho: microservice nội bộ, ứng dụng di động, hệ thống highload
- Spring HATEOAS: `RepresentationModel` + `WebMvcLinkBuilder`; vấn đề proxy được giải quyết qua `X-Forwarded-*`

**Các câu hỏi phụ thường gặp:**
- Affordance trong ngữ cảnh HATEOAS là gì? — Gợi ý của server về các hành động có sẵn (giống như một nút trên trang)
- Tại sao HATEOAS làm tăng kích thước JSON? — Mỗi phần tử chứa link; với collection overhead lên tới 2-3 lần
- Làm sao giải quyết vấn đề link sau proxy? — Các header `X-Forwarded-*` và cấu hình `ForwardedHeaderFilter` trong Spring
- Khi nào HATEOAS chắc chắn không cần thiết? — Microservice nội bộ, di động với màn hình cố định, highload

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "HATEOAS cần thiết trong mọi dự án" — quá mức đối với API nội bộ và di động
- "HATEOAS chỉ là các link trong JSON" — nó còn là một State Machine và cách quản lý ràng buộc
- "Link HATEOAS có thể được cache mà không cần `Vary: Authorization`" — CDN sẽ trả link của người khác cho một người dùng khác
- "HATEOAS làm giảm kích thước response" — nó làm tăng 30-50% cho một tài nguyên đơn lẻ
