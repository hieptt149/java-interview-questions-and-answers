# What problems arise when using shared database (Những vấn đề gì phát sinh khi dùng shared database)

## 🟢 Junior Level

**Shared DB** là một anti-pattern trong microservices nơi nhiều service dùng chung một database.

```
❌ Order Service → Shared DB ← User Service
                ← Payment Service
```

**Các vấn đề:**
1. **Coupling** — thay đổi schema (ALTER TABLE) có thể phá vỡ các service khác phụ thuộc vào cùng table. Các service không còn độc lập nữa.
2. **Deployment phối hợp** — tất cả service phải được cập nhật đồng thời
3. **Lock** — một service khóa table cho các service khác
4. **Không có cô lập** — DB crash ảnh hưởng đến tất cả service. Mặc dù connection pool retry có thể giảm thiểu các lỗi ngắn hạn, một DB outage kéo dài = toàn bộ hệ thống thất bại.

## 🟡 Middle Level

### Các Vấn Đề Chi Tiết

```java
// Hai service map vào cùng một table — đổi tên một cột phá vỡ cả hai:
// UserService.java: @Column("email") — đổi tên thành "email_address"
// OrderService.java: @Column("email") — bị hỏng!
```

**1. Coupling schema:**
```
User Service sửa đổi table users
Order Service bị hỏng — mong đợi schema cũ
```

**2. Hiệu năng:**
```
Order Service chạy một truy vấn nặng → khóa table
User Service chờ → latency tăng
```

**3. Quyền sở hữu dữ liệu:**
```
Ai sở hữu table users?
User Service? Order Service?
Ai chịu trách nhiệm cho migration?
```

### Các Lỗi Thường Gặp

1. **Legacy shared DB:**
```
Monolith được tách thành các service, nhưng DB vẫn dùng chung
→ nhận tất cả nhược điểm của microservices mà không có lợi ích
```

## 🔴 Senior Level

### Migration Khỏi Shared DB

**Strangler pattern:**
```
1. Tạo một DB mới cho mỗi service
2. Dual write → ghi vào cả hai DB
3. Chuyển các lượt đọc sang DB mới
4. Loại bỏ các lượt ghi vào DB cũ
5. Xóa DB cũ
```

### Best Practices

```
✅ Database per Service
✅ API để truy cập dữ liệu của các service khác
✅ Event để replicate dữ liệu

❌ Shared database giữa các service
❌ JOIN trực tiếp qua các table của các service khác nhau
```

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- Shared DB là một anti-pattern: thay đổi schema của một service phá vỡ các service khác
- Coupling schema: ALTER TABLE có thể phá vỡ các service phụ thuộc
- Deployment phối hợp — tất cả service phải cập nhật đồng thời
- Lock: một truy vấn nặng của một service khóa table cho các service khác
- Không có cô lập: DB crash = toàn bộ hệ thống sập
- Migration: Strangler pattern — dual write → chuyển đọc → xóa DB cũ
- Giải pháp: Database per Service + API/event để truy cập dữ liệu

**Các câu hỏi phụ thường gặp:**
- **Cách migrate khỏi Shared DB?** Strangler pattern: tạo DB cho mỗi service → dual write → chuyển đọc → loại bỏ DB cũ.
- **Dual write problem là gì?** Nếu ghi vào hệ thống cũ thành công nhưng ghi vào hệ thống mới thất bại, dữ liệu trở nên không đồng bộ — giải pháp: pattern Outbox hoặc CDC.
- **Ai sở hữu một table trong Shared DB?** Không ai — đó là vấn đề, không ai chịu trách nhiệm cho migration.
- **Có thể giảm thiểu Shared DB không?** Có — các schema riêng biệt, nhưng đây là một thỏa hiệp, không phải giải pháp.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Shared DB là một cách tiếp cận bình thường cho microservices" — không, đó là anti-pattern
- "Monolith đã được tách, DB có thể vẫn dùng chung" — không, bạn nhận nhược điểm mà không có ưu điểm
- "JOIN qua các table của service là một ý tưởng hay" — không, đó là coupling
- "Coupling schema được giải quyết bằng tài liệu" — không, cần cô lập kiến trúc
