# What Anti-Patterns Do You Know? (Bạn biết những Anti-Pattern nào?)

## Junior Level

**Anti-pattern** là những giải pháp tồi thường xuyên bị lặp lại. Chúng trông giống như pattern nhưng lại gây hại nhiều hơn là giúp ích.

**Các anti-pattern phổ biến:**

**1. God Object (Đối tượng Thượng đế):**
```java
// Một class làm TẤT CẢ mọi thứ
public class Application {
    public void connectToDatabase() { }
    public void validateUser() { }
    public void sendEmail() { }
    public void generateReport() { }
    public void backupData() { }
    // ... thêm 1000 phương thức khác
}
```

**2. Spaghetti Code (Code mì spaghetti):**
```java
// Code không có cấu trúc, khó đọc
public void process() {
    if (a) { for (...) { if (b) { ... } } }
    else { while (...) { switch (...) { ... } } }
}
```

**3. Copy-Paste Programming (Lập trình sao chép-dán):**
```java
// Cùng một đoạn code ở 10 nơi khác nhau
// Sửa ở một nơi — quên sửa ở những nơi còn lại
```

**Cách để tránh:**
- Chia code thành các class nhỏ
- Tuân theo các nguyên lý SOLID
- Đừng sao chép code — hãy dùng các phương thức dùng chung

## Middle Level

### Các Anti-Pattern chính

**1. Golden Hammer (Búa vàng):**
```java
// Sử dụng một pattern yêu thích ở mọi nơi có thể
// "Tôi có Spring — tôi sẽ làm mọi thứ thông qua bean!"
// Đôi khi một if-else đơn giản là đã đủ
```

**2. Inner-Platform Effect (Hiệu ứng nền tảng nội bộ):**
```java
// Phát minh lại bánh xe bên trong ứng dụng
// DB tự chế trên nền hệ thống file
// ORM tự chế trên nền JDBC
```

**3. Lava Flow (Dòng dung nham):**
```java
// Code không ai hiểu nhưng lại sợ không dám xóa
// "Đừng động vào, nó vẫn đang chạy"
// -> Nợ kỹ thuật (technical debt) ngày càng tăng
```

**4. Magic Push Button (Nút bấm phép thuật):**
```java
// Sử dụng code mà không hiểu nó hoạt động như thế nào
// Sao chép-dán từ StackOverflow
// -> Lỗi không thể debug được
```

**5. Poltergeist (Bóng ma):**
```java
// Các class stateless chỉ gọi các class khác
public class Manager {
    public void doWork() {
        service.process(new Processor().execute());
    }
}
// -> Tầng gián tiếp thừa thãi
```

### Cách để nhận biết

| Dấu hiệu                  | Anti-Pattern    |
| --------------------- | --------------- |
| Class > 500 dòng     | God Object      |
| Phương thức > 50 dòng     | Long Method     |
| 10+ tham số        | Parameter List  |
| Code trùng lặp      | Copy-Paste      |
| "Đừng động vào, nó vẫn chạy"  | Lava Flow       |

## Senior Level

### Các Anti-Pattern về kiến trúc

**1. Big Ball of Mud (Quả cầu bùn khổng lồ):**
```
Không có kiến trúc, mọi thứ kết nối với nhau chằng chịt
-> Thay đổi ở một nơi làm hỏng nơi khác
-> Không thể kiểm thử
-> Giải pháp: tái cấu trúc, module hóa
```

**2. Architecture by Implosion (Kiến trúc từ trong ra):**
```
Thiết kế từ chi tiết đến tổng quát
-> Bắt đầu code mà không có thiết kế
-> Đánh mất bức tranh tổng thể
```

**3. Cargo Cult Programming (Lập trình bắt chước mù quáng):**
```java
// Sao chép code/cấu hình mà không hiểu tại sao.
// Ví dụ, thêm @Transactional vào mọi phương thức "để phòng khi cần".
// Hoặc thêm @Service vào mọi class "vì đó là quy ước".
```

**4. Not Invented Here (Không phải do chúng tôi phát minh ra):**
```
"Của chúng tôi tốt hơn" -> viết lại mọi thứ từ đầu
-> Tốn nhiều năm cho những thứ đã có sẵn
```

### Các Anti-Pattern về tổ chức

**1. Design by Committee (Thiết kế theo ủy ban):**
```
Quá nhiều người tham gia đưa ra quyết định
-> Sự thỏa hiệp, thiết kế không tối ưu
-> "Một con lạc đà là một con ngựa được thiết kế bởi một ủy ban"
```

**2. Management by Numbers (Quản lý bằng con số):**
```
Chỉ đánh giá dựa trên các chỉ số (metric)
-> Bỏ qua chất lượng code
-> Nợ kỹ thuật ngày càng tăng
```

### Các Anti-Pattern về code

**1. Couplet (Cặp phụ thuộc):**
```java
// Sự phụ thuộc chặt chẽ giữa hai class
class A { private B b = new B(); }
class B { private A a = new A(); }
// -> Sự phụ thuộc vòng tròn (circular dependency)
```

**2. God Object (còn gọi là Blob):**
```
Một class làm mọi thứ, những class khác — chỉ truyền dữ liệu
-> Vi phạm SRP
-> Giải pháp: phân phối trách nhiệm
```

**3. Sequential Coupling (Phụ thuộc theo trình tự):**
```java
// Các phương thức phải được gọi theo một trình tự nghiêm ngặt
obj.init();
obj.configure();
obj.process();  // Nếu gọi mà không có init -> exception!
// -> Giải pháp: Builder hoặc constructor
```

### Các chiến lược phòng ngừa

1. **Code Review** — phát hiện anti-pattern trước khi merge
2. **Static Analysis (Phân tích tĩnh)** — SonarQube, Checkstyle
3. **Metrics (Các chỉ số)** — theo dõi độ phức tạp, sự trùng lặp
4. **Refactoring (Tái cấu trúc)** — thường xuyên dọn dẹp code
5. **Knowledge Sharing (Chia sẻ kiến thức)** — đào tạo cho nhóm

### Kinh nghiệm Production

**Tình huống thực tế: God Object giết chết dự án**
- Class UserService: 5000 dòng, 200 phương thức
- 15 lập trình viên làm việc đồng thời -> xung đột merge mỗi ngày
- Giải pháp: chia thành 12 class theo SRP
- Kết quả: xung đột biến mất, khả năng đọc được cải thiện đáng kể

### Best Practices (Thực hành tốt nhất)

1. **SOLID** — hàng phòng thủ tốt nhất chống lại anti-pattern
2. **KISS** — đừng làm phức tạp thêm
3. **YAGNI** — đừng xây dựng "cho tương lai"
4. **DRY** — đừng sao chép code
5. **Code Review** — trách nhiệm tập thể
6. **Refactoring** — dọn dẹp thường xuyên
7. **Metrics** — đo lường chất lượng

### Tóm tắt cho Senior

- **Anti-pattern** = các giải pháp tồi bị lặp lại nhiều lần
- **God Object** — phổ biến nhất trong môi trường doanh nghiệp (enterprise)
- **Lava Flow** — dấu hiệu của việc thiếu Code Review
- **Golden Hammer** — lạm dụng pattern
- **Big Ball of Mud** — không có kiến trúc
- **SOLID** — biện pháp phòng ngừa tốt nhất
- **Metrics** — phát hiện vấn đề sớm
- **Refactoring** — vệ sinh code thường xuyên

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- God Object — một class làm mọi thứ (>500 dòng, >200 phương thức), vi phạm SRP, giải pháp: chia theo trách nhiệm
- Golden Hammer — sử dụng một pattern yêu thích ở mọi nơi, overengineering giết chết khả năng đọc
- Lava Flow — code không ai hiểu nhưng lại sợ không dám xóa -> nợ kỹ thuật ngày càng tăng
- Big Ball of Mud — không có kiến trúc, mọi thứ kết nối với nhau chằng chịt, không thể kiểm thử
- Cargo Cult — sao chép code/cấu hình mà không hiểu (@Transactional trên mọi phương thức "để phòng khi cần")
- Poltergeist — các class stateless chỉ gọi các class khác -> tầng gián tiếp thừa thãi
- SOLID + KISS + YAGNI + DRY — biện pháp phòng ngừa anti-pattern tốt nhất

**Các câu hỏi phụ thường gặp:**
- **Làm sao để nhận biết một God Object?** — Class >500 dòng, >200 phương thức, 15+ lập trình viên làm việc đồng thời -> xung đột merge
- **Lava Flow là gì và tại sao nó nguy hiểm?** — "Đừng động vào, nó vẫn chạy" -> không ai hiểu code -> nợ kỹ thuật ngày càng tăng
- **Cargo Cult khác Golden Hammer như thế nào?** — Cargo Cult = sao chép mà không hiểu, Golden Hammer = lạm dụng pattern
- **Làm sao để chống lại Big Ball of Mud?** — Module hóa, Code Review, Static Analysis (SonarQube), tái cấu trúc thường xuyên

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Chúng tôi có một class cho toàn bộ service" — đó là một God Object, cần phải chia theo SRP
- "Tôi thêm @Transactional vào mọi nơi để đảm bảo an toàn" — Cargo Cult, chi phí phát sinh không cần thiết
- "Code này cũ nhưng vẫn hoạt động — đừng động vào nó" — Lava Flow, nguồn gốc của lỗi
- "Tôi không cần các chỉ số về chất lượng code" — không có metric, anti-pattern sẽ âm thầm phát triển mà không ai nhận ra
