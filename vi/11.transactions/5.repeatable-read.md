# What is Repeatable Read? (Repeatable Read là gì?)

## 🟢 Junior Level

**Repeatable Read** là một isolation level đảm bảo rằng: nếu một transaction đã đọc dữ liệu, tất cả các lần đọc tiếp theo của cùng các dòng đó sẽ trả về cùng kết quả.

### Các Thuộc Tính Chính

- **Dirty Read**: Bị cấm
- **Non-Repeatable Read**: Bị cấm — dữ liệu sẽ không thay đổi trong suốt transaction
- **Phantom Read**: Tùy thuộc vào DBMS (bị cấm trong MySQL, có thể xảy ra theo chuẩn)

### Ví Dụ Đơn Giản

```
Transaction A: SELECT price FROM products WHERE id = 1; -- Trả về 100
-- Một transaction khác thay đổi giá và commit
Transaction A: SELECT price FROM products WHERE id = 1; -- Vẫn là 100!
```

Ở level Repeatable Read, một transaction làm việc với một "snapshot" dữ liệu được chụp tại thời điểm của query đầu tiên.

### Khác Biệt So Với Read Committed

- **Read Committed**: Mỗi SELECT thấy dữ liệu đã commit mới nhất
- **Repeatable Read**: Tất cả các SELECT thấy dữ liệu như tại thời điểm bắt đầu transaction

## 🟡 Middle Level

### Cơ Chế Hiện Thực (MVCC)

Ở level Repeatable Read, snapshot dữ liệu được tạo **một lần duy nhất** — tại thời điểm của **query đầu tiên** trong transaction. Tất cả các query tiếp theo thấy cơ sở dữ liệu ở trạng thái tại thời điểm chụp snapshot.

### Khác Biệt Giữa MySQL Và PostgreSQL

Mặc dù tên gọi giống nhau, cách hiện thực khác nhau về cơ bản:

#### MySQL (InnoDB)
- Đây là isolation level **mặc định**
- Ngăn chặn phantom read thông qua **Next-Key Locking** (Record Lock + Gap Lock):

**Gap** = khoảng cách giữa hai mục index. Một Gap Lock chặn việc chèn các dòng mới vào khoảng này. Ví dụ, nếu index có id=5 và id=10, một gap lock trên (5,10) sẽ không cho phép chèn id=7.
- Không chỉ các dòng bị khóa, mà cả các khoảng trống giữa chúng
- Hoạt động gần giống Serializable

#### PostgreSQL
- Không sử dụng Gap Lock
- Nếu một transaction cố gắng sửa đổi một dòng mà một transaction khác đã commit sau khi transaction của bạn bắt đầu — bạn nhận được lỗi:
  `ERROR: could not serialize access due to concurrent update`
- Application phải **retry toàn bộ transaction**

### Các Kịch Bản Sử Dụng

- **Báo cáo**: Tạo báo cáo mà dữ liệu không nên "trôi" trong quá trình xử lý
- **Tính toán nhiều bước**: Khi các kết quả trung gian không nên thay đổi
- **Migration dữ liệu**: Sao chép dữ liệu ở một trạng thái nhất quán

**Đừng dùng RR cho:** các workload ghi với contention cao (>100 writer trên cùng dữ liệu),
các transaction chạy dài (>30 giây) — nguy cơ bloat và serialization failure.

### Overhead

- DBMS lưu trữ các phiên bản dòng cũ lâu hơn (cho đến khi transaction RR dài nhất kết thúc)
- Có thể dẫn đến database bloat (Table Bloat — phình bảng)
- Tăng tải cho tiến trình VACUUM

### Vấn Đề Lost Update

Repeatable Read trong PostgreSQL bảo vệ chống lại "lost update". Nếu hai luồng đồng thời sửa đổi cùng một bản ghi, luồng thứ hai sẽ nhận lỗi serialization khi commit.

## 🔴 Senior Level

### Vòng Đời Snapshot MVCC

#### Hành Vi Snapshot Của PostgreSQL
- Snapshot được tạo tại **lần đọc đầu tiên** trong transaction, không phải tại BEGIN
- Snapshot bao gồm:
  - `xmin`: transaction ID đang hoạt động cũ nhất
  - `xmax`: transaction ID tiếp theo sẽ được cấp phát
  - `xip_array`: snapshot của tất cả các transaction đang thực thi
- Tất cả các lần đọc tiếp theo sử dụng **cùng** snapshot này
- Các lần ghi thấy chính các thay đổi của mình ngay lập tức (quy tắc visibility theo own-XID)

#### Visibility Của Tuple Dưới RR
```c
// Kiểm tra visibility đơn giản hóa của PostgreSQL
bool HeapTupleSatisfiesMVCC(HeapTuple tuple, Snapshot snapshot) {
    if (tuple->xmin >= snapshot->xmax) return false;
    if (tuple->xmax < snapshot->xmin) return false;
    if (TransactionIdIsInProgress(tuple->xmin)) return false;
    if (!TransactionIdDidCommit(tuple->xmin)) return false;
    if (TransactionIdIsInProgress(tuple->xmax)) return true;
    if (TransactionIdDidCommit(tuple->xmax)) return false;
    return true;
}
```

### Next-Key Locking Của MySQL — Chi Tiết Nội Bộ

**Next-Key Lock = Record Lock + Gap Lock**

```sql
-- Index: id = 1, 5, 10, 15
SELECT * FROM t WHERE id = 10 FOR UPDATE;
```

Điều này khóa:
- Bản ghi với id=10 (record lock)
- Khoảng (5, 10) — ngăn INSERT id=6,7,8,9
- Khoảng (10, 15) — ngăn INSERT id=11,12,13,14

**Tại sao?** Ngăn chặn phantom read bằng cách chặn các insert khớp với predicate của query.

**Tác dụng phụ:** Xác suất deadlock cao hơn, đặc biệt với các range query.

### Xử Lý Serialization Failure (PostgreSQL)

```java
@Retryable(
    value = {CannotSerializeTransactionException.class},
    backoff = @Backoff(delay = 100, multiplier = 2, maxDelay = 1000),
    maxAttempts = 3
)
@Transactional(isolation = Isolation.REPEATABLE_READ)
public void updateBalance(Long accountId, BigDecimal amount) {
    Account account = repo.findById(accountId);
    account.setBalance(account.getBalance().add(amount));
    repo.save(account);
}
```

### Đào Sâu Vào Việc Ngăn Chặn Lost Update

**Kịch bản dưới RR trong PostgreSQL:**
```
T1: BEGIN;                              T2: BEGIN;
T1: SELECT balance FROM acc WHERE id=1; -- thấy 100
                                        T2: SELECT balance FROM acc WHERE id=1; -- thấy 100
T1: UPDATE acc SET balance = 90 WHERE id=1;
T1: COMMIT;
                                        T2: UPDATE acc SET balance = 80 WHERE id=1;
                                        -- T2 BỊ CHẶN, đợi T1
                                        -- T1 đã commit, T2 phát hiện xung đột
                                        -- ERROR: could not serialize access
```

PostgreSQL phát hiện rằng T2 đã đọc một dòng mà T1 sửa đổi sau snapshot của T2. T2 phải retry.

### Phân Tích Tác Động Đến Hiệu Năng

| Metric                  | Read Committed  | Repeatable Read          |
| ----------------------- | --------------- | ------------------------- |
| Tạo snapshot            | Mỗi statement   | Mỗi transaction           |
| Giữ phiên bản cũ        | Ngắn hạn        | Đến khi tx dài nhất kết thúc |
| Nguy cơ bloat           | Thấp            | Trung bình-Cao             |
| Áp lực VACUUM           | Thấp            | Cao                        |
| Lỗi xung đột            | Không có        | Có thể xảy ra khi ghi       |
| Nguy cơ deadlock        | Thấp            | Trung bình (MySQL)         |

### Khuyến Nghị Cho Production

**Khi nào nên dùng Repeatable Read:**
- Các báo cáo phức tạp yêu cầu tự nhất quán
- Logic nghiệp vụ nhiều bước với các bất biến
- Xử lý batch mà dữ liệu nguồn không được thay đổi
- Khi bạn cần bảo vệ chống lại lost update mà không cần locking tường minh

**Khi nào nên tránh:**
- Các workload ghi nặng với contention cao
- Các transaction chạy dài (nguy cơ bloat)
- Khi logic retry quá phức tạp cho use case của bạn

**Mẹo tinh chỉnh:**
- Giữ các transaction RR càng ngắn càng tốt
- Giám sát `pg_stat_user_tables.n_dead_tup` để phát hiện bloat
- Đặt `statement_timeout` để ngăn các transaction chạy vô tận
- Sử dụng `pg_stat_activity` để phát hiện các transaction RR chạy dài

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Repeatable Read đảm bảo: SELECT lại cùng các dòng trả về cùng kết quả
- Cấm dirty read và non-repeatable read; phantom — tùy thuộc DBMS
- PostgreSQL: snapshot được tạo tại query đầu tiên, một snapshot cho toàn bộ transaction
- MySQL: level mặc định, ngăn phantom thông qua Next-Key Locking (Gap Lock)
- PostgreSQL ném lỗi serialization khi xung đột cập nhật — cần retry
- RR bảo vệ chống lost update trong PostgreSQL — luồng thứ hai nhận serialization failure

**Các câu hỏi phụ thường gặp:**
- Tại sao MySQL và PG xử lý phantom khác nhau ở RR? — MySQL: Gap Lock, PG: MVCC snapshot
- Khi nào nên dùng RR? — Báo cáo, tính toán nhiều bước, migration dữ liệu
- Gap Lock là gì? — Lock trên khoảng giữa các mục index, ngăn insert
- RR khác gì với Serializable? — RR không ngăn write skew, Serializable thì có

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "RR giống nhau trong mọi DBMS" — MySQL và PG khác nhau về cơ bản
- "RR = Serializable" — RR không ngăn tất cả các hiện tượng bất thường (write skew)
- "RR không ảnh hưởng đến hiệu năng" — bloat từ các phiên bản dòng cũ, áp lực VACUUM
