# How is Dependency Inversion Related to Dependency Injection? (Dependency Inversion principle liên quan đến Dependency Injection như thế nào?)

---

## 🟢 Junior Level

### Định Nghĩa Đơn Giản

**DIP (Dependency Inversion Principle)** là một quy tắc nói rằng: "Phụ thuộc vào các abstraction, không phải vào các triển khai cụ thể." **DI (Dependency Injection)** là cách chúng ta truyền các abstraction đó vào một object từ bên ngoài, thay vì tạo chúng bên trong. DIP là "chúng ta muốn gì," DI là "chúng ta làm điều đó như thế nào."

### Analogy

Hãy tưởng tượng một ổ cắm điện tường. Bạn không quan tâm điện đến từ đâu — một nhà máy hạt nhân, một turbine gió, hay một tấm pin mặt trời. Bạn chỉ cần một interface chuẩn (phích cắm/ổ cắm). **DIP** là chuẩn ổ cắm. **DI** là người thợ điện đến và kết nối nguồn điện phù hợp vào ổ cắm đó cho bạn.

### Ví Dụ Đơn Giản

```java
// XẤU: vi phạm DIP — service biết về một DB cụ thể
public class OrderService {
    private MySqlRepository repo = new MySqlRepository();
}

// TỐT: phụ thuộc vào abstraction, triển khai đến từ bên ngoài (DI)
public class OrderService {
    private final OrderRepository repo;

    public OrderService(OrderRepository repo) {
        this.repo = repo;
    }
}
```

### Khi Nào Dùng

- Khi bạn muốn dễ dàng thay thế các triển khai (ví dụ, PostgreSQL sang MongoDB).
- Khi bạn cần viết unit test với mock thay vì một DB thật.
- Khi làm việc trong một team và bạn muốn tách các interface từ các triển khai.

## 🟡 Middle Level

### Cách Hoạt Động Nội Bộ

Sự kết hợp DIP + DI hoạt động thông qua ba khái niệm:

| Khái niệm   | Vai trò                                                                         | Ví dụ                                                                |
| --------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| **DIP**   | Nguyên tắc kiến trúc: logic cấp cao không nên phụ thuộc vào các chi tiết       | `OrderService` phụ thuộc vào `OrderRepository`, không phải `MySqlRepository`  |
| **DI**    | Kỹ thuật: truyền các dependency từ bên ngoài                       | Truyền `OrderRepository` thông qua constructor                      |
| **IoC**   | Framework quản lý vòng đời object                                           | Spring tạo các bean và kết nối chúng tự động                             |

IoC tuân theo **Hollywood Principle**: "Đừng gọi chúng tôi, chúng tôi sẽ gọi bạn" — container quyết định khi nào tạo một object và gọi các phương thức của nó.

### Ứng Dụng Thực Tế

**Constructor Injection** (cách tiếp cận được khuyến nghị):
```java
public class OrderService {
    private final OrderRepository repo;

    public OrderService(OrderRepository repo) {
        this.repo = Objects.requireNonNull(repo); // fail-fast
    }
}
```

**Setter Injection** (cho các dependency tùy chọn):
```java
public void setCacheProvider(CacheProvider cache) {
    this.cache = cache;
}
```

### DI vs Service Locator

| Cách tiếp cận          | Ưu điểm                                                                  | Nhược điểm                                                                                                              |
| ----------------- | --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| **DI**            | Các dependency hiển thị trong constructor, dễ mock, fail-fast khi khởi động | Nhiều boilerplate hơn khi dùng thủ công                                                                               |
| **Service Locator**| Ít code trong constructor                                             | Các dependency ẩn, khó test (cần mock static context), các dependency không biết đến cho tới runtime               |

```java
// Service Locator — xấu
OrderRepository repo = ServiceContext.get("repo"); // Dependency ẩn

// DI — tốt
public OrderService(OrderRepository repo) { ... }   // Dependency rõ ràng
```

### Khi Nào KHÔNG Nên Dùng

- **Script và tiện ích đơn giản** — overhead từ các interface không đáng giá.
- **Các class không có dependency** — nếu một class không phụ thuộc vào các service bên ngoài, không cần DI.
- **Code chức năng thuần túy** — các hàm không có trạng thái không cần injection.

## 🔴 Senior Level

### Triển Khai Nội Bộ Sâu

#### Triển Khai DI Trong Các JVM Hiện Đại

**Dựa trên Reflection (Spring, Guice):**
- Container quét các annotation thông qua `Class.getDeclaredFields()`.
- Gọi `Constructor.newInstance()` hoặc `Field.set()` thông qua reflection.
- **Chi phí:** Lần chạy đầu tiên chậm — với một đồ thị 1000 bean, Spring dành 0.5-3 giây khi khởi động chỉ cho reflection và giải quyết dependency.

**Sinh Mã Nguồn (Dagger 2, Micronaut):**
- Sinh code tại compile time (các class `*_Factory.java`).
- Tại runtime — một lệnh gọi `new` thông thường không có reflection.
- **Chi phí:** ~0 ms overhead khởi động, một đồ thị 1000 bean khởi tạo trong 10-50 ms.

#### Cấp Độ Bytecode

Constructor Injection cho phép đánh dấu các trường là `final`:
```java
private final OrderRepository repo;
```
Ở cấp độ bytecode điều này mang lại:
- Trường nhận modifier `ACC_FINAL` — JVM có thể inline các tham chiếu.
- JIT compiler dùng đảm bảo này cho **devirtualization** — nếu loại trường final đã biết, các lệnh gọi phương thức có thể inline mà không cần virtual dispatch.
- Không có `final`, JIT phải chèn các kiểm tra safepoint trong trường hợp khởi tạo lại.

### Đánh Đổi Kiến Trúc

| Cách tiếp cận                        | Ưu điểm                                                                        | Nhược điểm                                                                        |
| ------------------------------- | --------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| **Constructor DI**              | Fail-fast (NPE khi khởi động), các trường `final`, tính bất biến, dễ test      | Constructor có thể có 10+ tham số — mùi của "quá nhiều trách nhiệm"  |
| **Setter DI**                   | Các dependency tùy chọn, có thể thay đổi ngay lập tức                            | Các dependency có thể `null` trước khi khởi tạo, khó theo dõi thứ tự hơn     |
| **Field DI (thông qua reflection)**   | Boilerplate tối thiểu                                                         | Không thể làm trường `final`, các dependency ẩn, không thể thiếu container|
| **Pure DI (thủ công)**            | Kiểm soát hoàn toàn, overhead bằng không, minh bạch                                   | Quản lý đồ thị thủ công, boilerplate tăng theo kích thước dự án                |

### Edge Cases

**1. Circular Dependency:**
```java
class A { A(B b) { ... } }
class B { B(A a) { ... } }
```
Spring giải quyết các circular dependency ở constructor bằng cách ném `BeanCurrentlyInCreationException`. DI dựa trên setter cho phép các chu trình thông qua các proxy, nhưng điều này che giấu một vấn đề thiết kế. Một chu trình là chỉ báo rằng DIP đã biến thành mì spaghetti.

**Giải pháp:** Đưa vào một class coordinator thứ ba, dùng `@Lazy` (một giải pháp tạm), hoặc thiết kế lại các ranh giới trách nhiệm.

**2. Các Dependency Tùy Chọn:**
```java
public OrderService(Optional<CacheProvider> cache, @Nullable MetricsCollector metrics) { ... }
```
Dùng `Optional<T>` hoặc `@Nullable` — nhưng đừng lạm dụng: nếu một dependency tùy chọn trong 90% trường hợp, có thể nó không phải là một dependency mà là một decorator.

**3. Các Dependency Có Điều Kiện:**
```java
@Bean
@ConditionalOnProperty("cache.enabled")
public CacheProvider cache() { ... }
```
Spring hỗ trợ các bean có điều kiện, nhưng điều này làm phức tạp phân tích đồ thị — bạn không thể xác định tĩnh dependency nào sẽ khả dụng.

### Tác Động Hiệu Năng

| Metric               | Dựa trên Reflection (Spring)     | Compile-time (Dagger)  |
| -------------------- | ----------------------------- | ---------------------- |
| Khởi động (100 bean)  | 100-300 ms                    | 5-15 ms                |
| Khởi động (1000 bean) | 1-3 giây                       | 30-80 ms                |
| Bộ nhớ mỗi bean      | ~200 byte (metadata reflective) | ~0 byte            |
| Lệnh gọi runtime   | 0 ms (đã cache sau khởi động)   | 0 ms                   |
| GraalVM native       | Yêu cầu reflection-config    | Hoạt động ngay lập tức   |

**Constructor Injection + các trường `final`:** JVM có thể inline các trường final sau escape analysis. Trong hotspot profiling, điều này mang lại tăng tốc 2-5% trên các phương thức có truy cập trường thường xuyên.

### Tác Động Bộ Nhớ Và GC

- Mỗi bean trong một Spring container chiếm bộ nhớ: bản thân object + proxy (CGLIB — thư viện để sinh các proxy subclass bytecode / JDK Dynamic Proxy ~1-2 KB mỗi proxy) + metadata trong `BeanDefinition`.
- Trong các ứng dụng với 5000+ bean, điều này thêm 5-15 MB heap chỉ cho hạ tầng.
- **Singleton scope:** Một object mỗi JVM — tác động GC tối thiểu.
- **Prototype scope:** Object mới mỗi request — tăng tải Young GC, đặc biệt nếu các object "sống" lâu và di chuyển đến Old Generation.

### Thread Safety

- **Các bean singleton phải thread-safe** — Spring không đồng bộ hóa truy cập vào các bean.
- Constructor Injection đảm bảo **safe publication** — các trường final hiển thị với tất cả các thread sau khi constructor hoàn thành (happens-before theo JLS §17.5).
- Field Injection thông qua reflection không đảm bảo safe publication — về mặt lý thuyết, một thread có thể thấy một trường được khởi tạo một phần.

### Câu Chuyện Chiến Tranh Production

**Vấn đề:** Một microservice xử lý đơn hàng có 2000+ bean Spring. Khởi động mất 45 giây. Trong quá trình deployment Kubernetes, liveness probe giết các pod trước khi chúng khởi động hoàn toàn, gây ra các restart dây chuyền.

**Chẩn đoán:** `spring-boot-starter-actuator` + `/actuator/startup` cho thấy 30 giây dành cho quét reflection và tạo proxy cho các bean chỉ cần thiết trong 3 trên 20 endpoint.

**Giải pháp:**
1. Migration sang **Micronaut** (DI compile-time) — khởi động giảm xuống 2 giây.
2. Chia monolith thành 4 module với lazy loading — mỗi module chỉ tải các bean của riêng nó.
3. Thay thế `@Autowired` bằng Constructor Injection — phát hiện 12 dependency không dùng.

### Monitoring Và Chẩn Đoán

**ArchUnit** — kiểm tra các quy tắc kiến trúc ở cấp độ test:
```java
@ArchTest
static final ArchRule no_controller_should_access_repository_directly =
    noClasses().that().resideInAPackage("..controller..")
        .should().dependOnClassesThat().resideInAPackage("..repository..");
```

**SonarQube** — quy tắc `S3010` phát hiện các vi phạm DI (các trường được inject không có constructor).

**Spring Boot Actuator** — `/actuator/beans` hiển thị toàn bộ đồ thị dependency.

**jdeps** (công cụ JDK) — phân tích các dependency ở cấp độ bytecode.

### Best Practices Cho Highload

1. **Constructor Injection như cách tiếp cận ưu tiên** — fail-fast, các trường final, thân thiện với JIT. Nhưng Setter Injection chấp nhận được cho các dependency tùy chọn.
2. **DI compile-time cho serverless/lambda** — cold start là quan trọng.
3. **Giảm thiểu đồ thị** — ít bean hơn nghĩa là khởi động nhanh hơn và ít heap hơn.
4. **Tránh `@Autowired` trên các trường** — các dependency ẩn + không có safe publication.
5. **Dùng Pure DI cho các module nhỏ** — không có framework, chỉ truyền các dependency thủ công.

### Tóm Tắt Cho Senior

- DI là "bàn tay" để triển khai ý tưởng kiến trúc của DIP.
- Constructor Injection — chuẩn vàng: fail-fast, các trường final, các tối ưu JIT.
- DIP/DI — không phải về "một interface vì mục đích interface," mà về **quản lý coupling**.
- DI dựa trên reflection tiện lợi, nhưng DI compile-time thắng trong các kịch bản nhạy cảm về hiệu năng.
- Đừng nhầm lẫn DI với các framework. DI có thể được thực hiện thủ công ("Pure DI").

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- DIP — "cái gì" (phụ thuộc vào abstraction), DI — "cách nào" (truyền thông qua constructor/field/setter)
- Constructor Injection — chuẩn vàng: fail-fast, các trường `final`, các tối ưu JIT, safe publication
- DI dựa trên Reflection (Spring): 0.5-3 giây cho 1000 bean; Compile-time (Dagger): 10-50 ms
- Các trường `final` → `ACC_FINAL` → JIT devirtualization → inlining không cần kiểm tra safepoint
- Circular Dependency → `BeanCurrentlyInCreationException`; giải pháp: coordinator, `@Lazy`, thiết kế lại
- Các bean singleton phải thread-safe; Constructor Injection đảm bảo safe publication (happens-before)

**Các câu hỏi phụ thường gặp:**
- **Constructor vs Setter vs Field Injection?** — Constructor: fail-fast, final, dễ test; Setter: tùy chọn; Field: các dependency ẩn, không có safe publication
- **DI vs Service Locator?** — DI: các dependency hiển thị trong constructor, dễ mock; Service Locator: các dependency ẩn, khó test
- **Tại sao Spring chậm hơn Dagger?** — Reflection khi khởi động vs sinh code tại compile time
- **Pure DI là gì?** — Tạo và truyền các dependency thủ công mà không có framework

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Field Injection thông qua `@Autowired` tiện lợi" (các dependency ẩn, không thể làm `final`, không có safe publication)
- "Circular Dependency — Spring sẽ xử lý nó" (che giấu một vấn đề thiết kế thông qua các proxy)
- "Mọi class nên có một interface cho DI" (Lạm Dụng Abstraction, vi phạm YAGNI)
