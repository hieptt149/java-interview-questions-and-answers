# How can a memory leak occur in Java? (Rò rỉ bộ nhớ có thể xảy ra trong Java như thế nào?)

## Junior Level

Rò rỉ bộ nhớ xảy ra khi **một tham chiếu đến một đối tượng vẫn còn** mặc dù đối tượng đó không còn cần thiết nữa.

**Các nguyên nhân phổ biến nhất:**

**1. Các collection tĩnh (static):**
```java
// ❌ Collection tăng vô hạn
static List<String> log = new ArrayList<>();
log.add("message");  // Không bao giờ được dọn dẹp!
```

**2. ThreadLocal không dọn dẹp:**
```java
// ❌ Quên remove
ThreadLocal<User> user = new ThreadLocal<>();
user.set(currentUser);
// Trong thread pool, luồng được tái sử dụng → User cũ còn lại!
```

**3. Tài nguyên không được đóng:**
```java
// ❌ Quên close()
FileInputStream fis = new FileInputStream("file.txt");
// Các buffer còn lại trong bộ nhớ
```

**Cách tránh:**
- Dọn dẹp các collection
- Gọi `ThreadLocal.remove()`
- Dùng try-with-resources

## Middle Level

### 1. ThreadLocal trong Thread Pool

```java
// ❌ Vấn đề: các luồng được tái sử dụng
public class UserContext {
    private static ThreadLocal<User> context = new ThreadLocal<>();

    public static void set(User user) {
        context.set(user);
    }
}

// Request 1: User A
UserContext.set(userA);
// ... xử lý ...
// Quên UserContext.remove()!

// Request 2 (cùng luồng): User B
// context.get() → trả về userA! ← Bug + rò rỉ
```

**Giải pháp:**
```java
// ✅ Luôn remove trong finally
try {
    context.set(user);
    // xử lý
} finally {
    context.remove();  // Bắt buộc!
}
```

### 2. Inner Class (các tham chiếu ngầm)

```java
// ❌ Non-static inner class
public class Outer {
    private byte[] data = new byte[1_000_000];  // 1 MB

    class Inner {  // Ngầm giữ tham chiếu đến Outer.this
        void doWork() { }
    }

    public void leak() {
        Inner inner = new Inner();
        executor.submit(inner::doWork);  // Inner được truyền sang luồng khác
        // Outer (1 MB) sẽ không bị xóa khi Inner còn sống!
    }
}

// ✅ Static nested class
static class Inner {  // Không có tham chiếu đến Outer
    void doWork() { }
}
```

### 3. Các collection tĩnh

```java
// ❌ Cache không có giới hạn (unbounded)
static Map<String, Data> cache = new HashMap<>();

public Data getData(String key) {
    if (!cache.containsKey(key)) {
        Data data = loadFromDb(key);
        cache.put(key, data);  // Tăng vô hạn!
    }
    return cache.get(key);
}

// ✅ Cache có giới hạn (Caffeine)
static Cache<String, Data> cache = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(10, TimeUnit.MINUTES)
    .build();
```

### 4. Lạm dụng String.intern()

```java
// ❌ Intern hàng triệu chuỗi duy nhất (unique)
while (readingLogs) {
    String uniqueLog = readLine();
    uniqueLog.intern();  // Trong Java 7+, các chuỗi từ StringTable có thể bị GC (nếu ClassLoader nạp chúng bị thu gom).
                         // Nhưng khi intern() với cường độ cao, bảng tăng nhanh hơn tốc độ được dọn dẹp.
}

// StringTable trong Heap → đầy lên → OOM
```

`String.intern()` hữu ích để khử trùng lặp một tập chuỗi lặp lại đã biết
(các giá trị kiểu enum, các key). Có hại cho các chuỗi duy nhất (logs, UUID).

### 5. Listener và Observer

```java
// ❌ Đã subscribe, nhưng chưa unsubscribe
eventBus.subscribe(listener);
// đối tượng listener sẽ không bị xóa khi eventBus còn sống
```

## Senior Level

### ClassLoader Leak (Metaspace)

```
Sinh class động (dynamic class generation):
  Spring → các proxy qua CGLIB
  Hibernate → các proxy cho Entity
  Groovy/JavaScript → biên dịch script

Mỗi class được sinh ra → Metaspace
Các class chỉ được dọn dẹp cùng với ClassLoader

Nếu ClassLoader không bị GC:
  → Tất cả các class vẫn còn
  → Metaspace tăng lên → OOM

Nguyên nhân của ClassLoader leak:
  1. ThreadLocal giữ đối tượng từ ClassLoader của ứng dụng
  2. DriverManager giữ tham chiếu đến JDBC driver
  3. LogManager giữ tham chiếu đến Logger của ứng dụng
  4. java.beans.Introspector cache BeanInfo
```

**Chẩn đoán:**
```bash
# Kiểm tra Metaspace
jcmd <pid> VM.metaspace

# Theo dõi việc nạp class
-Xlog:class+load=info
-XX:+TraceClassLoading
-XX:+TraceClassUnloading

# Nếu số class được nạp nhiều hơn số class được unload → rò rỉ!
```

### Rò rỉ bộ nhớ Off-Heap

```java
// DirectByteBuffer — bộ nhớ nằm ngoài Heap
ByteBuffer buf = ByteBuffer.allocateDirect(100 * 1024 * 1024);
// 100 MB nằm ngoài -Xmx!

// Phantom Reference dọn dẹp buffer khi ByteBuffer bị GC
// Nhưng nếu GC không chạy (Heap trống) → Native Memory tăng lên

// NIO Cleaner hoạt động bất đồng bộ
→ Độ trễ giữa "đối tượng chết" và "bộ nhớ được giải phóng"

// Giải pháp:
// 1. Giới hạn: -XX:MaxDirectMemorySize=2g
// 2. Dọn dẹp thủ công: ((DirectBuffer) buf).cleaner().clean();
//    ⚠️ Cảnh báo: cleaner().clean() là API nội bộ của JDK, không được đảm bảo
//    giữa các phiên bản. Chỉ dùng như phương án cuối cùng.
// 3. Giám sát: NMT
```

### Dynamic Proxy và Metaspace

```java
// Mỗi lần sinh proxy → một class mới
for (int i = 0; i < 1_000_000; i++) {
    // Class mới cho mỗi lời gọi!
    Object proxy = Proxy.newProxyInstance(
        classLoader,
        new Class<?>[] { Interface.class },
        handler
    );
}

// 1 triệu class → Metaspace OOM!
// Giải pháp: cache các proxy
```

### Kinh nghiệm Production

**Tình huống thực tế #1: Các script Groovy**
- Ứng dụng biên dịch các script Groovy khi đang chạy (on the fly)
- Mỗi script → một ClassLoader mới → các class mới
- Trong 2 tuần: Metaspace 256 MB → 4 GB → OOM
- Giải pháp: cache các script đã biên dịch

**Tình huống thực tế #2: Direct Buffer của Netty**
- Netty cấp phát DirectByteBuffer cho mỗi kết nối
- 10,000 kết nối × 1 MB = 10 GB Native Memory
- Heap trống (dữ liệu được gửi đi ngay lập tức) → GC không chạy
- OOM Killer giết tiến trình
- Giải pháp: `-XX:MaxDirectMemorySize` + buffer pool

### Best Practices

1. **ThreadLocal.remove()** trong `finally` luôn luôn
2. **Các collection tĩnh** → giới hạn + eviction policy (chính sách loại bỏ)
3. **Inner class** — hãy làm cho nested class trở thành `static` nếu nó KHÔNG cần truy cập các trường của outer class. Nếu cần truy cập — giữ non-static, nhưng kiểm soát vòng đời.
4. **try-with-resources** cho tất cả các Closeable
5. **Unsubscribe** khỏi các listener khi hủy
6. **Cache** các proxy và các script đã biên dịch
7. **MaxDirectMemorySize** để kiểm soát Native Memory
8. **NMT** để giám sát off-heap

### Tóm tắt cho Senior

- **ThreadLocal** — nguyên nhân số 1 trong các ứng dụng web
- **Inner class** — tham chiếu ngầm đến outer
- **ClassLoader leak** — Metaspace tăng lên một cách âm thầm
- **DirectByteBuffer** — rò rỉ nằm ngoài Heap (cần NMT)
- **Dynamic proxy** — hãy cache chúng!
- **String.intern()** — cẩn thận với các chuỗi duy nhất
- **Listener** — luôn unsubscribe
- **Native Memory** — có thể giết tiến trình ngay cả khi Heap trống

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- ThreadLocal trong thread pool: các luồng được tái sử dụng → `.remove()` trong `finally` là bắt buộc
- Non-static inner class ngầm giữ tham chiếu đến `Outer.this` → làm cho nó `static` nếu không cần truy cập outer
- Các collection tĩnh không có giới hạn — tăng vô hạn → dùng Caffeine/Guava với `maximumSize`
- `String.intern()` cho các chuỗi duy nhất (logs, UUID) làm đầy StringTable → OOM
- ClassLoader Leak: sinh class động (Spring/CGLIB/Groovy) → Metaspace tăng lên
- DirectByteBuffer — bộ nhớ nằm ngoài Heap (`-XX:MaxDirectMemorySize` để kiểm soát)
- Listener/Observer: đã subscribe → unsubscribe khi hủy

**Các câu hỏi phụ thường gặp:**
- **Tại sao Inner Class gây rò rỉ?** — Mọi non-static inner class đều có một trường ngầm `Outer.this`; nếu inner được truyền sang luồng khác — toàn bộ outer sẽ không bị xóa
- **Làm sao ngăn ClassLoader Leak?** — Cache các proxy và các script đã biên dịch; kiểm tra ThreadLocal, DriverManager, Introspector
- **Tại sao DirectByteBuffer nguy hiểm?** — Bộ nhớ nằm ngoài `-Xmx`; GC có thể không chạy khi Heap trống → Native Memory tăng lên → OOM Killer giết tiến trình
- **Khi nào `String.intern()` hữu ích?** — Để khử trùng lặp một tập chuỗi lặp lại đã biết (các giá trị kiểu enum); có hại cho các chuỗi duy nhất

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "ThreadLocal an toàn trong Tomcat" — nếu không có `.remove()` thì nó là nguyên nhân số 1 gây rò rỉ và lỗ hổng bảo mật
- `cleaner().clean()` cho DirectByteBuffer — đây là API nội bộ của JDK, không được đảm bảo giữa các phiên bản
- "Inner class — chỉ là cú pháp, không rò rỉ" — tham chiếu ngầm đến outer là có tồn tại
