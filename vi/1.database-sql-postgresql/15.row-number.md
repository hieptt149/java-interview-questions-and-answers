# What does ROW_NUMBER() do? (ROW_NUMBER() làm gì?)

## 🟢 Junior Level

**ROW_NUMBER()** — một window function (hàm cửa sổ) gán một số thứ tự duy nhất cho mỗi dòng.

**Ví dụ minh họa đơn giản:** Giống như việc đánh số trang trong một cuốn sách hoặc số thứ tự xếp hàng ở cửa hàng — mỗi người đều nhận được một số duy nhất theo thứ tự.

**Ví dụ:**
```sql
-- Đánh số tất cả đơn hàng theo ngày
SELECT
    id,
    amount,
    created_at,
    ROW_NUMBER() OVER(ORDER BY created_at DESC) as row_num
FROM orders;

-- Kết quả:
-- id | amount | created_at | row_num
-- 5  | 100    | 2024-04-01 | 1
-- 4  | 200    | 2024-03-15 | 2
-- 3  | 150    | 2024-03-01 | 3
```

**Các cách dùng phổ biến:**
- Đánh số dòng trong báo cáo
- Phân trang (pagination)
- Tìm bản ghi đầu tiên/cuối cùng trong một nhóm
- Loại bỏ các bản ghi trùng lặp

## 🟡 Middle Level

### Cú pháp

```sql
ROW_NUMBER() OVER(
    PARTITION BY column1  -- Phân chia thành các nhóm (tùy chọn)
    ORDER BY column2      -- Sắp xếp trong phạm vi nhóm (bắt buộc!)
)
```

### Các mẫu hình phổ biến

**1. Top-N cho mỗi nhóm:**
```sql
-- 3 đơn hàng gần nhất cho mỗi người dùng
SELECT * FROM (
    SELECT
        user_id,
        amount,
        created_at,
        ROW_NUMBER() OVER(PARTITION BY user_id ORDER BY created_at DESC) as rn
    FROM orders
) sub
WHERE rn <= 3;
```

**2. Loại bỏ trùng lặp (Deduplication):**
```sql
-- Chỉ giữ lại phiên bản mới nhất của mỗi bản ghi
WITH ranked AS (
    SELECT id, email, created_at,
           ROW_NUMBER() OVER(PARTITION BY email ORDER BY created_at DESC) as rn
    FROM users
)
DELETE FROM users WHERE id IN (SELECT id FROM ranked WHERE rn > 1);
```

**3. Phân trang (Pagination):**
```sql
-- Trang 3, 20 bản ghi mỗi trang
SELECT * FROM (
    SELECT id, name,
           ROW_NUMBER() OVER(ORDER BY id) as rn
    FROM users
) sub
WHERE rn BETWEEN 41 AND 60;
```

### Tính không xác định (Nondeterminism) — một cái bẫy quan trọng!

```sql
-- ❌ VẤN ĐỀ: nếu có những người dùng có cùng created_at
SELECT id, name, created_at,
       ROW_NUMBER() OVER(ORDER BY created_at DESC) as rn
FROM users;
-- Thứ tự của các dòng có cùng created_at KHÔNG được đảm bảo!

-- ✅ GIẢI PHÁP: thêm một cột duy nhất
SELECT id, name, created_at,
       ROW_NUMBER() OVER(ORDER BY created_at DESC, id DESC) as rn
FROM users;
-- id đảm bảo một thứ tự duy nhất
```

### ROW_NUMBER vs COUNT(*) OVER()

```sql
-- ROW_NUMBER() — rẻ (chỉ đơn giản tăng một bộ đếm)
SELECT id, name, ROW_NUMBER() OVER() as rn FROM users LIMIT 10;

-- COUNT(*) OVER() — tốn kém (đọc TẤT CẢ các dòng trong partition)
SELECT id, name, COUNT(*) OVER() as total FROM users LIMIT 10;
-- ⚠️ Mặc dù có LIMIT 10, cơ sở dữ liệu vẫn sẽ đọc TẤT CẢ users!
```

### Các lỗi thường gặp

1. **Lọc trong cùng một truy vấn**
   ```sql
   -- ❌ LỖI: WHERE không thể nhìn thấy rn
   SELECT id, ROW_NUMBER() OVER(ORDER BY id) as rn
   FROM users
   WHERE rn <= 10;  -- Lỗi: column "rn" does not exist

   -- ✅ Subquery hoặc CTE
   SELECT * FROM (
       SELECT id, ROW_NUMBER() OVER(ORDER BY id) as rn FROM users
   ) sub WHERE rn <= 10;
   ```

2. **Quên ORDER BY**
   ```sql
   -- ❌ Lỗi cú pháp
   ROW_NUMBER() OVER(PARTITION BY user_id)

   -- ✅ ORDER BY là bắt buộc
   ROW_NUMBER() OVER(PARTITION BY user_id ORDER BY created_at)
   ```

### So sánh với các giải pháp thay thế

| Hàm       | Tính duy nhất | Xử lý các giá trị bằng nhau                   |
| -------------- | ---------- | --------------------------------------- |
| **ROW_NUMBER()** | ✅ Luôn luôn  | Đánh số chúng một cách tùy ý                |
| **RANK()**       | ❌ Không      | Giá trị bằng nhau = cùng thứ hạng, sau đó bỏ qua     |
| **DENSE_RANK()** | ❌ Không      | Giá trị bằng nhau = cùng thứ hạng, không bỏ qua      |

### Khi nào KHÔNG nên dùng ROW_NUMBER

1. **Để tổng hợp** (COUNT, SUM, AVG) — hãy dùng các hàm tổng hợp dạng window (window aggregate function) thay thế
2. **Để xếp hạng có xử lý trường hợp bằng nhau (ties)** — hãy dùng RANK hoặc DENSE_RANK thay thế
3. **Để phân trang API trên bảng lớn** (> 1 triệu dòng) — hãy dùng Keyset Pagination (`WHERE id > ?`)

## 🔴 Senior Level

### Tối ưu hóa vật lý: loại bỏ Sort

**Điểm mấu chốt:** Nếu dữ liệu đã được sắp xếp sẵn, PostgreSQL sẽ bỏ qua giai đoạn Sort!

```sql
-- Index trên (user_id, created_at DESC)
CREATE INDEX idx_orders_user_date ON orders(user_id, created_at DESC);

-- Truy vấn:
SELECT user_id, amount, created_at,
       ROW_NUMBER() OVER(PARTITION BY user_id ORDER BY created_at DESC) as rn
FROM orders;

-- Plan: WindowAgg → Index Scan (KHÔNG có Sort!)
-- WindowAgg — một node trong execution plan của PostgreSQL dùng để tính toán
-- window function. Khi bạn thấy `WindowAgg → Index Scan` — dữ liệu được đọc
-- theo đúng thứ tự sẵn có và giai đoạn Sort bị bỏ qua.
-- → Dữ liệu được đọc từ index theo đúng thứ tự sẵn có
-- → Nhanh hơn 10-50 lần trên các bảng lớn!
```

**Giám sát:**
```sql
EXPLAIN SELECT ... ROW_NUMBER() OVER(...);
-- Tìm: WindowAgg → Index Scan → tuyệt vời!
-- Tìm: WindowAgg → Sort → có thể được tối ưu bằng index
```

### Bounded Heap Sort (tối ưu hóa Top-N)

Khi `ROW_NUMBER()` được sử dụng cùng với `LIMIT`:

```sql
SELECT * FROM (
    SELECT id, amount,
           ROW_NUMBER() OVER(ORDER BY amount DESC) as rn
    FROM orders
) sub WHERE rn <= 10;

-- PostgreSQL áp dụng Bounded Heap Sort:
-- → KHÔNG sắp xếp toàn bộ bảng
-- → Chỉ giữ lại top-10 phần tử trong bộ nhớ (giống như bạn chọn
--   10 ứng viên hàng đầu mà không cần sắp xếp toàn bộ 1000 hồ sơ)
-- → Loại bỏ những phần tử thừa trong lúc xử lý
-- → Bộ nhớ: O(k) thay vì O(n), trong đó k = LIMIT
```

### Incremental Sort (Sắp xếp tăng dần) (PG 13+)

```sql
-- Index trên user_id
CREATE INDEX idx_orders_user ON orders(user_id);

-- Truy vấn với PARTITION BY
SELECT user_id, created_at,
       ROW_NUMBER() OVER(PARTITION BY user_id ORDER BY created_at DESC) as rn
FROM orders;

-- PG 13+: Incremental Sort
-- Dữ liệu đã được gộp nhóm sẵn theo user_id (từ index)
-- → Chỉ cần sắp xếp theo created_at trong phạm vi từng nhóm
-- → Rẻ hơn nhiều so với việc sắp xếp toàn bộ!
-- Ở PG 12 trở xuống — sắp xếp toàn bộ dữ liệu, ngay cả khi một phần đã được sắp xếp sẵn.
```

### Keyset Pagination (tốt hơn ROW_NUMBER)

```sql
-- ❌ Phân trang bằng ROW_NUMBER (chậm với OFFSET lớn)
SELECT * FROM (
    SELECT id, name, ROW_NUMBER() OVER(ORDER BY id) as rn
    FROM users
) sub WHERE rn BETWEEN 100001 AND 100020;

-- ✅ Keyset Pagination (nhanh, sử dụng index)
SELECT id, name FROM users
WHERE id > 100000  -- id cuối cùng từ trang trước
ORDER BY id
LIMIT 20;
-- → Index Scan, O(log n + k) thay vì O(n)
-- ROW_NUMBER yêu cầu đánh số TẤT CẢ các dòng cho đến OFFSET mong muốn,
-- trong khi Keyset Pagination nhảy thẳng đến đúng vị trí thông qua B-tree index.
-- Đối với trang 50,000: ROW_NUMBER xử lý 100,000 dòng, Keyset — chỉ 20 dòng.
```

**Khi nào nên dùng Keyset:**
- Cuộn vô hạn (infinite scroll)
- Phân trang API
- Bảng lớn (> 1 triệu dòng)

**Khi nào ROW_NUMBER vẫn ổn:**
- Trang bất kỳ (nhảy đến trang 57)
- Bảng nhỏ (< 100,000 dòng)
- Báo cáo có đánh số cố định

### Tính xác định (Determinism) và ổn định

```sql
-- Luôn làm cho ORDER BY có tính xác định!
-- Không tốt:
ROW_NUMBER() OVER(ORDER BY created_at)

-- Tốt (thêm PK):
ROW_NUMBER() OVER(ORDER BY created_at DESC, id DESC)

-- Tại sao?
-- Nếu 2 bản ghi có cùng created_at
-- → Thứ tự giữa chúng không được xác định
-- → Kết quả có thể thay đổi giữa các lần chạy
-- → Lỗi trong production!
```

### Các trường hợp đặc biệt (Edge Cases)

1. **PARTITION BY với một phần tử duy nhất**
   ```sql
   -- Nếu một nhóm chỉ có 1 dòng → rn = 1 luôn luôn
   SELECT user_id, ROW_NUMBER() OVER(PARTITION BY user_id ORDER BY id) as rn
   FROM orders;
   -- Với người dùng có 1 đơn hàng: rn = 1
   -- Với người dùng có N đơn hàng: rn = 1, 2, ..., N
   ```

2. **NULL trong ORDER BY**
   ```sql
   -- NULL mặc định là LAST trong DESC
   SELECT id, priority,
          ROW_NUMBER() OVER(ORDER BY priority DESC) as rn
   FROM tasks;

   -- Quản lý NULL một cách tường minh
   SELECT id, priority,
          ROW_NUMBER() OVER(ORDER BY priority DESC NULLS LAST) as rn
   FROM tasks;
   ```

3. **ROW_NUMBER() không có PARTITION BY**
   ```sql
   -- Đánh số TẤT CẢ các dòng
   SELECT id, name, ROW_NUMBER() OVER(ORDER BY id) as rn
   FROM users;
   -- rn = 1, 2, 3, ..., N
   ```

### Tinh chỉnh hiệu năng (Performance Tuning)

**Bộ nhớ cho Sort:**
```sql
-- Nếu Sort không đủ vừa với work_mem → tràn ra đĩa
EXPLAIN (ANALYZE) SELECT ... ROW_NUMBER() OVER(ORDER BY ...);
-- "external merge Disk: X kB" → hãy tăng work_mem

-- Tạm thời tăng cho truy vấn
SET work_mem = '256MB';
-- ... truy vấn ...
RESET work_mem;
```

**Tính song song:**
```sql
-- WindowAgg KHÔNG chạy song song trong PG < 14
-- PG 14+: có thể sử dụng Parallel Gather trước WindowAgg
-- Nhưng bản thân WindowAgg chạy trong một tiến trình duy nhất

-- Giải pháp thay thế cho dữ liệu lớn:
-- Phân vùng bảng (table partitioning) + UNION ALL
```

### Kinh nghiệm Production

**Tình huống thực tế #1: Loại bỏ trùng lặp trên 10 triệu bản ghi**
- CRM: các liên hệ trùng lặp (cùng email)
- Truy vấn với ROW_NUMBER + DELETE: 3 phút
- Giải pháp:
  - Index trên `(email, created_at DESC)`
  - DELETE theo lô (batch) từng 10,000 bản ghi
- Kết quả: 15 giây

**Tình huống thực tế #2: Phân trang API**
- API e-commerce: phân trang bằng ROW_NUMBER trên 10 triệu sản phẩm
- Trang 50,000: 8 giây
- Giải pháp: Keyset Pagination (WHERE id > ?)
- Kết quả: 50ms (nhanh hơn 160 lần)

### Giám sát (Monitoring)

```sql
-- 1. Kiểm tra execution plan
EXPLAIN (ANALYZE, BUFFERS)
SELECT ... ROW_NUMBER() OVER(...);
-- WindowAgg → Sort → có thể được tối ưu bằng index
-- WindowAgg → Index Scan → tuyệt vời!

-- 2. Kiểm tra bộ nhớ Sort
EXPLAIN (ANALYZE)
SELECT ... ROW_NUMBER() OVER(ORDER BY ...);
-- "Disk: X kB" → tràn dữ liệu! Hãy tăng work_mem

-- 3. Tìm các truy vấn có ROW_NUMBER
SELECT query, mean_exec_time
FROM pg_stat_statements
WHERE query LIKE '%ROW_NUMBER()%'
ORDER BY mean_exec_time DESC;
```

### Best Practices (Thực hành tốt nhất)

1. **Luôn thêm PK** vào ORDER BY để đảm bảo tính xác định
2. **Index** trên `(PARTITION BY, ORDER BY)` → không cần Sort
3. **Keyset Pagination** cho các bảng lớn
4. **ROW_NUMBER** chỉ dùng cho báo cáo/phân trang theo số trang
5. **Bounded Heap Sort** tự động khi có LIMIT
6. **Incremental Sort (PG 13+)** với index
7. **Subquery/CTE** để lọc theo rn

### Tóm tắt cho Senior

- **ROW_NUMBER()** — đánh số duy nhất, luôn có tính xác định khi có PK
- **Index** trên `(PARTITION BY, ORDER BY)` → WindowAgg không cần Sort
- **Bounded Heap Sort** với LIMIT → bộ nhớ O(k)
- **Keyset Pagination** > ROW_NUMBER cho API và infinite scroll
- **Incremental Sort (PG 13+)** tiết kiệm thời gian với sắp xếp một phần
- **Tính xác định:** luôn thêm PK vào ORDER BY
- **COUNT(*) OVER()** tốn kém — đọc TẤT CẢ các dòng trong partition, đừng dùng cùng với LIMIT
- **Lọc** chỉ trong subquery/CTE

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- ROW_NUMBER() — đánh số duy nhất cho mỗi dòng (1, 2, 3, ...)
- PARTITION BY — phân chia thành các nhóm, ORDER BY — sắp xếp bên trong nhóm (bắt buộc!)
- Tính xác định: luôn thêm PK vào ORDER BY (`ORDER BY created_at DESC, id DESC`)
- Lọc theo rn → CHỈ trong subquery/CTE (window function được tính toán SAU WHERE)
- Bounded Heap Sort: với LIMIT — bộ nhớ O(k) thay vì O(n)
- Keyset Pagination (`WHERE id > last_id`) > ROW_NUMBER cho API/infinite scroll
- Index trên `(PARTITION BY, ORDER BY)` → WindowAgg không cần Sort
- Incremental Sort (PG 13+): dữ liệu đã sắp xếp một phần → nhanh hơn
- COUNT(*) OVER() tốn kém — đọc TẤT CẢ các dòng trong partition, đừng dùng cùng với LIMIT
- Loại bỏ trùng lặp: ROW_NUMBER + DELETE WHERE rn > 1

**Các câu hỏi phụ thường gặp:**
- "Tại sao phân trang bằng ROW_NUMBER lại chậm với OFFSET lớn?" → Sắp xếp tất cả các dòng cho đến OFFSET
- "Keyset Pagination là gì?" → `WHERE id > last_id ORDER BY id LIMIT 20` → Index Scan
- "Tại sao cần PK trong ORDER BY?" → Nếu không có PK, thứ tự giữa các giá trị bằng nhau là không xác định
- "Khi nào COUNT(*) OVER() là một vấn đề?" → Mặc dù có LIMIT, nó vẫn đọc TẤT CẢ các dòng

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "ROW_NUMBER có thể được lọc trong WHERE" (sai, được tính toán sau WHERE)
- ❌ "Keyset Pagination giống với ROW_NUMBER" (Keyset = Index Scan, ROW_NUMBER = Sort)
- ❌ "`COUNT(*) OVER()` vẫn ổn khi dùng với LIMIT" (nó đọc TẤT CẢ các dòng!)
