# What are suppressed exceptions? (Suppressed exception là gì?)

## Junior Level

### Định nghĩa

**Suppressed exception** - một cơ chế của Java 7+ cho phép một exception mang theo một danh sách các exception khác xảy ra song song.

### Gặp ở đâu

Thường gặp nhất - trong **try-with-resources**:

```java
try (Resource r = new Resource()) {
    r.doWork(); // IOException #1 - chính
} // close() ném IOException #2 - suppressed
```

### Cách lấy chúng

```java
try {
    // code
} catch (Exception e) {
    System.out.println("Main: " + e.getMessage());

    Throwable[] suppressed = e.getSuppressed();
    for (Throwable t : suppressed) {
        System.out.println("Suppressed: " + t.getMessage());
    }
}
```

### Tại sao cần nó

Trước Java 7, nếu exception xảy ra ở cả `try` và `finally`, cái thứ hai xóa cái đầu tiên (shadowing). Lập trình viên mất thông tin về nguyên nhân gốc của lỗi.

**Tại sao lại là Java 7:** trong Java 7, **try-with-resources** xuất hiện (JLS 14.20.3), thứ tự động đóng resource. Khi đóng tự động qua `close()`, có xác suất cao rằng `close()` sẽ ném một exception **đồng thời** với một exception từ `try` chính. Không có cơ chế suppressed, một exception sẽ xóa cái kia, khiến việc debug trở nên bất khả thi. Suppressed exception là một bổ sung hạ tầng cho TWR, không phải một tính năng độc lập.

### Khi nào suppressed KHÔNG được thêm

1. **try-finally thủ công** - trong `try { ... } finally { close(); }` thông thường suppressed KHÔNG được thêm tự động. Exception từ `finally` che khuất exception từ `try`. Suppressed hoạt động **chỉ** trong try-with-resources hoặc khi gọi `addSuppressed()` thủ công.

2. **`enableSuppression = false`** - nếu exception được tạo với `new Exception(msg, cause, false, true)`, các lời gọi `addSuppressed()` sẽ bị bỏ qua.

3. **`close()` không ném** - nếu resource đóng đúng cách, danh sách suppressed sẽ rỗng. Đây là một tình huống bình thường.

4. **Exception chỉ ở một chỗ** - nếu chỉ `try` lỗi (nhưng không phải `close()`) hoặc chỉ `close()` lỗi (nhưng không phải `try`), sẽ không có suppressed - chỉ một exception bình thường.

### Khi nào KHÔNG nên dựa vào suppressed

1. **try-finally thủ công** - suppressed KHÔNG hoạt động tự động. Nếu bạn viết `try { ... } finally { resource.close(); }` và cả hai đều có thể lỗi - thông tin sẽ bị mất. Hãy dùng try-with-resources.

2. **Thư viện bên ngoài không có TWR** - nếu một thư viện bên thứ ba không implement `AutoCloseable` hoặc đóng resource thủ công, suppressed sẽ không được thêm.

3. **Ngữ cảnh async** - trong `CompletableFuture` hoặc reactive stream, các exception từ các thread khác nhau không được tổng hợp qua suppressed một cách tự động.

4. **Xử lý theo lô mà không có mẫu** - nếu bạn xử lý một lô các task và mỗi cái có thể lỗi, suppressed sẽ không tự thêm - bạn cần dùng `addSuppressed()` thủ công.

### Khi nào KHÔNG nên dùng suppressed exception

1. **Các object singleton sống lâu** - tích lũy các suppressed exception dẫn tới rò rỉ bộ nhớ
2. **Serialize qua mạng** - toàn bộ danh sách suppressed được truyền qua mạng, làm tăng payload
3. **Hệ thống Highload** - mỗi suppressed exception = object + stack trace trong heap
4. **Như một sự thay thế cho việc xử lý lỗi thông thường** - suppressed không thay thế try-catch trên mỗi resource
5. **Trong logic nghiệp vụ** - suppressed được dành cho code hạ tầng (resource, xử lý theo lô)

## Middle Level

### Hiện thực bên trong

Trong `Throwable` có một trường `private Throwable[] suppressedExceptions` (mảng, không phải list - để tăng hiệu suất).

- Được khởi tạo **một cách lười (lazily)** - chỉ ở lời gọi `addSuppressed` đầu tiên
- Có thể bị tắt khi tạo: `new Exception(msg, cause, false, true)` - `enableSuppression = false`

### Cách compiler sinh code cho try-with-resources

Khi bạn viết:

```java
try (Resource r = new Resource()) {
    r.doWork();
}
```

Compiler bung nó thành (đơn giản hóa):

```java
Resource r = new Resource();
Throwable primaryException = null;
try {
    r.doWork();
} catch (Throwable e) {
    primaryException = e;
    throw e;
} finally {
    if (r != null) {
        if (primaryException != null) {
            try {
                r.close();
            } catch (Throwable closeException) {
                primaryException.addSuppressed(closeException);
            }
        } else {
            r.close(); // Không có exception chính - close() ném như bình thường
        }
    }
}
```

**Điểm mấu chốt:** compiler lưu một tham chiếu tới exception chính (`primaryException`) và khi `close()` lỗi thêm nó dưới dạng suppressed vào cái chính, thay vì thay thế nó.

### Các tham số của constructor Throwable

```java
public Throwable(String message, Throwable cause,
                 boolean enableSuppression, boolean writableStackTrace)
```

- `enableSuppression` - bật/tắt suppressed (mặc định là true)
- `writableStackTrace` - nếu false, stack trace không được điền (tăng tốc việc tạo exception)

### Vai trò trong try-with-resources

Kịch bản:
1. Đọc file trong `try` -> `IOException` (đĩa bị ngắt kết nối)
2. TWR đóng file -> `IOException` thứ hai (đĩa biến mất)
3. Trong Java cũ cái thứ hai sẽ xóa cái đầu tiên
4. Trong hiện đại: cái đầu tiên tới bạn, cái thứ hai - `e.getSuppressed()`

### Sử dụng thủ công

Dù TWR làm việc này tự động, bạn có thể dùng nó thủ công:

```java
Exception mainException = new BatchException("Batch failed");

for (Task task : tasks) {
    try {
        task.execute();
    } catch (Exception e) {
        mainException.addSuppressed(e);
    }
}

if (mainException.getSuppressed().length > 0) {
    throw mainException;
}
```

### Các hạn chế

- **Self-Suppression:** `e.addSuppressed(e)` -> `IllegalArgumentException`
- **Null Suppression:** `e.addSuppressed(null)` -> `NullPointerException`
- **Thứ tự:** suppressed được lưu theo thứ tự thêm vào. Trong TWR - thứ tự ngược lại với việc khai báo resource (LIFO)

## Senior Level

### Rủi ro Memory Leak

Thêm suppressed exception vô tận vào một object sống lâu (singleton) - rò rỉ bộ nhớ. Mỗi exception mang theo stack trace của nó.

### Chi phí Serialization

Toàn bộ danh sách các suppressed exception được serialize cùng với cái chính. Trong các hệ thống phân tán - khối lượng dữ liệu khổng lồ qua mạng.

### Mẫu Batch Processing

```java
public class BatchException extends RuntimeException {
    private final List<Throwable> errors = new ArrayList<>();

    public BatchException(String message) {
        super(message);
    }

    public void addError(Throwable t) {
        if (errors.isEmpty()) {
            // Exception đầu tiên - như suppressed vào chính nó
            addSuppressed(t);
        } else {
            addSuppressed(t);
        }
        errors.add(t);
    }

    public int getErrorCount() {
        return errors.size();
    }
}
```

### Quản lý Resource tùy chỉnh

Nếu bạn viết resource manager của riêng mình (thread pool, transaction manager) không dùng TWR tiêu chuẩn:

```java
public class CustomResourceManager implements AutoCloseable {
    private final List<Resource> resources = new ArrayList<>();
    private Throwable primaryException;

    public void close() {
        for (Resource r : resources) {
            try {
                r.close();
            } catch (Throwable t) {
                if (primaryException == null) {
                    primaryException = t;
                } else {
                    primaryException.addSuppressed(t);
                }
            }
        }
        if (primaryException != null) {
            throw new RuntimeException("Close failed", primaryException);
        }
    }
}
```

### Chẩn đoán

- **Logging** - Logback/Log4j2 tự động in suppressed với tiền tố `Suppressed:`
- **Unit test** - kiểm tra `getSuppressed()` khi test việc dọn dẹp resource
- **JSON Layout** - suppressed như một trường mảng riêng trong ELK
- **Metric** - đếm suppressed qua Micrometer

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Suppressed exception - cơ chế Java 7+, cho phép một exception mang theo một danh sách các lỗi song song
- Xuất hiện cùng try-with-resources - cho các trường hợp khi cả `try` và `close()` đều lỗi
- Trong `try-finally` thông thường suppressed KHÔNG được thêm tự động - exception từ `finally` che khuất `try`
- `addSuppressed()` có thể được gọi thủ công để xử lý lỗi theo lô
- Self-suppression (`e.addSuppressed(e)`) -> `IllegalArgumentException`
- Mảng suppressed được khởi tạo một cách lười - chỉ ở lời gọi `addSuppressed` đầu tiên
- Có thể bị tắt: `new Exception(msg, cause, false, true)` - `enableSuppression = false`

**Các câu hỏi phụ thường gặp:**
- **Cách lấy suppressed?** - `e.getSuppressed()` trả về `Throwable[]`
- **Khi nào suppressed KHÔNG hoạt động?** - try-finally thủ công, `enableSuppression = false`, chỉ một exception
- **Tại sao cần trong xử lý theo lô?** - Thu thập tất cả các lỗi của một lô trong một `BatchException`
- **Có memory overhead không?** - Có, mỗi suppressed = object + stack trace, nguy hiểm cho các singleton

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Suppressed hoạt động trong try-finally thông thường" - không, chỉ trong try-with-resources hoặc thủ công
- "Không quan trọng tích lũy bao nhiêu suppressed" - rò rỉ bộ nhớ trong các object sống lâu
- "Suppressed thay thế việc xử lý lỗi thông thường" - không, đó là một cơ chế hạ tầng
- "Serialize suppressed là miễn phí" - toàn bộ stack trace của mỗi suppressed đi qua mạng
