# What is Metaspace (or PermGen)? (Metaspace hay PermGen là gì?)

## Junior Level

**Metaspace** — vùng bộ nhớ (nằm ngoài Heap) nơi Java lưu trữ metadata của class.

**Metadata bao gồm:** tên class, tên và chữ ký (signature) của các phương thức, các trường, các annotation, constant pool, vtable/itable (bảng phương thức ảo).

**Ví dụ minh họa đơn giản:** Nếu Heap là một cái tủ quần áo có quần áo, thì Metaspace là một cuốn catalog chứa các mô tả về quần áo.

**Những gì được lưu trữ:**
- Thông tin về class
- Các phương thức và byte-code của chúng
- Constant Pool

**PermGen → Metaspace (Java 8):**
- PermGen: kích thước cố định nằm bên trong Heap → OOM
- Metaspace: OOM xảy ra ít hơn, nhưng vẫn phổ biến khi sinh class động (Spring, Hibernate, Groovy, CGLIB)

---

## Middle Level

### PermGen vs Metaspace

| Đặc điểm           | PermGen       | Metaspace     |
| ------------------ | ------------- | ------------- |
| Vị trí             | Bên trong Heap | Native Memory |
| Kích thước         | Cố định       | Động          |
| OOM                | Thường xuyên  | Hiếm          |

### Điều gì gây ra sự tăng trưởng của Metaspace

```
1. Nhiều class trong ứng dụng
2. Sinh class động (các proxy của Spring, CGLIB)
3. Các ClassLoader leak
4. Các scripting engine (Groovy, JavaScript)
```

### Cấu hình

```bash
-XX:MetaspaceSize=256m      # Ngưỡng cho lần GC đầu tiên
-XX:MaxMetaspaceSize=512m   # Tối đa (bắt buộc!)
```

### ClassLoader Leaks

```
Các class sống chừng nào ClassLoader của chúng còn sống
  → Nếu ClassLoader không bị GC → tất cả các class vẫn còn

Nguyên nhân:
  - ThreadLocal giữ đối tượng từ ClassLoader
  - Trường tĩnh tham chiếu đến class của ứng dụng
  - JDBC driver trong DriverManager
```

## Senior Level

### Compressed Class Space

```
Vùng riêng biệt trong Metaspace cho các cấu trúc Klass
  → Mặc định 1 GB
  → -XX:CompressedClassSpaceSize để thay đổi

Klass = bản sao (mirror) bằng C++ của một Java class
  → InstanceKlass (vtable, itable)
  → Method Metadata
  → Constant Pool
```

### Cơ chế High-Water Mark

```
1. Metaspace tăng lên → đạt đến MetaspaceSize
2. Full GC → cố gắng unload các ClassLoader
3. Nếu không đủ → mở rộng và nâng ngưỡng lên
4. Lặp lại

Vấn đề: một chuỗi các Full GC khi ứng dụng khởi động
Giải pháp: MetaspaceSize = mức tiêu thụ điển hình sau khi warmup
```

### Elastic Metaspace (Java 16+)

```
JEP 387: cải thiện việc trả bộ nhớ về cho OS
  → Trước đây: các Chunk lớn → phân mảnh
  → Bây giờ: các khối nhỏ → trả về một cách tích cực
```

### Chẩn đoán

```bash
jcmd <pid> VM.metaspace       # Báo cáo chi tiết
jstat -gc <pid> 1000          # Cột MU
-Xlog:class+load=info         # Việc nạp class
```

### Best Practices

1. **MaxMetaspaceSize** — bắt buộc trong Docker. Đừng đặt quá sát với mức tiêu thụ thực tế — điều này gây ra Full GC thường xuyên. Giữ ít nhất 30-50% biên độ dự phòng.
2. **MetaspaceSize** = mức tiêu thụ sau khi warmup
3. **Giám sát** các ClassLoader leak
4. **Cache** các proxy và các script
5. **TraceClassLoading** để debug

### Tóm tắt cho Senior

- **Metaspace** = native memory cho metadata của class
- **High-Water Mark** = mở rộng động
- **ClassLoader Leaks** = nguyên nhân chính của OOM
- **Compressed Class Space** = giới hạn 1 GB
- **Elastic Metaspace (Java 16+)** = trả bộ nhớ tốt hơn

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Metaspace (Java 8+) lưu trữ metadata của class: tên class, các phương thức, các trường, các annotation, constant pool, vtable/itable
- PermGen (trước Java 7): bên trong Heap, kích thước cố định → OOM thường xuyên; Metaspace: native memory, tăng trưởng động
- ClassLoader Leak — nguyên nhân chính của Metaspace OOM; các class sống chừng nào ClassLoader của chúng còn sống
- High-Water Mark: Metaspace tăng lên → Full GC → nếu ít cái được unload → mở rộng → chuỗi các Full GC khi khởi động
- `-XX:MaxMetaspaceSize` là bắt buộc trong Docker; `-XX:MetaspaceSize` = mức tiêu thụ điển hình sau khi warmup
- Elastic Metaspace (Java 16+, JEP 387): các khối nhỏ thay vì các Chunk lớn → trả bộ nhớ về OS một cách tích cực
- Compressed Class Space: vùng riêng ~1 GB cho các cấu trúc Klass (bản sao C++ của các Java class)

**Các câu hỏi phụ thường gặp:**
- **Điều gì gây ra sự tăng trưởng của Metaspace?** — Sinh class động (Spring/CGLIB/Hibernate), các script Groovy/JavaScript, các ClassLoader leak
- **Tại sao MetaspaceSize gây Full GC khi khởi động?** — Khi đạt đến ngưỡng, JVM kích hoạt Full GC để unload các ClassLoader; nếu ngưỡng quá thấp — chuỗi các Full GC
- **Làm sao chẩn đoán ClassLoader leak?** — `jcmd <pid> VM.metaspace`, `-Xlog:class+load=info`, so sánh việc nạp/unload class
- **Tại sao không nên đặt MaxMetaspaceSize quá sát?** — Giữ ít nhất 30-50% biên độ trên mức tiêu thụ thực tế; nếu không Full GC thường xuyên

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Metaspace nằm bên trong Heap" — Metaspace nằm trong native memory (ngoài Heap)
- "PermGen và Metaspace là một" — PermGen cố định bên trong Heap, Metaspace động trong native memory
- "Metaspace OOM là không thể xảy ra" — xảy ra khi sinh class động và có ClassLoader leak
