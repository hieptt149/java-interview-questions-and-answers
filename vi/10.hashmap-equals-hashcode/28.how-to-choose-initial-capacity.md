# How to Choose the Initial Capacity for HashMap? (Làm sao chọn Initial Capacity cho HashMap?)

## 🟢 Junior Level

**Initial capacity** là kích thước của mảng nội bộ của HashMap, được đặt lúc tạo.

Nếu không chỉ định — nó mặc định là 16. Nhưng nếu bạn biết map sẽ có bao nhiêu phần tử, tốt hơn là đặt capacity ngay từ đầu.

**Tại sao?** Để HashMap không lãng phí thời gian vào việc resize, thứ vốn chậm.

**Công thức đơn giản:**
```java
int capacity = (expected_count / 0.75) + 1;
Map<String, Integer> map = new HashMap<>(capacity);
```

**Ví dụ:**
```java
// Mong đợi 100 phần tử:
int capacity = (int) (100 / 0.75) + 1; // = 134
// HashMap làm tròn thành lũy thừa của hai gần nhất hướng lên: 256
Map<String, Integer> map = new HashMap<>(134);
// threshold = 256 * 0.75 = 192 — 100 phần tử vừa vặn không cần resize
```

## 🟡 Middle Level

### Vấn đề Resize

Mỗi lần resize là O(n): tạo một mảng mới + sao chép mọi phần tử.

```java
// Không chỉ định capacity:
new HashMap<>();       // capacity = 16, threshold = 12
// Ở 13 phần tử: resize thành 32
// Ở 25 phần tử: resize thành 64
// Ở 49 phần tử: resize thành 128
// ... và cứ thế
```

Mỗi lần resize — một độ trễ và tải GC.

### Công thức Capacity lý tưởng

```java
initialCapacity = (expectedSize / loadFactor) + 1
```

**Tại sao +1?** threshold được kiểm tra như `++size > threshold`. Không có +1, phần tử cuối cùng trigger một lần resize.

### Làm tròn thành Lũy thừa của hai

HashMap luôn làm tròn capacity lên thành lũy thừa của hai:

| Truyền vào | Trở thành |
| -------- | -------- |
| 10       | 16       |
| 100      | 128      |
| 1000     | 1024     |
| 1335     | 2048     |

### Ví dụ thực tế cho 1000 phần tử

```java
// Sai:
new HashMap<>(1000);
// → capacity = 1024, threshold = 768
// → Ở 769 phần tử, resize thành 2048!

// Đúng:
new HashMap<>((int)(1000 / 0.75f) + 1); // = 1334
// → capacity = 2048, threshold = 1536
// → 1000 phần tử vừa vặn không cần resize
```

### Khi nào bạn không cần chỉ định Capacity

- Các collection nhỏ (2-5 phần tử) — overhead của việc tính toán vượt quá lợi ích
- Số lượng phần tử không rõ — constructor mặc định

### Các Helper của Guava

```java
// Google Guava — đã chứa sẵn công thức đúng:
Map<K, V> map = Maps.newHashMapWithExpectedSize(1000);
```

### Các sai lầm thường gặp

1. **Truyền số lượng mong đợi trực tiếp** — `new HashMap(1000)` cho threshold 768
2. **Quên +1** — phần tử cuối cùng trigger resize
3. **Capacity quá mức** — iterate chậm qua các bucket rỗng

## 🔴 Senior Level

### Bên trong tableSizeFor

```java
static final int tableSizeFor(int cap) {
    int n = cap - 1;
    n |= n >>> 1;
    n |= n >>> 2;
    n |= n >>> 4;
    n |= n >>> 8;
    n |= n >>> 16;
    return (n < 0) ? 1 : (n >= MAXIMUM_CAPACITY) ? MAXIMUM_CAPACITY : n + 1;
}
```

Thuật toán bit này tìm lũy thừa của hai gần nhất trong O(1).

### Phân tích Chi phí Resize

Khi resize capacity=N:
- Cấp phát: N tham chiếu × 8 byte
- Sao chép: size phần tử
- GC: mảng cũ → rác
- Tăng vọt latency: 1-100ms tùy kích thước

Trong các hệ thống nhạy về latency (HFT, real-time), resize là không chấp nhận được.

### Hiệu năng Iterate

```java
// capacity = 1.000.000, size = 10
for (var entry : map.entrySet()) { ... }
// Iterator duyệt 1.000.000 bucket, trong đó 10 được lấp đầy
// 999.990 lần kiểm tra rỗng — overhead khổng lồ
```

Đừng ước lượng capacity quá cao khi không cần.

### Đánh đổi về bộ nhớ

| Capacity            | Bộ nhớ (mảng)  | Số lần Resize | Iterate   |
| ------------------- | --------------- | --------- | ---------- |
| Kích thước chính xác | Tối thiểu      | Thường xuyên | Nhanh    |
| Có dư (công thức)   | Nhiều hơn một chút | Không   | Nhanh      |
| Ước lượng quá cao nhiều | Nhiều hơn nhiều | Không   | Chậm       |

### Production: Dynamic Sizing

Trong một số framework (Netty, Kafka), các map tùy chỉnh được dùng với:
- Latency dự đoán được (không resize)
- Ring buffer cho eviction
- Open addressing để tiết kiệm bộ nhớ

### Benchmark: Ảnh hưởng của Capacity sai

| Kịch bản              | Thời gian chèn 1M phần tử         |
| --------------------- | --------------------------------- |
| Không có capacity (resize) | 120ms                        |
| Capacity đúng         | 45ms                              |
| Ước lượng quá cao 10x | 50ms (chèn) / 500ms (iterate)     |

### Công thức Best Practice

```java
/**
 * Tạo một HashMap không resize cho expectedSize phần tử.
 */
public static <K, V> HashMap<K, V> newHashMap(int expectedSize) {
    return new HashMap<>((int) Math.ceil(expectedSize / 0.75) + 1);
}
```

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Công thức: `initialCapacity = (expectedSize / loadFactor) + 1` — để tránh resize
- HashMap làm tròn thành lũy thừa của hai gần nhất qua tableSizeFor()
- Không có công thức: new HashMap(1000) → capacity=1024, threshold=768 → resize ở 769 phần tử
- Có công thức: (1000/0.75)+1=1334 → capacity=2048, threshold=1536 → không resize
- Mỗi lần resize = O(n): cấp phát + sao chép + GC pressure + tăng vọt latency
- Capacity ước lượng quá cao = iterate chậm qua các bucket rỗng (O(capacity + size))
- Đừng chỉ định capacity cho các collection nhỏ (2-5 phần tử)

**Các câu hỏi phụ thường gặp:**
- **Tại sao +1 trong công thức?** — threshold được kiểm tra như `++size > threshold`; không có +1, phần tử cuối cùng trigger resize
- **tableSizeFor là gì?** — thuật toán bit: tìm lũy thừa của hai gần nhất trong O(1)
- **Khi nào dùng Guava Maps.newHashMapWithExpectedSize?** — đã chứa sẵn công thức đúng
- **Resize tốn gì?** — 1-100ms tùy kích thước; cho 1M phần tử ~150ns (P99 ~5000ns)

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "new HashMap(1000) tạo 1000 bucket" — không, 1024, và threshold = 768
- "Capacity càng lớn càng tốt" — không, iterate chậm hơn, bộ nhớ bị lãng phí
- "Capacity có thể được thay đổi sau khi tạo" — không, đặt trong constructor
