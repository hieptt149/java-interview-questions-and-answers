# Can you create custom exceptions? (Bạn có thể tạo custom exception không?)

## Junior Level

### Có, bạn có thể!

Một custom exception là một class thông thường kế thừa từ `Exception` hoặc `RuntimeException`.

**Custom** = do bạn tạo cho domain của bạn. **Standard** = từ JDK (IOException, IllegalArgumentException). Custom mang ý nghĩa domain: `OrderNotFoundException` nói lên nhiều hơn `IllegalArgumentException`.

```java
// Checked exception
public class UserNotFoundException extends Exception {
    public UserNotFoundException(String message) {
        super(message);
    }
}

// Unchecked exception
public class InsufficientFundsException extends RuntimeException {
    public InsufficientFundsException(String message) {
        super(message);
    }
}
```

### Cách dùng

```java
public User findUser(Long id) {
    User user = repository.findById(id);
    if (user == null) {
        throw new UserNotFoundException("User not found: " + id);
    }
    return user;
}

// Xử lý
try {
    findUser(1L);
} catch (UserNotFoundException e) {
    System.out.println(e.getMessage());
}
```

### Khi nào tạo checked, khi nào unchecked

- **Checked** (`extends Exception`) - nếu lỗi được lường trước và có thể phục hồi
- **Unchecked** (`extends RuntimeException`) - cho các lỗi nghiệp vụ và lỗi lập trình

### Mẹo

- Kế thừa từ `RuntimeException` trong hầu hết các trường hợp
- Đặt tên có ý nghĩa: `UserNotFoundException`, `OrderAlreadyShippedException`
- Gọi `super(message)` để truyền message

---

### Khi nào KHÔNG nên tạo custom exception

1. **Standard là đủ** - `IllegalArgumentException("Email invalid")` đã dễ đọc
2. **Exception chỉ dùng một lần** - không đáng tạo một class cho một lần throw duy nhất
3. **"Cây phân cấp song song"** - đừng tạo một Exception cho mỗi use case mới

## Middle Level

### Exception như DTO

Trong các hệ thống phân tán, một custom exception đóng vai trò DTO để truyền lỗi:

```java
public class BusinessException extends RuntimeException {
    private final ErrorCode code;
    private final Map<String, Object> context = new HashMap<>();

    public BusinessException(ErrorCode code, String message) {
        super(message);
        this.code = code;
    }

    public BusinessException with(String key, Object value) {
        this.context.put(key, value);
        return this;
    }

    public ErrorCode getCode() { return code; }
    public Map<String, Object> getContext() { return context; }
}
```

Cách dùng:
```java
throw new BusinessException(INSUFFICIENT_FUNDS, "Low balance")
    .with("userId", 123)
    .with("balance", 0.50);
```
// Ưu điểm của .with(): bạn có thể thêm ngữ cảnh tại nơi throw,
// mà không cần tạo một constructor với 10 tham số.
// Kiểu lambda: throw new BusinessException(code, msg).with("key", value)

### Domain-Driven Exception

Trong kiến trúc chất lượng, exception được chia thành các tầng:

1. **Infrastructure:** `DatabaseException`, `NetworkException`
2. **Domain:** `InsufficientFundsException`, `ProductOutOfStockException`

Domain exception nên mang tính thông tin - không chỉ "lỗi", mà là "người dùng X không thể mua sản phẩm Y".

### Vấn đề của microservice

Nếu service A ném `OrderNotFoundException`, và service B không có class này trong classpath - `NoClassDefFoundError`.

**Giải pháp:** ở biên của microservice, các exception được chuyển dịch thành các cấu trúc tiêu chuẩn (RFC 7807 Problem Details). Custom exception chỉ sống bên trong service.

RFC 7807 - định dạng JSON tiêu chuẩn cho các thông báo lỗi trong HTTP API. Định nghĩa các trường: type, title, status, detail, instance. Spring hỗ trợ nó qua `ProblemDetail` (từ Java 17).

## Senior Level

### Immutable & Stackless Exception cho Highload

Trong các hệ thống Highload, tạo `Throwable` là đắt đỏ do `fillInStackTrace()`:

```java
public class ValidationException extends RuntimeException {
    public ValidationException(String message) {
        super(message, null, false, false); // writableStackTrace = false
    }
}
```

Hàng nghìn exception mỗi giây mà không có tải CPU.

### Serialization UID

Luôn khai báo `serialVersionUID`:

```java
public class BusinessException extends RuntimeException {
    private static final long serialVersionUID = 1L;
    // ...
}
```

Không có nó, khi bạn thay đổi class (thêm một trường) và deserialize một phiên bản cũ từ Redis cache - `InvalidClassException`.

### Exception Masking và PII

Message của custom exception không được phơi bày dữ liệu nhạy cảm:

```java
// XẤU - mật khẩu trong log
throw new AuthException("Failed login for user: " + username + " with password: " + password);

// TỐT
throw new AuthException("Authentication failed for user: " + username);
```

### Global Error Handler trong Spring Boot

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BusinessException.class)
    public ResponseEntity<ErrorResponse> handleBusiness(BusinessException e) {
        return ResponseEntity.status(400)
            .body(ErrorResponse.of(e.getCode(), e.getMessage(), e.getContext()));
    }

    @ExceptionHandler(UserNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(UserNotFoundException e) {
        return ResponseEntity.status(404)
            .body(ErrorResponse.of("USER_NOT_FOUND", e.getMessage()));
    }
}
```

### Chẩn đoán

- **Log Correlation** - message của exception nên chứa dữ liệu để lọc trong ELK
- **Error Code** - mỗi exception nên có một mã duy nhất (ví dụ: `ERR-001`) cho việc bản địa hóa
- **Micrometer** - đếm mỗi custom exception qua metric

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Custom exception = class thông thường kế thừa từ `Exception` hoặc `RuntimeException`
- Kế thừa từ `RuntimeException` trong hầu hết các trường hợp (ít boilerplate hơn)
- `extends Exception` - nếu lỗi được lường trước và bên gọi có thể phục hồi
- Trong microservice, custom exception chỉ sống bên trong service; ở biên - chuyển dịch thành định dạng tiêu chuẩn (RFC 7807)
- Với highload dùng `writableStackTrace = false` để tránh `fillInStackTrace()` đắt đỏ
- Luôn khai báo `serialVersionUID` cho tính tương thích Serializable

**Các câu hỏi phụ thường gặp:**
- **Khi nào KHÔNG nên tạo một custom exception?** - Nếu standard là đủ (`IllegalArgumentException`), hoặc exception chỉ dùng một lần
- **Cách truyền ngữ cảnh trong một exception?** - Thêm các trường (`orderId`, `errorCode`) hoặc dùng phương thức fluent `.with(key, value)`
- **Exception Masking là gì?** - Exception không được phơi bày dữ liệu nhạy cảm (mật khẩu, PII) trong message
- **Cách xử lý custom exception trong Spring?** - Qua `@RestControllerAdvice` + `@ExceptionHandler` -> ánh xạ tới các HTTP status

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi tạo một exception cho mỗi use case" - Điều này dẫn tới "cây phân cấp song song" và phình code
- "Tôi truyền mật khẩu/PII trong message của exception" - Vi phạm bảo mật (PCI DSS, GDPR)
- "Custom exception tự động ánh xạ tới HTTP" - Cần `@ControllerAdvice`, nếu không nó là 500
