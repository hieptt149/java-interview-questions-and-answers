# What is Propagation in Spring (Propagation trong Spring là gì)

## 🟢 Junior Level

**Propagation** trong Spring là một cấu hình xác định điều gì xảy ra với một transaction khi một method transactional gọi một method transactional khác.

**Ví dụ minh họa đơn giản:** Hãy tưởng tượng bạn đang làm việc tại văn phòng (transaction bên ngoài). Một đồng nghiệp đến nhờ bạn giúp đỡ (method bên trong). Propagation quyết định: bạn tiếp tục công việc và giúp đỡ trong nhiệm vụ hiện tại (REQUIRED), bỏ mọi thứ và bắt đầu một nhiệm vụ mới (REQUIRES_NEW), hay từ chối nếu bạn đã có việc (NEVER).

**Ví dụ đơn giản:**

```java
@Service
public class OrderService {

    @Transactional  // propagation = REQUIRED theo mặc định
    public void createOrder(Order order) {
        orderRepo.save(order);
        auditService.logOrder(order);  // gọi một method @Transactional khác
    }
}

@Service
public class AuditService {

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void logOrder(Order order) {
        auditRepo.save(new AuditEntry(order));  // luôn được lưu, ngay cả khi createOrder thất bại
    }
}
```

**7 loại Propagation trong Spring:**

| Loại                        | Nếu transaction đã tồn tại                 | Nếu không có transaction            |
| --------------------------- | ------------------------------------- | ----------------------------- |
| **REQUIRED** (mặc định)      | Dùng transaction hiện tại                          | Tạo mới                  |
| **REQUIRES_NEW**            | Tạm ngưng hiện tại, tạo mới         | Tạo mới                  |
| **NESTED**                  | Tạo lồng nhau (savepoint)            | Tạo mới                  |
| **MANDATORY**               | Dùng transaction hiện tại                          | Ném exception             |
| **SUPPORTS**                | Dùng transaction hiện tại                          | Thực thi không có transaction |
| **NOT_SUPPORTED**           | Tạm ngưng transaction hiện tại                      | Thực thi không có transaction |
| **NEVER**                   | Ném exception                      | Thực thi không có transaction |

**Khi nào nên dùng:**
- **REQUIRED** — trong 90% các trường hợp (logic transactional tiêu chuẩn)
- **REQUIRES_NEW** — cho audit, logging, các thao tác độc lập
- **NESTED** — cho rollback từng phần của các thao tác lồng nhau

## 🟡 Middle Level

### Cách Nó Hoạt Động Nội Bộ

Spring hiện thực propagation thông qua **AOP Proxy** và **TransactionInterceptor**.

**AOP (Aspect-Oriented Programming) Proxy** — Spring tạo một wrapper quanh bean, chặn các lời gọi method và thêm logic cross-cutting (transaction, logging).

```
Lời gọi: serviceA.methodA() → proxy → TransactionInterceptor

1. Interceptor kiểm tra @Transactional(propagation = ...) trên method
2. Tham vấn PlatformTransactionManager:

   REQUIRED:
     - Nếu transaction tồn tại → tham gia
     - Nếu không → tạo mới

   REQUIRES_NEW:
     - Luôn tạm ngưng transaction hiện tại (suspend)
     - Tạo một transaction vật lý mới
     - Sau khi hoàn thành — khôi phục transaction trước đó

   NESTED:
     - Nếu transaction tồn tại → tạo JDBC Savepoint
     - Nếu không → tạo transaction mới

3. Method mục tiêu thực thi
4. Khi thành công → commit (hoặc không làm gì, nếu đã tham gia)
5. Khi có exception → rollback (hoặc rollback về savepoint cho NESTED)
```

**Điểm then chốt:** Propagation chỉ hoạt động **khi được gọi thông qua Spring Proxy** (theo mặc định). Gọi `this.method()` trong cùng class bỏ qua proxy — TransactionInterceptor không kích hoạt. Ở chế độ AspectJ với weaving, các lời gọi qua `this` cũng được chặn.

### Ứng Dụng Thực Tế

**Kịch bản 1: Audit Với REQUIRES_NEW**
```java
@Service
public class PaymentService {

    private final AuditService auditService;

    @Transactional
    public void processPayment(Payment payment) {
        paymentRepo.save(payment);

        try {
            auditService.logPayment(payment);  // REQUIRES_NEW — được lưu độc lập
        } catch (Exception e) {
            // Audit thất bại, nhưng payment vẫn nên tiếp tục
            log.warn("Audit failed, payment still processed", e);
        }

        // Nếu thất bại ở đây — payment rollback, nhưng audit đã commit rồi
    }
}
```

**Kịch bản 2: Xử Lý Batch Với NESTED**
```java
@Service
public class BatchService {

    @Transactional
    public void processBatch(List<Order> orders) {
        for (Order order : orders) {
            try {
                processOrderNested(order);  // NESTED — rollback từng phần
            } catch (Exception e) {
                // Chỉ item này rollback về savepoint
                log.error("Order {} failed, continuing", order.getId());
            }
        }
        // Commit cuối cùng — tất cả các item thành công
    }

    @Transactional(propagation = Propagation.NESTED)
    public void processOrderNested(Order order) {
        orderRepo.save(order);
        // Nếu có exception → rollback về savepoint
    }
}
```

**Kịch bản 3: MANDATORY Cho Xử Lý Nội Bộ**
```java
@Service
public class InternalOrderProcessor {

    @Transactional(propagation = Propagation.MANDATORY)
    public void validateOrder(Order order) {
        // Đảm bảo chỉ được gọi từ context transactional
        // Nếu gọi trực tiếp — exception
        if (order.getAmount().compareTo(BigDecimal.ZERO) <= 0) {
            throw new InvalidOrderException();
        }
    }
}
```

### Các Lỗi Điển Hình

| Lỗi                                      | Hậu quả                                                    | Giải pháp                                                                      |
| -------------------------------------------- | -------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Gọi method `@Transactional` qua `this`   | Propagation bị bỏ qua, transaction không được tạo                   | Gọi qua một bean khác hoặc dùng `@Autowired private SelfType self`           |
| REQUIRED + exception bên trong                   | Toàn bộ transaction (kể cả method bên ngoài) bị đánh dấu rollback-only | Bọc lời gọi bên trong trong try-catch hoặc dùng REQUIRES_NEW                              |
| REQUIRES_NEW cho dữ liệu liên quan                | Commit độc lập có thể tạo ra dữ liệu không nhất quán                | Dùng REQUIRED cho các thao tác liên quan về mặt logic                                 |
| NESTED với Hibernate                        | L1 cache của Hibernate không đồng bộ với savepoint rollback    | Dùng REQUIRED + xử lý lỗi thủ công hoặc JPA 3.1+                              |
| PROPAGATION_NOT_SUPPORTED bên trong transaction | Tạm ngưng transaction, mất context                          | Đảm bảo thao tác thực sự không cần transaction                      |

### So Sánh: REQUIRED vs REQUIRES_NEW vs NESTED

| Đặc điểm          | REQUIRED       | REQUIRES_NEW            | NESTED               |
| ----------------------- | -------------- | ------------------------ | --------------------- |
| Transaction vật lý   | 1              | 2+                      | 1 (với savepoint)  |
| Tạm ngưng tx bên ngoài     | Không             | Có                     | Không                   |
| Commit độc lập      | Không             | Có                     | Không                   |
| Rollback từng phần         | Không             | Có                     | Có (về savepoint)   |
| Rollback tx bên ngoài       | Rollback tất cả | Không ảnh hưởng bên trong    | Rollback tất cả       |
| Hỗ trợ DB              | Tất cả            | Tất cả                     | JDBC 3.0+ savepoint |
| Tương thích Hibernate | Đầy đủ           | Đầy đủ                    | Hạn chế               |

**Khác biệt thực tế chính:** nếu tx bên ngoài rollback, REQUIRES_NEW giữ nguyên dữ liệu (đã commit rồi), trong khi NESTED làm mất nó (savepoint bị rollback). Điều này quyết định lựa chọn: audit = REQUIRES_NEW, batch từng phần = NESTED.

### Khi Nào KHÔNG Nên Thay Đổi Propagation

- **CRUD tiêu chuẩn:** REQUIRED mặc định là lựa chọn đúng
- **Các service đơn giản không có lời gọi lồng nhau:** propagation không quan trọng
- **Kiến trúc event-driven:** mỗi handler là một transaction riêng, không cần propagation

## 🔴 Senior Level

### Hiện Thực Nội Bộ: Chi Tiết Bên Trong Transaction Của Spring

#### TransactionInterceptor Và Quyết Định Propagation

```java
// Logic đơn giản hóa từ Spring Framework 6.x
// org.springframework.transaction.interceptor.TransactionAspectSupport

protected Object invokeWithinTransaction(Method method, Class<?> targetClass,
                                          InvocationCallback invocation) {

    TransactionAttribute txAttr = getTransactionAttributeSource()
        .getTransactionAttribute(method, targetClass);

    PlatformTransactionManager tm = determineTransactionManager(txAttr);

    // Điểm then chốt: lấy hoặc tạo transaction
    TransactionInfo txInfo = createTransactionIfNecessary(tm, txAttr, joinpointIdentification);

    Object retVal = null;
    try {
        retVal = invocation.proceedWithInvocation();  // gọi method mục tiêu
    } catch (Throwable ex) {
        completeTransactionAfterThrowing(txInfo, ex);  // rollback hoặc rollback-to-savepoint
        throw ex;
    } finally {
        cleanupTransactionInfo(txInfo);
    }

    commitTransactionAfterReturning(txInfo);  // commit
    return retVal;
}
```

#### AbstractPlatformTransactionManager: handleExistingTransaction

```java
// Method then chốt cho logic propagation
// org.springframework.transaction.support.AbstractPlatformTransactionManager

private TransactionStatus handleExistingTransaction(
        TransactionDefinition definition, Object transaction, boolean debugEnabled) {

    switch (definition.getPropagationBehavior()) {

        case PROPAGATION_NEVER:
            throw new IllegalTransactionStateException(
                "Existing transaction found but propagation is NEVER");

        case PROPAGATION_NOT_SUPPORTED:
            Object suspendedResources = suspend(transaction);
            boolean newSynchronization = (getTransactionSynchronization() == SYNCHRONIZATION_ALWAYS);
            return prepareTransactionStatus(definition, null, true, newSynchronization, debugEnabled, suspendedResources);

        case PROPAGATION_REQUIRES_NEW:
            SuspendedResourcesHolder suspendedResources = suspend(transaction);
            // ... tạo một transaction vật lý mới
            return newTransactionStatus(definition, newTransaction, false, ...);

        case PROPAGATION_NESTED:
            if (useSavepointForNestedTransaction()) {
                // Tạo JDBC Savepoint
                DefaultTransactionStatus status =
                    prepareTransactionStatus(definition, transaction, false, false, debugEnabled, null);
                status.createAndHoldSavepoint();
                return status;
            } else {
                // Fallback: hành xử như REQUIRES_NEW (cho JTA)
                return handleExistingTransaction(... REQUIRES_NEW logic ...);
            }

        case PROPAGATION_SUPPORTS:
        case PROPAGATION_REQUIRED:
        default:
            // Tham gia transaction hiện có
            return prepareTransactionStatus(definition, transaction, false, ...);
    }
}
```

#### Hiện Thực Savepoint (JDBC)

```java
// org.springframework.jdbc.datasource.JdbcTransactionObjectSupport

public void createSavepoint(String name) {
    try {
        // JDBC 3.0+ Savepoint
        this.savepoint = getConnectionHolder().getConnection().setSavepoint(name);
    } catch (SQLException ex) {
        throw new CannotCreateSavepointException("Could not create JDBC savepoint", ex);
    }
}

public void rollbackToSavepoint() {
    try {
        getConnectionHolder().getConnection().rollback(this.savepoint);
    } catch (SQLException ex) {
        throw new TransactionSystemException("Could not roll back to JDBC savepoint", ex);
    }
}

// Giải phóng savepoint (không phải commit!)
public void releaseSavepoint() {
    try {
        getConnectionHolder().getConnection().releaseSavepoint(this.savepoint);
    } catch (SQLException ex) {
        // Không nghiêm trọng — một số DB tự động giải phóng khi commit
    }
}
```

#### Cơ Chế Suspend/Resume (REQUIRES_NEW)

```java
// Tạm ngưng transaction hiện tại:
protected final SuspendedResourcesHolder suspend(TransactionDefinition definition) {
    // 1. Gỡ connection khỏi ThreadLocal
    ConnectionHolder conHolder = (ConnectionHolder) TransactionSynchronizationManager.unbindResource(obtainDataSource());

    // 2. Tạm ngưng các transaction synchronization (Hibernate session, v.v.)
    List<TransactionSynchronization> suspendedSynchronizations =
        doSuspendSynchronization();

    // 3. Reset trạng thái TransactionSynchronizationManager
    TransactionSynchronizationManager.setActualTransactionActive(false);
    TransactionSynchronizationManager.setCurrentTransactionIsolationLevel(
        definition.getIsolationLevel());

    return new SuspendedResourcesHolder(conHolder, suspendedSynchronizations);
}

// Khôi phục sau khi transaction bên trong hoàn thành:
protected final void resume(Object transaction, SuspendedResourcesHolder resourcesHolder) {
    // 1. Gắn lại connection vào ThreadLocal
    TransactionSynchronizationManager.bindResource(obtainDataSource(), resourcesHolder.getConnectionHolder());

    // 2. Khôi phục các synchronization
    doResumeSynchronization(resourcesHolder.getSuspendedSynchronizations());

    // 3. Khôi phục trạng thái
    TransactionSynchronizationManager.setActualTransactionActive(true);
}
```

### Đánh Đổi Về Kiến Trúc (Trade-off)

**Cách A: REQUIRED (mặc định)**
- ✅ Ưu điểm: Tính đồng nhất (commit/rollback nguyên tử), đơn giản, overhead tối thiểu, tương thích ORM đầy đủ
- ❌ Nhược điểm: Exception bên trong → rollback toàn bộ chuỗi, không thể "cứu" một phần công việc
- Phù hợp cho: 90% logic nghiệp vụ nơi tất cả các thao tác đều nguyên tử

**Cách B: REQUIRES_NEW**
- ✅ Ưu điểm: Isolation (commit bên trong độc lập), audit trail được giữ nguyên, có thể xử lý thất bại một phần
- ❌ Nhược điểm: Hai transaction vật lý (overhead suspend/resume), nguy cơ không nhất quán, sử dụng connection pool x2
- Phù hợp cho: audit, logging, gửi thông báo, các side-effect độc lập

**Cách C: NESTED (savepoint)**
- ✅ Ưu điểm: Rollback từng phần mà không cần transaction thứ hai, một lần commit duy nhất, overhead thấp hơn REQUIRES_NEW
- ❌ Nhược điểm: Không hoạt động với JTA, hỗ trợ Hibernate hạn chế (L1 cache không nhất quán), chỉ JDBC 3.0+
- Phù hợp cho: xử lý batch, các thao tác hàng loạt chấp nhận thất bại từng phần

### Các Trường Hợp Biên Và Đặc Biệt

**1. Self-invocation (Bỏ Qua Proxy):**
```java
@Service
public class OrderService {

    @Transactional
    public void createOrder(Order order) {
        // XẤU: this.logOrder() bỏ qua proxy
        this.logOrder(order);  // REQUIRES_NEW bị bỏ qua!
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void logOrder(Order order) {
        auditRepo.save(new AuditEntry(order));
    }
}
```

**Các giải pháp:**
```java
// Giải pháp A: Self-injection
@Service
public class OrderService {
    @Autowired private OrderService self;  // proxy

    @Transactional
    public void createOrder(Order order) {
        self.logOrder(order);  // qua proxy — REQUIRES_NEW hoạt động
    }
}

// Giải pháp B: AopContext
@EnableAspectJAutoProxy(exposeProxy = true)
// ...
((OrderService) AopContext.currentProxy()).logOrder(order);

// Giải pháp C: Bean riêng biệt (best practice)
@Service
public class OrderAuditService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void logOrder(Order order) { ... }
}
```

**2. Đánh Dấu Rollback-Only Lan Truyền:**
```java
@Transactional
public void outerMethod() {
    try {
        innerService.innerMethod();  // REQUIRED, ném RuntimeException
    } catch (Exception e) {
        // Đã bắt exception, NHƯNG transaction đã bị đánh dấu rollback-only!
    }
    // Khi commit: UnexpectedRollingBackException — transaction đã được đánh dấu để rollback
}
```

**Cơ chế nội bộ:**
```java
// AbstractPlatformTransactionManager
public final void rollback(TransactionStatus status) {
    if (status.isRollbackOnly()) {
        // Ngay cả khi method bên ngoài không ném exception,
        // method bên trong (REQUIRED) đã gọi setRollbackOnly() rồi
        doRollback(status);
        throw new UnexpectedRollingBackException(
            "Transaction rolled back because it has been marked as rollback-only");
    }
}

Khi innerMethod ném RuntimeException, TransactionInterceptor thấy
exception TRƯỚC KHI outerMethod bắt nó (vì proxy bọc
lời gọi). Interceptor gọi setRollbackOnly() trên TransactionStatus, và đến
lúc outerMethod bắt exception — transaction đã bị đánh dấu để rollback rồi.
```

**3. NESTED + Sự Không Nhất Quán Của Hibernate L1 Cache:**
```java
@Transactional
public void batchUpdate(List<Entity> entities) {
    for (Entity e : entities) {
        try {
            nestedService.saveNested(e);  // NESTED
        } catch (Exception ex) {
            // Savepoint đã rollback, NHƯNG:
            // L1 cache của Hibernate (PersistenceContext) KHÔNG bị rollback!
            // Entity vẫn còn trong session.entities, có thể gây vấn đề dirty checking
        }
    }
    // Khi commit: Hibernate flush — có thể cố flush các entity đã bị rollback
}
```

**Giải pháp tạm thời:**
```java
@PersistenceContext
private EntityManager em;

@Transactional(propagation = Propagation.NESTED)
public void saveNested(Entity e) {
    em.persist(e);
    em.flush();  // Buộc flush trước savepoint
    em.clear();  // Xóa L1 cache để tránh trạng thái cũ (stale)
}
```

**4. Propagation Và Transaction Synchronization:**
```java
// Spring đăng ký các callback synchronization:
TransactionSynchronizationManager.registerSynchronization(
    new TransactionSynchronization() {
        @Override
        public void afterCommit() {
            // Chỉ được gọi sau commit cuối cùng
            // Với REQUIRES_NEW: được gọi sau khi tx bên trong commit
            // Với NESTED: chỉ được gọi sau khi tx bên ngoài commit
        }

        @Override
        public void afterCompletion(int status) {
            // Luôn được gọi (STATUS_COMMITTED, STATUS_ROLLED_BACK, STATUS_UNKNOWN)
        }
    }
);
```

**5. REQUIRES_NEW Và Cạn Kiệt Connection Pool:**
```
Thread-1: outerMethod() — lấy connection-1 (suspend)
  Thread-1: innerMethod() — lấy connection-2 (REQUIRES_NEW)

  Dưới tải cao:
  - Mỗi REQUIRES_NEW = +1 connection
  - 100 request đồng thời × 2 connection = cần 200 connection
  - Kích thước pool = 50 → cạn kiệt pool → wait timeout
```

**6. Propagation Và Reactive (R2DBC):**
```java
// Spring Framework 6.x: các transaction reactive hoạt động khác
// Không có ThreadLocal, suspend/resume qua Project Reactor context

@Transactional
public Mono<Void> processOrder(Order order) {
    return orderRepo.save(order)
        .then(auditService.logOrder(order))  // REQUIRES_NEW qua Reactor context switch
        .then();
}

// Propagation cho reactive: hoạt động qua Context Propagation (Reactor)
// Không phải tất cả các loại propagation đều được hỗ trợ đầy đủ trong reactive
```

### Tác Động Đến Hiệu Năng

| Propagation   | Overhead                           | Sử dụng Connection            | Tác động Throughput            |
| ------------- | ---------------------------------- | --------------------------- | ---------------------------- |
| REQUIRED      | Tối thiểu (~1ms)                     | 1 connection                | Cơ sở                     |
| REQUIRES_NEW  | Trung bình (+5-15ms khi suspend/resume) | 2 connection (lồng nhau)      | -10-20% dưới tải cao      |
| NESTED        | Thấp (+1-3ms khi savepoint)          | 1 connection                | -2-5%                        |
| MANDATORY     | Không                               | 0 (dùng hiện có)           | 0%                           |
| NOT_SUPPORTED | Trung bình (suspend/resume)            | 0 (trong lúc thực thi)        | +5% (giải phóng connection)       |

**Các con số cụ thể (Spring Boot 3.x, PostgreSQL, HikariCP pool=50):**
- Chỉ REQUIRED: ~25,000 TPS
- REQUIRED + 1 REQUIRES_NEW: ~20,000 TPS. Overhead: suspend ~2ms, connection mới ~0.5ms, Hibernate Session suspend ~2ms, resume ~2ms — tổng 5-15ms mỗi lần gọi.
- REQUIRED + 1 NESTED: ~24,000 TPS (overhead savepoint tối thiểu)
- 5 REQUIRES_NEW lồng nhau: ~10,000 TPS (suspend/resume theo tầng)

### Tác Động Đến Bộ Nhớ

- **Tài nguyên tạm ngưng (REQUIRES_NEW):** ConnectionHolder + TransactionSynchronization ~2-5KB mỗi lần suspend.
- **Savepoint (NESTED):** Object savepoint JDBC ~500 byte, cộng với trạng thái savepoint phía DB.
- **Trạng thái ThreadLocal:** TransactionSynchronizationManager lưu ~1-2KB mỗi thread.
- **Hibernate L1 cache (với NESTED):** Có thể chứa các entity cũ (stale) sau khi savepoint rollback — lên đến vài MB cho các thao tác batch lớn.

### Các Khía Cạnh Concurrency

**Concurrency của REQUIRES_NEW:**
```
Thread-1: outerMethod(REQUIRED) → suspend → innerMethod(REQUIRES_NEW) → commit → resume
Thread-2: outerMethod(REQUIRED) → suspend → innerMethod(REQUIRES_NEW) → commit → resume

Các transaction bên trong thực thi song song (connection độc lập)
Các transaction bên ngoài chờ (suspend) cho đến khi bên trong hoàn thành
```

**Concurrency của NESTED:**
```
Thread-1: outerMethod(REQUIRED) → innerMethod(NESTED) → savepoint → rollback/tiếp tục
Thread-2: outerMethod(REQUIRED) → innerMethod(NESTED) → savepoint → rollback/tiếp tục

Cả hai transaction dùng connection riêng của mình, các savepoint độc lập
```

### Tình Huống Thực Tế Trong Production

**Tình huống:** Nền tảng fintech (2024), Spring Boot 3.2, PostgreSQL, xử lý 10,000 khoản thanh toán/giờ.

**Vấn đề:** Khi payment gateway thất bại (~tỷ lệ thất bại 2%), các bản ghi audit không được lưu. Bộ phận tuân thủ (compliance) không thể theo dõi các lần thử thanh toán, vi phạm yêu cầu quy định.

**Code gốc:**
```java
@Service
public class PaymentService {

    @Autowired private AuditService auditService;  // AuditService.logPayment = REQUIRED

    @Transactional
    public PaymentResult processPayment(Payment payment) {
        paymentRepo.save(payment);

        // Lời gọi payment gateway — có thể thất bại
        PaymentGatewayResult gatewayResult = gateway.charge(payment);

        // Audit được gọi SAU gateway — nếu gateway thất bại, audit không được gọi
        auditService.logPayment(payment);  // REQUIRED

        return new PaymentResult(gatewayResult);
    }
}
```

**Phân tích nguyên nhân gốc rễ:**
1. `auditService.logPayment()` dùng REQUIRED — là một phần của transaction tổng thể
2. Khi có exception từ `gateway.charge()` → toàn bộ transaction rollback, bao gồm cả audit
3. Compliance yêu cầu audit TẤT CẢ các lần thử, kể cả những lần thất bại

**Giải pháp:**
```java
@Service
public class PaymentService {

    @Autowired private AuditService auditService;

    @Transactional
    public PaymentResult processPayment(Payment payment) {
        // Audit TRƯỚC payment — REQUIRES_NEW, được lưu độc lập
        auditService.logPaymentAttempt(payment);

        paymentRepo.save(payment);

        try {
            PaymentGatewayResult gatewayResult = gateway.charge(payment);
            auditService.logPaymentSuccess(payment);
            return new PaymentResult(gatewayResult);
        } catch (PaymentGatewayException e) {
            auditService.logPaymentFailure(payment, e);
            throw e;  // Payment rollback, nhưng audit của lần thử đã commit rồi
        }
    }
}

@Service
public class AuditService {

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void logPaymentAttempt(Payment payment) {
        auditRepo.save(new AuditEntry(payment, "ATTEMPT"));
        // Commit — độc lập với transaction bên ngoài
    }
}
```

**Kết quả:**
- Độ phủ audit: từ 0% (khi thất bại) lên 100%
- Compliance: đã pass audit
- Throughput: -5% (overhead của REQUIRES_NEW) — chấp nhận được
- Connection pool: tăng từ 50 lên 75

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Propagation kiểm soát điều gì xảy ra khi một method @Transactional gọi một method @Transactional khác
- 7 loại: REQUIRED (mặc định), REQUIRES_NEW, NESTED, MANDATORY, SUPPORTS, NOT_SUPPORTED, NEVER
- Propagation chỉ hoạt động qua Spring Proxy — self-invocation (this.method) bỏ qua nó
- REQUIRED: 90% các trường hợp, REQUIRES_NEW: audit/logging, NESTED: batch với khả năng thất bại từng phần
- REQUIRES_NEW tạm ngưng tx bên ngoài, tạo một transaction vật lý mới — 2 connection
- NESTED dùng JDBC savepoint trong cùng một transaction — 1 connection, có thể rollback từng phần

**Các câu hỏi phụ thường gặp:**
- Tại sao self-invocation không hoạt động? — Proxy bị bỏ qua, TransactionInterceptor không được gọi
- REQUIRED vs REQUIRES_NEW vs NESTED? — REQUIRED: tham gia, REQUIRES_NEW: suspend+tx mới, NESTED: savepoint
- Điều gì xảy ra nếu REQUIRED bên trong ném exception và bên ngoài bắt nó? — Transaction đã bị đánh dấu rollback-only → UnexpectedRollingBackException
- NESTED hoạt động như thế nào với Hibernate? — L1 cache không đồng bộ với savepoint rollback, cần flush+clear

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Propagation hoạt động với các method private" — proxy không chặn các method private
- "NESTED tạo một transaction mới" — nó tạo một savepoint trong cùng transaction
- "REQUIRES_NEW và NESTED giống nhau" — REQUIRES_NEW = commit độc lập, NESTED = savepoint
