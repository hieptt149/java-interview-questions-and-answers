# When to use synchronized collections? (Khi nào dùng synchronized collections?)

## 🟢 Junior Level

**Synchronized collections** là các collection thông thường với một khóa trên mỗi phương thức.

Hãy tưởng tượng một nhà vệ sinh với một chiếc chìa khóa duy nhất — trong khi một luồng đang ở bên trong, tất cả các luồng khác chờ xếp hàng, ngay cả khi chúng chỉ muốn kiểm tra xem nó có trống không.

```java
List<String> syncList = Collections.synchronizedList(new ArrayList<>());
Map<String, Integer> syncMap = Collections.synchronizedMap(new HashMap<>());
```

**Vấn đề:** Chỉ MỘT luồng có thể làm việc tại một thời điểm (ngay cả khi đọc!).

**Giải pháp thay thế hiện đại:**
```java
// ❌ Cách tiếp cận cũ (chậm)
List<String> list = Collections.synchronizedList(new ArrayList<>());

// ✅ Cách tiếp cận mới (nhanh)
Map<String, Integer> map = new ConcurrentHashMap<>();
List<String> list = new CopyOnWriteArrayList<>();
```

synchronizedList — một khóa cho TẤT CẢ các thao tác, kể cả các lần đọc. ConcurrentHashMap — đọc lock-free và các khóa chi tiết (granular) khi ghi, nên N luồng có thể đọc song song.

## 🟡 Middle Level

### Vấn đề: một khóa cho mọi thứ

```java
// 100 luồng muốn đọc
syncList.get(0);  // Tất cả chờ xếp hàng!
// → 0 song song
```

### Các thao tác kép KHÔNG nguyên tử

```java
// ❌ Race condition!
if (!syncList.contains(item)) {  // Luồng A đã kiểm tra
    // Luồng B xen vào và thêm
    syncList.add(item);  // Luồng A thêm một bản trùng lặp!
}

// ✅ synchronized bên ngoài
synchronized (syncList) {
    if (!syncList.contains(item)) {
        syncList.add(item);
    }
}
```

### Iterate yêu cầu khóa thủ công

```java
// ❌ ConcurrentModificationException!
for (String s : syncList) { ... }

// ✅ Đúng:
synchronized (syncList) {
    for (String s : syncList) { ... }
}
```

### Khi nào dùng

| Kịch bản           | Chọn cái gì                |
| ------------------ | -------------------------- |
| Code mới           | **ConcurrentHashMap**      |
| Các danh sách listener | **CopyOnWriteArrayList**   |
| Cần khóa toàn bộ   | **synchronizedList**       |
| Code legacy        | **synchronizedList**       |

COWAL tốt cho các listener: iterate (duyệt qua tất cả các listener) thường xuyên hơn việc thêm một listener. COWAL cung cấp iterate không có CME và thêm vào O(1).

## 🔴 Senior Level

### Khi nào KHÔNG dùng synchronized collections

1. **Contention cao (>10 luồng)** — ConcurrentHashMap sẽ cho throughput tốt hơn một bậc độ lớn
2. **Iterate thường xuyên** — mỗi lần đều yêu cầu `synchronized(list) { ... }` thủ công
3. **Các thao tác kép (check-then-act)** — vẫn cần synchronized bên ngoài, vậy tại sao lại dùng lớp bọc (wrapper)?

### Khóa thô (Coarse-grained locking)

```
Một monitor cho TOÀN BỘ collection:
  → 100 người đọc → tuần tự hóa (serialization)
  → Trên các CPU đa nhân → 0 khả năng mở rộng (scalability)

ConcurrentHashMap:
  → Đọc lock-free
  → CAS + synchronized cho mỗi bucket
  → 100 luồng làm việc song song
```

### Đồng bộ hóa kép (Double synchronization)

```java
// ❌ Khóa kép!
synchronized (syncList) {
    syncList.add(e);  // synchronized nội bộ + bên ngoài
}

// synchronizedList đã synchronized mọi phương thức rồi
// → Overhead thừa
```

### Để lộ collection gốc

```java
// ❌ Vi phạm thread-safety!
List<String> original = new ArrayList<>();
List<String> sync = Collections.synchronizedList(original);

// Sửa đổi bỏ qua lớp bọc:
original.add("x");  // KHÔNG được synchronized!
```

### Khi nào synchronized collections là hợp lý

```java
// 1. Các hệ thống legacy (code trước Java 5)

// 2. Tính nguyên tử thô của toàn bộ collection
synchronized (syncList) {
    // Đảm bảo không ai có thể xen vào
    for (var item : syncList) {
        process(item);
    }
}

// 3. Contention thấp + kích thước nhỏ
// → Lớp bọc rẻ hơn ConcurrentHashMap
```

### Kinh nghiệm Production

**Tình huống thực tế: synchronizedMap giết chết throughput**
- API: 1000 RPS, synchronizedMap cho cache
- Lock contention: 90% thời gian dành cho synchronized
- Giải pháp: ConcurrentHashMap
- Kết quả: +900% throughput

### Best Practices

1. **KHÔNG dùng** trong code mới
2. **ConcurrentHashMap** — theo mặc định
3. **CopyOnWriteArrayList** — cho các listener
4. **Iterate** → khối synchronized là bắt buộc
5. **Các thao tác kép** → synchronized bên ngoài
6. **Đừng để lộ** collection gốc
7. **Vector/Hashtable** → tránh trong code mới. Trường hợp duy nhất mà chúng có thể chấp nhận được là code legacy đơn luồng nơi việc thay thế không được biện minh bởi các rủi ro.

### Tóm tắt cho Senior

- **Một khóa duy nhất** → 0 khả năng mở rộng
- **Các thao tác kép** → race condition nếu không có synchronized bên ngoài
- **Iterate** → khối synchronized thủ công
- **ConcurrentHashMap** > synchronizedMap trong 99% các trường hợp
- **Legacy** → sự biện minh duy nhất
- **Vector/Hashtable** — synchronized tích hợp sẵn → legacy

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Synchronized collections — một khóa cho tất cả các phương thức (đọc + ghi)
- Các thao tác kép (check-then-act) KHÔNG nguyên tử — cần `synchronized` bên ngoài
- Iterate yêu cầu một khối `synchronized(list) { ... }` thủ công
- ConcurrentHashMap cho đọc lock-free và các khóa chi tiết khi ghi
- CopyOnWriteArrayList lý tưởng cho các danh sách listener (đọc thường xuyên, ghi hiếm)
- Synchronized collections không được khuyến nghị trong code mới
- Để lộ collection gốc phá vỡ thread-safety
- Vector/Hashtable — legacy, tránh trong code mới

**Các câu hỏi phụ thường gặp:**
- *Tại sao synchronizedMap giết chết throughput ở 1000 RPS?* — 90% thời gian dành cho lock contention; ConcurrentHashMap giải quyết vấn đề.
- *Cấu trúc `if (!list.contains(x)) list.add(x)` có nguyên tử không?* — Không, đó là hai lời gọi riêng biệt; cần một `synchronized(list)` bên ngoài.
- *Tại sao iterate qua một synchronizedList mà không có khối synchronized sẽ ném CME?* — Iterate là một thao tác kép (hasNext + next), không được bảo vệ bởi một lời gọi phương thức duy nhất.
- *Khi nào synchronized collections là hợp lý?* — Code legacy trước Java 5, contention thấp, tính nguyên tử thô của toàn bộ collection.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "synchronizedList là một lựa chọn tốt cho code mới" — không, ConcurrentHashMap/CopyOnWriteArrayList tốt hơn
- "Các thao tác kép là nguyên tử trong synchronizedList" — không, cần các khối synchronized bên ngoài
- "Vector là một lựa chọn bình thường" — nó là một class legacy với khóa thô
- "synchronizedList giải quyết tất cả các vấn đề concurrency" — nó không giải quyết race condition cho các thao tác kép
