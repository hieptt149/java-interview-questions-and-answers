# What do @PostConstruct and @PreDestroy Methods Do? (Các phương thức @PostConstruct và @PreDestroy làm gì?)

## Junior Level

**@PostConstruct** — chạy một lần sau khi bean được tạo.
**@PreDestroy** — chạy một lần trước khi bean bị gỡ bỏ.

> Spring 6 / Boot 3: package đổi từ `javax.annotation` sang `jakarta.annotation`.

```java
@Service
public class MyService {

    @PostConstruct
    public void init() {
        // Được gọi sau khi tạo và tiêm phụ thuộc
        System.out.println("Bean created!");
    }

    @PreDestroy
    public void cleanup() {
        // Được gọi trước khi bean bị gỡ bỏ
        System.out.println("Bean is being removed!");
    }
}
```

**Khi nào dùng:**
- `@PostConstruct` -> khởi tạo, validation
- `@PreDestroy` -> đóng các kết nối, dọn dẹp

## Middle Level

### Thứ tự thực thi

```
1. Constructor
2. @Autowired (inject)
3. @PostConstruct  <- Các phụ thuộc đã tồn tại!
4. Bean đã sẵn sàng

Khi gỡ bỏ:
1. @PreDestroy
2. Bean bị gỡ bỏ
```

### Tại sao không dùng Constructor?

```java
// Trong constructor, các phụ thuộc Field/Setter vẫn còn NULL!
public MyService() {
    repo.loadData();  // NPE! repo chưa được inject
}

// @PostConstruct - các phụ thuộc đã tồn tại
@PostConstruct
public void init() {
    repo.loadData();  // OK!
}
```

### Singleton so với Prototype

```java
// Singleton:
// -> @PostConstruct được gọi một lần
// -> @PreDestroy được gọi khi shutdown

// Prototype:
// -> @PostConstruct được gọi mỗi lần khi tạo
// -> @PreDestroy KHÔNG được gọi tự động cho prototype bean. Spring không theo dõi việc hủy chúng.
```

### Thứ tự khởi tạo

```
1. @PostConstruct
2. InitializingBean.afterPropertiesSet()
3. @Bean(initMethod = "init")

-> Chỉ dùng @PostConstruct (chuẩn)
```

## Senior Level

### Khi nào KHÔNG dùng @PostConstruct / @PreDestroy

1. **Khởi tạo nặng** — chặn quá trình khởi động context -> SmartLifecycle
2. **Gọi các phương thức @Transactional** — proxy chưa tồn tại -> ContextRefreshedEvent
3. **Các thao tác có retry** — @PostConstruct không retry -> SmartLifecycle
4. **Prototype bean** — @PreDestroy không được gọi -> thủ công hoặc DestructionCallback

### Bẫy Proxy

```
@PostConstruct được gọi TRƯỚC khi tạo proxy!

@Service
public class Service {
    @PostConstruct
    public void init() {
        loadData();  // @Transactional -> KHÔNG hoạt động!
    }

    @Transactional
    public void loadData() { }
}

-> Lời gọi đi tới đối tượng gốc, không phải proxy
-> Transaction KHÔNG được tạo

Giải pháp:
  @EventListener(ContextRefreshedEvent.class)
  public void init() {
      loadData();  // Proxy đã tồn tại -> transaction hoạt động
      // ContextRefreshedEvent được phát ra SAU khi tất cả bean được tạo
      // Và tất cả proxy cũng vậy. Nên gọi các phương thức @Transactional từ
      // handler này hoạt động đúng.
  }
```

### Kế thừa

```java
class Parent {
    @PostConstruct
    public void parentInit() { }
}

class Child extends Parent {
    // Nếu không override -> parentInit() được gọi
    // Nếu override -> childInit() được gọi
}
```

### CommonAnnotationBeanPostProcessor

```
Chịu trách nhiệm xử lý @PostConstruct và @PreDestroy
-> Được đăng ký tự động
-> Là một phần của bộ BPP chuẩn
```

### Kinh nghiệm Production

**Tình huống thực tế: @PreDestroy không được gọi**
```java
// Prototype bean với @PreDestroy
@Scope("prototype")
public class Connection {
    @PreDestroy
    public void close() { }  // Sẽ không bao giờ được gọi!
}

// Rò rỉ connection!
// Giải pháp: gọi close() thủ công
```

### Best Practices

1. **@PostConstruct** -> validation, khởi tạo nhẹ
2. **@PreDestroy** -> dọn dẹp tài nguyên
3. **KHÔNG gọi** các phương thức @Transactional từ @PostConstruct
4. **Prototype** -> @PreDestroy không hoạt động
5. **Exception trong @PostConstruct** -> context sẽ không khởi động.

**Điều này hữu ích** — ứng dụng fail nhanh khi cấu hình sai. **Nhưng:** nếu khởi tạo có thể thất bại theo dự kiến (chưa có kết nối DB), hãy dùng SmartLifecycle với retry thay vì @PostConstruct.
6. **ContextRefreshedEvent** -> khi cần proxy

### Tóm tắt cho Senior

- **@PostConstruct** -> sau DI, TRƯỚC proxy
- **@PreDestroy** -> chỉ cho Singleton
- **Bẫy Proxy** -> @Transactional không hoạt động trong @PostConstruct
- **ContextRefreshedEvent** -> khi proxy đã sẵn sàng
- **Prototype** -> @PreDestroy không bao giờ được gọi
- **Fail-fast** -> exception trong @PostConstruct = crash lúc khởi động

## Interview Cheat Sheet

**Cần phải biết:**
- `@PostConstruct` — chạy một lần SAU khi tạo bean và tiêm phụ thuộc, TRƯỚC khi tạo proxy
- `@PreDestroy` — chạy một lần TRƯỚC khi gỡ bỏ bean, chỉ cho Singleton
- Trong constructor, các phụ thuộc Field/Setter vẫn còn NULL, trong `@PostConstruct` — đã được inject
- `@Transactional` KHÔNG hoạt động trong `@PostConstruct` — proxy chưa tồn tại, lời gọi đi tới đối tượng gốc
- Prototype: `@PostConstruct` được gọi mỗi lần khi tạo, `@PreDestroy` KHÔNG được gọi tự động
- Exception trong `@PostConstruct` = ứng dụng sẽ không khởi động (fail-fast — hữu ích khi cấu hình sai)
- Spring 6 / Boot 3: `jakarta.annotation.PostConstruct` thay vì `javax.annotation`
- Thứ tự: `@PostConstruct` -> `InitializingBean.afterPropertiesSet()` -> `init-method` (chỉ dùng `@PostConstruct`)

**Các câu hỏi phụ thường gặp:**
- **Tại sao không dùng constructor để khởi tạo?** Trong constructor, các phụ thuộc Field/Setter vẫn còn NULL. Với Constructor Injection — các phụ thuộc tồn tại, nhưng proxy thì chưa.
- **Làm sao gọi phương thức `@Transactional` trong lúc khởi tạo?** `@EventListener(ContextRefreshedEvent.class)` — tất cả proxy đã được tạo.
- **Nếu khởi tạo nặng trong `@PostConstruct` thì sao?** Chặn quá trình khởi động context — dùng `SmartLifecycle` với retry.
- **Điều gì xảy ra với `@PreDestroy` trong Prototype?** Không bao giờ được gọi — rò rỉ tài nguyên, dọn dẹp thủ công.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Trong constructor, tất cả các phụ thuộc đã tồn tại" (với Field/Setter injection — NULL)
- "`@PreDestroy` hoạt động cho mọi scope" (KHÔNG hoạt động cho Prototype)
- "Có thể gọi các phương thức `@Transactional` từ `@PostConstruct`" (proxy chưa tồn tại, transaction KHÔNG được tạo)
- "Exception trong `@PostConstruct` là xấu" (thực ra fail-fast là hữu ích, nhưng với các lỗi dự kiến hãy dùng `SmartLifecycle`)
