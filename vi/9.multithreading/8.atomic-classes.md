# What are Atomic classes? (Các lớp Atomic là gì?)

---

## Junior Level

### Hiểu biết cơ bản

**Các lớp Atomic** là một tập các lớp từ java.util.concurrent.atomic cung cấp các thao tác thread-safe **không cần khóa** (lock-free).

**Lock-free** = không mutex, không chặn thread. Dùng một chu kỳ CAS: đọc giá trị, tính giá trị mới, thử ghi qua CAS. Nếu một thread khác đã thay đổi giá trị — CAS trả về false, lặp lại chu kỳ.

### Tại sao chúng cần thiết?

Một thao tác `count++` thông thường là **không thread-safe**:

```java
// KHÔNG an toàn!
public class UnsafeCounter {
    private int count = 0;

    public void increment() {
        count++; // 3 thao tác: đọc → sửa → ghi
        // Hai thread có thể đọc cùng một giá trị!
    }
}
```

### Giải pháp với Atomic

```java
// An toàn!
public class SafeCounter {
    private AtomicInteger count = new AtomicInteger(0);

    public void increment() {
        count.incrementAndGet(); // Thao tác atomic
    }
}
```

### Các lớp Atomic chính

| Lớp                  | Kiểu    | Ví dụ sử dụng             |
| -------------------- | ------- | ------------------------- |
| `AtomicBoolean`      | boolean | Cờ trạng thái             |
| `AtomicInteger`      | int     | Bộ đếm                    |
| `AtomicLong`         | long    | Bộ đếm (64-bit)           |
| `AtomicReference<T>` | Object  | Reference thread-safe     |
| `AtomicIntegerArray` | int[]   | Mảng các bộ đếm           |
| `LongAdder`          | long    | Bộ đếm tải cao            |

### Ví dụ sử dụng

```java
// AtomicInteger
AtomicInteger counter = new AtomicInteger(0);
counter.incrementAndGet();   // ++i (trả về giá trị mới)
counter.getAndIncrement();   // i++ (trả về giá trị cũ)
counter.addAndGet(5);        // i += 5
counter.compareAndSet(5, 10);// Nếu i==5, đặt thành 10

// AtomicBoolean
AtomicBoolean flag = new AtomicBoolean(false);
flag.set(true);
boolean oldValue = flag.getAndSet(false);

// AtomicReference
AtomicReference<String> ref = new AtomicReference<>("initial");
ref.compareAndSet("initial", "updated");
```

### Cơ chế: CAS + volatile

Các lớp Atomic hoạt động trên hai trụ cột:

1. **Field `volatile`** — đảm bảo visibility của các thay đổi
2. **CAS (Compare-And-Swap)** — cập nhật atomic

```java
// Hiện thực AtomicInteger đơn giản hóa
public class AtomicInteger {
    private volatile int value; // volatile cho visibility

    public final int incrementAndGet() {
        for (;;) { // Vòng lặp vô hạn
            int current = get();         // 1. Đọc
            int next = current + 1;      // 2. Tính
            if (compareAndSet(current, next)) { // 3. CAS — cập nhật
                return next;             // Thành công!
            }
            // CAS thất bại — ai đó khác đã cập nhật, thử lại
        }
    }
}
```

## Middle Level

### CAS (Compare-And-Swap) chi tiết

CAS là một lệnh CPU thực hiện atomic:
1. So sánh giá trị tại một địa chỉ với giá trị mong đợi
2. Nếu bằng nhau — ghi giá trị mới
3. Nếu không bằng — không làm gì

```java
// Mã giả CAS
boolean CAS(memoryAddress, expectedValue, newValue) {
    if (*memoryAddress == expectedValue) {
        *memoryAddress = newValue;
        return true;
    }
    return false;
}
```

Trên x86 đây là lệnh `LOCK CMPXCHG`.

  CMPXCHG (CoMPare and eXCHanGe) — lệnh x86 cho thao tác CAS. Trên ARM — `ldxr/stxr`, trên RISC-V — `lr.w/sc.w` (Load Reserved / Store Conditional).

### Cập nhật Reference

```java
public class AtomicReferenceDemo {
    private AtomicReference<List<String>> list = new AtomicReference<>(new ArrayList<>());

    public void addItem(String item) {
        list.updateAndGet(currentList -> {
            // Tạo một bản sao mới (immutable update)
            List<String> newList = new ArrayList<>(currentList);
            newList.add(item);
            return newList;
        });
    }
}
```

### VarHandle (Java 9+)

Bắt đầu từ Java 9, các lớp Atomic được viết lại dùng `VarHandle`:

  VarHandle (Java 9, JEP 193) — thay thế cho sun.misc.Unsafe cho các thao tác atomic. An toàn hơn (không truy cập bộ nhớ trực tiếp), nhưng với cùng các khả năng. API của các lớp Atomic vẫn tương thích ngược — không cần thay đổi code của bạn.

```java
// Thay vì sun.misc.Unsafe — API có kiểu và an toàn
public class AtomicInteger {
    private static final VarHandle VALUE;
    private volatile int value;

    static {
        try {
            MethodHandles.Lookup l = MethodHandles.lookup();
            VALUE = l.findVarHandle(AtomicInteger.class, "value", int.class);
        } catch (ReflectiveOperationException e) {
            throw new Error(e);
        }
    }
}
```

### Các mức đảm bảo bộ nhớ khác nhau

```java
AtomicLong counter = new AtomicLong(0);

// Các method ghi khác nhau:
counter.set(100);          // Ghi volatile — visibility đầy đủ
counter.lazySet(100);      // Visibility nới lỏng: không đặt rào chắn StoreLoad, lần ghi có thể trở nên nhìn thấy được với một độ trễ. Nhanh hơn!
counter.compareAndSet(0, 100); // CAS với rào chắn đầy đủ
```

| Method              | Đảm bảo                                                                                                                                                                                       | Tốc độ   |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------- |
| `set(v)`            | Visibility đầy đủ ngay lập tức                                                                                                                                                               | Chuẩn    |
| `lazySet(v)`        | Visibility cuối cùng (eventual)                                                                                                                                                              | Nhanh hơn|
| `compareAndSet`     | Rào chắn đầy đủ                                                                                                                                                                              | Chuẩn    |
| `weakCompareAndSet` | Có thể trả về false một cách giả (ngay cả khi giá trị khớp) trên một số kiến trúc. Đây không phải bug — được đặc tả cho phép để tối ưu trên các CPU với memory model yếu (ARM, RISC-V).       | Nhanh hơn|

### LongAdder cho tranh chấp cao

Với hàng trăm thread cập nhật một bộ đếm duy nhất, `AtomicLong` bắt đầu chậm lại (CAS liên tục thất bại).

```java
// XẤU khi tranh chấp cao:
AtomicLong counter = new AtomicLong(0);
// Mọi thread liên tục "trượt" trên CAS

// TỐT khi tranh chấp cao:
LongAdder counter = new LongAdder();
counter.increment(); // Phân tán qua các cell
long total = counter.sum(); // Cộng tất cả các cell
```

**LongAdder hoạt động như thế nào:**
- Thay vì một biến — một mảng các Cell
- Các thread khác nhau cập nhật các cell khác nhau
- Khi `sum()`, các giá trị được cộng lại

## Khi nào các lớp Atomic KHÔNG phù hợp

1. **Các thao tác gộp trên nhiều field**: cần cập nhật atomic hai field — AtomicInteger không giúp được, cần synchronized hoặc AtomicReference với một immutable object
2. **Tranh chấp cao (100+ thread)**: chu kỳ CAS lãng phí CPU — tốt hơn nên dùng LongAdder
3. **Các phép tính dài giữa đọc và ghi**: nếu nhiều thời gian trôi qua giữa đọc và ghi — CAS sẽ liên tục thất bại, tốt hơn nên dùng Lock

## Senior Level

### Bên trong: hiện thực CAS

Ở mức CPU x86:

```assembly
; LOCK CMPXCHG — thao tác atomic
; rax = expected, rcx = newValue, [memory] = giá trị thực tế

lock cmpxchg [memory], rcx
; Nếu [memory] == rax:
;   [memory] = rcx
;   ZF = 1 (thành công)
; Ngược lại:
;   rax = [memory]
;   ZF = 0 (thất bại)
```

`lock` prefix khóa memory bus trong suốt thời gian thao tác, đảm bảo atomicity trên các hệ thống đa xử lý.

### Vấn đề ABA

Một vấn đề CAS kinh điển:

```
Thread 1: đọc giá trị A
Thread 2: đổi A → B → A (giá trị được trả về!)
Thread 1: CAS(A, new_value) — THÀNH CÔNG! Nhưng trạng thái đã thay đổi!
```

#### Giải pháp: AtomicStampedReference

```java
// Lưu giá trị + version (stamp)
AtomicStampedReference<String> ref = new AtomicStampedReference<>("A", 0);

int[] stampHolder = new int[1];
String value = ref.get(stampHolder);
int stamp = stampHolder[0];

// CAS với kiểm tra version
boolean success = ref.compareAndSet("A", "B", stamp, stamp + 1);
```

#### AtomicMarkableReference

```java
// Lưu giá trị + cờ boolean
AtomicMarkableReference<Node> ref = new AtomicMarkableReference<>(node, false);

// Đánh dấu node là "removed"
ref.compareAndSet(node, node, false, true);
```

### Cấu trúc bên trong của LongAdder

```java
// Đơn giản hóa
public class LongAdder {
    // Giá trị base (dùng khi tranh chấp thấp)
    volatile long base;

    // Mảng cell (dùng khi tranh chấp cao)
    volatile Cell[] cells;

    static final class Cell {
        @Contended // Padding để tránh False Sharing
        volatile long value;
    }

    public void add(long x) {
        Cell[] as; long b, v; int m; Cell a;
        if ((as = cells) != null || !casBase(b = base, b + x)) {
            // Base CAS thất bại — dùng Cell
            // Mỗi thread hash vào cell riêng của nó
            // ...
        }
    }

    public long sum() {
        long sum = base;
        for (Cell a : cells) {
            if (a != null) sum += a.value;
        }
        return sum;
    }
}
```

### Hiệu năng và tải cao (Highload)

#### Benchmark (xấp xỉ, 100 thread)

| Thao tác       | Thời gian mỗi thao tác | Ghi chú               |
| -------------- | ---------------------- | --------------------- |
| `synchronized` | ~5000 ns               | Context switching     |
| `AtomicLong`   | ~100 ns                | CAS contention        |
| `LongAdder`    | ~10 ns                 | Cell phân tán         |

#### False Sharing

```java
// Vấn đề: mảng các phần tử Atomic trong một cache line
AtomicInteger[] counters = new AtomicInteger[16];
// counters[0] và counters[1] có thể nằm trong cùng một cache line
// Ghi vào counters[0] làm vô hiệu hóa counters[1]
```

Giải pháp — `@Contended` bên trong LongAdder:

```java
@jdk.internal.vm.annotation.Contended
volatile long value; // 128 byte padding xung quanh
```

### AtomicIntegerFieldUpdater — Tiết kiệm bộ nhớ

Nếu bạn có hàng triệu object và mỗi cái cần một bộ đếm atomic:

```java
// XẤU: hàng triệu object AtomicInteger bổ sung trong bộ nhớ
class User {
    AtomicInteger loginAttempts = new AtomicInteger(0); // +24 byte mỗi object
}

// TỐT: updater làm việc với một field int thông thường
class User {
    volatile int loginAttempts = 0; // 4 byte

    private static final AtomicIntegerFieldUpdater<User> UPDATER =
        AtomicIntegerFieldUpdater.newUpdater(User.class, "loginAttempts");

    public void increment() {
        UPDATER.incrementAndGet(this);
    }
}
```

### Best Practices

1. **Atomic*** cho các bộ đếm và cờ đơn giản khi tranh chấp vừa phải
2. **LongAdder** cho các bộ đếm tải cao (metric, thống kê)
3. **AtomicReference** với `updateAndGet` cho các immutable update
4. **AtomicStampedReference** khi vấn đề ABA quan trọng
5. **synchronized** cho các thao tác phức tạp (nhiều field cùng lúc)
6. **@Contended** cho các mảng bộ đếm atomic (cần cờ JVM)
7. **Tránh AtomicLong làm ID generator** ở 1000+ RPS — dùng cấp phát theo range

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Các lớp Atomic cung cấp thread safety lock-free qua CAS + volatile
- incrementAndGet = chu kỳ spin: đọc → sửa → CAS retry cho tới khi thành công
- Trên x86, CAS = lệnh `lock cmpxchg` với `lock` prefix (khóa memory bus)
- Java 9+ được viết lại để dùng VarHandle (thay thế an toàn cho sun.misc.Unsafe, JEP 193)
- Vấn đề ABA: giá trị đổi A→B→A, CAS "không nhận ra"; giải pháp — AtomicStampedReference
- LongAdder giải quyết tranh chấp ở 100+ thread: phân tán qua mảng Cell[], cộng khi sum()
- `lazySet()` — visibility nới lỏng (eventual), nhanh hơn `set()` — không đặt rào chắn StoreLoad

**Các câu hỏi phụ thường gặp:**
- **Tại sao AtomicLong chậm lại khi tranh chấp cao?** — CAS liên tục thất bại, các thread spin trong một chu kỳ, lãng phí CPU
- **LongAdder khác AtomicLong như thế nào?** — LongAdder: mảng cell, mỗi thread ghi vào cell riêng; AtomicLong: một biến, tất cả cạnh tranh
- **Vấn đề ABA là gì?** — Thread 1 đọc A, Thread 2 đổi A→B→A, Thread 1: CAS(A) — thành công, nhưng trạng thái đã thay đổi
- **Khi nào dùng AtomicReference?** — Cho việc thay thế atomic các immutable object (ví dụ: cập nhật cấu hình)

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Các lớp Atomic dùng khóa" — không, chúng lock-free qua CAS
- "CAS là atomic trên bất kỳ kiến trúc nào" — trên JVM 32-bit, AtomicLong có thể dùng một khóa nội bộ
- "lazySet() đảm bảo visibility ngay lập tức" — không, eventual consistency, không có rào chắn StoreLoad
- "LongAdder luôn tốt hơn AtomicLong" — không, LongAdder nhanh hơn chỉ khi tranh chấp cao; cho các trường hợp thông thường, dùng AtomicLong
