# What is the difference between Executors.newFixedThreadPool() and newCachedThreadPool()? (Sự khác biệt giữa Executors.newFixedThreadPool() và newCachedThreadPool() là gì?)

---

## Junior Level

### Hiểu biết cơ bản

Cả hai pool đều tạo một `ExecutorService`, nhưng hành vi của chúng khác nhau hoàn toàn.

### newFixedThreadPool

```java
ExecutorService pool = Executors.newFixedThreadPool(10);
```

- Số lượng thread **cố định** (10)
- Các tác vụ **chờ trong một hàng đợi** nếu mọi thread đều bận
- Các thread **không bao giờ chết** — luôn sẵn sàng làm việc

### newCachedThreadPool

```java
ExecutorService pool = Executors.newCachedThreadPool();
```

- Số lượng thread **động** (0 tới vô hạn)
- Mỗi tác vụ **lập tức nhận** một thread (mới hoặc rảnh)
- Các thread rảnh **chết sau 60 giây**

### So sánh

| Đặc điểm         | FixedThreadPool                     | CachedThreadPool                |
| ---------------- | ----------------------------------- | ------------------------------- |
| Kích thước Pool  | Cố định                             | Động                            |
| Hàng đợi         | LinkedBlockingQueue (không giới hạn) | SynchronousQueue (sức chứa 0)   |
| Thread nhàn rỗi  | Sống mãi mãi                        | Chết sau 60s                    |
| Tốt nhất cho     | Tải đều/ổn định                    | Tải bùng nổ (bursty)            |

## Middle Level

### Cấu hình bên trong

#### newFixedThreadPool

```java
new ThreadPoolExecutor(
    n,                    // corePoolSize = n
    n,                    // maximumPoolSize = n
    0L,                   // keepAliveTime = 0
    TimeUnit.MILLISECONDS,
    new LinkedBlockingQueue<Runnable>() // hàng đợi KHÔNG GIỚI HẠN
);
```

#### newCachedThreadPool

```java
new ThreadPoolExecutor(
    0,                    // corePoolSize = 0
    Integer.MAX_VALUE,    // maximumPoolSize = vô hạn!
    60L,                  // keepAliveTime = 60 giây
    TimeUnit.SECONDS,
    new SynchronousQueue<Runnable>() // Sức chứa = 0
);
```

### Các tác vụ được chuyển giao như thế nào

#### FixedThreadPool: Hàng đợi thụ động

```
Task → Hàng đợi (LinkedBlockingQueue) → Thread rảnh nhặt lên
       [1] [2] [3] [4] [5] ... [1000] ... [∞]
```

Mọi tác vụ tích tụ trong hàng đợi. Các thread xử lý từng cái một.

#### CachedThreadPool: Chuyển giao tay-trao-tay

```
Task → SynchronousQueue → NGAY LẬP TỨC tới một thread rảnh
                         → Hoặc một thread mới được tạo
```

`SynchronousQueue` có sức chứa 0. Mỗi tác vụ PHẢI được trao cho một thread ngay lập tức.

### Khi nào dùng cái nào

| Kịch bản                            | FixedThreadPool | CachedThreadPool |
| ----------------------------------- | --------------- | ---------------- |
| Web server (traffic ổn định)        | Có              | Không            |
| Batch processing                    | Có              | Không            |
| Các HTTP request ngắn               | Không           | Có               |
| Tác vụ nền (không thường xuyên)     | Không           | Có               |

## Senior Level

### Nguy hiểm của FixedThreadPool

**Vấn đề:** Hàng đợi không giới hạn → `OutOfMemoryError`

```java
ExecutorService pool = Executors.newFixedThreadPool(10);

for (int i = 0; i < 10_000_000; i++) {
    pool.submit(() -> {
        Thread.sleep(1000); // Tác vụ chậm
    });
}
// Hàng đợi: 10.000.000 object Runnable → OutOfMemoryError!
```

**Giải pháp:** Hàng đợi có giới hạn

```java
ExecutorService safePool = new ThreadPoolExecutor(
    10, 10, 0L, MILLISECONDS,
    new ArrayBlockingQueue<>(10000), // Giới hạn!
    new ThreadPoolExecutor.CallerRunsPolicy() // Back-pressure
);
```

### Nguy hiểm của CachedThreadPool

**Vấn đề:** Bùng nổ thread → `OutOfMemoryError: unable to create new native thread`

```java
ExecutorService pool = Executors.newCachedThreadPool();

for (int i = 0; i < 100_000; i++) {
    pool.submit(() -> {
        Thread.sleep(5000); // Tác vụ dài
    });
}
// Sẽ tạo 100.000 thread! OS không kham nổi → OOM
```

**Giải pháp:** Giới hạn maximumPoolSize

```java
ExecutorService safeCached = new ThreadPoolExecutor(
    0, 200,               // Tối đa 200 thread!
    60L, TimeUnit.SECONDS,
    new SynchronousQueue<>(),
    new ThreadPoolExecutor.CallerRunsPolicy()
);
```

### So sánh cơ chế (nâng cao)

| Đặc điểm             | FixedThreadPool                                                   | CachedThreadPool                            |
| -------------------- | --------------------------------------------------------------- | ------------------------------------------- |
| **Giới hạn resource**| Giới hạn cứng số thread                                          | Không có (rủi ro OOM từ thread)             |
| **Hàng đợi**         | Thụ động (tích tụ)                                              | Chủ động (tay-trao-tay)                     |
| **Thread nhàn rỗi**  | Các thread không bao giờ chết                                   | Các thread bị xóa sau một phút             |
| **Latency**          | ~cao hơn (tác vụ chờ trong hàng đợi cho một thread rảnh, +0-1000ms)| ~thấp hơn (lập tức nhận một thread, ~0ms)|
| **Bộ nhớ**           | Ổn định                                                         | Tăng trong lúc bùng nổ                      |

### Khuyến nghị cho Production

Trong production, `Executors.newCachedThreadPool()` nguy hiểm khi không có giới hạn, vì trong các đợt tải tăng đột biến nó tạo hàng nghìn thread. Cho các tác vụ ngắn, hãy dùng một ThreadPoolExecutor tùy chỉnh với maxPoolSize. Trong Java 21+, hãy cân nhắc virtual thread.

**Tại sao:**
- Vi phạm nguyên tắc dự đoán được (predictability)
- Trong các đợt tải tăng đột biến, tạo hàng nghìn thread
- Có thể giết OS hoặc JVM

**Cách làm đúng:**

```java
// Giải pháp an toàn thay thế cho CachedThreadPool
ExecutorService safePool = new ThreadPoolExecutor(
    0,                      // corePoolSize
    200,                    // maximumPoolSize — giới hạn cứng!
    60L, TimeUnit.SECONDS,
    new SynchronousQueue<>(),
    new ThreadPoolExecutor.CallerRunsPolicy() // Back-pressure
);
```

### Chẩn đoán

#### VisualVM / JConsole

```
FixedThreadPool:    ──────────────── đường thẳng ổn định (10 thread)
CachedThreadPool:   /\/\/\/\        "khu rừng" — xuất hiện và biến mất
```

#### Thread Dump

```bash
jstack <pid>
```

Các vấn đề của CachedThreadPool:
```
"pool-1-thread-1001" #1010 RUNNABLE
"pool-1-thread-1002" #1011 RUNNABLE
...
// Hàng trăm thread chờ trên SynchronousQueue
```

#### Giám sát

```java
// Ngưỡng phụ thuộc vào kích thước tác vụ trong bộ nhớ.
// Nếu Runnable = 1KB, thì 1000 tác vụ = 1MB.
// Nếu Runnable capture các object lớn — ngưỡng nên thấp hơn.
int queueSize = ((ThreadPoolExecutor)pool).getQueue().size();
if (queueSize > 1000) {
    log.warn("Queue is growing! Possible OOM risk");
}

// CachedThreadPool — giám sát kích thước pool
int poolSize = ((ThreadPoolExecutor)pool).getPoolSize();
if (poolSize > 100) {
    log.warn("Too many threads! Possible thread explosion");
}
```

### Best Practices

> **Java 21+:** Cho các tác vụ ngắn, `Executors.newVirtualThreadPerTaskExecutor()` thay thế CachedThreadPool. Virtual thread tốn ~KB (so với ~1MB cho thread thông thường) và có thể được tạo hàng triệu cái mà không có rủi ro bùng nổ thread.

1. **FixedThreadPool** — cho tải ổn định với một mức tối đa đã biết
2. **CachedThreadPool** — CHỈ cho các tác vụ ngắn với maxPoolSize có giới hạn
3. **Luôn giới hạn hàng đợi** — ArrayBlockingQueue với một giới hạn
4. **Luôn giới hạn maxPoolSize** — ngay cả cho CachedThreadPool
5. **CallerRunsPolicy** — back-pressure khi quá tải
6. **Giám sát queue.size()** cho FixedThreadPool
7. **Giám sát kích thước pool** cho CachedThreadPool
8. **Tránh Executors.* trong production** — tạo ThreadPoolExecutor trực tiếp

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- FixedThreadPool: kích thước cố định, LinkedBlockingQueue không giới hạn, các thread không bao giờ chết — rủi ro OOM từ hàng đợi
- CachedThreadPool: 0..Integer.MAX_VALUE thread, SynchronousQueue (sức chứa 0), các thread chết sau 60s — rủi ro bùng nổ thread
- SynchronousQueue có sức chứa 0 — mỗi tác vụ PHẢI được trao cho một thread ngay lập tức hoặc một thread mới được tạo
- Latency của FixedThreadPool cao hơn (tác vụ chờ trong hàng đợi), latency của CachedThreadPool thấp hơn (~0ms độ trễ)
- FixedThreadPool — cho tải đều ổn định; CachedThreadPool — cho các tác vụ ngắn với traffic bùng nổ
- Trong production cả hai đều nguy hiểm: FixedThreadPool → OOM từ hàng đợi, CachedThreadPool → unable to create new native thread
- Giải pháp: ThreadPoolExecutor tùy chỉnh với ArrayBlockingQueue và maxPoolSize + CallerRunsPolicy cho back-pressure
- Java 21+: Executors.newVirtualThreadPerTaskExecutor() thay thế CachedThreadPool (~KB mỗi thread so với ~1MB)

**Các câu hỏi phụ thường gặp:**
- **Tại sao FixedThreadPool có thể gây OOM?** — LinkedBlockingQueue không có giới hạn — nếu tác vụ đến nhanh hơn mức xử lý, hàng đợi tăng vô hạn
- **Tại sao CachedThreadPool có thể tạo hàng nghìn thread?** — SynchronousQueue không buffer, mỗi slot rảnh → thread mới, maximumPoolSize = Integer.MAX_VALUE
- **Back-pressure là gì và CallerRunsPolicy hoạt động như thế nào?** — Tác vụ chạy trong thread đã submit, thứ không thể submit tác vụ mới — tự động làm chậm nguồn
- **Làm sao tạo một giải pháp an toàn thay thế cho CachedThreadPool?** — ThreadPoolExecutor với maxPoolSize=200 và CallerRunsPolicy

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "CachedThreadPool là mặc định của tôi cho mọi tác vụ" — nguy hiểm cho các tác vụ dài, bùng nổ thread
- "FixedThreadPool hoàn toàn an toàn" — không, hàng đợi không giới hạn = OOM
- "SynchronousQueue lưu các tác vụ trong một hàng đợi" — không, sức chứa 0, chỉ chuyển giao trực tiếp
- "Các thread trong CachedThreadPool sống mãi mãi" — không, chúng chết sau 60 giây nhàn rỗi
