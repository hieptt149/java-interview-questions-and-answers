# What Happens if a Class Has Multiple Reasons to Change (Điều gì xảy ra nếu một class có nhiều lý do để thay đổi)

## 🟢 Junior Level

Khi một class có **nhiều lý do để thay đổi** (vi phạm SRP), nó trở nên dễ vỡ và phức tạp. Bất kỳ thay đổi nhỏ nào cũng có thể phá vỡ chức năng hoàn toàn không liên quan.

**Analogy đơn giản:** Hãy tưởng tượng một con dao đa năng Thụy Sĩ với 50 công cụ. Nếu bạn cần thay lưỡi dao — bạn phải tháo rời toàn bộ con dao. Và nếu bạn làm hỏng tuốc nơ vít — cái mở nút chai cũng ngừng hoạt động.

**Ví dụ vi phạm:**
```java
// Xấu: 4 lý do khác nhau để thay đổi
public class User {
    private String name;              // Dữ liệu

    public void validate() { }        // Validation (thay đổi bởi luật sư)
    public void save() { }            // Persistence (thay đổi bởi DBA)
    public String toJson() { }        // Định dạng (thay đổi bởi frontend)
}
```

**Điều gì sẽ xảy ra:**
- Thay đổi validation → có thể phá vỡ persistence, vì cả hai phương thức chia sẻ các trường của class
- Thay đổi định dạng JSON → cần test lại mọi thứ, vì code trong một file
- Các team khác nhau xung đột trên một file khi merge

**Cách sửa:**
```java
// Tốt: mỗi trách nhiệm trong class riêng của nó
public class User { private String name; }              // Chỉ dữ liệu
public class UserValidator { void validate(User u) { } } // Chỉ validation
public class UserRepository { void save(User u) { } }    // Chỉ DB
public class UserMapper { String toJson(User u) { } }    // Chỉ định dạng
```

## 🟡 Middle Level

### Cách Hoạt Động

Khi một class có nhiều lý do để thay đổi, nó trở nên **"Rigid"** và **"Fragile"**. Mỗi trách nhiệm là một "trục thay đổi." Nếu có nhiều trục — class sụp đổ dưới áp lực.

### Hậu Quả Cho Dự Án

| Vấn đề           | Mô tả                                      | Tác động                                                                           |
| ----------------- | ------------------------------------------------ | -------------------------------------------------------------------------------- |
| **Tải Nhận Thức**| Class với 5 trách nhiệm = hàng trăm tổ hợp | Developer sợ thay đổi code                                |
| **Tính Dễ Vỡ**     | Thay đổi ở một nơi phá vỡ nơi khác               | Bug dây chuyền                                                                   |
| **Merge Conflict**| Các team khác nhau thay đổi cùng file            | Trong các dự án lớn — một phần lớn thời gian dành cho giải quyết xung đột   |

### Ứng Dụng Thực Tế

**Metric Cognitive Complexity (SonarQube):**
- Phương thức > 15 → khó bảo trì
- Class > 200 dòng → khó giữ toàn bộ logic trong đầu, nguy cơ bug tăng

**Phân Tích Code Churn (metric về tần suất một file thay đổi):**
- Nếu một file xuất hiện trong hầu hết các commit → quá nhiều lý do để thay đổi

### Các Lỗi Thường Gặp

| Lỗi                                                                     | Giải pháp                                                 |
| --------------------------------------------------------------------------- | -------------------------------------------------------- |
| God Object (một class với hàng chục trường và phương thức cho mọi trường hợp)   | Chia theo trách nhiệm                                |
| Hiệu Ứng Cánh Bướm (1 thay đổi → 10 lần sửa trong các file khác)                       | Trích xuất các service riêng biệt                                |
| Merge conflict hàng ngày                                                       | Package-by-Feature (nhóm theo tính năng, không theo tầng)       |

### Khi Nào KHÔNG Nên Tuân Thủ SRP Nghiêm Ngặt

- Prototype/MVP (xác thực nhanh)
- Script migration (code một lần)
- Khi chi phí thay đổi tối thiểu

## 🔴 Senior Level

### Triển Khai Nội Bộ: Cơ Chế Của Tính Dễ Vỡ

**Vấn Đề Shared State:**
```java
class GodObject {
    private Date lastProcessed;  // Dùng cho logging VÀ business logic
    // Thay đổi định dạng ngày trong log phá vỡ các tính toán
}
```

**Các Vấn Đề Về Bố Cục Bộ Nhớ:**
- **False Sharing**: Các trường của các trách nhiệm khác nhau rơi vào cùng cache line (64 byte)
- **Tác động**: Các CPU core làm mất hiệu lực cache của nhau → chậm 10-100 lần

### Đánh Đổi Kiến Trúc

**SRP Nghiêm Ngặt:**
- ✅ Ưu điểm: Side effect tối thiểu, phát triển song song, test dễ dàng
- ❌ Nhược điểm: Bùng nổ class, phức tạp điều hướng, overhead giao tiếp

**SRP Vừa Phải:**
- ✅ Ưu điểm: Cân bằng giữa tính thuần khiết và thực dụng
- ❌ Nhược điểm: Yêu cầu phán đoán trưởng thành, nguy cơ suy thoái kiến trúc dần dần

### Edge Cases

1. **Lock Contention**: Singleton God Object → các thread khác nhau cạnh tranh cho một monitor
   - **Giải pháp**: Chia thành các bean riêng biệt với các lock độc lập

2. **Tác Động Metaspace**: Các class khổng lồ → nhiều bytecode hơn → nhiều metaspace hơn
   - **Tác động**: +2-5MB cho mỗi class 5000+ dòng

3. **Ranh Giới Transaction**: Một class điều phối một transaction qua nhiều domain
   - **Giải pháp**: Pattern Orchestrator (một class coordinator gọi các service riêng biệt theo đúng thứ tự nhưng không chứa business logic của chúng), `@Transactional` trên orchestrator

### Hiệu Năng

| Metric                   | God Object            | Tuân Thủ SRP           |
| ------------------------ | --------------------- | ----------------------- |
| **Cognitive Complexity** | 50-200+               | <15                     |
| **Tỷ Lệ L1 Cache Hit**    | 40-60%                | 85-95%                  |
| **Lock Contention**      | Cao (một monitor duy nhất) | Thấp (các lock độc lập) |
| **Thực Thi Test**       | Chậm (nhiều mock)     | Nhanh (cô lập)          |

**Tác Động False Sharing:**
```
Field A (logging) và Field B (business logic) trong cùng cache line
→ Thread 1 ghi A → làm mất hiệu lực cache của Thread 2 cho B
→ chậm 10-100 lần dưới tranh chấp cao
```

### Thread Safety

- **Bottleneck monitor duy nhất**: Tất cả các thread chờ một God Object
- **Các service độc lập**: Các lock khác nhau → thực thi song song
- **Tỷ lệ tranh chấp**: God Object → 60-80% thời gian chờ, SRP → <10%

### Kinh Nghiệm Production

**Refactoring BillingEngine (15,000 dòng):**

**Vấn đề:**
- 8 trách nhiệm: tính toán, validation, DB, email, PDF, audit, cache, logging
- Cognitive Complexity: 340 (chuẩn < 15 — metric độ rối rắm code từ SonarQube)
- Merge conflict: hàng ngày, 2-3 giờ để giải quyết
- Tỷ lệ bug: 40% deployment có bug

**Giải pháp (6 sprint):**
1. Phân tích tính năng: nhóm các phương thức theo domain
2. Trích xuất: `TaxCalculator`, `InvoiceGenerator`, `PaymentProcessor`
3. Tạo `BillingOrchestrator` để điều phối
4. Event-driven: `BillingCompletedEvent` cho audit/email

**Kết quả:**
- Cognitive Complexity: 8-12 mỗi class
- Merge conflict: <1 mỗi tháng
- Tỷ lệ bug: 8% deployment
- Thời gian deployment: 30 phút → 5 phút

### Monitoring

**ArchUnit:**
```java
@ArchTest
static void no_god_objects = classes()
    .should().haveLessThanNMethods(30)
    .andShould().haveLessThanNFields(15)
    .andShould().haveLessThanNDependencies(7);
```

**SonarQube:**
- Cognitive Complexity > 15 → Code Smell
- Kích thước class > 300 dòng → ứng viên refactoring

**Phân Tích Git:**
```bash
# Tần suất thay đổi file
git log --oneline -- User.java | wc -l
# Nếu >90% commit chạm vào file này → vi phạm SRP
```

### Best Practices Cho Highload

- **Tối đa 300 dòng** mỗi class
- **Tối đa 15 trường** mỗi class
- **Tối đa 7 dependency**
- **Package-by-Feature** cho tính module
- **Kiểm tra CI ArchUnit**
- **Giám sát code churn** trong Git

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- Class với nhiều lý do để thay đổi = "Rigid" và "Fragile"
- Tải Nhận Thức: hàng trăm tổ hợp → developer sợ thay đổi code
- Hiệu Ứng Cánh Bướm: 1 thay đổi → 10 lần sửa trong các file khác
- False Sharing: các trường của các trách nhiệm khác nhau trong cùng cache line → chậm 10-100 lần
- God Object → bottleneck monitor duy nhất → 60-80% thời gian chờ trong môi trường đa luồng
- Pattern Orchestrator giải quyết vấn đề: điều phối mà không có business logic
- Metric: Cognitive Complexity > 15, Kích thước class > 300 dòng, Dependency > 7

**Các câu hỏi phụ thường gặp:**
- **Vấn Đề Shared State là gì?** — Một trường được dùng cho các mục đích khác nhau (logging VÀ business logic), thay đổi định dạng phá vỡ các tính toán
- **God Object ảnh hưởng đến Thread Safety như thế nào?** — Một monitor cho toàn bộ object → tất cả thread chờ, tỷ lệ tranh chấp 60-80%
- **Code Churn là gì?** — Metric tần suất thay đổi file; >90% commit chạm vào một file → vi phạm SRP
- **Kết quả refactoring là gì?** — Cognitive Complexity 8-12, tỷ lệ bug 8%, thời gian deployment 5 phút thay vì 30

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Một vi phạm SRP nhỏ là ổn" (bug dây chuyền và merge conflict tích lũy)
- "God Object có thể sửa trong một sprint" (trường hợp thực tế: 6 sprint cho 15,000 dòng)
- "SRP chỉ dành cho các class lớn" (một class 30 dòng có thể làm 3 việc)
