# How does Kafka ensure fault tolerance (Kafka đảm bảo fault tolerance như thế nào)

## Junior Level

### Các Cơ Chế Chính

Kafka đảm bảo khả năng chịu lỗi thông qua **replication**:

```
1. Replication — dữ liệu trên nhiều broker
2. Bầu leader — chọn tự động một leader mới
3. Consumer group — các consumer restart và tiếp tục
```

### Ví Dụ Failover

```
Broker A (Leader) → dừng hoạt động
Broker B (Follower) → trở thành Leader
Các consumer → tiếp tục đọc từ leader mới
Các producer → tiếp tục ghi vào leader mới
```

### Replication Factor

```
replication-factor=3 → chịu được lỗi của 2 broker (giả sử các replica được
phân phối trên các broker khác nhau, điều này xảy ra theo mặc định với đủ
số lượng broker).
replication-factor=2 → chịu được lỗi của 1 broker
replication-factor=1 → không có khả năng chịu lỗi
```

### Tạo Một Topic Chịu Lỗi

```bash
kafka-topics.sh --create \
  --topic orders \
  --partitions 3 \
  --replication-factor 3 \
  --bootstrap-server localhost:9092
```

## Middle Level

### Khả Năng Chịu Lỗi Ở Các Cấp Độ Khác Nhau

**Broker:**
```
RF=3 → dữ liệu trên 3 broker
Chịu được lỗi của 2 broker
```

**Producer:**
```
acks=all + retries → retry tự động
enable.idempotence → bảo vệ khỏi trùng lặp
```

**Consumer:**
```
Các offset đã commit → tiếp tục sau khi restart
Consumer group → rebalancing tự động
```

### Bầu Leader

```
1. Leader dừng hoạt động
2. Controller phát hiện lỗi
3. Chọn một leader mới từ ISR
4. Các producer và consumer chuyển đổi
```

### Min.insync.replicas

```
min.insync.replicas=2:
  Các ghi chỉ được phép nếu >= 2 replica ở trong ISR
  Bảo vệ khỏi việc ghi vào chỉ một bản sao
```

### Các Lỗi Thường Gặp

1. **Replication không đủ:**
```
RF=2, min.insync=1 → mất dữ liệu khi leader lỗi
```

2. **Unclean leader election:**
```
unclean.leader.election.enable=true → rủi ro mất dữ liệu
```

## Senior Level

### Replication Chéo Trung Tâm Dữ Liệu

**MirrorMaker 2:**
```
Replication giữa các trung tâm dữ liệu
Topology active-passive hoặc active-active
Replication bất đồng bộ
```

**Các Lựa Chọn Topology:**
```
1. Active-Passive:
   DC1 (active) → DC2 (passive)
   Nếu DC1 dừng hoạt động → DC2 trở thành active

2. Active-Active:
   DC1 ← → DC2
   Cả hai DC đều chấp nhận ghi
   Tính nhất quán phức tạp hơn
```

### Các Kịch Bản Lỗi

**1. Lỗi Một Broker Duy Nhất:**
```
RF=3, min.insync=2:
  Broker A (Leader) dừng hoạt động
  ISR=[B,C] → leader mới từ B hoặc C
  Các ghi tiếp tục (ISR >= 2)
  Dữ liệu không bị mất
```

**2. Network Partition:**
```
Các broker chia thành hai nhóm:
  Nhóm 1: Broker A, B
  Nhóm 2: Broker C

Nhóm 1: ISR=[A,B] → hoạt động
Nhóm 2: ISR=[C] → các ghi bị từ chối (ISR < min.insync)
```

**3. Lỗi Trung Tâm Dữ Liệu:**
```
Active-Passive:
  DC1 dừng hoạt động → MirrorMaker dừng lại
  DC2 được kích hoạt → tiếp tục hoạt động
  RPO = dữ liệu được replicate trước khi lỗi
  RTO = thời gian để kích hoạt DC2
```

### Các Quy Trình Phục Hồi

**1. Phục Hồi Broker:**
```
Broker lỗi restart:
  → Kết nối đến cluster
  → Bắt đầu replicate từ leader
  → Khi nó bắt kịp → được thêm trở lại vào ISR
  → Có thể trở thành leader ở lần failover tiếp theo
```

**2. Phục Hồi Trung Tâm Dữ Liệu:**
```
DC1 được khôi phục:
  → MirrorMaker tiếp tục replication
  → Đồng bộ dữ liệu giữa các DC
  → Chuyển trở lại hoặc tiếp tục ở DC2
```

### Cấu Hình Production

```yaml
# Cấp độ topic
replication-factor: 3
min.insync.replicas: 2
unclean.leader.election.enable: false

# Cấp độ broker
replica.lag.time.max.ms: 30000
auto.leader.rebalance.enable: true

# Cấp độ producer
acks: all
enable.idempotence: true
retries: Integer.MAX_VALUE

# Cấp độ consumer
enable.auto.commit: false
isolation.level: read_committed
// isolation.level=read_committed cần thiết để chỉ đọc các message
// transactional đã commit, bỏ qua các message đã abort.
```

### Monitoring

**Các metrics chính:**
```
kafka.server:UnderReplicatedPartitions
kafka.server:IsrShrinksPerSec
kafka.server:ActiveControllerCount
kafka.server:OfflinePartitionsCount
kafka.server:LeaderElectionRate
```

**Các Alert:**
```yaml
- Under-replicated partitions > 0 → warning
- Offline partitions > 0 → critical
- Tỷ lệ ISR shrink > ngưỡng → warning
- Controller thay đổi → điều tra
- Tỷ lệ bầu leader > ngưỡng → warning
```

### Các Thực Hành Tốt Nhất

```
✅ RF=3 cho production
✅ min.insync.replicas=2
✅ acks=all cho dữ liệu quan trọng
✅ Replication chéo DC cho disaster recovery
✅ Leader rebalancer tự động
✅ Giám sát under-replicated partitions

❌ RF < 3 cho production
❌ Một trung tâm dữ liệu duy nhất cho dữ liệu quan trọng
❌ unclean.leader.election.enable=true
❌ min.insync.replicas=1 với acks=all
❌ Không có giám sát sức khỏe ISR
```

### Các Quyết Định Kiến Trúc

1. **RF=3 + min.insync=2** — cân bằng giữa tính khả dụng và tính bền vững
2. **Replication chéo DC** — cho disaster recovery
3. **Unclean election = mất dữ liệu** — tránh trong production
4. **Giám sát under-replicated partitions** — chỉ báo vấn đề sớm

### Tóm Tắt Cho Senior

- Khả năng chịu lỗi được xây dựng trên replication và ISR
- RF=3 chịu được lỗi của 2 broker
- Replication chéo DC cho disaster recovery
- Giám sát under-replicated partitions rất quan trọng
- Unclean leader election là biện pháp cuối cùng với rủi ro mất dữ liệu

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- Khả năng chịu lỗi được xây dựng trên replication (RF=3), ISR, và bầu leader
- RF=3 chịu được 2 lỗi broker; RF=2 — 1 lỗi broker
- `min.insync.replicas=2` + `acks=all` — bảo vệ khỏi việc ghi vào chỉ một bản sao
- Producer: `acks=all` + `enable.idempotence=true` + `retries=INT_MAX`
- Consumer: các offset đã commit + rebalancing tự động của consumer group khi failover
- Khi network partition: nhóm có đa số ISR hoạt động, phần còn lại — các ghi bị từ chối
- Replication chéo DC (MirrorMaker 2) — cho disaster recovery

**Các câu hỏi phụ thường gặp:**
- *Điều gì xảy ra khi một broker dừng hoạt động với RF=3?* — Một follower trở thành leader, dữ liệu không bị mất.
- *Producer xử lý failover như thế nào?* — Retry + idempotence → các trùng lặp bị broker từ chối.
- *Điều gì xảy ra khi network partition?* — Nhóm có đa số ISR tiếp tục, thiểu số — các ghi bị từ chối.
- *Consumer phục hồi như thế nào?* — Các offset đã commit → tiếp tục từ offset đã lưu cuối cùng.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "RF=2 đủ cho dữ liệu quan trọng" — min.insync=1 ở RF=2 = rủi ro mất dữ liệu
- "Kafka không bao giờ mất dữ liệu" — nó có thể mất với unclean leader election
- "Consumer phải khôi phục offset thủ công" — tự động qua consumer group
- "Replication chéo DC là đồng bộ" — nó bất đồng bộ, RPO > 0
