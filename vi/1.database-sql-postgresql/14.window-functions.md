# What Are Window Functions? (Window Functions (hàm cửa sổ) là gì?)

## 🟢 Junior Level

**Window functions (hàm cửa sổ)** là các hàm thực hiện tính toán trên một tập hợp các dòng có liên quan đến dòng hiện tại, mà **không làm gộp/mất** kết quả thành một dòng duy nhất (như GROUP BY vẫn làm).

**Ưu điểm chính:** bạn có được cả chi tiết của từng dòng lẫn giá trị tổng hợp — chỉ trong một truy vấn duy nhất. Với GROUP BY bạn sẽ cần một subquery hoặc JOIN. Với window function: một truy vấn, một lượt duyệt qua dữ liệu.

**Ví dụ minh họa đơn giản:** GROUP BY giống như khi bạn dồn tất cả táo vào một đống và đếm chúng. Một window function là khi với mỗi quả táo, bạn ghi lại tổng số táo có trong giống của nó, nhưng quả táo đó vẫn giữ nguyên vị trí.

**Ví dụ:**
```sql
-- Với mỗi đơn hàng, hiển thị số tiền của nó và giá trị trung bình của người dùng
SELECT
    user_id,
    amount,
    AVG(amount) OVER(PARTITION BY user_id) as user_avg
FROM orders;

-- Kết quả:
-- user_id | amount | user_avg
-- 1       | 100    | 150      ← giá trị trung bình cho người dùng 1
-- 1       | 200    | 150      ← cùng giá trị trung bình, dòng không bị gộp/mất
-- 2       | 300    | 250      ← giá trị trung bình cho người dùng 2
-- 2       | 200    | 250
```

**Các window function chính:**
- `ROW_NUMBER()` — số thứ tự dòng
- `RANK()`, `DENSE_RANK()` — thứ hạng
- `SUM() OVER()`, `AVG() OVER()` — giá trị tổng hợp mà không cần GROUP BY
- `LAG()`, `LEAD()` — truy cập vào dòng trước/sau

## 🟡 Middle Level

### Cấu trúc giải phẫu của một Window Function

```sql
FUNCTION() OVER (
    PARTITION BY column1, column2  -- Phân chia thành các nhóm (giống như GROUP BY)
    ORDER BY column3               -- Sắp xếp trong phạm vi nhóm
    ROWS BETWEEN ... AND ...       -- Ranh giới khung (frame)
)
```

**Sự khác biệt chính so với GROUP BY:**

| GROUP BY                        | Window Functions              |
| -------------------------------- | ----------------------------- |
| Làm gộp/mất các dòng                  | Giữ nguyên các dòng                |
| Một dòng cho mỗi nhóm               | Mỗi dòng + kết quả tính toán        |
| Không thể trộn lẫn chi tiết và giá trị tổng hợp| Bạn có thể!                      |

### Các loại Window Function

**1. Tổng hợp (Aggregate):**
```sql
SELECT
    name,
    salary,
    department,
    AVG(salary) OVER(PARTITION BY department) as dept_avg,
    SUM(salary) OVER(PARTITION BY department) as dept_total,
    COUNT(*) OVER(PARTITION BY department) as dept_count
FROM employees;
```

**2. Xếp hạng (Ranking):**
```sql
SELECT
    name,
    salary,
    ROW_NUMBER() OVER(ORDER BY salary DESC) as row_num,
    RANK() OVER(ORDER BY salary DESC) as rank,
    DENSE_RANK() OVER(ORDER BY salary DESC) as dense_rank
FROM employees;
```

**3. Độ lệch (Offset):**
```sql
-- So sánh với dòng trước
SELECT
    month,
    revenue,
    LAG(revenue, 1) OVER(ORDER BY month) as prev_month,
    LEAD(revenue, 1) OVER(ORDER BY month) as next_month,
    revenue - LAG(revenue, 1) OVER(ORDER BY month) as growth
FROM monthly_sales;
```

### ROWS vs RANGE vs GROUPS

```sql
-- ROWS: các dòng vật lý (nhanh nhất)
SELECT
    date,
    amount,
    AVG(amount) OVER(ORDER BY date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) as moving_avg_7d
FROM sales;

-- RANGE: các giá trị logic (chậm hơn, nhưng chính xác hơn)
SELECT
    date,
    amount,
    SUM(amount) OVER(ORDER BY date RANGE BETWEEN INTERVAL '7 days' PRECEDING AND CURRENT ROW) as weekly_sum
FROM sales;
```

**Sự khác biệt chính minh họa bằng ví dụ:** Nếu cột `date` có các giá trị trùng lặp (hai đơn hàng cùng ngày), thì `ROWS BETWEEN 6 PRECEDING AND CURRENT ROW` sẽ lấy đúng 6 ROW trước đó (bỏ qua ngày tháng), trong khi `RANGE BETWEEN ... 7 days PRECEDING` sẽ lấy tất cả các dòng trong 7 ngày gần nhất (kể cả khi có tới 20 dòng). ROWS = 6 dòng, RANGE = 7 ngày.

### Các lỗi thường gặp

1. **Lọc theo kết quả window trong cùng một truy vấn**
   ```sql
   -- ❌ LỖI: window được tính toán SAU WHERE
   -- Thứ tự thực thi SQL:
   -- FROM → WHERE → GROUP BY → HAVING → SELECT (bao gồm cả window function) → ORDER BY → LIMIT
   -- Vì WHERE thực thi TRƯỚC SELECT, nó không thể thấy được kết quả của window function.
   -- Vì vậy cần một lớp bọc (wrapper): truy vấn bên trong tính toán window, truy vấn bên ngoài — lọc.
   SELECT * FROM (
       SELECT user_id, amount,
              ROW_NUMBER() OVER(PARTITION BY user_id ORDER BY created_at DESC) as rn
       FROM orders
   ) sub
   WHERE rn = 1;  -- ✅ Đúng: trong subquery
   ```

2. **Trộn lẫn nhiều PARTITION BY khác nhau**
   ```sql
   -- ❌ Tốn kém: hai lần sắp xếp khác nhau
   SELECT
       AVG(amount) OVER(PARTITION BY user_id) as user_avg,
       SUM(amount) OVER(PARTITION BY department) as dept_total
   FROM orders;
   -- → Hai giai đoạn sort!
   ```

3. **COUNT(*) OVER() trên dữ liệu lớn**
   ```sql
   -- ❌ Buộc phải đọc TẤT CẢ các dòng của partition
   SELECT id, name, COUNT(*) OVER() as total FROM users LIMIT 10;

   -- ✅ Tốt hơn nên dùng một truy vấn riêng cho tổng số
   SELECT COUNT(*) FROM users;  -- Một lần
   SELECT id, name FROM users LIMIT 10;  -- Riêng biệt
   ```

### Ví dụ thực tiễn

**Tổng lũy kế (Running Total):**
```sql
SELECT
    date,
    amount,
    SUM(amount) OVER(ORDER BY date ROWS UNBOUNDED PRECEDING) as running_total
FROM transactions;
```

**Tỷ lệ phần trăm của nhóm (Percentage of Group):**
```sql
SELECT
    name,
    salary,
    department,
    ROUND(100.0 * salary / SUM(salary) OVER(PARTITION BY department), 2) as pct_of_dept
FROM employees;
```

## 🔴 Senior Level

### Khi nào KHÔNG nên dùng Window Function

1. **Khi bạn chỉ cần một giá trị tổng hợp duy nhất** (tổng, giá trị trung bình) — hãy dùng GROUP BY, nó đơn giản hơn và nhanh hơn
2. **Khi bạn chỉ dùng `COUNT(*) OVER()` để phân trang (pagination)** — một `SELECT COUNT(*)` riêng biệt sẽ nhanh hơn, vì nó không cần đọc tất cả các dòng
3. **Khi có quá nhiều PARTITION BY khác nhau trong một truy vấn** — mỗi tổ hợp duy nhất = một giai đoạn sort riêng biệt, làm giảm nghiêm trọng hiệu năng

### Thứ tự thực thi và các tối ưu hóa

**Thứ tự tính toán SQL:**
```
1. FROM / JOIN
2. WHERE
3. GROUP BY
4. HAVING
5. SELECT / Window Functions  ← Window được tính toán TẠI ĐÂY
6. DISTINCT
7. ORDER BY
8. LIMIT
```

**Lưu ý quan trọng:** Window được tính toán SAU `WHERE`, `GROUP BY`, và `HAVING`. Vì vậy, bạn không thể lọc theo kết quả của window trong cùng một truy vấn.

### ROWS vs RANGE vs GROUPS: Đào sâu chi tiết

**ROWS:**
```sql
-- Các dòng vật lý: 6 PRECEDING + CURRENT
AVG(amount) OVER(ORDER BY date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)

-- Nhanh: chỉ đơn giản lấy N dòng
-- Vấn đề: nếu có trùng lặp trong ORDER BY → không xác định (non-deterministic)
```

**RANGE:**
```sql
-- Các giá trị logic: tất cả các dòng có cùng giá trị
SUM(amount) OVER(ORDER BY amount RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)

-- Chậm hơn: kiểm tra giá trị, không chỉ vị trí
-- Cần thiết để xử lý trùng lặp một cách chính xác
```

**GROUPS (PG 11+):**
```sql
-- Các nhóm dòng có cùng giá trị
AVG(amount) OVER(ORDER BY date GROUPS BETWEEN 1 PRECEDING AND 1 FOLLOWING)

-- Gộp các dòng "ngang hàng" (peer rows) lại với nhau
```

> Ở PG 10 trở xuống, GROUPS không khả dụng. Giải pháp thay thế: subquery với RANGE hoặc lọc thủ công.

### EXCLUDE (PG 11+)

```sql
-- Loại trừ dòng hiện tại khỏi phép tính
SELECT
    name,
    salary,
    AVG(salary) OVER(
        PARTITION BY department
        ORDER BY salary
        ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING
        EXCLUDE CURRENT ROW
    ) as others_avg
FROM employees;
```

**Các tùy chọn của EXCLUDE:**
- `EXCLUDE CURRENT ROW` — không tính dòng hiện tại
- `EXCLUDE GROUP` — không tính dòng hiện tại + các dòng ngang hàng
- `EXCLUDE TIES` — không tính các dòng ngang hàng, nhưng vẫn tính dòng hiện tại
- `EXCLUDE NO OTHERS` — mặc định

> Ở PG 10 trở xuống, EXCLUDE không khả dụng. Giải pháp thay thế: CASE WHEN để loại trừ dòng hiện tại hoặc dùng subquery.

### Incremental Sort (Sắp xếp tăng dần) (PG 13+)

```sql
-- Index trên (department, created_at)
CREATE INDEX idx_orders_dept_date ON orders(department, created_at);

-- Truy vấn với PARTITION BY + ORDER BY
SELECT
    department,
    created_at,
    amount,
    SUM(amount) OVER(PARTITION BY department ORDER BY created_at) as running_total
FROM orders;

-- PG 13+: Incremental Sort
-- Dữ liệu đã được sắp xếp sẵn theo department (từ index)
-- → Chỉ cần sắp xếp theo created_at trong phạm vi từng department
-- → Nhanh hơn 5-10 lần so với sắp xếp toàn bộ!
-- Incremental Sort hoạt động vì dữ liệu đã được sắp xếp sẵn theo phần
-- đầu tiên của key (từ index). Thay vì sắp xếp toàn bộ theo (department, created_at)
-- cơ sở dữ liệu chỉ cần sắp xếp theo created_at trong phạm vi từng nhóm department.
-- Nếu có 10 nhóm, mỗi lần sắp xếp sẽ nhỏ hơn 10 lần.
-- Ở PG 12 trở xuống — sắp xếp toàn bộ dữ liệu, ngay cả khi một phần đã được sắp xếp sẵn.
```

### Chi phí của Window Frame (Khung cửa sổ)

```sql
-- Frame rẻ: từ đầu đến dòng hiện tại (mặc định)
SUM(amount) OVER(ORDER BY date ROWS UNBOUNDED PRECEDING)
-- → Tính toán gia tăng (incremental), cơ sở dữ liệu không cần "trừ đi" các dòng đã hết hạn

-- Frame tốn kém: cửa sổ trượt (sliding window)
AVG(amount) OVER(ORDER BY date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)
-- → Với mỗi dòng, một cửa sổ gồm 7 phần tử được tính toán lại
-- → Yêu cầu quản lý trạng thái (thêm mới, loại bỏ cũ)
```

### Named Windows (Mệnh đề WINDOW)

```sql
-- DRY (Don't Repeat Yourself) cho window function
SELECT
    department,
    AVG(salary) OVER w as avg_sal,
    SUM(salary) OVER w as total_sal,
    COUNT(*) OVER w as emp_count
FROM employees
WINDOW w AS (PARTITION BY department ORDER BY hire_date);

-- → Một định nghĩa window duy nhất cho tất cả các hàm
-- → Ít lần sort hơn, thực thi nhanh hơn
```

### FILTER với Window Function

```sql
SELECT
    department,
    salary,
    SUM(salary) FILTER (WHERE status = 'ACTIVE')
        OVER(PARTITION BY department) as active_payroll
FROM employees;
```

### Các trường hợp đặc biệt (Edge Cases)

1. **Window rỗng**
   ```sql
   -- Không có PARTITION BY và ORDER BY
   SELECT name, salary,
          SUM(salary) OVER() as total_payroll  -- Tổng trên toàn bộ bảng
   FROM employees;
   ```

2. **NULL trong ORDER BY**
   ```sql
   -- NULL mặc định là LAST trong DESC, FIRST trong ASC
   SELECT name, salary,
          RANK() OVER(ORDER BY salary DESC NULLS LAST) as rank
   FROM employees;
   ```

3. **Window lồng nhau (Nested windows)** — KHÔNG ĐƯỢC PHÉP
   ```sql
   -- ❌ LỖI: các window function không thể lồng nhau
   SELECT AVG(SUM(amount) OVER(PARTITION BY user_id)) OVER() FROM orders;

   -- ✅ Giải pháp: CTE
   WITH user_totals AS (
       SELECT user_id, SUM(amount) as total
       FROM orders GROUP BY user_id
   )
   SELECT AVG(total) FROM user_totals;
   ```

### Tinh chỉnh hiệu năng (Performance Tuning)

**Giảm thiểu số lượng window duy nhất:**
```sql
-- ❌ Tốn kém: 3 PARTITION BY khác nhau → 3 lần sort
SELECT
    AVG(amount) OVER(PARTITION BY user_id) as u_avg,
    AVG(amount) OVER(PARTITION BY department) as d_avg,
    AVG(amount) OVER(PARTITION BY region) as r_avg
FROM orders;

-- ✅ Tốt hơn: cùng một PARTITION BY → 1 lần sort
SELECT
    AVG(amount) OVER(PARTITION BY user_id) as u_avg,
    SUM(amount) OVER(PARTITION BY user_id) as u_total,
    COUNT(*) OVER(PARTITION BY user_id) as u_count
FROM orders;
```

**Index cho WindowAgg:**
```sql
-- Index trên (các cột PARTITION BY, các cột ORDER BY)
CREATE INDEX idx_orders_user_date ON orders(user_id, created_at);

-- Truy vấn không cần Sort
SELECT user_id, created_at, amount,
       SUM(amount) OVER(PARTITION BY user_id ORDER BY created_at) as running_total
FROM orders;
-- Plan: WindowAgg → Index Scan (không cần Sort!)
```

### Kinh nghiệm Production

**Tình huống thực tế #1: Running Total cho báo cáo**
- Fintech: số dư hàng ngày cho 1 triệu giao dịch
- Truy vấn: 30 giây (Sort trên đĩa)
- Giải pháp:
  - Index trên `(account_id, date)`
  - `ROWS UNBOUNDED PRECEDING` (frame rẻ)
  - work_mem = 256MB
- Kết quả: 2 giây

**Tình huống thực tế #2: Window trộn lẫn giết chết hiệu năng**
- Phân tích dữ liệu: 5 window function với các PARTITION BY khác nhau
- Thời gian: 2 phút (5 lần sort!)
- Giải pháp: chia thành 2 CTE
- Kết quả: 15 giây

### Giám sát (Monitoring)

```sql
-- 1. Kiểm tra plan với window function
EXPLAIN (ANALYZE, BUFFERS)
SELECT ... OVER(PARTITION BY ... ORDER BY ...);
-- Tìm: WindowAgg → Sort (hoặc Index Scan nếu có index)

-- 2. Kiểm tra bộ nhớ cho Sort
EXPLAIN (ANALYZE)
SELECT ... OVER(...);
-- "external merge Disk: X kB" → tràn dữ liệu! Hãy tăng work_mem

-- 3. Tìm các truy vấn chậm có window
SELECT query, mean_exec_time
FROM pg_stat_statements
WHERE query LIKE '%OVER(%'
ORDER BY mean_exec_time DESC
LIMIT 10;
```

### Best Practices (Thực hành tốt nhất)

1. **Index** trên `(PARTITION BY, ORDER BY)` → không cần Sort
2. **ROWS** thay vì **RANGE** ở những nơi có thể (nhanh hơn)
3. **Mệnh đề WINDOW** để tái sử dụng định nghĩa window
4. **FILTER** cho việc tổng hợp có điều kiện
5. **EXCLUDE** cho thống kê phức tạp (PG 11+)
6. **Giảm thiểu** số lượng PARTITION BY duy nhất
7. **Incremental Sort (PG 13+)** sử dụng cùng với index
8. **Subquery/CTE** để lọc theo kết quả window

### Tóm tắt cho Senior

- Window function được tính toán **SAU** WHERE, GROUP BY, HAVING
- **ROWS** nhanh hơn RANGE, nhưng RANGE chính xác hơn khi có trùng lặp
- **Incremental Sort (PG 13+)** tiết kiệm chi phí sắp xếp một phần
- **EXCLUDE (PG 11+)** cho thống kê phức tạp
- **FILTER** được hỗ trợ trong window function
- **Chi phí Frame:** `UNBOUNDED PRECEDING` rẻ hơn so với cửa sổ trượt (sliding window)
- **Giảm thiểu** số lượng PARTITION BY duy nhất → ít giai đoạn Sort hơn
- **Index** trên `(PARTITION BY, ORDER BY)` → WindowAgg không cần Sort

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Window function: tính toán trên một nhóm dòng, KHÔNG làm gộp/mất dòng (khác với GROUP BY)
- Cú pháp: `FUNCTION() OVER(PARTITION BY ... ORDER BY ... ROWS/RANGE BETWEEN ...)`
- 3 loại: tổng hợp (SUM, AVG), xếp hạng (ROW_NUMBER, RANK), độ lệch (LAG, LEAD)
- ROWS = các dòng vật lý (nhanh hơn), RANGE = các giá trị logic (chính xác hơn khi có trùng lặp)
- GROUPS (PG 11+): gộp các dòng "ngang hàng" có cùng giá trị
- EXCLUDE (PG 11+): `EXCLUDE CURRENT ROW`, `EXCLUDE GROUP`, `EXCLUDE TIES`
- Lọc theo kết quả window → CHỈ trong subquery/CTE (window được tính toán SAU WHERE)
- Index trên `(PARTITION BY, ORDER BY)` → WindowAgg không cần Sort
- Incremental Sort (PG 13+): dữ liệu đã được sắp xếp một phần → chỉ sắp xếp phần còn lại
- Named windows (mệnh đề WINDOW): DRY cho window function
- Các window function không thể lồng nhau → cần dùng CTE

**Các câu hỏi phụ thường gặp:**
- "Tại sao bạn không thể lọc theo window function trong WHERE?" → Window được tính toán SAU WHERE
- "ROWS vs RANGE — nên chọn cái nào?" → ROWS nhanh hơn, RANGE chính xác hơn khi có trùng lặp
- "Làm sao để tăng tốc một window function?" → Index trên `(PARTITION BY, ORDER BY)`
- "Incremental Sort là gì?" → PG 13+: chỉ sắp xếp phần dữ liệu còn thiếu

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "Window function làm gộp/mất các dòng" (sai, đó là GROUP BY)
- ❌ "Bạn có thể lọc theo window function trong WHERE" (sai, được tính toán sau WHERE)
- ❌ "RANGE luôn luôn tốt hơn ROWS" (ROWS nhanh hơn, RANGE chỉ cần thiết khi có trùng lặp)
