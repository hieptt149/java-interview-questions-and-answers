# Can You Use == to Compare Strings? (Bạn có thể dùng == để so sánh String không?)

## 🟢 Junior Level

Về mặt kỹ thuật — **có**, nhưng trong 99% các trường hợp đây sẽ là một **lỗi**.

Toán tử `==` so sánh các **tham chiếu** (địa chỉ bộ nhớ), không phải nội dung chuỗi.

**Ví dụ về vấn đề:**
```java
String s1 = "Hello";
String s2 = new String("Hello");

System.out.println(s1 == s2);      // false — các object khác nhau!
System.out.println(s1.equals(s2)); // true — nội dung giống nhau
```

**Quy tắc:** Để so sánh nội dung chuỗi, luôn dùng `equals()`. Toán tử `==` — chỉ dùng để kiểm tra `null`.

**Khi nào == sẽ hoạt động:**
```java
String s1 = "Hello";
String s2 = "Hello";
System.out.println(s1 == s2); // true — cả hai đều từ String Pool, cùng object
```
Nhưng bạn không thể dựa vào điều này — dữ liệu từ DB hoặc file sẽ nằm trong heap thông thường, không phải trong pool.

## 🟡 Middle Level

### Khi Nào == Trả Về true

| Kịch bản       | Code                               | Kết quả ==          |
| -------------- | ---------------------------------- | ------------------ |
| Hai literal   | `"A" == "A"`                       | true (String Pool) |
| Literal + new  | `"A" == new String("A")`           | false              |
| new + new      | `new String("A") == new String("A")`| false             |
| Gán     | `s1 = s2; s1 == s2`                | true (cùng tham chiếu) |
| Sau intern() | `s1.intern() == s2.intern()`       | true               |

### Các Lỗi Điển Hình
1. **Lỗi:** `if (str == "admin")` — chỉ hoạt động nếu `"admin"` từ pool và `str` cũng vậy
   **Giải pháp:** `if ("admin".equals(str))` — an toàn và với hằng số ở bên trái (null-safe)

2. **Lỗi:** So sánh các chuỗi từ DB qua `==`
   **Giải pháp:** Các chuỗi từ ResultSet — luôn là các object mới. Chỉ dùng `equals()`

### Quy Tắc Thực Tế
```java
// XẤU
if (status == "ACTIVE") { ... }

// TỐT
if ("ACTIVE".equals(status)) { ... }

// TỐT HƠN (null-safe)
if (Objects.equals(status, "ACTIVE")) { ... }
```

## 🔴 Senior Level

### Hiện Thực Nội Bộ

**Toán tử ==:**
- Lệnh JVM: `if_acmpeq` (if address compare equal)
- So sánh các giá trị tham chiếu (địa chỉ 32/64-bit)
- Thời gian: O(1) — so sánh con trỏ đơn

**String.equals():**
```java
public boolean equals(Object anObject) {
    if (this == anObject) return true;       // Tối ưu hóa: kiểm tra identity
    if (anObject instanceof String another) {
        if (coder == another.coder) {         // Cùng encoding?
            return isLatin1()
                ? StringLatin1.equals(value, another.value)
                : StringUTF16.equals(value, another.value);
        }
    }
    return false;
}
```
- Kiểm tra identity (==) như một fast path
- Sau đó: kiểm tra coder, kiểm tra độ dài, so sánh từng ký tự
- Thời gian: O(n) — lặp qua từng ký tự

### Đánh Đổi Về Kiến Trúc (Trade-off)

**Khi == có thể hợp lý:**

Trong các hệ thống độ trễ cực thấp (HFT, trading), nơi mỗi nanosecond đều quan trọng:
```java
// Tất cả các chuỗi đã được intern trước
String eventType = parseEvent().intern();
if (eventType == ORDER_EVENT) { // O(1) thay vì O(n)
    processOrder();
}
```
- Lợi ích: 1 chu kỳ CPU vs n chu kỳ (độ dài chuỗi)
- Rủi ro: một chuỗi chưa intern — và logic bị hỏng

**Tại sao điều này gần như không bao giờ đáng để chấp nhận rủi ro:**
- `equals()` có một fast path `==` — với các object giống hệt nhau trả về ngay lập tức
- JVM inline `equals()` cho các chuỗi ngắn
- Branch prediction của CPU hoạt động tốt với việc so sánh từng ký tự

### Các Trường Hợp Biên

1. **Constant folding:** `"A" + "B" == "AB"` → `true` (compiler gộp cả hai thành `"AB"`)

2. **Nối chuỗi tại thời điểm chạy:**
   ```java
   String a = "A";
   String ab = a + "B";
   System.out.println(ab == "AB"); // false — nối chuỗi tại thời điểm chạy
   ```

3. **Các chuỗi đã intern:**
   ```java
   String s1 = new String("test").intern();
   String s2 = "test";
   System.out.println(s1 == s2); // true — cả hai đều từ pool
   ```

4. **String deduplication (G1 GC):** KHÔNG làm `==` trả về true! Deduplication kết hợp `byte[]`, nhưng các object `String` vẫn khác nhau.

### Hiệu Năng
| Thao tác                   | Thời gian                       | Khi nào nên dùng                            |
| --------------------------- | -------------------------- | -------------------------------------- |
| `==`                        | ~0.3ns (1 chu kỳ CPU)       | Chỉ sau khi `intern()` được đảm bảo       |
| `equals()` (giống hệt)      | ~0.3ns (fast path)         | Luôn luôn — fast path bắt được identity    |
| `equals()` (nội dung giống nhau)   | ~2-10ns (tùy độ dài)| Luôn luôn — lựa chọn đúng                 |

> `equals()` cho các chuỗi ngắn được JVM tối ưu hóa qua các lệnh SIMD (so sánh 8-16 byte mỗi chu kỳ đồng hồ), vì vậy sự khác biệt so với `==` là tối thiểu.

### Kinh Nghiệm Production
**Kịch bản:** Parser giao thức (10M message/giây):
- Lập trình viên dùng `==` để so sánh loại sự kiện sau `intern()`
- Sau một tháng: một phiên bản thư viện mới trả về các chuỗi chưa intern
- Bug: 0.01% message được xử lý sai → thiệt hại tài chính
- Sửa lỗi: `equals()` — overhead 5ns trên 10M = 50ms/giây (chấp nhận được)

### Giám Sát
```java
// Assert rằng các chuỗi đã được intern (trong test)
assert s1 == s2 : "Strings should be interned";

// JMH cho benchmark
@Benchmark
public boolean testEquals() { return s1.equals(s2); }

@Benchmark
public boolean testIdentity() { return s1 == s2; }
```

### Best Practices Cho Highload
- **Mặc định:** luôn `equals()` hoặc `Objects.equals()`
- **Kiểm tra null:** `"CONSTANT".equals(variable)` hoặc `Objects.equals(a, b)`
- **Trường hợp biên độ trễ thấp:** `==` chấp nhận được trong hai trường hợp: (1) kiểm tra null, (2) các chuỗi đã được đảm bảo intern.
  - Có các unit test xác minh đảm bảo này
  - Benchmark cho thấy sự khác biệt là quan trọng
- Cho việc so sánh với `null`: `==` là lựa chọn đúng

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- `==` so sánh tham chiếu (địa chỉ), `equals()` — nội dung
- `==` trả về true cho các literal (`"A" == "A"`), nhưng false cho `new String("A")`
- `equals()` có một fast path: nếu `==` là true — trả về ngay lập tức mà không cần so sánh ký tự
- Sau `intern()`, cả hai chuỗi đều từ pool — `==` trả về true
- String deduplication (G1 GC) KHÔNG làm `==` trả về true — các object khác nhau, chỉ có `byte[]` được chia sẻ
- Trong các hệ thống độ trễ cực thấp, `==` chấp nhận được cho các chuỗi đã đảm bảo intern

**Các câu hỏi phụ thường gặp:**
- **Khi nào `==` trả về true?** — Với các literal, các phép gán (`s1 = s2`), sau `intern()`, constant folding (`"A"+"B" == "AB"`).
- **Tại sao `equals()` có một fast path `==`?** — Nếu đó là cùng một object — không cần so sánh nội dung. Tiết kiệm thời gian cho các tham chiếu giống hệt nhau.
- **Bạn có thể dùng `==` sau `intern()` không?** — Có, nhưng nó rủi ro: một chuỗi chưa intern — và logic bị hỏng. `equals()` an toàn hơn.
- **Điều gì xảy ra với `nối chuỗi tại thời điểm chạy == literal`?** — `false`. `String a = "A"; (a + "B") == "AB"` — nối chuỗi tại thời điểm chạy tạo một object mới.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "`==` so sánh nội dung" — chỉ so sánh tham chiếu
- ❌ "`equals()` luôn chậm hơn `==`" — với các object giống hệt nhau, `equals()` = `==` qua fast path
- ❌ "String deduplication làm `==` trả về true" — không, các object vẫn khác nhau
- ❌ "`==` hoạt động sau khi nối chuỗi" — nối chuỗi tại thời điểm chạy tạo một object mới
