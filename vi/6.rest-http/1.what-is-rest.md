# What is REST? (REST là gì?)

## Junior Level

**REST** (Representational State Transfer) là một kiến trúc phần mềm để xây dựng các web service, được giới thiệu bởi Roy Fielding vào năm 2000.

Nó không phải là một protocol hoặc thư viện, mà là một tập hợp các hướng dẫn (constraints — ràng buộc). Một service chỉ có thể được gọi là RESTful nếu nó tuân thủ tất cả các ràng buộc này.

### Các nguyên tắc cốt lõi:
- **Resources (tài nguyên):** Mọi thứ trong REST đều là một tài nguyên, được định danh bằng URI (ví dụ: `/users/1`).
- **HTTP methods (các phương thức HTTP):** Các HTTP method tiêu chuẩn được dùng cho các hoạt động trên tài nguyên:
  - `GET` — truy lấy dữ liệu
  - `POST` — tạo dữ liệu
  - `PUT` — cập nhật dữ liệu
  - `DELETE` — xóa dữ liệu
- **Stateless (không trạng thái):** Mỗi request chứa tất cả các thông tin cần thiết. Server không lưu trữ trạng thái của client giữa các request.
- **Data format (định dạng dữ liệu):** Thường là JSON hoặc XML.

### Ví dụ REST API:
```
GET    /users        — lấy tất cả user
GET    /users/1      — lấy user với ID 1
POST   /users        — tạo user mới
PUT    /users/1      — cập nhật user với ID 1
DELETE /users/1      — xóa user với ID 1
```

// Lưu ý: tài nguyên được đặt tên ở số nhiều (`/users`),
// và một instance cụ thể được truy cập qua `/users/{id}`. Đây là một quy ước tiêu chuẩn.

### Sáu ràng buộc của REST:
1. **Client-Server** — tách biệt mối quan tâm giữa client và server
2. **Stateless** — mỗi request độc lập
3. **Cacheable (có thể cache)** — các response có thể được cache
4. **Layered System (hệ thống phân lớp)** — client không biết về các lớp trung gian (proxy, CDN)
5. **Uniform Interface (giao diện đồng nhất)** — tính đồng nhất của giao diện: bất kỳ tài nguyên nào cũng có sẵn thông qua cùng một tập hợp các hoạt động (GET/PUT/POST/DELETE), bất kể tài nguyên đó là gì.
6. **Code on Demand (mã theo yêu cầu)** (tùy chọn) — server có thể chuyển code thực thi được

### Khi nào KHÔNG nên dùng REST

1. **Streaming thời gian thực tần suất cao** — dùng WebSockets hoặc gRPC streams
2. **Microservices nội bộ với yêu cầu độ trễ chặt chẽ** — dùng gRPC (binary, serialization nhanh hơn)
3. **Truy vấn graph phức tạp** — dùng GraphQL (một request thay vì N REST call)

## Middle Level

### REST so với RESTful
- **REST** — một kiến trúc phần mềm
- **RESTful** — một cài đặt API cụ thể tuân thủ phong cách REST
- Hầu hết "REST API" thực tế chỉ là HTTP API vì chúng bỏ qua HATEOAS

Một HTTP API dùng HTTP làm transport nhưng có thể bỏ qua các ràng buộc REST
(ví dụ: không dùng HATEOAS hoặc vi phạm idempotency).
Một API RESTful tuân thủ tất cả 6 ràng buộc.

### Richardson Maturity Model

- **Level 0:** HTTP như transport (RPC qua HTTP)
- **Level 1:** Dùng resources (các URI riêng lẻ)
- **Level 2:** HTTP methods và status codes (tiêu chuẩn ngành)
- **Level 3:** HATEOAS (hypermedia as the engine of application state)

### Content Negotiation (thương lượng nội dung)

Server và client đồng ý về định dạng dữ liệu thông qua header:
- `Content-Type: application/json` — định dạng dữ liệu được gửi
- `Accept: application/json` — định dạng response được mong đợi

### Vary Header

Header `Vary` chỉ ra request header nào ảnh hưởng tới response:
```
Vary: Accept-Encoding, Authorization
```
Cấu hình sai có thể dẫn tới các vấn đề cache.

## Senior Level

### Những sắc thái kiến trúc

#### Vấn đề HATEOAS trong Microservices

HATEOAS yêu cầu server trả lại các link tới các hành động liên quan. Trong microservices điều này trở thành một vấn đề:
- Microservice không biết URL của API Gateway bên ngoài
- **Giải pháp:** Dùng `X-Forwarded-Host` header hoặc các thư viện đặc biệt (Spring HATEOAS)

#### Giới hạn chiều dài URI

Tiêu chuẩn không giới hạn chiều dài URI, nhưng hầu hết các server và proxy (Nginx, AWS ALB) giới hạn ở 8KB. Nếu bạn truyền những filter lớn trong một GET request, bạn có thể nhận `414 URI Too Long`.

#### HTTP Method Tunneling

Nếu firewall công ty chặn PUT/DELETE, dùng `X-HTTP-Method-Override: DELETE` bên trong một POST request.

### Hiệu suất và Highload

- **Thundering Herd Problem (bầy đàn gầm gừ):** Khi cache của một tài nguyên phổ biến hết hạn, hàng ngàn request có thể đánh vào DB cùng lúc
  - **Giải pháp:** "Soft expiry" hoặc khóa ở lớp caching (Redis/Memcached)
- **Binary Format (định dạng nhị phân):** Cho các client di động hoặc hệ thống highload, REST có thể phục vụ **MessagePack** hoặc **CBOR**, bảo tồn ngữ nghĩa HTTP

### Hiện đại (Java 21 / Spring Boot 3.3)

- **Virtual Threads (Project Loom):** Các REST controller có thể xử lý hàng chục ngàn kết nối mà không cần WebFlux (từ Java 21, 2023; trước đó reactive stack là cách duy nhất để xử lý hàng chục ngàn kết nối)
- **HTTP/3 (QUIC):** Loại bỏ Head-of-Line blocking ở mức TCP
- **Declarative Clients (client khai báo):** `@HttpExchange` cho phép mô tả hợp đồng API trong một interface
- **Problem Details (RFC 9457):** JSON tiêu chuẩn với các trường `type`, `title`, `status`, `detail`, `instance` cho việc xử lý lỗi

## Interview Cheat Sheet

**Cần phải biết:**
- REST là một kiến trúc phần mềm, được giới thiệu bởi Roy Fielding vào năm 2000, không phải một protocol
- 6 ràng buộc REST: Client-Server, Stateless, Cacheable, Layered System, Uniform Interface, Code on Demand
- API RESTful tuân thủ tất cả 6 ràng buộc; hầu hết "REST API" chỉ là HTTP API mà không có HATEOAS
- Richardson Maturity Model: Level 0-3, trong đó Level 2 (HTTP Verbs + Status Codes) là tiêu chuẩn ngành
- REST không phù hợp cho streaming thời gian thực (dùng WebSockets/gRPC) và truy vấn graph phức tạp (dùng GraphQL)
- Content Negotiation hoạt động thông qua Content-Type và Accept header
- HTTP/3 (QUIC) loại bỏ Head-of-Line blocking ở mức TCP
- Virtual Threads trong Java 21 cho phép xử lý hàng chục ngàn kết nối mà không cần reactive stack

**Các câu hỏi phụ thường gặp:**
- *Sự khác nhau giữa REST và RESTful là gì?* — REST là một phong cách, RESTful là một cài đặt tuân thủ tất cả các ràng buộc REST.
- *Uniform Interface là gì?* — Tính đồng nhất: bất kỳ tài nguyên nào cũng có sẵn thông qua cùng một tập hợp các hoạt động (GET/PUT/POST/DELETE).
- *Mức Richardson maturity nào là tiêu chuẩn ngành?* — Level 2: HTTP methods và status codes.
- *Khi nào REST là lựa chọn tồi?* — Streaming thời gian thực, microservices nội bộ với yêu cầu độ trễ chặt chẽ, truy vấn graph.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "REST là một protocol" — nó là một kiến trúc phần mềm, không phải protocol.
- "Bất kỳ HTTP API nào cũng là REST" — REST yêu cầu tất cả 6 ràng buộc bao gồm HATEOAS.
- "GET có thể được dùng để xóa" — GET phải là safe, không được thay đổi trạng thái.
- "HATEOAS là bắt buộc trong mọi project" — cho các microservices nội bộ và ứng dụng di động, HATEOAS là quá mức.
