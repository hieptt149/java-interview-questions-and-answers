# What does Propagation.NESTED do (Propagation.NESTED làm gì)

## 🟢 Junior Level

**Propagation.NESTED** là một loại propagation transaction trong Spring tạo ra một transaction "lồng nhau" bên trong một transaction đã tồn tại. Nếu transaction bên ngoài rollback, transaction lồng nhau cũng rollback. Nhưng nếu transaction lồng nhau rollback — transaction bên ngoài vẫn có thể tiếp tục hoạt động.

**Ví dụ minh họa đơn giản:** Bạn đang viết một tài liệu (transaction bên ngoài). Định kỳ bạn "lưu một phiên bản" (savepoint). Nếu một chỉnh sửa mới làm hỏng tài liệu, bạn có thể quay lại phiên bản gần nhất (savepoint) mà không mất tất cả công việc trước đó. Nhưng nếu bạn quyết định vứt bỏ toàn bộ tài liệu — tất cả các phiên bản cũng biến mất.

**Ví dụ SQL (JDBC Savepoint):**

```java
@Service
public class BatchImportService {

    @Autowired private NestedImportService nestedImportService;

    @Transactional
    public void importAll(List<Data> dataList) {
        for (Data data : dataList) {
            try {
                // Mỗi bản ghi — một "mini-transaction" lồng nhau
                nestedImportService.importOne(data);
            } catch (Exception e) {
                // Chỉ bản ghi này rollback, các bản ghi khác tiếp tục
                log.warn("Failed to import: {}", data.getId());
            }
        }
        // Cuối cùng — một COMMIT chung cho tất cả các bản ghi thành công
    }
}

@Service
public class NestedImportService {

    @Transactional(propagation = Propagation.NESTED)
    public void importOne(Data data) {
        repo.save(data);
        // Nếu có exception → rollback về savepoint (không phải toàn bộ batch)
    }
}
```

**Khác biệt then chốt so với REQUIRES_NEW:**
- **NESTED:** Một COMMIT duy nhất ở cuối cùng, nested là một savepoint trong cùng transaction
- **REQUIRES_NEW:** Hai COMMIT độc lập, transaction bên trong commit ngay lập tức

**Khi nào nên dùng:**
- Xử lý dữ liệu batch với thất bại từng phần có thể chấp nhận được
- Khi bạn cần "cứu" một phần công việc, nhưng commit cuối cùng phải nguyên tử

## 🟡 Middle Level

### Cách Nó Hoạt Động Nội Bộ

Spring hiện thực NESTED thông qua **JDBC Savepoint** (không phải thông qua các transaction mới):

```
Lời gọi: outerMethod() → innerMethod(NESTED)

1. Spring kiểm tra: có transaction đang hoạt động không? → Có
2. Spring tạo JDBC Savepoint:

   Connection conn = dataSource.getConnection();
   Savepoint sp = conn.setSavepoint("NESTED_SAVEPOINT_1");

3. innerMethod() thực thi
4. Nếu thành công → savepoint được giải phóng (nhưng KHÔNG commit!)
5. Nếu có exception → conn.rollback(sp) → rollback về savepoint
6. Cuối outerMethod() → một conn.commit() chung
```

**Quan trọng:** NESTED chỉ hoạt động với `DataSourceTransactionManager` và `JpaTransactionManager`. Nó KHÔNG hoạt động với JTA ở chế độ savepoint. JTA (Java Transaction API) — API cho các transaction phân tán trải rộng nhiều DB hoặc hệ thống. Spring tự động fallback về hành vi của REQUIRES_NEW. Vì vậy với JTA, tốt hơn nên chỉ định REQUIRES_NEW một cách tường minh.

### Ứng Dụng Thực Tế

**Kịch bản 1: Import Batch Với Khả Năng Chịu Thất Bại Từng Phần**
```java
@Service
public class CsvImportService {

    @Autowired private RowImportService rowImportService;

    @Transactional
    public ImportResult importCsv(MultipartFile file) {
        int success = 0;
        int failed = 0;

        List<String> rows = parseCsv(file);
        for (String row : rows) {
            try {
                rowImportService.importRow(row);  // NESTED
                success++;
            } catch (ValidationException e) {
                failed++;
                // Dòng này đã rollback về savepoint, tiếp tục
            }
        }
        return new ImportResult(success, failed);
        // COMMIT — tất cả các dòng thành công được lưu
    }
}

@Service
public class RowImportService {

    @Transactional(propagation = Propagation.NESTED)
    public void importRow(String row) {
        Data data = validateAndParse(row);  // có thể ném ValidationException
        repo.save(data);
    }
}
```

**Kịch bản 2: Orchestration Với Bù Trừ (Compensation)**
```java
@Service
public class OrderOrchestrator {

    @Autowired private InventoryService inventoryService;
    @Autowired private PaymentService paymentService;
    @Autowired private NotificationService notificationService;

    @Transactional
    public OrderResult createOrder(Order order) {
        try {
            inventoryService.reserve(order.getItems());     // NESTED
        } catch (Exception e) {
            return OrderResult.failed("No stock");
        }

        try {
            paymentService.charge(order.getTotal());        // NESTED
        } catch (Exception e) {
            // Payment thất bại — việc đặt trước cũng rollback (transaction chung)
            throw new OrderException("Payment failed", e);
        }

        // Tất cả thành công — thông báo (REQUIRED, một phần của transaction chung)
        notificationService.sendOrderConfirmation(order);

        return OrderResult.success();
        // COMMIT — tất cả các thay đổi nguyên tử
    }
}
```

### Các Lỗi Điển Hình

| Lỗi                                    | Hậu quả                                          | Giải pháp                                                  |
| ------------------------------------------ | ---------------------------------------------------- | ----------------------------------------------------------------------- |
| NESTED không có transaction bên ngoài đang hoạt động    | Hành xử như REQUIRED (tạo mới)                  | Đảm bảo method bên ngoài là @Transactional                     |
| NESTED + L1 cache của Hibernate không nhất quán  | Entity cũ (stale) sau savepoint rollback              | `em.flush()` + `em.clear()` sau khi rollback                |
| NESTED với JTA                            | Không được hỗ trợ — fallback về REQUIRES_NEW             | Dùng REQUIRES_NEW tường minh cho JTA                       |
| Giả định NESTED = REQUIRES_NEW             | Các thay đổi bên trong KHÔNG hiển thị với người khác cho đến khi commit chung | Hiểu rõ: NESTED = savepoint, REQUIRES_NEW = tx mới  |
| Transaction dài với nhiều savepoint      | Tích lũy undo log, áp lực bộ nhớ               | Giới hạn số lượng lời gọi lồng nhau                              |

### So Sánh: NESTED vs REQUIRES_NEW

| Đặc điểm              | NESTED                         | REQUIRES_NEW                   |
| --------------------------- | ------------------------------ | ------------------------------ |
| Transaction vật lý       | 1                              | 2                              |
| Cơ chế                   | JDBC Savepoint                 | Suspend + transaction mới      |
| Commit bên trong                | Không (chỉ release savepoint)    | Có, ngay lập tức                 |
| Rollback bên trong                | Về savepoint                   | Toàn bộ tx bên trong                  |
| Visibility dữ liệu với tx khác | Chỉ sau khi commit chung       | Ngay sau khi tx bên trong commit |
| Rollback tx bên ngoài           | Rollback cả bên trong              | Không ảnh hưởng bên trong               |
| Hỗ trợ JTA                 | **Không**                         | Có                             |
| L1 cache Hibernate          | Có vấn đề khi rollback             | Không có vấn đề               |
| Sử dụng connection            | 1 connection                   | 2 connection (suspend + mới)  |
| Overhead                    | Thấp (~1-3ms)                   | Trung bình (~5-15ms)           |

### Khi Nào KHÔNG Nên Dùng NESTED

- **JTA / các transaction phân tán** — không được hỗ trợ
- **Khi transaction bên trong phải commit độc lập** — dùng REQUIRES_NEW
- **Với Hibernate mà không flush/clear** — nguy cơ L1 cache không nhất quán
- **Cho audit** — audit thường cần độc lập với tx bên ngoài, tốt hơn nên dùng REQUIRES_NEW

### Khi Nào NESTED vs REQUIRES_NEW

- **Audit/logging** = REQUIRES_NEW (dữ liệu phải tồn tại ngay cả khi tx bên ngoài rollback)
- **Xử lý batch với thất bại từng phần** = NESTED (một commit duy nhất, một connection)
- **Transaction phân tán** = REQUIRES_NEW (NESTED không hỗ trợ JTA)
- **Cần thấy dữ liệu bên trong từ tx khác** = REQUIRES_NEW (NESTED chỉ hiển thị sau commit chung)

## 🔴 Senior Level

### Hiện Thực Nội Bộ: Cơ Chế Savepoint Và Tích Hợp Với Spring

#### JdbcTransactionObjectSupport — Quản Lý Savepoint

```java
// org.springframework.jdbc.datasource.JdbcTransactionObjectSupport
// Spring Framework 6.x

public class JdbcTransactionObjectSupport implements SavepointManager, SmartTransactionObject {

    private ConnectionHolder connectionHolder;
    private Savepoint currentSavepoint;
    private Integer previousIsolationLevel;
    private boolean rollbackOnly = false;
    private boolean savepointAllowed = false;

    @Override
    public Object createSavepoint(String name) throws TransactionException {
        try {
            if (!this.savepointAllowed) {
                throw new NestedTransactionNotSupportedException(
                    "Cannot create savepoint — no active transaction or not supported");
            }
            // JDBC 3.0 API
            this.currentSavepoint = getConnection().setSavepoint(name);
            return this.currentSavepoint;
        } catch (SQLException ex) {
            throw new CannotCreateSavepointException("Could not create JDBC savepoint", ex);
        }
    }

    @Override
    public void rollbackToSavepoint(Object savepoint) throws TransactionException {
        try {
            Savepoint sp = (Savepoint) savepoint;
            // JDBC rollback về savepoint
            getConnection().rollback(sp);
            // Quan trọng: connection vẫn hoạt động, transaction tiếp tục
            this.currentSavepoint = null;
        } catch (SQLException ex) {
            throw new TransactionSystemException("Could not roll back to JDBC savepoint", ex);
        }
    }

    @Override
    public void releaseSavepoint(Object savepoint) throws TransactionException {
        try {
            Savepoint sp = (Savepoint) savepoint;
            getConnection().releaseSavepoint(sp);
            // Không nghiêm trọng nếu DB tự động giải phóng khi commit (MySQL)
        } catch (SQLException ex) {
            // Log nhưng không fail — một số cơ sở dữ liệu tự động giải phóng savepoint
        }
    }
}
```

#### AbstractPlatformTransactionManager — Xử Lý NESTED

```java
// Đoạn code then chốt từ handleExistingTransaction()

case PROPAGATION_NESTED:
    if (!isNestedTransactionAllowed()) {
        throw new NestedTransactionNotSupportedException(
            "Transaction manager does not allow nested transactions");
    }

    if (useSavepointForNestedTransaction()) {
        // DataSourceTransactionManager, JpaTransactionManager → savepoint
        DefaultTransactionStatus status =
            prepareTransactionStatus(definition, transaction, false, false, debugEnabled, null);

        // Tạo savepoint
        status.createAndHoldSavepoint();

        return status;
    } else {
        // JTA → không hỗ trợ savepoint → fallback về REQUIRES_NEW
        SuspendedResourcesHolder suspendedResources = suspend(transaction);
        // ... tạo một transaction mới
    }
```

#### Quyết Định useSavepointForNestedTransaction()

```java
// DataSourceTransactionManager → true (hỗ trợ savepoint)
// JpaTransactionManager → true (ủy quyền cho JDBC)
// JtaTransactionManager → false (JTA không hỗ trợ savepoint)
// HibernateTransactionManager → true (thông qua JDBC connection)

protected boolean useSavepointForNestedTransaction() {
    return (getDataSource() != null);  // Đơn giản hóa
}
```

### Hiện Thực Savepoint Trong Các DB Khác Nhau

**PostgreSQL:**
```sql
BEGIN;
  SAVEPOINT sp1;
  INSERT INTO orders (id, amount) VALUES (1, 100);

  -- Rollback về savepoint
  ROLLBACK TO SAVEPOINT sp1;
  -- orders trống — insert bị hoàn tác, nhưng transaction vẫn hoạt động

  INSERT INTO orders (id, amount) VALUES (2, 200);
COMMIT;
-- orders: (2, 200)

-- Savepoint của PostgreSQL:
-- - Được lưu trong bộ nhớ (không trên đĩa)
-- - Có thể lồng nhau (savepoint trong savepoint)
-- - Tự động giải phóng khi commit
```

**MySQL/InnoDB:**
```sql
START TRANSACTION;
  SAVEPOINT sp1;
  INSERT INTO orders VALUES (1, 100);

  ROLLBACK TO SAVEPOINT sp1;
  -- Trong MySQL: tự động giải phóng savepoint sau khi rollback!
  -- ROLLBACK TO SAVEPOINT sp1 lặp lại → ERROR

  INSERT INTO orders VALUES (2, 200);
COMMIT;

-- Savepoint của MySQL:
-- - Tự động giải phóng sau ROLLBACK TO (không thể tái sử dụng)
-- - Không được ghi vào binlog (an toàn với statement-based replication)
-- - Hành vi này ổn định trên tất cả các phiên bản được hỗ trợ MySQL 5.7+ và PostgreSQL 9+.
--   Spring sinh các tên savepoint duy nhất kể từ phiên bản 3.x.
```

**Oracle:**
```sql
-- Savepoint của Oracle:
-- - Có thể tái sử dụng tên (khác với MySQL)
-- - Được lưu trong PGA (bộ nhớ)
-- - Hỗ trợ savepoint lồng nhau
```

### Đánh Đổi Về Kiến Trúc (Trade-off)

**Cách A: NESTED (savepoint)**
- ✅ Ưu điểm: Một connection, một commit duy nhất, rollback từng phần, overhead thấp hơn REQUIRES_NEW
- ❌ Nhược điểm: Không hoạt động với JTA, vấn đề L1 cache Hibernate, hạn chế của savepoint (MySQL tự động giải phóng), không có commit độc lập
- Phù hợp cho: xử lý batch, các thao tác hàng loạt, các pattern bù trừ (compensation) trong cùng một DB

**Cách B: REQUIRES_NEW**
- ✅ Ưu điểm: Isolation đầy đủ, hoạt động với JTA, commit độc lập, semantics Hibernate sạch sẽ
- ❌ Nhược điểm: Hai connection, overhead suspend/resume, nguy cơ không nhất quán (bên trong đã commit, bên ngoài rollback)
- Phù hợp cho: audit, thông báo, các thao tác đa cơ sở dữ liệu

**Cách C: Quản Lý Savepoint Thủ Công**
```java
@Transactional
public void manualSavepoint() {
    Connection conn = DataSourceUtils.getConnection(dataSource);
    Savepoint sp = conn.setSavepoint("my_sp");

    try {
        // logic nghiệp vụ
    } catch (Exception e) {
        conn.rollback(sp);  // Rollback thủ công
    }
    // ...
}
```
- ✅ Ưu điểm: Kiểm soát đầy đủ, có thể tích hợp với bất kỳ logic nào
- ❌ Nhược điểm: Boilerplate, dễ mắc lỗi, bỏ qua quản lý transaction của Spring
- Phù hợp cho: các kịch bản phức tạp mà propagation của Spring không đủ

### Các Trường Hợp Biên Và Đặc Biệt

**1. Tự Động Giải Phóng Savepoint Trong MySQL:**
```java
@Transactional
public void mysqlSavepointIssue() {
    nestedService.doWork();  // NESTED → SAVEPOINT sp1
    // Nếu rollback về sp1 bên trong doWork() → MySQL tự động giải phóng sp1

    nestedService.doWork2();  // NESTED → cố tạo SAVEPOINT sp1 lần nữa
    // PostgreSQL: OK (savepoint có thể tái sử dụng)
    // MySQL: OK (tên mới sp2)

    // Nhưng nếu Spring tái sử dụng cùng tên → MySQL ERROR:
    // "Savepoint 'NESTED_SAVEPOINT_1' does not exist"
}
```

**Spring giải quyết vấn đề này bằng cách sinh các tên duy nhất:**
```java
// DefaultTransactionStatus
private String generateSavepointName() {
    return "NESTED_SAVEPOINT_" + System.identityHashCode(this);
}
```

**2. L1 Cache Của Hibernate Và Savepoint Rollback:**
```java
@Transactional
public void hibernateSavepointIssue() {
    Entity e1 = new Entity("first");
    em.persist(e1);
    em.flush();  // INSERT vào DB

    try {
        nestedService.failOperation();  // NESTED → ném exception
    } catch (Exception ex) {
        // Savepoint rollback: DB đã rollback INSERT
        // NHƯNG: L1 cache của Hibernate (PersistenceContext) vẫn chứa e1!
        // e1.status = MANAGED, nhưng không có dòng trong DB
    }

    // Khi flush/commit:
    // Hibernate có thể cố UPDATE e1 → ERROR (dòng không tồn tại)
    // Hoặc: Hibernate dirty checking → INSERT e1 lần nữa → trùng lặp
}
```

**Giải pháp:**
```java
@Transactional(propagation = Propagation.NESTED)
public void failOperation() {
    Entity e = new Entity("will-fail");
    em.persist(e);
    em.flush();
    // Sau flush, nếu có exception → savepoint rollback xóa INSERT khỏi DB
    // Nhưng L1 cache vẫn chứa e → cần em.clear()
    throw new RuntimeException("fail");
}

// Method bên ngoài:
@Transactional
public void safeNestedOperation() {
    try {
        nestedService.failOperation();
    } catch (Exception e) {
        em.clear();  // Xóa L1 cache khỏi các entity có thể đã bị rollback
    }
}

Từng bước: (1) em.persist() đăng ký entity vào PersistenceContext với trạng thái MANAGED.
(2) em.flush() gửi INSERT đến DB. (3) Exception kích hoạt savepoint rollback —
INSERT bị xóa khỏi DB. (4) Nhưng PersistenceContext vẫn chứa entity với
trạng thái MANAGED. (5) Khi commit cuối cùng, Hibernate cố flush lại → lỗi.
em.clear() giải quyết vấn đề bằng cách loại bỏ toàn bộ PersistenceContext.
```

**3. Savepoint Lồng Nhau (savepoint trong savepoint):**
```java
@Transactional
public void deeplyNested() {
    level1Service.doWork();  // NESTED → SAVEPOINT sp1

    try {
        level2Service.doWork();  // NESTED → SAVEPOINT sp2 (bên trong sp1)
    } catch (Exception e) {
        // Rollback về sp2 — sp1 vẫn hoạt động
    }

    try {
        level3Service.doWork();  // NESTED → SAVEPOINT sp3
    } catch (Exception e) {
        // Rollback về sp3 — sp1 và sp2 (nếu chưa giải phóng) vẫn hoạt động
    }
}

// Giới hạn: PostgreSQL — savepoint lồng nhau không giới hạn
// MySQL — không giới hạn, nhưng mỗi rollback tự động giải phóng
// Oracle — không giới hạn
```

**4. Savepoint Và Sequence (PostgreSQL):**
```sql
BEGIN;
  SAVEPOINT sp1;
  SELECT nextval('my_seq');  -- trả về 1
  ROLLBACK TO SAVEPOINT sp1;

  -- Giá trị sequence KHÔNG bị rollback!
  SELECT nextval('my_seq');  -- trả về 2, không phải 1

  -- Điều này vì sequence là một cấu trúc phi-transactional
```

**Tác động:** Nếu logic nghiệp vụ phụ thuộc vào giá trị sequence bên trong các transaction lồng nhau, sẽ có các khoảng trống (gap).

**5. Savepoint Và Bảng Tạm:**
```sql
-- PostgreSQL: các bảng tạm KHÔNG rollback về savepoint
BEGIN;
  CREATE TEMP TABLE tmp_data (id INT);
  SAVEPOINT sp1;
  INSERT INTO tmp_data VALUES (1);
  ROLLBACK TO SAVEPOINT sp1;

  SELECT * FROM tmp_data;  -- TRỐNG — rollback đã hoạt động

  -- NHƯNG: DROP TEMP TABLE KHÔNG rollback
  SAVEPOINT sp2;
  DROP TABLE tmp_data;
  ROLLBACK TO SAVEPOINT sp2;

  SELECT * FROM tmp_data;  -- ERROR: bảng không tồn tại!
```

**6. Savepoint Và Trigger:**
```sql
-- Nếu trigger ném exception bên trong transaction lồng nhau:
CREATE TRIGGER order_before_insert
    BEFORE INSERT ON orders
    FOR EACH ROW
    EXECUTE FUNCTION validate_order();

-- Nếu trigger thất bại:
-- Savepoint rollback hoàn tác INSERT
-- NHƯNG: các side-effect của trigger (ví dụ: sequence nextval) không bị rollback
```

### Tác Động Đến Hiệu Năng

| Thao tác             | Latency                               | Tác động Throughput         |
| --------------------- | ------------------------------------- | ------------------------- |
| Tạo savepoint    | ~0.1ms                                | Không đáng kể                |
| Giải phóng savepoint     | ~0.05ms                               | Không đáng kể                |
| Rollback về savepoint | ~0.5-2ms (tùy số lượng thay đổi)    | Thấp                       |
| 10 savepoint lồng nhau  | ~1-3ms tổng cộng                          | -2-5%                     |
| 100 savepoint lồng nhau | ~10-30ms                              | -10-15% (tăng undo log) |

**Các con số cụ thể (Spring Boot 3.x, PostgreSQL 15, HikariCP pool=50):**
- Chỉ REQUIRED: ~25,000 TPS
- REQUIRED + 1 NESTED: ~24,000 TPS (overhead savepoint ~4%)
- REQUIRED + 10 NESTED: ~22,000 TPS (overhead savepoint tích lũy)
- REQUIRED + 1 REQUIRES_NEW: ~20,000 TPS (suspend/resume ~20%)

**Overhead bộ nhớ:**
- Object savepoint: ~500 byte (JDBC) + trạng thái phía DB
- PostgreSQL: savepoint trong shared memory, ~1KB mỗi savepoint
- MySQL: savepoint trong struct trx của InnoDB, ~2KB mỗi savepoint
- Giữ undo log: với các transaction dài và savepoint — dead tuple tích lũy

### Tác Động Đến Bộ Nhớ

- **JDBC Savepoint:** ~500 byte mỗi object savepoint (phía client)
- **Trạng thái savepoint phía DB:** 1-2KB mỗi savepoint trong shared memory
- **Undo log / dead tuple:** Mỗi thao tác bên trong savepoint tạo các bản ghi undo. Khi rollback — các bản ghi undo không được giải phóng cho đến khi commit chính.
- **L1 cache Hibernate:** Có thể chứa các entity cũ (stale) sau savepoint rollback — lên đến vài MB cho các thao tác lớn.
- **Trạng thái connection holder:** Spring lưu tham chiếu savepoint trong TransactionStatus — ~200 byte mỗi cấp lồng nhau.

### Các Khía Cạnh Concurrency

```
Mô hình concurrency của NESTED:

Thread-1: outerMethod(REQUIRED)
  → nestedService.doWork(NESTED) → savepoint sp1
    → Nếu có exception: rollback về sp1 (chỉ Thread-1 bị ảnh hưởng)
  → nestedService.doWork2(NESTED) → savepoint sp2
    → commit sp2 (giải phóng)
  → commit bên ngoài (commit tất cả)

Thread-2: outerMethod(REQUIRED)
  → nestedService.doWork(NESTED) → savepoint sp3

Thread-1 và Thread-2 dùng các connection khác nhau → độc lập
Các savepoint chỉ hiển thị trong transaction của riêng chúng
```

**Hành vi Savepoint và lock:**
```sql
-- Các row lock lấy bên trong savepoint được giải phóng khi rollback về savepoint
BEGIN;
  SAVEPOINT sp1;
  UPDATE accounts SET balance = 100 WHERE id = 1;  -- row lock được lấy
  ROLLBACK TO SAVEPOINT sp1;
  -- Row lock được giải phóng!

-- NHƯNG: DDL bên trong savepoint (PostgreSQL):
  SAVEPOINT sp2;
  ALTER TABLE orders ADD COLUMN new_col TEXT;  -- DDL
  ROLLBACK TO SAVEPOINT sp2;
  -- DDL KHÔNG rollback về savepoint! (DDL commit ngầm định)
```

### Tình Huống Thực Tế Trong Production

**Tình huống:** Nền tảng tổng hợp log (2024), Spring Boot 3.1, PostgreSQL, ingest 50,000 sự kiện/giây.

**Vấn đề:** Trong lúc insert log theo batch (1000 sự kiện/batch), một sự kiện dị dạng gây rollback toàn bộ batch. Throughput giảm 30% do phải xử lý lại.

**Code gốc:**
```java
@Transactional
public void ingestBatch(List<LogEvent> events) {
    for (LogEvent event : events) {
        LogEvent validated = validate(event);  // Có thể ném ValidationException
        logRepo.save(validated);
    }
    // Một ValidationException → rollback toàn bộ batch (mất 1000 sự kiện)
}
```

**Thử nghiệm #1: try-catch bên trong REQUIRED**
```java
@Transactional
public void ingestBatch(List<LogEvent> events) {
    for (LogEvent event : events) {
        try {
            LogEvent validated = validate(event);
            logRepo.save(validated);
        } catch (ValidationException e) {
            failedCount++;
            // Vấn đề: transaction bị đánh dấu rollback-only!
            // Khi commit: UnexpectedRollingBackException
        }
    }
}
```

**Giải pháp cuối cùng: NESTED**
```java
@Autowired private EventImportService eventImportService;

@Transactional
public void ingestBatch(List<LogEvent> events) {
    int success = 0, failed = 0;

    for (LogEvent event : events) {
        try {
            eventImportService.importEvent(event);  // NESTED
            success++;
        } catch (ValidationException e) {
            failed++;
            // Chỉ sự kiện này rollback về savepoint
        }
    }

    metrics.record(success, failed);
    // COMMIT — tất cả các sự kiện thành công được lưu
}

@Service
public class EventImportService {

    @Transactional(propagation = Propagation.NESTED)
    public void importEvent(LogEvent event) {
        LogEvent validated = validate(event);  // ValidationException → savepoint rollback
        logRepo.save(validated);
        // Không có exception → savepoint được giải phóng
    }
}
```

**Kết quả:**
- Tỷ lệ hoàn thành batch: từ 70% (30% rollback) lên 99.5%
- Throughput: từ 35,000 lên 48,000 sự kiện/giây (+37%)
- Latency p99: từ 200ms xuống 50ms (ít retry hơn)
- Đánh đổi: overhead ~3% từ quản lý savepoint

### Giám Sát Và Chẩn Đoán

**Theo dõi việc tạo và rollback savepoint:**
```java
@Component
public class SavepointMonitor implements TransactionSynchronization {

    private final MeterRegistry registry;

    @Override
    public void beforeCommit(boolean readOnly) {
        // Theo dõi việc sử dụng savepoint
    }

    @Override
    public void afterCompletion(int status) {
        if (status == STATUS_ROLLED_BACK) {
            Counter.builder("transaction.savepoint.rollback")
                .increment();
        }
    }
}

// Đăng ký
TransactionSynchronizationManager.registerSynchronization(new SavepointMonitor(registry));
```

### Best Practices Cho Highload

1. **Giới hạn độ sâu lồng nhau** — không quá 10-20 savepoint lồng nhau mỗi transaction.
2. **Chỉ dùng NESTED cho khả năng chịu thất bại từng phần** — không dùng cho logic nghiệp vụ.
3. **Flush + Clear sau khi rollback nested với Hibernate:**
   ```java
   try {
       nestedService.doWork();
   } catch (Exception e) {
       em.clear();  // Bắt buộc sau savepoint rollback
   }
   ```
4. **Tránh phụ thuộc sequence bên trong các transaction lồng nhau** — các khoảng trống là không thể tránh khỏi.
5. **Giám sát tỷ lệ rollback savepoint** — tỷ lệ cao cho thấy vấn đề validation, không phải vấn đề transaction.

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- NESTED tạo một JDBC savepoint trong transaction đã tồn tại — KHÔNG phải một transaction vật lý mới
- Nếu tx bên ngoài rollback → tx nested cũng rollback. Nếu tx nested rollback → tx bên ngoài có thể tiếp tục
- Khác biệt then chốt so với REQUIRES_NEW: NESTED = một commit ở cuối, REQUIRES_NEW = commit độc lập
- NESTED không hoạt động với JTA — Spring fallback về REQUIRES_NEW
- L1 cache của Hibernate KHÔNG bị rollback cùng savepoint — cần em.flush() + em.clear()
- Savepoint tùy thuộc từng DB: MySQL tự động giải phóng sau rollback, PostgreSQL cho phép tái sử dụng

**Các câu hỏi phụ thường gặp:**
- NESTED vs REQUIRES_NEW? — NESTED: savepoint, một commit duy nhất; REQUIRES_NEW: suspend + tx mới, commit độc lập
- Điều gì xảy ra nếu tx bên ngoài rollback với NESTED? — Mọi thứ rollback (kể cả savepoint)
- NESTED có hoạt động với JTA không? — Không, JTA không hỗ trợ savepoint, fallback về REQUIRES_NEW
- Tại sao L1 cache của Hibernate là vấn đề với NESTED? — PersistenceContext không rollback cùng savepoint

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "NESTED tạo một transaction mới" — nó tạo một savepoint trong cùng transaction
- "NESTED hoạt động với JTA" — JTA không hỗ trợ savepoint
- "Dữ liệu nested hiển thị ngay với các transaction khác" — chỉ hiển thị sau commit chung
