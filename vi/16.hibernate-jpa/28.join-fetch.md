# How to Use JOIN FETCH to Solve the N+1 Problem (Cách dùng JOIN FETCH để giải quyết N+1 problem)

## Overview

`JOIN FETCH` là cách phổ biến nhất để giải quyết N+1 problem trong JPA. Nó cho phép tải các entity liên quan trong một truy vấn SQL duy nhất thay vì N truy vấn riêng biệt.

---

## Junior Level

### JOIN FETCH Là Gì

`JOIN FETCH` - tải các entity liên quan **trong một truy vấn** thay vì N+1.

```java
// N+1 problem:
List<Order> orders = em.createQuery("SELECT o FROM Order o", Order.class)
    .getResultList();  // 1 truy vấn
for (Order o : orders) {
    o.getItems().size();  // N truy vấn
}
// 100 order -> 101 truy vấn

// Giải pháp với JOIN FETCH:
List<Order> orders = em.createQuery(
    "SELECT DISTINCT o FROM Order o JOIN FETCH o.items", Order.class)
    .getResultList();  // 1 truy vấn với JOIN!
// 100 order -> 1 truy vấn
```

### Cú Pháp

```java
// Một JOIN FETCH
@Query("SELECT DISTINCT o FROM Order o JOIN FETCH o.items")
List<Order> findAllWithItems();

// Nhiều JOIN FETCH
@Query("SELECT DISTINCT o FROM Order o " +
       "JOIN FETCH o.items i " +
       "JOIN FETCH o.user u")
List<Order> findAllWithItemsAndUser();
```

### Tại Sao Cần DISTINCT

```java
// JOIN có thể trùng lặp Order (một cho mỗi OrderItem)
// DISTINCT loại bỏ trùng lặp trong bộ nhớ
SELECT DISTINCT o FROM Order o JOIN FETCH o.items

// Không có DISTINCT:
// Order(id=1) - trùng lặp 5 lần (theo số lượng item)
// Có DISTINCT:
// Order(id=1) - một lần
```

## Middle Level

### Một JOIN FETCH Mỗi Truy Vấn

```java
// Một JOIN FETCH
@Query("SELECT DISTINCT o FROM Order o JOIN FETCH o.items WHERE o.id = :id")
Order findByIdWithItems(@Param("id") Long id);

// Nhiều JOIN FETCH - Cartesian Product
@Query("SELECT o FROM Order o " +
       "JOIN FETCH o.items " +
       "JOIN FETCH o.payments " +
       "JOIN FETCH o.shippings")
// 10 order x 5 item x 3 payment x 2 shipping = 300 dòng!
```

### Khi Nào Nhiều JOIN FETCH Chấp Nhận Được

```java
// Chỉ khi tập kết quả nhỏ
@Query("SELECT DISTINCT o FROM Order o " +
       "JOIN FETCH o.items " +
       "JOIN FETCH o.user " +
       "WHERE o.id = :id")
// Một order -> Cartesian product không phải là vấn đề
```

### Lựa Chọn Thay Thế - @BatchSize

```java
// Thay vì nhiều JOIN FETCH:
@Query("SELECT DISTINCT o FROM Order o JOIN FETCH o.user")
List<Order> findAllWithUser();

// + @BatchSize cho items
@OneToMany(mappedBy = "order")
@BatchSize(size = 25)
private List<OrderItem> items;

// Kết quả:
// 1 truy vấn cho Order + User
// N/25 truy vấn cho items
```

### Các Lỗi Thường Gặp

```java
// Không có DISTINCT - trùng lặp
@Query("SELECT o FROM Order o JOIN FETCH o.items")
List<Order> findAll();  // Order trùng lặp!

// JOIN FETCH với phân trang
@Query("SELECT DISTINCT o FROM Order o JOIN FETCH o.items")
Page<Order> findAll(Pageable pageable);  // có thể không hoạt động đúng

// Với truy vấn count riêng biệt
@Query(value = "SELECT DISTINCT o FROM Order o JOIN FETCH o.items",
       countQuery = "SELECT COUNT(o) FROM Order o")
Page<Order> findAll(Pageable pageable);
```

## Senior Level

### Các Cải Tiến Của Hibernate 6

```
Hibernate 6.2+ đã thêm một số cải tiến ở cấp độ truy vấn, nhưng vấn đề Cartesian
product với nhiều JOIN FETCH vẫn cần giải quyết thủ công.
```

### Các Pattern Nâng Cao

```java
// Pattern 1: EntityGraph để tải động
@NamedEntityGraph(
    name = "Order.withItems",
    attributeNodes = @NamedAttributeNode("items")
)
@Entity
public class Order { }

// Cách dùng
EntityGraph<Order> graph = entityManager.getEntityGraph("Order.withItems");
List<Order> orders = entityManager.createQuery("SELECT o FROM Order o", Order.class)
    .setHint("jakarta.persistence.fetchgraph", graph)
    .getResultList();

// Pattern 2: Các repository khác nhau cho các use case khác nhau
public interface OrderRepository extends JpaRepository<Order, Long> {
    // Cho danh sách - không có items
    List<Order> findByStatus(String status);

    // Cho view chi tiết - có items
    @Query("SELECT DISTINCT o FROM Order o JOIN FETCH o.items WHERE o.id = :id")
    Optional<Order> findByIdWithItems(@Param("id") Long id);

    // Cho admin - có user và items
    @EntityGraph(attributePaths = {"user", "items"})
    Optional<Order> findAdminViewById(Long id);
}
```

### JOIN FETCH Và Phân Trang - Vấn Đề

Tại sao JOIN FETCH + phân trang có vấn đề: Hibernate không thể áp dụng đúng
LIMIT/OFFSET vào một truy vấn có JOIN - kết quả chứa các bản sao trùng lặp
của root entity. Truy vấn count cũng có thể sai do JOIN.
Ví dụ: LIMIT 10 trên một truy vấn có JOIN FETCH trả về ít hơn 10 Order riêng biệt.

```java
// Vấn đề: JOIN FETCH + Pageable có thể cho count sai
@Query("SELECT DISTINCT o FROM Order o JOIN FETCH o.items")
Page<Order> findAll(Pageable pageable);

// Giải pháp 1: truy vấn count riêng biệt
@Query(value = "SELECT DISTINCT o FROM Order o JOIN FETCH o.items",
       countQuery = "SELECT COUNT(DISTINCT o) FROM Order o")
Page<Order> findAllWithPage(Pageable pageable);

// Giải pháp 2: hai truy vấn
@Query("SELECT o.id FROM Order o")
Page<Long> findOrderIds(Pageable pageable);

@Query("SELECT DISTINCT o FROM Order o JOIN FETCH o.items WHERE o.id IN :ids")
List<Order> findByIds(@Param("ids") List<Long> ids);
```

### Phân Tích Hiệu Năng

```
Hiệu năng của JOIN FETCH:
- 1 truy vấn thay vì N+1
- Nhưng có thể tạo ra kết quả lớn (Cartesian product)
- DISTINCT xử lý trùng lặp trong bộ nhớ
- Cho collection lớn - @BatchSize tốt hơn
- JOIN FETCH có thể gây OutOfMemoryError khi collection rất lớn. Một order với 10,000 item tải toàn bộ 10,000 vào bộ nhớ cùng lúc. Cho collection lớn, @BatchSize hoặc sub-select an toàn hơn.

Quy tắc:
- Một JOIN FETCH mỗi truy vấn
- @BatchSize cho các association bổ sung
- EntityGraph để tải động
```

### Best Practices

```
Một JOIN FETCH mỗi truy vấn
DISTINCT để loại bỏ trùng lặp
@BatchSize cho các association bổ sung
EntityGraph để tải động
Các phương thức khác nhau cho các use case khác nhau

Nhiều JOIN FETCH (Cartesian product)
Không có DISTINCT
Bỏ qua Cartesian product
JOIN FETCH với phân trang không có countQuery
```

## Interview Cheat Sheet

**Cần phải biết:**
- JOIN FETCH tải các entity liên quan trong một truy vấn SQL - giải pháp N+1
- DISTINCT bắt buộc - loại bỏ các root object trùng lặp (một cho mỗi child)
- Một JOIN FETCH mỗi truy vấn - nhiều -> Cartesian product (10 x 5 item x 3 payment = 150 dòng)
- Cho phân trang với JOIN FETCH, cần countQuery riêng biệt - LIMIT/OFFSET không đúng với JOIN
- Lựa chọn thay thế cho các association bổ sung - @BatchSize thay vì nhiều JOIN FETCH
- EntityGraph - tải động khi cần các fetch plan khác nhau

**Các câu hỏi phụ thường gặp:**
- **Tại sao cần DISTINCT?** JOIN trả về một dòng cho mỗi child, DISTINCT loại bỏ các root trùng lặp trong bộ nhớ
- **Tại sao phân trang với JOIN FETCH có vấn đề?** Hibernate không thể áp dụng đúng LIMIT - các root object trùng lặp
- **Khi nào nhiều JOIN FETCH chấp nhận được?** Khi tập kết quả nhỏ (một order theo ID), Cartesian product không phải vấn đề
- **JOIN FETCH vs @BatchSize?** JOIN FETCH - 1 truy vấn khi dữ liệu luôn cần, @BatchSize - N/batchSize khi thỉnh thoảng

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Nhiều JOIN FETCH trong một truy vấn" - Cartesian product, kết quả khổng lồ
- "Không có DISTINCT" - Order trùng lặp trong kết quả
- "JOIN FETCH với phân trang không có countQuery" - LIMIT sai, ít kết quả riêng biệt hơn
- "Tôi luôn dùng JOIN FETCH cho tất cả association" - Cartesian product với nhiều collection
