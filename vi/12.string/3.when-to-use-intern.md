# When to Use intern()? (Khi nào nên dùng intern()?)

## 🟢 Junior Level

Method `intern()` thêm một chuỗi vào String Pool và trả về một tham chiếu đến nó từ pool.

Hãy tưởng tượng: bạn đang load 10,000 bản ghi từ DB, và mỗi bản ghi có cùng từ 'Ukraine'.
Không có `intern()` — 10,000 object riêng biệt. Với `intern()` — một object và 10,000 tham chiếu đến nó.

**Ví dụ đơn giản:**
```java
String s1 = new String("Hello"); // Trong heap thông thường
String s2 = s1.intern();          // Được thêm vào pool

String s3 = "Hello";              // Từ pool
System.out.println(s2 == s3);     // true — cùng chuỗi từ pool
```

**Khi nào nên dùng:** Khi bạn có nhiều chuỗi giống hệt nhau và muốn tiết kiệm bộ nhớ. Ví dụ, nếu bạn load 10,000 bản ghi từ một cơ sở dữ liệu, và mỗi bản ghi có trường `country = "Ukraine"` — thay vì 10,000 object trong bộ nhớ sẽ chỉ có một object trong pool.

**Khi nào KHÔNG nên dùng:** Cho các chuỗi tồn tại ngắn bị xóa nhanh chóng. Garbage Collector thông thường sẽ tự xử lý chúng.

## 🟡 Middle Level

### Cách Nó Hoạt Động

Method `intern()` kiểm tra String Pool:
1. Nếu chuỗi đó đã tồn tại — trả về một tham chiếu từ pool
2. Nếu chưa — thêm chuỗi hiện tại vào pool và trả về tham chiếu

### Ứng Dụng Thực Tế
```java
// Load dữ liệu từ DB — nhiều giá trị trùng lặp
while (rs.next()) {
    String city = rs.getString("city").intern();
    String country = rs.getString("country").intern();
    users.add(new User(city, country));
}
```

Nếu cơ sở dữ liệu có 1,000,000 bản ghi, nhưng chỉ có 100 thành phố độc nhất:
- Không có `intern()`: 1,000,000 object String
- Có `intern()`: 100 object String trong pool + 1,000,000 tham chiếu đến chúng

### Các Lỗi Điển Hình
1. **Lỗi:** Gọi `intern()` cho mọi chuỗi mà không phân tích
   **Giải pháp:** Chỉ dùng cho dữ liệu tồn tại lâu với các bản trùng lặp

2. **Lỗi:** Kỳ vọng kết quả tức thì
   **Giải pháp:** `intern()` là một lời gọi native có overhead, nó không miễn phí

### So Sánh: intern() vs String Deduplication
| Đặc điểm        | intern()                | -XX:+UseStringDeduplication |
| --------------------- | ----------------------- | --------------------------- |
| Khi nào nó hoạt động         | Khi gọi (đồng bộ)   | Trong lúc GC (bất đồng bộ)    |
| Nó kết hợp cái gì      | Các object String          | Các mảng byte[] nội bộ      |
| Có cần thay đổi code không? | Có                     | Không (chỉ cần cờ JVM)          |
| Chỉ dành cho G1 GC?           | Không                      | Có                          |

## 🔴 Senior Level

### Hiện Thực Nội Bộ

`String.intern()` là một method native:
```cpp
JVM_ENTRY(jstring, JVM_InternString(JNIEnv *env, jstring str))
  if (str == NULL) return NULL;
  oop string = JNIHandles::resolve_non_null(str);
  oop result = StringTable::intern(string, CHECK_NULL);
  return (jstring) JNIHandles::make_local(env, result);
JVM_END
```

`StringTable::intern()` thực hiện:
1. Tính hash của chuỗi
2. Tra cứu trong hash table StringTable
3. Nếu tìm thấy — trả về tham chiếu
4. Nếu không tìm thấy — chèn vào bảng (có thể resize)

### Đánh Đổi Về Kiến Trúc (Trade-off)

**Ưu điểm của intern():**
- Tiết kiệm RAM: với tỷ lệ trùng lặp 1000:1, tiết kiệm >99%
- Ít object hơn → Full GC ít thường xuyên hơn
- So sánh nhanh qua `==` (sau khi intern)

**Nhược điểm của intern():**
- Overhead CPU: mỗi lời gọi — hashing + tra cứu trong bảng toàn cục
- Contention: StringTable là một cấu trúc dữ liệu toàn cục có locking
- Nguy cơ OOM: với hàng triệu chuỗi độc nhất, pool có thể lấp đầy Heap
- StringTableSize: nếu bảng nhỏ — xung đột → suy giảm O(n)

### Các Trường Hợp Biên

1. **Contention đa luồng:** Khi `intern()` được gọi song song từ hàng trăm thread, xảy ra contention trên lock của StringTable.

2. **Kích Thước String Table:** Mặc định là 60013 (Java 8+). Nếu dự kiến 1M+ chuỗi độc nhất:
   ```
   -XX:StringTableSize=1000003
   ```

3. **Các chuỗi Young Gen:** `intern()` cho các chuỗi tồn tại ngắn là phản tác dụng — dù sao chúng cũng sẽ chết ở Minor GC tiếp theo.

### Hiệu Năng
- `intern()` không có xung đột: ~50-100ns
- `intern()` với 1M mục và StringTableSize phù hợp: ~200-500ns
- `intern()` với 1M mục và StringTableSize nhỏ: **10-50μs** (xung đột!)

### Kinh Nghiệm Production
**Kịch bản:** Phân tích 10GB log, nơi có 500 log level độc nhất xuất hiện (`INFO`, `WARN`, `ERROR`, `DEBUG`, `TRACE`):
- Không có `intern()`: ~50M object String cho các key → 2.4GB
- Có `intern()`: 500 object trong pool → ~50KB
- Kết quả: Full GC mỗi 30 giây → mỗi 15 phút, độ trễ p99 giảm từ 200ms xuống 15ms
// Ít object hơn trong Eden → lấp đầy chậm hơn → ít Minor GC hơn → độ trễ thấp hơn.

**Kịch bản ngược lại:** UUID của user — mỗi chuỗi là độc nhất. `intern()` ở đây chỉ lãng phí CPU và lấp đầy pool bằng rác.

### Giám Sát
```bash
# Thống kê StringTable
jcmd <pid> VM.stringtable -verbose

# Kết quả:
# StringTable statistics:
# Number of buckets       : 60013
# Number of entries       : 1234567
# Number of loaded classes: N/A
# Maximum bucket size     : 42         ← nếu > 10, tăng StringTableSize
```

### Best Practices Cho Highload
- Dùng `intern()` **chỉ** cho các chuỗi tồn tại lâu với tỷ lệ trùng lặp cao
- Đừng intern UUID, hash, token — chúng là độc nhất
- Profile: đôi khi overhead CPU từ `intern()` tốn kém hơn số MB tiết kiệm được trong Heap
- Giải pháp thay thế: một `ConcurrentHashMap<String, String>` cache riêng — kiểm soát eviction và kích thước
- Cho việc dedup tự động mà không thay đổi code: `-XX:+UseStringDeduplication` (G1 GC, từ Java 8u20)

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- `intern()` thêm chuỗi vào String Pool và trả về tham chiếu từ pool
- Tiết kiệm bộ nhớ với nhiều chuỗi trùng lặp (1M bản ghi, 100 thành phố → 100 object thay vì 1M)
- `intern()` là một lời gọi native có overhead CPU (~50-100ns không xung đột)
- Contention: StringTable là một cấu trúc toàn cục có locking, nút thắt cổ chai với hàng trăm thread
- `-XX:StringTableSize=1000003` — tăng lên cho 1M+ chuỗi độc nhất
- Đừng dùng `intern()` cho UUID, hash, token — chúng đều độc nhất

**Các câu hỏi phụ thường gặp:**
- **Khi nào `intern()` hữu ích?** — Khi load dữ liệu có tỷ lệ trùng lặp cao: từ điển, danh mục, thành phố, trạng thái.
- **Khi nào `intern()` có hại?** — Với các chuỗi độc nhất: UUID, ID, email, hash. Lấp đầy pool, lãng phí CPU, không tiết kiệm bộ nhớ.
- **Cái nào nhanh hơn: `intern()` hay cache `ConcurrentHashMap` tùy chỉnh?** — `ConcurrentHashMap` mang lại kiểm soát về eviction và kích thước, nhưng `intern()` là native của JVM, không cần quản lý thủ công.
- **Overhead của `intern()` là gì?** — ~50-100ns không xung đột. Với 1M mục và StringTableSize nhỏ: 10-50μs (xung đột!).

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "intern() cho mọi chuỗi — thực hành tốt" — chỉ dành cho các chuỗi có bản trùng lặp
- ❌ "intern() là miễn phí" — lời gọi native, overhead CPU, contention trên StringTable
- ❌ "intern() tăng tốc mọi thứ" — tiết kiệm bộ nhớ, nhưng làm chậm CPU
- ❌ "intern() — tối ưu hóa chuỗi duy nhất" — còn có `-XX:+UseStringDeduplication` (tự động, không cần code)
