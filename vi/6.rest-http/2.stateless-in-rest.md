# What does Stateless mean in REST context? (Stateless có nghĩa gì trong bối cảnh REST?)

## Junior Level

**Stateless** có nghĩa là server không lưu trữ thông tin session của client giữa các request. Mỗi request được xử lý như thể nó là request đầu tiên.

Điều này có nghĩa là server không cần phải nhớ bạn là ai 5 giây trước đó. Mỗi request giống như một lần gặp gỡ lần đầu với một người lạ: client phải cung cấp tất cả dữ liệu cần thiết (token, parameters).

### Các nguyên tắc cốt lõi:
- **Mỗi request độc lập:** Server không nhớ client đã làm gì trước đó
- **Client giữ trạng thái:** Tất cả thông tin session (token, parameters) được gửi với mỗi request
- **Server chỉ lưu trữ dữ liệu:** Dữ liệu trong DB (products, users) không phải là session state — điều này được phép

### Ví dụ:
```
// Mỗi request chứa một token xác thực
// Token được gửi mỗi lần vì server không nhớ bạn giữa các request
// — đó là ý nghĩa của Stateless.
GET /users/1
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...

GET /users/1/orders
Authorization: Bearer eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...
```

### Ưu điểm của Stateless:
- Vì server không cần lưu trữ session, bất kỳ request nào cũng có thể đi tới bất kỳ server nào.
  Không cần sticky sessions, không cần đồng bộ session giữa các node.
- Bất kỳ server nào cũng có thể xử lý bất kỳ request nào
- Dễ dàng triển khai và bảo trì

## Middle Level

### Trạng thái được lưu ở đâu?
1. **Trên server (Resource State — trạng thái tài nguyên):** Dữ liệu trong database — điều này được **cho phép**
2. **Trên client (Session State — trạng thái phiên):** Thông tin phiên (token, filter) — điều này là **bắt buộc** đối với Stateless

### TLS và Session Resumption (khôi phục phiên)
Trạng thái tồn tại ở tầng TCP/TLS:
- **TLS Session Tickets:** Client lưu một session ticket đã được mã hóa
- **TLS Session ID:** Cho phép bỏ qua Handshake đầy đủ ở mỗi request
- REST vẫn "Stateless" ở tầng ứng dụng, ngay cả khi hạ tầng có thể là "Stateful"

### Cookie so với Header
- `Cookie` được gửi tự động — tiện lợi cho trình duyệt
- `Authorization: Bearer` linh hoạt hơn cho ứng dụng di động và giúp tránh tấn công CSRF

### Token Bloat (token phình to)
Nếu bạn lưu quá nhiều dữ liệu trong một JWT (roles, permissions, họ tên đầy đủ), kích thước header sẽ tăng lên:
- **Giải pháp:** Chỉ lưu `sub` (ID) và các `scopes` quan trọng trong token
- Lấy phần còn lại từ một cache nhanh khi cần

### Chẩn đoán
- **Sticky Session Check:** Trong Kubernetes/Nginx, kiểm tra rằng `sticky sessions` không được bật
- **Distributed Tracing (truy vết phân tán):** Correlation ID (`X-B3-TraceId`) là cách duy nhất để liên kết các request từ cùng một client

## Senior Level

### Vấn đề JWT Revocation (thu hồi JWT)
JWT là một công cụ Stateless. Nhưng nếu bạn cần đăng xuất một người dùng ngay lập tức (ví dụ: token bị đánh cắp), bạn phải kiểm tra một "blacklist" các token trong Redis.

**Nghịch lý:** Ngay khi bạn thêm việc xác minh token trong DB/Redis ở mỗi request, ứng dụng của bạn trên thực tế trở thành **Stateful**, vì nó phụ thuộc vào một kho lưu trữ trạng thái phiên dùng chung bên ngoài.

### Tác động lên Highload và Scaling (mở rộng quy mô)

#### Zero-Downtime Deployment (triển khai không gián đoạn)
Với kiến trúc Stateless, bạn có thể tắt bất kỳ server instance nào vào bất kỳ lúc nào. Client chỉ đơn giản chuyển sang một instance khác.

#### Data Locality và Anycast IP
Stateless cho phép dùng **Anycast IP**. Một request từ Tokyo đi tới một server ở Tokyo, từ London — ở London. Với session, bạn sẽ phải đồng bộ chúng giữa các châu lục.

### Các trường hợp biên (Edge Case)

#### Race Condition trong Client Session
Nếu một client gửi hai request Stateless song song cùng cập nhật một tài nguyên:
- **Giải pháp:** Optimistic Locking (`If-Match` + `ETag`)

#### Server-Side Rendering (SSR)
Với SSR, server thường cần trạng thái cho lần render đầu tiên. Điều này tạo ra các mô hình lai: lần tải đầu là Stateful, các lời gọi API tiếp theo — Stateless.

### Hiệu suất
- Race condition yêu cầu **Optimistic Locking** thông qua `If-Match` + `ETag`
- SSR thường liên quan đến các mô hình lai (lần tải đầu Stateful, API — Stateless)

## Interview Cheat Sheet

**Cần phải biết:**
- Stateless có nghĩa là server không lưu trữ trạng thái session của client giữa các request
- Mỗi request phải chứa tất cả thông tin cần thiết (token, parameters)
- Dữ liệu trong DB (resources) không phải là session state — lưu trữ nó được phép
- Stateless cho phép mở rộng server theo chiều ngang mà không cần sticky sessions
- JWT là một công cụ Stateless, nhưng thêm xác minh Redis làm hệ thống trở thành Stateful
- TLS Session Tickets tồn tại ở mức cơ sở hạ tầng, nhưng ứng dụng vẫn Stateless

**Các câu hỏi phụ thường gặp:**
- *Sự khác nhau giữa Session State và Resource State là gì?* — Session State (session của client) được lưu trữ trên client, Resource State (dữ liệu DB) — trên server, được phép như vậy.
- *Tại sao JWT revocation tạo ra vấn đề?* — Xác minh token trong DB/Redis trên mỗi request làm ứng dụng trở thành Stateful.
- *Làm sao để liên kết các request mà không có session?* — Thông qua Correlation ID (`X-B3-TraceId`) cho distributed tracing.
- *Token Bloat là gì?* — Khi JWT chứa quá nhiều dữ liệu, tăng kích thước header.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Stateless có nghĩa là server không lưu trữ gì cả" — server lưu trữ dữ liệu (DB), chỉ không lưu session.
- "Cookie và Bearer token giống nhau" — Cookie được gửi tự động, Bearer — thủ công; Bearer bảo vệ chống CSRF.
- "Stateless không thể mở rộng" — Stateless thực tế đơn giản hóa việc mở rộng theo chiều ngang.
