# What is the difference between Heap and Stack? (Sự khác nhau giữa Heap và Stack là gì?)

## Junior Level

**Heap và Stack** — hai vùng bộ nhớ ảo riêng biệt mà JVM yêu cầu từ hệ điều hành.

**Tại sao cần hai vùng:** chúng có các mẫu truy cập (access pattern) khác nhau. Stack có tính tuần tự (LIFO): dữ liệu được thêm và loại bỏ theo đúng thứ tự nghiêm ngặt của lời gọi phương thức. Heap có tính tùy ý: các đối tượng sống lâu và có thể truy cập được từ bất kỳ đâu.

**Ví dụ minh họa đơn giản:**
- **Stack** — giống như bàn làm việc của bạn: truy cập nhanh, nhưng không gian hạn chế. Dùng cho các công việc hiện tại.
- **Heap** — giống như một nhà kho: rất rộng lớn, nhưng bạn cần phải đi lại để lấy đồ. Dùng để lưu trữ toàn bộ đồ đạc của bạn.

**Sự khác biệt chính:**

| Stack                                     | Heap                               |
| ----------------------------------------- | ----------------------------------- |
| Lưu trữ các biến cục bộ và tham chiếu     | Lưu trữ các đối tượng (`new Object()`)    |
| Truy cập nhanh                               | Chậm hơn                             |
| Nhỏ (1 MB cho mỗi luồng)                   | Lớn (hàng gigabyte)                   |
| Được dọn dẹp tự động                  | Được dọn dẹp bởi Garbage Collector    |
| Riêng cho mỗi luồng                    | Được chia sẻ giữa tất cả các luồng          |

**Ví dụ:**
```java
public void example() {
    int x = 10;           // Stack (kiểu nguyên thủy - primitive)
    String name = "Ivan"; // Stack (tham chiếu) → "Ivan" nằm trong Heap
    User user = new User(); // Stack (tham chiếu) → đối tượng User nằm trong Heap
}
```

**Các lỗi:**
- Tràn Stack → `StackOverflowError` (đệ quy vô hạn)
- Tràn Heap → `OutOfMemoryError: Java heap space`

## Middle Level

### Stack: Bộ nhớ thực thi

**Cấu trúc Stack frame:**
```
Stack Frame (được tạo khi gọi phương thức):
├── Local Variable Table  ← các biến cục bộ
├── Operand Stack         ← stack toán hạng cho các phép tính
├── Dynamic Linking       ← tham chiếu đến Constant Pool
└── Return Address        ← nơi cần quay về sau khi phương thức kết thúc
```

**Vòng đời:**
- Được tạo khi gọi phương thức → bị loại bỏ khi return
- **Có tính xác định (Deterministic)** — bộ nhớ được giải phóng ngay lập tức
- Không yêu cầu Garbage Collector

**Tham số:** `-Xss` (mặc định 1 MB)

### Heap: Bộ nhớ trạng thái

**Những gì được lưu trữ:**
- Tất cả các đối tượng (`new ...`)
- Các mảng (array) (kể cả mảng của kiểu nguyên thủy `int[]`)
- Các trường tĩnh (static field) của class
- String Pool

**Cấp phát (Allocation):**
- **TLAB (Thread Local Allocation Buffer)** — một bộ đệm (buffer) riêng cho mỗi luồng trong Eden. Mỗi luồng cấp phát trong TLAB riêng của mình mà không cần đồng bộ hóa → rất nhanh.
- **Pointer Bumping** — cấp phát = chỉ đơn giản là di chuyển một con trỏ về phía trước (nhanh!)

**Các tham số:** `-Xms` (ban đầu), `-Xmx` (tối đa)

### Escape Analysis: Tối ưu hóa JIT

**Các thuật ngữ:**
- **TLAB (Thread Local Allocation Buffer)** — một buffer riêng cho mỗi luồng trong Eden. Mỗi luồng cấp phát trong TLAB riêng của mình mà không cần đồng bộ hóa → rất nhanh.
- **Compressed OOPs (Compressed Ordinary Object Pointers)** — nén các tham chiếu từ 8 xuống còn 4 byte khi Heap < 32 GB. Tiết kiệm ~30% bộ nhớ.
- **Escape Analysis (Phân tích thoát)** — phân tích của JIT: liệu một đối tượng có "thoát" ra khỏi một phương thức hay không? Nếu không — JIT có thể cấp phát nó trên Stack hoặc loại bỏ hoàn toàn (Scalar Replacement).

```java
// JIT có thể quyết định rằng đối tượng không "thoát" ra khỏi phương thức
// và cấp phát nó trên stack thay vì heap!
public Point createPoint() {
    Point p = new Point(10, 20);  // Có thể được cấp phát trên Stack!
    return p;  // Đối tượng "thoát" — JIT không thể loại bỏ việc cấp phát.
// JIT phân tích tất cả các đường thoát: nếu một tham chiếu được trả về hoặc
// được lưu trong một trường — đối tượng "thoát". Kiểm tra: -XX:+PrintEscapeAnalysis
}

// Scalar Replacement: đối tượng bị "phân rã" thành các biến
// Lock Elision: synchronized bị loại bỏ nếu đối tượng chỉ được dùng bởi một luồng
```

### Bảng so sánh

| Tiêu chí      | Stack                             | Heap                  |
| -------------- | --------------------------------- | ---------------------- |
| **Tính khả kiến** | Cục bộ cho từng luồng (Thread-local)                      | Được chia sẻ                |
| **Quản lý** | Phần cứng (Stack Pointer)          | GC                    |
| **Dọn dẹp**    | Tức thì (Stack Unwinding)         | Nền (STW pauses) |
| **Tối ưu hóa** | Register Allocation            | TLAB, Compressed OOPs |
| **Lỗi**     | `StackOverflowError`              | `OutOfMemoryError`    |

### Project Loom (Virtual Threads, Java 21+)

```
Platform thread: stack nằm trong bộ nhớ native (cố định 1 MB)
Virtual thread: stack nằm trong Heap dưới dạng một đối tượng!
  → Mount (gắn): được sao chép vào stack của platform thread
  → Unmount (tháo): được sao chép ngược lại vào Heap
  → Kết quả: hàng triệu luồng!
```

## Senior Level

### Bên trong Stack Frame

```
Cấu trúc Stack Frame:
┌─────────────────────────────────────┐
│ Local Variable Table                │
│   [0] = this (đối với non-static)       │
│   [1] = param1                      │
│   [2] = param2                      │
│   ...                               │
├─────────────────────────────────────┤
│ Operand Stack (cho các thao tác byte-code)   │
│   push a, push b, iadd, store c     │
├─────────────────────────────────────┤
│ Dynamic Linking → Constant Pool     │
│ Return Address → lệnh tiếp theo   │
│ Exception Table Reference           │
└─────────────────────────────────────┘

Kích thước frame được tính toán tại thời điểm biên dịch!
```

### TLAB (Thread Local Allocation Buffer)

```
Eden Space:
┌────────────────────────────────────┐
│ Thread 1: [TLAB_1] 64KB            │
│ Thread 2: [TLAB_2] 64KB            │
│ Thread 3: [TLAB_3] 64KB            │
│ ...                                │
└────────────────────────────────────┘

Cấp phát trong TLAB:
  pointer += object_size  // Bump-the-pointer (di chuyển con trỏ)
  → 0 sự đồng bộ hóa!
  → Thường nhanh hơn malloc() trong môi trường đa luồng, vì malloc yêu cầu đồng bộ hóa, trong khi TLAB thì không.

Nếu đối tượng > TLAB → cấp phát trong Eden có đồng bộ hóa
```

### NUMA Awareness (Nhận thức về NUMA)

```
Server đa vi xử lý (Multi-processor):
CPU 1 ── Memory A (nhanh)
CPU 2 ── Memory B (nhanh đối với CPU 2, chậm đối với CPU 1)

-XX:+UseNUMA → JVM phân phối Heap trên các NUMA node
→ Các luồng trên CPU 1 sẽ cấp phát trong Memory A
→ Tăng 10-20% hiệu năng đối với Highload!
```

### Bố cục đối tượng trong bộ nhớ (Object Layout)

```
Object Header (12-16 byte):
├── Mark Word (8 byte)
│     ├── Hash Code (31 bit)
│     ├── Age (4 bit) → dành cho GC
│     ├── Lock State (2 bit)
│     └── GC bit
├── Klass Pointer (4 byte với Compressed OOPs)
│     → Con trỏ đến metadata của class trong Metaspace
├── Instance Data (các trường của đối tượng)
└── Padding (căn chỉnh theo 8 byte)
```

### Compressed OOPs: Ngưỡng 32 GB

```
Con trỏ 64-bit = 8 byte
Compressed OOPs = 4 byte (dịch chuyển × 8)

Địa chỉ tối đa: 2^32 × 8 = 32 GB

→ Heap 31 GB nhanh hơn 33 GB!
→ Vượt qua ngưỡng 32 GB = giảm 10-15% hiệu năng
→ Tiết kiệm được bộ nhớ cache L1/L2 của CPU
```

### Tương lai: Project Valhalla (Value Types)

```java
// Tương lai: lưu trữ theo giá trị (by value), không phải theo tham chiếu (by reference)
public final class Point {
    public final int x;
    public final int y;
}

// Hiện tại:
Point[] arr = new Point[1000];  // 1000 đối tượng trong Heap + 1000 tham chiếu

// Tương lai (Value Types):
Point[] arr = new Point[1000];  // Được lưu trữ trực tiếp trong mảng!
→ Không có object header
→ Không có gián tiếp (indirection)
→ Cache locality (tính cục bộ của cache) tăng gấp 10 lần
```

### Kinh nghiệm Production

**Tình huống thực tế: Ngưỡng 32 GB đã giết chết hiệu năng**
- Server: 64 GB RAM, `-Xmx48g`
- Vượt qua 32 GB → Compressed OOPs bị vô hiệu hóa
- Kết quả: giảm 15% throughput (thông lượng), tăng 20% latency (độ trễ)
- Giải pháp: `-Xmx30g` → Compressed OOPs được kích hoạt → đã khắc phục

### Best Practices (Thực hành tốt nhất)

1. **`-Xms = -Xmx`** trong production đối với các server chạy dài hạn (ngăn ngừa chi phí phát sinh khi resize). Đối với các tiện ích CLI, hãy giữ -Xms nhỏ để khởi động nhanh.
2. **Tránh vượt quá 32 GB** khi không cần thiết (Compressed OOPs)
3. **Escape Analysis** — hãy viết code sao cho đối tượng không "thoát"
4. **TLAB** — Cấp phát Heap có thể nhanh hơn cả Stack!
5. **Virtual Threads** (Java 21+) cho các ứng dụng có tính đồng thời cao
6. **StackWalker** (Java 9+) để phân tích stack
7. **Giám sát** `-Xss` — đệ quy sâu = StackOverflowError

### Tóm tắt cho Senior

- **Stack** = thực thi (nhanh, có tính xác định, riêng cho từng luồng)
- **Heap** = dữ liệu (lớn, được chia sẻ, cần GC)
- **TLAB** = di chuyển con trỏ → cấp phát nhanh hơn malloc
- **Escape Analysis** = Stack Allocation + Lock Elision
- **Compressed OOPs** = ngưỡng 32 GB → cực kỳ quan trọng đối với hiệu năng
- **NUMA** = phân phối Heap trên các node cho các server đa vi xử lý
- **Object Layout** = Mark Word + Klass Pointer + Data + Padding
- **Virtual Threads** = stack nằm trong Heap → hàng triệu luồng

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Stack — LIFO, riêng cho từng luồng, lưu trữ các biến cục bộ và tham chiếu; Heap — được chia sẻ, lưu trữ các đối tượng và mảng
- Stack được dọn dẹp tự động khi phương thức return, Heap — bởi Garbage Collector
- Tràn Stack → `StackOverflowError`, Tràn Heap → `OutOfMemoryError`
- TLAB cho phép cấp phát đối tượng trong Heap mà không cần đồng bộ hóa (di chuyển con trỏ)
- Escape Analysis (JIT) có thể cấp phát một đối tượng trên Stack nếu nó không "thoát" ra khỏi phương thức
- Compressed OOPs: khi Heap < 32 GB, các tham chiếu được nén từ 8 xuống còn 4 byte → 31 GB thường nhanh hơn 33 GB
- Object Layout: Mark Word (8 byte) + Klass Pointer (4 byte) + Data + Padding
- Virtual Threads (Java 21+): stack nằm trong Heap, ~2 KB cho mỗi luồng thay vì 1 MB

**Các câu hỏi phụ thường gặp:**
- **Tại sao Heap 31 GB lại nhanh hơn 33 GB?** — Compressed OOPs bị vô hiệu hóa khi vượt quá 32 GB, kích thước con trỏ tăng gấp đôi → nhiều cache miss hơn
- **Có thể tạo một đối tượng trên Stack không?** — Có thể, thông qua JIT Escape Analysis có thể thực hiện Stack Allocation hoặc Scalar Replacement
- **TLAB là gì?** — Thread Local Allocation Buffer, một buffer riêng cho mỗi luồng trong Eden để cấp phát mà không cần khóa (lock-free)
- **Tham số nào thiết lập kích thước Stack?** — `-Xss` (mặc định 1 MB)

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Heap và Stack là cùng một thứ, chỉ khác tên gọi" — chúng là hai vùng bộ nhớ khác nhau
- "GC dọn dẹp Stack" — Stack được dọn dẹp tự động khi phương thức return
- "Các đối tượng luôn luôn được tạo trong Heap" — JIT có thể cấp phát trên Stack thông qua Escape Analysis
