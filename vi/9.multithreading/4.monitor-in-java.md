# What is monitor in Java? (Monitor trong Java là gì?)

---

## Junior Level

### Hiểu biết cơ bản

Một **monitor** là một cơ chế đồng bộ hóa trong Java cung cấp mutual exclusion (loại trừ lẫn nhau). Mọi object trong Java đều có monitor tích hợp sẵn (intrinsic) của riêng nó.

Intrinsic monitor — mọi object Java đều có một monitor "ngay từ đầu". JVM tự động gắn một cấu trúc dữ liệu để đồng bộ hóa với mỗi object. Đó là lý do bất kỳ object nào cũng có thể được dùng làm khóa (lock key).

### Ví dụ minh họa đơn giản

Hãy tưởng tượng một phòng họp với một cửa:
- **Monitor** = phòng họp
- **Key** (chìa khóa) = cái khóa
- **Hàng đợi bên ngoài** = các thread chờ để vào (EntryList)
- **Phòng chờ** = các thread đã gọi wait() (WaitSet)

### Ví dụ sử dụng

```java
public class Counter {
    private int count = 0;

    // synchronized dùng monitor của object 'this'
    public synchronized void increment() {
        count++; // Chỉ một thread được ở đây
    }

    public synchronized int getCount() {
        return count;
    }
}
```

### Các dạng tương đương

```java
// Cách 1: synchronized method
public synchronized void method() {
    // code
}

// Cách 2: synchronized block (giống hệt)
public void method() {
    synchronized(this) { // Acquire monitor của object 'this'
        // code
    } // Release monitor
}
```

### wait() và notify()

Các method của monitor để giao tiếp giữa các thread:

```java
synchronized(lock) {
    while (!condition) {
        lock.wait(); // Giải phóng monitor và chờ
    }
    // Tiếp tục khi notify() được gọi
}

// Ở thread khác:
synchronized(lock) {
    condition = true;
    lock.notify(); // Đánh thức một thread đang chờ
}
```

### Các quy tắc quan trọng

| Quy tắc                    | Mô tả                                                       |
| -------------------------- | ---------------------------------------------------------- |
| Chỉ một owner              | Chỉ một thread có thể sở hữu monitor tại một thời điểm      |
| Reentrancy (tái nhập)      | Owner có thể vào lại monitor mà không bị chặn              |
| wait() giải phóng          | Gọi wait() tạm thời giải phóng monitor                    |
| Chỉ bên trong synchronized | wait()/notify() chỉ hoạt động bên trong một synchronized block |

## Middle Level

### Liên hệ với Object Header (Mark Word)

Mọi object trong Java đều có một header chứa **Mark Word**:

Mark Word — một phần của object header trong JVM. Lưu thông tin khóa: thread nào sở hữu, trạng thái (unlocked, biased, thin, fat). Trên JVM 64-bit = 8-12 byte.

```
|--------------------------------------------------------------|
| Object Header                                                  |
| -------------------------------------------------------------- | ------------------------- |
| Mark Word (64/32 bit)                                          | Class Pointer (64/32 bit) |
| -------------------------------------------------------------- |                           |
```

Mark Word lưu các bit trạng thái khóa:

| Bit (JVM 64-bit)  | Trạng thái                   |
| ----------------- | ---------------------------- |
| `01`              | No Lock / Biasable           |
| `01`              | Biased Locking (kèm Thread ID) |
| `00`              | Lightweight Lock (Thin Lock) |
| `10`              | Heavyweight Lock (Fat Lock)  |
| `11`              | Đánh dấu cho GC              |

### Cấu trúc ObjectMonitor (mức C++ của JVM)

Khi một monitor được "inflate" (bơm phồng) lên trạng thái heavyweight, Mark Word chứa một con trỏ tới `ObjectMonitor`:

```cpp
// Cấu trúc đơn giản hóa từ HotSpot
class ObjectMonitor {
    void* _owner;          // Thread sở hữu
    ObjectWaiter* _EntryList; // Hàng đợi các thread BLOCKED
    ObjectWaiter* _WaitSet;   // Hàng đợi các thread WAITING
    int _Recursion;           // Bộ đếm reentrancy
    int _WaitSetLock;         // Bảo vệ WaitSet
};
```

### Vòng đời của Thread trong một Monitor

```
                    ┌─────────────────────────────────┐
                    │                                 │
                    ▼                                 │
┌──────────┐  ┌──────────────┐  ┌──────────┐  ┌──────────────┐
│   NEW    │→│  EntryList   │→│  OWNER   │→│   EXIT       │
│ (đã tạo) │  │  (BLOCKED)   │  │(RUNNING) │  │ (đã giải phóng)│
└──────────┘  └──────────────┘  └──────────┘  └──────────────┘
                                     │
                                     │ wait()
                                     ▼
                              ┌──────────────┐
                              │   WaitSet    │
                              │  (WAITING)   │
                              └──────────────┘
                                     │
                                     │ notify()
                                     ▼
                              ┌──────────────┐
                              │  EntryList   │
                              │  (BLOCKED)   │
                              └──────────────┘
```

### Các thao tác của Monitor

| Method            | Mô tả                                          |
| ----------------- | ---------------------------------------------- |
| `monitor.enter()` | Acquire monitor (chặn nếu đang bận)            |
| `monitor.exit()`  | Release monitor                                |
| `wait()`          | Giải phóng monitor và chuyển sang WAITING      |
| `notify()`        | Chuyển một thread từ WaitSet sang EntryList    |
| `notifyAll()`     | Chuyển tất cả các thread từ WaitSet sang EntryList |

### Lock Record trên Stack

Lock Record — một cấu trúc dữ liệu trên stack của thread lưu một bản sao của Mark Word khi acquire một lock. Cần để khôi phục Mark Word khi giải phóng.

Với các lightweight lock, JVM tránh việc tạo `ObjectMonitor` nặng:

1. JVM sao chép Mark Word của object vào **Lock Record** trên stack của thread
2. Thread dùng các **thao tác CAS** nhanh để acquire
3. Nếu không có tranh chấp — mọi thứ ở lại trên stack (rất nhanh)
4. Nếu tranh chấp xuất hiện — xảy ra **Lock Inflation** lên Heavyweight

Lock Inflation — chuyển từ khóa nhẹ (biased/thin) sang khóa nặng (fat lock). Xảy ra khi có tranh chấp: khi nhiều thread cùng cố acquire một monitor.

### Khi nào KHÔNG nên dùng monitor

1. **Throughput cao, nhiều thao tác ghi**: hàng triệu ops/giây — các thuật toán lock-free (Atomic, CHM) nhanh hơn
2. **Tải nhiều thao tác đọc**: ReentrantReadWriteLock cho phép đọc song song, monitor thì không
3. **Cần tryLock với timeout**: monitor chặn mãi mãi, ReentrantLock.tryLock(timeout) thì không

## Senior Level

### Bên trong: sự tiến hóa trạng thái khóa

JVM (HotSpot) dùng chiến lược **lock escalation** (leo thang khóa — Lock Inflation):

#### 1. No Lock (001)

```
|---------------------------------------------------------------|
| unused:25                                                       | identity_hashcode:31 | unused:1 | age:4 | bias:0 | 01  |
| --------------------------------------------------------------- | -------------------- | -------- | ----- | ------ | --- |
```

Object không bị khóa. Mark Word chứa hash code và tuổi object (GC age).

#### 2. Biased Locking

```
|-------------------------------------------------------------------------|
| thread:54                                                                 | epoch:2 | unused:1 | age:4 | bias:1 | 01  |
| ------------------------------------------------------------------------- | ------- | -------- | ----- | ------ | --- |
```

- Nếu một object chỉ được acquire bởi một thread, JVM "bias" (thiên vị) nó về phía thread đó
- Thread vào synchronized mà không cần CAS, chỉ kiểm tra thread ID trong header
- Biased Locking — bị tắt mặc định từ Java 15 (JEP 374), gỡ bỏ hoàn toàn ở Java 21 (JEP 416). Trong các phiên bản Java hiện đại, việc chuyển trạng thái đi theo: No Lock → Thin Lock → Fat Lock.

#### 3. Thin Lock (lightweight lock)

```
|---------------------------------------------|
| thread:54                                     | lock record:6 | 00  |
| --------------------------------------------- | ------------- | --- |
```

- Khi có tranh chấp, CAS được dùng để thay Mark Word bằng một con trỏ tới Lock Record
- Thread không ngủ — thực hiện **adaptive spinning** (một vài vòng rỗng)

#### 4. Fat Lock (heavyweight lock)

```
|----------------------------------------------|
| object monitor pointer:62                      | 10  |
| ---------------------------------------------- | --- |
```

- Khi tranh chấp cao, một `ObjectMonitor` đầy đủ được tạo
- Thread bị park qua OS (`futex` trong Linux, `WaitForSingleObject` trong Windows) — trạng thái **BLOCKED**
- Context Switch — rất đắt (~1000+ ns)

### Adaptive Spinning

HotSpot JVM ghi nhớ lịch sử khóa:

```java
// JVM theo dõi:
// - Spinning đã thành công bao nhiêu lần trên monitor này
// - Thread đã park ngay lập tức bao nhiêu lần

// Nếu spinning thành công — spin lâu hơn
// Nếu không — park thread ngay lập tức
```

Điều này cải thiện đáng kể hiệu năng cho các khóa tồn tại ngắn.

### Monitor Inflation và Deflation

```
No Lock → Biased → Thin → Fat (Inflation — xảy ra tự động)
Fat → Thin → ... (Deflation — chỉ trong lúc Safe Point / GC)
```

Nhiều Fat Lock → hiệu năng giảm do các context switch.

### Các tối ưu hóa của trình biên dịch JIT

#### Lock Coarsening

```java
// Trước tối ưu:
synchronized(lock) { list.add(a); }
synchronized(lock) { list.add(b); }
synchronized(lock) { list.add(c); }

// Sau Lock Coarsening:
synchronized(lock) {
    list.add(a);
    list.add(b);
    list.add(c);
}
```

#### Lock Elision (qua Escape Analysis)

```java
public void method() {
    Object lock = new Object(); // Object không "escape" khỏi method
    synchronized(lock) {
        // JIT sẽ loại bỏ hoàn toàn khóa này!
        // Vì không ai khác có thể truy cập lock
    }
}
```

### Hiệu năng và tải cao (Highload)

#### Tranh chấp và EntryList

Nếu hàng trăm thread cùng cố acquire một monitor:
- `EntryList` trở thành một điểm nghẽn (bottleneck)
- Các thread liên tục context-switch
- CPU dành nhiều thời gian chuyển đổi hơn là làm việc

**Giải pháp:**
- Segmented lock (như trong `ConcurrentHashMap`)
- Dùng `LongAdder` thay vì `AtomicInteger`
- ReadWriteLock khi đọc chiếm ưu thế so với ghi

#### JMC (Java Mission Control)

- Event `Java Monitor Wait` — thời gian trong wait()
- Event `Java Monitor Enter` — thời gian ở BLOCKED
- Hiển thị các object cụ thể có mức tranh chấp cao nhất

### Best Practices

1. **Giảm thiểu phạm vi khóa** — giữ các synchronized block ngắn nhất có thể
2. **Dùng private final Object lock** — đóng gói, không code bên ngoài nào giành được lock của bạn
3. **Tránh các khóa mức class** — `synchronized(ClassName.class)` rất nguy hiểm
4. **Cân nhắc ReadWriteLock** — nếu đọc chiếm ưu thế so với ghi
5. **Giám sát tranh chấp** qua JMC — thời gian wait tăng dần = vấn đề
6. **Tránh synchronized trong các hệ thống tải cao** — ưu tiên các cấu trúc lock-free

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Mọi object Java đều có một monitor tích hợp (intrinsic) — một cơ chế mutual exclusion
- Monitor = EntryList (hàng đợi các thread BLOCKED) + WaitSet (hàng đợi các thread WAITING) + bộ đếm reentrancy
- Mark Word trong object header lưu trạng thái khóa: No Lock → Thin → Fat (leo thang)
- Biased Locking gỡ bỏ ở Java 21; đường đi hiện đại: No Lock → Thin Lock → Fat Lock
- wait() tạm thời giải phóng monitor và chuyển thread vào WaitSet; notify() chuyển nó sang EntryList
- JVM tối ưu: Lock Coarsening (gộp), Lock Elision (loại bỏ qua Escape Analysis)
- Khi tranh chấp cao, Thin Lock "inflate" lên Fat Lock với ObjectMonitor (context switch ~1000+ ns)

**Các câu hỏi phụ thường gặp:**
- **Điều gì xảy ra khi synchronized được gọi?** — JVM cố acquire monitor: đầu tiên biased → thin (CAS + spinning) → fat (ObjectMonitor + OS parking)
- **Có thể gọi wait() mà không có synchronized không?** — Không, IllegalStateException — wait/notify chỉ hoạt động bên trong một synchronized block
- **Lock Record là gì?** — Một cấu trúc trên stack của thread với một bản sao của Mark Word; dùng trong Thin Locking
- **Khi nào một monitor KHÔNG phù hợp?** — Các tải throughput cao nhiều thao tác ghi; tốt hơn nên dùng lock-free (Atomic, ConcurrentHashMap)

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Monitor là một object riêng trong bộ nhớ" — không, nó tích hợp vào mọi object (intrinsic)
- "wait() giải phóng monitor mãi mãi" — không, tạm thời; thread quay lại EntryList sau notify()
- "Synchronized luôn dùng ObjectMonitor" — không, khi tranh chấp thấp nó dùng thin lock trên stack
- "Biased Locking vẫn còn liên quan trong Java 21" — không, đã gỡ bỏ hoàn toàn (JEP 416)
