# What does the printStackTrace() method do? (Phương thức printStackTrace() làm gì?)

## Junior Level

### Định nghĩa

`printStackTrace()` - một phương thức của `Throwable` xuất đầy đủ thông tin exception (kiểu, message, call stack) ra `System.err`.

### Ví dụ

```java
try {
    int x = 10 / 0;
} catch (ArithmeticException e) {
    e.printStackTrace();
    // Output: java.lang.ArithmeticException: / by zero
    //         at com.example.Main.main(Main.java:10)
}
```

### Nó hiển thị cái gì

1. Kiểu exception: `java.lang.ArithmeticException`
2. Message: `/ by zero`
3. Call stack: lỗi xảy ra trong file, phương thức và dòng nào

### Khi nào dùng

- Chỉ để debug và làm prototype, khi bạn cần nhanh chóng thấy stack trong console mà không cần cấu hình một logger
- **Đừng dùng** trong code production

### TẠI SAO printStackTrace() tệ cho production

`printStackTrace()` là output "thô" mà:
1. **Ghi ra `System.err`**, không phải file log của bạn. Trong production, log được thu thập tập trung (ELK, Splunk), và `System.err` có thể bị chuyển hướng tới `/dev/null` hoặc bị mất khi container khởi động lại
2. **Không thêm ngữ cảnh nào**: không timestamp, không trace ID, không tên class - chỉ stack trần trụi. Thử tìm đúng lỗi giữa hàng nghìn cái tương tự xem
3. **Tách stack thành các dòng riêng biệt**. Trong Kubernetes mỗi dòng của `printStackTrace()` trở thành một bản ghi JSON riêng trong ElasticSearch - thay vì một log dễ đọc bạn có 50 cái rải rác
4. **Chặn thread** - `System.err` là synchronized. Dưới tải cao, 100 thread sẽ xếp hàng chờ ghi

### Khi nào KHÔNG nên dùng printStackTrace()

1. **Code production** - thay bằng logger (`log.error("msg", e)`)
2. **Ứng dụng đa luồng** - `System.err` là synchronized, tạo tranh chấp (contention)
3. **Ứng dụng web** - stack trong HTTP response phơi bày cấu trúc nội bộ (Bảo mật)
4. **Hạ tầng ELK/Splunk** - `printStackTrace()` tách một stack thành 50+ bản ghi JSON riêng biệt
5. **Hệ thống Highload** - chặn trên `System.err` khi đĩa/pipe đầy

## Middle Level

### Tại sao nó chạy chậm

**1. Đồng bộ hóa:**
`System.err` là một object `PrintStream`. Tất cả các phương thức của nó dùng **đồng bộ hóa**. Trong một ứng dụng đa luồng, 100 thread sẽ chờ lock.

**2. Chuyển đổi stack native:**
`Throwable` chuyển đổi một cách lười `backtrace` native thành mảng `StackTraceElement[]` đúng vào thời điểm truy cập stack.

### Xuất ra chuỗi

```java
StringWriter sw = new StringWriter();
e.printStackTrace(new PrintWriter(sw));
String stackTrace = sw.toString();
```

### So sánh với logger

```java
// XẤU - đồng bộ hóa, không ngữ cảnh, tách log
e.printStackTrace();

// TỐT - async, có ngữ cảnh, thân thiện với JSON
log.error("Failed to process order id={}", id, e);
```

Logger có thể:
- Định dạng stack thành một dòng hoặc JSON
- Cắt bớt các stack quá dài
- Thêm thông tin file JAR và phiên bản
- Ghi ra file, không phải console

### Nơi nó thực sự ghi vào

Trong Kubernetes/Docker, `System.err` được bắt lại và ghi vào các log JSON. Nhưng `printStackTrace()` xuất mỗi dòng thành một **bản ghi riêng biệt**.

**Kết quả:** thay vì một log lỗi - 50+ bản ghi rải rác trong ElasticSearch.

## Senior Level

### Chặn I/O tiêu chuẩn

Nếu đĩa đầy hoặc pipe của console bị nghẽn, `printStackTrace()` sẽ **chặn** thread thực thi trong một khoảng thời gian không xác định.

**Quy tắc cho Senior:** trong code production, `printStackTrace()` nên bị chặn bởi các luật static analysis (Checkstyle/Sonar).

### Circular Causes (cause vòng lặp)

Khi có phụ thuộc vòng lặp trong `cause` (dù `initCause` có kiểm tra điều này), `printStackTrace` có cơ chế bảo vệ và in `[CIRCULAR REFERENCE]`, không đi vào đệ quy vô hạn.

### Bảo mật

Stack trace trong console phơi bày các phiên bản thư viện và cấu trúc đường dẫn. Trong ứng dụng web, **đừng bao giờ** trả về `printStackTrace()` trong HTTP response - hãy dùng `@ControllerAdvice`.

### Các giải pháp thay thế

```java
// Lấy stack dưới dạng chuỗi bằng chương trình
String stackTrace = ExceptionUtils.getStackTrace(e); // Apache Commons

// Logger
log.error("Context message", e); // Logback/Log4j2

// Thread Dump - nếu ứng dụng bị treo
// jstack <pid> hoặc jcmd <pid> Thread.print
```

### Chẩn đoán

- **`jstack <pid>`** - trạng thái của tất cả các monitor và thread
- **`jcmd <pid> Thread.print`** - giải pháp thay thế cho jstack
- **Static analysis** - Sonar chặn `printStackTrace()` trong code production
- **JSON Layout** - log nên ở định dạng JSON cho ELK/Splunk

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- `printStackTrace()` xuất kiểu exception, message và call stack ra `System.err`
- **ĐỪNG dùng trong production**: ghi ra `System.err`, không phải file log; không timestamp/trace ID; chặn thread (synchronized)
- Trong Kubernetes/Docker mỗi dòng của `printStackTrace()` trở thành một bản ghi JSON riêng trong ELK - một stack bị tách thành 50+ bản ghi
- `System.err` - `PrintStream` với đồng bộ hóa; dưới tải cao các thread xếp hàng
- Trong production thay bằng `log.error("context", e)` - async, có ngữ cảnh, thân thiện với JSON
- `printStackTrace()` bảo vệ chống circular cause - in `[CIRCULAR REFERENCE]`

**Các câu hỏi phụ thường gặp:**
- **Tại sao printStackTrace() tệ cho production?** - 4 lý do: ghi ra System.err (không phải log), không ngữ cảnh, tách stack thành các dòng, chặn thread
- **Cách lấy stack dưới dạng chuỗi bằng chương trình?** - `StringWriter` + `PrintWriter` hoặc `ExceptionUtils.getStackTrace(e)` từ Apache Commons
- **Điều gì xảy ra khi đĩa đầy?** - `printStackTrace()` chặn thread vô thời hạn, vì `System.err` là synchronized
- **Cách tránh rò rỉ stack trong HTTP response trong Spring?** - Dùng `@ControllerAdvice`, đừng bao giờ trả về `printStackTrace()` cho client

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi dùng printStackTrace() trong production - nó vẫn chạy" - Bạn mất log, chặn thread, phơi bày cấu trúc code
- "Không có khác biệt giữa printStackTrace() và logger" - Logger thêm ngữ cảnh, định dạng, ghi vào đúng chỗ
- "Stack trong HTTP response là thực hành bình thường" - Phơi bày các phiên bản thư viện và cấu trúc đường dẫn (lỗ hổng bảo mật)
