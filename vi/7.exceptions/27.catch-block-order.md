# In what order should catch blocks be arranged? (Các khối catch nên được sắp xếp theo thứ tự nào?)

## Junior Level

### Quy tắc chính: từ cụ thể tới chung

Các khối `catch` phải đi **từ cụ thể hơn tới chung hơn**:

```java
try {
    Files.readAllLines(Paths.get("file.txt"));
} catch (FileNotFoundException e) {
    // 1. Trường hợp cụ thể trước
    System.out.println("File not found");
} catch (IOException e) {
    // 2. Chung hơn tiếp theo
    System.out.println("IO error");
} catch (Exception e) {
    // 3. Chung nhất - ở cuối
    System.out.println("Unknown error");
}
```

### Tại sao

Nếu bạn đặt `catch` chung lên trước, nó bắt mọi thứ, và các khối `catch` cụ thể không bao giờ thực thi:

```java
// Lỗi biên dịch!
try {
    // code
} catch (Exception e) {
    // Bắt mọi thứ, bao gồm IOException
} catch (IOException e) {
    // Không bao giờ thực thi - code không thể tiếp cận
}
```

Compiler xuất ra: `"exception IOException has already been caught"`.

### Cơ chế "first match wins" ở mức compiler

**Lúc biên dịch:**

Compiler javac kiểm tra mỗi khối catch tuần tự từ trên xuống dưới (JLS 14.20). Với mỗi catch mới nó hỏi: "Kiểu của catch này có phải là kiểu con của bất kỳ catch nào ở trên không?"

- Nếu **có** - compiler báo lỗi, vì code trong khối catch này là **không thể tiếp cận** (unreachable code, JLS 14.21).
- Nếu **không** - catch được thêm vào Exception Table của class.

Đây là một **kiểm tra tĩnh** - compiler không cho phép biên dịch với thứ tự sai. Do đó trong code được biên dịch đúng thứ tự luôn đúng.

**Lúc runtime (JVM):**

Exception Table là một mảng các mục `{from, to, target, type}`. Khi một exception được ném, JVM:

1. Tìm mục đầu tiên mà kiểu khớp với exception (hoặc kiểu cha của nó).
2. Nhảy tới `target` - địa chỉ của khối catch tương ứng.
3. Các mục còn lại **bị bỏ qua**.

Do đó "first match" theo nghĩa đen là mục khớp đầu tiên trong Exception Table.

### Quy tắc đơn giản

Sắp xếp theo cây phân cấp kế thừa - từ con tới cha.

### Khi nào KHÔNG nên tuân theo quy tắc "cụ thể tới chung"

1. **Đừng bao giờ vi phạm nó** - quy tắc này được compiler ép buộc, thứ tự ngược sẽ không biên dịch
2. **Multi-catch bên trong** - thứ tự các kiểu trong `catch (A | B e)` không quan trọng, vì cả hai kiểu trỏ tới cùng một target trong Exception Table
3. **Đừng bắt `Throwable` trong logic nghiệp vụ** - chỉ ở biên của hệ thống
4. **Đừng đặt các exception hiếm trước các cái thường gặp** - nếu `FileNotFoundException` xảy ra thường xuyên hơn `EOFException` 100 lần, hãy bắt nó trước để vi tối ưu hóa việc tìm kiếm trong Exception Table
5. **Đừng trộn lẫn các mức abstraction** - đừng xen kẽ các exception nghiệp vụ và hạ tầng mà không có logic

### Lưu ý: Java 7+ multi-catch thay đổi cách tiếp cận với thứ tự

Với sự xuất hiện của multi-catch trong Java 7, câu hỏi về thứ tự trở nên ít then chốt hơn trong một số kịch bản. Nếu bạn có 3+ exception với xử lý **giống hệt nhau**, thay vì:

```java
// 3 khối catch - thứ tự quan trọng (FileNotFoundException trước IOException)
catch (FileNotFoundException e) { handle(); }
catch (SQLException e) { handle(); }
catch (IOException e) { handle(); }
```

Bạn có thể viết:

```java
// 1 khối catch - thứ tự bên trong multi-catch KHÔNG quan trọng
catch (FileNotFoundException | SQLException | IOException e) { handle(); }
```

Multi-catch loại bỏ vấn đề thứ tự, vì tất cả các kiểu được xử lý giống hệt nhau và trỏ tới một target trong Exception Table.

### Khi nào thứ tự khối catch KHÔNG quan trọng

1. **Tất cả các khối catch xử lý giống hệt nhau** - nếu mỗi catch làm `log.error(e); throw new ServiceException(e);`, thứ tự không ảnh hưởng kết quả. Tuy nhiên trong trường hợp này tốt hơn nên dùng multi-catch.

2. **Các exception không có quan hệ kế thừa** - `catch (SQLException e)` và `catch (NullPointerException e)` không có kiểu con chung. Chúng không bao giờ giao nhau, và thứ tự giữa chúng không ảnh hưởng tính đúng đắn (dù có thể ảnh hưởng hiệu suất tìm kiếm).

3. **Multi-catch** - bên trong `catch (A | B e)` thứ tự các kiểu không quan trọng. Compiler sinh các mục riêng biệt trong Exception Table, nhưng tất cả chúng trỏ tới một target.

4. **Một khối catch duy nhất** - `catch (Exception e)` - không có gì để sắp xếp.

## Middle Level

### First Match Wins

JVM quét Exception Table **từ trên xuống dưới**. Khớp đầu tiên giành quyền điều khiển.

### Chiến lược sắp xếp

**1. Expected so với Exceptional:**
Bắt các business exception thường gặp nhất (ví dụ: `ValidationException`) trước - chúng sẽ ở đầu Exception Table.

**2. Xử lý khác nhau:**
```java
@PostMapping("/orders")
public ResponseEntity<?> createOrder(@RequestBody OrderRequest req) {
    try {
        return ResponseEntity.ok(orderService.create(req));
    } catch (ValidationException e) {
        // 400 Bad Request - lỗi client
        return ResponseEntity.badRequest().body(e.getMessage());
    } catch (ResourceNotFoundException e) {
        // 404 Not Found
        return ResponseEntity.notFound().build();
    } catch (DataAccessException e) {
        // 500 Server Error - vấn đề của chúng ta
        log.error("Database error processing order", e);
        return ResponseEntity.internalServerError().build();
    }
}
```

### Thứ tự multi-catch

Trong `catch (A | B e)` thứ tự bên trong khối **không quan trọng**:

```java
catch (IOException | SQLException e) { }
catch (SQLException | IOException e) { }
// Cùng một thứ
```

Nhưng bạn vẫn không thể kết hợp cha và con.

### Tương tác với try-with-resources

Các exception khi đóng resource tự động (`close()`) xảy ra **trước khi** tới các khối `catch` của bạn. `catch` của bạn có thể bắt một exception từ `close()` nếu không có lỗi nào trong `try` chính.

## Senior Level

### Exception Table và hiệu suất

Tìm kiếm trong Exception Table - độ phức tạp **O(n)**. Trong các phương thức với hàng chục khối `catch` điều này có thể có tác động cực nhỏ lên hiệu suất. Hãy đặt các exception thường gặp nhất lên trước.

### Bắt Error

Nếu bạn bắt `Throwable`, bạn cũng bắt `Error` (ví dụ: `OutOfMemoryError`):

```java
// Quy tắc: Exception cụ thể ở trên Throwable
try { ... }
catch (BusinessException e) { }      // Lỗi nghiệp vụ
catch (DataAccessException e) { }    // Hạ tầng
catch (Throwable t) { }              // Chỉ ở cuối, ở biên của hệ thống
```

**Đừng bao giờ** làm `catch (Throwable t)` ở giữa logic nghiệp vụ - chỉ ở các biên ngoài cùng của hệ thống.

### Exception Hiding (giấu exception)

Thứ tự sai có thể "giấu" một lỗi quan trọng trong một log chung. Việc giám sát sẽ không thấy sự khác biệt giữa `ValidationException` và `OutOfMemoryError`.

### Static Analysis

Dùng **Checkstyle** hoặc **Sonar** để đảm bảo một cách tiếp cận nhất quán với cây phân cấp bắt exception trên toàn bộ dự án.

### Chẩn đoán

- **`javap -c`** - hiển thị Exception Table với các ưu tiên nhảy tới các label `catch`
- **Metric** - đếm mỗi loại exception riêng biệt
- **Log Correlation** - lưu Trace ID cho mọi loại lỗi
- **Global Error Handler** - `@ControllerAdvice` bắt mọi thứ không được bắt cục bộ

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Quy tắc chính: từ cụ thể tới chung - con trước cha trong Exception Table
- Compiler sẽ không cho phép thứ tự ngược - lỗi "exception X has already been caught"
- JVM quét Exception Table từ trên xuống dưới, khớp đầu tiên giành quyền điều khiển (first match wins)
- Thứ tự bên trong `catch (A | B e)` KHÔNG quan trọng - tất cả các kiểu trỏ tới một target
- Các exception không có quan hệ kế thừa có thể được sắp xếp theo bất kỳ thứ tự nào giữa chúng
- Đặt các exception thường gặp nhất lên trước để vi tối ưu hóa việc tìm kiếm
- `catch (Throwable t)` - chỉ ở biên của hệ thống, không bao giờ trong logic nghiệp vụ

**Các câu hỏi phụ thường gặp:**
- **Điều gì xảy ra nếu bạn nhầm thứ tự?** - Lỗi biên dịch, code sẽ không biên dịch
- **Thứ tự có ảnh hưởng hiệu suất không?** - Tìm kiếm O(n), các exception thường gặp lên trước
- **Khi nào thứ tự KHÔNG quan trọng?** - Multi-catch, các kiểu không có quan hệ kế thừa, một catch duy nhất
- **Tại sao chúng ta bắt `Throwable` chỉ ở cuối?** - Bắt `Error` bao gồm `OutOfMemoryError`

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi đặt catch chung lên trước cho tiện" - sẽ không biên dịch
- "Thứ tự trong multi-catch quan trọng" - không, tất cả các kiểu -> một target
- "Tôi bắt `Throwable` ở giữa logic nghiệp vụ" - bắt `Error`, trạng thái không dự đoán được
- "Thứ tự catch ảnh hưởng tính đúng đắn của code đã biên dịch" - compiler đảm bảo thứ tự đúng
