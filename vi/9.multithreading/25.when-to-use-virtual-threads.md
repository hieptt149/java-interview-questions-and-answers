# When Should You Use Virtual Threads? (Khi nào nên dùng Virtual Thread?)

---

## Junior Level

### Hiểu biết cơ bản

Virtual Thread (VT) không phải là một sự thay thế cho thread thông thường, mà là một công cụ chuyên biệt cho các tác vụ cụ thể. Chúng mang lại lợi ích khi ứng dụng dành **phần lớn thời gian để chờ** (I/O): phản hồi DB, microservice, đọc từ S3, các HTTP request.

**Tại sao VT giúp cụ thể với I/O:** khi một thread thông thường gọi một thao tác blocking (ví dụ, `socket.read()`), nó ngủ và chiếm 1MB bộ nhớ OS. Một virtual thread trong cùng thao tác đó "unmount" — JVM lưu stack của nó vào heap (vài KB) và trao Carrier Thread cho một virtual thread khác. Khi I/O hoàn tất, VT "mount" trở lại và tiếp tục.

### Các kịch bản lý tưởng cho VT

#### 1. Tải I/O-bound (Chờ đợi)

Nếu ứng dụng dành 90% thời gian để chờ (phản hồi DB, microservice, đọc từ S3):

```java
// VT — lựa chọn tốt nhất
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (Request request : requests) {
        executor.submit(() -> {
            String data = httpClient.get(url);    // Chờ network
            Result result = db.query(data);       // Chờ DB
            s3.upload(result);                     // Chờ S3
            return result;
        });
    }
}
// Trong khi một VT chờ — Carrier Thread xử lý các VT khác
// Carrier Thread — đây là thread OS thật mà hàng chục nghìn VT "ngồi" trên đó
```

#### 2. Mô hình Thread-per-Request

```java
// Code đơn giản và rõ ràng thay vì reactive
public void handleRequest(HttpServletRequest req, HttpServletResponse resp) {
    String data = database.query(req.getParameter("id")); // Lời gọi blocking
    String processed = externalApi.call(data);            // Lời gọi blocking
    resp.getWriter().write(processed);                    // Lời gọi blocking
}
// Với VT: một triệu request như vậy được xử lý song song!
```

### Khi nào KHÔNG ĐƯỢC dùng VT

#### 1. Các tác vụ CPU-bound (Tính toán)

```java
// XẤU: VT cho tính toán
Thread.ofVirtual().start(() -> {
    calculatePi(1_000_000); // Không có blocking — VT sẽ không unmount
});
// Overhead của scheduler JVM mà không có lợi ích

// TỐT: FixedThreadPool
ExecutorService cpuPool = Executors.newFixedThreadPool(
    Runtime.getRuntime().availableProcessors() + 1
);
cpuPool.submit(() -> calculatePi(1_000_000));
```

#### 2. Giới hạn resource (Throttling)

```java
// XẤU: VT không giới hạn tới DB
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 1_000_000; i++) {
        executor.submit(() -> {
            database.execute("UPDATE ..."); // Một triệu truy vấn DB cùng lúc!
        });
    }
}
// DB sẽ sập!

// TỐT: Semaphore để giới hạn
Semaphore dbSemaphore = new Semaphore(20); // Tối đa 20 kết nối DB

try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 1_000_000; i++) {
        executor.submit(() -> {
            dbSemaphore.acquire();
            try {
                database.execute("UPDATE ...");
            } finally {
                dbSemaphore.release();
            }
        });
    }
}
```

```yaml
# application.yml
spring:
  threads:

      enabled: true
```

```java
// Toàn bộ Tomcat/Undertow chuyển sang VT tự động
@RestController
public class MyController {
    @GetMapping("/user/{id}")
    public User getUser(@PathVariable Long id) {
        // Mỗi request — một VT riêng
        return userService.findById(id); // Lời gọi blocking — OK!
    }
}
```

### Vấn đề Pinning

Một virtual thread "dính" vào một Carrier Thread và không unmount:

| Nguyên nhân        | Ảnh hưởng                   | Giải pháp       |
| ------------------ | --------------------------- | --------------- |
| `synchronized`     | Carrier Thread bị chặn      | `ReentrantLock` |
| Native method (JNI)| Carrier Thread bị chặn      | Thread riêng    |

```java
// XẤU: synchronized trong VT
public synchronized Data loadData() {
    return httpClient.get(url); // VT "dính" — Carrier Thread bận
}

// TỐT: ReentrantLock
private final ReentrantLock lock = new ReentrantLock();

public Data loadData() {
    lock.lock();
    try {
        return httpClient.get(url); // VT unmount — Carrier rảnh
    } finally {
        lock.unlock();
    }
}
```

### Vấn đề ThreadLocal

```java
// Triệu VT = triệu bản sao ThreadLocal = Vấn đề bộ nhớ!
ThreadLocal<Context> context = ThreadLocal.withInitial(Context::new);

// Giải pháp: Scoped Values (Java 21 Preview)
static final ScopedValue<Context> CONTEXT = new ScopedValue<>();

ScopedValue.runWhere(CONTEXT, new Context(), () -> {
    process(); // CONTEXT.get() có sẵn
});
```

### Audit Dependency

Trước khi chuyển sang VT:

```bash
# Kiểm tra các thư viện để tìm các synchronized block
java -Djdk.tracePinnedThreads=full -jar app.jar

# Tìm trong log:
# "VirtualThread pinning" — chỉ ra các vùng có vấn đề
```

**Các thư viện có vấn đề điển hình:**
- Các driver JDBC cũ (dùng `synchronized`)
- `java.text.SimpleDateFormat` (bên trong `synchronized`)
- Một số HTTP client cũ

## Senior Level

### Bên trong: Tại sao Pinning xảy ra

#### synchronized không hỗ trợ Unmount

```
VT vào synchronized:
  1. Acquire monitor (như thường lệ)
  2. Thao tác blocking bên trong
  3. JVM KHÔNG THỂ unmount — phải giữ monitor
  4. VT "dính" vào Carrier Thread
  5. Carrier Thread bận → các VT khác chờ

Kết quả: commonPool bị nghẽn → mọi parallel stream chậm lại
```

#### Các Native Method

```
VT gọi native method:
  1. Chuyển sang code native (JNI)
  2. JVM không biết khi nào code native kết thúc
  3. Không thể unmount — stack nằm trong code native
  4. VT "dính" cho tới khi native trả về
```

### Throttling qua Semaphore

```java
public class ThrottledExecutor {
    private final Semaphore semaphore;
    private final ExecutorService virtualExecutor;

    public ThrottledExecutor(int maxConcurrent) {
        this.semaphore = new Semaphore(maxConcurrent);
        this.virtualExecutor = Executors.newVirtualThreadPerTaskExecutor();
    }

    public Future<?> submit(Runnable task) {
        return virtualExecutor.submit(() -> {
            semaphore.acquire();
            try {
                task.run();
            } finally {
                semaphore.release();
            }
        });
    }
}

// Sử dụng:
ThrottledExecutor dbExecutor = new ThrottledExecutor(20); // Tối đa 20 tới DB
ThrottledExecutor apiExecutor = new ThrottledExecutor(100); // Tối đa 100 tới API
```

### Hiệu năng và Benchmark

```
Kịch bản: 10.000 HTTP request (latency 100ms mỗi cái)

Platform Thread (pool 100):
  - Thời gian: ~10 giây
  - Thread: 100
  - Bộ nhớ: ~100MB

Virtual Thread:
  - Thời gian: ~1 giây
  - Thread: 10.000
  - Bộ nhớ: ~50MB
  - Carrier Thread: 8
```

### Chẩn đoán

#### `-Djdk.tracePinnedThreads=full`

```bash
# In stack trace đầy đủ mỗi lần pinning
java -Djdk.tracePinnedThreads=full MyApp

# Đầu ra:
# VirtualThread pinning detected at:
#   at java.net.SocketInputStream.socketRead0(Native Method)
#   at com.example.MyClass.synchronizedMethod(MyClass.java:42)
```

#### Giám sát JMX

```java
// Metric: số lượng pinned thread
MBeanServer mbs = ManagementFactory.getPlatformMBeanServer();
ObjectName name = new ObjectName("jdk:type=VirtualThread");
Long pinned = (Long) mbs.getAttribute(name, "VirtualThreadPinned");

if (pinned > 0) {
    log.warn("Pinned virtual threads detected: {}", pinned);
}
```

#### Thread Dump

```bash
# jstack không hiệu quả cho một triệu thread
jstack <pid> # Có thể mất vài phút

# Dùng thay vào đó:
jcmd <pid> Thread.dump_to_file -format=json threads.json
# Định dạng JSON — nhanh và hiệu quả hơn
```

### Khi nào VT mang lại lợi ích tối đa

| Kịch bản                              | Lợi ích             |
| ------------------------------------- | ------------------- |
| API Gateway (proxying)                | throughput 10x-100x |
| Web Scraper (nhiều HTTP request)      | throughput 5x-50x   |
| Microservice với các lời gọi DB + HTTP| throughput 3x-10x   |
| Bộ xử lý file (I/O)                   | throughput 5x-20x   |

### Khi nào VT vô dụng hoặc gây hại

| Kịch bản                  | Vấn đề          | Giải pháp       |
| ------------------------- | --------------- | --------------- |
| Tính toán (ML, crypto)    | Không có blocking| FixedThreadPool |
| Legacy nhiều synchronized | Pinning         | ReentrantLock   |
| Resource hạn chế (DB)     | Cần throttling  | Semaphore       |
| Nhiều ThreadLocal         | Bộ nhớ          | Scoped Values   |

### Best Practices

1. **VT cho I/O-bound** — API gateway, web server, proxy
2. **ReentrantLock thay vì synchronized** — tránh pinning
3. **Semaphore để giới hạn** — thay vì giới hạn kích thước pool
4. **Scoped Values thay vì ThreadLocal** — cho context
5. **Audit dependency** — kiểm tra các thư viện để tìm synchronized
6. **-Djdk.tracePinnedThreads=full** — trong lúc phát triển
7. **Cập nhật các driver JDBC/HTTP** — các phiên bản tương thích VT
8. **Không cho CPU-bound** — dùng FixedThreadPool cho tính toán
9. **Giám sát VirtualThreadPinned** — qua JMX/JFR
10. **Spring Boot 3.2+** — `spring.threads.virtual.enabled=true`

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- VT lý tưởng cho I/O-bound: web server, API gateway, proxy, microservice với các lời gọi DB + HTTP
- VT KHÔNG phù hợp cho CPU-bound (tính toán, ML, mật mã) — dùng FixedThreadPool(N+1)
- Khi làm việc với các resource hạn chế (DB pool 20 kết nối) — VT + Semaphore
- Pinning: synchronized và JNI không cho phép VT unmount; thay synchronized bằng ReentrantLock
- ThreadLocal + triệu VT = Vấn đề bộ nhớ; giải pháp thay thế — Scoped Values (Java 21 Preview)
- Audit dependency là bắt buộc: các driver JDBC cũ, SimpleDateFormat dùng synchronized
- Lợi ích: API Gateway throughput 10-100x, Web Scraper 5-50x, microservice 3-10x

**Các câu hỏi phụ thường gặp:**
- **Làm sao giới hạn các truy vấn DB đồng thời khi dùng VT?** — Semaphore với một giới hạn, bọc trong VT executor
- **Tại sao Spring Boot 3.2+ đơn giản hóa việc di chuyển VT?** — `spring.threads.virtual.enabled=true` chuyển toàn bộ Tomcat sang VT tự động, không cần thay đổi code của controller
- **Làm sao kiểm tra một thư viện có tương thích VT không?** — Chạy với `-Djdk.tracePinnedThreads=full` và kiểm tra log để tìm "VirtualThread pinning"
- **Làm gì nếu một dependency dùng synchronized bên trong?** — Bọc lời gọi trong một Platform Thread riêng hoặc thay thế thư viện

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "VT luôn nhanh hơn — nên dùng ở mọi nơi" — VT chậm hơn cho CPU-bound và thêm overhead khi tranh chấp thấp
- "Một triệu VT tới DB không giới hạn — là ổn" — DB sẽ sập, cần Semaphore
- "Di chuyển VT là miễn phí" — cần audit các dependency để tìm synchronized, cập nhật các driver JDBC/HTTP
- "VT giải quyết vấn đề ThreadLocal" — VT làm vấn đề tệ hơn: triệu VT = triệu bản sao ThreadLocal
