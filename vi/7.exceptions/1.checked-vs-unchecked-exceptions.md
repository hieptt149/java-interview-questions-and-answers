# What is the difference between checked and unchecked exceptions? (Sự khác biệt giữa checked và unchecked exception là gì?)

## Junior Level

### Kiến thức cơ bản

Trong Java, mọi exception đều kế thừa từ `java.lang.Throwable`. Exception được chia thành hai loại:

**Checked exception:**
- Là các lớp con của `Exception` (trừ `RuntimeException`)
- Trình biên dịch (compiler) **bắt buộc** bạn phải xử lý chúng: hoặc qua `try-catch`, hoặc qua `throws` trong chữ ký phương thức
- Ví dụ: `IOException`, `SQLException`, `ClassNotFoundException`

**Unchecked exception:**
- Là các lớp con của `RuntimeException`
- Trình biên dịch **không bắt buộc** xử lý
- Ví dụ: `NullPointerException`, `IllegalArgumentException`, `IndexOutOfBoundsException`

### Khi nào dùng

- **Checked** - cho các lỗi bên ngoài có thể phục hồi (không tìm thấy file, mạng không khả dụng)
- **Unchecked** - cho các lỗi lập trình (null, sai tham số) và lỗi nghiệp vụ

```java
// Checked - phải xử lý hoặc khai báo throws
public void readFile() throws IOException {
    Files.readAllLines(Paths.get("file.txt"));
}

// Unchecked - compiler không bắt buộc xử lý
public void divide(int a, int b) {
    if (b == 0) throw new ArithmeticException("Division by zero");
}
```

## Middle Level

### Khi nào KHÔNG nên dùng checked exception

1. **Logic nghiệp vụ** - checked exception phá vỡ tính kết hợp (composition) (phải khai báo throws ở mọi phương thức đi lên trên stack)
2. **REST controller** - Spring tự xử lý các unchecked exception qua @ExceptionHandler
3. **Stream API** - lambda không hỗ trợ checked exception (`Function<T,R>` không khai báo throws)
4. **CompletableFuture** - exception bị bọc trong `CompletionException`, checked mất đi ý nghĩa của nó

### Cách hoạt động

JVM không ép buộc kiểm tra kiểu exception lúc runtime - sự phân tách checked/unchecked chỉ hoạt động ở thời điểm biên dịch. Trong bytecode, mọi exception đều được xử lý như nhau. Lệnh `athrow` chỉ đơn giản là ném một object.

### Exception Translation (chuyển dịch exception)

Thực hành tốt - bắt các checked exception ở biên giữa các tầng và bọc chúng trong các domain unchecked exception:

```java
public class UserRepository {
    public User findById(Long id) {
        try {
            return jdbcTemplate.queryForObject("SELECT * FROM users WHERE id = ?",
                (rs, rowNum) -> new User(rs.getLong("id"), rs.getString("name")), id);
        } catch (DataAccessException e) {
            throw new UserNotFoundException("User not found: " + id, e);
        }
    }
}
```

### Multi-catch (Java 7+)

```java
try {
    // code
} catch (IOException | SQLException e) {
    log.error("Resource error", e);
    throw new ServiceException("Failed", e);
}
```

### Tại sao các ngôn ngữ hiện đại từ bỏ checked exception

Kotlin và Scala không có checked exception vì:
1. **Ô nhiễm chữ ký (signature pollution)** - thêm `throws` đòi hỏi thay đổi mọi phương thức đi lên trên stack
2. **Không tương thích với FP** - các functional interface (Stream API, CompletableFuture) không hỗ trợ checked exception

## Senior Level

### Bên trong: bytecode và JVM

Thuộc tính `Exceptions` trong file `.class` lưu thông tin về các checked exception, nhưng JVM chỉ dùng nó cho việc xác minh (verification), không phải để kiểm soát lúc runtime.

### Sneaky Throws - qua mặt compiler

Vì JVM không kiểm tra kiểu exception, bạn có thể ném một checked exception mà không cần `throws`:

```java
@SuppressWarnings("unchecked")
private static <E extends Throwable> void sneakyThrow(Throwable e) throws E {
    throw (E) e;
}
// Cách dùng: sneakyThrow(new IOException()); - biên dịch được mà không cần throws!
```

Lombok `@SneakyThrows` dùng chính cơ chế này.

**Type erasure:** generic `E` bị xóa (erased) thành `Throwable` lúc runtime. Compiler nghĩ rằng phương thức ném `E` (một tham số kiểu của phương thức), trong khi JVM ném kiểu thật. Đó là lý do không cần `throws` trong chữ ký.

Điều này **nguy hiểm:** bên gọi không biết phương thức có thể ném IOException. Chỉ dùng bên trong framework, không bao giờ dùng trong logic nghiệp vụ.

### Hiệu suất trong Highload

`fillInStackTrace()` - phần đắt đỏ nhất của một exception. JVM duyệt toàn bộ call stack. Ở mức 100k+ RPS, việc tạo exception trở thành nút thắt cổ chai.

**Tối ưu hóa:** với các exception dùng làm tín hiệu, hãy tắt stack trace:
```java
public class FastException extends RuntimeException {
    public FastException(String message) {
        super(message, null, false, false); // writableStackTrace = false
    }
}
```
Điều này tăng tốc việc tạo lên 10-50 lần.

### Lựa chọn kiến trúc

Checked exception chỉ tốt cho **các lỗi bên ngoài có thể phục hồi** trong các thư viện tầng thấp:
- `InterruptedException` - Java ép buộc xử lý để không phá vỡ việc quản lý thread

Unchecked exception được ưa chuộng hơn vì:
- Logic nghiệp vụ sạch sẽ không có tạp nhiễu `try-catch`
- Xử lý tập trung qua `@ControllerAdvice`
- Tương thích với lập trình Reactive

### Các trường hợp biên (Edge Case)

- **Exception Translation ở biên giữa các tầng** - DAO bắt `SQLException` và bọc trong domain unchecked exception
- **UncaughtExceptionHandler** - luôn đặt một handler toàn cục cho các thread
- **Stack Trace Filtering** - trong Highload, hãy cắt bớt stack trace hoặc dùng định dạng JSON (Logstash)

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Checked exception - lớp con của `Exception` (trừ `RuntimeException`), compiler bắt buộc xử lý
- Unchecked exception - lớp con của `RuntimeException`, compiler không bắt buộc xử lý
- Checked - cho các lỗi bên ngoài có thể phục hồi (file, mạng, DB)
- Unchecked - cho các lỗi lập trình và lỗi nghiệp vụ
- JVM không kiểm tra kiểu exception lúc runtime - sự phân tách chỉ ở mức compiler
- Kotlin và Scala từ bỏ checked exception vì ô nhiễm chữ ký và không tương thích FP
- `sneakyThrow` cho phép qua mặt kiểm tra của compiler qua type erasure
- Với highload, hãy tắt stack trace (`writableStackTrace = false`)

**Các câu hỏi phụ thường gặp:**
- **Tại sao các ngôn ngữ hiện đại từ bỏ checked exception?** - Ô nhiễm chữ ký, không tương thích với lambda và Stream API
- **Exception translation là gì?** - Bắt một checked exception ở biên của một tầng và bọc trong một domain unchecked exception
- **sneakyThrow hoạt động như thế nào?** - Generic `E extends Throwable` bị xóa thành `Throwable`, JVM không kiểm tra kiểu
- **Khi nào một checked exception là hợp lý?** - Cho các lỗi bên ngoài có thể phục hồi trong các thư viện tầng thấp (IOException, InterruptedException)

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi luôn dùng checked exception để ép đồng nghiệp phải xử lý lỗi" - đây là anti-pattern cho logic nghiệp vụ
- "JVM kiểm tra checked exception lúc runtime" - không, chỉ compiler
- "Kotlin hoàn toàn không hỗ trợ exception" - Kotlin hỗ trợ unchecked, nó chỉ bỏ checked
