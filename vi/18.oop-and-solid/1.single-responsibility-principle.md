# What is Single Responsibility Principle and How to Apply It (Single Responsibility Principle là gì và cách áp dụng nó)

## 🟢 Junior Level

**Single Responsibility Principle (SRP)** là một trong năm nguyên tắc SOLID, nói rằng: **"Một class chỉ nên có một lý do để thay đổi.**

**Lý do để thay đổi** — một yêu cầu từ một stakeholder cụ thể hoặc hệ thống. Ví dụ: phòng kế toán yêu cầu bạn thay đổi công thức tính lương (một lý do), trong khi IT yêu cầu thay đổi database driver (một lý do khác). Nếu hai phòng ban khác nhau có thể yêu cầu bạn thay đổi cùng một class — SRP bị vi phạm."**.

Nói đơn giản hơn, mỗi class nên xử lý một điều cụ thể. Điều này không có nghĩa là "làm một việc" — nó nghĩa là một class nên chịu trách nhiệm cho một phần cụ thể của chức năng hệ thống.

**Analogy đơn giản:** Hãy nghĩ về một nhà hàng. Đầu bếp nấu ăn, người phục vụ phục vụ khách, thu ngân nhận thanh toán. Nếu một người làm tất cả — sẽ hỗn loạn.

**Ví dụ vi phạm SRP:**
```java
// Xấu: class làm quá nhiều thứ
public class Employee {
    public void calculateSalary() { /* tính lương */ }
    public void saveToDatabase() { /* lưu vào DB */ }
    public void generateReport() { /* tạo report */ }
    public void sendEmail() { /* gửi email */ }
}
```

**Ví dụ tuân thủ SRP:**
```java
// Tốt: mỗi trách nhiệm trong class riêng của nó
public class Employee {
    // Chỉ dữ liệu employee
    private String name;
    private BigDecimal salary;
}

public class SalaryCalculator {
    public BigDecimal calculate(Employee emp) { /* tính toán */ }
}

public class EmployeeRepository {
    public void save(Employee emp) { /* lưu vào DB */ }
}

public class EmailService {
    public void sendNotification(Employee emp) { /* gửi email */ }
}
```

**Khi nào dùng:**
- Như một hướng dẫn — tuân theo SRP trong hầu hết trường hợp. Ngoại lệ: prototype, MVP, các tiện ích ổn định, script 50-100 dòng.
- Khi tạo các class mới
- Khi refactor code hiện có

## 🟡 Middle Level

### Cách Hoạt Động

SRP liên quan chặt chẽ đến các khái niệm:
- **Cohesion** — các phương thức của một class hướng đến một mục đích như thế nào. Cao hơn thì tốt hơn.
- **Coupling** — một class phụ thuộc vào các class khác như thế nào. Ít hơn thì tốt hơn.

### Cách Phát Hiện Vi Phạm SRP

**Dấu hiệu vi phạm:**

1. **Quy tắc "Và"**: nếu bạn mô tả một class là "nó làm X **VÀ** Y **VÀ** Z" — SRP bị vi phạm
2. **Các stakeholder khác nhau**: nếu các phòng ban khác nhau có thể yêu cầu thay đổi trong một class
3. **Danh sách import khổng lồ**: nếu một class import quá nhiều dependency
4. **Testing khó khăn**: nếu test một phương thức yêu cầu mock 5+ dependency

### Ứng Dụng Thực Tế

```java
// Vi phạm SRP: OrderProcessor làm mọi thứ
public class OrderProcessor {
    public void process(Order order) {
        validateOrder(order);         // Validation
        saveOrder(order);             // Thao tác DB
        sendConfirmation(order);      // Gửi thông báo
        logToAnalytics(order);        // Logging
        updateInventory(order);       // Cập nhật inventory
    }
}

// Tuân thủ SRP: ủy quyền trách nhiệm
public class OrderProcessor {
    private final OrderValidator validator;
    private final OrderRepository repository;
    private final NotificationService notifier;
    private final AnalyticsLogger logger;
    private final InventoryService inventory;

    public void process(Order order) {
        validator.validate(order);
        repository.save(order);
        notifier.sendConfirmation(order);
        logger.log(order);
        inventory.update(order);
    }
}
```

### Các Lỗi Thường Gặp

1. **Lỗi**: Tạo các class `Utils`, `Helper`, `Manager`
   **Giải pháp**: Chia chúng thành các class chuyên biệt theo lĩnh vực domain

2. **Lỗi**: Spring `@Service` với 20+ dependency được autowire
   **Giải pháp**: Chia thành nhiều service theo khả năng nghiệp vụ

3. **Lỗi**: Phân rã quá mức (100 class mỗi cái 5 dòng)
   **Giải pháp**: Tìm sự cân bằng — nhóm theo tính năng, không phải theo tầng kỹ thuật

### Khi Nào KHÔNG Nên Tuân Thủ SRP Nghiêm Ngặt

1. **Prototype và MVP** — tốc độ quan trọng hơn kiến trúc
2. **Script 50-100 dòng** — chia thành 5 class thêm phức tạp
3. **Các tiện ích ổn định** — nếu code không thay đổi, không cần SRP

## 🔴 Senior Level

### Triển Khai Nội Bộ Và Kiến Trúc

SRP là một **nguyên tắc quản lý thay đổi**, không chỉ là "một class — một chức năng". Định nghĩa gốc của Robert Martin (Uncle Bob) nói rằng:

> *"Một module chỉ nên có một lý do để thay đổi"*

Ở cấp độ Senior, quan trọng là phải hiểu: SRP áp dụng không chỉ cho class, mà còn cho module, service, và thậm chí cả microservice.

### Các Cấp Độ Cohesion

Một Senior developer nên phân biệt các loại cohesion:

| Loại Cohesion               | Mô tả                                          | Ví dụ                            |
| --------------------------- | ---------------------------------------------------- | ----------------------------------- |
| **Functional (tốt nhất)**       | Tất cả các phần của class cần thiết cho một chức năng   | `BCryptPasswordEncoder`            |
| **Sequential**              | Output của một phương thức là input cho phương thức khác            | `OrderPipeline`                    |
| **Communicational**         | Các phương thức làm việc với cùng dữ liệu                      | `UserService` với các trường user     |
| **Procedural**              | Các phương thức thực thi theo một thứ tự nhất định                   | `TransactionManager`               |
| **Temporal**                | Các phương thức thực thi cùng lúc                     | `StartupInitializer`               |
| **Utility**                 | Cohesion yếu, nhóm ngẫu nhiên                       | `CommonUtils` ❌                    |
| **Coincidental (tệ nhất)**    | Các phần tình cờ đi cùng nhau                  | `Helper` class ❌                   |

### Đánh Đổi Kiến Trúc

**Tuân thủ SRP nghiêm ngặt:**
- ✅ Ưu điểm: Test dễ dàng, coupling thấp, cohesion cao, ít merge conflict tối thiểu
- ❌ Nhược điểm: Số lượng class lớn, phức tạp khi điều hướng, nguy cơ "bụi nguyên tử"

**Tuân thủ SRP vừa phải:**
- ✅ Ưu điểm: Cân bằng giữa khả năng đọc và linh hoạt
- ❌ Nhược điểm: Yêu cầu phán đoán trưởng thành, nguy cơ suy thoái dần dần

### Edge Cases

1. **Vấn Đề Bùng Nổ Class**: Khi SRP bị lạm dụng, hệ thống trở thành hàng nghìn class nhỏ
   - **Giải pháp**: Nhóm theo khả năng nghiệp vụ (Package-by-Feature), không phải theo tầng kỹ thuật

2. **Merge Conflict trong các team lớn**: Một class "phổ biến" được sửa bởi 10+ developer
   - **Giải pháp**: Tách trách nhiệm theo các lĩnh vực domain

3. **Tải Nhận Thức**: Các class khổng lồ (God Object) không thể ghi nhớ hết được
   - **Giải pháp**: Giới hạn kích thước class (200-300 dòng như một hướng dẫn)

### Hiệu Năng

- **Memory footprint**: Nhiều class hơn → nhiều metadata hơn trong Metaspace. Trong thực tế, điều này không đáng kể đối với JVM (vài KB mỗi class)
- **Method dispatch**: Delegation thêm các lệnh gọi phương thức. JIT compiler thường thực hiện **inlining**, giảm overhead xuống không
- **Startup time**: Số lượng lớn các class nhỏ có thể làm chậm khởi động nhẹ (tải metadata)

### Kinh Nghiệm Production

**Kịch bản production thực tế:**

Trong một dự án e-commerce lớn, có một `OrderService` với 3000+ dòng code và 25 dependency. Bất kỳ thay đổi nào cũng dẫn đến regression bug. Team đã dành 3 sprint để refactor:

1. Trích xuất `PaymentProcessor`, `InventoryChecker`, `NotificationService`
2. Tạo `OrderOrchestrator` để điều phối
3. Bao phủ mỗi component với các test độc lập

**Kết quả**: Bug khi deployment giảm 60%, thời gian code review giảm một nửa.

### Monitoring Và Chẩn Đoán

**Cách phát hiện vi phạm SRP trong code:**

1. **Các metric code**:
   - Số dòng code > 300
   - Số phương thức > 10
   - Độ phức tạp cyclomatic > 15
   - Số dependency > 7

2. **Công cụ**:
   - SonarQube (các metric cohesion)
   - Checkstyle (kích thước class)
   - ArchUnit (kiểm tra kiến trúc)

3. **Dấu hiệu Code Review**:
   - Các reviewer khác nhau cho các phần khác nhau của class
   - Xung đột Git thường xuyên
   - Khó viết unit test

### Best Practices Cho Highload

- **SRP trong microservices**: Một microservice — một mục tiêu nghiệp vụ (analogy SRP ở cấp độ hệ thống)
- **Feature Toggle**: Nếu một tính năng yêu cầu thay đổi trong 5+ service — có lẽ ranh giới service được vẽ không đúng
- **Domain-Driven Design**: Aggregate Root nên có một trách nhiệm trong Aggregate của nó

### Mối Quan Hệ Với Các Nguyên Tắc Khác

- **SRP → OCP**: Khi một class có một trách nhiệm, dễ mở rộng hơn mà không cần sửa đổi
- **SRP → LSP**: Các class nhỏ với một mục đích duy nhất dễ kế thừa đúng cách hơn
- **SRP → ISP**: Tách interface một cách tự nhiên xuất phát từ việc tách trách nhiệm
- **SRP → DIP**: Ủy quyền dependency dẫn đến đảo ngược dependency

### Tóm Tắt Cho Senior

- SRP là về **quản lý thay đổi**, không phải về số dòng
- Hướng tới **Functional Cohesion**, tránh **Coincidental Cohesion**
- SRP giảm **tính dễ vỡ của hệ thống**: thay đổi logic email không nên phá vỡ tính toán giá
- Dùng **ArchUnit** để xác minh tự động các ranh giới kiến trúc
- Nhớ sự cân bằng: đừng biến code thành "bụi nguyên tử"
- SRP là một **khoản đầu tư** vào khả năng bảo trì code cho nhiều năm tới

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- SRP: một class chỉ nên có một lý do để thay đổi
- Lý do để thay đổi = yêu cầu từ một stakeholder cụ thể
- Cohesion cao là kết quả tự nhiên của việc tuân theo SRP
- Vi phạm SRP dẫn đến God Object, tính dễ vỡ, và merge conflict
- SRP áp dụng không chỉ cho class, mà còn cho module, service, microservice
- Tránh các class `Utils`, `Helper`, `Manager` — chia chúng theo các lĩnh vực domain
- Spring `@Service` với 20+ dependency được autowire là dấu hiệu rõ ràng vi phạm SRP
- SRP giảm tính dễ vỡ của hệ thống: thay đổi một phần không phá vỡ phần khác

**Các câu hỏi phụ thường gặp:**
- **Cách phát hiện vi phạm SRP?** — LCOM > 1.0, >300 dòng, >10 phương thức, >7 dependency, test phức tạp với 5+ mock
- **Khi nào có thể vi phạm SRP?** — Prototype/MVP, script lên đến 100 dòng, các tiện ích ổn định
- **Atomic Dust là gì?** — Phân rã quá mức, khi hệ thống trở thành hàng nghìn class nhỏ
- **SRP liên quan đến các nguyên tắc SOLID khác như thế nào?** — SRP làm cho code có thể test được (DIP), mở rộng được (OCP), kế thừa được (LSP)

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "SRP nghĩa là một class chỉ nên có một phương thức" (không — một trách nhiệm, không phải một hành động)
- "Tôi luôn tuân theo SRP mà không có ngoại lệ" (không — prototype và script không cần nó)
- "Càng nhiều class càng tốt" (không — cân bằng giữa cohesion và số lượng file)
