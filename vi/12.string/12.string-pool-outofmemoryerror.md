# Can String Pool Cause OutOfMemoryError? (String Pool có thể gây ra OutOfMemoryError không?)

## 🟢 Junior Level

**Có, nó có thể.** Nhưng loại lỗi phụ thuộc vào phiên bản Java.

Mỗi chuỗi độc nhất trong pool là một object (~48 byte) + một mục hash table (~32 byte). 100 triệu chuỗi độc nhất = ~8GB chỉ riêng cho pool.

**Java 6 trở xuống:**
```
java.lang.OutOfMemoryError: PermGen space
```
String pool nằm trong vùng PermGen có kích thước cố định. Nhiều `intern()` → hết bộ nhớ → crash.

**Java 7+:**
```
java.lang.OutOfMemoryError: Java heap space
```
Pool chuyển sang heap chính. Nếu bạn intern hàng triệu chuỗi độc nhất — chúng sẽ lấp đầy toàn bộ heap.

**Ví dụ:**
```java
// Code nguy hiểm — có thể gây OOM
List<String> list = new ArrayList<>();
for (int i = 0; i < 100_000_000; i++) {
    list.add(String.valueOf(i).intern()); // Mỗi chuỗi là độc nhất!
}
```

**Cách tránh:** Đừng dùng `intern()` cho các chuỗi độc nhất (UUID, hash, ID). Chỉ dùng cho các chuỗi có bản trùng lặp.

## 🟡 Middle Level

### Khi Nào OOM Xảy Ra

**Kịch bản 1: intern() hàng loạt các chuỗi độc nhất**
```java
// Mỗi chuỗi là độc nhất — pool tăng không kiểm soát
for (User user : users) {
    String email = user.getEmail().intern(); // UUID/email — tất cả khác nhau
}
```

**Kịch bản 2: Rò rỉ qua các tham chiếu mạnh**
```java
// Các chuỗi trong pool + tham chiếu trong collection = không bao giờ được GC thu gom
Set<String> cache = new HashSet<>();
while (true) {
    String data = readFromNetwork().intern();
    cache.add(data); // Tăng vô hạn
}
```

### Cách Ngăn Chặn
1. **Giám sát:** `jcmd <pid> VM.stringtable -verbose`
2. **Tinh chỉnh:** `-XX:StringTableSize=1000003`
3. **Thay thế:** `-XX:+UseStringDeduplication` (G1 GC)
4. **Cache tùy chỉnh:** `ConcurrentHashMap<String, String>` với eviction

### Các Lỗi Điển Hình
1. **Lỗi:** Nghĩ rằng GC sẽ tự động dọn dẹp pool
   **Giải pháp:** StringTable là một hash table native của JVM lưu trữ các tham chiếu mạnh đến các object String. Chừng nào mục đó còn trong bảng — object không đủ điều kiện để GC.

2. **Lỗi:** `intern()` cho mọi chuỗi từ DB
   **Giải pháp:** Chỉ dùng cho các trường có tỷ lệ trùng lặp cao

## 🔴 Senior Level

### Hiện Thực Nội Bộ

**StringTable — hash table native:**
```cpp
oop StringTable::intern(Symbol* string, TRAPS) {
  unsigned int hashValue = hash_string(string);
  int index = the_table()->hash_to_index(hashValue);
  oop found_string = the_table()->lookup(index, string, hashValue);

  // Tìm thấy
  if (found_string != NULL) return found_string;

  // Không tìm thấy — tạo mục mới trong StringTable
  Handle string_object = java_lang_String::create_from_symbol(string, CHECK_NULL);
  the_table()->basic_add(index, string_object, string, hashValue, CHECK_NULL);
  return string_object();
}
```

Mỗi mục trong StringTable là một tham chiếu mạnh. GC sẽ không xóa String trong khi mục đó còn ở trong bảng.

### Hai Loại OOM

**Loại 1: Tràn StringTable (xung đột hash)**
- Khi `StringTableSize` < số lượng chuỗi → các chuỗi collision dài
- `intern()` suy giảm xuống O(n)
- Ứng dụng "treo" — CPU 100% khi tra cứu bảng
- Có thể biểu hiện như `GC Overhead Limit Exceeded`

**Loại 2: Cạn kiệt Heap**
- Hàng triệu chuỗi độc nhất đã intern lấp đầy Heap
- `OOM: Java heap space`
- Xảy ra khi pool cạnh tranh bộ nhớ với các object nghiệp vụ

### Đánh Đổi Về Kiến Trúc (Trade-off)

**String Pool và GC:**
- Young Gen: intern() mới → Eden → chết nhanh (nếu không có tham chiếu)
- Old Gen: intern() tồn tại lâu → Old Gen → Full GC quét tất cả chúng
- G1 GC: việc quét StringTable thêm vào evacuation pause

**Contention:**
- `StringTable` — cấu trúc toàn cục có locking
- Với `intern()` song song từ hàng trăm thread → contention
- Có thể trở thành nút thắt cổ chai trong các hệ thống tải cao

### Các Trường Hợp Biên

1. **StringTableSize mặc định (60013):** Nếu bạn intern 1M+ chuỗi độc nhất, độ dài chuỗi trung bình = 1M / 60013 ≈ 16. Trường hợp xấu nhất — NHIỀU HƠN đáng kể.

2. **GC và việc dọn dẹp String Pool:** Kể từ Java 7u40, JVM xóa các mục không còn tham chiếu khỏi StringTable trong lúc Full GC. Nhưng điều này chỉ hoạt động nếu không có tham chiếu mạnh nào đến các chuỗi.

3. **ZGC/Shenandoah:** Các GC này dùng concurrent marking. Việc quét StringTable xảy ra đồng thời, nhưng overhead vẫn tồn tại.

### Hiệu Năng
| Metric                           | Giá trị                                          |
| -------------------------------- | ---------------------------------------------- |
| StringTableSize mặc định          | 60013                                          |
| Số mục an toàn tối đa (kích thước mặc định)  | ~100K                                          |
| intern() không xung đột      | ~50-100ns                                      |
| intern() có xung đột (1M)    | **10-50μs**                                    |
| Bộ nhớ mỗi mục                 | ~48 byte (String) + ~32 byte (mục Hashtable)|

### Kinh Nghiệm Production
**Kịch bản:** ETL pipeline — load 50M bản ghi từ CSV:
- Trường `category` — 500 giá trị độc nhất → `intern()` tiết kiệm 99.9% bộ nhớ
- Trường `id` — 50M giá trị độc nhất → `intern()` gây OOM sau 20 phút
- Sửa lỗi: `intern()` chỉ cho `category`, cho `id` — String thông thường
- Kết quả: hoạt động ổn định, mức sử dụng heap giảm từ 8GB xuống 3GB

> Quy tắc: nếu số lượng giá trị độc nhất cho một trường < 1% tổng số bản ghi — `intern()` hợp lý. Nếu > 50% — nó có hại.

**Kịch bản 2:** API gateway — 100K RPS:
- Mỗi request: `intern()` cho tên header (`Content-Type`, `Authorization`)
- StringTable tăng lên 500K mục
- Không tăng StringTableSize: latency p99 tăng từ 5ms lên 50ms
- Sửa lỗi: `-XX:StringTableSize=1000003` → p99 trở lại 5ms

### Giám Sát
```bash
# Thống kê StringTable
jcmd <pid> VM.stringtable -verbose
# Kết quả:
# Number of buckets       : 60013
# Number of entries       : 500234
# Maximum bucket size     : 87   ← nếu > 10, có vấn đề!

# Log GC
java -Xlog:gc*:file=gc.log:time,level,tags ...

# Histogram heap
jmap -histo:live <pid> | head -20
```

### Best Practices Cho Highload
- **Không bao giờ** intern các chuỗi độc nhất (UUID, ID, hash, timestamp)
- Tăng `-XX:StringTableSize` khi dự kiến > 100K chuỗi độc nhất
- Giám sát `Maximum bucket size` qua `jcmd`
- Cân nhắc `ConcurrentHashMap<String, String>` với giới hạn kích thước + LRU eviction
- Cho tiết kiệm tự động: `-XX:+UseStringDeduplication` (G1 GC)

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- String Pool có thể gây OOM: trong Java 6 — `PermGen space`, trong Java 7+ — `Java heap space`
- `intern()` hàng loạt các chuỗi độc nhất (UUID, email, ID) — nguyên nhân chính gây OOM
- StringTable lưu trữ các tham chiếu mạnh — GC sẽ không xóa các chuỗi khi các mục còn trong bảng
- Hai loại vấn đề: tràn hash table (xung đột) và cạn kiệt heap
- `Maximum bucket size > 10` — dấu hiệu của vấn đề, cần tăng `StringTableSize`
- Quy tắc: `intern()` hợp lý nếu các giá trị độc nhất < 1% tổng số bản ghi

**Các câu hỏi phụ thường gặp:**
- **Những chuỗi nào KHÔNG nên intern?** — Các chuỗi độc nhất: UUID, ID, email, hash, timestamp.
- **Làm sao ngăn OOM từ String Pool?** — Tăng `StringTableSize`, đừng intern các chuỗi độc nhất, giám sát qua `jcmd VM.stringtable`.
- **StringTable contention là gì?** — `StringTable` là một cấu trúc toàn cục có locking. Với `intern()` song song từ hàng trăm thread — nút thắt cổ chai.
- **GC có thể dọn dẹp String Pool không?** — Trong Java 7+ có, nếu không có tham chiếu mạnh. Nhưng nếu bạn giữ tham chiếu — chúng sẽ không bị thu gom.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "intern() cho mọi chuỗi từ DB — ý tưởng hay" — chỉ dành cho các trường có bản trùng lặp
- ❌ "String Pool không thể gây OOM" — nó có thể, và đây là vấn đề phổ biến
- ❌ "GC tự động dọn dẹp pool" — chỉ khi không có tham chiếu mạnh
- ❌ "StringTableSize không cần tinh chỉnh" — cần thiết cho > 100K chuỗi độc nhất
