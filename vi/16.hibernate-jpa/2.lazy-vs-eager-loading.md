# What is the Difference Between Lazy and Eager Loading (Sự khác biệt giữa Lazy và Eager Loading là gì)

## Overview

FetchType xác định **khi nào** Hibernate tải các entity liên quan: ngay lập tức cùng với parent (EAGER) hoặc chỉ khi truy cập (LAZY). Đây là một quyết định nền tảng ảnh hưởng đến hiệu năng và kiến trúc ứng dụng.

**Analogy:** Hãy tưởng tượng việc tải một cuốn sách. EAGER - cũng tải tất cả các đánh giá, bình luận, và lịch sử chỉnh sửa. LAZY - chỉ tải cuốn sách, và lấy các đánh giá khi người dùng click vào tab.

---

## Junior Level

### Định Nghĩa

**LAZY (lazy loading)** - dữ liệu liên quan được tải **chỉ khi truy cập lần đầu**.

**EAGER (eager loading)** - dữ liệu liên quan được tải **ngay lập tức** cùng với object chính.

```java
// EAGER - tải items ngay lập tức
@OneToMany(fetch = FetchType.EAGER)
private List<OrderItem> items;

Order order = entityManager.find(Order.class, 1L);
// items ĐÃ được tải!

// LAZY - chỉ tải items khi truy cập
@OneToMany(fetch = FetchType.LAZY)
private List<OrderItem> items;

Order order = entityManager.find(Order.class, 1L);
// items CHƯA được tải - đây là một proxy

order.getItems().size();  // CHỈ Ở ĐÂY truy vấn DB mới xảy ra
```

### Các Giá Trị Mặc Định

| Annotation   | FetchType Mặc Định |
| ----------- | ---------------------- |
| @ManyToOne  | EAGER                  |
| @OneToMany  | LAZY                   |
| @OneToOne   | EAGER                  |
| @ManyToMany | LAZY                   |

Các giá trị mặc định dành cho JPA 2.x. Trong Hibernate 5/6 bạn có thể ghi đè thông qua `@LazyToOne`.

### Khi Nào Dùng Cái Gì

- **LAZY** - hầu như luôn luôn, đặc biệt cho các collection
- **EAGER** - chỉ cho các association bắt buộc nhỏ cần thiết trong 100% trường hợp

## Middle Level

### LazyInitializationException

Vấn đề phổ biến nhất với LAZY:

```java
@Transactional
public Order getOrder(Long id) {
    return entityManager.find(Order.class, id);
}

// Bên ngoài transaction:
Order order = service.getOrder(1L);
order.getItems().size();  // LazyInitializationException!
// Session Hibernate đã đóng, proxy không thể tải dữ liệu
```

### Các Giải Pháp

```java
// 1. JOIN FETCH - tải trong transaction
@Query("SELECT DISTINCT o FROM Order o JOIN FETCH o.items WHERE o.id = :id")
Order findByIdWithItems(@Param("id") Long id);

// 2. Hibernate.initialize() - khởi tạo bắt buộc
@Transactional
public Order getOrderWithItems(Long id) {
    Order order = entityManager.find(Order.class, id);
    Hibernate.initialize(order.getItems());
    return order;
}

// 3. @EntityGraph - tải động
@EntityGraph(attributePaths = {"items"})
Order findById(Long id);

// 4. Khởi tạo ở tầng service
@Transactional(readOnly = true)
public OrderDto getOrderDto(Long id) {
    Order order = repository.findById(id).orElseThrow();
    order.getItems().size();  // khởi tạo bắt buộc
    return OrderDto.from(order);
}
```

### Open Session In View - Antipattern

```yaml
// Không khuyến nghị trong production
spring.jpa.open-in-view: true
```

Chế độ này giữ session mở cho đến khi hoàn thành render view, dẫn đến:
- Transaction dài
- Rò rỉ connection
- Vấn đề hiệu năng ẩn

### Các Lỗi Thường Gặp

```java
// EAGER cho các collection lớn
@OneToMany(fetch = FetchType.EAGER)
private List<Order> orders;
// Tải TẤT CẢ order -> OutOfMemoryError

// EAGER "phòng khi cần"
@ManyToOne(fetch = FetchType.EAGER)
private User user;
// Ngay cả khi không cần user - JOIN thừa
```

## Senior Level

### Triển Khai Nội Bộ

**Cách LAZY loading hoạt động:**

```
1. Hibernate tạo một proxy cho entity/collection liên quan
2. Cho @ManyToOne - ByteBuddy proxy kế thừa lớp đó
   ByteBuddy là một thư viện để tạo các lớp con tại runtime. Hibernate dùng nó để tạo một lớp con của entity của bạn, chặn việc truy cập các trường và tải dữ liệu từ DB ở lần truy cập đầu tiên.
3. Cho @OneToMany - PersistentCollection (PersistentBag/PersistentSet)
4. Khi truy cập proxy:
   - Kiểm tra Session.isOpen()
   - Nếu mở -> thực thi SELECT
   - Nếu đóng -> LazyInitializationException
5. Sau khi tải, proxy được thay thế bằng object thật
```

**Tại sao @ManyToOne là EAGER theo mặc định:**

@ManyToOne tham chiếu đến MỘT entity (ví dụ: Order -> User). Thông thường bạn cần user cùng với order. @OneToMany tham chiếu đến một COLLECTION (Order -> OrderItems), có thể chứa hàng trăm bản ghi - tải tất cả chúng mỗi lần sẽ lãng phí.

Một quyết định lịch sử trong đặc tả JPA, dựa trên giả định rằng entity parent thường cần thiết cùng với child. Trong thực tế, điều này hiếm khi có căn cứ.

### Đánh Đổi Kiến Trúc

| LAZY                                      | EAGER                      |
| ----------------------------------------- | -------------------------- |
| Linh hoạt và hiệu năng tốt hơn            | Đơn giản hơn để phát triển  |
| Yêu cầu lập kế hoạch tải dữ liệu          | Luôn khả dụng               |
| Có thể gây LazyInitializationException    | Có thể gây N+1 problem      |
| Phù hợp cho hệ thống tải cao               | Phù hợp cho prototype       |

### Chiến Lược "LAZY Theo Mặc Định"

```
QUY TẮC: Khai báo tất cả association là LAZY, tải rõ ràng khi cần.

Tại sao điều này đúng:
1. EAGER không thể bị hủy trong một truy vấn cụ thể
2. LAZY có thể "biến thành" EAGER thông qua JOIN FETCH
3. LAZY mang lại tính linh hoạt tối đa

@Entity
public class Order {
    // Ghi đè mặc định EAGER thành LAZY
    @ManyToOne(fetch = FetchType.LAZY)
    private User user;

    // LAZY - mặc định cho collection
    @OneToMany(mappedBy = "order")
    private List<OrderItem> items;
}
```

### DTO Projection Thay Vì EAGER

```java
// Thay vì tải toàn bộ entity với các association EAGER
@Query("""
    SELECT new com.example.OrderSummaryDto(
        o.id, o.date, o.status, u.name, COUNT(i)
    )
    FROM Order o
    JOIN o.user u
    LEFT JOIN o.items i
    WHERE o.id = :id
    GROUP BY o.id, u.name
    """)
OrderSummaryDto findOrderSummary(@Param("id") Long id);
```

### Best Practices

```
LAZY theo mặc định cho đại đa số các association. EAGER chỉ khi bạn đã đo lường và xác nhận association đó cần thiết trong 100% các request.
Ghi đè @ManyToOne và @OneToOne thành LAZY
JOIN FETCH khi dữ liệu liên quan cần thiết
@EntityGraph để tải động
DTO projection cho response API
Khởi tạo trong các phương thức @Transactional

EAGER cho collection (@OneToMany, @ManyToMany)
Open Session In View trong production
Truy cập trường LAZY bên ngoài transaction
EAGER "phòng khi cần"
```

## Interview Cheat Sheet

**Cần phải biết:**
- LAZY - dữ liệu tải khi truy cập lần đầu, EAGER - tải ngay lập tức
- Mặc định: @ManyToOne = EAGER, @OneToMany = LAZY, @OneToOne = EAGER, @ManyToMany = LAZY
- LAZY theo mặc định là chiến lược tốt nhất cho tất cả association
- EAGER không thể bị hủy trong một truy vấn, LAZY có thể "biến thành" EAGER thông qua JOIN FETCH
- LAZY hoạt động thông qua proxy (ByteBuddy) và PersistentCollection
- LazyInitializationException xảy ra khi truy cập LAZY bên ngoài transaction
- DTO projection là lựa chọn thay thế tốt nhất cho EAGER trong API

**Các câu hỏi phụ thường gặp:**
- **Tại sao LAZY tốt hơn EAGER?** LAZY linh hoạt - có thể tải khi cần; EAGER xâm lấn - không thể bị hủy
- **Tại sao @ManyToOne là EAGER theo mặc định?** Quyết định lịch sử của JPA - giả định entity parent thường cần thiết
- **Cách giải quyết LazyInitializationException?** JOIN FETCH, EntityGraph, khởi tạo bên trong @Transactional, DTO projection
- **Open Session In View là gì?** Session vẫn mở cho đến khi render view - antipattern cho production

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "EAGER đơn giản hơn - tôi dùng nó" - tạo ra vấn đề N+1 và bộ nhớ
- "Tôi giải quyết LazyInitializationException thông qua EAGER" - chữa triệu chứng, tạo ra vấn đề mới
- "LAZY chỉ cho các collection lớn" - LAZY cho TẤT CẢ association
- "Open Session In View là thực hành bình thường" - antipattern cho production
