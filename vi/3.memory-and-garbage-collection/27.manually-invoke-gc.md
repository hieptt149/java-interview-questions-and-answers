# Can you manually invoke GC? (Bạn có thể chủ động gọi GC theo cách thủ công không?)

## Junior Level

**Có, bạn có thể:** `System.gc()` — một yêu cầu gửi tới JVM để chạy garbage collection.

```java
System.gc();  // "Làm ơn, hãy dọn rác đi"
```

**NHƯNG đây là một anti-pattern!**
- GC tự biết khi nào cần dọn dẹp
- Gọi thủ công = dừng ứng dụng
- Trong production, KHÔNG dùng System.gc() để dọn dẹp định kỳ.
  Ngoại lệ: ExplicitGCInvokedConcurrent cho Concurrent GC theo lịch
  (yêu cầu hiểu sâu về GC của bạn).

**Khi nào chấp nhận được:**
- Trong các test
- Trong các benchmark
- Trước khi chụp một dump

---

## Middle Level

### Tại sao nó tệ

```
1. Full GC = Stop-The-World
   → Tất cả các luồng dừng lại
   → Khoảng dừng: hàng giây trên các Heap lớn

2. GC biết rõ hơn khi nào nên thu gom
   → Các thuật toán tự học (G1, ZGC)
   → Gọi thủ công làm reset các thống kê

3. Không hiệu quả
   → Eden vẫn còn rất nhiều không gian
   → Lãng phí CPU
```

### Direct Buffers — ngoại lệ

```java
// NIO cấp phát bộ nhớ nằm ngoài Heap
ByteBuffer buf = ByteBuffer.allocateDirect(100_000_000);
// 100 MB nằm ngoài -Xmx!

// JVM không thấy tải của Native Memory
// → GC không chạy (Heap trống)
// → Native Memory cạn kiệt
// → NIO gọi System.gc()!

// Nếu bị tắt: -XX:+DisableExplicitGC
// → OOM trong Native Memory với Heap trống!
```

### Các flag kiểm soát

```bash
# Bỏ qua hoàn toàn System.gc()
-XX:+DisableExplicitGC

# Thực thi đồng thời (concurrently) (G1)
-XX:+ExplicitGCInvokedConcurrent
```

### Giải pháp thay thế: jcmd

```bash
# Gọi GC từ bên ngoài (không cần thay đổi code)
jcmd <PID> GC.run
```

## Senior Level

### ExplicitGCInvokedConcurrent

```
Thay vì Full GC STW:
  → G1 khởi chạy một chu kỳ nền (background)
  → Ứng dụng vẫn tiếp tục làm việc
  → Khoảng dừng tối thiểu

"Điểm cân bằng vàng" cho production
```

### Che khuất GC Thrashing

```java
// ❌ Cố gắng "chữa" một rò rỉ
try {
    allocate();
} catch (OutOfMemoryError e) {
    System.gc();  // Che khuất vấn đề!
    allocate();   // Vẫn crash
}

// Ứng dụng rơi vào Thrashing:
// 95% thời gian dành cho GC, 5% cho công việc
```

### JIT Deoptimization

```
Full GC có thể kích hoạt class unloading, điều này gây ra deoptimization
của các phương thức hot. Code Cache được dọn dẹp riêng (CodeCache sweeper),
nhưng class unloading trong lúc Full GC ảnh hưởng đến các phương thức đã được JIT biên dịch.

  → Sau GC: thông dịch (interpretation)
  → JIT biên dịch lại từ đầu
  → Throughput giảm
```

### Chẩn đoán

```bash
# Ai đang gọi System.gc()?

# 1. GC Logs
-Xlog:gc*
→ Tìm: "Pause Full (System.gc())"

# 2. JFR
→ Sự kiện "System GC"
→ Stack trace đầy đủ của lời gọi

# 3. jcmd
jcmd <PID> GC.run  # Gọi thủ công cho các test
```

### Best Practices

1. **KHÔNG dùng** System.gc() trong code nghiệp vụ
2. **ExplicitGCInvokedConcurrent** cho production
3. **jcmd GC.run** để chẩn đoán
4. **DisableExplicitGC** một cách cẩn thận (Direct Buffers!)
5. **Tìm ra người gọi** qua JFR
6. **Benchmark** — trường hợp sử dụng hợp pháp duy nhất

### Tóm tắt cho Senior

- **System.gc()** = anti-pattern trong production
- **Direct Buffers** = ngoại lệ duy nhất
- **ExplicitGCInvokedConcurrent** = thỏa hiệp
- **JFR** = tìm ra người gọi
- **JIT deoptimization** = chi phí ẩn giấu
- **jcmd** = gọi từ bên ngoài cho các test

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- `System.gc()` — yêu cầu gửi tới JVM để Full GC (STW, hàng giây trên các Heap lớn); anti-pattern trong production
- GC biết rõ hơn khi nào nên thu gom: các thuật toán tự học (G1, ZGC) thích ứng với Allocation Rate; gọi thủ công làm reset các thống kê
- Direct Buffers — ngoại lệ: bộ nhớ NIO nằm ngoài Heap; GC không thấy tải (Heap trống) → Native Memory cạn kiệt → NIO gọi `System.gc()`
- `-XX:+DisableExplicitGC` — bỏ qua hoàn toàn `System.gc()`; nguy hiểm cho Direct Buffers (OOM trong Native Memory với Heap trống)
- `-XX:+ExplicitGCInvokedConcurrent` — "điểm cân bằng vàng": G1 khởi chạy một chu kỳ concurrent nền thay vì Full GC STW
- JIT deoptimization: Full GC → class unloading → các phương thức hot bị deoptimize → thông dịch → throughput giảm
- Chẩn đoán: `-Xlog:gc*` (tìm "Pause Full (System.gc())"), JFR (sự kiện "System GC" với stack trace)

**Các câu hỏi phụ thường gặp:**
- **Tại sao Direct Buffers là ngoại lệ?** — `ByteBuffer.allocateDirect()` cấp phát bộ nhớ native nằm ngoài Heap; GC không thấy tải Heap → không chạy → Native Memory cạn kiệt → NIO gọi `System.gc()`
- **GC Thrashing là gì?** — Ứng dụng rơi vào vòng lặp: 95% thời gian dành cho GC, 5% cho công việc; `System.gc()` che khuất vấn đề, không giải quyết nó
- **Tại sao JIT deoptimization là một vấn đề?** — Full GC → class unloading → các phương thức hot bị biên dịch lại từ đầu → throughput giảm trong vài giây
- **Khi nào việc gọi System.gc() là hợp pháp?** — Benchmark (JMH), các test, trước khi chụp một dump để dọn rác

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi gọi System.gc() sau các thao tác lớn để tối ưu" — GC tự biết; gọi thủ công = STW + reset thống kê
- "DisableExplicitGC luôn an toàn" — Direct Buffers: OOM trong Native Memory với Heap trống
- "System.gc() chữa được một memory leak" — che khuất vấn đề; ứng dụng vẫn sẽ rơi vào GC Thrashing
