# What Happens If You Modify a Key After Adding It to HashMap? (Điều gì xảy ra nếu bạn sửa đổi một key sau khi thêm nó vào HashMap?)

## 🟢 Junior Level

Nếu bạn sửa đổi các field của một object key sau `put()`, HashMap sẽ không thể tìm thấy phần tử đó. Object vẫn còn trong map nhưng trở nên "vô hình" — nó không thể được lấy, cập nhật, hoặc xóa.

**Ví dụ:**
```java
MutableKey key = new MutableKey(1);
map.put(key, "Hello");  // Rơi vào bucket #1
key.setValue(2);        // Đã sửa đổi key — hash giờ khác
System.out.println(map.get(key));  // null!

// put(key, "Hello"): key.hashCode() = 1 → bucket #1
// key.setValue(2): key.hashCode() giờ = 2
// get(key): tính hash = 2 → tìm trong bucket #2 → null!
// Phần tử về mặt vật lý ở bucket #1 — nhưng get() tìm trong #2
```

**Ví dụ minh họa:** Bạn đổi địa chỉ nhưng không báo cho ngân hàng. Ngân hàng gửi thư cho bạn tới địa chỉ cũ — bạn sẽ không nhận được.

## 🟡 Middle Level

### Cơ chế thất bại từng bước

1. **Thêm**: `map.put(user, "Active")` — `user.hashCode() = 100` → bucket #100
2. **Sửa đổi**: `user.setName("New")` — `user.hashCode() = 200`
3. **Tìm kiếm**: `map.get(user)` — tính hash 200 → bucket #200 → `null`

**Nghịch lý:** Bạn có một tham chiếu trực tiếp tới object key, nhưng không thể lấy giá trị!

### Khả năng nhìn thấy qua Iterator

Khi duyệt `entrySet()`, bạn **có thể thấy** phần tử này:
```java
for (Map.Entry<MutableKey, String> e : map.entrySet()) {
    System.out.println(e.getKey() + " = " + e.getValue());
    // In ra: MutableKey(id=2) = Hello
}
```
Iterator duyệt qua mọi bucket vật lý, nên nó tìm thấy phần tử "bị mất".

### Làm sao sửa?

Cách đơn giản nhất — tạo một map mới:
```java
Map<MutableKey, String> newMap = new HashMap<>(oldMap);
// Khi sao chép, hash thực tế được tính cho mỗi key
```
Cách thay thế: xóa key cũ qua iterator entrySet(), sửa đổi, chèn lại.

### Các sai lầm thường gặp

1. **Sửa đổi ID của entity** — trường hợp phổ biến nhất
2. **Sửa đổi name/email** — nếu chúng tham gia vào hashCode
3. **JPA Entity làm key** — Entity thay đổi khi persist/merge

## 🔴 Senior Level

### Ghost Entry Pattern

Các entry "ghost" là một rò rỉ bộ nhớ mà:
- Không được các profiler chuẩn phát hiện (object có thể tiếp cận)
- Tăng tỷ lệ thuận với số lượng sửa đổi
- Chỉ biểu hiện qua OutOfMemoryError

```java
// Trong production: service cập nhật các key và put các phiên bản mới
Map<ConfigKey, Config> cache = new HashMap<>();
// Ở mỗi lần cập nhật: key cũ bị "mất", cái mới được thêm
// Sau 1000 lần cập nhật: 999 ghost entry trong bộ nhớ
```

### So sánh với IdentityHashMap

```java
Map<MutableKey, Value> map = new IdentityHashMap<>();
// Dùng System.identityHashCode() — địa chỉ object
// Địa chỉ không thay đổi khi sửa đổi field → hoạt động đúng
```

Nhưng ngữ nghĩa khác: `new Key(1)` và `new Key(1)` — các key khác nhau.

### Cơ chế bên trong

HashMap khi `get()`:
1. Tính `hash(key)` — dùng hashCode **hiện tại**
2. Đi tới bucket theo chỉ số **hiện tại**
3. Không tìm thấy phần tử (nó ở bucket **cũ**)

HashMap không lưu một "snapshot" của hash của key. Mỗi `get()` tính lại hash từ đầu.

### Các trường hợp biên (Edge Case)

1. **Sửa đổi một phần**: Đổi một field, nhưng hashCode không đổi (ví dụ, field không nằm trong hashCode) — hoạt động, nhưng mong manh
2. **Khôi phục**: Nếu các field được đưa về trạng thái gốc — hashCode khớp, phần tử được "tìm thấy"
3. **Concurrent modification**: Một thread sửa đổi key, một thread khác tìm — race condition. Kết quả phụ thuộc vào thứ tự thực thi thread: mất bản cập nhật hoặc đọc dữ liệu cũ đều có thể xảy ra.

### Giám sát Production

Để phát hiện:
- So sánh `map.size()` với số lượng key duy nhất qua iterator
- Dùng JFR để phân tích phân bố bucket
- Heap dump hiển thị các ghost entry (các phần tử có hash "sai")

### Chiến lược phòng thủ

```java
// Pattern: Delete → Modify → Insert
Value v = map.remove(key);
key.modify();
map.put(key, v != null ? v : newValue);
```

Hoặc dùng các key immutable:
```java
record Key(String id) {} // Không thể sửa đổi
```

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Phần tử ở lại bucket cũ, get() tìm trong bucket mới → null
- Iterator entrySet() THẤY phần tử "bị mất" — duyệt qua mọi bucket vật lý
- Nghịch lý: bạn có một tham chiếu trực tiếp tới key, nhưng không thể lấy giá trị
- HashMap không lưu một hash snapshot — mỗi get() tính lại hashCode từ đầu
- Ghost Entry Pattern: rò rỉ bộ nhớ, tăng tỷ lệ thuận với số lần sửa đổi
- Giải pháp: pattern Delete → Modify → Insert, hoặc các key immutable

**Các câu hỏi phụ thường gặp:**
- **Có thể xóa một phần tử bị mất không?** — qua iterator entrySet() thì có, qua remove() thì không
- **Nếu các field được đưa về nguyên trạng — nó có được tìm thấy không?** — có, hashCode khớp, phần tử được "tìm thấy"
- **Cái này khác vấn đề mutable-key như thế nào?** — nó là một trường hợp cụ thể: key đã ở trong Map, rồi bị sửa đổi
- **Tại sao iterator thấy phần tử?** — iterator duyệt vật lý qua mọi bucket, không theo hash

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Phần tử tự động bị xóa" — không, nó ở lại trong bộ nhớ
- "HashMap ghi lại phần tử vào một bucket mới" — không, nó ở lại chỗ cũ
- "Điều này an toàn nếu đổi lại như cũ" — quyết định mong manh, race condition trong đa luồng
