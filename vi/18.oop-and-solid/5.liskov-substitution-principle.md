# What is Liskov Substitution Principle? (Liskov Substitution Principle là gì?)

## 🟢 Junior Level

**Liskov Substitution Principle (LSP)** là một trong năm nguyên tắc SOLID, nói rằng: **"Các object của một subclass phải có thể thay thế cho các object của base class mà không phá vỡ tính đúng đắn của chương trình."**

Nói đơn giản hơn: nếu class `B` kế thừa từ class `A`, thì ở bất kỳ đâu `A` được dùng, `B` cũng nên hoạt động — không có bất ngờ.

**Analogy đơn giản:** Hãy nghĩ về một ổ cắm điện. Nếu bạn mua bất kỳ phích cắm nào tuân theo chuẩn, nó sẽ hoạt động. Nếu một phích cắm nào đó "đặc biệt" và không vừa — chuẩn bị vi phạm.

**Ví dụ vi phạm LSP:**
```java
// Xấu: subclass ném exception trên phương thức của parent
public class Bird {
    public void fly() {
        System.out.println("Flying!");
    }
}

public class Ostrich extends Bird {
    @Override
    public void fly() {
        throw new UnsupportedOperationException("Ostriches don't fly!");
    }
}

// Code client — sẽ hỏng khi Ostrich được thay thế vào
public void makeBirdsFly(List<Bird> birds) {
    for (Bird bird : birds) {
        bird.fly(); // ClassCastException hoặc UnsupportedOperationException!
    }
}
```

**Ví dụ tuân thủ LSP:**
```java
// Tốt: tách theo hành vi
public interface Bird {
    void sing();
}

public interface FlyingBird extends Bird {
    void fly();
}

public class Sparrow implements FlyingBird {
    @Override
    public void sing() { System.out.println("Chirping!"); }
    @Override
    public void fly() { System.out.println("Flying!"); }
}

public class Ostrich implements Bird {
    @Override
    public void sing() { System.out.println("Hissing!"); }
    // fly() vắng mặt — và điều đó đúng
}
```

**Khi nào dùng:**
- Luôn luôn khi thiết kế các hierarchy inheritance
- Khi tạo base class sẽ được mở rộng
- Khi làm việc với các collection của base type

## 🟡 Middle Level

### Cách Hoạt Động

LSP là nguyên tắc SOLID phức tạp nhất về mặt kỹ thuật. Nó không chỉ là về inheritance, mà về **Design by Contract**.

Các thuật ngữ Design by Contract:
- **Precondition** — các yêu cầu cho dữ liệu đầu vào (điều gì phải đúng TRƯỚC khi gọi)
- **Postcondition** — các đảm bảo về kết quả (điều gì sẽ đúng SAU khi gọi)
- **Invariant** — các điều kiện LUÔN LUÔN đúng cho một object
- **History Constraint** — object không được thay đổi trạng thái quá khứ một cách không thể dự đoán

**Các quy tắc contract của LSP:**

1. **Precondition không thể mạnh hơn**: Subclass không thể yêu cầu nhiều hơn parent. (Nếu parent chấp nhận bất kỳ số nào, subclass không thể chỉ yêu cầu số dương)
2. **Postcondition không thể yếu hơn**: Subclass phải đảm bảo ít nhất cùng kết quả như parent
3. **Invariant phải được bảo toàn**: Trạng thái object đúng với parent phải vẫn đúng với subclass
4. **History Constraint**: Subclass không được thay đổi trạng thái được coi là bất biến trong parent

### Cách Phát Hiện Vi Phạm LSP

**Dấu hiệu vi phạm:**

1. **`instanceof` trong code**: Nếu bạn kiểm tra loại object để gọi một phương thức cụ thể — hierarchy được thiết kế sai
2. **Phương thức rỗng**: Subclass ghi đè phương thức của parent với triển khai rỗng vì "nó không cần"
3. **Ném các exception không mong đợi**: Như trong ví dụ `UnsupportedOperationException`
4. **Tài liệu "không hỗ trợ"**: Javadoc override nói "Triển khai này không hỗ trợ..."

### Ứng Dụng Thực Tế

**Ví dụ kinh điển: Square và Rectangle**
```java
// Vi phạm LSP
public class Rectangle {
    protected int width;
    protected int height;

    public void setWidth(int width) { this.width = width; }
    public void setHeight(int height) { this.height = height; }
    public int getArea() { return width * height; }
}

public class Square extends Rectangle {
    @Override
    public void setWidth(int width) {
        this.width = width;
        this.height = width; // "Side effect"
    }

    @Override
    public void setHeight(int height) {
        this.width = height; // "Side effect"
        this.height = height;
    }
}

// Code client — sẽ hỏng khi Square được thay thế vào
public void testRectangle(Rectangle r) {
    r.setWidth(10);
    r.setHeight(20);
    // Với Rectangle: diện tích = 200
    // Với Square: diện tích = 400 — client bị sốc!
}
```

**Giải pháp đúng — composition, không phải inheritance:**
```java
// Tốt: interface thay vì inheritance
public interface Shape {
    int getArea();
}

public class Rectangle implements Shape {
    private int width;
    private int height;

    public Rectangle(int width, int height) {
        this.width = width;
        this.height = height;
    }

    public void setWidth(int width) { this.width = width; }
    public void setHeight(int height) { this.height = height; }
    @Override
    public int getArea() { return width * height; }
}

public class Square implements Shape {
    private int side;

    public Square(int side) { this.side = side; }
    @Override
    public int getArea() { return side * side; }
}
```

### Các Lỗi Thường Gặp

1. **Lỗi**: Inheritance để tái sử dụng code ("chúng có các trường chung!")
   **Giải pháp**: Dùng composition thay vì inheritance

2. **Lỗi**: `java.util.Collections.unmodifiableList()` ném `UnsupportedOperationException` trên `add()`
   **Giải pháp**: Đây là một vi phạm LSP đã biết. Dùng wrapper `ReadOnlyList` với một interface chỉ đọc

3. **Lỗi**: Sửa đổi invariant của parent
   **Giải pháp**: Ghi chép rõ ràng các invariant của mỗi class

### Khi Nào LSP Đặc Biệt Quan Trọng

- API công khai và thư viện (người dùng mong đợi hành vi có thể dự đoán)
- Framework với plugin/extension
- Các hệ thống với các collection polymorphic

## 🔴 Senior Level

### Triển Khai Nội Bộ Và Kiến Trúc

LSP là về **tính có thể dự đoán của hành vi**. Inheritance là một **nghĩa vụ** tuân thủ tất cả các invariant của parent. Nếu subclass hành xử "kỳ lạ" từ góc nhìn của client base class — LSP bị vi phạm.

Ở cấp độ Senior, quan trọng là nói bằng các thuật ngữ ràng buộc contract:

| Ràng buộc         | Quy tắc                                       | Ví dụ vi phạm                                                                    |
| ------------------ | ------------------------------------------ | ------------------------------------------------------------------------------------ |
| **Precondition**  | Không thể mạnh hơn                     | `SavingsAccount.withdraw` yêu cầu `amount <= balance`, trong khi `Account` cho phép overdraft |
| **Postcondition** | Không thể yếu hơn                         | `FastSort` có thể trả về mảng chỉ được sắp xếp một phần                                         |
| **Invariant**     | Phải được bảo toàn                          | `Square` thay đổi `width` khi `setHeight` được gọi                                  |
| **History**        | Trạng thái không được thay đổi không thể dự đoán         | `CachingList` trả về dữ liệu cũ                                                    |

// Câu hỏi chính: nếu code client được viết cho Account và dựa vào
// overdraft, thay thế bằng SavingsAccount sẽ phá vỡ logic của nó.
// Nếu client KHÔNG dựa vào overdraft — không có vi phạm LSP.

### LSP Và Typing Trong Java

Java hỗ trợ LSP ở cấp độ compiler thông qua **covariant return type**:
```java
public class Parent {
    public Number get() { return 1; }
}

public class Child extends Parent {
    @Override
    public Integer get() { return 1; } // Covariance: Integer là một Number. OK.
}
```

Tuy nhiên, compiler **không thể kiểm tra tính đúng đắn về ngữ nghĩa** (như trong ví dụ Square và Rectangle). Đây là trách nhiệm của kiến trúc sư.

**Contravariance của tham số** (không được hỗ trợ trong Java):
```
// Về mặt lý thuyết chấp nhận được trong LSP:
// Nếu Parent.accept(Object o), thì Child.accept(String s) — thu hẹp loại
// Nhưng Java không cho phép điều này khi override
```

### Vấn Đề Fragile Base Class

LSP bảo vệ chúng ta khỏi các tình huống mà thay đổi logic nội bộ của một subclass phá vỡ logic mà client dựa vào.

- **Ví dụ kinh điển**: `ArrayList` vs `Collections.unmodifiableList()`
  - `unmodifiableList` là một wrapper trên `List`, nhưng ném `UnsupportedOperationException` trên `add()`
  - **Đây là một vi phạm LSP**, vì một client mong đợi một `List` không sẵn sàng cho hành vi này

### Đánh Đổi Kiến Trúc

**Tuân thủ LSP nghiêm ngặt:**
- ✅ Ưu điểm: Hành vi có thể dự đoán, inheritance đáng tin cậy, lỗi runtime tối thiểu
- ❌ Nhược điểm: Giới hạn tái sử dụng code, yêu cầu thiết kế cẩn thận hơn

**Composition thay vì inheritance:**
- ✅ Ưu điểm: Tự do hành vi hoàn toàn, không có nghĩa vụ với contract của parent
- ❌ Nhược điểm: Nhiều boilerplate code hơn, cần ủy quyền các phương thức

### Edge Cases

1. **Pattern Template Method**: Base class định nghĩa thuật toán, subclass — các bước. Điều này có vi phạm LSP không?
   - **Trả lời**: Không, nếu các subclass không thay đổi invariant của thuật toán. Nhưng nếu một bước có thể "phá vỡ" thuật toán — đó là một vi phạm

2. **Decorator**: Các wrapper thêm hành vi. Chúng có vi phạm LSP không?
   - **Trả lời**: Không, nếu chúng ủy quyền tất cả các phương thức cho object gốc và không thay đổi invariant của nó

3. **Proxy và Mock**: Dynamic proxy để testing
   - **Trả lời**: Có thể vi phạm LSP nếu chúng không tái tạo tất cả các postcondition của bản gốc

### Hiệu Năng

- **Virtual dispatch**: Gọi một phương thức đã override = sự gián tiếp. JIT thực hiện **inline caching** và **class hierarchy analysis**
- **Inlining barrier**: Nếu JIT không thể chứng minh rằng một phương thức không bị override — nó không thể inline. Điều này ảnh hưởng đến hiệu năng trong hot path
- **Escape Analysis**: Khi tạo các object subclass, JVM có thể tối ưu việc cấp phát, nhưng chỉ khi hierarchy đã biết tại giai đoạn JIT

### Kinh Nghiệm Production

**Kịch bản production thực tế:**

Một dự án dùng `BaseRepository` với một phương thức `save(Entity)`. Một subclass `AuditRepository` đã override `save()` và thêm logging **sau khi** lưu. Một subclass khác `ValidatingRepository` — validation **trước khi** lưu.

Khi `CachingRepository` xuất hiện, nó đã override `save()` và thêm caching **thay vì** DB — mọi thứ hỏng: validation không hoạt động, audit không log.

**Giải pháp**: Thay thế inheritance bằng một chuỗi các decorator (Decorator Pattern), nơi mỗi cái thêm hành vi của nó vào `save()` gốc.

### Monitoring Và Chẩn Đoán

**Cách phát hiện vi phạm LSP trong code:**

1. **Dấu hiệu Code Review**:
   - Nếu `instanceof` được dùng để né tránh các hành vi khác nhau thay vì polymorphism — đây là một vi phạm LSP. Pattern matching với sealed type là một ngoại lệ hợp pháp.
   - Các phương thức override rỗng
   - `throw new UnsupportedOperationException(...)`

2. **Dấu hiệu Unit Test**:
   - Test cho base class thất bại khi chạy với subclass
   - Hành vi khác nhau của cùng một phương thức cho các subclass khác nhau

3. **Công cụ**:
   - Mutation Testing (Pitest): xác minh rằng test bắt được các thay đổi hành vi
   - ArchUnit: xác minh rằng các subclass không dùng các pattern bị cấm

### Best Practices Cho Highload

- **Sealed Interface (Java 17+)**: Giới hạn hierarchy — compiler kiểm tra tính đầy đủ, JIT tối ưu dispatch
- **Immutability**: Các object bất biến dễ tương thích LSP hơn (không có mutable state = không vi phạm invariant)
- **Contract Testing**: Viết test cho các contract của base type và chạy chúng cho tất cả subclass

### Mối Quan Hệ Với Các Nguyên Tắc Khác

- **LSP ← OCP**: Nếu các subclass được thay thế đúng cách, hệ thống mở để mở rộng
- **LSP ← SRP**: Các class nhỏ với một trách nhiệm dễ kế thừa đúng cách hơn
- **LSP → ISP**: Tách interface tự động giúp tuân thủ LSP, vì contract trở nên nhỏ hơn

### Tóm Tắt Cho Senior

- LSP là về **tính có thể dự đoán của hành vi**, không phải cú pháp inheritance
- Inheritance là một **nghĩa vụ** tuân thủ tất cả các invariant của parent
- Nếu subclass hành xử "kỳ lạ" từ góc nhìn của client base class — LSP bị vi phạm
- Nhớ: Square về mặt hình học là một trường hợp đặc biệt của Rectangle, nhưng trong OOP `Square` không thể kế thừa từ `Rectangle` với các phương thức `setWidth/setHeight`
- **Composition over Inheritance**: LSP thường bị vi phạm khi cố gắng tiết kiệm code thông qua inheritance. Một Senior developer sẽ ưu tiên composition

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- LSP: các object subclass phải có thể thay thế cho các object base class mà không phá vỡ tính đúng đắn
- Design by Contract: precondition không thể mạnh hơn, postcondition không thể yếu hơn, invariant phải được bảo toàn
- Ví dụ vi phạm kinh điển — Square extends Rectangle (side effect trong setter)
- `UnsupportedOperationException` trong một subclass — dấu hiệu rõ ràng vi phạm LSP
- `instanceof` trong code để né tránh các hành vi khác nhau = LSP bị vi phạm
- Composition được ưu tiên hơn inheritance để tuân thủ LSP
- `java.util.Date` / `java.sql.Date` — một vi phạm LSP đã biết trong JDK

**Các câu hỏi phụ thường gặp:**
- **Cách phát hiện vi phạm LSP?** — Test base class thất bại cho subclass, kiểm tra `instanceof`, các phương thức override rỗng
- **Fragile Base Class Problem là gì?** — Thay đổi parent phá vỡ tất cả subclass một cách không thể dự đoán
- **LSP có thể bị vi phạm với interface không?** — Có, nếu triển khai ném các exception không mong đợi hoặc thay đổi contract
- **Contract Testing là gì?** — Các test chung cho một interface, chạy cho tất cả các triển khai

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**

- "Nếu compiler không phàn nàn — LSP được tuân thủ" (LSP là một nguyên tắc ngữ nghĩa, không phải cú pháp)
