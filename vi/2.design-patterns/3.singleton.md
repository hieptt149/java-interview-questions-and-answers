# What is Singleton? (Singleton là gì?)

## Junior Level

**Singleton** là một pattern đảm bảo một class sẽ chỉ có **duy nhất một instance (thực thể)**.

**Tại sao:** Khi một tài nguyên được chia sẻ (file log, kết nối DB, cấu hình) và việc có nhiều bản sao sẽ dẫn đến xung đột hoặc trạng thái không nhất quán.

**Ví dụ minh họa đơn giản:** Một quốc gia chỉ có thể có một tổng thống. Nếu bạn hỏi "ai là tổng thống?", bạn sẽ luôn nhận được cùng một người.

**Cách hoạt động:**
1. Constructor riêng tư (private) (không thể tạo thông qua `new`)
2. Trường tĩnh (static field) chứa instance duy nhất
3. Phương thức tĩnh (static method) để lấy instance đó

**Ví dụ:**
```java
public class Logger {
    // 1. Instance duy nhất
    private static Logger instance = new Logger();

    // 2. Constructor riêng tư
    private Logger() {}

    // 3. Phương thức để lấy instance
    public static Logger getInstance() {
        return instance;
    }

    public void log(String message) {
        System.out.println(message);
    }
}

// Cách sử dụng — luôn luôn là cùng một đối tượng
Logger logger1 = Logger.getInstance();
Logger logger2 = Logger.getInstance();
System.out.println(logger1 == logger2); // true (cùng một đối tượng!)
```

**Khi nào nên sử dụng:**
- Logger (một cái duy nhất cho toàn bộ ứng dụng)
- Cấu hình (Configuration) (một file settings duy nhất)
- Kết nối DB (connection pool)

### Singleton vs static class

Singleton có thể triển khai một interface (khả năng kiểm thử thông qua mock), static class — thì không thể.
Singleton hỗ trợ khởi tạo lười (lazy initialization), static class được khởi tạo ngay khi class được load.

## Middle Level

### Các cách triển khai Singleton

**1. Early Initialization (khởi tạo sớm, đơn giản):**
```java
public class Singleton {
    private static Singleton instance = new Singleton(); // Khi class được load
    private Singleton() {}
    public static Singleton getInstance() { return instance; }
}
// An toàn với luồng (thread-safe)
// Không lười (được tạo ra ngay cả khi không cần dùng đến)
```

**2. Lazy Initialization (khởi tạo lười):**
```java
public class Singleton {
    private static Singleton instance;
    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) {
            instance = new Singleton();
        }
        return instance;
    }
}
// Lười (lazy)
// KHÔNG an toàn với luồng!
```

**3. Thread-Safe (an toàn với luồng, dùng synchronized):**
```java
public class Singleton {
    private static Singleton instance;
    private Singleton() {}

    public static synchronized Singleton getInstance() {
        if (instance == null) {
            instance = new Singleton();
        }
        return instance;
    }
}
// An toàn với luồng
// Chậm: synchronized thêm ~10-50ns cho mỗi lần gọi, quan trọng trong các hot path với hàng triệu lần gọi.
```

**4. Enum Singleton (tốt nhất):**
```java
public enum Singleton {
    INSTANCE;

    public void doWork() {
        System.out.println("Working...");
    }
}

// Cách sử dụng
Singleton.INSTANCE.doWork();
// An toàn với luồng
// Được bảo vệ khỏi reflection
// Được bảo vệ khỏi serialization
```

### Cách để "phá vỡ" Singleton

**1. Reflection:**
```java
// Singleton thông thường có thể bị phá vỡ
Constructor<Singleton> constructor = Singleton.class.getDeclaredConstructor();
constructor.setAccessible(true);
Singleton fake = constructor.newInstance();  // Instance thứ hai!

// Enum thì được bảo vệ
Constructor<SingletonEnum> constructor = SingletonEnum.class.getDeclaredConstructor();
// → IllegalArgumentException: Cannot reflectively create enum objects
```

**2. Serialization:**
```java
// Khi deserialization, một đối tượng mới được tạo ra
ObjectOutputStream out = ...;
out.writeObject(Singleton.getInstance());

ObjectInputStream in = ...;
Singleton another = (Singleton) in.readObject();  // Đối tượng mới!

// Giải pháp: phương thức readResolve()
private Object readResolve() {
    return getInstance();  // Trả về instance hiện có
}
```

**3. ClassLoader:**
```java
// Nhiều ClassLoader → nhiều Singleton!
// Một cái trong Tomcat, một cái khác trong OSGi
```

### Singleton trong Spring

```java
// Spring tự quản lý Singleton
@Component  // Mặc định là Singleton scope!
public class UserService { }

// Luôn luôn là cùng một bean
@Autowired UserService service1;
@Autowired UserService service2;
// service1 == service2 → true
```

### Các lỗi thường gặp

1. **Singleton thay vì DI**
   ```java
   // Sự phụ thuộc bị ẩn giấu
   public class OrderService {
       public void create() {
           Logger.getInstance().log("...");  // Sự phụ thuộc bị ẩn giấu!
       }
   }

   // Cách tiếp cận DI
   public class OrderService {
       private final Logger logger;
       public OrderService(Logger logger) { this.logger = logger; }
   }
   ```

2. **Trạng thái có thể thay đổi (mutable state) trong Singleton**
   ```java
   // Singleton có thể thay đổi = các vấn đề về đồng thời (concurrency)
   public class Counter {
       private int count = 0;  // Race condition (điều kiện tranh chấp)!
       public void increment() { count++; }
   }
   ```

## Senior Level

### Tính ngữ cảnh (Contextuality) của Singleton

**"Instance duy nhất" chỉ mang tính tương đối:**

| Ngữ cảnh                    | Tính duy nhất                                          |
| -------------------------- | ----------------------------------------------------- |
| **JVM**                    | Một instance cho mỗi JVM                                |
| **ClassLoader**            | Một instance cho mỗi ClassLoader (có thể có nhiều!)              |
| **Spring Context**         | Một instance cho mỗi ApplicationContext                          |
| **Hệ thống phân tán (Distributed system)**     | **KHÔNG TỒN TẠI** (cần có distributed lock)         |

**Trong một cluster:**
```
Node 1: Singleton instance A
Node 2: Singleton instance B
Node 3: Singleton instance C
→ 3 instance! Cần Redis/Zookeeper để điều phối
```

### Java Memory Model và Singleton

JMM (Java Memory Model) — bộ đặc tả (specification) định nghĩa cách các luồng (threads) nhìn thấy bộ nhớ của nhau.
Bill Pugh Singleton — được đặt tên theo nhà nghiên cứu đã đề xuất giải pháp static inner class.
SRP (Single Responsibility Principle — Nguyên lý trách nhiệm đơn nhất).

**Vấn đề về tính khả kiến (visibility) khi không có volatile:**
```java
// Code không an toàn
public class UnsafeSingleton {
    private static UnsafeSingleton instance;

    public static UnsafeSingleton getInstance() {
        if (instance == null) {
            instance = new UnsafeSingleton();
        }
        return instance;
    }
}

// Thread 1: cấp phát bộ nhớ → công bố tham chiếu → gọi constructor
// Thread 2: thấy instance != null → nhận được đối tượng CHƯA ĐƯỢC KHỞI TẠO ĐẦY ĐỦ!

// Giải pháp: volatile + double-checked locking
private static volatile UnsafeSingleton instance;

public static UnsafeSingleton getInstance() {
    UnsafeSingleton local = instance;
    if (local == null) {
        synchronized (UnsafeSingleton.class) {
            local = instance;
            if (local == null) {
                instance = local = new UnsafeSingleton();
            }
        }
    }
    return local;
}
```

**Tại sao volatile lại quan trọng:**
- Không có volatile: có thể xảy ra tái sắp xếp lệnh (instruction reorder) (cấp phát bộ nhớ → công bố → constructor)
- Có volatile: đảm bảo happens-before → constructor HOÀN THÀNH trước khi công bố

### Singleton như một Anti-pattern

**Các vấn đề:**

1. **Tight Coupling (Sự phụ thuộc chặt chẽ)**
   ```java
   // Sự phụ thuộc không nhìn thấy được trong chữ ký (signature)
   public class OrderService {
       public void process() {
           Database.getInstance().save(...);  // Sự phụ thuộc bị ẩn giấu!
       }
   }
   ```

2. **Khả năng kiểm thử (Testability)**
   ```java
   // Không thể mock được
   @Test
   void testOrder() {
       // Singleton giữ nguyên trạng thái giữa các bài test!
       // Không thể thay thế Database.getInstance()
   }
   ```

3. **Vi phạm SRP**
   ```java
   // Class này chịu trách nhiệm cho:
   // 1. Logic nghiệp vụ
   // 2. Quản lý vòng đời của chính nó
   // 3. Truy cập đồng thời (concurrent access)
   ```

4. **Rò rỉ bộ nhớ (Memory Leak)**
   ```java
   // Singleton sống mãi mãi (static field)
   // Trong Tomcat khi redeploy → ClassLoader cũ không bị GC
   // → Rò rỉ Metaspace
   ```

### Bill Pugh Singleton (Static Holder)

```java
public class BillPughSingleton {
    private BillPughSingleton() {
        if (INSTANCE_HOLDER.INSTANCE != null) {
            throw new IllegalStateException("Already initialized");
        }
    }

    private static class INSTANCE_HOLDER {
        static final BillPughSingleton INSTANCE = new BillPughSingleton();
    }

    public static BillPughSingleton getInstance() {
        return INSTANCE_HOLDER.INSTANCE;
    }
}

// JVM đảm bảo:
// 1. Tính lười (Laziness) (class chỉ được load ở lần gọi đầu tiên)
// 2. An toàn với luồng (Thread-safety) (việc khởi tạo class vốn đã an toàn với luồng)
// 3. Không có chi phí phát sinh của synchronized
```

### GC và Singleton

```java
// Singleton sẽ KHÔNG bị GC trong khi:
// 1. ClassLoader vẫn còn sống
// 2. Vẫn còn tham chiếu đến trường static

// Trong Java tiêu chuẩn: ClassLoader sống cho đến khi tiến trình kết thúc
// → Singleton sống "mãi mãi"

// Trong Tomcat/OSGi: ClassLoader có thể bị unload
// → Nhưng Singleton lại ngăn cản việc GC → Rò rỉ bộ nhớ (Memory Leak)
```

### Kinh nghiệm Production

**Tình huống thực tế #1: Singleton giết chết khả năng kiểm thử**
- 500 bài test, tất cả đều sử dụng `Config.getInstance()`
- Vấn đề: các bài test phụ thuộc lẫn nhau (trạng thái được chia sẻ)
- Giải pháp: chuyển sang dùng Spring DI
- Kết quả: các bài test được cô lập, có thể thực thi song song

**Tình huống thực tế #2: Singleton trong một cluster**
- Bộ sinh ID (ID generator) được triển khai như Singleton
- Vấn đề: 5 node trong cluster → 5 bộ sinh ID → trùng lặp ID!
- Giải pháp: dùng Redis INCR để sinh ID
- Bài học: Singleton != tính duy nhất trong hệ thống phân tán

### Best Practices (Thực hành tốt nhất)

1. **ĐỪNG tự viết Singleton thủ công** trong các ứng dụng Spring
2. **Sử dụng DI** (`@Component` = Singleton scope)
3. **Enum** — an toàn nhất cho các thư viện/SDK
4. **Bill Pugh** — dành cho việc khởi tạo lười
5. **Tránh trạng thái có thể thay đổi (mutable state)** trong Singleton
6. **readResolve()** để bảo vệ khỏi serialization
7. **Kiểm tra trong constructor** để bảo vệ khỏi reflection
8. **Trong các cluster** → dùng Redis/Zookeeper để điều phối

### Tóm tắt cho Senior

- **Singleton != tính duy nhất trong hệ thống phân tán** — chỉ đúng trong phạm vi một JVM
- **Enum** — cách bảo vệ duy nhất khỏi các cuộc tấn công reflection/serialization
- **DI container** thay thế cho Singleton thủ công trong 99% trường hợp
- **Memory Model:** volatile rất quan trọng đối với DCL
- **Khả năng kiểm thử:** Singleton = kẻ thù số 1 của unit test
- **GC:** Singleton sống mãi mãi — hãy cẩn thận với tài nguyên
- **Bill Pugh** = tính lười + an toàn với luồng mà không cần synchronized
- **Sự phụ thuộc bị ẩn giấu** = phụ thuộc chặt chẽ = nợ kỹ thuật (technical debt)

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Singleton đảm bảo một instance duy nhất của class thông qua private constructor + phương thức truy cập tĩnh
- Enum Singleton — an toàn nhất: được bảo vệ khỏi reflection và serialization ngay từ đầu
- Bill Pugh (Static Holder) — khởi tạo lười mà không cần synchronized, thông qua static inner class
- Trong Spring @Component = Singleton scope theo mặc định, ĐỪNG tự viết Singleton thủ công
- Singleton không hoạt động trong một cluster — mỗi node sẽ tự tạo instance riêng của mình
- Không có volatile trong DCL, việc tái sắp xếp lệnh có thể xảy ra: luồng nhận được đối tượng chưa được khởi tạo đầy đủ
- Singleton được coi là một anti-pattern: vi phạm SRP, DIP, khả năng kiểm thử

**Các câu hỏi phụ thường gặp:**
- **Làm sao để "phá vỡ" Singleton?** — Reflection (tạo instance mới), serialization (deserialization tạo ra đối tượng mới), ClassLoader (nhiều loader)
- **Tại sao Enum tốt hơn Singleton thông thường?** — JVM cấm việc tạo enum thông qua reflection, serialization hoạt động đúng đắn
- **Khi nào Singleton có thể chấp nhận được?** — Logger, cấu hình, cache — các đối tượng stateless hoặc immutable
- **Bill Pugh Singleton là gì?** — Khởi tạo lười thông qua static inner class, JVM đảm bảo tính an toàn với luồng

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi dùng Singleton để lưu trữ trạng thái trong Spring" — Spring quản lý điều này thông qua DI
- "Singleton hoạt động trong một cluster" — mỗi node sẽ tự tạo instance riêng của mình
- "Singleton của tôi an toàn với luồng mà không cần volatile" — DCL không có volatile = hành vi không xác định (undefined behavior)
- "Singleton là pattern tốt nhất" — đây là một trong những pattern bị chỉ trích nhiều nhất
