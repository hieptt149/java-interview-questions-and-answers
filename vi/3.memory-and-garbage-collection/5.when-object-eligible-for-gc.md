# When does an object become eligible for GC? (Khi nào một đối tượng đủ điều kiện để được GC dọn dẹp?)

## Junior Level

Một đối tượng trở nên **đủ điều kiện để bị loại bỏ** khi nó không thể được tiếp cận từ bất kỳ GC Root nào.

**GC Roots** — các điểm đầu vào (entry point) mà từ đó GC bắt đầu duyệt: các biến cục bộ trong stack, các trường tĩnh (static field), các luồng đang hoạt động, các tham chiếu JNI. Nếu một đối tượng không thể tiếp cận được từ GC Roots — nó là rác, ngay cả khi có các tham chiếu từ những đối tượng không thể tiếp cận khác ("islands of isolation" — đảo cô lập).

**Quy tắc đơn giản:** Không có đường đi từ GC Root → đối tượng là rác → GC sẽ loại bỏ nó.

**Ví dụ:**
```java
public void example() {
    String s = new String("hello");  // Đối tượng được tạo
    s = null;                        // Tham chiếu bị xóa → đối tượng trở thành rác!

    String s2 = new String("world"); // Đối tượng mới
    // Khi phương thức kết thúc → s2 bị loại khỏi Stack
    // → đối tượng "world" không còn truy cập được → rác!
}
```

**GC Roots — các điểm khởi đầu:**
- Các biến cục bộ trong Stack
- Các trường tĩnh (static field) của class
- Các luồng đang hoạt động

Nếu một đối tượng **không thể được tiếp cận** từ GC Roots → nó là rác.

## Middle Level

### Reachability Analysis (Phân tích khả năng tiếp cận)

Java dùng cách **duyệt đồ thị (graph traversal)** từ GC Roots, chứ không phải đếm tham chiếu (reference counting) (như Python):

```
GC Roots:
├── Các biến trong Stack (biến cục bộ của các luồng)
├── Các trường tĩnh của class
├── Các luồng đang hoạt động (đối tượng Thread)
├── Các tham chiếu JNI (từ native code)
└── Các đối tượng nội bộ của JVM

Đối tượng còn sống nếu:
  Có một đường đi từ bất kỳ GC Root nào → đối tượng

Đối tượng là rác nếu:
  Không có đường đi từ GC Root → đối tượng
```

### Tại sao không dùng Reference Counting?

```java
// Reference Counting (Python) không hoạt động với các chu trình (cycle):
class Node { Node next; }

Node a = new Node();
Node b = new Node();
a.next = b;  // a → b
b.next = a;  // b → a

a = null;
b = null;

// Reference Counting:
//   a.refCount = 1 (b tham chiếu a)
//   b.refCount = 1 (a tham chiếu b)
//   → Không bao giờ bị xóa! "Island of Isolation" (đảo cô lập)

// Reachability Analysis (Java):
//   Không có đường đi từ GC Roots → a và b → cả hai bị xóa! ✅
```

### Tối ưu hóa Reachability của JIT

```java
public void process() {
    HeavyResource res = new HeavyResource();
    res.doAction();

    // JIT thấy: 'res' không còn được dùng nữa
    // → Đối tượng có thể bị GC loại bỏ ngay bây giờ!
    // Ngay cả khi phương thức process() vẫn còn đang chạy!

    doSomethingElse();  // res có thể đã bị xóa
}
```

### Các loại Reference (java.lang.ref)

| Loại         | Khi nào bị loại bỏ        | Trường hợp sử dụng |
| ------------ | ------------------------ | ------------------ |
| **Strong**   | Không bao giờ (tham chiếu thông thường) | Các đối tượng nghiệp vụ |
| **Soft**     | Khi bộ nhớ thấp          | Cache              |
| **Weak**     | Ở lần thu gom tiếp theo  | WeakHashMap        |
| **Phantom**  | Sau khi finalization     | Dọn dẹp tài nguyên |

```java
// Soft Reference — cho cache
SoftReference<ExpensiveObject> ref = new SoftReference<>(obj);
ExpensiveObject cached = ref.get();  // null nếu GC đã loại bỏ

// Weak Reference — cho WeakHashMap
WeakReference<User> ref = new WeakReference<>(user);
// GC sẽ loại bỏ ở lần thu gom tiếp theo nếu không có Strong reference nào
```

### Các lỗi thường gặp

1. **Quên xóa tham chiếu**
   ```java
   // ❌ Đối tượng sẽ không bị xóa khi list còn sống
   static List<Object> cache = new ArrayList<>();
   cache.add(expensiveObject);  // Quên xóa → rò rỉ!
   ```

2. **finalize() — "hồi sinh" (resurrection) đối tượng**
   ```java
   // ❌ Trong finalize() bạn có thể gán this cho một biến tĩnh
   // → Đối tượng sẽ "hồi sinh"!
   protected void finalize() {
       GlobalCache.add(this);  // Hồi sinh!
   }
   ```
   // finalize() chỉ được gọi một lần. Nếu bạn gán `this` cho một trường tĩnh
   // — đối tượng lại trở nên có thể tiếp cận được. Điều này gọi là "resurrection" (hồi sinh).
   // Trong Java 9+ finalize() đã bị deprecated — hãy dùng Cleaner.

## Senior Level

### GC Roots: Phân loại đầy đủ

```
GC Roots bao gồm:
├── Stack Locals (biến cục bộ của các phương thức đang hoạt động)
├── Stack Parameters (tham số của các phương thức trong stack)
├── Static Fields (trường tĩnh của các class đã được nạp)
├── JNI Global References (tham chiếu toàn cục từ native code)
├── JNI Local References (tham chiếu cục bộ trong các phương thức JNI)
├── Thread Objects (bản thân các đối tượng Thread — khi chưa kết thúc)
├── Monitor Used (các đối tượng trong synchronized/wait)
├── System Dictionary (các class đã được nạp)
├── JVM Internal (các exception được cấp phát trước, các ClassLoader)
└── Unreachable Finalizer Queue (các đối tượng trong hàng đợi finalization)
```

### JIT Reachability: reachabilityFence

```java
// Vấn đề: đối tượng có thể bị xóa trong lúc native code đang thực thi
public void nativeAction() {
    NativeResource res = new NativeResource();
    res.doNativeOperation();  // Thao tác native (chạy lâu)

    // JIT thấy: 'res' không được dùng sau lời gọi
    // → Có thể xóa res TRƯỚC KHI thao tác native hoàn tất!
    // → Native code sẽ crash!
}

// Giải pháp: reachabilityFence (Java 9+)
public void nativeAction() {
    NativeResource res = new NativeResource();
    res.doNativeOperation();
    Reference.reachabilityFence(res);  // Đảm bảo: res còn sống cho đến đây!
}
```

### Đào sâu Reference API

```java
// Soft Reference — công thức dọn dẹp
// JVM dọn dẹp khi:
//   idle_time < free_memory × SoftRefLRUPolicyMSPerMB
// Mặc định: 1000 ms cho mỗi MB heap trống

// Trên các heap lớn (32 GB):
//   32 GB × 1000 ms/MB = 32,000 giây = 9 giờ!
//   → SoftReference có thể sống hàng giờ sau khi "chết"

// Tinh chỉnh: -XX:SoftRefLRUPolicyMSPerMB=100
//   → Dọn dẹp ở mức 100 ms/MB → tích cực hơn

// Weak Reference — được dọn ở lần thu gom TIẾP THEO
// → Không chờ đến khi thiếu bộ nhớ!

// Phantom Reference — get() luôn trả về null
// → Chỉ dùng để theo dõi việc loại bỏ
// → Thay thế finalize()
```

### Reference Handler Thread

```
JVM có một luồng ưu tiên cao — Reference Handler

Khi GC phát hiện sự thay đổi về reachability:
  1. Đối tượng được đưa vào Pending List
  2. Reference Handler lấy ra khỏi Pending List
  3. Đưa vào ReferenceQueue (được chỉ định lúc tạo)
  4. Ứng dụng poll queue → thực thi logic

→ Cơ chế bất đồng bộ, không chặn GC
```

### Cleaner (Java 9+)

```java
// Thay thế cho finalize()
public class NativeResource implements AutoCloseable {
    private static final Cleaner CLEANER = Cleaner.create();
    private final Cleaner.Cleanable cleanable;
    private final NativeHandle handle;

    public NativeResource() {
        this.handle = nativeAllocate();
        // Lambda KHÔNG có tham chiếu đến this → không có "hồi sinh"!
        this.cleanable = CLEANER.register(this, () -> {
            nativeFree(handle);  // Dọn dẹp bộ nhớ native
        });
    }

    @Override
    public void close() {
        cleanable.clean();  // Dọn dẹp thủ công
    }
}

// Khi GC: nếu không có Strong reference → Cleaner gọi lambda
// Khi close(): dọn dẹp thủ công không cần chờ GC
```

### Kinh nghiệm Production

**Tình huống thực tế: JIT xóa đối tượng quá sớm**
- Thư viện JNI: thao tác native 100 ms
- Đối tượng Java bị GC xóa sau lời gọi phương thức native
- Native code truy cập vào bộ nhớ đã được giải phóng → SEGFAULT
- Giải pháp: `reachabilityFence(obj)` sau lời gọi native

### Best Practices

1. **Đừng dựa vào finalize()** — hãy dùng Cleaner/try-with-resources
2. **SoftReference** cho cache, nhưng hãy tinh chỉnh `SoftRefLRUPolicyMSPerMB`
   Đừng dùng SoftReference làm cơ chế cache duy nhất trong production —
   hãy dùng Caffeine/Guava với các giới hạn tường minh. SoftReference có thể gây ra
   áp lực GC quá mức khi tải cao.
3. **WeakReference** cho metadata và các registry
4. **reachabilityFence** cho các thao tác native
5. **Dọn dẹp các tham chiếu** trong các collection tĩnh
6. **Giám sát** ReferenceQueue cho các phantom reference
7. **Tránh** "hồi sinh" (resurrection) đối tượng

### Tóm tắt cho Senior

- **Reachability Analysis** = duyệt đồ thị từ GC Roots
- **Reference Counting** không được dùng (vấn đề chu trình)
- **JIT** có thể xóa đối tượng TRƯỚC KHI phương thức hoàn tất
- **reachabilityFence** (Java 9+) bảo vệ khỏi việc bị loại bỏ sớm
- **SoftReference** = cache, dọn dẹp khi bộ nhớ thấp
- **WeakReference** = metadata, dọn dẹp ở lần thu gom tiếp theo
- **PhantomReference** + **Cleaner** = thay thế cho finalize()
- **Reference Handler** = luồng bất đồng bộ để xử lý các reference

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Đối tượng đủ điều kiện để bị loại bỏ khi không thể tiếp cận từ GC Roots (không có đường đi từ bất kỳ root nào)
- Java dùng Reachability Analysis (duyệt đồ thị), không phải Reference Counting — điều này giải quyết vấn đề "island of isolation" (đảo cô lập)
- JIT có thể loại bỏ một đối tượng trước khi phương thức hoàn tất nếu nó thấy đối tượng không còn được dùng
- 4 loại reference: Strong (không bao giờ), Soft (khi bộ nhớ thấp), Weak (ở lần GC tiếp theo), Phantom (sau finalization)
- `finalize()` bị deprecated từ Java 9 — hãy dùng Cleaner hoặc try-with-resources
- `reachabilityFence(obj)` đảm bảo đối tượng không bị loại bỏ trong lúc thao tác native
- Hồi sinh đối tượng trong `finalize()` — anti-pattern; Cleaner không thể hồi sinh (lambda không có tham chiếu đến this)

**Các câu hỏi phụ thường gặp:**
- **Tại sao Java không dùng Reference Counting?** — Không phát hiện được các tham chiếu vòng (a→b→a), chi phí trên mỗi lần gán
- **"Island of isolation" là gì?** — Nhóm các đối tượng tham chiếu lẫn nhau nhưng không thể tiếp cận được từ GC Roots
- **Khi nào SoftReference được dọn dẹp?** — Khi thiếu bộ nhớ; công thức phụ thuộc vào `SoftRefLRUPolicyMSPerMB` (mặc định 1000 ms/MB)
- **Tại sao PhantomReference.get() luôn trả về null?** — Được thiết kế riêng chỉ để theo dõi sự kiện đối tượng bị loại bỏ

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Đối tượng bị xóa khi tất cả các tham chiếu là null" — điều quan trọng là reachability từ GC Roots, không phải các tham chiếu null
- "finalize() là một cách tốt để giải phóng tài nguyên" — bị deprecated, không dự đoán được, có thể hồi sinh đối tượng
- "JIT không ảnh hưởng đến vòng đời của đối tượng" — JIT có thể loại bỏ đối tượng trước khi phương thức hoàn tất
- "GC loại bỏ đối tượng ngay sau `obj = null`" — việc loại bỏ xảy ra ở lần thu gom tiếp theo nếu đối tượng không thể tiếp cận
