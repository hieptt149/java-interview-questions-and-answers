# Why String is Immutable (Tại sao String là bất biến)

## 🟢 Junior Level

**Tính bất biến (Immutability)** nghĩa là sau khi một object `String` được tạo, nội dung của nó không thể thay đổi. Không có method nào có thể sửa đổi các ký tự bên trong một chuỗi — thay vào đó, một chuỗi mới được tạo ra.

**Tại sao điều này quan trọng:**
1. **Bảo mật** — mật khẩu và đường dẫn file không thể bị giả mạo
2. **Thread safety** — các chuỗi có thể được truyền giữa các thread mà không cần đồng bộ hóa
3. **String Pool** — chỉ có thể tồn tại vì các chuỗi không thể thay đổi

**Ví dụ:**
```java
String s = "Hello";
s.toUpperCase();       // Tạo một chuỗi MỚI "HELLO"
System.out.println(s); // In ra "Hello" — bản gốc không thay đổi!
```

**Ví dụ minh họa đơn giản:** Một chuỗi giống như một cuốn sách đã in. Bạn không thể thay đổi văn bản trong một cuốn sách đã in — bạn cần in một cuốn mới thay vào đó.

## 🟡 Middle Level

### Cái Giá Của Tính Bất Biến

Mỗi lần sửa đổi (nối, thay thế, cắt chuỗi) tạo ra một object mới — điều này tạo áp lực GC. Trong các hệ thống độ trễ thấp cho các hot path, StringBuilder hoặc byte[] trực tiếp được sử dụng.

### Cách Nó Được Hiện Thực Trong JDK

1. **Class `final`:** `public final class String` — không thể kế thừa và các method không thể bị override
2. **Trường `final`:** `private final byte[] value` (Java 9+) — tham chiếu đến mảng không thể thay đổi
3. **Không có mutator:** Không có method như `setCharAt()` để thay đổi nội dung
4. **Defensive copying:** Các method `substring()`, `replace()`, `concat()` trả về các object **mới**

### Nơi Nó Được Dùng Trong Thực Tế
- **Key của HashMap/HashSet:** hashCode() được cache tại lần gọi đầu tiên và không bao giờ thay đổi
- **Các tham số bảo mật:** đường dẫn file, URL, credential — không thể thay đổi sau khi xác minh
- **Đa luồng:** các chuỗi được truyền giữa các thread mà không cần bất kỳ lock nào

### Các Lỗi Điển Hình
1. **Lỗi:** Kỳ vọng `replace()` thay đổi chuỗi tại chỗ
   **Giải pháp:** Nhớ gán lại kết quả: `s = s.replace("a", "b");`

2. **Lỗi:** Nối chuỗi trong vòng lặp qua `+`
   **Giải pháp:** Dùng `StringBuilder` — mỗi lần nối tạo một object mới

### So Sánh Với Các Lựa Chọn Thay Thế
| Loại          | Bất biến    | Thread-safe     | Cho việc sửa đổi  |
| ------------- | ------------ | --------------- | ------------------ |
| String        | Có          | Có             | Không                 |
| StringBuilder | Không           | Không              | Có (một thread) |
| StringBuffer  | Không           | Có (synchronized) | Có (nhiều thread) |

## 🔴 Senior Level

### Hiện Thực Nội Bộ

```java
// OpenJDK — cấu trúc String (Java 9+)
public final class String implements Serializable, Comparable<String>, CharSequence {
    @Stable
    private final byte[] value;  // COMPACT STRINGS: byte[] thay vì char[]
    private final byte coder;    // LATIN1=0 hoặc UTF16=1
    private int hash;            // hashCode được cache, mặc định là 0
    // ...
}
```

Annotation `@Stable` (JVM intrinsic) báo cho JIT compiler biết rằng trường `value` sẽ không thay đổi sau khi construct. Điều này cho phép các tối ưu hóa mạnh mẽ: constant folding, escape analysis.

### Đánh Đổi Về Kiến Trúc (Trade-off)

**Tại sao không mutable:**

1. **Bảo mật:** Các chuỗi được dùng trong `ClassLoader`, `SecurityManager`, kết nối mạng, các câu SQL query. Nếu các chuỗi mutable:
   ```java
   // Một kẻ tấn công có thể:
   checkAccess("/admin/config");  // Kiểm tra đã pass
   // ... sửa đổi chuỗi trong bộ nhớ ...
   readFile("/admin/config");     // Đọc một file khác!
   ```

2. **String Pool:** Nếu các chuỗi mutable, việc sửa đổi `"Hello"` ở một nơi sẽ thay đổi tất cả các tham chiếu đến literal này trong toàn bộ ứng dụng.

Nếu các chuỗi mutable, sửa đổi s1 cũng sẽ thay đổi s2,
vì chúng tham chiếu đến cùng một object trong pool. Tính bất biến đảm bảo
rằng một chuỗi trong pool là an toàn cho tất cả những ai tham chiếu đến nó.
```java
String s1 = "Hello";
String s2 = "Hello";
// s1 và s2 — cùng một object. Nếu s1 có thể sửa đổi, s2 cũng sẽ thay đổi theo.
```

3. **Tính ổn định của HashMap:** Một key mutable trong HashMap — mất dữ liệu khi hashCode thay đổi.

4. **Thread safety:** Các object bất biến an toàn với thread theo thiết kế. Không có race condition, không có `volatile`, không có lock.

### Các Trường Hợp Biên

1. **Reflection:** Trước Java 9, bạn có thể sửa đổi `value` qua `Field.setAccessible(true)`.
Trong Java 9, quyền truy cập theo module xuất hiện (JEP 261), và kể từ Java 16 (JEP 396) sự đóng gói mạnh (strong encapsulation)
được bật theo mặc định — `--add-opens` là bắt buộc để truy cập các trường nội bộ.

2. **StringBuilder bên dưới:** `String.format()`, `String.join()` bên trong sử dụng các buffer mutable, nhưng kết quả luôn là một String bất biến.

3. **Nối chuỗi String qua invokedynamic (Java 9+):** `StringConcatFactory` sinh code hiệu quả, nhưng kết quả vẫn bất biến.

### Hiệu Năng
- **Cấp phát:** String mới (Java 9+, Latin1, 10 ký tự) ≈ 48 byte (object + byte[])
- **GC:** Các object String tồn tại ngắn được xử lý hiệu quả bởi Young Gen (Eden → Survivor → chết)
- **hashCode được cache:** Được tính lazy một lần, sau đó truy cập O(1)

### Kinh Nghiệm Production
**Kịch bản:** Logging trong một service tải cao (100K request/giây):
- Mỗi chuỗi log tạo ra 3-5 object String tạm thời
- Không có Compact String: 500MB/giây cấp phát → Minor GC mỗi 200ms
- Có Compact String (Java 9+): 250MB/giây → Minor GC mỗi 400ms
- Giải pháp: structured logging (byte[] trực tiếp vào logging framework)

### Giám Sát
```java
// JOL — kích thước String thực tế
System.out.println(GraphLayout.parseInstance("Hello").toPrintable());
// java.lang.String object internals:
// OFFSET  SIZE  TYPE     DESCRIPTION
// 0       12             (object header)
// 12      4     byte[]   String.value
// 16      1     byte     String.coder
// ...
// Total: 24 bytes + array size
```

### Best Practices Cho Highload
- Cho các thao tác sửa đổi thường xuyên: `StringBuilder` với capacity chỉ định trước
- Cho việc trao đổi giữa các thread: `String` (thread-safe không cần lock)
- Cho việc parse văn bản lớn: làm việc trực tiếp với `byte[]`/`CharBuffer`, chuyển sang String chỉ khi cần
- Cân nhắc pattern `byte[]` + `coder` cho các hệ thống độ trễ cực thấp

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Tính bất biến = nội dung không thể thay đổi sau khi tạo, mọi sửa đổi tạo ra một object mới
- Hiện thực: class `final`, `final byte[] value`, annotation `@Stable`, không có mutator
- String Pool chỉ có thể tồn tại nhờ tính bất biến — nếu không thì việc thay đổi một chuỗi sẽ ảnh hưởng đến tất cả tham chiếu
- Thread-safe theo thiết kế — không cần lock, race condition là không thể xảy ra
- Bảo mật: các chuỗi được dùng trong SecurityManager, ClassLoader, các câu SQL query — chuỗi mutable = lỗ hổng
- Key của HashMap: hashCode() được cache và không bao giờ thay đổi

**Các câu hỏi phụ thường gặp:**
- **Tại sao String bất biến?** — 4 lý do: (1) String Pool — không thể với các chuỗi mutable, (2) Thread safety — không cần lock, (3) Bảo mật — đường dẫn, URL, credential không thể bị giả mạo, (4) Tính ổn định của HashMap — hashCode không thay đổi.
- **Cái giá của tính bất biến là gì?** — Áp lực GC khi sửa đổi. Mỗi lần nối/thay thế tạo một object mới.
- **Bạn có thể sửa đổi String qua reflection không?** — Về mặt kỹ thuật là có, nhưng nó phá vỡ contract, phá vỡ String Pool, HashMap, các tối ưu hóa JIT.
- **Dùng gì cho việc sửa đổi?** — `StringBuilder` (một thread), `StringBuffer` (nhiều thread), `byte[]` (cấp độ thấp).

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "`replace()` sửa đổi chuỗi tại chỗ" — trả về một chuỗi mới
- ❌ "String bất biến nghĩa là bạn không thể tạo chuỗi mới" — bạn có thể, bản gốc không thay đổi
- ❌ "String thread-safe vì nó là một class `final`" — thread-safe vì trạng thái không thay đổi
- ❌ "Reflection là một cách bình thường để sửa đổi String" — đây là một antipattern, vi phạm contract
