# What is Database per Service pattern (Database per Service pattern là gì)

## Junior Level

**Database per Service** — mỗi microservice có **database riêng của nó**, mà không ai khác dùng trực tiếp.

**Cái giá phải trả:** bạn không thể làm SELECT ... JOIN giữa các table của các service khác nhau nữa.
Thay vào đó — các lệnh gọi API hoặc replication dựa trên event.

```
Order Service -> Order DB
User Service -> User DB
Payment Service -> Payment DB
```

**Tại sao:**
- **Độc lập** — mỗi service có thể thay đổi schema của nó mà không ảnh hưởng đến các service khác
- **Cô lập** — DB của một service sập không ảnh hưởng đến các service khác
- **Linh hoạt** — các service khác nhau có thể dùng các database khác nhau (SQL, NoSQL)

---

## Middle Level

### Khi Nào KHÔNG Nên Dùng Database per Service

- **Team nhỏ** (2-3 dev) — không thể quản lý nhiều database
- **Startup ở giai đoạn validation** — schema thay đổi hàng ngày
- **Yêu cầu nhất quán nghiêm ngặt** cho reporting — khó khăn với eventual consistency

### Cách Các Service Lấy Dữ Liệu Của Nhau

**1. Gọi API:**
```
Order Service -> User Service API -> lấy dữ liệu user
```

**2. Dựa trên event:**
```
User Service -> event "UserUpdated" -> Order Service lắng nghe và cache
```

**3. CQRS:**
```
(CQRS — Command Query Responsibility Segregation, các model riêng biệt cho ghi và đọc.)
(Materialized View — biểu diễn dữ liệu được tính toán sẵn để truy vấn nhanh.)
Write model -> Order DB
Read model -> materialized view (từ các event)
```

### Các Lỗi Thường Gặp

1. **Shared database:**
```
Order Service -> table User trực tiếp
Vi phạm encapsulation -> coupling
```

## Senior Level

### Đánh Đổi Kiến Trúc

| Database per Service                                                                                                                                                                               | Shared Database           |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------- |
| Cô lập hoàn toàn                                                                                                                                                                                     | Đơn giản hơn                   |
| Eventual consistency: khi User Service cập nhật dữ liệu và publish một event, Order Service nhận nó với một độ trễ (ms hoặc giây). Trong khoảng thời gian này, Order Service thấy dữ liệu cũ.            | ACID transaction         |
| Truy vấn cross-service phức tạp                                                                                                                                                                      | JOIN cross-service       |
| Deployment độc lập                                                                                                                                                                             | Deployment phối hợp    |

### Kinh Nghiệm Production

**Polyglot persistence:**
```
(Polyglot Persistence — dùng các DBMS khác nhau cho các tác vụ khác nhau.)
User Service -> PostgreSQL
Session Service -> Redis
Analytics Service -> ClickHouse
Search Service -> Elasticsearch
```

### Database per Service vs Schema per Service

Bạn có thể có cô lập logic (các schema riêng biệt) trên một server database vật lý.
Đây là một thỏa hiệp: dễ vận hành hơn, nhưng ít cô lập hơn khi server sập.

### Best Practices

```
✅ Mỗi service — database riêng của nó
✅ API hoặc event để truy cập dữ liệu
✅ Polyglot persistence khi cần
✅ Eventual consistency

❌ Truy cập trực tiếp vào database của service khác
❌ Shared database giữa các service
❌ Distributed transaction mà không cần thiết
```

## Interview Cheat Sheet

**Cần phải biết:**
- Database per Service — mỗi microservice có database RIÊNG của nó, không ai khác dùng trực tiếp
- Độc lập: mỗi service thay đổi schema mà không ảnh hưởng cái khác, cô lập khi DB lỗi
- Các service lấy dữ liệu của nhau thông qua gọi API, event, hoặc CQRS
- Polyglot persistence — các service khác nhau có thể dùng các DBMS khác nhau
- Eventual consistency: dữ liệu của service khác có thể cũ trong khoảng ms-giây
- Cô lập logic (các schema riêng biệt) trên một server vật lý là khả thi — một thỏa hiệp
- KHÔNG phù hợp cho team nhỏ (2-3 dev) và startup có schema thay đổi thường xuyên

**Các câu hỏi phụ thường gặp:**
- **Cách lấy dữ liệu của service khác?** Gọi API (đồng bộ), dựa trên event (bất đồng bộ), hoặc materialized view (CQRS).
- **Polyglot persistence là gì?** User Service -> PostgreSQL, Session -> Redis, Analytics -> ClickHouse.
- **Database per Service vs Schema per Service?** Schema per Service — cô lập logic trên một server — dễ vận hành hơn, nhưng ít cô lập hơn khi server lỗi.
- **Khi nào KHÔNG nên dùng nó?** Team nhỏ, startup, yêu cầu nhất quán nghiêm ngặt cho reporting.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Bạn có thể đọc trực tiếp từ database của service khác" — vi phạm encapsulation, coupling
- "Eventual consistency = dữ liệu luôn sai" — không, nó sẽ trở nên đúng theo thời gian
- "JOIN giữa các service là thực hành bình thường" — không, đó là anti-pattern
- "Mỗi service cần một server database riêng" — không, bạn có thể dùng các schema trên một server
