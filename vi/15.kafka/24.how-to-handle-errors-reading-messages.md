# How to handle errors when reading messages in Kafka (Cách xử lý lỗi khi đọc message trong Kafka)

## Junior Level

### Định Nghĩa Đơn Giản

**Xử lý lỗi khi đọc** là một tập hợp các pattern để xử lý đúng cách các tình huống mà một consumer không thể xử lý một message: lỗi parse, cơ sở dữ liệu không khả dụng, timeout dịch vụ bên ngoài, v.v.

### Phép So Sánh

Hãy tưởng tượng một bưu điện. Nếu một lá thư không thể giao được (sai địa chỉ):
1. Thử lại sau một giờ (retry)
2. Nếu sau 3 lần thử vẫn thất bại — đặt nó vào bộ phận "thư chết" (DLQ)
3. Không bao giờ vứt một lá thư mà không ghi log nó (log mọi thứ)

### Template Xử Lý Cơ Bản

```java
KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props);
consumer.subscribe(List.of("orders"));

try {
    while (running) {
        ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));
        for (ConsumerRecord<String, String> record : records) {
            try {
                processRecord(record);
            } catch (Exception e) {
                log.error("Error processing record: {}", record, e);
                // ĐỪNG commit offset → message sẽ được đọc lại
            }
        }
        consumer.commitSync();
    }
} catch (WakeupException e) {
    log.info("Shutdown requested");
} finally {
    consumer.commitSync();  // commit cuối cùng
    consumer.close();
}

private void processRecord(ConsumerRecord<String, String> record) {
    String value = record.value();
    Order order = parseOrder(value);  // có thể ném exception
    saveToDatabase(order);            // có thể ném exception
}
```

### Graceful Shutdown

```java
// Trong một thread khác (ví dụ: shutdown hook):
Runtime.getRuntime().addShutdownHook(new Thread(() -> {
    running = false;
    consumer.wakeup();  // ngắt poll()
}));
```

### Khi Nào Điều Này Quan Trọng

- **Bất kỳ ứng dụng production nào** — lỗi là không thể tránh khỏi
- **Dữ liệu tài chính** — các giao dịch không thể bị mất
- **Tích hợp dịch vụ bên ngoài** — timeout, rate limit
- **Data pipeline** — dữ liệu hỏng, không khớp schema

## Middle Level

### Các Chiến Lược Xử Lý Lỗi

#### 1. Retry Với Exponential Backoff

```java
private static final int MAX_RETRIES = 3;
private static final long BASE_DELAY_MS = 1000;

private void processWithRetry(ConsumerRecord<String, String> record) {
    int retries = 0;
    while (retries < MAX_RETRIES) {
        try {
            processRecord(record);
            return;  // thành công
        } catch (RetryableException e) {
            retries++;
            long delay = BASE_DELAY_MS * (long) Math.pow(2, retries - 1);
            // Exponential backoff: 1s, 2s, 4s
            log.warn("Retryable error, attempt {}/{}: {}", retries, MAX_RETRIES, e.getMessage());
            // ⚠️ ANTI-PATTERN: Thread.sleep() trong vòng lặp consumer chặn poll()
            // và có thể gây vượt max.poll.interval.ms.
            // Dùng retry bất đồng bộ hoặc DLQ thay vì sleep.
            try {
                Thread.sleep(delay);
            } catch (InterruptedException ie) {
                Thread.currentThread().interrupt();
                throw new RuntimeException(ie);
            }
        }
    }
    throw new MaxRetriesExceededException("Failed after " + MAX_RETRIES + " retries");
}
```

#### 2. Dead Letter Queue (DLQ)

```java
KafkaProducer<String, String> dlqProducer = new KafkaProducer<>(dlqProps);

private void processWithDLQ(ConsumerRecord<String, String> record) {
    try {
        processWithRetry(record);
    } catch (Exception e) {
        // Gửi đến DLQ
        ProducerRecord<String, String> dlqRecord = new ProducerRecord<>(
            "orders-dlq",
            record.key(),
            record.value()
        );
        // Làm giàu với metadata lỗi
        dlqRecord.headers().add("x-original-topic", record.topic().getBytes());
        dlqRecord.headers().add("x-original-partition", String.valueOf(record.partition()).getBytes());
        dlqRecord.headers().add("x-original-offset", String.valueOf(record.offset()).getBytes());
        dlqRecord.headers().add("x-exception-message", e.getMessage().getBytes());
        dlqRecord.headers().add("x-exception-stacktrace", getStackTrace(e).getBytes());
        dlqRecord.headers().add("x-timestamp", String.valueOf(System.currentTimeMillis()).getBytes());

        dlqProducer.send(dlqRecord);
        log.error("Sent to DLQ: {}", record, e);
    }
}
```

#### 3. Skip And Continue

```java
// Cho dữ liệu không quan trọng — log và bỏ qua
for (ConsumerRecord<String, String> record : records) {
    try {
        processRecord(record);
    } catch (NonCriticalException e) {
        log.warn("Skipping non-critical error: {}", e.getMessage());
        // Tiếp tục — offset sẽ được commit
    } catch (CriticalException e) {
        log.error("Critical error, stopping: {}", e.getMessage());
        throw e;  // Đừng commit → retry khi restart
    }
}
consumer.commitSync();
```

### Bảng Các Lỗi Thường Gặp

| Lỗi                             | Triệu chứng                                            | Hậu quả                             | Giải pháp                       |
| --------------------------------- | --------------------------------------------------- | ----------------------------------------- | ------------------------------ |
| Retry vô hạn                    | Consumer kẹt trên một message                       | Consumer lag tăng, pipeline bị đình trệ  | Retry tối đa + DLQ              |
| Commit trước khi xử lý          | Mất dữ liệu khi crash                                  | Mất dữ liệu âm thầm                         | Commit SAU khi xử lý        |
| Không có DLQ                       | Các message có vấn đề bị mất                       | Không có khả năng phân tích                    | Luôn dùng DLQ                 |
| Thread.sleep trong vòng lặp consumer     | Vượt max.poll.interval.ms                       | Rebalancing, xử lý trùng lặp        | Retry bất đồng bộ                    |
| Catch Exception (quá rộng)       | Che giấu các lỗi nghiêm trọng                               | Hành vi không thể dự đoán                   | Catch các exception cụ thể      |
| Xử lý trong cùng một thread     | Một record thất bại chặn toàn bộ partition      | Throughput = 0                           | Thread xử lý lỗi riêng biệt |

### Phân Loại Lỗi

| Loại Lỗi             | Ví dụ                       | Retry?        | DLQ?                    |
| ---------------------- | ------------------------------ | ------------- | ------------------------ |
| **Tạm thời (Transient)**          | Timeout DB, trục trặc network    | Có (3–5×)    | Nếu hết retry    |
| **Poison pill**        | Dữ liệu hỏng, không khớp schema | Không            | Ngay lập tức đến DLQ      |
| **Dependency bên ngoài**| API dừng hoạt động, rate limit          | Có (backoff) | Nếu hết retry    |
| **Business logic**     | Số tiền đơn hàng không hợp lệ         | Không            | Đến DLQ với metadata    |
| **Fatal (nghiêm trọng)**              | OOM, đầy đĩa                | Không            | Alert + dừng               |

### Khi Nào KHÔNG Nên Dùng Retry

- **Poison pill** — dữ liệu hỏng, vi phạm schema (sẽ không bao giờ được sửa bởi retry)
- **Vi phạm quy tắc kinh doanh** — số tiền âm, trạng thái không hợp lệ (cần xem xét thủ công)
- **Lỗi authentication/authorization** — vấn đề thông tin xác thực không được giải quyết bởi retry
- **Rate limit từ API bên ngoài** — retry với backoff, nhưng không vô hạn

### Cơ Chế Nội Bộ Sâu

#### Xử Lý Lỗi Trong Spring Kafka

```java
@KafkaListener(topics = "orders", groupId = "order-service")
public void listen(ConsumerRecord<String, String> record) {
    processOrder(record.value());
}

// Cấu hình DefaultErrorHandler
@Bean
public DefaultErrorHandler errorHandler(KafkaOperations<String, String> template) {
    // Các exception có thể retry
    var retryableExceptions = Map.of(
        RetriableException.class, RetryState.ALWAYS_RETRY
    );

    // FixedBackOff hoặc ExponentialBackOff
    var backOff = new ExponentialBackOff(1000L, 2.0);
    backOff.setMaxElapsedTime(60000L);  // tối đa 60s tổng thời gian retry
    backOff.setMaxAttempts(5);

    // Producer DLQ
    var dlqSender = new DeadLetterPublishingRecoverer(template);

    return new DefaultErrorHandler(dlqSender, backOff);
}
```

#### Xử Lý Lỗi Trong Kafka Streams

```java
StreamsBuilder builder = new StreamsBuilder();
KStream<String, String> stream = builder.stream("orders");

stream.process(() -> new Processor<String, String>() {
    @Override
    public void process(Record<String, String> record) {
        try {
            processRecord(record);
        } catch (Exception e) {
            // Kafka Streams không có DLQ tích hợp sẵn
            // Dùng side output thay thế
            context().forward(record.withValue("ERROR: " + e.getMessage()),
                             To.child("error-topic"));
        }
    }
});
```

#### ConsumerRebalanceListener + Xử Lý Lỗi

```java
consumer.subscribe(List.of("orders"), new ConsumerRebalanceListener() {
```

### Đánh Đổi (Trade-offs)

| Chiến lược            | An Toàn Dữ Liệu  | Throughput  | Độ Phức Tạp  | Khi Nào Dùng              |
| ------------------- | ------------ | ----------- | ----------- | ------------------------ |
| Retry + commit sau| Cao         | Thấp         | Trung bình      | Dữ liệu quan trọng            |
| Retry + async DLQ   | Cao         | Trung bình      | Cao        | Tiêu chuẩn production      |
| Skip + log          | Thấp          | Cao        | Thấp        | Metrics, log             |
| Chặn cho đến khi thành công | Tối đa      | 0 khi lỗi  | Thấp        | Xử lý từng record |
| Side output (Streams)| Cao        | Cao        | Trung bình      | Các ứng dụng Kafka Streams       |

### Edge Case

**1. Poison Pill — một message luôn thất bại:**

```
Kịch bản:
  Partition 0: offset 1000 — JSON hỏng
  Consumer đọc offset 1000 → lỗi parse → retry → lỗi → retry...
  Vòng lặp consumer kẹt trên một message vô hạn
  Tất cả các message tiếp theo (1001, 1002, ...) KHÔNG được xử lý

Phát hiện:
  Consumer lag cho partition 0 không thay đổi
  Log hiển thị lỗi lặp lại ở offset 1000

Giải quyết:
  1. DLQ sau số retry tối đa
  2. Seek qua poison pill:
     consumer.seek(new TopicPartition("orders", 0), 1001);
  3. Phân tích message DLQ và sửa schema producer
```

**2. Vượt max.poll.interval.ms Trong Quá Trình Retry:**

```java
// VẤN ĐỀ:
while (retries < MAX_RETRIES) {
    try {
        process(record);
        break;
    } catch (Exception e) {
        Thread.sleep(10000);  // sleep 10s × 5 retry = 50s
        retries++;
    }
}
// Nếu max.poll.interval.ms = 300000 (5 phút) — OK
// Nếu max.poll.interval.ms = 30000 (30s) — consumer bị đá ra ngoài!

// GIẢI PHÁP: retry bất đồng bộ
CompletableFuture.runAsync(() -> {
    retryWithBackoff(record);
}).whenComplete((result, ex) -> {
    if (ex == null) {
        commitOffset(record);
    } else {
        sendToDLQ(record, ex);
        commitOffset(record);
    }
});
```

**3. Lỗi Batch Một Phần:**

```
Kịch bản:
  Consumer nhận một batch gồm 500 record
  Các record 0–499 xử lý thành công
  Record 500 gây ra OutOfMemoryError
  Consumer crash → không có offset nào từ batch được commit

Khi restart:
  Tất cả 500 record sẽ được đọc lại
  Các record 0–499 → xử lý trùng lặp!

Giải quyết:
  1. Xử lý idempotent (upsert, các key dedup)
  2. Commit từng record (hiếm, overhead cao)
  3. Commit tại các điểm an toàn (mỗi 100 record)
  4. Xử lý transactional
```

**4. Xử Lý Lỗi Với Gán Partition Thủ Công:**

```java
// Với assign() thay vì subscribe() — không có rebalance
TopicPartition partition = new TopicPartition("orders", 0);
consumer.assign(List.of(partition));
consumer.seek(partition, lastProcessedOffset);

// Xử lý lỗi đơn giản hơn — không có gián đoạn rebalance
// NHƯNG: bạn phải xử lý thủ công:
//  - Theo dõi offset
//  - Quản lý partition
//  - Vòng đời consumer
```

**5. Xử Lý Lỗi Đồng Thời:**

```java
// Xử lý đa thread với xử lý lỗi
ExecutorService executor = Executors.newFixedThreadPool(10);
Map<TopicPartition, Long> currentOffsets = new ConcurrentHashMap<>();

while (running) {
    ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100));

    for (ConsumerRecord<String, String> record : records) {
        executor.submit(() -> {
            try {
                processRecord(record);
                currentOffsets.compute(
                    new TopicPartition(record.topic(), record.partition()),
                    (tp, offset) -> Math.max(offset == null ? 0L : offset, record.offset() + 1)
                );
            } catch (Exception e) {
                sendToDLQ(record, e);
                // Vẫn commit — DLQ đã xử lý
                currentOffsets.compute(
                    new TopicPartition(record.topic(), record.partition()),
                    (tp, offset) -> Math.max(offset == null ? 0L : offset, record.offset() + 1)
                );
            }
        });
    }

    // Commit offset tối đa
    consumer.commitSync(buildOffsetMap(currentOffsets));
}
```

### Hiệu Năng (Các Con Số Production)

| Chiến lược             | Throughput  | Latency P99  | Overhead Lỗi | Tác Động CPU |
| -------------------- | ----------- | ------------ | -------------- | ---------- |
| Không có xử lý lỗi    | 100K msg/s  | 5ms          | 0%             | cơ sở   |
| Try-catch + skip     | 98K msg/s   | 5ms          | +2%            | +1%        |
| Retry (3x) + DLQ     | 85K msg/s   | 15ms         | +15%           | +5%        |
| Retry (5x) + async DLQ | 80K msg/s | 20ms         | +20%           | +8%        |
| Commit từng record    | 50K msg/s   | 50ms         | +100%          | +20%       |

### Câu Chuyện Production Thực Tế

**Tình huống:** Một công ty logistics, xử lý các track GPS từ 50K người giao hàng. 200K event/phút.

**Vấn đề:** Cứ mỗi 2-3 giờ, một người giao hàng gửi dữ liệu GPS hỏng (lat/lon null). Consumer crash với NullPointerException, restart → crash lần nữa trên cùng message. Consumer lag tăng ở 50K/phút trong thời gian downtime.

**Điều tra:**
- Xử lý lỗi: catch-all + retry không có DLQ
- Logic retry: retry vô hạn trên tất cả các exception
- Hiệu ứng poison pill: một record hỏng chặn partition
- 30 phút downtime × 50K event/phút = 1.5M backlog
- Rebalancing mỗi lần crash → lỗi dây chuyền

**Giải quyết:**
```java
// 1. Chỉ retry cho các lỗi tạm thời
Set<Class<? extends Throwable>> retryable = Set.of(
    TimeoutException.class,
    ConnectException.class,
    SocketException.class
);

// 2. DLQ cho tất cả các lỗi khác
DefaultErrorHandler handler = new DefaultErrorHandler(
    new DeadLetterPublishingRecoverer(kafkaTemplate),
    new FixedBackOff(1000L, 3)  // 3 retry, cách nhau 1s
);
handler.setRetryableExceptions(retryable);

// 3. Alert cho các message DLQ
// 4. DLQ consumer để xem xét thủ công và replay
// 5. Validate schema ở phía producer (phòng ngừa)
```

Kết quả: 0 downtime trong 12 tháng. DLQ trung bình 2 message/ngày (tất cả GPS hỏng).

### Các Thực Hành Tốt Nhất Cho Highload

```
✅ Chỉ retry cho các lỗi tạm thời (định nghĩa một allowlist)
✅ Số retry tối đa (3–5) + DLQ cho các lỗi không thể retry
✅ DLQ với metadata được làm giàu (topic gốc, offset, exception)
✅ Xử lý lỗi bất đồng bộ cho các retry dài (đừng chặn vòng lặp poll)
✅ Exponential backoff với jitter (ngăn thundering herd)
✅ Xử lý idempotent (bảo vệ khỏi trùng lặp khi retry)
✅ Alert cho các message DLQ (không bao giờ bỏ qua DLQ)
✅ Graceful shutdown với commit các offset in-flight
✅ Validate schema ở phía producer (ngăn ngừa poison pill)
✅ Thread xử lý lỗi riêng biệt (đừng chặn xử lý chính)

❌ Retry trên tất cả các exception (rủi ro vòng lặp vô hạn)
❌ Retry trong thread consumer chính (vượt max.poll.interval)
❌ Không có DLQ (mất poison pill)
❌ Commit trước khi xử lý (mất dữ liệu khi lỗi)
❌ Không có alerting cho các lỗi (suy giảm âm thầm)
❌ Không có xử lý idempotent (trùng lặp khi retry)
```

### Các Quyết Định Kiến Trúc

1. **Phân loại lỗi** — tạm thời vs vĩnh viễn, quyết định chiến lược retry
2. **Làm giàu DLQ** — metadata cho debug và khả năng replay
3. **Xử lý lỗi bất đồng bộ** — đừng chặn vòng lặp poll, tránh rebalancing
4. **Xử lý idempotent** — nền tảng cho retry an toàn
5. **Phòng ngừa > chữa trị** — validate schema ở phía producer

### Tóm Tắt Cho Senior

- Xử lý lỗi là một thành phần quan trọng của các hệ thống Kafka production
- Poison pill — nguyên nhân phổ biến nhất gây stall consumer
- DLQ — bắt buộc để cô lập poison pill và phân tích sau này
- Chỉ retry các lỗi tạm thời — các lỗi vĩnh viễn đi đến DLQ ngay lập tức
- max.poll.interval.ms — giới hạn tổng thời gian xử lý + retry
- Xử lý lỗi bất đồng bộ cho các retry dài — tránh chặn vòng lặp poll
- Xử lý idempotent — điều kiện tiên quyết cho retry an toàn
- Monitoring: tỷ lệ lỗi, kích thước DLQ, consumer lag — tất cả cần alert
- Phòng ngừa: validate schema, kiểm tra phía producer — giảm lỗi từ nguồn

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- Chỉ retry cho các lỗi tạm thời (timeout, network); poison pill → ngay lập tức đến DLQ
- DLQ (Dead Letter Queue) — bộ cô lập cho các message có vấn đề sau retry tối đa
- Thread.sleep trong vòng lặp consumer là một anti-pattern: vượt max.poll.interval → rebalancing
- Xử lý lỗi bất đồng bộ — đừng chặn vòng lặp poll, tránh rebalancing
- Xử lý idempotent — điều kiện tiên quyết cho retry an toàn (bảo vệ khỏi trùng lặp)
- Phân loại: Transient (retry), Poison pill (DLQ), External dependency (retry + DLQ), Fatal (dừng)
- ConsumerRebalanceListener: commitSync trong onPartitionsRevoked, chờ xử lý in-flight

**Các câu hỏi phụ thường gặp:**
- *Poison pill là gì?* — Một message luôn thất bại (dữ liệu hỏng); retry là vô hạn.
- *Tại sao Thread.sleep tồi?* — Nó chặn poll() → vượt max.poll.interval → rebalancing.
- *Khi nào KHÔNG dùng retry?* — Poison pill, vi phạm quy tắc kinh doanh, lỗi auth.
- *Làm sao xử lý lỗi batch một phần?* — Xử lý idempotent + commit tại các điểm an toàn.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Retry trên tất cả các exception" — poison pill = vòng lặp vô hạn
- "Commit trước khi xử lý là thực hành tiêu chuẩn" — mất dữ liệu khi crash
- "Không cần DLQ nếu retry hoạt động" — poison pill vượt qua retry
- "Thread.sleep trong vòng lặp consumer là bình thường" — gây ra rebalancing
