# What is @Transactional annotation? (Annotation @Transactional là gì?)

## 🟢 Junior Level

`@Transactional` là một annotation của Spring cho phép bạn quản lý transaction một cách khai báo (declarative). Thay vì `BEGIN`/`COMMIT`/`ROLLBACK` thủ công, bạn chỉ cần thêm annotation — Spring sẽ tự động làm mọi thứ.

### Ví Dụ Đơn Giản Nhất

```java
@Service
public class UserService {

    @Transactional
    public void createUser(User user) {
        userRepository.save(user);
        // Spring tự động COMMIT khi thành công
        // hoặc ROLLBACK khi có RuntimeException
    }
}
```

### Ví Dụ Minh Họa

Hãy nghĩ về một khoản chuyển tiền ngân hàng: bạn hoặc chuyển toàn bộ số tiền, hoặc không chuyển gì cả. `@Transactional` đảm bảo rằng một nửa giao dịch chuyển tiền không bao giờ "treo" trong cơ sở dữ liệu.

### Các Tham Số Chính

| Tham số     | Nó làm gì                     | Giá trị mặc định               |
| ------------- | -------------------------------- | --------------------------- |
| `propagation` | Transaction liên hệ với các transaction khác như thế nào| `REQUIRED`                  |
| `isolation`   | Isolation level                  | `DEFAULT` (level của DB)        |
| `readOnly`    | Tối ưu hóa chỉ đọc           | `false`                     |
| `rollbackFor` | Exception nào kích hoạt rollback| `RuntimeException`, `Error` |
| `timeout`     | Timeout tính bằng giây           | `-1` (không timeout)           |

### Khi Nào Nên Dùng

Bất kỳ method nào thực hiện nhiều thao tác DB phải nguyên tử: chuyển tiền, tạo đơn hàng có kèm item, cập nhật các entity liên quan.

### Các Quy Tắc Quan Trọng

- Chỉ hoạt động trên các method **public**
- Chỉ hoạt động khi được gọi **từ bên ngoài** class (không phải qua `this`)
- Theo mặc định chỉ rollback khi có **RuntimeException** và **Error**

## 🟡 Middle Level

### Cách Nó Hoạt Động: Cơ Chế AOP Proxy

```
Lời gọi bên ngoài → Proxy → TransactionInterceptor → PlatformTransactionManager
                                                        ↓
                                               Mở transaction → Thực thi method → COMMIT/ROLLBACK
```

1. Spring tạo một **object Proxy** quanh bean (JDK Dynamic Proxy hoặc CGLIB)
2. Khi gọi method, quyền điều khiển chuyển đến `TransactionInterceptor`
3. Interceptor tham vấn `PlatformTransactionManager`, cái mà mở connection và bắt đầu transaction
4. Method của bạn thực thi
5. Khi thành công — `commit`, khi có exception — `rollback`

### Bạn Có Thể Đặt Annotation Ở Đâu

| Cấp độ         | Hoạt động?   | Khuyến nghị                     |
| ------------- | -------- | ----------------------------------- |
| Method        | ✅ Có    | Lựa chọn tốt nhất — kiểm soát chính xác      |
| Class         | ✅ Có    | Tất cả các method public đều transactional|
| Interface     | ⚠️ Tùy | Chỉ với JDK Dynamic Proxy        |
| Method private| ❌ Không     | Proxy không chặn được |

### Ví Dụ Với Các Tham Số

```java
@Transactional(
    propagation = Propagation.REQUIRED,
    isolation = Isolation.READ_COMMITTED,
    timeout = 30,
    readOnly = false,
    rollbackFor = Exception.class,
    noRollbackFor = NotFoundException.class
)
public void processOrder(Order order) { ... }
```

### Các Lỗi Thường Gặp

| Lỗi                              | Điều gì xảy ra                                    | Cách khắc phục                                             |
| ------------------------------------ | ----------------------------------------------- | ------------------------------------------------------ |
| `@Transactional` trên method private   | Annotation bị bỏ qua                              | Chuyển method thành public                                     |
| Gọi `this.method()` trong cùng class | Proxy bị bỏ qua, không có transaction                  | Tách sang bean riêng biệt hoặc self-injection             |
| Checked Exception không có `rollbackFor` | COMMIT thay vì ROLLBACK                   | Thêm `rollbackFor = Exception.class`                    |
| `@Transactional` trên Controller       | Giữ connection DB trong lúc serialize JSON    | Chuyển sang tầng Service                                  |
| Bắt và nuốt exception    | Spring không thấy exception → COMMIT           | Ném lại exception hoặc gọi `setRollbackOnly()`          |

### Khi Nào KHÔNG Nên Dùng

| Tình huống                       | Tại sao không cần                        | Giải pháp thay thế                        |
| ------------------------------- | ------------------------------------- | ----------------------------------- |
| Method chỉ đọc một bản ghi    | Độ phức tạp dư thừa                  | readOnly = true hoặc không dùng transaction  |
| Gọi HTTP bên trong method         | Giữ connection DB không cần thiết     | Đưa lời gọi HTTP ra ngoài transaction |
| Logging/audit                | Không yêu cầu tính nguyên tử với logic  | REQUIRES_NEW trong bean riêng biệt      |
| Xử lý message nền   | Có thể cần chiến lược khác           | Transaction lập trình (programmatic)        |

### So Sánh: Cách Tiếp Cận Khai Báo vs Lập Trình

| Cách tiếp cận              | Ưu điểm                                    | Nhược điểm               | Khi nào nên dùng              |
| --------------------- | --------------------------------------- | ------------------ | ------------------------ |
| `@Transactional`      | Code sạch, khai báo                 | Bị giới hạn bởi proxy   | Các kịch bản tiêu chuẩn       |
| `TransactionTemplate` | Kiểm soát đầy đủ, hoạt động bên trong `this`       | Nhiều boilerplate hơn   | Logic transaction có điều kiện |

## 🔴 Senior Level

### Spring Transaction AOP — Kiến Trúc Nội Bộ

#### Luồng Tạo Proxy

```java
// InfrastructureAdvisorAutoProxyCreator (BeanPostProcessor)
@Override
public Object postProcessAfterInitialization(Object bean, String beanName) {
    if (isInfrastructureClass(bean.getClass())) return bean;

    if (AnnotationUtils.findAnnotation(bean.getClass(), Transactional.class) != null
        || hasTransactionalMethods(bean.getClass())) {

        ProxyFactory proxyFactory = new ProxyFactory(bean);
        proxyFactory.addAdvice(new TransactionInterceptor(tm, transactionAttributeSource));
        return proxyFactory.getProxy();
    }
    return bean;
}
```

#### Thực Thi TransactionInterceptor

```java
public Object invoke(MethodInvocation invocation) throws Throwable {
    Class<?> targetClass = AopProxyUtils.ultimateTargetClass(invocation.getThis());

    TransactionAttribute txAttr = tas.getTransactionAttribute(
        invocation.getMethod(), targetClass);

    PlatformTransactionManager tm = determineTransactionManager(txAttr);
    TransactionInfo txInfo = createTransactionIfNecessary(tm, txAttr, invocation.getMethod().toString());

    Object retVal;
    try {
        retVal = invocation.proceed();
    } catch (Throwable ex) {
        completeTransactionAfterThrowing(txInfo, ex);
        throw ex;
    } finally {
        cleanupTransactionInfo(txInfo);
    }

    commitTransactionAfterReturning(txInfo);
    return retVal;
}
```

### JDK Dynamic Proxy vs CGLIB

| Đặc điểm               | JDK Dynamic Proxy    | CGLIB                     |
| ---------------------------- | -------------------- | ------------------------- |
| Cơ chế                    | Hiện thực các interface| Kế thừa class             |
| Tốc độ tạo               | Nhanh hơn (~5-10μs)     | Chậm hơn (~20-50μs)         |
| Overhead lời gọi                | Thấp                  | Cao hơn một chút            |
| `@Transactional` trên interface| ✅ Hoạt động              | ❌ Bị bỏ qua                |
| Method final                | ✅ Không phải vấn đề      | ❌ Không thể override        |
| Bộ nhớ                       | Ít hơn                 | Nhiều hơn (sinh class)    |

```java
// JDK Dynamic Proxy
UserService proxy = (UserService) Proxy.newProxyInstance(
    classLoader,
    new Class[]{UserService.class},
    handler
);

// CGLIB
UserService proxy = (UserService) Enhancer.create(UserService.class, handler);
```

Spring Boot mặc định dùng CGLIB nếu không có interface. Có thể ép buộc: `@EnableTransactionManagement(proxyTargetClass = true)`.

### Trạng Thái Transaction Theo Thread-Local

```java
public abstract class TransactionSynchronizationManager {
    private static final ThreadLocal<Map<Object, Object>> resources = new NamedThreadLocal<>("Transactional resources");
    private static final ThreadLocal<Set<TransactionSynchronization>> synchronizations = new NamedThreadLocal<>("Transaction synchronizations");
    private static final ThreadLocal<String> currentTransactionName = new NamedThreadLocal<>("Current transaction name");
    private static final ThreadLocal<Boolean> currentTransactionReadOnly = new NamedThreadLocal<>("Current transaction read-only status");
    private static final ThreadLocal<Integer> currentTransactionIsolationLevel = new NamedThreadLocal<>("Current transaction isolation level");
    private static final ThreadLocal<Boolean> actualTransactionActive = new NamedThreadLocal<>("Actual transaction active");
}
```

Đây là lý do tại sao `@Transactional` **không hoạt động xuyên thread** trong cấu hình tiêu chuẩn — ThreadLocal không được truyền đi. Các method `@Async` nhận một context transaction riêng biệt. Khi dùng TaskExecutor tùy chỉnh với việc truyền ThreadLocal hoặc Virtual Thread (Java 21+), việc truyền context là có thể nhưng đòi hỏi cấu hình tường minh.

### Các Trường Hợp Biên (Tối Thiểu 3)

1. **UnexpectedRollbackException**: Trong một chuỗi REQUIRED → REQUIRED, method bên trong ném RuntimeException. Bên ngoài bắt nó, nhưng TransactionInterceptor đã đặt cờ `rollback-only`. Khi cố gắng commit — `UnexpectedRollbackException` được ném ra.

2. **@Transactional trên method final**: CGLIB không thể override method final → annotation bị bỏ qua âm thầm. JDK Proxy cũng không chặn được các method interface final.

3. **Kế thừa và @Transactional**: Nếu subclass override method mà không thêm lại annotation — hành vi phụ thuộc vào loại proxy. Với CGLIB, annotation của superclass có thể không được phát hiện.

4. **Nhiều TransactionManager**: Nếu ứng dụng có hai `PlatformTransactionManager`, `@Transactional` không có qualifier sẽ dùng `@Primary`. Gọi hai method khác nhau với hai manager khác nhau = **hai transaction độc lập**, không phải một distributed transaction. Cần JTA/Atomikos cho 2PC. JTA (Java Transaction API) và Atomikos (một hiện thực JTA). 2PC (Two-Phase Commit) — giao thức để commit nguyên tử qua nhiều resource.

### Các Con Số Về Hiệu Năng

| Thao tác                         | Thời gian       |
| --------------------------------- | ---------- |
| Overhead lời gọi proxy         | ~1-2 μs    |
| Thiết lập transaction (phía Spring)   | ~5-10 μs   |
| Lấy connection (HikariCP) | ~50-200 μs |
| Query DB thông thường                  | 1-10 ms    |

Overhead của Spring không đáng kể. Các thao tác DB chiếm ưu thế.

### Tác Động Đến Bộ Nhớ

Mỗi transaction đang hoạt động giữ:
- JDBC Connection từ pool (~2-4 KB)
- L1 cache của Hibernate (Persistence Context) — tăng theo số entity được load
- Các mục ThreadLocal trong `TransactionSynchronizationManager`
- Undo log trong DB (transaction dài hơn = lớn hơn)

Các transaction dài = cạn kiệt connection pool + bloat trong DB.

### Thread Safety

`@Transactional` **không thread-safe** tự bản thân nó. Mỗi thread nhận:
- Transaction riêng
- Connection DB riêng
- Hibernate Session riêng

Bản thân service bean là một singleton. Nhưng trạng thái transaction được lưu trong ThreadLocal, nên các lời gọi đồng thời đến cùng một method `@Transactional` được cô lập.

### Câu Chuyện Thực Tế Trong Production

Trong production, một service với `@Transactional` bắt một `BusinessException` (checked). Lập trình viên không chỉ định `rollbackFor`. Transaction đã COMMIT, nhưng một phần dữ liệu đã được ghi. Client nhận lỗi, nhưng nửa đơn hàng vẫn còn trong cơ sở dữ liệu. Giải pháp: `rollbackFor = Exception.class` trên tất cả các method ghi + integration test cho hành vi rollback.

Tại sao Spring commit: theo mặc định, rollback chỉ cho RuntimeException + Error.
Checked exception (kế thừa từ Exception, không phải RuntimeException) được xử lý bởi
TransactionInterceptor như "hoàn thành bình thường" → commit. Ngay cả khi method ném ra
một exception, Spring không thấy nó như một tín hiệu rollback — vì exception
đã được bắt trong một khối catch, và rollbackFor không được chỉ định.

### Best Practices Cho Highload

1. **Phạm vi transaction tối thiểu**: Chỉ các thao tác DB. Các lời gọi HTTP, file I/O — để bên ngoài.
2. **readOnly cho các lần đọc**: Vô hiệu hóa dirty checking (Hibernate so sánh entity với snapshot khi flush; với readOnly = true cơ chế này bị vô hiệu hóa). Có thể định tuyến đến read replica.
3. **Tinh chỉnh connection pool**: `maximumPoolSize` của HikariCP = `số core CPU * 2 + số disk spindle` (quy tắc kinh nghiệm từ tác giả của HikariCP. Với SSD, "disk spindle" = 1. Điểm khởi đầu — 10-20, sau đó tinh chỉnh dưới tải thực tế).
4. **Tránh các transaction dài**: Chia các thao tác batch thành các chunk.
5. **Dùng REQUIRES_NEW cho các side-effect**: Logging, thông báo — không nên chặn transaction chính.
6. **Cân nhắc các transaction lập trình**: Với logic điều kiện phức tạp, `TransactionTemplate` linh hoạt hơn.

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- @Transactional — quản lý transaction khai báo qua AOP Proxy (JDK Dynamic Proxy hoặc CGLIB)
- Chỉ hoạt động trên các method public và chỉ khi được gọi từ bên ngoài class (không qua `this`)
- Theo mặc định chỉ rollback cho RuntimeException và Error, checked exception → commit
- Các tham số: propagation (REQUIRED), isolation (DEFAULT), readOnly (false), timeout (-1), rollbackFor
- Trạng thái được lưu trong ThreadLocal — không hoạt động xuyên thread (@Async = context riêng biệt)
- @Transactional trên interface chỉ hoạt động với JDK Dynamic Proxy, bị bỏ qua với CGLIB

**Các câu hỏi phụ thường gặp:**
- Tại sao @Transactional không hoạt động khi gọi qua this? — Proxy bị bỏ qua, TransactionInterceptor không tham gia
- JDK Proxy vs CGLIB? — JDK: dựa trên interface, CGLIB: dựa trên subclass (không chặn được method final)
- Điều gì xảy ra với @Transactional trên Controller? — Connection DB bị giữ trong lúc serialize JSON — anti-pattern
- UnexpectedRollbackException hoạt động như thế nào? — REQUIRED bên trong đặt rollback-only, bên ngoài cố commit

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "@Transactional trên method private hoạt động" — proxy không chặn các method private
- "Checked exception gây ra rollback" — Spring commit theo mặc định
- "Có thể đặt trên Controller" — connection bị giữ trong lúc serialize JSON, cạn kiệt pool
