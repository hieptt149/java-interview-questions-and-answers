# Difference Between Factory Method and Abstract Factory? (Sự khác nhau giữa Factory Method và Abstract Factory?)

## Junior Level

Cả hai pattern đều giúp tạo đối tượng, nhưng ở các cấp độ khác nhau:

**Factory Method** — tạo ra **một loại** đối tượng duy nhất:
```java
// Factory method tạo ra một sản phẩm duy nhất
interface Button { void render(); }
class WinButton implements Button { ... }
class MacButton implements Button { ... }

abstract class Dialog {
    // Factory Method — subclass quyết định tạo loại button nào
    abstract Button createButton();
}
```

**Abstract Factory** — tạo ra một **họ (family)** các đối tượng có liên quan:
```java
// Abstract factory tạo ra cả một họ sản phẩm
// Có liên quan = chúng phải thuộc cùng một "họ" (tất cả thành phần Windows hoặc tất cả thành phần Mac),
// nếu không thì UI sẽ trông thiếu nhất quán.
interface GUIFactory {
    Button createButton();
    Checkbox createCheckbox();
    Menu createMenu();
}

class WinFactory implements GUIFactory {
    Button createButton() { return new WinButton(); }
    Checkbox createCheckbox() { return new WinCheckbox(); }
    Menu createMenu() { return new WinMenu(); }
}
```

**Sự khác biệt chính:**
- **Factory Method** = một sản phẩm (button)
- **Abstract Factory** = một họ sản phẩm (button + checkbox + menu)

## Middle Level

**OCP (Open/Closed Principle)** — mở để mở rộng, đóng để sửa đổi.

### Factory Method

**Cơ chế:** Kế thừa (subclass quyết định)

```java
// Abstract class với Factory Method
public abstract class PaymentService {
    // Template method
    public void processPayment() {
        PaymentGateway gateway = createGateway();  // Factory Method
        gateway.authorize();
        gateway.capture();
    }

    // Subclass triển khai việc tạo đối tượng
    abstract PaymentGateway createGateway();
}

// Các cách triển khai cụ thể
public class CreditCardService extends PaymentService {
    @Override
    PaymentGateway createGateway() {
        return new StripeGateway();  // Subclass quyết định
    }
}

public class PayPalService extends PaymentService {
    @Override
    PaymentGateway createGateway() {
        return new PayPalGateway();
    }
}
```

**Khi nào nên sử dụng:**
- Cần mở rộng hệ thống với các loại mới
- Class không biết cần tạo đối tượng nào
- Việc tạo đối tượng được ủy quyền (delegate) cho các subclass

### Abstract Factory

**Cơ chế:** Composition (các đối tượng được truyền vào)

```java
// Interface của factory
public interface DatabaseFactory {
    Connection createConnection();
    Statement createStatement();
    ResultSet createResultSet();
}

// Factory cụ thể cho MySQL
public class MySQLFactory implements DatabaseFactory {
    public Connection createConnection() { return new MySQLConnection(); }
    public Statement createStatement() { return new MySQLStatement(); }
    public ResultSet createResultSet() { return new MySQLResultSet(); }
}

// Factory cụ thể cho PostgreSQL
public class PostgresFactory implements DatabaseFactory {
    public Connection createConnection() { return new PostgresConnection(); }
    public Statement createStatement() { return new PostgresStatement(); }
    public ResultSet createResultSet() { return new PostgresResultSet(); }
}

// Client hoạt động với bất kỳ factory nào
public class DatabaseService {
    private final DatabaseFactory factory;

    public DatabaseService(DatabaseFactory factory) {
        this.factory = factory;  // Truyền vào factory cần thiết
    }

    public void query() {
        Connection conn = factory.createConnection();
        Statement stmt = factory.createStatement();
        // Tất cả các đối tượng đều tương thích với nhau!
    }
}
```

**Khi nào nên sử dụng:**
- Cần tạo một họ (family) các đối tượng có liên quan
- Quan trọng rằng các đối tượng thuộc cùng một họ
- Client không nên biết về các class cụ thể

### So sánh

| Tiêu chí       | Factory Method  | Abstract Factory                      |
| --------------- | --------------- | -------------------------------------- |
| **Tạo ra**     | Một đối tượng      | Một họ đối tượng                     |
| **Cơ chế**   | Kế thừa     | Composition                           |
| **Mở rộng**   | Subclass mới      | Factory mới                           |
| **Độ phức tạp**  | Thấp             | Cao                                  |
| **OCP**         | Tuân thủ        | Bị vi phạm khi thêm sản phẩm mới        |

### Các lỗi thường gặp

1. **Abstract Factory cho một sản phẩm duy nhất**
   ```java
   // Overengineering
   interface ButtonFactory { Button create(); }

   // Factory Method là đủ dùng
   abstract class Dialog { abstract Button createButton(); }
   ```

2. **Vi phạm OCP trong Abstract Factory**
   ```java
   // Thêm một sản phẩm mới -> làm hỏng TẤT CẢ các factory
   interface GUIFactory {
       Button createButton();
       Checkbox createCheckbox();
       Tooltip createTooltip();  // <- Mới!
   }
   // Tất cả các cách triển khai đều phải thay đổi!
   ```

## Senior Level

### Phạm vi kiến trúc

**Factory Method = điểm mở rộng trong một hệ thống phân cấp:**
```
Dialog (abstraction)
  |-- createButton() <- điểm mở rộng
  |     |-- WinButton
  |     +-- MacButton
  +-- Template method sử dụng createButton()
```

**Abstract Factory = ranh giới tương thích:**
```
GUIFactory (ranh giới họ)
  |-- WinFactory -> WinButton + WinCheckbox + WinMenu
  +-- MacFactory -> MacButton + MacCheckbox + MacMenu

Đảm bảo: các sản phẩm từ các họ khác nhau sẽ KHÔNG bị trộn lẫn!
```

### Đánh đổi với nguyên lý Open/Closed

**Factory Method tuân thủ OCP:**
```java
// Thêm một loại mới -> subclass mới (không cần thay đổi code hiện có)
class CryptoService extends PaymentService {
    @Override
    PaymentGateway createGateway() {
        return new CoinbaseGateway();
    }
}
// Code hiện có không thay đổi
```

**Abstract Factory vi phạm OCP khi mở rộng:**
```java
// Thêm một sản phẩm mới -> thay đổi interface -> làm hỏng TẤT CẢ các cách triển khai
interface GUIFactory {
    Button createButton();
    Slider createSlider();  // <- Sản phẩm mới
}

// Tất cả các factory đều phải được cập nhật:
class WinFactory implements GUIFactory {
    Slider createSlider() { return new WinSlider(); }  // <- Phải thêm vào!
}
class MacFactory implements GUIFactory {
    Slider createSlider() { return new MacSlider(); }  // <- Phải thêm vào!
}
// Code hiện có bị thay đổi
```

### Sự tiến hóa của hệ thống

```
Simple Factory (phương thức static)
  -> (cần khả năng mở rộng)
Factory Method (kế thừa)
  -> (cần nhiều sản phẩm)
Abstract Factory (các họ)
  -> (cần tính linh hoạt)
DI Container (Spring)
```

### Simple Factory vs Factory Method

**Simple Factory** = phương thức static. Không thể mở rộng thông qua kế thừa.
**Factory Method** = phương thức ảo (virtual method) trong subclass. Có thể mở rộng.

### Các cách triển khai trong Java hiện đại

**Factory Method -> Supplier:**
```java
// Thay vì kế thừa
public class Dialog {
    private final Supplier<Button> buttonFactory;

    public Dialog(Supplier<Button> buttonFactory) {
        this.buttonFactory = buttonFactory;
    }

    public void render() {
        Button button = buttonFactory.get();
        button.render();
    }
}

// Cách sử dụng
Dialog dialog = new Dialog(WinButton::new);
```

**Abstract Factory -> Record:**
```java
// Record để lưu trữ một họ
public record GUIFactory(
    Supplier<Button> button,
    Supplier<Checkbox> checkbox,
    Supplier<Menu> menu
) {}

// Các factory được định nghĩa sẵn
public static final GUIFactory WINDOWS = new GUIFactory(
    WinButton::new, WinCheckbox::new, WinMenu::new
);

public static final GUIFactory MAC = new GUIFactory(
    MacButton::new, MacCheckbox::new, MacMenu::new
);
```

### Spring Context như một Meta-Factory

```java
// Bản thân Spring tự quyết định bean nào cần tạo
@Configuration
public class DatabaseConfig {

    @Bean
    @Profile("mysql")
    public DatabaseFactory mysqlFactory() {
        return new MySQLFactory();
    }

    @Bean
    @Profile("postgres")
    public DatabaseFactory postgresFactory() {
        return new PostgresFactory();
    }
}

// Spring = Abstract Factory phiên bản nâng cấp
// + Profile = lựa chọn họ tại thời điểm chạy (runtime)
```

### Ảnh hưởng đến hiệu năng

**Factory Method:**
```
Monomorphic call (1 subclass) -> được inline
Bimorphic call (2 subclass) -> vẫn nhanh
Megamorphic call (>2 subclass) -> gọi gián tiếp
```

**Abstract Factory:**
```
Thêm một tầng gián tiếp:
  client -> interface của factory -> factory cụ thể -> sản phẩm

Chi phí phát sinh: 2 lần gọi ảo thay vì 1
```

### Kinh nghiệm Production

**Tình huống thực tế: Abstract Factory ngăn chặn được sự trộn lẫn**
- Framework UI: các theme Windows và Mac
- Vấn đề: các lập trình viên đang trộn lẫn các thành phần
- Giải pháp: Abstract Factory đảm bảo tính tương thích
- Kết quả: không thể tạo MacButton trong theme Windows

### Best Practices (Thực hành tốt nhất)

1. **Factory Method** cho một sản phẩm có thể mở rộng duy nhất
2. **Abstract Factory** cho một họ các sản phẩm có liên quan
3. **Supplier<T>** thay vì Factory Method trong Java hiện đại

**Supplier<T>** — interface hàm (functional interface) của Java 8+, trả về một đối tượng mà không cần tham số.

4. **Spring Profiles** thay vì tự viết Abstract Factory thủ công
5. **Tránh** dùng Abstract Factory nếu chỉ có một họ duy nhất
6. **Ghi nhớ** việc vi phạm OCP khi mở rộng Abstract Factory
7. **Record** để lưu trữ các họ factory

**Record** — các class immutable (bất biến) gọn nhẹ của Java 16+.

### Tóm tắt cho Senior

- **Factory Method** = kế thừa, một sản phẩm, thân thiện với OCP
- **Abstract Factory** = composition, một họ sản phẩm, vi phạm OCP
- **Sự tiến hóa:** Simple -> Factory Method -> Abstract Factory -> DI
- **Java hiện đại:** Supplier<T> thay thế Factory Method
- **Spring** = Meta-Factory với Profile
- **Đánh đổi OCP:** Thêm một sản phẩm mới vào Abstract Factory yêu cầu phải thay đổi TẤT CẢ các cách triển khai factory. Nếu có 10 factory — cần chỉnh sửa 10 file.
- **Đảm bảo:** Abstract Factory ngăn chặn việc trộn lẫn sản phẩm

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Factory Method tạo ra một sản phẩm thông qua kế thừa, Abstract Factory — một họ sản phẩm thông qua composition
- Factory Method tuân thủ OCP (subclass mới không làm thay đổi code), Abstract Factory vi phạm OCP khi thêm một sản phẩm mới
- Sự tiến hóa: Simple Factory -> Factory Method -> Abstract Factory -> DI Container (Spring)
- Trong Java hiện đại: Factory Method được thay thế bằng Supplier<T>, Abstract Factory — bằng Record hoặc Map<Enum, Supplier>
- Spring Context = Meta-Factory với @Profile để lựa chọn họ tại thời điểm chạy
- Megamorphic call: >2 subclass trong Factory Method -> JIT không thể inline
- Abstract Factory đảm bảo: các sản phẩm từ các họ khác nhau sẽ KHÔNG bị trộn lẫn

**Các câu hỏi phụ thường gặp:**
- **Khi nào nên chọn Factory Method vs Abstract Factory?** — Một sản phẩm = Factory Method, một họ có liên quan = Abstract Factory
- **Tại sao Abstract Factory lại vi phạm OCP?** — Thêm một sản phẩm mới yêu cầu phải thay đổi interface -> TẤT CẢ các cách triển khai đều phải được cập nhật
- **Simple Factory khác với Factory Method như thế nào?** — Simple Factory = phương thức static (không thể mở rộng), Factory Method = phương thức ảo trong subclass
- **Spring thay thế Abstract Factory như thế nào?** — @Configuration + @Profile = lựa chọn họ bean tại thời điểm chạy

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi dùng Abstract Factory cho một sản phẩm duy nhất" — overengineering, Factory Method là đủ dùng
- "Factory Method và Abstract Factory giống nhau" — chúng có cơ chế và mục tiêu hoàn toàn khác nhau
- "Abstract Factory tuân thủ OCP" — nó vi phạm OCP khi thêm một sản phẩm mới
- "Spring không cần các pattern Factory" — bản thân Spring cũng sử dụng Abstract Factory ở bên dưới
