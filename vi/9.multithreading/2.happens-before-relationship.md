# What is happens-before relationship? (Quan hệ happens-before là gì?)

---

## Junior Level

### Hiểu biết cơ bản

**Happens-before** là đảm bảo của Java về khả năng nhìn thấy (visibility) kết quả giữa các thread.

**Quan trọng:** Happens-before KHÔNG có nghĩa là hành động A sẽ thực thi sớm hơn B về mặt thời gian. Các thread CÓ THỂ thực thi theo bất kỳ thứ tự nào. HB chỉ đảm bảo: nếu A happens-before B, thì kết quả của A sẽ được nhìn thấy trong B — như thể A đã xảy ra trước.

### Ví dụ đơn giản

```java
// Thread 1:
int x = 10;             // Hành động A
ready = true;           // Hành động B (volatile)

// Thread 2:
if (ready) {            // Hành động C
    System.out.println(x); // Luôn in ra 10!
}
```

Ở đây: `x = 10` happens-before `ready = true` (quy tắc program order: trong MỘT thread, một thao tác trước được nhìn thấy bởi thao tác sau), và `ready = true` happens-before lần đọc `ready` ở thread khác (quy tắc volatile). Theo tính bắc cầu (transitivity): `x = 10` happens-before các lần đọc ở thread 2.

### Tại sao điều này quan trọng?

Không có happens-before, trình biên dịch và bộ xử lý có thể sắp xếp lại các lệnh:

```java
// KHÔNG có đảm bảo happens-before:
int x = 10;
boolean flag = false; // không có volatile

// Thread 1:           // Thread 2:
x = 10;               if (flag) {
flag = true;              System.out.println(x); // Có thể là 0!
// Bộ xử lý có thể sắp xếp lại              }
```

## Middle Level

### 8 quy tắc Happens-Before (JSR-133)

Java Memory Model định nghĩa 8 quy tắc:

| #   | Quy tắc                | Mô tả                                                                                          |
| --- | ---------------------- | ----------------------------------------------------------------------------------------------- |
| 1   | **Program Order**      | Trong một thread đơn, mỗi hành động HB mọi hành động xuất hiện sau nó trong code                 |
| 2   | **Monitor Lock**       | Việc unlock một monitor (ra khỏi synchronized) HB một lần lock tiếp theo của cùng monitor đó    |
| 3   | **Volatile Variable**  | Một lần ghi vào field volatile HB một lần đọc tiếp theo của cùng field đó                        |
| 4   | **Thread Start**       | Lời gọi `Thread.start()` HB mọi hành động trong thread được khởi động                            |
| 5   | **Thread Termination** | Mọi hành động trong một thread HB việc kết thúc thread đó (khi `join()` trả về)                  |
| 6   | **Interruption**       | Lời gọi `interrupt()` HB việc phát hiện interrupt (`isInterrupted()` hoặc `InterruptedException`) |
| 7   | **Finalizer**          | Kết thúc của một constructor HB lúc bắt đầu method `finalize()`                                  |
| 8   | **Transitivity**       | Nếu A HB B và B HB C, thì A HB C                                                                |

### Ví dụ cho từng quy tắc

#### 1. Quy tắc Program Order

```java
int a = 1;    // HB
int b = a + 1; // HB
int c = b + 1; // HB — thứ tự được đảm bảo trong một thread
```

#### 2. Quy tắc Monitor Lock

```java
synchronized(lock) {
    x = 42;  // Ghi bên trong synchronized
} // Release monitor

// Ở thread khác:
synchronized(lock) {
    System.out.println(x); // Thấy 42 — acquire cùng monitor đó
}
```

#### 3. Quy tắc Volatile Variable

```java
volatile boolean flag = false;
int data = 0;

// Thread 1:
data = 100;     // HB (program order)
flag = true;    // Ghi volatile

// Thread 2:
if (flag) {     // Đọc volatile — HB từ lần ghi
    System.out.println(data); // Luôn là 100!
}
```

#### 4. Quy tắc Thread Start

```java
int sharedData = 50;
Thread t = new Thread(() -> {
    System.out.println(sharedData); // Luôn thấy 50!
});
sharedData = 100;  // HB (program order) trước start()
t.start();         // start() HB mọi hành động trong thread t
// HB chỉ đảm bảo visibility của những gì đã happened-before start()
// sharedData = 100 (sau start()) — KHÔNG được nhìn thấy bởi thread t
// sharedData = 50 (trước start()) — được nhìn thấy bởi thread t
```

#### 5. Quy tắc Thread Termination

```java
Thread t = new Thread(() -> {
    result = compute(); // Hành động trong thread
});
t.start();
t.join(); // join() trả về — HB
System.out.println(result); // Thấy kết quả!
```

### Piggybacking

Nhờ tính bắc cầu, bạn có thể đảm bảo visibility của một nhóm biến thông thường thông qua một biến volatile duy nhất:

```java
int x = 0, y = 0, z = 0;
volatile boolean published = false;

// Thread writer:
x = 10;
y = 20;
z = 30;
published = true; // Ghi volatile — mọi lần ghi trước đó "đi ké" theo

// Thread reader:
if (published) { // Đọc volatile — "nhặt lên" mọi lần ghi trước đó
    System.out.println(x + y + z); // Luôn là 60!
}
```

## Senior Level

### Bên trong: Memory Fence

Mỗi quan hệ HB được hiện thực thông qua các **Memory Fence** ở mức CPU:

Memory Fence (rào chắn bộ nhớ) — giống với Memory Barrier. Ngăn bộ xử lý sắp xếp lại các thao tác xung quanh rào chắn.

| Loại Barrier   | Ngăn chặn                                                        | Được chèn khi     |
| -------------- | --------------------------------------------------------------- | ----------------- |
| **LoadLoad**   | Đọc không thể bị dời lên trên qua rào chắn                       | đọc volatile      |
| **StoreStore** | Ghi không thể bị dời lên trên qua rào chắn                       | ghi volatile      |
| **LoadStore**  | Ghi không thể bị dời lên trên qua rào chắn                       | đọc volatile      |
| **StoreLoad**  | Đọc không thể bị dời lên trên qua rào chắn (đắt nhất)            | ghi volatile      |

Trên kiến trúc x86:
- `LoadLoad`, `LoadStore` — miễn phí (x86 không sắp xếp lại các lần đọc)
- `StoreStore` — miễn phí (x86 không sắp xếp lại các lần ghi)
- `StoreLoad` — cần lệnh `mfence` (Memory Fence) trên x86. Rào chắn đắt nhất, ngăn MỌI việc sắp xếp lại xung quanh nó.

### CPU Reordering và Out-of-Order Execution

Bộ xử lý thực thi các lệnh không theo thứ tự để tối ưu:

```
// Code nguồn:
A = 1;       // Lệnh 1
B = 2;       // Lệnh 2
flag = true; // Lệnh 3 (volatile)

// Bộ xử lý có thể thực thi:
flag = true; // Đầu tiên — rẻ hơn
A = 1;       // Rồi
B = 2;       // Rồi
```

Không có rào chắn volatile, một thread khác có thể thấy `flag = true`, nhưng `A` và `B` chưa được ghi.

### Hiệu năng và tải cao (Highload)

#### Chi phí của Memory Barrier

```java
// Benchmark (xấp xỉ):
volatile write:  ~10-50 ns (phụ thuộc kiến trúc)
regular write:   ~1 ns
synchronized:    ~50-500 ns (phụ thuộc mức tranh chấp)
```

Càng nhiều biến volatile = càng nhiều "khựng lại" (stall) trong pipeline của CPU.

#### False Sharing với volatile

```java
public class VolatilePair {
    public volatile long v1; // Trong cùng một cache line (64 byte)
    public volatile long v2; // Ghi v1 làm vô hiệu hóa v2!
}
```

Giải pháp — `@Contended`:

```java
public class ContendedPair {
    @Contended
    public volatile long v1; // Ở các cache line khác nhau

    @Contended
    public volatile long v2;
}
```

Chạy với `-XX:-RestrictContended` cho Java 8+.

### Chẩn đoán

#### JCStress (Java Concurrency Stress)

Công cụ duy nhất để kiểm chứng HB bằng thực nghiệm:

```java
@JCStressTest
@Outcome(id = "0", expect = ACCEPTABLE, desc = "Not published")
@Outcome(id = "42", expect = ACCEPTABLE, desc = "Published correctly")
@Outcome(id = "0", expect = FORBIDDEN, desc = "Visibility bug!")
public class HBTest {
    int data = 0;
    volatile boolean ready = false;

    @Actor
    public void actor1() {
        data = 42;
        ready = true;
    }

    @Actor
    public void actor2(IntResult2 r) {
        if (ready) {
            r.r1 = data;
        }
    }
}
```

#### FindBugs/SpotBugs

Phát hiện các vi phạm JMM tiềm tàng:

```java
// SpotBugs sẽ tìm ra cái này:
public class Bug {
    private int data;        // Không volatile
    private boolean ready;   // Không volatile

    public void write() {
        data = 42;
        ready = true; // Không có HB! Thread khác có thể không thấy data
    }
}
```

### Best Practices

1. **Dùng volatile** cho các cờ và các pattern publish đơn giản
2. **Dùng synchronized** cho các thao tác gộp
3. **Dùng Atomic*** cho các bộ đếm lock-free
4. **final field** tự động nhận đảm bảo HB sau constructor
5. **Tránh** quản lý HB thủ công qua Unsafe/VarHandle trừ khi thật sự cần thiết
6. **Test** code đa luồng qua JCStress, không chỉ các test thông thường

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Happens-before là một đảm bảo về visibility, không phải thứ tự thực thi theo thời gian
- 8 quy tắc JMM: Program Order, Monitor Lock, Volatile Variable, Thread Start, Thread Termination, Interruption, Finalizer, Transitivity
- Nhờ tính bắc cầu, bạn có thể "đi ké" (piggyback) visibility của các biến thông thường lên một biến volatile duy nhất
- Trên x86, rào chắn StoreLoad cần `mfence` — đắt nhất trong tất cả các rào chắn
- Không có happens-before, bộ xử lý và JIT có thể sắp xếp lại các lệnh
- Các field `final` tự động nhận đảm bảo HB sau khi constructor hoàn tất
- HB đảm bảo visibility của kết quả: nếu A HB B, kết quả của A sẽ được nhìn thấy trong B

**Các câu hỏi phụ thường gặp:**
- **Happens-before có nghĩa là A thực thi trước B về mặt thời gian không?** — Không, chỉ là kết quả của A sẽ được nhìn thấy trong B
- **Làm sao đảm bảo visibility của nhiều biến thông thường?** — Ghi chúng, rồi ghi một cờ volatile (piggybacking qua tính bắc cầu)
- **Quy tắc HB nào bao trùm synchronized?** — Monitor Lock: unlock một monitor HB một lần lock tiếp theo của cùng monitor
- **HB khác memory barrier như thế nào?** — HB là đảm bảo ở mức JMM, memory barrier là hiện thực ở mức CPU

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Happens-before nghĩa là các thao tác thực thi theo thứ tự" — không, nó nói về visibility
- "Cứ dùng volatile cho mọi biến" — không, một volatile "gánh" theo mọi lần ghi trước đó
- "Thread.start() không liên quan gì đến HB" — có liên quan: start() HB mọi hành động trong thread được khởi động
- "Trên x86 mọi rào chắn đều đắt" — LoadLoad và StoreStore trên x86 là miễn phí
