# How String Pool Works (String Pool hoạt động như thế nào)

## 🟢 Junior Level

**String Pool** là một cơ chế đặc biệt trong JVM lưu trữ chỉ một bản sao duy nhất của mỗi chuỗi (string) độc nhất. Điều này giúp tiết kiệm bộ nhớ.

Trong một ứng dụng Java điển hình, các chuỗi chiếm 25-40% tổng số object. Không có pool, mỗi bản sao của `"Hello"` sẽ tạo ra một object riêng biệt, ngay cả khi văn bản hoàn toàn giống hệt nhau.

Khi bạn tạo một chuỗi qua literal, JVM kiểm tra xem chuỗi đó đã tồn tại trong pool chưa. Nếu có — nó trả về một tham chiếu đến object đã tồn tại. Nếu không — nó tạo một object mới và thêm vào pool.

**Ví dụ:**
```java
String s1 = "Hello";
String s2 = "Hello";
// s1 và s2 — đây là cùng một object trong bộ nhớ!
System.out.println(s1 == s2); // true
```

**Tại sao điều này cần thiết:** Nếu mỗi chuỗi được tạo như một object riêng biệt, ứng dụng sẽ tiêu tốn nhiều bộ nhớ hơn, đặc biệt nếu các chuỗi giống hệt nhau xuất hiện thường xuyên.

**Khi nào nên dùng:** Dùng string literal (`String s = "value";`) theo mặc định — JVM sẽ tự động đặt chúng vào pool.

## 🟡 Middle Level

### Cách Nó Hoạt Động

String Pool được hiện thực dưới dạng một hash table `StringTable` bên trong JVM. Khi một class được load, tất cả các string literal từ Constant Pool của class đó tự động được đặt vào String Pool.

Constant Pool — một bảng trong file .class chứa tất cả các literal, tên method, và các hằng số khác của class.

**Hai cách một chuỗi vào pool:**
1. **Literal** — tự động khi class load: `String s = "Hello";`
2. **Method intern()** — thủ công tại thời điểm chạy: `String s = new String("Hello").intern();`

### Ứng Dụng Thực Tế
```java
String s1 = "Java";              // Literal → ngay lập tức trong pool
String s2 = new String("Java");  // new → object mới trong heap (KHÔNG trong pool)
String s3 = s2.intern();         // intern() → trả về tham chiếu từ pool đến s1

System.out.println(s1 == s2); // false (các object khác nhau)
System.out.println(s1 == s3); // true (cùng object trong pool)
```

### Các Lỗi Điển Hình
1. **Lỗi:** Dùng `new String("literal")` không cần thiết
   **Giải pháp:** Dùng literal — `String s = "literal";`

2. **Lỗi:** So sánh các chuỗi bằng `==` thay vì `equals()`
   **Giải pháp:** Luôn dùng `equals()` để so sánh nội dung

### So Sánh Các Cách Tiếp Cận
| Cách tiếp cận             | Trong pool?           | Tạo object?      | Khi nào nên dùng                              |
| -------------------- | ------------------ | -------------------- | ---------------------------------------- |
| Literal `"Hello"`    | Có                | Chỉ khi chưa có trong pool  | 99% các trường hợp                             |
| `new String("Hello")`| Không (literal — có) | Luôn tạo mới           | Gần như không bao giờ                        |
| `s.intern()`         | Có                | Chỉ khi chưa có trong pool  | Khi làm việc với số lượng lớn các bản trùng lặp |

## 🔴 Senior Level

### Hiện Thực Nội Bộ

String Pool là một hash table native `StringTable` với open addressing (method chaining). Key và value là các tham chiếu đến các object `java.lang.String`.

```cpp
// Cấu trúc đơn giản hóa từ OpenJDK
class StringTable : public RehashableHashtable<oop, mtSymbol> {
  // oop — con trỏ đến object Java
  // Sử dụng hashing qua String::hash_code
};
```

**Các tham số JVM then chốt:**
- `-XX:StringTableSize=N` — kích thước hash table (mặc định 60013 trong Java 8+, trước đó là 1009)
- Kể từ JDK 11 (JEP 341), StringTable hỗ trợ resize động khi load factor bị vượt quá, tương tự HashMap.

### Sự Phát Triển Bộ Nhớ Của String Pool

| Phiên bản Java          | Vị trí                    | Vấn đề                                      |
| --------------------- | ---------------------------- | --------------------------------------------- |
| Java 6 trở xuống      | **PermGen**                 | Kích thước cố định, OOM thường xuyên: PermGen space       |
| Java 7+               | **Java Heap**               | Được quản lý bởi GC, chỉ giới hạn bởi -Xmx               |
| Java 8+ (Metaspace)   | **Java Heap** (không phải Metaspace!) | Vẫn có thể gây OOM: Java heap space      |

**Nhầm lẫn phổ biến:** String Pool nằm trong Metaspace. Điều này không đúng — nó vẫn ở trong Heap.

### Đánh Đổi Về Kiến Trúc (Trade-off)

**Sử dụng intern() hàng loạt:**

Ưu điểm:
- Giảm mạnh RAM cho các chuỗi trùng lặp
- Ít object hơn → ít GC pause hơn

Nhược điểm:
- `intern()` là một lời gọi native với việc tính hash và tra cứu bảng
- Với số lượng lớn chuỗi, xảy ra contention trên StringTable toàn cục
- Nếu `StringTableSize` nhỏ → các chuỗi collision dài → suy giảm O(n)

### Các Trường Hợp Biên

1. **Xung đột StringTable:** Nếu số lượng chuỗi >> StringTableSize, việc tìm kiếm suy giảm từ O(1) xuống O(n). Kiểm tra: `jcmd <pid> VM.stringtable -verbose`

2. **String Pool và GC:** Trong Java 7+, các chuỗi trong pool có thể bị GC nếu không còn tham chiếu. Nhưng nếu bạn giữ tham chiếu — chúng sẽ không bao giờ bị thu gom.

3. **Compact String (Java 9+):** Không ảnh hưởng trực tiếp đến cơ chế pool, nhưng tiết kiệm 50% bộ nhớ cho các chuỗi Latin trong pool.

### Hiệu Năng
- Tra cứu trong pool trống: ~nanosecond
- Tra cứu trong pool với 1M chuỗi (StringTableSize phù hợp): ~vài chục nanosecond
- Tra cứu trong pool với 1M chuỗi (StringTableSize nhỏ): **microsecond** (xung đột!)

### Kinh Nghiệm Production
Khi load hàng triệu bản ghi từ DB (ví dụ: 1M user với trường `country`), nơi chỉ có 200 quốc gia độc nhất:
- Không dùng `intern()`: 1M object String → ~48MB
- Với `intern()`: 200 object trong pool + 1M tham chiếu → ~5MB
- Nhưng: overhead CPU trên mỗi lời gọi `intern()` có thể là 10-50%

### Giám Sát
```bash
# Thống kê StringTable
jcmd <pid> VM.stringtable -verbose

# Phân tích qua JOL
System.out.println(GraphLayout.parseInstance(stringTable).toFootprint());
```

### Best Practices Cho Highload
- Tăng `-XX:StringTableSize` lên một số nguyên tố > số lượng chuỗi độc nhất dự kiến
- Đừng dùng `intern()` cho các chuỗi tồn tại ngắn (chúng sẽ chết trong Young Gen dù sao đi nữa)
- Cân nhắc `-XX:+UseStringDeduplication` (G1 GC) như một giải pháp thay thế trong suốt

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- String Pool — hash table (`StringTable`) trong JVM, lưu trữ một bản sao của mỗi chuỗi độc nhất
- Các literal tự động vào pool khi class load
- `new String("...")` tạo một object riêng biệt trong heap, KHÔNG trong pool
- `intern()` thêm chuỗi vào pool và trả về tham chiếu từ pool
- Trong Java 7+, String Pool nằm trong Java Heap (không phải PermGen/Metaspace!)
- `-XX:StringTableSize` — kích thước hash table (mặc định 60013 trong Java 8+)
- Với xung đột StringTable, việc tìm kiếm suy giảm từ O(1) xuống O(n)
- Compact String (Java 9+) tiết kiệm 50% bộ nhớ cho các chuỗi Latin-1 trong pool

**Các câu hỏi phụ thường gặp:**
- **String Pool nằm ở đâu?** — Trong Java Heap (kể từ Java 7). Lỗi phổ biến — trả lời Metaspace.
- **Một chuỗi vào pool như thế nào?** — Qua literal (tự động) hoặc lời gọi `intern()` (thủ công).
- **Một chuỗi có thể bị xóa khỏi pool không?** — Có, trong Java 7+ GC có thể thu gom các mục trong pool nếu không còn tham chiếu.
- **Điều gì xảy ra với `new String("Hello").intern()`?** — Một object được tạo trong Heap, sau đó `intern()` tìm `"Hello"` trong pool và trả về tham chiếu pool. Object trong Heap trở thành rác.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "String Pool nằm trong Metaspace" — không đúng, nó nằm trong Heap
- ❌ "`==` luôn hoạt động với các chuỗi" — chỉ hoạt động với literal/chuỗi đã intern
- ❌ "`intern()` là miễn phí" — nó là một lời gọi native với overhead CPU
- ❌ "String Pool có kích thước cố định" — nó chỉ bị giới hạn bởi `-Xmx` trong Java 7+
