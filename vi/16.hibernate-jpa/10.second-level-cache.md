# What is the Second-Level Cache and When to Use It (Second-level cache là gì và khi nào dùng nó)

## Overview

Second-level cache (L2 cache) là một cache ở cấp độ EntityManagerFactory, được chia sẻ giữa tất cả các session. Khác với L1 cache, nó tồn tại qua việc đóng session và có thể được nhiều transaction sử dụng.

**Tại sao:** khi 100 người dùng đồng thời yêu cầu cùng dữ liệu tham chiếu (ví dụ, một danh sách các quốc gia), L1 cache vô dụng - mỗi session có cache riêng của nó. L2 cache tải các quốc gia MỘT LẦN và chia sẻ giữa tất cả.

---

## Junior Level

### L2 Cache Là Gì

Second-level cache là một cache **được chia sẻ giữa các session**. Nếu một session tải một entity, session khác có thể lấy nó từ L2 cache mà không cần truy cập DB.

```
Session 1: tải User(1) -> L1 cache + L2 cache
Session 1: đóng -> L1 cache bị xóa, L2 cache vẫn giữ nguyên
Session 2: tải User(1) -> L2 cache (KHÔNG có DB!)
```

### L1 vs L2 Cache

| Đặc tính            | L1 Cache      | L2 Cache                  |
| ------------------- | ------------- | ------------------------- |
| **Cấp độ**          | EntityManager | EntityManagerFactory      |
| **Theo mặc định**   | Bật           | Cần bật                    |
| **Vòng đời**        | Một session   | Toàn bộ ứng dụng           |
| **Chia sẻ**         | Không         | Giữa các session           |
| **Provider**        | Tích hợp sẵn  | Ehcache, Hazelcast, Redis |

### Khi Nào L2 Cache Hữu Ích

**Phù hợp khi:**
- Dữ liệu hiếm khi thay đổi (dữ liệu tham chiếu, quốc gia, tiền tệ)
- Nhiều đọc, ít ghi
- Nhiều instance ứng dụng

**Không phù hợp khi:**
- Dữ liệu thay đổi thường xuyên (order, log)
- Yêu cầu dữ liệu tươi tuyệt đối
- Nhiều ghi hơn đọc

## Middle Level

### Khi Nào KHÔNG Nên Dùng L2 Cache

L2 cache KHÔNG hoạt động với:
- Truy vấn SQL native (Hibernate không biết entity nào bị ảnh hưởng)
- Query cache cho phân trang (được cache riêng biệt)
- EntityManager.clear() không xóa L2 cache

### Cấu Hình

```xml
<!-- Dependency cho JCache provider -->
<dependency>
    <groupId>org.hibernate.orm</groupId>
    <artifactId>hibernate-jcache</artifactId>
</dependency>
```

```yaml
# application.yml
spring:
  jpa:
    properties:
      hibernate:
        cache:
          use_second_level_cache: true
          region:
            factory_class: org.hibernate.cache.jcache.JCacheRegionFactory
      javax.persistence.sharedCache.mode: ENABLE_SELECTIVE
```

Trong Hibernate 5.x, `javax.persistence` được dùng. Trong Hibernate 6+ / Jakarta EE, thay bằng `jakarta.persistence` và cập nhật đường dẫn factory class.

```java
// Đánh dấu entity để cache
@Entity
@Cacheable
@org.hibernate.annotations.Cache(usage = CacheConcurrencyStrategy.READ_WRITE)
public class User {
    @Id
    private Long id;
    private String name;
}
```

### Các Chiến Lược Caching

```
READ_ONLY:
- Chỉ đọc, dữ liệu không bao giờ thay đổi
- Chiến lược nhanh nhất
- Cho dữ liệu tham chiếu, quốc gia, tiền tệ

READ_WRITE:
- Đọc và ghi với đồng bộ hóa
- Dùng soft lock
- Cho dữ liệu thay đổi vừa phải

NONSTRICT_READ_WRITE:
- Đọc và ghi mà không có đồng bộ hóa nghiêm ngặt
- Có thể trả về dữ liệu cũ
- Cho dữ liệu hiếm khi thay đổi

TRANSACTIONAL:
- Tính nhất quán transactional đầy đủ
- Yêu cầu XA transaction
- Cho dữ liệu quan trọng
```

### Quản Lý Cache

```java
Cache cache = entityManager.getEntityManagerFactory().getCache();

// Evict entity cụ thể
cache.evict(User.class, userId);

// Evict tất cả entity của loại đó
cache.evict(User.class);

// Evict mọi thứ
cache.evictAll();
```

### Các Lỗi Thường Gặp

```java
// Cache dữ liệu thay đổi thường xuyên
@Cache(usage = CacheConcurrencyStrategy.READ_ONLY)
public class Order { }
// Order thay đổi thường xuyên -> dữ liệu cũ!

// Không có TTL
// Cache tăng vô hạn -> rò rỉ bộ nhớ
// Giải pháp: luôn đặt TTL
```

## Senior Level

Soft lock - cơ chế khóa mềm: Hibernate đánh dấu entry trong cache là "đang cập nhật", các thread khác chờ. Khác với khóa cứng ở DB, cách này không khóa dòng của table.

XA transaction - transaction hai pha đảm bảo tính atomic của các thao tác cả trong DB lẫn trong cache.

Eventual consistency - tính nhất quán cuối cùng đạt được: sau khi cập nhật, dữ liệu trong cache trên các node khác nhau trở nên giống nhau không ngay lập tức, mà sau một khoảng thời gian.

### Cơ Chế Invalidation

```
Việc invalidate L2 cache xảy ra khi:
- UPDATE/DELETE của entity -> loại khỏi cache
- evict() rõ ràng -> loại bỏ khỏi cache
- TTL hết hạn -> tự động loại bỏ
- Cluster replication -> replicate giữa các node
```

### Clustered Cache

```yaml
# Hazelcast L2 cache cho cluster
spring:
  jpa:
    properties:
      hibernate:
        cache:
          region:
            factory_class: com.hazelcast.hibernate.HazelcastCacheRegionFactory
```

```
Cho nhiều instance ứng dụng:
- Replicate cache giữa các node (Hazelcast, Redis)
- Eventual consistency (không phải strong)
- Overhead network khi replicate
- Phải được cân nhắc trong thiết kế

Khi User được cập nhật trên Node 1: (1) Hibernate cập nhật DB;
(2) invalidate entry trong L2 cache Node 1;
(3) Hazelcast broadcast thông báo invalidation đến Node 2, 3;
(4) Request tiếp theo trên Node 2 miss cache và tải từ DB.
```

### Monitoring Production

```java
// Hibernate Statistics
Statistics stats = entityManagerFactory.unwrap(SessionFactory.class).getStatistics();

// Metric L2 cache
long hitCount = stats.getSecondLevelCacheHitCount();
long missCount = stats.getSecondLevelCacheMissCount();
double hitRatio = (double) hitCount / (hitCount + missCount);

// Cho giám sát production
// hitRatio > 0.8 - xuất sắc, cache dùng hiệu quả
// hitRatio < 0.5 - kiểm tra: có chọn đúng entity để cache không, kích thước cache có đủ không, TTL có quá ngắn không
```

### Cấu Hình Ehcache

```xml
<!-- ehcache.xml -->
<config>
    <cache alias="com.example.User">
        <heap unit="entries">1000</heap>
        <offheap unit="MB">50</offheap>
        <expiry>
            <ttl unit="minutes">30</ttl>
        </expiry>
    </cache>

    <cache alias="com.example.Country">
        <heap unit="entries">500</heap>
        <expiry>
            <ttl unit="hours">24</ttl>
        </expiry>
    </cache>
</config>
```

### Query Cache vs L2 Cache

Query cache lưu: "truy vấn X với tham số Y trả về các entity với ID [1,2,3]".
L2 cache lưu: "entity User(1) = {name: John, ...}".
Chúng hoạt động cùng nhau: Query cache đưa ra ID, L2 cache đưa ra dữ liệu.
Query cache vô dụng nếu không có L2 cache.

### Best Practices

```
READ_ONLY cho dữ liệu tham chiếu và hằng số
READ_WRITE cho dữ liệu thay đổi vừa phải
Giám sát tỷ lệ hit/miss
Đặt TTL cho mỗi region
Giới hạn kích thước heap
Invalidate khi cập nhật
Clustered cache cho multi-node

Cho dữ liệu thay đổi thường xuyên
Không giám sát hit ratio
Không có TTL và giới hạn bộ nhớ
Cache cho các entity có vấn đề N+1
Dùng như một sự thay thế cho kiến trúc đúng đắn
```

## Interview Cheat Sheet

**Cần phải biết:**
- L2 cache - ở cấp độ EntityManagerFactory, chia sẻ giữa các session
- Cần được bật: chọn provider (Ehcache, Hazelcast, Redis), cấu hình
- Các chiến lược: READ_ONLY (dữ liệu tham chiếu), READ_WRITE (thay đổi vừa phải), NONSTRICT_READ_WRITE, TRANSACTIONAL
- Hữu ích cho: dữ liệu hiếm khi thay đổi, nhiều đọc/ít ghi, dữ liệu tham chiếu
- Query cache lưu ID entity, dữ liệu thực tế - từ L2 cache (vô dụng nếu không có L2)
- Monitoring: hitRatio > 0.8 xuất sắc, < 0.5 - kiểm tra cấu hình

**Các câu hỏi phụ thường gặp:**
- **L1 vs L2 cache?** L1 - trong phạm vi session (luôn bật), L2 - giữa các session (cần bật)
- **Khi nào L2 cache KHÔNG hoạt động?** Truy vấn SQL native, query cache cho phân trang, sau EntityManager.clear()
- **Clustered cache hoạt động như thế nào?** Replicate giữa các node (Hazelcast, Redis), eventual consistency
- **Soft lock là gì?** Khóa mềm - Hibernate đánh dấu entry là "đang cập nhật", các thread khác chờ

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi cache tất cả entity một cách bừa bãi" - chỉ nên cache những cái đọc nhiều
- "Không có TTL - cache tăng vô hạn" - rò rỉ bộ nhớ
- "L2 cache cho Order/Log" - dữ liệu thay đổi thường xuyên, cache không hiệu quả
- "Query cache không có L2 cache" - vô dụng, chỉ lưu ID
