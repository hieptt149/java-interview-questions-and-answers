# What does map() operation do? (Thao tác map() làm gì?)

## Junior Level

**`map(Function)`** là một thao tác intermediate biến đổi mỗi phần tử của stream thành một phần tử khác ("một-đối-một").

Nhận một `Function<T, R>` — một functional interface với phương thức `R apply(T t)`.

```java
List<String> words = List.of("hello", "world");

// Biến đổi các từ thành độ dài của chúng
List<Integer> lengths = words.stream()
    .map(String::length)
    .collect(Collectors.toList());
// Kết quả: [5, 5]

// Biến đổi thành chữ hoa
List<String> upper = words.stream()
    .map(String::toUpperCase)
    .collect(Collectors.toList());
// Kết quả: ["HELLO", "WORLD"]
```

**Quan trọng:** `map` luôn trả về một object cho mỗi phần tử đầu vào.

## Middle Level

### Hiện thực bên trong

`map` tích hợp vào chuỗi `Sink`:
```java
public void accept(T t) {
    downstream.accept(mapper.apply(t));
}
```

Do tính lười, nếu kết quả của `map` không được dùng bởi một thao tác terminal, hàm biến đổi sẽ không bao giờ được gọi.

### Tránh Wrapper Hell (Autoboxing)

```java
// XẤU — tạo hàng triệu object Integer trên heap
list.stream().map(s -> s.length()).reduce(0, Integer::sum);

// TỐT — làm việc với các primitive trên stack
list.stream().mapToInt(String::length).sum();
```

**Primitive Stream** (`IntStream`, `LongStream`, `DoubleStream`) giảm mạnh tải cho GC và mức tiêu thụ bộ nhớ.

IntStream/LongStream/DoubleStream lưu các primitive trực tiếp, không có wrapper (Integer, Long). Với 1 triệu phần tử: Stream<Integer> = 1 triệu object trên heap (~24MB), IntStream = một mảng int[] (~4MB). Khác biệt bộ nhớ 6 lần.

### Map vs FlatMap

- **`map`**: trả về **một** object cho mỗi đầu vào
- **`flatMap`**: trả về một **stream** các object (từ 0 tới vô hạn), thứ được "làm phẳng" thành một stream duy nhất

### Tính thuần khiết của hàm (Function Purity)

Hàm trong `map` nên **thuần khiết (pure)** (không có side effect). Trên thực tế các hàm không thuần khiết vẫn hoạt động, nhưng có rủi ro: trong parallelStream kết quả sẽ không dự đoán được.
- Đừng sửa đổi object đầu vào (tính bất biến)
- Không có side effect (đừng ghi vào DB, đừng sửa đổi các trường static)
- Trả về cùng một kết quả cho cùng một dữ liệu đầu vào

### Khi nào KHÔNG nên dùng map

1. **Bạn không cần kết quả của phép biến đổi** — dùng forEach (cho các hành động) hoặc peek (để debug)
2. **Lọc + biến đổi trong một** — đôi khi một vòng lặp với if + biến đổi thì tốt hơn
3. **Làm việc với side effect** — map không dành cho I/O, hãy dùng forEach

## Senior Level

### Method Reference và tối ưu hóa JIT

Dùng `String::toUpperCase` thay vì `s -> s.toUpperCase()`. Điều này không chỉ sạch hơn mà còn giúp trình biên dịch JIT tối ưu hóa các lời gọi tốt hơn qua `invokedynamic`.

### Xử lý Null

Nếu hàm mapping trả về `null`, stream sẽ tiếp tục với một phần tử `null`. Điều này thường dẫn tới NPE trong các mắt xích tiếp theo:

```java
// Cách tiếp cận an toàn
stream.map(User::getEmail)
      .filter(Objects::nonNull)
      .map(String::toLowerCase)
```

### Checked Exception

Các lambda trong `map` không thể ném các checked exception. Bạn phải bọc chúng trong `RuntimeException` hoặc dùng các interface trợ giúp:

```java
// Bọc checked exception
stream.map(s -> {
    try {
        return URLEncoder.encode(s, "UTF-8");
    } catch (UnsupportedEncodingException e) {
        throw new RuntimeException(e);
    }
})
```

### Cấp phát Object và Highload

Nếu hàm trong `map` tạo các object nặng, hãy cân nhắc tái sử dụng object (Object Pooling), dù điều này khó hiện thực trong các stream.

### Chẩn đoán

- **Thay đổi kiểu:** Theo dõi cách kiểu của stream thay đổi dọc theo chuỗi — IntelliJ IDEA tô sáng các kiểu
- **Phát hiện Side Effect:** Nếu `map` chứa `System.out.println` hoặc `log.info` — đây là một dấu hiệu của thiết kế tồi. Để ghi log, hãy dùng `peek()`.

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- `map(Function)` — thao tác intermediate, biến đổi một-đối-một
- Nhận `Function<T, R>`, trả về `Stream<R>`
- Primitive Stream (mapToInt, mapToLong) tránh autoboxing và tiết kiệm bộ nhớ
- Hàm mapping nên thuần khiết: không có side effect, có tính tất định
- Method Reference (`String::toUpperCase`) được ưa chuộng hơn lambda — sạch hơn và giúp JIT
- Nếu mapper trả về null — stream tiếp tục với một phần tử null (rủi ro NPE)

**Các câu hỏi phụ thường gặp:**
- map vs flatMap? — map trả về một object, flatMap trả về một stream các object được "làm phẳng"
- Tại sao mapToInt tốt hơn map? — IntStream lưu các primitive trong một mảng, Stream<Integer> tạo các object trên heap
- Cách xử lý checked exception trong một lambda? — Bọc trong RuntimeException hoặc dùng các interface trợ giúp
- Có thể dùng map cho I/O không? — Không, map không dành cho side effect, hãy dùng forEach

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "map có thể trả về nhiều object cho một phần tử" — đó là flatMap
- "Autoboxing không ảnh hưởng hiệu suất" — với hàng triệu phần tử khác biệt bộ nhớ là 6 lần
- "Hàm trong map có thể sửa đổi các biến bên ngoài" — điều này vi phạm tính thuần khiết và phá vỡ parallelStream
- "map và forEach có thể thay thế cho nhau" — map biến đổi, forEach thực hiện một hành động
