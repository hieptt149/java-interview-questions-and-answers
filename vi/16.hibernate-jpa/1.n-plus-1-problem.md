# What is the N+1 Problem and How to Solve It (N+1 problem là gì và cách giải quyết)

## Overview

N+1 problem là một trong những vấn đề hiệu năng phổ biến nhất trong Hibernate. Nó xảy ra khi các entity liên quan được tải không đúng cách, gây ra sự tăng trưởng tuyến tính trong số lượng truy vấn SQL: 1 truy vấn cho parent + N truy vấn cho các entity con.

---

## Junior Level

### N+1 Problem Là Gì

Đây là tình huống mà Hibernate thực thi **một truy vấn** để lấy danh sách các object, sau đó **N truy vấn bổ sung** (một cho mỗi object) để tải dữ liệu liên quan.

```java
@Entity
public class Order {
    @Id
    private Long id;

    @OneToMany(mappedBy = "order", fetch = FetchType.LAZY)
    private List<OrderItem> items;
}

// N+1 problem:
List<Order> orders = entityManager.createQuery("SELECT o FROM Order o", Order.class)
    .getResultList();  // 1 truy vấn: SELECT * FROM orders

for (Order order : orders) {
    order.getItems().size();  // N truy vấn: SELECT * FROM order_items WHERE order_id = ?
}

// Tổng: 1 + N = N+1 truy vấn!
// 100 order -> 101 truy vấn đến DB
```

### Cách Nhận Biết

- Log hiển thị nhiều truy vấn SELECT giống hệt nhau
- Ứng dụng chậm khi tải các collection
- Số lượng truy vấn tỷ lệ thuận với số lượng bản ghi

### Các Giải Pháp Cơ Bản

1. **JOIN FETCH** - gộp thành một truy vấn
2. **@BatchSize** - tải theo từng batch
3. **EntityGraph** - chỉ định động cái gì cần tải

### Khi Nào KHÔNG Nên Dùng Từng Cách Tiếp Cận

- **JOIN FETCH** - không dùng với nhiều collection (Cartesian product)
- **@BatchSize** - không dùng khi dữ liệu LUÔN LUÔN cần thiết (nên dùng JOIN FETCH hơn)
- **EntityGraph** - không dùng trong các thao tác CRUD đơn giản (overhead khi tạo graph)
- **Subselect** - không dùng khi các parent được tải từng cái một (Hibernate rơi lại về SELECT)

## Middle Level

### Các Giải Pháp Chi Tiết

#### 1. JOIN FETCH trong JPQL

```java
@Query("SELECT DISTINCT o FROM Order o JOIN FETCH o.items")
List<Order> findAllWithItems();

// Sinh ra một truy vấn:
// SELECT DISTINCT o.* FROM orders o
// JOIN order_items oi ON o.id = oi.order_id
```

**Luôn dùng DISTINCT** - nếu không có nó, Hibernate trả về các Order trùng lặp (một cho mỗi OrderItem).

#### 2. @BatchSize

```java
@Entity
public class Order {
    @OneToMany(mappedBy = "order")
    @BatchSize(size = 10)
    private List<OrderItem> items;
}

// Thay vì N truy vấn: N/10 truy vấn
// Hibernate: SELECT * FROM order_items WHERE order_id IN (?,?,?,?,?,?,?,?,?,?)
```

#### 3. EntityGraph

```java
@EntityGraph(attributePaths = {"items"})
@Query("SELECT o FROM Order o")
List<Order> findAllWithItems();

// Hoặc theo cách lập trình:
EntityGraph<Order> graph = entityManager.createEntityGraph(Order.class);
graph.addSubgraph("items");

List<Order> orders = entityManager.createQuery("SELECT o FROM Order o", Order.class)
    .setHint("jakarta.persistence.fetchgraph", graph)
    .getResultList();
```

### So Sánh Các Cách Tiếp Cận

| Cách tiếp cận | Khi nào dùng                  | Số truy vấn |
| ----------- | ---------------------------- | ----------- |
| JOIN FETCH  | Dữ liệu liên quan luôn cần    | 1           |
| @BatchSize  | Dữ liệu liên quan đôi khi cần | N/batchSize |
| EntityGraph | Tải động                      | 1           |
| EAGER       | Không bao giờ (antipattern)  | N           |

### Các Lỗi Thường Gặp

```java
// EAGER loading cho collection
@OneToMany(fetch = FetchType.EAGER)
private List<OrderItem> items;
// Luôn tải tất cả phần tử -> vấn đề hiệu năng

// Nhiều JOIN FETCH -> Cartesian Product
@Query("SELECT o FROM Order o JOIN FETCH o.items JOIN FETCH o.payments")
// 10 order x 5 item x 3 payment = 150 dòng!
```

## Senior Level

### Triển Khai Nội Bộ

N+1 problem xảy ra vì cách Hibernate làm việc với **lazy loading proxy**:

```
1. Order.getItems() trả về một proxy PersistentCollection
   Một proxy là một lớp con đặc biệt mà Hibernate tạo ra thay cho object thật. Khi bạn truy cập các trường của nó, Hibernate chặn lời gọi và tải dữ liệu từ DB.
2. Ở lần truy cập đầu tiên vào proxy, Hibernate kiểm tra xem collection đã được khởi tạo chưa
3. Nếu chưa - thực thi SELECT cho order_id cụ thể
4. Với mỗi Order - một SELECT riêng biệt, vì mỗi proxy được khởi tạo riêng lẻ
```

### Các Chiến Lược Nâng Cao

#### 1. Subselect fetching

```java
@OneToMany(mappedBy = "order")
@Fetch(FetchMode.SUBSELECT)
private List<OrderItem> items;

// Một subquery cho tất cả:
// SELECT * FROM order_items WHERE order_id IN (SELECT id FROM orders)
```

SUBSELECT vs @BatchSize: SUBSELECT thực thi một truy vấn cho TẤT CẢ các parent đã tải, trong khi @BatchSize chia thành các nhóm. SUBSELECT hiệu quả hơn khi có ít parent, BatchSize khi có nhiều.

#### 2. Cải tiến của Hibernate 6

```java
// Hibernate 6.2+ hỗ trợ batching SELECT riêng biệt theo mặc định
// @BatchSize không còn cần thiết cho collection nữa
// Nhưng vẫn hữu ích cho @ManyToOne
```

#### 3. Phát Hiện Trong Production

```java
// p6spy - log tất cả SQL
// datasource-proxy - chặn theo cách lập trình
// Spring Boot Actuator + Hibernate Statistics

@Bean
public DataSource dataSource() {
    return ProxyDataSourceBuilder.create(actualDataSource)
        .logQueryBySlf4j()
        .countQuery()
        .build();
}
```

### Khuyến Nghị Kiến Trúc

```
LAZY theo mặc định cho tất cả các association
JOIN FETCH khi dữ liệu liên quan luôn cần thiết
@BatchSize (10-50) cho các collection
DTO projection cho các kịch bản chỉ đọc
Giám sát truy vấn SQL trong production
Review định kỳ slow query log

EAGER không có lý do chính đáng
Bỏ qua N+1 trong code review
Không giám sát truy vấn
Dùng entity thay vì DTO cho API
```

### Khi Nào N+1 Chấp Nhận Được

Trong một số trường hợp hiếm, N+1 có thể chấp nhận được:
- Dữ liệu nhỏ (< 10 bản ghi)
- Dữ liệu liên quan được cache trong L2 cache
- Dùng với @BatchSize có size lớn

## Interview Cheat Sheet

**Cần phải biết:**
- N+1 problem: 1 truy vấn cho parent + N truy vấn cho các entity con
- Giải pháp chính - JOIN FETCH (một truy vấn với JOIN)
- @BatchSize tải theo batch: N truy vấn -> N/batchSize
- EntityGraph để tải động các association
- EAGER cho collection là một antipattern, gây ra N+1
- DISTINCT là bắt buộc với JOIN FETCH để loại bỏ trùng lặp
- Nhiều JOIN FETCH -> Cartesian product (tránh nó)
- Giám sát truy vấn SQL trong production (p6spy, datasource-proxy)

**Các câu hỏi phụ thường gặp:**
- **Khi nào N+1 chấp nhận được?** Dữ liệu nhỏ (<10 bản ghi), L2 cache, hoặc với @BatchSize
- **Tại sao cần DISTINCT?** JOIN trả về một dòng cho mỗi child, DISTINCT loại bỏ các root object trùng lặp trong bộ nhớ
- **Cái nào tốt hơn - JOIN FETCH hay @BatchSize?** JOIN FETCH khi dữ liệu luôn cần, @BatchSize khi thỉnh thoảng cần
- **Cách phát hiện N+1?** Bật SQL logging, đếm truy vấn, dùng p6spy

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi dùng EAGER để tránh N+1" - EAGER tự nó gây ra N+1
- "N+1 không phải là vấn đề với các ORM hiện đại" - đó là vấn đề trong bất kỳ ORM nào
- "Tôi luôn dùng JOIN FETCH cho mọi thứ" - Cartesian product với nhiều collection
- "Tôi không giám sát truy vấn SQL" - không giám sát, N+1 là vô hình
