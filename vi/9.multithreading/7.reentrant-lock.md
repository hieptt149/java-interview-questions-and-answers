# What is reentrant lock? (Reentrant lock là gì?)

---

## Junior Level

### Hiểu biết cơ bản

Một **Reentrant Lock** (khóa tái nhập) là một cơ chế cho phép một thread đã sở hữu một khóa acquire lại nó mà không tự gây deadlock.

**Tại sao nó quan trọng:** không có reentrancy, một lời gọi đệ quy tới một synchronized method sẽ dẫn tới deadlock — thread sẽ chờ chính nó. Với reentrancy, JVM đếm số lần thread acquire khóa (một bộ đếm) và chỉ giải phóng khi bộ đếm = 0.

### Ví dụ minh họa đơn giản

Hãy tưởng tượng một cánh cửa có khóa mã số:
- Khóa thông thường: ngay cả khi bạn đã ở bên trong, để vào lại — bạn phải chờ
- Reentrant lock: nếu bạn đã ở bên trong, bạn có thể ra và vào lại bao nhiêu lần tùy thích

### Ví dụ trong Java

#### synchronized (reentrant theo mặc định)

```java
public class ReentrantDemo {
    public synchronized void methodA() {
        System.out.println("Method A");
        methodB(); // Gọi một synchronized method khác — KHÔNG bị chặn!
    }

    public synchronized void methodB() {
        System.out.println("Method B");
    }
}
```

#### ReentrantLock

```java
import java.util.concurrent.locks.ReentrantLock;

public class ReentrantLockDemo {
    private final ReentrantLock lock = new ReentrantLock();

    public void methodA() {
        lock.lock();
        try {
            System.out.println("Method A");
            methodB(); // Cùng thread có thể acquire khóa lần nữa
        } finally {
            lock.unlock();
        }
    }

    public void methodB() {
        lock.lock();
        try {
            System.out.println("Method B");
        } finally {
            lock.unlock();
        }
    }
}
```

### Bộ đếm Reentrancy hoạt động như thế nào

```
Thread 1: lock.lock()    → counter = 1, vào
Thread 1: lock.lock()    → counter = 2, vào (cùng thread!)
Thread 1: lock.unlock()  → counter = 1, vẫn là owner
Thread 1: lock.unlock()  → counter = 0, giải phóng
Thread 2: lock.lock()    → counter = 1, bây giờ Thread 2 là owner
```

### Khi nào dùng ReentrantLock thay vì synchronized

| Tình huống                     | synchronized            | ReentrantLock               |
| ------------------------------ | ----------------------- | --------------------------- |
| Đồng bộ hóa đơn giản           | Có                      | Quá mức cần thiết           |
| Timeout khi chờ                | Không                   | Có (`tryLock(timeout)`)     |
| Chờ có thể bị interrupt        | Không                   | Có (`lockInterruptibly()`)  |
| Nhiều điều kiện (Condition)    | Không (chỉ wait/notify) | Có (nhiều Condition)        |
| Fairness (hàng đợi công bằng)  | Không                   | Có                          |

## Middle Level

### Cấu trúc bên trong (AQS)

`ReentrantLock` được xây dựng trên **AbstractQueuedSynchronizer (AQS)** — một framework từ `java.util.concurrent`:

  AQS — một framework class trừu tượng từ java.util.concurrent, thứ mà TẤT CẢ các tiện ích concurrency của Java được xây dựng trên: ReentrantLock, Semaphore, CountDownLatch, ReentrantReadWriteLock. Nếu bạn hiểu AQS — bạn hiểu toàn bộ concurrency của Java.

```java
// Cấu trúc AQS đơn giản hóa
abstract class AbstractQueuedSynchronizer {
    private volatile int state;        // Bộ đếm khóa (reentrancy)
    private transient Thread exclusiveOwnerThread; // Thread sở hữu

    // Hàng đợi chờ (danh sách liên kết đôi)
    static final class Node {
        volatile Thread thread;
        volatile int waitStatus;
        Node prev, next;
    }
    private transient volatile Node head;
    private transient volatile Node tail;
}
```

#### Thuật toán Acquire

```java
// Mã giả lock()
protected final boolean tryAcquire(int acquires) {
    Thread current = Thread.currentThread();
    int c = getState();

    if (c == 0) {
        // Khóa đang rảnh — thử acquire
        if (!hasQueuedPredecessors() && compareAndSetState(0, acquires)) {
            setExclusiveOwnerThread(current);
            return true;
        }
    } else if (current == getExclusiveOwnerThread()) {
        // Cùng thread — reentrancy
        int nextc = c + acquires;
        if (nextc < 0) throw new Error("Maximum lock count exceeded");
        setState(nextc);
        return true;
    }
    return false;
}
```

### Fairness (tính công bằng)

```java
// Chế độ non-fair (mặc định) — nhanh hơn
ReentrantLock nonFair = new ReentrantLock(); // fair = false

// Non-fair (mặc định) — cho phép "barge": nếu khóa vừa được giải phóng và một thread mới cố acquire nó, nó có thể lấy được ngay lập tức mà không cần vào hàng đợi. Điều này tránh context switch (park/wakeup) và cho throughput cao hơn.

// Chế độ fair — FIFO nghiêm ngặt
ReentrantLock fair = new ReentrantLock(true); // fair = true
```

| Chế độ                 | Hành vi                                                                  | Hiệu năng                      |
| ---------------------- | ------------------------------------------------------------------------- | ------------------------------ |
| **Non-fair** (mặc định)| Thread có thể "barge" và acquire khóa ngay cả khi có các thread trong hàng đợi | Throughput cao hơn             |
| **Fair**               | Các thread được cấp quyền truy cập đúng theo thứ tự hàng đợi (FIFO)       | Throughput thấp hơn, không starvation |

### Các tính năng nâng cao của ReentrantLock

#### 1. tryLock() — thử mà không chờ

```java
if (lock.tryLock()) {
    try {
        // Đã acquire — thực thi
    } finally {
        lock.unlock();
    }
} else {
    // Thất bại — làm việc khác
    System.out.println("Lock is busy, skipping");
}
```

#### 2. tryLock(timeout) — chờ với timeout

```java
if (lock.tryLock(100, TimeUnit.MILLISECONDS)) {
    try {
        // Thực thi
    } finally {
        lock.unlock();
    }
} else {
    // Timeout — không acquire được trong 100ms
}
```

#### 3. lockInterruptibly() — chờ có thể bị interrupt

```java
try {
    lock.lockInterruptibly();
    try {
        // Thực thi
    } finally {
        lock.unlock();
    }
} catch (InterruptedException e) {
    // Thread bị interrupt trong lúc chờ
    Thread.currentThread().interrupt();
}
```

### Condition — thay thế cho wait/notify

```java
ReentrantLock lock = new ReentrantLock();
Condition notEmpty = lock.newCondition();
Condition notFull = lock.newCondition();

public void produce(int item) throws InterruptedException {
    lock.lock();
    try {
        while (queue.size() == MAX_SIZE) {
            // while (chưa sẵn sàng) — BẮT BUỘC! Spurious wakeup (đánh thức giả):
            // thread có thể thức dậy MÀ KHÔNG có signal(). while kiểm tra lại điều kiện.
            // Nếu bạn dùng if — thread tiếp tục mà không có signal thật sự.
            notFull.await(); // Chờ chỗ trống
        }
        queue.add(item);
        notEmpty.signal(); // Thông báo cho các consumer
    } finally {
        lock.unlock();
    }
}

public int consume() throws InterruptedException {
    lock.lock();
    try {
        while (queue.isEmpty()) {
            // while (chưa sẵn sàng) — BẮT BUỘC! Spurious wakeup (đánh thức giả):
            // thread có thể thức dậy MÀ KHÔNG có signal(). while kiểm tra lại điều kiện.
            // Nếu bạn dùng if — thread tiếp tục mà không có signal thật sự.
            notEmpty.await(); // Chờ dữ liệu
        }
        int item = queue.remove(0);
        notFull.signal(); // Thông báo cho các producer
        return item;
    } finally {
        lock.unlock();
    }
}
```

**Ưu điểm so với wait/notify:** bạn có thể có các Condition khác nhau cho các sự kiện khác nhau.

## Khi nào KHÔNG cần ReentrantLock

1. **Đồng bộ hóa đơn giản** — một synchronized là đủ, code đơn giản và dễ đọc hơn
2. **Không có tranh chấp** — synchronized được JVM tối ưu (thin lock, elision)
3. **Không cần các tính năng của Lock** — tryLock, fairness, Condition không cần thiết

**Khác biệt then chốt:** synchronized là một từ khóa ngôn ngữ (mức JVM), ReentrantLock là một class thư viện. Điều này quyết định mọi khác biệt khác.

## Senior Level

### Bên trong: NonfairSync và FairSync

`ReentrantLock` dùng hai class nội bộ:

```java
public class ReentrantLock implements Lock {
    private final Sync sync;

    public ReentrantLock() {
        sync = new NonfairSync(); // Mặc định
    }

    public ReentrantLock(boolean fair) {
        sync = fair ? new FairSync() : new NonfairSync();
    }
}
```

#### NonfairSync

```java
static final class NonfairSync extends Sync {
    protected final boolean tryAcquire(int acquires) {
        // Thread có thể acquire khóa ngay cả khi các thread khác đang trong hàng đợi
        // Cái này gọi là "barge"

        // "barge" — một thread mới cố acquire khóa mà không vào hàng đợi chờ. Nếu may mắn — khóa đang rảnh, thread lấy được ngay lập tức mà không cần parking.
        return nonfairTryAcquire(acquires);
    }
}
```

#### FairSync

```java
static final class FairSync extends Sync {
    protected final boolean tryAcquire(int acquires) {
        // Kiểm tra trước: có waiter nào trong hàng đợi không?
        if (!hasQueuedPredecessors() && compareAndSetState(0, acquires)) {
            setExclusiveOwnerThread(Thread.currentThread());
            return true;
        }
        return false;
    }
}
```

### Hiệu năng: Fair vs Non-fair

```
Non-fair: throughput ~100K ops/giây
Fair:     throughput ~50K ops/giây  (~50% chậm hơn; giá trị xấp xỉ, phụ thuộc CPU và JVM)
```

**Tại sao fair chậm hơn:**
- Cần kiểm tra hàng đợi mỗi lần
- Các thread park/wakeup thường xuyên hơn (context switching)
- Không có tối ưu "barge"

**Khi nào dùng fair:**
- Khi phải tránh starvation
- Khi thứ tự xử lý là then chốt

### AQS: Hàng đợi chờ hoạt động như thế nào

```
                    ┌─────────────────────────────────────┐
                    │           AQS Queue                  │
                    └─────────────────────────────────────┘

    head ←→ [Node T1] ←→ [Node T2] ←→ [Node T3] ←→ tail
             (WAITING)    (WAITING)    (WAITING)

Khi T1 nhận signal:
    head ←→ [Node T2] ←→ [Node T3] ←→ tail
             (ACTIVE)     (WAITING)
```

### ReentrantLock vs synchronized trong Java 8+

| Đặc điểm                             | synchronized        | ReentrantLock            |
| ------------------------------------ | ------------------- | ------------------------ |
| **Hiệu năng (không tranh chấp)**     | ~10-20 ns           | ~15-25 ns                |
| **Hiệu năng (có tranh chấp)**        | ~1000+ ns           | ~500-1000 ns             |
| **Reentrancy**                       | Có (tự động)        | Có (bộ đếm state)        |
| **Fairness**                         | Không               | Có (tùy chọn)            |
| **tryLock**                          | Không               | Có                       |
| **lockInterruptibly**                | Không               | Có                       |
| **Nhiều Condition**                  | Không (một wait set)| Có                       |
| **Tính dễ đọc**                      | Cao hơn             | Thấp hơn (cần try/finally)|

**Kết luận:** Trong Java 8+, hiệu năng của synchronized được tối ưu rất nhiều. Chỉ dùng `ReentrantLock` cho các tính năng nâng cao (timeout, fairness, nhiều condition).

### Best Practices

1. **Luôn dùng try/finally:**
   ```java
   lock.lock();
   try {
       // code
   } finally {
       lock.unlock(); // BẮT BUỘC nếu không sẽ khóa vĩnh viễn
   }
   ```

2. **Ưu tiên synchronized** — nếu bạn không cần các tính năng nâng cao của ReentrantLock

3. **Tránh fairness** — trừ khi thật sự cần thiết (hiệu năng!)

4. **Dùng tryLock(timeout)** — để tránh deadlock

5. **Nhiều Condition** — để quản lý wait/notify chi tiết

6. **Giám sát queueLength** — hàng đợi tăng dần = vấn đề tranh chấp

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Reentrancy = một thread sở hữu khóa có thể acquire lại nó mà không deadlock (tăng/giảm bộ đếm)
- synchronized là reentrant tự động; ReentrantLock — một giải pháp thư viện thay thế xây dựng trên AQS
- AQS (AbstractQueuedSynchronizer): volatile state (bộ đếm) + hàng đợi chờ (danh sách liên kết đôi)
- Non-fair (mặc định) cho phép "barge" — chen hàng; Fair — FIFO nghiêm ngặt
- Chế độ fair chậm hơn non-fair ~50% do việc kiểm tra hàng đợi và các context switch thường xuyên
- ReentrantLock cung cấp: tryLock(), tryLock(timeout), lockInterruptibly(), nhiều Condition
- Condition — thay thế cho wait/notify với ưu điểm: bạn có thể có nhiều condition (notEmpty, notFull)

**Các câu hỏi phụ thường gặp:**
- **Tại sao non-fair nhanh hơn fair?** — Một thread mới có thể acquire một khóa rảnh mà không cần parking, tránh context switch
- **"barge" là gì?** — Khi một thread cố acquire khóa mà không vào hàng đợi; nếu may mắn — lấy được ngay lập tức
- **Tại sao cần try/finally với ReentrantLock?** — Nếu một exception xảy ra trước unlock(), khóa vẫn bị giữ mãi mãi → deadlock
- **Khi nào chọn chế độ fair?** — Khi thứ tự xử lý quan trọng và phải tránh starvation (hiếm)

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "ReentrantLock luôn nhanh hơn synchronized" — không, trong Java 8+ synchronized được tối ưu rất nhiều
- "Fairness luôn cần cho tính đúng đắn" — không, chỉ khi starvation là then chốt
- "Condition giống hệt wait/notify" — không, Condition cho phép nhiều wait set
- "AQS chỉ là một bộ đếm" — không, nó là một framework đầy đủ với một hàng đợi chờ và các thao tác CAS
