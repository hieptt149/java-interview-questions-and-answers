# Why should an immutable class be final? (Tại sao một immutable class nên là final?)

---

## Basic Level

Một immutable class phải là `final` để không ai có thể kế thừa nó và thêm các trường hoặc method mutable.

```java
public final class Point {  // final — không thể kế thừa
    private final int x;
    private final int y;
    // ...
}
```

Nếu bạn bỏ `final`, ai đó có thể viết:
```java
public class MutablePoint extends Point {
    private int z; // trường mới
    public void setZ(int z) { this.z = z; } // sự đột biến!
}
```

---

## Intermediate Level

### Bảo Vệ Chống Lại Việc Thay Thế Hành Vi

Không có `final`, một subclass có thể:
1. **Thêm trạng thái mutable** — các trường mới với setter
2. **Ghi đè getter** — trả về dữ liệu khác
3. **Ghi đè equals/hashCode** — phá vỡ hoạt động trong `HashMap`

### Kịch Bản Tấn Công
```java
public void process(ImmutablePoint point) {
    validate(point);         // kiểm tra tọa độ
    // ở đây một subclass có thể thay đổi dữ liệu
    saveToDatabase(point);   // lưu dữ liệu đã bị thay đổi
}
```

### Các Ví Dụ Từ JDK
```java
public final class String { ... }
public final class Integer { ... }
public final class BigDecimal { ... }
public final class LocalDate { ... }
```

### Nếu Bạn Cần Kế Thừa?
Dùng **Sealed classes** (Java 17+) để kiểm soát các lớp con, hoặc **composition**.

### Khi final Có Thể Là Một Vấn Đề

- **Mocking trong test**: Mockito không thể mock các final class nếu không có bytebuddy-agent
- **Các framework proxy**: một số yêu cầu kế thừa (Spring AOP qua CGLIB)
- **Giải pháp**: sealed classes hoặc Mockito inline-mock-maker

## Advanced Level

### Các Đảm Bảo Của JMM Và JIT

`final class` + `final fields` tạo ra một "lớp vỏ bất khả xâm phạm":
- **JMM**: các trường `final` đảm bảo việc công bố an toàn (safe publication) với memory barrier
- **JIT**: trình biên dịch có thể inline method và cache giá trị một cách tích cực, vì biết class sẽ không bị ghi đè

### Các Vấn Đề Nếu Không Có final

1. **Hỏng HashMap** — một subclass có thể ghi đè `hashCode()`, trả về các giá trị khác
2. **Lỗ hổng bảo mật** — tấn công TOCTOU thông qua việc thay thế getter
3. **Mất tính thread-safe** — subclass truy cập các trường không phải `final` mà không đồng bộ hóa

### Tóm Tắt Cho Advanced
- `final` class ngăn chặn việc thay đổi logic thông qua ghi đè method
- Không có `final`, bạn không thể đảm bảo tính thread-safe hoặc sự ổn định của hash code
- `final class` — một tín hiệu cho các lập trình viên khác và trình biên dịch về một hợp đồng không thay đổi
- Dùng các class `sealed` để kế thừa có kiểm soát (Java 17+)

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- `final` cấm kế thừa — subclass không thể thêm tính mutable
- Không có `final`, một subclass có thể: thêm các trường mutable, ghi đè getter, phá vỡ equals/hashCode
- Hỏng HashMap — subclass ghi đè `hashCode()`, object bị thất lạc
- Lỗ hổng bảo mật — tấn công TOCTOU thông qua việc thay thế getter
- JMM: `final class + final fields` = lớp vỏ bất khả xâm phạm với việc công bố an toàn
- Khi final gây trở ngại: mocking trong test, các framework proxy (CGLIB); giải pháp: sealed classes hoặc inline-mock-maker

**Các câu hỏi phụ thường gặp:**
- *Điều gì xảy ra nếu không có final?* — Subclass thêm các trường mutable, phá vỡ hashCode và tính thread-safe
- *Mockito không thể mock các final class?* — Cần inline-mock-maker hoặc bytebuddy-agent
- *Sealed classes như một lựa chọn thay thế?* — Có, Java 17+: giới hạn phạm vi các lớp con
- *JIT có được lợi từ final không?* — Có: inline tích cực, caching, vì class sẽ không bị ghi đè

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tính bất biến hoạt động mà không cần final" — một subclass có thể phá vỡ mọi thứ
- "Final chỉ là về phong cách" — đó là một đảm bảo về bảo mật và các tối ưu hóa JIT
- "Mockito không hoạt động với final" — nó hoạt động với inline-mock-maker
- "Sealed classes = final" — sealed cho phép kế thừa từ các class cụ thể
