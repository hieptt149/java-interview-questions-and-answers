# What Thread Pool Is Used by Default for Async Methods? (Thread pool nào được dùng theo mặc định cho các phương thức bất đồng bộ)

## 🟢 Junior Level

Theo mặc định, tất cả các phương thức bất đồng bộ của `CompletableFuture` (không có tham số `Executor`) dùng **`ForkJoinPool.commonPool()`**.

```java
// Dùng ForkJoinPool.commonPool()
CompletableFuture<String> cf = CompletableFuture.supplyAsync(() -> {
    return "Hello";
});

// Cũng dùng commonPool
cf.thenApplyAsync(s -> s.toUpperCase());
```

**Đặc điểm của commonPool:**
- **Parallelism**: `Runtime.getRuntime().availableProcessors() - 1`
- **Thuật toán**: Work-Stealing (các worker "đánh cắp" tác vụ của nhau)
- **Loại thread**: Daemon thread (không ngăn JVM shutdown)

## 🟡 Middle Level

### Vấn Đề "Nhà Bếp Chung"

`commonPool` được dùng **bởi toàn bộ JVM**:
- Parallel Stream
- `CompletableFuture`
- Một số thư viện (Selenium, cơ chế nội bộ của Spring)

Tất cả chúng đều cạnh tranh cùng các thread. Nếu một phần của ứng dụng chạy một stream nặng, các phản hồi bất đồng bộ ở module khác sẽ chậm lại.

### Chặn (Starvation)

`commonPool` được thiết kế cho các tác vụ **CPU-bound**.

```java
// ❌ I/O chặn trong commonPool
CompletableFuture.supplyAsync(() -> {
    return httpClient.get(url);  // chặn một thread từ pool chung!
});
```

Khi tất cả các thread (thường là 7 trên CPU 8 lõi) đều bận chờ mạng, ứng dụng sẽ ngừng thực thi bất kỳ tác vụ bất đồng bộ nào — **Thread Starvation** (đói tài nguyên thread).

### Hệ Thống Ít Lõi

Với 1 lõi CPU, ForkJoinPool.commonPool() vẫn được dùng,
nhưng với parallelism = 1. CompletableFuture KHÔNG chuyển sang thread-per-task.
Kích thước pool có thể thay đổi qua:
```java
System.setProperty("java.util.concurrent.ForkJoinPool.common.parallelism", "N");
```

### Khi Nào Nên Dùng Executor Riêng?

1. **Thao tác I/O**: Luôn luôn. Pool nên lớn hơn (50-100 thread) hoặc dùng Virtual Threads.
2. **Cách ly**: Đảm bảo rằng một lỗi trong module "Notifications" không làm sập module "Payments".
3. **Giám sát**: `commonPool` khó giám sát. Một `ThreadPoolExecutor` tùy chỉnh cho phép bạn thấy kích thước hàng đợi và số lượng tác vụ bị từ chối.

### Chẩn Đoán

```bash
# Thay đổi kích thước pool qua JVM flag
-Djava.util.concurrent.ForkJoinPool.common.parallelism=N

# Kiểm tra kích thước theo chương trình
ForkJoinPool.getCommonPoolParallelism()

# Các thread được đặt tên ForkJoinPool.commonPool-worker-X
# Nếu bạn thấy WAITING trên network socket — vấn đề kiến trúc
jstack <pid>
```

## 🔴 Senior Level

### Triển Khai Nội Bộ

**Thuật toán Work-Stealing:**
- **LIFO cho tác vụ cục bộ**: Các worker ForkJoin xử lý tác vụ của chính mình theo thứ tự LIFO. Điều này giữ dữ liệu "nóng" trong CPU cache (L1/L2).
- **FIFO cho việc đánh cắp**: Các thread "đánh cắp" lấy tác vụ từ đuôi của hàng đợi, giảm thiểu contention.

### Đánh Đổi Kiến Trúc

| Cách tiếp cận                       | Ưu điểm                    | Nhược điểm                            |
| ------------------------------ | ----------------------- | -------------------------------- |
| **commonPool**                 | Không cần thiết lập         | Tài nguyên chung, khó giám sát|
| **FixedThreadPool**            | Kích thước dự đoán được        | Không có work-stealing                |
| **Virtual Threads (Java 21+)** | Lý tưởng cho I/O           | Chỉ Java 21+                   |

### Chiến Lược Production

**Tách các pool theo loại workload:**

```java
// I/O-Bound (HTTP, DB, File)
Executor ioExecutor = new ThreadPoolExecutor(
    10, 100, 60L, TimeUnit.SECONDS,
    new LinkedBlockingQueue<>(1000),
    new ThreadFactoryBuilder().setNameFormat("io-pool-%d").build(),
    new ThreadPoolExecutor.CallerRunsPolicy()  // Backpressure
);

// CPU-Bound (Tính toán, Mapping)
Executor cpuExecutor = Executors.newFixedThreadPool(
    Runtime.getRuntime().availableProcessors()
);

// Virtual Threads (Java 21+) — cho I/O
Executor vtExecutor = Executors.newVirtualThreadPerTaskExecutor();
```

**Cách ly tại mỗi giai đoạn của chuỗi:**
```java
// ❌ Chỉ giai đoạn đầu tiên ở pool riêng, phần còn lại — trong commonPool
CF.supplyAsync(task, myExecutor)
  .thenApplyAsync(transform);  // commonPool!

// ✅ Duy trì sự cách ly
CF.supplyAsync(task, myExecutor)
  .thenApplyAsync(transform, myExecutor);
```

### Quản Lý Vòng Đời

```java
@PreDestroy
public void shutdown() {
    ((ExecutorService) ioExecutor).shutdown();
    ((ExecutorService) cpuExecutor).shutdown();
}
```

Không có `shutdown()` — các "thread zombie" ngăn cản việc kết thúc tiến trình đúng cách.

### Best Practices

```java
// ✅ Luôn dùng Executor riêng cho production
CompletableFuture.supplyAsync(task, ioExecutor);

// ✅ CallerRunsPolicy cho backpressure
new ThreadPoolExecutor.CallerRunsPolicy();

// ✅ Đặt tên thread để chẩn đoán
new ThreadFactoryBuilder().setNameFormat("pool-%d").build();

// ❌ commonPool cho I/O
// ❌ Chặn trong commonPool
// ❌ Không có shutdown() khi thoát
```

### Tóm Tắt Cho Senior
- Pool mặc định — **ForkJoinPool.commonPool()**.
- Nó chỉ dành cho **tính toán nhanh**.
- Chặn trong commonPool làm giảm throughput cho tất cả các tác vụ dùng pool đó.
Đây là một trong những nguyên nhân phổ biến nhất gây suy giảm hiệu năng.
- Trong các dự án nghiêm túc, luôn inject `Executors` riêng của bạn qua Spring `@Bean`.

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- Theo mặc định — ForkJoinPool.commonPool() (availableProcessors - 1)
- Thuật toán Work-Stealing: LIFO cho cục bộ, FIFO cho đánh cắp
- commonPool chỉ dành cho tác vụ CPU-bound, đối với I/O — Executor riêng
- Tất cả tác vụ của JVM (Parallel Stream, các CF khác) chia sẻ một commonPool
- Kích thước pool: -Djava.util.concurrent.ForkJoinPool.common.parallelism=N

**Các câu hỏi phụ thường gặp:**
- **Tại sao commonPool xấu cho I/O?** — Ít thread (N-1), chặn → thread pool starvation
- **Work-Stealing hoạt động như thế nào?** — Worker xử lý tác vụ của chính mình (LIFO), "đánh cắp" từ đuôi hàng đợi của người khác (FIFO)
- **Cách chẩn đoán starvation?** — jstack: ForkJoinPool-worker-X ở trạng thái WAITING trên network socket
- **Còn 1 lõi CPU thì sao?** — commonPool với parallelism = 1, KHÔNG chuyển sang thread-per-task

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "commonPool ổn cho HTTP request" — I/O chặn → thread starvation
- "commonPool mở rộng vô hạn" — bị giới hạn bởi availableProcessors - 1
- "Daemon thread ngăn JVM shutdown" — daemon thread KHÔNG ngăn, nhưng không có shutdown() — thread zombie
