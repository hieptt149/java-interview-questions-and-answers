# How to prevent deadlock? (Làm sao phòng ngừa deadlock?)

Deadlock có thể được phòng ngừa bằng cách vi phạm ít nhất một trong 4 điều kiện Coffman. Ý tưởng then chốt: **deadlock cần cả 4 điều kiện đồng thời tồn tại**, nên vi phạm bất kỳ điều kiện nào trong số đó cũng làm cho deadlock không thể xảy ra.

Khác với việc **phát hiện** deadlock (file 19), thứ chỉ chẩn đoán vấn đề, file này mô tả các **chiến lược phòng ngừa** — làm sao thiết kế một hệ thống để deadlock không bao giờ xảy ra.

## Junior Level

### Hiểu biết cơ bản

Deadlock có thể được phòng ngừa bằng cách vi phạm ít nhất một trong 4 điều kiện Coffman. Phương pháp hiệu quả nhất — **Lock Ordering**.

### Phương pháp 1: Lock Ordering

Luôn acquire các resource theo một thứ tự được xác định nghiêm ngặt:

```java
public class BankAccount {
    private final int id; // ID duy nhất để xác định thứ tự
    private double balance;

    public BankAccount(int id, double balance) {
        this.id = id;
        this.balance = balance;
    }

    // Chuyển tiền an toàn — luôn theo thứ tự ID
    public static void transfer(BankAccount from, BankAccount to, int amount) {
        // Xác định thứ tự theo ID
        BankAccount first = from.id < to.id ? from : to;
        BankAccount second = from.id < to.id ? to : from;

        synchronized(first) {
            synchronized(second) {
                from.withdraw(amount);
                to.deposit(amount);
            }
        }
    }

    private void withdraw(int amount) { balance -= amount; }
    private void deposit(int amount) { balance += amount; }
}
```

### Phương pháp 2: tryLock với Timeout

Dùng `ReentrantLock.tryLock()` thay vì `synchronized`:

```java
ReentrantLock lock1 = new ReentrantLock();
ReentrantLock lock2 = new ReentrantLock();

public void safeOperation() throws InterruptedException {
    while (true) {
        if (lock1.tryLock(100, TimeUnit.MILLISECONDS)) {
            try {
                if (lock2.tryLock(100, TimeUnit.MILLISECONDS)) {
                    try {
                        // Cả hai đã acquire — làm việc
                        return;
                    } finally {
                        lock2.unlock();
                    }
                }
            } finally {
                lock1.unlock(); // Luôn giải phóng cái đầu!
            }
        }
        // Thất bại — dừng và thử lại
        Thread.sleep(50);
    }
}
```

### Phương pháp 3: Một Global Lock

```java
// Đơn giản, nhưng chậm
private final Object globalLock = new Object();

public void operation1() {
    synchronized(globalLock) {
        // Mọi thao tác đi qua một khóa — deadlock không thể xảy ra
    }
}

public void operation2() {
    synchronized(globalLock) {
        // Không có khóa lồng nhau → không có deadlock
    }
}
```

Tại sao nó chậm: mọi thread thực hiện các thao tác **tuần tự**, ngay cả khi chúng không xung đột (ví dụ, operation1 đọc dữ liệu trong khi operation2 ghi vào một file khác). Điều này giảm đa luồng xuống thành đơn luồng. Chỉ dùng khi các thao tác thực sự phải tuần tự nghiêm ngặt.

## Middle Level

### Lock Ordering với hashCode

Khi các resource không có một thứ tự tự nhiên:

```java
public void safeOperation(Object resource1, Object resource2) {
    // Thứ tự theo identity hash code
    int h1 = System.identityHashCode(resource1);
    int h2 = System.identityHashCode(resource2);

    if (h1 < h2) {
        synchronized(resource1) {
            synchronized(resource2) { /* ... */ }
        }
    } else if (h1 > h2) {
        synchronized(resource2) {
            synchronized(resource1) { /* ... */ }
        }
    } else {
        // Va chạm HashCode — dùng một global tie-breaker
        synchronized(globalLock) {
            synchronized(resource1) {
                synchronized(resource2) { /* ... */ }
            }
        }
    }
}
```

### Try-Lock với Rollback

```java
ReentrantLock lockA = new ReentrantLock();
ReentrantLock lockB = new ReentrantLock();

public boolean tryTransfer(Account from, Account to, int amount) {
    if (!lockA.tryLock()) return false;
    try {
        if (!lockB.tryLock()) return false; // Thất bại — giải phóng A
        try {
            from.withdraw(amount);
            to.deposit(amount);
            return true;
        } finally {
            lockB.unlock();
        }
    } finally {
        lockA.unlock();
    }
}
```

Cái này vi phạm **Hold and Wait** — nếu resource thứ hai không acquire được, ta giải phóng cái đầu.

### Các cấu trúc dữ liệu Lock-Free

Cách tốt nhất để phòng ngừa deadlock — đừng dùng khóa:

```java
// Thay vì synchronized HashMap:
Map<String, String> map = Collections.synchronizedMap(new HashMap<>());

// Dùng ConcurrentHashMap — lock-free:
ConcurrentHashMap<String, String> map = new ConcurrentHashMap<>();

// Thay vì AtomicInteger + synchronized:
AtomicInteger counter = new AtomicInteger(0);
counter.incrementAndGet(); // CAS — không khóa → không deadlock
```

### So sánh các cách tiếp cận

| Phương pháp      | Ưu điểm               | Nhược điểm              | Khi nào dùng             |
| ---------------- | --------------------- | ----------------------- | ------------------------ |
| **Lock Ordering**| Đáng tin cậy, đơn giản| Cần thứ tự resource     | Hầu hết các trường hợp   |
| **Try-Lock**     | Linh hoạt, có timeout | Cần vòng lặp retry      | Khi thứ tự không rõ      |
| **Một khóa**     | Đơn giản              | Song song thấp          | Các hệ thống đơn giản    |
| **Lock-free**    | Không deadlock hoàn toàn | Khó hiện thực hơn     | Tải cao                  |

## Senior Level

### Bên trong: Vi phạm các điều kiện Coffman

| Phương pháp           | Điều kiện nào bị vi phạm    | Cơ chế                     |
| --------------------- | --------------------------- | -------------------------- |
| Lock Ordering         | Circular Wait               | Không thể tạo chu trình    |
| Try-Lock + giải phóng | Hold and Wait               | Không giữ trong lúc chờ    |
| lockInterruptibly     | No Preemption               | Có thể bị interrupt        |
| Lock-free/Atomic      | Mutual Exclusion            | Không có quyền sở hữu độc quyền |
| Một global lock       | Circular Wait               | Không có sự lồng nhau      |

### Các resource riêng cho từng thread (Sharding)

Thiết kế hệ thống để các thread không chia sẻ resource:

```java
// Mỗi thread làm việc với segment riêng của nó
public class ShardedCounter {
    private final Map<Integer, AtomicInteger> shards = new ConcurrentHashMap<>();

    public void increment(int userId) {
        int shard = userId % 16; // 16 shard
        shards.computeIfAbsent(shard, k -> new AtomicInteger(0))
              .incrementAndGet();
    }
}
// Các thread với userId khác nhau không bao giờ cạnh tranh → không deadlock
```

### Kiểm chứng: Phân tích tĩnh

#### ThreadSanitizer (TSan)

```bash
# Cho Java qua LLVM
java -agentpath:/path/to/libtsan.so MyApp
```

Tìm các race và deadlock tiềm tàng ngay cả ở giai đoạn testing.

#### SonarQube

Phát hiện các synchronized block lồng nhau theo các thứ tự khác nhau:

```java
// SonarQube sẽ cảnh báo:
public void method1() {
    synchronized(lockA) {
        synchronized(lockB) { // Deadlock tiềm tàng
        }
    }
}

public void method2() {
    synchronized(lockB) {
        synchronized(lockA) { // Thứ tự ngược!
        }
    }
}
```

### Các trường hợp biên (Edge Case)

#### Deadlock với các hệ thống bên ngoài

```
Thread Java: giữ lock → chờ phản hồi từ DB
DB: giữ table lock → chờ dữ liệu từ Java (qua callback)

→ Deadlock giữa Java và DB!
```

Giải pháp: đừng giữ các khóa Java trong lúc thực hiện các thao tác I/O.

```java
// XẤU:
synchronized(lock) {
    database.update(); // Giữ lock trong lúc I/O
}

// TỐT:
Object result = database.update(); // I/O không có lock
synchronized(lock) {
    // Cập nhật trạng thái
}
```

#### Interruption và synchronized

```java
// synchronized KHÔNG thể bị interrupt:
synchronized(lock) {
    // Nếu deadlock — thread sẽ treo cho tới khi restart JVM
}

// ReentrantLock CÓ thể bị interrupt:
lock.lockInterruptibly();
try {
    // Nếu deadlock — có thể gọi thread.interrupt()
} finally {
    lock.unlock();
}
```

### Chẩn đoán và giám sát

#### ThreadMXBean

```java
public class DeadlockMonitor {
    public static void checkAndAlert() {
        ThreadMXBean mxBean = ManagementFactory.getThreadMXBean();
        long[] deadlocked = mxBean.findDeadlockedThreads();

        if (deadlocked != null) {
            for (long threadId : deadlocked) {
                ThreadInfo info = mxBean.getThreadInfo(threadId, true, true);
                log.error("DEADLOCK: Thread {} blocked on {}",
                    info.getThreadName(),
                    info.getLockName());
            }
            // Gửi alert, restart, v.v.
        }
    }
}
```

**Cảnh báo:** Đây là một thao tác đắt — đừng chạy nó quá thường xuyên (mỗi 30+ giây).

#### Metric LockWaitTime

```java
// Giám sát thời gian acquire khóa
long start = System.nanoTime();
lock.lock();
long waitTime = System.nanoTime() - start;

if (waitTime > 1_000_000) { // > 1ms
    log.warn("High lock wait time: {} ms", waitTime / 1_000_000);
}
// Tăng đột ngột = điềm báo của deadlock hoặc tranh chấp
```

### Best Practices

1. **Lock Ordering** — phương pháp đáng tin cậy nhất, luôn dùng cho các khóa lồng nhau
2. **tryLock(timeout)** — để tránh chờ vĩnh viễn
3. **Tránh các khóa trong lúc I/O** — đừng giữ các khóa trong lúc request DB/API
4. **Các cấu trúc lock-free** — ConcurrentHashMap, Atomic* thay vì synchronized
5. **ReentrantLock thay vì synchronized** — để có tính interruptible
6. **Sharding** — các thread với dữ liệu độc lập = không deadlock
7. **Giám sát** LockWaitTime — tăng dần = điềm báo của các vấn đề
8. **Phân tích tĩnh** — SonarQube sẽ tìm các khóa lồng nhau ở giai đoạn phát triển

## Khi nào KHÔNG cần dùng các chiến lược phòng ngừa

- **Một khóa, một thread** — nếu bạn chỉ có một khóa và một thread, deadlock không thể xảy ra theo định nghĩa, không cần làm phức tạp
- **Các thao tác chỉ đọc** — nếu mọi thread chỉ đọc dữ liệu (ReadLock hoặc immutable), Mutual Exclusion không áp dụng, deadlock không thể xảy ra
- **Prototype/MVP trong 1-2 ngày** — một global lock là ổn, refactor khi tải thực xuất hiện
- **Mô hình actor (Akka)** — nếu bạn đã dùng actor, việc phòng ngừa deadlock ở mức khóa không áp dụng — các actor không chia sẻ state

## Lock Ordering vs Try-Lock: Chọn gì?

| Tình huống                              | Lựa chọn           | Tại sao                                                             |
| -------------------------------------- | ------------------ | ------------------------------------------------------------------- |
| Tập resource cố định (DB, file)        | Lock Ordering      | Thứ tự đã biết trước, đơn giản và đáng tin cậy                      |
| Resource động (tạo tại chỗ)            | Try-Lock           | Thứ tự không rõ, tryLock linh hoạt hơn                             |
| Tải cao + resource đã biết             | Lock Ordering      | Zero overhead khi acquire                                          |
| Cần tránh chờ vĩnh viễn                | Try-Lock + timeout | Lock Ordering có thể chờ mãi mãi nếu có bug trong thứ tự           |
| Code legacy với synchronized lồng nhau | Try-Lock           | Viết lại thành ordering khó hơn thay synchronized bằng tryLock     |

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Deadlock được phòng ngừa bằng cách vi phạm ít nhất một trong 4 điều kiện Coffman
- Lock Ordering — vi phạm Circular Wait — phương pháp đáng tin cậy nhất và miễn phí
- TryLock + giải phóng khi thất bại — vi phạm Hold and Wait
- ReentrantLock thay vì synchronized — vi phạm No Preemption (hỗ trợ interrupt)
- Lock-free/Atomic — vi phạm Mutual Exclusion
- Đừng giữ các khóa trong lúc thực hiện các thao tác I/O — điều này dẫn tới deadlock với các hệ thống bên ngoài (DB, API)

**Các câu hỏi phụ thường gặp:**
- **Chọn gì: Lock Ordering hay Try-Lock?** — Lock Ordering cho một tập resource cố định (zero overhead), Try-Lock cho các resource động hoặc code legacy
- **SonarQube giúp phòng ngừa deadlock như thế nào?** — Tìm các synchronized block lồng nhau theo các thứ tự khác nhau ở giai đoạn phát triển
- **Sharding như một phương pháp phòng ngừa là gì?** — Các thread làm việc với các segment dữ liệu độc lập, không cạnh tranh = không deadlock

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Một global lock là một giải pháp tốt cho production" — giết chết tính song song, chỉ dành cho prototype
- "TryLock đảm bảo không deadlock" — TryLock ngăn chờ vĩnh viễn, nhưng pattern deadlock vẫn có thể xảy ra với logic retry không đúng
- "Phòng ngừa deadlock không cần cho các ứng dụng web" — các ứng dụng web cũng dùng DB, cache, các API bên ngoài
- "ReentrantLock giải quyết mọi vấn đề deadlock" — nó chỉ cung cấp nhiều công cụ hơn, deadlock vẫn có thể xảy ra khi dùng sai
