# What is Accept header? (Accept header là gì?)

## Junior Level

**Accept** là một header HTTP cho server biết client muốn nhận response **ở định dạng nào**.

### Ví dụ:

```
Accept: application/json        — tôi muốn JSON
Accept: application/xml         — tôi muốn XML
Accept: text/html               — tôi muốn HTML
Accept: */*                     — định dạng nào cũng được
```

### Khác biệt so với Content-Type:
- **Content-Type** — định dạng dữ liệu tôi đang **gửi đi**
- **Accept** — định dạng dữ liệu tôi **muốn nhận về**

### Ví dụ request:
```
GET /users/1
Accept: application/json

// Response của server:
{"id": 1, "name": "Ivan", "age": 30}
```

### Điều gì xảy ra nếu server không hỗ trợ định dạng được yêu cầu?
Server trả về **406 Not Acceptable** — "Tôi không thể phản hồi ở định dạng bạn yêu cầu".

## Middle Level

### Content Negotiation trong Spring

Thuật toán content negotiation (thương lượng nội dung):
1. Client gửi `Accept: application/json`
2. Spring tìm các phương thức controller có `produces = "application/json"`
3. Kiểm tra xem có một **`HttpMessageConverter`** nào ghi được kiểu này không
4. Nếu không khớp — trả về **406 Not Acceptable**

### Hệ số chất lượng (q-value)

Header `Accept` hỗ trợ các trọng số ưu tiên:
```
Accept: text/html,application/xhtml+xml,application/xml;q=0.9,image/webp,*/*;q=0.8
```
- `text/html` — ưu tiên `1.0` (mặc định)
- `application/xml` — ưu tiên `0.9`
- `*/*` (mọi thứ còn lại) — `0.8`
  - Trong ví dụ trên, `*/*` có q=0.8 — đây là giá trị của một trình duyệt cụ thể. Client có thể đặt bất kỳ q nào từ 0.0 đến 1.0.

**Tại sao?** Điều này cho phép **Graceful Degradation (suy giảm êm ái)** — nếu server không thể phục vụ định dạng ưa thích, nó sẽ phục vụ một định dạng thay thế. Một ứng dụng di động yêu cầu `application/json;q=1.0` và `text/plain;q=0.5`.

### Hiệu suất và Caching

#### Header Vary
Nếu một endpoint trả về các định dạng khác nhau (JSON/XML) trên cùng một URL tùy theo `Accept`, RFC 7231 yêu cầu trả về `Vary: Accept` nếu nội dung phụ thuộc vào header này và response có thể được cache. Không có Vary, CDN/proxy có thể phục vụ sai định dạng.

**Tại sao?** Để cache (Nginx/CDN) không phục vụ một response JSON cho một người dùng đã yêu cầu XML.

### Các trường hợp biên (Edge Case)

- **Accept-Charset và Accept-Encoding:** Đừng nhầm lẫn chúng. `Accept` — về định dạng dữ liệu, `Accept-Charset` — về encoding, `Accept-Encoding` — về nén (gzip/brotli)
- **Wildcard của trình duyệt:** Trình duyệt thường gửi `Accept: */*`. Spring sẽ chọn converter phù hợp đầu tiên (thường là JSON)

### Chẩn đoán

- **Phân tích 406 Not Acceptable:** Tăng đột biến 406 = client yêu cầu một định dạng bạn chưa hiện thực (hoặc bạn vô tình bỏ một converter)
- **ContentNegotiationManager:** Có thể cấu hình ưu tiên: phần mở rộng đường dẫn (`.json`) → query parameter (`?format=json`) → header `Accept`. Ở cấp Senior, khuyến nghị chỉ dựa vào **header**

## Senior Level

### Khi nào không cần header Accept

1. **API với một định dạng cố định duy nhất** (chỉ JSON)
2. **Microservice nội bộ** — định dạng được cố định bởi hợp đồng
3. **Khi Content Negotiation thêm overhead mà không có lợi ích**

### Content Negotiation — đào sâu

Content Negotiation là quá trình server xác định định dạng response tốt nhất cho client.

#### Spring ContentNegotiationManager
Bạn có thể cấu hình thứ tự ưu tiên khi chọn:
1. Phần mở rộng đường dẫn (`.json`)
2. Query parameter (`?format=json`)
3. Header `Accept`

**Khuyến nghị:** Ở cấp Senior, chỉ dựa vào **header**. Phần mở rộng đường dẫn và query parameter tạo ra các vấn đề về caching và ngữ nghĩa URL.

### Vendor MIME Types cho versioning

Dùng `application/vnd.mycompany.v1+json` là một cách tiếp cận versioning rất tốt:
- Cho phép cache các phiên bản API khác nhau dưới một URI duy nhất
- Nếu cache tôn trọng header `Accept`, các phiên bản khác nhau sẽ không bị lẫn lộn

### Hiệu suất

- **Vary: Accept** được khuyến nghị khi hỗ trợ nhiều định dạng — không có nó, CDN có thể phục vụ sai định dạng từ cache
- **Vendor MIME Types** cho phép versioning từng thực thể một cách độc lập
- **Negative Caching (cache phủ định):** CDN có thể cache các response 406, bảo vệ backend khỏi các request lặp lại cho những định dạng không được hỗ trợ

### Chẩn đoán và Giám sát

- **Phân tích 406:** Tăng đột biến 406 nghĩa là client đã cập nhật và đang yêu cầu một định dạng bạn chưa hiện thực
- **Thứ tự Converter:** Thứ tự đăng ký converter có ý nghĩa — Spring chọn khớp đầu tiên
- **Hành vi của trình duyệt:** Trình duyệt thường gửi `Accept: */*`, điều này có thể dẫn đến việc chọn định dạng bất ngờ. Hãy test với các header User-Agent thật

## Interview Cheat Sheet

**Cần phải biết:**
- Accept cho server biết định dạng client muốn nhận: `application/json`, `application/xml`
- Content-Type = cái tôi đang gửi, Accept = cái tôi muốn nhận
- q-value (hệ số chất lượng): `Accept: application/json;q=1.0,text/plain;q=0.5` — ưu tiên từ 0.0 đến 1.0
- 406 Not Acceptable — server không hỗ trợ định dạng được yêu cầu
- Vary: Accept là bắt buộc khi hỗ trợ nhiều định dạng — không có nó, CDN phục vụ sai định dạng từ cache
- Vendor MIME Types (`application/vnd.mycompany.v1+json`) — một cách tiếp cận versioning API
- Spring ContentNegotiationManager: ưu tiên — phần mở rộng đường dẫn → query parameter → header Accept

**Các câu hỏi phụ thường gặp:**
- Vary: Accept làm gì? — Cho cache biết response phụ thuộc vào header Accept; không có Vary, CDN phục vụ JSON thay vì XML
- Tại sao cần q-value? — Graceful Degradation: nếu server không thể phục vụ định dạng ưa thích, nó phục vụ một định dạng thay thế
- Tại sao không nên dùng phần mở rộng (.json) cho Content Negotiation? — Chúng tạo ra các vấn đề về caching và ngữ nghĩa URL
- Làm sao versioning qua Accept? — Vendor MIME Types: `application/vnd.myapi.v2+json`, cache tôn trọng Accept

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Accept và Content-Type giống nhau" — Accept = response mong đợi, Content-Type = định dạng request
- "Trình duyệt luôn gửi một Accept cụ thể" — trình duyệt thường gửi `Accept: */*`
- "406 là một lỗi server" — 406 = client yêu cầu một định dạng server không hỗ trợ
- "Không cần Vary: Accept" — không có Vary, CDN có thể phục vụ một response JSON cho một client đã yêu cầu XML
