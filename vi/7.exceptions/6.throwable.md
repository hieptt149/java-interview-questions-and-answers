# What is Throwable? (Throwable là gì?)

## Junior Level

### Định nghĩa

**`java.lang.Throwable`** là lớp cơ sở cho tất cả các object có thể được ném (`throw`) và bắt (`catch`). Nếu không kế thừa từ `Throwable`, một object không thể được dùng làm exception.

Throwable là một lớp (class), không phải một interface, vì nó lưu trạng thái: stack trace, message, cause, danh sách suppressed. Một interface không thể lưu dữ liệu.

### Cây phân cấp

```
Throwable
  ├── Error - lỗi JVM nghiêm trọng
  │     ├── OutOfMemoryError
  │     └── StackOverflowError
  └── Exception - lỗi ứng dụng
        ├── RuntimeException (unchecked)
        └── Checked Exceptions
```

### Các phương thức chính

```java
Throwable t = new Exception("Something went wrong");

t.getMessage();       // "Something went wrong"
t.printStackTrace();  // In call stack ra System.err
t.getCause();         // Trả về cause (nếu có)
t.getStackTrace();    // Mảng StackTraceElement[]
```

### Khi nào dùng

`Throwable` hiếm khi được dùng trực tiếp. Thường bạn làm việc với các lớp con của nó:
- `Exception` và các lớp con - cho các lỗi ứng dụng
- `Error` và các lớp con - cho các lỗi JVM nghiêm trọng (nhưng chúng không bị bắt)

## Middle Level

### Khi nào KHÔNG nên dùng catch(Throwable)

Đừng bao giờ dùng `catch (Throwable t)` trong logic nghiệp vụ - nó sẽ bắt OutOfMemoryError và để JVM ở trạng thái không ổn định. Ngoại lệ: handler toàn cục ở biên của ứng dụng.

### Cấu trúc bên trong

`Throwable` chứa một trường ẩn `backtrace` (kiểu `Object`), được điền bởi phương thức native `fillInStackTrace()`. Trường này giữ call stack native trong bộ nhớ JVM.

Khi `getStackTrace()` được gọi, cấu trúc native được chuyển đổi thành mảng `StackTraceElement[]` - đây là một tối ưu hóa lười (lazy).

### Constructor với điều khiển stack trace

```java
public Throwable(String message,
                 Throwable cause,
                 boolean enableSuppression,
                 boolean writableStackTrace)
```

Tham số:
- `enableSuppression` - có cho phép các suppressed exception hay không
  // Suppressed exception - xem file 'What are suppressed exceptions.md'.
  // Tóm tắt: nếu một exception được ném trong try và một cái khác trong close(),
  // cái thứ hai không bị mất mà được thêm vào danh sách suppressed của cái đầu tiên.
- `writableStackTrace` - có điền stack trace hay không

### Suppressed Exception

Một cơ chế để bảo toàn các exception "bị mất":

```java
try (FileInputStream fis = new FileInputStream("file.txt")) {
    fis.read(); // IOException #1
} // close() ném IOException #2
// #1 - chính, #2 - suppressed
```

Khi ghi log qua Logback/Log4j2, các suppressed exception được in ra với tiền tố `Suppressed:`.

### Serialization

Khi truyền qua mạng (RMI, microservice), `backtrace` native bị mất. JVM chuyển đổi nó thành các object Java, làm tăng kích thước dữ liệu.

## Senior Level

### Tắt stack trace để tăng hiệu suất

Với các exception dùng làm tín hiệu (validation), stack trace là không cần thiết:

```java
public class FastException extends RuntimeException {
    public FastException(String message) {
        super(message, null, true, false); // writableStackTrace = false
    }
}
```

Tăng tốc việc tạo lên **hàng chục lần** - việc duyệt stack native không được thực thi.

### Immutable Exception

Trong các hệ thống tải cao, các instance tĩnh được tạo ra:

```java
public static final ValidationException INVALID_EMAIL =
    new ValidationException("Invalid email", null, true, false);
```

Ưu điểm: không tạo object ở mỗi lời gọi, không có tải cho GC.
Nhược điểm: stack trace giống hệt nhau cho mọi trường hợp.

### Hệ thống phân tán

Truyền các stack trace đầy đủ là một anti-pattern:

```java
// Ở biên của service
try {
    service.process();
} catch (Throwable t) {
    // Chỉ truyền DTO, không phải toàn bộ stack
    return ErrorResponse.of(t.getClass().getSimpleName(), t.getMessage());
}
```

Tiết kiệm hàng megabyte lưu lượng trong các đợt lỗi hàng loạt.

### printStackTrace() - không bao giờ dùng trong production

`printStackTrace()` ghi ra `System.err`, thứ mà:
- Được đồng bộ hóa (synchronized) - chặn thread
- Không tới được các file log nếu không chuyển hướng
- Trong Kubernetes, bị tách thành các dòng riêng biệt

Hãy dùng logger: `log.error("Msg", throwable)`.

### Chẩn đoán

- `toString()` - chỉ tên lớp và message
- `printStackTrace()` - toàn bộ cây (chậm)
- `getStackTrace()` - mảng các phần tử (để phân tích bằng chương trình)
- Trong các hệ thống phân tán, dùng `Trace ID / Span ID` để liên kết log giữa các service

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- `Throwable` - lớp cơ sở cho tất cả các object có thể `throw` và `catch`
- Các lớp con: `Error` (JVM nghiêm trọng) và `Exception` (lỗi ứng dụng)
- Lưu trạng thái: stack trace, message, cause, danh sách suppressed
- Các phương thức chính: `getMessage()`, `getCause()`, `getStackTrace()`, `printStackTrace()`
- Chứa trường ẩn `backtrace`, được điền bởi native `fillInStackTrace()`
- Constructor với `writableStackTrace = false` tắt việc duyệt stack (tăng tốc 10-50 lần)
- Suppressed exception - bảo toàn các exception từ `close()` trong try-with-resources
- `printStackTrace()` - không bao giờ dùng trong production (ghi ra `System.err`, synchronized)

**Các câu hỏi phụ thường gặp:**
- **Tại sao Throwable là một lớp, không phải interface?** - Lưu trạng thái (stack trace, cause, suppressed), interface không lưu dữ liệu
- **Khi nào KHÔNG nên dùng `catch(Throwable)`?** - Trong logic nghiệp vụ: sẽ bắt OutOfMemoryError; chỉ chấp nhận được trong một handler toàn cục
- **Suppressed exception là gì?** - Nếu cả try và close() đều ném hai exception, cái thứ hai được thêm vào danh sách suppressed của cái đầu tiên
- **Tại sao printStackTrace() tệ cho production?** - Synchronized, không tới được các file log, trong Kubernetes bị tách thành các dòng

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi dùng Throwable thay vì Exception cho mọi lỗi" - nó sẽ bắt cả Error
- "printStackTrace() là một cách ghi log bình thường" - hãy dùng logger
- "Throwable không serializable" - có, nhưng backtrace native bị mất
