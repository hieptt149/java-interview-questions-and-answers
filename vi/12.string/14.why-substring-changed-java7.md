# Why substring() Implementation Was Changed in Java 7? (Tại sao cách hiện thực substring() được thay đổi trong Java 7?)

## 🟢 Junior Level

Các nhà phát triển Java đã thay đổi `substring()` trong phiên bản 7 update 6 vì phiên bản cũ gây ra các **rò rỉ bộ nhớ ẩn**.

**Vấn đề:** Trong phiên bản cũ, `substring()` không sao chép dữ liệu, mà tham chiếu đến cùng mảng với chuỗi gốc. Nếu bạn lấy một chuỗi con nhỏ từ một văn bản khổng lồ, toàn bộ văn bản khổng lồ đó vẫn còn trong bộ nhớ.

**Ví dụ:**
```java
// Java 6 — chuỗi KHỔNG LỒ (ví dụ: nội dung file)
String huge = loadBigFile(); // 100 MB
// Lấy một phần nhỏ — chỉ 10 ký tự
String small = huge.substring(0, 10);
huge = null; // "Xóa" chuỗi lớn
// NHƯNG: 100 MB vẫn còn trong bộ nhớ vì small tham chiếu đến cùng mảng!
```

**Giải pháp:** Trong Java 7+, `substring()` luôn sao chép dữ liệu cần thiết. Một chuỗi con nhỏ chiếm chính xác lượng bộ nhớ mà nó nên chiếm.

## 🟡 Middle Level

### Điều Gì Đã Có Trước Java 7u6

Object `String` có ba trường:
- `char[] value` — mảng ký tự
- `int offset` — vị trí bắt đầu của chuỗi
- `int count` — độ dài

`substring()` tạo một `String` mới với cùng `value`, nhưng `offset` và `count` khác nhau.

### Điều Gì Đã Thay Đổi

Kể từ Java 7u6:
- Các trường `offset` và `count` bị loại bỏ khỏi `String`
- `substring()` luôn tạo một mảng **mới** và sao chép dữ liệu
- Header của object `String` trở nên nhỏ hơn (tiết kiệm bộ nhớ cho TẤT CẢ các chuỗi)

### Ứng Dụng Thực Tế
```java
// Java 7+ — an toàn
String huge = loadBigFile();     // 100 MB
String small = huge.substring(0, 10); // ~50 byte (sao chép!)
huge = null;                     // 100 MB được giải phóng cho GC
```

### Các Lỗi Điển Hình
1. **Lỗi:** Kỳ vọng hiệu năng O(1)
   **Giải pháp:** `substring()` — O(n), sao chép dữ liệu

2. **Lỗi:** Dùng `new String(substring)` như một "tối ưu hóa"
   **Giải pháp:** Điều này cần thiết trong Java 6. Trong Java hiện đại — cấp phát thừa

## 🔴 Senior Level

### Hiện Thực Nội Bộ — Động Cơ Cho Sự Thay Đổi

**JDK-7068364:** Báo cáo bug chính thức của Oracle.

Các vấn đề với cách tiếp cận mảng dùng chung:
1. **Rò rỉ bộ nhớ:** Chuỗi con giữ toàn bộ mảng cha
2. **Độ phức tạp:** Ba trường (`value`, `offset`, `count`) thay vì một
3. **Overhead GC:** Một mảng lớn được tham chiếu bởi nhiều chuỗi con — khó hơn cho các thuật toán GC

### Đánh Đổi Về Kiến Trúc (Trade-off)

**Trước Java 7u6:**
```
Object String (Java 6):
├── char[] value (tham chiếu) ──┐
├── int offset                  │  char[] dùng chung
├── int count                   │  [H][e][l][l][o][,][ ][W][o][r][l][d]...
└── int hash                    │  (có thể 10MB+)
```

**Sau Java 7u6:**
```
Object String (Java 7+):
├── char[] value ──→ [W][o][r][l][d]  (chỉ chuỗi con)
└── int hash
```

### Tại Sao Sự Đánh Đổi Về Hiệu Năng Là Hợp Lý

| Metric           | Java 6 (dùng chung) | Java 7+ (sao chép) |
| ---------------- | --------------- | ----------------- |
| Thời gian substring() | O(1)            | O(n)              |
| Bộ nhớ substring()  | 0 byte thêm   | O(n) byte              |
| Kích thước object String  | 32 byte         | 24 byte             |
| Nguy cơ rò rỉ bộ nhớ | Cao            | Không            |
| Thân thiện với GC  | Kém            | Tốt              |

**Nhận định then chốt:** Trong các ứng dụng điển hình, `substring()` được gọi cho các chuỗi có kích thước hợp lý (< 1KB). Sao chép O(n) cho các chuỗi như vậy chỉ mất vài nanosecond. Nhưng rò rỉ bộ nhớ từ mảng dùng chung — đây là OOM trong production.

### Các Trường Hợp Biên

1. **Giải pháp tạm thời legacy không còn cần thiết:**
   ```java
   // Giải pháp tạm thời của Java 6:
   String copy = new String(original.substring(0, 10));

   // Java 7+: substring() đã sao chép rồi, new String() — cấp phát thừa
   String copy = original.substring(0, 10);
   ```

2. **Compact String Java 9+:** Việc sao chép trở nên hiệu quả hơn nữa — `byte[]` thay vì `char[]` tiết kiệm 50% cho các chuỗi Latin.

3. **Các lựa chọn thay thế zero-copy:** Nếu hiệu năng không cần sao chép là quan trọng:
   - Wrapper `CharSequence` — không sao chép dữ liệu
   - `java.nio.CharBuffer` — view trên mảng
   - Các thư viện bên thứ ba: `StringView` (Guava), `Slice`

### Benchmark Hiệu Năng
| Thao tác                | Java 6      | Java 8  | Java 17       |
| ------------------------ | ----------- | ------- | ------------- |
| substring(0, 10) từ 1KB| ~1ns        | ~5ns    | ~3ns (Latin1) |
| substring(0, 100) từ 1KB| ~1ns       | ~20ns   | ~12ns         |
| substring(0, 10) từ 1MB | ~1ns       | ~500ns  | ~250ns        |
| Tác động GC                | Cao (dùng chung)| Thấp    | Thấp           |

// Các benchmark là gần đúng. Giá trị thực tế phụ thuộc vào JVM, CPU và warmup.

### Best Practices Cho Highload
- Trong Java hiện đại: `substring()` an toàn — dùng mà không lo lắng
- Cho zero-copy: các wrapper `CharSequence` hoặc `CharBuffer`
- Cho việc parse các file khổng lồ: xử lý theo stream, không load mọi thứ vào String
- Đừng dùng `new String(substring())` — dư thừa trong Java 7+

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Lý do thay đổi: rò rỉ bộ nhớ — chuỗi con giữ toàn bộ mảng cha
- JDK-7068364 — báo cáo bug chính thức của Oracle
- Trước Java 7u6: `String` có 3 trường (`value`, `offset`, `count`), sau đó — chỉ `value`
- Đánh đổi: O(1) → O(n) về thời gian, nhưng nguy cơ rò rỉ bộ nhớ → không có
- Loại bỏ `offset` và `count` giảm kích thước object String đi 8 byte
- Trong Java 9+, compact string (`byte[]`) làm cho việc sao chép hiệu quả hơn nữa

**Các câu hỏi phụ thường gặp:**
- **Tại sao đánh đổi hiệu năng?** — Trong các ứng dụng điển hình, `substring()` cho các chuỗi < 1KB — vài nanosecond. Nhưng rò rỉ bộ nhớ — OOM trong production.
- **Giải pháp tạm thời legacy `new String(substring)` có cần hiện nay không?** — Không, trong Java hiện đại `substring()` đã sao chép rồi, `new String()` — cấp phát thừa.
- **Những lựa chọn thay thế zero-copy nào tồn tại?** — Wrapper `CharSequence`, `CharBuffer`, `StringView` của Guava.
- **Kích thước object String đã thay đổi như thế nào?** — Trở nên nhỏ hơn: loại bỏ `offset` và `count` — tiết kiệm ~8 byte mỗi chuỗi.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "Thay đổi không có lý do" — có một rò rỉ bộ nhớ nghiêm trọng
- ❌ "`substring()` vẫn là O(1)" — O(n) kể từ Java 7u6
- ❌ "Cần dùng `new String(substring())` để an toàn" — dư thừa trong Java 7+
- ❌ "Thay đổi phá vỡ khả năng tương thích ngược" — hành vi của `substring()` với người dùng không thay đổi
