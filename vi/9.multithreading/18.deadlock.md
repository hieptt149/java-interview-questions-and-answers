# What is deadlock? (Deadlock là gì?)

---

## Junior Level

### Hiểu biết cơ bản

**Deadlock** (khóa chết) là tình huống hai hoặc nhiều thread chặn lẫn nhau vĩnh viễn.

**Trong code:** Thread 1 giữ `lockA` và chờ `lockB`. Thread 2 giữ `lockB` và chờ `lockA`. Không ai chịu giải phóng khóa của mình trước. Cả hai thread kẹt mãi mãi.

### Ví dụ minh họa đơn giản

Hai người trên một cây cầu hẹp từ hai phía đối diện:
- Người A: "Tôi không cho anh qua cho tới khi anh cho tôi qua"
- Người B: "Tôi không cho anh qua cho tới khi anh cho tôi qua"
- **Kết quả:** Cả hai đứng mãi mãi

### Ví dụ trong Java

```java
public class DeadlockDemo {
    private final Object lock1 = new Object();
    private final Object lock2 = new Object();

    public void methodA() {
        synchronized(lock1) {
            System.out.println("Thread 1: Acquired lock1");
            // Dừng lại để thread kia có thể acquire lock2
            try { Thread.sleep(100); } catch (InterruptedException e) {}
            synchronized(lock2) { // CHỜ lock2 — nhưng thread kia đang giữ nó!
                System.out.println("Thread 1: Acquired lock2");
            }
        }
    }

    public void methodB() {
        synchronized(lock2) {
            System.out.println("Thread 2: Acquired lock2");
            try { Thread.sleep(100); } catch (InterruptedException e) {}
            synchronized(lock1) { // CHỜ lock1 — nhưng thread kia đang giữ nó!
                System.out.println("Thread 2: Acquired lock1");
            }
        }
    }
}

// Khởi chạy:
new Thread(demo::methodA).start();
new Thread(demo::methodB).start();
// → DEADLOCK! Thread 1 chờ lock2, Thread 2 chờ lock1
```

### Deadlock vs Livelock vs Starvation

| Loại           | Hành vi                                                                | CPU     |
| -------------- | ----------------------------------------------------------------------- | ------- |
| **Deadlock**   | Các thread "ngủ" và không bao giờ thức dậy                             | 0%      |
| **Livelock**   | Các thread liên tục phản ứng với nhau nhưng không có tiến triển        | 100%    |
| **Starvation** | Thread sẵn sàng làm việc nhưng không bao giờ nhận được resource        | Tùy     |

#### Ví dụ Livelock

```java
// Hai người trong một hành lang — cả hai cố tránh sang một bên, nhưng cùng một hướng
while (otherPersonMoving) {
    stepAside(); // Liên tục phản ứng, nhưng không đi qua được
}
```

#### Ví dụ Starvation

```java
// Thread với priority thấp không bao giờ nhận được CPU
Thread lowPriority = new Thread(task);
lowPriority.setPriority(Thread.MIN_PRIORITY); // Luôn chờ
```

## Middle Level

### Wait-for-Graph

Về lý thuyết, deadlock được biểu diễn như một chu trình (cycle) trong một đồ thị:

```
Thread 1 ──chờ──→ Lock B ──được giữ bởi──→ Thread 2
  ▲                                             │
  │                                             │
  └───────────chờ──────────── Lock A ◄──────────┘
                được giữ bởi

CHU TRÌNH = DEADLOCK
```

### Các điều kiện Coffman

Deadlock CHỈ có thể xảy ra khi cả 4 điều kiện được thỏa mãn đồng thời:

| #   | Điều kiện                                                                                                                                                                                             | Mô tả                                                |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| 1   | **Mutual Exclusion**                                                                                                                                                                                 | Một resource chỉ có thể được giữ bởi một thread       |
| 2   | **Hold and Wait**                                                                                                                                                                                    | Một thread giữ một resource và chờ một resource khác  |
| 3   | **No Preemption** — nếu một thread đã acquire `synchronized(lock)`, không ai có thể ép lấy nó đi. Chỉ chính thread đó mới có thể ra khỏi `synchronized`.                                              |                                                       |
| 4   | **Circular Wait**                                                                                                                                                                                    | Có một chuỗi chờ vòng tròn                            |

### Deadlock ở Database

Deadlock cũng có thể xảy ra ở mức database:

```java
// Thread 1:
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

// Thread 2:
UPDATE accounts SET balance = balance - 50 WHERE id = 2;
UPDATE accounts SET balance = balance + 50 WHERE id = 1;
// → DEADLOCK! DB sẽ phát hiện và rollback một transaction
```

**Khác biệt:** DB có thể phát hiện deadlock và tự động rollback một transaction. Trong Java, bạn phải tự phát hiện.

### Deadlock ẩn

```java
// Deadlock qua Thread Pool Starvation
ExecutorService pool = Executors.newFixedThreadPool(1);

// Từng bước:
// Bước 1: pool.submit(A) — thread duy nhất bắt đầu thực thi tác vụ A
// Bước 2: Bên trong A, pool.submit(B).get() được gọi — tác vụ B được đưa vào hàng đợi
// Bước 3: .get() chặn thread A chờ B
// Bước 4: Thread duy nhất đang bận, B sẽ không bao giờ bắt đầu = DEADLOCK
// Cái này gọi là "thread pool starvation deadlock"
Future<String> future = pool.submit(() -> {
    // Tác vụ này chờ một tác vụ khác từ cùng pool
    return pool.submit(() -> "result").get(); // DEADLOCK!
});
// Một thread bận với tác vụ đầu tiên, tác vụ thứ hai chờ trong hàng đợi
```

### Static Initialization Deadlock

```java
// Class A
class A {
    static {
        System.out.println(B.value); // Tham chiếu B
    }
}

// Class B
class B {
    static {
        System.out.println(A.value); // Tham chiếu A
    }
}

// Hai thread nạp A và B đồng thời → deadlock trong ClassLoader
```

## Senior Level

### Khi nào KHÔNG dùng synchronized lồng nhau

1. **Không thể đảm bảo thứ tự acquire khóa** — các đường code khác nhau acquire khóa theo các thứ tự khác nhau
2. **Có các lời gọi bên ngoài bên trong khóa** (DB, HTTP, file system) — một resource bên ngoài có thể block và tạo deadlock
3. **Code không rõ** — bạn truyền một khóa cho method của người khác, thứ có thể acquire một khóa khác

**Giải pháp thay thế:** ReentrantLock.tryLock(timeout), các cấu trúc lock-free (ConcurrentHashMap, AtomicReference), hoặc một khóa dùng chung duy nhất.

### Bên trong: JVM phát hiện Deadlock

JVM có một bộ phát hiện deadlock tích hợp qua `ThreadMXBean`:

```java
ThreadMXBean mxBean = ManagementFactory.getThreadMXBean();
long[] deadlockedThreads = mxBean.findDeadlockedThreads();

if (deadlockedThreads != null) {
    for (long threadId : deadlockedThreads) {
        ThreadInfo info = mxBean.getThreadInfo(threadId, true, true);
        System.out.println("Deadlock: " + info.getThreadName());
        System.out.println("Blocked on: " + info.getLockName());
        System.out.println("Blocked by: " + info.getLockOwnerName());
    }
}
```

**Quan trọng:** Đây là một thao tác đắt — đừng chạy nó quá thường xuyên.

### Deadlock trong Highload

```
Vấn đề: Deadlock có thể làm tê liệt một hệ thống trong vài mili giây
JVM Detector: Chạy định kỳ (không tức thì)

Kết quả: các thread cần các resource bị khóa sẽ treo mãi mãi. Phần còn lại của hệ thống tiếp tục hoạt động, nhưng throughput giảm.
```

### Các trường hợp biên (Edge Case)

#### Deadlock với các hệ thống bên ngoài

```
Thread Java: giữ lockA → chờ phản hồi từ DB
Transaction DB: giữ table lock → chờ HTTP từ ứng dụng Java

→ DEADLOCK giữa Java và DB!
```

#### ReentrantLock và Interruption

```java
// synchronized không thể bị interrupt — thread sẽ treo cho tới khi restart JVM
synchronized(lock) {
    // Deadlock ở đây = chờ vĩnh viễn
}

// ReentrantLock có thể bị interrupt
lock.lockInterruptibly();
try {
    // Deadlock ở đây = có thể bị interrupt qua thread.interrupt()
} finally {
    lock.unlock();
}
```

### Chẩn đoán

#### jstack — phương pháp nhanh nhất

```bash
jstack -l <pid>
```

Đầu ra:
```

=============================
"Thread-1":
  waiting to lock monitor 0x00007f... (object 0x000000076af0c8d0),
  which is held by "Thread-2"
"Thread-2":
  waiting to lock monitor 0x00007f... (object 0x000000076af0c8e0),
  which is held by "Thread-1"
```

#### VisualVM / JConsole

Nút "Check Deadlock" — kiểm tra tức thì.

#### Kiểm tra bằng code

```java
// Kiểm tra định kỳ (mỗi 30 giây)
ScheduledExecutorService monitor = Executors.newSingleThreadScheduledExecutor();
monitor.scheduleAtFixedRate(() -> {
    ThreadMXBean mxBean = ManagementFactory.getThreadMXBean();
    long[] deadlocked = mxBean.findDeadlockedThreads();
    if (deadlocked != null) {
        log.error("DEADLOCK DETECTED! Threads: {}", Arrays.toString(deadlocked));
        // Alert, restart, v.v.
    }
}, 0, 30, TimeUnit.SECONDS);
```

### Quy tắc phòng ngừa: Lock Ordering

Phương pháp phòng ngừa hiệu quả nhất — **luôn acquire các resource theo một thứ tự được xác định nghiêm ngặt**:

```java
// Xác định thứ tự qua hashCode
void transfer(Account from, Account to, int amount) {
    Object first = System.identityHashCode(from) < System.identityHashCode(to) ? from : to;
    Object second = first == from ? to : from;

    synchronized(first) {
        synchronized(second) {
            from.withdraw(amount);
            to.deposit(amount);
        }
    }
}
```

### Best Practices

1. **Lock Ordering** — luôn acquire các resource theo một thứ tự được xác định
2. **tryLock(timeout)** — dùng ReentrantLock với một timeout
3. **Tránh các khóa lồng nhau** — nếu có thể
4. **Các cấu trúc lock-free** — ConcurrentHashMap, Atomic*
5. **Các resource riêng cho từng thread** — sharding, dữ liệu độc lập
6. **Giám sát** qua ThreadMXBean.findDeadlockedThreads()
7. **jstack** — công cụ đầu tiên khi nghi ngờ deadlock
8. **Dùng ReentrantLock** — thay vì synchronized để có tính interruptible

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Deadlock = hai thread chặn lẫn nhau mãi mãi (Thread 1 giữ lockA và chờ lockB, Thread 2 giữ lockB và chờ lockA)
- 4 điều kiện Coffman (tất cả đồng thời): Mutual Exclusion, Hold and Wait, No Preemption, Circular Wait
- Deadlock vs Livelock vs Starvation: deadlock — các thread ngủ (0% CPU), livelock — phản ứng nhưng không tiến triển (100% CPU), starvation — thread không bao giờ nhận được resource
- Lock Ordering — phòng ngừa chính: luôn acquire các resource theo một thứ tự nghiêm ngặt (ví dụ, theo hashCode)
- ReentrantLock.tryLock(timeout) — tránh chờ vĩnh viễn, khác với synchronized
- JVM phát hiện deadlock qua ThreadMXBean.findDeadlockedThreads(), nhưng đây là một thao tác đắt
- Deadlock ẩn: thread pool starvation — một tác vụ chờ .get() từ một tác vụ khác trong cùng pool (đặc biệt là single-thread pool)
- DB tự động phát hiện và rollback deadlock, Java — thì không (cần giám sát thủ công)

**Các câu hỏi phụ thường gặp:**
- **Làm sao phòng ngừa deadlock?** — Lock ordering (thứ tự acquire cố định), tryLock(timeout), các cấu trúc lock-free, một khóa dùng chung
- **synchronized khác ReentrantLock trong deadlock như thế nào?** — synchronized không thể bị interrupt (chờ vĩnh viễn), ReentrantLock.lockInterruptibly() có thể bị interrupt qua thread.interrupt()
- **Thread pool starvation deadlock là gì?** — Một tác vụ trong pool chờ .get() từ một tác vụ khác trong cùng pool; nếu pool là single-thread — deadlock được đảm bảo
- **Làm sao phát hiện deadlock trong production?** — jstack -l <pid>, ThreadMXBean.findDeadlockedThreads(), VisualVM "Check Deadlock"

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Deadlock không thể xảy ra trong code của tôi" — nó thường bị ẩn (synchronized lồng nhau, các lời gọi bên ngoài)
- "JVM tự động giải quyết deadlock" — không, JVM chỉ phát hiện, nhưng không giải quyết (khác với DB)
- "shutdownNow() sẽ sửa deadlock" — không, nó gửi interrupt(), nhưng synchronized không thể bị interrupt
- "Một khóa là đủ để phòng ngừa" — không, deadlock xảy ra với 2+ resource theo các thứ tự khác nhau
