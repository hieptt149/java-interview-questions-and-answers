# How HashMap Works in a Multi-threaded Environment? (HashMap hoạt động trong môi trường đa luồng như thế nào?)

## 🟢 Junior Level

**HashMap không thread-safe.** Nếu nhiều thread truy cập HashMap đồng thời, các vấn đề có thể nảy sinh:

1. **Mất dữ liệu** — một thread có thể ghi đè kết quả của thread khác
2. **Hành vi không dự đoán được** — `get()` có thể trả về giá trị sai
3. **ConcurrentModificationException** — khi iterate với sửa đổi đồng thời

**Ví dụ về vấn đề:**
```java
Map<String, Integer> map = new HashMap<>();

// Rủi ro chính — hỏng cấu trúc khi resize, không phải khi chèn thông thường
// Nếu các key khác nhau và các bucket khác nhau — mất mát khó xảy ra
// Nhưng khi resize đồng thời, mất phần tử là có thể!
// Tệ hơn: nếu các key GIỐNG NHAU:
// Thread 1: put("key", 100)
// Thread 2: put("key", 200) → ghi đè!
```

**Giải pháp:** Dùng `ConcurrentHashMap` cho truy cập đa luồng.

## 🟡 Middle Level

### Các rủi ro chính

| Rủi ro             | Mô tả                                | Hệ quả                        |
| ------------------ | ----------------------------------- | ----------------------------- |
| Race Condition     | Hai thread ghi vào cùng một bucket  | Mất dữ liệu                   |
| Visibility         | Các thay đổi không được thread khác nhìn thấy | Dữ liệu cũ           |
| Resize             | Hai thread mở rộng đồng thời         | Mất dữ liệu, hỏng cấu trúc    |
| Fail-Fast Iterator | Sửa đổi trong lúc iterate            | ConcurrentModificationException |

### Vấn đề của Java 7: Vòng lặp vô hạn

Trong Java 7, khi resize song song, các phần tử của list bị đảo ngược (head insertion). Hai thread có thể tạo một **tham chiếu vòng** → vòng lặp vô hạn khi `get()` → 100% CPU.

Trong Java 8+, điều này đã được sửa qua tail insertion, nhưng **mất dữ liệu khi resize vẫn có thể xảy ra**.

### Làm sao làm việc an toàn?

| Phương pháp                     | Cơ chế                            | Hiệu năng         |
| ------------------------------- | --------------------------------- | ----------------- |
| `ConcurrentHashMap`             | CAS + khóa mức bucket             | Cao               |
| `Collections.synchronizedMap()` | Một mutex duy nhất cho mọi thứ    | Thấp              |
| `Hashtable`                     | Các method synchronized           | Thấp (deprecated) |

### Khi nào có thể dùng HashMap trong đa luồng?

Chỉ khi nó được populate **trước khi** các thread bắt đầu và được dùng **read-only**. **Quan trọng:** cần safe publication — không có volatile/final, một thread khác có thể không thấy dữ liệu đã ghi.
```java
Map<String, Integer> map = new HashMap<>();
map.put("config", 42);
// Bắt đầu các thread — chỉ đọc!
```

### Các sai lầm thường gặp

1. **Nghĩ fail-fast = an toàn** — đây chỉ là phát hiện best-effort
2. **Dùng HashMap trong Spring Singleton** — một instance cho mọi request
3. **Check-then-act không có atomicity** — race condition TOCTOU

## 🔴 Senior Level

### Các Race Condition bên trong

```java
// putVal — code đơn giản hóa:
if ((p = tab[i = (n - 1) & hash]) == null)
    tab[i] = newNode(hash, key, value, null);
```

Hai thread đồng thời:
1. Cả hai thấy `tab[i] == null`
2. Cả hai tạo `newNode`
3. Cả hai ghi vào `tab[i]` — một cái mất phần tử của nó

Không có đồng bộ hóa, đây là một data race dưới Java Memory Model.

### Vấn đề Visibility

Các field của HashMap không phải `volatile`. Ngay cả khi thread A ghi một phần tử, thread B có thể không thấy nó trong CPU cache của mình (L1/L2). Cần một memory barrier.

### Race Condition khi Resize

```java
// Hai thread đồng thời gọi resize():
// 1. Cả hai tạo newTab
// 2. Cả hai sao chép các phần tử
// 3. Cả hai ghi `table = newTab`
// Kết quả: một mảng mất các phần tử
```

### Cơ chế Fail-Fast

```java
transient int modCount; // Tăng ở mỗi lần sửa đổi

// Trong iterator:
int expectedModCount = modCount;
public V next() {
    if (modCount != expectedModCount)
        throw new ConcurrentModificationException();
}
```

Đây **không phải là một cơ chế đồng bộ hóa**, mà chỉ là một trợ giúp cho việc debug.

### Pattern Safe Publication

HashMap an toàn để đọc sau safe publication:
```java
// Qua field final:
private final Map<K, V> map = createAndFillMap();

// Qua volatile:
private volatile Map<K, V> map;

// Qua AtomicReference:
private final AtomicReference<Map<K, V>> mapRef;
```

### ConcurrentHashMap: Kiến trúc bên trong

```
Java 7: Segment[] (16 segment, mỗi cái có khóa riêng)
Java 8+: Khóa mức Node (synchronized trên đầu bucket) + CAS
```

Trong Java 8+:
- CAS cho bucket rỗng (không khóa)
- `synchronized` trên đầu bucket cho va chạm
- Visibility được đảm bảo qua Unsafe.compareAndSwap (các thao tác CAS) và các memory barrier, không phải qua các khai báo field Node volatile.

### Kinh nghiệm Production

Trong các ứng dụng Spring, HashMap làm field của một `@Service` — một bug phổ biến:
```java
@Service
public class CacheService {
    private Map<String, Data> cache = new HashMap<>(); // KHÔNG AN TOÀN!
}
// Nhiều HTTP request = nhiều thread
```

Giải pháp: `ConcurrentHashMap` hoặc `Collections.synchronizedMap()`.

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- HashMap KHÔNG thread-safe: data race, mất dữ liệu, hỏng cấu trúc khi resize
- Safe publication: một Map được lấp đầy trước khi thread bắt đầu cần volatile/final để có visibility
- Fail-fast iterator (modCount) — một trợ giúp cho việc debug, KHÔNG phải một cơ chế đồng bộ hóa
- Java 7: vòng lặp vô hạn khi resize song song (head insertion); Java 8+: đã sửa (tail insertion)
- Ba lựa chọn an toàn: ConcurrentHashMap (CAS + khóa bucket), synchronizedMap, Hashtable
- ConcurrentModificationException không đảm bảo phát hiện mọi race

**Các câu hỏi phụ thường gặp:**
- **Có thể đọc HashMap từ nhiều thread không?** — có, nếu safe publication (final/volatile) và không ai ghi
- **Tại sao Spring @Service với HashMap là một bug?** — một instance cho mọi HTTP request (nhiều thread)
- **TOCTOU race là gì?** — Time-Of-Check-Time-Of-Use: kiểm tra và hành động không atomic
- **Visibility không có volatile?** — một thread khác có thể không thấy dữ liệu đã ghi (CPU cache)

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Fail-fast = thread safety" — không, chỉ là phát hiện
- "HashMap an toàn nếu các key khác nhau" — không, hỏng cấu trúc khi resize là có thể
- "synchronizedMap = giải pháp nhanh" — không, một mutex duy nhất cho mọi thứ, hiệu năng thấp
