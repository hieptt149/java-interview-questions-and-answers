# What is Double-Checked Locking? (Double-Checked Locking là gì?)

## Junior Level

**Double-Checked Locking (DCL)** là một tối ưu hóa của cách tiếp cận synchronized. Thay vì khóa (block) ở MỌI lần gọi, ta chỉ khóa trong lần tạo đối tượng đầu tiên.

**Vấn đề:** synchronized thông thường thêm ~10-50ns cho mỗi lần gọi. Trong một hot path với hàng triệu lần gọi, điều này cộng dồn thành hàng giây chi phí phát sinh.

**Giải pháp:** Kiểm tra hai lần — lần đầu không khóa, lần sau có khóa.

**Ví dụ:**
```java
public class Singleton {
    private static volatile Singleton instance;

    public static Singleton getInstance() {
        // Kiểm tra lần 1 (nhanh)
        if (instance == null) {
            // Chỉ khóa nếu cần tạo đối tượng
            synchronized (Singleton.class) {
                // Kiểm tra lần 2 (an toàn)
                if (instance == null) {
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

**Cách hoạt động:**
1. Luồng đầu tiên: instance = null -> synchronized -> tạo đối tượng
2. Luồng thứ hai: instance = null -> đợi lock -> thấy nó đã được tạo rồi
3. Luồng thứ ba: instance != null -> trả về ngay lập tức (không cần synchronized!)

**Tại sao cần volatile:** Không có nó, một luồng khác có thể nhận được một đối tượng chưa được tạo hoàn chỉnh.

### Khi nào KHÔNG nên dùng DCL

1. **Bạn không hiểu JMM** — hãy dùng Bill Pugh Singleton
2. **Bill Pugh là đủ dùng** — đơn giản hơn và đáng tin cậy hơn
3. **Không phải hot path** — synchronized method đã đủ nhanh

## Middle Level

### Tại sao cần kiểm tra hai lần?

```java
// Một lần kiểm tra = chậm
public static synchronized Singleton getInstance() {
    if (instance == null) {
        instance = new Singleton();
    }
    return instance;
}
// synchronized được gọi MỖI LẦN!

// DCL = nhanh sau khi đã khởi tạo
public static Singleton getInstance() {
    if (instance == null) {  // Kiểm tra nhanh
        synchronized (Singleton.class) {
            if (instance == null) {  // Kiểm tra chính xác
                instance = new Singleton();
            }
        }
    }
    return instance;
}
// synchronized chỉ dùng trong lúc tạo đối tượng!
```

### Tại sao volatile là bắt buộc?

```java
// Không có volatile — NGUY HIỂM!
private static Singleton instance;

// instance = new Singleton() bao gồm:
// 1. Cấp phát bộ nhớ
// 2. Gọi constructor
// 3. Gán tham chiếu cho instance

// Processor có thể tái sắp xếp: 1 -> 3 -> 2
// Thread B thấy instance != null (bước 3)
// Nhưng constructor chưa được thực thi (bước 2)!
// -> NullPointerException hoặc trạng thái bị hỏng

// Có volatile — an toàn
private static volatile Singleton instance;
// volatile ngăn chặn việc tái sắp xếp!
```

### Tối ưu hóa Local Variable

```java
public static Singleton getInstance() {
    Singleton local = instance;  // Đọc volatile một lần
    if (local == null) {
        synchronized (Singleton.class) {
            local = instance;
            if (local == null) {
                instance = local = new Singleton();
            }
        }
    }
    return local;
}

// Không tối ưu hóa: instance được đọc 2-3 lần (volatile = chậm)
// Có tối ưu hóa: instance được đọc 1 lần -> nhanh hơn ~25%
```

### So sánh các cách tiếp cận

| Cách tiếp cận             | Tốc độ     | An toàn    | Độ phức tạp |
| -------------------- | --------- | --------- | ---------- |
| **Synchronized**     | Chậm      | Có       | Đơn giản     |
| **DCL không có volatile** | Nhanh   | Không        | Trung bình     |
| **DCL + volatile**   | Nhanh      | Có       | Cao       |
| **Bill Pugh**        | Nhanh      | Có       | Đơn giản     |
| **Enum**             | Nhanh      | Có       | Tối thiểu     |

## Senior Level

**JSR-133** — bộ đặc tả Java Memory Model (2004), đảm bảo hành vi đúng đắn cho volatile.
**Instruction Reordering (Tái sắp xếp lệnh)** — processor/compiler sắp xếp lại các lệnh để tối ưu hóa.

### Đào sâu về Java Memory Model

**Instruction Reordering (Tái sắp xếp lệnh):**
```
Không có volatile, JIT/processor có thể làm:

Thread A:
  1. obj = allocate()         // Bộ nhớ được cấp phát, các trường = null/0
  2. instance = obj           // Tham chiếu được công bố!
  3. invokeConstructor(obj)   // Constructor thực thi

Thread B (can thiệp sau bước 2):
  if (instance != null) {
    instance.doWork();  // Đối tượng vẫn chưa được khởi tạo!
  }
```

**Memory Barrier từ volatile:**
```
Volatile write chèn thêm:
  StoreStore barrier — tất cả các thao tác ghi TRƯỚC volatile được hoàn thành
  StoreLoad barrier — tất cả các thao tác ghi SAU volatile nhìn thấy dữ liệu mới nhất

Volatile read chèn thêm:
  LoadLoad barrier — tất cả các thao tác đọc SAU volatile nhìn thấy dữ liệu mới nhất
  LoadStore barrier — tất cả các thao tác ghi SAU volatile sẽ không bị tái sắp xếp
```

**Happens-Before:**
```
Việc ghi vào volatile xảy ra trước (happens-before) việc đọc từ volatile
-> Tất cả các thao tác ghi trong constructor đều HIỂN THỊ (visible) đối với luồng đang đọc instance
```

### Giải pháp thay thế VarHandle (Java 9+)

```java
public class VarHandleDCL {
    private static final VarHandle HANDLE = MethodHandles.lookup()
        .findStaticVarHandle(VarHandleDCL.class, "instance", VarHandleDCL.class);

    private static VarHandleDCL instance;

    public static VarHandleDCL getInstance() {
        // getAcquire — yếu hơn so với volatile read
        VarHandleDCL local = (VarHandleDCL) HANDLE.getAcquire();
        if (local == null) {
            synchronized (VarHandleDCL.class) {
                local = (VarHandleDCL) HANDLE.getAcquire();
                if (local == null) {
                    local = new VarHandleDCL();
                    // setRelease — yếu hơn so với volatile write
                    HANDLE.setRelease(null, local);
                }
            }
        }
        return local;
    }
}

// getAcquire/setRelease = Ordered Access (truy cập có thứ tự)
// Rẻ hơn volatile, nhưng đủ dùng cho ngữ nghĩa của DCL
```

### DCL không chỉ dành cho Singleton

```java
// Lưu bộ nhớ đệm (Caching) cho các phép tính tốn kém
public class ExpensiveCalculator {
    private volatile int cachedHash;
    private volatile boolean hashComputed;

    public int hashCode() {
        if (!hashComputed) {
            synchronized (this) {
                if (!hashComputed) {
                    cachedHash = computeExpensiveHash();
                    hashComputed = true;
                }
            }
        }
        return cachedHash;
    }
}

// String.hashCode() sử dụng cùng nguyên tắc này!
```

### Benchmark hiệu năng

```
10 triệu lần gọi getInstance():

Synchronized:           150ms  (khóa mỗi lần)
DCL không có volatile:   12ms   (nhanh, nhưng bị lỗi!)
DCL + volatile:         18ms   (chi phí phát sinh khi đọc volatile)
DCL + volatile + local: 15ms   (tối ưu hóa)
Bill Pugh:              12ms   (phép thuật của class loading)
VarHandle DCL:          13ms   (barrier yếu hơn)

Kết luận: Bill Pugh — cân bằng tốt nhất giữa sự đơn giản và tốc độ
```

### Các cạm bẫy thường gặp

1. **DCL trong Java < 5 không hoạt động**
   - Trước JSR-133 (2004) Memory Model bị lỗi
   - volatile không đảm bảo happens-before

2. **Quên volatile**
   - Vẫn biên dịch được, hoạt động trong test
   - Trong production -> lỗi ngẫu nhiên

3. **Sử dụng biến cục bộ không đúng cách**
   ```java
   // Vô nghĩa
   if (instance == null) {
       Singleton local = new Singleton();
       synchronized (...) { instance = local; }
   }

   // Đúng
   Singleton local = instance;  // Đọc TRƯỚC TIÊN
   if (local == null) { ... }
   ```

### Kinh nghiệm Production

**Tình huống thực tế: Lỗi DCL sau 3 năm vận hành**
- Ứng dụng hoạt động bình thường không gặp vấn đề gì
- Migration sang server mới (CPU khác) -> xuất hiện NPE
- Nguyên nhân: bộ xử lý ARM -> việc tái sắp xếp khác
- Giải pháp: thêm volatile -> vấn đề biến mất
- Bài học: DCL không có volatile = hành vi không xác định (undefined behavior)

### Best Practices (Thực hành tốt nhất)

1. **volatile là BẮT BUỘC** trong DCL
2. **Tối ưu hóa biến cục bộ (Local variable)** để tăng hiệu năng
3. **Bill Pugh** được ưu tiên hơn DCL đối với Singleton
4. **VarHandle (Java 9+)** cho hiệu năng cực cao
5. **Đừng sử dụng DCL** nếu bạn không hiểu JMM
6. **DCL hữu ích** cho việc lazy caching (không chỉ Singleton)

### Tóm tắt cho Senior

- **DCL** = tối ưu hóa cho việc khởi tạo lười (lazy initialization)
- **volatile** rất quan trọng — ngăn chặn Instruction Reordering
- **Memory Barrier:** StoreStore/LoadLoad đảm bảo happens-before
- **Local variable:** giảm 25% số lần đọc volatile
- **VarHandle:** barrier yếu hơn -> nhanh hơn volatile
- **Trước Java 5** DCL không hoạt động (Memory Model bị lỗi)
- **String.hashCode()** sử dụng nguyên tắc DCL
- **Không có volatile** — hành vi không xác định, đặc biệt trên ARM

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- DCL — tối ưu hóa: chỉ khóa trong lúc tạo đối tượng, không phải mỗi lần gọi
- volatile là BẮT BUỘC — ngăn chặn việc tái sắp xếp lệnh (bộ nhớ -> công bố -> constructor)
- Memory Barrier: StoreStore/LoadLoad đảm bảo happens-before
- Tối ưu hóa biến cục bộ giúp giảm 25% số lần đọc volatile
- Trước Java 5 (JSR-133) DCL không hoạt động — Memory Model bị lỗi
- DCL được sử dụng không chỉ cho Singleton, mà còn cho việc lazy caching
- VarHandle (Java 9+): getAcquire/setRelease — rẻ hơn volatile

**Các câu hỏi phụ thường gặp:**
- **Điều gì xảy ra nếu không có volatile?** — Tái sắp xếp: luồng nhìn thấy tham chiếu trước khi constructor thực thi -> NPE hoặc trạng thái bị hỏng
- **Tại sao lại kiểm tra hai lần?** — Lần đầu (không có sync) để tăng tốc, lần thứ hai (trong sync) để đảm bảo an toàn với luồng
- **DCL chỉ dùng cho Singleton thôi sao?** — Không, dùng cho bất kỳ việc lazy caching nào (ví dụ: String.hashCode())
- **Tại sao Bill Pugh được ưu tiên hơn DCL?** — Đơn giản hơn, đáng tin cậy hơn, không yêu cầu volatile, JIT tối ưu hóa được

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "DCL không có volatile vẫn hoạt động — tôi đã kiểm tra rồi" — hành vi không xác định, biểu hiện khác nhau trên các CPU/JDK khác nhau
- "Synchronized trên method đã đủ nhanh rồi" — 150ms so với 15ms trên 10 triệu lần gọi
- "Tôi không dùng volatile, tôi không gặp vấn đề gì cả" — lỗi có thể xuất hiện khi migration sang CPU khác
- "DCL chỉ dùng cho Singleton" — nó được dùng cho bất kỳ việc khởi tạo lười nào
