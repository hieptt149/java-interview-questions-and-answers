# How to Refactor Code that Violates Open-Closed Principle? (Cách refactor code vi phạm Open-Closed Principle?)

## 🟢 Junior Level

**Vấn đề:** Code vi phạm Open-Closed Principle khi thêm chức năng mới yêu cầu sửa đổi các phương thức đang hoạt động. Thường thấy nhất, điều này biểu hiện dưới dạng các chuỗi `if-else` hoặc `switch` dài theo loại object.

**Ví dụ vi phạm đơn giản:**
```java
public class DiscountCalculator {
    public double calculateDiscount(String customerType, double amount) {
        if ("regular".equals(customerType)) {
            return amount * 0.05; // giảm giá 5%
        } else if ("vip".equals(customerType)) {
            return amount * 0.15; // giảm giá 15%
        } else if ("premium".equals(customerType)) {
            return amount * 0.25; // giảm giá 25%
        }
        return 0;
    }
}
```
Mỗi loại khách hàng mới nghĩa là sửa đổi code hiện có, có nguy cơ phá vỡ logic cũ.

**Cách tiếp cận refactoring cơ bản:**

**Bước 1:** Trích xuất một interface
```java
public interface DiscountStrategy {
    double calculateDiscount(double amount);
    String getCustomerType();
}
```

**Bước 2:** Tạo các class riêng biệt cho mỗi nhánh
```java
public class RegularDiscount implements DiscountStrategy {
    @Override
    public double calculateDiscount(double amount) {
        return amount * 0.05;
    }
    @Override
    public String getCustomerType() { return "regular"; }
}

public class VipDiscount implements DiscountStrategy {
    @Override
    public double calculateDiscount(double amount) {
        return amount * 0.15;
    }
    @Override
    public String getCustomerType() { return "vip"; }
}
```

**Bước 3:** Dùng một Map để chọn strategy
```java
public class DiscountCalculator {
    private final Map<String, DiscountStrategy> strategies;

    public DiscountCalculator(List<DiscountStrategy> strategyList) {
        this.strategies = new HashMap<>();
        for (DiscountStrategy s : strategyList) {
            strategies.put(s.getCustomerType(), s);
        }
    }

    public double calculateDiscount(String customerType, double amount) {
        DiscountStrategy strategy = strategies.get(customerType);
        if (strategy == null) {
            throw new IllegalArgumentException("Unknown type: " + customerType);
        }
        return strategy.calculateDiscount(amount);
    }
}
```

Bây giờ một loại giảm giá mới chỉ là một class mới, không sửa đổi code hiện có.

## 🟡 Middle Level

### Cách Nhận Biết Vi Phạm OCP

**Các dấu hiệu chính:**

1. **Switch/If theo loại**: `if (obj instanceof X)`, `switch (type)`, `switch (enum)`
2. **God Method**: Các phương thức 100+ dòng "làm một chút mọi thứ"
3. **Bug regression**: Thêm một tính năng mới phá vỡ chức năng cũ
4. **Merge Conflict**: Nhiều developer sửa cùng một file đồng thời

### Refactoring Từng Bước

**Trước (vi phạm OCP):**
```java
public class NotificationService {
    public void send(String channel, String message) {
        switch (channel) {
            case "email":
                sendEmail(message);
                break;
            case "sms":
                sendSms(message);
                break;
            case "push":
                sendPush(message);
                break;
            case "telegram":
                sendTelegram(message);
                break;
            // Mỗi channel mới — sửa đổi phương thức này!
        }
    }
}
```

**Sau (pattern Strategy + Factory):**
```java
public interface NotificationChannel {
    String getType();
    void send(String message);
}

public class EmailChannel implements NotificationChannel {
    @Override
    public String getType() { return "email"; }
    @Override
    public void send(String message) { /* logic email */ }
}

public class SmsChannel implements NotificationChannel {
    @Override
    public String getType() { return "sms"; }
    @Override
    public void send(String message) { /* logic sms */ }
}

public class NotificationService {
    private final Map<String, NotificationChannel> channels;

    public NotificationService(List<NotificationChannel> channelList) {
        this.channels = channelList.stream()
            .collect(Collectors.toMap(NotificationChannel::getType, c -> c));
    }

    public void send(String channelType, String message) {
        NotificationChannel channel = channels.get(channelType);
        if (channel == null) {
            throw new IllegalArgumentException("Unknown channel: " + channelType);
        }
        channel.send(message);
    }
}
```

### Refactoring An Toàn: Strategy

1. **Bao phủ bằng test** code hiện có (ngay cả khi nó "xấu")
2. **Tạo một abstraction** (interface)
3. **Triển khai từng cái một** class cho mỗi nhánh
4. **Thay thế** switch/if bằng delegation
5. **Xóa** code cũ
6. **Chạy test** — hành vi không nên thay đổi

### Các Lỗi Refactoring Thường Gặp

1. **Lỗi**: Refactoring không có test
   **Giải pháp**: Luôn bắt đầu bằng cách viết test cho hành vi hiện tại

2. **Lỗi**: Tạo abstraction "phòng khi cần"
   **Giải pháp**: Chỉ refactor khi có nhu cầu mở rộng thực sự

3. **Lỗi**: Phân rã quá mức (mỗi if — một class riêng)
   **Giải pháp**: Nhóm logic liên quan; không phải mọi `if` đều xứng đáng có class riêng

4. **Lỗi**: Quên xóa code cũ
   **Giải pháp**: Dead code gây nhầm lẫn cho các developer sau — hãy mạnh dạn xóa

### Khi Nào KHÔNG Cần Refactoring

- Code ổn định và không thay đổi trong nhiều năm
- Prototype / proof of concept
- Ít nhánh (2-3) và không mong đợi thêm
- Chi phí refactoring vượt quá chi phí bảo trì

### Cách Chọn Chiến Lược Refactoring

- **Pattern Matching** — cho các hierarchy đóng (sealed interface), khi tập các loại đã biết
- **Strategy** — khi các triển khai được thêm động (plugin, cấu hình)
- **Visitor** — khi có nhiều thao tác khác nhau trên một hierarchy (thuế, report, validation)
- **SPI (ServiceLoader)** — cho các thư viện, khi các triển khai được tải từ classpath

> SPI không hỗ trợ dependency injection — mỗi class phải có constructor không tham số.

## 🔴 Senior Level

### Triển Khai Nội Bộ Và Kiến Trúc

Refactoring OCP không chỉ là "thay switch bằng strategy". Đó là **thiết kế lại các điểm mở rộng** của hệ thống. Ở cấp độ Senior, quan trọng là phải hiểu:

> *Refactoring sang OCP là một khoản đầu tư để giảm TCO (Total Cost of Ownership). Nó chỉ đáng giá nếu hệ thống thực sự sẽ được mở rộng.*

### Các Chiến Lược Refactoring

#### 1. Pattern Matching (Java 21+)
Thay vì refactoring hoàn toàn, có thể dùng các khả năng Java hiện đại:
```java
public double calculateDiscount(Object customer, double amount) {
    return switch (customer) {
        case RegularCustomer c -> amount * 0.05;
        case VipCustomer c -> amount * 0.15;
        case PremiumCustomer c -> amount * 0.25;
        case null, default -> 0;
    };
}
```
**Đánh đổi**: Đây vẫn là một vi phạm OCP (cần sửa đổi switch cho một loại mới), nhưng compiler sẽ cảnh báo về các case còn thiếu. Chấp nhận được cho các hierarchy đóng (`sealed interface`).

// Tại sao đây là vi phạm OCP? Khi thêm GoldCustomer, bạn sẽ phải
// quay lại switch này và thêm một case mới. Bạn đang SỬA ĐỔI
// code hiện có, không phải mở rộng.

#### 2. Double Dispatch (Pattern Visitor)
Cho các hierarchy phức tạp với nhiều thao tác:
```java
public interface Customer {
    <R> R accept(CustomerVisitor<R> visitor);
}

public interface CustomerVisitor<R> {
    R visit(RegularCustomer c);
    R visit(VipCustomer c);
    R visit(PremiumCustomer c);
}

public class DiscountVisitor implements CustomerVisitor<Double> {
    private final double amount;
    public DiscountVisitor(double amount) { this.amount = amount; }

    @Override
    public Double visit(RegularCustomer c) { return amount * 0.05; }
    @Override
    public Double visit(VipCustomer c) { return amount * 0.15; }
    @Override
    public Double visit(PremiumCustomer c) { return amount * 0.25; }
}
```

#### 3. Plugin Registry (SPI — Service Provider Interface)
Cho các hệ thống thực sự có thể mở rộng:
```java
public interface DiscountProvider {
    boolean supports(String customerType);
    double calculate(double amount);
}

// Trong META-INF/services/com.example.DiscountProvider
// đăng ký tất cả các triển khai
```

### Đánh Đổi Kiến Trúc

**Refactoring hoàn toàn sang OCP:**
- ✅ Ưu điểm: Kiến trúc sạch, dễ mở rộng, regression tối thiểu
- ❌ Nhược điểm: Chi phí refactoring cao, nguy cơ regression trong quá trình migration, nhiều class hơn

**Refactoring một phần (sealed type, enum):**
- ✅ Ưu điểm: Nhanh, compiler giúp đỡ, boilerplate tối thiểu
- ❌ Nhược điểm: Vẫn cần sửa đổi code khi thêm một loại

**Không refactoring:**
- ✅ Ưu điểm: Chi phí bằng không ngay bây giờ
- ❌ Nhược điểm: Tích lũy nợ kỹ thuật, giảm tốc phát triển trong tương lai

### Edge Cases

1. **Legacy Code Không Có Test**: Refactor như thế nào?
   - **Cách tiếp cận**: Characterization Test — viết test bắt lại hành vi hiện tại, ngay cả khi nó "xấu"
   - **Công cụ**: Approval Tests, Golden Master Testing

> **Strangler Fig Pattern** — thay thế dần dần hệ thống cũ bằng hệ thống mới thông qua một facade. Giống như một dây leo bao trùm một cái cây: code mới dần dần tiếp quản chức năng từ cái cũ.
>
> **Characterization Test** — các test bắt lại hành vi hiện tại của legacy code. Bạn không biết cái gì là "đúng", nhưng bạn biết "hiện tại nó hoạt động thế này".
>
> **Golden Master** — output tham chiếu đã lưu của hệ thống để so sánh sau khi refactoring.

2. **Cross-cutting Concerns**: Khi switch ảnh hưởng đến 5+ module
   - **Cách tiếp cận**: Strangler Fig Pattern — thay thế dần dần code cũ bằng code mới, route thông qua một facade

3. **Runtime Discovery**: Khi các triển khai mới được tải động (plugin)
   - **Cách tiếp cận**: `ServiceLoader`, quét `@Component` của Spring, OSGi

### Hiệu Năng

- **Interface dispatch**: Gọi thông qua một interface chậm hơn gọi trực tiếp (~1-2 ns). JIT thực hiện **inline caching**, nhưng với > 2 loại, một **megamorphic transition** xảy ra — giảm xuống 10-20 ns
- **Map lookup**: `HashMap.get()` — O(1), nhưng có overhead trên hashCode + boxing. Với < 10 strategy, một `if-else` đơn giản có thể nhanh hơn
- **Overhead bộ nhớ**: Mỗi class thêm = metadata trong Metaspace (~1-5 KB). Với 1000+ strategy, điều này trở nên đáng chú ý

### Kinh Nghiệm Production

**Kịch bản production thực tế:**

Trong một hệ thống thanh toán, có một `PaymentProcessor` với 40+ nhánh `if-else` cho các phương thức thanh toán khác nhau. Thêm một phương thức mới mất 3-5 ngày (tìm vị trí, sửa đổi, test regression).

Team đã thực hiện refactoring:
1. Viết 200+ characterization test (không thay đổi hành vi)
2. Trích xuất interface `PaymentMethod`
3. Tạo 40+ class triển khai (một cho mỗi nhánh)
4. Inject thông qua Spring DI với auto-discovery

**Kết quả**: Phương thức thanh toán mới — 2 giờ (một class + test). Bug regression giảm 80%.

### Monitoring Và Chẩn Đoán

**Cách phát hiện nhu cầu refactoring:**

1. **Phân tích Git**:
   - `git log --follow -- <file>` — file thay đổi nhiều hơn 2 lần/tháng?
   - `git blame` — nhiều tác giả khác nhau trong một file?

2. **Metric**:
   - Độ phức tạp Cyclomatic > 15
   - Số lượng Branch > 5
   - Tần suất regression khi thêm loại mới

3. **Công cụ**:
   - SonarQube (Cognitive Complexity)
   - Checkstyle (Method Length, Cyclomatic Complexity)
   - ArchUnit (dependency giữa các tầng)

### Best Practices Cho Highload

- **Hot Path**: Trong các phần quan trọng về hiệu năng, tránh interface — dùng `switch` trên enum (JIT tối ưu thông qua tableswitch)
- **Cold Path**: Trong business logic, dùng strategy — hiệu năng không quan trọng, linh hoạt quan trọng hơn
- **JIT-friendly**: Nếu có > 3 strategy, cân nhắc `sealed interface` + pattern matching — JIT có thể tối ưu tốt hơn

### Tóm Tắt Cho Senior

- Refactoring sang OCP là một **khoản đầu tư**, không phải một giáo điều
- Luôn bắt đầu với **characterization test**
- Dùng **Strangler Fig Pattern** cho migration legacy
- Nhớ về **JIT megamorphic call** — trong hot path, `switch` có thể nhanh hơn
- Đừng refactor code sẽ không được mở rộng (YAGNI)

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- Bước đầu tiên của refactoring OCP — bao phủ code bằng test (Characterization Test cho legacy)
- Các chiến lược: Strategy (triển khai động), Visitor (nhiều thao tác trên hierarchy), sealed interface (tập loại đóng)
- Strangler Fig Pattern — thay thế dần dần code cũ bằng code mới thông qua một facade
- Refactoring an toàn: test → abstraction → các triển khai → delegation → xóa code cũ
- Refactoring sang OCP — khoản đầu tư để giảm TCO, chỉ đáng giá nếu hệ thống sẽ được mở rộng
- Trong hot path, `switch` trên enum có thể nhanh hơn strategy (JIT tối ưu thông qua tableswitch)

**Các câu hỏi phụ thường gặp:**
- **Cách refactor legacy không có test?** — Characterization Test: bắt lại hành vi hiện tại, sau đó thay đổi
- **Strategy vs sealed interface — chọn cái nào?** — Strategy cho tập động, sealed cho tập đã biết tại compile-time
- **Khi nào KHÔNG cần refactoring?** — Code ổn định và không thay đổi, prototype, ít nhánh (2-3) và không mong đợi thêm
- **Golden Master Testing là gì?** — Output tham chiếu đã lưu của hệ thống để so sánh sau khi refactoring

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Mỗi if xứng đáng có class riêng" (phân rã quá mức)
- "Refactoring không có test là ổn" (nguy cơ regression)
- "OCP cần được áp dụng cho tất cả code" (YAGNI: chỉ cho các điểm mở rộng)
