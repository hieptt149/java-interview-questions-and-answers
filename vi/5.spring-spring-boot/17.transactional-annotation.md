# What Does the @Transactional Annotation Do? (Annotation @Transactional làm gì?)

## Junior Level

**@Transactional** là một annotation tự động quản lý các transaction của DB.

**Ví dụ minh họa đơn giản:** Một giao dịch chuyển tiền ngân hàng. Hoặc là tiền được trừ VÀ được cộng, hoặc là không có gì xảy ra. Không thể có chuyện tiền bị trừ nhưng không được cộng.

```java
@Service
public class OrderService {

    @Transactional
    public void createOrder(Order order) {
        orderRepository.save(order);       // SQL INSERT
        paymentRepository.charge(order);   // SQL UPDATE
        // Nếu có lỗi -> mọi thứ sẽ được rollback!
    }
}
```

**Cách hoạt động:**
```
Proxy -> BEGIN TRANSACTION -> gọi phương thức -> COMMIT
                               | (lỗi)
                            ROLLBACK
```

## Middle Level

### Propagation (lan truyền)

| Propagation                 | Hành vi                                       |
| --------------------------- | ----------------------------------------------- |
| **REQUIRED** (mặc định) | Dùng transaction hiện có hoặc tạo mới       |
| **REQUIRES_NEW**            | Luôn tạo mới (tạm dừng transaction hiện tại) |
| **NESTED**                  | Lồng nhau qua Savepoint                       |
| **MANDATORY**               | Yêu cầu phải có transaction hiện có (nếu không thì lỗi)             |

### Isolation (mức cô lập)

| Isolation           | Ngăn chặn điều gì            |
| ------------------- | ---------------------------- |
| **READ_COMMITTED**  | Dirty Read                  |
| **REPEATABLE_READ** | Non-repeatable Read         |
| **SERIALIZABLE**    | Phantom Read (nhưng chậm!) |

### Quy tắc Rollback

```java
// Theo mặc định: chỉ RuntimeException và Error (unchecked exception). Checked exception (Exception và các lớp con) KHÔNG gây rollback.
@Transactional
public void save() throws IOException { }
// IOException -> sẽ KHÔNG rollback!

// Chỉ định tường minh
@Transactional(rollbackFor = Exception.class)
public void save() throws IOException { }
// IOException -> sẽ rollback!
```

### Tối ưu hóa readOnly

```java
@Transactional(readOnly = true)
public List<User> findAll() {
    // -> Hibernate tắt Dirty Checking
    // -> Tiết kiệm CPU và bộ nhớ
}
```

## Senior Level

### Rủi ro của REQUIRES_NEW

```java
@Transactional
public void outer() {
    inner();  // REQUIRES_NEW -> transaction mới!
}

@Transactional(propagation = REQUIRES_NEW)
public void inner() {
    // Tạm dừng transaction bên ngoài
    // Lấy một connection KHÁC từ pool!
    // -> Rủi ro deadlock với pool nhỏ
}
```

### Vấn đề giải phóng Connection

```java
@Transactional
public void process() {
    repository.save(order);     // Connection bị chiếm
    httpClient.callExternal();  // 5 giây -> connection bị giữ!
    repository.save(payment);
}

// -> Connection có thể bị giữ trong suốt transaction. Hành vi phụ thuộc vào ConnectionReleaseMode: theo mặc định trong Spring + Hibernate, connection bị giữ đến khi commit/rollback.

// Giải pháp: tách thành hai phương thức
```

### TransactionalEventListener

```java
// Gửi lên Kafka CHỈ sau khi commit!
@TransactionalEventListener(phase = AFTER_COMMIT)
public void onOrderCreated(OrderCreatedEvent event) {
    kafkaTemplate.send("orders", event);
}

// -> Nếu transaction rollback -> event KHÔNG được gửi!
// -> Nếu phương thức phát ra event KHÔNG nằm trong một transaction - event được gửi ngay lập tức, như thể nó là một ApplicationEvent thông thường.
```

### Kinh nghiệm Production

**Tình huống thực tế: transaction dài**
```
Phương thức @Transactional:
  1. Lưu order (10 ms)
  2. Lời gọi HTTP tới API bên ngoài (3 giây)
  3. Lưu payment (10 ms)

-> Connection bận trong 3+ giây!
-> Ở 100 RPS -> cần 300 connection!
-> Pool có 20 -> tất cả đều bận -> timeout!

Giải pháp: tách thành hai phương thức
```

### Best Practices

1. **REQUIRED** — theo mặc định
2. **rollbackFor = Exception.class** — luôn chỉ định tường minh
3. **readOnly = true** — cho các thao tác đọc
4. **Tránh REQUIRES_NEW** khi không có lý do
5. **Đừng tạo các transaction dài**
6. **TransactionalEventListener** -> cho các event sau khi commit
7. **Self-invocation** -> không hoạt động!

### Tóm tắt cho Senior

- **Proxy** -> TransactionInterceptor quản lý transaction
- **Propagation** -> REQUIRED/REQUIRES_NEW/NESTED
- **rollbackFor** -> chỉ định tường minh Exception.class
- **readOnly** -> tắt Dirty Checking
- **Giải phóng Connection** -> đừng giữ lâu
- **TransactionalEventListener** -> AFTER_COMMIT
- **Self-invocation** -> không hoạt động!

## Interview Cheat Sheet

**Cần phải biết:**
- @Transactional = quản lý transaction tự động: BEGIN -> phương thức -> COMMIT / ROLLBACK
- Theo mặc định: propagation = REQUIRED, rollback chỉ cho RuntimeException và Error
- Propagation: REQUIRED (dùng/tạo), REQUIRES_NEW (luôn mới), NESTED (qua Savepoint)
- Isolation: READ_COMMITTED, REPEATABLE_READ, SERIALIZABLE — chúng ngăn chặn điều gì
- rollbackFor = Exception.class — luôn chỉ định tường minh cho các checked exception
- readOnly = true — tắt Hibernate Dirty Checking, tiết kiệm CPU/bộ nhớ
- REQUIRES_NEW lấy một connection KHÁC từ pool -> rủi ro deadlock với pool nhỏ
- TransactionalEventListener(AFTER_COMMIT) — event chỉ được gửi sau khi commit
- Self-invocation KHÔNG hoạt động — gọi qua this vòng qua proxy

**Các câu hỏi phụ thường gặp:**
- *Những exception nào gây rollback theo mặc định?* -> Chỉ unchecked (RuntimeException, Error). Checked Exception — KHÔNG rollback
- *REQUIRES_NEW khác NESTED như thế nào?* -> REQUIRES_NEW = transaction riêng biệt, NESTED = lồng nhau qua Savepoint trong cùng một transaction
- *Tại sao REQUIRES_NEW nguy hiểm?* -> Lấy một connection khác, với pool nhỏ — deadlock/timeout
- *Làm gì với các transaction dài?* -> Tách thành các phương thức, đưa các lời gọi HTTP ra khỏi transaction

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "@Transactional rollback mọi exception" — chỉ unchecked theo mặc định
- "REQUIRES_NEW = transaction lồng nhau" — đó là NESTED, REQUIRES_NEW là riêng biệt
- "readOnly = true cấm ghi" — nó là một tối ưu hóa của Hibernate, không phải lệnh cấm ghi
- "Transaction giải phóng connection giữa các lời gọi" — giữ đến khi commit/rollback
