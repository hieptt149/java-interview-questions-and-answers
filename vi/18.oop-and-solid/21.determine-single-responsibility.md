# How to Determine if a Class Has Single Responsibility? (Cách xác định xem một class có single responsibility không)

## 🟢 Junior Level

**Single Responsibility (SRP)** nghĩa là một class nên làm một việc. Nếu bạn có thể mô tả những gì một class làm trong một câu đơn giản mà không dùng các từ như "và," "hoặc," "cũng" — trách nhiệm có khả năng là duy nhất.

Hãy tưởng tượng một văn phòng: kế toán tính lương, luật sư kiểm tra hợp đồng, sysadmin cấu hình server. Nếu một người cố gắng làm mọi thứ cùng lúc — chất lượng giảm xuống.

**Ví dụ vi phạm SRP:**
```java
// Class này làm quá nhiều: validate, lưu, và gửi email
public class OrderProcessor {
    public void process(Order order) {
        validate(order);       // Validation — trách nhiệm của validator
        save(order);           // Persistence — trách nhiệm của repository
        sendEmail(order);      // Notification — trách nhiệm của notification service
        generateInvoice(order);// Tạo PDF — trách nhiệm của report generator
    }
}
```

**Ví dụ tuân thủ SRP:**
```java
// Mỗi class — một trách nhiệm
public class OrderValidator {
    public void validate(Order order) {
        if (order.getItems().isEmpty()) {
            throw new IllegalArgumentException("Order is empty");
        }
    }
}

public class OrderRepository {
    public void save(Order order) {
        // lưu vào DB
    }
}

public class EmailNotificationService {
    public void sendConfirmation(Order order) {
        // gửi email
    }
}

// Orchestrator chỉ điều phối
public class OrderService {
    private final OrderValidator validator;
    private final OrderRepository repository;
    private final EmailNotificationService notifier;

    public OrderService(OrderValidator validator,
                        OrderRepository repository,
                        EmailNotificationService notifier) {
        this.validator = validator;
        this.repository = repository;
        this.notifier = notifier;
    }

    public void process(Order order) {
        validator.validate(order);
        repository.save(order);
        notifier.sendConfirmation(order);
    }
}
```

**Test SRP đơn giản:** Cố gắng mô tả mục đích của class trong một câu. Nếu bạn dùng từ "và" — class có nhiều trách nhiệm.

## 🟡 Middle Level

### 5 Test Để Xác Định SRP

#### 1. Test Đặt Tên
Mô tả những gì class làm mà không dùng "và," "hoặc," "cũng," "nữa."

| Class            | Mô Tả                                        | Kết Quả              |
| ---------------- | -------------------------------------------------- | -------------------- |
| `OrderProcessor` | "Validate đơn hàng VÀ lưu VÀ gửi email"        | ❌ 3 trách nhiệm|
| `OrderValidator` | "Validate tính đúng đắn của đơn hàng"                      | ✅ 1 trách nhiệm  |
| `PdfGenerator`   | "Tạo tài liệu PDF"                          | ✅ 1 trách nhiệm  |
| `UserManager`    | "Quản lý user" — nhưng chính xác là gì?                | ❌ Mơ hồ             |

#### 2. Test Thay Đổi
Định nghĩa chính xác nhất từ Robert Martin. Hỏi: "Ai có thể đến và yêu cầu thay đổi class này?"

Nếu đó là luật sư (nội dung hợp đồng), kế toán (công thức tính toán), và admin (đường dẫn log) — class có ít nhất 3 trách nhiệm.

#### 3. Test Import
Nhìn vào các import của class:

```java
import java.sql.*;          // DB
import javax.mail.*;        // Email
import com.fasterxml.jackson.*; // JSON
import org.springframework.web.*; // Web
```
Nếu một class có `java.sql`, `javax.mail`, và `com.fasterxml.jackson` — nó "trải rộng" trên DB, networking, và serialization.

#### 4. Test Mocking
Cố gắng viết một unit test cho một phương thức. Nếu test một `if` cần thiết lập 5-7 mock — class bị quá tải với trách nhiệm của người khác.

```java
// Xấu: 7 mock cho một test
@Mock private OrderRepository repo;
@Mock private EmailService email;
@Mock private SmsService sms;
@Mock private PdfGenerator pdf;
@Mock private TaxCalculator tax;
@Mock private DiscountService discount;
@Mock private AuditLogger audit;

// Tốt: 1-2 mock, test một trách nhiệm
@Mock private OrderRepository repo;
@Test void shouldSaveValidOrder() { ... }
```

#### 5. Metric Cohesion LCOM4

**LCOM4** (Lack of Cohesion in Methods) được tính bởi các trình phân tích tĩnh:
- Hãy tưởng tượng một đồ thị trong đó node là các phương thức và trường, cạnh là việc sử dụng phương thức-trường
- Nếu đồ thị chia thành 2+ thành phần không liên kết — các "cơ thể" độc lập sống bên trong một class

| LCOM4   | Ý Nghĩa                                     |
| ------- | ------------------------------------------- |
| 1       | ✅ Cohesion cao, single responsibility      |
| 2-3     | ⚠️ Class có thể được chia                       |
| 4+      | ❌ Class chắc chắn cần được chia          |

Công cụ: **SonarQube**, **jdepend**, **IntelliJ IDEA** (phân tích tích hợp sẵn).

### Yếu Tố Xã Hội Của SRP

Một góc nhìn thú vị: **"Một class — một team developer."** Nếu người từ các team khác nhau (team Billing và team Delivery) làm việc trên một class — nó trở thành một điểm nghẽn. Chia theo ranh giới trách nhiệm của team.

### Các Lỗi Thường Gặp

1. **Lỗi**: "Class nhỏ — vì vậy SRP được tuân thủ."
   **Giải pháp**: Kích thước không quyết định trách nhiệm. Một class 30 dòng có thể làm 3 việc. Một class 300 dòng có thể làm một việc phức tạp.

2. **Lỗi**: "Class có một phương thức public — vì vậy SRP được tuân thủ."
   **Giải pháp**: Một phương thức có thể ủy quyền cho 10 subsystem khác nhau. Nhìn vào cohesion, không phải số lượng phương thức.

3. **Lỗi**: Anemic model (chỉ getter/setter) — đây không phải vi phạm SRP, đó là chuyển trách nhiệm sang service.
   **Giải pháp**: Trong OOP cổ điển, logic nằm gần dữ liệu. Trong Enterprise Java, anemic model thường được biện minh (ORM, DI).

### Khi Nào KHÔNG Nên Tuân Thủ SRP Nghiêm Ngặt

- **DTO / Value Objects**: Class chỉ chứa dữ liệu — trách nhiệm của chúng là "lưu trữ dữ liệu," điều đó ổn
- **Test Utilities**: Test fixture, builder — có thể chứa logic không đồng nhất
- **Tiện Ích Nhỏ**: Một class 20 dòng với hai phương thức liên quan không cần chia

### So Sánh Cách Tiếp Cận

| Cách tiếp cận                                              | Ưu điểm                      | Nhược điểm                              | Khi Nào Dùng                                                                                         |
| ----------------------------------------------------- | ------------------------- | ------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| SRP Nghiêm Ngặt (mỗi thao tác — class riêng)          | Khả năng test tối đa       | Bùng nổ class, khó điều hướng | Hệ thống an toàn quan trọng (hàng không, y tế), nơi chi phí lỗi cực kỳ cao             |
| SRP Hợp Lý (1 domain = 1 class)                   | Cân bằng                   | Cần phán đoán trưởng thành             | Hầu hết dự án enterprise                                                                            |
| Không Có SRP                                           | Nhanh lúc bắt đầu             | Không thể bảo trì trong vòng một năm         | Prototype, script một lần                                                                        |

## 🔴 Senior Level

### Triển Khai Nội Bộ: JVM "Nhìn" SRP Như Thế Nào

Ở tầng JVM, SRP không tồn tại — đó là một ràng buộc kiến trúc. Nhưng hậu quả của vi phạm SRP có thể đo lường được:

**Dấu chân bộ nhớ:** Một class với 5 trách nhiệm = 5 nhóm trường hiếm khi được dùng đồng thời. Điều này có nghĩa:
- Object chiếm 200+ byte, nhưng chỉ 20 byte được dùng trong một ngữ cảnh nhất định
- 180 byte còn lại là "trọng lượng chết" trong CPU cache (ô nhiễm cache line)
- Đối với L1 cache (32-48KB mỗi core), điều này có nghĩa ít dữ liệu hữu ích hơn mỗi cache line

**Tác động GC:** Object lớn với nhiều trường:
- Được thăng cấp lên old generation nhanh hơn (kích thước lớn hơn, lấp đầy tenured nhanh hơn)
- Với việc sử dụng một phần — lãng phí bộ nhớ trong old gen
- G1 GC cấp phát các vùng 1-32MB. Một class lớn với nhiều tham chiếu có thể "móc" nhiều vùng

**Biên dịch JIT:** Một class với 50 phương thức và 30 trường:
- JIT không thể tối ưu hóa hiệu quả — quá nhiều đường thực thi
- Các phương thức hiếm khi được gọi cùng nhau — không có lợi ích từ batching biên dịch
- Phân mảnh code cache — các "trách nhiệm" khác nhau biên dịch riêng biệt nhưng chiếm các vùng liền kề

### Đánh Đổi Kiến Trúc

**SRP Nghiêm Ngặt (mỗi thao tác — class riêng):**
- ✅ Ưu điểm: Cô lập thay đổi; blast radius tối thiểu; mỗi class được test riêng biệt; dễ mock
- ❌ Nhược điểm: Bùng nổ class (5000+ class); khó điều hướng; overhead tạo object; khó theo dõi luồng

**SRP Vừa Phải (nhóm theo ngữ cảnh domain):**
- ✅ Ưu điểm: Cân bằng giữa khả năng đọc và cô lập; các thao tác liên quan về mặt logic cùng nhau
- ❌ Nhược điểm: Ranh giới chủ quan; nguy cơ trách nhiệm "bò dần"

**SRP Lai (nghiêm ngặt trong domain, vừa phải trong infrastructure):**
- ✅ Ưu điểm: Domain model sạch; thực dụng trong infrastructure
- ❌ Nhược điểm: Không nhất quán; cần nhớ phong cách nào áp dụng ở đâu

### Edge Cases

1. **Anemic Domain Model**: `User` và `Order` chỉ với getter/setter. Về mặt hình thức — không phải vi phạm SRP (một trách nhiệm: lưu trữ dữ liệu). Nhưng tất cả business logic chuyển sang service, trở thành God Object.
   **Giải pháp**: Trong DDD, dùng Rich Domain Model. Trong Transaction Script — chấp nhận anemic model nhưng kiểm soát kích thước service.

2. **Bùng Nổ Class**: 50 class cho SRP đối với một thao tác CRUD đơn giản.
   **Giải pháp**: Đừng sợ tạo nhiều class (IDE xử lý được 10,000+ file). Hãy sợ một file 10,000 dòng. Nhưng nếu một class 3 phương thức làm một việc — đừng chia nó.

3. **God Class Với Một Cái Tên "Tốt"**: `PaymentOrchestrator` với 5000 dòng và 30 dependency. Cái tên nghe như "một trách nhiệm" (điều phối), nhưng đó là một lớp ngụy trang.
   **Giải pháp**: Dùng metric Dependency Count (đếm số class mà một class nhất định phụ thuộc vào). Nếu một class phụ thuộc vào 10+ class khác — đó là God Class.

4. **Cross-cutting Concerns** (logging, metrics, tracing — cần thiết trên nhiều class): Logging, metrics, tracing — các trách nhiệm "trải rộng" trên tất cả các class.
   **Giải pháp**: Dùng aspect (AOP — lập trình hướng khía cạnh), decorator, hoặc middleware. Đừng trộn cross-cutting concern với business logic trong một class.

```java
// Xấu: logging là một phần trách nhiệm của service
public class OrderService {
    private final Logger log = LoggerFactory.getLogger(OrderService.class);
    private final MeterRegistry metrics;

    public Order process(OrderRequest req) {
        log.info("Processing order {}", req.getId());
        metrics.counter("orders.processed").increment();
        // business logic...
        log.info("Order {} processed", req.getId());
    }
}

// Tốt: cross-cutting concern qua decorator
public class MeteredOrderService implements OrderService {
    private final OrderService delegate;
    private final MeterRegistry metrics;

    @Override
    public Order process(OrderRequest req) {
        metrics.counter("orders.processed").increment();
        return delegate.process(req);
    }
}
```

### Hiệu Năng

So sánh cho một hệ thống xử lý đơn hàng (100K đơn hàng/giờ):

| Cách Tiếp Cận SRP                     | Kích Thước Class (trung bình)  | Bộ Nhớ Mỗi Object  | Tỷ Lệ CPU Cache Hit  | Áp Lực GC   |
| -------------------------------- | --------------------- | ------------------ | -------------------- | ------------- |
| God Class (1 class, 5000 dòng)  | 5000 dòng            | 2KB                | 60%                 | Thấp           |
| SRP Nghiêm Ngặt (100 class)         | 30 dòng              | 120 byte              | 95%                 | Cao          |
| SRP Vừa Phải (15 class)        | 200 dòng             | 400 byte              | 85%                 | Trung bình        |

Đối với hầu hết các hệ thống enterprise, SRP vừa phải là cân bằng tối ưu. Đối với highload với ngân sách độ trễ nghiêm ngặt — SRP nghiêm ngặt có thể có lợi (cache locality tốt hơn), nhưng overhead cấp phát cần được bù đắp bằng object pooling.

### Kinh Nghiệm Production

**War Story: Refactoring Hệ Thống Billing (2024)**

Một công ty viễn thông lớn, hệ thống billing trên Java 17. `BillingEngine` — 12,000 dòng, 67 dependency, LCOM4 = 8. Bốn team làm việc trên nó đồng thời. Mỗi release — 3-4 bug regression, gây ra bởi một team phá vỡ chức năng của team khác.

**Chẩn đoán:**
```bash
# SonarQube cho thấy:
# - Cognitive Complexity: 180 (giới hạn 15)
# - LCOM4: 8.0 (chuẩn <= 1)
# - Số lượng dependency: 67 (khuyến nghị <= 10)
```

**Refactoring:**
```
BillingEngine (12,000 dòng)
├── TariffCalculator (800 dòng) — tính toán biểu giá
├── UsageAggregator (600 dòng) — tổng hợp tiêu thụ
├── InvoiceGenerator (1,200 dòng) — tạo hóa đơn
├── DiscountEngine (900 dòng) — giảm giá và tiền thưởng
├── TaxCalculator (500 dòng) — thuế
├── PaymentProcessor (700 dòng) — xử lý thanh toán
├── NotificationDispatcher (400 dòng) — thông báo
└── BillingOrchestrator (300 dòng) — điều phối
```

Kết quả:
- LCOM4: 8.0 → 1.0 cho mỗi class
- Bug regression: 3-4 mỗi release → 0-1
- Phát triển song song: 4 team không xung đột
- Thời gian thêm loại biểu giá mới: 2 tuần → 2 ngày

**War Story: Phân Rã Microservices (2023)**

Monolith e-commerce, `UserService` — 6,000 dòng. Team Authentication và team Profiles liên tục xung đột khi merge. LCOM4 = 5, Dependencies = 42.

Chia theo ranh giới trách nhiệm của team:
- `AuthService` (xác thực, phân quyền, token)
- `ProfileService` (dữ liệu user, tùy chọn)
- `NotificationPreferencesService` (cài đặt thông báo)

Kết quả: xung đột merge giảm 90%, các lần triển khai trở nên độc lập.

### Giám Sát Và Chẩn Đoán

- **ArchUnit**: Kiểm tra tự động trong CI/CD:
```java
@ArchTest
static final ArchRule classes_should_have_single_responsibility =
    classes()
        .that().resideInAPackage("..domain..")
        .should().haveLessThan10Dependencies()
        .andShould().haveSimpleNameNotContaining("And")
        .andShould().haveSimpleNameNotContaining("Manager")
        .andShould().haveSimpleNameNotContaining("Processor")
        .as("Domain classes should follow SRP");

@ArchTest
static final ArchRule no_god_classes =
    noClasses()
        .that().resideInAPackage("..service..")
        .should().dependOnMoreThan(10Classes())
        .as("No God classes in service layer");
```

- **Metric SonarQube**:
  - **Cognitive Complexity**: >15 → tín hiệu vi phạm SRP
  - **LCOM4**: >1 → class có thể được chia
  - **Số lượng dependency**: >10 → tiềm năng God Class
  - **Kích thước class**: >500 dòng → xem xét lại cho SRP

- **Dependency Graph**: JDepend hoặc IntelliJ IDEA Dependency Matrix. Nếu một class kết nối đến mọi thứ — đó là God Class.

- **Quy Tắc Code Review**: Nếu bạn không thể giải thích mục đích của class trong 10 giây — nó cần refactoring.

### Best Practices Cho Highload

- **Cohesion > Kích Thước**: Class nhỏ ≠ SRP. Class lớn ≠ vi phạm SRP. Nhìn vào cohesion, không phải kích thước.
- **Data Locality**: Trong highload, nhóm theo pattern truy cập, không chỉ theo domain. Dữ liệu được đọc cùng nhau nên ở cùng nhau (cache locality).
- **Tránh Chia Sớm**: Đừng chia một class cho đến khi bạn thấy các thay đổi thực sự từ các bên liên quan khác nhau. Nguyên tắc YAGNI ("You Aren't Gonna Need It") cũng áp dụng cho SRP.
- **Dùng Command/Query Separation (CQS)** (tách các phương thức thay đổi trạng thái khỏi các phương thức chỉ đọc dữ liệu): Tách các class thay đổi trạng thái khỏi các class chỉ đọc. Đây là một cách chia trách nhiệm tự nhiên.

### Xu Hướng Tương Lai

- **Java 21 Record**: Record là SRP tự nhiên cho dữ liệu. Trách nhiệm duy nhất của chúng là lưu trữ dữ liệu bất biến. `equals`, `hashCode`, `toString` — tự động sinh, không tính là trách nhiệm riêng biệt.
- **Module System (JPMS)**: Các module Java 9+ giúp thực thi SRP ở tầng package. `exports` và `requires` chính thức hóa ranh giới trách nhiệm.
- **AI-assisted Refactoring**: Các IDE hiện đại (IntelliJ IDEA với AI Assistant) gợi ý tự động trích xuất trách nhiệm từ các class lớn dựa trên phân tích sử dụng trường và phương thức.

## Tóm Tắt

- SRP nói về **ranh giới trách nhiệm**, không phải kích thước class.
- Một class nên là một **hộp đen** cho một nhiệm vụ cụ thể.
- Cohesion nội bộ cao là dấu hiệu của SRP đúng đắn.
- Tin vào trực giác của bạn: nếu một class cảm thấy "bẩn" và "cồng kềnh" — nó có thể đúng là như vậy.
- Một class — một lý do để thay đổi.

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- 5 test SRP: Đặt Tên (không có "và"), Thay Đổi (ai là bên liên quan?), Dependency (import), Mocking (<5), LCOM4
- LCOM4: đồ thị chia thành N thành phần → chia thành N class; LCOM4 = 1 — single responsibility
- Yếu tố xã hội: "Một class — một team developer"; team khác nhau = trách nhiệm khác nhau
- Kích thước không quyết định SRP: 30 dòng có thể làm 3 việc, 300 dòng — một việc phức tạp
- Dependency Count > 10+ = tiềm năng God Class
- Cross-cutting Concerns (logging, metrics) — giải quyết qua AOP/decorator, đừng trộn với business logic
- Cohesion > Kích thước: nhìn vào cohesion, không phải kích thước

**Các câu hỏi phụ thường gặp:**
- **JVM "nhìn thấy" vi phạm SRP như thế nào?** — Object lớn = ô nhiễm cache line (200 byte, 20 dùng), lãng phí bộ nhớ
- **Anemic Domain Model và SRP là gì?** — Chỉ getter/setter — không phải vi phạm SRP, nhưng logic chuyển sang God Service
- **Class Explosion có xấu không?** — Không, IDE xử lý được 10,000+ file; hãy sợ một file 10,000 dòng
- **Data Locality trong highload?** — Nhóm theo pattern truy cập: dữ liệu đọc cùng nhau nên ở cùng nhau

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Class nhỏ nghĩa là SRP được tuân thủ" (30 dòng có thể làm 3 việc không liên quan)
- "Một phương thức public = SRP" (một phương thức có thể ủy quyền cho 10 subsystem)
