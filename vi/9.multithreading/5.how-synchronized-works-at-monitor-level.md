# How does synchronized work at monitor level? (synchronized hoạt động ở mức monitor như thế nào?)

---

## Junior Level

### Hiểu biết cơ bản

`synchronized` là một từ khóa trong Java đảm bảo thread safety thông qua việc khóa (locking). Chỉ một thread có thể thực thi code bên trong một synchronized block tại một thời điểm.

**Cơ chế:** chỉ một thread có thể vào một synchronized block tại một thời điểm. Các thread khác chờ (bị park qua OS). Khi thread đầu tiên ra — một trong các thread đang chờ được cấp quyền truy cập.

### Hai cách sử dụng

#### 1. synchronized method

```java
public class Counter {
    private int count = 0;

    // Khóa toàn bộ method trên object 'this'
    public synchronized void increment() {
        count++;
    }
}
```

#### 2. synchronized block

```java
public class Counter {
    private int count = 0;
    private final Object lock = new Object();

    public void increment() {
        synchronized(lock) { // Chỉ khóa block này
            count++;
        }
    }
}
```

### Cái gì bị khóa?

| Loại                              | Object bị khóa                    |
| --------------------------------- | --------------------------------- |
| `synchronized` method của instance| `this` (object hiện tại)          |
| `static synchronized` method      | `ClassName.class` (object class)  |
| block `synchronized(this)`        | `this` (object hiện tại)          |
| block `synchronized(lock)`        | Object `lock`                     |

### Ví dụ đơn giản: Tài khoản ngân hàng

```java
public class BankAccount {
    private double balance = 0;

    public synchronized void deposit(double amount) {
        balance += amount; // Chỉ một thread tại một thời điểm
    }

    public synchronized void withdraw(double amount) {
        if (balance >= amount) {
            balance -= amount;
        }
    }

    public synchronized double getBalance() {
        return balance;
    }
}
```

### wait() và notify()

```java
public class ProducerConsumer {
    private final List<Integer> queue = new ArrayList<>();
    private final int MAX_SIZE = 10;

    public synchronized void produce(int value) throws InterruptedException {
        while (queue.size() == MAX_SIZE) {
            wait(); // Chờ tới khi có chỗ trống
        }
        queue.add(value);
        notifyAll(); // Thông báo cho các consumer
    }

    public synchronized int consume() throws InterruptedException {
        while (queue.isEmpty()) {
            wait(); // Chờ tới khi có dữ liệu
        }
        int value = queue.remove(0);
        notifyAll(); // Thông báo cho các producer
        return value;
    }
}
```

## Middle Level

### Sự tiến hóa trạng thái khóa

JVM (HotSpot) không phải lúc nào cũng dùng khóa nặng. Có **4 trạng thái**:

### 1. No Lock

Object không bị khóa. Mark Word (object header) chứa:
- Identity hashcode
- Age (cho GC)

### 2. Biased Locking — ĐÃ GỠ BỎ ở Java 21

Nếu một object chỉ được acquire bởi một thread, JVM ghi nhớ thread đó:

```
Mark Word: [Thread ID: 54 bits] [Epoch: 2] [Age: 4] [Bias: 1] [01]
```

- Thread vào synchronized mà không cần các thao tác CAS
- Chỉ kiểm tra: "có phải ID của tôi trong header không?" → có → vào
- **Vấn đề**: khi một thread thứ hai xuất hiện, khóa phải bị revoke (thu hồi) — đắt

### 3. Thin Lock (lightweight lock)

Khi có tranh chấp:

```
Mark Word: [Thread ID: 54 bits] [Lock Record: 6 bits] [00]
```

- **CAS** (Compare-And-Swap) được dùng để acquire

  CAS (Compare-And-Swap) — một thao tác atomic: "ghi giá trị mới chỉ khi current == expected". Dùng để acquire thin lock mà không cần OS blocking. Chi tiết — trong [[9. What is CAS (Compare-And-Swap)]].

- Thread không ngủ — nó **spin** (lặp vòng, chờ đợi)

  Spinning (spin-waiting) — thread lặp trong một vòng rỗng, kiểm tra xem có thể acquire khóa không. Nhanh hơn parking (không chuyển quyền điều khiển cho OS), nhưng tiêu tốn CPU.

- Nhanh khi tranh chấp thấp

### 4. Fat Lock (heavyweight lock)

Khi tranh chấp cao:

```
Mark Word: [Object Monitor Pointer: 62 bits] [10]
```

- Một `ObjectMonitor` được tạo trong native memory
- Thread bị **park** qua OS (futex trong Linux)

  Thread parking — thread "ngủ" và không tiêu tốn CPU cho tới khi OS đánh thức nó (khi khóa được giải phóng). Rẻ hơn spinning cho các lần chờ dài, nhưng đắt hơn cho các lần chờ ngắn (context switch).

- Chuyển sang trạng thái **BLOCKED**
- Đắt (~1000+ ns do context switch)

### Thuật toán acquire khóa

```

         │

    Đây có phải Biased Lock?
    │ có          │ không
    ▼             ▼

          Thin Lock   Spin thành công?
                      │ có   │ không
                      ▼      ▼
                    Vào    Park (Fat Lock)
```

### Bytecode: monitorenter / monitorexit

```java
synchronized(obj) {
    // vùng critical
}
```

Dịch thành bytecode:

```
0: aload_1          // Nạp obj
1: dup              // Nhân đôi cho astore
2: astore_2         // Lưu cho monitorexit
3: monitorenter     // === ACQUIRE MONITOR ===
4: ...              // Vùng critical
N: aload_2
N+1: monitorexit    // === RELEASE (lối ra bình thường) ===
N+2: goto end
N+3: astore_3       // Trình xử lý exception
N+4: aload_2
N+5: monitorexit    // === RELEASE (khi có exception) ===
N+6: aload_3
N+7: athrow
end: return
```

**Quan trọng:** Với các method `synchronized`, bytecode KHÔNG chứa monitorenter/monitorexit. Thay vào đó, header của method có cờ `ACC_SYNCHRONIZED`, thứ JVM xử lý tự động.

### Adaptive Spinning

HotSpot JVM không chỉ spin trong một vòng lặp. Nó ghi nhớ lịch sử:

- Nếu spinning đã thành công trên monitor này lần trước → spin lâu hơn
- Nếu không → park thread ngay lập tức

Điều này cải thiện đáng kể hiệu năng cho các khóa tồn tại ngắn.

#### Cấu trúc ObjectMonitor (C++)

### Các tối ưu hóa của trình biên dịch JIT

#### Lock Coarsening

```java
// Code nguồn:
synchronized(lock) { sb.append("a"); }
synchronized(lock) { sb.append("b"); }
synchronized(lock) { sb.append("c"); }

// JIT gộp thành một khóa:
synchronized(lock) {
    sb.append("a");
    sb.append("b");
    sb.append("c");
}
```

Điều này giảm overhead của việc acquire/release monitor.

#### Lock Elision (qua Escape Analysis)

```java
public String buildString() {
    Object lock = new Object(); // Object không escape khỏi method
    synchronized(lock) {
        // JIT hiểu: không ai khác có thể lấy được lock
        // → loại bỏ hoàn toàn khóa này khỏi machine code!
        return "result";
    }
}
```

Escape Analysis xác định:
- Object không được trả về từ method
- Object không được truyền vào các method khác
- Object không được lưu vào các static field

### Hiệu năng và tải cao (Highload)

#### Benchmark (xấp xỉ)

| Kịch bản                    | Thời gian                                                                                                | Ghi chú                  |
| --------------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------ |
| Không khóa                  | ~1 ns                                                                                                   | Thao tác cơ bản          |
| synchronized không tranh chấp | ~10-20 ns                                                                                             | Thin lock, không tranh chấp |
| synchronized có tranh chấp  | ~1000-5000 ns (phụ thuộc JVM, CPU, OS, tải — tập trung vào bậc độ lớn, không phải con số chính xác)     | Fat lock + context switch |
| Biased locking (deprecated) | ~5 ns                                                                                                   | Chỉ một thread           |

#### Các yếu tố ảnh hưởng hiệu năng

1. **Contention Level** — bao nhiêu thread cạnh tranh
2. **Lock Hold Time** — khóa được giữ bao lâu
3. **Lock Frequency** — nó được acquire thường xuyên như thế nào
4. **Number of Locks** — bao nhiêu khóa khác nhau

#### Khuyến nghị cho Highload

```java
// XẤU: Global lock
private static final Object globalLock = new Object();
public void process(Request r) {
    synchronized(globalLock) { // Mọi request tuần tự!
        handle(r);
    }
}

// TỐT: Segmented lock
private final Object[] locks = new Object[16];
public void process(Request r) {
    int segment = r.userId() % 16;
    synchronized(locks[segment]) { // Song song theo segment
        handle(r);
    }
}

// TỐT HƠN: Lock-free
private final ConcurrentHashMap<Integer, Data> map = new ConcurrentHashMap<>();
public void process(Request r) {
    map.compute(r.userId(), (k, v) -> handle(r, v)); // Lock-free
}
```

### Chẩn đoán

#### Java Flight Recorder (JFR)

```bash
java -XX:StartFlightRecording=filename=recording.jfr MyApp
```

Các event:
- `jdk.JavaMonitorEnter` — thời gian chờ khóa
- `jdk.ThreadPark` — thời gian trong park()

#### `-XX:+PrintFlagsFinal`

```bash
java -XX:+PrintFlagsFinal -version | grep -i lock
```

Các cờ chính:
- `UseBiasedLocking` (gỡ bỏ ở Java 21)
- `PreBlockSpin` / `SpinBackoffMultiplier`

#### jstack

```bash
jstack <pid>
```

Tìm:
```
"thread-1" #10 BLOCKED (on object monitor)
  - waiting to lock <0x000000076af0c8d0>
  - locked <0x000000076af0c8e0>
```

### Best Practices

1. **Giảm thiểu các synchronized block** — chỉ vùng critical
2. **Dùng private final Object lock** — đóng gói
3. **Tránh synchronized mức class** — `synchronized(ClassName.class)`
4. **Cân nhắc Lock Coarsening** — đừng phân mảnh khóa không cần thiết
5. **Cho Highload** — dùng ConcurrentHashMap, LongAdder, Atomic*
6. **Giám sát tranh chấp** qua JFR — thời gian tăng dần = vấn đề
7. **Với Java < 15: tắt biased locking trong các hệ thống tải cao** (`-XX:-UseBiasedLocking`). Với Java 15+, nó đã bị tắt mặc định.

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- 4 trạng thái khóa: No Lock → Biased (gỡ bỏ ở Java 21) → Thin Lock (CAS + spinning) → Fat Lock (ObjectMonitor)
- Bytecode của synchronized block: monitorenter/monitorexit; synchronized method: cờ ACC_SYNCHRONIZED
- Hai monitorexit được sinh ra — cho lối ra bình thường và cho exception (`finally` ẩn)
- Adaptive Spinning: JVM ghi nhớ lịch sử — nếu spinning đã thành công, spin lâu hơn
- Lock Coarsening: JIT gộp các khóa nhỏ trên cùng một object thành một khóa lớn
- Lock Elision: JIT loại bỏ khóa nếu Escape Analysis cho thấy object không "escape"
- Fat Lock = context switch qua OS (futex trong Linux), ~1000-5000 ns

**Các câu hỏi phụ thường gặp:**
- **Tại sao một synchronized method không chứa monitorenter?** — JVM xử lý cờ ACC_SYNCHRONIZED tự động khi gọi method
- **Lock Record là gì?** — Một cấu trúc trên stack của thread với một bản sao của Mark Word; dùng trong Thin Lock mà không tạo ObjectMonitor
- **JVM quyết định park hay spin như thế nào?** — Adaptive Spinning: nhìn vào lịch sử spin thành công trên monitor này
- **Khi nào JIT sẽ loại bỏ synchronized?** — Khi Escape Analysis cho thấy NoEscape: object không được trả về, không được truyền, không được lưu

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Synchronized luôn tạo ObjectMonitor" — không, chỉ khi tranh chấp cao (Fat Lock)
- "Biased Locking được bật trong Java hiện đại" — không, gỡ bỏ ở Java 21
- "Một monitorexit cho mỗi synchronized block" — không, hai: cho lối ra bình thường và cho exception
- "Lock Elision hoạt động cho synchronized(this)" — hiếm khi, vì `this` gần như luôn "escape"
