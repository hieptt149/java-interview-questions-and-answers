# What is Lost Update? (Lost Update là gì?)

## 🟢 Junior Level

**Lost Update** là một hiện tượng bất thường trong đó các thay đổi được thực hiện bởi một transaction bị ghi đè bởi một transaction khác, và bản cập nhật đầu tiên bị mất vĩnh viễn.

**Điểm then chốt:** cả hai transaction không chỉ đọc mà còn GHI. Lần ghi cuối cùng xóa sạch kết quả của lần đầu tiên.

**Ví dụ minh họa đơn giản:** Hai biên tập viên cùng lúc chỉnh sửa một tài liệu. Biên tập viên A sửa 5 lỗi và nhấn "Save". Biên tập viên B sửa 3 lỗi khác và nhấn "Save". File chỉ lưu các thay đổi của B — các thay đổi của A bị mất.

**Ví dụ SQL:**

```sql
-- Giá trị ban đầu: balance = 1000

-- Transaction 1: cộng +500
BEGIN;
SELECT balance FROM accounts WHERE id = 1;    -- đọc 1000
-- (tính toán: 1000 + 500 = 1500)

-- Transaction 2: trừ -200
BEGIN;
SELECT balance FROM accounts WHERE id = 1;    -- cũng đọc 1000
-- (tính toán: 1000 - 200 = 800)

-- Transaction 1:
UPDATE accounts SET balance = 1500 WHERE id = 1;  -- ghi 1500
COMMIT;

-- Transaction 2:
UPDATE accounts SET balance = 800 WHERE id = 1;   -- ghi đè thành 800!
COMMIT;

-- Kết quả: balance = 800. Khoản +500 bị mất!
```

**Vấn đề then chốt:** Cả hai transaction đều đọc **cùng** một giá trị và ghi kết quả tính toán **của riêng mình**, ghi đè lên nhau.

**Isolation level nào bảo vệ:**
| Level            | Lost Update có thể xảy ra? |
| ---------------- | --------------------- |
| Read Uncommitted | Có                   |
| Read Committed   | Có                   |
| Repeatable Read  | Tùy DBMS       |
| Serializable     | Không                    |

**Khi nào điều này quan trọng:** Số dư tài khoản, counter, kho hàng, mọi thao tác "read-modify-write".

## 🟡 Middle Level

### Cách Nó Hoạt Động Nội Bộ

Lost Update không trực tiếp là vấn đề của isolation level, mà là vấn đề của pattern **read-modify-write**. Nó xảy ra khi:

1. Transaction A đọc giá trị X
2. Transaction B đọc giá trị X (cùng snapshot)
3. Transaction A tính giá trị mới và ghi nó
4. Transaction B tính giá trị của nó và **ghi đè** lên kết quả của A

Ở level **Read Committed**, điều này xảy ra một cách tự nhiên vì mỗi SELECT thấy dữ liệu đã commit mới nhất. Ở **Repeatable Read** trong PostgreSQL, khả năng thấp hơn (nhờ snapshot MVCC), nhưng vẫn có thể xảy ra trong một số kịch bản nhất định.

### Các Kịch Bản Thực Tế

**Kịch bản 1: Cập Nhật Tài Khoản Qua API**
```java
// Không có bảo vệ — Lost Update chắc chắn xảy ra khi có request đồng thời
@Transactional
public void deposit(Long accountId, BigDecimal amount) {
    Account account = accountRepo.findById(accountId);   // đọc balance = 1000
    account.setBalance(account.getBalance().add(amount)); // 1000 + 500 = 1500
    accountRepo.save(account);                            // ghi 1500
}
// Hai lệnh gọi deposit(500) song song có thể ra kết quả 1500 thay vì 2000
```

**Kịch bản 2: Bộ Đếm Lượt Xem**
```java
@Transactional
public void incrementViews(Long articleId) {
    Article article = articleRepo.findById(articleId);     // views = 99
    article.setViews(article.getViews() + 1);              // 99 + 1 = 100
    articleRepo.save(article);                              // ghi 100
}
// 100 request song song có thể ra 101 thay vì 199
```

### Các Lỗi Thường Gặp

| Lỗi                                                   | Hậu quả                                      | Giải pháp                                       |
| --------------------------------------------------------- | ------------------------------------------------ | ---------------------------------------------- |
| Read-modify-write không có lock                            | Lost update khi có truy cập đồng thời                | `SELECT ... FOR UPDATE` hoặc optimistic locking  |
| Giả định @Transactional bảo vệ khỏi lost update          | Transaction != bảo vệ khỏi các lần ghi đồng thời | Dùng `@Version` hoặc pessimistic lock             |
| Retry optimistic lock không giới hạn                        | Vòng lặp retry vô tận dưới contention cao        | Thêm `maxRetries` và fallback                  |
| UPDATE không có WHERE version = ?                           | Bỏ qua optimistic locking                       | Luôn dùng version trong điều kiện            |

### So Sánh Các Cách Tiếp Cận Bảo Vệ

| Cách tiếp cận                        | Cơ chế                  | Ưu điểm                             | Nhược điểm                                           |
| ------------------------------- | -------------------------- | --------------------------------- | ---------------------------------------------- |
| `SELECT ... FOR UPDATE`         | Pessimistic lock           | Đơn giản, bảo vệ được đảm bảo | Lock, deadlock, giảm throughput         |
| `@Version` (optimistic)         | Kiểm tra version khi ghi     | Không lock, tốc độ cao             | Retry khi xung đột, không phù hợp với hot-spot  |
| UPDATE nguyên tử (`SET x = x + 1`) | Một query duy nhất không cần đọc  | Hiệu năng tối đa              | Chỉ dùng cho các thao tác đơn giản, không validate được      |
| Isolation Serializable          | Serialization đầy đủ         | Bảo vệ khỏi mọi hiện tượng bất thường    | Serialization failure, throughput thấp         |

### Khi Nào KHÔNG Nên Dùng Pessimistic Locking

- **Contention cao** trên một bản ghi duy nhất (counter, leader) — tỷ lệ deadlock tăng theo cấp số nhân
- **Workload đọc nặng** — 95%+ query là đọc, lock trở nên dư thừa
- **Microservice với eventual consistency** — lock không mở rộng theo chiều ngang

### Khi Nào KHÔNG Nên Dùng Optimistic Locking (@Version)

**Đừng dùng optimistic locking (@Version):**
- Với các bản ghi hot-spot (counter, queue) — contention >20%, retry vô tận
- Với các transaction tài chính có bất biến nghiêm ngặt — logic retry làm phức tạp code

## 🔴 Senior Level

### Hiện Thực Nội Bộ: MVCC, Các Loại Lock Và Write Skew

> **Các thuật ngữ:**
> - **Write Skew** — hai transaction đọc dữ liệu chồng lấn, ra quyết định dựa trên những gì đã đọc, và ghi kết quả vi phạm một bất biến.
> - **HOT update (Heap Only Tuple)** — một update không thay đổi các cột được đánh index, nên PostgreSQL cập nhật dòng mà không cần cập nhật index.
> - **EvalPlanQual** — cơ chế của PG: khi có UPDATE đồng thời, đọc lại dòng và kiểm tra xem nó có còn thỏa mãn điều kiện WHERE trong phiên bản mới không.

#### PostgreSQL MVCC Ngăn Chặn (Và Không Ngăn Chặn) Lost Update Như Thế Nào

```
PostgreSQL Read Committed (mặc định):
  Mỗi SELECT thấy snapshot đã commit mới nhất
  T1: SELECT balance → 1000 (snapshot tại thời điểm T1)
  T2: SELECT balance → 1000 (snapshot tại thời điểm T2, đã thấy T1 đã commit nếu T1 đã commit)

  Nếu T1 và T2 chạy song song (chưa transaction nào commit):
  T1: SELECT balance → 1000
  T2: SELECT balance → 1000 (MVCC: xmax = 0, dòng chưa bị xóa)
  T1: UPDATE balance = 1500 → tạo phiên bản dòng mới (tuple mới, xmin = T1)
  T2: UPDATE balance = 800 → CHỜ (T1 chưa commit, dòng bị khóa)
  T1: COMMIT → T2 tiếp tục, thấy phiên bản dòng mới
  T2: UPDATE balance = 800 → ghi đè! Lost Update!
```

**Nhận định then chốt:** Ở Read Committed, PostgreSQL **KHÔNG** ngăn Lost Update cho pattern read-modify-write, vì sau khi chờ lock, T2 đọc lại dòng (nhưng không nhất thiết thấy thay đổi của T1 nếu logic nằm ở cấp độ application).

#### Pessimistic Locking: Chi Tiết Nội Bộ Của Row-Level Lock

```sql
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
```

**Điều gì xảy ra bên trong:**
1. PostgreSQL đặt một `ExclusiveLock` trên tuple (dòng)
2. Các transaction khác cố gắng `SELECT ... FOR UPDATE` hoặc `UPDATE` bị chặn
3. Lock được lưu trong shared memory của `LockManager` (~200 byte mỗi lock)
4. Khi deadlock: PostgreSQL chọn nạn nhân dựa trên chi phí transaction (ít công việc hơn → bị abort)

**Phát hiện deadlock:**
```
PostgreSQL chạy deadlock detector mỗi deadlock_timeout (mặc định 1 giây)
Thuật toán: xây dựng wait-for graph, tìm kiếm các chu trình
Độ phức tạp: O(V + E) với V = số transaction, E = số lần chờ
```

#### Optimistic Locking: Hiện Thực @Version

```java
@Entity
public class Account {
    @Id
    private Long id;

    private BigDecimal balance;

    @Version
    private Long version;  // Hibernate thêm WHERE version = ?
}
```

**SQL được sinh ra:**
```sql
-- Hibernate khi save():
UPDATE accounts
SET balance = ?, version = version + 1
WHERE id = ? AND version = ?;

-- Nếu rows_affected == 0 → OptimisticLockException
```

**Cơ chế nội bộ trong Hibernate:**
1. Khi load entity: đọc version hiện tại
2. Khi flush: sinh UPDATE với `WHERE version = old_version`
3. Nếu `executeUpdate() == 0`: một transaction khác đã sửa đổi dòng
4. Hibernate ném `OptimisticLockException` (hoặc `StaleObjectStateException`)

### Đánh Đổi Về Kiến Trúc (Trade-off)

**Cách A: SQL nguyên tử (SET balance = balance + ?)**
- ✅ Ưu điểm: Không lost update, throughput tối đa (50K+ TPS), không lock
- ❌ Nhược điểm: Chỉ dùng cho các thao tác đơn giản, không thể validate, không có audit trail
- Phù hợp cho: counter, tăng/giảm đơn giản

**Cách B: Optimistic Locking (@Version)**
- ✅ Ưu điểm: Không lock, hành vi xác định, dễ hiện thực
- ❌ Nhược điểm: Retry khi có contention (tỷ lệ abort 5-30% dưới tải cao), không hoạt động tốt cho hot-spot
- Phù hợp cho: CRUD với contention vừa phải (cập nhật profile, thay đổi cấu hình)

**Cách C: Pessimistic Locking (SELECT ... FOR UPDATE)**
- ✅ Ưu điểm: Bảo vệ được đảm bảo, đơn giản, hoạt động tốt cho logic nghiệp vụ phức tạp
- ❌ Nhược điểm: Deadlock, throughput giảm 3-10 lần, nguy cơ cạn kiệt connection pool
- Phù hợp cho: các transaction tài chính với contention thấp

**Cách D: Event Sourcing / CQRS**
- ✅ Ưu điểm: Không lost update (append-only), audit trail đầy đủ, mở rộng theo chiều ngang
- ❌ Nhược điểm: Độ phức tạp, eventual consistency, cần event store
- Phù hợp cho: các hệ thống tải cao với yêu cầu audit

### Các Trường Hợp Biên Và Đặc Biệt

**1. Lost Update Với Composite Key:**
```java
// UPDATE có thể bị "mất" nếu điều kiện WHERE không duy nhất
UPDATE accounts SET balance = ? WHERE user_id = ? AND currency = 'USD';
// Nếu hai request đến đồng thời, cả hai tìm thấy cùng dòng, nhưng UPDATE là nguyên tử
// Tuy nhiên, read-modify-write TRƯỚC UPDATE đã bị hỏng rồi
```

**2. Hibernate First-Level Cache Và Lost Update:**
```java
@Transactional
public void updateAccount(Long id, BigDecimal amount) {
    Account a1 = repo.findById(id);      // được load vào L1 cache
    Account a2 = repo.findById(id);      // trả về cùng object từ L1 cache!

    // Nếu một transaction khác thay đổi DB giữa hai lần gọi findById,
    // cả a1 và a2 đều sẽ hiển thị giá trị cũ
    a1.setBalance(a1.getBalance().add(amount));
    repo.save(a1);  // Có thể ghi đè lên thay đổi của người khác
}
```

**3. Write Skew (Lost Update Tinh Vi):**
```sql
-- ràng buộc bác sĩ trực: phải có ít nhất 1 bác sĩ trực
-- T1: SELECT COUNT(*) FROM doctors WHERE on_call = true;  → 2
-- T2: SELECT COUNT(*) FROM doctors WHERE on_call = true;  → 2
-- T1: UPDATE doctors SET on_call = false WHERE name = 'Alice';  → giờ là 1
-- T2: UPDATE doctors SET on_call = false WHERE name = 'Bob';    → giờ là 0! Vi phạm ràng buộc
```
Ở Repeatable Read, cả hai SELECT đều trả về 2. Cả hai UPDATE đều thành công. Ràng buộc bị vi phạm. Đây là **Write Skew** — một biến thể của Lost Update.

**4. Lost Update Với Batching:**
```java
// Batch update: cập nhật 1000 bản ghi
@Transactional
public void batchUpdate() {
    List<Account> accounts = repo.findAll();  // snapshot 1
    for (Account a : accounts) {
        a.setBalance(calculate(a));           // tính toán
    }
    repo.saveAll(accounts);                   // flush — có thể ghi đè thay đổi của người khác
}
// Trong khi batch chạy, một transaction khác có thể thay đổi 500 trong 1000 bản ghi
```

**5. Lost Update Qua Secondary Index:**
```sql
-- UPDATE bằng index không duy nhất có thể gây leo thang row lock
UPDATE accounts SET balance = ? WHERE status = 'active';
-- Nếu có 10,000 dòng, PostgreSQL có thể leo thang lên lock cấp trang hoặc cấp bảng
```

### Tác Động Đến Hiệu Năng

| Cách tiếp cận          | Latency (p99)                        | Throughput                                    | Tác động Contention             |
| ----------------- | ------------------------------------ | --------------------------------------------- | ------------------------------ |
| SQL nguyên tử        | 1-3ms                                | 50,000+ TPS                                   | Tối thiểu                      |
| Optimistic Locking| 2-5ms (happy path), 50-200ms (retry) | 30,000 TPS (contention thấp), 5,000 TPS (cao) | Tăng theo cấp số nhân khi retry      |
| Pessimistic Locking| 5-20ms                              | 5,000-10,000 TPS                              | Giảm tuyến tính              |
| Serializable      | 20-100ms                             | 2,000-8,000 TPS                               | Tỷ lệ abort 10-30%             |

**Các con số cụ thể (PostgreSQL 15, 8 core, NVMe, 1M dòng):**
- SQL nguyên tử `SET balance = balance + 1`: ~55,000 TPS
- Optimistic Lock với contention 10%: ~25,000 TPS, trung bình 3 lần retry
- Pessimistic Lock: ~8,000 TPS, tỷ lệ deadlock 0.1% ở 100 kết nối đồng thời
- Serializable: ~5,000 TPS, tỷ lệ serialization failure 15%

### Tác Động Đến Bộ Nhớ

- **Row lock (FOR UPDATE):** ~200 byte mỗi lock trong shared memory. Ở 10,000 lock đồng thời = ~2MB.
- **Hibernate L1 cache:** Một entity ~500-2000 byte. Load 10,000 entity = 5-20MB trong heap.
- **MVCC dead tuple:** Mỗi UPDATE tạo một phiên bản dòng mới. Phiên bản cũ = dead tuple. AutoVacuum xóa chúng, nhưng dưới tần suất update cao → table bloat (tăng 2-5 lần).
- **Retry buffer:** Với optimistic locking, mỗi lần retry cấp phát một transaction context mới. Ở 1000 retry/giây = tỷ lệ cấp phát ~50MB/giây.

### Các Khía Cạnh Concurrency

**Phát hiện Write Skew:**
```
PostgreSQL Serializable: theo dõi các phụ thuộc RW
  T1: đọc {doctors WHERE on_call = true}
  T2: đọc {doctors WHERE on_call = true}
  T1: ghi (update Alice)
  T2: ghi (update Bob)

  Đồ thị phụ thuộc:
    T1 → đọc → predicate P → T2 ghi vào P
    T2 → đọc → predicate P → T1 ghi vào P

  Phát hiện chu trình → serialization failure → một transaction bị abort
```

### Tình Huống Thực Tế Trong Production

**Tình huống:** Sàn giao dịch tiền mã hóa (2023), xử lý lệnh (order).

**Vấn đề:** Dưới biến động cao (5000 lệnh/giây), số dư người dùng bị mất đồng bộ. Tổng số dư không khớp với tổng số tiền nạp — $2M "biến mất" trong 30 phút.

**Nguyên nhân gốc rễ:**
```java
@Transactional  // Read Committed theo mặc định
public void executeOrder(Long userId, BigDecimal amount) {
    User user = userRepo.findById(userId);       // balance = 10,000
    // Xử lý lệnh...
    user.setBalance(user.getBalance().subtract(amount));  // 10,000 - 500 = 9,500
    userRepo.save(user);
}
```

Ở 5000 lệnh/giây, nhiều transaction đọc cùng số dư, trừ số tiền của mình, và ghi kết quả. Transaction cuối cùng ghi đè lên tất cả các transaction trước đó.

**Giải pháp (nhanh):** SQL nguyên tử:
```java
@Modifying
@Query("UPDATE User u SET u.balance = u.balance - :amount WHERE u.id = :userId AND u.balance >= :amount")
int subtractBalance(@Param("userId") Long userId, @Param("amount") BigDecimal amount);

// Trả về số dòng bị ảnh hưởng — nếu 0, nghĩa là không đủ tiền
```

Tại sao SQL nguyên tử hoạt động? `SET balance = balance - amount` thực thi trong một bước: DBMS đọc giá trị hiện tại và ghi ngay giá trị mới. Không có cửa sổ nào giữa đọc và ghi để một transaction khác có thể xen vào.

**Giải pháp (dài hạn):** Event Sourcing với ledger append-only:
```java
// Thay vì cập nhật balance — INSERT một transaction
@Transactional
public void executeOrder(Long userId, BigDecimal amount) {
    // Kiểm tra bằng cách tính tổng tất cả các transaction (chậm hơn nhưng chính xác hơn)
    BigDecimal currentBalance = ledgerRepo.sumByUser(userId);
    if (currentBalance.compareTo(amount) < 0) {
        throw new InsufficientFundsException();
    }
    ledgerRepo.save(new LedgerEntry(userId, amount.negated(), "ORDER"));
    // Balance = tổng của tất cả các bản ghi, không có lost update
}
```

**Tác động:**
- Trước: $2M lost update trong 30 phút
- Sau (SQL nguyên tử): 0 lost update, throughput 8,000 TPS
- Sau (event sourcing): 0 lost update, throughput 5,000 TPS, audit trail đầy đủ

### Giám Sát Và Chẩn Đoán

**PostgreSQL — phát hiện các pattern lost update:**
```sql
-- Kiểm tra xung đột cập nhật
SELECT
    schemaname,
    relname,
    n_tup_upd,
    n_tup_hot_upd,  -- HOT update = tốt (không cập nhật index)
    n_dead_tup,     -- Dead tuple từ lost update
    last_autovacuum
FROM pg_stat_user_tables
WHERE relname = 'accounts';

-- Các transaction chạy dài (cửa sổ nguy cơ cho lost update)
SELECT pid, now() - xact_start AS duration, query
FROM pg_stat_activity
WHERE state = 'active'
ORDER BY duration DESC;
```

**Hibernate — Lỗi Optimistic Lock:**
```java
@EntityListener
public class OptimisticLockMonitor {
    @PostUpdate
    public void onUpdate(Object entity) {
        // Log các xung đột version
    }
}

// Bộ đếm Micrometer
Counter.builder("hibernate.optimistic_lock.failures")
    .tag("entity", "Account")
    .register(meterRegistry);
```

### Best Practices Cho Highload

1. **Dùng SQL nguyên tử cho counter và số dư:** `UPDATE table SET counter = counter + 1` thay vì read-modify-write.
2. **Optimistic locking cho contention vừa phải:** Thêm exponential backoff với jitter cho retry.
3. **Pessimistic locking chỉ cho các luồng quan trọng:** Giảm thiểu thời gian giữ FOR UPDATE.
4. **Partitioning để giảm hot-spot:** Chia các bảng có update thường xuyên (ví dụ: theo hash của user_id).
5. **Event Sourcing cho các hệ thống tài chính:** Ledger append-only loại bỏ lost update ở cấp độ kiến trúc.
6. **Tránh các transaction chạy dài:** Transaction càng dài, cửa sổ cho lost update càng lớn.
7. **Giám sát dead tuple:** AutoVacuum thường xuyên, cấu hình `autovacuum_vacuum_threshold` cho các bảng update nhiều.

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Lost Update — hai transaction đọc cùng giá trị, cả hai đều sửa đổi và ghi, kết quả đầu tiên bị ghi đè bởi kết quả thứ hai
- Đây là vấn đề của pattern read-modify-write, không phải vấn đề của một isolation level cụ thể
- Giải pháp: SQL nguyên tử (`SET balance = balance + 1`), SELECT FOR UPDATE, optimistic locking (@Version), Serializable
- PostgreSQL ở Read Committed KHÔNG ngăn lost update cho read-modify-write ở cấp độ application
- Event Sourcing / ledger append-only loại bỏ hoàn toàn lost update ở cấp độ kiến trúc
- Write Skew — một biến thể của lost update: hai transaction đọc dữ liệu chồng lấn và vi phạm một bất biến

**Các câu hỏi phụ thường gặp:**
- SQL nguyên tử ngăn lost update như thế nào? — Một bước duy nhất: DBMS đọc và ghi nguyên tử, không có cửa sổ để xen vào
- Pessimistic locking khác gì với optimistic? — Pessimistic khóa trước, optimistic kiểm tra version khi ghi
- Khi nào nên dùng Event Sourcing? — Các hệ thống tài chính có yêu cầu audit, các hệ thống tải cao
- Write Skew là gì? — Hai transaction đọc cùng dữ liệu, cả hai sửa đổi — bất biến bị vi phạm (ví dụ: bác sĩ trực)

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "@Transactional bảo vệ khỏi lost update" — transaction != bảo vệ khỏi các lần ghi đồng thời
- "Optimistic locking luôn tốt hơn pessimistic" — với hot-spot, optimistic = retry vô tận
- "Lost Update = vấn đề của isolation level" — đây là vấn đề của pattern read-modify-write
