# How to organize communication between microservices (Cách tổ chức giao tiếp giữa các microservice)

## 🟢 Junior Level

Microservices giao tiếp theo hai cách chính:

**1. Đồng bộ (HTTP/gRPC):**
```
Service A → HTTP request → Service B → HTTP response → Service A
```

**2. Bất đồng bộ (Kafka/RabbitMQ):**
```
Service A → message đến Queue → Service B lấy khi sẵn sàng
```

---

## 🟡 Middle Level

### Giao Tiếp Đồng Bộ

**REST:**
```java
@RestController
public class OrderController {
    private final UserServiceClient userService;

    @GetMapping("/orders/{id}")
    public Order getOrder(@PathVariable Long id) {
        Order order = orderRepository.findById(id);
        User user = userService.getUser(order.userId());
        return new Order(order, user);
    }
}
```

**gRPC:**
```protobuf
service UserService {
    rpc GetUser (UserRequest) returns (UserResponse);
}
```

### Giao Tiếp Bất Đồng Bộ

**Kafka:**
```java
@KafkaListener(topics = "user-events")
public void onUserEvent(UserEvent event) {
    if (event.type() == USER_CREATED) {
        userRepository.save(event.toUser());
    }
}
```

### Các Lỗi Thường Gặp

1. **Cascading failure:**
```
Service A → B → C → D
D sập → C sập → B sập → A sập
Giải pháp: Circuit Breaker, Timeout
```

## 🔴 Senior Level

### Đánh Đổi Kiến Trúc

### Khi Nào KHÔNG Nên Dùng Giao Tiếp Đồng Bộ

- **Chuỗi gọi dài** (A→B→C→D) — nguy cơ cascade failure
- **Các tác vụ nền** (gửi email, tạo report)
- **Tải cao** — bất đồng bộ đệm tốt hơn cho các đợt tăng traffic

| Đồng bộ                                                                 | Bất đồng bộ           |
| --------------------------------------------------------------------------- | ---------------------- |
| Đơn giản hơn: một HTTP call → response, không có overhead broker/serialization.        | Fault-tolerant hơn    |
| Nhanh hơn cho các trường hợp đơn giản: không có overhead broker/serialization.                  | Tốt hơn cho scaling         |
| Coupling tạm thời                                                           | Tách rời                 |
| Cascading failure                                                          | Eventual consistency   |

### Kinh Nghiệm Production

**API Composition:**
```java
// thenCombine — kết hợp hai future, chờ cả hai.
// join() — chặn cho đến khi có kết quả (giống get(), nhưng không có checked exception).
// Nếu một future thất bại — toàn bộ pipeline CompletableFuture thất bại.
@GetMapping("/dashboard/{userId}")
public CompletableFuture<Dashboard> getDashboard(@PathVariable Long userId) {
    CompletableFuture<User> user = userService.getUserAsync(userId);
    CompletableFuture<List<Order>> orders = orderService.getOrdersAsync(userId);
    CompletableFuture<List<Notification>> notifications =
        notificationService.getNotificationsAsync(userId);

    return user.thenCombine(orders, (u, o) ->
        new Dashboard(u, o, notifications.join()));
}
```

### Best Practices

```
✅ Async cho các event
✅ Sync cho các request dữ liệu
✅ Circuit Breaker cho các call sync
✅ Idempotency cho các message async

❌ Chuỗi gọi dài
❌ Không có timeout và retry
❌ Không có xử lý lỗi
```

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- Hai cách tiếp cận: đồng bộ (HTTP/gRPC) và bất đồng bộ (Kafka/RabbitMQ)
- Đồng bộ: đơn giản hơn, response tức thì, nhưng nguy cơ cascade failure
- Bất đồng bộ: fault-tolerant hơn, mở rộng được, nhưng eventual consistency
- API composition: kết hợp kết quả từ nhiều service (CompletableFuture.thenCombine)
- Circuit Breaker là bắt buộc cho các call sync
- Idempotency là bắt buộc cho các message async
- KHÔNG dùng đồng bộ cho các chuỗi dài (A→B→C→D), các tác vụ nền, tải cao

**Các câu hỏi phụ thường gặp:**
- **REST vs gRPC?** REST đơn giản hơn, gRPC nhanh hơn (protobuf), contract nghiêm ngặt hơn.
- **Kafka vs RabbitMQ?** Kafka — log persistent, replay, throughput cao hơn. RabbitMQ — routing linh hoạt, thiết lập dễ hơn.
- **Cách tránh cascade failure?** Circuit Breaker, Timeout, Retry — cho sync; queue async — cho nền.
- **API composition là gì?** Truy vấn nhiều service song song, kết hợp kết quả (thenCombine).

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Đồng bộ luôn tốt hơn, nó đơn giản hơn" — không, nguy cơ cascade failure
- "Bất đồng bộ cho mọi thứ" — không, khó debug hơn, eventual consistency
- "Chuỗi A→B→C→D→E là thực hành bình thường" — không, cascade failure chắc chắn xảy ra
- "Không cần idempotency cho Kafka" — cần, việc gửi trùng lặp có thể xảy ra
