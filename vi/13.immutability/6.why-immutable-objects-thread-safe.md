# Why are immutable objects thread-safe? (Tại sao immutable object thread-safe?)

---

## Basic Level

Immutable object thread-safe vì một race condition đòi hỏi ít nhất một lần ghi và một lần đọc. Nếu không có lần ghi nào sau khi tạo — race condition là không thể xảy ra về mặt vật lý.

```java
public final class Config {
    private final String url;
    private final int timeout;

    public Config(String url, int timeout) {
        this.url = url;
        this.timeout = timeout;
    }

    public String getUrl() { return url; }
    public int getTimeout() { return timeout; }
    // Không có setter — không ai có thể thay đổi trạng thái
}
```

Object này có thể được truyền an toàn giữa các thread — không cần `synchronized` hay `Lock`.

### Quan Trọng: Tính Bất Biến ≠ Thread-Safe Cho Các Tham Chiếu

Một immutable object an toàn để đọc từ nhiều thread. Nhưng nếu trường của nó tham chiếu đến một object mutable — object đó cần được bảo vệ riêng.

---

## Intermediate Level

### Sự Vắng Mặt Của Race Condition

Một Race Condition xảy ra khi các thread đồng thời đọc và ghi cùng dữ liệu. Một immutable object không cho phép ghi — xung đột ghi là không thể xảy ra về mặt vật lý.

### Các Đảm Bảo Của Java Memory Model Cho Các Trường Final

Ngay cả khi object không thay đổi, vẫn có nguy cơ thấy nó ở trạng thái khởi tạo một phần. Từ khóa `final` ngăn điều này:

- Ở cuối constructor, một sự **"đóng băng" (freeze)** của tất cả các trường `final` xảy ra
- Bất kỳ thread nào nhận được tham chiếu đến object sau khi constructor hoàn thành sẽ thấy tất cả các trường `final` đã được khởi tạo
- Bộ xử lý và compiler không thể sắp xếp lại các lệnh sao cho tham chiếu trở nên khả dụng trước khi các trường `final` được thiết lập

### Copy-On-"Modification"
```java
public final class Counter {
    private final int value;

    public Counter(int value) { this.value = value; }

    public Counter increment() {
        return new Counter(this.value + 1); // object mới
    }
}
```

## Advanced Level

### Ngữ Nghĩa Freeze Và Memory Barrier

JLS (Java Language Specification) §17.5 đảm bảo: sau khi constructor hoàn thành, tất cả các trường `final` hiển thị với bất kỳ thread nào. Điều này được đảm bảo bởi một **memory barrier** ở cuối constructor, cái mà:

1. Cấm việc sắp xếp lại các lệnh vượt qua barrier
2. Đảm bảo visibility của tất cả các trường `final`
3. Tạo **publish an toàn (safe publication)** mà không cần `volatile` hoặc synchronization

### Object vs Reference

Quan trọng cần phân biệt tính bất biến của bản thân object với tính bất biến của tham chiếu đến nó:
```java
public class Service {
    private ImmutableObject data = new ImmutableObject("v1"); // Tham chiếu là mutable!

    public void update(String val) {
        this.data = new ImmutableObject(val); // Không thread-safe nếu không có volatile/final
    }
}
```
Bản thân `ImmutableObject` thread-safe, nhưng tham chiếu `data` thì không. Các thread khác có thể thấy tham chiếu cũ từ cache của chúng.

### Các Pattern Sử Dụng
- **Copy-On-Write** — `CopyOnWriteArrayList` dựa vào tính bất biến của mảng
- **Value Object** trong DDD — các immutable object để truyền dữ liệu giữa các tầng
- **Actor / Event Sourcing** — mỗi event là bất biến, trạng thái được tính toán lại

### Tóm Tắt Cho Advanced
- Thread-safety = **không có mutation** + **các đảm bảo JMM** cho các trường `final`
- Tính bất biến loại bỏ overhead synchronization — truy cập lock-free loại bỏ contention giữa các thread, cái mà dưới contention cao có thể giảm throughput 50-90%.
- Luôn dùng `final` để publish các immutable object
- Với các tham chiếu mutable đến các immutable object, dùng `volatile` hoặc `AtomicReference`

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Race condition không thể xảy ra — không có lần ghi nào sau khi tạo object
- Các trường `final` đảm bảo publish an toàn — JLS §17.5, freeze ở cuối constructor
- Memory barrier ở cuối constructor cấm việc sắp xếp lại lệnh
- Tính bất biến ≠ thread-safe cho các tham chiếu: tham chiếu đến object có thể là mutable
- Pattern Copy-On-Write — `CopyOnWriteArrayList` dựa vào tính bất biến của mảng
- Với các tham chiếu mutable: `volatile` hoặc `AtomicReference`

**Các câu hỏi phụ thường gặp:**
- *Tại sao không cần synchronized?* — Không có ghi = không có cạnh tranh dữ liệu
- *Freeze trong JMM là gì?* — Memory barrier ở cuối constructor, đảm bảo visibility trường final
- *Một thread có thể thấy một object được tạo một phần không?* — Không có trường final — có; có final — không (publish an toàn)
- *Điều gì nếu tham chiếu đến một immutable object là mutable?* — Cần `volatile` hoặc `AtomicReference` để thay thế an toàn

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tất cả các object không có setter đều thread-safe" — các trường mutable bên trong vẫn nguy hiểm
- "synchronized làm cho một object bất biến" — đó là về synchronization, không phải tính bất biến
- "Các trường final có thể bị thay đổi qua reflection" — trong Java 16+ điều này bị chặn cho java.base
- "Immutable object = tham chiếu thread-safe" — bản thân tham chiếu có thể là mutable
