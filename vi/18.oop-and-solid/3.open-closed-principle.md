# What is Open-Closed Principle? (Open-Closed Principle là gì?)

## 🟢 Junior Level

**Open-Closed Principle (OCP)** là một trong năm nguyên tắc SOLID, nói rằng: **"Các thực thể phần mềm nên mở để mở rộng, nhưng đóng để sửa đổi.**

**Giải thích:** Thực thể phần mềm = class, module, function. "Đóng để sửa đổi" = đừng thay đổi code đã được test và hoạt động. Thay vào đó — thêm các class/module mới. "Mở để mở rộng" = chức năng mới có thể được thêm mà không sửa đổi code hiện có.".

Nói đơn giản hơn: bạn nên có thể thêm chức năng mới vào hệ thống mà không thay đổi code đã tồn tại và đang hoạt động.

**Analogy đơn giản:** Hãy nghĩ về một smartphone với cổng USB. Bạn có thể kết nối các thiết bị mới (tai nghe, USB, bàn phím) mà không cần mở hoặc sửa đổi chính chiếc điện thoại.

**Ví dụ vi phạm OCP:**
```java
// Xấu: thêm một hình dạng mới yêu cầu sửa đổi phương thức này
public double calculateArea(Object shape) {
    if (shape instanceof Circle) {
        Circle c = (Circle) shape;
        return Math.PI * c.radius * c.radius;
    } else if (shape instanceof Rectangle) {
        Rectangle r = (Rectangle) shape;
        return r.width * r.height;
    }
    // Loại hình dạng mới — cần sửa đổi phương thức này!
    throw new IllegalArgumentException("Unknown shape");
}
```

**Ví dụ tuân thủ OCP:**
```java
// Tốt: mỗi class biết diện tích của chính nó
public interface Shape {
    double calculateArea();
}

public class Circle implements Shape {
    private double radius;
    @Override
    public double calculateArea() {
        return Math.PI * radius * radius;
    }
}

public class Rectangle implements Shape {
    private double width;
    private double height;
    @Override
    public double calculateArea() {
        return width * height;
    }
}

// Code client — KHÔNG THAY ĐỔI khi thêm hình dạng mới
public double calculateTotalArea(List<Shape> shapes) {
    return shapes.stream().mapToDouble(Shape::calculateArea).sum();
}
```

**Khi nào dùng:**
- Luôn luôn khi hệ thống được kỳ vọng mở rộng với các loại, định dạng, quy tắc mới
- Khi thiết kế API, thư viện, plugin
- Khi tạo business logic sẽ thay đổi theo thời gian

## 🟡 Middle Level

### Cách Hoạt Động

OCP dựa vào hai cơ chế chính:

1. **Abstraction (interface, abstract class)**: code client phụ thuộc vào abstraction, không phải vào một triển khai cụ thể
2. **Polymorphism**: các triển khai mới có thể được thay thế mà không thay đổi code client

### Cách Phát Hiện Vi Phạm OCP

**Dấu hiệu vi phạm:**

1. **Chuỗi `if-else` hoặc `switch` theo loại object**: mỗi loại mới yêu cầu thêm một nhánh mới
2. **Sửa đổi thường xuyên trong các module ổn định**: code lẽ ra phải "đóng băng" liên tục bị sửa
3. **Regression bug**: các thay đổi cho tính năng mới phá vỡ chức năng cũ
4. **Kiểm tra `instanceof` thô** — dấu hiệu vi phạm OCP. Ngoại lệ — pattern matching với `sealed interface` (Java 21+), nơi compiler đảm bảo tính đầy đủ của tất cả các biến thể.

> Pattern Matching với sealed interface khả dụng từ Java 21. Với Java 8/11, hãy dùng pattern Strategy.

### Ứng Dụng Thực Tế

**Pattern Strategy cho OCP:**
```java
// Vi phạm OCP: phương thức với nhiều điều kiện
public class PaymentService {
    public void processPayment(String type, BigDecimal amount) {
        if ("credit_card".equals(type)) {
            processCreditCard(amount);
        } else if ("paypal".equals(type)) {
            processPayPal(amount);
        } else if ("crypto".equals(type)) {
            processCrypto(amount);
        }
        // Phương thức thanh toán mới — sửa đổi code hiện có!
    }
}

// Tuân thủ OCP: strategy
public interface PaymentStrategy {
    void process(BigDecimal amount);
}

public class CreditCardPayment implements PaymentStrategy {
    @Override
    public void process(BigDecimal amount) { /* logic */ }
}

public class PaymentService {
    private final Map<String, PaymentStrategy> strategies;

    public PaymentService(List<PaymentStrategy> strategyList) {
        this.strategies = strategyList.stream()
            .collect(Collectors.toMap(
                s -> s.getClass().getSimpleName(),
                s -> s
            ));
    }

    public void processPayment(String type, BigDecimal amount) {
        PaymentStrategy strategy = strategies.get(type);
        if (strategy == null) {
            throw new IllegalArgumentException("Unknown payment type: " + type);
        }
        strategy.process(amount);
    }
}
```

### Các Lỗi Thường Gặp

1. **Lỗi**: Tạo một interface "cho tương lai" cho một class chỉ có một triển khai
   **Giải pháp**: Tuân theo YAGNI — thêm abstraction khi triển khai thứ hai hoặc nhu cầu thực xuất hiện

2. **Lỗi**: Lạm dụng inheritance thay vì composition
   **Giải pháp**: Ưu tiên composition — nó mang lại tính linh hoạt hơn

3. **Lỗi**: OCP chỉ ở một cấp độ (mở rộng service, nhưng không mở rộng repository)
   **Giải pháp**: Áp dụng nguyên tắc nhất quán trên toàn bộ kiến trúc

### Khi Nào KHÔNG Nên Tuân Thủ OCP Nghiêm Ngặt

- Các ứng dụng CRUD đơn giản với tập thao tác cố định
- Prototype và MVP (xác thực giả thuyết nhanh)
- Code chắc chắn sẽ không được mở rộng (tiện ích, bộ chuyển đổi định dạng)

## 🔴 Senior Level

### Triển Khai Nội Bộ Và Kiến Trúc

OCP không chỉ là "dùng interface". Đó là một nguyên tắc **quản lý rủi ro thay đổi**. Bertrand Meyer, người đã đưa ra OCP vào năm 1988, có ý sau:

> *Một module là "đóng" khi nó sẵn sàng để các module khác sử dụng. Nó là "mở" khi nó vẫn sẵn sàng để mở rộng (các hành vi mới có thể được định nghĩa trong nó).*

Ở cấp độ Senior, quan trọng là phải hiểu: OCP không áp dụng cho mọi class, mà cho **các điểm mở rộng quan trọng về mặt kiến trúc**.

### Đánh Đổi Kiến Trúc

**Tuân thủ OCP nghiêm ngặt:**
- ✅ Ưu điểm: Bug regression tối thiểu, mở rộng dễ dàng, API ổn định, phát triển song song
- ❌ Nhược điểm: Nhiều abstraction hơn, độ phức tạp thiết kế ban đầu, tải nhận thức

**Tuân thủ OCP vừa phải:**
- ✅ Ưu điểm: Cân bằng giữa đơn giản và linh hoạt, ít boilerplate hơn
- ❌ Nhược điểm: Yêu cầu phán đoán trưởng thành, nguy cơ tích lũy nợ kỹ thuật dần dần

### Edge Cases

1. **Lạm Dụng Abstraction**: Không cần tạo một interface cho mọi class. Nếu một class chỉ có một triển khai — một interface có thể là phức tạp không cần thiết (vi phạm YAGNI)

2. **Các mở rộng phụ thuộc lẫn nhau**: Khi một tính năng mới yêu cầu thay đổi trong 3+ tầng (controller → service → repository)
   - **Giải pháp**: Thiết kế trước các "điểm mở rộng" ở cấp độ API/contract

3. **Inheritance vs Composition**: Inheritance tạo ra coupling cứng nhắc. Composition với delegation — linh hoạt
   - **Quy tắc**: Ưu tiên composition, inheritance — chỉ cho các mối quan hệ "is-a" thực sự

### Hiệu Năng

- **Virtual method dispatch**: Gọi một phương thức thông qua một interface thêm sự gián tiếp. JVM thực hiện **inline caching** và **devirtualization**, giảm thiểu overhead
- **Startup time**: Số lượng lớn các class/interface nhỏ làm chậm khởi động nhẹ (tải metadata, classloading)
- **Tối ưu JIT**: Càng nhiều triển khai cụ thể của một interface, JIT càng khó chọn chiến lược inlining tối ưu. Với > 2-3 triển khai, một **megamorphic call** có thể xảy ra — suy giảm hiệu năng đáng kể. Khi một interface có 3+ triển khai, JVM không thể tối ưu lệnh gọi. Thay vì gọi trực tiếp (1-2 ns), một tra cứu bảng xảy ra (~10-20 ns).

### Kinh Nghiệm Production

**Kịch bản production thực tế:**

Trong một dự án tài chính, có một hệ thống tính phí với logic hardcode cho 3 loại khách hàng. Khi vào một thị trường mới (10+ quốc gia), cần 6 tháng refactoring:

1. Trích xuất interface `FeeCalculator`
2. Tạo `PercentageFeeCalculator`, `TieredFeeCalculator`, `FlatFeeCalculator`
3. Triển khai một factory dựa trên cấu hình

**Kết quả**: Thêm một quốc gia mới giảm từ 2 tuần xuống 2 ngày (chỉ cần cấu hình + một class mới).

### Monitoring Và Chẩn Đoán

**Cách phát hiện vi phạm OCP trong code:**

1. **Các metric code**:
   - Số nhánh `if-else` / `switch` theo loại > 3
   - Tần suất thay đổi file (> 5 lần sửa/tháng trong một module ổn định)
   - Số kiểm tra `instanceof`

2. **Công cụ**:
   - SonarQube (Cognitive Complexity, Number of Branches)
   - Git history (`git log --follow -- <file>` — sửa thường xuyên = vi phạm OCP)
   - ArchUnit (kiểm tra kiến trúc trên các dependency)

3. **Dấu hiệu CI/CD**:
   - Bug regression khi thêm tính năng mới
   - Code review dài do diff lớn trong các class ổn định

### Best Practices Cho Highload

- **Plugin Architecture**: Thiết kế hệ thống như core + plugin. Core ổn định, plugin mở rộng
- **Specification Pattern**: Cho business logic phức tạp, dùng kết hợp specification thay vì if-else
- **Event-Driven Extension**: Thay vì gọi trực tiếp, dùng event — các handler mới đăng ký mà không sửa đổi publisher

### Mối Quan Hệ Với Các Nguyên Tắc Khác

- **OCP ← SRP**: Khi một class có một trách nhiệm, dễ mở rộng hơn mà không cần sửa đổi
- **OCP → LSP**: Các triển khai mới phải thay thế đúng cách abstraction
- **OCP → ISP**: Các interface nhỏ dễ mở rộng hơn
- **OCP → DIP**: Phụ thuộc vào abstraction là nền tảng cho OCP

### Tóm Tắt Cho Senior

- OCP là về **giảm rủi ro**, không phải vẻ đẹp kiến trúc
- Áp dụng OCP cho **các điểm mở rộng**, không phải cho mọi class
- Nhớ về **JIT megamorphic call** — quá nhiều triển khai interface làm suy giảm hiệu năng
- Dùng cách tiếp cận **Event-Driven** cho coupling lỏng lẻo của các mở rộng
- OCP không có nhu cầu mở rộng thực sự là **over-engineering**

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- OCP: các class mở để mở rộng, đóng để sửa đổi
- Dấu hiệu vi phạm chính — chuỗi `if-else` / `switch` theo loại object
- Pattern Strategy — công cụ chính để tuân thủ OCP
- OCP dựa vào abstraction (interface) và polymorphism
- Megamorphic call: với >2-3 triển khai interface, JIT mất tối ưu
- OCP áp dụng cho các điểm mở rộng, không phải cho mọi class
- Pattern matching với sealed interface (Java 21+) — lựa chọn thay thế hợp pháp cho Strategy

**Các câu hỏi phụ thường gặp:**
- **Cách phát hiện vi phạm OCP?** — Kiểm tra `instanceof`, sửa thường xuyên trong các module ổn định, bug regression
- **Khi nào KHÔNG cần OCP?** — CRUD với các thao tác cố định, prototype, code sẽ không được mở rộng
- **Megamorphic call là gì?** — Khi một interface có 3+ triển khai, JVM không thể tối ưu lệnh gọi (10-20 ns thay vì 1-2 ns)
- **OCP và Plugin Architecture?** — Core ổn định, plugin mở rộng thông qua SPI/ServiceLoader

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Cần tạo một interface cho mọi class cho tương lai" (vi phạm YAGNI)
- "OCP nghĩa là code không thể thay đổi chút nào" (không thể sửa đổi cái đang hoạt động, nhưng có thể mở rộng)
- "Switch luôn xấu" (cho các hierarchy đóng với sealed interface — chấp nhận được)
