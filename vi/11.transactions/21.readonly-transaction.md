# What is readonly transaction? (Readonly transaction là gì?)

## 🟢 Junior Level

**Readonly transaction** là một transaction có cờ `readOnly = true`, báo cho Spring và cơ sở dữ liệu: "Tôi sẽ chỉ đọc dữ liệu, không sửa đổi."

### Cách Sử Dụng

```java
@Service
public class UserService {

    @Transactional(readOnly = true)
    public User findById(Long id) {
        return userRepository.findById(id).orElse(null);
    }
}
```

### Ví Dụ Minh Họa

Giống như một khóa "chỉ đọc" trên một tài liệu — bạn có thể xem và sao chép, nhưng không thể thay đổi bản gốc.

### Tại Sao Nó Cần Thiết

1. **Tối ưu hóa**: Hibernate vô hiệu hóa dirty checking — cơ chế mà khi flush, so sánh các entity với snapshot của chúng để xác định dòng nào cần UPDATE. Với readOnly = true, Hibernate không flush các UPDATE.
2. **An toàn**: Việc ghi ngoài ý muốn sẽ gây ra lỗi
3. **Cơ sở dữ liệu**: Một số DBMS áp dụng các tối ưu hóa cho các transaction chỉ đọc

### Pattern Phổ Biến

Đánh dấu toàn bộ service là readOnly, sau đó ghi đè các method ghi:

```java
@Service
@Transactional(readOnly = true)  // readOnly theo mặc định
public class UserService {

    public User findById(Long id) { ... }  // readOnly = true

    @Transactional  // Ghi đè — KHÔNG readOnly
    public void update(User user) { ... }
}
```

### Khi Nào KHÔNG Nên Đặt readOnly = true

1. **Method có thể ghi** — ngay cả khi nó không ghi bây giờ, các thay đổi tương lai có thể thêm các thao tác ghi. Khi đó bạn sẽ phải thay đổi annotation.
2. **Transaction chứa cả đọc và ghi** — readOnly trên toàn bộ method sẽ phá vỡ phần ghi.
3. **Dùng Sequence** — `nextval()` = ghi, readOnly sẽ chặn nó.

## 🟡 Middle Level

### Các Tối Ưu Hóa Ở Cấp Độ Hibernate

Với `readOnly = true`:
- **FlushMode.MANUAL**: Hibernate vô hiệu hóa dirty checking tự động
- **Bộ nhớ**: Hibernate có thể bỏ qua việc lưu trữ các snapshot object (về lý thuyết, tùy phiên bản)

### Các Tối Ưu Hóa Ở Cấp Độ JDBC Và DBMS

| DBMS       | Nó làm gì                                                                                                                                                                                                                                              |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PostgreSQL | `SET TRANSACTION READ ONLY` — tối ưu hóa execution plan                                                                                                                  |
| MySQL      | Có thể định tuyến đến replica — nếu AbstractRoutingDataSource hoặc một framework như Hibernate Shards được cấu hình. readOnly tự nó không định tuyến, phụ thuộc vào cấu hình routing.      |
| Oracle     | Read consistency ở cấp độ transaction, tránh các lock không cần thiết                                                                                                               |

### Các Tối Ưu Hóa — Cái Nào Thực Sự Hoạt Động

| Tối ưu hóa                         | Có hoạt động?              | Hiệu quả                         |
| ------------------------------------ | ------------------- | ------------------------------------- |
| Vô hiệu hóa dirty checking của Hibernate    | ✅ Có               | Đáng kể với các object lớn         |
| DB tối ưu hóa execution plan          | ⚠️ Tùy DBMS   | Nhỏ trong PostgreSQL, rõ rệt hơn trong Oracle |
| Định tuyến Read-Replica                 | ⚠️ Cần cấu hình    | Phụ thuộc vào hạ tầng             |
| Không đặt lock                         | ✅ Có               | Tùy DBMS                       |

### Các Lỗi Thường Gặp

| Lỗi                              | Điều gì xảy ra                                                        | Cách khắc phục                                  |
| ------------------------------------ | ------------------------------------------------------------------- | ------------------------------------------- |
| readOnly trên method ghi             | `PSQLException: cannot execute UPDATE in a read-only transaction`   | Ghi đè `readOnly = false`                 |
| Kỳ vọng exception khi dùng setter       | Hibernate không ném exception — chỉ đơn giản là không flush              | Hiểu rằng readOnly ≠ tính bất biến          |
| readOnly không áp dụng cho connection   | Connection từ pool đã được dùng cho việc ghi                        | Spring chỉ đặt readOnly trên connection mới |
| Sửa đổi entity trong readOnly      | Setter hoạt động, nhưng thay đổi không được lưu                                 | Không phải bug — FlushMode.MANUAL               |

### Khi Nào KHÔNG Nên Dùng readOnly

| Tình huống                          | Tại sao                                    | Giải pháp thay thế                           |
| ---------------------------------- | -------------------------------------- | ------------------------------------- |
| Method đọc và ghi            | readOnly chặn việc ghi                 | Transaction thông thường                   |
| Các query không trạng thái (`JdbcTemplate`) | Dù sao cũng không có dirty checking của Hibernate     | Không dùng `@Transactional`              |
| SELECT rất ngắn theo ID            | Overhead mở transaction > lợi ích | Không có transaction hoặc không có `@Transactional` |

### So Sánh: readOnly vs Không Có Transaction

| Khía cạnh               | `readOnly = true`          | Không có `@Transactional`       |
| -------------------- | -------------------------- | ------------------------------ |
| Dirty checking       | Bị vô hiệu hóa                   | Không có session                     |
| Định tuyến read replica | Có thể                   | Không                             |
| Snapshot nhất quán  | Được đảm bảo (trong tx)     | Mỗi query — snapshot riêng      |
| Overhead             | Thấp                        | Tối thiểu                         |

## 🔴 Senior Level

### readOnly Của Hibernate — Hành Vi Nội Bộ

#### Thay Đổi FlushMode

```java
// Khi readOnly = true, Spring đặt:
session.setFlushMode(FlushMode.MANUAL);

// Điều này có nghĩa:
// - Không tự động flush trước khi thực thi query
// - Không tự động flush khi commit transaction
// - flush() có thể được gọi thủ công
```

**Tác Động Đến Dirty Checking:**

```java
@Transactional(readOnly = true)
public User findById(Long id) {
    User user = em.find(User.class, id);
    user.setName("changed");  // Không có exception!
    // Nhưng thay đổi KHÔNG được lưu — flush là MANUAL
    return user;
}
```

Hibernate **không ném exception** khi có sửa đổi trong transaction readOnly — nó chỉ đơn giản không flush. Thay đổi chỉ tồn tại trong L1 cache.

#### Tác Động Đến First-Level Cache

```java
@Transactional(readOnly = true)
public List<User> findAll() {
    // Hibernate không cần theo dõi snapshot cho dirty checking
    // Nhưng các entity vẫn được cache trong L1 (Persistence Context)
    return em.createQuery("SELECT u FROM User u", User.class).getResultList();
}
```

**Tối ưu hóa bộ nhớ**: Về lý thuyết Hibernate có thể bỏ qua việc tạo snapshot. Trong thực tế, hầu hết các phiên bản Hibernate vẫn tạo snapshot — tối ưu hóa chỉ giới hạn ở hành vi flush.

### Cờ readOnly Của JDBC

```java
// Spring đặt điều này trên connection
connection.setReadOnly(true);
```

**Các DBMS khác nhau làm gì:**

#### PostgreSQL
```sql
SET TRANSACTION READ ONLY;
```
- Cấm `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `CREATE`, `ALTER`, `DROP`
- Cho phép `SELECT`, `EXPLAIN`, `SHOW`
- **Ngoại lệ**: Bảng tạm trong một số cấu hình
- **Tối ưu hóa**: Tránh một số lock nội bộ, giảm nhẹ overhead

> Trong PostgreSQL, readOnly = true gửi một gợi ý đến optimizer, nhưng không đảm bảo một transaction chỉ đọc ở cấp độ DBMS. Để thực sự chỉ đọc, dùng `SET TRANSACTION READ ONLY`.

#### MySQL
```java
conn.setReadOnly(true);
```
- Theo mặc định: không có thay đổi ở cấp độ SQL
- Với routing tùy chỉnh: có thể định tuyến đến replica
- HikariCP có thể dùng cho các quyết định routing

#### Oracle
- `setReadOnly(true)` → read consistency ở cấp độ transaction
- Đảm bảo tất cả các query thấy một snapshot
- Cấm bất kỳ thao tác DML nào

### Hiện Thực readOnly Của Spring

```java
// DataSourceTransactionManager.doBegin()
if (definition.isReadOnly()) {
    if (con.isReadOnly()) {
        // Đã chỉ đọc rồi
    } else {
        if (txObject.isNewConnection()) {
            con.setReadOnly(true);
        }
    }
}
```

**Quan trọng:** Spring chỉ đặt `readOnly` trên connection nếu đó là một **connection mới**. Nếu connection được tái sử dụng từ pool và trước đó được dùng cho việc ghi, `readOnly` có thể không được đặt.

### Kiến Trúc Định Tuyến Read-Replica

```java
public class RoutingDataSource extends AbstractRoutingDataSource {

    @Override
    protected Object determineCurrentLookupKey() {
        if (TransactionSynchronizationManager.isCurrentTransactionReadOnly()) {
            return "replica";
        }
        return "master";
    }
}
```

**Cấu hình:**
```java
@Bean
public DataSource dataSource() {
    RoutingDataSource routing = new RoutingDataSource();

    Map<Object, Object> targetDataSources = new HashMap<>();
    targetDataSources.put("master", masterDataSource());
    targetDataSources.put("replica", replicaDataSource());

    routing.setTargetDataSources(targetDataSources);
    routing.setDefaultTargetDataSource(masterDataSource());

    return routing;
}
```

**Cách nó hoạt động:**
1. `@Transactional(readOnly = true)` → Spring đặt cờ thread-local
2. `RoutingDataSource.determineCurrentLookupKey()` kiểm tra cờ
3. Trả về "replica" → query đi đến read replica
4. `@Transactional` (không readOnly) → trả về "master"

### Các Trường Hợp Biên (Tối Thiểu 3)

1. **Sửa đổi trong transaction readOnly**: `user.setName("new")` không ném exception — Hibernate chỉ đơn giản không flush. Nhưng `em.createQuery("UPDATE User ...").executeUpdate()` ném `PSQLException: cannot execute UPDATE in a read-only transaction`. Các sửa đổi entity của Hibernate bị bỏ qua âm thầm, SQL trực tiếp thì ném lỗi.

2. **Ghi đè readOnly không kích hoạt**: `@Transactional(readOnly = true)` cấp độ class + `@Transactional` trên method = `readOnly = false`. Nhưng nếu method **không** có annotation riêng, nó kế thừa `readOnly = true`. Điều này có thể dẫn đến `PSQLException` bất ngờ nếu method gọi một thao tác ghi.

3. **readOnly và Propagation.REQUIRED**: Method readOnly gọi method ghi với `REQUIRED` (mặc định) → method ghi tham gia transaction readOnly → ghi thất bại. Sửa lỗi: method ghi cần `REQUIRES_NEW` cho transaction không-readOnly của riêng nó.

4. **Tái sử dụng connection pool**: Spring chỉ đặt `readOnly` trên connection mới. Nếu connection từ pool trước đó được dùng cho việc ghi, cờ có thể không được đặt. Tùy thuộc vào hiện thực pool và hành vi `resetConnection`.

5. **readOnly với query `@Modifying`**: Query `@Modifying` trong service `readOnly = true` → `TransactionRequiredException`. Repository có `@Transactional` riêng của nó, nhưng tham số của service ghi đè nó.

### Benchmark Tác Động Của readOnly

```
Kịch bản: Lấy 10,000 entity với Hibernate

Cấu hình              | Thời gian (ms) | Bộ nhớ (MB)
---------------------------|-----------|------------
Mặc định                    | 850       | 120
readOnly = true            | 620       | 85
readOnly + stateless session| 450       | 30
```

readOnly mang lại cải thiện thời gian ~27% và tiết kiệm bộ nhớ ~30% cho các thao tác đọc lớn.

### Các Con Số Về Hiệu Năng

| Thao tác                      | Mặc định                       | readOnly                 |
| ------------------------------ | ----------------------------- | ------------------------ |
| Dirty checking (mỗi entity)    | ~0.5 μs                       | 0 (bị vô hiệu hóa)             |
| Tạo snapshot (mỗi entity) | ~1 μs                         | ~1 μs (có thể không bị bỏ qua) |
| Flush khi commit                | ~5-10 ms (cho các entity dirty) | 0 (không cần thiết)           |

### Tác Động Đến Bộ Nhớ

- Transaction readOnly: Hibernate có thể bỏ qua việc tạo snapshot → tiết kiệm bộ nhớ tỷ lệ thuận với số lượng entity
- L1 cache vẫn hoạt động — các entity được load vào Persistence Context
- Với 10,000 entity: tiết kiệm ~35 MB (từ benchmark)
- Stateless session: footprint bộ nhớ tối thiểu, không có L1 cache

### Thread Safety

Cờ readOnly được lưu trong ThreadLocal (`TransactionSynchronizationManager.currentTransactionReadOnly`). Mỗi thread được cô lập. Service singleton thread-safe.

### Câu Chuyện Thực Tế Trong Production

Service reporting với `@Transactional(readOnly = true)` gọi một method `@Modifying` để dọn dẹp dữ liệu tạm thời. Nhận `PSQLException: cannot execute UPDATE in a read-only transaction`. Toàn bộ batch job ban đêm thất bại. Sửa lỗi: việc dọn dẹp được chuyển sang một service riêng biệt với `REQUIRES_NEW`.

**Actuator:** các metric connection pool hiển thị các connection đang hoạt động cho các thao tác đọc so với ghi.

### Best Practices Cho Highload

1. **readOnly trên tất cả các method truy vấn**: Cơ sở cho bất kỳ method nào không ghi. Tiết kiệm từ dirty checking đáng kể cho các tập kết quả lớn.
2. **`readOnly = true` cấp độ class**: Cho các service chỉ đọc — một annotation cho mỗi class.
3. **Định tuyến read replica**: `AbstractRoutingDataSource` + `isCurrentTransactionReadOnly()` = tự động định tuyến đến các replica.
4. **Stateless session cho các tập kết quả lớn**: `Session#doStatelessWork()` — không có L1 cache, bộ nhớ tối thiểu.
5. **Tránh readOnly + ghi trong cùng một tx**: Đừng trộn lẫn. Nếu method đọc và ghi — dùng transaction thông thường.
6. **Giám sát độ trễ replica**: Với định tuyến read replica — độ trễ replica có thể gây ra đọc dữ liệu cũ (stale). Chấp nhận được cho báo cáo, không cho dữ liệu thời gian thực.

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- readOnly = true báo cho Spring và DB: "chỉ đọc, không ghi"
- Hibernate vô hiệu hóa dirty checking (FlushMode.MANUAL) — tiết kiệm ~27% thời gian, ~30% bộ nhớ
- readOnly ≠ tính bất biến: các entity có thể được sửa đổi, nhưng thay đổi không được flush vào DB
- PostgreSQL: SET TRANSACTION READ ONLY — cấm INSERT/UPDATE/DELETE, tối ưu hóa plan
- Định tuyến read replica: AbstractRoutingDataSource + isCurrentTransactionReadOnly() → replica
- SQL trực tiếp (UPDATE/DELETE) trong transaction readOnly ném PSQLException

**Các câu hỏi phụ thường gặp:**
- Hibernate có ném exception khi user.setName() trong readOnly không? — Không, chỉ đơn giản không flush (FlushMode.MANUAL)
- Còn về JPQL UPDATE trong readOnly? — PSQLException: cannot execute UPDATE in a read-only transaction
- Khi nào readOnly không được đặt trên connection? — Nếu connection được tái sử dụng từ pool và trước đó được dùng cho việc ghi
- readOnly + REQUIRED gọi method ghi? — Ghi tham gia transaction readOnly → ghi thất bại

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "readOnly = cấm sửa đổi entity" — setter vẫn hoạt động, chỉ là không flush
- "readOnly luôn định tuyến đến replica" — chỉ khi AbstractRoutingDataSource được cấu hình
- "readOnly = overhead bằng không" — mở transaction vẫn có chi phí
