# What is reachability in the context of GC? (Reachability trong ngữ cảnh của GC là gì?)

## Junior Level

**Reachability (khả năng tiếp cận)** — trạng thái của đối tượng: liệu nó có thể được tiếp cận từ code hay không.

**5 cấp độ:**
1. **Strong** — tham chiếu thông thường (`Object obj = new Object()`)
2. **Soft** — bị loại bỏ khi bộ nhớ thấp
3. **Weak** — bị loại bỏ ở lần thu gom tiếp theo
4. **Phantom** — đối tượng gần như đã bị loại bỏ
5. **Unreachable** — rác

---

## Middle Level

### Các loại Reference

| Loại         | Khi nào bị loại bỏ  | Trường hợp sử dụng |
| ------------ | ------------------- | ------------------ |
| **Strong**   | Không bao giờ       | Các đối tượng nghiệp vụ |
| **Soft**     | Khi có nguy cơ OOM  | Cache              |
| **Weak**     | Ở lần GC tiếp theo  | WeakHashMap        |
| **Phantom**  | Sau khi finalization | Dọn dẹp tài nguyên |

```java
// Soft Reference
SoftReference<Data> ref = new SoftReference<>(data);
Data cached = ref.get();  // null nếu GC đã loại bỏ

// Weak Reference
WeakReference<User> ref = new WeakReference<>(user);
// GC loại bỏ ở lần thu gom gần nhất

// Phantom Reference
PhantomReference<Resource> ref = new PhantomReference<>(resource, queue);
// get() luôn null! Chỉ để theo dõi việc loại bỏ
```

### Cleaner (Java 9+)

```java
// Thay thế cho finalize()
Cleaner cleaner = Cleaner.create();
Cleanable cleanable = cleaner.register(obj, () -> {
    nativeFree(handle);  // Dọn dẹp
    // handle là một con trỏ native (long), lấy được từ JNI/MemorySegment.
    // Cleaner cho phép giải phóng bộ nhớ native mà GC không kiểm soát.
});

cleanable.clean();  // Dọn dẹp thủ công
```

## Senior Level

### Công thức của SoftReference

```
JVM dọn dẹp khi:
  current_time - last_access < free_memory × SoftRefLRUPolicyMSPerMB

Mặc định: 1000 ms cho mỗi MB
  → "9 giờ" — mức tối đa lý thuyết khi có 32 GB trống và policy mặc định.
  → Trong thực tế, các SoftReference bị dọn dẹp sớm hơn nhiều khi tải cao.

Tinh chỉnh: -XX:SoftRefLRUPolicyMSPerMB=100
```

### Reference Handler Thread

```
Luồng hệ thống ưu tiên cao:
  1. GC phát hiện sự thay đổi về reachability
  2. Đối tượng → Pending List
  3. Reference Handler → ReferenceQueue
  4. Ứng dụng poll queue

→ Bất đồng bộ, không chặn GC
```

### Resurrection (Hồi sinh)

```java
// ❌ Trong finalize() bạn có thể hồi sinh một đối tượng
protected void finalize() {
    GlobalCache.add(this);  // Strong reference → đối tượng còn sống!
}

// Cleaner không thể hồi sinh:
// → Lambda KHÔNG có tham chiếu đến this
```

### Best Practices

1. **Strong** = logic nghiệp vụ
2. **Soft** = cache (tinh chỉnh SoftRefLRUPolicyMSPerMB)
3. **Weak** = metadata
4. **Phantom/Cleaner** = các tài nguyên native
5. **Tránh** hồi sinh (resurrection)
6. **ReferenceQueue** để giám sát

### Tóm tắt cho Senior

- **5 cấp độ** của reachability
- **Soft** = cache, dọn dẹp khi có nguy cơ OOM
- **Weak** = lần thu gom tiếp theo
- **Phantom** = theo dõi việc loại bỏ
- **Cleaner** = thay thế cho finalize()
- **Reference Handler** = luồng bất đồng bộ
- **Resurrection** = tai họa về mặt kiến trúc

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- 5 cấp độ reachability: Strong (tham chiếu thông thường), Soft (khi bộ nhớ thấp), Weak (ở lần GC tiếp theo), Phantom (sau finalization), Unreachable (rác)
- SoftReference: cho cache; công thức dọn dẹp: `free_memory × SoftRefLRUPolicyMSPerMB` (mặc định 1000 ms/MB); trên 32 GB — lý thuyết 9 giờ, nhưng thực tế sớm hơn nhiều
- WeakReference: cho WeakHashMap, metadata; được dọn ở lần thu gom TIẾP THEO (không chờ đến khi thiếu bộ nhớ)
- PhantomReference: `get()` luôn null; CHỈ dùng với ReferenceQueue để theo dõi việc loại bỏ; thay thế `finalize()`
- Cleaner (Java 9+): thay thế cho `finalize()`; lambda KHÔNG có tham chiếu đến this → không có "hồi sinh"; `cleanable.clean()` để dọn dẹp thủ công
- Reference Handler: luồng hệ thống ưu tiên cao; GC → Pending List → Reference Handler → ReferenceQueue → ứng dụng poll
- Resurrection: trong `finalize()` bạn có thể gán `this` cho một trường tĩnh → đối tượng "hồi sinh"; Cleaner không thể hồi sinh

**Các câu hỏi phụ thường gặp:**
- **Tại sao SoftReference trên 32 GB có thể sống hàng giờ?** — Công thức: 32 GB × 1000 ms/MB = 9 giờ; tinh chỉnh: `-XX:SoftRefLRUPolicyMSPerMB=100` → tích cực hơn
- **Tại sao PhantomReference.get() luôn trả về null?** — Được thiết kế riêng: đối tượng gần như đã bị loại bỏ, tham chiếu không còn cần nữa; chỉ ReferenceQueue để theo dõi
- **Cleaner tốt hơn finalize() ở điểm nào?** — Lambda của Cleaner KHÔNG có tham chiếu đến this → không thể hồi sinh đối tượng; finalize() có thể gán `this` → hồi sinh
- **Tại sao Reference Handler là bất đồng bộ?** — Không chặn GC; GC đưa đối tượng vào Pending List; Reference Handler xử lý sau → ứng dụng poll ReferenceQueue

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "SoftReference được dọn dẹp ngay sau khi Strong reference bị loại bỏ" — chỉ được dọn dẹp KHI có nguy cơ OOM
- "PhantomReference cho phép lấy được đối tượng" — `get()` luôn null; chỉ ReferenceQueue
- "finalize() là một cách bình thường để dọn dẹp tài nguyên" — bị deprecated (Java 9+), không dự đoán được, có thể hồi sinh đối tượng
