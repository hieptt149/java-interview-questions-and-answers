# How to Implement Thread-Safe Singleton? (Cách triển khai Singleton an toàn với luồng (Thread-Safe)?)

## Junior Level

Nếu hai luồng (thread) cùng lúc kiểm tra `instance == null`, cả hai đều sẽ tạo ra đối tượng riêng của mình — dẫn đến hai instance thay vì một.
Để Singleton hoạt động trong môi trường đa luồng, bạn cần phải bảo vệ việc tạo instance.

**Vấn đề đơn giản:**
```java
// Hai luồng có thể cùng lúc tạo ra hai instance!
if (instance == null) {
    instance = new Singleton();  // Thread 1 và Thread 2 cùng lúc!
}
```

**Cách tiếp cận đơn giản nhất — Enum:**
```java
public enum Singleton {
    INSTANCE;  // JVM đảm bảo chỉ có một instance duy nhất

    public void doWork() {
        System.out.println("Working...");
    }
}

// Cách sử dụng
Singleton.INSTANCE.doWork();
// An toàn với luồng, được bảo vệ khỏi reflection và serialization
```

**Tại sao Enum an toàn:**
- Java cấm việc tạo enum thông qua `new`
- Serialization hoạt động đúng đắn
- Tính đồng thời (Concurrency) được đảm bảo bởi JVM

### Khi nào KHÔNG nên tự triển khai Singleton an toàn với luồng thủ công

Trong các ứng dụng Spring: `@Component` + singleton scope (mặc định) đã tự quản lý việc này rồi.
Trong CDI: `@ApplicationScoped`. Đừng phát minh lại bánh xe.

## Middle Level

### Cách tiếp cận 1: Enum Singleton (Được khuyến nghị)

```java
public enum Singleton {
    INSTANCE;

    private final String config;

    Singleton() {
        this.config = loadConfig();
    }

    public String getConfig() {
        return config;
    }
}
```

**Ưu điểm:**
- An toàn với luồng (JVM)
- Được bảo vệ khỏi reflection
- Được bảo vệ khỏi serialization
- Code đơn giản

**Nhược điểm:**
- Không lười (được tạo ra ngay khi class được load)

### Cách tiếp cận 2: Bill Pugh (Static Holder)

```java
public class BillPughSingleton {
    private BillPughSingleton() {}

    // Inner class chỉ được load khi lần đầu truy cập
    private static class SingletonHolder {
        private static final BillPughSingleton INSTANCE = new BillPughSingleton();
    }

    public static BillPughSingleton getInstance() {
        return SingletonHolder.INSTANCE;
    }

    // Bảo vệ khỏi serialization
    protected Object readResolve() {
        return getInstance();
    }
}
```

**Tại sao nó hoạt động:**
- JVM đảm bảo tính nguyên tử (atomicity) khi khởi tạo trường tĩnh (static field)
- Class `SingletonHolder` chỉ được load khi lần đầu gọi `getInstance()`
- **Khởi tạo lười mà không cần synchronized tường minh — tính an toàn với luồng được đảm bảo bởi cơ chế khóa của ClassLoader (JLS 12.4.2).**

### Cách tiếp cận 3: Double-Checked Locking

```java
public class DclSingleton {
    private static volatile DclSingleton instance;

    private DclSingleton() {
        if (instance != null) {
            throw new IllegalStateException("Already created");
        }
    }

    public static DclSingleton getInstance() {
        DclSingleton local = instance;  // Tối ưu hóa
        if (local == null) {
            synchronized (DclSingleton.class) {
                local = instance;
                if (local == null) {
                    instance = local = new DclSingleton();
                }
            }
        }
        return local;
    }
}
```

**Tại sao cần volatile:**
- Không có volatile, việc tái sắp xếp lệnh (reordering) có thể xảy ra
- Một luồng có thể nhận được tham chiếu đến một đối tượng CHƯA ĐƯỢC KHỞI TẠO ĐẦY ĐỦ
- volatile ngăn chặn việc tái sắp xếp lệnh

Trước Java 5 (JSR-133), Memory Model không đảm bảo happens-before cho volatile, và DCL đã bị lỗi.

### So sánh

| Cách tiếp cận           | Lười (Lazy)        | An toàn với luồng     | Độ phức tạp  |
| ------------------ | ----------- | ------------------ | ----------- |
| **Enum**           | Không          | Đầy đủ              | Tối thiểu     |
| **Bill Pugh**      | Có         | Đầy đủ              | Thấp     |
| **DCL + volatile** | Có         | Đầy đủ              | Cao       |

```java

```

## Senior Level

### Đào sâu về Java Memory Model

**Vấn đề khi không có volatile:**
```java
// instance = new Singleton() bao gồm 3 bước:
// 1. Cấp phát bộ nhớ
// 2. Gọi constructor
// 3. Gán tham chiếu cho instance

// Không có volatile, việc tái sắp xếp có thể xảy ra: 1 -> 3 -> 2
// Thread B thấy instance != null ở bước 3
// Nhưng constructor (bước 2) vẫn chưa được thực thi!
// -> Thread B nhận được một đối tượng với các trường mặc định (default fields)!
```

**Volatile giải quyết vấn đề này:**
```java
// volatile chèn thêm Memory Barrier (rào chắn bộ nhớ):
// StoreStore trước khi ghi vào biến volatile
// LoadLoad sau khi đọc từ biến volatile

// Điều này đảm bảo:
// Tất cả các thao tác ghi trong constructor đều được hoàn thành TRƯỚC KHI tham chiếu được công bố
```

**Tối ưu hóa Local Variable (biến cục bộ):**
```java
public static DclSingleton getInstance() {
    DclSingleton local = instance;  // Đọc volatile MỘT LẦN
    if (local == null) {
        synchronized (DclSingleton.class) {
            local = instance;
            if (local == null) {
                instance = local = new DclSingleton();
            }
        }
    }
    return local;  // Sử dụng biến cục bộ
}

// Không tối ưu hóa: 2 lần đọc volatile (chậm)
// Có tối ưu hóa: 1 lần đọc volatile (nhanh hơn ~25%)
```

### VarHandle (Java 9+)

```java
// Dành cho hiệu năng cực cao
public class VarHandleSingleton {
    private static final VarHandle HANDLE = MethodHandles.lookup()
        .findStaticVarHandle(VarHandleSingleton.class, "instance", VarHandleSingleton.class);

    private static VarHandleSingleton instance;

    public static VarHandleSingleton getInstance() {
        VarHandleSingleton local = (VarHandleSingleton) HANDLE.getAcquire();
        if (local == null) {
            synchronized (VarHandleSingleton.class) {
                local = (VarHandleSingleton) HANDLE.getAcquire();
                if (local == null) {
                    local = new VarHandleSingleton();
                    HANDLE.setRelease(null, local);
                }
            }
        }
        return local;
    }
}

// getAcquire/setRelease rẻ hơn volatile
// Nhưng vẫn đủ cho ngữ nghĩa của DCL
```

### Initialization-on-demand Holder: Cơ chế bên trong

```java
// Cơ chế JVM Class Loading:
// 1. Class được load khi lần đầu truy cập
// 2. Việc khởi tạo trường tĩnh = có tính nguyên tử
// 3. Cơ chế khóa nội bộ của ClassLoader đảm bảo tính an toàn với luồng

// Đây KHÔNG phải là "phép thuật" — đó là JLS (Java Language Specification) 12.4.1:
// "Việc khởi tạo một class bao gồm việc thực thi các static initializer của nó"
// "Ngôn ngữ lập trình Java triển khai đúng đắn việc khởi tạo đa luồng"
```

### Bảo vệ khỏi mọi kiểu tấn công

```java
public class SecureSingleton implements Serializable {
    private static final SecureSingleton INSTANCE = new SecureSingleton();

    private SecureSingleton() {
        if (INSTANCE != null) {
            throw new IllegalStateException("Singleton violation");
        }
    }

    public static SecureSingleton getInstance() {
        return INSTANCE;
    }

    // Bảo vệ khỏi serialization
    private Object readResolve() throws ObjectStreamException {
        return INSTANCE;
    }

    // Bảo vệ khỏi cloning
    @Override
    protected Object clone() throws CloneNotSupportedException {
        throw new CloneNotSupportedException("Singleton cannot be cloned");
    }
}
```

### So sánh hiệu năng

```
Benchmark (10 triệu lần gọi):
  Enum:              10ms  (static final, được JIT tối ưu)
  Bill Pugh:         12ms  (class được load một lần)
  DCL + volatile:    15ms  (chi phí phát sinh khi đọc volatile)
  VarHandle:         11ms  (barrier yếu hơn)
  synchronized:      150ms (chi phí phát sinh cho lock mỗi lần!)
```

### Kinh nghiệm Production

**Tình huống thực tế: DCL không có volatile trong production**
- Ứng dụng đã hoạt động 2 năm mà không gặp vấn đề gì
- Sau khi nâng cấp lên JDK mới → xuất hiện NPE ngẫu nhiên
- Nguyên nhân: JDK đã thay đổi chiến lược tối ưu hóa JIT
- Giải pháp: thêm volatile → vấn đề biến mất

### Best Practices (Thực hành tốt nhất)

1. **Enum** — cho 99% trường hợp (an toàn > tính lười)
2. **Bill Pugh** — khi tính lười là yếu tố quan trọng
3. **DI Container** — trong các ứng dụng Spring (ĐỪNG tự viết thủ công!)
4. **volatile là BẮT BUỘC** trong DCL
5. **Tối ưu hóa biến cục bộ** trong DCL
6. **readResolve()** để bảo vệ khỏi serialization
7. **Kiểm tra trong constructor** để bảo vệ khỏi reflection
8. **VarHandle (Java 9+)** cho hiệu năng cực cao

### Tóm tắt cho Senior

- **JMM:** volatile ngăn chặn việc tái sắp xếp lệnh thông qua Memory Barrier
- **Bill Pugh:** dựa vào các đảm bảo của JLS 12.4.1
- **Enum:** bảo vệ tự nhiên khỏi reflection/serialization
- **Local variable:** giảm 25% số lần đọc volatile
- **VarHandle:** barrier yếu hơn -> nhanh hơn volatile
- **Spring:** ĐỪNG tự viết Singleton — hãy dùng `@Component`
- **DCL không có volatile** = một quả bom nổ chậm

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Enum Singleton — cách tiếp cận được khuyến nghị: an toàn với luồng, được bảo vệ khỏi reflection và serialization
- Bill Pugh (Static Holder) — khởi tạo lười mà không cần synchronized, thông qua static inner class (JLS 12.4.1)
- Double-Checked Locking yêu cầu volatile để ngăn chặn việc tái sắp xếp lệnh
- Tối ưu hóa biến cục bộ trong DCL giúp giảm 25% số lần đọc volatile
- Trong các ứng dụng Spring ĐỪNG tự viết Singleton thủ công — dùng @Component với singleton scope
- VarHandle (Java 9+) cung cấp getAcquire/setRelease — rẻ hơn volatile
- Không có volatile: việc tái sắp xếp 1->3->2 (cấp phát bộ nhớ -> công bố -> constructor) -> đối tượng chưa được khởi tạo đầy đủ

**Các câu hỏi phụ thường gặp:**
- **Tại sao volatile là bắt buộc trong DCL?** — Không có nó, JIT/CPU có thể tái sắp xếp: cấp phát bộ nhớ -> công bố tham chiếu -> gọi constructor
- **Bill Pugh hoạt động như thế nào?** — Nested class chỉ được load khi lần đầu truy cập, JLS đảm bảo việc khởi tạo có tính nguyên tử
- **Enum vs Bill Pugh — nên chọn cái nào?** — Enum nếu không cần tính lười, Bill Pugh nếu tính lười là yếu tố quan trọng
- **Tại sao Spring không yêu cầu Singleton thủ công?** — @Component với singleton scope, + khả năng kiểm thử thông qua DI

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Trong Spring tôi tự viết Singleton thủ công thông qua synchronized" — @Component đã tự quản lý việc này rồi
- "Không cần volatile, nó vẫn hoạt động với tôi" — việc tái sắp xếp chỉ xuất hiện trên các CPU/JDK cụ thể
- "DCL không có volatile vẫn an toàn" — hành vi không xác định (undefined behavior), đặc biệt trên các bộ xử lý ARM
- "Enum không phù hợp với Singleton" — đây là cách tiếp cận được Joshua Bloch khuyến nghị
