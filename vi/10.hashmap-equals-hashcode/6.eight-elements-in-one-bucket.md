# What Happens When 8 Elements Are Reached in One Bucket? (Điều gì xảy ra khi đạt 8 phần tử trong một bucket?)

## 🟢 Junior Level

Khi 8 phần tử rơi vào một bucket, HashMap quyết định tối ưu việc tìm kiếm. Nhưng việc chuyển sang một tree không phải lúc nào cũng xảy ra!

*(Hành vi được mô tả cho Java 8+. Trong Java 7, treeification không tồn tại.)*

**Điều gì xảy ra:**
1. HashMap kiểm tra tổng kích thước table
2. Nếu table có ít hơn 64 bucket — nó **resize table**
3. Nếu table có 64 hoặc nhiều hơn — list chuyển thành một **tree**

**Tại sao:** Resize được ưu tiên hơn treeification: khi table tăng đôi, các phần tử có cùng hashCode trải ra HAI bucket khác nhau (được kiểm tra bằng một bit), thứ có thể loại bỏ va chạm hoàn toàn. Một tree chỉ tối ưu việc tìm kiếm trong một bucket, nhưng không giải quyết va chạm.

**Ví dụ:**
```java
// Kịch bản đầy đủ:
// capacity=16, threshold=12 → 8 phần tử < 12 → resize KHÔNG xảy ra
// Ở phần tử thứ 13 → resize thành 32 → vẫn < 64 → treeification KHÔNG kích hoạt
// Ở phần tử thứ 25 → resize thành 64 → giờ >= 64 → treeification KÍCH HOẠT
```

## 🟡 Middle Level

### Method treeifyBin() và điều kiện 64

```java
if (tab == null || (n = tab.length) < MIN_TREEIFY_CAPACITY)
    resize();  // Tăng table
else {
    // Chuyển đổi tree thực sự
}
```

Các tham số:
- `TREEIFY_THRESHOLD = 8` — trigger để gọi treeifyBin()
- `MIN_TREEIFY_CAPACITY = 64` — kích thước table tối thiểu cho tree
- `UNTREEIFY_THRESHOLD = 6` — chuyển đổi nghịch

### Tại sao chính xác là 8?

Xác suất một bucket với 8 phần tử ở loadFactor 0.75 và một hashCode tốt: **0.00000006** (phân phối Poisson). Sự xuất hiện của 8 phần tử là một bất thường.

### Tại sao khoảng cách giữa 8 và 6? (Hysteresis)

Nếu các ngưỡng là 8 và 7, việc liên tục thêm/xóa phần tử thứ 8 sẽ khiến HashMap tái xây dựng cấu trúc không ngừng. Một khoảng cách 2 đảm bảo sự ổn định.

### Ảnh hưởng tới hiệu năng

| Chỉ số              | List          | Tree                     |
| ------------------- | ------------- | ------------------------ |
| Tìm kiếm (8 phần tử)| 8 so sánh     | 3 so sánh                |
| Tìm kiếm (1024 phần tử) | 1024      | 10                       |
| Chèn                | Nhanh         | Chậm hơn (cân bằng)      |
| Bộ nhớ              | ~32 byte/Node | ~64 byte/TreeNode        |

### Các sai lầm thường gặp

1. **Nghĩ 8 phần tử = luôn là một tree** — còn cần capacity >= 64
2. **Bỏ qua tín hiệu** — 8 va chạm nghĩa là một hashCode() kém

### Treeification là một tín hiệu vấn đề

Nếu bạn thấy treeification trong production — đây không phải "HashMap hoạt động như thiết kế", nó là một chỉ báo của một vấn đề. Hoặc hashCode() của key bị hỏng, hoặc một Hash Flooding Attack đang diễn ra (một kẻ tấn công cố tình tạo va chạm).

## 🔴 Senior Level

### Quá trình chuyển đổi

1. Mọi `Node` được thay bằng `TreeNode`
2. List được chuyển thành một list liên kết đôi (`prev` được thêm)
3. Một cây đỏ-đen được xây dựng với việc cân bằng

**Red-black tree** — một cây nhị phân nơi mỗi node được 'tô màu' đỏ hoặc đen. Các quy tắc tô màu đảm bảo cân bằng: chiều cao của các nhánh trái và phải khác nhau không quá 2x.

**TieBreakOrder** — một cơ chế 'phá hòa': khi hai key có cùng hash và không implement Comparable, Java so sánh qua `System.identityHashCode()` hoặc tên class.

Khi tìm kiếm trong tree:
```java
// 1. So sánh theo hash
// 2. Nếu các hash bằng nhau và key implement Comparable — dùng compareTo()
// 3. Nếu không — tieBreakOrder() qua System.identityHashCode()
```

### TieBreakOrder

Khi các key không implement `Comparable`:
```java
static int tieBreakOrder(Object a, Object b) {
    int d;
    if (a == null || b == null ||
        (d = a.getClass().getName().compareTo(b.getClass().getName())) == 0)
        d = (System.identityHashCode(a) <= System.identityHashCode(b) ? -1 : 1);
    return d;
}
```
Đây là một cơ chế fallback để xây dựng một tree tất định.

### Các đánh đổi kiến trúc

**Tại sao không tạo một tree ngay?**
- TreeNode nặng gấp 2x Node
- Với 2-7 phần tử, một list nhanh hơn (ít overhead hơn)
- Treeification là bảo vệ khỏi các bất thường, không phải một chế độ chuẩn

### Các trường hợp biên (Edge Case)

1. **Multi-threaded resize** — hai thread có thể đồng thời trigger treeification; ConcurrentHashMap giải quyết điều này qua CAS + synchronized trên đầu bucket
2. **null key** — luôn ở `table[0]`, ở 8 null key (không thể xảy ra vì null chỉ có một) — về lý thuyết, một tree cho null không bao giờ được tạo

### Hiệu năng

- Treeification: O(k * log k) cho k phần tử
- Ở 1024 va chạm: tìm kiếm mất 10 thao tác so với 1024 (list) — lợi 100x
- Nhưng chèn chậm đi ~30-50% do cân bằng

### Giám sát Production

Treeification bất thường = chỉ báo vấn đề:
- Kiểm tra `hashCode()` của các key của bạn
- Có thể là một Hash Flooding Attack
- Trong JFR, kiểm tra `HashMap.CollisionRate`

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- TREEIFY_THRESHOLD = 8, MIN_TREEIFY_CAPACITY = 64, UNTREEIFY_THRESHOLD = 6
- Ở 8 phần tử VÀ capacity < 64 — resize, KHÔNG phải tree
- Ở 8 phần tử VÀ capacity >= 64 — treeification (list → cây đỏ-đen)
- Hysteresis (8 → tree, 6 → list) ngăn cấu trúc dội qua dội lại
- TieBreakOrder: nếu các key không phải Comparable — System.identityHashCode() được dùng
- Implement Comparable cho các key tăng tốc treeification
- Treeification trong production = tín hiệu vấn đề (hashCode tồi hoặc tấn công)

**Các câu hỏi phụ thường gặp:**
- **Tại sao resize được ưu tiên hơn tree?** — resize trải các phần tử qua các bucket khác nhau, tree chỉ tối ưu tìm kiếm trong một bucket
- **TieBreakOrder là gì?** — fallback để xây dựng tree khi các key không phải Comparable
- **Một null key có thể tạo một tree không?** — không, null chỉ có một, không có tự va chạm
- **Độ phức tạp của treeification là gì?** — O(k * log k) cho k phần tử

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "8 phần tử = luôn là một tree" — còn cần capacity >= 64
- "Treeification là hoạt động bình thường" — nó là bảo vệ khỏi bất thường
- "Tree giải quyết vấn đề va chạm" — không, nó chỉ tối ưu tìm kiếm trong một bucket
