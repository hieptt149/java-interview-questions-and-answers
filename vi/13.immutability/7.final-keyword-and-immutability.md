# What is the final keyword and how does it help create immutable classes? (Từ khóa final là gì và nó giúp gì cho việc tạo immutable class?)

---

## Basic Level

Từ khóa `final` trong Java có ba ý nghĩa tùy vào ngữ cảnh:
- **final cho biến** = không thể gán lại
- **final cho method** = không thể override trong subclass
- **final cho class** = không thể kế thừa

### 1. Biến final
```java
final int MAX = 100;
// MAX = 200; // LỖI! Không thể gán lại
```

### 2. Method final
```java
public final void doSomething() {
    // Method này không thể được override trong subclass
}
```

### 3. Class final
```java
public final class MyImmutableClass {
    // Class này không thể tạo subclass
}
```

### Cho Các Immutable Class
Dùng `final` cho class và cho tất cả các trường:
```java
public final class Point {
    private final int x;
    private final int y;
    // ...
}
```

### Khi final Trên Một Trường Gây Cản Trở

final không tương thích với lazy initialization — nếu giá trị được tính khi truy cập lần đầu, trường không thể là final. Dùng holder pattern hoặc AtomicReference.

---

## Intermediate Level

### final Ở Cấp Độ Class
Khai báo một class là `final` cấm kế thừa. Điều này quan trọng cho tính bất biến: một subclass không thể thêm các trường mutable hoặc override getter.

### final Ở Cấp Độ Trường
Một trường `final` chỉ có thể được khởi tạo một lần — tại khai báo hoặc trong constructor:
```java
public final class Config {
    private final String url;  // khởi tạo trong constructor
    private final int timeout = 30; // hoặc ngay lập tức tại khai báo

    public Config(String url) {
        this.url = url;
    }
}
```

### final Không Bảo Vệ Nội Dung
```java
private final List<String> list = new ArrayList<>();
list.add("New Item"); // ĐƯỢC PHÉP! Tham chiếu vẫn giữ nguyên, nội dung thay đổi
```

Đó là lý do tại sao các collection cần defensive copy bổ sung.

### Các Method final
Nếu class không phải là `final`, nhưng các method riêng lẻ là `final` — điều này không đảm bảo tính bất biến đầy đủ, nhưng bảo vệ các method cụ thể khỏi bị override.

## Advanced Level

### Publish An Toàn Và Các Đảm Bảo JMM

`final` đảm bảo một sự **"đóng băng" (freeze)** của giá trị ở cuối constructor. Bất kỳ thread nào thấy một tham chiếu đến object đều được đảm bảo thấy các trường `final` của nó ở trạng thái đã khởi tạo. Không có `final`, một tình huống có thể xảy ra trong đó một thread thấy object nhưng các trường của nó vẫn chứa các giá trị mặc định (`null` hoặc `0`) do việc sắp xếp lại lệnh bởi bộ xử lý.

### Các Tối Ưu Hóa JIT

JIT compiler có thể tối ưu hóa code mạnh mẽ hơn:
- **Inlining** — thay thế trực tiếp các giá trị trường `final`
- **Constant folding** — tính toán các biểu thức tại thời điểm biên dịch
- **Hoisting** — kéo các trường `final` ra khỏi vòng lặp, vì chúng không thay đổi

### final Và Module System (Java 9+)
Bắt đầu từ Java 16 (JEP 396 — Strong Encapsulation), quyền truy cập reflection vào các trường final của `java.base` bị chặn theo mặc định. Trong Java 17 (JEP 403), điều này được tăng cường cho tất cả các nội bộ JDK. `--add-opens` là bắt buộc.

### Tóm Tắt Cho Advanced
- Class `final` ngăn việc phá vỡ tính bất biến thông qua kế thừa
- Các trường `final` đảm bảo visibility dữ liệu nguyên tử trong đa luồng (JMM freeze)
- Tham chiếu `final` ≠ dữ liệu bất biến tại tham chiếu — defensive copy vẫn cần thiết
- JIT dùng `final` cho các tối ưu hóa mạnh mẽ

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- `final` cho biến = không thể gán lại, cho method = không thể override, cho class = không thể kế thừa
- Cho tính bất biến: class `final` + các trường `final` = publish an toàn (JMM freeze)
- `final` không bảo vệ nội dung tại tham chiếu — `final List` có thể bị sửa đổi, cần một bản sao
- Các tối ưu hóa JIT: inlining, constant folding, hoisting — tất cả nhờ `final`
- Publish an toàn: sau khi construct, tất cả các trường `final` hiển thị với bất kỳ thread nào
- Bắt đầu từ Java 16, reflection đến các trường final của java.base bị chặn (JEP 396)

**Các câu hỏi phụ thường gặp:**
- *Các trường final có thể được khởi tạo ở đâu?* — Tại khai báo hoặc trong constructor
- *Một class final có thể mock trong test không?* — Mockito cần inline-mock-maker hoặc bytebuddy agent
- *Tham chiếu final = dữ liệu bất biến?* — Không, `final List` cho phép add/remove — cần một bản sao
- *Tại sao một method final?* — Để một subclass không override và phá vỡ tính bất biến

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Các trường final là đủ cho tính bất biến" — không có class final và defensive copy, không đủ
- "final = const" — final không thể gán lại, nhưng object tại tham chiếu có thể thay đổi
- "method final làm class bất biến" — chỉ method cụ thể được bảo vệ, không phải toàn bộ class
- "Reflection có thể thay đổi một trường final" — trong Java 16+ với java.base điều này là không thể
