# What is the difference between choreography and orchestration in Saga (Sự khác biệt giữa choreography và orchestration trong Saga là gì)

## Junior Level

**Choreography** và **orchestration** là hai cách để triển khai pattern Saga.

**Choreography** — không có bộ điều khiển trung tâm. Mỗi service lắng nghe event từ các service khác và phản ứng.

**Orchestration** — có một **orchestrator** trung tâm nói cho mỗi service biết phải làm gì.

// Orchestrator khác với một phương thức thông thường như thế nào:
// 1. Lưu trữ trạng thái (sống sót qua các lần restart)
// 2. Xử lý các event bất đồng bộ
// 3. Có sẵn cơ chế retry và compensation

```
Choreography:
Order Service -> "OrderCreated" -> Payment Service -> "PaymentDone" -> Shipping Service

Orchestration:
     Orchestrator
    /     |      \
Order  Payment  Shipping
  ↓       ↓        ↓
"create" "charge" "ship"
```

## Middle Level

### Choreography — Event-driven

```java
// Order Service
@EventListener
public void on(OrderCreatedEvent event) {
    paymentService.reserve(event.orderId());
    eventPublisher.publish(new PaymentReservedEvent(event.orderId()));
}

// Payment Service
@EventListener
public void on(PaymentReservedEvent event) {
    shippingService.ship(event.orderId());
    eventPublisher.publish(new ShippingCompletedEvent(event.orderId()));
}

// Compensation
@EventListener
public void on(PaymentFailedEvent event) {
    orderService.cancel(event.orderId());
    eventPublisher.publish(new OrderCancelledEvent(event.orderId()));
}
```

### Orchestration — Điều phối trung tâm

```java
@Component
public class OrderOrchestrator {

    public void processOrder(Order order) {
        try {
            orderService.create(order);
            paymentService.charge(order);
            inventoryService.reserve(order);
            shippingService.ship(order);
        } catch (PaymentException e) {
            orderService.cancel(order);
            // throw e — exception truyền đến HTTP controller,
            // nơi nó trả về 500 với mô tả lỗi compensation.
            throw e;
        } catch (InventoryException e) {
            paymentService.refund(order);
            orderService.cancel(order);
            // throw e — exception truyền đến HTTP controller,
            // nơi nó trả về 500 với mô tả lỗi compensation.
            throw e;
        }
    }
}
```

### So Sánh

| Choreography                                                   | Orchestration                                                                                           |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Không có kiểm soát trung tâm                                    | Orchestrator trung tâm                                                                                    |
| Dựa trên event                                                   | Dựa trên command                                                                                          |
| Khó theo dõi luồng                                              | Dễ hiểu luồng                                                                                             |
| Phụ thuộc vòng lặp                                              | Không có phụ thuộc vòng lặp                                                                               |
| Với 2-3 service luồng event vẫn có thể quản lý được.            | Với 5+ service các kết nối tăng theo cấp số bậc hai, và không có orchestrator thì không thể hiểu ai gọi ai. |

Event-driven = các service phản ứng với các event (ai đó đã publish một fact).
Command-driven = orchestrator nói rõ ràng cho mỗi service "làm X".

### Các lỗi thường gặp

1. **Phụ thuộc vòng lặp trong choreography:**
```
Service A -> event -> Service B -> event -> Service A -> vòng lặp vô hạn!
```

## Senior Level

### Đánh Đổi Kiến Trúc

**Choreography:**
```
Ưu điểm:
- Không có single point of failure
- Coupling lỏng lẻo giữa các service
- Phong cách event-driven tự nhiên

Nhược điểm:
- Khó debug (luồng không rõ ràng)
- Nguy cơ phụ thuộc vòng lặp
- Khó thêm một bước mới
- Không có nơi tập trung để giám sát
```

**Orchestration:**
```
Ưu điểm:
- Luồng thực thi rõ ràng
- Dễ thêm một bước
- Giám sát tập trung
- Không có phụ thuộc vòng lặp

Nhược điểm:
- Orchestrator là bottleneck
- Orchestrator là single point of failure
- Orchestrator biết quá nhiều về các service khác
```

### Kinh Nghiệm Production

**Khi nào chọn choreography:**
```
- 2-3 service
- Logic đơn giản
- Hạ tầng event-driven đã có sẵn
- Cần fault tolerance tối đa
```

**Khi nào chọn orchestration:**
```
- 5+ service
- Logic phức tạp với các điều kiện
- Cần monitoring và tracing
- Các team khác nhau cho mỗi service
```

**Orchestrator thực tế (Axon Framework):**
```java
@Saga
public class OrderSaga {
    @Autowired
    private transient CommandGateway commandGateway;

    @StartSaga
    @SagaEventHandler(associationProperty = "orderId")
    public void handle(OrderCreatedEvent event) {
        commandGateway.send(new ReserveInventoryCommand(event.getOrderId()));
    }

    @SagaEventHandler(associationProperty = "orderId")
    public void handle(InventoryReservedEvent event) {
        commandGateway.send(new ProcessPaymentCommand(event.getOrderId()));
    }

    @SagaEventHandler(associationProperty = "orderId")
    public void handle(PaymentCompletedEvent event) {
        commandGateway.send(new CompleteOrderCommand(event.getOrderId()));
        end();
    }

    @SagaEventHandler(associationProperty = "orderId")
    public void handle(PaymentFailedEvent event) {
        commandGateway.send(new CancelOrderCommand(event.getOrderId()));
        end();
    }
}
```

### Best Practices

```
✅ Choreography cho các Saga đơn giản (2-3 bước)
✅ Orchestration cho các Saga phức tạp (5+ bước)
✅ Giám sát Saga ở cả hai cách tiếp cận
✅ Triển khai idempotency

❌ Đừng trộn lẫn các cách tiếp cận trong một Saga
❌ Đừng tạo các phụ thuộc vòng lặp trong choreography
❌ Đừng làm orchestrator quá "thông minh"
```

## Interview Cheat Sheet

**Cần phải biết:**
- Choreography — dựa trên event, không có kiểm soát trung tâm, các service phản ứng với event
- Orchestration — dựa trên command, coordinator trung tâm quản lý luồng
- Choreography: không có SPOF, nhưng khó debug, nguy cơ phụ thuộc vòng lặp
- Orchestration: luồng rõ ràng, dễ giám sát, nhưng orchestrator là bottleneck
- Choreography cho Saga đơn giản (2-3 bước), orchestration cho phức tạp (5+)
- Trong choreography mỗi service chỉ biết về hàng xóm; trong orchestration orchestrator biết về tất cả
- Cả hai cách tiếp cận đều cần idempotency và compensation

**Các câu hỏi phụ thường gặp:**
- **Cách tránh phụ thuộc vòng lặp trong choreography?** Thiết kế một đồ thị event có hướng, dùng orchestration cho logic phức tạp.
- **Điều gì nếu orchestrator crash?** Trạng thái được lưu trữ — sau khi restart nó tiếp tục từ điểm thất bại.
- **Có thể kết hợp các cách tiếp cận không?** Không trong cùng một Saga, nhưng các Saga khác nhau trong hệ thống có thể dùng các cách tiếp cận khác nhau.
- **Cách test một orchestrator?** Unit test cho logic + integration test với các service mock.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Choreography đơn giản hơn cho 10 service" — không, luồng trở nên khó đọc
- "Orchestrator không thể thất bại" — nó có thể, cần lưu trữ trạng thái
- "Không có coupling trong choreography" — có, thông qua các event
- "Orchestrator = anti-pattern, vi phạm loose coupling" — đó là một đánh đổi, không phải tuyệt đối
