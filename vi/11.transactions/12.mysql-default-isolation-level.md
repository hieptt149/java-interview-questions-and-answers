# What is the default isolation level in MySQL (Isolation level mặc định trong MySQL là gì)

## 🟢 Junior Level

Trong MySQL (khi dùng engine **InnoDB**), isolation level mặc định là **Repeatable Read**.

**Điều này có nghĩa gì một cách đơn giản:** Trong một transaction, bạn luôn thấy cùng một dữ liệu, ngay cả khi các transaction khác sửa đổi nó trong lúc đó. Như thể bạn đã chụp một "snapshot" của dữ liệu tại thời điểm bắt đầu transaction và đang làm việc với snapshot đó.

**Ví dụ minh họa đơn giản:** Bạn đã tải một bản PDF của một bài viết và đang đọc nó. Trong khi bạn đọc, tác giả có thể chỉnh sửa bài viết trên website, nhưng bạn vẫn thấy bản đã tải của mình mà không có bất kỳ thay đổi nào.

**Ví dụ SQL:**

```sql
-- Trạng thái ban đầu: account.balance = 1000

-- Transaction 1
BEGIN;
SELECT balance FROM accounts WHERE id = 1;  -- thấy 1000

-- Transaction 2 (đồng thời)
BEGIN;
UPDATE accounts SET balance = 1500 WHERE id = 1;
COMMIT;

-- Transaction 1 tiếp tục:
SELECT balance FROM accounts WHERE id = 1;  -- VẪN thấy 1000!
COMMIT;
```

**Điều gì được bảo vệ ở Repeatable Read:**

| Hiện tượng bất thường                     | Có thể xảy ra?                                                                                                                                   |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Dirty Read                  | **Không**                                                                                                                                      |
| Non-repeatable Read         | **Không**                                                                                                                                      |
| Phantom Read                | **Không** với các query dùng index (gap/next-key lock). Với full table scan hoặc range query không đánh index, phantom vẫn có thể xảy ra!                     |

**Khác biệt then chốt so với PostgreSQL:** Trong PostgreSQL mặc định là Read Committed, còn trong MySQL là Repeatable Read. MySQL chọn một level nghiêm ngặt hơn.

**Cách thay đổi:**

```sql
-- Trong config (my.cnf)
[mysqld]
transaction-isolation = READ-COMMITTED

-- Tại thời điểm chạy
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

## 🟡 Middle Level

### Cách Nó Hoạt Động Nội Bộ

MySQL/InnoDB hiện thực Repeatable Read thông qua sự kết hợp của:
- **MVCC** (Multi-Version Concurrency Control — lưu trữ nhiều phiên bản dòng)
- **Next-Key Locking** (Record Lock + Gap Lock). Gap = khoảng cách giữa các mục index. Gap Lock chặn việc chèn các dòng mới vào khoảng đó.

```
MVCC (Multi-Version Concurrency Control):
  - Mỗi dòng có các trường ẩn:
    * DB_TRX_ID: ID của transaction đã sửa đổi dòng
    * DB_ROLL_PTR: con trỏ đến phiên bản trước (trong undo log)
    * DB_ROW_ID: định danh duy nhất

  - Tại SELECT đầu tiên trong một transaction, một snapshot được tạo
  - Tất cả các SELECT tiếp theo dùng cùng snapshot này
  - Snapshot xác định phiên bản dòng nào "hiển thị"
```

**Nhận định Senior:** InnoDB ở Repeatable Read bảo vệ không chỉ khỏi non-repeatable read mà còn khỏi **phantom read** — điều này vượt ra ngoài chuẩn ANSI SQL. Điều này đạt được thông qua **Gap Lock** và **Next-Key Lock**.

### Next-Key Locking (Tính Năng Đặc Trưng Của MySQL)

```sql
SELECT * FROM orders WHERE id BETWEEN 10 AND 20 FOR UPDATE;

InnoDB khóa:
1. Record lock: các dòng có id = 10, 11, ..., 20
2. Gap lock: các khoảng (9,10), (10,11), ..., (19,20), (20,21)
3. Next-key lock = record lock + gap lock

Kết quả: INSERT INTO orders (id=15) là không thể — gap đã bị khóa!
```

Điều này ngăn phantom read ở Repeatable Read, nhưng tạo ra một tác dụng phụ — nhiều lock hơn và xác suất deadlock cao hơn.

### Tại Sao MySQL Chọn Repeatable Read Làm Mặc Định?

1. **Statement-based Replication (lý do lịch sử):** Trong các phiên bản MySQL cũ hơn, replication sao chép các câu SQL. Replication đúng trên các slave đòi hỏi tính xác định (determinism), điều mà Repeatable Read cung cấp. Không có RR, một SELECT trên slave có thể thấy các trạng thái trung gian mà master chưa bao giờ thấy trong transaction gốc của nó. Điều này sẽ khiến các UPDATE được replicate ảnh hưởng đến các dòng khác nhau.
2. **Đảm bảo tính ổn định:** Các nhà phát triển MySQL quyết định rằng sự an toàn quan trọng hơn hiệu năng mặc định.
3. **Khả năng tương thích ngược:** Thay đổi mặc định sẽ phá vỡ các ứng dụng hiện có.

### Ứng Dụng Thực Tế

**Khi Repeatable Read Hữu Ích:**
- Các ứng dụng đang migrate từ MySQL sang các DBMS khác (ít thay đổi hành vi hơn)
- Các báo cáo phức tạp yêu cầu một snapshot nhất quán
- Statement-based replication kiểu cũ

**Khi Nên Chuyển Sang Read Committed:**
- Các hệ thống tải cao với các cập nhật thường xuyên
- Microservice mà mỗi transaction ngắn
- Row-based replication (cách tiếp cận hiện đại, không yêu cầu RR)

### Các Lỗi Điển Hình

| Lỗi                                                    | Hậu quả                                        | Giải pháp                                          |
| ---------------------------------------------------------- | -------------------------------------------------- | ------------------------------------------------- |
| Giả định mọi DBMS có cùng mặc định                    | Hành vi khác nhau khi migrate PostgreSQL → MySQL | Nắm rõ mặc định của từng DBMS                       |
| Bỏ qua tác dụng phụ của gap lock                             | Deadlock không lường trước được                               | Dùng Read Committed cho các bảng hot-spot            |
| Transaction dài ở Repeatable Read                        | Undo log tăng, các phiên bản dòng cũ không được xóa        | Rút ngắn transaction, dùng Read Committed           |
| Gap lock trên một khoảng lớn                                  | Khóa nhiều dòng không liên quan                          | Dùng point query bằng primary key                  |

### So Sánh: Mặc Định MySQL vs PostgreSQL

| Đặc điểm     | MySQL (InnoDB)        | PostgreSQL                 |
| ------------------ | --------------------- | --------------------------- |
| Level mặc định      | **Repeatable Read**   | **Read Committed**         |
| MVCC               | Undo log              | Dead tuple trong bảng      |
| Phantom ở RR     | Không (Next-Key Lock)   | Không (MVCC snapshot)         |
| Deadlock          | Thường xuyên hơn (gap lock)| Ít thường xuyên hơn                 |
| Overhead undo      | Tăng theo tx dài    | Table bloat với tx dài   |
| Tương đương VACUUM  | Purge thread          | Autovacuum                 |

### Khi Nào KHÔNG Nên Dùng Repeatable Read Trong MySQL

- **Row-based replication** (MySQL 5.7+) — Read Committed an toàn và nhanh hơn
- **Workload ghi cao** — gap lock tạo ra contention không cần thiết
- **Microservice** — transaction ngắn, overhead của RR là dư thừa

## 🔴 Senior Level

### Hiện Thực Nội Bộ: MVCC Của InnoDB Và Hệ Thống Lock

#### MVCC Thông Qua Undo Log

```
InnoDB lưu trữ các phiên bản dòng trong undo log (không phải trong bảng, khác với PostgreSQL):

Cấu trúc bản ghi clustered index:
  +------------------+
  | DB_ROW_ID (6B)   |  ← PK ẩn nếu không có PK tường minh
  | DB_TRX_ID (6B)   |  ← transaction ID đã sửa đổi dòng
  | DB_ROLL_PTR (7B) |  ← con trỏ đến bản ghi undo log
  | các cột dữ liệu...  |
  +------------------+

Bản ghi undo log:
  +------------------+
  | type: INSERT/UPDATE |
  | table_id           |
  | prev_version_ptr   |  ← chuỗi phiên bản
  | old_values...      |
  +------------------+

Khi SELECT:
  1. Một read view (snapshot) được chụp với up_limit_id và low_limit_id
  2. Nếu DB_TRX_ID < up_limit_id → phiên bản hiển thị
  3. Nếu DB_TRX_ID >= low_limit_id → phiên bản KHÔNG hiển thị
  4. Nếu up_limit_id <= DB_TRX_ID < low_limit_id → kiểm tra commit
  5. Nếu không hiển thị → theo DB_ROLL_PTR đến phiên bản trước
```

**Cấu trúc Read View:**
```c
struct ReadView {
    trx_id_t up_limit_id;     // Transaction đang hoạt động cũ nhất
    trx_id_t low_limit_id;    // ID của transaction tiếp theo (chưa được tạo)
    trx_id_t creator_trx_id;  // ID của transaction đã tạo read view này
    ids_t m_ids;              // Tập các transaction ID đang hoạt động
};
```

#### Next-Key Locking: Cấu Trúc Nội Bộ

```
InnoDB lock manager lưu trữ các lock trong một hash table:

struct lock_t {
    trx_t* trx;        // transaction sở hữu
    uint32_t type_mode; // LOCK_REC | LOCK_GAP | LOCK_ORDINARY
    hash_node_t hash;   // cho hash table
    // ...
};

LOCK_ORDINARY = next-key lock (record + gap)
LOCK_GAP = chỉ gap (không record)
LOCK_REC = chỉ record (không gap)
LOCK_INSERT = lock cho thao tác INSERT
```

**Leo thang Gap Lock:**
```sql
-- Query không có index:
SELECT * FROM orders WHERE status = 'pending' FOR UPDATE;

-- Không có index trên status → full table scan
-- InnoDB khóa TẤT CẢ các dòng + TẤT CẢ các gap → lock cấp bảng!
-- Điều này gọi là "gap lock trên toàn bảng"

-- Với index:
SELECT * FROM orders WHERE status = 'pending' FOR UPDATE;
-- (INDEX idx_status (status))

-- InnoDB chỉ khóa các dòng có status='pending' + các gap liền kề
```

### Đánh Đổi Về Kiến Trúc (Trade-off)

**Cách A: Repeatable Read (mặc định MySQL)**
- ✅ Ưu điểm: Snapshot nhất quán, bảo vệ khỏi phantom, tương thích statement-based replication
- ❌ Nhược điểm: Undo log bloat (giữ các phiên bản cũ), deadlock do gap lock, throughput thấp hơn cho workload ghi nặng
- Phù hợp cho: hệ thống legacy, reporting, tương thích migration

**Cách B: Read Committed**
- ✅ Ưu điểm: Ít lock hơn (không gap lock cho SELECT), purge undo log nhanh hơn, throughput cao hơn
- ❌ Nhược điểm: Non-repeatable read, phantom read, không tương thích với statement-based replication
- Phù hợp cho: hệ thống ghi cao, row-based replication, microservice

**Cách C: Serializable**
- ✅ Ưu điểm: ACID đầy đủ
- ❌ Nhược điểm: LOCK IN SHARE MODE ngầm định trên mọi SELECT, locking tối đa
- Phù hợp cho: các hệ thống tài chính legacy (hiếm khi dùng trong production)

### Các Trường Hợp Biên Và Đặc Biệt

**1. Gap Lock Trên Các Dòng Không Tồn Tại:**
```sql
-- Bảng có: id = 10, 20, 30
BEGIN;
SELECT * FROM t WHERE id = 15 FOR UPDATE;  -- không tìm thấy gì
-- NHƯNG: gap lock được đặt trên khoảng (10, 20)!

-- Một transaction khác:
INSERT INTO t (id, val) VALUES (15, 'test');
-- BỊ CHẶN! Chờ gap lock được giải phóng
```

**2. Deadlock Do Gap Lock:**
```
T1: SELECT * FROM t WHERE id BETWEEN 10 AND 20 FOR UPDATE;  -- khóa các gap (10,20)
T2: SELECT * FROM t WHERE id BETWEEN 15 AND 25 FOR UPDATE;  -- khóa các gap (15,25)
T1: INSERT INTO t (id) VALUES (17);  -- chờ gap lock của T2
T2: INSERT INTO t (id) VALUES (18);  -- chờ gap lock của T1
→ DEADLOCK

Tại sao deadlock: các gap lock không tương thích với nhau cho INSERT. Khi T1 giữ gap (10,20)
và T2 giữ gap (15,25), mỗi INSERT trong vùng chồng lấn (15-20) chờ
gap lock của transaction kia được giải phóng → chờ vòng tròn (circular wait).
```

**3. Undo Log Bùng Nổ:**
```
T1: BEGIN; (Repeatable Read)
T1: SELECT * FROM accounts;  -- tạo read view

-- 10,000 UPDATE trên accounts từ các transaction khác
-- Mỗi UPDATE tạo một bản ghi undo log
-- Read view của T1 ngăn purge xóa các phiên bản cũ

T1: SELECT * FROM accounts;  -- vẫn thấy dữ liệu cũ
-- Kích thước undo log: có thể tăng đến GB trong một transaction dài
```

**4. Implicit Locking Và Gap Lock:**
```sql
-- InnoDB đặt một implicit lock khi INSERT
-- Một transaction khác thực hiện SELECT ... LOCK IN SHARE MODE
-- có thể tạo một gap lock trên một dòng đã được insert (nhưng chưa commit)
-- Điều này dẫn đến blocking không lường trước được
```

**5. Auto-Increment Locking (MySQL 5.7 vs 8.0):**
```
MySQL 5.7: AUTO-INC lock — lock cấp bảng trong suốt thời gian INSERT (với innodb_autoinc_lock_mode = 1 — truyền thống)
MySQL 8.0: AUTO-INC lock — được giải phóng ngay sau khi sinh ID (với innodb_autoinc_lock_mode = 2 — interleaved, mặc định từ 8.0+)

Với Read Committed trong MySQL 8.0:
  T1: INSERT INTO t (val) VALUES ('a');  -- id=1
  T2: INSERT INTO t (val) VALUES ('b');  -- id=2
  T1: ROLLBACK;
  T2: COMMIT;

  Kết quả: id = 2, nhưng auto-inc tiếp theo = 3 (khoảng trống!)
```

**6. Consistent Read vs Locking Read:**
```sql
-- Repeatable Read:
SELECT * FROM t WHERE id = 1;       -- consistent read (snapshot, không lock)
SELECT * FROM t WHERE id = 1 FOR UPDATE;  -- locking read (giá trị hiện tại, khóa dòng)

-- Quan trọng: FOR UPDATE CẬP NHẬT read view!
-- Sau FOR UPDATE, các consistent read tiếp theo thấy dữ liệu HIỆN TẠI
```

### Tác Động Đến Hiệu Năng

| Level           | Latency (p50)  | Latency (p99)   | Throughput        | Overhead lock              |
| --------------- | -------------- | --------------- | ----------------- | -------------------------- |
| Read Committed  | 1-2ms          | 3-10ms          | 40,000+ TPS       | Tối thiểu                    |
| Repeatable Read | 1-3ms          | 5-20ms          | 30,000-35,000 TPS | Gap lock: overhead 5-15%  |
| Serializable    | 10-50ms        | 100-500ms       | 3,000-8,000 TPS   | Có thể xảy ra lock cấp bảng |

**Các con số cụ thể (MySQL 8.0, InnoDB, 8 core, NVMe, sysbench):**
- Read Committed, chỉ đọc: ~45,000 TPS
- Repeatable Read, chỉ đọc: ~42,000 TPS (overhead 7% từ quản lý gap lock)
- Read Committed, 50/50 đọc/ghi: ~20,000 TPS
- Repeatable Read, 50/50 đọc/ghi: ~15,000 TPS (giảm 25% do contention gap lock)
- Tỷ lệ deadlock (RR, 100 writer đồng thời): ~0.5-2%

**Tác động đến undo log:**
- Với RR và các transaction dài: undo log có thể tăng 5-10 lần kích thước bình thường
- Purge thread không thể xóa các phiên bản mà các read view đang hoạt động vẫn thấy
- Dung lượng đĩa: undo tablespace có thể tăng lên 100GB+ với các query reporting chạy dài

### Tác Động Đến Bộ Nhớ

- **Read View:** ~100-500 byte (tùy vào số transaction đang hoạt động). Được cấp phát tại SELECT đầu tiên.
- **Gap lock:** ~100 byte mỗi lock trong lock hash table. Với 10,000 gap lock = ~1MB.
- **Giữ undo log:** Mỗi phiên bản dòng ~50-200 byte. Với 1M update = giữ 50-200MB undo.
- **InnoDB Buffer Pool:** Các phiên bản dòng cũ chiếm chỗ trong buffer pool → đẩy các trang hot ra khỏi bộ nhớ → tăng I/O đĩa.

### Các Khía Cạnh Concurrency

**Phát hiện deadlock:**
```
InnoDB deadlock detector:
  - Chạy mỗi khi có lock wait timeout
  - Xây dựng wait-for graph: transaction → chờ → transaction → ...
  - Phát hiện chu trình: DFS, O(V + E)
  - Nạn nhân: transaction có ít "công việc" nhất (ít bản ghi undo log hơn)
  - Rollback nạn nhân: tỷ lệ thuận với số bản ghi undo
```

**Pattern tần suất deadlock:**
```
Read Committed:  tỷ lệ deadlock ~0.01-0.1% (chỉ record lock)
Repeatable Read: tỷ lệ deadlock ~0.5-5% (record + gap lock)
Serializable:    tỷ lệ deadlock ~5-20% (có thể xảy ra lock cấp bảng)
```

### Tình Huống Thực Tế Trong Production

**Tình huống:** Nền tảng e-commerce (2023), MySQL 8.0, xử lý 3000 đơn hàng/giờ.

**Vấn đề:** Trong giờ cao điểm (Black Friday), tỷ lệ deadlock tăng lên 15%, các đơn hàng thất bại với:
```
Deadlock found when trying to get lock; try restarting transaction
```

**Nguyên nhân gốc rễ:** Repeatable Read + Gap Lock trên order_items:
```java
@Transactional  // Repeatable Read theo mặc định
public void processOrder(Long orderId) {
    Order order = orderRepo.findById(orderId);

    // InnoDB: gap lock trên order_items theo order_id
    List<OrderItem> items = orderItemRepo.findByOrderId(orderId);

    // Xử lý từng item
    for (OrderItem item : items) {
        // UPDATE với gap lock trên tồn kho sản phẩm
        productRepo.decrementStock(item.getProductId(), item.getQuantity());
    }

    order.setStatus("PROCESSED");
    orderRepo.save(order);
}
```

Với 3000 đơn hàng/giờ, nhiều transaction chặn các khoảng chồng lấn trong `order_items` và `product_inventory`. Các gap lock tạo ra phụ thuộc vòng tròn → deadlock.

**Giải pháp 1 (nhanh):** Chuyển sang Read Committed:
```sql
SET GLOBAL transaction_isolation = 'READ-COMMITTED';
-- my.cnf: transaction-isolation = READ-COMMITTED
```

**Giải pháp 2 (dài hạn):** Loại bỏ các trigger gap lock:
```java
@Transactional
public void processOrder(Long orderId) {
    // Point SELECT bằng primary key — không gap lock
    Order order = orderRepo.findById(orderId);

    // Dùng atomic update thay vì read-modify-write
    productRepo.decrementStockWhereSufficient(itemId, quantity);

    order.setStatus("PROCESSED");
    orderRepo.save(order);
}
```

**Kết quả:**
- Tỷ lệ deadlock: từ 15% xuống 0.1%
- Throughput: +25% (ít lock hơn)
- Latency p99: từ 500ms xuống 50ms

### Giám Sát Và Chẩn Đoán

**Thống kê nội bộ MySQL:**
```sql
-- Các lock hiện tại
SELECT
    r.trx_id AS waiting_trx_id,
    r.trx_query AS waiting_query,
    b.trx_id AS blocking_trx_id,
    b.trx_query AS blocking_query
FROM information_schema.innodb_lock_waits w
JOIN information_schema.innodb_trx r ON r.trx_id = w.requesting_trx_id
JOIN information_schema.innodb_trx b ON b.trx_id = w.blocking_trx_id;

-- Log deadlock (deadlock gần nhất)
SHOW ENGINE INNODB STATUS\G
-- Tìm phần "LATEST DETECTED DEADLOCK"

-- Isolation level của transaction
SELECT @@GLOBAL.transaction_isolation, @@SESSION.transaction_isolation;

-- Kích thước undo log
SELECT
    table_name,
    table_rows,
    data_length,
    index_length
FROM information_schema.tables
WHERE table_name LIKE '%undo%';

-- Các transaction chạy dài
SELECT
    trx_id, trx_state, trx_started,
    TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS duration,
    trx_query
FROM information_schema.innodb_trx
ORDER BY trx_started;
```

**Giám sát ở cấp độ application:**
```java
// Micrometer: theo dõi deadlock
Counter.builder("mysql.deadlocks")

// Theo dõi việc sử dụng isolation level
Counter.builder("db.transaction.isolation")

    .register(meterRegistry);
```

**Giám sát Percona:**
```sql

```

### Best Practices Cho Highload

1. **Chuyển sang Read Committed cho các workload ghi nặng** — giảm tỷ lệ deadlock 80-95%.
2. **Dùng point query bằng primary key** — tránh gap lock.
3. **Giữ transaction ngắn** — cửa sổ contention lock nhỏ hơn.
4. **Sắp xếp các update theo thứ tự nhất quán** — ngăn deadlock (ví dụ: luôn theo product_id ASC).
5. **Đặt innodb_deadlock_detect = 0** cho throughput cực cao (với retry ở cấp độ application). Chỉ áp dụng cho MySQL 5.7+.
6. **Giám sát kích thước undo log** — cảnh báo khi >10GB.
7. **Dùng row-based replication** (binlog_format=ROW) — không yêu cầu Repeatable Read.
8. **Cho reporting — dùng read replica** với connection pool riêng.
9. **Optimistic locking cho các bảng hot-spot:**
   ```java
   @Version
   private Long version;
   // Thay vì SELECT ... FOR UPDATE
   ```
10. **Tinh chỉnh các cấu hình lock của InnoDB:**
    ```ini
    innodb_lock_wait_timeout = 10  # mặc định 50, giảm để phát hiện deadlock nhanh hơn
    innodb_table_locks = ON        # cho LOCK TABLES tường minh
    ```

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Mặc định MySQL (InnoDB): Repeatable Read — snapshot ổn định cho toàn bộ transaction
- MySQL ngăn phantom ở RR thông qua Next-Key Locking (Record + Gap Lock)
- MVCC qua undo log (không phải dead tuple trong bảng, như PostgreSQL)
- Lý do lịch sử: RR để đảm bảo tính xác định cho statement-based replication
- Gap Lock — lý do deadlock xảy ra thường xuyên hơn trong MySQL so với PostgreSQL
- Cho các workload ghi nặng, khuyến nghị chuyển sang Read Committed

**Các câu hỏi phụ thường gặp:**
- Tại sao MySQL chọn RR làm mặc định? — Statement-based replication, tính ổn định, tương thích ngược
- MVCC trong MySQL khác gì với PostgreSQL? — MySQL: undo log, PG: dead tuple trong cùng các trang
- Điều gì xảy ra khi có Gap Lock deadlock? — InnoDB deadlock detector chọn nạn nhân (ít bản ghi undo hơn)
- Khi nào nên chuyển sang Read Committed? — Row-based replication, workload ghi cao, microservice

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "MySQL và PostgreSQL có cùng mặc định" — MySQL: RR, PG: RC
- "Gap Lock luôn tốt" — có thể gây ra deadlock không cần thiết
- "Undo log không ảnh hưởng đến hiệu năng" — với các transaction RR dài, undo log tăng đáng kể
