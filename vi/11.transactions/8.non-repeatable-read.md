# What is Non-Repeatable Read? (Non-Repeatable Read là gì?)

## 🟢 Junior Level

**Non-Repeatable Read** là một hiện tượng bất thường trong đó một query lặp lại trên cùng dữ liệu trong một transaction trả về kết quả khác vì một transaction khác đã kịp sửa đổi và commit dữ liệu. Đây là vấn đề vì logic nghiệp vụ của bạn có thể ra quyết định dựa trên giá trị đầu tiên, rồi sau đó phát hiện rằng giá trị thực tế đã thay đổi — và báo cáo sẽ không khớp.

### Ví Dụ Đơn Giản

```
Transaction A: SELECT price FROM products WHERE id = 1;  -- 100
-- Một transaction khác: UPDATE products SET price = 150 WHERE id = 1; COMMIT;
Transaction A: SELECT price FROM products WHERE id = 1;  -- 150!
```

Cùng một query, cùng một thời điểm trong transaction — nhưng kết quả lại khác nhau.

### Xảy Ra Ở Level Nào

Xảy ra ở level **Read Committed**. Ở các level **Repeatable Read** và **Serializable**, vấn đề này không thể xảy ra.

### Khác Biệt So Với Phantom Read

- **Non-Repeatable Read**: dữ liệu thay đổi ở các dòng **đã tồn tại** (giá 100 → 150)
- **Phantom Read**: các dòng **mới** xuất hiện (trước có 5 bản ghi, giờ có 6)

## 🟡 Middle Level

### Kịch Bản

| Thời gian | Transaction A (Read Committed)                       | Transaction B (Update)                                    |
| ----- | ---------------------------------------------------- | --------------------------------------------------------- |
| T1    | `BEGIN;`                                             | `BEGIN;`                                                  |
| T2    | `SELECT price FROM products WHERE id = 1;` → **100** |                                                           |
| T3    |                                                      | `UPDATE products SET price = 150 WHERE id = 1; COMMIT;`   |
| T4    | `SELECT price FROM products WHERE id = 1;` → **150** |                                                           |
| T5    | Logic bị lỗi — giá thay đổi giữa chừng transaction    |                                                           |

> Nguyên nhân gốc rễ: ở Read Committed, PostgreSQL tạo một snapshot mới cho MỖI statement, không phải cho toàn bộ transaction. Đến thời điểm T4, Transaction B đã commit, và snapshot mới thấy các thay đổi đó.

### Tại Sao Điều Này Xảy Ra

Ở level **Read Committed**, DBMS (PostgreSQL) chụp một snapshot dữ liệu **trước mỗi statement**, không phải cho toàn bộ transaction. Đến thời điểm của query thứ hai, Transaction B đã commit, vì vậy snapshot mới thấy dữ liệu đã được cập nhật.

### Hậu Quả

- **Reporting**: Số dư tại thời điểm bắt đầu báo cáo không khớp với số dư khi tính thuế
- **Bất biến**: Kiểm tra `price < limit` đã pass, nhưng trước khi mua giá đã cao hơn
- **Tính toán nhiều bước**: Các kết quả trung gian dựa trên các phiên bản dữ liệu khác nhau

### Cách Ngăn Chặn

1. **Nâng level lên Repeatable Read**: Snapshot được chụp một lần cho toàn bộ transaction
2. **SELECT ... FOR UPDATE**: Khóa tường minh dòng khỏi các thay đổi cho đến khi kết thúc transaction

### Khác Biệt So Với Phantom Read

| Non-Repeatable Read              | Phantom Read                          |
| ------------------------------- | ------------------------------------- |
| Sửa đổi các dòng đã tồn tại      | Xuất hiện/biến mất của các dòng       |
| `UPDATE` từ transaction khác     | `INSERT`/`DELETE` từ transaction khác |
| Cùng các dòng, giá trị khác nhau | Tập các dòng khác nhau                 |

> Trong thực tế, sự khác biệt là then chốt: **Non-repeatable read** phá vỡ read-modify-write (đọc giá, tính thuế, giá đã thay đổi). **Phantom read** phá vỡ các aggregate (đếm được 100 đơn hàng, xử lý 100, nhưng giờ có 105).

## 🔴 Senior Level

### Thời Điểm Chụp Snapshot MVCC — Nguyên Nhân Gốc Rễ

#### Read Committed: Snapshot Theo Từng Statement

Trong PostgreSQL dưới Read Committed:
```
Statement 1: BEGIN;
Statement 2: SELECT ...  → Snapshot A được tạo (thấy trạng thái đã commit tại T2)
Statement 3:             → Transaction khác commit
Statement 4: SELECT ...  → Snapshot B được tạo (thấy trạng thái đã commit tại T4, gồm cả thay đổi của tx khác)
Statement 5: COMMIT;
```

Mỗi statement nhận một snapshot mới. Đây là chủ ý thiết kế — đó là sự đánh đổi để đạt concurrency tối đa.

#### Repeatable Read: Snapshot Ở Cấp Độ Transaction

```
Statement 1: BEGIN;
Statement 2: SELECT ...  → Snapshot A được tạo và ĐÓNG BĂNG cho toàn bộ transaction
Statement 3:             → Transaction khác commit (KHÔNG hiển thị)
Statement 4: SELECT ...  → Vẫn dùng Snapshot A (kết quả giống Statement 2)
Statement 5: COMMIT;
```

### Phân Tích Tác Động Nghiệp Vụ

#### Ví Dụ Hệ Thống Tài Chính
```java
// Non-Repeatable Read có thể gây ra các tính toán không nhất quán
@Transactional // Read Committed theo mặc định
public Statement generateStatement(Long accountId) {
    BigDecimal balance = repo.getBalance(accountId);       // Đọc 1: 1000
    // Một khoản nạp tiền đồng thời commit: balance giờ là 1500
    BigDecimal fee = calculateFee(balance);                 // Dùng 1000
    BigDecimal interest = calculateInterest(balance);       // Dùng 1000
    // Nhưng query total_assets có thể thấy 1500
    BigDecimal total = repo.getTotalAssets(accountId);      // Đọc 2: 1500

    // Statement hiển thị: balance=1000, total=1500 — không nhất quán!
}
```

#### Các Cách Tiếp Cận Giải Quyết

**Cách 1: Repeatable Read**
```java
@Transactional(isolation = Isolation.REPEATABLE_READ)
public Statement generateStatement(Long accountId) {
    // Tất cả các lần đọc thấy cùng một snapshot
}
```

**Cách 2: Pessimistic Locking**
```java
@Query("SELECT a FROM Account a WHERE a.id = :id FOR UPDATE")
Account findByIdLocked(Long id);

@Transactional
public Statement generateStatement(Long accountId) {
    Account account = repo.findByIdLocked(accountId);
    // Đã khóa — không ai có thể thay đổi cho đến khi chúng ta commit
}
```

**Cách 3: Tính Nhất Quán Ở Cấp Độ Application**
```java
@Transactional
public Statement generateStatement(Long accountId) {
    // Đọc tất cả dữ liệu cần thiết cùng lúc vào các biến local
    var snapshot = repo.getAccountSnapshot(accountId);
    // Chỉ dùng các biến local, không đọc DB thêm nữa
}
```

### Hành Vi Đặc Thù Của PostgreSQL

#### Quy Tắc Visibility Của UPDATE
Dưới Read Committed, PostgreSQL có hành vi đặc biệt cho UPDATE/DELETE:
```sql
-- Transaction A (Read Committed)
BEGIN;
UPDATE accounts SET balance = balance - 10 WHERE id = 1;
```

Nếu một transaction khác đã sửa đổi và commit cùng dòng đó giữa SELECT và UPDATE của A:
- PostgreSQL **đánh giá lại** mệnh đề WHERE dựa trên phiên bản đã commit mới nhất
- Nếu dòng vẫn khớp, UPDATE tiến hành trên phiên bản mới
- Điều này được gọi là kiểm tra lại "EvalPlanQual"

Điều này ngăn lost update dưới Read Committed, nhưng chỉ cho các UPDATE trực tiếp, không phải các pattern read-modify-write trong code application.

### Giám Sát Các Vấn Đề Non-Repeatable Read

```sql
-- Phát hiện các transaction chạy dài trên Read Committed
SELECT pid, now() - xact_start AS duration, state, query
FROM pg_stat_activity
WHERE state != 'idle'
  AND xact_start < now() - interval '30 seconds'
ORDER BY xact_start;

-- Theo dõi phân phối thời lượng transaction
SELECT
    percentile_cont(0.5) WITHIN GROUP (ORDER BY duration) as p50,
    percentile_cont(0.95) WITHIN GROUP (ORDER BY duration) as p95,
    percentile_cont(0.99) WITHIN GROUP (ORDER BY duration) as p99
FROM (
    SELECT extract(epoch FROM (now() - xact_start)) AS duration
    FROM pg_stat_activity
    WHERE state != 'idle'
) sub;
```

### Khi Nào Non-Repeatable Read Có Thể Chấp Nhận Được

1. **Hệ thống eventual consistency**: Nơi sự cũ (staleness) nhẹ trong một transaction có thể chấp nhận được
2. **Kiểm tra trạng thái**: Đọc một flag có thể thay đổi (ví dụ: `is_active`)
3. **Các kịch bản caching**: Nơi bạn muốn dữ liệu mới nhất một cách tường minh

### Khi Nào Điều Này KHÔNG Thể Chấp Nhận Được

1. **Các tính toán tài chính nhiều bước**
2. **Tạo báo cáo yêu cầu tự nhất quán**
3. **Kiểm tra bất biến trước các thao tác quan trọng**
4. **Read-modify-write không có locking phù hợp**

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Non-Repeatable Read — SELECT lại cùng các dòng trả về giá trị khác (UPDATE từ transaction khác)
- Xảy ra ở Read Committed vì mỗi SELECT nhận một snapshot mới
- Được ngăn chặn ở Repeatable Read (một snapshot cho mỗi transaction) và Serializable
- Khác biệt so với Phantom Read: NRR = các dòng đã tồn tại thay đổi, Phantom = các dòng mới xuất hiện
- Trong PostgreSQL: snapshot theo từng statement ở RC so với theo từng transaction ở RR
- Giải pháp: RR, SELECT FOR UPDATE, tính nhất quán ở cấp độ application (đọc tất cả vào biến local)

**Các câu hỏi phụ thường gặp:**
- Làm sao ngăn NRR mà không nâng isolation level? — SELECT ... FOR UPDATE cho các dòng cụ thể
- Tại sao PostgreSQL tạo snapshot mới ở RC? — Concurrency tối đa, mỗi statement thấy dữ liệu mới nhất
- EvalPlanQual là gì? — Cơ chế của PG: khi có UPDATE đồng thời, đọc lại dòng và kiểm tra mệnh đề WHERE

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "NRR và Phantom Read là một" — NRR = UPDATE dòng có sẵn, Phantom = INSERT dòng mới
- "Ở RC, hai SELECT trả về cùng kết quả" — ở RC, mỗi SELECT thấy snapshot riêng của nó
- "FOR UPDATE chỉ dành cho việc ghi" — FOR UPDATE cũng ngăn NRR
