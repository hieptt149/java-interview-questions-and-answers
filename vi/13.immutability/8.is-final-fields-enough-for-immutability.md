# Is it enough to make all fields final for immutability? (Chỉ cần đặt tất cả các trường là final có đủ để bất biến không?)

---

## Basic Level

**Không, chưa đủ!** `final` chỉ bảo vệ bản thân biến (tham chiếu), không phải dữ liệu mà nó trỏ đến.

### Ví Dụ Về Vấn Đề
```java
public final class NotReallyImmutable {
    private final List<String> items; // trường là final

    public NotReallyImmutable(List<String> items) {
        this.items = items; // lưu một tham chiếu trực tiếp!
    }

    public List<String> getItems() {
        return items; // trả về một tham chiếu trực tiếp!
    }
}
```

```java
List<String> myItems = new ArrayList<>();
myItems.add("A");
NotReallyImmutable obj = new NotReallyImmutable(myItems);

myItems.add("B"); // Đã thay đổi object "bất biến" từ bên ngoài!
// this.items = items lưu cùng tham chiếu với myItems.
// Vì vậy myItems.add("B") thay đổi list bên trong object.
obj.getItems().clear(); // Cũng có thể bị thay đổi qua getter!
```

### Còn Cần Gì Nữa
1. Class phải là `final`
2. Tạo bản sao của các collection trong constructor
3. Trả về các bản sao (hoặc wrapper bất biến) từ getter

### Các Trường final vs Immutable Class

|                            | Các trường final | Immutable class |
| -------------------------- | ---------- | ------------------- |
| Các trường không thể gán lại | Có          | Có                   |
| Các trường mutable được bảo vệ  | Không          | Có (defensive copy)  |
| Kế thừa bị cấm     | Không          | Có (final class)     |
| Getter trả về các bản sao   | Không          | Có                   |

## Intermediate Level

### Shallow Immutability vs Deep Immutability

**Shallow (Nông)** — các trường `final`, nhưng nội dung của các object mutable có thể bị thay đổi:
```java
private final List<User> users; // list không thể bị thay thế, nhưng các phần tử có thể bị thay đổi
```

**Deep (Sâu)** — mọi thứ, kể cả các object lồng nhau, đều bất biến:
```java
public final class Group {
    private final List<String> names; // String bất biến — bảo vệ sâu được đảm bảo

    public Group(List<String> names) {
        this.names = List.copyOf(names); // sao chép
    }

    public List<String> getNames() {
        return names; // List.copyOf đã trả về một list bất biến rồi
    }
}
```

### Khi final Là Đủ
Nếu class chỉ bao gồm các kiểu nguyên thủy (`int`, `double`, `boolean`) và các kiểu bất biến (`String`, `BigDecimal`, `LocalDate`), thì `final` cho tất cả các trường + `final` cho class — là đủ.

### Khi final KHÔNG Đủ
- Mảng — các phần tử có thể bị thay đổi
- Collection (`List`, `Map`, `Set`) — nội dung có thể bị thay đổi
- `Date` — có các method `setTime()`, `setYear()`, v.v.
- Các class mutable tùy chỉnh

## Advanced Level

### Tấn Công Reflection

Ngay cả một class "hoàn toàn" bất biến cũng có thể bị cố gắng thay đổi qua Reflection:
```java
Field field = MyClass.class.getDeclaredField("value");
field.setAccessible(true);
field.set(obj, newValue); // phá vỡ tính bất biến
```
Bắt đầu từ Java 9 (Project Jigsaw), module system hạn chế reflection, và với Java 16 (JEP 396), quyền truy cập vào các trường `java.base` bị chặn theo mặc định.

### Công Thức Đầy Đủ Cho Tính Bất Biến
```
final class + final fields + defensive copies + no this-escape = True Immutability
```

### Tóm Tắt Cho Advanced
- `final` chỉ bảo vệ tham chiếu, không phải dữ liệu tại tham chiếu
- Với các collection và mảng, defensive copy là **bắt buộc**
- Tính bất biến là một thuộc tính của toàn bộ hệ thống phân cấp object, không chỉ cấp độ cao nhất
- Hãy nhớ: `final fields + final class + defensive copies = Immutable`
- Trong Java 14+, dùng `record` — nó tự động áp dụng hầu hết các quy tắc

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- `final` chỉ bảo vệ tham chiếu, không phải dữ liệu tại tham chiếu
- Shallow Immutability — các trường final, nhưng nội dung của các object mutable có thể bị thay đổi
- Deep Immutability — mọi thứ, kể cả các object lồng nhau, đều bất biến
- Công thức: `final class + final fields + defensive copies + no this-escape = True Immutability`
- Khi final là đủ: các kiểu nguyên thủy + các kiểu bất biến (String, BigDecimal, LocalDate)
- Khi final KHÔNG đủ: mảng, collection, Date, các class mutable tùy chỉnh
- Tấn công Reflection: ngay cả một class hoàn toàn bất biến cũng có thể bị thay đổi qua reflection (trước Java 16)

**Các câu hỏi phụ thường gặp:**
- *Tại sao final List không bảo vệ?* — `list.add()` thay đổi nội dung, tham chiếu vẫn giữ nguyên
- *Khi nào final là đủ?* — Chỉ khi class bao gồm các kiểu nguyên thủy và các kiểu bất biến
- *Shallow vs Deep Immutability là gì?* — Shallow: container không đổi, các phần tử — không đổi; Deep: mọi thứ đều không đổi
- *Reflection có thể phá vỡ tính bất biến không?* — Có, nhưng trong Java 16+ quyền truy cập vào các trường java.base bị chặn

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Các trường final = immutable class" — không có defensive copy và final class, không đủ
- "Không cần List.copyOf nếu trường là final" — final bảo vệ tham chiếu, không phải nội dung
- "clone() là cách tốt nhất để sao chép" — clone() được coi là hỏng (Effective Java Item 13)
- "Reflection — không phải vấn đề" — trước Java 16, đây là mối đe dọa thực sự
