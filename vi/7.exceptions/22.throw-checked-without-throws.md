# Can you throw a checked exception from a method without throws? (Có thể ném một checked exception từ một phương thức không có throws không?)

## Junior Level

### Câu trả lời ngắn gọn

Thông thường là **không** - compiler Java sẽ không cho phép. Nhưng có những cách để qua mặt điều này.

### Hành vi tiêu chuẩn

```java
// Sẽ không biên dịch - IOException không được khai báo trong throws
public void readFile() {
    throw new IOException("Error"); // Lỗi biên dịch: Unhandled exception
}

// Đúng - khai báo throws
public void readFile() throws IOException {
    throw new IOException("Error");
}
```

### Ngoại lệ: RuntimeException

Unchecked exception có thể được ném mà không cần `throws`:

```java
public void fail() {
    throw new RuntimeException("Error"); // Biên dịch được mà không cần throws
}
```

### Bọc trong RuntimeException

Cách đơn giản và an toàn nhất để "ném" một checked exception mà không cần `throws`:

```java
public void readFile() { // Không có throws!
    try {
        Files.readAllLines(Paths.get("file.txt"));
    } catch (IOException e) {
        throw new RuntimeException("Failed to read file", e); // Bọc nó lại
    }
}
```

## Middle Level

### Kỹ thuật 1: Generic Hack (Type Erasure) - từng bước

Dùng type erasure để đánh lừa compiler:

```java
public class Sneaky {
    public static void main(String[] args) {
        throwSneaky(new IOException("Surprise!")); // Biên dịch được mà không cần throws!
    }

    @SuppressWarnings("unchecked")
    private static <E extends Throwable> void throwSneaky(Throwable e) throws E {
        throw (E) e;
    }
}
```

**Cơ chế type erasure từng bước:**

1. **Khai báo:** `<E extends Throwable> void throwSneaky(Throwable e) throws E` - compiler thấy kiểu generic `E` với cận trên `Throwable`.

2. **Lời gọi:** `throwSneaky(new IOException(...))` - compiler cố suy ra `E`. Tham số có kiểu `Throwable`, nên `E` vẫn ở mức `Throwable`.

3. **Cast `(E) e`:** lúc biên dịch cast trông có vẻ an toàn - `e` có kiểu `Throwable`, và `E extends Throwable`. Compiler **không thể** kiểm tra rằng kiểu thật của `e` là `IOException`, vì thông tin generic bị xóa.

4. **Erasure:** lúc biên dịch `E` được thay bằng cận trên `Throwable`. Chữ ký bytecode trở thành: `throws Throwable`. Nhưng JVM không kiểm tra checked exception lúc runtime - đây thuần túy là một kiểm tra của compiler.

5. **Kết quả:** `throw (Throwable) e` vượt qua biên dịch, và lúc runtime `IOException` gốc được ném. Kiểm tra `throws E` trong chữ ký sau erasure không hạn chế kiểu exception, vì `Throwable` là cận trên.

**Nhận định then chốt:** kiểm tra checked/unchecked là **phân tích tĩnh của compiler**, không phải một cơ chế lúc runtime. JVM không phân biệt checked và unchecked khi ném một exception. Bytecode cho `throw new IOException()` và `throw new RuntimeException()` là giống hệt nhau - lệnh `athrow`.

### Kỹ thuật 2: Lombok @SneakyThrows

```java
@SneakyThrows
public void readFile() {
    // IOException không cần throws!
    Files.readAllLines(Paths.get("file.txt"));
}
```

Đây là tiêu chuẩn trên thực tế (de facto) trong các dự án hiện đại. Làm cùng một việc như Generic Hack.

### Kỹ thuật 3: Unsafe.throwException()

```java
import sun.misc.Unsafe;

// Cách ở mức thấp
unsafe.throwException(new IOException("Direct throw"));
```

Ném trực tiếp, bỏ qua mọi kiểm tra của compiler.

### Tại sao bạn cần điều này

**1. Biểu thức lambda:**
```java
// Sẽ không biên dịch
list.stream().map(path -> Files.readString(path))

// Với sneaky throws - hoạt động
list.stream().map(path -> sneakyRead(path))
```

**2. Các interface của thư viện bên thứ ba:**
```java
public class MyRunnable implements Runnable {
    @SneakyThrows
    public void run() {
        // Làm việc với I/O mà không cần try-catch
        Files.readAllLines(Paths.get("data.txt"));
    }
}
```

## Senior Level

### Vi phạm hợp đồng

Code gọi mong đợi phương thức là an toàn (vì không có `throws`). Nếu nó nhận một `IOException` - nó không thể bắt qua `catch (IOException e)`:

```java
try {
    sneakyMethod();
} catch (Exception e) { // Phải bắt Exception chung
    // Không rõ chính xác điều gì đã xảy ra
}
```

### Không có Overhead

Không giống như bọc trong `RuntimeException`, Sneaky Throws không tạo một object wrapper trong heap. Đây là một cú throw "miễn phí" từ góc độ tài nguyên.

### Kiểm tra Bytecode

Trong bytecode của một phương thức với `@SneakyThrows` - lệnh `athrow` thông thường. Phép màu chỉ ở trong đầu của compiler.

### Sức khỏe của Thread

Nếu một thread "chết" vì một checked exception bất ngờ, `UncaughtExceptionHandler` vẫn sẽ bắt nó - hoạt động với `Throwable` cơ sở.

### Các nguy hiểm

- **Khó debug** - stack trace là đúng, nhưng logic xử lý lỗi không dự đoán được
- **Vi phạm nguyên tắc ít bất ngờ nhất (principle of least surprise)** - các lập trình viên khác không mong đợi hành vi này
- **Đừng dùng trong logic nghiệp vụ** - chỉ trong code hạ tầng

### Khi nào KHÔNG nên dùng sneaky throws

1. **Logic nghiệp vụ** - vi phạm hợp đồng của phương thức, bên gọi không biết về các exception
2. **API của public library** - client sẽ không thể xử lý lỗi đúng cách qua `catch (SpecificException e)`
3. **Phát triển theo đội** - code review nên chặn những mẹo như vậy, chúng vi phạm nguyên tắc ít bất ngờ nhất
4. **Code production không có UncaughtExceptionHandler** - checked exception bất ngờ sẽ giết thread mà không cảnh báo
5. **Thay cho việc bọc trong RuntimeException** - luôn ưa chuộng wrapper tường minh nếu bên gọi có thể xử lý lỗi một cách có ý nghĩa
6. **Khi bên gọi và bên bị gọi từ các đội khác nhau** - không có sự phối hợp hợp đồng, sneaky throws tạo ra các phụ thuộc ẩn

### Lưu ý: Java 21+ và các phiên bản tương lai

Bắt đầu từ Java 21, Project Amber và các sáng kiến cải thiện xử lý lỗi khác có thể ảnh hưởng đến hành vi của sneaky throws. Dù tính đến Java 21 kỹ thuật này vẫn tiếp tục hoạt động, hãy để mắt tới:

- **JEP 443 (Unnamed Patterns and Variables)** - không ảnh hưởng trực tiếp, nhưng cho thấy hướng đơn giản hóa code
- **Các JEP tương lai về xử lý exception** - các thay đổi có thể có của compiler sẽ siết chặt hoặc nới lỏng các luật
- **Tính tương thích Lombok** - `@SneakyThrows` có thể cần cập nhật cho các phiên bản JDK mới

Tại thời điểm này (Java 21) kỹ thuật này hoạt động, nhưng trong các dự án mới các wrapper tường minh hoặc `@SneakyThrows` từ Lombok (dễ gỡ bỏ nếu có thay đổi xảy ra) là được ưa chuộng hơn.

### Chẩn đoán

- **`javap -c`** - bạn sẽ thấy lệnh `athrow` thông thường
- **Static Analysis** - Sonar có thể cảnh báo về sneaky throws
- **UncaughtExceptionHandler** - bắt tất cả các exception, bao gồm cả sneaky

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Câu trả lời tiêu chuẩn: không - compiler sẽ không cho phép ném checked exception mà không có `throws`
- Bọc trong `RuntimeException` - cách an toàn nhất để qua mặt hạn chế
- Generic Hack (type erasure): `<E extends Throwable> void throwSneaky(Throwable e) throws E { throw (E) e; }` - được compiler kiểm tra, nhưng không phải JVM
- Lombok `@SneakyThrows` - tiêu chuẩn de facto, làm cùng một việc như generic hack
- Kiểm tra checked/unchecked - phân tích tĩnh của compiler, JVM không phân biệt chúng khi `athrow`
- Sneaky throws vi phạm hợp đồng - bên gọi không thể `catch (SpecificException e)`
- Đừng dùng trong logic nghiệp vụ và public API - chỉ code hạ tầng

**Các câu hỏi phụ thường gặp:**
- **Tại sao Generic Hack hoạt động?** - Type erasure thay `E` bằng `Throwable`, JVM không kiểm tra checked lúc runtime
- **Các nguy hiểm của sneaky throws là gì?** - Bên gọi không biết về các exception, không thể xử lý đúng cách
- **Cái nào tốt hơn - wrapper hay sneaky?** - Wrapper luôn được ưa chuộng hơn, sneaky - chỉ cho lambda/interface
- **Nó có hoạt động trong Java 21+ không?** - Có, nhưng hãy theo dõi các thay đổi trong các JEP tương lai về xử lý exception

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi dùng sneaky throws trong logic nghiệp vụ" - vi phạm nguyên tắc ít bất ngờ nhất
- "Tôi ném checked mà không có `throws` và `RuntimeException`" - chỉ qua các mẹo unsafe
- "Sneaky throws tạo ra overhead" - ngược lại, không tạo object wrapper
- "Compiler và JVM kiểm tra checked theo cùng một cách" - không, JVM không kiểm tra, chỉ compiler
