# How to implement horizontal scaling of microservices (Cách triển khai horizontal scaling cho microservices)

## Junior Level

**Horizontal scaling** nghĩa là thêm **nhiều instance hơn** của một service để xử lý tải.

Vertical scaling (thêm CPU/RAM) chạm giới hạn của một server duy nhất
và yêu cầu downtime. Horizontal scaling về mặt lý thuyết là vô hạn và không có downtime.

```
Một instance:
Client -> Service

Horizontal scaling:
Client -> Load Balancer -> Service #1
                       -> Service #2
                       -> Service #3
```

**Các phương pháp:**
1. **Kubernetes** — tự động (HPA — Horizontal Pod Autoscaler, K8s tự động thêm Pod khi tải tăng)
2. **Docker Compose** — `docker-compose up --scale service=3`
3. **Cloud** — auto-scaling group

## Middle Level

### Khi Nào KHÔNG Nên Dùng Horizontal Scaling

- **Các service stateful** (kết nối WebSocket, in-memory cache)
- **Phần mềm có bản quyền** với giá theo instance
- **Các service khởi tạo tốn kém** (mất vài phút để khởi động)

### Kubernetes HPA

```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: user-service-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: user-service
  minReplicas: 2
  maxReplicas: 10
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70
// 70% — vùng đệm cho các đợt tăng tải. Ở 90% một instance mới sẽ không kịp khởi động
// trước khi đợt tăng xảy ra. Ở 50% bạn sẽ trả tiền thừa cho các instance dư thừa.
```

### Statelessness

```
Để horizontal scaling, các service phải stateless:
(Stateless — service không giữ trạng thái trong bộ nhớ; bất kỳ instance nào cũng có thể thay thế.)
✅ Không có state cục bộ
✅ Session trong Redis
✅ Dữ liệu trong DB
✅ Configuration từ bên ngoài
```

### Các Lỗi Thường Gặp

1. **Các service stateful:**
```
Session trong bộ nhớ -> khi scale, các request đi đến instance khác -> không có session
Giải pháp: lưu trữ session bên ngoài
```

## Senior Level

### Custom Metric

```yaml
metrics:
- type: Pods
  pods:
    metric:
      name: http_requests_per_second
    target:
      type: AverageValue
      averageValue: 1000
```

### Kinh Nghiệm Production

**Blue-Green Deployment:**
```
(Blue-Green Deployment — chiến lược deployment không có downtime: hai môi trường, chuyển đổi traffic.)
v1 (Blue) -> traffic production
v2 (Green) -> đã deploy, đang test
Chuyển traffic sang v2 -> rollback nếu có vấn đề
```

### Best Practices

```
✅ Các service stateless
✅ Health check
✅ Graceful shutdown
✅ Giới hạn tài nguyên
✅ Monitoring + alerting

❌ Stateful mà không có lưu trữ bên ngoài
❌ Không có giới hạn tài nguyên
❌ Không có graceful shutdown
```

## Interview Cheat Sheet

**Cần phải biết:**
- Horizontal scaling = nhiều instance hơn phía sau một load balancer
- Vertical scaling = nhiều CPU/RAM hơn, chạm giới hạn của một server duy nhất
- Các service PHẢI stateless để horizontal scaling
- Kubernetes HPA — scaling tự động dựa trên CPU/metric (target CPU 70%)
- Session trong Redis, dữ liệu trong DB, configuration từ bên ngoài
- Blue-Green deployment — deployment không có downtime
- KHÔNG phù hợp cho các service stateful (WebSocket, in-memory cache)

**Các câu hỏi phụ thường gặp:**
- **Tại sao target CPU 70%?** Vùng đệm cho các đợt tăng tải — ở 90% một instance mới sẽ không kịp scale up.
- **Cách làm cho một service stateless?** Session trong Redis, dữ liệu trong DB, configuration từ bên ngoài, không có state cục bộ.
- **Graceful shutdown là gì?** Hoàn thành các request hiện tại trước khi dừng, hủy đăng ký khỏi Registry.
- **Custom metric cho HPA?** http_requests_per_second, độ dài queue, các metric nghiệp vụ.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Các service stateful dễ scale" — không, cần quản lý state bên ngoài
- "Vertical scaling luôn đơn giản hơn" — đúng, nhưng chạm giới hạn
- "HPA ở 90% CPU — hiệu quả" — không, sẽ không scale kịp trong đợt tăng tải
- "Session trong bộ nhớ là ổn" — không, các request sẽ đi đến instance khác
