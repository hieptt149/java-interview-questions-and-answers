# What is Content-Type header? (Content-Type header là gì?)

## Junior Level

**Content-Type** là một header HTTP cho server biết dữ liệu đang được gửi **ở định dạng nào**.

### Ví dụ:

```
Content-Type: application/json        — dữ liệu ở định dạng JSON
Content-Type: application/xml         — dữ liệu ở định dạng XML
Content-Type: text/plain              — văn bản thuần
Content-Type: multipart/form-data     — form có file
```

### Tại sao cần đến nó?
Server cần biết cách đọc dữ liệu từ request. Không có `Content-Type`, server sẽ không biết cách deserialize các byte.

### Ví dụ request:
```
POST /users
Content-Type: application/json

{"name": "Ivan", "age": 30}
```

### Các media type thường gặp:
| Type                                | Mô tả             |
| ----------------------------------- | ----------------- |
| `application/json`                  | dữ liệu JSON      |
| `application/xml`                   | dữ liệu XML       |
| `text/html`                         | trang HTML        |
| `multipart/form-data`               | form có file      |
| `application/x-www-form-urlencoded` | dữ liệu form      |

## Middle Level

### Content-Type trong Spring MVC

**`HttpMessageConverter`** chịu trách nhiệm xử lý `Content-Type`:

1. Request đến với `Content-Type: application/json`
2. Spring duyệt qua các converter (Jackson, Gson, v.v.)
3. Phương thức `canRead(clazz, mediaType)` trả về `true`
4. Bắt đầu đọc và ánh xạ sang một đối tượng Java

### Bảo mật và MIME Sniffing

#### X-Content-Type-Options: nosniff
Trình duyệt đôi khi cố "đoán" content type, bỏ qua header. **MIME Sniffing** — một cơ chế của trình duyệt: nó cố xác định content type dựa theo nội dung, bỏ qua Content-Type. Hữu ích cho tương thích ngược, nhưng tạo ra lỗ hổng XSS.

**Rủi ro:** Một người dùng upload một ảnh mà thực chất là JavaScript. Trình duyệt có thể thực thi nó.

**Giải pháp:** Luôn trả về `X-Content-Type-Options: nosniff`.

### Boundary trong Multipart

Với `multipart/form-data`, header chứa một dấu phân tách (delimiter) duy nhất:
```
Content-Type: multipart/form-data; boundary=----WebKitFormBoundary7MA4YWxkTrZu0gW
```
Dấu phân tách này được dùng để phân tích request body thành các phần riêng biệt.

### Các trường hợp biên (Edge Case)

- **Thiếu Content-Type:** Nếu client không gửi header — trả về **415 Unsupported Media Type**. Đừng cố đoán kiểu
- **Custom MIME Types:** Cho versioning, dùng các kiểu của riêng bạn: `application/vnd.mycompany.v1+json`

### Hiệu suất

- **Charset:** Với `application/json`, UTF-8 là mặc định theo RFC 8259, nên `charset=utf-8` là tùy chọn. Với các kiểu `text/*`, việc chỉ định charset là bắt buộc, vì mặc định là `iso-8859-1`.
- **Binary Formats (định dạng nhị phân):** Trong các hệ thống Highload, `application/x-protobuf` hoặc `application/octet-stream` được dùng — Protobuf thường parse nhanh hơn JSON 3-10 lần (tùy vào kích thước payload và ngôn ngữ). Định dạng nhị phân không cần phân tích từ vựng (lexical parsing), không parse key dạng chuỗi — mà dùng tag trường dạng số.

## Senior Level

### Khi nào có thể bỏ qua Content-Type

Các request GET không có body, DELETE không có body. Với các request có body (POST, PUT, PATCH) — nó là bắt buộc.

### Quá trình chọn Converter

Trong Spring MVC, `HttpMessageConverter` được chọn dựa trên:
1. Header `Content-Type` từ request
2. Các converter đã đăng ký trong ứng dụng
3. Phương thức `canRead(clazz, mediaType)`

### Multipart/Related so với Multipart/Form-Data

- **Multipart/Form-Data:** Để upload file qua form
- **Multipart/Related:** Khi bạn cần gửi một đối tượng (JSON) và một file nhị phân liên quan (ảnh) trong một request duy nhất. Hiệu quả hơn hai request riêng biệt

### Hiệu suất và Highload

- **Charset Overhead:** Việc chỉ định encoding ngăn các proxy cố mã hóa lại văn bản
- **Binary Formats:** Protobuf thường parse nhanh hơn JSON 3-10 lần (tùy vào kích thước payload và ngôn ngữ). Định dạng nhị phân không cần phân tích từ vựng, không parse key dạng chuỗi — mà dùng tag trường dạng số.
- **Multipart/Related:** Hiệu quả hơn để gửi JSON + file nhị phân trong một request duy nhất

### Chẩn đoán

- **Curl Debugging:** `curl -v -H "Content-Type: application/json" -d '{"key":"val"}' ...` — điều cơ bản để chẩn đoán API
- **Bẫy của Postman/Insomnia:** Các công cụ này thường tự thêm `Content-Type`. Khi test một API "thô", hãy tắt tính năng tự điền
- **415 Unsupported Media Type:** Nếu server không hỗ trợ kiểu được gửi — trả về 415, đừng cố đoán

## Interview Cheat Sheet

**Cần phải biết:**
- Content-Type cho server biết định dạng dữ liệu trong request body: `application/json`, `application/xml`, `multipart/form-data`
- Content-Type là bắt buộc với các request có body (POST, PUT, PATCH); không cần cho GET/DELETE không body
- Trong Spring MVC, HttpMessageConverter đảm nhận việc xử lý (Jackson, Gson, v.v.)
- X-Content-Type-Options: nosniff ngăn MIME Sniffing và các tấn công XSS
- multipart/form-data dùng một dấu phân tách boundary để phân tích body thành các phần
- Thiếu Content-Type → trả về 415 Unsupported Media Type, đừng đoán
- Binary Formats (Protobuf) parse nhanh hơn JSON 3-10 lần

**Các câu hỏi phụ thường gặp:**
- Tại sao cần X-Content-Type-Options: nosniff? — Ngăn MIME Sniffing, khi trình duyệt "đoán" kiểu và thực thi JS
- Spring chọn converter như thế nào? — Theo Content-Type của request → kiểm tra `canRead(clazz, mediaType)` → khớp đầu tiên
- Khi nào có thể bỏ qua Content-Type? — Với GET và DELETE không body; với POST/PUT/PATCH — bắt buộc
- Multipart/Related là gì? — Gửi JSON + file nhị phân liên quan trong một request, hiệu quả hơn hai request

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Content-Type và Accept giống nhau" — Content-Type = cái tôi đang gửi, Accept = cái tôi muốn nhận
- "Content-Type cần thiết cho các request GET" — GET không body không yêu cầu Content-Type
- "Server có thể đoán content type" — nên trả về 415, không đoán
- "charset=utf-8 là bắt buộc với JSON" — UTF-8 là mặc định theo RFC 8259, tùy chọn
