# What is stored in Heap? (Những gì được lưu trữ trong Heap?)

## Junior Level

**Heap** — một vùng bộ nhớ ảo (từ vài chục MB đến hàng terabyte) được JVM cấp phát để lưu trữ các đối tượng. Được tách biệt khỏi Stack vì các đối tượng tồn tại lâu hơn cả lời gọi phương thức.

**Cụ thể là gì:**
- Mọi thứ được tạo thông qua `new` → nằm trong Heap
- Các mảng (array) → nằm trong Heap
- Các chuỗi (String) → nằm trong Heap (String Pool)
- Các trường tĩnh (static field) → nằm trong Heap

**Ví dụ:**
```java
public class Example {
    static int count = 0;        // Trường static → nằm trong Heap

    public void method() {
        int x = 10;              // Kiểu nguyên thủy (Primitive) → nằm trong Stack
        String s = "hello";      // Tham chiếu nằm trong Stack, "hello" → nằm trong Heap
        User user = new User();  // Tham chiếu nằm trong Stack, đối tượng → nằm trong Heap
        int[] arr = new int[5];  // Tham chiếu nằm trong Stack, mảng → nằm trong Heap
    }
}
```

**Kích thước Heap:**
- Có thể cấu hình: `-Xms` (ban đầu), `-Xmx` (tối đa)
- Mặc định: tùy thuộc vào hệ thống (thường là 1/4 RAM)
- Lỗi tràn: `OutOfMemoryError: Java heap space`

## Middle Level

### Những gì được lưu trữ trong Heap

**1. Các instance của đối tượng:**
```java
new User("Ivan")        // Đối tượng User nằm trong Heap
new ArrayList<>()       // Đối tượng ArrayList + các mảng nội bộ
```

**2. Các mảng (kể cả mảng của kiểu nguyên thủy):**
```java
int[] numbers = new int[1000];  // Mảng là một đối tượng → nằm trong Heap
byte[] data = new byte[1024];   // Ngay cả byte[] cũng là một đối tượng trong Heap
```

**3. Các trường tĩnh (kể từ Java 8):**
```java
public class Config {
    private static String DB_URL = "jdbc:...";  // Nằm trong Heap (đối tượng Class)
}
```

**4. String Pool:**
```java
String s1 = "hello";  // Nằm trong String Pool (một phần của Heap)
String s2 = "hello";  // Cùng một tham chiếu (pool giúp tiết kiệm bộ nhớ)
```

### Cấu trúc giải phẫu của đối tượng trong bộ nhớ

```
Đối tượng trong Heap:
┌─────────────────────────┐
│ Header (12-16 byte)    │
│   Mark Word (8 byte)   │
│   Klass Pointer (4 byte)│
├─────────────────────────┤
│ Instance Data (các trường)  │
│   int age = 25  (4 byte)│
│   String name   (4 byte - tham chiếu)│
├─────────────────────────┤
│ Padding (đến 8 byte)    │
└─────────────────────────┘
```

**Mark Word lưu trữ:**
- Hash code của đối tượng
- Tuổi (age) dành cho GC (đã sống sót qua bao nhiêu lần thu gom)
- Trạng thái khóa (lock state)

**Klass Pointer:**
- Con trỏ đến metadata của class trong Metaspace
- 4 byte khi có Compressed OOPs (Heap < 32 GB)
- 8 byte khi không có Compressed OOPs (Heap > 32 GB)

### Tối ưu hóa Compressed OOPs

```
JVM 32-bit: con trỏ = 4 byte
JVM 64-bit: con trỏ = 8 byte

Compressed OOPs (Heap < 32 GB):
  Con trỏ = 4 byte (dịch chuyển × 8)
  → Tiết kiệm 50% bộ nhớ cho các tham chiếu!
  → Nhiều dữ liệu hơn trong cache CPU

Ngưỡng: Heap 32 GB
  2^32 × 8 byte = 32 GB
```

**Tại sao 31 GB lại nhanh hơn 33 GB:**
- 31 GB → Compressed OOPs được kích hoạt → giảm 50% bộ nhớ cho tham chiếu
- 33 GB → Compressed OOPs bị vô hiệu hóa → nhiều RAM hơn, nhưng chậm hơn
- Thường thì 31 GB có Compressed OOPs sẽ **nhanh hơn** so với 33 GB không có

### Các lỗi thường gặp

1. **Lưu trữ quá nhiều thứ trong Heap**
   ```java
   // ❌ Cache không giới hạn
   static Map<String, Object> cache = new HashMap<>();
   cache.put(key, value);  // Tăng dần vô hạn → OOM!
   ```

2. **Tạo ra các đối tượng không cần thiết**
   ```java
   // ❌ Rác trong Heap
   String s = new String("hello");  // Hai đối tượng:
   // 1. Literal "hello" trong String Pool (đối tượng #1)
   // 2. new String() — lớp bọc (wrapper) quanh literal (đối tượng #2)

   // ✅
   String s = "hello";  // Một đối tượng duy nhất từ pool
   ```

3. **Rò rỉ thông qua các collection tĩnh**
   ```java
   // ❌ Collection tĩnh tăng dần vô hạn
   static List<String> history = new ArrayList<>();
   history.add(data);  // Không bao giờ được dọn dẹp!
   ```

## Senior Level

### Cấu trúc Heap (HotSpot JVM)

```
Bố cục Heap:
┌──────────────────────────────────────────┐
│ Young Generation                         │
│   Eden      (80%)                        │
│   Survivor 0 (10%)                       │
│   Survivor 1 (10%)                       │
├──────────────────────────────────────────┤
│ Old Generation (Tenured)                 │
│   Các đối tượng sống lâu                     │
├──────────────────────────────────────────┤
│ Humongous Regions (G1)                   │
│   Các đối tượng > 50% kích thước của region                   │
└──────────────────────────────────────────┘
```

### TLAB (Thread Local Allocation Buffer)

```
Vấn đề: hàng trăm luồng cấp phát cùng lúc → tranh chấp (contention)

Giải pháp: mỗi luồng nhận được một phần riêng của Eden
  Thread 1: TLAB[64KB] → di chuyển con trỏ (pointer bumping)
  Thread 2: TLAB[64KB] → di chuyển con trỏ
  Thread 3: TLAB[64KB] → di chuyển con trỏ

Cấp phát trong TLAB:
  obj_ptr = thread.tlab_ptr
  thread.tlab_ptr += obj_size
  → 0 sự đồng bộ hóa!
  → Nhanh hơn cả malloc() trong C++!

PLAB (Promotion Local Allocation Buffer):
  → Tương tự như TLAB nhưng dành cho Old Gen
  → Được sử dụng khi sao chép các đối tượng sống sót
```

### Heap nhận thức NUMA (NUMA-Aware Heap)

```
NUMA (Non-Uniform Memory Access - Truy cập bộ nhớ không đồng nhất):
  CPU 1 ── Bộ nhớ cục bộ (nhanh, 100ns)
  CPU 2 ── Bộ nhớ từ xa (chậm, 150ns)

-XX:+UseNUMA:
  → JVM cấp phát bộ nhớ cục bộ cho mỗi CPU
  → Tăng 10-20% hiệu năng trên các server đa vi xử lý

Quan trọng đối với Highload có > 2 socket CPU
```

### Đào sâu về Object Layout

```
JVM 64-bit, có Compressed OOPs:

┌─────────────────────────────────┐
│ Mark Word       (8 byte)       │
│   Hash: 31 bit                 │
│   Age: 4 bit (tối đa 15)          │
│   Lock: 2 bit                  │
│   GC: 1 bit                     │
├─────────────────────────────────┤
│ Klass Pointer   (4 byte)       │
│   → Dịch chuyển × 8 → địa chỉ trong Metaspace│
├─────────────────────────────────┤
│ Array Length    (4 byte)       │ ← chỉ dành cho mảng
├─────────────────────────────────┤
│ Instance Data                   │
│   long  (8 byte)               │
│   int   (4 byte)               │
│   short (2 byte)               │
│   byte  (1 byte)                │
│   ref   (4 byte có Compressed)│
├─────────────────────────────────┤
│ Padding (bội số của 8)      │
└─────────────────────────────────┘

→ Đối tượng tối thiểu: 16 byte (Object rỗng)
→ Integer: 24 byte (16 header + 4 int + 4 padding)
```

### Căn chỉnh bộ nhớ (Memory Alignment)

```
CPU đọc bộ nhớ theo từ (word) (8 byte = 64 bit)

Truy cập không căn chỉnh:
  [1234][5678][9...]
   ^  dữ liệu trải rộng trên hai từ → 2 chu kỳ đọc

Truy cập có căn chỉnh:
  [1234][5678][9...]
      ^  dữ liệu trong một từ → 1 chu kỳ đọc

→ JVM tự động thêm padding thành bội số của 8 byte
→ Nhóm các trường theo kích thước: long/long → int/int → short → byte
```

### Giám sát Heap

```java
// Runtime API
Runtime rt = Runtime.getRuntime();
long max = rt.maxMemory();         // -Xmx
long total = rt.totalMemory();     // Đã committed hiện tại
long free = rt.freeMemory();       // Còn trống
long used = total - free;          // Đã sử dụng

// MemoryMXBean
MemoryMXBean mem = ManagementFactory.getMemoryMXBean();
MemoryUsage heap = mem.getHeapMemoryUsage();
```

### Tương lai: Project Valhalla

```java
// Value Types (Java tương lai):
public final class Point {
    public final int x;
    public final int y;
}

// Hiện tại:
Point[] arr = new Point[100];
→ 100 đối tượng trong Heap (1600 byte của header)
→ 100 tham chiếu (400 byte)
→ Tổng cộng: chi phí phát sinh ~4 KB

// Với Value Types:
Point[] arr = new Point[100];
→ Dữ liệu được lưu trữ trực tiếp trong mảng!
→ Không có header, không có tham chiếu
→ Cache locality tăng gấp 10 lần
```

### Kinh nghiệm Production

**Tình huống thực tế: Heap 33 GB chậm hơn 31 GB**
- Ứng dụng: Spring Boot, `-Xmx33g`
- Compressed OOPs bị vô hiệu hóa → con trỏ 8 byte
- Tỷ lệ L3 cache miss: 25%
- Giải pháp: `-Xmx30g` → Compressed OOPs được kích hoạt
- Kết quả: tỷ lệ L3 miss còn 12%, tăng 15% throughput

### Best Practices (Thực hành tốt nhất)

1. **Tránh vượt quá 32 GB** khi không cần thiết (Compressed OOPs)
2. **Nhóm các trường** theo kích thước để căn chỉnh
3. **TLAB** — việc cấp phát đối tượng gần như miễn phí
4. **String Pool** giúp tiết kiệm bộ nhớ cho chuỗi
5. **Collection tĩnh** — nguồn gốc chính của rò rỉ
6. **NUMA** — hãy bật trên các server đa vi xử lý. Đừng bật trên server đơn vi xử lý — chi phí phát sinh mà không có lợi ích gì.
7. **Object Layout** ảnh hưởng đến cache locality

### Tóm tắt cho Senior

- **Heap** lưu trữ: các đối tượng, mảng, trường static, String Pool
- **Object Layout** = Header (Mark Word + Klass) + Data + Padding
- **Compressed OOPs** = ngưỡng 32 GB → tiết kiệm 50% cho tham chiếu
- **TLAB** = cấp phát không cần khóa (lock-free) → nhanh hơn malloc()
- **NUMA** = bộ nhớ cục bộ cho mỗi CPU → tăng 10-20%
- **Memory Alignment** = bội số của 8 byte → 1 chu kỳ đọc
- **Value Types** (Valhalla) = lưu trữ theo giá trị → không có chi phí phát sinh
- **31 GB thường nhanh hơn 33 GB** do Compressed OOPs

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Trong Heap: tất cả các đối tượng (`new`), mảng (kể cả kiểu nguyên thủy), trường static, String Pool
- Đối tượng tối thiểu trên JVM 64-bit có Compressed OOPs: 16 byte (header 12 + padding)
- Compressed OOPs nén các tham chiếu từ 8 xuống còn 4 byte khi Heap < 32 GB
- TLAB — buffer riêng cho mỗi luồng trong Eden, cấp phát = di chuyển con trỏ (0 đồng bộ hóa)
- String Pool — một phần của Heap, các string literal được tái sử dụng
- Collection tĩnh — nguồn gốc chính của rò rỉ bộ nhớ
- Heap 31 GB thường nhanh hơn 33 GB do Compressed OOPs

**Các câu hỏi phụ thường gặp:**
- **Tại sao `new String("hello")` lại tạo ra 2 đối tượng?** — Literal "hello" trong String Pool + lớp bọc `new String()`
- **Mark Word lưu trữ những gì?** — Hash code, tuổi (age) dành cho GC, trạng thái khóa
- **PLAB là gì?** — Promotion Local Allocation Buffer, tương tự như TLAB nhưng dành cho Old Gen khi sao chép các đối tượng sống sót
- **Tại sao collection tĩnh lại là nguyên nhân rò rỉ phổ biến?** — Trường static = GC Root, các đối tượng không bao giờ bị thu gom

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Kiểu nguyên thủy được lưu trữ trong Heap" — các kiểu nguyên thủy cục bộ được lưu trữ trong Stack
- "String Pool nằm trong Metaspace" — kể từ Java 7, String Pool nằm trong Heap
- "Heap được dọn dẹp tự động khi phương thức return" — Heap được dọn dẹp bởi GC, Stack được dọn dẹp khi phương thức return
