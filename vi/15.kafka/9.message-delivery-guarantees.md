# What message delivery guarantees does Kafka provide (Kafka cung cấp những đảm bảo delivery message nào)

## Junior Level

### Ba Cấp Độ Đảm Bảo

Kafka cung cấp **ba cấp độ đảm bảo delivery**:

**1. At most once:**
```
Message sẽ được delivered nhiều nhất một lần
Có thể bị mất khi có lỗi
```

**Cách nó bị mất:** producer gửi và quên (acks=0). Nếu network dừng hoạt động — message bị mất. Consumer tự động commit offset trước khi xử lý — nếu consumer crash sau commit nhưng trước khi xử lý — message bị mất.

**2. At least once:**
```
Message sẽ được delivered ít nhất một lần
Có thể bị trùng lặp khi retry
```

**3. Exactly once:**
```
Message sẽ được delivered chính xác một lần
Chỉ hoạt động cho các kịch bản Kafka-to-Kafka. Với các thao tác tài chính ghi vào một DB, bạn cần pattern Outbox hoặc ghi idempotent.
```

### Trực Quan Hóa

```
At most once:
  Producer → Kafka → (có thể bị mất) → Consumer

At least once:
  Producer → Kafka → Consumer → (có thể trùng lặp)

Exactly once:
  Producer → Kafka → Consumer → chính xác một lần
```

### Cấu Hình Đơn Giản

```java
// At most once
props.put("acks", "0");

// At least once (khuyến nghị)
props.put("acks", "all");
props.put("enable.idempotence", "true");

// Exactly once
props.put("enable.idempotence", "true");
props.put("isolation.level", "read_committed");
```

### Khi Nào KHÔNG Nên Dùng Mỗi Ngữ Nghĩa

- **At-most-once** — KHÔNG cho thanh toán, đơn hàng, thông báo
- **At-least-once** — KHÔNG khi trùng lặp là quan trọng (không có xử lý idempotent)
- **Exactly-once** — KHÔNG cho Kafka-to-Database, KHÔNG cho Kafka-to-HTTP

## Middle Level

### Cấu Hình Các Đảm Bảo

**At most once:**
```java
props.put("acks", "0");
props.put("enable.idempotence", "false");
props.put("enable.auto.commit", "true");
// Nhanh, nhưng có thể mất dữ liệu
```

**At least once:**
```java
props.put("acks", "all");
props.put("enable.idempotence", "true");
props.put("retries", Integer.MAX_VALUE);
props.put("enable.auto.commit", "false");
// Đáng tin cậy, nhưng có thể trùng lặp
```

**Exactly once:**
```java
// Producer
props.put("enable.idempotence", "true");
props.put("acks", "all");

// Consumer
props.put("isolation.level", "read_committed");
props.put("enable.auto.commit", "false");
```

### Transaction API Cho Exactly Once

```java
producer.initTransactions();

try {
    producer.beginTransaction();

    // Đọc
    ConsumerRecords<String, String> records = consumer.poll();

    // Xử lý
    for (var record : records) {
        process(record);
    }

    // Ghi kết quả
    producer.send(new ProducerRecord<>("output", result));

    // Commit cả hai hành động một cách nguyên tử
    producer.commitTransaction();

} catch (Exception e) {
    // Rollback khi có lỗi
    producer.abortTransaction();
}
```

### Các Lỗi Thường Gặp

1. **At least once không có idempotency:**
```
Retry → trùng lặp trong topic → xử lý hai lần
```

2. **Commit trước khi xử lý:**
```java
consumer.commitSync();  // commit trước
process(records);       // sau đó xử lý
// Nếu crash → mất dữ liệu
```

3. **Exactly once không có transaction:**
```
Producer và consumer không nằm trong cùng một transaction
→ Có thể mất mát hoặc trùng lặp
```

## Senior Level

### Cài Đặt Nội Bộ

**Idempotent Producer:**
```
Mỗi producer nhận một PID (Producer ID) duy nhất
Mỗi message nhận một Sequence Number
Broker theo dõi sequence

Trùng lặp với cùng PID + Sequence → bị từ chối
```

**Transaction Coordinator:**
```
Một thành phần riêng biệt điều phối các transaction
Lưu trữ trạng thái transaction trong topic __transaction_state
Đảm bảo commit/abort nguyên tử
```

### Exactly Once — Các Giới Hạn

```
Exactly Once chỉ hoạt động cho:
  Kafka → Kafka (read-process-write)

KHÔNG hoạt động cho:
  Kafka → Database (Kafka không kiểm soát transaction DB)
  Kafka → HTTP API (không có đảm bảo ở phía API)
```

**Giải Pháp Cho Các Hệ Thống Bên Ngoài:**
```
1. Ghi idempotent vào DB (ràng buộc unique)
2. Two-phase commit (XA — không được khuyến nghị)
3. Pattern Outbox
4. Debezium CDC
```

### End-to-End Exactly Once

```
Kịch bản: Kafka → Xử lý → PostgreSQL

Giải pháp: Pattern Outbox
1. Ghi vào bảng outbox (trong cùng transaction)
2. Debezium CDC đọc outbox
3. Gửi đến Kafka
4. Consumer xử lý và ghi vào bảng đích
5. Upsert idempotent theo business key
```

### Các Kịch Bản Lỗi

**1. Lỗi Producer:**
```
Đã gửi → không nhận ack → retry
Idempotent producer → trùng lặp bị từ chối
```

**2. Lỗi Broker:**
```
Đã ghi vào Leader → chưa replicate → Leader crash
acks=all + min.insync.replicas=2 → dữ liệu được lưu
```

**3. Lỗi Consumer:**
```
Đọc → chưa xử lý → chưa commit
Khi restart → đọc lại (at least once)
Xử lý idempotent → trùng lặp được xử lý đúng cách
```

### Đánh Đổi Hiệu Năng

| Đảm bảo     | Latency     | Throughput   | An Toàn Dữ Liệu   |
| ------------- | ----------- | ------------ | ------------- |
| At most once  | Tối thiểu     | Tối đa      | Thấp           |
| At least once | Trung bình      | Cao         | Cao           |
| Exactly once  | Cao        | Trung bình       | Tối đa       |

### Các Thực Hành Tốt Nhất

```
✅ At least once theo mặc định
✅ Exactly once khi quan trọng (tài chính, billing)
✅ Xử lý idempotent trên consumer
✅ Idempotent producer (enable.idempotence=true)
✅ Read-process-write transactional cho Kafka-to-Kafka
✅ Pattern Outbox cho các hệ thống bên ngoài

❌ At most once cho dữ liệu quan trọng
❌ Không có xử lý trùng lặp
❌ Exactly once mà không hiểu các giới hạn
❌ Commit trước khi xử lý
```

### Các Quyết Định Kiến Trúc

1. **At least once + consumer idempotent** — cân bằng tối ưu
2. **Exactly chỉ cho Kafka-to-Kafka** — không hoạt động với các hệ thống bên ngoài
3. **Pattern Outbox** — cho các đảm bảo end-to-end
4. **Ghi idempotent** — giải pháp phổ quát cho các hệ thống bên ngoài

### Tóm Tắt Cho Senior

- Exactly Once chỉ hoạt động trong kịch bản Kafka-to-Kafka
- Với các hệ thống bên ngoài hãy dùng pattern Outbox hoặc ghi idempotent
- At least once + consumer idempotent — cách tiếp cận tối ưu
- Transaction API cung cấp read-process-write nguyên tử
- Hiểu các giới hạn là quan trọng cho kiến trúc đúng đắn

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- Ba đảm bảo: at-most-once (0-1 lần), at-least-once (1+ lần), exactly-once (chính xác 1)
- At-most-once: `acks=0`, nhanh nhưng có thể mất dữ liệu
- At-least-once: `acks=all` + `enable.idempotence=true`, đáng tin cậy nhưng có thể trùng lặp
- Exactly-once: Transaction API, chỉ hoạt động cho các kịch bản Kafka-to-Kafka
- Với các hệ thống bên ngoài (DB, HTTP) — pattern Outbox hoặc ghi idempotent
- Idempotent producer: PID + Sequence Number, broker từ chối trùng lặp khi retry
- Commit TRƯỚC khi xử lý = mất dữ liệu; commit SAU = at-least-once

**Các câu hỏi phụ thường gặp:**
- *Tại sao exactly-once không hoạt động cho Kafka → DB?* — Kafka không kiểm soát transaction DB.
- *Làm sao đảm bảo đảm bảo end-to-end?* — Pattern Outbox: ghi vào outbox_table + CDC (Debezium).
- *Idempotent producer làm gì?* — PID duy nhất + số sequence, broker từ chối trùng lặp khi retry.
- *Nên chọn đảm bảo nào theo mặc định?* — At-least-once + xử lý idempotent ở consumer.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Exactly-once hoạt động cho bất kỳ hệ thống nào" — chỉ Kafka-to-Kafka
- "At-most-once ổn cho thanh toán" — mất dữ liệu là không chấp nhận được
- "Commit trước khi xử lý là ổn" — khi crash, dữ liệu bị mất
- "Idempotent producer không cần thiết" — không có nó, retry = trùng lặp
