# Can You Reuse a Single CompletableFuture in Multiple Chains? (Có thể tái sử dụng một CompletableFuture duy nhất trong nhiều chuỗi không)

## 🟢 Junior Level

**Có, bạn có thể!** Một `CompletableFuture` có thể được dùng trong nhiều chuỗi. Đây được gọi là **fan-out** — một kết quả, nhiều bên tiêu thụ.

```java
CompletableFuture<User> userCf = userService.fetchAsync(id);

// Ba chuỗi độc lập, một CF chung
userCf.thenAccept(user -> loadOrders(user));
userCf.thenAccept(user -> checkBalance(user));
userCf.thenRun(() -> updateLastLogin());
```

**Điểm chính:**
- Kết quả được tính toán **đúng một lần**
- Tất cả các bên đăng ký nhận **cùng** một object
- Nếu CF đã hoàn thành — callback mới thực thi ngay lập tức

## 🟡 Middle Level

### Pattern Promise Caching

Lưu `CompletableFuture` vào cache thay vì giá trị thực tế:

```java
private final Map<Long, CompletableFuture<User>> cache = new ConcurrentHashMap<>();

public CompletableFuture<User> getUserAsync(Long id) {
    return cache.computeIfAbsent(id, userId ->
        userService.fetchAsync(userId)
            .whenComplete((result, ex) -> {
                // Xóa khỏi cache sau khi hoàn thành (thành công hoặc lỗi)
                cache.remove(userId);
            })
    );
}
```

**Ưu điểm:** Nếu 10 thread yêu cầu cùng dữ liệu đồng thời, tất cả chúng đều đăng ký vào một CF. Chỉ cái đầu tiên khởi tạo truy vấn DB, các cái còn lại chờ kết quả.

### Nguy Hiểm: Sửa Đổi Kết Quả Chung

Tất cả các chuỗi nhận một tham chiếu đến **cùng một object**.

```java
CompletableFuture<User> userCf = userService.fetchAsync(id);

// Chuỗi 1 — sửa đổi object!
userCf.thenAccept(user -> user.setName("Modified"));

// Chuỗi 2 — thấy dữ liệu đã bị sửa đổi!
userCf.thenAccept(user -> System.out.println(user.getName())); // "Modified"
```

**Quy tắc:** Kết quả được truyền cho nhiều chuỗi phải là **bất biến (immutable)**.

### Thứ Tự Thực Thi Callback

JDK không đảm bảo thứ tự thực thi callback. Trong triển khai hiện tại (JDK 8-21)
thứ tự phụ thuộc vào chi tiết nội bộ. Nếu thứ tự quan trọng — thực thi nó một cách rõ ràng thông qua
`thenCompose` hoặc `thenCombine`.

```java
// ❌ Thứ tự không được đảm bảo
cf.thenAccept(a -> step1(a));
cf.thenAccept(a -> step2(a));  // không nhất thiết sau step1

// ✅ Thứ tự rõ ràng
cf.thenCompose(a -> step1Async(a).thenAccept(r -> step2(r)));
```

## 🔴 Senior Level

### Cơ Chế Memory Leak

Mỗi CF phụ thuộc (kết quả của `thenApply`, `thenAccept`, v.v.) giữ một tham chiếu
đến upstream của nó. Cho đến khi chuỗi phụ thuộc hoàn thành và có các tham chiếu đến nó,
GC không thể thu gom toàn bộ đồ thị. Trong các ứng dụng chạy dài, điều này có thể dẫn đến
rò rỉ nếu bạn tạo các chuỗi vô tận mà không hoàn thành.

```java
// Vấn đề: sự tích lũy chuỗi vô tận
CompletableFuture<Void> cf = CompletableFuture.completedFuture(null);
for (int i = 0; i < 1_000_000; i++) {
    cf = cf.thenAccept(v -> doSomething());
    // Mỗi CF mới giữ một tham chiếu đến cái trước
    // Cho đến khi cái cuối cùng còn sống — GC không thể thu gom toàn bộ đồ thị
}
```

### Lan Truyền Việc Hủy

Nếu bạn hủy CF gốc, tất cả các chuỗi phụ thuộc hoàn thành với `CancellationException`. Việc hủy một chuỗi con không ảnh hưởng đến CF gốc.

```java
CompletableFuture<String> root = CompletableFuture.supplyAsync(() -> "data");
CompletableFuture<String> child1 = root.thenApply(s -> s + " -> 1");
CompletableFuture<String> child2 = root.thenApply(s -> s + " -> 2");

child1.cancel(false);
// root và child2 vẫn tiếp tục làm việc
```

### Pattern Kiến Trúc: Request Collapsing

Trong các hệ thống highload, một CF được dùng để ngăn các request trùng lặp:

```java
public CompletableFuture<Data> getData(String key) {
    return inFlight.computeIfAbsent(key, k ->
        loadDataFromDb(k)
            .whenComplete((v, ex) -> inFlight.remove(k))
    );
}
// 100 request đồng thời cho cùng một key → 1 truy vấn DB thực tế
```

### Best Practices

```java
// ✅ Một CF → nhiều bên đăng ký (fan-out)
// ✅ Kết quả bất biến
// ✅ Dọn dẹp cache sau khi hoàn thành (whenComplete)
// ✅ Thứ tự rõ ràng thông qua thenCompose/thenCombine

// ❌ Sửa đổi kết quả chung
// ❌ Các chuỗi vô tận không hoàn thành
// ❌ Phụ thuộc vào thứ tự callback
// ❌ Tham chiếu bị quên trong cache đến các CF đã hoàn thành
```

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- Một CF có thể được dùng trong nhiều chuỗi — pattern fan-out
- Kết quả được tính toán đúng một lần, tất cả các bên đăng ký nhận cùng một object
- Promise Caching: Map<Key, CompletableFuture> để ngăn các request trùng lặp
- Request Collapsing: 100 request cho cùng một key → 1 truy vấn DB thực tế
- Thứ tự callback KHÔNG được JDK đảm bảo

**Các câu hỏi phụ thường gặp:**
- **Thứ tự callback có được đảm bảo không?** — Không. Nếu quan trọng — thực thi rõ ràng qua thenCompose/thenCombine
- **Memory leak xảy ra như thế nào?** — Chuỗi vô tận: mỗi CF giữ tham chiếu đến upstream, GC không thể thu gom
- **Việc hủy một chuỗi con có ảnh hưởng đến gốc không?** — Không. Hủy gốc — ảnh hưởng đến tất cả các con
- **Sửa đổi kết quả chung có phải là vấn đề không?** — Có, tất cả các chuỗi thấy cùng một object. Kết quả phải bất biến

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Mỗi bên đăng ký nhận một bản sao của kết quả" — tất cả đều nhận cùng một object
- "Thứ tự thenAccept được đảm bảo" — JDK không đảm bảo thứ tự
- "Không cần cache CF — CF tự dọn dẹp" — các CF đã hoàn thành cần được xóa khỏi cache
