# What types of OutOfMemoryError exist? (Có những loại OutOfMemoryError nào?)

## Junior Level

**OutOfMemoryError** có nhiều loại khác nhau — mỗi loại chỉ ra một vấn đề riêng:

| Loại                                     | Ý nghĩa là gì                    |
| ---------------------------------------- | -------------------------------- |
| **Java heap space**                      | Heap bị tràn                     |
| **GC overhead limit exceeded**           | GC chạy liên tục                 |
| **Metaspace**                            | Metadata của class bị tràn       |
| **Direct buffer memory**                 | Bộ nhớ nằm ngoài Heap (NIO)      |
| **Unable to create new native thread**   | Giới hạn luồng của OS            |

---

## Middle Level

### Java heap space

```
Nguyên nhân: rò rỉ hoặc -Xmx nhỏ
Giải pháp:
  1. -XX:+HeapDumpOnOutOfMemoryError
  2. Phân tích trong MAT
  3. Tìm rò rỉ hoặc tăng -Xmx
```

### GC overhead limit exceeded

```
98% thời gian dành cho GC, < 2% được giải phóng
→ Ứng dụng "đóng băng" trong một vòng lặp Full GC vô hạn

Giải pháp:
  - Tăng Heap
  - Tìm rò rỉ
  - Tắt: -XX:-UseGCOverheadLimit (không khuyến nghị!)
```

### Metaspace

```
Metadata của class bị tràn
Nguyên nhân:
  - Sinh class động (Spring, CGLIB)
  - Các ClassLoader leak

Giải pháp:
  -XX:MaxMetaspaceSize=512m
  jcmd <pid> VM.metaspace
```

### Direct buffer memory

```
Bộ nhớ NIO nằm ngoài Heap
Nguyên nhân: Netty, ByteBuffer.allocateDirect()

Giải pháp:
  -XX:MaxDirectMemorySize=2g
  Kiểm tra các rò rỉ Netty
```

### Unable to create new native thread

```
OS không thể tạo luồng
Nguyên nhân:
  - Đã đạt ulimit -u
  - RAM cho các stack (-Xss) đã cạn kiệt

Giải pháp:
  Giảm -Xmx (nhiều RAM hơn cho các stack)
  Kiểm tra ulimit -u
```

## Senior Level

### Requested array size exceeds VM limit

```
Mảng > Integer.MAX_VALUE phần tử
→ Thường chỉ ra một lỗi logic. Nhưng vẫn có các trường hợp hợp lệ: cố gắng nạp toàn bộ một file lớn vào bộ nhớ.
```

### Compressed Class Space

```
Compressed Class Space — một phần của Metaspace cho các con trỏ class được nén (4 byte thay vì 8).
Giới hạn: -XX:CompressedClassSpaceSize (mặc định 1 GB). Tràn → OOME, ngay cả khi Metaspace còn không gian trống.
```

### Map failed (Memory Mapped Files)

```
MappedByteBuffer.map() → lỗi
  → Đã đạt vm.max_map_count
  → Không còn bộ nhớ ảo cho việc mapping

Giải pháp: sysctl -w vm.max_map_count=262144
```

### Linux OOM Killer

```
KHÔNG phải là một lỗi của Java!
  → Container: giới hạn < RSS
  → OS giết tiến trình qua SIGKILL
  → Không có dump, không có logs!

Chẩn đoán:
  dmesg | grep -i oom
  → "Out of memory: Kill process"
```

### Bảng tóm tắt

| Loại                | Nơi cần tìm         | Flag          |
| ------------------- | ------------------- | ------------- |
| **Heap**            | Các rò rỉ Heap      | HeapDumpOnOOM |
| **Metaspace**       | Các ClassLoader leak | VM.metaspace  |
| **Direct buffer**   | Netty/NIO           | NMT           |
| **Native thread**   | ulimit, -Xss        | ps -Hu        |
| **GC overhead**     | Thrashing           | GC Logs       |

### Best Practices

1. **HeapDumpOnOutOfMemoryError** — bắt buộc
2. **NMT=detail** cho Native Memory
3. **MaxMetaspaceSize** — giới hạn cho các container
4. **MaxDirectMemorySize** — kiểm soát NIO
5. **Giám sát dmesg** cho OOM Killer
6. **jcmd VM.metaspace** để phân tích Metaspace

### Tóm tắt cho Senior

- **Loại OOME** = manh mối đầu tiên trong quá trình điều tra
- **Heap space** = các rò rỉ Heap
- **Metaspace** = các ClassLoader leak
- **Direct buffer** = các rò rỉ NIO (nằm ngoài Heap)
- **Native thread** = các giới hạn của OS
- **OOM Killer** = không phải lỗi của Java (các container)
- **NMT** = chẩn đoán Native Memory

---

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- `Java heap space` — Heap bị tràn; giải pháp: HeapDumpOnOOM + phân tích bằng MAT + tìm rò rỉ hoặc tăng -Xmx
- `GC overhead limit exceeded` — 98% thời gian dành cho GC, < 2% được giải phóng; vòng lặp Full GC vô hạn
- `Metaspace` — metadata của class bị tràn; nguyên nhân: sinh class động (Spring, CGLIB), các ClassLoader leak
- `Direct buffer memory` — bộ nhớ NIO nằm ngoài Heap; Netty, ByteBuffer.allocateDirect(); giải pháp: MaxDirectMemorySize
- `Unable to create new native thread` — đã đạt ulimit -u hoặc RAM cho các stack (-Xss) đã cạn kiệt
- `Requested array size exceeds VM limit` — mảng > Integer.MAX_VALUE; thường là một lỗi logic
- Linux OOM Killer — KHÔNG phải lỗi của Java! Container: giới hạn < RSS → OS giết qua SIGKILL → không có dump

**Các câu hỏi phụ thường gặp:**
- **Làm sao phân biệt JVM OOME với OS OOM Killer?** — JVM OOME: stack trace trong logs; OOM Killer: `dmesg | grep -i oom`, tiến trình biến mất không có logs
- **Compressed Class Space OOME là gì?** — Một phần của Metaspace cho các con trỏ class được nén (giới hạn 1 GB); tràn → OOME, ngay cả khi Metaspace còn trống
- **Tại sao "Requested array size exceeds VM limit" xảy ra?** — Cố gắng tạo mảng > Integer.MAX_VALUE phần tử; thường là một bug (nạp toàn bộ file lớn)
- **Làm sao chẩn đoán OOM Killer trong Kubernetes?** — `dmesg | grep -i oom`; Pod bị terminated (OOMKilled); giải pháp: tăng giới hạn hoặc giảm RSS

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi sẽ tắt `-XX:-UseGCOverheadLimit` và vấn đề được giải quyết" — điều này che khuất vấn đề; ứng dụng vẫn sẽ crash với Heap space OOME
- "OOM Killer là một bug của Java" — đó là quyết định của OS; Java không kiểm soát các giới hạn của container
- "Direct buffer memory = một phần của Heap" — DirectByteBuffer cấp phát bộ nhớ NẰM NGOÀI Heap (`-Xmx` không ảnh hưởng đến nó)
