# What happens when calling @Transactional method from another method of the same class? (Điều gì xảy ra khi gọi một method @Transactional từ một method khác trong cùng class?)

## 🟢 Junior Level

Nếu bạn gọi một method `@Transactional` từ một method khác **trong cùng class** — **annotation bị bỏ qua** và transaction không bắt đầu.

Đây được gọi là **vấn đề Self-invocation**.

### Ví Dụ Đơn Giản

```java
@Service
public class OrderService {

    public void createOrderExternal() {
        saveOrder();  // Lời gọi trong class — @Transactional KHÔNG hoạt động!
    }

    @Transactional
    public void saveOrder() {
        // Logic này thực thi KHÔNG có transaction
        orderRepository.save(order);
    }
}
```

### Ví Dụ Minh Họa

Hãy tưởng tượng bạn gọi cho một người bạn qua thư ký (Proxy). Thư ký ghi lại cuộc trò chuyện (quản lý transaction). Nhưng nếu bạn hét qua tường với bạn của mình (this) — thư ký không biết gì về cuộc trò chuyện đó.

### Tại Sao Điều Này Xảy Ra

Spring quản lý transaction thông qua một **object Proxy** (wrapper). Khi code bên ngoài gọi một method — nó đi qua proxy. Nhưng khi một method gọi một method khác của cùng class — lời gọi đi trực tiếp qua `this`, bỏ qua proxy.

**Cơ chế:** Spring tạo một object proxy chặn các lời gọi từ bên ngoài. Nhưng khi method A gọi method B của cùng object, `this.methodB()` đi trực tiếp — proxy không tham gia, TransactionInterceptor không kích hoạt.

### Các Quy Tắc Quan Trọng

- `@Transactional` chỉ hoạt động khi được gọi **từ bên ngoài** class
- `this.method()` — luôn bỏ qua proxy
- Các method private/protected không bao giờ bị chặn

### Cách Sửa

1. **Tách method sang một bean khác** (lựa chọn tốt nhất)
2. **Self-injection**: inject service vào chính nó với `@Lazy`
3. **TransactionTemplate**: quản lý transaction lập trình

### Khi Nào Self-Invocation KHÔNG Phải Là Vấn Đề

1. **Method không cần transaction** — nếu @Transactional chỉ để đảm bảo tính nhất quán nhưng method chỉ đọc
2. **Lời gọi bên ngoài đã ở trong transaction** — nếu outerMethod đã là @Transactional, innerMethod hoạt động trong cùng transaction (propagation = REQUIRED theo mặc định)
3. **Dùng chế độ AspectJ** — compile-time/load-time weaving chặn các lời gọi `this`

## 🟡 Middle Level

### Cơ Chế Proxy

```
Lời gọi bên ngoài:
Client → Proxy → TransactionInterceptor → TransactionManager → Method thực sự
                       ↓
               Mở transaction → Thực thi → COMMIT/ROLLBACK

Lời gọi bên trong (this):
Method A → this.method B() → Method thực sự (bỏ qua Proxy!)
                                ↓
                          Không có transaction!
```

Spring tạo một bean wrapper (Proxy) quanh object của bạn. Khi một client bên ngoài gọi một method, nó gọi trên **Proxy**. Proxy chặn lời gọi, mở transaction, và chuyển quyền điều khiển.

Lời gọi qua `this` đi trực tiếp đến object thực sự — proxy hoàn toàn bị bỏ qua.

### Các Giải Pháp

#### A. Tách Method Sang Một Bean Khác (Được Khuyến Nghị)

```java
@Service
public class OrderService {
    @Autowired
    private OrderRepositoryService orderRepositoryService;

    public void createOrderExternal() {
        orderRepositoryService.saveOrder();  // Qua một bean khác — hoạt động!
    }
}

@Service
public class OrderRepositoryService {
    @Transactional
    public void saveOrder() {
        // Giờ transaction hoạt động
    }
}
```

#### B. Self-Injection

```java
@Service
public class OrderService {

    @Autowired
    @Lazy  // Để tránh circular dependency
    private OrderService self;

    public void createOrderExternal() {
        self.saveOrder();  // Qua proxy — transaction hoạt động!
    }

    @Transactional
    public void saveOrder() {
        // Giờ transaction hoạt động
    }
}
```

#### C. TransactionTemplate

```java
@Service
public class OrderService {

    @Autowired
    private TransactionTemplate transactionTemplate;

    public void createOrderExternal() {
        transactionTemplate.execute(status -> {
            saveOrder();  // Transaction lập trình
            return null;
        });
    }

    public void saveOrder() {
        // Được thực thi trong transaction qua TransactionTemplate
    }
}
```

#### D. AspectJ

Chuyển sang AspectJ weaving sửa đổi bytecode tại thời điểm biên dịch, và các lời gọi trong class được chặn đúng cách. Yêu cầu cấu hình phức tạp.

### Các Lỗi Thường Gặp

| Lỗi                                      | Điều gì xảy ra                                    | Cách khắc phục                                |
| -------------------------------------------- | ----------------------------------------------- | ----------------------------------------- |
| Không biết về self-invocation            | Code hoạt động trong test, thất bại trong production        | Tách sang bean riêng biệt                  |
| Self-injection không có `@Lazy`               | `BeanCurrentlyInCreationException`              | Thêm `@Lazy`                               |
| `AopContext.currentProxy()` không có `exposeProxy` | `IllegalStateException: Cannot find current proxy` | `@EnableAspectJAutoProxy(exposeProxy = true)` |
| Trộn lẫn các cách tiếp cận                            | Hành vi khó dự đoán                          | Chọn một cách tiếp cận                       |

### So Sánh Các Giải Pháp

| Giải pháp                  | Độ phức tạp | Self-invocation | Method private | Được khuyến nghị                |
| ------------------------- | ---------- | --------------- | --------------- | -------------------------- |
| Tách sang bean riêng biệt  | Thấp        | ✅               | ❌               | ✅ Tốt nhất                     |
| Self-injection (@Lazy)    | Thấp        | ✅               | ❌               | Tốt                       |
| AopContext.currentProxy() | Trung bình     | ✅               | ❌               | Được                         |
| TransactionTemplate       | Trung bình     | ✅               | ✅               | Tốt cho logic phức tạp     |
| AspectJ weaving           | Cao       | ✅               | ✅               | Chỉ khi cần thiết             |

### Khi Nào KHÔNG Nên Dùng Các Giải Pháp

| Tình huống                            | Tại sao                                               | Giải pháp thay thế               |
| ------------------------------------ | ------------------------------------------------- | ------------------------- |
| Method không cần transaction riêng  | Self-invocation không phải vấn đề nếu bên gọi đã ở trong tx | Giữ nguyên như vậy           |
| Method chỉ đọc đơn giản              | ReadOnly không cần transaction phức tạp       | `readOnly = true` trên bên gọi |
| Method là tiện ích, không phải logic nghiệp vụ | Không thuộc về tầng service                  | Tách sang util class     |

## 🔴 Senior Level

### AOP Dựa Trên Proxy — Phân Tích Nguyên Nhân Gốc Rễ

#### Cách Spring Tạo Proxy

**JDK Dynamic Proxy:**
```java
UserService proxy = (UserService) Proxy.newProxyInstance(
    classLoader,
    new Class[]{UserService.class},
    new TransactionalInvocationHandler(target, interceptor)
);
```

**CGLIB:**
```java
UserService proxy = (UserService) Enhancer.create(
    UserService.class,
    new TransactionalMethodInterceptor(target, interceptor)
);
```

Trong cả hai trường hợp, proxy bọc object mục tiêu. Các lời gọi bên ngoài đi qua proxy → interceptor → mục tiêu. Các lời gọi bên trong (`this.method()`) đi trực tiếp: mục tiêu → mục tiêu. Điều này đúng cho cả JDK Dynamic Proxy và CGLIB — trong cả hai trường hợp `this` tham chiếu đến object mục tiêu, không phải proxy. CGLIB tạo một subclass, nhưng `this` bên trong các method của subclass vẫn trỏ đến object mục tiêu.

#### Vấn Đề Tham Chiếu `this`

```java
public class OrderService {
    // this = OrderService@123 (object MỤC TIÊU, không phải proxy)

    public void createOrderExternal() {
        // this.saveOrder() gọi mục tiêu trực tiếp
        // Bỏ qua: OrderServiceProxy@456.saveOrder()
        saveOrder();
    }
}
```

`this` luôn trỏ đến object thực sự, không bao giờ trỏ đến proxy. Không có cách nào để Spring chặn các lời gọi `this.*()` với AOP tiêu chuẩn.

### Đào Sâu Vào Các Giải Pháp

#### Giải Pháp 1: Self-Injection Với @Lazy

```java
@Service
public class OrderService {
    @Autowired
    @Lazy
    private OrderService self;

    public void createOrderExternal() {
        // self = proxy (OrderService$$EnhancerBySpringCGLIB$$...)
        self.saveOrder();  // Đi qua proxy → interceptor
    }
}
```

**Tại sao @Lazy:** Không có `@Lazy`, Spring cố inject `OrderService` trong lúc nó đang được tạo → lỗi circular dependency. `@Lazy` tạo một proxy lazy giải quyết bean thực sự khi lần đầu được sử dụng.

#### Giải Pháp 2: AopContext.currentProxy()

```java
@EnableAspectJAutoProxy(exposeProxy = true)  // Bắt buộc!

@Service
public class OrderService {
    public void createOrderExternal() {
        ((OrderService) AopContext.currentProxy()).saveOrder();
    }
}
```

**Cách nó hoạt động:** `exposeProxy = true` lưu proxy trong ThreadLocal. `AopContext.currentProxy()` lấy nó ra.

**Nhược điểm:** Gắn kết chặt chẽ với API của Spring, ThreadLocal — không hoạt động xuyên thread, `exposeProxy` có overhead về hiệu năng.

// exposeProxy = true thêm overhead trên mỗi lời gọi (ThreadLocal).
// Đừng dùng trong highload. Thay thế: tách method sang bean riêng biệt.

#### Giải Pháp 3: Các Transaction Lập Trình

```java
@Service
public class OrderService {
    @Autowired
    private PlatformTransactionManager transactionManager;

    public void createOrderExternal() {
        TransactionTemplate template = new TransactionTemplate(transactionManager);
        template.execute(status -> {
            saveOrder();  // Trong transaction
            return null;
        });
    }
}
```

**Ưu điểm:** Không cần proxy, ranh giới transaction tường minh, hoạt động trong bất kỳ context nào.
**Nhược điểm:** Dài dòng hơn, trộn lẫn quản lý transaction với logic nghiệp vụ.

### AspectJ Weaving — Giải Pháp "Vũ Khí Hạt Nhân"

#### Compile-Time Weaving

```xml
<plugin>
    <groupId>org.codehaus.mojo</groupId>
    <artifactId>aspectj-maven-plugin</artifactId>
    <configuration>
        <aspectLibraries>
            <aspectLibrary>
                <groupId>org.springframework</groupId>
                <artifactId>spring-aspects</artifactId>
            </aspectLibrary>
        </aspectLibraries>
    </configuration>
</plugin>
```

Sửa đổi bytecode tại thời điểm biên dịch:
```java
// TRƯỚC
public void createOrderExternal() { saveOrder(); }

// SAU (đã được AspectJ-weave)
public void createOrderExternal() {
    TransactionInterceptor.invoke(this, "saveOrder", ...);
    saveOrder();
}
```

**Lợi ích:** Self-invocation hoạt động, các method private/protected có thể là `@Transactional`, không có giới hạn của proxy.
**Nhược điểm:** Cấu hình build phức tạp, sửa đổi bytecode (khó debug hơn), hỗ trợ IDE hạn chế, không tương thích với tất cả các tính năng của Spring Boot.

### Các Trường Hợp Biên (Tối Thiểu 3)

1. **`@Transactional` trên interface + CGLIB**: Nếu proxy là CGLIB (dựa trên class), annotation trên interface không hiển thị. Self-invocation đã không hoạt động rồi, cộng thêm annotation không được áp dụng cho proxy. Vấn đề kép.

2. **Self-invocation lồng nhau**: `methodA()` → `this.methodB()` (không tx) → `this.methodC()` (có `@Transactional`). Cả B lẫn C đều không transactional. Toàn bộ chuỗi bị bỏ qua.

3. **`@Transactional(propagation = REQUIRES_NEW)` với self-invocation**: Ngay cả `REQUIRES_NEW` cũng sẽ không hoạt động trên lời gọi `this.method()`. Transaction mới sẽ không mở — method thực thi trong context của bên gọi (không có transaction nếu bên gọi cũng không ở trong tx).

4. **Self-invocation và `@Async`**: Các method `@Async` cũng đi qua proxy. `this.asyncMethod()` — method thực thi đồng bộ, không bất đồng bộ. Bỏ qua proxy kép: cả transaction lẫn async.

5. **Lời gọi từ constructor**: Nếu constructor gọi một method `@Transactional` — proxy chưa được tạo (việc khởi tạo bean chưa hoàn thành). Lời gọi luôn đi trực tiếp.

### JDK Proxy vs CGLIB Cho Self-Invocation

| Đặc điểm      | JDK Dynamic Proxy    | CGLIB                    |
| -------------------- | -------------------- | ------------------------ |
| Self-invocation      | ❌ Không hoạt động       | ❌ Không hoạt động           |
| Method final        | N/A (interface)      | ❌ Không bị chặn        |
| Method private      | ❌ Không bị chặn    | ❌ Không bị chặn        |
| Overhead hiệu năng | Thấp                  | Trung bình                   |
| Sinh bytecode  | Không                    | Có (sinh subclass) |

Cả hai loại proxy đều **không giải quyết** vấn đề self-invocation. Chỉ AspectJ weaving mới giải quyết được.

### Các Con Số Về Hiệu Năng

| Thao tác                         | Thời gian                          |
| --------------------------------- | ------------------------------ |
| Overhead lời gọi proxy         | ~1-2 μs                        |
| Tra cứu AopContext.currentProxy()  | ~0.5 μs (ThreadLocal get)      |
| Overhead exposeProxy              | ~0.1 μs mỗi lời gọi               |
| Giải quyết self-injection (@Lazy) | ~1 μs (lần gọi đầu), 0 (đã cache) |

### Tác Động Đến Bộ Nhớ

- `exposeProxy = true`: ThreadLocal cho mỗi proxy — ~1 KB mỗi thread đang hoạt động
- Self-injection: tham chiếu proxy thêm trong bean — không đáng kể (~8 byte)
- AspectJ weaving: Sửa đổi bytecode — file class lớn hơn, không có tác động bộ nhớ tại thời điểm chạy

### Thread Safety

AopContext.currentProxy() dùng ThreadLocal — không hoạt động xuyên thread. Các method `@Async` trong một thread khác sẽ không nhận proxy từ ThreadLocal của bên gọi. Tham chiếu proxy self-injection — thread-safe (tham chiếu proxy singleton).

### Câu Chuyện Thực Tế Trong Production

Service xử lý đơn hàng: `createOrder()` gọi `this.validateOrder()` (có `@Transactional`). Validation ghi audit log vào DB. Trong test (một thread duy nhất, không có contention) — hoạt động. Trong production — audit log không được ghi, vì transaction không mở. Dữ liệu bị mất. Sửa lỗi: `validateOrder()` được tách sang `OrderValidationService` riêng biệt.

### Giám Sát

**Phát hiện self-invocation tại thời điểm chạy:**
```java
@Bean
public BeanPostProcessor selfInvocationDetector() {
    return new BeanPostProcessor() {
        @Override
        public Object postProcessAfterInitialization(Object bean, String beanName) {
            if (AopUtils.isAopProxy(bean)) {
                // Log: bean này có một proxy — self-invocation sẽ bỏ qua nó
            }
            return bean;
        }
    };
}
```

### Best Practices Cho Highload

1. **Tách sang bean riêng biệt — luôn luôn**: Đây không phải là một cách giải quyết tạm thời, mà là sự phân tách trách nhiệm đúng đắn. Nếu một method cần transaction riêng của nó — nó nên có trách nhiệm riêng của nó.
2. **Tránh `AopContext.currentProxy()`**: Gắn kết chặt chẽ, vấn đề ThreadLocal, overhead hiệu năng. Không dùng cho production.
3. **Self-invocation = code smell**: Nếu bạn đang chiến đấu với self-invocation — service có lẽ đang làm quá nhiều việc. Chia nhỏ theo SRP.
4. **Kiểm thử hành vi self-invocation**: Unit test với Mockito không bắt được vấn đề này (mock của Mockito đi qua proxy). Cần integration test của Spring.
5. **Cân nhắc các transaction lập trình**: Với logic điều kiện phức tạp, `TransactionTemplate` sạch hơn là chiến đấu với proxy.
6. **Quy tắc kiến trúc**: Đưa vào test ArchUnit: `noClass().should().callMethodWhere(target declaresAnnotation(Transactional.class)).fromSameClass()`.

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Vấn đề self-invocation: gọi method @Transactional qua `this` bỏ qua Spring Proxy
- Spring quản lý transaction thông qua AOP Proxy (JDK Dynamic Proxy hoặc CGLIB)
- `this.method()` đi trực tiếp đến object mục tiêu — TransactionInterceptor không kích hoạt
- 4 giải pháp: tách sang bean khác (tốt nhất), self-injection @Lazy, AopContext.currentProxy(), TransactionTemplate
- REQUIRES_NEW cũng KHÔNG hoạt động với self-invocation — transaction mới sẽ không mở
- @Async với self-invocation thực thi đồng bộ — bỏ qua proxy kép

**Các câu hỏi phụ thường gặp:**
- Tại sao proxy không chặn các lời gọi this? — `this` luôn tham chiếu đến object mục tiêu, không phải proxy
- JDK Proxy vs CGLIB trong ngữ cảnh self-invocation? — Cả hai đều KHÔNG giải quyết vấn đề self-invocation
- Khi nào self-invocation KHÔNG phải là vấn đề? — Nếu bên gọi đã ở trong @Transactional (propagation REQUIRED tham gia)
- Tại sao Mockito không bắt được vấn đề này? — Mock của Mockito = proxy, self-invocation hoạt động trên mock

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Self-invocation hoạt động trong production" — proxy bị bỏ qua, transaction không mở
- "REQUIRES_NEW giải quyết self-invocation" — REQUIRES_NEW cũng cần proxy
- "AopContext.currentProxy() = best practice" — gắn kết chặt chẽ với API của Spring, overhead ThreadLocal
