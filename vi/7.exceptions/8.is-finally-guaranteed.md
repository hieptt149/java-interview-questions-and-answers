# Is the execution of a finally block guaranteed? (Việc thực thi khối finally có được đảm bảo không?)

## Junior Level

### Nguyên tắc cơ bản

Khối `finally` **luôn luôn** thực thi (với vài ngoại lệ hiếm gặp - xem Middle Level). Với người mới bắt đầu, hãy coi finally là được đảm bảo thực thi.

```java
try {
    System.out.println("try");
} finally {
    System.out.println("finally"); // Chắc chắn sẽ thực thi
}
// Output: try \n finally
```

### Với một exception

```java
try {
    throw new RuntimeException("Error");
} finally {
    System.out.println("Cleanup"); // Vẫn thực thi
}
// Output: Cleanup, rồi exception lan truyền tiếp
```

### Tại sao cần finally

Để giải phóng resource - đóng file, connection, lock:

```java
FileInputStream fis = null;
try {
    fis = new FileInputStream("file.txt");
    // làm việc với file
} finally {
    if (fis != null) fis.close(); // Sẽ đóng trong mọi trường hợp
}
```

Trong Java hiện đại, hãy dùng **try-with-resources** - nó làm việc này tự động.

## Middle Level

### Khi nào KHÔNG nên dùng finally

Để đóng resource, hãy dùng **try-with-resources** thay vì finally với close(). Dùng finally cho: giải phóng lock (ReentrantLock.unlock()), khôi phục trạng thái (Thread.currentThread().interrupt()), ghi log.

### Cách hoạt động trong bytecode

Trong Java cũ (trước 6), lệnh `jsr` (Jump to Subroutine) được dùng. Trong Java hiện đại, compiler **sao chép** bytecode của khối `finally` vào tất cả các nhánh thoát của phương thức - sau `try`, sau mỗi `catch`, và trong bộ xử lý exception ngầm định.

Điều này làm tăng kích thước phương thức nhưng làm cho control flow tuyến tính.

### Khi nào finally sẽ KHÔNG thực thi

1. **`System.exit(n)`** - kết thúc JVM một cách cưỡng bức
2. **`Runtime.halt(n)`** - còn khắc nghiệt hơn, thậm chí không chạy các Shutdown Hook
3. **Vòng lặp vô hạn** trong `try` - thread không bao giờ tới được điểm thoát
4. **Deadlock** - thread bị chặn mãi mãi
5. **Kill -9** - tín hiệu `SIGKILL` giết tiến trình ở mức OS
6. **Daemon Thread** - nếu chỉ còn lại các daemon, JVM kết thúc mà không chờ
7. **JVM crash** - `VirtualMachineError` tại thời điểm chuyển sang `finally`

### Nguy hiểm: ghi đè return

```java
int method() {
    try { return 1; }
    finally { return 2; }
}
// Trả về 2! finally ghi đè giá trị trả về
```

`return` trong finally thực thi SAU KHI giá trị đã được chuẩn bị trong try. Finally có cơ hội cuối cùng để thay đổi kết quả. Trong bytecode: giá trị từ try được lưu vào một biến tạm, finally thực thi, và nếu nó có `return` của riêng mình - nó ghi đè kết quả.

### Nguy hiểm: nuốt exception

```java
try {
    throw new RuntimeException("Original error");
} finally {
    throw new RuntimeException("Finally error");
}
// Exception gốc bị mất vĩnh viễn!
```

## Senior Level

### Shadowing - mất Root Cause

Shadowing - khi một exception "che giấu" một exception khác.
Root Cause - exception đầu tiên nhất trong chuỗi, thứ đã gây ra tất cả những cái còn lại.

Nếu exception A xảy ra trong `try`, và exception B trong `finally`, thì A sẽ bị **mất**:

```java
try {
    // SQLException - DB không khả dụng
    connection.executeQuery("...");
} finally {
    // NPE - che khuất SQLException
    connection.close(); // connection == null
}
// Log chỉ hiện NPE, không có thông tin về DB
```

**Giải pháp:** try-with-resources thêm các exception từ `close()` vào danh sách `suppressed`, thay vì ghi đè cái chính.

### Mẫu đúng cho lock

```java
Lock lock = new ReentrantLock();
lock.lock(); // Lock TRƯỚC try
try {
    // vùng tới hạn (critical section)
} finally {
    lock.unlock(); // Luôn giải phóng
}
```

Hãy đảm bảo `lock()` nằm **trước** `try`. Nếu `lock()` ném exception, `unlock()` sẽ cố giải phóng một lock chưa được giành -> `IllegalMonitorStateException`.

### Cạm bẫy Locking trong finally

Nếu `finally` gọi một phương thức có thể bị chặn (ghi ra log trên một đĩa đầy), bạn sẽ làm treo toàn bộ thread dọn dẹp resource.

### finally và try-with-resources

```java
try (Resource r = new Resource()) {
    // làm việc
} catch (Exception e) {
    // resource ĐÃ được đóng ở đây rồi
} finally {
    // resource cũng đã được đóng rồi
}
```

Các khối `catch` và `finally` viết thủ công thực thi **sau** khi resource được đóng tự động.

### Chẩn đoán

- **Deadlock trong finally** - nếu `finally` gọi một phương thức chặn, thread sẽ treo
- Giữ code trong `finally` càng đơn giản và nhanh càng tốt
- Luôn bảo vệ `finally` khỏi các exception mới
- Để phân tích dùng `javap -c` - bạn sẽ thấy cách `finally` được sao chép vào tất cả các nhánh

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- `finally` luôn thực thi (với vài ngoại lệ hiếm gặp)
- Khi nào finally sẽ KHÔNG thực thi: `System.exit()`, `Runtime.halt()`, vòng lặp vô hạn, deadlock, kill -9, daemon thread, JVM crash
- `return` trong `finally` ghi đè giá trị từ `try` - trả về giá trị từ finally
- Exception trong `finally` ghi đè exception chính từ `try` (shadowing)
- Compiler sao chép bytecode của `finally` vào tất cả các nhánh - làm tăng kích thước phương thức
- Để đóng resource dùng try-with-resources, không phải finally
- Dùng finally cho: giải phóng lock, khôi phục trạng thái, ghi log
- Các khối `catch` và `finally` thực thi SAU khi resource được đóng tự động trong TWR

**Các câu hỏi phụ thường gặp:**
- **finally có thể không thực thi không?** - Có: System.exit(), kill -9, vòng lặp vô hạn, JVM crash
- **Điều gì xảy ra với return trong finally?** - Ghi đè giá trị trả về từ try - đây là một bug
- **Exception shadowing là gì?** - Exception từ finally ghi đè cái chính từ try; giải pháp - try-with-resources với suppressed
- **Mẫu đúng cho lock?** - `lock.lock()` TRƯỚC try, `lock.unlock()` trong finally

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Finally thực thi tuyệt đối luôn luôn" - không, System.exit() và kill -9 dừng JVM
- "Tôi dùng return trong finally để trả về một giá trị mặc định" - đây là anti-pattern, ghi đè kết quả của try
- "Tôi bắt exception trong finally và tiếp tục" - exception gốc bị mất vĩnh viễn
