# What is visibility problem? (Vấn đề visibility là gì?)

---

## Junior Level

### Hiểu biết cơ bản

**Visibility Problem** (vấn đề khả năng nhìn thấy) là tình huống một thread sửa đổi một biến, nhưng một thread khác vẫn tiếp tục nhìn thấy giá trị cũ.

**Tại sao:** mỗi CPU core có cache riêng (L1/L2). Một thread đọc một biến từ cache của core mình. Khi một thread khác trên core khác thay đổi biến đó, bản cập nhật ban đầu nằm lại trong cache của core đó và không lập tức được mọi thread nhìn thấy.

### Ví dụ đơn giản

```java
public class VisibilityDemo {
    private boolean flag = false; // KHÔNG có volatile

    public void setFlag() {
        flag = true; // Thread 1 sửa đổi
    }

    public void checkFlag() {
        while (!flag) {
            // Thread 2 có thể KHÔNG BAO GIỜ thoát khỏi vòng lặp!
            // Nó thấy bản sao cục bộ flag = false
        }
        System.out.println("Flag is true");
    }
}
```

### Tại sao điều này xảy ra?

Mỗi thread có thể lưu các bản sao của biến trong:
- **CPU register** — nhanh nhất, nhưng hoàn toàn cục bộ
- **CPU cache (L1/L2/L3)** — nhanh, nhưng không phải lúc nào cũng được đồng bộ
- **Main memory (RAM)** — dùng chung, nhưng chậm

### Giải pháp

Dùng `volatile`:

```java
public class VisibilityDemo {
    private volatile boolean flag = false; // Với volatile — luôn thấy giá trị mới nhất. volatile chèn một memory barrier: khi ghi — flush cache line xuống RAM (Store barrier), khi đọc — vô hiệu hóa cache line và đọc lại từ RAM (Load barrier).

    public void setFlag() {
        flag = true; // Mọi thread sẽ thấy giá trị này ngay lập tức
    }

    public void checkFlag() {
        while (!flag) {
            // Bây giờ thread 2 chắc chắn thấy thay đổi
        }
        System.out.println("Flag is true");
    }
}
```

### Khi nào vấn đề visibility xảy ra?

| Tình huống                                 | Xảy ra? | Giải pháp               |
| ------------------------------------------ | ------- | ----------------------- |
| Biến thông thường, nhiều thread            | Có      | volatile / synchronized |
| Biến `volatile`                            | Không   | —                       |
| Block `synchronized`                       | Không   | —                       |
| Field `final` (sau constructor)            | Không   | —                       |
| `AtomicInteger`                            | Không   | —                       |

## Middle Level

### Nguyên nhân vật lý (mức phần cứng)

Các bộ xử lý hiện đại có một phân cấp bộ nhớ phức tạp:

```
CPU Registers → L1 Cache (32-64KB) → L2 Cache (256KB-1MB) → L3 Cache (8-64MB) → RAM
   ~1 cycle        ~4 cycles             ~10 cycles            ~40 cycles         ~100 cycles
```

#### Điều gì xảy ra khi ghi

1. Thread trên Core 1 thay đổi biến → ghi vào **Store Buffer**

Store Buffer — buffer ghi của CPU. Khi một core ghi dữ liệu, nó đi vào Store Buffer trước, không trực tiếp xuống cache/RAM. Điều này tăng tốc việc ghi (bộ xử lý không phải chờ), nhưng tạo ra vấn đề visibility.

2. Dữ liệu đi vào **L1 cache của Core 1**
3. Core 2 đọc biến → lấy nó từ **L1 cache của chính nó** (giá trị cũ!)
4. Giao thức **MESI** đồng bộ các cache, nhưng việc này xảy ra bất đồng bộ

### Giao thức MESI

Giao thức MESI (Modified, Exclusive, Shared, Invalid) — một giao thức nhất quán cache (cache coherency) cho CPU nhiều core. Khi một core ghi dữ liệu (Modified), nó gửi tín hiệu tới các core khác — bản sao của chúng trở thành Invalid và phải được đọc lại từ RAM.

| Trạng thái        | Ý nghĩa                                              |
| ----------------- | ---------------------------------------------------- |
| **Modified (M)**  | Dữ liệu đã sửa trong cache này, cần được flush xuống RAM |
| **Exclusive (E)** | Dữ liệu chỉ có trong cache này, giống hệt RAM        |
| **Shared (S)**    | Dữ liệu tồn tại trong nhiều cache, tất cả giống RAM  |
| **Invalid (I)**   | Dữ liệu đã cũ (ai đó khác đã sửa nó)                 |

Khi một thread ghi vào một `volatile`, nó phát tín hiệu cho tất cả các core vô hiệu hóa bản sao của chúng.

### Các tối ưu hóa JIT làm vấn đề tệ hơn

#### Hoisting

Hoisting — trình biên dịch JIT nâng (hoist) việc đọc biến ra khỏi vòng lặp vào một register, tránh việc đọc từ RAM mỗi vòng lặp. Không có volatile, JIT "không biết" rằng một thread khác có thể thay đổi biến.

```java
// Code nguồn:
while (!flag) {
    doSomething(); // flag không thay đổi bên trong vòng lặp
}

// JIT có thể tối ưu thành:
if (!flag) {
    while (true) {
        doSomething(); // Vòng lặp vô hạn, ngay cả khi flag thay đổi!
    }
}
```

#### Register Allocation

Một biến có thể được cache trong một register của CPU, thứ hoàn toàn không nằm trong hệ thống nhất quán cache.

### Các cách giải quyết

#### 1. volatile

```java
volatile boolean flag = false;
```

Đảm bảo:
- Đọc luôn từ main memory
- Ghi luôn xuống main memory
- Ngăn việc sắp xếp lại (memory barrier)

#### 2. synchronized

```java
synchronized(lock) {
    while (!flag) {
        // ...
    }
}
```

Khi vào synchronized — cache bị vô hiệu hóa
Khi ra — dữ liệu được flush xuống RAM

#### 3. final field

```java
public class Config {
    public final String value; // Đảm bảo visibility sau constructor

    public Config(String value) {
        this.value = value;
    }
}
```

#### 4. Các lớp Atomic

```java
AtomicBoolean flag = new AtomicBoolean(false);
// Bên trong: volatile + CAS
```

### Khi nào volatile KHÔNG giải quyết vấn đề visibility

1. **Các thao tác gộp**: `volatile count++` — đọc và ghi không atomic
2. **Nhóm các biến**: volatile trên `x` và `y` không đảm bảo một thread khác thấy một cặp (x, y) nhất quán
3. **Các phép tính phụ thuộc**: kết quả phụ thuộc vào nhiều biến, mỗi biến volatile — nhưng tổ hợp của chúng có thể không nhất quán

## Senior Level

### Bên trong: giao thức Cache Coherence

Ở mức kiến trúc x86, giao thức **MESIF** (MESI mở rộng) được dùng:

| Sự kiện                    | Hành động                                                    |
| ------------------------- | ----------------------------------------------------------- |
| Ghi vào cache line        | Chuyển sang Modified, gửi Invalidate tới mọi core khác      |
| Đọc cache line ở Shared   | Có thể đọc không hạn chế                                    |
| Đọc cache line ở Invalid  | Yêu cầu dữ liệu từ RAM hoặc từ cache khác                   |
| Ghi vào cache line Modified | Ghi cục bộ, các core khác không được thông báo cho tới khi có xung đột |

#### Bus Traffic và Cache Invalidation

Khi core 1 ghi vào một biến volatile:
1. Một thông điệp **Invalidate** được gửi trên bus (Ring Bus / Mesh)
2. Tất cả các core khác kiểm tra cache của chúng
3. Các core có cache line đó phản hồi bằng **Ack** và chuyển sang Invalid
4. Chỉ sau khi có tất cả các Ack thì lần ghi mới được coi là hoàn tất

Việc này mất **hàng trăm chu kỳ CPU** — đó là lý do ghi volatile đắt hơn đọc.

### False Sharing — một vấn đề hiệu năng

```java
public class FalseSharingDemo {
    // Cả hai volatile trong cùng một cache line (64 byte)
    public volatile long counter1 = 0;
    public volatile long counter2 = 0;
}
```

Khi thread 1 ghi vào `counter1`, cache line bị vô hiệu hóa với thread 2, ngay cả khi nó đang làm việc với `counter2`.

#### Giải pháp: @Contended

```java
public class ContendedDemo {
    @Contended
    public volatile long counter1 = 0;

    @Contended
    public volatile long counter2 = 0;
}
```

`@Contended` thêm **padding** (128 byte) xung quanh biến để nó chiếm một cache line riêng.

Cần `-XX:-RestrictContended` để dùng trong code người dùng (Java 8+).

### Padding thủ công (cho Java cũ)

```java
public class PaddedCounter {
    // Padding trước biến
    public long p1, p2, p3, p4, p5, p6, p7;
    public volatile long value = 0;
    // Padding sau biến
    public long q1, q2, q3, q4, q5, q6, q7;
}
```

### Hiệu năng và tải cao (Highload)

#### Benchmark (xấp xỉ)

| Thao tác                       | Thời gian  | Ghi chú        |
| ------------------------------ | ---------- | -------------- |
| Đọc thông thường               | ~1 ns      | Từ cache       |
| Đọc volatile                   | ~5-10 ns   | Có rào chắn    |
| Ghi thông thường               | ~1 ns      | Xuống cache    |
| Ghi volatile                   | ~50-100 ns | Có Invalidate  |
| synchronized (không tranh chấp)| ~10-20 ns  | Thin lock      |
| synchronized (có tranh chấp)   | ~1000+ ns  | Context switch |

#### Write Barrier

Việc dùng `volatile` làm chậm việc ghi nhiều hơn việc đọc:
- **Read**: chỉ rào chắn (LoadLoad + LoadStore)
- **Write**: rào chắn + vô hiệu hóa các cache khác + chờ Ack

### Chẩn đoán

#### `-XX:+PrintAssembly`

Cho phép bạn thấy các lệnh CPU thực tế:

```bash
java -XX:+PrintAssembly -XX:+UnlockDiagnosticVMOptions
```

Tìm lệnh `lock` trước một lần ghi — đó là Memory Barrier trên x86:

```assembly
lock or dword ptr [rsp], 0  # StoreLoad barrier
mov [rax], 1                # ghi volatile
```

#### Flaky Test

Các vấn đề visibility là nguyên nhân chính của các test mà:
- Pass ở máy local (1-2 core)
- Fail trên CI server (8+ core)
- Fail "thỉnh thoảng" (timing của race condition)

#### Java Memory Model Stress Testing

```java
@JCStressTest
public class VisibilityStressTest {
    int x = 0;
    volatile boolean ready = false;

    @Actor
    public void writer() {
        x = 42;
        ready = true;
    }

    @Actor
    public void reader(IntResult2 r) {
        if (ready) {
            r.r1 = x; // Luôn phải là 42
        }
    }
}
```

### Best Practices

1. **Luôn dùng `volatile`** cho các cờ được đọc từ các thread khác nhau
2. **Tránh** lưu trạng thái dùng chung trong các field thông thường
3. **Field `final`** — một cách miễn phí để đảm bảo visibility của dữ liệu bất biến
4. **Cẩn thận với False Sharing** cho các field volatile được cập nhật thường xuyên
5. **Test** trên các hệ thống đa xử lý, không chỉ ở local
6. **Dùng JCStress** để stress test code đa luồng

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Vấn đề visibility: một thread thay đổi một biến, thread khác thấy giá trị cũ từ cache của core
- Nguyên nhân: phân cấp bộ nhớ (register → cache L1/L2/L3 → RAM), mỗi core có cache riêng
- Giao thức MESI (Modified, Exclusive, Shared, Invalid) đảm bảo nhất quán cache
- Tối ưu hóa hoisting của JIT có thể nâng một lần đọc ra khỏi vòng lặp → vòng lặp vô hạn nếu không có volatile
- 4 giải pháp: volatile, synchronized, final field, các lớp Atomic
- Volatile KHÔNG giải quyết vấn đề cho các thao tác gộp và nhóm các biến
- False Sharing: hai biến volatile trong cùng một cache line — ghi vào một cái làm vô hiệu hóa cái kia

**Các câu hỏi phụ thường gặp:**
- **Tại sao một test pass ở local nhưng fail trên CI?** — Local 1-2 core (ít vấn đề cache hơn), CI — 8+ core
- **Store Buffer là gì?** — Buffer ghi của CPU; các lần ghi đi vào đó trước, không phải xuống RAM — nguyên nhân của vấn đề visibility
- **JIT làm vấn đề tệ hơn như thế nào?** — Hoisting: nâng việc đọc biến ra khỏi vòng lặp vào register, bỏ qua các thay đổi từ thread khác
- **@Contended làm gì?** — Thêm padding (128 byte) xung quanh volatile để tránh false sharing

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Volatile giải quyết mọi vấn đề đa luồng" — không, chỉ visibility của một biến duy nhất
- "CPU cache luôn được đồng bộ" — không, MESI hoạt động bất đồng bộ
- "Synchronized chậm hơn volatile cho một cờ đơn giản" — không, volatile rẻ hơn cho các trường hợp đơn giản
- "Final field không liên quan gì đến visibility" — có liên quan: các field final được nhìn thấy sau constructor
