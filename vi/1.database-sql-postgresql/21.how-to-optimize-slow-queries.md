# How to optimize slow queries? (Cách tối ưu các truy vấn chậm?)

## 🟢 Junior Level

**Tối ưu hóa truy vấn** là quá trình tăng tốc các câu lệnh SQL chạy chậm.

**Thuật toán đơn giản:**
1. Tìm ra truy vấn chậm
2. Xem plan của nó thông qua `EXPLAIN`
3. Hiểu điều gì đang làm nó chậm
4. Khắc phục (thường gặp nhất — thêm một index)

**Ví dụ:**
```sql
-- 1. Tìm ra truy vấn chậm
-- (log ứng dụng, pg_stat_statements)

-- 2. Kiểm tra plan
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'test@example.com';

-- 3. Ta thấy được vấn đề
-- Seq Scan on users  ← đọc toàn bộ bảng!
--   Rows Removed by Filter: 999999

-- 4. Khắc phục
CREATE INDEX idx_users_email ON users(email);

-- Bây giờ:
-- Index Scan using idx_users_email  ← nhanh!
-- Execution Time: 0.05 ms (trước đó là 500 ms)
```

**Các nguyên nhân phổ biến nhất gây ra truy vấn chậm:**
- ❌ Không có index trên trường trong WHERE
- ❌ Có index nhưng không được sử dụng (do có hàm trong WHERE)
- ❌ Tập kết quả quá lớn (không có LIMIT)
- ❌ JOIN mà không có index trên các trường join

## 🟡 Middle Level

### Thuật toán tối ưu hóa

**Bước 1: Tìm ra các truy vấn có vấn đề**
```sql
-- pg_stat_statements — công cụ chính
CREATE EXTENSION pg_stat_statements;

-- Top 10 truy vấn chậm nhất
SELECT query, calls, mean_exec_time, total_exec_time
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;

-- Top 10 truy vấn đọc từ đĩa nhiều nhất
SELECT query, shared_blks_read, mean_exec_time
FROM pg_stat_statements
ORDER BY shared_blks_read DESC
LIMIT 10;
```

**Bước 2: Phân tích plan**
```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT ...;

-- Tìm kiếm:
-- Seq Scan trên các bảng lớn → cần một index
-- Sort → tràn ra đĩa (Disk Spill) → tăng work_mem
-- Nested Loop trên các bảng lớn → plan không tốt
-- rows ≠ actual rows → thống kê lỗi thời
```

**Bước 3: Khắc phục**

### Các vấn đề thường gặp và giải pháp

**1. Không có index**
```sql
-- ❌ Seq Scan trên 1 triệu dòng
SELECT * FROM users WHERE email = 'test@example.com';

-- ✅ Tạo một index
CREATE INDEX idx_users_email ON users(email);
```

**2. Hàm trong WHERE làm mất tác dụng index**
```sql
-- ❌ Index không được sử dụng
SELECT * FROM users WHERE LOWER(email) = 'test@example.com';

-- ✅ Functional index (index dựa trên hàm)
CREATE INDEX idx_users_email_lower ON users(LOWER(email));
```

**3. Sai kiểu dữ liệu**
```sql
-- ❌ Việc ép kiểu ngầm định (implicit cast) làm chặn index
SELECT * FROM users WHERE phone = 89001234567;  -- phone = text

-- ✅ Kiểu đúng
SELECT * FROM users WHERE phone = '89001234567';
```

**4. work_mem không đủ**
```sql
-- ❌ Sort trên đĩa
EXPLAIN ANALYZE SELECT * FROM orders ORDER BY created_at DESC;
-- Sort Method: external merge  Disk: 5000kB

-- ✅ Tăng work_mem
SET work_mem = '256MB';
-- Bây giờ: Sort Method: quicksort  Memory: 50000kB
```

**5. JOIN không có index**
```sql
-- ❌ Hash Join không có index
SELECT * FROM users u JOIN orders o ON u.id = o.user_id;

-- ✅ Index trên trường join
CREATE INDEX idx_orders_user_id ON orders(user_id);
-- Bây giờ: Nested Loop + Index Scan → nhanh hơn
```

### Các lỗi thường gặp

1. **Quá nhiều index**
   - Mỗi index đều làm chậm INSERT/UPDATE
   - Hãy loại bỏ những index không sử dụng: `idx_scan = 0`

2. **SELECT \***
   - Chỉ chọn những cột bạn thực sự cần
   - Ít dữ liệu hơn → truyền tải nhanh hơn

3. **Vấn đề N+1**
   ```sql
   -- ❌ 1000 truy vấn trong một vòng lặp
   for user in users:
       SELECT * FROM orders WHERE user_id = user.id

   -- ✅ 1 truy vấn duy nhất với JOIN
   SELECT u.*, o.* FROM users u LEFT JOIN orders o ON u.id = o.user_id
   ```

## 🔴 Senior Level

### Cách tiếp cận có hệ thống đối với việc tối ưu hóa

**Các cấp độ tối ưu hóa:**
```
1. Cấp độ SQL (truy vấn)
   ├── Index
   ├── Tái cấu trúc truy vấn (Query refactoring)
   └── Thống kê

2. Cấu hình
   ├── work_mem
   ├── shared_buffers
   ├── effective_cache_size
   └── random_page_cost

3. Kiến trúc
   ├── Phi chuẩn hóa (Denormalization)
   ├── Phân vùng (Partitioning)
   ├── Materialized Views
   └── Read Replicas

4. Cơ sở hạ tầng
   ├── SSD vs HDD
   ├── RAM
   ├── Connection Pooling
   └── Huge Pages
```

### Các vấn đề của Plan Cache

**Generic vs Custom Plans:**
```sql
-- Vấn đề: truy vấn nhanh trong psql, nhưng chậm trong ứng dụng
-- Nguyên nhân: JDBC sử dụng Prepared Statements → Generic Plan

-- Chẩn đoán
EXPLAIN (ANALYZE) SELECT * FROM users WHERE email = $1;
-- Generic Plan: Seq Scan

-- Giải pháp 1: plan_cache_mode
SET plan_cache_mode = 'force_custom_plan';

-- Giải pháp 2: tắt Prepared Statements
-- JDBC URL: jdbc:postgresql://...?prepareThreshold=0
```

### Implicit Casts (Ép kiểu ngầm định)

```sql
-- Kiểm tra việc ép kiểu ngầm định
EXPLAIN (ANALYZE) SELECT * FROM users WHERE phone = 89001234567;
-- Filter: (phone = '89001234567'::text)  ← có ép kiểu!
-- → Index không được sử dụng

-- Giải pháp: đảm bảo kiểu dữ liệu khớp nhau
-- 1. Thay đổi kiểu của cột
ALTER TABLE users ALTER COLUMN phone TYPE bigint;

-- 2. Hoặc truyền đúng kiểu
SELECT * FROM users WHERE phone = '89001234567';  -- text
```

### Tính biến động của hàm (Function volatility)

```sql
-- Các hàm được đánh dấu là:
-- IMMUTABLE  → luôn luôn cho ra cùng kết quả với cùng tham số
-- STABLE     → cùng kết quả trong phạm vi một truy vấn
-- VOLATILE   → có thể thay đổi (mặc định)

-- ❌ Hàm VOLATILE ngăn cản việc tối ưu hóa
CREATE OR REPLACE FUNCTION get_status(id int) RETURNS text AS $$
  SELECT status FROM users WHERE id = $1;
$$ LANGUAGE sql;  -- Mặc định là VOLATILE

-- ✅ STABLE cho phép lưu vào cache
CREATE OR REPLACE FUNCTION get_status(id int) RETURNS text AS $$
  SELECT status FROM users WHERE id = $1;
$$ LANGUAGE sql STABLE;

-- STABLE: trong phạm vi MỘT truy vấn duy nhất, hàm trả về cùng một kết quả
-- với cùng các tham số. Planner chỉ gọi nó một lần rồi thay thế giá trị vào.
-- Cache tồn tại cho đến khi kết thúc truy vấn.
```

### Các quyết định về kiến trúc

**Phi chuẩn hóa (Denormalization):**
```sql
-- ❌ JOIN 10 bảng cho mỗi truy vấn
SELECT u.name, o.amount, p.title, c.name as category
FROM users u
JOIN orders o ON u.id = o.user_id
JOIN products p ON o.product_id = p.id
JOIN categories c ON p.category_id = c.id
WHERE ...

-- ✅ Các cột được phi chuẩn hóa
ALTER TABLE orders ADD COLUMN product_title text;
ALTER TABLE orders ADD COLUMN category_name text;

-- Cập nhật thông qua trigger
-- Truy vấn: không cần JOIN → nhanh hơn 10 lần
```

**Materialized Views:**
```sql
-- Đối với các truy vấn phân tích phức tạp
CREATE MATERIALIZED VIEW mv_sales_summary AS
SELECT
    department,
    COUNT(*) as orders_count,
    SUM(amount) as total_sales,
    AVG(amount) as avg_order
FROM orders
GROUP BY department;

-- Làm mới định kỳ (Refresh)
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_sales_summary;

-- Truy vấn: tức thì
SELECT * FROM mv_sales_summary;
```

**Phân vùng (Partitioning):**
```sql
-- Đối với các bảng > 100 triệu dòng
CREATE TABLE orders (
    id serial,
    created_at date,
    amount numeric
) PARTITION BY RANGE (created_at);

CREATE TABLE orders_y2023 PARTITION OF orders
    FOR VALUES FROM ('2023-01-01') TO ('2024-01-01');

CREATE TABLE orders_y2024 PARTITION OF orders
    FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');

-- Partition Pruning: planner loại bỏ các partition
-- không cần thiết khỏi plan. Dữ liệu từ chúng thậm chí còn không được đọc từ đĩa.
-- WHERE created_at > '2024-01-01' → chỉ quét orders_y2024
```

### Tinh chỉnh hệ thống (System tuning)

**Các tham số cho SSD:**
```sql
-- Planner nên tin tưởng vào cache
SET random_page_cost = 1.1;       -- Mặc định 4.0 (dành cho HDD)
SET effective_cache_size = '24GB'; -- 75% RAM
SET shared_buffers = '8GB';       -- 25% RAM
```

**Connection Pooling:**
```
pgBouncer ở chế độ transaction mode:
  - 1000 kết nối từ ứng dụng → 50 kết nối đến DB
  - Tiết kiệm 30% CPU cho việc chuyển đổi ngữ cảnh (context switching)
  - Ít bộ nhớ cho các session hơn
```

**Huge Pages:**
```
Hệ điều hành + PostgreSQL:
  - Huge Pages = các page 2MB thay vì 4KB
  - Ít TLB miss hơn
    (TLB — Translation Lookaside Buffer, bộ nhớ đệm của CPU cho các địa chỉ.
    Ở 4KB đối với 8GB RAM → 2 triệu mục TLB (không đủ vừa).
    Ở 2MB → 4000 mục (vừa với TLB))
  - Tăng 10-20% hiệu năng ở mức tải cao
```

### Thuật toán của một Senior developer

```
1. pg_stat_statements → tìm các truy vấn có shared_blks_read cao
2. EXPLAIN (ANALYZE, BUFFERS) → tìm node gây nghẽn cổ chai (bottleneck)
3. Kiểm tra khóa (locks): pg_blocking_pids()
4. Kiểm tra thống kê: rows ≠ actual → cần ANALYZE
5. Kiểm tra work_mem: Disk Spill → tăng lên
6. Kiểm tra plan_cache_mode: các vấn đề về Generic Plan
7. Tái cấu trúc (Refactoring): phi chuẩn hóa, phân vùng, caching
8. Nếu SQL đã tối ưu → sharding (Citus)
```

### Khi nào KHÔNG nên áp dụng các quyết định kiến trúc

- **Phi chuẩn hóa:** ĐỪNG dùng khi có UPDATE thường xuyên trên các trường đã phi chuẩn hóa (xung đột trigger, mất đồng bộ)
- **Materialized Views:** ĐỪNG dùng cho dữ liệu cần phải cập nhật theo thời gian thực (độ trễ giữa các lần REFRESH)
- **Phân vùng:** ĐỪNG dùng cho các bảng < 10 triệu dòng — chi phí quản lý partition lớn hơn lợi ích mang lại

### Kinh nghiệm Production

**Tình huống thực tế #1: Tối ưu hóa toàn diện**
- SaaS: API > 2 giây (p95)
- Phân tích:
  1. Vấn đề N+1 queries (100 truy vấn cho mỗi trang)
  2. Seq Scan trên một bảng 50 triệu dòng
  3. work_mem = 4MB → tràn ra đĩa
  4. Generic Plan trong Hibernate
- Giải pháp:
  1. DataLoader → 5 truy vấn thay vì 100
  2. Index trên các trường "nóng"
  3. work_mem = 256MB
  4. plan_cache_mode = force_custom_plan
- Kết quả: p95 < 200ms (nhanh hơn 10 lần)

**Tình huống thực tế #2: Thay đổi kiến trúc**
- Phân tích dữ liệu: báo cáo mất 5 phút (JOIN 12 bảng)
- Giải pháp:
  - Materialized View với REFRESH mỗi 5 phút
  - Các cột phi chuẩn hóa cho các trường "nóng"
  - Phân vùng theo ngày
- Kết quả: báo cáo < 1 giây

### Dashboard giám sát

```sql
-- 1. Top các truy vấn chậm
SELECT
    query,
    calls,
    mean_exec_time,
    total_exec_time,
    shared_blks_read,
    rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;

-- 2. Khóa (Locks)
SELECT
    blocked_locks.pid AS blocked_pid,
    blocked_activity.query AS blocked_query,
    blocking_locks.pid AS blocking_pid,
    blocking_activity.query AS blocking_query
FROM pg_catalog.pg_locks blocked_locks
JOIN pg_catalog.pg_stat_activity blocked_activity ON blocked_activity.pid = blocked_locks.pid
JOIN pg_catalog.pg_locks blocking_locks ON blocking_locks.locktype = blocked_locks.locktype
JOIN pg_catalog.pg_stat_activity blocking_activity ON blocking_activity.pid = blocking_locks.pid
WHERE NOT blocked_locks.granted;

-- 3. Bloat
SELECT
    relname,
    n_dead_tup,
    n_live_tup,
    ROUND(100.0 * n_dead_tup / NULLIF(n_live_tup + n_dead_tup, 0), 2) as dead_pct
FROM pg_stat_user_tables
WHERE n_live_tup > 10000
ORDER BY dead_pct DESC;

-- 4. Cache Hit Rate
SELECT
    sum(heap_blks_read) as heap_read,
    sum(heap_blks_hit) as heap_hit,
    ROUND(100.0 * sum(heap_blks_hit) / NULLIF(sum(heap_blks_read) + sum(heap_blks_hit), 0), 2) as cache_hit_pct
FROM pg_statio_user_tables;
-- > 99% → tuyệt vời
```

### Best Practices (Thực hành tốt nhất)

1. **Giám sát** thông qua `pg_stat_statements` liên tục
2. **EXPLAIN (ANALYZE, BUFFERS)** cho mỗi truy vấn có vấn đề
3. **Index** — giải pháp đầu tiên, nhưng không phải là giải pháp duy nhất
4. **Kiểm soát work_mem** trong lúc Sort/Hash
5. **Kiểm tra plan_cache_mode** khi sử dụng ORM
6. **Phi chuẩn hóa** cho các truy vấn hot-path
7. **Materialized Views** cho phân tích dữ liệu
8. **pgBouncer** được khuyến nghị khi > 50 kết nối. Đối với các dự án nhỏ
   (< 10 người dùng) bạn có thể không cần dùng đến nó.
9. **Phân vùng** đối với các bảng > 100 triệu dòng
10. **Cache Hit Ratio > 99%** — mục tiêu cần đạt

### Tóm tắt cho Senior

- Tối ưu hóa **không chỉ là index**, đó là một quá trình có hệ thống
- **Plan Cache** (Generic vs Custom) — nguyên nhân phổ biến gây ra sự chênh lệch giữa prod/dev
- **Implicit Casts** làm chặn index → hãy sử dụng kiểu dữ liệu khớp nhau
- **Phi chuẩn hóa** cho hot-path, **MV** cho phân tích dữ liệu
- **Kiểm soát work_mem** → Disk Spill = thảm họa
- **pgBouncer** ở chế độ transaction mode → tiết kiệm 30% CPU
- **Cache Hit Ratio > 99%** → chỉ số sức khỏe chính của cơ sở dữ liệu
- **Phân vùng** + Partition Pruning cho các bảng lớn
- **Write Amplification**: mỗi INSERT/UPDATE không chỉ ghi vào bảng
  mà còn ghi vào TẤT CẢ các index. 10 index = ghi nhiều gấp 10 lần. Về mặt vật lý,
  lượng dữ liệu được ghi nhiều hơn gấp 10 lần so với những gì người dùng đã thay đổi.

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Thuật toán: pg_stat_statements → EXPLAIN (ANALYZE, BUFFERS) → khắc phục → xác minh
- Các vấn đề thường gặp: không có index, hàm trong WHERE, ép kiểu ngầm định, tràn ra đĩa, N+1
- Generic vs Custom Plans: Prepared Statements → plan_cache_mode = force_custom_plan
- Implicit Casts: `phone = 8900...` (int) vs `phone = '8900...'` (text) → ép kiểu làm chặn index
- Tính biến động của hàm: IMMUTABLE, STABLE, VOLATILE → ảnh hưởng đến tối ưu hóa
- Phi chuẩn hóa: các cột "nóng" → dùng trigger để cập nhật
- Materialized Views: các truy vấn phân tích phức tạp → REFRESH CONCURRENTLY
- Phân vùng: các bảng > 100 triệu dòng → Partition Pruning
- Connection Pooling: pgBouncer ở chế độ transaction mode → 1000 kết nối → 50 kết nối đến DB
- Tinh chỉnh hệ thống: `random_page_cost = 1.1` (SSD), `shared_buffers = 25% RAM`
- Cache Hit Ratio > 99% — mục tiêu cần đạt; < 95% → có vấn đề

**Các câu hỏi phụ thường gặp:**
- "Làm sao để tìm các truy vấn chậm?" → pg_stat_statements ORDER BY total_exec_time DESC
- "Tại sao một truy vấn nhanh trong console nhưng lại chậm trong ứng dụng?" → Generic Plan
- "Cần làm gì khi có Disk Spill?" → SET work_mem = '256MB' cho session
- "Khi nào phi chuẩn hóa là hợp lý?" → Các truy vấn hot-path, JOIN 10+ bảng

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "Tối ưu hóa = chỉ có index" (đó là một quá trình có hệ thống: SQL, cấu hình, kiến trúc, cơ sở hạ tầng)
- ❌ "plan_cache_mode không quan trọng" (Generic Plan — nguyên nhân phổ biến gây ra sự chênh lệch)
- ❌ "Materialized Views dành cho OLTP" (chỉ dành cho phân tích dữ liệu!)
- ❌ "pgBouncer là không cần thiết" (1000 kết nối = 30% CPU cho việc chuyển đổi ngữ cảnh)
