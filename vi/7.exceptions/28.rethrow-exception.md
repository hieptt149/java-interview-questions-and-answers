# Can you rethrow an exception? (Có thể rethrow một exception không?)

## Junior Level

### Có, bạn có thể!

Rethrow - bắt một exception trong `catch` để thực hiện một hành động (ghi log) và gửi nó đi tiếp:

```java
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

public class OrderService {
    private static final Logger log = LoggerFactory.getLogger(OrderService.class);

    public void processOrder(Long orderId) {
        try {
            orderRepository.save(orderId);
        } catch (Exception e) {
            log.error("Failed to process order id={}", orderId, e); // Ghi log
            throw e; // Lan truyền đi tiếp
        }
    }
}
```

### Tại sao cần nó

- **Ghi log** - ghi lại lỗi trước khi nó đi tiếp
- **Metric** - đếm số lượng lỗi
- **Cleanup** - giải phóng resource trước khi lan truyền

```java
try {
    connection.beginTransaction();
    connection.save(order);
} catch (SQLException e) {
    connection.rollback(); // Rollback transaction
    throw e; // Lan truyền đi tiếp
}
```

### Wrapping khi rethrow

Thường được bọc trong một exception khác:

```java
try {
    repository.save(order);
} catch (SQLException e) {
    throw new OrderException("Failed to save order id=" + order.getId(), e); // Kiểu mới + ngữ cảnh
}
```

### Khi nào KHÔNG nên dùng rethrow

1. **Không thêm giá trị** - `catch (Exception e) { throw e; }` là vô dụng nếu không có ghi log/metric
2. **Ghi log trùng lặp** - nếu exception đã được ghi log ở mức này, đừng ghi log lại khi rethrow
3. **Thay cho wrapping** - nếu bạn cần một kiểu exception mới, hãy dùng wrapping với cause, không phải rethrow trần
4. **Trong transaction mà không rollback** - rethrow một unchecked exception trong `@Transactional` sẽ rollback transaction, checked - thì không
5. **Rethrow nhiều lần** - đừng catch/throw cùng một exception ở mọi tầng - một tầng là đủ

## Middle Level

### Lệnh athrow

Ở mức bytecode, rethrow là một lệnh `athrow` thông thường. Nó lấy object exception từ operand stack và tìm một handler trong Exception Table.

**Quan trọng:** khi `throw e;` stack trace **không thay đổi**. Nó hiển thị vị trí xảy ra gốc, không phải dòng `throw e`.

### Precise Rethrow (Java 7+)

Một trong những tính năng hữu ích nhất nhưng hiếm khi được bàn tới:

```java
public void process() throws IOException, SQLException {
    try {
        if (condition) throw new IOException();
        else throw new SQLException();
    } catch (Exception e) { // Bắt tổ tiên chung
        log.error("Intermediary processing");
        throw e; // Compiler "biết" - chỉ IOException hoặc SQLException
    }
}
```

Trước Java 7, bạn sẽ phải khai báo `throws Exception`. Giờ đây compiler phân tích nội dung của `try`.

### Rethrow với wrapping (Exception Chaining)

```java
// Ưu: thêm ngữ cảnh của tầng hiện tại
throw new MyException("Context: processing order " + orderId, e);

// Nhược: object mới + fillInStackTrace() mới
// Luôn truyền exception gốc làm cause!
```

### Side Effect trong rethrow

Trong các hệ thống tải cao, rethrow được dùng cho metric:

```java
catch (RuntimeException e) {
    metrics.increment("errors.count");
    throw e;
}
```

## Senior Level

### Double Traversal (duyệt hai lần)

Rethrow buộc JVM quét lại Exception Table. Trong các cây phân cấp sâu, các rethrow thường xuyên tạo một tải CPU nhỏ.

### Checked thành Unchecked

Thường các checked exception được lan truyền dưới dạng unchecked - "phá vỡ" các nghĩa vụ trong chữ ký:

```java
try {
    // checked exception
    Files.readAllLines(path);
} catch (IOException e) {
    throw new RuntimeException(e); // Unchecked - phương thức không còn khai báo throws
}
```

### Sneaky Throws

Mẹo với việc lan truyền một checked exception mà không khai báo trong `throws`:

```java
@SuppressWarnings("unchecked")
private static <E extends Throwable> void sneakyThrow(Throwable e) throws E {
    throw (E) e;
}
```

Lombok `@SneakyThrows` dùng chính cơ chế này.

### Mất Exception

Nếu khối `catch` gọi một phương thức mà bản thân nó ném một exception, và bạn không lan truyền cái gốc - cái gốc bị mất:

```java
catch (Exception e) {
    log.info("Error");        // OK
    doSomethingThatAlsoThrows(); // Exception mới! e gốc bị mất!
    throw e; // Không bao giờ thực thi
}
```

### fillInStackTrace() - cập nhật stack trace

Nếu bạn muốn cập nhật stack trace tới dòng hiện tại (để log hiển thị vị trí rethrow):

```java
throw (RuntimeException) e.fillInStackTrace();
```

Chỉ làm điều này nếu bạn hiểu tại sao - stack trace gốc sẽ bị mất.

### Chẩn đoán

- **Log Analysis** - đảm bảo mỗi rethrow được ghi log kèm ngữ cảnh
- **Metric** - đếm các rethrow qua Micrometer
- **Debugger** - trong IntelliJ mở rộng node `cause` để thấy toàn bộ chuỗi
- **`javap -c`** - hiển thị lệnh `athrow` trong bytecode

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Rethrow - bắt exception trong `catch` kèm hành động (log, metric, rollback) và lan truyền đi tiếp qua `throw e`
- Khi `throw e;` stack trace **không thay đổi** - hiển thị vị trí lỗi gốc
- Checked exception có thể được lan truyền mà không mất kiểu nhờ Precise Rethrow (Java 7+)
- Wrapping khi rethrow thêm ngữ cảnh: `throw new OrderException("msg", e)` - luôn truyền `cause`
- Rethrow một unchecked trong `@Transactional` sẽ rollback transaction, checked - thì không
- Rethrow vô dụng: `catch (Exception e) { throw e; }` không có ghi log/metric/cleanup
- `e.fillInStackTrace()` cập nhật stack trace - dùng một cách có ý thức, stack gốc sẽ bị mất

**Các câu hỏi phụ thường gặp:**
- **Stack trace có thay đổi khi `throw e` không?** - Không, hiển thị vị trí lỗi gốc
- **Precise Rethrow là gì?** - Java 7+: compiler phân tích `try` và giữ các kiểu chính xác trong `throws`
- **Khi nào rethrow là vô dụng?** - Không có ghi log, metric, cleanup - `catch { throw e; }` trần
- **Cách cập nhật stack trace?** - `e.fillInStackTrace()` - nhưng stack gốc sẽ bị mất

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Khi rethrow stack trace được cập nhật" - không, chỉ khi `fillInStackTrace()`
- "Rethrow một checked exception không rollback `@Transactional`" - tùy vào kiểu: unchecked rollback, checked - thì không
- "Rethrow nhiều lần ở mọi tầng là thực hành tốt" - một tầng là đủ
- "Rethrow không có cause làm mất lỗi gốc" - khi `throw e` không có wrapper, lỗi không bị mất
