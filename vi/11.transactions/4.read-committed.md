# What is Read Committed? (Read Committed là gì?)

## 🟢 Junior Level

**Read Committed** là một isolation level trong đó một transaction chỉ thấy dữ liệu đã được xác nhận chính thức (COMMIT) bởi các transaction khác.

### Các Thuộc Tính Chính

- **Dirty Read**: Bị cấm — bạn không bao giờ thấy dữ liệu chưa commit vì DBMS chỉ hiển thị các phiên bản dòng mà transaction tạo ra chúng đã COMMIT.
- **Non-Repeatable Read**: Có thể xảy ra — cùng một query có thể trả về các kết quả khác nhau
- **Phantom Read**: Có thể xảy ra — các dòng mới có thể xuất hiện ở các lần query lặp lại

### Ví Dụ Đơn Giản

```
Transaction A: SELECT balance FROM accounts WHERE id = 1; -- Trả về 100
Transaction B: UPDATE accounts SET balance = 200 WHERE id = 1; COMMIT;
Transaction A: SELECT balance FROM accounts WHERE id = 1; -- Trả về 200!
```

SELECT thứ hai trả về giá trị khác vì Transaction B đã commit các thay đổi của nó.

### Nơi Nó Được Dùng

Đây là level mặc định trong PostgreSQL, Oracle và SQL Server. Level phổ biến nhất cho các ứng dụng thông thường.

## 🟡 Middle Level

### Cơ Chế Hiện Thực Qua MVCC

Trong các cơ sở dữ liệu có MVCC (PostgreSQL), ở level Read Committed, một snapshot dữ liệu được tạo **trước mỗi query** trong transaction.

**Khác biệt chính với Repeatable Read:**
- Read Committed: snapshot mới trước mỗi statement
- Repeatable Read: một snapshot cho toàn bộ transaction

### Tại Sao Nó Là "Tiêu Chuẩn Vàng"

1. **Cân bằng**: Độ chính xác dữ liệu đủ dùng cho hầu hết các quy trình nghiệp vụ với overhead tối thiểu
2. **Không chặn**: Trong MVCC, các reader không chặn writer và ngược lại
3. **Ít lỗi nhất**: Ở Read Committed, DBMS không bao giờ abort một transaction do xung đột isolation (không như Serializable). Lỗi duy nhất là vi phạm ràng buộc hoặc logic ở tầng application.

### Các Hiện Tượng Bất Thường Ở Level Này

#### Non-repeatable Read
```sql
-- Transaction A (Read Committed)
BEGIN;
SELECT price FROM products WHERE id = 1;  -- 100
-- Transaction khác: UPDATE products SET price = 150 WHERE id = 1; COMMIT;
SELECT price FROM products WHERE id = 1;  -- 150 (đã thay đổi!)
COMMIT;
```

Tại sao? Ở Read Committed, mỗi SELECT nhận snapshot riêng của nó. Giữa SELECT thứ nhất và thứ hai, một transaction khác đã kịp commit các thay đổi, và snapshot thứ hai thấy chúng.

#### Phantom Read
```sql
-- Transaction A
BEGIN;
SELECT COUNT(*) FROM users WHERE age > 20;  -- 5 dòng
-- Transaction khác: INSERT INTO users (age) VALUES (25); COMMIT;
SELECT COUNT(*) FROM users WHERE age > 20;  -- 6 dòng (một dòng mới xuất hiện!)
COMMIT;
```

### Cách Tránh Các Hiện Tượng Bất Thường

Nếu cần sự ổn định dữ liệu trong một transaction:
- **SELECT ... FOR UPDATE**: Khóa các dòng cho đến khi kết thúc transaction
- **Nâng level lên Repeatable Read**: Cho toàn bộ transaction

### Đặc Điểm Trong PostgreSQL

Ở level Read Committed, mỗi statement thấy một snapshot cơ sở dữ liệu được chụp tại **thời điểm bắt đầu thực thi statement đó**, chứ không phải tại thời điểm bắt đầu toàn bộ transaction.

## 🔴 Senior Level

### Cơ Chế Snapshot MVCC Trong PostgreSQL

#### Cách Snapshot Hoạt Động Nội Bộ
- Mỗi snapshot chứa:
  - `xmin`: transaction ID sớm nhất vẫn đang chạy
  - `xmax`: transaction ID đầu tiên chưa bắt đầu
  - `xip_list`: danh sách các transaction ID đang thực thi
- Quy tắc visibility: một tuple hiển thị nếu:
  - `xmin` < snapshot.xmin (đã commit trước snapshot của chúng ta)
  - `xmax` chưa được thiết lập HOẶC `xmax` >= snapshot.xmin (chưa bị xóa)

#### Hành Vi Snapshot Của Read Committed
- Snapshot mới được tạo cho **mỗi statement**, không phải mỗi transaction
- Điều này có nghĩa là GIỮA hai SELECT trong cùng một transaction, một transaction khác có thể commit các thay đổi
- SELECT thứ hai sẽ thấy các thay đổi đó vì nó nhận một snapshot mới

### Đặc Điểm Hiệu Năng

#### Ưu Điểm
- **Không chặn**: Các reader không bao giờ chặn writer, các writer không bao giờ chặn reader
- **Không có serialization failure**: Không như Serializable, không có transaction nào bị abort do xung đột
- **Overhead tối thiểu**: Việc tạo snapshot rẻ (chỉ ghi lại trạng thái txid hiện tại)

#### Đánh Đổi (Trade-off)
- **Non-repeatable read**: Application phải xử lý các kết quả có thể khác nhau
- **Phantom read**: Các range query có thể trả về số lượng dòng khác nhau
- **Độ phức tạp của logic nghiệp vụ**: Các tính toán nhiều bước có thể cần locking tường minh

### SELECT FOR UPDATE — Đào Sâu

```sql
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
```

- Lấy exclusive row-level lock
- Các transaction khác cố gắng `FOR UPDATE` trên cùng dòng sẽ bị chặn
- Ngăn cả non-repeatable read LẪN lost update cho dòng đó
- Lock được giữ cho đến khi transaction kết thúc (COMMIT/ROLLBACK)
- Có thể gây deadlock nếu không dùng cẩn thận

**Khi nào nên dùng:**
- Các pattern read-modify-write (tính toán số dư)
- Khi bạn cần hành vi Repeatable Read chỉ cho các dòng cụ thể
- Tránh lost update mà không cần thay đổi isolation level

### Các Pattern Trong Production

#### Pattern 1: Cách tiếp cận optimistic (Read Committed mặc định)
```java
@Transactional // Sử dụng Read Committed
public void transfer(Long fromId, Long toId, BigDecimal amount) {
    // Nếu xảy ra xung đột, xử lý ở tầng application
    Account from = repo.findById(fromId);
    Account to = repo.findById(toId);
    // ... logic
}
```

#### Pattern 2: Cách tiếp cận pessimistic (FOR UPDATE)
```java
@Query("SELECT a FROM Account a WHERE a.id = :id FOR UPDATE")
Account findByIdForUpdate(@Param("id") Long id);

@Transactional
public void transfer(Long fromId, Long toId, BigDecimal amount) {
    Account from = repo.findByIdForUpdate(fromId); // Đã khóa!
    Account to = repo.findByIdForUpdate(toId);     // Đã khóa!
    // An toàn để sửa đổi
}
```

### Read Committed vs Read Committed Snapshot (SQL Server)

SQL Server có hai biến thể:
- **Read Committed (locking)**: Sử dụng shared lock, reader có thể chặn writer
- **Read Committed Snapshot (RCSI)**: Sử dụng row versioning giống MVCC của PostgreSQL

PostgreSQL luôn sử dụng cách tiếp cận MVCC — không tồn tại Read Committed dựa trên locking.

### Giám Sát Và Tinh Chỉnh

- Theo dõi tỷ lệ `tup_fetched` so với `tup_returned` (sequential scan vs index scan)
- Giám sát `deadlocks` — Read Committed có tỷ lệ deadlock thấp nhất
- Kiểm tra `temp_files` và `temp_bytes` — các query phức tạp trên RC có thể cần thêm temp space
- Các transaction chạy dài trên RC không gây bloat (không như RR/Serializable)

### Khi Nào KHÔNG Nên Dùng Read Committed
- Các bất biến tài chính yêu cầu xác minh nhiều bước
- Các báo cáo phải tự nhất quán (self-consistent)
- Khi logic application giả định các lần đọc ổn định
- Các distributed transaction yêu cầu tính nhất quán nghiêm ngặt

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Read Committed — level mặc định trong PostgreSQL, Oracle, SQL Server
- Cấm dirty read nhưng cho phép non-repeatable read và phantom read
- Mỗi SELECT nhận một snapshot mới — hai SELECT trong một transaction có thể trả về dữ liệu khác nhau
- Được hiện thực qua MVCC — reader không chặn writer
- SELECT ... FOR UPDATE khóa các dòng để ngăn lost update
- 90% các application hoạt động tốt trên Read Committed

**Các câu hỏi phụ thường gặp:**
- Read Committed khác gì với Repeatable Read? — RC: snapshot mỗi statement, RR: một snapshot cho mỗi transaction
- Làm sao tránh non-repeatable read trên RC? — SELECT FOR UPDATE hoặc nâng lên RR
- Tại sao RC là mặc định tốt? — Cân bằng giữa bảo vệ và hiệu năng, không có serialization failure
- EvalPlanQual trong PostgreSQL là gì? — Cơ chế của PG để đánh giá lại mệnh đề WHERE khi có UPDATE đồng thời

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Read Committed = isolation đầy đủ" — cho phép non-repeatable read và phantom read
- "Hai SELECT trong một transaction luôn trả về cùng kết quả" — không đúng trên RC
- "RC cần lock" — MVCC hoạt động mà không cần read lock
