# What are Virtual Threads in Java 21? (Virtual Thread trong Java 21 là gì?)

Virtual Thread là các thread nhẹ được quản lý bởi JVM, không phải hệ điều hành. Chúng trở thành một **tính năng ổn định trong Java 21** (phiên bản LTS), nhưng đã được phát triển dưới Project Loom từ 2017 và trải qua vài bản preview (Java 19-20).

**Lưu ý quan trọng:** trong khi API đã ổn định trong Java 21, một số tính năng liên quan (Scoped Values, Structured Concurrency) vẫn ở dạng preview. Điều này nghĩa là API của chúng có thể thay đổi trong các phiên bản tương lai. Nếu bạn chỉ dùng `Thread.ofVirtual()` cơ bản, nó đã sẵn sàng cho production.

## Junior Level

### Hiểu biết cơ bản

**Virtual Thread** là các thread nhẹ được quản lý bởi JVM, không phải hệ điều hành. Chúng cho phép tạo **hàng triệu** thread thay vì hàng nghìn.

**Tại sao các thread thông thường đắt:** mỗi Platform Thread giữ trước ~1MB bộ nhớ OS khi tạo, ngay cả khi nó chỉ dùng vài kilobyte. Thêm nữa, chuyển đổi giữa các thread cần vào kernel mode, thứ tốn hàng nghìn chu kỳ CPU.

**Tại sao virtual thread rẻ:** stack của chúng được lưu trong JVM heap thông thường và tăng động — từ vài kilobyte. Chuyển đổi xảy ra trong user-space không cần system call, nhanh hơn 100-1000 lần.

### Ví dụ minh họa đơn giản

- **Platform Thread** (thông thường): như taxi — mỗi cái cần một chiếc xe (1MB bộ nhớ)
- **Virtual Thread**: như xe buýt — nhiều hành khách trên một phương tiện

### Tạo và sử dụng

```java
// Platform Thread (cách cũ)
Thread platform = new Thread(() -> {
    System.out.println("Platform thread");
});
platform.start();

// Virtual Thread (Java 21+)
Thread virtual = Thread.ofVirtual().start(() -> {
    System.out.println("Virtual thread");
});

// Hoặc qua builder
Thread vThread = Thread.startVirtualThread(() -> {
    System.out.println("Virtual thread");
});
```

### So sánh

| Đặc điểm             | Platform Thread      | Virtual Thread               |
| -------------------- | -------------------- | ---------------------------- |
| **Được quản lý bởi** | OS (Kernel)          | JVM (Runtime)                |
| **Stack Size**       | ~1 MB (tĩnh)         | Vài KB (động)                |
| **Thời gian tạo**    | ~1-10 ms             | ~micro giây                  |
| **Tối đa**           | Hàng nghìn           | Hàng triệu                   |

### Ví dụ: Thread-per-Request

```java
// Với virtual thread — mô hình đơn giản lại hoạt động!
ServerSocket server = new ServerSocket(8080);

while (true) {
    Socket client = server.accept();
    Thread.ofVirtual().start(() -> {
        handleRequest(client); // Một virtual thread mỗi request
    });
}
// Hàng triệu kết nối — không cần lập trình reactive!
```

## Middle Level

### Kiến trúc: Continuations

Virtual thread dựa trên khái niệm **Continuations**:

```
1. Virtual thread chạy code trên một Carrier Thread (thread OS thật)
2. Khi có một thao tác blocking (sleep, I/O):
   a. JVM lưu stack của virtual thread vào Heap
   b. Thread "unmount" khỏi Carrier Thread
   c. Carrier Thread đi thực thi một virtual thread khác
3. Khi I/O hoàn tất:
   a. JVM khôi phục stack từ heap
   b. Thread "mount" vào một Carrier Thread rảnh
   c. Tiếp tục thực thi từ chỗ nó dừng
```

### Carrier Thread Pool

```java
// Các virtual thread dùng chung các thread thật (Carrier Thread)
// Mặc định: ForkJoinPool có kích thước = số lõi CPU

// Ví dụ: 1.000.000 virtual thread trên 8 Carrier Thread
// Mỗi Carrier Thread xử lý ~125.000 virtual thread
// theo lượt, khi chúng unmount
```

### Cơ chế Stack Chunking

JVM lưu stack của một virtual thread như các object **`StackChunk`** trong heap:

```
Virtual Thread:
┌────────────────────────┐
│ StackChunk #1 (heap)   │ ← Stack hiện tại
│ StackChunk #2 (heap)   │ ← Frame trước
│ StackChunk #3 (heap)   │ ← Sâu hơn
└────────────────────────┘
```

Khi mount, dữ liệu được sao chép từ heap sang stack CPU thật; khi unmount — ngược lại.

### Tạo một Virtual Thread Pool

```java
// ExecutorService cho các virtual thread
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 1_000_000; i++) {
        executor.submit(() -> {
            // Xử lý tác vụ
            Thread.sleep(1000); // Unmount — không chặn Carrier
        });
    }
}
// Một triệu tác vụ — và JVM không sập!
```

## Senior Level

### Bên trong: Pinning

Đây là cái bẫy chính của virtual thread. Một virtual thread có thể **"dính"** vào một Carrier Thread và không unmount khi blocking:

#### Nguyên nhân của Pinning

| Nguyên nhân                | Mô tả                                                  | Giải pháp                   |
| -------------------------- | ------------------------------------------------------ | --------------------------- |
| block/method **synchronized** | Virtual thread trong synchronized KHÔNG unmount     | Thay bằng `ReentrantLock`   |
| **Native method (JNI)**    | Các lời gọi code native không hỗ trợ unmount           | Bọc trong một thread riêng  |

```java
// XẤU: synchronized chặn Carrier Thread
synchronized(lock) {
    Thread.sleep(10000); // Virtual thread "dính" vào carrier trong 10 giây!
}

// TỐT: ReentrantLock hỗ trợ unmount
ReentrantLock lock = new ReentrantLock();
lock.lock();
try {
    Thread.sleep(10000); // Unmount — Carrier Thread rảnh
} finally {
    lock.unlock();
}
```

#### Chẩn đoán Pinning

```bash
# Cờ bắt buộc khi phát triển với Virtual Thread
java -Djdk.tracePinnedThreads=full MyApp

# Sẽ in stack trace mỗi lần một thread "dính"
```

### ThreadLocal và Virtual Thread

```java
// CẨN THẬN: triệu VT = triệu bản sao của ThreadLocal!
ThreadLocal<ExpensiveObject> local = ThreadLocal.withInitial(ExpensiveObject::new);

// Giải pháp: Scoped Values (Java 21 Preview)
static final ScopedValue<UserContext> CONTEXT = new ScopedValue<>();

ScopedValue.runWhere(CONTEXT, new UserContext("user123"), () -> {
    // CONTEXT.get() có sẵn bên trong
});
// Sau khi ra — tự động được dọn, không rò rỉ
```


### Phân tích bộ nhớ

```
Một triệu virtual thread = một triệu object trong heap
Mỗi VT ~ vài KB (stack) + các object

Kiểm tra -Xmx trước khi khởi chạy!
Khuyến nghị: ít nhất 256MB cho một triệu VT
```

### Khi nào VT KHÔNG mang lại lợi ích

| Kịch bản                   | Tại sao                                     | Giải pháp thay thế    |
| -------------------------- | ------------------------------------------- | --------------------- |
| **Các tác vụ CPU-bound**   | VT không unmount, overhead của scheduler    | FixedThreadPool (N+1) |
| **Code nhiều synchronized**| Pinning — chặn các Carrier Thread           | ReentrantLock         |
| **Resource hạn chế**       | Triệu VT sẽ giết DB                         | Semaphore             |

### Best Practices

1. **Dùng VT cho I/O-bound** — web server, API gateway, proxy
2. **Thay synchronized bằng ReentrantLock** — tránh pinning
3. **Dùng Semaphore** — để giới hạn truy cập các resource khan hiếm
4. **Cẩn thận với ThreadLocal** — triệu bản sao = nhiều bộ nhớ
5. **Scoped Values** — để truyền context (Java 21 Preview)
6. **-Djdk.tracePinnedThreads=full** — trong lúc phát triển
7. **Đừng dùng VT cho CPU-bound** — FixedThreadPool tốt hơn
8. **Giám sát jdk.VirtualThreadPinned** — qua JFR

## Khi nào KHÔNG dùng Virtual Thread

- **Dưới Java 21** — VT không có sẵn. Với Java 17 dùng reactive stack (WebFlux, CompletableFuture)
- **Các tác vụ CPU-bound** (tính toán, ML, mật mã) — VT không unmount trong lúc tính toán, chỉ thêm overhead của scheduler. Dùng `Executors.newFixedThreadPool(N)` với N = số lõi + 1
- **Code legacy nhiều synchronized** — pinning sẽ chặn các Carrier Thread. Refactor sang ReentrantLock trước
- **Resource hạn chế** (DB pool 20 kết nối) — triệu VT sẽ giết DB. Dùng Semaphore
- **Các ứng dụng nhiều ThreadLocal** — triệu VT = triệu bản sao ThreadLocal = OutOfMemoryError. Chuyển sang Scoped Values

## Virtual Thread vs Platform Thread vs ExecutorService: Chọn gì?

| Tình huống                          | Lựa chọn                      | Tại sao                                          |
| ----------------------------------- | ----------------------------- | ------------------------------------------------ |
| Web server, API gateway (I/O-bound) | Virtual Thread                | Hàng triệu kết nối đồng thời, code đơn giản      |
| Tính toán (ML, parsing)             | FixedThreadPool               | VT không unmount, overhead không có lợi ích      |
| Legacy với synchronized             | FixedThreadPool + refactor    | Pinning của VT sẽ giết hiệu năng                 |
| Resource hạn chế (DB, giới hạn API) | VT + Semaphore                | VT scale, Semaphore giới hạn                     |

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Virtual Thread (VT) — các thread nhẹ được quản lý bởi JVM, không phải OS; stack trong heap (động), không phải native stack (tĩnh 1MB)
- Khi blocking I/O, VT "unmount" — JVM lưu stack vào StackChunk và trao Carrier Thread cho một VT khác
- Carrier Thread Pool mặc định là ForkJoinPool có kích thước = số lõi CPU
- Pinning: synchronized và các native method ngăn VT unmount — Carrier Thread bị chặn; giải pháp: ReentrantLock
- ThreadLocal + triệu VT = OutOfMemoryError; giải pháp thay thế: Scoped Values (Java 21 Preview)
- VT cho I/O-bound (web server, API), KHÔNG cho CPU-bound (tính toán)
- Spring Boot 3.2+: `spring.threads.virtual.enabled=true`

**Các câu hỏi phụ thường gặp:**
- **Tại sao VT không phù hợp cho các tác vụ CPU-bound?** — VT không unmount trong lúc tính toán, chỉ thêm overhead của scheduler JVM
- **StackChunk là gì?** — Một object trong heap lưu stack của một virtual thread; khi mount, được sao chép sang stack CPU thật
- **Làm sao chẩn đoán pinning?** — Cờ `-Djdk.tracePinnedThreads=full` xuất stack trace mỗi sự kiện pinning
- **Có thể tạo bao nhiêu VT?** — Hàng triệu; giới hạn là heap (khuyến nghị ít nhất 256MB cho một triệu VT)

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Virtual Thread giống hệt goroutine trong Go" — VT tương tự goroutine nhưng chạy trên JVM với các Carrier Thread
- "VT luôn nhanh hơn Platform Thread" — VT nhanh hơn chỉ cho I/O-bound; cho CPU-bound VT chậm hơn do overhead
- "Có thể chỉ cần thay mọi synchronized bằng VT mà không thay đổi gì" — synchronized gây pinning, cần thay bằng ReentrantLock
- "VT không tương thích với ExecutorService" — `Executors.newVirtualThreadPerTaskExecutor()` là cách chuẩn để làm việc với VT
