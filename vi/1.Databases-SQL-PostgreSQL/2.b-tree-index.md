# How does B-tree index work? (B-tree index hoạt động như thế nào?)

## 🟢 Junior Level

**B-tree (Balanced Tree — cây cân bằng)** là một cây cân bằng mà PostgreSQL sử dụng để lưu trữ index theo mặc định.

**Tại sao gọi là "cân bằng"?** Tất cả các đường đi từ root (gốc) đến leaf (lá) đều có cùng độ dài. Điều này đảm bảo rằng bất kỳ tìm kiếm nào cũng sẽ mất cùng một khoảng thời gian — không có trường hợp "xấu" như trong cây nhị phân (binary tree) thông thường, vốn có thể suy biến thành một danh sách liên kết (linked list).

**Ví dụ minh họa đơn giản:** Hãy tưởng tượng mục lục trong một cuốn sách, được chia thành các cấp độ:
- Cấp cao nhất: các phần (Chương 1-10)
- Cấp giữa: các mục con (1.1, 1.2, 1.3...)
- Cấp thấp nhất: các trang cụ thể

Để tìm một trang, bạn đi từ trên xuống dưới, loại bỏ các phần không cần thiết.

**Ý tưởng chính:**
- Toàn bộ dữ liệu đã được sắp xếp
- Tìm kiếm nhanh: ngay cả với một triệu phần tử, bạn chỉ cần ~20-30 lần so sánh
- PostgreSQL tự động duy trì sự cân bằng của cây

**Ví dụ:**
```sql
-- Tạo một B-tree index (mặc định)
CREATE INDEX idx_users_email ON users(email);

-- Tìm kiếm có index: O(log n) thay vì O(n)
SELECT * FROM users WHERE email = 'test@example.com';
```

**Khi nào nên sử dụng:**
- Cho hầu hết các trường hợp (đây là loại index mặc định)
- Cho tìm kiếm so sánh bằng: `WHERE id = 5`
- Cho tìm kiếm theo khoảng giá trị: `WHERE price BETWEEN 100 AND 500`
- Cho việc sắp xếp: `ORDER BY created_at DESC`

## 🟡 Middle Level

### Cách hoạt động bên trong

Index được lưu trữ trong các **page (trang) 8 KB**. Cấu trúc là phân cấp (hierarchical):

```
Root (Gốc)
  ├── Internal Node (Nút trung gian) → Internal Node → Leaf Node (Nút lá)
  └── Internal Node → Leaf Node
```

**Cấu trúc page:**
1. **Page Header (Tiêu đề trang)** — metadata (LSN — Log Sequence Number, số thứ tự bản ghi trong WAL log dùng để khôi phục khi gặp sự cố; checksum để kiểm tra tính toàn vẹn)
2. **Index Tuples** — các cặp `key + TID` (con trỏ trỏ đến dòng trong bảng)
3. **Special Area (Vùng đặc biệt)** — các con trỏ trỏ đến các page lân cận (P_NEXT, P_PREV)
4. **High Key** — giá trị lớn nhất trên page

### Thuật toán tìm kiếm

1. Bắt đầu từ page **Root**
2. So sánh giá trị cần tìm với các key
3. Đi xuống child node (nút con) phù hợp
4. Lặp lại cho đến khi đến được page **Leaf**
5. Trong Leaf, tìm TID và đọc dòng dữ liệu từ bảng

### Tại sao dùng B-tree thay vì cây nhị phân thông thường?

| Đặc điểm              | Cây nhị phân      | B-tree (PostgreSQL)         |
| --------------------------- | ---------------- | --------------------------- |
| **Hệ số phân nhánh (branching factor)**        | 2 (trái/phải)   | 100+ (nhiều nút con)     |
| **Chiều cao cho 1 triệu bản ghi**   | ~20 cấp       | ~3-4 cấp                 |
| **Số thao tác I/O**          | Nhiều             | Tối thiểu (đọc theo page)    |

### Các lỗi thường gặp

1. **Cố gắng index mọi thứ**
   - B-tree chiếm dung lượng đĩa và RAM
   - Mỗi lần INSERT/UPDATE đều yêu cầu cập nhật index

2. **Sai thứ tự trong composite index (index kết hợp)**
   ```sql
   -- Index (last_name, first_name)
   -- ✅ Sẽ được sử dụng
   WHERE last_name = 'Ivanov'

   -- ✅ Sẽ được sử dụng
   WHERE last_name = 'Ivanov' AND first_name = 'Ivan'

   -- ❌ Sẽ KHÔNG được sử dụng (hoặc kém hiệu quả)
   WHERE first_name = 'Ivan'
   ```

3. **Tìm kiếm với hàm (functions)**
   ```sql
   -- ❌ Index sẽ không được sử dụng
   WHERE UPPER(name) = 'IVAN'

   -- ✅ Tạo một functional index (index dựa trên hàm)
   CREATE INDEX idx_users_name_upper ON users(UPPER(name));
   ```

### Khi nào KHÔNG nên dùng B-tree

- Cho tìm kiếm toàn văn (full-text search) → dùng **GIN**
- Cho dữ liệu địa lý (geospatial) → dùng **GiST**
- Chỉ cần so sánh bằng và cần dung lượng bộ nhớ tối thiểu → **Hash**
- Cho mảng (arrays) và JSONB → **GIN**

### Ví dụ thực tiễn

```sql
-- B-tree hỗ trợ sắp xếp
CREATE INDEX idx_orders_date ON orders(created_at DESC);

-- Truy vấn không cần sắp xếp (dữ liệu đã được sắp xếp sẵn trong index)
SELECT * FROM orders ORDER BY created_at DESC LIMIT 10;
-- Plan: Index Scan Backward (rất nhanh)
```

## 🔴 Senior Level

### Triển khai nội bộ (Internal Implementation)

Việc triển khai B-tree của PostgreSQL dựa trên thuật toán **Lehman và Yao** đã được cải tiến, cung cấp khả năng truy cập đồng thời (concurrency) cao mà không cần khóa toàn bộ đường đi từ root đến leaf.

**Cấu trúc Meta-page (page 0):**
```
Meta-page
  ├── Magic number (số định danh loại index)
  ├── Version (phiên bản)
  ├── Root page number (số hiệu page gốc)
  └── Fastroot (bộ nhớ đệm root để truy cập nhanh hơn)
```

**Cấu trúc Leaf Node:**
```
┌─────────────────────────────────┐
│ Page Header (16 bytes)          │
├─────────────────────────────────┤
│ ItemId_1 → IndexTuple_1         │
│ ItemId_2 → IndexTuple_2         │
│ ...                             │
├─────────────────────────────────┤
│ High Key (giá trị lớn nhất)        │
├─────────────────────────────────┤
│ Special Area (P_NEXT, P_PREV)   │
└─────────────────────────────────┘
```

**High Key:** Rất quan trọng để đảm bảo tính đúng đắn của tìm kiếm trong lúc xảy ra split (tách trang) đồng thời. Nếu trong quá trình đi xuống ta thấy giá trị > High Key → ta đi đến P_NEXT mà không cần quay lại root.

### Thuật toán truy cập đồng thời (Concurrent access)

**Tìm kiếm:**
1. Lấy một `AccessShareLock` ngắn hạn trên page (một loại khóa nhẹ không ngăn cản các tiến trình khác đọc song song page đó)
2. Đi xuống, giải phóng khóa trên các page cha
3. Ngay cả khi một tiến trình song song khác đang thực hiện Split, việc tìm kiếm vẫn đảm bảo tính đúng đắn

**Page Split (Tách trang):**
```
Trước khi split:          Sau khi split:
┌──────────┐        ┌──────────┐   ┌──────────┐
│ A B C D E│  →     │ A B C    │→  │ D E      │
└──────────┘        └──────────┘   └──────────┘
                         ↑
                    Node cha được cập nhật
```

1. Tạo một page mới bên "phải"
2. Di chuyển một nửa dữ liệu
3. Cập nhật node cha
4. **Lưu ý quan trọng:** Các cột INCLUDE KHÔNG được lưu trong các node Internal, chỉ lưu trong Leaf

### Các tối ưu hóa hiện đại (PG 13+)

> Ở PG 12 trở xuống, không có deduplication (loại bỏ trùng lặp) — mỗi key được lưu riêng biệt. Với nhiều giá trị trùng lặp, index sẽ phình to đáng kể. Giải pháp: REINDEX định kỳ.

**Deduplication (Loại bỏ trùng lặp):**
```sql
-- PostgreSQL 13+ gộp các key giống nhau lại
-- Trước: (key=1, TID=1), (key=1, TID=2), (key=1, TID=3)
-- Sau: (key=1, TIDs=[1,2,3])

-- Đặc biệt hiệu quả cho các cột có cardinality (độ đa dạng giá trị) thấp
CREATE INDEX idx_orders_status ON orders(status);
-- Cardinality thấp = nhiều key trùng lặp. Thay vì lưu
-- (key='ACTIVE', TID=1), (key='ACTIVE', TID=2), ..., (key='ACTIVE', TID=1000000)
-- deduplication lưu: (key='ACTIVE', TIDs=[1,2,...,1000000])
-- → tiết kiệm tỷ lệ thuận với số lượng trùng lặp: 70-90% dung lượng
```

**Đánh dấu LP_DEAD:**
- Khi một dòng bị xóa khỏi Heap, mục tương ứng trong index được đánh dấu `LP_DEAD`
- `VACUUM` sẽ xóa vật lý các mục đó
- **Lưu ý quan trọng:** VACUUM giải phóng không gian bên trong các page nhưng **KHÔNG làm giảm** kích thước file vật lý trên đĩa

### Các trường hợp đặc biệt (Edge Cases)

1. **Bloat (Phình)**
   ```sql
   -- Chẩn đoán thông qua pgstattuple
   SELECT * FROM pgstatindex('idx_users_email');
   -- avg_leaf_density < 50% → cần REINDEX

   -- Xử lý
   REINDEX INDEX CONCURRENTLY idx_users_email;
   ```

2. **Fill Factor (Hệ số lấp đầy)**
   ```sql
   -- Đối với các index được cập nhật thường xuyên, hãy dành sẵn không gian
   CREATE INDEX idx_orders_status ON orders(status) WITH (fillfactor = 70);
   -- 30% của page vẫn còn trống cho các lần cập nhật
   -- Giảm thiểu Page Split
   ```

3. **Index bị hỏng (Corrupted Index)**
   ```sql
   -- Kiểm tra tính toàn vẹn
   SELECT bt_page_items('idx_users_email', 1);

   -- Xây dựng lại sau sự cố
   REINDEX DATABASE my_database;
   ```

### Hiệu năng

**Độ phức tạp của thao tác:**
- Tìm kiếm: **O(logₙ N)**, trong đó n là hệ số phân nhánh (thường là 100-1000)
- Chiều cao của cây cho 1 tỷ bản ghi: **3-4 cấp**
- Số thao tác I/O cho một lần tìm kiếm: **3-4 lần đọc page**

**Dung lượng bộ nhớ chiếm dụng (Memory Footprint):**
- Mỗi mục trong index: ~16-24 byte + kích thước key
- Với 100 triệu bản ghi có key kiểu int: ~2-3 GB dung lượng index
- **Quan trọng:** Index nên vừa với `shared_buffers` (RAM)

### Kinh nghiệm Production

**Tình huống thực tế:**
- Nền tảng thương mại điện tử: 500 triệu đơn hàng
- Vấn đề: Index trên `order_id` phình lên đến 50 GB (60% Bloat)
- Triệu chứng: Truy vấn chậm hơn 10 lần, tỷ lệ Cache Miss > 40%
- Giải pháp:
  - `REINDEX CONCURRENTLY` (không khóa)
  - Thêm `fillfactor = 80` khi xây dựng lại
  - Kết quả: Index giảm còn 20 GB, tỷ lệ Cache Hit > 95%

### Giám sát (Monitoring)

```sql
-- Kiểm tra trạng thái index
SELECT
    indexrelname,
    pg_size_pretty(pg_relation_size(indexrelid)) as size,
    idx_scan,
    idx_tup_read,
    idx_tup_fetch
FROM pg_stat_user_indexes
WHERE relname = 'orders';

-- Kiểm tra Bloat
SELECT
    index_name,
    bloat_pct,
    real_size,
    extra_size
FROM pg_index_bloat_stats
WHERE schemaname = 'public';

-- Kiểm tra độ sâu (level) của cây
SELECT * FROM pgstatindex('idx_orders_id');
-- tree_level = 0 → tất cả nằm trong một page
-- tree_level = 3 → cây lớn bình thường
```

### Best Practices (Thực hành tốt nhất)

1. Sử dụng `CONCURRENTLY` khi tạo/xây dựng lại index trong production
2. Đặt `fillfactor = 70-80` cho các index được cập nhật thường xuyên
3. Thường xuyên kiểm tra `avg_leaf_density` thông qua `pgstattuple`
4. Deduplication được bật mặc định trong PG 13+ — hãy đảm bảo bạn đang dùng phiên bản cập nhật
5. Giám sát kích thước index so với RAM

### Tóm tắt cho Senior

- B-tree là một **cấu trúc trên đĩa (disk structure)** được tối ưu cho khả năng đồng thời (Lehman & Yao)
- **High Key** đảm bảo tính đúng đắn của tìm kiếm trong lúc xảy ra split đồng thời
- **Các cột INCLUDE** chỉ nằm trong node Leaf — không làm phình cây tìm kiếm
- **Deduplication** (PG 13+) giảm đáng kể Bloat đối với các cột có cardinality thấp
- `REINDEX CONCURRENTLY` — công cụ chính để chống lại Bloat trong production

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- B-tree là một cấu trúc phân cấp: Root → Internal → Leaf (TID → Heap)
- Hệ số phân nhánh 100+ → chiều cao 3-4 cấp ngay cả với 1 tỷ bản ghi
- Độ phức tạp tìm kiếm: O(logₙ N), trong đó n là hệ số phân nhánh
- Thuật toán Lehman-Yao: truy cập đồng thời mà không cần khóa toàn bộ đường đi
- **High Key** — giá trị lớn nhất trên một page, cần thiết để đảm bảo tính đúng đắn trong lúc split
- Deduplication (PG 13+): gộp các key giống nhau → tiết kiệm 70-90% dung lượng
- `fillfactor = 70-80` cho các index được cập nhật thường xuyên → ít split hơn

**Các câu hỏi phụ thường gặp:**
- "Tại sao dùng B-tree thay vì cây nhị phân?" → B-tree có hệ số phân nhánh 100+ so với 2, ít I/O hơn
- "Page Split là gì và tại sao nó không tốt?" → việc phân chia page khi insert → gây ra Bloat
- "Deduplication tiết kiệm dung lượng như thế nào?" → `(key=1, TIDs=[1,2,3])` thay vì 3 mục riêng biệt
- "Điều gì xảy ra khi Bloat đạt 60%?" → Cache Miss, Random I/O, cần `REINDEX CONCURRENTLY`
- "Tại sao các cột INCLUDE chỉ nằm trong Leaf?" → Chúng không làm phình các node Internal → ít cấp cây hơn

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "B-tree là một cây nhị phân" (sai, B-tree = cây đa nhánh)
- ❌ "VACUUM làm giảm kích thước file index" (sai, cần REINDEX)
- ❌ "Deduplication hoạt động với tất cả các index" (chỉ từ PG 13+, không áp dụng cho unique)
