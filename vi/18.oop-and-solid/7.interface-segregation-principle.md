# What is Interface Segregation Principle? (Interface Segregation Principle là gì?)

## Deep Dive (Under the Hood)

Interface Segregation Principle (ISP) nói rằng: **"Client không nên phụ thuộc vào các phương thức mà chúng không dùng.**

**Client** — một class phụ thuộc vào một interface (gọi các phương thức của nó hoặc triển khai nó). Nếu một interface ép một class triển khai các phương thức nó không cần — ISP bị vi phạm."

Ở cấp độ bytecode và JVM, một interface lớn (Fat Interface) tạo ra các dependency không cần thiết trong Constant Pool của mỗi class triển khai. Constant Pool — một bảng tham chiếu trong file .class. Mỗi phương thức interface thêm một entry. VTable — bảng phương thức ảo. Nhiều phương thức hơn = bảng lớn hơn = hơi nhiều bộ nhớ hơn và các lệnh gọi chậm hơn. Nhưng vấn đề chính là kiến trúc: "ô nhiễm" code với các phương thức stub.

## Senior Insight: Role Interfaces vs Header Interfaces

### 1. Header Interfaces (Anti-pattern)
Đây là khi với mỗi class `MyService` một interface `IMyService` được tạo ra chỉ đơn giản sao chép tất cả các phương thức công khai của nó.
- **Vấn đề**: Đây không phải là một abstraction, nó chỉ là trùng lặp. Khi thêm một phương thức vào service, nó được thêm vào interface, và tất cả các client của nó bị buộc phải biên dịch lại.

### 2. Role Interfaces (Cách Tiếp Cận Senior)
Một interface nên mô tả **vai trò** của một object trong một tương tác cụ thể, không phải tất cả khả năng của nó.
- Một class có thể triển khai 10 role interface nhỏ (`Serializable`, `Cloneable`, `Printable`).
- Một client (ví dụ, máy in) chỉ yêu cầu `Printable`, và nó không quan tâm liệu object có thể lưu vào database hay không.

## Dấu Hiệu Vi Phạm ISP

1.  **`UnsupportedOperationException`**: Dấu hiệu rõ ràng nhất. Bạn triển khai một phương thức chỉ vì interface ép bạn làm vậy, nhưng không có logic nào cho nó.
2.  **Các phương thức rỗng**: Tương tự, phương thức đơn giản không làm gì cả.
3.  **Fat contract**: Khi test một phương thức yêu cầu mock 20 hàm trong interface, mặc dù phương thức chỉ dùng một.

## Giải Pháp Thông Qua Pattern Adapter

Đôi khi bạn không thể thay đổi interface "béo" của một thư viện bên thứ ba. Trong trường hợp này, hãy dùng một **Adapter**:
```java
// Interface béo của bên thứ ba
public interface ThirdPartyCloud {
    void upload();
    void delete();
    void list();
    void billing(); // Chúng ta không cần cái này
}

// Interface hẹp của chúng ta
public interface SimpleUploader {
    void upload();
}

// Adapter tuân thủ ISP cho ứng dụng của chúng ta
public class CloudAdapter implements SimpleUploader {
    private final ThirdPartyCloud cloud;
    public void upload() { cloud.upload(); }
}
```

## Hiệu Năng Và Highload

- **Binary Compatibility**: ISP cải thiện binary compatibility. Nếu bạn thêm một phương thức vào một interface `Payment` hẹp, nó chỉ ảnh hưởng đến các service thực sự làm việc với thanh toán, không phải toàn bộ dự án.
- **Cache Locality**: Ít phương thức hơn trong interface (và, tương ứng, trong VTable của các object) về mặt lý thuyết có thể vừa vặn hơi tốt hơn trong CPU instruction cache, nhưng trong thực tế đây là một tối ưu vi mô.

## Edge Cases

- **Default Method (Java 8+)**: Cho phép thêm các phương thức vào interface mà không phá vỡ các triển khai. Tuy nhiên, điều này **không cứu** khỏi vi phạm ISP. Interface vẫn "béo", nó chỉ bây giờ làm ô nhiễm namespace của client với các default method.
- **Single Method Interface**: Interface một phương thức là một hướng dẫn tốt, nhưng không phải một giáo điều. Một interface với 2-3 phương thức liên quan (ví dụ, `open()/close()/isOpen()`) cũng có thể đúng.

### Khi Nào KHÔNG Nên Tuân Thủ ISP Nghiêm Ngặt

1. **Interface với 1-2 phương thức** — không có ý nghĩa để chia tách thêm
2. **Tất cả các triển khai dùng tất cả các phương thức** — chia tách không mang lại lợi ích
3. **Interface nội bộ package** — không hiển thị ra bên ngoài, tác động tối thiểu

## Tóm Tắt Cho Senior
- Các interface thuộc về **client**, không phải các triển khai.
- Ưu tiên nhiều interface nhỏ hơn một interface lớn.
- Dùng **Default Method** một cách thận trọng.
- Nhớ: ISP giảm coupling và đơn giản hóa testing bằng cách giảm số lượng mock.

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- ISP: client không nên phụ thuộc vào các phương thức mà chúng không dùng
- Fat Interface ép các class triển khai các phương thức không cần thiết → `UnsupportedOperationException` và các stub
- Role Interface > Header Interface: interface mô tả một vai trò, không phải tất cả khả năng của class
- Các interface thuộc về client, không phải các triển khai
- Pattern Adapter giúp tuân thủ ISP cho các thư viện bên thứ ba
- Default Method (Java 8+) không cứu khỏi vi phạm ISP — chúng chỉ làm ô nhiễm namespace

**Các câu hỏi phụ thường gặp:**
- **Header Interface vs Role Interface?** — Header sao chép tất cả các phương thức class (anti-pattern), Role mô tả một vai trò cụ thể (`Printable`, `Serializable`)
- **ISP đơn giản hóa testing như thế nào?** — Ít mock hơn: class được test chỉ phụ thuộc vào các phương thức nó cần
- **Một interface với 1-2 phương thức có nên chia tách không?** — Không, chia tách thêm không mang lại lợi ích
- **ISP liên quan đến DIP như thế nào?** — Các interface hẹp là các abstraction ổn định hơn mà các module phụ thuộc vào

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Mỗi class cần interface riêng của nó" (đó là Header Interface — một anti-pattern)
- "Default method giải quyết vấn đề ISP" (không, interface vẫn béo)
- "Một interface 20 phương thức là ổn" (phụ thuộc vào việc client dùng bao nhiêu phương thức)
