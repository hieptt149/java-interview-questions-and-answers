# What are GC roots? (GC roots là gì?)

## Junior Level

**GC Roots** — các đối tượng "gốc" (root) mà từ đó GC bắt đầu tìm kiếm các đối tượng còn sống.

**Ví dụ minh họa đơn giản:** Một cái cây. Rễ chính là GC Roots. Nếu một cành cây (đối tượng) có thể được tiếp cận từ một cái rễ → nó còn sống.

**GC Roots là gì:**
- Các biến cục bộ (local variable) trong các phương thức
- Các trường tĩnh (static field) của class
- Các luồng đang hoạt động
- Các tham chiếu JNI

**Quy tắc:** Đối tượng có thể được tiếp cận từ GC Root → đối tượng còn sống.

---

## Middle Level

### Phân loại đầy đủ

```
GC Roots:
├── Stack Locals (các biến cục bộ)
├── Static Fields (các trường tĩnh)
├── Thread Objects (các luồng đang hoạt động)
├── JNI Global (các tham chiếu native toàn cục)
├── JNI Local (các tham chiếu native cục bộ)
├── Monitor Used (các đối tượng trong synchronized)
└── JVM Internal (các đối tượng hệ thống)
```

### OopMaps

```
OopMaps (Ordinary Object Pointer Maps): JIT tạo một bản đồ trong đó mỗi byte của
code chỉ định các biến cục bộ nào chứa tham chiếu. Không có OopMaps, GC
sẽ phải quét từng byte của stack — chậm, cộng thêm các false positive
(các giá trị int bình thường mà tình cờ trông giống như con trỏ).
  → Tại các Safepoint, JIT biết register/offset nào = tham chiếu
  → Root Scanning trong vài mili-giây
```

### Path to GC Roots (MAT)

```
MAT: Path to GC Roots
  → loại trừ soft/weak/phantom → chỉ các strong reference
  → Hiển thị ai đang giữ đối tượng

→ 99% các rò rỉ = các strong reference từ Static hoặc Thread
```

## Senior Level

### Root Scanning và Latency

```
Số lượng Roots ảnh hưởng đến các khoảng dừng:
  → 1000 luồng → quét stack lâu
  → Hàng triệu key trong một static HashMap

Java hiện đại (Handshakes):
  → Quét theo từng luồng (per-thread)
  → Khoảng dừng toàn cục được giảm thiểu
```

### Các rò rỉ JNI Global Reference

```
Native code đã tạo một tham chiếu toàn cục:
  → NewGlobalRef(obj)
  → Quên DeleteGlobalRef

→ Đối tượng sẽ không bị GC!
→ Rò rỉ "vô hình"

MAT hiển thị các JNI Global Reference như là GC Roots. Chúng xuất hiện dưới dạng
"JNI Global" trong view Path to GC Roots. Nhưng các JNI Local Reference (các tham chiếu
trong native code) không hiển thị với MAT — đây là một "điểm mù" (blind spot).
```

### Finalizer Queue

```
Các đối tượng có finalize():
  → Sau khi chết, đi vào Finalizer Queue
  → Trở thành một GC Root tạm thời
  → Cho đến khi finalize() thực thi xong → đối tượng còn sống

→ Việc loại bỏ bị trì hoãn
→ Luồng Reference Handler xử lý hàng đợi
```

### Best Practices

1. **Giám sát** thời gian Root Scanning trong GC logs
2. **JNI** → DeleteGlobalRef là bắt buộc
3. **exclude weak/soft** trong MAT
4. **Handshakes (Java 11+)** → ít STW toàn cục hơn
5. **Giảm thiểu** số lượng luồng

### Tóm tắt cho Senior

- **GC Roots** = nền tảng của Reachability Analysis
- **OopMaps** = quét nhanh
- **JNI Global** = các rò rỉ vô hình
- **Root Scanning time** → chỉ báo các vấn đề
- **Path to GC Roots** = công cụ MAT chính
- **Finalizer Queue** = GC Root tạm thời

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- GC Roots — các đối tượng gốc mà từ đó GC bắt đầu duyệt reachability: Stack Locals, Static Fields, Thread Objects, JNI Global, JNI Local, Monitor Used, JVM Internal
- OopMaps: JIT tạo một bản đồ trong đó mỗi byte của code chỉ định các biến nào chứa tham chiếu; không có OopMaps, GC sẽ quét từng byte (chậm + false positive)
- Path to GC Roots (MAT): loại trừ soft/weak/phantom → chỉ các strong reference; 99% các rò rỉ = các tham chiếu từ Static hoặc Thread
- Các rò rỉ JNI Global Reference: `NewGlobalRef(obj)` không có `DeleteGlobalRef` → đối tượng sẽ không bị GC; MAT hiển thị dưới dạng "JNI Global" trong Path to GC Roots
- Finalizer Queue: các đối tượng có `finalize()` trở thành GC Root tạm thời sau khi chết; cho đến khi `finalize()` thực thi xong → đối tượng còn sống
- Root Scanning time: số lượng Roots ảnh hưởng đến các khoảng dừng; 1000 luồng → quét stack lâu; Handshakes (Java 11+) giảm thiểu khoảng dừng toàn cục

**Các câu hỏi phụ thường gặp:**
- **Tại sao OopMaps quan trọng cho hiệu năng?** — Không có OopMaps, GC quét từng byte của stack → chậm + false positive (int tình cờ trông giống con trỏ)
- **Làm sao JNI Global Reference gây rò rỉ?** — Native code đã tạo một tham chiếu toàn cục và quên xóa; GC coi nó như một GC Root → đối tượng không bao giờ bị xóa
- **Tại sao Finalizer Queue là một GC Root tạm thời?** — Đối tượng có `finalize()` đi vào Finalizer Queue sau khi chết; cho đến khi `finalize()` thực thi xong → đối tượng còn sống → trì hoãn việc loại bỏ
- **Root Scanning time trong GC logs là gì?** — Thời gian để quét tất cả các GC Roots; nếu tăng lên → quá nhiều luồng hoặc các tham chiếu tĩnh

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "GC Roots chỉ là các trường tĩnh" — cũng bao gồm Stack Locals, Thread Objects, các tham chiếu JNI, các đối tượng Monitor
- "Các rò rỉ JNI hiển thị trong Heap Dump" — JNI Global thì hiển thị, nhưng JNI Local (trong native code) là "điểm mù" của MAT
- "finalize() nhanh và an toàn" — đối tượng còn sống cho đến khi `finalize()` thực thi xong; luồng Reference Handler xử lý hàng đợi một cách bất đồng bộ
