# Why Is It Important to Avoid Blocking Operations in CompletableFuture? (Tại sao quan trọng phải tránh các thao tác chặn trong CompletableFuture)

## 🟢 Junior Level

CompletableFuture thường chạy trong **ForkJoinPool.commonPool()**, nơi có **rất ít thread** (thường = số lõi CPU - 1).

Nếu một trong các thread bị chặn, các tác vụ khác sẽ không thể chạy — điều này được gọi là **thread pool starvation** (đói tài nguyên thread pool).

```java
// ❌ Nguy hiểm — chặn một thread ForkJoinPool
CompletableFuture.supplyAsync(() -> {
    return httpClient.get(url);  // I/O chặn
});

// ✅ An toàn — Executor riêng cho I/O
ExecutorService ioExecutor = Executors.newFixedThreadPool(20);
CompletableFuture.supplyAsync(() -> {
    return httpClient.get(url);
}, ioExecutor);
```

**Analogy đơn giản:**
- ForkJoinPool giống như 4 quầy thu ngân trong một cửa hàng
- Nếu một thu ngân ngủ gật — hàng đợi ngừng di chuyển
- Bạn cần giữ cho các thu ngân tỉnh táo!

## 🟡 Middle Level

### Thread Pool Starvation

```java
// commonPool có 7 thread (trên CPU 8 lõi)
// Nếu 7 tác vụ chặn — tất cả các tác vụ mới phải chờ

for (int i = 0; i < 100; i++) {
    CompletableFuture.supplyAsync(() -> {
        Thread.sleep(5000);  // chặn thread
        return "done";
    });
}
// Chỉ 7 tác vụ đầu tiên thực thi
// 93 tác vụ còn lại chờ một thread trở nên trống
```

### Hậu Quả

1. **Deadlock:**
```java
CompletableFuture<String> cf1 = CompletableFuture.supplyAsync(() -> {
    return cf2.join();  // chờ cf2
});

CompletableFuture<String> cf2 = CompletableFuture.supplyAsync(() -> {
    return cf1.join();  // chờ cf1 — deadlock!
});
```

2. **Suy giảm hiệu năng:**
```java
// Tất cả thread bị chiếm dụng bởi các thao tác chặn
// Độ trễ tăng, throughput giảm
```

### Các Lỗi Thường Gặp

1. **Chặn trong thenApply:**
```java
// ❌ thenApply chạy trong ForkJoinPool
cf.thenApply(s -> {
    return httpClient.sendBlocking(url);  // chặn!
});

// ✅ thenApplyAsync với Executor I/O
cf.thenApplyAsync(s -> httpClient.sendBlocking(url), ioExecutor);
```

## 🔴 Senior Level

### Triển Khai Nội Bộ

**ForkJoinPool.commonPool():**
```java
// Kích thước = Runtime.getRuntime().availableProcessors() - 1
// Với 8 lõi = 7 thread
// Đối với tác vụ CPU-bound — lý tưởng
// Theo mặc định, kích thước pool = availableProcessors() - 1 (có thể thay đổi qua
// `java.util.concurrent.ForkJoinPool.common.parallelism`). Hoạt động tốt cho các tác vụ
// CPU-bound, nhưng đối với I/O nó có thể trở thành nút thắt cổ chai dưới tải chặn nặng.
```

**Work-stealing:**
```
// ForkJoinPool dùng work-stealing
// Nhưng nếu tất cả thread đều bị chặn — việc đánh cắp không giúp được gì

// Thread 1: [BLOCKED trên I/O]
// Thread 2: [BLOCKED trên I/O]
// Thread 3: [BLOCKED trên I/O]
// ...
// Hàng đợi: [các tác vụ đang chờ...]  // không ai xử lý chúng
```

### Đánh Đổi Kiến Trúc

| Cách tiếp cận            | Ưu điểm                 | Nhược điểm                  |
| ------------------- | -------------------- | --------------------- |
| **commonPool**      | Không cần thiết lập      | Chỉ dành cho CPU-bound        |
| **Custom Executor** | Kiểm soát toàn diện         | Cần quản lý   |
| **Virtual Threads** | Tốt nhất của cả hai thế giới  | Chỉ Java 21+              |

### Edge Cases

**1. Chặn theo tầng (Cascading blocking):**
```java
// Một lời gọi chặn kéo theo những cái khác
cf1.thenApply(s -> blockingCall1(s))
   .thenCompose(r -> blockingCall2(r))
   .thenAccept(result -> blockingCall3(result));
// Một CF = 3 thao tác chặn = gấp 3 lần thời gian chặn
```

**2. Workload hỗn hợp:**
```java
// CPU-bound + I/O trong cùng một pool
CompletableFuture.supplyAsync(() -> heavyCalculation());  // CPU
CompletableFuture.supplyAsync(() -> httpClient.get(url)); // I/O

// I/O chặn thread — các tác vụ CPU phải chờ
```

### Hiệu Năng

```
Hiệu ứng thread pool starvation:
- Trong trường hợp xấu nhất, khi pool đã bão hòa hoàn toàn với các tác vụ, một tác vụ chặn
  làm giảm throughput khoảng 1/N, trong đó N là kích thước pool. Mức thiệt hại thực tế
  phụ thuộc vào bản chất của các tác vụ và hành vi work-stealing.
- 7 tác vụ chặn = mất 100% (deadlock hoàn toàn)

Giải pháp Virtual Threads:
- 100000+ tác vụ chặn = không có vấn đề gì
- Mỗi lời gọi chặn tạm dừng, không chặn OS thread
```

### Kinh Nghiệm Production

**Phát hiện starvation:**
```bash
# Thread dump
jstack <pid> | grep -A 10 "ForkJoinPool"

# Metric
- Active thread < kích thước pool
- Kích thước hàng đợi tăng
- Độ trễ tăng
```

**Phòng ngừa:**
```java
// ✅ Tách pool
ExecutorService cpuExecutor = Executors.newFixedThreadPool(
    Runtime.getRuntime().availableProcessors());
ExecutorService ioExecutor = Executors.newFixedThreadPool(50);

// Tác vụ CPU
CompletableFuture.supplyAsync(cpuTask, cpuExecutor);

// Tác vụ I/O
CompletableFuture.supplyAsync(ioTask, ioExecutor);

// ✅ Virtual Threads (Java 21+)
ExecutorService vThreads = Executors.newVirtualThreadPerTaskExecutor();
CompletableFuture.supplyAsync(anyTask, vThreads);
```

### Best Practices

```java
// ✅ Executor riêng cho I/O
CompletableFuture.supplyAsync(ioTask, ioExecutor);

// ✅ Virtual Threads
Executors.newVirtualThreadPerTaskExecutor();

// ✅ Giám sát thread pool
metrics.recordQueueSize(executor.getQueue().size());

// ❌ Chặn trong commonPool
// ❌ join()/get() không có timeout
// ❌ Bỏ qua thread starvation
```

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- ForkJoinPool.commonPool() có ít thread (availableProcessors - 1)
- Thread pool starvation: tất cả thread bị chặn, các tác vụ mới phải chờ
- Chặn trong commonPool làm giảm throughput cho TẤT CẢ các tác vụ (Parallel Stream, các CF khác)
- Chặn theo tầng: một lời gọi chặn kéo theo những cái khác trong chuỗi
- Giải pháp: Executor riêng cho I/O, Virtual Threads (Java 21+), tách pool

**Các câu hỏi phụ thường gặp:**
- **Điều gì xảy ra nếu 7 tác vụ chặn commonPool?** — Tất cả các tác vụ mới phải chờ, deadlock hoàn toàn
- **Work-stealing có giúp gì với việc chặn không?** — Không, nếu tất cả thread đều bị chặn — việc đánh cắp không hoạt động
- **Cách phát hiện starvation?** — jstack: ForkJoinPool-worker-X ở trạng thái BLOCKED/WAITING, kích thước hàng đợi tăng
- **Virtual Threads có giải quyết vấn đề không?** — Có, 100000+ tác vụ chặn không có vấn đề (Java 21+)

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Chặn trong thenApply cũng ổn — nó nhẹ" — thenApply chạy trong cùng thread, chặn phá hủy pool
- "commonPool tự động mở rộng" — bị giới hạn bởi availableProcessors - 1
- "join() không có timeout trong production là ổn" — chờ đợi vô hạn, lỗi dây chuyền
