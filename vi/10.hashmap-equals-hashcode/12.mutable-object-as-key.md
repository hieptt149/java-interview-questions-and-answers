# Can You Use a Mutable Object as a Key in HashMap? (Có thể dùng một object mutable làm key trong HashMap không?)

## 🟢 Junior Level

Về mặt kỹ thuật — **có, có thể**, nhưng **không được khuyến nghị**. Nếu bạn sửa đổi các field của một object key sau khi thêm nó vào HashMap, bạn sẽ không thể tìm thấy phần tử đó.

**Ví dụ minh họa đơn giản:** Bạn đặt một lá thư vào hộp thư #5. Rồi bạn sơn lại hộp thư một màu khác và đổi số thành #10. Người đưa thư sẽ tìm theo số mới và sẽ không tìm thấy lá thư.

**Ví dụ về vấn đề:**
```java
public class MutableKey {
    private int id; // Không final! Có thể thay đổi

    public void setId(int id) { this.id = id; }

    @Override public int hashCode() { return id; }
    @Override public boolean equals(Object o) { /* theo id */ }
}

MutableKey key = new MutableKey(1);
map.put(key, "Value"); // Rơi vào bucket #1
key.setId(2);          // Hash giờ = 2
System.out.println(map.get(key)); // null! Key bị "vỡ"
```

**Giải pháp:** Dùng các object immutable làm key — `String`, `Integer`, `Record`.

## 🟡 Middle Level

### Vấn đề "Key bị vỡ"

HashMap "ghi nhớ" vị trí của object theo `hashCode()` của nó tại thời điểm `put()`. Nếu hash thay đổi — phần tử ở lại bucket cũ, nhưng tìm kiếm đi tới bucket mới.

**Cơ chế thất bại:**
1. `key.hashCode() = 100` → `put(key, "Value")` → bucket #100
2. `key.setId(2)` → `hashCode() = 200`
3. `get(key)` → tìm trong bucket #200 → `null`
4. `remove(key)` → cũng sẽ không tìm thấy → rò rỉ bộ nhớ

### Có thể sửa đổi các field không nằm trong hashCode/equals không?

Về mặt kỹ thuật có, nhưng đó là **thực hành tồi**:
- Gây hiểu nhầm cho các developer khác
- Rủi ro: các field đó có thể được thêm vào contract sau này

### Cách làm đúng

| Cách tiếp cận        | Ví dụ                                 |
| -------------------- | ------------------------------------- |
| Các class immutable  | `String`, `Integer`, `LocalDate`      |
| Record (Java 14+)    | `public record Key(String id) {}`     |
| Các field final      | `private final String id;`            |
| Delete-Update-Insert | Xóa → sửa đổi → thêm lại              |

### Các sai lầm thường gặp

1. **Dùng JPA Entity làm key** — Entity thay đổi trong lúc hoạt động
2. **StringBuilder làm key** — mutable: nội dung của nó có thể bị thay đổi sau khi thêm vào Map, phá vỡ hashCode. String đảm bảo tính bất biến.
3. **Các collection làm key** — `ArrayList` là mutable, dùng một wrapper

## 🔴 Senior Level

### Pattern rò rỉ bộ nhớ

```java
Map<MutableKey, LargeObject> cache = new HashMap<>();
// Các key bị sửa đổi và "mất" — không thể xóa, không thể tìm
// Old Gen đầy → Full GC → OutOfMemoryError
```

Các entry "ghost" chiếm bộ nhớ nhưng không thể tiếp cận. Trong các hệ thống tải cao, điều này dẫn tới suy giảm qua hàng giờ/ngày.

### IdentityHashMap như một giải pháp thay thế

```java
Map<MutableKey, Value> map = new IdentityHashMap<>();
// Dùng System.identityHashCode() và == thay vì equals/hashCode
// Địa chỉ của object không thay đổi khi các field bị sửa đổi
```

⚠️ Nhưng điều này thay đổi ngữ nghĩa: hai object khác nhau với cùng các field = các key khác nhau. ĐỪNG dùng IdentityHashMap nếu bạn cần so sánh key dựa trên nội dung (hai object khác nhau với cùng các field nên được coi là cùng một key). Giải pháp này chỉ dành cho các trường hợp mà reference identity quan trọng.

### Cơ chế bên trong

HashMap không theo dõi các thay đổi của key. Nó:
- Không sao chép key (lưu một tham chiếu)
- Không kiểm chứng hash khi get/put
- Hoàn toàn tin tưởng `hashCode()` hiện tại của key

### Các trường hợp biên (Edge Case)

1. **Concurrent modification**: Một thread sửa đổi key, một thread khác tìm — race condition
2. **Serialization**: Khi deserialize, một object mới được tạo — cái "ghost" cũ còn lại
3. **WeakHashMap**: Nếu value tham chiếu tới key — phụ thuộc vòng, rò rỉ

### Chẩn đoán Production

Dấu hiệu của các vấn đề mutable-key:
- Kích thước Map tăng dần không khớp với business logic
- `get()` trả về null cho các key "chắc chắn tồn tại"
- Iterator tìm thấy các phần tử không thể tiếp cận qua `get()`

### Best Practices cho Highload

1. **Luôn các field `final`** trong các key: `private final String id;`
2. **Record** — trình biên dịch đảm bảo tính bất biến
3. **Defensive copy** khi nhận một key trong constructor
4. **Phân tích tĩnh** — cấm các key mutable qua code review

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Về mặt kỹ thuật có thể, nhưng KHÔNG được khuyến nghị: sửa đổi các field của key = "key bị vỡ"
- HashMap ghi nhớ bucket theo hashCode() lúc put; khi sửa đổi — tìm ở chỗ khác
- get() = null, remove() sẽ không tìm thấy → ghost entry, rò rỉ bộ nhớ
- IdentityHashMap như một giải pháp thay thế (dùng == và identityHashCode), nhưng thay đổi ngữ nghĩa
- Các key tốt nhất: String, Integer, Record (immutable theo thiết kế)
- StringBuilder/ArrayList là mutable — đừng dùng làm key

**Các câu hỏi phụ thường gặp:**
- **Có thể sửa đổi các field không nằm trong hashCode không?** — về mặt kỹ thuật có, nhưng thực hành tồi
- **Làm sao sửa một key mutable?** — xóa → sửa đổi → chèn lại, hoặc tạo lại Map
- **Tại sao JPA Entity là một key tồi?** — Entity thay đổi khi persist/merge
- **Ghost Entry Pattern là gì?** — các entry chiếm bộ nhớ nhưng không thể tiếp cận qua get

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Có thể dùng một object mutable nếu bạn không thay đổi nó" — quyết định mong manh
- "IdentityHashMap giải quyết mọi vấn đề" — không, nó thay đổi ngữ nghĩa thành identity-based
- "HashMap theo dõi các thay đổi của key" — không, nó không theo dõi
