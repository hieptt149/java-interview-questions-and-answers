# What is the difference between synchronized and volatile? (Sự khác biệt giữa synchronized và volatile là gì?)

---

## Junior Level

### Hiểu biết cơ bản

`synchronized` và `volatile` là hai từ khóa trong Java để làm việc với đa luồng (multithreading). Chúng giải quyết các vấn đề khác nhau:

| Đặc điểm             | volatile                                                                                                 | synchronized                                                                                                   |
| -------------------- | ------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| **Nó làm gì**        | Đảm bảo visibility (khả năng nhìn thấy: một lần ghi bởi một thread lập tức được mọi thread đọc nhìn thấy, không bị cache cục bộ) | Đảm bảo visibility + atomicity (tính nguyên tử: một thao tác gộp được thực thi trọn vẹn, không bị các thread khác xen vào) |
| **Áp dụng ở đâu**    | Chỉ cho field (biến)                                                                                     | Cho method hoặc block code                                                                                    |
| **Khóa (Locking)**   | Không                                                                                                    | Có (acquire monitor của object)                                                                               |
| **Deadlock**         | Không thể xảy ra                                                                                         | Có thể xảy ra                                                                                                 |

### Ví dụ volatile

```java
public class Worker {
    private volatile boolean running = true;

    public void stop() {
        running = false; // Mọi thread sẽ thấy giá trị này ngay lập tức
    }

    public void doWork() {
        while (running) {
            // Đang làm việc...
        }
    }
}
```

### Ví dụ synchronized

```java
public class Counter {
    private int count = 0;

    public synchronized void increment() {
        count++; // Thao tác atomic — chỉ một thread được thực thi tại một thời điểm
    }

    public synchronized int getCount() {
        return count;
    }
}
```

### Khi nào dùng cái nào

- **`volatile`** — cho các cờ (stop flag, ready flag), khi một thread ghi và các thread khác đọc
- **`synchronized`** — khi bạn cần đọc-sửa-ghi (read-modify-write) một cách atomic (bộ đếm, các thao tác gộp)

### Khi nào volatile KHÔNG phù hợp

1. **Các thao tác gộp** (increment, check-then-act): `volatile count++` KHÔNG atomic — hãy dùng AtomicInteger
2. **Nhóm các biến**: nếu bạn cần cập nhật atomic hai field — volatile không giúp được, bạn cần synchronized
3. **Các biến phụ thuộc**: nếu giá trị B phụ thuộc vào A — volatile không đảm bảo tính atomic của cặp (A, B)

## Middle Level

### Java Memory Model (JMM)

Cả hai cơ chế đều hoạt động bên trong **Java Memory Model (JMM)**, được định nghĩa trong JSR-133.

#### volatile hoạt động như thế nào

Khi ghi vào một biến `volatile`, JVM chèn vào các **Memory Barrier** (rào chắn bộ nhớ):

Memory Barrier (hàng rào bộ nhớ) — một lệnh CPU ngăn việc sắp xếp lại (reorder) các thao tác đọc/ghi xung quanh rào chắn. Không có rào chắn, bộ xử lý có thể sắp xếp lại các lệnh để tối ưu, dẫn tới hành vi sai trong môi trường đa luồng.

**Các loại rào chắn trong JVM:**
- **LoadLoad**: ngăn việc sắp xếp lại hai lần đọc
- **StoreStore**: ngăn việc sắp xếp lại hai lần ghi
- **LoadStore**: một lần đọc không thể bị sắp xếp lại sau một lần ghi
- **StoreLoad**: một lần ghi không thể bị sắp xếp lại sau một lần đọc (đắt nhất)

Trong đó "Load" = đọc từ bộ nhớ, "Store" = ghi vào bộ nhớ.

- **Store-Store barrier** — đảm bảo mọi lần ghi thông thường trước lần ghi volatile được đẩy (flush) xuống bộ nhớ
- **Store-Load barrier** — đảm bảo các lần đọc tiếp theo nhìn thấy dữ liệu mới nhất

```java
// Không có volatile — vấn đề visibility
int x = 0;
boolean ready = false; // không có volatile

// Thread 1:
x = 42;
ready = true;

// Thread 2:
if (ready) {
    System.out.println(x); // Có thể in ra 0! (x chưa được nhìn thấy)
}
```

```java
// Có volatile — đảm bảo visibility
int x = 0;
volatile boolean ready = false;

// Thread 1:
x = 42;
ready = true; // Store-Load barrier — x chắc chắn đã được ghi

// Thread 2:
if (ready) {
    System.out.println(x); // Luôn in ra 42!
}
```

#### Đảm bảo Happens-Before

Một lần ghi vào biến `volatile` **happens-before** một lần đọc tiếp theo của chính biến đó. Điều này nghĩa là mọi thay đổi được thực hiện trước lần ghi volatile sẽ được nhìn thấy bởi thread đọc nó.

### synchronized hoạt động như thế nào

`synchronized` cung cấp:
1. **Mutual Exclusion** (loại trừ lẫn nhau) — chỉ một thread thực thi code tại một thời điểm
2. **Visibility** — khi vào một synchronized block, cache bị vô hiệu hóa; khi ra, dữ liệu được flush xuống bộ nhớ
3. **Atomicity** — các thao tác gộp được thực thi như một đơn vị duy nhất

```java
// Vấn đề: volatile KHÔNG đảm bảo atomicity
volatile int counter = 0;
counter++; // KHÔNG an toàn! Đây là 3 thao tác: đọc → sửa → ghi

// Giải pháp: synchronized đảm bảo atomicity
synchronized(lock) {
    counter++; // An toàn — chỉ một thread thực thi
}
```

**volatile vs AtomicBoolean:** volatile chỉ đảm bảo visibility. AtomicBoolean đảm bảo visibility + atomicity qua CAS. Với một cờ đơn giản (`running = true`), volatile là đủ. Với `if (!flag.compareAndSet(false, true))`, bạn cần AtomicBoolean.

### Double-Checked Locking Pattern

Một ví dụ kinh điển nơi `volatile` là then chốt:

```java
public class Singleton {
    // BẮT BUỘC phải volatile! Không có nó, có thể xảy ra một object được khởi tạo dở dang
    private static volatile Singleton instance;

    public static Singleton getInstance() {
        if (instance == null) {                  // Kiểm tra lần đầu (không khóa)
            synchronized (Singleton.class) {
                if (instance == null) {          // Kiểm tra lần hai (có khóa)
                    instance = new Singleton();  // Tạo object
                }
            }
        }
        return instance;
    }
}
```

Không có `volatile`, kịch bản sau có thể xảy ra:
1. Thread A bắt đầu tạo `instance` (cấp phát bộ nhớ, nhưng constructor chưa xong)
2. JVM sắp xếp lại: gán reference trước, rồi mới gọi constructor
3. Thread B thấy `instance != null` và nhận về một object được khởi tạo dở dang

## Senior Level

### Bên trong: hiện thực ở mức CPU

#### volatile ở mức CPU

Trên kiến trúc x86, việc ghi vào một field volatile được dịch thành một lệnh có **`lock` prefix**, thứ:

`lock` prefix là một lệnh x86 khóa cache line trong suốt thời gian thao tác. Các core khác không thể đọc/ghi cache line này cho tới khi thao tác hoàn tất.

- Khóa cache line trong suốt thời gian ghi
- Gửi tín hiệu vô hiệu hóa (invalidation) tới các core khác (giao thức MESI)
- Ngăn việc sắp xếp lại lệnh xuyên qua rào chắn

Giao thức MESI (Modified, Exclusive, Shared, Invalid) — một giao thức nhất quán cache (cache coherency) cho CPU nhiều core. Khi một core ghi dữ liệu (Modified), nó gửi tín hiệu tới các core khác — bản sao của chúng trở thành Invalid và phải được đọc lại từ RAM.

```assembly
# Ghi thông thường (không volatile):
mov [rax], 1

# Ghi volatile (có memory barrier):
lock or dword ptr [rax], 0  # Store barrier
mov [rax], 1
lock or dword ptr [rax], 0  # Load barrier
```

#### synchronized ở mức bytecode

```java
synchronized(obj) { /* code */ }
```

Bytecode:
```
aload_1         // Nạp obj
dup
astore_2
monitorenter    // Acquire monitor
/* code */
aload_2
monitorexit     // Release monitor
```

Quan trọng: trình biên dịch sinh ra **hai** lệnh `monitorexit` — một cho lối ra bình thường, một cho việc xử lý exception (`finally` ẩn).

### Sắp xếp lại và Memory Barrier

Bộ xử lý và trình biên dịch JIT sắp xếp lại các lệnh để tối ưu. `volatile` áp đặt các hạn chế:

| Loại Barrier | Ngăn chặn                                                        |
| ------------ | --------------------------------------------------------------- |
| LoadLoad     | Đọc sau đọc không thể bị dời lên trên                            |
| StoreStore   | Ghi sau ghi không thể bị dời lên trên                            |
| LoadStore    | Ghi sau đọc không thể bị dời lên trên                            |
| StoreLoad    | Đọc sau ghi không thể bị dời lên trên (đắt nhất)                 |

`volatile` write = rào chắn StoreStore + StoreLoad
`volatile` read = rào chắn LoadLoad + LoadStore

### Hiệu năng và tải cao (Highload)

#### Cache Invalidation và False Sharing

```java
public class Counters {
    public volatile int counter1; // Có thể nằm trong cùng một cache line
    public volatile int counter2; // Ghi vào counter1 làm vô hiệu hóa counter2!
}
```

Giải pháp — `@Contended` (Java 8+):

```java
public class ContendedCounters {
    @Contended
    public volatile int counter1;

    @Contended
    public volatile int counter2; // Bây giờ nằm ở các cache line khác nhau
}
```

#### Adaptive Spinning

Các JVM hiện đại không đưa thread vào trạng thái BLOCKED ngay lập tức. Đầu tiên, thread thực hiện **spin-wait** — một vòng lặp rỗng chờ monitor được giải phóng. Nếu spinning thành công — ta tiết kiệm được một lần context switch. Nếu không — ta park thread qua OS.

### Bảng so sánh (nâng cao)

| Đặc điểm          | volatile                          | synchronized                                   |
| ----------------- | --------------------------------- | --------------------------------------------- |
| Loại đảm bảo       | Visibility + ordering             | Visibility + atomicity + exclusion            |
| Mức áp dụng        | Biến (field)                      | Method hoặc block code                         |
| Locking           | Không (Lock-free)                 | Có (Blocking)                                  |
| CPU Cache         | Tắt việc cache biến đó            | Flush toàn bộ cache cục bộ khi vào/ra          |
| Deadlock          | Không thể                         | Có thể                                         |
| Overhead          | Thấp (memory barrier)             | Trung bình/cao (phụ thuộc mức tranh chấp)      |
| Reentrancy        | Không áp dụng                     | Có                                             |

```bash

jstack <pid> | grep "BLOCKED"

# Với các vấn đề volatile — chỉ có phân tích hành vi

```

### Best Practices

1. **volatile** — cho các cờ và việc publish các immutable object
2. **synchronized** — cho các thao tác gộp (read-modify-write)
3. **Atomic*** — cho các bộ đếm đơn giản (CAS nhanh hơn synchronized)
4. **Private lock** — dùng `private final Object lock` thay vì `synchronized(this)`
5. **Tránh** `volatile long/double` trừ khi bạn cần atomicity (trên JVM 32-bit)

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- `volatile` chỉ đảm bảo visibility, `synchronized` đảm bảo visibility + atomicity + mutual exclusion
- `volatile` chỉ áp dụng cho field, `synchronized` áp dụng cho method và block code
- `volatile` KHÔNG bảo vệ các thao tác gộp (count++ không atomic ngay cả với volatile)
- `volatile` dùng memory barrier (StoreStore, StoreLoad), `synchronized` dùng việc acquire monitor
- Deadlock không thể xảy ra với `volatile`, nhưng có thể với `synchronized`
- Trên x86, ghi `volatile` được dịch thành `lock` prefix và cache line invalidation (MESI)
- Double-Checked Locking cần `volatile` để publish Singleton đúng đắn
- `volatile` là lock-free, overhead thấp hơn `synchronized` khi mức tranh chấp thấp

**Các câu hỏi phụ thường gặp:**
- **Có thể dùng volatile cho một bộ đếm không?** — Không, count++ = read-modify-write (3 thao tác), hãy dùng AtomicInteger
- **Điều gì xảy ra nếu không có volatile trong Double-Checked Locking?** — JVM có thể sắp xếp lại: reference được gán trước khi constructor xong → object khởi tạo dở dang
- **volatile chèn các memory barrier nào?** — Write: StoreStore + StoreLoad; Read: LoadLoad + LoadStore
- **Khi nào volatile được ưu tiên hơn synchronized?** — Cho các cờ đơn giản (stop, ready), nơi một thread ghi, các thread khác đọc

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Volatile làm cho các thao tác trở nên atomic" — không, đó là AtomicInteger/CAS
- "Synchronized và volatile có thể thay thế cho nhau" — không, chúng giải quyết các vấn đề khác nhau
- "Volatile bảo vệ một nhóm biến" — không, chỉ một biến duy nhất
- "Synchronized dùng cho visibility, volatile dùng cho atomicity" — hoàn toàn ngược lại
