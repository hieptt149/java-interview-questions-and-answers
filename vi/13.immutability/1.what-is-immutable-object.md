# What is an immutable (unchangeable) object? (Immutable object là gì?)

---

## Basic Level

Một **immutable (bất biến) object** là một object mà trạng thái của nó không thay đổi sau khi tạo. Tất cả các trường được thiết lập một lần trong constructor, và sau đó object không cung cấp cách nào để sửa đổi dữ liệu của nó.

Điều này có nghĩa là object được tạo một lần và mãi mãi giữ nguyên cùng trạng thái — giống như một bức ảnh không thể chỉnh sửa.

### Ví Dụ Đơn Giản
```java
public final class Point {
    private final int x;
    private final int y;

    public Point(int x, int y) {
        this.x = x;
        this.y = y;
    }

    public int getX() { return x; }
    public int getY() { return y; }
    // Không có setter — trạng thái không thể thay đổi
}
```

### Các Đặc Điểm Chính
- Không có setter (setX, setY, v.v.)
- Tất cả các trường đều là `private final`
- Class là `final` (không thể tạo subclass)

### Khi Nào KHÔNG Nên Dùng Immutable Object

1. **Hot-path cấp phát cao** — hàng triệu lần sửa đổi/giây, áp lực GC
2. **Cấu trúc dữ liệu khổng lồ** — sao chép tốn kém hơn mutation
3. **Prototype và script** — tốc độ phát triển quan trọng hơn độ tin cậy

### Immutable vs Trường Final vs Không Có Setter

- **Không có setter** ≠ immutable: bạn vẫn có thể sửa đổi thông qua các tham chiếu được trả về đến các trường mutable
- **Trường final** ≠ immutable: nếu một trường tham chiếu đến một object mutable, nó có thể bị thay đổi
- **Immutable**: không có thay đổi trạng thái quan sát được sau khi construct

## Intermediate Level

### Năm Quy Tắc Để Tạo Một Immutable Class

1. **Class phải là `final`** — các subclass không thể thêm trạng thái mutable
2. **Tất cả các trường là `private final`** — chỉ truy cập qua getter
3. **Không có method mutator** — không có setX(), add(), remove()
4. **Bảo vệ các trường mutable** — nếu một trường tham chiếu đến một object có thể sửa đổi (ví dụ: `List` hoặc `Date`), bạn phải tạo defensive copy
5. **Publish an toàn** — không expose `this` trong quá trình construct

### Làm Việc Với Collection
```java
public final class UserProfile {
    private final String username;
    private final List<String> roles;

    public UserProfile(String username, List<String> roles) {
        this.username = username;
        this.roles = List.copyOf(roles); // defensive copy
        // List.copyOf trả về một list mới độc lập.
        // Nếu null được truyền vào — NPE sẽ được ném, vì vậy hãy thêm kiểm tra null.
    }

    public List<String> getRoles() {
        return roles; // List.copyOf đã trả về một list bất biến rồi
    }
}
```

### Cách Tiếp Cận Hiện Đại — Record (Java 14+)
```java
public record UserProfile(String username, List<String> roles) {
    public UserProfile {
        roles = List.copyOf(roles);
    }
}
```
Một `record` tự động làm cho class thành `final`, các trường thành `private final`, và sinh constructor, `equals()`, `hashCode()`, và `toString()`.

## Advanced Level

### Các Đảm Bảo Của Java Memory Model (JMM)

Việc dùng các trường `final` cung cấp **publish an toàn (safe publication)**. Theo đặc tả JMM, sau khi constructor của một immutable object hoàn thành, bất kỳ thread nào lấy được tham chiếu đến object này đều được đảm bảo thấy các giá trị đúng của các trường `final` của nó. Điều này loại bỏ nhu cầu dùng `volatile` hoặc synchronization.

Ở cuối constructor, một sự **"đóng băng" (freeze)** của tất cả các trường `final` xảy ra — một memory barrier được tạo ra ngăn việc sắp xếp lại lệnh (instruction reordering).

### Hiệu Năng Và Garbage Collection

Người ta thường tin rằng tính bất biến gây hại cho hiệu năng. Nhưng trong HotSpot JVM (hiện thực OpenJDK chính): việc cấp phát trong Young Generation cực kỳ nhanh (Bump-the-pointer — chỉ di chuyển một con trỏ). Các JVM khác (Zing, GraalVM) có thể khác:
- Các object tồn tại ngắn được dọn dẹp miễn phí trong lúc Minor GC
- Không có Write Barrier (không sửa đổi Old Generation)

### Nguy Hiểm Của Constructor Escape
```java
public ImmutableClass() {
    ExternalService.register(this); // LỖI! Object được publish trước khi khởi tạo hoàn thành
}
```
Một thread khác có thể thấy các trường `final` ở trạng thái mặc định của chúng (`null` hoặc `0`).

### Deep Copy Cho Các Object Mutable Lồng Nhau
Nếu list chứa không phải `String` mà là các object `User` mutable, `List.copyOf` là không đủ — mỗi phần tử phải được clone.

### Tóm Tắt Cho Advanced
- Tính bất biến là một "hợp đồng bảo mật"
- `final` ở cấp độ class và trường là một yêu cầu của JMM
- Luôn tạo bản sao của các thành phần mutable
- Dùng **Record** để giảm boilerplate

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Immutable object — trạng thái không thay đổi sau khi tạo
- Ba đặc điểm then chốt: class `final`, các trường `private final`, không có setter
- Năm quy tắc: class final, các trường private final, không có mutator, bảo vệ các trường mutable, publish an toàn
- `List.copyOf()` / `Collections.unmodifiableList()` để bảo vệ collection
- Record (Java 14+) tự động sinh một immutable class
- JMM đảm bảo publish an toàn cho các trường `final` sau khi construct
- Immutability ≠ thread-safe cho các tham chiếu đến object mutable
- Constructor Escape — lỗi nghiêm trọng khi publish `this` trước khi constructor hoàn thành

**Các câu hỏi phụ thường gặp:**
- *Các trường final có đủ không?* — Không, bạn cũng cần bảo vệ trường mutable và một class `final`
- *Deep copy là gì?* — Sao chép đệ quy tất cả các object mutable lồng nhau
- *Khi nào KHÔNG nên dùng tính bất biến?* — Hot-path cấp phát cao, cấu trúc khổng lồ, prototype
- *Record vs class thông thường?* — Record: boilerplate tối thiểu, nhưng không có kế thừa và không có trường thêm

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Immutable = chỉ đơn giản là không có setter" — các trường mutable vẫn có thể bị thay đổi qua getter
- "Các trường final là đủ" — không có defensive copy, các object mutable vẫn dễ bị tổn thương
- "Tính bất biến luôn chậm hơn" — trong môi trường đa luồng không có lock, nó nhanh hơn
- "Bạn có thể thay đổi một immutable object qua reflection" — điều này bị chặn trong Java 17+
