# Why String Is Often Used as a Key in HashMap? (Tại sao String thường được dùng làm key trong HashMap?)

## 🟢 Junior Level

`String` là kiểu key phổ biến nhất trong HashMap vì một số lý do:

1. **Immutable** — một khi đã tạo, một String không thể bị thay đổi
2. **Có ý nghĩa** — con người đọc được: "userId", "email", v.v.
3. **Cache hashCode** — được tính một lần và lưu lại

**Tại sao tính bất biến quan trọng:**
```java
String key = "user_42";
map.put(key, data);
// key KHÔNG THỂ bị sửa đổi — hash sẽ không thay đổi
// Phần tử sẽ luôn được tìm thấy
```

**Ví dụ:**
```java
Map<String, Integer> ages = new HashMap<>();
ages.put("Alice", 30);
ages.put("Bob", 25);
// "Alice" — luôn là cùng một object, cùng hashCode
System.out.println(ages.get("Alice")); // 30 — luôn hoạt động
```

## 🟡 Middle Level

### Tại sao String là key lý tưởng

| Tính chất             | Mô tả                                                |
| --------------------- | -------------------------------------------------- |
| Immutable             | Không thể bị sửa đổi — hash không thay đổi          |
| Cache hashCode        | Được tính ở lời gọi đầu tiên, lưu trong field `hash` private |
| Phân bố tốt           | Công thức hashCode dựa trên các ký tự: s[0]*31^(n-1) + ... |
| Implement Comparable  | Tăng tốc treeification (compareTo thay vì tieBreakOrder) |
| Được dùng rộng rãi    | Mọi developer đều mong đợi nó làm key               |

### Caching hashCode

```java
// Bên trong String:
private int hash; // Mặc định 0 — nghĩa là "chưa được tính"

public int hashCode() {
    int h = hash;
    if (h == 0 && value.length > 0) {
        hash = h = hashCode(value); // Tính một lần
    }
    return h;
}
```

Lời gọi đầu tiên tính hash, các lời gọi sau trả về giá trị đã cache trong O(1). Điều này then chốt cho hiệu năng HashMap — ở mọi get/put, hashCode được gọi nhiều lần.

### String Pool

Các String literal được lưu trong String Pool (interned):
```java
String s1 = "key";
String s2 = "key";
// s1 == s2 — cùng một object! So sánh tham chiếu hoạt động
```

Điều này tiết kiệm bộ nhớ: các literal giống hệt tham chiếu cùng một object.

### Tại sao 31 làm hệ số nhân?

```java
// Công thức String.hashCode():
hash = s[0]*31^(n-1) + s[1]*31^(n-2) + ... + s[n-1]
```

31 được chọn vì:
1. Số nguyên tố lẻ — giảm thiểu va chạm
2. 31 * i = (i << 5) - i — JVM tối ưu phép nhân thành một dịch và trừ
3. 31 cho phân bố tốt với dữ liệu string điển hình

### Các sai lầm thường gặp

1. **Dùng nối chuỗi String làm key trong một vòng lặp** — tạo nhiều object tạm
2. **`new String("key")`** — tạo một object mới, không dùng String Pool
3. **Các string rất dài làm key** — tính hashCode đắt (O(n))

## 🔴 Senior Level

### Hiện thực bên trong của String.hashCode()

```java
public int hashCode() {
    int h = hash;
    if (h == 0 && value.length > 0) {
        char val[] = value;
        for (int i = 0; i < value.length; i++) {
            h = 31 * h + val[i];
        }
        hash = h;
    }
    return h;
}
```

Hash được tính lười — ở lời gọi hashCode() đầu tiên. Điều này an toàn vì String là immutable: value không thể thay đổi giữa các lời gọi.

### Compact Strings (Java 9+)

Bắt đầu từ Java 9, String dùng `byte[]` thay vì `char[]` bên trong:
```java
private final byte[] value;
private final byte coder; // LATIN1 hoặc UTF16
```

Với các string ASCII, điều này giảm một nửa tiêu thụ bộ nhớ. Công thức hashCode giữ nguyên.

### Hiệu năng: Tính hashCode

| Độ dài String | Chi phí hashCode() |
| ------------- | ---------------- |
| 1-10 ký tự    | ~5-15 ns         |
| 100 ký tự     | ~50-100 ns       |
| 10000 ký tự   | ~5-10 µs         |

Với các string dài, caching hashCode là then chốt: không có nó, mọi thao tác HashMap sẽ phải trả toàn bộ chi phí.

### Các trường hợp biên (Edge Case)

1. **Empty String**: `"".hashCode() = 0` — rơi vào bucket 0, giống null key
2. **Các string rất dài**: hashCode = O(n), nhưng được cache — chỉ lời gọi đầu tiên đắt
3. **String.substring (trước Java 7u6)**: dùng chung char[] gốc — rò rỉ bộ nhớ tiềm tàng. Đã sửa trong Java 7u6 — sao chép mảng.

### String vs Enum làm Key

| Tiêu chí     | String        | Enum          |
| ------------ | ------------- | ------------- |
| Chi phí hashCode | O(n) lần đầu, rồi O(1) | O(1) (ordinal) |
| Bộ nhớ       | Object + char[]/byte[]     | Singleton       |
| Type safety  | Không         | Có            |
| Tính linh hoạt | Cao         | Tập cố định   |

Với một tập key cố định — Enum (hoặc EnumMap) tốt hơn. Với các key động — String là lựa chọn phổ quát.

### Bảo mật

- **Hash Flooding qua các va chạm String**: các va chạm đã biết tồn tại ("Aa" và "BB"). Trong Java 8+, treeification giảm nhẹ điều này
- **DoS qua các string dài**: tính hashCode trên các string 1MB có thể được dùng để làm cạn kiệt CPU
- **String deduplication (G1 GC)**: `-XX:+UseStringDeduplication` giảm overhead bộ nhớ cho các key lặp lại

### Best Practices

1. **Dùng các key String ngắn** — ID, tên, các định danh ngắn
2. **Tránh nối chuỗi trong các hot path** — dựng key trước
3. **Dùng `String.intern()` cẩn thận** — tiết kiệm bộ nhớ, nhưng làm ô nhiễm pool toàn cục
4. **Với các tập cố định — ưu tiên Enum hoặc EnumMap**

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- String là immutable — hash không thay đổi, không có rủi ro "key bị vỡ"
- String cache hashCode — được tính một lần, trả về trong O(1) ở các lời gọi sau
- String implement Comparable — tăng tốc treeification (compareTo thay vì tieBreakOrder)
- Phân bố hashCode tốt: công thức dùng hệ số nhân 31 (=(i<<5)-i)
- String Pool: các literal giống hệt tham chiếu cùng một object — tiết kiệm bộ nhớ
- Các string ngắn là tối ưu; các string dài có lần tính hashCode đầu tiên đắt

**Các câu hỏi phụ thường gặp:**
- **Tại sao 31 làm hệ số nhân?** — số nguyên tố lẻ, JVM tối ưu 31*i = (i<<5)-i, phân bố tốt
- **String.hashCode() có tính mỗi lần không?** — không, được cache trong một field private sau lời gọi đầu tiên
- **Tại sao không dùng các string rất dài làm key?** — tính hashCode là O(n), lời gọi đầu tiên đắt
- **String vs Enum làm key?** — Enum nhanh hơn (O(1) ordinal), nhưng String linh hoạt hơn

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "String là mutable" — không, nó immutable theo thiết kế
- "hashCode được tính mỗi lần" — không, được cache sau lời gọi đầu tiên
- "String là key tốt nhất luôn luôn" — với các tập cố định, Enum/EnumMap tốt hơn
