# What is String Deduplication in G1 GC? (String Deduplication trong G1 GC là gì?)

## 🟢 Junior Level

**String Deduplication** là một tính năng của garbage collector G1 tự động tìm các chuỗi giống hệt nhau trong bộ nhớ và gộp các mảng nội bộ của chúng để tiết kiệm bộ nhớ.

**Cách nó hoạt động:**
1. JVM nhận thấy hai object `String` khác nhau chứa cùng văn bản
2. Thay vì lưu trữ hai mảng byte giống hệt nhau, nó làm cả hai chuỗi tham chiếu đến **một** mảng
3. Điều này xảy ra **tự động** — bạn không cần thay đổi code

**Cách bật:**
```bash
java -XX:+UseG1GC -XX:+UseStringDeduplication -jar app.jar
```

**Ví dụ minh họa đơn giản:** Hãy tưởng tượng bạn có 100 bản sao của cùng một cuốn sách trong thư viện. Deduplication là khi thủ thư để lại một cuốn sách trên kệ và đưa cho tất cả độc giả khác một tham chiếu đến nó. Cùng văn bản, nhưng tiết kiệm không gian.

**Khác biệt so với String Pool:**
|                   | String Pool (`intern()`)  | String Deduplication       |
| ----------------- | ------------------------- | -------------------------- |
| Kết hợp cái gì     | Các object `String`          | Các mảng `byte[]` nội bộ   |
| Cần thay đổi code? | Có (`str.intern()`)      | Không (chỉ cần cờ JVM)         |
| Khi nào nó hoạt động     | Khi gọi `intern()`        | Trong lúc GC (chạy nền)  |

## 🟡 Middle Level

### Cách Nó Hoạt Động Nội Bộ

1. **Quét:** Trong lúc GC (giai đoạn evacuation) G1 đánh dấu các object `String` trong các region được thu gom
2. **Hàng đợi:** Các tham chiếu đến chuỗi ứng viên được đặt vào hàng đợi deduplication
3. **Thread nền:** Một thread riêng biệt tính hash của `byte[]` và tìm kiếm các khớp trong bảng deduplication
4. **Gộp:** Nếu tìm thấy mảng giống hệt, trường `value` được chuyển hướng đến mảng hiện có qua thao tác nguyên tử

### Khác Biệt So Với String Pool — So Sánh Chi Tiết

| Đặc điểm     | String Pool (`intern()`)           | String Deduplication                |
| ------------------ | ---------------------------------- | ----------------------------------- |
| Kết hợp cái gì      | Các object `String`                   | Các mảng `byte[]` nội bộ            |
| Khi nào               | Khi gọi `intern()` (đồng bộ)   | Trong lúc GC (bất đồng bộ)            |
| Quản lý         | Thủ công (cần gọi `intern()`)   | Tự động (cờ JVM)            |
| Hoạt động với mọi GC  | Có                                | Chỉ G1 GC và Shenandoah           |
| Ảnh hưởng đến `==`     | Làm `==` trở thành true                    | `==` vẫn **false** (các object khác nhau) |
| Overhead CPU       | Mỗi lần `intern()`                 | Thread nền, ~2–5% CPU        |
| Bộ nhớ bảng       | StringTable trong Heap (~32 byte/mục) | Native memory (~10–50MB)        |

### Khi Nào Nên Bật
- Profiler cho thấy nhiều chuỗi trùng lặp trong Heap
- Bạn không thể dùng `intern()` (code legacy, logic phức tạp, không có quyền truy cập code)
- Ứng dụng chạy trên G1 GC (mặc định trong Java 9+)
- Heap > 4GB và các chuỗi chiếm phần đáng kể

### Bảng Các Lỗi Điển Hình

| Lỗi                        | Hậu quả                        | Giải pháp                                                                     |
| ------------------------------ | ----------------------------------- | ---------------------------------------------------------------------------- |
| Kỳ vọng kết quả tức thì      | "Đã bật, nhưng bộ nhớ không được giải phóng"   | Deduplication xảy ra trong lúc GC, không tức thì; cần vài chu kỳ GC      |
| Bật mà không giám sát    | Không biết nó có hoạt động không       | Kiểm tra qua `-XX:+PrintStringDeduplicationStatistics`                          |
| Kỳ vọng `==` trở thành true  | Logic so sánh bị hỏng             | Deduplication không thay đổi tham chiếu object, chỉ các mảng nội bộ          |
| Bật trên ZGC               | Không hoạt động                        | ZGC không hỗ trợ String Deduplication                                     |

### Khi Nào KHÔNG Nên Dùng
- **Ít bản trùng lặp:** nếu các chuỗi hầu hết là độc nhất — overhead mà không có lợi ích
- **Các chuỗi tồn tại ngắn:** chết trước khi đến hàng đợi deduplication
- **ZGC:** không được hỗ trợ (dùng `-XX:+UseStringDeduplication` với Shenandoah)
- **Độ trễ cực thấp:** overhead CPU 2–5% có thể quan trọng

## 🔴 Senior Level

### Hiện Thực Nội Bộ — Pipeline Deduplication Của G1 GC

```
┌──────────────────────────────────────────────────────────────┐
│  GC (Giai đoạn Evacuation)                                        │
│  ├── Xác định các object String trong collection set                │
│  ├── Lọc: tuổi >= DeduplicationAgeThreshold (mặc định 3)     │
│  ├── Đưa các ứng viên vào hàng đợi dedup                        │
│  └── Tiếp tục evacuation                                      │
├──────────────────────────────────────────────────────────────┤
│  Thread Deduplication (concurrent, ưu tiên thấp)              │
│  ├── Lấy các tham chiếu String ra khỏi hàng đợi                                │
│  ├── Tính hash của giá trị byte[] (age hash, không phải String.hashCode) │
│  ├── Tra cứu trong bảng deduplication (hash table native memory)  │
│  ├── Nếu tìm thấy: so sánh từng byte để xác nhận             │
│  ├── Nếu khớp: CAS chuyển hướng tham chiếu value → mảng dùng chung             │
│  └── Nếu không tìm thấy: thêm vào bảng                               │
└──────────────────────────────────────────────────────────────┘
```

**Bảng Deduplication:**
- Hash table native (bên ngoài Java Heap, trong C-heap)
- Lưu trữ hash của các mảng `byte[]` + weak reference
- Khi khớp hash — **so sánh từng byte** để xác nhận (bảo vệ khỏi collision)
- Cập nhật tham chiếu qua **CAS** (Compare-And-Swap) — thread-safe không cần lock

**Thuật Toán Đánh Dấu:**
- G1 dùng concurrent marking
- Các chuỗi được đánh dấu trong giai đoạn marking
- Ngưỡng tuổi (mặc định 3 chu kỳ GC) — chỉ các chuỗi "sống sót" đủ lâu mới được dedup
- Điều này lọc ra các chuỗi tồn tại ngắn chết trước khi xử lý hàng đợi

### Đánh Đổi Về Kiến Trúc (Trade-off)

**Ưu điểm:**
- **Trong suốt:** không cần thay đổi code — chỉ cần cờ JVM
- **Tiết kiệm:** 10–20% Heap cho các ứng dụng nhiều văn bản
- **An toàn:** không có nguy cơ hỏng String Pool (dữ liệu không thay đổi)
- **Hoạt động với mọi chuỗi,** không chỉ các chuỗi đã intern

**Nhược điểm:**
- **Overhead CPU:** hashing + tra cứu + so sánh byte (~2–5% CPU)
- **Bộ nhớ:** bảng deduplication (~10–50MB native memory)
- **Chỉ G1 GC** (và Shenandoah trong OpenJDK)
- **Độ trễ:** deduplication xảy ra sau vài chu kỳ GC (ngưỡng tuổi)
- **Không dedup:** các chuỗi có `coder` khác nhau (Latin-1 vs UTF-16 — các mảng có độ dài khác nhau)

### Các Trường Hợp Biên (Tối Thiểu 3)

**1. Không dedup các chuỗi có coder khác nhau:**
```java
String s1 = "Hello"; // Latin-1, byte[5]
String s2 = new String("Hello".getBytes(StandardCharsets.UTF_16), StandardCharsets.UTF_16); // UTF-16, byte[12]
// coder khác nhau → các mảng byte[] khác nhau → deduplication sẽ không hoạt động
// Ngay cả khi nội dung giống nhau, các mảng có kích thước và byte khác nhau
```

**2. Các chuỗi tồn tại rất ngắn:**
```java
void process() {
    String temp = "duplicate"; // Eden
    String temp2 = "duplicate"; // Eden
    // Cả hai chuỗi chết trong Young GC — không đạt ngưỡng tuổi (3 GC)
    // Deduplication sẽ không kịp hoạt động
}
```

**3. Race condition khi chuyển hướng:**
```java
// Thread dedup thực hiện CAS:
// if (CAS(oldValue, sharedValue)) → thành công
// Nếu hai thread đồng thời cố chuyển hướng — chỉ một thành công
// Thread kia thấy value đã được chuyển hướng, và bỏ qua
// Thread đọc s.value luôn thấy giá trị nhất quán (@Stable + CAS)
// @Stable — annotation JVM báo cho JIT biết trường được ghi một lần trong lúc construct.
```

**4. String Pool vs Deduplication — tương tác:**
```java
String s1 = new String("Hello");
String s2 = new String("Hello");
// s1.value và s2.value — các mảng byte[] khác nhau (cả hai đều Latin-1, byte[5])
// Sau deduplication: s1.value và s2.value → CÙNG byte[]
// Nhưng s1 != s2 (các object String vẫn khác nhau!)
// Tiết kiệm: một byte[5] thay vì hai → 5 byte
```

**5. Các chuỗi bất thường (rất dài):**
```java
String huge = "A".repeat(10_000_000); // 10MB
String huge2 = "A".repeat(10_000_000); // 10MB
// So sánh từng byte của 10MB — tốn kém (~10ms)
// Thread deduplication có thể làm chậm GC
// Trong thực tế: các chuỗi dài có thể giống hệt nhau trong bộ tổng hợp log hoặc data pipeline
// (cùng payload JSON), nhưng điều này hiếm gặp với các ứng dụng web điển hình.
```

### Hiệu Năng

| Metric              | Không dedup  | Có dedup       | Chênh lệch    |
| ------------------- | -------------- | ---------------- | -------- |
| Sử dụng Heap          | 4.0 GB         | 3.2 GB           | **-20%** |
| GC pause (trung bình)      | 50ms           | 55ms             | +10%     |
| Overhead CPU        | Cơ sở       | +2–5%            | Nhỏ     |
| Young GC            | 10ms           | 10ms             | Không đổi|
| Mixed GC            | 50ms           | 55ms             | +5ms     |
| Native memory (bảng)| 0MB           | 10–50MB          | Thêm    |

**Tiết kiệm bộ nhớ (các kịch bản thực tế):**
- Service JSON API: 15–25% chuỗi là bản trùng lặp (key, giá trị status)
- Bộ tổng hợp log: 30–40% bản trùng lặp (level, tên service, tên host)
- ETL pipeline: 5–10% bản trùng lặp (tên danh mục, mã quốc gia)

### Thread Safety

Deduplication **thread-safe**:
- Cập nhật tham chiếu `value` qua **CAS** (thao tác nguyên tử)
- Trường `value` là `@Stable`, nhưng JVM cho phép chuyển hướng trong lúc GC
- Các thread đọc luôn thấy giá trị nhất quán (memory barrier trong lúc GC)
- Thread deduplication — đơn (single-threaded), không có contention giữa các thread dedup

### Câu Chuyện Thực Tế Trong Production

**Kịch bản 1:** Service JSON API (G1 GC, 8GB Heap, Spring Boot, 50K RPS):
- **Không dedup:** Mức sử dụng Heap 6.5GB, Full GC mỗi 30 phút, latency p99 = 25ms
- **Có dedup:** Mức sử dụng Heap 5.2GB, Full GC mỗi 50 phút, latency p99 = 20ms
- Overhead CPU: +3% (chấp nhận được)
- Thống kê: dedup 2.3GB chuỗi, 850K mảng byte[] độc nhất được gộp
- **Kết quả:** giảm số instance từ 10 xuống 8 (tiết kiệm $15K/tháng)

**Kịch bản 2:** Bộ tổng hợp log (1M dòng log/phút, G1 GC, 12GB Heap):
- Các trường `level`, `service`, `host` — nhiều bản trùng lặp (`"INFO"`, `"UserService"`, `"host-1"`)
- **Không dedup:** 12GB Heap
- **Có dedup:** 9GB Heap
- Tiết kiệm: 3GB → ít instance hơn trong cluster
- **Vấn đề:** Overhead CPU tăng lên 7% do số lượng chuỗi khổng lồ. Sửa lỗi: `-XX:StringDeduplicationAgeThreshold=5` (tăng ngưỡng tuổi, ít ứng viên hơn → ít CPU hơn).

**Kịch bản 3 (anti-pattern):** Team bật deduplication "để phòng khi cần" cho một ứng dụng với các chuỗi độc nhất (UUID, hash, timestamp). Overhead CPU +4%, tiết kiệm bộ nhớ 0.5%. Họ đã vô hiệu hóa nó.

### Giám Sát

```bash
# Bật thống kê deduplication
-XX:+PrintStringDeduplicationStatistics
-XX:+PrintGC

# Kết quả trong log GC:
# [GC concurrent string deduplication]
# String Deduplication: 1.2GB deduplicated (500K strings)
# [DEDUP: 500K strings, 1.2GB, 2.3ms]

# JCmd — thống kê tại thời điểm chạy
jcmd <pid> GC.string_deduplication_statistics

# Kết quả:
# String Deduplication Statistics:
#   Executed: 1234 times
#   Deduplicated: 567890 strings (1.2GB)
#   Skipped: 123456 strings (already deduplicated)

# JFR (Java Flight Recorder)
java -XX:StartFlightRecording=filename=recording.jfr ...
# Các event: StringDeduplicationStatistics
# Trong JDK Mission Controller: Memory → String Deduplication

# Cấu hình ngưỡng tuổi
-XX:StringDeduplicationAgeThreshold=3  # Mặc định 3 chu kỳ GC
# Tăng lên 5–10 nếu overhead CPU quá cao
```

### Best Practices Cho Highload

- Bật khi profiler cho thấy **> 10% chuỗi trùng lặp** trong Heap
- **Đừng dùng thay thế cho `intern()`** với các chuỗi tồn tại lâu có tỷ lệ trùng lặp cao (từ điển, config) — `intern()` hiệu quả hơn
- **Giám sát overhead CPU** — nếu > 5%, tăng `-XX:StringDeduplicationAgeThreshold=5`
- **Kết hợp:** `intern()` cho dữ liệu từ điển (giá trị enum, mã status) + deduplication cho phần còn lại
- Cho **ZGC**: không được hỗ trợ (ZGC tính đến JDK 21: không hỗ trợ String Deduplication) — cân nhắc Shenandoah (`-XX:+UseShenandoahGC -XX:+UseStringDeduplication`)
- Cho **tiết kiệm tối đa:** tinh chỉnh `-XX:G1HeapRegionSize` — region nhỏ hơn → evacuation thường xuyên hơn → nhiều ứng viên dedup hơn
- **Đừng bật** cho các ứng dụng tồn tại ngắn (CLI, batch job < 1 phút) — sẽ không kịp hoạt động
- Cho **độ trễ cực thấp:** benchmark có và không có deduplication; đôi khi việc tăng GC pause 5ms là quan trọng

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- String Deduplication — tính năng của G1 GC, tự động gộp các mảng `byte[]` của các chuỗi giống hệt nhau
- Được bật với cờ: `-XX:+UseG1GC -XX:+UseStringDeduplication` (không cần thay đổi code)
- Khác biệt so với String Pool: deduplication gộp `byte[]`, không phải object String; `==` vẫn false
- Hoạt động bất đồng bộ trong lúc GC, ngưỡng tuổi (mặc định 3 chu kỳ GC) — lọc ra các chuỗi tồn tại ngắn
- Overhead CPU: ~2-5%, native memory cho bảng dedup: ~10-50MB
- Không dedup các chuỗi có coder khác nhau (Latin-1 vs UTF-16)

**Các câu hỏi phụ thường gặp:**
- **Deduplication khác gì với `intern()`?** — `intern()` gộp các object String (== trở thành true), cần thay đổi code. Deduplication — chỉ các mảng `byte[]`, `==` vẫn false, không cần thay đổi code.
- **Tiết kiệm bộ nhớ nào?** — 10-20% Heap cho các ứng dụng có chuỗi trùng lặp. JSON API: 15-25%, bộ tổng hợp log: 30-40%.
- **Tại sao nó không hoạt động với ZGC?** — ZGC (tính đến JDK 21) không hỗ trợ String Deduplication. Thay thế: Shenandoah GC.
- **Cách giảm overhead CPU?** — Tăng `-XX:StringDeduplicationAgeThreshold=5` — ít ứng viên hơn, ít CPU hơn.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "Deduplication làm `==` trở thành true" — các object String vẫn khác nhau, chỉ `byte[]` được gộp
- ❌ "Điều này thay thế `intern()`" — không, `intern()` hiệu quả hơn cho dữ liệu từ điển
- ❌ "Hoạt động tức thì" — xảy ra trong lúc GC, cần vài chu kỳ
- ❌ "Hoạt động với mọi GC" — chỉ G1 GC và Shenandoah
