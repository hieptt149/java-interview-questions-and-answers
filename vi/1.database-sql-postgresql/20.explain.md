# What is Explain plan? (Explain plan là gì?)

## 🟢 Junior Level

**EXPLAIN** — một lệnh của PostgreSQL cho thấy **cách cơ sở dữ liệu dự định thực thi một truy vấn**, mà không thực sự chạy nó.

**Ví dụ minh họa đơn giản:** Trước khi đi du lịch, GPS sẽ hiển thị lộ trình: những con đường nào, bao nhiêu lượt rẽ, thời gian ước tính. EXPLAIN giống như một GPS cho truy vấn: cho thấy index nào, bảng nào, sẽ mất bao lâu.

**Ví dụ:**
```sql
-- Hiển thị plan của truy vấn
EXPLAIN SELECT * FROM users WHERE email = 'test@example.com';

-- Kết quả:
-- Index Scan using idx_users_email on users  (cost=0.42..8.44 rows=1 width=100)
--   Index Cond: (email = 'test@example.com'::text)
```

**Các con số có ý nghĩa gì:**
- `cost=0.42..8.44` — chi phí: khởi động (startup)..tổng cộng (để lấy tất cả các dòng)
- `rows=1` — cơ sở dữ liệu dự đoán bao nhiêu dòng
- `width=100` — kích thước trung bình của mỗi dòng, tính bằng byte

**Khi nào nên sử dụng:**
- Truy vấn chạy chậm
- Bạn muốn kiểm tra xem một index có đang được sử dụng hay không
- Trước khi tạo một index — liệu nó có giúp ích không?

## 🟡 Middle Level

### EXPLAIN vs EXPLAIN ANALYZE

```sql
-- EXPLAIN: chỉ hiển thị plan, KHÔNG thực thi truy vấn
EXPLAIN SELECT * FROM users WHERE email = 'test@example.com';

-- EXPLAIN ANALYZE: thực thi truy vấn + hiển thị thời gian thực tế
EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'test@example.com';

-- Kết quả:
-- Index Scan using idx_users_email on users  (cost=0.42..8.44 rows=1 width=100)
--   (actual time=0.035..0.037 rows=1 loops=1)
--                     ↑ thời gian thực tế tính bằng ms
-- Planning Time: 0.123 ms
-- Execution Time: 0.058 ms
```

### Các cờ (flags) quan trọng

```sql
-- Bộ đầy đủ để phân tích
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT) SELECT ...;

-- Các cờ:
-- ANALYZE  → thực thi truy vấn + thời gian thực tế
-- BUFFERS  → hiển thị số lần đọc từ cache/đĩa
-- COSTS    → hiển thị chi phí (mặc định bật)
-- ROWS     → hiển thị số dòng ước tính
-- WIDTH    → hiển thị kích thước dòng
-- FORMAT   → TEXT (mặc định), JSON, YAML, XML
```

### Đọc một plan

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT u.name, COUNT(o.id) as orders
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
WHERE u.city = 'Moscow'
GROUP BY u.name;

-- Plan:
-- HashAggregate  (cost=... rows=... actual time=15.2..15.3 rows=500 loops=1)
--   Buffers: shared hit=250 read=50
--   → Hash Left Join  (cost=... actual time=10.1..12.5 rows=2000 loops=1)
--        Buffers: shared hit=200 read=40
--        Hash Cond: (o.user_id = u.id)
--        → Seq Scan on orders o  (actual time=0.01..5.2 rows=10000 loops=1)
--             Buffers: shared hit=150
--        → Hash  (cost=... actual time=3.1..3.1 rows=500 loops=1)
--             Buffers: shared hit=50 read=40
--             → Seq Scan on users u  (actual time=0.02..2.8 rows=500 loops=1)
--                  Filter: (city = 'Moscow')
--                  Rows Removed by Filter: 999500
-- Planning Time: 0.5 ms
-- Execution Time: 16.0 ms
```

**Đọc từ dưới lên trên:**
1. Seq Scan on users → lọc còn 500 trong tổng số 1 triệu
2. Hash → xây dựng bảng hash cho JOIN
3. Seq Scan on orders → đọc 10,000 đơn hàng
4. Hash Left Join → kết hợp lại
5. HashAggregate → gộp nhóm

### Các loại Scan

| Loại                  | Khi nào                              | Tốc độ                                     |
| --------------------- | --------------------------------- | ------------------------------------------ |
| **Seq Scan**          | Đọc toàn bộ bảng              | Chậm với bảng lớn, nhanh với bảng nhỏ            |
| **Index Scan**        | Tìm kiếm bằng index → đọc dòng        | Nhanh với các tập kết quả nhỏ                 |
| **Index Only Scan**   | Toàn bộ dữ liệu đã có trong index             | Rất nhanh                                 |
| **Bitmap Index Scan** | Index → bitmap → các dòng             | Các tập kết quả vừa phải (100-10,000 dòng)       |

> Bitmap Index Scan: thu thập TẤT CẢ các TID khớp điều kiện từ index vào một bitmap, sau đó đọc các dòng. Hiệu quả hơn Index Scan đối với 100-10,000 dòng nằm ở các vị trí khác nhau — ít thao tác I/O ngẫu nhiên hơn.

### Các vấn đề thường gặp

1. **Seq Scan trên một bảng lớn**
   ```sql
   EXPLAIN SELECT * FROM users WHERE email = 'test@example.com';
   -- Seq Scan on users  ← không tốt!
   --   Filter: (email = ...)
   --   Rows Removed by Filter: 999999

   -- Giải pháp: tạo một index
   CREATE INDEX idx_users_email ON users(email);
   ```

2. **Ước tính không khớp với thực tế**
   ```sql
   -- rows=1000 actual rows=1
   -- Planner đã sai lệch tới 1000 lần!

   -- Nguyên nhân: thống kê lỗi thời
   -- Giải pháp: ANALYZE users;
   ```

3. **Tràn ra đĩa (Spill to disk)**
   ```sql
   EXPLAIN (ANALYZE) SELECT ... GROUP BY ...;
   -- HashAggregate (actual time=... rows=...)
   --   Disk: 5GB  ← không tốt! work_mem không đủ

   -- Giải pháp: SET work_mem = '256MB';
   ```

### Ví dụ thực tiễn

```sql
-- Kiểm tra việc sử dụng index
EXPLAIN SELECT * FROM orders WHERE user_id = 123;
-- Index Scan using idx_orders_user_id → tuyệt vời!

-- Kiểm tra JOIN
EXPLAIN SELECT * FROM users u JOIN orders o ON u.id = o.user_id;
-- Hash Join → bình thường đối với các bảng lớn
-- Nested Loop → tuyệt vời nếu có index

-- Kiểm tra việc sắp xếp
EXPLAIN SELECT * FROM orders ORDER BY created_at DESC LIMIT 10;
-- Limit → Index Scan Backward → tuyệt vời!
-- Limit → Sort → có thể được tối ưu bằng index
```

## 🔴 Senior Level

### Cấu trúc giải phẫu của Costs (chi phí) trong node

```sql
Sort (cost=150.10..155.10 rows=2000 width=40)
         ↑         ↑
    Startup    Total
    Cost       Cost
```

**Startup Cost:** Chi phí để lấy dòng **đầu tiên**
- Rất quan trọng đối với `LIMIT 1`, `WHERE EXISTS`
- Planner có thể chọn một plan có Total Cost khổng lồ nhưng Startup Cost thấp

**Total Cost:** Chi phí để lấy **tất cả** các dòng
- Rất quan trọng đối với việc lấy toàn bộ dữ liệu

**Đơn vị tùy ý (Arbitrary units):**
- 1 đơn vị ≈ đọc một page 8KB từ đĩa
- cost=100 ≈ đọc 100 page

### BUFFERS: phân tích I/O

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;

-- Buffers: shared hit=250 read=50 written=10
--               ↑       ↑         ↑
--            từ cache  từ đĩa  đã ghi

-- shared hit: 250 / (250+50) = 83% Cache Hit Rate
-- read=50: 50 × 8KB = 400KB đọc từ đĩa
-- written=10: 10 × 8KB = 80KB đã ghi (file tạm?)
```

**Diễn giải:**
- `shared hit` >> `shared read` → tuyệt vời (mọi thứ đều nằm trong cache)
- `shared read` >> `shared hit` → có vấn đề (nhiều Disk I/O)
- `written` > 0 → tràn ra đĩa hoặc ghi vào file tạm

### Generic vs Custom Plans

**Vấn đề với Prepared Statements:**

```sql
-- Custom Plan (biết giá trị cụ thể)
EXPLAIN SELECT * FROM users WHERE id = 5;
-- Plan: Index Scan (hoàn hảo cho id=5)

-- Generic Plan (dùng chung cho mọi $1)
PREPARE stmt(int) AS SELECT * FROM users WHERE id = $1;
EXPLAIN EXECUTE stmt(5);
-- Plan: Seq Scan (dùng chung, "trung bình" cho tất cả các id)
```

**Tại sao Generic Plan có thể tệ hơn:**
```
Dữ liệu bị lệch (skewed):
  id=5 → 1 dòng (Index Scan là lý tưởng)
  id=100 → 500,000 dòng (Seq Scan là lý tưởng)

Generic Plan: "trung bình hóa" → Seq Scan
→ Đối với id=5, chậm một cách thảm khốc!

Planner "lấy trung bình" chi phí: đối với id=5, cần Index Scan (1 dòng),
đối với id=100 — cần Seq Scan (500,000 dòng). Seq Scan "an toàn hơn" trung bình,
nhưng đối với các giá trị cụ thể có tập kết quả nhỏ — đây là thảm họa.
```

**Giải pháp:**
```sql
-- 1. plan_cache_mode
SET plan_cache_mode = 'force_custom_plan';  -- Luôn dùng Custom
SET plan_cache_mode = 'force_generic_plan'; -- Luôn dùng Generic
SET plan_cache_mode = 'auto';               -- Mặc định (5 lần Custom, sau đó Generic)

-- 2. Trong JDBC/Hibernate:
-- Kiểm tra: prepareThreshold=0 (tắt Prepared Statements)
```

### JIT Compilation (Biên dịch JIT)

**JIT (Just-In-Time)** — PostgreSQL biên dịch một phần của truy vấn thành mã máy thông qua LLVM. Giống như cơ sở dữ liệu "viết lại" một phần của truy vấn bằng ngôn ngữ C.

**Tăng tốc:**
1. Các biểu thức nặng `(a * b + c / d)` trên hàng triệu dòng
2. Các hàm tổng hợp (SUM, AVG) với nhiều nhóm gộp
3. Đánh giá tuple trong lúc Hash Join

**Làm chậm:** các truy vấn đơn giản (`SELECT * FROM t WHERE id = 1`) — việc biên dịch mất nhiều thời gian hơn cả việc thực thi!

```sql
-- Trong EXPLAIN ANALYZE, có thể xuất hiện một khối JIT
-- JIT:
--   Functions: 5
--   Options: Inlining, Optimization
--   Timing: Min 2.1 ms, Max 2.5 ms

-- Ưu điểm: tăng tốc các biểu thức phức tạp và hàm tổng hợp
-- Nhược điểm: đối với các truy vấn ngắn, biên dịch > thực thi!

-- Tắt cho OLTP
SET jit = off;

-- Kiểm tra
SHOW jit;
```

### Parallel Query trong plan

```sql
EXPLAIN SELECT COUNT(*) FROM large_table;

-- Gather
--   Workers Planned: 4
--   → Parallel Seq Scan on large_table
--        Workers Launched: 4

-- Các chỉ số quan trọng:
-- Workers Planned: có bao nhiêu worker mà optimizer đã lên kế hoạch
-- Workers Launched: có bao nhiêu worker thực sự đã khởi động
-- Nếu Launched < Planned → hãy kiểm tra:
--   max_parallel_workers_per_gather
--   max_parallel_workers
--   Tải của server
```

### Incremental Sort (Sắp xếp tăng dần) (PG 13+)

```sql
EXPLAIN SELECT * FROM orders ORDER BY user_id, created_at;

-- Incremental Sort  ← PG 13+!
--   Sort Key: user_id, created_at
--   Presorted Key: user_id  ← dữ liệu đã được sắp xếp sẵn theo user_id
--   → Chỉ sắp xếp theo created_at trong phạm vi từng user_id
--   → Nhanh hơn 5-10 lần so với sắp xếp toàn bộ!
```

> Ở PG 12 trở xuống — sắp xếp toàn bộ tất cả các cột, ngay cả khi một phần đã được sắp xếp sẵn.

### Các trường hợp đặc biệt (Edge Cases)

1. **EXPLAIN ANALYZE sẽ thực thi truy vấn!**
   ```sql
   -- ⚠️ Truy vấn DML sẽ được thực thi!
   EXPLAIN ANALYZE DELETE FROM users WHERE status = 'INACTIVE';
   -- → Tất cả người dùng không hoạt động sẽ bị XÓA!

   -- ✅ Cách an toàn:
   BEGIN;
   EXPLAIN ANALYZE DELETE FROM users WHERE status = 'INACTIVE';
   ROLLBACK;  -- Hoàn tác các thay đổi
   ```

2. **Lần chạy EXPLAIN ANALYZE đầu tiên có thể gây hiểu nhầm**
   ```
   Dữ liệu có thể chưa nằm trong cache → lần chạy đầu tiên sẽ chậm hơn.
   Hãy chạy 2-3 lần và xem kết quả của lần thứ hai/ba.
   Hoặc: DISCARD ALL; — xóa cache.
   ```

3. **Tạo WAL (PG 13+)**
   ```sql
   EXPLAIN (ANALYZE, WAL) INSERT INTO orders SELECT ...;

   -- WAL:
   --   Records: 50000
   --   Bytes: 10MB
   --   FPI: 100 (Full Page Images — bản sao toàn bộ các page 8KB trong WAL khi
   --   trang đó bị sửa đổi lần đầu tiên sau một checkpoint. Số lượng FPI lớn =
   --   tải cao đối với WAL và replication)

   -- Rất quan trọng để ước tính tải replication
   ```

> Ở PG 12 trở xuống, cờ WAL trong EXPLAIN không khả dụng. Hãy ước tính tải replication thông qua `pg_stat_wal` hoặc log.

4. **Chi phí phát sinh cho Timing**
   ```sql
   -- EXPLAIN ANALYZE thêm chi phí phát sinh cho việc đo thời gian
   -- Đối với các tối ưu hóa nhỏ (micro-optimization), hãy tắt TIMING

   EXPLAIN (ANALYZE, TIMING off) SELECT ...;
   -- Nhanh hơn, nhưng không có phép đo chi tiết theo từng node
   ```

### Kinh nghiệm Production

**Tình huống thực tế #1: Generic Plan giết chết API**
- Ứng dụng: JDBC Prepared Statement để tìm kiếm email
- Trong console: 5ms (Custom Plan, Index Scan)
- Trong ứng dụng: 500ms (Generic Plan, Seq Scan)
- Nguyên nhân: email bị lệch (skewed) (một số người dùng có tới 1000 bản ghi)
- Giải pháp: `plan_cache_mode = 'force_custom_plan'`
- Kết quả: ổn định ở mức 5ms

**Tình huống thực tế #2: JIT làm chậm OLTP**
- REST API: các truy vấn đơn giản < 1ms
- EXPLAIN ANALYZE: JIT Timing: 8ms
- Nguyên nhân: JIT được bật theo mặc định, thời gian biên dịch > thực thi
- Giải pháp: `SET jit = off` cho session
- Kết quả: 0.5ms thay vì 8.5ms (nhanh hơn 17 lần)

### Giám sát (Monitoring)

```sql
-- 1. Tìm các truy vấn chậm
SELECT query, mean_exec_time, calls, shared_blks_read
FROM pg_stat_statements
ORDER BY mean_exec_time DESC
LIMIT 10;

-- 2. Kiểm tra một truy vấn cụ thể
EXPLAIN (ANALYZE, BUFFERS, WAL)
SELECT ...;

-- 3. Tìm các truy vấn gặp vấn đề Generic Plan
-- (chậm trong log ứng dụng, nhưng nhanh trong console)

-- 4. Kiểm tra JIT
EXPLAIN (ANALYZE) SELECT ...;
-- Tìm khối "JIT" và phần Timing

-- 5. Hiệu quả của Parallel Query
EXPLAIN (ANALYZE) SELECT ...;
-- Workers Launched vs Planned
```

### Best Practices (Thực hành tốt nhất)

1. **Luôn sử dụng** `EXPLAIN (ANALYZE, BUFFERS)`
2. **So sánh Estimated vs Actual rows** → sự chênh lệch = có vấn đề về thống kê
3. **Kiểm tra Cache Hit Rate** thông qua Buffers
4. **Generic vs Custom** — hãy kiểm thử Prepared Statements
5. **JIT** — tắt cho OLTP, bật cho OLAP
6. **DML + EXPLAIN ANALYZE** → chỉ trong một transaction với ROLLBACK
7. **WAL (PG 13+)** để ước tính tải replication
8. **SETTINGS (PG 12+)** — `EXPLAIN (ANALYZE, SETTINGS)` hiển thị các tham số session đã bị thay đổi. Ở PG 11 trở xuống — hãy kiểm tra các tham số thủ công thông qua `SHOW`.

### Tóm tắt cho Senior

- **Startup Cost** rất quan trọng đối với `LIMIT`, **Total Cost** đối với việc lấy toàn bộ dữ liệu
- **BUFFERS** = chỉ số I/O chính (hit vs read)
- **Generic vs Custom Plans** — nguyên nhân phổ biến gây ra sự chênh lệch giữa prod/dev
- **plan_cache_mode** kiểm soát hành vi của Prepared Statements
- **JIT** tăng tốc OLAP, làm chậm OLTP → hãy tắt nơi không cần thiết
- **WAL (PG 13+)** cho thấy tải replication
- **Estimated ≠ Actual rows** → cần `ANALYZE` hoặc `SET STATISTICS`
- **DML + EXPLAIN ANALYZE** → luôn luôn trong `BEGIN...ROLLBACK`

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- EXPLAIN: hiển thị plan MÀ KHÔNG thực thi; EXPLAIN ANALYZE: thực thi + thời gian thực tế
- Cost: `startup..total` tính theo đơn vị tùy ý (1 đơn vị ≈ đọc một page 8KB)
- BUFFERS: `shared hit` (từ cache), `shared read` (từ đĩa), `written` (ghi)
- Generic Plan (Prepared Statements): dùng chung, có thể tệ hơn với dữ liệu bị lệch
- Custom Plan: biết giá trị cụ thể, tốt hơn cho dữ liệu bị lệch
- plan_cache_mode: `auto` (5 lần Custom → Generic), `force_custom_plan`, `force_generic_plan`
- JIT: tăng tốc các biểu thức/hàm tổng hợp phức tạp, làm chậm OLTP (các truy vấn < 1ms)
- Parallel Query: Workers Planned vs Launched → nếu Launched < Planned, hãy kiểm tra cài đặt
- Incremental Sort (PG 13+): dữ liệu đã sắp xếp một phần → chỉ sắp xếp phần còn lại
- WAL (PG 13+): Records, Bytes, FPI → ước tính tải replication
- DML + EXPLAIN ANALYZE → THỰC THI truy vấn thật! Chỉ nên dùng trong BEGIN...ROLLBACK

**Các câu hỏi phụ thường gặp:**
- "Tại sao trong ứng dụng lại chậm hơn trong console?" → Generic Plan trong Prepared Statements
- "Làm sao để kiểm tra Cache Hit Rate?" → BUFFERS: hit / (hit + read)
- "Tại sao JIT lại làm chậm mọi thứ?" → Biên dịch mất 8ms > thực thi 1ms → hãy tắt cho OLTP
- "Estimated rows ≠ Actual có nghĩa là gì?" → Thống kê lỗi thời → cần ANALYZE

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "EXPLAIN ANALYZE an toàn đối với DML" (nó THỰC THI truy vấn thật!)
- ❌ "Generic Plan luôn luôn tốt" (đối với dữ liệu bị lệch — thảm họa)
- ❌ "JIT luôn luôn giúp tăng tốc" (nó làm chậm OLTP!)
- ❌ "Cost là mili giây" (sai, đó là đơn vị tùy ý!)
