# How to Monitor Applications in Kubernetes? (Cách giám sát ứng dụng trong Kubernetes?)

---

## Junior Level

### Định Nghĩa Đơn Giản

**Monitoring trong Kubernetes** là thực hành thu thập, lưu trữ, và phân tích dữ liệu về trạng thái của cluster, container, và ứng dụng. Monitoring trả lời ba câu hỏi: "Điều gì đang xảy ra?", "Tại sao nó xảy ra?" và "Làm sao ngăn chặn nó?"

### Phép So Sánh

Monitoring giống như bảng đồng hồ của ô tô. Đồng hồ tốc độ cho biết tốc độ (mức sử dụng CPU), đồng hồ nhiệt độ — quá nhiệt (mức sử dụng memory), đèn CHECK ENGINE — có gì đó bị hỏng (tỷ lệ lỗi). Không có bảng đồng hồ, bạn đang lái xe trong mù mịt.

### Ví Dụ: Cài Đặt Prometheus Stack (Helm)

```bash
# Thêm repository
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update

# Cài đặt kube-prometheus-stack
helm install monitoring prometheus-community/kube-prometheus-stack \
  --namespace monitoring --create-namespace
```

### Ví Dụ: Spring Boot Actuator + Micrometer

```xml
<!-- pom.xml -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-actuator</artifactId>
</dependency>
<dependency>
    <groupId>io.micrometer</groupId>
    <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
```

```yaml
# application.yml
management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus
  metrics:
    export:
      prometheus:
        enabled: true
```

### Ví Dụ kubectl

```bash
# Mở dashboard Grafana
kubectl port-forward svc/monitoring-grafana 3000:80 -n monitoring
# http://localhost:3000 (admin/prom-operator)

# Mở UI Prometheus
kubectl port-forward svc/monitoring-prometheus 9090:9090 -n monitoring

# Liệt kê các Pod monitoring

```

### Khi Nào Dùng

- Luôn luôn trong production — không có monitoring bạn đang mù
- Để theo dõi mức sử dụng CPU, memory, disk, network
- Để phát hiện lỗi và suy giảm hiệu năng
- Để alerting: SMS/email/Slack khi có vấn đề xảy ra

## Middle Level

### Cách Nó Hoạt Động

Monitoring trong Kubernetes được xây dựng trên bốn thành phần:

1. **Prometheus** — cơ sở dữ liệu chuỗi thời gian (time-series database), thu thập metrics qua phương thức **pull** (poll các endpoint mỗi 15-30 giây)

> Prometheus -- tiêu chuẩn thực tế cho monitoring trong K8s. Mô hình pull: Prometheus scrape metrics từ các Pod qua endpoint HTTP (/metrics).
2. **Node Exporter** — DaemonSet trên mỗi node, thu thập metrics OS (CPU, RAM, disk, network)
3. **cAdvisor** — được tích hợp sẵn trong kubelet, thu thập metrics container (CPU, memory, network mỗi container)
4. **kube-state-metrics** — Deployment, sinh ra các metrics về trạng thái các object K8s (trạng thái Pod, replica Deployment, mức sử dụng PVC)
5. **Grafana** — trực quan hóa, dashboard, alerting

**Chuỗi thu thập metrics:**
```
App (/actuator/prometheus) ← Prometheus scrape mỗi 15s
Node Exporter (DaemonSet)  ← Prometheus scrape mỗi 15s
cAdvisor (kubelet)         ← Prometheus scrape mỗi 15s
kube-state-metrics         ← Prometheus scrape mỗi 15s
                              ↓
                          Prometheus TSDB (lưu trữ 15 ngày)
                              ↓
                          Grafana (dashboard)
                              ↓
                          Alertmanager (thông báo)
```

### Các Kịch Bản Thực Tế

**Kịch bản 1: Monitoring ứng dụng Java**
```promql
# Mức sử dụng memory JVM
jvm_memory_used_bytes{area="heap"}

# Thời gian khoảng dừng GC
rate(jvm_gc_pause_seconds_sum[5m])

# Tỷ lệ request HTTP
rate(http_server_requests_seconds_count[5m])

# Tỷ lệ lỗi HTTP (5xx)
rate(http_server_requests_seconds_count{status=~"5.."}[5m])

# Độ trễ request p99
histogram_quantile(0.99, rate(http_server_requests_seconds_bucket[5m]))
```

**Kịch bản 2: Alert khi lỗi 5xx tăng**
```yaml
# PrometheusRule
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: app-alerts
spec:
  groups:
    - name: app.rules
      rules:
        - alert: HighErrorRate
          expr: |
            sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
            / sum(rate(http_server_requests_seconds_count[5m])) > 0.05
          for: 5m
          labels:
            severity: critical
          annotations:
            summary: "Tỷ lệ lỗi 5xx > 5% trong 5 phút"
```

**Kịch bản 3: Logging qua Loki**
```yaml
# Helm values cho Loki
loki:
  commonConfig:
    replication_factor: 1
  storage:
    type: filesystem

promtail:
  enabled: true
```
Promtail (DaemonSet) thu thập log từ mỗi node -> gửi đến Loki -> Grafana trực quan hóa.

### Bảng Các Lỗi Thường Gặp

| Lỗi                                          | Hậu quả                                                  | Giải pháp                                                               |
| ------------------------------------------------ | ------------------------------------------------------------ | ---------------------------------------------------------------------- |
| Chỉ có metrics hạ tầng, không có metrics kinh doanh | CPU trông ổn, nhưng thanh toán không diễn ra            | Thêm metrics kinh doanh: payments_per_second, order_processing_time       |
| Prometheus chỉ lưu trữ metrics 15 ngày           | Không thể phân tích xu hướng dài hạn                               | Dùng Thanos/Cortex cho lưu trữ dài hạn (S3)                           |
| Quá nhiều alert (alert fatigue)                  | Team bỏ qua các alert, bỏ lỡ các alert quan trọng                    | Giảm xuống 5-10 alert quan trọng, dùng alert grouping                     |
| Không có tracing (chỉ có metrics và log)               | Có thể thấy request chậm, nhưng không biết ở đâu                | Thêm OpenTelemetry + Jaeger/Tempo                                       |
| Prometheus là điểm lỗi đơn               | Khi Prometheus lỗi — không có metrics, không có alert            | Dùng Prometheus HA (2 replica, cluster Alertmanager)                    |
| Metrics được thu thập quá thường xuyên (mỗi 5s)           | Tải cao lên lưu trữ và network của Prometheus                  | Đặt 15-30s cho hầu hết các metrics, 5s cho các metrics quan trọng                      |

### So Sánh: Observability Stack

| Thành phần        | Metrics                       | Logs                              | Traces                                    |
| ---------------- | ----------------------------- | --------------------------------- | ----------------------------------------- |
| **Công cụ**         | Prometheus                    | Loki / ELK                        | Jaeger / Tempo                            |
| **Nó hiển thị gì**| Các con số (CPU, latency, errors)| Các sự kiện (dòng log, stack trace)  | Đường đi request qua các service             |
| **Thu thập**   | Pull (scrape)                 | Push (agent -> lưu trữ)           | Push (SDK -> collector)                   |
| **Lưu trữ**      | TSDB (15 ngày)                | Index + chunks (30 ngày)          | Trace index + span store                  |
| **Ngôn ngữ truy vấn**| PromQL                       | LogQL                             | Tra cứu Trace ID                           |
| **Khi nào dùng**  | Xu hướng, alerting, dashboard  | Debug, audit, compliance          | Distributed tracing, phát hiện bottleneck |

> Monitoring (Prometheus/Grafana) -- metrics: CPU, RAM, latency, tỷ lệ lỗi. Logging (ELK/Loki) -- log: stdout/stderr của container. Tracing (Jaeger/Zipkin) -- distributed tracing: đường đi request qua các service.

### Khi Nào KHÔNG Nên Dùng

- **Phát triển dev/local** — quá nặng, hãy dùng log đơn giản và các health endpoint
- **Các cluster rất nhỏ (1-2 Pod)** — overhead của Prometheus có thể vượt quá lợi ích
- **Khi không có team để hỗ trợ nó** — monitoring cần bảo trì: cập nhật dashboard, cấu hình alert, quản lý lưu trữ
- **Cho phân tích kinh doanh** — Prometheus không phải là một data warehouse. Hãy dùng ClickHouse/BigQuery cho phân tích kinh doanh

## Senior Level

### Cơ Chế Sâu: Prometheus TSDB, Scraping, Và Controller Reconciliation

**Kiến Trúc Prometheus:**
Prometheus hoạt động theo **mô hình pull** — nó poll các target qua endpoint HTTP `/metrics`.

1. **Service Discovery**: Prometheus khám phá các target qua API Kubernetes:
   - `kubernetes_sd_configs` với role `pod`, `service`, `endpoints`, `node`
   - Tự động tìm các Pod với annotation `prometheus.io/scrape: "true"`
   - Cập nhật danh sách target khi các Pod thay đổi (qua informer Kubernetes)

2. **Scraping**: Mỗi `scrape_interval` (mặc định 15s):
   - HTTP GET endpoint `/metrics`
   - Phân tích định dạng văn bản (Prometheus exposition format)
   - Lưu trong TSDB (Time-Series Database)

3. **TSDB (Time-Series Database)**:
   - Dữ liệu được lưu dưới dạng **block** (các đoạn 2 giờ) trên đĩa
   - Mỗi block: index (series -> chunk), chunk (mẫu thô), meta.json
   - WAL (Write-Ahead Log) cho tính bền vững khi crash
   - Compaction: block 2h -> 4h -> 8h -> ... (giảm cardinality)
   - Các file memory-mapped để đọc nhanh

4. **Prometheus Operator** (CoreOS):
   - Operator Kubernetes quản lý Prometheus qua CRD: `Prometheus`, `ServiceMonitor`, `PodMonitor`, `PrometheusRule`
   - `ServiceMonitor` — định nghĩa scrape target khai báo (thay vì cấu hình thủ công)
   - Tự động sinh ra cấu hình Prometheus từ CRD

**Cơ Chế Nội Bộ Của kube-state-metrics:**
kube-state-metrics kết nối đến API Server qua các informer và sinh ra các metrics về trạng thái các object K8s:
```
kube_pod_status_phase{namespace="default", pod="my-app", phase="Running"} -> 1
kube_deployment_status_replicas{namespace="default", deployment="my-app"} -> 3
kube_persistentvolumeclaim_status_phase{namespace="default", pvc="data", phase="Bound"} -> 1
```

**Alertmanager:**
Prometheus gửi các alert đang firing đến Alertmanager. Alertmanager:
1. **Groups**: Nhóm các alert tương tự (theo label)
2. **Inhibition**: Ức chế các alert phụ thuộc (nếu node lỗi, đừng alert cho mỗi Pod trên node đó)
3. **Routing**: Gửi đến đúng receiver (Slack, PagerDuty, email)
4. **Deduplication**: Prometheus HA (2 replica) gửi các alert giống hệt nhau, Alertmanager loại bỏ trùng lặp

**OpenTelemetry (Tracing):**
OpenTelemetry SDK instrument ứng dụng, thu thập **span** (các thao tác riêng lẻ) và nhóm chúng thành **trace** (toàn bộ đường đi request). Các span được gửi qua giao thức OTLP đến collector -> Jaeger/Tempo để lưu trữ và trực quan hóa.

### Đánh Đổi (Trade-offs)

| Khía cạnh                                 | Đánh đổi                                                                                                                                   |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| **Pull vs Push**                       | Pull (Prometheus) = service discovery đơn giản hơn, nhưng không hoạt động cho các target ngắn hạn. Push (StatsD) = hoạt động cho batch job, nhưng cần gateway |
| **Prometheus vs VictoriaMetrics**      | Prometheus = tiêu chuẩn, cộng đồng khổng lồ. VictoriaMetrics = hiệu năng tốt hơn, ít RAM hơn, nhưng hệ sinh thái kém trưởng thành hơn                            |
| **Loki vs ELK**                        | Loki = nhẹ hơn, rẻ hơn, tốt hơn cho K8s. ELK = full-text search mạnh hơn, nhưng nặng hơn (Elasticsearch JVM)                               |
| **Lưu trữ Prometheus local vs remote** | Local = đơn giản hơn, nhưng giới hạn 15-30 ngày. Remote (Thanos/Cortex) = lưu trữ dài hạn, nhưng phức tạp hơn                                   |
| **Label cardinality cao**            | Nhiều label hơn = truy vấn chính xác hơn, nhưng số series tăng theo hàm mũ -> nhiều RAM/CPU hơn                                                            |
| **Scrape interval**                    | Ngắn (5s) = chính xác hơn, nhưng tải cao hơn. Dài (30s) = tải thấp hơn, nhưng có thể bỏ lỡ các đợt tăng đột biến                                                      |

> Prometheus lưu trữ dữ liệu local (thường 15-30 ngày). Cho lưu trữ dài hạn, hãy dùng Thanos hoặc Cortex.

### Edge Case (7+)

**Edge Case 1: Bùng Nổ High Cardinality**
```promql
# TỒI: http_requests_total{path="/users/123", method="GET", status="200"}
# path chứa ID -> series duy nhất mỗi user -> hàng triệu series
```
Bùng nổ cardinality: Prometheus lưu trữ mỗi tổ hợp label duy nhất như một chuỗi thời gian riêng biệt. 1000 user x 10 endpoint x 5 status = 50,000 series. Điều này ngốn RAM và làm chậm các truy vấn. Giải pháp: dùng `path="/users/:id"` (nhóm lại), không phải ID cụ thể.

**Edge Case 2: Prometheus OOM Khi Số Lượng Series Lớn**
Prometheus lưu trữ tất cả các series đang hoạt động trong RAM. Với 10 triệu series, Prometheus cần ~20-30GB RAM. Nếu giới hạn ResourceQuota của namespace thấp hơn, Prometheus bị OOMKilled. Giải pháp: `--storage.tsdb.max-block-duration=2h`, giới hạn cardinality, hoặc VictoriaMetrics (dấu chân RAM nhỏ hơn).

**Edge Case 3: Target Scraping Biến Mất Trước Khi Scrape Hoàn Thành**
Pod bị xóa trong khi scrape. Prometheus nhận connection refused hoặc phản hồi một phần. Metrics cho lần scrape đó bị mất. Với các deployment thường xuyên (100+ Pod/ngày), điều này tạo ra các khoảng trống trong metrics. Giải pháp: `honor_labels: true` + `scrape_timeout < scrape_interval`.

**Edge Case 4: Alertmanager Ngập Lụt Thông Báo**
Node lỗi -> 50 Pod trên node không sẵn sàng -> 50 alert firing đồng thời. Alertmanager gửi 50 tin nhắn Slack. Team gặp alert fatigue. Giải pháp: alert grouping (`group_by: ['node']`), các quy tắc inhibition (nếu node lỗi, ức chế các alert của pod).

**Edge Case 5: Overhead Tracing**
OpenTelemetry với `sampling: 1.0` (100% các trace) thêm 5-15% overhead vào độ trễ mỗi request. Ở tải cao (10K RPS), đây là sự suy giảm đáng kể. Giải pháp: sampling xác suất (0.1-1%), hoặc adaptive sampling (tăng tỷ lệ sampling cho lỗi).

**Edge Case 6: Cardinality Label Của Loki**
Loki chỉ index các label, không phải nội dung dòng log. Nếu `pod_name` được dùng làm label, mỗi tổ hợp label duy nhất = stream riêng biệt. Với 1000 Pod = 1000 stream. Giải pháp: dùng các label có cardinality thấp hơn (`app`, `namespace`), không phải `pod_name`.

**Edge Case 7: Độ Phức Tạp Của Thanos/Cortex**
Thanos thêm sidecar (vào Prometheus), query gateway, store gateway (S3), compactor, ruler. Đây là 5+ thành phần bổ sung. Với một team 3 DevOps, đây có thể là overhead. Giải pháp: bắt đầu với Prometheus + retention 30 ngày, chuyển sang Thanos chỉ khi cần lưu trữ dài hạn.

**Edge Case 8: Tải API Server Của kube-state-metrics**
kube-state-metrics watch tất cả các object K8s qua các informer API Server. Với 5000 Pod, 1000 Service, 500 Deployment, cache informer chiếm ~500MB RAM. Các thao tác List/Watch thêm tải lên API Server. Giải pháp: cờ `--resources` để giới hạn chỉ watch các tài nguyên cần thiết.

### Bảo Mật

- **Endpoint Prometheus không được phép công khai** — `/metrics` phơi bày cấu trúc nội bộ của ứng dụng. Giới hạn qua NetworkPolicy
- **mTLS cho scraping** — nếu dùng Istio, scrape của Prometheus phải được loại trừ khỏi mTLS hoặc dùng sidecar injection
- **RBAC cho SA của Prometheus** — Service Account của Prometheus yêu cầu `get`, `list`, `watch` trên các Pod, Service, Endpoints. Giới hạn chỉ vào các namespace cần thiết
- **Xác thực webhook Alertmanager** — các webhook Slack/PagerDuty nên dùng token xác thực, không phải URL văn bản thô
- **Làm sạch log Loki** — log có thể chứa dữ liệu nhạy cảm (PII, thông tin xác thực). Dùng log redaction (các pipeline stage của Promtail) trước khi gửi đến Loki
- **Mã hóa Thanos/S3** — lưu trữ metrics dài hạn trong S3 nên được mã hóa (SSE-S3 hoặc SSE-KMS)
- **Xác thực OpenTelemetry collector** — endpoint OTLP nên yêu cầu xác thực (API key, mTLS), nếu không bất kỳ ai cũng có thể gửi các span giả

### Câu Chuyện Production Thực Tế

**Tình huống:** Nền tảng SaaS, cluster 1000 Pod, Prometheus + Grafana + Alertmanager. Ứng dụng: các microservice Java/Spring Boot với tracing OpenTelemetry.

**Sự cố:**
1. Developer thêm metric `http_requests_total{path="/users/{id}", user_id="<id-thực>", ...}` — user_id là ID user thực, không phải một template
2. Trong 2 giờ, cardinality tăng từ 500K lên 15 triệu series (100K user_id duy nhất)
3. Mức sử dụng RAM của Prometheus tăng từ 8GB lên 25GB
4. Prometheus bị OOMKilled (giới hạn ResourceQuota: 20GB)
5. Alertmanager ngừng nhận alert — team không biết về vấn đề
6. Sau 30 phút, kỹ sư trực nhận thấy các dashboard Grafana trống rỗng
7. Prometheus restart, nhưng khi khởi động replay WAL (Write-Ahead Log) -> OOM lần nữa -> crash loop
8. Gián đoạn monitoring trong 4 giờ cho đến khi metric high-cardinality bị loại bỏ và RAM được tăng lên

**Post-mortem và fix:**
1. **Cardinality guard** — cấu hình Prometheus `--storage.tsdb.max-block-duration=2h` + alert trên tốc độ tăng series
2. **Quy ước đặt tên metric** — `path="/users/:id"` (template), không phải ID cụ thể. Code review cho các metric mới
3. **Prometheus HA** — 2 replica Prometheus với deduplication Alertmanager
4. **ResourceQuota cho namespace Prometheus** — namespace riêng biệt với tài nguyên được đảm bảo
5. **Alert trên sức khỏe Prometheus** — health check bên ngoài (qua synthetic monitoring), không phụ thuộc vào Prometheus
6. **Thanos cho lưu trữ dài hạn** — sidecar upload lên S3, ngay cả khi Prometheus crash

**Monitoring sau khi fix:**
```promql
# Alert: Tốc độ tăng series của Prometheus
rate(prometheus_tsdb_head_series[1h]) > 100000  # >100K series mới/giờ

# Alert: Mức sử dụng memory của Prometheus
process_resident_memory_bytes{job="prometheus"} / 20e9 > 0.8  # >80% của 20GB

# Alert: Prometheus down (kiểm tra bên ngoài)
up{job="prometheus"} == 0

# Alert: Alertmanager không nhận alert
rate(alertmanager_notifications_total{status="success"}[5m]) == 0
```

### Monitoring (Prometheus/Grafana)

**Các metrics chính để giám sát chính hệ thống monitoring:**
```promql
# Sức khỏe Prometheus
up{job="prometheus"}

# Số lượng series (cardinality)
prometheus_tsdb_head_series

# Thời lượng scrape
rate(prometheus_target_interval_length_seconds_sum[5m])
/ rate(prometheus_target_interval_length_seconds_count[5m])

# Compaction TSDB
rate(prometheus_tsdb_compactions_total[1h])

# Các alert của Alertmanager
alertmanager_alerts{state="firing"}

# Độ trễ kube-state-metrics
kube_state_metrics_list_duration_seconds
```

**Các metrics chính cho ứng dụng (Golden Signals):**
```promql
# 1. Latency (p50, p95, p99)
histogram_quantile(0.50, rate(http_server_requests_seconds_bucket[5m]))
histogram_quantile(0.95, rate(http_server_requests_seconds_bucket[5m]))
histogram_quantile(0.99, rate(http_server_requests_seconds_bucket[5m]))

# 2. Traffic (RPS)
sum(rate(http_server_requests_seconds_count[5m])) by (service)

# 3. Errors (tỷ lệ 5xx)
sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m]))
/ sum(rate(http_server_requests_seconds_count[5m]))

# 4. Saturation (CPU, memory, disk)
sum(rate(container_cpu_usage_seconds_total[5m])) by (pod)
container_memory_working_set_bytes / container_spec_memory_limit_bytes
```

**Các panel Grafana Dashboard:**
1. **Tổng Quan Golden Signals**: Latency p50/p95/p99, Traffic RPS, Error Rate, Saturation (CPU/Memory)
2. **JVM Metrics**: Memory Heap/Non-Heap, thời gian khoảng dừng GC, số lượng thread, class loading
3. **Tổng Quan Kubernetes**: Trạng thái Pod, các replica Deployment, mức sử dụng PVC, tài nguyên Node
4. **Tổng Quan Alerting**: Các alert đang firing theo mức độ nghiêm trọng, tỷ lệ alert, độ trễ thông báo alertmanager
5. **Tổng Quan Tracing** (Tempo/Jaeger): Số lượng trace, tỷ lệ trace lỗi, các endpoint chậm nhất
6. **Self-Monitoring Prometheus**: Số lượng series, thời lượng scrape, kích thước TSDB, mức sử dụng memory

### Các Thực Hành Tốt Nhất Cho Highload

1. **Golden Signals: Latency, Traffic, Errors, Saturation** — luôn giám sát 4 metrics này
2. **Quản lý cardinality** — đừng dùng các label high-cardinality (user_id, request_id). Dùng template: `path="/users/:id"`
3. **Prometheus HA** — 2 replica Prometheus + Alertmanager với deduplication
4. **Scrape interval: 15s cho hầu hết, 5s cho quan trọng** — cân bằng giữa độ chính xác và tải
5. **Retention: 15 ngày local + Thanos/Cortex cho dài hạn** — lưu trữ S3 cho compliance và phân tích xu hướng
6. **Định tuyến alert theo mức độ nghiêm trọng**:
   - Critical -> PagerDuty (ngay lập tức)
   - Warning -> Slack (trong giờ làm việc)
   - Info -> Email (tổng hợp hàng ngày)
7. **Các quy tắc inhibition** — nếu node lỗi, đừng alert cho mỗi Pod trên node đó
8. **Sampling OpenTelemetry: 0.1-1%** cho production, 100% cho lỗi
9. **Cardinality label Loki** — dùng `app`, `namespace`, không phải `pod_name`
10. **Giám sát chính hệ thống monitoring** — health check bên ngoài cho Prometheus/Alertmanager, không phụ thuộc vào chúng
11. **ResourceQuota Prometheus** — namespace riêng biệt với 20-30GB RAM được đảm bảo cho 10M series
12. **Dashboard as code** — các dashboard Grafana trong Git (JSON), được deploy qua CI/CD
13. **Theo dõi SLO/SLI** — định nghĩa các Service Level Objective (99.9% khả dụng, p99 < 500ms) và theo dõi error budget
14. **Xem xét alert thường xuyên** — xem xét hàng tháng các alert đang firing, loại bỏ các alert gây nhiễu, thêm những cái còn thiếu

## Interview Cheat Sheet

**Cần phải biết:**
- Observability = Metrics (Prometheus) + Logs (Loki/ELK) + Traces (Jaeger/Tempo)
- Prometheus — mô hình pull, DB chuỗi thời gian; scrape `/metrics` mỗi 15-30 giây
- Golden Signals: Latency, Traffic, Errors, Saturation — luôn giám sát
- kube-prometheus-stack = Prometheus + Grafana + Alertmanager + Node Exporter + kube-state-metrics
- Bùng nổ cardinality — vấn đề chính của Prometheus (label high-cardinality = OOM)
- Với Java: memory JVM, khoảng dừng GC, tỷ lệ lỗi HTTP, độ trễ request (histogram_quantile)
- Định tuyến alert theo mức độ nghiêm trọng: Critical -> PagerDuty, Warning -> Slack, Info -> digest

**Các câu hỏi phụ thường gặp:**
- *"Tại sao bùng nổ cardinality lại nguy hiểm?"* — Mỗi tổ hợp label duy nhất = series; hàng triệu series -> OOM
- *"Prometheus HA — tại sao?"* — Điểm lỗi đơn; 2 replica + deduplication Alertmanager
- *"Pull vs Push?"* — Pull (Prometheus) = service discovery đơn giản hơn; Push (StatsD) = cho batch job
- *"Làm sao giám sát chính hệ thống monitoring?"* — Health check bên ngoài cho Prometheus/Alertmanager, không phụ thuộc vào chúng

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Prometheus lưu trữ metrics vĩnh viễn" (local 15-30 ngày; Thanos/Cortex cho dài hạn)
- "Tôi chỉ giám sát CPU/RAM" (cần các metrics kinh doanh: tỷ lệ lỗi, latency, throughput)
- "Sampling 100% cho tracing trong production" (overhead 5-15%; hãy dùng 0.1-1%)
- "Alert fatigue là bình thường" (giảm xuống 5-10 alert quan trọng; nếu không team sẽ bỏ qua)
