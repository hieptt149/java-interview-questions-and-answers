# What is Load Factor in HashMap? (Load Factor trong HashMap là gì?)

## 🟢 Junior Level

**Load Factor** là một con số xác định khi nào HashMap nên tăng kích thước của nó.

Theo mặc định, load factor = **0.75** (75%).

**Cách nó hoạt động:**
```java
HashMap<String, Integer> map = new HashMap<>();
// capacity = 16, load factor = 0.75
// threshold = 16 * 0.75 = 12
// Khi thêm phần tử thứ 13, HashMap tăng lên 32 bucket
```

**Ví dụ minh họa đơn giản:** Hãy tưởng tượng một cái ly được đổ nước tới 75%. Nếu bạn đổ thêm — nó tràn, và bạn cần một cái ly to hơn. Load factor là dấu "75%" trên cái ly.

**Tại sao 0.75?** Đó là một sự cân bằng: không quá nhiều slot rỗng (bộ nhớ) và không quá nhiều va chạm (tốc độ).

## 🟡 Middle Level

### Công thức ngưỡng Resize

```
threshold = capacity * loadFactor
```

Khi `size > threshold`, resize (tăng đôi mảng) xảy ra.

### Ảnh hưởng tới hiệu năng và bộ nhớ

| Load Factor         | Bộ nhớ                      | Tốc độ                                                                                   | Va chạm          |
| ------------------- | --------------------------- | ---------------------------------------------------------------------------------------- | ---------------- |
| 0.5 (thấp)          | Nhiều hơn (50% bucket rỗng) | Nhanh hơn (các bucket chứa 0-1 phần tử, tìm kiếm gần như luôn O(1) không cần duyệt list/tree) | Va chạm tối thiểu |
| 0.75 (mặc định)     | Cân bằng                    | Cân bằng                                                                                 | Ít               |
| 0.9 (cao)           | Ít hơn                      | Chậm hơn                                                                                 | Nhiều hơn        |
| 1.0+                | Tối thiểu                   | Thậm chí chậm hơn                                                                        | Nhiều            |

### Khi nào thay đổi loadFactor?

**Thấp (0.5):** Khi tốc độ truy cập là then chốt (các hệ thống low latency)
```java
new HashMap<>(1000, 0.5f); // Truy cập nhanh, nhưng 2x bộ nhớ
```

**Cao (>0.75):** Khi tiết kiệm bộ nhớ là then chốt (Embedded, IoT)
```java
new HashMap<>(1000, 0.9f); // Tiết kiệm bộ nhớ, nhưng nhiều va chạm hơn
```

### Tương tác với Initial Capacity

```java
// Tính đúng cho 1000 phần tử:
int capacity = (int)(1000 / 0.75f) + 1; // = 1334
Map<K, V> map = new HashMap<>(capacity, 0.75f);
// HashMap làm tròn lên 2048, threshold = 1536
```

### Các sai lầm thường gặp

1. **Load factor > 1.0** — được cho phép, nhưng tìm kiếm suy giảm xuống O(n)
2. **Quá thấp** — lãng phí bộ nhớ, các lần resize thường xuyên khi fill thấp
3. **Không tính đến việc làm tròn** — HashMap luôn làm tròn capacity thành lũy thừa của hai

## 🔴 Senior Level

### Phân phối Poisson

Việc chọn 0.75 được biện minh về mặt thống kê. Ở hệ số này, phân bố phần tử qua các bucket:

```
P(x) = (0.75^x * e^-0.75) / x!

x=0: 47.2%
x=1: 35.4%
x=2: 13.3%
x=8: 0.000006% — thực tế bất khả thi
```

Xác suất một chuỗi 8 phần tử: **0.00000006**. Treeification — bảo vệ khỏi bất thường.

### Ảnh hưởng tới Cache Locality

Load factor cao ảnh hưởng đến hiệu năng thực tế nhiều hơn phân tích tiệm cận gợi ý:
- Các chuỗi dài → các node rải rác khắp Heap → Cache Miss
- CPU chờ dữ liệu từ RAM (100+ ns) thay vì cache L1/L2 (1-5 ns)
- O(log n) với cache locality kém (các node của tree rải rác khắp heap) có thể chậm hơn O(1) với một load factor tốt. CPU chờ dữ liệu từ RAM (~100 ns) thay vì cache L1 (~1 ns).

### Memory Footprint

Ở capacity = 1024:
- Load factor 0.5: 512 phần tử, ~512 bucket rỗng → ~4KB "lãng phí"
- Load factor 0.75: 768 phần tử, ~256 rỗng → ~2KB "lãng phí"
- Load factor 0.9: 922 phần tử, ~102 rỗng → ~1KB "lãng phí"

### Các trường hợp biên (Edge Case)

1. **Load factor = 1.0**: Tối thiểu các bucket rỗng, nhưng các chuỗi được đảm bảo
2. **Load factor > 1.0**: HashMap hoạt động như một mảng các list, tìm kiếm là O(n)
3. **Load factor < 0.1**: Cực kỳ nhanh, nhưng overhead bộ nhớ 10x

### Tinh chỉnh Production

Trong các hệ thống tải cao:
- **Read-heavy**: load factor 0.5-0.6 — va chạm tối thiểu, tốc độ tối đa
- **Write-heavy**: load factor 0.75 — cân bằng, ít resize hơn
- **Memory-constrained**: load factor 0.9+ — tiết kiệm bộ nhớ, _chậm ở mức chấp nhận được_

### Giám sát

Để phân tích tính hiệu quả:
- Đo số lượng phần tử trung bình mỗi bucket
- So sánh latency get/put ở các load factor khác nhau
- Dùng JFR để phân tích phân bố

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Load factor = 0.75 theo mặc định — cân bằng giữa bộ nhớ và va chạm
- threshold = capacity * loadFactor; khi vượt — resize
- Phân phối Poisson: ở 0.75, xác suất 8+ phần tử trong một bucket ≈ 0.00000006
- LF thấp (0.5): nhanh hơn, nhưng 2x bộ nhớ; cao (0.9): tiết kiệm bộ nhớ, nhưng nhiều va chạm hơn
- Load factor cao = các chuỗi dài = Cache Miss = hiệu năng thực tế tệ hơn phân tích tiệm cận
- LF > 1.0 được cho phép, nhưng tìm kiếm suy giảm xuống O(n)

**Các câu hỏi phụ thường gặp:**
- **Khi nào dùng LF = 0.5?** — các hệ thống read-heavy, low latency
- **Khi nào LF = 0.9?** — memory-constrained (Embedded, IoT)
- **Tại sao 0.75, không phải 0.5 hay 1.0?** — thỏa hiệp được biện minh về mặt thống kê (Poisson)
- **LF có ảnh hưởng đến việc iterate không?** — gián tiếp: capacity lớn hơn ở LF thấp = iterate chậm hơn

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Load factor = 1.0 là tối ưu" — không, các chuỗi và va chạm được đảm bảo
- "Có thể thay đổi load factor sau khi tạo" — không, nó được đặt trong constructor
- "0.75 nghĩa là 75% các bucket được lấp đầy" — không, 75% của capacity trước khi resize
