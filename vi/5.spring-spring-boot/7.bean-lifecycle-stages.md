# What are the Bean Lifecycle Stages? (Các giai đoạn của Bean Lifecycle là gì?)

## Junior Level

**Các giai đoạn tạo bean:**

```
1. Constructor -> đối tượng được tạo
2. @Autowired -> các phụ thuộc được inject
3. @PostConstruct -> khởi tạo
4. Sẵn sàng hoạt động
5. @PreDestroy -> dọn dẹp khi bị gỡ bỏ
```

```java
@Service
public class MyService {

    private final Repo repo;

    // 1. Constructor
    public MyService(Repo repo) {
        this.repo = repo;
    }

    // 2. @Autowired đã chạy (qua constructor)

    // 3. Khởi tạo
    @PostConstruct
    public void init() {
        System.out.println("Bean is ready!");
    }

    // 5. Dọn dẹp
    @PreDestroy
    public void cleanup() {
        System.out.println("Bean is being removed");
    }
}
```

## Middle Level

> Câu hỏi này đi sâu vào các giai đoạn từ file [[06. What is Bean Lifecycle]] (Bean Lifecycle là gì). Nếu file đó giải thích TẠI SAO, thì file này giải thích chính xác NHƯ THẾ NÀO (12 bước).

### Thứ tự chi tiết

```
1. Instantiation (constructor)
2. Populate Properties (các field/setter có @Autowired)
3. Aware Interfaces
   -> BeanNameAware.setBeanName()
   -> BeanFactoryAware.setBeanFactory()
   -> ApplicationContextAware.setApplicationContext()
4. BeanPostProcessor.postProcessBeforeInitialization()
5. @PostConstruct
6. InitializingBean.afterPropertiesSet()
7. init-method (@Bean(initMethod="init"))
8. BeanPostProcessor.postProcessAfterInitialization() <- Proxy!
9. READY
10. @PreDestroy
11. DisposableBean.destroy()
12. destroy-method
```

### Singleton so với Prototype

```java
// Singleton:
// -> Tất cả các giai đoạn 1-12
// -> Bị hủy khi context được đóng

// Prototype:
// -> Chỉ các giai đoạn 1-9
// -> @PreDestroy KHÔNG được gọi tự động. Spring không theo dõi việc hủy chúng. Nếu cần - hãy gọi cleanup thủ công hoặc dùng ConfigurableBeanFactory.registerDestructionCallback().
```

### ContextRefreshedEvent

```java
// Khi TẤT CẢ bean đã được tạo và khởi tạo:
@EventListener(ContextRefreshedEvent.class)
public void onApplicationReady() {
    // Tất cả proxy đã được tạo, tất cả bean đã sẵn sàng
    // Có thể gọi các phương thức @Transactional!
}
```

## Senior Level

### Instantiation so với Initialization

```
Instantiation:
  -> new Service() qua reflection
  -> Đối tượng tồn tại trong Heap

Initialization:
  -> Tiêm phụ thuộc
  -> @PostConstruct
  -> Tạo Proxy

-> Trong constructor, các phụ thuộc chưa được inject (trừ Constructor Injection)
```

### Chuỗi BPP

BPP (BeanPostProcessor) là cơ chế của Spring để sửa đổi các bean. Các BPP chính:
- **CommonAnnotationBeanPostProcessor** — xử lý @PostConstruct/@PreDestroy
- **AutowiredAnnotationBeanPostProcessor** — xử lý @Autowired
- **AnnotationAwareAspectJAutoProxyCreator** — tạo proxy cho @Transactional, @Async

```
Nhiều BPP chạy tuần tự:
  1. CommonAnnotationBeanPostProcessor -> @PostConstruct
  2. AutowiredAnnotationBeanPostProcessor -> @Autowired
  3. AnnotationAwareAspectJAutoProxyCreator -> Proxy

-> Mỗi cái có thể sửa đổi hoặc thay thế bean
-> Thứ tự quan trọng! -> @Order
```

### Khởi tạo BPP sớm

```java
// Nếu BPP của bạn phụ thuộc vào MyService:
// -> MyService được tạo TRƯỚC các BPP khác
// -> MyService có thể không nhận được một proxy!

// Tại sao: Các BPP tạo proxy (ví dụ AnnotationAwareAspectJAutoProxyCreator cho @Transactional) chưa được đăng ký. MyService được tạo "trần trụi", không có lớp bọc proxy. Giải pháp: đừng inject bean vào BPP - dùng ObjectProvider hoặc ApplicationContext.getBean() một cách thận trọng.

// Giải pháp: @Lazy hoặc các BPP độc lập
```

### Kinh nghiệm Production

**Tình huống thực tế: BPP không nhận được proxy**
- Một BPP tùy chỉnh phụ thuộc vào DataSource
- DataSource được tạo sớm hơn -> không có transaction
- Giải pháp: phụ thuộc @Lazy trong BPP
- Kết quả: proxy được tạo đúng cách

### Best Practices

1. **Constructor** -> chỉ gán field
2. **@PostConstruct** -> validation, khởi tạo nhẹ
3. **@PreDestroy** -> dọn dẹp tài nguyên
4. **Prototype** -> tự dọn dẹp
5. **ContextRefreshedEvent** -> khi mọi thứ đã sẵn sàng
6. **Các phụ thuộc của BPP** -> @Lazy

### Tóm tắt cho Senior

- **12 giai đoạn** -> từ constructor đến destroy
- **Proxy** được tạo ở giai đoạn 8 (sau @PostConstruct)
- **Prototype** -> không có các giai đoạn 10-12
- **Thứ tự BPP** -> quan trọng, qua @Order
- **ContextRefreshedEvent** -> tất cả bean đã sẵn sàng
- **Khởi tạo sớm** -> có thể làm hỏng proxy

## Interview Cheat Sheet

**Cần phải biết:**
- 12 giai đoạn: Instantiation -> Populate Properties -> Aware Interfaces -> BPP Before -> @PostConstruct -> afterPropertiesSet -> init-method -> BPP After (Proxy!) -> Ready -> @PreDestroy -> DisposableBean -> destroy-method
- Các interface Aware: `BeanNameAware`, `BeanFactoryAware`, `ApplicationContextAware` — bean nhận thông tin từ container
- Proxy được tạo ở giai đoạn 8 — `BPP.postProcessAfterInitialization()`, sau `@PostConstruct`
- Singleton đi qua cả 12 giai đoạn, Prototype — chỉ 1-9 (không có destroy)
- `ContextRefreshedEvent` — được phát ra khi TẤT CẢ bean và proxy đã được tạo, có thể gọi các phương thức `@Transactional`
- Khởi tạo BPP sớm: nếu BPP phụ thuộc vào một bean, bean đó được tạo trước các BPP khác và có thể không nhận được proxy
- Thứ tự BPP qua `@Order` — thứ tự quan trọng, mỗi BPP có thể thay thế một bean

**Các câu hỏi phụ thường gặp:**
- **Sự khác nhau giữa Instantiation và Initialization là gì?** Instantiation = `new` qua reflection (đối tượng tồn tại). Initialization = DI, `@PostConstruct`, tạo Proxy.
- **Bạn biết những interface Aware nào?** `BeanNameAware` (tên bean), `BeanFactoryAware` (factory), `ApplicationContextAware` (context).
- **Tại sao một BPP tùy chỉnh có thể không nhận được proxy?** Nếu bean được tạo trước BPP tạo proxy — bean vẫn "trần trụi".
- **Làm sao quản lý thứ tự BPP?** Annotation `@Order` — giá trị nhỏ hơn = chạy sớm hơn.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Trong constructor, tất cả các phụ thuộc đã được inject" (trừ Constructor Injection — các phụ thuộc vẫn còn NULL)
- "Prototype bean gọi `@PreDestroy`" (không, Spring không theo dõi việc hủy chúng)
- "Thứ tự BPP không quan trọng" (cực kỳ quan trọng — BPP đầu tiên có thể thay thế bean cho BPP thứ hai)
- "Có thể kéo bất kỳ phụ thuộc nào vào BPP" (điều này gây khởi tạo sớm và làm hỏng proxy)
