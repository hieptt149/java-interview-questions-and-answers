# What happens if you modify a mutable key in HashMap? (Điều gì xảy ra nếu bạn thay đổi một mutable key trong HashMap?)

---

## Basic Level

Nếu bạn sửa đổi một object được dùng làm key trong `HashMap`, nó sẽ bị **thất lạc** — bạn sẽ không thể tìm thấy nó.

```java
List<String> key = new ArrayList<>(List.of("A"));
Map<List<String>, String> map = new HashMap<>();
map.put(key, "value");

key.add("B"); // Đã sửa đổi key!
System.out.println(map.get(key)); // null — không tìm thấy!
```

### Tại Sao

- Khi `put`, HashMap đã tính hash của `["A"]` → đặt vào bucket #5
- Sau khi key bị sửa đổi, hash của `["A", "B"]` → bucket khác
- `get` tìm trong bucket sai → `null`

Object vẫn nằm trong map, nhưng bạn không thể lấy nó ra.

---

## Intermediate Level

### Cơ Chế Của Sự Cố

1. **put(key, value)** — hash của key → bucket #5
2. **Mutation** — đã thay đổi một trường của key → hash mới
3. **get(key)** — hash mới → bucket #10 → rỗng → `null`

Object vẫn nằm về mặt vật lý trong bucket #5, nhưng đã trở nên **không thể truy cập được**.

### Hậu Quả

**Không thể truy cập về mặt logic**: object không thể được lấy ra qua get() hoặc xóa qua
remove() bằng key đã sửa đổi. Nó chiếm chỗ cho đến khi toàn bộ map bị xóa
hoặc entrySet() được duyệt qua.

**Trùng lặp trong HashSet**:
```java
Set<List<String>> set = new HashSet<>();
set.add(new ArrayList<>(List.of("A")));
// Đã sửa đổi một phần tử bên trong list
set.add(new ArrayList<>(List.of("A"))); // Được thêm lại lần nữa!
```

### Cách Tìm Object Bị Thất Lạc

Thông qua duyệt qua toàn bộ — **O(n)** thay vì **O(1)**:
```java
for (var entry : map.entrySet()) {
    if (entry.getKey().contains("A")) {
        // đã tìm thấy
    }
}
```

## Advanced Level

### Cách Tránh

1. **Các key bất biến** — `String`, `UUID`, `Record` — luôn luôn
2. **Remove → sửa đổi → add**:
   ```java
   V value = map.remove(key);
   key.mutate();
   map.put(key, value);
   ```
3. **IdentityHashMap** — nếu mutation là không thể tránh khỏi và bạn không kiểm soát object (so sánh theo `==`)
   ```java
   Map<List<String>, String> map = new IdentityHashMap<>();
   // So sánh theo ==, không phải equals — mutation không phá vỡ việc tra cứu miễn là đó là cùng một object.
   ```

### Vấn Đề Sâu Xa

Việc sửa đổi một key mutable phá vỡ **bất biến (invariant)** của HashMap: `hashCode` của key phải ổn định. Đây không phải là một bug của HashMap, mà là một vi phạm hợp đồng của `hashCode()` — nếu `equals` không đổi, thì `hashCode` cũng nên giống nhau, nhưng mutation thay đổi cả hai.

### Tóm Tắt Cho Advanced
- Sửa đổi một key mutable "làm hỏng" map — object không thể truy cập qua `get()`
- Đây là một rò rỉ bộ nhớ kinh điển và nguồn gốc của các bug khó tìm
- Luôn thiết kế các key như các entity bất biến
- Nếu mutation là cần thiết: `remove` → `mutate` → `put`
- `IdentityHashMap` — giải pháp cuối cùng khi không thể kiểm soát key

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Sửa đổi key mutable → hashCode mới → get tìm trong một bucket khác → null
- Object vẫn nằm về mặt vật lý trong map, nhưng trở nên **không thể truy cập được** — rò rỉ bộ nhớ về mặt logic
- Trùng lặp trong HashSet: object đã sửa đổi được thêm lại lần nữa như "mới"
- Object bị thất lạc chỉ có thể tìm thấy qua việc duyệt entrySet — O(n) thay vì O(1)
- Cách tránh: luôn dùng các key bất biến, hoặc remove → mutate → put
- IdentityHashMap — so sánh theo `==`, mutation không phá vỡ việc tra cứu (miễn là cùng một object)

**Các câu hỏi phụ thường gặp:**
- *Object có bị xóa khỏi map không?* — Không, nó ở lại bucket cũ, nhưng không thể truy cập qua get/remove
- *Làm sao để tìm một object bị thất lạc?* — Duyệt entrySet — O(n)
- *IdentityHashMap có giải quyết được vấn đề không?* — Có, so sánh theo tham chiếu, nhưng đó là một trường hợp sử dụng cụ thể
- *Đây có phải là bug của HashMap không?* — Không, đó là vi phạm hợp đồng: hashCode phải ổn định

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Object bị xóa khỏi map" — không, nó vẫn ở lại nhưng không thể truy cập được
- "HashMap tự sửa hashCode" — không, đó là hợp đồng của lập trình viên
- "Key mutable là ổn" — nguồn gốc kinh điển của rò rỉ bộ nhớ và bug
- "IdentityHashMap là một thay thế cho HashMap" — đó là một cấu trúc hoàn toàn khác, so sánh theo tham chiếu
