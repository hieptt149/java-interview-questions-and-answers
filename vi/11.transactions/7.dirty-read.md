# What is Dirty Read? (Dirty Read là gì?)

## 🟢 Junior Level

**Dirty Read** là một hiện tượng bất thường (anomaly) trong đó một transaction đọc dữ liệu đã được sửa đổi bởi một transaction khác chưa hoàn thành (chưa phát hành COMMIT).

### Ví Dụ Đơn Giản

```
Transaction A: UPDATE accounts SET balance = 500 WHERE id = 1;
Transaction B: SELECT balance FROM accounts WHERE id = 1; -- Thấy 500
Transaction A: ROLLBACK; -- Hoàn tác các thay đổi, balance trở lại 100
```

Transaction B đã đọc giá trị 500, giá trị mà giờ không còn tồn tại. Đây là dữ liệu "bẩn" (dirty).

### Tại Sao Điều Này Xấu

Bạn ra quyết định dựa trên dữ liệu thực tế không tồn tại trong cơ sở dữ liệu.

### Xảy Ra Ở Level Nào

Chỉ ở level **Read Uncommitted**. Tất cả các level khác đều cấm dirty read.

### Nơi Nó Xảy Ra

PostgreSQL và Oracle không có level này — chúng tự động bảo vệ chống lại dirty read.

## 🟡 Middle Level

### Kịch Bản Chi Tiết

| Thời gian | Transaction A                                     | Transaction B (Read Uncommitted)                         |
| ----- | ------------------------------------------------- | -------------------------------------------------------- |
| T1    | `BEGIN;`                                          | `BEGIN;`                                                 |
| T2    | `UPDATE accounts SET balance = 500 WHERE id = 1;` |                                                          |
| T3    |                                                   | `SELECT balance FROM accounts WHERE id = 1;` → **500**   |
| T4    | `ROLLBACK;`                                       |                                                          |
| T5    |                                                   | Làm việc với balance 500, thực tế là 100                     |

### Hậu Quả Cho Hệ Thống

- **Tài chính**: Quyết định tín dụng dựa trên số dư chưa được xác nhận
- **Kho hàng**: Đặt trước hàng hóa không tồn tại
- **Tính bất biến**: Vi phạm tính toàn vẹn — chúng ta thấy một trạng thái trung gian không hợp lệ

### DBMS Bảo Vệ Chống Dirty Read Như Thế Nào

> **Các thuật ngữ:**
> - **S-lock (Shared)** — read lock: nhiều transaction có thể đọc đồng thời, nhưng không ai được ghi.
> - **X-lock (Exclusive)** — write lock: chỉ một transaction ghi, các transaction khác phải chờ.
> - **MVCC** — lưu trữ nhiều phiên bản dòng, mỗi phiên bản gắn với transaction ID tạo ra nó.

#### Shared Lock (S-lock)
Một transaction đọc chờ exclusive lock (X-lock) trên bản ghi được giải phóng. Việc đọc bị chặn cho đến khi việc ghi hoàn thành.

#### MVCC (Multi-Version Concurrency Control)
Việc đọc diễn ra từ phiên bản dòng **đã commit** gần nhất. Các thay đổi chưa commit tạo ra một phiên bản tạm thời mà người khác không thấy.

### Nơi Nó Được Cho Phép

Chỉ một level duy nhất — **Read Uncommitted**.

**Quan trọng**: PostgreSQL không có level này (tự động nâng lên Read Committed). Oracle cũng vậy.

### Dirty Read So Với Các Hiện Tượng Bất Thường Khác

> **Dirty Read**: bạn thấy một GIÁ TRỊ chưa tồn tại trong cơ sở dữ liệu (transaction tạo ra nó đã ROLLBACK).
> **Non-Repeatable Read**: bạn thấy một giá trị đã commit THỰC SỰ, nhưng nó thay đổi giữa hai lần SELECT của bạn.

- **Dirty Read**: Đọc dữ liệu chưa commit
- **Non-Repeatable Read**: Đọc dữ liệu đã commit nhưng thay đổi giữa hai lần SELECT
- **Phantom Read**: Các dòng mới xuất hiện giữa hai lần SELECT

## 🔴 Senior Level

### Cơ Chế Bảo Vệ Của MVCC — Đào Sâu

#### Hiện Thực Trong PostgreSQL
Trong PostgreSQL, mỗi heap tuple chứa:
- `t_xmin`: transaction ID đã insert phiên bản dòng này
- `t_xmax`: transaction ID đã delete/update phiên bản dòng này

Kiểm tra visibility để ngăn dirty read:
```c
bool TupleIsVisibleToSnapshot(HeapTuple tuple, Snapshot snap) {
    // Nếu transaction insert vẫn đang chạy → KHÔNG hiển thị
    if (TransactionIdIsInProgress(tuple->t_xmin))
        return false;

    // Nếu transaction insert chưa commit → KHÔNG hiển thị
    if (!TransactionIdDidCommit(tuple->t_xmin))
        return false;

    // Nếu transaction delete đã commit → KHÔNG hiển thị
    if (TransactionIdIsValid(tuple->t_xmax) &&
        TransactionIdDidCommit(tuple->t_xmax))
        return false;

    return true;
}
```

Việc kiểm tra này **miễn phí** — nó là một phần của visibility MVCC thông thường, không có overhead bổ sung để ngăn dirty read.

#### Lưu Trữ Đa Phiên Bản
- Các thay đổi chưa commit tạo ra các phiên bản tuple mới tại chỗ
- Các phiên bản này có `t_xmin` = transaction ID hiện tại (đang chạy)
- Snapshot của các transaction khác loại trừ các transaction ID đang chạy
- Kết quả: dirty read không thể xảy ra theo thiết kế, không tốn thêm chi phí

### Tại Sao Dirty Read Đặc Biệt Nguy Hiểm

#### 1. Hỏng Dữ Liệu Âm Thầm
Không giống crash hay lỗi tường minh, dirty read tạo ra **kết quả sai mà không có bất kỳ lỗi nào**. Application tiếp tục hoạt động bình thường với dữ liệu bị hỏng.

#### 2. Hiệu Ứng Lan Truyền (Cascading)
```
Dirty Read → Quyết định sai → Ghi DB sai → Càng nhiều dữ liệu bẩn hơn
```
Sự hỏng hóc lan truyền qua hệ thống, khiến việc debug cực kỳ khó khăn.

#### 3. Hành Vi Không Xác Định (Non-Deterministic)
Dirty read phụ thuộc vào thời gian (timing). Chúng có thể chỉ xảy ra dưới các pattern tải cụ thể, khiến gần như không thể tái hiện trong testing.

### Đào Sâu Vào SQL Server NOLOCK

```sql
SELECT * FROM accounts WITH (NOLOCK);
```

NOLOCK thực sự làm gì:
- Không lấy Shared (S) lock
- Không chặn khi có Exclusive (X) lock
- **Có thể đọc các dòng chưa commit từ các transaction đang bay (in-flight)**
- **Có thể đọc trùng dòng** (nếu xảy ra page split trong lúc scan)
- **Có thể bỏ sót dòng** (nếu scan theo thứ tự allocation và các trang di chuyển)

Trong thực tế, NOLOCK có thể trả về:
- Các dòng sau đó bị rollback
- Các dòng trùng lặp
- Các dòng bị thiếu
- Sự không nhất quán theo thứ tự allocation

### Bối Cảnh Lịch Sử

Các hệ thống cơ sở dữ liệu đời đầu (trước MVCC) sử dụng concurrency dựa trên lock:
- Reader lấy S-lock, writer lấy X-lock
- Xung đột S-lock với X-lock → reader bị chặn
- Để tránh bị chặn, một số hệ thống cung cấp Read Uncommitted
- Đây là một mẹo về hiệu năng, không phải một tính năng

Các hệ thống MVCC hiện đại (PostgreSQL, Oracle) đã làm cho sự đánh đổi này trở nên lỗi thời:
- Reader không bao giờ chặn writer
- Writer không bao giờ chặn reader
- Việc ngăn dirty read là miễn phí

### Khi Người Ta Nghĩ Rằng Họ Cần Dirty Read

**Kịch bản**: "Tôi cần đếm gần đúng nhanh, tôi không quan tâm đến độ chính xác"

**Các giải pháp thay thế tốt hơn:**
1. `SELECT reltuples FROM pg_class WHERE relname = 'table'` — ước tính của PostgreSQL
2. Materialized view được refresh định kỳ
3. Đếm từ read replica với độ trễ chấp nhận được
4. Các hệ thống phân tích bên ngoài (ClickHouse, Druid)

### Thực Tế Trong Production

**Đại đa số các hệ thống production không nên dùng Read Uncommitted.** Ngoại lệ duy nhất là các dashboard gần đúng và giám sát nội bộ. "Lợi ích về hiệu năng" là không đáng kể so với:
- Nguy cơ các quyết định nghiệp vụ bị hỏng
- Độ phức tạp khi debug
- Vi phạm tính toàn vẹn dữ liệu
- Các giải pháp thay thế hiện đại (read replica, caching)

Nếu bạn đang dùng PostgreSQL hoặc Oracle, bạn thậm chí không thể dùng nó — các cơ sở dữ liệu ngăn chặn nó ở cấp độ kiến trúc.

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Dirty Read — đọc dữ liệu chưa commit từ một transaction khác có thể ROLLBACK
- Chỉ có thể xảy ra ở level Read Uncommitted; tất cả các level khác đều cấm
- PostgreSQL và Oracle ngăn dirty read về mặt kiến trúc thông qua MVCC
- SQL Server dùng WITH (NOLOCK) cho dirty read, nhưng nó rủi ro (trùng lặp, bỏ sót)
- Dirty read đặc biệt nguy hiểm: application làm việc với dữ liệu "chưa từng tồn tại"
- MVCC ngăn dirty read miễn phí — reader luôn chỉ thấy các phiên bản đã commit

**Các câu hỏi phụ thường gặp:**
- Tại sao MVCC ngăn dirty read mà không tốn overhead? — Các thay đổi chưa commit tạo ra các phiên bản tuple với transaction ID đang chạy, vô hình với các snapshot khác
- Dirty read khác gì với non-repeatable read? — Dirty read = dữ liệu chưa commit, non-repeatable = đã commit nhưng thay đổi
- EvalPlanQual là gì? — Cơ chế của PostgreSQL để đánh giá lại WHERE khi có UPDATE đồng thời

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "NOLOCK là một cách tiếp cận bình thường cho production" — có thể đọc trùng và bỏ sót dòng
- "Dirty read = hiệu năng tốt hơn" — không có khác biệt trong các hệ thống MVCC
- "Đây là vấn đề hiếm gặp" — sự hỏng hóc lan truyền có thể thảm khốc
