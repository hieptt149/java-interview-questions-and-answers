# How does HashSet work internally? (HashSet hoạt động bên trong như thế nào?)

## 🟢 Junior Level

**HashSet dùng một HashMap bên trong!**

```java
// Bên trong HashSet:
private transient HashMap<E, Object> map;
private static final Object PRESENT = new Object();

public boolean add(E e) {
    return map.put(e, PRESENT) == null;
}
```

**Cách nó hoạt động:**
- Phần tử của bạn → key trong HashMap
- Value → cùng một đối tượng `PRESENT`
- Tính duy nhất → HashMap không cho phép các key trùng lặp

**Ví dụ:**
```java
HashSet<String> set = new HashSet<>();
set.add("A");
// Bên trong: map.put("A", PRESENT)

set.add("A");
// Bên trong: map.put("A", PRESENT) → đã tồn tại! → false
```

## 🟡 Middle Level

### Tại sao thông qua HashMap?

```
Các ưu điểm:
  → Chia sẻ code giữa HashMap và HashSet
  → Tất cả các cải tiến của HashMap tự động có trong HashSet
  → Java 8: Treeification — chuyển đổi danh sách liên kết thành một cây đỏ-đen khi có > 8 phần tử trong một bucket. Bảo vệ chống lại sự suy giảm O(1) → O(n) khi có va chạm hashCode (collision).
```

### Bộ nhớ

```
Mỗi phần tử trong HashSet:
  HashMap$Node:
    Header: 12 byte
    int hash: 4 byte
    K key: 4-8 byte (tham chiếu)
    V value: 4 byte (tham chiếu đến PRESENT)
    Node next: 4-8 byte
    Padding: tối đa 8 byte

Tổng: ~32 byte overhead cho mỗi phần tử!

→ HashSet<Long> lớn hơn long[] 8 lần
```

### Va chạm (Collision) và Java 8+

```
Ít va chạm (< 8 trong một bucket):
  → Danh sách liên kết
  → Tìm kiếm: O(n)

Nhiều va chạm (> 8, size > 64):
  → Cây đỏ-đen
  → Tìm kiếm: O(log n)

→ Bảo vệ chống lại các cuộc tấn công Hash DoS!
```

### Serialization

```java
// Trường map là transient (không được serialize trực tiếp). Lý do: hash table phụ thuộc vào hashCode() đặc thù của JDK và tính ngẫu nhiên hóa — khi deserialize trên một JVM khác, một phần tử có thể kết thúc ở một bucket khác. Thay vào đó, HashSet serialize các phần tử và xây dựng lại map.
```

### Bẫy: các phần tử mutable

```java
// ❌ Phần tử bị mất
Person p = new Person("Ivan");
set.add(p);
p.setName("Petr");  // hashCode() đã thay đổi!
set.remove(p);      // → FALSE! Tìm kiếm ở sai bucket

// ✅ Các phần tử bất biến (immutable)
record Person(String name) {}
```

---

### Khi nào KHÔNG dùng HashSet

1. **Cần thứ tự iterate** — hãy dùng LinkedHashSet
2. **Các phần tử có hashCode tệ** — bạn sẽ nhận được O(n) thay vì O(1) (nhiều va chạm)
3. **Lưu các kiểu nguyên thủy (primitive)** — hãy dùng fastutil/eclipse-collections để tiết kiệm 4 lần bộ nhớ

## 🔴 Senior Level

### Bảo vệ chống tấn công Hash DoS

```
Tấn công: kẻ xấu tạo ra các key có hashCode() giống hệt nhau
  → Tất cả đi vào cùng một bucket
  → Tìm kiếm O(n) thay vì O(1)
  → Server "treo"

Java 8+: Treeification khi có > 8 phần tử
  → Tìm kiếm O(log n) ngay cả khi bị tấn công
  → Hàm hash có tính ngẫu nhiên hóa
```

### Đào sâu về Bộ nhớ

```
HashSet<String> cho 1 triệu chuỗi:

1 triệu HashMap$Node: 32 MB
1 triệu đối tượng String: ~40 MB
1 triệu mảng char[]: ~24 MB
Mảng table của HashMap: ~4 MB

Tổng: ~100 MB

→ ArrayList<String>: ~68 MB
→ HashSet lớn hơn 50%!
```

### Đánh đổi của Load Factor

```
Mặc định: 0.75

Tăng lên (0.9):
  → Ít bộ nhớ hơn
  → Nhiều va chạm hơn
  → Tìm kiếm chậm hơn

Giảm xuống (0.5):
  → Nhiều bộ nhớ hơn
  → Ít va chạm hơn
  → Tìm kiếm nhanh hơn
```

### Các giải pháp thay thế cho kiểu nguyên thủy

```java
// ❌ HashSet<Long> cho 100 triệu phần tử
// → 100 triệu đối tượng Node → 3.2 GB!

// ✅ fastutil (open addressing)
LongOpenHashSet set = new LongOpenHashSet();
// → Không có đối tượng Node → 800 MB
// → Ít bộ nhớ hơn 4 lần!
```

### Cấu trúc bên trong

```
HashSet → AbstractSet → AbstractCollection

Ủy thác (Delegation):
  add(e)         → map.put(e, PRESENT)
  remove(e)      → map.remove(e) == PRESENT
  contains(e)    → map.containsKey(e)
  size()         → map.size()
  iterator()     → map.keySet().iterator()
  clear()        → map.clear()

→ HashSet = lớp bọc mỏng bên trên keySet!
```

### Kinh nghiệm Production

**Tình huống thực tế: hashCode tệ**
- Các đối tượng có hashCode() = 0 cho tất cả
- Tất cả nằm trong một bucket → tìm kiếm O(n)
- 100,000 phần tử → 5 giây cho contains!
- Giải pháp: viết lại hashCode()
- Kết quả: 0.1 ms

### Best Practices

1. **Các phần tử phải bất biến trên thực tế (effectively immutable)** khi còn nằm bên trong Set. Thay đổi một phần tử sau khi thêm vào sẽ phá vỡ hợp đồng hashCode/equals — phần tử trở nên "vô hình" đối với tìm kiếm.
2. **Hợp đồng hashCode/equals** — cực kỳ quan trọng
3. **initialCapacity** — tránh các lần resize
4. **fastutil** cho các kiểu nguyên thủy
5. **Treeification** → chỉ báo của hashCode tệ
6. **Serialization** — tùy chỉnh, không phải chuẩn

### Tóm tắt cho Senior

- **HashSet** = lớp bọc bên trên HashMap.keySet()
- **PRESENT** = placeholder static final Object
- **Bộ nhớ** = ~32 byte overhead cho mỗi phần tử
- **Treeification** = bảo vệ Hash DoS (> 8)
- **Transient map** = serialization tùy chỉnh
- **Các phần tử mutable** = mất dữ liệu!
- **Open addressing** = ít bộ nhớ hơn (fastutil)

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- HashSet bên trong là một lớp bọc bên trên HashMap.keySet(), mỗi phần tử = key, value = static final Object PRESENT
- Độ phức tạp: O(1) cho add/remove/contains trung bình
- Java 8+: treeification khi có > 8 phần tử trong một bucket — danh sách liên kết chuyển thành cây đỏ-đen (O(log n))
- Memory overhead: ~32 byte cho mỗi phần tử (HashMap$Node: hash, key, value, next)
- Load factor mặc định 0.75 — cân bằng giữa bộ nhớ và va chạm
- Serialization tùy chỉnh: trường map = transient, các phần tử được serialize riêng
- Các phần tử mutable phá vỡ tìm kiếm — hashCode() thay đổi, phần tử bị "mất"
- Với các kiểu nguyên thủy, fastutil/Trove tốt hơn — open addressing, ít bộ nhớ hơn 4 lần

**Các câu hỏi phụ thường gặp:**
- **Tại sao HashSet dùng HashMap thay vì cấu trúc riêng của nó?** — Tái sử dụng code, tất cả các tối ưu hóa của HashMap tự động có sẵn.
- **Treeification là gì và tại sao cần đến nó?** — Khi có > 8 va chạm trong một bucket, danh sách chuyển thành cây — bảo vệ chống các cuộc tấn công Hash DoS (O(n) → O(log n)).
- **Tại sao serialization là tùy chỉnh?** — Hash table phụ thuộc vào hashCode() đặc thù của JVM và tính ngẫu nhiên hóa — khi deserialize, các phần tử có thể kết thúc ở các bucket khác nhau.
- **Làm sao giảm memory footprint của HashSet cho các kiểu nguyên thủy?** — Dùng fastutil LongOpenHashSet và tương tự — không có đối tượng Node, open addressing.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "HashSet lưu các phần tử trực tiếp" — nó lưu chúng như là các key của HashMap với một placeholder PRESENT
- ❌ "HashSet hoàn toàn thread-safe" — không, bạn cần ConcurrentHashMap hoặc Collections.synchronizedSet
- ❌ "HashSet đảm bảo thứ tự iterate" — thứ tự không được đảm bảo, phụ thuộc vào hashCode()
- ❌ "Treeification luôn xảy ra khi có va chạm" — chỉ khi có > 8 phần tử VÀ size > 64
