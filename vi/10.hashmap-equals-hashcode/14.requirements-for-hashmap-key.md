# What Are the Requirements for a HashMap Key? (Các yêu cầu đối với một key của HashMap là gì?)

## 🟢 Junior Level

Một key của HashMap phải tuân theo một số quy tắc quan trọng:

1. **Override equals() và hashCode()** — cả hai method phải hoạt động cùng nhau
2. **Là immutable** — sau khi tạo, key không được thay đổi
3. **Trả về cùng hashCode ở các lời gọi lặp lại** — nếu các field không đổi

**Các key tốt:**
```java
String key = "userId";           // Key lý tưởng
Integer id = 42;                 // Cũng tuyệt vời
record Key(String name) {}       // Java 14+ — tự động immutable
```

**Các key tồi:**
```java
StringBuilder key = new StringBuilder("userId"); // Mutable!
List<String> listKey = new ArrayList<>();         // Có thể bị sửa đổi
```

## 🟡 Middle Level

### Các yêu cầu chính

| Yêu cầu                   | Mô tả                                            | Hệ quả của việc vi phạm               |
| ------------------------- | ------------------------------------------------ | ------------------------------------- |
| Contract equals/hashCode  | Nếu `equals()` = true, thì `hashCode()` giống nhau | Các phần tử bị mất trong map        |
| Tính bất biến             | Các field của key không được thay đổi            | "Key bị vỡ", rò rỉ bộ nhớ            |
| Consistency               | Các lời gọi lặp lại cho cùng kết quả             | Hành vi không dự đoán được            |
| Phân bố chất lượng        | hashCode nên phân bố các key đều                 | Va chạm, suy giảm hiệu năng           |

### Tại sao String là key lý tưởng

1. Immutable theo thiết kế
2. Cache hashCode của nó
3. Implement `Comparable`
4. Phân bố hashCode tốt

### Các anti-pattern

```java
// Anti-pattern 1: hashCode phụ thuộc thời gian
@Override public int hashCode() { return System.currentTimeMillis(); }

// Anti-pattern 2: hashCode phụ thuộc các số ngẫu nhiên
@Override public int hashCode() { return new Random().nextInt(); }

// Anti-pattern 3: URL làm key (thực hiện các request mạng trong equals)
Map<URL, Data> map = new HashMap<>(); // Rất chậm!
```

### Hỗ trợ Comparable

Nếu key implement `Comparable<K>`, HashMap dùng `compareTo()` thay vì `tieBreakOrder()` cho việc cân bằng cây khi va chạm (Java 8+). Cách này nhanh hơn, vì `compareTo()` làm việc với nội dung của object, trong khi `tieBreakOrder()` cần tính toán bổ sung qua `System.identityHashCode()`.

## 🔴 Senior Level

### Các yêu cầu chính thức

Từ tài liệu của `Map`:
> Hành vi của một map không được xác định nếu giá trị của một object dùng làm key bị thay đổi theo cách ảnh hưởng đến các so sánh equals.

### Contract Consistency

Các method `equals()` và `hashCode()` phải **consistent**:
- Không được phụ thuộc vào các resource bên ngoài (mạng, file system)
- Không được dùng các giá trị ngẫu nhiên/thời gian
- `URL.equals()` — một ví dụ vi phạm kinh điển: thực hiện các request DNS, block khi mạng lỗi

### Bên trong: Comparable cho Treeification

Khi treeification bucket:
```java
// Nếu key instanceof Comparable:
//   compareTo() được dùng cho cân bằng cây
// Nếu không:
//   tieBreakOrder() qua System.identityHashCode() — chậm hơn
```

Implement `Comparable` tăng tốc đáng kể việc cân bằng cây, vì `compareTo()` làm việc với nội dung của object, trong khi `tieBreakOrder()` cần tính toán bổ sung.

### Hệ quả về bộ nhớ

- Mỗi entry = object Node (~32-48 byte) + key + value
- Các String literal từ String Pool — tiết kiệm bộ nhớ, vì các literal giống hệt tham chiếu cùng một object. Điều này KHÔNG áp dụng cho `new String(...)`.
- Các key Record — gọn nhẹ, nhưng cần Java 14+

### Các trường hợp biên (Edge Case)

1. **null key**: Được cho phép (một cái), luôn ở `table[0]`. Trong các hệ thống lớn — anti-pattern
2. **Enum làm key**: Lựa chọn lý tưởng — EnumMap. Nó nhanh hơn vì dùng một mảng với ordinal() làm chỉ số — O(1) không cần hashCode hay va chạm.
3. **Mảng làm key**: `equals()` so sánh các tham chiếu, không phải nội dung. Dùng một wrapper

### Bảo mật

Các key có thể là một vector tấn công:
- Hash Flooding: tạo các key có cùng hashCode
- DoS qua `equals()` nặng (so sánh dữ liệu lớn)
- Các tấn công side-channel qua phân tích timing của `equals()`

### Best Practices

1. **Record** cho các key phức tạp (Java 14+)
2. **Các field final** — mức tối thiểu bạn có thể làm
3. **Defensive copy** trong constructor và các getter
4. **Đừng dùng các collection mutable** làm key
5. **Giảm thiểu các field** trong equals/hashCode — chỉ các định danh

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Contract equals/hashCode: nếu equals = true, hashCode giống nhau
- Tính bất biến: các field của key không được thay đổi sau khi tạo
- Consistency: các lời gọi hashCode lặp lại = cùng kết quả
- Phân bố chất lượng: hashCode nên phân bố các key đều
- String — key lý tưởng: immutable, cache hashCode, implement Comparable
- Hỗ trợ Comparable tăng tốc treeification (compareTo thay vì tieBreakOrder)

**Các câu hỏi phụ thường gặp:**
- **Tại sao URL là một key tồi?** — equals() thực hiện các request DNS, vi phạm consistency
- **Một mảng có thể là key không?** — không, equals so sánh các tham chiếu; dùng một wrapper
- **Tại sao EnumMap nhanh hơn HashMap?** — mảng với ordinal() làm chỉ số, O(1) không cần hashCode
- **null có thể là key không?** — có, một cái, nhưng trong các hệ thống lớn — anti-pattern

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Key mutable là ổn nếu bạn không thay đổi nó" — quyết định mong manh
- "hashCode có thể phụ thuộc thời gian" — không, vi phạm consistency
- "Bất kỳ object nào cũng hoạt động làm key" — không, phải tuân theo contract
