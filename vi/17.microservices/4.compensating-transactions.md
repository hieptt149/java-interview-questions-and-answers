# What are compensating transactions (Compensating transaction là gì)

## Junior Level

Một **compensating transaction** là một hành động **hoàn tác** kết quả của một transaction thành công trước đó trong một Saga.

**Quan trọng:** transaction gốc đã được commit và hiển thị với các bên khác. Một compensation
không phải là ROLLBACK — đó là một transaction mới làm điều ngược lại.

Trong microservices bạn không thể `ROLLBACK` như trong một database thông thường. Thay vào đó, bạn cần **hoàn tác thủ công** mỗi bước.

```
Saga:
1. ✅ Tạo đơn hàng
2. ✅ Tính phí
3. ❌ Giữ chỗ sản phẩm (THẤT BẠI!)

Các compensating transaction (theo thứ tự ngược lại):
2. ✅ Hoàn tiền (compensation cho bước 2)
1. ✅ Hủy đơn hàng (compensation cho bước 1)
```

---

## Middle Level

### Các Quy Tắc Của Compensating Transaction

**1. Thực thi theo thứ tự ngược lại:**
```
Các bước: A -> B -> C -> D (thất bại)
Compensation: compensate(C) -> compensate(B) -> compensate(A)
```

**2. Phải idempotent:**
```java
public void refundPayment(String paymentId) {
    if (paymentRepository.isRefunded(paymentId)) {
        return;  // Đã hoàn tiền rồi — không làm gì
    }
    paymentRepository.refund(paymentId);
    paymentRepository.markRefunded(paymentId);
}
```

**3. Có thể không phải là đối lập chính xác:**
```
// Bước: "Giữ chỗ sản phẩm"
// Compensation: KHÔNG phải "xóa việc giữ chỗ", mà là "đặt status thành available"

// Bước: "Gửi email"
// Compensation: KHÔNG phải "xóa email", mà là "gửi email hủy"
```

### Các Lỗi Thường Gặp

1. **Thiếu compensation:**
```
Order -> Payment -> Inventory (thất bại)
Compensation: refund(Payment) ... quên cancel(Order)!
Kết quả: đơn hàng được tạo, tiền được hoàn, nhưng đơn hàng không bị hủy
```

## Senior Level

### Đánh Đổi Kiến Trúc

**Semantic compensation vs technical undo:**
```
Technical undo = DELETE khỏi table.
Semantic compensation = gửi email cho khách hàng "đơn hàng của bạn đã bị hủy" + tặng điểm thưởng.

Semantic tốt hơn cho nghiệp vụ, nhưng phức tạp hơn để triển khai
```

### Edge Cases

**1. Thất bại của compensation:**
```java
// Nếu compensation cũng thất bại — retry
// Ví dụ đơn giản hóa — trong production hãy thêm exponential backoff và jitter.
// Một retry vòng lặp đơn giản có thể làm quá tải một service đang lỗi.
public void compensateWithRetry(SagaStep step, int maxRetries) {
    for (int i = 0; i < maxRetries; i++) {
        try {
            step.compensate();
            return;
        } catch (Exception e) {
            log.warn("Compensation retry {}", i, e);
        }
    }
    // Sau tất cả các lần retry — can thiệp thủ công
    alertService.sendAlert("Compensation failed after retries", step);
}
```

**2. Các bước không thể compensate:**
```
Một số bước không thể hoàn tác:
- Email đã gửi — không thể "lấy lại"
- SMS đã gửi — không thể hủy
- Sản phẩm vật lý đã được gửi đi

Giải pháp: đánh dấu là non-compensatable và alert để sửa thủ công
```

### Kinh Nghiệm Production

**Saga với các compensation:**
```java
public class OrderSaga {

    public void onPaymentFailed(PaymentFailedEvent event) {
        // Các compensation theo thứ tự ngược lại
        compensateInventory(event.orderId());
        compensateOrder(event.orderId());
    }

    private void compensateInventory(String orderId) {
        try {
            inventoryClient.releaseReservation(orderId);
        } catch (Exception e) {
            log.error("Inventory compensation failed", e);
            alertService.sendAlert("Inventory compensation failed", orderId);
            // Retry hoặc can thiệp thủ công
        }
    }

    private void compensateOrder(String orderId) {
        try {
            orderClient.cancelOrder(orderId);
        } catch (Exception e) {
            log.error("Order compensation failed", e);
            alertService.sendAlert("Order compensation failed", orderId);
        }
    }
}
```

### Best Practices

```
✅ Compensation theo thứ tự ngược lại
✅ Idempotency cho mỗi compensation
✅ Retry cho các compensation
✅ Alert khi compensation thất bại
✅ Ghi log mỗi bước compensation

❌ Đừng quên các compensation
❌ Đừng bỏ qua các thất bại của compensation
❌ Đừng giả định compensation sẽ luôn hoạt động
```

## Interview Cheat Sheet

**Cần phải biết:**
- Một compensating transaction KHÔNG phải là ROLLBACK — đó là một transaction mới với hành động ngược lại
- Các compensation được thực thi theo thứ tự ngược lại (C->B->A)
- Mỗi compensation phải idempotent
- Semantic compensation tốt hơn technical undo (email hủy vs DELETE)
- Một số bước không thể compensate (email đã gửi, sản phẩm đã gửi đi)
- Khi compensation thất bại — retry + alert để can thiệp thủ công
- Compensation có thể không phải là đối lập chính xác của bước gốc

**Các câu hỏi phụ thường gặp:**
- **Điều gì nếu compensation cũng thất bại?** Retry với exponential backoff, sau đó alert để sửa thủ công.
- **Những bước nào không thể hoàn tác?** Gửi email/SMS, gửi sản phẩm thực tế — đánh dấu là non-compensatable.
- **Tại sao idempotency cần thiết cho compensation?** Một compensation có thể được gọi hai lần (retry, event trùng lặp).
- **Semantic vs technical compensation?** Technical = DELETE khỏi table, semantic = tặng điểm thưởng + thông báo cho khách hàng.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Compensation = ROLLBACK" — không, transaction gốc đã được commit rồi
- "Compensation luôn khả thi" — không, bạn không thể "lấy lại" một email
- "Bạn có thể compensate theo bất kỳ thứ tự nào" — không, nghiêm ngặt theo thứ tự ngược lại
- "Idempotency không quan trọng cho compensation" — cực kỳ quan trọng
