# What is Composition and Inheritance (Composition và Inheritance là gì)

## 🟢 Junior Level

**Composition và inheritance** là hai cách chính để tổ chức các mối liên hệ giữa các class trong OOP. **Inheritance** tạo ra một mối quan hệ "is-a" (IS-A): một class trở thành một trường hợp đặc biệt của class khác. **Composition** tạo ra một mối quan hệ "has-a" (HAS-A): một object chứa một object khác như một phần.

**Analogy đơn giản:** Inheritance — giống như kế thừa các đặc điểm từ cha mẹ (bạn _là_ một con người). Composition — giống như mua một chiếc điện thoại (bạn _có_ một chiếc điện thoại, có thể thay thế nó).

**Ví dụ inheritance (IS-A):**
```java
public class Animal {
    public void eat() { System.out.println("Eating..."); }
}

public class Dog extends Animal {  // Dog IS-A Animal
    public void bark() { System.out.println("Woof!"); }
}
```

**Ví dụ composition (HAS-A):**
```java
public class Engine {
    public void start() { System.out.println("Engine started"); }
}

public class Car {
    private final Engine engine;  // Car HAS-A Engine

    public Car(Engine engine) {
        this.engine = engine;
    }

    public void start() {
        engine.start();  // Delegation
    }
}
```

**Khi nào dùng:**
- **Inheritance**: khi có một hierarchy loại thực sự (Dog IS-A Animal)
- **Composition**: trong hầu hết các trường hợp khác — đó là cách tiếp cận linh hoạt hơn

## 🟡 Middle Level

### Cách Hoạt Động

**Inheritance** triển khai mối quan hệ **"is-a" (IS-A)** và dùng virtual method table (VTable) ở cấp độ JVM. Subclass nhận được quyền truy cập vào các trường `protected` của parent — đây là "white-box reuse".

**Composition** triển khai mối quan hệ **"has-a" (HAS-A)** thông qua các lệnh gọi phương thức trên một object khác. Tương tác chỉ thông qua public interface — đây là "black-box reuse".

White-box reuse — nội bộ parent hiển thị (inheritance). Black-box reuse — chỉ public interface (composition).
Devirtualization — JIT thay thế virtual call bằng direct. Monomorphic = một loại call → inlining. Megamorphic = 3+ loại → table lookup.

### Ứng Dụng Thực Tế

**Tại sao Effective Java nói "Ưu tiên Composition hơn Inheritance":**

| Tiêu chí         | Inheritance                          | Composition              |
| ----------------- | ------------------------------------ | ------------------------ |
| **Coupling**      | Tĩnh (compile-time)                | Động (runtime)        |
| **Encapsulation** | Bị phá vỡ (các trường protected hiển thị)     | Được bảo toàn                |
| **Linh hoạt**   | Không thể thay đổi parent                 | Có thể thay đổi component      |
| **Khả năng test**   | Khó mock                         | Dễ thay thế bằng mock  |
| **Tính dễ vỡ**     | Thay đổi parent phá vỡ tất cả subclass  | Các thay đổi được cô lập                |

### Các Lỗi Thường Gặp

| Lỗi                                          | Giải pháp                                |
| ------------------------------------------------ | ---------------------------------------- |
| Inheritance để tái sử dụng code                       | Dùng composition + delegation            |
| Hierarchy sâu (5+ cấp)                       | Refactor hướng về composition             |
| `ArrayList` → `MySpecialList` thông qua inheritance    | `MySpecialList` với một trường `List` bên trong |

### Các Lựa Chọn Thay Thế Cho Inheritance

1. **Strategy**: thay vì `SmsNotification extends Notification` → `NotificationService` với một trường `SenderStrategy`
2. **Decorator**: bọc một object để thêm chức năng (logging, caching)
3. **Delegation**: một class triển khai một interface nhưng gọi các phương thức delegate

### Khi Nào KHÔNG Nên Dùng Composition

- Các hierarchy loại sạch (ngoại lệ: `IOException` → `SocketException`)
- Các framework với pattern Template Method
- Khi cần polymorphism và làm việc thông qua một base type chung

**Template Method vs Strategy:**
Template Method = bạn kiểm soát thuật toán, các subclass kiểm soát các bước. Strategy = client chọn toàn bộ thuật toán. Template Method — khi khung thuật toán ổn định. Strategy — khi toàn bộ thuật toán có thể thay đổi.

## 🔴 Senior Level

### Triển Khai Nội Bộ Ở Cấp Độ JVM

**Inheritance và VTable:**
Khi gọi một virtual method, JVM dùng một virtual method table (VTable). Mỗi class có VTable riêng của nó với các con trỏ đến các triển khai phương thức. Với các hierarchy sâu (5+ cấp), khó hơn cho JIT compiler thực hiện **devirtualization** và **inlining**.

```java
// Inheritance: invokevirtual, VTable lookup
class Parent { void foo() {} }
class Child extends Parent { @Override void foo() {} }
// parent.foo() → invokevirtual → VTable lookup

// Composition với final: JIT có thể inline
class Service {
    private final Delegate delegate;  // final → monomorphic call
    void execute() { delegate.run(); } // JIT inline → direct call
}
```

### Đánh Đổi Kiến Trúc

**Inheritance:**
- ✅ Ưu điểm: Polymorphism sẵn có, tái sử dụng code, Template Method
- ❌ Nhược điểm: Fragile base class, rò rỉ triển khai, coupling tĩnh

**Composition:**
- ✅ Ưu điểm: Hành vi động, khả năng test (dễ mock), coupling lỏng lẻo
- ❌ Nhược điểm: Nhiều boilerplate code hơn (delegation), nhiều object hơn trên heap

### Edge Cases

1. **Vấn Đề Fragile Base Class**: thay đổi `addAll` trong parent, cái gọi `add`, phá vỡ subclass đã override cả hai phương thức
   - **Giải pháp**: Composition + Forwarding
   - Đây là một chi tiết triển khai của HashSet: addAll gọi add nội bộ. Nhưng bạn không thể dựa vào điều này — trong một triển khai khác nó có thể khác. Đó là lý do tại sao inheritance từ các class không được thiết kế cho nó là dễ vỡ.

2. **Shared State Trong Composition**: nhiều delegate làm việc với dữ liệu chung
   - **Giải pháp**: Truyền context rõ ràng hoặc State Object

3. **Circular Delegation**: A → B → A → StackOverflowError
   - **Giải pháp**: Phân tích kiến trúc, các quy tắc ArchUnit

### Hiệu Năng

| Metric               | Inheritance                        | Composition                      |
| -------------------- | ---------------------------------- | --------------------------------- |
| **Kích thước object**      | Tất cả trường parent trong một object    | Các object riêng biệt + header       |
| **Lệnh gọi phương thức**      | invokevirtual (VTable lookup)      | invokevirtual + có thể inline|
| **Tối ưu JIT** | Khó hơn với hierarchy sâu         | Dễ hơn với các trường final      |
| **Bộ nhớ**           | ~16 byte header + tất cả trường          | ~16 byte × N object + tham chiếu     |

- **Inlining**: JIT dễ dàng inline các delegate `final` → overhead ~0
- **VTable**: Ở độ sâu 5+ cấp, các megamorphic call → deoptimization

### Thread Safety

- **Inheritance**: `synchronized` trên phương thức parent khóa toàn bộ object
- **Composition**: Các lock khác nhau có thể dùng cho các delegate khác nhau → concurrency chi tiết hơn

### Kinh Nghiệm Production

**Refactoring trong một dự án enterprise:**
`NotificationService` với 2000 dòng và các subclass `EmailNotification`, `SmsNotification`, `PushNotification`. Vấn đề: thêm một strategy mới yêu cầu thay đổi base class.

Refactoring: trích xuất interface `NotificationStrategy`, mỗi loại — một triển khai riêng biệt. `NotificationService` trở thành một coordinator. **Kết quả**: các loại mới được thêm mà không sửa đổi code hiện có (OCP).

### Monitoring

**Các quy tắc ArchUnit:**
```java
@ArchTest
static void no_deep_inheritance = classes()
    .should().notHaveSimpleNameMatching(".*Impl.*")
    .andShould().haveLessThanNAncestors(3);
```

**SonarQube**: Depth of Inheritance Hierarchy > 5 → Code Smell

### Best Practices Cho Highload

- **Delegate final** để inline tốt hơn
- **Package-private** cho các component nội bộ
- **Sealed class** (Java 17+) cho inheritance có kiểm soát

> Sealed class khả dụng từ Java 17. Với Java 8/11, hãy dùng các class `final` và ghi chép class nào được dùng để kế thừa.
- **Composition over Inheritance** như lựa chọn mặc định

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- Inheritance = IS-A (coupling tĩnh, white-box reuse), Composition = HAS-A (động, black-box)
- "Favor Composition over Inheritance" — Effective Java, Josh Bloch
- Composition bảo toàn encapsulation, inheritance phá vỡ nó (các trường `protected` hiển thị)
- JIT dễ dàng inline các delegate `final` → overhead composition ~0
- Inheritance: fragile base class, rò rỉ triển khai, coupling tĩnh
- Fragile Base Class: thay đổi `addAll` trong parent phá vỡ subclass đã override `add`
- Sealed class (Java 17+) cho inheritance có kiểm soát

**Các câu hỏi phụ thường gặp:**
- **Tại sao composition tốt hơn?** — Thay thế component động, khả năng test (dễ mock), coupling lỏng lẻo
- **Khi nào inheritance chấp nhận được?** — IS-A thực sự, các framework với Template Method, các trường hạ tầng chung (`BaseEntity`)
- **Devirtualization là gì?** — JIT thay thế virtual call bằng direct call khi nó biết loại chính xác
- **Overhead VTable với inheritance?** — 5+ cấp → megamorphic call → JIT deoptimization

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Inheritance là cách tốt nhất để tái sử dụng code" (nguyên nhân chính của tính dễ vỡ)
- "Hierarchy sâu là dấu hiệu của thiết kế tốt" (5+ cấp — code smell)
- "Composition luôn tốt hơn" (có các trường hợp inheritance hợp lệ: Template Method, IS-A)
