# What is CopyOnWriteArrayList? (CopyOnWriteArrayList là gì?)

## 🟢 Junior Level

**CopyOnWriteArrayList** là một list thread-safe **sao chép mảng ở mỗi lần ghi**.

**Ví dụ minh họa đơn giản:** Một bức ảnh. Người đọc nhìn vào một bức ảnh (phiên bản cũ), trong khi tác giả chụp một bức ảnh mới (một bản sao có các thay đổi).

```java
List<String> list = new CopyOnWriteArrayList<>();

// Đọc: nhanh, không có khóa.
// volatile Object[] array → get() = đọc đơn giản từ mảng, không có thao tác nguyên tử hay synchronized.
String s = list.get(0);

// Ghi: tạo một bản sao của mảng
list.add("A");  // Sao chép → thêm → thay thế
```

**Khi nào dùng:**
- Nhiều đọc, ít ghi
- Các danh sách listener

## 🟡 Middle Level

### Cách nó hoạt động

```java
// Bên trong: volatile Object[] array

// Đọc (get):
return array[index];  // Không có khóa!

// Ghi (add):
1. Lock
2. newArray = Arrays.copyOf(array, size + 1)
3. newArray[size] = element
4. array = newArray  // ghi volatile
5. Unlock
```

### Iterator = Snapshot

```java
List<String> list = new CopyOnWriteArrayList<>();
list.add("A");

Iterator<String> it = list.iterator();  // Snapshot!
list.add("B");  // Đã sửa đổi list

it.next();  // → "A" (iterator KHÔNG nhìn thấy "B"!)
// → Fail-Safe, không bao giờ ném Exception

// it.remove() → UnsupportedOperationException!
```

### Khi nào dùng

```java
// ✅ Các danh sách listener
List<Listener> listeners = new CopyOnWriteArrayList<>();

// Các lần đọc (thông báo) >>> các lần ghi (đăng ký)
for (Listener l : listeners) {  // Nhanh!
    l.onEvent();
}

// ✅ Các cache hiếm khi thay đổi
```

### Khi nào KHÔNG dùng

```java
// ❌ Ghi thường xuyên
list.add(e);  // Sao chép mảng mỗi lần!
// → O(n) cho mỗi lần ghi
// → Bộ nhớ tạm thời tăng gấp đôi

// ✅ Các giải pháp thay thế:
ConcurrentLinkedQueue<String> queue;
Collections.synchronizedList(list);

**Sự khác biệt then chốt:** synchronizedList chặn mọi lần đọc, COWAL thì không. Iterator của synchronizedList ném CME khi có sửa đổi, COWAL — không (snapshot).
```

## 🔴 Senior Level

### Memory Footprint

```java
// Khi ghi:
oldArray: 1 triệu phần tử → 4 MB
newArray: 1 triệu + 1 → 4 MB
// → 8 MB tạm thời!

// Với các list lớn → nguy cơ OOM
// → Áp lực GC khi ghi thường xuyên
```

### Đảm bảo Happens-Before

```java
// volatile array = Happens-Before
// Ghi trong một luồng → nhìn thấy được bởi tất cả trong các luồng khác

// Nhưng: cửa sổ giữa việc sao chép và ghi
// → Người đọc có thể nhìn thấy dữ liệu "cũ" (stale)
```

### Vấn đề Stale Data

- **Fail-Safe** = iterator không bao giờ ném ConcurrentModificationException (làm việc trên một bản sao)
- **Stale Data** = "dữ liệu lỗi thời" — người đọc nhìn thấy phiên bản mảng từ thời điểm iterator được tạo
- **Eventual Consistency** = dữ liệu sẽ trở nên hiện hành không phải ngay lập tức, mà sau lần ghi tiếp theo

```java
// Luồng 1: đọc array (phiên bản cũ)
// Luồng 2: sao chép, sửa đổi, ghi array mới
// Luồng 1: vẫn đọc array cũ

→ Tính nhất quán là eventual (cuối cùng), không phải strong (mạnh)!
```

### Các hạn chế của Iterator

```java
// Fail-Safe:
// → Không bao giờ ConcurrentModificationException
// → Nhưng: không nhìn thấy các thay đổi sau khi tạo

// Các phương thức của Iterator:
it.remove()  // → UnsupportedOperationException!
it.add()     // → UnsupportedOperationException!
it.set()     // → UnsupportedOperationException!
```

### Kinh nghiệm Production

**Tình huống thực tế: Danh sách listener**
```java
// Event Bus: 1000 subscriber
// Thông báo: 100,000/giây
// Subscribe/unsubscribe: 1/giây

// Tỉ lệ 100,000 lần đọc trên 1 lần ghi → sao chép mảng (O(n)) xảy ra 1 lần trên 100,000 thao tác → overhead là không đáng kể.

CopyOnWriteArrayList:
  → Đọc: O(1), lock-free
  → Ghi: O(n), nhưng hiếm!
  → Hoàn toàn phù hợp!
```

### Best Practices

1. **Chủ yếu** cho các kịch bản nặng về đọc (read-heavy). Chấp nhận được cho các collection nhỏ (< 100) ngay cả khi ghi ở mức độ vừa phải.
2. **Các danh sách listener** — trường hợp sử dụng lý tưởng
3. **Tránh** khi ghi thường xuyên
4. **Iterator = snapshot**, không phải view sống
5. **Memory spike** khi ghi → nguy cơ OOM
6. **Stale data** — có chấp nhận được cho kịch bản của bạn không?
7. **Các giải pháp thay thế:** ConcurrentLinkedQueue, synchronizedList

### Tóm tắt cho Senior

- **Copy-On-Write** = sao chép mảng khi ghi
- **Đọc** = O(1), lock-free, volatile array
- **Ghi** = O(n), sao chép + thay thế
- **Iterator** = snapshot, fail-safe
- **Bộ nhớ** = tạm thời tăng gấp đôi khi ghi
- **Listener** = trường hợp sử dụng lý tưởng
- **Stale data** = eventual consistency
- **Tránh** cho các kịch bản nặng về ghi

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- CopyOnWriteArrayList — ở mỗi lần ghi (add/set/remove), tạo một bản sao của mảng nội bộ, các lần đọc là lock-free thông qua volatile
- Đọc = O(1), không có khóa. Ghi = O(n), sao chép mảng + thay thế + lock
- Iterator = snapshot tại thời điểm tạo, fail-safe (không ném CME), không nhìn thấy các thay đổi sau khi tạo
- Iterator KHÔNG hỗ trợ remove/add/set — UnsupportedOperationException
- Trường hợp sử dụng lý tưởng: các danh sách listener — tỉ lệ đọc-trên-ghi là 100,000:1
- Bộ nhớ: tạm thời tăng gấp đôi bộ nhớ khi ghi (oldArray + newArray) — nguy cơ OOM cho các list lớn
- Đảm bảo Happens-Before thông qua volatile array, nhưng eventual consistency — người đọc có thể nhìn thấy dữ liệu cũ
- Các giải pháp thay thế cho write-heavy: ConcurrentLinkedQueue, Collections.synchronizedList

**Các câu hỏi phụ thường gặp:**
- **Tại sao iterator không nhìn thấy các phần tử được thêm vào?** — Iterator làm việc trên một snapshot (một bản sao của mảng tại thời điểm tạo). Các phần tử mới được thêm vào một mảng mới — snapshot không nhìn thấy chúng.
- **COWAL khác synchronizedList như thế nào?** — synchronizedList chặn MỌI lần đọc. COWAL không chặn các lần đọc. Iterator của synchronizedList ném CME khi có sửa đổi, COWAL — không (snapshot).
- **Khi nào COWAL là một lựa chọn tệ?** — Khi ghi thường xuyên: mỗi lần ghi = sao chép toàn bộ mảng. Với 1 triệu phần tử = sao chép 4 MB + bộ nhớ tạm thời tăng gấp đôi.
- **Eventual consistency trong COWAL là gì?** — Một luồng đọc mảng cũ, một luồng khác ghi một mảng mới. Người đọc sẽ nhìn thấy dữ liệu mới không phải ngay lập tức, mà chỉ sau lần tham chiếu tiếp theo đến mảng.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "COWAL chặn các lần đọc" — không, các lần đọc hoàn toàn lock-free thông qua volatile
- ❌ "Iterator của COWAL hiển thị dữ liệu sống" — nó là một snapshot, không nhìn thấy các thay đổi sau khi tạo
- ❌ "COWAL phù hợp cho việc ghi thường xuyên" — O(n) cho mỗi lần ghi + bộ nhớ tăng gấp đôi, hãy dùng ConcurrentLinkedQueue thay thế
- ❌ "Iterator của COWAL hỗ trợ remove()" — không, UnsupportedOperationException cho tất cả các sửa đổi
