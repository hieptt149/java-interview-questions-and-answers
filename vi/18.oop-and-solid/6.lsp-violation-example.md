# Give an Example of Liskov Substitution Principle Violation (Cho một ví dụ về vi phạm Liskov Substitution Principle)

## 🟢 Junior Level

Các vi phạm LSP thường được ngụy trang thành "tái sử dụng code". Chúng ta cố kế thừa một class từ class khác đơn giản vì chúng có chung các trường, bỏ qua sự khác biệt trong hành vi của chúng.

**Ví dụ 1: Subclass "Lười Biếng"**
Khi một subclass override phương thức của parent và ném exception hoặc không làm gì cả.

```java
// Xấu: subclass không hỗ trợ phương thức của parent
public class Bird {
    public void fly() {
        System.out.println("Flying!");
    }
}

public class Penguin extends Bird {
    @Override
    public void fly() {
        throw new UnsupportedOperationException("Penguins don't fly!");
    }
}

// Sẽ hỏng:
public void letBirdsFly(List<Bird> birds) {
    for (Bird bird : birds) {
        bird.fly(); // UnsupportedOperationException cho Penguin!
    }
}
```

**Ví dụ 2: Rectangle và Square**
```java
// Xấu: Square thay đổi hành vi setter
public class Rectangle {
    protected int width;
    protected int height;

    public void setWidth(int w) { this.width = w; }
    public void setHeight(int h) { this.height = h; }
}

public class Square extends Rectangle {
    @Override
    public void setWidth(int w) {
        this.width = w;
        this.height = w; // Side effect!
    }

    @Override
    public void setHeight(int h) {
        this.width = h;  // Side effect!
        this.height = h;
    }
}

// Client mong đợi một hành vi, nhận được một hành vi khác:
public void test(Rectangle r) {
    r.setWidth(5);
    r.setHeight(10);
    // Với Rectangle: width=5, height=10
    // Với Square: width=10, height=10 — bug!
}
```

**Cách sửa?**
1. **Trích xuất một interface chung**: Thay vì `Square extends Rectangle`, tạo một interface `Shape` với phương thức `getArea()`
2. **Composition**: Nếu bạn cần chức năng của một class khác, đừng kế thừa nó — biến nó thành một trường

```java
// Tốt: composition thay vì inheritance
public class ReadOnlyList<T> implements Iterable<T> {
    private final List<T> list;
    public ReadOnlyList(List<T> list) { this.list = list; }
    // Chỉ các phương thức chỉ đọc...
}
```

## 🟡 Middle Level

### Các Ví Dụ Vi Phạm LSP Tinh Vi

#### 1. Vấn Đề Subclass "Lười Biếng" (The Refusal of Bequest)
Khi một subclass override phương thức của parent và ném exception hoặc không làm gì cả.

- **Ví dụ thực tế từ Java**: `java.util.Date` và `java.sql.Date`
- **Bản chất**: `java.sql.Date` (subclass) "vô hiệu hóa" việc xử lý thời gian (giờ, phút, giây), mặc dù base class `java.util.Date` hỗ trợ chúng. Nếu code mong đợi độ chính xác mili giây và nhận `sql.Date`, nó sẽ hỏng.
- **Gọi với java.sql.Date sẽ ném IllegalArgumentException!**
- **getHours() trong java.sql.Date không được hỗ trợ (ném exception), mặc dù parent class hỗ trợ phương thức này.**

#### 2. Vi Phạm Invariant (Ví Dụ Account)
```java
public class Account {
    protected double balance;
    public void withdraw(double amount) {
        this.balance -= amount;
    }
}

public class SavingsAccount extends Account {
    @Override
    public void withdraw(double amount) {
        if (amount > balance) throw new RuntimeException("No overdraft!"); // Làm mạnh precondition
        super.withdraw(amount);
    }
}
```
**Tại sao đây là một vi phạm?**
Nếu code client được viết cho `Account` gốc, nó có thể dựa vào việc balance có thể trở nên âm (overdraft). Thay thế bằng `SavingsAccount` sẽ phá vỡ logic của client, cái không mong đợi một exception.

> Không phải mọi `if` đều là một vi phạm. Vi phạm là khi contract của parent cho phép một hành động, nhưng subclass cấm nó. Nếu cả hai class đồng ý về contract (cả hai đều cấm overdraft) — không có vi phạm LSP.

#### 3. Hỏng Trạng Thái Ẩn (Side Effect)
Ví dụ kinh điển với Rectangle và Square.
- Client: `rect.setWidth(10); rect.setHeight(20);`
- Với Rectangle: diện tích 200
- Với Square: diện tích 400 (vì `setHeight` đã ghi đè `width`)
**Kết quả**: Client bị sốc, invariant "thay đổi height không ảnh hưởng đến width" bị phá vỡ.

### Tại Sao Chúng Ta Làm Điều Này? (Nguyên Nhân Gốc Rễ)

1. **Mong muốn tiết kiệm công sức**: "Tại sao lại viết trường `name` một lần nữa nếu nó đã có trong `User`?". Vì vậy chúng ta kế thừa `Admin` từ `User`, mặc dù chúng có vòng đời khác nhau.
2. **Hierarchy không chính xác**: Chúng ta mô hình hóa thế giới "như nó vốn có", không phải "như nó được sử dụng". Trong sinh học, một con đà điểu là một con chim; trong OOP, `Ostrich` không thể kế thừa từ `FlyingBird`.

### Cách Nhận Biết Vi Phạm

**Dấu hiệu:**

1. **Kiểm tra `instanceof`**: Nếu bạn kiểm tra loại để gọi logic cụ thể
2. **`UnsupportedOperationException`**: Phương thức "không được hỗ trợ" trong subclass
3. **Override rỗng**: Phương thức được override với một triển khai rỗng
4. **Hành vi test khác nhau**: Test base class thất bại cho subclass

### Cách Sửa

#### 1. Trích Xuất Một Interface Chung
```java
// Thay vì Square extends Rectangle:
public interface Shape {
    int getArea();
}

public class Rectangle implements Shape {
    private int width, height;
    // các setter hoạt động độc lập
    @Override
    public int getArea() { return width * height; }
}

public class Square implements Shape {
    private int side;
    @Override
    public int getArea() { return side * side; }
}
```

#### 2. Composition (Delegation)
```java
// TỐT: Dùng composition thay vì inheritance méo mó
public class ReadOnlyList<T> implements Iterable<T> {
    private final List<T> list; // Delegate
    public ReadOnlyList(List<T> list) { this.list = list; }
    @Override
    public Iterator<T> iterator() { return list.iterator(); }
    public int size() { return list.size(); }
    // Chỉ các phương thức chỉ đọc — không có add/remove
}
```

#### 3. Chia Tách Hierarchy
```java
// Thay vì Penguin extends Bird:
public interface Bird {
    void sing();
}

public interface FlyingBird extends Bird {
    void fly();
}

public class Sparrow implements FlyingBird {
    @Override public void sing() { /* ... */ }
    @Override public void fly() { /* ... */ }
}

public class Penguin implements Bird {
    @Override public void sing() { /* ... */ }
    // fly() vắng mặt — và điều đó đúng
}
```

## 🔴 Senior Level

### Triển Khai Nội Bộ Và Kiến Trúc

Ở cấp độ Senior, quan trọng là phải hiểu: vi phạm LSP không chỉ là một "lỗi code". Đó là một **vi phạm contract** có thể chỉ biểu hiện tại runtime, trong production, dưới một số điều kiện nhất định.

LSP là về **Design by Contract**: một subclass chỉ có thể **làm yếu các yêu cầu đầu vào** và **làm mạnh các đảm bảo đầu ra**.

| Ràng buộc         | Quy tắc                                    | Vi phạm                                            |
| ------------------ | --------------------------------------- | ---------------------------------------------------- |
| **Precondition**  | Không thể mạnh hơn                  | `SavingsAccount` yêu cầu `amount <= balance`        |
| **Postcondition** | Không thể yếu hơn                      | `FastSort` trả về mảng chỉ được sắp xếp một phần            |
| **Invariant**     | Phải được bảo toàn                       | `Square` thay đổi `width` khi `setHeight`              |
| **History**        | Trạng thái không được thay đổi không thể dự đoán     | `CachingList` trả về dữ liệu cũ                                     |

### Các Ví Dụ Thực Tế Từ JDK

#### `java.util.Date` và `java.sql.Date`
```java
// java.util.Date — lưu trữ thời gian với độ chính xác mili giây
// java.sql.Date — subclass, nhưng "vô hiệu hóa" thời gian (giờ, phút, giây)

public class java.sql.Date extends java.util.Date {
    // Nhiều phương thức bị override và ném IllegalArgumentException
    @Override
    public int getHours() {
        throw new IllegalArgumentException();
    }
}
```
Đây là một trong những vi phạm LSP nổi tiếng nhất trong Java Standard Library.

#### `Collections.unmodifiableList()`
```java
List<String> modifiable = new ArrayList<>();
List<String> unmodifiable = Collections.unmodifiableList(modifiable);

// unmodifiable được triển khai như một wrapper trên List,
// nhưng add() ném UnsupportedOperationException
unmodifiable.add("test"); // BOOM!
```

### Hậu Quả Cho Highload Và Testing

- **Unit Test Bị Hỏng**: Các test được viết cho base class bắt đầu "flaky" hoặc thất bại khi chạy với một object subclass. Đây là dấu hiệu chắc chắn của vi phạm LSP
- **Heisenbug**: Các bug chỉ biểu hiện trong một số điều kiện nhất định, khi một object loại sai "rò rỉ" vào hệ thống thông qua DI hoặc một factory. Heisenbug — một bug chỉ biểu hiện trong các điều kiện nhất định (loại object cụ thể trong DI, tải cụ thể) và khó tái tạo. Được đặt tên theo nguyên lý bất định của Heisenberg.
- **Regression Testing**: Mỗi subclass mới yêu cầu chạy toàn bộ test của base type

### Đánh Đổi Kiến Trúc

**Inheritance (vi phạm LSP):**
- ✅ Ưu điểm: Tái sử dụng code, boilerplate tối thiểu
- ❌ Nhược điểm: Contract cứng nhắc, vi phạm LSP, tính dễ vỡ

**Composition (tuân thủ LSP):**
- ✅ Ưu điểm: Tự do hành vi hoàn toàn, coupling lỏng lẻo
- ❌ Nhược điểm: Nhiều boilerplate hơn, cần ủy quyền các phương thức

**Interface (tuân thủ LSP):**
- ✅ Ưu điểm: Contract sạch, nghĩa vụ tối thiểu
- ❌ Nhược điểm: Không có tái sử dụng triển khai

### Edge Cases

1. **Template Method Với Các Bước "Tùy Chọn"**: Base class định nghĩa thuật toán, subclass có thể bỏ qua một bước
   - **Vấn đề**: Bỏ qua một bước có thể phá vỡ invariant của thuật toán
   - **Giải pháp**: Chain of Responsibility hoặc Decorator thay vì Template Method

2. **Abstract Class Với Triển Khai Mặc Định "Không Làm Gì"**: Phương thức "không làm gì" trong base class
   - **Vấn đề**: Các subclass có thể quên override — vi phạm contract âm thầm
   - **Giải pháp**: Các phương thức abstract không có triển khai (buộc override)

3. **Proxy Và Dynamic Proxy**: Các object được tạo động
   - **Vấn đề**: Có thể không tái tạo tất cả các postcondition của bản gốc
   - **Giải pháp**: Contract Testing cho các proxy

### Hiệu Năng

- **Virtual dispatch + LSP**: Khi JIT tin tưởng rằng tất cả các subclass tuân thủ LSP, nó có thể thực hiện **devirtualization** và **inlining** mạnh mẽ hơn
- **Chi phí vi phạm LSP**: Nếu một subclass vi phạm contract, các tối ưu JIT có thể tạo ra **kết quả không đúng** (về mặt lý thuyết; trong thực tế, JVM thực hiện deoptimization)
- **Branch prediction**: Các kiểm tra `instanceof` để né tránh vi phạm LSP phá hủy branch prediction

### Kinh Nghiệm Production

**Kịch bản production thực tế:**

Trong một dự án e-commerce, `BaseOrderProcessor` có một phương thức `calculateTax(Order)`. Subclass `InternationalOrderProcessor` đã override nó và áp dụng một công thức khác. Vấn đề: base class cũng gọi `calculateTax` bên trong `processOrder`, và các developer của `InternationalOrderProcessor` không tính đến việc `calculateTax` được gọi hai lần — cho sản phẩm và cho vận chuyển.

**Kết quả**: Tính toán thuế không chính xác cho các đơn hàng quốc tế. Thiệt hại — $50K mỗi tháng trước khi phát hiện.

**Giải pháp**: Trích xuất `TaxCalculator` thành một component riêng biệt (composition) thay vì kế thừa logic tính toán.

### Monitoring Và Chẩn Đoán

**Cách phát hiện vi phạm LSP:**

1. **Contract Test**:
   ```java
   // Test chung cho tất cả các triển khai Shape
   public abstract class ShapeContractTest<T extends Shape> {
       abstract T createShape();

       @Test
       void areaIsAlwaysNonNegative() {
           assertThat(createShape().getArea()).isGreaterThanOrEqualTo(0);
       }
   }
   ```

2. **Metric**:
   - Số kiểm tra `instanceof`
   - Số `UnsupportedOperationException`
   - Số phương thức override rỗng

3. **Công cụ**:
   - Pitest (Mutation Testing): xác minh rằng test bắt được các thay đổi hành vi
   - ArchUnit: các test kiến trúc trên inheritance

### Best Practices Cho Highload

- **Sealed Interface (Java 17+)**: Giới hạn hierarchy — compiler kiểm tra tính đầy đủ
- **Immutability**: Các object bất biến dễ tương thích LSP hơn
- **Contract Testing**: Viết test cho các contract của base type và chạy chúng cho tất cả subclass
- **Nếu bạn dùng `if (obj instanceof Subclass)` — bạn đã vi phạm LSP rồi**

### Tóm Tắt Cho Senior

- Nếu bạn dùng `if (obj instanceof Subclass)`, bạn đã vi phạm LSP rồi
- Inheritance là coupling mạnh nhất trong OOP. Chỉ dùng nó khi subclass **thay thế hoàn toàn** parent trong mọi kịch bản
- Nhớ **Design by Contract**: một subclass chỉ có thể làm yếu các yêu cầu đầu vào và làm mạnh các đảm bảo đầu ra
- **Composition over Inheritance** — cách tiếp cận được ưu tiên cho một Senior developer

## 🎯 Interview Cheat Sheet

**Cần phải biết:**
- Subclass "lười biếng" — ném `UnsupportedOperationException` hoặc làm phương thức rỗng
- Square extends Rectangle — side effect: `setHeight` thay đổi `width`, diện tích 400 thay vì 200
- `java.sql.Date` kế thừa `java.util.Date`, nhưng ném `IllegalArgumentException` trong `getHours()` — vi phạm LSP trong JDK
- `Collections.unmodifiableList()` ném `UnsupportedOperationException` trên `add()` — vi phạm LSP
- `instanceof` để né tránh các hành vi khác nhau = LSP đã bị vi phạm
- Giải pháp: composition (Delegation) hoặc chia tách hierarchy thông qua interface

**Các câu hỏi phụ thường gặp:**
- **Tại sao Square không thể kế thừa Rectangle?** — Vì nó thay đổi hành vi setter, vi phạm invariant của parent
- **Heisenbug trong ngữ cảnh LSP là gì?** — Một bug chỉ biểu hiện với một loại object cụ thể trong DI, khó tái tạo
- **Cách test LSP?** — Contract Testing: các test chung cho base type, chạy cho tất cả các triển khai
- **Hậu quả thực tế của vi phạm?** — Trong e-commerce: tính toán thuế không chính xác, thiệt hại $50K/tháng

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Không phải mọi if đều là một vi phạm LSP" (đúng, nhưng tốt hơn là không gây ra câu hỏi)
- "Inheritance ổn nếu các class chia sẻ các trường" (bỏ qua behavioral subtyping)
- "LSP chỉ bị vi phạm với các exception" (không — side effect cũng là các vi phạm)
