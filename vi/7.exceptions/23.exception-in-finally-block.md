# What happens if an exception also occurs in the finally block? (Điều gì xảy ra nếu một exception cũng xảy ra trong khối finally?)

## Junior Level

### Hiệu ứng chính

Nếu một exception xảy ra trong `finally`, nó sẽ **thế chỗ** exception từ `try`. Lỗi gốc sẽ bị mất.

```java
try {
    throw new RuntimeException("Original error");
} finally {
    throw new RuntimeException("Finally error");
}
// Chỉ "Finally error" sẽ hiện ra
```

### Tại sao điều đó nguy hiểm

```java
try {
    // Lỗi nghiêm trọng - DB không khả dụng
    connection.executeQuery("SELECT * FROM users");
} finally {
    // Lỗi khi đóng - NPE
    connection.close(); // connection == null
}
// Log chỉ hiện NPE, thông tin về DB bị mất
```

Bạn sẽ đi debug `NPE` trong khi vấn đề thực sự là hạ tầng.

### Cách tránh

Dùng **try-with-resources** - nó tự động xử lý các suppressed exception:

```java
try (Connection conn = dataSource.getConnection()) {
    conn.executeQuery("SELECT * FROM users");
}
// Nếu cả try và close() đều lỗi - cả hai exception được bảo toàn
```

### Khi nào KHÔNG nên dựa vào finally để dọn dẹp

1. **Code trong finally có thể ném exception** - nếu `close()`, `disconnect()`, `release()` có thể lỗi, hãy bọc mỗi lời gọi trong một `try-catch` riêng bên trong finally
2. **Nhiều resource mà không có TWR** - nếu đóng 3+ resource trong một finally, hãy dùng try-catch riêng cho mỗi cái, nếu không exception đầu tiên sẽ làm gián đoạn việc đóng các cái còn lại
3. **Các transaction then chốt** - trong finally bạn không thể rollback an toàn một transaction nếu exception chính đã xảy ra; hãy dùng khối `catch` riêng cho rollback
4. **Ngữ cảnh async** - trong `CompletableFuture` khối finally có thể thực thi trong một thread khác, và exception ở đó sẽ bị mất nếu không có UncaughtExceptionHandler
5. **Shutdown hook** - khi `System.exit()` finally có thể không thực thi chút nào
6. **Dọn dẹp resource native** - với JNI/native memory dùng `Cleaner` (Java 9+) thay vì finally, vì các resource native có thể không được giải phóng đúng cách

## Middle Level

### Cơ chế thế chỗ (Shadowing) - từng bước

JVM chỉ mang **một** object exception làm "active" trong stack tại mỗi thời điểm. Đây là điều xảy ra từng bước:

**Bước 1:** Code trong `try` ném exception **A** (`new RuntimeException("Original")`).

**Bước 2:** JVM đánh dấu stack frame hiện tại là "đang ném exception" và lưu một tham chiếu tới **A** trong một slot đặc biệt của frame.

**Bước 3:** Trước khi thoát phương thức JVM thực thi khối `finally` (điều này được đảm bảo bởi đặc tả JLS 14.20.2).

**Bước 4:** Code trong `finally` ném exception **B** (`new RuntimeException("Finally")`).

**Bước 5:** JVM **thay** tham chiếu trong slot exception của frame từ **A** sang **B**. Tham chiếu tới **A** bị mất vĩnh viễn - không có cách nào lấy được nó từ `catch` hay từ bên ngoài.

**Bước 6:** Exception **B** lan truyền lên trên stack. **A** chỉ trở nên không thể tiếp cận cho GC sau khi toàn bộ stack được tháo gỡ (unwound).

**Trực quan:**
```
Stack frame (trước finally):  pendingException = A
Stack frame (sau finally): pendingException = B  // A bị mất!
```

### Ví dụ code cụ thể

```java
public class FinallyShadowing {
    public static void main(String[] args) {
        try {
            System.out.println("Step 1: throw SQLException");
            throw new SQLException("Database connection lost");
        } finally {
            System.out.println("Step 2: finally tries to close resource");
            // close() cũng lỗi - và điều này che khuất SQLException
            throw new NullPointerException("Connection was null in finally");
        }
    }
}
```

**Output trong stack trace:**
```
Exception in thread "main" java.lang.NullPointerException: Connection was null in finally
    at FinallyShadowing.main(FinallyShadowing.java:8)
```

Lưu ý: `SQLException` hoàn toàn vắng mặt khỏi stack trace. Bạn sẽ đi debug NPE trong khi vấn đề thực sự là mất kết nối DB.

**Cách bảo toàn exception gốc:**
```java
try {
    throw new SQLException("Database connection lost");
} catch (Exception e) {
    try {
        // logic của finally một cách riêng biệt
        closeSafely();
    } catch (Exception closeEx) {
        e.addSuppressed(closeEx); // Bảo toàn cả hai
    }
    throw e; // Exception gốc lan truyền
}
```

### Shadowing qua return

`finally` có thể "nuốt" một exception ngay cả khi không ném một cái mới:

```java
public int dangerousMethod() {
    try {
        throw new RuntimeException("Error");
    } finally {
        return 42; // Exception bị nuốt! Phương thức sẽ trả về 42
    }
}
```

Lệnh `return` trong bytecode của `finally` hoàn tất stack frame trước khi cơ chế xử lý exception kịp lan truyền lỗi. SonarQube đánh dấu điều này là **Blocker**.

### Giải pháp hiện đại: Try-with-resources

Bắt đầu từ Java 7:
- Nếu có exception trong `try`, rồi trong `close()` tự động - exception từ `try` vẫn là cái chính
- Exception từ `close()` được thêm dưới dạng **Suppressed**
- Bức tranh đầy đủ: `Error A (Suppressed: Error B)`

```java
try (Resource r = new Resource()) {
    r.doWork(); // IOException #1
} // close() ném IOException #2

// #1 - chính, #2 - suppressed
catch (Exception e) {
    System.out.println(e.getMessage());         // #1
    System.out.println(e.getSuppressed()[0]);   // #2
}
```

## Senior Level

### Rò rỉ Resource khi có exception trong finally

Nếu exception trong `finally` xảy ra ở giữa việc dọn dẹp (đóng cái đầu tiên trong năm socket), các resource còn lại **sẽ không được đóng** - việc thực thi `finally` sẽ bị gián đoạn.

**Best Practice cho Senior:** bọc mỗi `close()` trong một `try-catch` riêng bên trong `finally`:

```java
finally {
    try { resource1.close(); } catch (Exception e) { log.warn("Failed to close 1", e); }
    try { resource2.close(); } catch (Exception e) { log.warn("Failed to close 2", e); }
}
```

Hoặc dùng **try-with-resources** - nó làm việc này tự động.

### Phân tích Log

Nếu bạn thấy các exception lạ từ các khối dọn dẹp trong log (`SocketClosedException`), luôn kiểm tra xem chúng có đang giấu các lỗi sớm hơn không.

### Debugger

Khi step debugging, hãy theo dõi quá trình chuyển sang `finally`. Nếu biến exception trong stack frame đột nhiên thay đổi - bạn đã bắt được Shadowing.

### Phân tích bytecode

```
javap -c MyClass
```

Sẽ hiển thị cách `return` trong `finally` ghi đè giá trị trả về và cách exception ghi đè cái trước đó.

### Chẩn đoán

- **`getSuppressed()`** - kiểm tra mảng các suppressed exception
- **Static Analysis** - Sonar cảnh báo về các khối finally rủi ro
- **Log Correlation** - liên kết các exception từ `try` và `finally` bằng Trace ID

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Exception từ `finally` **thế chỗ** exception từ `try` - lỗi gốc mất vĩnh viễn
- JVM chỉ lưu một pending exception trong slot của frame - `finally` ghi đè nó
- `return` trong `finally` cũng "nuốt" exception - phương thức sẽ trả về giá trị thay vì lỗi
- Try-with-resources tự động bảo toàn cả hai exception: chính + suppressed từ `close()`
- Không có TWR hãy bọc mỗi `close()` trong một `try-catch` riêng bên trong `finally`
- Với nhiều resource trong `finally`, exception đầu tiên sẽ làm gián đoạn việc đóng các cái còn lại - rò rỉ resource
- Trong ngữ cảnh async, exception trong `finally` có thể bị mất nếu không có `UncaughtExceptionHandler`

**Các câu hỏi phụ thường gặp:**
- **Cách thấy exception gốc?** - Không có TWR, không có cách nào - nó bị mất. Hãy dùng try-with-resources
- **Tại sao TWR tốt hơn `finally`?** - Bảo toàn cả hai exception qua cơ chế suppressed
- **Nếu `finally` làm `return` thì sao?** - Exception từ `try` bị nuốt, phương thức trả về giá trị
- **Cách đóng resource đúng cách mà không có TWR?** - Mỗi `close()` trong một `try-catch` riêng bên trong `finally`

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Ném exception trong `finally` là an toàn" - chúng sẽ che khuất lỗi gốc
- "Tôi dùng `finally` để đóng resource" - cách tiếp cận lỗi thời, hãy dùng TWR
- "Return trong `finally` là thực hành bình thường" - SonarQube đánh dấu là Blocker
- "Mất exception không phải chuyện lớn" - bạn sẽ đi debug sai vấn đề
