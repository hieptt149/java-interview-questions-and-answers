# How to configure rollback for checked exceptions? (Cách cấu hình rollback cho checked exception?)

## 🟢 Junior Level

Theo mặc định, Spring **không rollback** transaction khi có checked exception (các subclass của `Exception`, nhưng không phải `RuntimeException`). Để sửa điều này, dùng tham số `rollbackFor`.

### Cách Đơn Giản Nhất

```java
@Transactional(rollbackFor = Exception.class)
public void businessMethod() throws MyCheckedException {
    // Giờ BẤT KỲ exception nào cũng sẽ gây rollback
}
```

// rollbackFor báo cho TransactionInterceptor: "hãy xử lý exception này
// cũng là một tín hiệu rollback". Kiểm tra: nếu exception instanceof rollbackFor → setRollbackOnly().

### Ví Dụ Minh Họa

Hãy nghĩ về một hệ thống báo cháy: theo mặc định nó chỉ kích hoạt khi có hỏa hoạn (RuntimeException). Checked exception là một vụ rò rỉ khí ga, cũng cần được xử lý. `rollbackFor` báo cho hệ thống: "bất kỳ trường hợp khẩn cấp nào = sơ tán".

### Cho Một Exception Cụ Thể

```java
@Transactional(rollbackFor = IOException.class)
public void readFile() throws IOException {
    // IOException sẽ gây rollback
}
```

### Cho Nhiều Exception

```java
@Transactional(rollbackFor = {IOException.class, MyBusinessException.class})
public void process() throws IOException, MyBusinessException {
    // Cả hai exception đều sẽ gây rollback
}
```

### Quy Tắc Vàng

Nếu exception nghiệp vụ của bạn có nghĩa là thao tác không thể hoàn thành thành công — nó nên kích hoạt rollback. Dùng `rollbackFor = Exception.class` để an toàn.

### Khi Nào KHÔNG Nên Thay Đổi Quy Tắc Rollback

1. **Nếu exception = tín hiệu bug** (NPE, IAE) — rollback mặc định là đúng
2. **Nếu không có chính sách rõ ràng của team** — rollbackFor khác nhau ở các service khác nhau tạo ra sự hỗn loạn
3. **Nếu dùng @ControllerAdvice** — để exception đến controller, rồi quyết định trả gì cho client

## 🟡 Middle Level

### Tại Sao Điều Này Quan Trọng

Trong các dự án thực tế, các service thường dùng các exception nghiệp vụ tùy chỉnh. Nếu chúng kế thừa từ `Exception` (checked), Spring sẽ COMMIT theo mặc định khi chúng xảy ra. Điều này có thể để lại cơ sở dữ liệu ở trạng thái không nhất quán.

```java
// XẤU — InsufficientFundsException extends Exception
@Transactional
public void withdraw(BigDecimal amount) throws InsufficientFundsException {
    if (balance.compareTo(amount) < 0) {
        throw new InsufficientFundsException();
    }
    balance = balance.subtract(amount);
    // Spring sẽ COMMIT mặc dù có exception!
}
```

### Ba Cách Tiếp Cận Để Giải Quyết

#### 1. rollbackFor (Được Khuyến Nghị Cho Checked)
```java
@Transactional(rollbackFor = Exception.class)
public void withdraw(BigDecimal amount) throws InsufficientFundsException {
    // Rollback cho tất cả các exception
}
```

#### 2. Chuyển Sang RuntimeException
```java
// InsufficientFundsException giờ kế thừa RuntimeException
@Transactional
public void withdraw(BigDecimal amount) {
    if (balance.compareTo(amount) < 0) {
        throw new InsufficientFundsException();  // Rollback tự động
    }
}
```

#### 3. Rollback Lập Trình
```java
@Transactional
public void withdraw(BigDecimal amount) {
    try {
        if (balance.compareTo(amount) < 0) {
            throw new InsufficientFundsException();
        }
    } catch (InsufficientFundsException e) {
        TransactionAspectSupport.currentTransactionStatus()
            .setRollbackOnly();
        throw e;
    }
}
```

### Các Lỗi Thường Gặp

| Lỗi                                     | Điều gì xảy ra                | Cách khắc phục                               |
| ------------------------------------------- | --------------------------- | ---------------------------------------- |
| Quên `rollbackFor`                    | COMMIT khi có checked exception | `rollbackFor = Exception.class`          |
| Lỗi chính tả trong `rollbackForClassName`              | Quy tắc âm thầm không kích hoạt  | Dùng `rollbackFor` với Class literal     |
| `rollbackFor` + `noRollbackFor` xung đột | Hành vi khó dự đoán      | Các quy tắc rõ ràng                        |
| Catch không có `setRollbackOnly()`           | Exception bị bắt → COMMIT   | Gọi `setRollbackOnly()` trong catch        |

### So Sánh Các Cách Tiếp Cận

| Cách tiếp cận                                    | Ưu điểm                                          | Nhược điểm                                    | Khi nào nên dùng                                   |
| ------------------------------------------- | --------------------------------------------- | --------------------------------------- | --------------------------------------------- |
| `rollbackFor = Exception.class`             | Đơn giản, đáng tin cậy                              | Rollback cả với những gì "không phải lỗi"          | Cách tiếp cận tiêu chuẩn                             |
| `rollbackFor = {SpecificException.class}`   | Kiểm soát chính xác                               | Cần liệt kê tất cả                        | Khi một số checked exception = không phải lỗi      |
| Chuyển sang RuntimeException                | Rollback tự động, ít boilerplate hơn            | Đòi hỏi refactor hệ thống phân cấp exception   | Dự án mới hoặc refactoring                    |
| `setRollbackOnly()` lập trình            | Rollback có điều kiện                          | Boilerplate, gắn kết với Spring            | Logic nghiệp vụ phức tạp                        |

### Khi Nào KHÔNG Nên Rollback Cho Checked Exception

| Tình huống          | Tại sao                                  | Giải pháp thay thế                               |
| ------------------ | ------------------------------------ | ----------------------------------------- |
| Validation nghiệp vụ| Tình huống dự đoán trước, dữ liệu hợp lệ       | `noRollbackFor = ValidationException.class` |
| Graceful degradation | Hệ thống nên tiếp tục hoạt động         | Không phải exception, mà là một object kết quả          |
| Thành công từng phần    | Một phần dữ liệu là đúng              | Xử lý, commit, log lỗi                 |

## 🔴 Senior Level

### Giải Quyết Thuộc Tính rollbackFor

Spring giải quyết các quy tắc rollback thông qua chuỗi ưu tiên:

```java
// AbstractFallbackTransactionAttributeSource
protected TransactionAttribute determineTransactionAttribute(AnnotatedElement ae) {
    for (TransactionAnnotationParser parser : annotationParsers) {
        TransactionAttribute attr = parser.parseTransactionAnnotation(ae);
        if (attr != null) return attr;
    }
    return null;
}

// SpringTransactionAnnotationParser
public TransactionAttribute parseTransactionAnnotation(Transactional ann) {
    RuleBasedTransactionAttribute rbta = new RuleBasedTransactionAttribute();

    Class<? extends Throwable>[] rollbackFor = ann.rollbackFor();
    for (Class<? extends Throwable> ex : rollbackFor) {
        rbta.getRollbackRules().add(new RollbackRuleAttribute(ex));
    }

    String[] rollbackForClassName = ann.rollbackForClassName();
    for (String ex : rollbackForClassName) {
        rbta.getRollbackRules().add(new RollbackRuleAttribute(ex));
    }

    Class<? extends Throwable>[] noRollbackFor = ann.noRollbackFor();
    for (Class<? extends Throwable> ex : noRollbackFor) {
        rbta.getRollbackRules().add(new NoRollbackRuleAttribute(ex));
    }

    return rbta;
}
```

### Các Quy Tắc Rollback Dựa Trên String — Nguy Hiểm Ẩn Giấu

```java
@Transactional(rollbackForClassName = {"MyBusinessException"})
public void process() { ... }
```

Spring giải quyết tên class tại thời điểm chạy:
```java
public RollbackRuleAttribute(String exceptionPattern) {
    this.exceptionName = exceptionPattern;
    // KHÔNG được validate khi khởi động — được giải quyết một cách lazy trong lúc xử lý exception
}
```

**Nguy cơ:** Lỗi chính tả → quy tắc âm thầm không kích hoạt → không rollback. Dùng `rollbackFor` với Class literal để đảm bảo type safety.

### Kết Hợp rollbackFor Và noRollbackFor

```java
@Transactional(
    rollbackFor = Exception.class,
    noRollbackFor = {NotFoundException.class, ValidationException.class}
)
public void process() {
    // Exception → rollback
    // NotFoundException → KHÔNG rollback (commit dù có exception)
    // ValidationException → KHÔNG rollback
}
```

**Thứ tự khớp quy tắc:**
1. Khớp cụ thể nhất thắng (sâu nhất trong hệ thống phân cấp)
2. Cùng độ sâu — quy tắc khớp đầu tiên
3. Các quy tắc mặc định (RuntimeException, Error) được kiểm tra cuối cùng

// noRollbackFor = "đây là một RuntimeException, nhưng ĐỪNG rollback". Hữu ích cho
// các exception nghiệp vụ dự đoán trước kế thừa từ RuntimeException.

### Rollback Lập Trình — Khi Nào Và Tại Sao

#### Kịch Bản 1: Checked Exception Không Lan Truyền
```java
@Transactional
public void processFiles(List<File> files) {
    for (File file : files) {
        try {
            processFile(file);  // ném IOException
        } catch (IOException e) {
            log.error("File {} failed", file.getName());
            TransactionAspectSupport.currentTransactionStatus()
                .setRollbackOnly();
            break;  // Dừng xử lý, nhưng đánh dấu để rollback
        }
    }
}
```

#### Kịch Bản 2: Rollback Có Điều Kiện
```java
@Transactional
public void transferWithLimit(Long from, Long to, BigDecimal amount) {
    if (amount.compareTo(DAILY_LIMIT) > 0) {
        log.warn("Exceeds daily limit");
        TransactionAspectSupport.currentTransactionStatus()
            .setRollbackOnly();
        return;  // Method trả về bình thường, nhưng transaction rollback
    }
    // ... logic chuyển tiền
}
```

### Các Trường Hợp Biên (Tối Thiểu 3)

1. **Lỗi chính tả String trong `rollbackForClassName`**: `@Transactional(rollbackForClassName = "BusinesException")` — bị bỏ qua âm thầm. Spring không validate tên class khi khởi tạo.

2. **Các quy tắc xung đột**: `rollbackFor = Exception.class` + `noRollbackFor = RuntimeException.class`. Tính cụ thể quyết định người thắng. RuntimeException sâu hơn → `noRollbackFor` thắng → không rollback cho RuntimeException, rollback cho checked.

3. **Thứ tự AOP**: Aspect xử lý exception tùy chỉnh có thể bắt exception trước `TransactionInterceptor`. Interceptor thấy trả về bình thường → COMMIT. Giải pháp: `@Order` để kiểm soát thứ tự.

4. **Bỏ qua self-invocation**: Gọi `this.method()` bên trong class — proxy không tham gia, các quy tắc rollback hoàn toàn không được áp dụng. Không có transaction = không có rollback.

5. **Các method Async**: `@Async` với checked exception — exception không lan truyền đến context transaction của bên gọi. Bên gọi tiếp tục với COMMIT. Future chứa exception — cần `future.get()`.

### Cấu Hình Rollback Toàn Cục

```java
@Configuration
public class TransactionConfig {

    @Bean
    public TransactionInterceptor transactionInterceptor(
            PlatformTransactionManager tm) {

        TransactionInterceptor interceptor = new TransactionInterceptor();
        interceptor.setTransactionManager(tm);

        RuleBasedTransactionAttribute defaultRule =
            new RuleBasedTransactionAttribute();
        defaultRule.setRollbackRules(
            List.of(new RollbackRuleAttribute(Exception.class)));

        NameMatchTransactionAttributeSource source =
            new NameMatchTransactionAttributeSource();
        source.addTransactionalMethod("*", defaultRule);

        interceptor.setTransactionAttributeSource(source);
        return interceptor;
    }
}
```

### Chiến Lược Migration: Từ Checked Sang Unchecked

```java
// Bước 1: Thêm rollbackFor vào các method hiện có
@Transactional(rollbackFor = Exception.class)
public void oldMethod() throws BusinessException { ... }

// Bước 2: Thay đổi hệ thống phân cấp exception
public class BusinessException extends RuntimeException { ... }  // Trước đó extends Exception

// Bước 3: Xóa throws và rollbackFor
@Transactional
public void newMethod() { ... }  // Sạch sẽ

// Bước 4: Cập nhật các bên gọi (không còn cần try-catch)
service.newMethod();  // Thay vì: try { service.oldMethod(); } catch...
```

### Các Con Số Về Hiệu Năng

| Thao tác                         | Thời gian                                |
| --------------------------------- | ----------------------------------- |
| Giải quyết quy tắc rollback (đã cache) | ~0.5 μs                             |
| Khớp class `rollbackFor`      | ~0.1 μs                             |
| Giải quyết dựa trên string           | ~5-10 μs (class loading)            |
| Rollback DB thực tế                | 1-5 ms (PostgreSQL), 5-50 ms (InnoDB) |

### Tác Động Đến Bộ Nhớ

- Các object `RollbackRuleAttribute` — ~100 byte mỗi cái, được lưu trong `TransactionAttribute`
- Các quy tắc dựa trên string: Class loading tại thời điểm chạy — overhead bộ nhớ nếu exception class lớn
- Stack trace của exception — có thể lớn. Với rollback thường xuyên = áp lực GC.

### Thread Safety

Các quy tắc rollback là bất biến — thread-safe. Trạng thái ThreadLocal trong `TransactionSynchronizationManager` — các lời gọi đồng thời được cô lập.

### Câu Chuyện Thực Tế Trong Production

Service tài chính: `withdraw()` ném `InsufficientFundsException extends Exception`. `@Transactional` không có `rollbackFor`. Khi có exception thiếu tiền — transaction COMMIT, số dư bị trừ, nhưng khoản chuyển không hoàn thành. Tiền biến mất. Sửa lỗi: `rollbackFor = Exception.class` + migration sang hệ thống phân cấp RuntimeException.

### Best Practices Cho Highload

1. **Cơ sở**: `rollbackFor = Exception.class` trên tất cả các method ghi. Không có ngoại lệ.
2. **Giảm thiểu checked exception**: Chuyển các exception nghiệp vụ sang RuntimeException. Phù hợp với triết lý của Spring.
3. **Cấu hình toàn cục**: Dùng `TransactionInterceptor` với các quy tắc rollback toàn cục thay vì lặp lại annotation.
4. **Không bao giờ dùng `rollbackForClassName`**: Các quy tắc dựa trên string — nguy cơ thất bại âm thầm. Dùng Class literal.
5. **Kiểm thử rollback**: Integration test nên xác minh rollback thực sự xảy ra cho từng loại exception.
6. **Giám sát tỷ lệ rollback**: % rollback cao = vấn đề trong validation/logic nghiệp vụ.

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- rollbackFor = Exception.class — rollback cho tất cả các exception, cơ sở được khuyến nghị
- rollbackFor = {SpecificException.class} — kiểm soát chính xác cho các loại cụ thể
- Rollback lập trình: TransactionAspectSupport.currentTransactionStatus().setRollbackOnly()
- rollbackForClassName (string) — rủi ro: lỗi chính tả bị bỏ qua âm thầm, dùng Class literal
- noRollbackFor loại trừ các exception cụ thể khỏi rollback (ví dụ: NotFoundException)
- Thứ tự khớp quy tắc: khớp cụ thể nhất (sâu nhất trong hệ thống phân cấp) thắng

**Các câu hỏi phụ thường gặp:**
- Ba cách tiếp cận cho rollback checked exception? — rollbackFor, chuyển sang RuntimeException, setRollbackOnly lập trình
- Tại sao rollbackForClassName nguy hiểm? — Giải quyết string là lazy, lỗi chính tả không được validate khi khởi động
- Khi nào nên dùng rollback lập trình? — Rollback có điều kiện, các quy tắc nghiệp vụ phức tạp
- Cấu hình rollback toàn cục — như thế nào? — TransactionInterceptor với RuleBasedTransactionAttribute

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "rollbackForClassName = cách an toàn" — thất bại âm thầm khi có lỗi chính tả
- "Bắt exception = rollback tự động" — Spring không thấy các exception đã bị bắt
- "Có thể trộn rollbackFor và noRollbackFor tùy tiện" — các quy tắc xung đột tạo ra hành vi khó dự đoán
