# What happens on OutOfMemoryError? (Điều gì xảy ra khi có OutOfMemoryError?)

## Junior Level

**OutOfMemoryError (OOME)** — lỗi khi Java **không thể cấp phát bộ nhớ** cho một đối tượng.

**Điều gì xảy ra:**
1. Cố gắng cấp phát bộ nhớ → không có không gian
2. GC cố gắng dọn dẹp → vẫn không có không gian
3. OutOfMemoryError được ném ra
4. Luồng yêu cầu bộ nhớ → chết

**Các loại OOME:**
- `Java heap space` — Heap bị tràn
- `Metaspace` — metadata của class bị tràn
- `GC overhead limit exceeded` — GC chạy liên tục

---

## Middle Level

### Cơ chế của OOME

```
1. Allocation Failure → không có bộ nhớ
2. Full GC → cố gắng dọn dẹp
3. SoftReference được dọn dẹp → vẫn không có không gian
4. GC Overhead Limit — ĐÂY LÀ MỘT loại OOME CỤ THỂ (GC overhead limit exceeded).
   Kích hoạt khi JVM dành >98% thời gian cho GC và giải phóng <2% Heap.
   KHÔNG phải tất cả các OOME đều đi qua phép kiểm tra này — nó là một heuristic riêng biệt.
5. → OutOfMemoryError!
```

### Trạng thái Zombie

```
OOME có thể xảy ra ở BẤT KỲ ĐÂU, kể cả trong lúc cấp phát tài nguyên.
Nếu OOME xảy ra trong lúc mở một file → file có thể vẫn còn mở.
Nếu OOME trong lúc acquire một lock → lock sẽ không được release.
⚠️ Các khối finally có thể KHÔNG được thực thi nếu OOME xảy ra trong lúc cấp phát bộ nhớ cho chính stack frame đó.

OOME KHÔNG giết JVM ngay lập tức!
  → Chỉ luồng yêu cầu bị chết
  → Các luồng khác vẫn tiếp tục làm việc
  → NHƯNG: trạng thái có thể bị hỏng!
```

### JVM OOME vs OS OOM Killer

```
JVM OOME:
  → Bạn thấy stack trace trong logs
  → Có một heap dump

OS OOM Killer (Docker/K8s):
  → Tiến trình đơn giản là biến mất
  → Trong dmesg: "Out of memory: Kill process"
  → Không có logs Java nào!
  → Nguyên nhân: RSS > giới hạn của container
```

### Production: Fail-Fast

```bash
# Bắt buộc trong production:
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/var/log/dumps/
-XX:+ExitOnOutOfMemoryError

# → Khi OOME: dump + thoát
# → Orchestrator sẽ restart
# → Không có trạng thái zombie
```

## Senior Level

### Cái chết của luồng và sự hỏng hóc (Corruption)

```
OOME trong một luồng đang giữ một Lock:
  → Lock không được release
  → Các luồng khác chờ mãi mãi
  → Deadlock!

OOME trong một ConcurrentHashMap:
  → Map ở trạng thái trung gian (intermediate)
  → Các thao tác tiếp theo → hành vi không xác định (undefined behavior)
```

### Native Memory OOME

```
Rò rỉ DirectByteBuffer:
  → Heap trống
  → Native Memory = 100%
  → OOM Killer giết tiến trình
  → Không có logs Java nào!

Chẩn đoán:
  -XX:NativeMemoryTracking=detail
  dmesg | grep -i oom
```

### Chẩn đoán theo loại

| Loại lỗi            | Nguyên nhân               | Giải pháp          |
| ------------------- | ------------------------- | ------------------ |
| **Heap space**      | Rò rỉ hoặc -Xmx nhỏ       | Phân tích dump bằng MAT |
| **GC overhead**     | Heap gần đầy              | GC Logs, tối ưu    |
| **Metaspace**       | ClassLoader leak          | jcmd VM.metaspace  |
| **Direct buffer**   | Rò rỉ Netty/NIO           | NMT                |
| **Native thread**   | Giới hạn luồng của OS     | ulimit -u          |

### Phân tích Heap Dump

```bash
# Tự động dump khi OOME
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/dumps/

# Phân tích trong Eclipse MAT:
→ Dominator Tree
→ Path to GC Roots
→ Tìm ra rò rỉ
```

### Best Practices

1. **Không bao giờ catch OOME** trong code nghiệp vụ
2. **ExitOnOutOfMemoryError** trong production
3. **HeapDumpOnOutOfMemoryError** — bắt buộc
4. **HeapDumpPath** → một volume bên ngoài
5. **Giám sát RSS** và Native Memory
6. **NMT** cho các rò rỉ off-heap
7. **Fail-fast** > trạng thái zombie

### Tóm tắt cho Senior

- **OOME** ≠ JVM chết ngay lập tức
- **Trạng thái zombie** = các lock và cấu trúc bị hỏng
- **OS OOM Killer** = không có logs, tiến trình biến mất
- **Fail-fast** = ExitOnOutOfMemoryError
- **Heap Dump** = công cụ chẩn đoán chính
- **Native Memory** ≠ Heap (cần NMT)
- **Không bao giờ catch OOME**

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- OOME: JVM không thể cấp phát bộ nhớ → GC cố gắng dọn dẹp → SoftReference được dọn dẹp → vẫn không có → OutOfMemoryError
- OOME chỉ giết luồng yêu cầu, KHÔNG phải toàn bộ JVM; các luồng khác làm việc trong trạng thái bị hỏng (zombie state)
- Trạng thái zombie: OOME trong lúc acquire lock → lock không được release → deadlock; OOME trong ConcurrentHashMap → undefined behavior
- JVM OOME vs OS OOM Killer: JVM OOME cho stack trace và dump; OS OOM Killer (Docker/K8s) — tiến trình biến mất, không có logs
- GC Overhead Limit: một loại OOME cụ thể; kích hoạt khi JVM dành >98% thời gian cho GC và giải phóng <2% Heap
- `ExitOnOutOfMemoryError` + `HeapDumpOnOutOfMemoryError` — bắt buộc trong production: dump + thoát → orchestrator restart
- Các khối finally có thể KHÔNG được thực thi nếu OOME xảy ra trong lúc cấp phát bộ nhớ cho chính stack frame đó

**Các câu hỏi phụ thường gặp:**
- **Tại sao không nên catch OOME trong code nghiệp vụ?** — Trạng thái bị hỏng: lock không được release, Map ở trạng thái trung gian; ứng dụng không đáng tin cậy
- **JVM OOME khác OS OOM Killer như thế nào?** — JVM OOME: stack trace trong logs, có dump; OS OOM Killer: `dmesg | grep oom`, tiến trình bị giết qua SIGKILL, không có logs Java
- **Trạng thái zombie là gì?** — JVM tiếp tục làm việc sau OOME của một luồng, nhưng với các lock/cấu trúc bị hỏng → undefined behavior
- **Tại sao HeapDumpPath nên nằm trên một volume bên ngoài?** — Trong Kubernetes, ephemeral storage bị lấp đầy bởi dump → pod sẽ không restart

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Tôi catch OOME và tiếp tục làm việc" — trạng thái zombie, dữ liệu bị hỏng; tốt hơn là fail-fast
- "OOME giết JVM ngay lập tức" — chỉ luồng bị chết; JVM tiếp tục trong trạng thái bị hỏng
- "OS OOM Killer là một vấn đề của Java" — đó là quyết định của OS; nguyên nhân: RSS > giới hạn của container, không phải `-Xmx`
