# How to properly work with collections in immutable classes? (Cách làm việc đúng cách với collection trong immutable class?)

---

## Basic Level

Collection là phần phức tạp nhất của các immutable class. Bạn cần bảo vệ collection ở mọi giai đoạn.

### Ba Quy Tắc

**1. Sao chép khi đầu vào (constructor)**
```java
public final class Group {
    private final List<String> members;

    public Group(List<String> members) {
        this.members = List.copyOf(members); // sao chép!
    }
}
```

**2. Trả về một phiên bản được bảo vệ (getter)**
```java
public List<String> getMembers() {
    return members; // List.copyOf đã trả về một list bất biến rồi
}
```

**3. Không lưu trữ các tham chiếu trực tiếp**
```java
// TỒI
public Group(List<String> members) {
    this.members = members; // tham chiếu trực tiếp — có thể bị sửa đổi từ bên ngoài
}
```

## Intermediate Level

### Bảo Vệ Khi Tạo
```java
// Java 10+ — lựa chọn tốt nhất
this.list = List.copyOf(input);

// Java 8
this.list = Collections.unmodifiableList(new ArrayList<>(input));
```

### Bảo Vệ Khi Đọc
- Nếu trường đã bất biến rồi (`List.copyOf`) — có thể trả về trực tiếp
- Nếu mutable — bọc: `Collections.unmodifiableList(this.list)`

### Vấn Đề Tính Bất Biến Sâu

`List.copyOf` bảo vệ **container**, nhưng không bảo vệ **các phần tử**:
```java
public record Team(String name, List<User> users) {
    public Team {
        users = List.copyOf(users); // container được bảo vệ
    }
}
// Nhưng: team.users().get(0).setName("...") — CÓ THỂ!
```

**Giải pháp** — sao chép sâu:
```java
public record Team(String name, List<User> users) {
    public Team {
        users = users.stream()
            .map(u -> new User(u.getName(), u.getRole())) // sao chép mỗi cái
            .toList();
    }
}
```

Sao chép sâu chỉ cần thiết nếu các phần tử của collection là mutable.
Với String, Integer, Record — `List.copyOf()` là đủ.

### Các Thư Viện Chuyên Dụng

- **Vavr** — các collection persistent (structural sharing)
- **Guava** — `ImmutableList`, `ImmutableMap`

## Advanced Level

### Phân Biệt Unmodifiable Và Immutable

| Đặc điểm            | Unmodifiable Wrapper  | Immutable Copy   |
| -------------------- | ---------------------- | ----------------- |
| Sao chép dữ liệu     | Không                   | Có                |
| Liên kết với bản gốc | Sống                    | Bị phá vỡ         |
| Tốc độ tạo           | O(1)                    | O(n)              |
| An toàn              | Một phần                | Đầy đủ            |

```java
List<String> original = new ArrayList<>(List.of("A"));
List<String> unmod = Collections.unmodifiableList(original);
original.set(0, "B"); // unmod cũng thay đổi! — tham chiếu sống

List<String> immutable = List.copyOf(original);
original.set(0, "C"); // immutable vẫn giữ "B" — bản sao độc lập
```

### Hiệu Năng Sao Chép

- `List.copyOf()` được tối ưu hóa: nếu đầu vào đã bất biến rồi, trả về cùng object —
  tiết kiệm bộ nhớ và CPU
- Với các collection lớn trong hot path, cân nhắc **Vavr** với $O(\log n)$ qua structural sharing
- Sao chép sâu — $O(n \times m)$, với m = độ sâu của đồ thị

### Record Và Collection
```java
public record UserGroup(String name, List<String> members) {
    public UserGroup {
        members = List.copyOf(members); // bắt buộc trong compact constructor
    }
}
```

### Tóm Tắt Cho Advanced
- Luôn phá vỡ liên kết với collection gốc thông qua sao chép
- Phân biệt "unmodifiable wrapper" với "immutable copy"
- Các collection của JDK — chỉ có Shallow Immutability
- Với dữ liệu lớn — các cấu trúc dữ liệu persistent (Vavr)
- Deep Copy là bắt buộc với các phần tử collection mutable

## Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Ba quy tắc: sao chép trong constructor, trả về phiên bản được bảo vệ từ getter, không lưu trữ tham chiếu trực tiếp
- `List.copyOf(input)` — lựa chọn tốt nhất (Java 10+), tạo một bản sao bất biến độc lập
- Tính bất biến sâu: nếu các phần tử là mutable, cần clone từng cái qua stream.map
- Unmodifiable vs Immutable: wrapper (O(1), liên kết) so với bản sao (O(n), độc lập)
- Record: phải sao chép các collection trong compact constructor
- `List.copyOf` được tối ưu hóa: nếu đầu vào đã bất biến rồi, trả về cùng object

**Các câu hỏi phụ thường gặp:**
- *List.copyOf có bảo vệ các phần tử không?* — Không, chỉ bảo vệ container; các phần tử mutable vẫn có thể bị sửa đổi
- *Khi nào KHÔNG cần sao chép sâu?* — Khi các phần tử tự chúng đã bất biến (String, Integer, Record)
- *UnmodifiableList vs List.copyOf trong getter?* — Nếu trường đã là List.copyOf — trả về trực tiếp; nếu mutable — unmodifiableList
- *Vavr vs các collection của JDK?* — Vavr: structural sharing O(log n), JDK: sao chép toàn bộ O(n)

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "List.copyOf = bảo vệ hoàn toàn" — nó nông (shallow), các phần tử vẫn như cũ
- "Có thể trả về bản gốc nếu collection là private" — bên gọi có thể vẫn giữ một tham chiếu đến bản gốc
- "Sao chép sâu luôn cần thiết" — thừa thãi với các phần tử String/Integer
- "UnmodifiableList trong constructor — bảo vệ" — đó là một wrapper, không phải một bản sao
