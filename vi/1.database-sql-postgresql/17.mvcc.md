# How does MVCC work in PostgreSQL? (MVCC hoạt động như thế nào trong PostgreSQL?)

## 🟢 Junior Level

**MVCC (Multi-Version Concurrency Control — Kiểm soát đồng thời đa phiên bản)** — một cơ chế cho phép PostgreSQL hiển thị cho mỗi người dùng **phiên bản dữ liệu riêng của họ**, mà không chặn việc đọc trong lúc ghi.

**Ví dụ minh họa đơn giản:** Hãy tưởng tượng Google Docs. Khi bạn chỉnh sửa một tài liệu, những người khác vẫn thấy phiên bản cũ cho đến khi bạn lưu. Trong lúc đó, họ vẫn có thể tiếp tục đọc — họ không cần phải đợi bạn hoàn tất.

**Sự khác biệt so với các RDBMS khác:** Oracle sử dụng undo segments, SQL Server sử dụng tempdb. PostgreSQL lưu trữ TẤT CẢ các phiên bản trong cùng một bảng → đơn giản hơn, nhưng gây ra bloat (phình bảng) từ UPDATE/DELETE.

**Ý tưởng cốt lõi:**
- Khi `UPDATE`, PostgreSQL không ghi đè lên dòng đó, mà tạo ra một **phiên bản mới**
- Khi `DELETE`, dòng đó không bị xóa vật lý, mà chỉ được đánh dấu là đã xóa
- Mỗi transaction chỉ nhìn thấy những dòng đã tồn tại tại thời điểm nó bắt đầu

**Ví dụ:**
```sql
-- Transaction 1                    -- Transaction 2
BEGIN;                              BEGIN;
SELECT * FROM users WHERE id=1;     -- Thấy: name='Ivan'

UPDATE users SET name='Petr'
WHERE id=1;                         -- Vẫn thấy: name='Ivan'!

SELECT * FROM users WHERE id=1;     -- Thấy: name='Petr'
COMMIT;

                                    SELECT * FROM users WHERE id=1;
                                    -- Bây giờ thấy: name='Petr'
```

**Tại sao cần thiết:**
- Người đọc không chặn người ghi
- Người ghi không chặn người đọc
- Không có vấn đề "dirty read" (đọc dữ liệu bẩn)

## 🟡 Middle Level

### Cách hoạt động bên trong

Mỗi dòng (tuple) chứa các **trường hệ thống ẩn**:

| Trường    | Mô tả                                            |
| -------- | ------------------------------------------------------ |
| **xmin** | ID của transaction đã tạo ra dòng này             |
| **xmax** | ID của transaction đã xóa dòng này (0 = chưa bị xóa) |
| **ctid** | Địa chỉ vật lý của dòng (số hiệu page, số hiệu dòng)  |

**Cơ chế:**
```sql
-- Trạng thái ban đầu
-- Bảng users:
-- xmin=100, xmax=0, name='Ivan', ctid=(1,1)

-- Transaction 101 thực hiện UPDATE
UPDATE users SET name='Petr' WHERE id=1;

-- Phiên bản mới của dòng:
-- xmin=101, xmax=0, name='Petr', ctid=(1,2)
-- Phiên bản cũ:
-- xmin=100, xmax=101, name='Ivan', ctid=(1,1) ← xmax=101 (đã đánh dấu)

-- Transaction 102 (bắt đầu trước 101):
-- → Thấy dòng có xmin=100 (xmax=101 chưa được commit đối với nó)
-- → name='Ivan'

-- Transaction 103 (bắt đầu sau 101):
-- → Thấy dòng có xmin=101 (đã được commit)
-- → name='Petr'
```

### Snapshots (Ảnh chụp)

Khi một transaction bắt đầu một SELECT, nó chụp lại một **snapshot** của trạng thái cơ sở dữ liệu:

```
Snapshot:
  xmin = 100  ← Tất cả các transaction < 100 đã được commit
  xmax = 105  ← Tất cả các transaction >= 105 chưa bắt đầu
  xip_list = [101, 102, 103]  ← Các transaction đang hoạt động

Quy tắc khả kiến (Visibility rule):
  Một dòng được coi là khả kiến (visible) nếu:
    - xmin của nó < snapshot.xmin HOẶC xmin nằm trong xip_list (vẫn đang hoạt động)
    - xmax của nó = 0 HOẶC xmax >= snapshot.xmax
```

### UPDATE = DELETE + INSERT

```sql
-- Đây KHÔNG phải là cập nhật tại chỗ (in-place update)!
UPDATE users SET name='Petr' WHERE id=1;

-- Thực tế:
-- 1. Một phiên bản MỚI của dòng được tạo ra (name='Petr')
-- 2. Phiên bản cũ được đánh dấu (xmax = transaction hiện tại)
-- 3. Các index được cập nhật (tham chiếu đến ctid mới)
```

### VACUUM: dọn dẹp các dòng đã chết

```sql
-- Sau UPDATE/DELETE, các dòng "đã chết" (dead tuples) vẫn còn tồn tại
-- VACUUM loại bỏ chúng, giải phóng không gian

-- Kiểm tra các dòng đã chết
SELECT
    schemaname,
    relname,
    n_live_tup,    -- Các dòng còn sống
    n_dead_tup,    -- Các dòng đã chết
    last_vacuum
FROM pg_stat_user_tables
WHERE relname = 'users';

-- Chạy thủ công
VACUUM users;
```

### Các vấn đề thường gặp

1. **Bloat (Phình bảng)**
   ```sql
   -- Bảng chiếm dung lượng nhiều hơn 10 lần so với mức cần thiết
   -- Nguyên nhân: quá nhiều dead tuples, VACUUM không theo kịp

   -- Giải pháp
   VACUUM FULL users;  -- ⚠️ Khóa bảng!
   -- hoặc
   pg_repack -t users; -- Không khóa
   ```

2. **Transaction dài chặn VACUUM**
   ```sql
   -- Nếu một transaction đã mở suốt 2 giờ
   -- VACUUM không thể loại bỏ những dòng mà nó có thể nhìn thấy

   -- Tìm các transaction dài
   SELECT pid, now() - xact_start as duration, query
   FROM pg_stat_activity
   WHERE state = 'active'
   ORDER BY xact_start ASC;
   ```

3. **Transaction ID Wraparound (Tràn số ID transaction)**
   ```sql
   -- XID là một số 32-bit (4 tỷ)
   -- Nếu các dòng cũ không được "đóng băng" (frozen) → xảy ra tràn số

   -- Kiểm tra tuổi (age)
   SELECT datname, age(datfrozenxid)
   FROM pg_database
   ORDER BY age DESC;

   -- > 200 triệu → cần VACUUM khẩn cấp!
   -- > 1.5 tỷ → cơ sở dữ liệu sẽ chuyển sang chế độ READ ONLY
   ```

## 🔴 Senior Level

### Tối ưu hóa Hint Bits

**Vấn đề:** Việc kiểm tra trạng thái transaction thông qua CLOG (Commit Log) tốn kém (phải đọc từ đĩa).

**CLOG** — các file trong `pg_xact/`, nơi mỗi transaction = 2 bit (IN_PROGRESS/COMMITTED/ABORTED). Đây KHÔNG phải là WAL. Việc đọc CLOG = vài micro giây, nhưng với hàng triệu dòng → có thể mất vài giây.

**Giải pháp:** PostgreSQL sử dụng **Hint Bits** — 2 bit trong header của dòng:

```
Heap Tuple Header:
  ...
  t_infomask:
    HEAP_XMIN_COMMITTED    ← xmin đã được commit
    HEAP_XMIN_INVALID      ← xmin đã bị hủy (aborted)
    HEAP_XMAX_COMMITTED    ← xmax đã được commit
    HEAP_XMAX_INVALID      ← xmax đã bị hủy (aborted)
  ...
```

**Cơ chế:**
```
1. Người đọc đầu tiên kiểm tra trạng thái xmin trong CLOG
2. Đặt Hint Bits trong header của dòng
3. Tất cả những người đọc tiếp theo kiểm tra Hint Bits ngay lập tức
   → Không cần tra cứu CLOG nữa!

Điều này được gọi là "Hint Bits propagation" (lan truyền Hint Bits) hoặc "Lazy hinting" (đánh dấu lười biếng)
```

**Lưu ý quan trọng:** Hint Bits KHÔNG được ghi vào WAL! Sau khi crash, chúng sẽ được tính toán lại.

### Multixacts

Khi nhiều transaction cùng khóa (lock) một dòng (`SELECT FOR SHARE`):

```sql
-- Transaction 1: SELECT FOR SHARE → khóa
-- Transaction 2: SELECT FOR SHARE → cũng khóa

-- xmax không thể lưu hai ID cùng lúc!
-- Giải pháp: MultiXact ID

-- xmax lưu một tham chiếu đến pg_multixact
-- pg_multixact lưu danh sách các transaction: [101, 102]
```

**Vấn đề:** Multixact cũng "già đi" giống như XID → cần VACUUM.

### Serializable Snapshot Isolation (SSI)

PostgreSQL triển khai **SERIALIZABLE** mà không cần khóa đọc (read locks):

```sql
-- Mức SERIALIZABLE trong PG ≠ SERIALIZABLE trong các RDBMS khác
-- PG sử dụng SSI (Serializable Snapshot Isolation)

-- Cơ chế:
-- 1. Theo dõi các SIRead lock (predicate lock)
-- 2. Phát hiện các chu trình xung đột RW (RW-conflict cycle)
-- 3. Nếu tìm thấy một chu trình → hủy một trong các transaction với lỗi:
--    ERROR: could not serialize access due to read/write dependencies
```

**Ví dụ:**
```sql
-- Transaction 1                           -- Transaction 2
SET TRANSACTION ISOLATION LEVEL
  SERIALIZABLE;                            SET TRANSACTION ISOLATION LEVEL
                                             SERIALIZABLE;
SELECT SUM(balance) FROM accounts;
                                           UPDATE accounts SET balance = 1000
                                             WHERE id = 1;
UPDATE accounts SET balance = 500
  WHERE id = 2;
COMMIT;
                                           COMMIT;  ← ERROR: serialization failure!
```

> ⚠️ **KHÔNG nên dùng SERIALIZABLE trong hệ thống OLTP có tải cao:** với xung đột RW thường xuyên, các transaction liên tục bị rollback. Hãy dùng READ COMMITTED hoặc REPEATABLE READ thay thế.

### HOT (Heap Only Tuple) updates

> **Heap** = vùng lưu trữ chính của các dòng bảng (không phải index). "Heap Only Tuple" = phiên bản mới trên cùng một page, các index không được cập nhật.

**Cơ chế HOT:**

Một tối ưu hóa quan trọng cho UPDATE:

```sql
-- UPDATE thông thường:
-- 1. Dòng mới trong Heap
-- 2. Cập nhật TẤT CẢ các index (ctid mới)
-- 3. Đánh dấu dòng cũ (xmax)

-- HOT UPDATE (nếu điều kiện được thỏa mãn):
-- 1. Dòng mới trong Heap (trên cùng một page!)
-- 2. Các index KHÔNG được cập nhật
-- 3. Một chuỗi HOT được tạo ra: cũ → mới

-- Điều kiện để có HOT:
-- - Các cột bị cập nhật KHÔNG được index
-- - Còn không gian trên page Heap (fillfactor < 100)
```

**Giám sát HOT:**
```sql
SELECT
    relname,
    n_tup_hot_update,     -- Số lần HOT update
    n_tup_upd,            -- Tổng số lần update
    ROUND(100.0 * n_tup_hot_update / NULLIF(n_tup_upd, 0), 2) as hot_pct
FROM pg_stat_user_tables
WHERE n_tup_upd > 0;

-- hot_pct > 70% → tuyệt vời
-- hot_pct < 20% → có vấn đề (quá nhiều lần update trên cột có index)
```

### CLOG (pg_xact)

```
pg_xact/ — thư mục chứa các file 256 KB
Mỗi transaction = 2 bit:
  00 = IN_PROGRESS
  01 = COMMITTED
  10 = ABORTED
  11 = SUB_COMMITTED

-- 4 transaction mỗi byte
-- 256 KB = 1 tỷ transaction
-- Các file bị xóa sau VACUUM + Freeze
```

### XID Wraparound: phân tích chuyên sâu

```sql
-- XID 32-bit = 4,294,967,296 transaction
-- So sánh XID: số học tuần hoàn (cyclic arithmetic)

-- autovacuum thực hiện "Freezing" (đóng băng):
-- 1. Tìm các dòng có xmin < freeze_limit
-- 2. Thay xmin bằng FrozenXID (một giá trị đặc biệt)
-- 3. FrozenXID luôn được coi là "thuộc quá khứ"
-- "Freezing" = thay xmin bằng FrozenXID, LUÔN LUÔN được coi là "thuộc quá khứ".
-- Một dòng đã được frozen thì khả kiến (visible) với bất kỳ transaction nào.
-- Giống như một ngày tháng "1900" trên một tài liệu — được đảm bảo là "cũ hơn" bất kỳ transaction hiện tại nào.

-- Giám sát:
SELECT
    datname,
    age(datfrozenxid),
    ROUND(100.0 * age(datfrozenxid) / 2000000000, 2) as pct_to_wraparound
FROM pg_database;

-- > 1.5 tỷ = 75% → nguy cấp!
-- 2 tỷ = 100% → cơ sở dữ liệu chuyển sang chế độ READ ONLY
```

### Các trường hợp đặc biệt (Edge Cases)

1. **Các transaction chạy trong thời gian dài**
   ```sql
   -- Trên replica: hot_standby_feedback = on
   -- Replica yêu cầu master không xóa những dòng mà nó đang đọc
   -- → Master tích lũy dead tuples → Bloat!
   ```

2. **TOAST và MVCC**
   ```sql
   -- Các trường lớn (text, bytea) được lưu trong các bảng TOAST
   -- Các dòng TOAST cũng được đánh phiên bản (versioned)
   -- Nhưng TOAST KHÔNG sử dụng MVCC khi đọc!
   -- → Có thể trả về dữ liệu từ một dòng đã bị xóa trong một số trường hợp hiếm gặp
   ```

3. **Visibility Map (Bản đồ khả kiến)**
   ```sql
   -- VM: bitmap của các page mà TẤT CẢ các dòng đều khả kiến với mọi người
   -- Được sử dụng cho:
   -- 1. Index Only Scan (kiểm tra khả kiến mà không cần vào Heap)
   -- 2. VACUUM (bỏ qua các page "sạch")

   -- Được cập nhật trong quá trình VACUUM
   ```

### Ảnh hưởng đến hiệu năng

| Thao tác  | Ảnh hưởng của MVCC                                |
| ---------- | ------------------------------------------ |
| **SELECT** | Không bị chặn, tạo ra Snapshot              |
| **INSERT** | Tạo dòng mới (xmin = hiện tại)           |
| **UPDATE** | Tạo dòng mới + đánh dấu dòng cũ (xmax)             |
| **DELETE** | Đánh dấu dòng (xmax = hiện tại)                 |
| **VACUUM** | Loại bỏ các dòng có xmax < oldest_active_xid |

### Kinh nghiệm Production

**Tình huống thực tế #1: Bloat từ một transaction dài**
- Nhà phân tích mở một transaction rồi đi ăn trưa (4 giờ)
- VACUUM không thể loại bỏ dead tuples
- Bảng phình từ 10 GB lên 80 GB
- Giải pháp: `SELECT pg_terminate_backend(pid)` → VACUUM FULL

**Tình huống thực tế #2: Khủng hoảng Wraparound**
- autovacuum bị tắt "vì lý do hiệu năng"
- age(datfrozenxid) = 1.9 tỷ (95%)
- Cơ sở dữ liệu bắt đầu cảnh báo trong log
- Giải pháp: chạy khẩn cấp `VACUUM FREEZE` trên toàn bộ cơ sở dữ liệu
- Bài học: không bao giờ được tắt autovacuum!

### Giám sát (Monitoring)

```sql
-- 1. Các dead tuple
SELECT relname, n_dead_tup, last_vacuum, last_autovacuum
FROM pg_stat_user_tables
WHERE n_dead_tup > 10000
ORDER BY n_dead_tup DESC;

-- 2. Tuổi XID
SELECT datname, age(datfrozenxid)
FROM pg_database
ORDER BY age DESC;

-- 3. Các transaction dài
SELECT pid, now() - xact_start as duration, state, query
FROM pg_stat_activity
WHERE xact_start < now() - INTERVAL '1 hour'
ORDER BY xact_start;

-- 4. Tỷ lệ HOT
SELECT
    relname,
    ROUND(100.0 * n_tup_hot_update / NULLIF(n_tup_upd, 0), 2) as hot_pct
FROM pg_stat_user_tables
WHERE n_tup_upd > 1000
ORDER BY hot_pct ASC;
```

### Best Practices (Thực hành tốt nhất)

1. **Không giữ transaction mở** lâu hơn mức cần thiết
2. **autovacuum — KHÔNG được tắt!** Hãy tinh chỉnh nó, nhưng đừng tắt nó
3. **fillfactor = 70-80** cho các bảng được cập nhật thường xuyên → có nhiều HOT hơn
4. **Tạo index một cách có ý thức** — mỗi index đều làm mất tác dụng HOT đối với cột đó
5. **Giám sát age(datfrozenxid)** — ngăn ngừa wraparound
6. **pg_repack** để chống lại Bloat mà không cần khóa
7. **hot_standby_feedback = on** → giám sát Bloat trên master
8. **VACUUM FULL** chỉ nên chạy trong khung giờ bảo trì (locks!)

### Tóm tắt cho Senior

- **MVCC** = phiên bản dòng = xmin/xmax, không chặn việc đọc
- **Hint Bits** tăng tốc các lần đọc tiếp theo mà không cần CLOG
- **HOT** = tối ưu hóa UPDATE mà không cần cập nhật index
- **SSI** = SERIALIZABLE mà không cần khóa đọc (PG rất độc đáo!)
- **XID Wraparound** — một mối đe dọa thực sự → giám sát age()
- **Các transaction dài** = nguyên nhân chính gây ra Bloat
- **VACUUM** không làm giảm kích thước file → hãy dùng **pg_repack**
- **Visibility Map** rất quan trọng đối với Index Only Scan

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- MVCC: mỗi dòng có xmin (đã tạo) và xmax (đã xóa)
- Snapshot: một transaction nhìn thấy những dòng đã tồn tại khi nó bắt đầu
- UPDATE = DELETE + INSERT (phiên bản dòng mới, phiên bản cũ → dead tuple)
- Hint Bits: 2 bit trong header dòng → tránh việc đọc CLOG sau người đọc đầu tiên
- HOT (Heap Only Tuple): UPDATE mà không cần cập nhật index (nếu cột không được index + còn chỗ trên page)
- SSI (Serializable Snapshot Isolation): SERIALIZABLE mà không cần khóa đọc
- XID Wraparound: XID 32-bit → 4 tỷ transaction → autovacuum thực hiện Freeze
- Visibility Map: bitmap của các page "sạch" → dùng cho Index Only Scan + VACUUM bỏ qua
- CLOG (pg_xact): 2 bit cho mỗi transaction → IN_PROGRESS/COMMITTED/ABORTED
- Transaction dài → VACUUM không thể loại bỏ dead tuples → Bloat

**Các câu hỏi phụ thường gặp:**
- "Điều gì xảy ra nếu autovacuum bị tắt?" → XID Wraparound → cơ sở dữ liệu chuyển sang chế độ READ ONLY
- "Tại sao VACUUM không làm giảm kích thước file?" → Nó giải phóng không gian cho dữ liệu mới, không trả lại cho hệ điều hành
- "HOT hoạt động như thế nào?" → Phiên bản mới trên cùng một page → các index không được cập nhật
- "hot_standby_feedback là gì?" → Replica yêu cầu master không xóa dòng → gây ra Bloat trên master

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "VACUUM làm giảm kích thước file bảng" (sai, cần VACUUM FULL hoặc pg_repack)
- ❌ "autovacuum có thể tắt để tăng hiệu năng" (Wraparound → READ ONLY!)
- ❌ "MVCC chặn việc đọc trong lúc ghi" (sai, người đọc không chặn người ghi!)
- ❌ "Hint Bits được ghi vào WAL" (sai, chúng được tính toán lại sau khi crash)
