# # What is a Correlated Subquery? (Correlated subquery (truy vấn con tương quan) là gì?)

## 🟢 Junior Level

**Correlated subquery** là một subquery (truy vấn con) phụ thuộc vào các giá trị từ truy vấn bên ngoài. Nó thực thi **cho mỗi dòng** của truy vấn bên ngoài.

**Tại sao cần hiểu điều này:** những subquery như vậy trông rất thanh lịch và dễ hiểu một cách trực quan, nhưng trên các bảng lớn chúng có thể làm tê liệt cơ sở dữ liệu — subquery thực thi cho mỗi dòng của truy vấn bên ngoài, dẫn đến độ phức tạp O(N × M).

**Ví dụ minh họa đơn giản:** Hãy tưởng tượng bạn đang kiểm tra từng tài liệu trong một thư mục. Với mỗi tài liệu, bạn mở một thư mục riêng biệt và tìm kiếm các file liên quan ở đó. Nó giống như một vòng lặp trong code: với mỗi phần tử → thực hiện một lượt tìm kiếm.

**Ví dụ:**
```sql
-- Với mỗi người dùng, tìm đơn hàng gần đây nhất của họ
SELECT u.name,
       (SELECT o.amount
        FROM orders o
        WHERE o.user_id = u.id  -- ← phụ thuộc vào dòng bên ngoài!
        ORDER BY o.created_at DESC
        LIMIT 1) as last_order
FROM users u;
```

**Cách hoạt động:**
1. Lấy dòng đầu tiên từ `users`
2. Thực thi subquery cho `user_id` này
3. Lấy dòng thứ hai từ `users`
4. Thực thi subquery cho `user_id` này
5. ... và cứ tiếp tục như vậy cho mỗi dòng

**Khi nào nên sử dụng:**
- Khi bạn cần tính toán riêng biệt điều gì đó cho từng dòng
- Cho các trường hợp đơn giản với bảng nhỏ
- Thường tốt hơn nên thay thế bằng JOIN hoặc window function

## 🟡 Middle Level

### Mô hình thực thi logic (Logical Execution Model)

Mô hình cổ điển: **O(N × M)** — subquery thực thi N lần (theo số dòng trong truy vấn bên ngoài).

```sql
-- Correlated subquery trong SELECT
SELECT u.name,
       (SELECT SUM(amount) FROM orders o WHERE o.user_id = u.id) as total
FROM users u;

-- Về mặt logic điều này giống như:
for user in users:              -- 1,000,000 dòng
    total = SELECT SUM(amount)  -- Thực thi 1,000,000 lần!
        FROM orders
        WHERE user_id = user.id
    print(user.name, total)
```

### Thực tế vật lý: Decorrelation (Khử tương quan)

PostgreSQL cố gắng "mở gấp" (unfold) các correlated subquery:

```sql
-- Truy vấn gốc
SELECT * FROM users u
WHERE EXISTS (
    SELECT 1 FROM orders o WHERE o.user_id = u.id AND amount > 100
);

-- Sau khi decorrelation:
-- Plan: Hash Semi-Join (thực thi MỘT LẦN cho tất cả các dòng!)
-- Độ phức tạp: O(N + M) thay vì O(N × M)
```

### SubPlan vs InitPlan trong EXPLAIN

**SubPlan** — thực thi cho mỗi dòng (không tốt):
```sql
EXPLAIN SELECT u.name,
       (SELECT SUM(amount) FROM orders o WHERE o.user_id = u.id)
FROM users u;

-- Plan:
-- Seq Scan on users
--   SubPlan 1
--     -> Aggregate
--        -> Index Scan on orders
-- ⚠️ SubPlan 1 thực thi cho mỗi dòng của users!
```

**InitPlan** — thực thi một lần (tốt):
```sql
EXPLAIN SELECT * FROM users
WHERE amount > (SELECT AVG(amount) FROM orders);

-- Plan:
-- InitPlan 1
--   -> Aggregate (AVG)
--      -> Seq Scan on orders
-- → Seq Scan on users
-- ✅ InitPlan thực thi 1 lần!
```

### Correlated Subquery trong UPDATE và DELETE

Đây là nguyên nhân phổ biến gây ra các thao tác chậm:

```sql
-- ❌ KHÔNG TỐT: correlated subquery trong UPDATE
UPDATE orders o SET status = 'OLD'
WHERE created_at < (
    SELECT MIN(created_at)
    FROM users u
    WHERE u.id = o.user_id
);
-- Với mỗi đơn hàng → một subquery!

-- ✅ TỐT: UPDATE với FROM (cú pháp giống như JOIN)
UPDATE orders o SET status = 'OLD'
FROM users u
WHERE o.user_id = u.id
  AND o.created_at < u.min_created_at;
-- Plan: Hash Join (nhanh hơn nhiều!)
```

### EXISTS: Những điều tinh tế quan trọng

```sql
-- Hai truy vấn này là TƯƠNG ĐƯƠNG trong PostgreSQL:
EXISTS (SELECT 1 FROM orders WHERE user_id = u.id)
EXISTS (SELECT * FROM orders WHERE user_id = u.id)
EXISTS (SELECT amount FROM orders WHERE user_id = u.id)

-- Optimizer bỏ qua danh sách SELECT bên trong EXISTS
-- Nó chỉ quan tâm đến việc có ít nhất một dòng tồn tại hay không
-- Hãy viết theo phong cách mà nhóm của bạn ưa thích (thường là SELECT 1)
```

### Các lỗi thường gặp

1. **Scalar subquery trong SELECT trên dữ liệu lớn**
   ```sql
   -- ❌ 1 triệu người dùng → 1 triệu subquery
   SELECT u.name,
          (SELECT COUNT(*) FROM orders WHERE user_id = u.id) as orders_count
   FROM users u;

   -- ✅ Thay thế bằng JOIN + GROUP BY
   SELECT u.name, COUNT(o.id) as orders_count
   FROM users u
   LEFT JOIN orders o ON u.id = o.user_id
   GROUP BY u.id, u.name;
   ```

2. **Correlated UPDATE không có index**
   ```sql
   -- ❌ Nếu orders.user_id không có index → Seq Scan trong một vòng lặp!
   UPDATE users u SET total_orders =
       (SELECT COUNT(*) FROM orders o WHERE o.user_id = u.id);

   -- ✅ Trước tiên hãy tạo một index
   CREATE INDEX idx_orders_user_id ON orders(user_id);
   ```

3. **Bỏ qua Memoize (PG 14+)**
   ```sql
   -- Trên PG 14+ với Memoize, nó có thể nhanh ngay cả khi dùng LATERAL
   -- Hãy kiểm tra EXPLAIN, đừng vội tối ưu hóa quá sớm
   ```

### Các giải pháp thay thế

| Tình huống                 | Correlated Subquery    | Giải pháp thay thế          |
| ------------------------- | ---------------------- | --------------------- |
| Tổng hợp theo từng dòng       | Subquery trong SELECT     | **JOIN + GROUP BY**  |
| Tìm một giá trị duy nhất         | Subquery với LIMIT 1  | **LATERAL JOIN**     |
| Kiểm tra sự tồn tại           | Subquery trong WHERE      | **EXISTS (Semi-Join)** |
| Logic phức tạp theo từng dòng     | Correlated subquery    | **Window Functions** |

### Ví dụ thực tiễn

```sql
-- ❌ Correlated subquery (chậm)
SELECT u.name,
       (SELECT AVG(amount) FROM orders WHERE user_id = u.id) as avg_amount
FROM users u
WHERE (SELECT AVG(amount) FROM orders WHERE user_id = u.id) > 100;

-- ✅ Window function (nhanh)
-- Một window function chỉ cần một lượt duyệt qua dữ liệu với việc sắp xếp: O(N log N).
-- Một correlated subquery thực thi một truy vấn riêng biệt cho mỗi dòng:
-- O(N × M). Trên một bảng có 1 triệu dòng, điều này tương đương với 1 triệu
-- truy vấn riêng biệt so với một lượt duyệt duy nhất — chênh lệch hàng trăm hoặc hàng nghìn lần.
SELECT name, avg_amount
FROM (
    SELECT u.name,
           AVG(o.amount) OVER(PARTITION BY u.id) as avg_amount
    FROM users u
    INNER JOIN orders o ON u.id = o.user_id
) sub
WHERE avg_amount > 100;
```

## 🔴 Senior Level

### Các cơ chế thực thi vật lý

**1. SubPlan (ngây thơ - naive)**
```
Với mỗi dòng của truy vấn bên ngoài:
  → Thực thi subquery
  → Trả về kết quả

Độ phức tạp: O(N × M)
```

**2. InitPlan (độc lập)**
```
Một lần trước truy vấn chính:
  → Tính toán subquery
  → Lưu kết quả

Truy vấn chính sử dụng kết quả đó
Độ phức tạp: O(M) + O(N)
```

**3. Param (tương quan, nhưng đã được tối ưu)**
```
Subquery nhận một tham số từ dòng bên ngoài
→ Có thể sử dụng index trên tham số đó
→ Có thể được lưu bộ nhớ đệm (Memoize)
```

### Decorrelation (Unnesting)

Optimizer cố gắng biến một correlated subquery thành một JOIN:

```sql
-- Gốc: EXISTS tương quan
SELECT * FROM users u
WHERE EXISTS (
    SELECT 1 FROM orders o WHERE o.user_id = u.id AND o.amount > 100
);

-- Sau khi decorrelation:
-- Hash Semi-Join
--   Hash Cond: (o.user_id = u.id)
--   Hash Filter: (o.amount > 100)

-- Độ phức tạp: O(N + M) thay vì O(N × M)!
```

**Khi nào decorrelation KHÔNG thể thực hiện:**
- Subquery chứa `LIMIT` / `OFFSET`
- Subquery chứa các hàm tổng hợp (aggregate) phụ thuộc vào dòng bên ngoài
- Subquery chứa `ORDER BY` mà không có key có thể decorrelate được

### Memoize Node (PostgreSQL 14+)

**Tối ưu hóa mang tính cách mạng** cho các truy vấn tương quan:

```sql
-- Truy vấn với LATERAL (buộc phải dùng Nested Loop)
SELECT u.name, o.amount
FROM users u
LEFT JOIN LATERAL (
    SELECT amount FROM orders o
    WHERE o.user_id = u.id
    ORDER BY created_at DESC
    LIMIT 1
) o ON true;

-- Plan với Memoize (PG 14+):
-- Nested Loop
--   → Seq Scan on users
--   → Memoize (cache_size: 10MB)
--       → Limit
--          → Index Scan Backward on orders

-- Memoize lưu bộ nhớ đệm:
--   user_id = 1 → amount = 500
--   user_id = 2 → amount = 300
--   user_id = 1 → HIT! (lấy từ cache)
```

**Các chỉ số của Memoize:**
```
Memoize (cost=... rows=...)
  Hits: 950,000     ← lấy từ cache
  Misses: 50,000    ← tính toán lại
  Evictions: 5,000  ← bị đẩy ra khỏi cache (hết chỗ)

Hit rate = 950,000 / 1,000,000 = 95% → tuyệt vời!
Hit rate < 50% → Memoize không giúp ích gì (có quá nhiều key duy nhất)
```

**Các giới hạn của Memoize:**
- Cache bị giới hạn về bộ nhớ (tham số `memoize_cache_size`, mặc định 10MB)
- Chỉ hoạt động trong phạm vi một node Nested Loop duy nhất
- Không giúp ích gì nếu tất cả các key đều duy nhất (0% lặp lại)

### Correlated UPDATE/DELETE: Phân tích chuyên sâu

**Vấn đề:**
```sql
UPDATE orders o SET status = 'OLD'
WHERE created_at < (
    SELECT MIN(created_at)
    FROM users u
    WHERE u.id = o.user_id
);
```

**Điều gì xảy ra:**
```
for order in orders:                      -- 100,000,000 dòng
    min_date = SELECT MIN(created_at)     -- 100,000,000 subquery!
        FROM users
        WHERE id = order.user_id
    if order.created_at < min_date:
        UPDATE order SET status = 'OLD'
```

**Giải pháp thông qua UPDATE FROM:**
```sql
-- Bước 1: Tính toán trước giá trị nhỏ nhất một lần duy nhất
WITH user_min_dates AS (
    SELECT user_id, MIN(created_at) as min_date
    FROM users
    GROUP BY user_id
)
-- Bước 2: JOIN thay vì subquery
UPDATE orders o SET status = 'OLD'
FROM user_min_dates umd
WHERE o.user_id = umd.user_id
  AND o.created_at < umd.min_date;

-- Plan:
-- CTE Scan on user_min_dates
--   → HashAggregate (1 lần)
-- Hash Join
--   → Seq Scan on orders
--   → Hash on user_min_dates
-- Tổng cộng: 2 lượt duyệt thay vì 100,000,000!
```

### EXISTS và NULL: Những lầm tưởng

```sql
-- Lầm tưởng: SELECT 1 nhanh hơn SELECT *
-- Thực tế: OPTIMIZER BỎ QUA DANH SÁCH SELECT trong EXISTS

EXPLAIN EXISTS (SELECT 1 FROM orders WHERE user_id = 1);
EXPLAIN EXISTS (SELECT * FROM orders WHERE user_id = 1);
EXPLAIN EXISTS (SELECT amount, created_at FROM orders WHERE user_id = 1);

-- Cả ba đều cho ra các plan GIỐNG HỆT NHAU!
-- Hãy viết SELECT 1 để dễ đọc (rõ ràng về mặt ngữ nghĩa rằng ta đang kiểm tra sự tồn tại)
```

### Window Function như một giải pháp thay thế

```sql
-- ❌ Correlated subquery cho mỗi dòng
SELECT o.*,
       (SELECT AVG(amount)
        FROM orders o2
        WHERE o2.user_id = o.user_id) as user_avg
FROM orders o;

-- ✅ Window function (một lượt duyệt duy nhất!)
SELECT o.*,
       AVG(amount) OVER(PARTITION BY user_id) as user_avg
FROM orders o;

-- Sự khác biệt:
-- Subquery: O(N × M) — với mỗi dòng, tìm tất cả đơn hàng của người dùng đó
-- Window: O(N log N) — một lượt duyệt duy nhất với sort/hash
```

### Các trường hợp đặc biệt (Edge Cases)

1. **Scalar subquery trả về > 1 dòng**
   ```sql
   -- ❌ Lỗi: more than one row returned by a subquery used as an expression
   SELECT u.name,
          (SELECT amount FROM orders WHERE user_id = u.id) -- 10 đơn hàng!
   FROM users u;

   -- ✅ LIMIT 1 hoặc dùng hàm tổng hợp
   SELECT u.name,
          (SELECT amount FROM orders WHERE user_id = u.id ORDER BY created_at DESC LIMIT 1)
   FROM users u;
   ```

2. **Scalar subquery trả về NULL**
   ```sql
   -- Nếu subquery không tìm thấy dòng nào → NULL
   SELECT u.name,
          (SELECT amount FROM orders WHERE user_id = u.id LIMIT 1)
   FROM users u;
   -- Người dùng không có đơn hàng → NULL

   -- ⚠️ NULL trong phép toán số học → NULL
   SELECT u.name,
          (SELECT SUM(amount) FROM orders WHERE user_id = u.id) + 10
   FROM users u;
   -- Không có đơn hàng: NULL + 10 = NULL!
   -- Giải pháp: COALESCE
   ```

3. **Nhiều correlated subquery**
   ```sql
   -- ❌ 3 subquery cho mỗi dòng → 3N lần thực thi
   SELECT u.name,
          (SELECT COUNT(*) FROM orders WHERE user_id = u.id) as orders_count,
          (SELECT SUM(amount) FROM orders WHERE user_id = u.id) as total_amount,
          (SELECT MAX(created_at) FROM orders WHERE user_id = u.id) as last_order
   FROM users u;

   -- ✅ Một JOIN + GROUP BY duy nhất
   SELECT u.name,
          COUNT(o.id) as orders_count,
          COALESCE(SUM(o.amount), 0) as total_amount,
          MAX(o.created_at) as last_order
   FROM users u
   LEFT JOIN orders o ON u.id = o.user_id
   GROUP BY u.id, u.name;
   ```

### So sánh hiệu năng

| Cách tiếp cận                  | Độ phức tạp        | Khi nào sử dụng                            |
| ------------------------- | ----------------- | -------------------------------------- |
| **SubPlan**               | O(N × M)          | **Nên tránh** trên dữ liệu lớn                |
| **InitPlan**              | O(M) + O(N)       | Subquery không phụ thuộc vào dòng bên ngoài   |
| **Decorrelated (Semi-Join)** | O(N + M)       | EXISTS / IN có decorrelation         |
| **Memoize (PG 14+)**      | O(N × log M) với cache | LATERAL có các key lặp lại         |
| **Window Function**       | O(N log N)        | Tổng hợp theo từng dòng                    |
| **UPDATE FROM**           | O(N + M)          | Correlated UPDATE                      |

### Kinh nghiệm Production

**Tình huống thực tế #1: SubPlan làm tê liệt DB**
- Hệ thống CRM: tính tổng giao dịch cho mỗi liên hệ
- Truy vấn: scalar subquery trong SELECT (50,000 liên hệ)
- Thời gian: 12 phút (50,000 subquery đến orders)
- EXPLAIN: `SubPlan 1 → Index Scan (thực thi 50,000 lần)`
- Giải pháp:
  ```sql
  SELECT c.*, COALESCE(SUM(o.amount), 0) as total_deals
  FROM contacts c
  LEFT JOIN orders o ON c.id = o.contact_id
  GROUP BY c.id;
  ```
- Kết quả: 800ms (nhanh hơn 900 lần)

**Tình huống thực tế #2: Memoize cứu vãn LATERAL**
- API: 3 đơn hàng gần nhất cho mỗi khách hàng (100,000 khách hàng)
- LATERAL không có Memoize (PG 13): > 3 phút
- LATERAL có Memoize (PG 14): 2 giây
- Memoize: Hits = 98%, Misses = 2% (nhiều khách hàng lặp lại trong cache)

**Tình huống thực tế #3: Correlated UPDATE**
- E-commerce: đánh dấu các đơn hàng cũ (100 triệu dòng)
- UPDATE với correlated subquery: > 8 giờ
- Giải pháp: UPDATE FROM + CTE
  ```sql
  WITH cutoff_dates AS (
      SELECT user_id, MIN(created_at) + INTERVAL '1 year' as cutoff
      FROM users
      GROUP BY user_id
  )
  UPDATE orders o SET status = 'ARCHIVED'
  FROM cutoff_dates cd
  WHERE o.user_id = cd.user_id
    AND o.created_at < cd.cutoff;
  ```
- Kết quả: 15 phút (nhanh hơn 32 lần)

### Giám sát (Monitoring)

```sql
-- 1. Tìm SubPlan trong plan
EXPLAIN (ANALYZE, BUFFERS)
SELECT u.name, (SELECT COUNT(*) FROM orders WHERE user_id = u.id)
FROM users u;

-- Tìm kiếm:
-- "SubPlan" → thực thi cho mỗi dòng
-- "InitPlan" → thực thi một lần

-- 2. Kiểm tra hiệu quả của Memoize
EXPLAIN (ANALYZE)
SELECT ... LATERAL ...;

-- Memoize (actual rows=...)
--   Hits: 500000
--   Misses: 10000
--   Evictions: 500
-- Hit rate = Hits / (Hits + Misses)

-- 3. Tìm các correlated subquery trong pg_stat_statements
SELECT query, mean_exec_time, calls
FROM pg_stat_statements
WHERE query ~ '\(SELECT.*WHERE.*=.*\)'
  AND query LIKE '%SELECT%'
ORDER BY mean_exec_time DESC
LIMIT 10;

-- 4. Kiểm tra UPDATE có subquery
SELECT query FROM pg_stat_activity
WHERE query LIKE 'UPDATE%'
  AND query LIKE '%SELECT%';
```

### Best Practices (Thực hành tốt nhất)

1. **Tránh scalar subquery trong SELECT** trên các bảng lớn
2. **EXISTS > IN** khi kiểm tra sự tồn tại (Semi-Join)
3. **UPDATE FROM / DELETE USING** thay vì correlated subquery
4. **Window function** để tổng hợp theo từng dòng
5. **Memoize (PG 14+)** có thể cứu vãn LATERAL — hãy kiểm tra Hit rate
6. **Index trên các key tương quan (correlation keys)** rất quan trọng đối với SubPlan
7. **COALESCE** cho các subquery có thể trả về NULL
8. Luôn kiểm tra plan: tìm **SubPlan** hay **InitPlan**

### Tóm tắt cho Senior

- **SubPlan** = thực thi theo từng dòng → O(N × M) → **nên tránh**
- **InitPlan** = thực thi một lần → O(M) + O(N) → **rất tốt**
- **Decorrelation** biến SubPlan thành Semi-Join → O(N + M)
- **Memoize (PG 14+)** lưu bộ nhớ đệm kết quả LATERAL → hãy kiểm tra **Hits/Misses**
- **Window function** — giải pháp thay thế tốt nhất cho tổng hợp theo từng dòng
- **UPDATE FROM** / **DELETE USING** — luôn nhanh hơn correlated subquery
- **EXISTS** bỏ qua danh sách SELECT — hãy viết `SELECT 1` để dễ đọc
- Giám sát: `EXPLAIN (ANALYZE)`, tìm SubPlan, kiểm tra Memoize Hit rate

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Correlated subquery phụ thuộc vào dòng bên ngoài → thực thi theo từng dòng
- SubPlan = O(N × M) → thảm họa trên dữ liệu lớn
- InitPlan = O(M) + O(N) → được tính toán một lần
- Decorrelation: optimizer biến subquery thành Hash Semi-Join → O(N + M)
- Decorrelation KHÔNG thể thực hiện khi có LIMIT, OFFSET, hàm tổng hợp phụ thuộc vào bên ngoài
- Memoize (PG 14+): lưu bộ nhớ đệm kết quả → Hit rate > 80% = tuyệt vời
- EXISTS = Semi-Join: dừng lại sau lần khớp đầu tiên, không trùng lặp
- Scalar subquery trong SELECT → JOIN + GROUP BY tốt hơn
- UPDATE FROM / DELETE USING → Hash Join thay vì N subquery
- Window function: O(N log N) thay vì O(N × M) cho tổng hợp theo từng dòng

**Các câu hỏi phụ thường gặp:**
- "Làm sao để tìm SubPlan trong plan?" → Tìm `SubPlan` trong EXPLAIN (thực thi theo từng dòng)
- "Khi nào Memoize trở nên vô dụng?" → Tất cả các key đều duy nhất → 0% Hits
