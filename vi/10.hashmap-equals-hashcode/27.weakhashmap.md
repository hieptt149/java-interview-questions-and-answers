# What is WeakHashMap? (WeakHashMap là gì?)

## 🟢 Junior Level

**WeakHashMap** là một Map đặc biệt tự động xóa các entry khi không còn tham chiếu nào tới key.

**Ví dụ minh họa đơn giản:** Hãy tưởng tượng bạn buộc các ghi chú vào các quả bóng bay. Khi quả bóng bay đi mất (key bị garbage collect), ghi chú cũng biến mất.

**Ví dụ:**
```java
WeakHashMap<Object, String> map = new WeakHashMap<>();
Object key = new Object();
map.put(key, "Some data");

System.out.println(map.size()); // 1

key = null; // Không còn tham chiếu nào tới key

System.gc(); // chỉ là một khuyến nghị — GC có thể không chạy

System.out.println(map.size()); // 0 (nếu GC chạy) hoặc 1 (nếu không)
```

**Khi nào dùng:** Để cache metadata gắn với các object mà bạn không kiểm soát.

## 🟡 Middle Level

### Cách nó hoạt động

WeakHashMap lưu các key dưới dạng **weak reference** (`WeakReference`):
1. GC phát hiện chỉ còn một weak reference cho key
2. Đưa reference vào một `ReferenceQueue`
3. Ở thao tác WeakHashMap tiếp theo, `expungeStaleEntries()` được gọi
4. Các entry "chết" bị xóa khỏi table

### Khi nào WeakHashMap sẽ KHÔNG xóa các entry

Key sẽ chỉ bị GC thu gom khi không còn tham chiếu **strong** nào tới nó. Nếu ai đó BÊN NGOÀI WeakHashMap giữ một strong reference tới key — các entry sẽ không bao giờ bị xóa:

```java
Object key = new Object();
strongRef = key;  // ai đó khác giữ một tham chiếu
map.put(key, "value");
key = null;
System.gc();
// Key KHÔNG bị xóa — strongRef vẫn tồn tại!
map.size(); // 1
```

**Rò rỉ bộ nhớ thật sự:** khi bạn quên xóa strong reference tới key, và WeakHashMap đang "chờ đợi" GC.

### Các trường hợp sử dụng

1. **Cache metadata** — gắn dữ liệu vào các object từ code ngoài
2. **Lapsed Listener** — lưu các listener mà không ngăn GC
3. **Dữ liệu thread-local** — giải pháp thay thế ThreadLocal

### WeakHashMap KHÔNG làm gì

| Tính năng          | WeakHashMap   | Cache thật (Caffeine) |
| ------------------ | ------------- | -------------------------- |
| Tự động dọn dẹp bởi GC | Có          | Không                     |
| Eviction LRU/LFU   | Không         | Có                         |
| TTL (thời gian sống) | Không       | Có                         |
| Kích thước cache   | Không giới hạn | Có giới hạn               |
| Thread safety      | Không         | Có                         |

### Các sai lầm thường gặp

1. **Dùng các string literal** làm key — chúng ở trong String Pool, không bao giờ bị xóa
2. **Mong đợi dọn dẹp tức thì** — dọn dẹp là lười, chỉ khi truy cập
3. **Quên strong reference** — ai đó bên ngoài Map giữ một tham chiếu tới key, GC sẽ không xóa nó

## 🔴 Senior Level

### Hiện thực bên trong

```java
private static class Entry<K,V> extends WeakReference<Object> implements Map.Entry<K,V> {
    V value;
    int hash;
    Entry<K,V> next;

    Entry(Object key, V value, ReferenceQueue<Object> queue, int hash, Entry<K,V> next) {
        super(key, queue); // Key — WeakReference với queue
        this.value = value;
        this.hash = hash;
        this.next = next;
    }
}
```

### Cơ chế ReferenceQueue


Dọn dẹp là **lười** — chỉ khi `get`, `put`, `size`, `containsKey`, v.v.

### Reachability và GC

Java xác định khả năng tiếp cận (reachability) của object:
- Khả năng tiếp cận **Strong**: các tham chiếu thông thường → không bị xóa
- Khả năng tiếp cận **Soft**: qua SoftReference → bị xóa khi bộ nhớ thấp
- Khả năng tiếp cận **Weak**: qua WeakReference → bị xóa ở lần GC tiếp theo
- Khả năng tiếp cận **Phantom**: qua PhantomReference → cho dọn dẹp post-mortem

WeakHashMap dùng Weak → object bị xóa ở lần GC tiếp theo, ngay cả khi có nhiều bộ nhớ.

### Các trường hợp biên (Edge Case)

1. **Integer Cache** (-128 tới 127): Các key Integer từ cache không bao giờ bị xóa
2. **String Pool**: Các string literal — các strong reference từ JVM
3. **Thread safety**: WeakHashMap không thread-safe — cần đồng bộ hóa bên ngoài

### Khi nào KHÔNG nên dùng

- **Cache production**: Dùng Caffeine/Guava Cache với LRU + TTL
- **High-throughput**: WeakHashMap chậm hơn HashMap do polling ReferenceQueue
- **Truy cập đồng thời**: Cần `Collections.synchronizedMap(new WeakHashMap<>())`

### Giám sát Production

Để phân tích WeakHashMap:
- Giám sát `size()` — giảm mạnh = hoạt động GC
- Heap dump hiển thị ReferenceQueue với các entry đang chờ
- JFR: các event GC tương quan với việc dọn dẹp WeakHashMap

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- WeakHashMap tự động xóa các entry khi không còn strong reference tới key
- Các key được lưu dưới dạng WeakReference + ReferenceQueue; dọn dẹp là lười (khi get/put/size)
- GC xóa key chỉ khi không còn strong reference BÊN NGOÀI WeakHashMap
- Strong reference tới key = các entry KHÔNG bị xóa (rò rỉ bộ nhớ thật sự)
- ĐỪNG dùng các string literal làm key — chúng ở trong String Pool, không bao giờ bị xóa
- Không dành cho cache production — dùng Caffeine/Guava Cache với LRU + TTL

**Các câu hỏi phụ thường gặp:**
- **Tại sao System.gc() không đảm bảo việc xóa?** — nó chỉ là một khuyến nghị, JVM có thể phớt lờ nó
- **Khi nào WeakHashMap sẽ không xóa các entry?** — ai đó bên ngoài Map giữ một strong reference tới key
- **WeakHashMap có thread-safe không?** — không, cần Collections.synchronizedMap()
- **WeakReference khác SoftReference như thế nào?** — Weak bị xóa ở bất kỳ lần GC nào, Soft — chỉ khi bộ nhớ thấp

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "WeakHashMap = một cache đầy đủ tính năng" — không, không có TTL, LRU, hay giới hạn kích thước
- "GC chạy ngay sau key = null" — không, System.gc() chỉ là một khuyến nghị
- "Value cũng là một weak reference" — không, chỉ key; value = strong reference
