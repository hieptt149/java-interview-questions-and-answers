# How to Properly Convert String to byte[] and Back (Cách chuyển đổi đúng String sang byte[] và ngược lại)

## 🟢 Junior Level

Chuyển đổi một chuỗi sang byte và ngược lại là một trong những thao tác phổ biến nhất khi làm việc với file, mạng, và cơ sở dữ liệu.

**Quy tắc chính:** LUÔN chỉ định encoding một cách tường minh!

```java
import java.nio.charset.StandardCharsets;

String str = "Hello, World!";

// String → byte[]
byte[] bytes = str.getBytes(StandardCharsets.UTF_8);

// byte[] → String
String restored = new String(bytes, StandardCharsets.UTF_8);

System.out.println(restored); // "Hello, World!"
```

**Không bao giờ làm thế này:**
```java
// ❌ XẤU — dùng encoding của OS (khác nhau trên Windows và Linux!)
byte[] bytes = str.getBytes();
String restored = new String(bytes);
```

**Tại sao:** Encoding mặc định phụ thuộc vào hệ điều hành. Trên Windows có thể là `Windows-1251`, trên Linux — `UTF-8`. Một chuỗi được chuyển đổi trên một hệ thống sẽ biến thành "văn bản lỗi ký tự" trên hệ thống khác.

**String → byte[] — giống như ghi âm giọng nói vào máy ghi âm (văn bản → byte).
byte[] → String — giống như phát lại bản ghi (byte → văn bản).
Nếu bạn chọn sai định dạng ghi (encoding), bạn sẽ nghe thấy tiếng ồn thay vì từ ngữ.**

## 🟡 Middle Level

### Các Phương Pháp Chuyển Đổi Đúng

**String → byte[]:**
```java
// Java 7+ — cách tiếp cận được khuyến nghị (hằng số, không cấp phát)
byte[] bytes = str.getBytes(StandardCharsets.UTF_8);

// Nếu encoding được xác định động
byte[] bytes = str.getBytes(Charset.forName("Windows-1251"));
```

**byte[] → String:**
```java
// Java 7+ — cách tiếp cận được khuyến nghị
String str = new String(bytes, StandardCharsets.UTF_8);

// Nếu encoding động
String str = new String(bytes, Charset.forName("Windows-1251"));
```

**Làm việc theo stream với dữ liệu lớn:**
```java
// Đọc file với encoding
try (BufferedReader reader = Files.newBufferedReader(path, StandardCharsets.UTF_8)) {
    String line = reader.readLine();
}

// Ghi file với encoding
try (BufferedWriter writer = Files.newBufferedWriter(path, StandardCharsets.UTF_8)) {
    writer.write("Hello");
}
```

### Bảng Các Lỗi Điển Hình

| Lỗi                               | Hậu quả                          | Giải pháp                                                        |
| ------------------------------------- | ------------------------------------- | --------------------------------------------------------------- |
| `getBytes()` không có encoding         | "Văn bản lỗi ký tự" khi đổi OS           | Luôn `getBytes(StandardCharsets.UTF_8)`                       |
| `new String(bytes)` không có encoding  | Không thể khôi phục văn bản gốc          | Luôn `new String(bytes, StandardCharsets.UTF_8)`              |
| Nhầm lẫn `str.length()` với `bytes.length` | Logic xử lý dữ liệu sai   | `"Привет".length()` = 6, `"Привет".getBytes(UTF_8).length` = 12 |
| Chuyển đổi dữ liệu nhị phân sang String      | Mất dữ liệu, hỏng dữ liệu                 | Với nhị phân — dùng trực tiếp `byte[]`/`ByteBuffer`                 |

### So Sánh Encoding Cho Việc Chuyển Đổi

| Encoding     | Byte/ký tự (Latin) | Byte/ký tự (Cyrillic) | Khi nào nên dùng                          |
| ------------ | ------------------ | --------------------- | ------------------------------------ |
| UTF-8        | 1                  | 2                     | Internet, JSON, HTTP — chuẩn thực tế |
| UTF-16       | 2                  | 2                     | Định dạng nội bộ Java, Windows API    |
| Latin-1      | 1                  | N/A                   | Chỉ Tây Âu                |
| Windows-1251 | N/A                | 1                     | Các hệ thống Windows legacy               |

### Khi Nào KHÔNG Nên Chuyển String → byte[]
- **Dữ liệu nhị phân** (hình ảnh, PDF, protobuf) — làm việc trực tiếp với `byte[]`
- **Các hệ thống độ trễ cực thấp** — chuyển đổi thêm overhead 50–200ns
- **Dữ liệu encoding không rõ** — dùng auto-detect hoặc `BOMInputStream`

## 🔴 Senior Level

### Hiện Thực Nội Bộ

**`String.getBytes(Charset)`:**
```java
public byte[] getBytes(Charset charset) {
    if (charset == null) throw new NullPointerException();
    return StringCoding.encode(value, coder, charset);
}
```

**`StringCoding.encode` — điều gì xảy ra:**
1. Kiểm tra `coder` (Latin-1 hoặc UTF-16)
2. Chọn thuật toán encoding:
   - **Latin-1 → UTF-8:** 1 byte → 1 byte (ASCII), 1 byte → 2 byte (Latin-1 mở rộng, U+0080–U+00FF)
   - **UTF-16 → UTF-8:** 2 byte → 1–3 byte (tùy code point)
3. Với UTF-8: chuyển đổi từng ký tự qua `CharsetEncoder`
4. Cấp phát `byte[]` mới với kích thước cần thiết

**`new String(byte[], Charset)`:**
```java
public String(byte[] bytes, Charset charset) {
    this(bytes, 0, bytes.length, charset);
}
// → StringCoding.decode → CharsetDecoder → byte[] value + coder
```

1. `CharsetDecoder` decode byte thành ký tự
2. `coder` được xác định: nếu tất cả ký tự trong khoảng U+0000–U+00FF → LATIN1, nếu không → UTF16
3. Byte không hợp lệ → thay thế bằng `�` (ký tự thay thế)
4. String mới được tạo với `byte[] value` + `coder`

### Đánh Đổi Về Encoding

**UTF-8:**
- Ưu điểm: Chuẩn thực tế, tương thích ASCII, độ dài biến đổi (tiết kiệm cho Latin)
- Nhược điểm: Cyrillic = 2 byte/ký tự, chữ tượng hình = 3 byte, độ dài biến đổi làm phức tạp truy cập ngẫu nhiên

**UTF-16:**
- Ưu điểm: Kích thước cố định cho BMP (2 byte/ký tự), định dạng nội bộ của Java (chuyển đổi tối thiểu)
- Nhược điểm: Endianness (LE vs BE), BOM, gấp đôi kích thước cho ASCII, không tương thích ASCII

**Latin-1 (ISO-8859-1):**
- Ưu điểm: 1 byte/ký tự, overhead tối thiểu, kích thước cố định
- Nhược điểm: Chỉ 256 ký tự, Cyrillic trong Latin-1 mở rộng, không phải Unicode

### Các Trường Hợp Biên (Tối Thiểu 3)

**1. BOM (Byte Order Mark):**
```java
// File UTF-8 có BOM: EF BB BF
byte[] bomUtf8 = {(byte)0xEF, (byte)0xBB, (byte)0xBF, 'H', 'i'};
String s = new String(bomUtf8, StandardCharsets.UTF_8);
// s.charAt(0) = '﻿' — ký tự BOM vô hình!
// s.startsWith("Hi") → false!
```
Giải pháp: `BOMInputStream` (Apache Commons IO) hoặc kiểm tra thủ công 3 byte đầu:
```java
if (bytes.length >= 3 && bytes[0] == (byte)0xEF && bytes[1] == (byte)0xBB && bytes[2] == (byte)0xBF) {
    s = new String(bytes, 3, bytes.length - 3, StandardCharsets.UTF_8);
}
```

**2. Input dị dạng — byte UTF-8 không hợp lệ:**
```java
byte[] malformed = {(byte) 0xFF, (byte) 0xFE, (byte) 0x80};
String s = new String(malformed, StandardCharsets.UTF_8);
// Các chuỗi không hợp lệ → '�' (ký tự thay thế)
// s = "���"
```
Hành vi được kiểm soát qua `CodingErrorAction`:
```java
CharsetDecoder decoder = StandardCharsets.UTF_8.newDecoder();
decoder.onMalformedInput(CodingErrorAction.REPORT);  // Ném MalformedInputException
decoder.onMalformedInput(CodingErrorAction.IGNORE);  // Bỏ qua
decoder.onMalformedInput(CodingErrorAction.REPLACE); // Mặc định → �
```

**3. Chuỗi đa byte bị cắt cụt:**
```java
// Cyrillic 'А' = D0 90 trong UTF-8
byte[] truncated = {(byte) 0xD0}; // Chỉ byte đầu
String s = new String(truncated, StandardCharsets.UTF_8);
// '�' — chuỗi không hoàn chỉnh
```
Quan trọng cho I/O theo stream: nếu buffer bị vỡ giữa chừng một chuỗi đa byte, bạn cần lưu "phần đuôi" và thêm nó vào buffer tiếp theo.

**4. Bảo mật — bypass encoding:**
```java
// SQL injection thông qua bypass encoding đa byte
String input = "%C0%27 OR 1=1 --";
// Trong một số hệ thống cũ %C0%27 decode thành một dấu nháy đơn
// Điều này bypass các filter kiểm tra input TRƯỚC khi decode
// Luôn validate input SAU KHI decode!
```

**5. Cặp surrogate và độ dài byte:**
```java
String emoji = "😀"; // "😀" — cặp surrogate
emoji.length();                         // 2 (char)
emoji.getBytes(StandardCharsets.UTF_8).length; // 4 (byte)
emoji.getBytes(StandardCharsets.UTF_16).length; // 6 (2 BOM + 4 data)
// StandardCharsets.UTF_16 bao gồm BOM. UTF_16BE/UTF_16LE — không có BOM, sẽ là 4 byte.
// Đừng dùng bytes.length để xác định số lượng ký tự!
```

### Hiệu Năng

| Thao tác                   | UTF-8   | UTF-16   | Latin-1   |
| --------------------------- | ------- | -------- | --------- |
| Encode 100 ký tự (Latin-1)  | ~100ns  | ~50ns    | ~20ns     |
| Encode 100 ký tự (Cyrillic) | ~200ns  | ~50ns    | N/A       |
| Decode 200 byte (UTF-8)    | ~150ns  | N/A      | N/A       |
| Decode 200 byte (UTF-16)   | N/A     | ~40ns    | N/A       |
| Encode văn bản 10KB (trộn)    | ~8μs    | ~3μs     | ~2μs      |

**Cấp phát:**
- `getBytes(UTF_8)`: cấp phát `byte[]` mới với kích thước ~N–3N (tùy nội dung)
- `new String(bytes, UTF_8)`: cấp phát `byte[]` mới + object String (~24 byte overhead)
- Với 1M lần chuyển đổi: ~100MB cấp phát → áp lực Young GC

### Thread Safety

- `StandardCharsets.UTF_8` — **thread-safe** (singleton bất biến)
- `Charset.forName(...)` — **thread-safe** (cache kết quả)
- `CharsetEncoder` / `CharsetDecoder` — **KHÔNG thread-safe**! Một instance duy nhất không thể được dùng từ nhiều thread đồng thời
- Giải pháp: tạo encoder/decoder mới ở mỗi lần gọi hoặc dùng `ThreadLocal<CharsetEncoder>`

### Câu Chuyện Thực Tế Trong Production

**Kịch bản 1:** HTTP API — đọc request body (Spring Boot):
```java
// Spring Boot — tự động dùng UTF-8
@PostMapping
public void handle(@RequestBody String body) { ... }

// Servlet thô — cần chỉ định tường minh
request.setCharacterEncoding("UTF-8");
String body = request.getReader().readLine();
```
Vấn đề: client gửi request POST bằng `Windows-1251`, Spring đọc như UTF-8 → "văn bản lỗi ký tự". Sửa lỗi: header `Content-Type: text/plain; charset=Windows-1251` hoặc migration client sang UTF-8.

**Kịch bản 2:** Kafka message — serialize/deserialize:
```java
// Producer
byte[] bytes = jsonString.getBytes(StandardCharsets.UTF_8);
producer.send(new ProducerRecord<>(topic, keyBytes, bytes));

// Consumer
String message = new String(record.value(), StandardCharsets.UTF_8);
```
Vấn đề: một producer dùng `getBytes()` không có encoding (mặc định trên Windows = Cp1251). Consumer trên Linux đọc như UTF-8 → message bị hỏng. Sửa lỗi: chuẩn UTF-8 thống nhất ở cấp độ hợp đồng Kafka.

**Kịch bản 3:** Parser log tải cao (500K dòng/giây):
- Chuyển đổi mỗi dòng `new String(bytes, UTF_8)` → 500K cấp phát/giây
- Young GC mỗi 2 giây, pause 15ms
- Sửa lỗi: zero-copy qua `ByteBuffer` + parser tùy chỉnh, không chuyển sang String
- Kết quả: Young GC mỗi 8 giây, pause 5ms

### Best Practices Cho Highload

- **Luôn** chỉ định `Charset` — dùng `StandardCharsets.UTF_8` (hằng số, không cấp phát tra cứu)
- Cho **JSON/XML/HTTP**: UTF-8 — chuẩn thực tế
- Cho **các giao thức nhị phân** (Kafka, gRPC, TCP): làm việc trực tiếp với `byte[]`/`ByteBuf`, không chuyển sang String
- Cho **I/O theo stream**: `InputStreamReader`/`OutputStreamWriter` với Charset tường minh — buffer bên trong
- **Xử lý BOM:** `BOMInputStream` (Apache Commons IO) hoặc kiểm tra thủ công các byte đầu
- Cho **độ trễ cực thấp**: tránh String — dùng `ByteBuf` (Netty), `ByteBuffer`, các cách tiếp cận zero-copy
- **Bảo mật:** validate input SAU KHI decode, dùng so sánh thời gian hằng số cho các bí mật
- `CharsetEncoder`/`CharsetDecoder` — **đừng chia sẻ giữa các thread**, dùng `ThreadLocal` hoặc tạo mỗi lần gọi
- Cho **dữ liệu lớn**: theo stream qua `Reader`/`Writer`, đừng load toàn bộ file vào `byte[]`

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- `str.getBytes(StandardCharsets.UTF_8)` — cách đúng để chuyển đổi String → byte[]
- `new String(bytes, StandardCharsets.UTF_8)` — cách đúng để chuyển đổi byte[] → String
- `getBytes()` và `new String(bytes)` không có encoding — phụ thuộc vào OS, gây ra "văn bản lỗi ký tự"
- BOM trong UTF-8 (3 byte `EF BB BF`) tạo ra ký tự vô hình `﻿` ở đầu chuỗi
- Các byte UTF-8 không hợp lệ được thay thế bằng `�` (ký tự thay thế)
- `CharsetEncoder`/`CharsetDecoder` — KHÔNG thread-safe, cần `ThreadLocal`

**Các câu hỏi phụ thường gặp:**
- **Tại sao `new String(bytes)` không có encoding lại xấu?** — Encoding mặc định phụ thuộc vào OS. Chuỗi được encode trên Windows (Cp1251) trở thành "văn bản lỗi ký tự" trên Linux (UTF-8).
- **Cách xử lý BOM khi đọc file UTF-8?** — `BOMInputStream` hoặc kiểm tra: nếu 3 byte đầu là `EF BB BF`, bỏ qua chúng.
- **Điều gì xảy ra khi chuyển đổi dữ liệu nhị phân sang String?** — Mất dữ liệu. Với nhị phân — làm việc trực tiếp với `byte[]`/`ByteBuffer`.
- **Cách tăng tốc chuyển đổi trong highload?** — Zero-copy: `ByteBuffer`, `ByteBuf` (Netty), stream qua `Reader`/`Writer`.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- ❌ "`getBytes()` không có encoding — ổn thôi" — phụ thuộc vào OS, hỏng khi migration
- ❌ "`CharsetEncoder` có thể chia sẻ giữa các thread" — KHÔNG thread-safe
- ❌ "BOM — chỉ là vấn đề của UTF-16" — UTF-8 cũng có thể có BOM
- ❌ "Bạn có thể dùng `bytes.length` để xác định số lượng ký tự" — với UTF-8, 1 ký tự = 1-4 byte
