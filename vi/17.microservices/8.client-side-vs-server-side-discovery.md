# What is the difference between client-side and server-side discovery (Sự khác biệt giữa client-side và server-side discovery là gì)

## Junior Level

**Client-side discovery:**
```
Service A tự hỏi Registry và gọi Service B
Service A -> Registry: "Service B ở đâu?" -> 10.0.0.5:8080 -> gọi
```

**Server-side discovery:**
```
Service A gọi Load Balancer, và LB tìm Service B
Service A -> Load Balancer -> Registry -> Service B
```

**Sự khác biệt:** ai thực hiện request đến Registry — client hay server (LB).

---

## Middle Level

### Client-side

```java
// Service A tự tra cứu service B
ServiceRegistry registry = new ConsulRegistry("consul:8500");
ServiceInstance instance = registry.getInstance("service-b");

HttpClient client = HttpClient.newBuilder()
    .connectTimeout(Duration.ofSeconds(5))
    .build();

HttpResponse<String> response = client.send(
    HttpRequest.newBuilder(URI.create("http://" + instance.getAddress() + "/api"))
        .GET().build(),
    BodyHandlers.ofString()
);
```

**Ưu điểm:**
- Nhiều kiểm soát hơn: service tự quyết định chọn instance nào (round-robin,
least-connections, theo availability zone). Với server-side discovery quyết định
này được LB thực hiện, và client không thể ảnh hưởng đến nó.
- Không có hop bổ sung qua LB

**Nhược điểm:**
- Cần triển khai logic discovery trong mỗi service
- Phụ thuộc vào SDK của Registry

### Server-side

```
Service A -> Load Balancer (Nginx/HAProxy) -> Service B

# Cấu hình Nginx
# Trong production, Nginx Plus hoặc consul-template cập nhật upstream động.
# IP tĩnh — đơn giản hóa cho ví dụ.
upstream service_b {
    server 10.0.0.5:8080;
    server 10.0.0.6:8080;
}
```

**Ưu điểm:**
- Đơn giản hơn cho client
- LB xử lý việc discovery và balancing

**Nhược điểm:**
- Hop bổ sung (độ trễ)
- LB — single point of failure

### Các Lỗi Thường Gặp

1. **Client-side: cache mà không có TTL:**
```
Service A cache IP của service B
Service B chuyển sang IP mới
Service A vẫn gọi vào IP cũ
```

## Senior Level

### Đánh Đổi Kiến Trúc

| Client-side                       | Server-side       |
| --------------------------------- | ----------------- |
| Không có single point of failure  | LB có thể sập     |
| Phức tạp hơn để triển khai        | Đơn giản hơn      |
| Ít độ trễ hơn                     | +1 hop            |
| Linh hoạt (retry, circuit breaker) | Ít kiểm soát hơn  |

### Kinh Nghiệm Production

**Kubernetes (server-side):**
```
K8s Service -> kube-proxy -> Endpoints
Service A -> my-service:8080 -> kube-proxy -> Pod B
```

**Netflix Ribbon (client-side):**
⚠️ Netflix Ribbon đã deprecated (ở chế độ maintenance từ năm 2018).
Trong các dự án hiện đại, hãy dùng Spring Cloud LoadBalancer hoặc K8s Service.
```java
@LoadBalanced
@Bean
public RestTemplate restTemplate() {
    return new RestTemplate();
}

// Ribbon xử lý discovery + load balancing
restTemplate.getForObject("http://service-b/api", String.class);
```

### Best Practices

```
✅ Client-side: cache với TTL
✅ Server-side: nhiều LB cho HA
✅ Health check trong cả hai trường hợp
✅ Fallback khi Registry không khả dụng

❌ Không có cache (quá nhiều lượt gọi Registry)
❌ Không có fallback khi LB không khả dụng
```

## Interview Cheat Sheet

**Cần phải biết:**
- Client-side: service tự hỏi Registry và chọn instance (round-robin, least-connections)
- Server-side: LB xử lý việc discovery và balancing (Nginx, K8s Service)
- Client-side: không có hop thừa, nhưng cần triển khai logic trong mỗi service
- Server-side: đơn giản hơn cho client, nhưng +1 hop và LB là một SPOF tiềm ẩn
- Netflix Ribbon đã deprecated (chế độ maintenance từ 2018) — dùng Spring Cloud LoadBalancer
- Cache phía client BẮT BUỘC phải có TTL, nếu không sẽ có IP cũ
- K8s dùng server-side: kube-proxy -> Endpoints

**Các câu hỏi phụ thường gặp:**
- **Khi nào chọn client-side?** Cần linh hoạt (retry, circuit breaker), độ trễ tối thiểu.
- **Khi nào chọn server-side?** Đơn giản hơn, khi team không muốn viết logic discovery.
- **Điều gì xảy ra nếu không có TTL trong cache?** Service chuyển sang IP mới — client vẫn gọi vào IP cũ.
- **K8s thuộc loại nào?** Server-side: Service -> DNS -> kube-proxy -> Pod.

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Netflix Ribbon là lựa chọn tốt nhất" — đã deprecated, dùng Spring Cloud LoadBalancer
- "Không cần cache, Registry nhanh" — tải không cần thiết lên Registry với mỗi lần gọi
- "Server-side luôn tốt hơn" — phụ thuộc vào yêu cầu về tính linh hoạt
- "LB không bao giờ sập" — cần HA (nhiều LB)
