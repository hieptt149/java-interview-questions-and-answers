# What Happens If You Override equals() But Not hashCode()? (Điều gì xảy ra nếu bạn override equals() nhưng không override hashCode()?)

## 🟢 Junior Level

Nếu bạn override `equals()` nhưng quên `hashCode()`, các object bằng nhau về mặt logic sẽ có **các hash code khác nhau**. Điều này phá vỡ HashMap và HashSet.

**Điều gì xảy ra:**
```java
public class User {
    private Long id;
    // equals() được override, hashCode() — KHÔNG

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof User)) return false;
        User user = (User) o;
        return id != null && id.equals(user.id);
    }
}

Set<User> set = new HashSet<>();
set.add(new User(1L));  // hashCode = identity_A → bucket X
set.add(new User(1L));  // hashCode = identity_B → bucket Y (khác nhau!)
System.out.println(set.size()); // 2! HashSet chỉ kiểm tra equals bên trong một bucket.
// Các bucket KHÁC NHAU — equals thậm chí không bao giờ được gọi.
```

**Quy tắc chính:** Nếu bạn override equals — hãy override cả hashCode!

## 🟡 Middle Level

### Hệ quả thực tế

**1. Mất dữ liệu trong HashMap:**
- `objA` được đặt vào bucket #100 (identity hash code của nó)
- `objB` (bằng objA theo equals) được tìm trong bucket #200 (identity hash code khác)
- `map.get(objB)` trả về `null`, mặc dù key tồn tại

**2. Trùng lặp trong HashSet:**
- Các object bằng nhau rơi vào các bucket khác nhau
- HashSet cho phép "các bản trùng lặp" — vi phạm business logic

**3. Không thể xóa:**
- `map.remove(objB)` tìm trong bucket sai
- Object còn lại trong bộ nhớ — rò rỉ bộ nhớ

### Tại sao khó debug

Lỗi có thể không biểu hiện:
- Nếu các object không được dùng trong các hash collection
- Nếu các hashCode khác nhau tình cờ rơi vào cùng một bucket
- Ở lần resize tiếp theo, các chỉ số thay đổi — **bug không tất định**

### Cách phòng ngừa

| Công cụ                     | Nó làm gì                            |
| --------------------------- | ------------------------------------ |
| SonarQube                   | Đánh dấu là Critical Bug             |
| SpotBugs                    | Cảnh báo về vi phạm contract         |
| IntelliJ IDEA               | Cảnh báo trong lúc sinh code         |
| Lombok `@EqualsAndHashCode` | Sinh cả hai method                   |
| Java 14+ Record             | Sinh tự động                         |

## 🔴 Senior Level

### Cơ chế thất bại ở mức JVM

`Object.hashCode()` mặc định trả về **identity hash code** — một con số mà JVM gắn với object ở lời gọi đầu tiên tới `System.identityHashCode()`. Nó KHÔNG phải là địa chỉ bộ nhớ (dù có thể được suy ra từ nó) và KHÔNG thay đổi khi GC di chuyển. Hai instance khác nhau của `new User(1L)` luôn có các identity hash code khác nhau, ngay cả khi `equals()` trả về `true`.

### Heisenbug trong Production

Heisenbug — một bug biểu hiện hoặc biến mất tùy điều kiện (đặt tên theo nguyên lý bất định của Heisenberg). Trong trường hợp này: trong các test nhỏ, các hashCode khác nhau tình cờ rơi vào cùng một bucket — test pass. Trong production với một map lớn — các bucket khác nhau — bug biểu hiện.

```java
// Trong test (map nhỏ): các hashCode khác nhau rơi vào cùng bucket → hoạt động
// Trong production (map lớn, resize khác): các bucket khác nhau → sập
```

Đây là một trong những bug nguy hiểm nhất: pass mọi test, nhưng sập trong production dưới các điều kiện nhất định.

### Pattern rò rỉ bộ nhớ

```java
Map<User, Data> cache = new HashMap<>();
cache.put(new User(1L), loadData()); // Bucket A
// Object bằng nhau tìm trong bucket B → null → nạp lại
cache.put(new User(1L), loadData()); // Một bản sao khác trong bucket B
// Kết quả: rò rỉ bộ nhớ + trùng lặp dữ liệu
```

### Hệ quả về bảo mật

Trong các hệ thống có caching với key là object, vi phạm contract có thể dẫn tới:
- Bỏ qua cache (cache miss cho các key bằng nhau)
- Rò rỉ dữ liệu nhạy cảm (trùng lặp trong bộ nhớ)

### Best Practices

1. **Nếu một object sẽ là key trong một hash collection — hãy sinh cả hai method. Ngoại lệ: ngữ nghĩa identity là có chủ đích.**
2. **Dùng một IDE** — sinh tự động `equals()` và `hashCode()`
3. **Record** (Java 14+) — lý tưởng cho các key. Record sinh hashCode từ TẤT CẢ các field. Nếu bạn có các field transient hoặc computed — chúng cũng sẽ được bao gồm trong hashCode, thứ có thể không mong muốn.
4. **Unit test** — kiểm chứng contract:
```java
assertEquals(a.equals(b), a.hashCode() == b.hashCode() || !a.equals(b));
```

### Cạm bẫy của Lombok

```java
@EqualsAndHashCode // Sinh cả hai method từ TẤT CẢ các field
class User {
    Long id;
    transient String cache; // Đừng bao gồm các field transient/cache!
}
```
Dùng `@EqualsAndHashCode(exclude = "cache")`.

## 🎯 Tóm tắt phỏng vấn (Interview Cheat Sheet)

**Cần phải biết:**
- Không có hashCode(), các object bằng nhau rơi vào các bucket KHÁC NHAU (identity hash code khác nhau)
- HashSet cho phép các bản trùng lặp: size = 2 cho hai object bằng nhau
- map.get() trả về null cho một object bằng nhau — tìm trong bucket sai
- remove() không thể → rò rỉ bộ nhớ (các ghost entry)
- Heisenbug: có thể pass test trên các map nhỏ, sập trong production
- Một trong những bug nguy hiểm nhất — các object bằng nhau tình cờ rơi vào cùng một bucket → test xanh

**Các câu hỏi phụ thường gặp:**
- **Tại sao Set.size() = 2 cho các object bằng nhau?** — HashSet chỉ kiểm tra equals bên trong một bucket; các bucket khác nhau → equals không bao giờ được gọi
- **IDE giúp như thế nào?** — SonarQube (Critical Bug), SpotBugs, IntelliJ IDEA cảnh báo về nó
- **Cạm bẫy của Lombok là gì?** — @EqualsAndHashCode sinh từ TẤT CẢ các field, kể cả transient/cache
- **Record có giải quyết vấn đề không?** — có, chúng sinh cả hai method từ tất cả các component

**Dấu hiệu cảnh báo (Red flags — KHÔNG nên nói):**
- "Có thể chỉ override equals nếu các object không nằm trong Map" — quyết định mong manh
- "Điều này dễ nhận ra" — không, nó có thể chỉ biểu hiện dưới các điều kiện resize nhất định
- "hashCode không cần cho ngữ nghĩa identity" — vậy thì cũng đừng override equals
